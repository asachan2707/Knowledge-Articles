How to Build AI Agents That Pick Up Where They Left Off After Failure

Long-running AI agents crash — networks timeout, rate limits kick in, processes die. The difference between a demo and a production agent is whether it restarts from scratch or resumes from exactly where it failed. This guide covers durable execution, checkpoint design, idempotent tool calls, and the Redis-backed resumable agent loop pattern used in real production systems.

Domain: agents / reliability Published: 2026-09-03 Source: lets-code-future · Medium

Every multi-step AI agent is a distributed system in miniature — and distributed systems fail. A 12-step research agent that crashes on step 11 and re-runs every LLM call from scratch is not just slow; it is dangerous. It may email duplicates, make double charges, or create ghost tickets. Production-grade agents treat failure as a first-class concern by persisting state after each step and making every tool invocation replay-safe.

Core idea: Durable execution means saving a checkpoint after every significant step so that a resume path can replay only the failed tail of the plan — never the already-committed head. Idempotency ensures that replaying a step that partially completed does not double-apply its side effects.

Story · The $40k duplicate payout

A fintech startup built a reconciliation agent: it would pull ledger rows, call an LLM to classify each transaction, then issue correction payouts via a payments API. The agent ran nightly on 2,000 transactions. One night, their cloud provider had a transient networking blip at step 1,847. The agent crashed. The on-call engineer restarted it — from step 1 — because there was no checkpoint. The first 1,846 payouts ran again. By the time anyone noticed, $40k in duplicate payouts had hit customer accounts. Reversals took a week and strained customer trust permanently.

The fix was not more retries or better error handling. It was a three-line change: write a checkpoint after each payout, read it on startup, skip any step whose ID already existed in the checkpoint store. That pattern — checkpoint, resume, skip-if-done — is the entire subject of this article.

Section 1 — Failure taxonomy

Why Long-Running Agents Fail Mid-Task

Understanding the failure modes informs which parts of the checkpoint and recovery stack you need to build.

Failure Type Typical Cause Recovery Complexity
Network timeout LLM API, search tool, or downstream REST call exceeds socket timeout Low — retry with same inputs if tool is read-only
Rate limit (429) OpenAI, Anthropic, SerpAPI throttle at token or request limits Low — exponential backoff, resume from checkpoint
Context window overflow Accumulated tool outputs exceed model context; request rejected Medium — need to summarise history before resuming
Tool execution failure Code sandbox OOM, browser session drop, DB connection lost Medium — re-provision the tool, replay from last checkpoint
Process crash / OOM kill Container evicted, OOM killer, host reboot High — in-memory state lost; checkpoint must be external
Partial write side effect Tool call started a write (DB insert, email send) then crashed mid-flight High — idempotency required on resume to avoid double-apply

The worst case: A non-idempotent write tool that crashed after the write committed but before the agent received confirmation. On resume, the agent will call the tool again. Without idempotency at the tool layer, the write runs twice.

Section 2 — Persistence strategies

Where to Store Checkpoints: In-Memory vs Redis vs Database

The choice of checkpoint backend determines your durability guarantee, query capability, and operational overhead.

Strategy Survives Process Crash? Survives Host Failure? Best For
In-memory Map No No Development only; useful for unit-testing the resume logic
Local file / SQLite Yes No (unless volume-mounted) Single-machine agents, CLI tools, short-lived jobs
Redis (AOF + replica) Yes Partial (replica lag risk) High-throughput, low-latency step logging; TTL-based expiry
PostgreSQL / DynamoDB Yes Yes Auditable, queryable checkpoints; long-running multi-day tasks
Temporal / Durable Execution platform Yes Yes Complex branching workflows; built-in retry, versioning, signals

For most agentic use-cases, Redis with AOF persistence is the right starting point: sub-millisecond writes, TTL-based cleanup, and simple key namespacing by run ID. Graduate to PostgreSQL when you need cross-run analytics or compliance audit trails.

Section 3 — Checkpoint schema design

What State to Capture in Each Checkpoint

A checkpoint must contain enough information to reconstruct the agent's decision context at the point of failure — without relying on any in-memory state that no longer exists.

  • Run ID — a UUID stable across restarts; used as the checkpoint namespace key
  • Plan snapshot — the full ordered list of steps (or graph nodes) the agent planned at the start of the run
  • Step cursor — the index (or node ID) of the last successfully completed step
  • Tool call log — for each completed step: tool name, input args, output, timestamp, and idempotency key
  • Partial outputs — any intermediate artefacts (scraped text, code output, transformed data) needed by later steps
  • Context summary — a compressed narrative of what the agent has learned so far (prevents context-window overflow on resume)
  • Error log — the last failure reason and retry count per step, to prevent infinite retry loops

Insight: Do not checkpoint the raw context window. The full message history grows O(n) with steps and will overflow the context on resume. Instead, checkpoint a summarised "agent memory" blob after every 5 steps. LangGraph's MemorySaver does exactly this under the hood.

Keep checkpoint writes atomic. In Redis, use a single HSET over a pipeline to write multiple fields in one round-trip. In PostgreSQL, wrap the checkpoint upsert in a transaction with the tool-output insert to avoid a partial checkpoint that records the step as done before its output is saved.

Section 4 — Idempotency

Making Tool Calls Safe to Replay

Checkpointing tells the agent where to resume. Idempotency makes the resume safe. These are two separate concerns — checkpointing without idempotency still causes duplicates on partial writes.

  1. Assign an idempotency key to every tool call before execution Derive it deterministically: hash(runId + stepIndex + toolName + inputArgs). The same logical call always produces the same key.
  2. Check the key against a store before executing the tool If the key already exists and has a committed result, return the cached result immediately. Do not re-execute the tool.
  3. Write the key + result atomically after successful execution Use a two-field hash in Redis: { status: "done", result: "..." }. Write status="pending" before the call so a crash mid-call is detectable.
  4. Treat pending keys as ambiguous on resume A step with status="pending" may or may not have committed its side effect. Either re-validate the external state or treat it as a re-run candidate guarded by the downstream system's own idempotency (e.g., Stripe's Idempotency-Key header).
  5. Pass idempotency keys to all external APIs that support them Stripe, Twilio, Mailgun, and most payment/notification APIs accept a caller-supplied idempotency key. Always pass it; never let the API auto-generate one.

Rule: Read tools (search, fetch, classify) are naturally idempotent — re-running them produces the same result. Write tools (email, DB insert, payment) are never idempotent by default — you must make them so explicitly via key-based deduplication.

Section 5 — Code example

Resumable Agent Loop with Redis Checkpointing

JavaScript Example 
// resumable-agent.mjs  — Node 22+, ioredis, openai
import OpenAI from "openai";
import Redis from "ioredis";
import crypto from "crypto";

const redis = new Redis({ host: "localhost", port: 6379 });
const openai = new OpenAI();

// ── Deterministic idempotency key ────────────────────────────────────────────
function idempKey(runId, stepIdx, toolName, args) {
  const raw = `${runId}:${stepIdx}:${toolName}:${JSON.stringify(args)}`;
  return `idem:${crypto.createHash("sha256").update(raw).digest("hex").slice(0, 24)}`;
}

// ── Checkpoint helpers ───────────────────────────────────────────────────────
async function loadCheckpoint(runId) {
  const raw = await redis.hgetall(`ckpt:${runId}`);
  if (!raw || !raw.stepCursor) return null;
  return {
    stepCursor: parseInt(raw.stepCursor, 10),
    toolLog: JSON.parse(raw.toolLog || "[]"),
    contextSummary: raw.contextSummary || "",
    errorCount: parseInt(raw.errorCount || "0", 10),
  };
}

async function saveCheckpoint(runId, cursor, toolLog, contextSummary) {
  const pipeline = redis.pipeline();
  pipeline.hset(`ckpt:${runId}`, {
    stepCursor: cursor,
    toolLog: JSON.stringify(toolLog),
    contextSummary,
    updatedAt: Date.now(),
  });
  pipeline.expire(`ckpt:${runId}`, 60 * 60 * 24 * 7); // 7-day TTL
  await pipeline.exec();
}

// ── Tool registry (each tool must declare its idempotency class) ─────────────
const tools = {
  async searchWeb({ query }) {
    // idempotent: safe to replay
    const results = await fakeSearch(query);
    return { results };
  },
  async sendEmail({ to, subject, body }) {
    // non-idempotent: guarded by external API idempotency key below
    await fakeEmailAPI({ to, subject, body });
    return { sent: true };
  },
};

// ── Core resumable executor ──────────────────────────────────────────────────
async function executeStep(runId, stepIdx, toolName, args) {
  const iKey = idempKey(runId, stepIdx, toolName, args);
  const stored = await redis.hgetall(iKey);

  // Fast-path: already completed on a prior run
  if (stored?.status === "done") {
    console.log(`[RESUME] Step ${stepIdx} (${toolName}) — replaying cached result`);
    return JSON.parse(stored.result);
  }

  // Mark as in-flight before calling tool (crash detection)
  await redis.hset(iKey, { status: "pending", startedAt: Date.now() });
  await redis.expire(iKey, 86400);

  let result;
  try {
    result = await tools[toolName](args);
  } catch (err) {
    await redis.hset(iKey, { status: "failed", error: err.message });
    throw err;
  }

  // Commit result atomically
  await redis.hset(iKey, { status: "done", result: JSON.stringify(result) });
  return result;
}

// ── Main agent loop ──────────────────────────────────────────────────────────
async function runAgent(runId, initialGoal) {
  console.log(`[START] run=${runId}`);
  const checkpoint = await loadCheckpoint(runId);
  let cursor = checkpoint?.stepCursor ?? -1;
  let toolLog = checkpoint?.toolLog ?? [];
  let contextSummary = checkpoint?.contextSummary ?? "";

  if (cursor >= 0) {
    console.log(`[RESUME] Continuing from step ${cursor + 1}`);
  }

  // Step 0: planning (always idempotent — same goal -> same plan if cached)
  const planKey = `plan:${runId}`;
  let plan;
  const cachedPlan = await redis.get(planKey);
  if (cachedPlan) {
    plan = JSON.parse(cachedPlan);
    console.log(`[RESUME] Using cached plan (${plan.length} steps)`);
  } else {
    plan = await buildPlan(openai, initialGoal);
    await redis.set(planKey, JSON.stringify(plan), "EX", 86400);
  }

  // Execute remaining steps
  for (let i = cursor + 1; i < plan.length; i++) {
    const step = plan[i];
    console.log(`[STEP ${i}] ${step.tool}(${JSON.stringify(step.args)})`);

    let result;
    try {
      result = await executeStep(runId, i, step.tool, step.args);
    } catch (err) {
      console.error(`[FAIL] Step ${i}: ${err.message}`);
      // Save checkpoint before bubbling error — next run resumes from i
      await saveCheckpoint(runId, i - 1, toolLog, contextSummary);
      throw err;
    }

    toolLog.push({ step: i, tool: step.tool, args: step.args, result });

    // Summarise context every 5 steps to prevent window overflow
    if (i % 5 === 0) {
      contextSummary = await summariseToolLog(openai, toolLog, contextSummary);
    }

    // Checkpoint after every successful step
    await saveCheckpoint(runId, i, toolLog, contextSummary);
  }

  console.log(`[DONE] run=${runId}`);
  await redis.del(`ckpt:${runId}`); // clean up on success
  return { toolLog, contextSummary };
}

// ── Stubs (replace with real implementations) ────────────────────────────────
async function buildPlan(client, goal) {
  const response = await client.chat.completions.create({
    model: "gpt-4o-mini",
    messages: [
      { role: "system", content: "Return a JSON array of {tool, args} steps." },
      { role: "user", content: goal },
    ],
    response_format: { type: "json_object" },
  });
  return JSON.parse(response.choices[0].message.content).steps;
}

async function summariseToolLog(client, log, prior) {
  const response = await client.chat.completions.create({
    model: "gpt-4o-mini",
    messages: [
      { role: "system", content: "Summarise the agent progress so far in 3 sentences." },
      { role: "user", content: `Prior: ${prior}\nNew steps: ${JSON.stringify(log.slice(-5))}` },
    ],
  });
  return response.choices[0].message.content;
}

async function fakeSearch(query) { return [`Result for "${query}"`]; }
async function fakeEmailAPI(opts) { /* stub */ }

// ── Entry point ──────────────────────────────────────────────────────────────
const RUN_ID = process.env.RUN_ID ?? crypto.randomUUID();
await runAgent(RUN_ID, "Research the top 5 AI orchestration frameworks and email a summary.");
await redis.quit();

To resume a crashed run, simply re-invoke with the same RUN_ID environment variable. The agent reads the checkpoint, rebuilds context from the tool log summary, and executes only the remaining steps. All already-committed tool calls return their cached results instantly.

Section 6 — Re-entry strategies

Full Restart vs Mid-Task Resume vs Rollback

Not every failure should trigger a resume from the last checkpoint. Choose the re-entry strategy based on what failed and whether the world state changed while the agent was down.

Strategy When to Use Risk
Full restart Plan was invalid, goal changed, or checkpoint is corrupt / older than TTL Re-runs side effects unless every tool is idempotent
Mid-task resume Process crash or transient API error after writing a valid checkpoint World state may have changed (external data freshness); re-validate if critical
Rollback to Nth checkpoint An LLM reasoning error was detected downstream; need to undo and re-plan from step N Must reverse or compensate committed side effects (Saga-style compensation)
Partial replay with override A specific tool call returned a bad result due to a transient data issue Must bust the idempotency key for that step before replaying

LangGraph's StateGraph enables rollback by storing every node's output as a versioned message in the graph state. You can call graph.update_state(config, values, as_node="plan_step") to inject a corrected value at any node and re-run the downstream subgraph only.

Section 7 — Production frameworks

Temporal, LangGraph, and Checkpointed Agent Loops Compared

Temporal Workflows

Temporal treats every workflow function as automatically durable. Activity functions (the equivalent of tool calls) are retried by the Temporal server, not your code. State is event-sourced in Temporal's history log — the workflow replays the log to reconstruct in-memory state after any crash. The cost: you write your agent as a Temporal Workflow, which requires Temporal SDK idioms (no raw I/O in workflows, only in Activities).

Netflix uses Temporal to orchestrate multi-day content encoding pipelines. Each encoding step is a durable Activity; a process crash replays only the outstanding step. Uber's driver-lifecycle workflows run for months using the same model.

LangGraph State Machines

LangGraph's StateGraph is a directed graph where each node is a Python (or JS) function that transforms the shared state object. The built-in MemorySaver checkpointer serialises the full graph state after every node execution to an in-process store; PostgresSaver and RedisSaver are drop-in replacements for durable storage. Resume is a one-liner: call graph.invoke(None, config={"configurable": {"thread_id": run_id}}) — LangGraph loads the checkpoint and re-enters the graph at the interrupted node automatically.

Custom Checkpointed Loop (the pattern shown in the code example)

For teams not yet on Temporal or LangGraph, a hand-rolled checkpointed loop in Node or Python gives you 80% of the value with no framework dependency. The pattern: plan once, checkpoint after each step, check idempotency key before each tool call, save a context summary every N steps. Add a dead-letter queue for steps that fail beyond max retries.

Temporal: full durability, event sourcing LangGraph: graph-native, built-in checkpointers Custom loop: zero deps, maximum control
Section 8 — Observability

Tracing and Dead-Letter Queues for Failed Agents

An agent that silently fails and does not resume is worse than one that crashes loudly. Build observability in from day one.

Structured Step Traces

Emit a structured JSON log line for every step: { runId, stepIdx, tool, status, durationMs, tokenCost, errorCode }. This feeds dashboards that show agent health across runs — which steps fail most, which tools are slowest, which runs exceed token budgets. OpenTelemetry's AgentSpan pattern is the emerging standard; LangSmith and Langfuse both ingest it natively.

Dead-Letter Queue

When a step exceeds its max retry count, push the entire checkpoint — runId, stepIdx, last error, serialised state — to a dead-letter queue (Redis stream, SQS, or Kafka). A separate consumer alerts on-call, stores the artefact for manual inspection, and can replay the step after a human fix. This prevents silent agent death and gives you a recovery workflow for systemic failures (e.g., a tool's API changing its response schema).

Stale Checkpoint Detection

A checkpoint with updatedAt older than 2× the expected step duration but status != done is a zombie agent — it crashed and never cleaned up. A cron job that scans for stale checkpoints and alerts (or auto-resumes) is a cheap reliability win. AWS Step Functions calls this "execution heartbeat timeout."

Section 9 — Failure modes

What Goes Wrong Even With Checkpointing

Non-deterministic planning: If the LLM re-generates the plan on resume (because plan generation was not checkpointed), the new plan may differ. Step indices shift; cached tool outputs map to the wrong steps. Always checkpoint the plan on first generation.

Stale world state: A checkpoint saved 6 hours ago may reference data that has since changed. A resumed agent that uses cached search results from before a breaking news event will reason incorrectly. Add a staleness TTL to data-fetching steps — if the checkpoint for a read step is older than N minutes, re-run it even if cached.

Context window desync: If you restore a summarised context but some tool outputs were summarised away, the LLM may re-derive facts it already established. Include a "facts proven" section in the summary that is never compressed.

Idempotency key collision: If two different logical calls hash to the same key (birthday collision or insufficient entropy in the key derivation), one call's result will be silently returned for the other's input. Use SHA-256 over the full input JSON, not just a truncated hash.

Infinite resume loop: A step that always fails (broken tool, malformed args) will be retried on every resume. Cap retries per step (3 is a common default) and send to a dead-letter queue on exhaustion rather than crashing the whole agent.

Section 10 — Scaling constraints

Production Gotchas at Scale

  • Checkpoint write latency: At hundreds of agents/second, synchronous Redis writes add up. Use fire-and-forget writes (acknowledge-then-write) only for non-critical checkpoints; use synchronous writes for steps with irreversible side effects.
  • Checkpoint size: Tool outputs can be large (HTML pages, code files, image URLs). Store large artefacts in S3 and checkpoint only the S3 key, not the raw bytes. A checkpoint entry over 1 MB is a smell.
  • Run ID fan-out: A single agent may spawn sub-agents. Use a hierarchical run ID scheme: parent-uuid/child-uuid/grandchild-uuid. Each level has its own checkpoint; the parent resumes by re-checking whether each child run completed.
  • Clock skew on multi-host: If agents run across multiple hosts without synchronised clocks, timestamp-based staleness detection is unreliable. Use logical step counters, not wall-clock times, as the primary ordering signal.
  • Checkpoint TTL expiry mid-run: A run that takes longer than the checkpoint TTL will lose its state mid-flight. Either extend the TTL on every write or use absolute expiry (expire-at a far-future timestamp set on run start).
Section 11 — Production checklist

Resumable Agent Launch Checklist

  • Stable run ID assigned at job creation, not at process start
  • Plan generated once and checkpointed; never regenerated on resume
  • Checkpoint written after every completed step (not just at the end)
  • Checkpoint includes: cursor, tool log, context summary, error count
  • Every tool call prefixed with an idempotency key check
  • Write tools marked "pending" before execution, "done" after commit
  • External write APIs receive a caller-controlled idempotency key header
  • Context summarised every N steps to prevent window overflow on resume
  • Max retry count per step with dead-letter queue on exhaustion
  • Structured trace emitted per step (runId, tool, status, durationMs)
  • Stale checkpoint detector (cron or scheduled scan) alerts on zombie runs
  • Checkpoint TTL set to at least 2× expected maximum run duration
  • Large tool outputs stored in object storage; checkpoint holds only the key
Section 12 — FAQ

Frequently Asked Questions

Do I need Temporal or can I roll my own?

For agents with under 20 steps and no branching, a hand-rolled Redis-backed loop is sufficient and far easier to operate. Temporal pays off when you need durable timers (wait for human approval for up to 30 days), complex branching with compensation logic, or multi-tenant workflow isolation. Do not add Temporal as a dependency just for checkpointing — the operational overhead is real.

How does LangGraph's MemorySaver differ from my own Redis checkpoint?

LangGraph's MemorySaver stores the entire graph state (all node outputs) in-process, which means it does not survive a process crash. PostgresSaver and RedisSaver write state to an external store after every node execution and are production-safe. The key difference from a hand-rolled solution: LangGraph automatically handles the re-entry point — you do not write resume logic; the framework replays the graph from the correct node. The trade-off is that your agent must be expressed as a LangGraph StateGraph.

What if my tool does not support idempotency keys?

Wrap the tool in a proxy that checks your own idempotency store before forwarding the call. If the proxy finds a "done" record, it returns the cached output without calling the upstream API. If it finds "pending" (a prior crash), it re-calls the API but catches duplicate-resource errors (HTTP 409 or provider-specific conflict codes) and treats them as success. This pattern is the same one Stripe's server uses internally for its own idempotency layer.

How do I handle an LLM reasoning mistake discovered after 10 completed steps?

This is a rollback scenario. In LangGraph, inject a correction at the step where the error was introduced using graph.update_state, then re-invoke from that node. In a custom loop, delete the idempotency keys and checkpoint entries for steps N through current, reset the cursor to N-1, and re-run. For steps with committed side effects (emails sent, DB rows written), you need explicit compensation: send a corrective email, soft-delete the rows, etc. This is exactly the Saga compensating transaction pattern.

How should I handle context window overflow mid-resume?

At resume time, do not reconstruct the full tool log as messages. Instead, load only the contextSummary blob from the checkpoint as a single system message, then add the outputs of only the last 2-3 steps as user messages before continuing. The summary should contain the proven facts and completed artefact references. This keeps the resume context well under the model's limit regardless of how many prior steps ran.

Key Takeaway

Durable execution is the difference between an agent that runs in demos and one that runs in production. The core pattern is deceptively simple — checkpoint after every step, check idempotency before every write, resume from cursor on restart — but the devil is in the details: checkpointing the plan before the run, summarising context before window overflow, capping retries before the loop becomes infinite, and propagating idempotency keys all the way to external APIs. Get these five things right and your agent handles any failure mode — from a transient 429 to a full host reboot — without ever repeating work it already completed or silently losing progress the user was counting on.
