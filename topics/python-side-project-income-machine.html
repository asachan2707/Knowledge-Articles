The Python Side Project That Became a Monthly Income Machine

Turning repetitive, zero-creativity work tasks into a productised Python automation service. Covers the full stack: task identification, script architecture, scheduling, error recovery, client delivery, and the business model that makes it recurring income — not a one-time gig.

Domain: Python · Automation · Freelance Engineering Credit: Suleman Safdar (Medium) Published: 2026-07-22

The best automation businesses are not built by finding a clever tech idea — they are built by noticing you are acting like a human API. You receive input (a spreadsheet, an email, a CSV drop), you transform it the same way every time, and you deliver output. That loop is a Python script waiting to exist, and every business that relies on someone doing it manually is a potential client.

Core insight: The value of an automation is not in the code — it is in reliability and trust. A script that runs correctly at 3 AM every Monday without you touching it is worth more to a client than any feature. Build for operator-free operation from day one.

Story · "I was the bottleneck every Monday morning"

Every Monday the author downloaded three CSV files from three client portals, cleaned inconsistent column names, merged them, ran a few calculations, and emailed a formatted report. It took 90 minutes. After four months and 18 repetitions, the pattern was clear: zero creativity was involved. The inputs changed but the transformation was identical.

The first script took a weekend to write and cut Monday mornings to 5 minutes. The second realisation came when a colleague complained about the same pattern in their own team. The same script, lightly parameterised, was worth money. That weekend side project became the first paying client.

Step 1 — Identifying Automatable Work

The signal is simple: if you have done a task more than three times without significant variation, it is automatable. The four highest-value categories in small-to-medium businesses:

  • Report generation — pulling data from one or more sources, aggregating, formatting, and sending. Every company does this. Most do it manually.
  • Data reconciliation — comparing records between two systems (ERP vs spreadsheet, CRM vs finance tool) and surfacing discrepancies.
  • File transformation pipelines — received CSV → clean parquet → upload to BI tool. The receiving end never changes, the sending end never changes, only the human in the middle does.
  • Notification and alerting — checking a threshold (inventory below X, invoice overdue Y days) and sending an email or Slack message. Trivially automatable, extremely sticky.

Qualification test: Can you describe the task in under 30 seconds with no ambiguity? If yes, it is automatable. If you find yourself saying "well sometimes it depends…", it is not ready yet.

Step 2 — The Script Architecture That Actually Works in Production

Beginner automation scripts are brittle because they are written for the happy path. Production-grade automation has three mandatory properties: idempotency (safe to re-run), observability (you know when it ran, what it did, and what failed), and parameterisation (the same logic works for multiple clients without forking).

The recommended structure is a three-layer model: extract → transform → load (ETL), but with an explicit state checkpoint between each layer so a crash at any point can resume from the last good state rather than restarting from scratch.

JavaScript Example — ETL Pipeline with Checkpointing 
// automation-pipeline.js
// Node.js 20+ — same architectural pattern as the Python original
import fs from 'fs/promises';
import path from 'path';

const STATE_FILE = './pipeline-state.json';

async function loadState() {
  try {
    const raw = await fs.readFile(STATE_FILE, 'utf8');
    return JSON.parse(raw);
  } catch {
    return { lastRun: null, phase: 'idle', processedRows: 0 };
  }
}

async function saveState(state) {
  await fs.writeFile(STATE_FILE, JSON.stringify(state, null, 2));
}

async function extract(config) {
  // Simulate fetching a CSV from an SFTP or API
  const raw = await fs.readFile(config.inputPath, 'utf8');
  const rows = raw.trim().split('\n').map(line => {
    const [date, amount, description] = line.split(',');
    return { date, amount: parseFloat(amount), description: description?.trim() };
  });
  return rows.filter(r => !isNaN(r.amount)); // drop malformed rows
}

function transform(rows, config) {
  // Normalise, aggregate, apply business rules
  const byDate = new Map();
  for (const row of rows) {
    const key = row.date.slice(0, 7); // YYYY-MM
    const existing = byDate.get(key) ?? { month: key, total: 0, count: 0 };
    existing.total += row.amount;
    existing.count += 1;
    byDate.set(key, existing);
  }
  return Array.from(byDate.values())
    .map(r => ({ ...r, avg: +(r.total / r.count).toFixed(2) }))
    .sort((a, b) => a.month.localeCompare(b.month));
}

async function load(summary, config) {
  const lines = ['Month,Total,Count,Avg', ...summary.map(r =>
    `${r.month},${r.total},${r.count},${r.avg}`)];
  await fs.writeFile(config.outputPath, lines.join('\n'));
  console.log(`[load] Written ${summary.length} rows to ${config.outputPath}`);
}

async function run(config) {
  const state = await loadState();
  const startTime = Date.now();
  console.log(`[pipeline] Starting — last run: ${state.lastRun ?? 'never'}`);

  try {
    await saveState({ ...state, phase: 'extracting' });
    const raw = await extract(config);

    await saveState({ ...state, phase: 'transforming', processedRows: raw.length });
    const summary = transform(raw, config);

    await saveState({ ...state, phase: 'loading' });
    await load(summary, config);

    await saveState({
      lastRun: new Date().toISOString(),
      phase: 'idle',
      processedRows: raw.length,
      durationMs: Date.now() - startTime
    });
    console.log(`[pipeline] Done in ${Date.now() - startTime}ms`);
  } catch (err) {
    await saveState({ ...state, phase: 'error', error: err.message });
    console.error('[pipeline] FAILED:', err.message);
    throw err; // re-throw so the scheduler knows to alert
  }
}

// Usage:
run({ inputPath: './data/invoices.csv', outputPath: './reports/summary.csv' });

The STATE_FILE survives a process crash. On the next scheduled run, the operator (or a monitoring alert) can inspect the phase and decide whether to resume or restart. This is what "production-grade" means in practice.

Step 3 — Scheduling: Cron, Cloud, and Reliability

A script that only runs when you manually trigger it is not an automation — it is a time-saver. True automation runs without you. The progression of scheduling options:

The recommended starting point is a $5 DigitalOcean VPS with cron. The upgrade trigger is when a missed run would cost the client money. At that point, move to a managed scheduler with alerting.

Step 4 — Error Recovery and Alerting

The single most important feature you can add to a client-facing automation is an alert when something goes wrong. Not logs you check manually — an immediate notification.

The failure taxonomy for automation pipelines:

  • Source changed — the client renamed a column, moved a file, or changed the export format. Most common failure. Fix: validate schema on extraction, fail loudly before touching the database.
  • Network/credential failure — SFTP password rotated, API token expired. Fix: credential expiry monitoring with proactive alerts 7 days before.
  • Logic error with new data — division by zero, unexpected null, date format change. Fix: unit tests over transformation layer with representative edge-case fixtures.
  • Output delivery failure — SMTP server bounced, wrong recipient list. Fix: delivery receipt confirmation with retry.

A simple alerting pattern: wrap the entire pipeline in a try/catch that sends a Slack webhook or email on failure with the phase name, error message, and a link to the logs. Clients who see "your Monday report failed at 06:01 due to a missing column — we are investigating" trust the service infinitely more than if the report simply did not arrive.

Step 5 — The Business Model: Why This Becomes Recurring Income

A one-time automation is a freelance project. A maintained automation is a product. The difference is a service level agreement and a retainer.

The productised service model that converts well:

  1. Setup fee (£500–£2,000 depending on complexity) — covers initial build, testing, and deployment.
  2. Monthly retainer (£150–£500/month) — covers monitoring, source changes (when the client changes their export format), and on-call response.
  3. The retention driver — the client's data pipeline runs invisibly every Monday. They forget it exists. Cancellation means recreating the problem they no longer think about.

The key insight is that retainer income is not "support" — it is change management. Every time the client's source system changes (and it always changes), they need you. Build this expectation into the contract language from day one.

Scaling signal: Once you have three clients on retainers running the same core architecture with different configs, extract the config into a YAML or JSON file per client and run one parameterised deployment. The fourth and fifth clients cost almost no additional engineering time.

Failure Modes and Production Gotchas

  • State file corruption — if the process is killed mid-write, the state file may be half-written. Use atomic writes: write to a temp file, then rename() (which is atomic on POSIX filesystems).
  • Timezone landmines — cron runs in server timezone, client data is in their local timezone, report comparisons break. Fix: store all timestamps as UTC, convert only at display time.
  • Silent data quality degradation — the pipeline succeeds but produces wrong numbers because an upstream system changed a calculation. Fix: add statistical assertions (total revenue this month should be ±20% of last month; alert on outliers).
  • Client CSV encoding chaos — Windows clients produce CP-1252 encoded CSVs; your UTF-8 parser breaks on £ signs. Always detect encoding with chardet or pass it as a config option.
  • Memory exhaustion on large files — streaming parsers (csv.reader in Python, readline in Node) for files over ~100MB. Never readFileSync an unknown-size input.

Checklist: From Script to Income

  • ☐ Task passes the 30-second description test
  • ☐ Script is idempotent (safe to re-run on same input)
  • ☐ Schema validation on extraction (fail loud, fail early)
  • ☐ State file with atomic writes for crash recovery
  • ☐ Failure alert to Slack or email within 5 minutes of error
  • ☐ Scheduler runs without manual intervention
  • ☐ Config is parameterised (one script, N clients)
  • ☐ Deployment documented so a non-engineer can understand what it does
  • ☐ Retainer contract includes "source change support" language
