Microservices Design Patterns: A Crash Course on the 9 Essential Patterns

Nine essential microservices patterns — Database Per Service, CQRS, Event Sourcing, Saga, API Gateway, BFF, Circuit Breaker, Service Discovery, and Sidecar — each explained with the problem it solves, how it works, when to use it, and JavaScript examples for Saga orchestration, CQRS, Service Discovery, and Event Sourcing replay.

Microservices patterns are not decoration — each one exists because a specific failure mode bit someone hard enough that they built a reusable solution. Understanding the failure mode first makes the pattern obvious; memorising the pattern name without the failure mode gives you vocabulary without judgment.

Core idea: Patterns compose. CQRS + Event Sourcing is one of the most common pairings. Saga + API Gateway handles distributed transactions with a clean client interface. An API Gateway typically embeds a Circuit Breaker, and the Sidecar runs the service mesh that implements Service Discovery. Choose patterns based on the problem, not on what sounds architecturally impressive.

Data & state

Pattern reference: data ownership and consistency

1. Database Per Service
Solves: shared DB coupling
Each microservice owns a dedicated database. Data exchange happens only through well-defined APIs. Prevents the "shared DB = shared fate" problem where one service's schema change breaks every other service. Requires bounded context definition and distributed transaction management (→ Saga).
2. CQRS
Solves: read/write contention
Separates read (Query) and write (Command) paths with separate data models. Write path optimised for consistency; read path optimised for query performance via denormalised projections. A microservice publishes domain events on writes; a listener updates the read-optimised store.
3. Event Sourcing
Solves: lost history & audit gaps
Problem: traditional databases store current state only, losing the history of how state changed — valuable for audit, debugging, and deriving new projections retroactively. Solution: every state change is stored as an immutable event; current state is the result of replaying the log. Enables full audit trail, time-travel queries, and replay for new read models. Often paired with CQRS. Cost: replay can be slow for large histories (mitigate with snapshots).
4. Saga Pattern
Solves: distributed transactions
Problem: a business operation spans multiple services (order + payment + inventory) and two-phase commit across microservices is impractical. Solution: break the transaction into a sequence of local transactions. Each step publishes an event; the next service reacts. Failures trigger compensating transactions that undo prior steps. Two forms: Choreography (services react to events autonomously) and Orchestration (a central coordinator directs each step).
Client access

Pattern reference: client-facing patterns

5. API Gateway
Solves: client complexity
Problem: clients need data from multiple services for a single screen; calling each directly creates N network hops and exposes internal topology. Solution: a single entry point that routes, aggregates, authenticates, and rate-limits, handling cross-cutting concerns (auth, rate limiting, caching) centrally. Can translate protocols (REST → gRPC) and typically embeds a Circuit Breaker. Use when: you have multiple client types (web, mobile, partner) or would otherwise duplicate cross-cutting concerns. Risk: becomes a SPOF if not load-balanced.
6. Backends for Frontends (BFF)
Solves: UI-specific data needs
Separate backend service per client type (web, mobile, partner API). Each BFF aggregates and shapes data for its consumer: the mobile BFF reduces payload for bandwidth; the web BFF serves richer data. Prevents one-size-fits-all API bloat.
Resilience & operations

Pattern reference: resilience and operational patterns

7. Circuit Breaker
Solves: cascading failures
Problem: a slow or failed downstream service makes the caller queue threads waiting for responses, exhausting resources and taking down the caller too. Solution: a proxy wraps every downstream call and tracks failure rate. When failures exceed a threshold the circuit opens and requests fail fast with a graceful fallback instead of waiting for a timeout. Three states: Closed (normal) → Open (fail fast, no requests) → Half-Open (allow limited test requests; close if they succeed, reopen if they fail).
8. Service Discovery
Solves: dynamic service location
Problem: services in containers get new IP addresses on every restart, so hardcoded URLs break immediately. Solution: services register in a Service Registry on startup and send heartbeats; clients (or a load balancer) query it for healthy instances. Two forms: Client-Side (client queries the registry, e.g. Netflix Eureka) or Server-Side (load balancer queries the registry, e.g. AWS ALB, Kubernetes).
9. Sidecar
Solves: cross-cutting operational concerns
Problem: every service needs logging, metrics, config refresh, certificate rotation, and mesh proxying; implementing these in each service adds boilerplate and inconsistency. Solution: a helper container runs alongside the main service in the same pod/VM, sharing its filesystem and network namespace, and handles these concerns with no application code changes. It is created and retired with the parent service. Used in Istio and Linkerd, and it runs the mesh that implements Service Discovery.
JavaScript Example

Saga orchestration + CQRS in Node.js

JavaScript Example 
// Saga orchestrator for e-commerce order flow
// Order → Payment → Inventory → Shipping (each is a local transaction)

class OrderSaga {
  constructor(services) {
    this.order = services.orderService;
    this.payment = services.paymentService;
    this.inventory = services.inventoryService;
    this.shipping = services.shippingService;
  }

  async execute(orderData) {
    const saga = { orderId: null, paymentId: null, inventoryReserved: false };

    try {
      // Step 1: Create order
      saga.orderId = await this.order.create(orderData);

      // Step 2: Charge payment
      saga.paymentId = await this.payment.charge({
        orderId: saga.orderId,
        amount: orderData.amount,
        userId: orderData.userId,
      });

      // Step 3: Reserve inventory
      await this.inventory.reserve({ orderId: saga.orderId, items: orderData.items });
      saga.inventoryReserved = true;

      // Step 4: Create shipment
      const shipmentId = await this.shipping.create({ orderId: saga.orderId });

      return { success: true, orderId: saga.orderId, shipmentId };

    } catch (err) {
      // Compensating transactions — undo in reverse order
      console.error(`[saga] Step failed: ${err.message} — running compensation`);
      await this._compensate(saga, err);
      throw new Error(`Order saga failed: ${err.message}`);
    }
  }

  async _compensate(saga, originalError) {
    if (saga.inventoryReserved) {
      await this.inventory.release({ orderId: saga.orderId }).catch(console.error);
    }
    if (saga.paymentId) {
      await this.payment.refund({ paymentId: saga.paymentId }).catch(console.error);
    }
    if (saga.orderId) {
      await this.order.cancel({ orderId: saga.orderId, reason: originalError.message }).catch(console.error);
    }
  }
}

// CQRS: separate write and read paths
class OrderCommandService {
  async createOrder(data, eventBus) {
    const order = await db.orders.insert(data);
    // Publish event so read-side projection can update
    await eventBus.publish('order.created', { orderId: order.id, ...data });
    return order.id;
  }
}

class OrderQueryService {
  // Read from denormalised, query-optimised projection
  async getOrderDashboard(userId) {
    return db.order_projections.findAll({ userId, include: ['user', 'items', 'shipment'] });
  }
}
Orchestration vs Choreography: Choreography feels elegant but becomes an untraceable web of events as system complexity grows. Orchestration (explicit saga coordinator) is easier to reason about, test, and monitor — especially for multi-step workflows where partial failure is common. Start with orchestration.
JavaScript Example

Service Discovery client + Event Sourcing replay

JavaScript Example 
// Client-side Service Discovery: client queries registry for healthy instances
class ServiceDiscoveryClient {
  constructor(registryUrl) {
    this.registryUrl = registryUrl;
    this._cache = new Map();
    this._ttl = 10_000; // cache entries for 10 seconds
  }

  async resolve(serviceName) {
    const cached = this._cache.get(serviceName);
    if (cached && Date.now() - cached.fetchedAt < this._ttl) {
      return this._roundRobin(cached.instances);
    }

    const res = await fetch(`${this.registryUrl}/services/${serviceName}`);
    const { instances } = await res.json(); // [{ url, healthy, weight }]
    const healthy = instances.filter(i => i.healthy);
    this._cache.set(serviceName, { instances: healthy, fetchedAt: Date.now(), index: 0 });
    return this._roundRobin(this._cache.get(serviceName));
  }

  _roundRobin(entry) {
    const url = entry.instances[entry.index % entry.instances.length].url;
    entry.index++;
    return url;
  }
}

// Event Sourcing: store events, rebuild state by replay
class EventStore {
  constructor() {
    this._events = new Map(); // aggregateId → events[]
  }

  append(aggregateId, event) {
    if (!this._events.has(aggregateId)) this._events.set(aggregateId, []);
    this._events.get(aggregateId).push({
      ...event,
      timestamp: new Date().toISOString(),
      seq: this._events.get(aggregateId).length,
    });
  }

  getEvents(aggregateId, fromSeq = 0) {
    return (this._events.get(aggregateId) ?? []).slice(fromSeq);
  }
}

// Rebuild current order state from events
function replayOrderEvents(events) {
  return events.reduce((state, event) => {
    switch (event.type) {
      case 'order.created':
        return { ...state, id: event.payload.id, status: 'pending', items: event.payload.items };
      case 'payment.completed':
        return { ...state, status: 'confirmed', paymentId: event.payload.paymentId };
      case 'order.shipped':
        return { ...state, status: 'shipped', trackingId: event.payload.trackingId };
      case 'order.cancelled':
        return { ...state, status: 'cancelled', reason: event.payload.reason };
      default:
        return state;
    }
  }, {});
}

// Usage
const store = new EventStore();
const orderId = 'ord-001';
store.append(orderId, { type: 'order.created', payload: { id: orderId, items: ['item-1'] } });
store.append(orderId, { type: 'payment.completed', payload: { paymentId: 'pay-123' } });
store.append(orderId, { type: 'order.shipped', payload: { trackingId: 'TRACK-456' } });

const currentState = replayOrderEvents(store.getEvents(orderId));
console.log(currentState);
// { id: 'ord-001', status: 'shipped', items: ['item-1'], paymentId: 'pay-123', trackingId: 'TRACK-456' }
Event Sourcing cost: The main cost is rebuild time. A long-lived aggregate with 10,000 events takes 10,000 reductions to compute current state. Mitigation: snapshots — periodically save a state snapshot and replay only events since the snapshot. Snapshots are an optimization, not the source of truth; the event log remains the canonical record.

Key Takeaway

These nine patterns address the core challenges of microservices: data ownership (Database Per Service), client complexity (API Gateway, BFF), state management (CQRS, Event Sourcing, Saga), and operational resilience (Circuit Breaker, Service Discovery, Sidecar). They are frequently combined — a production system may use all of them: API Gateway + Circuit Breaker at the entry point, Service Discovery in the gateway or load balancer, Saga for distributed workflows, Event Sourcing for audit-critical aggregates, Sidecar for cross-cutting concerns. Start with Circuit Breaker and Service Discovery as operational safety nets; add Saga and Event Sourcing when business requirements demand distributed transactions and audit history. Understand the failure each pattern prevents, then decide which failures are worth spending complexity budget on for your system's scale and team size.
