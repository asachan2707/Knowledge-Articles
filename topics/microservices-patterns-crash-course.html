A Crash Course on Microservices Design Patterns

Eight essential microservices patterns — Database Per Service, API Gateway, BFF, CQRS, Event Sourcing, Saga, Sidecar, and Circuit Breaker — each explained with the problem it solves, when to use it, and a JavaScript example showing how it works in practice.

Microservices patterns are not decoration — each one exists because a specific failure mode bit someone hard enough that they built a reusable solution. Understanding the failure mode first makes the pattern obvious; memorising the pattern name without the failure mode gives you vocabulary without judgment.

Core idea: Patterns are frequently combined. CQRS + Event Sourcing is one of the most common pairings. Saga + API Gateway handles distributed transactions with a clean client interface. Choose patterns based on the problem, not based on what sounds architecturally impressive.

The 8 patterns

Pattern reference

1. Database Per Service
Solves: shared DB coupling
Each microservice owns a dedicated database. Data exchange happens only through well-defined APIs. Prevents the "shared DB = shared fate" problem where one service's schema change breaks every other service. Requires bounded context definition and distributed transaction management (→ Saga).
2. API Gateway
Solves: client complexity
Single entry point routing, aggregating, and securing client-to-microservice communication. Handles cross-cutting concerns — auth, rate limiting, caching — centrally rather than duplicating them in every service. Can translate between protocols (REST → gRPC). Risk: becomes a SPOF if not load-balanced.
3. Backends for Frontends (BFF)
Solves: UI-specific data needs
Separate backend service per client type (web, mobile, partner API). Each BFF aggregates and shapes data specifically for its consumer. Mobile BFF reduces payload for bandwidth; web BFF serves richer data. Prevents one-size-fits-all API bloat.
4. CQRS
Solves: read/write contention
Separates read (Query) and write (Command) paths with separate data models. Write path optimised for consistency; read path optimised for query performance via denormalised projections. A microservice publishes domain events on writes; a listener updates the read-optimised store.
5. Event Sourcing
Solves: lost history & audit gaps
Every state change is stored as an immutable event rather than updating a record. Current state is reconstructed by replaying the event log. Enables full audit trail, time-travel queries, and replay for new read models. Often paired with CQRS. Cost: event replay can be slow for large histories.
6. Saga Pattern
Solves: distributed transactions
Breaks a distributed transaction into a sequence of local transactions. Each step publishes an event; the next service reacts. Failures trigger compensating transactions that undo prior steps. Two forms: Choreography (services react to events autonomously) and Orchestration (a central coordinator directs each step).
7. Sidecar Pattern
Solves: cross-cutting operational concerns
A helper container runs alongside the main service, sharing its filesystem and network. Handles logging, config refresh, certificate rotation, service mesh proxying — without any changes to the application code. The sidecar is created and retired with the parent service.
8. Circuit Breaker
Solves: cascading failures
A proxy monitors failure rates between services. When failures exceed a threshold, the circuit "trips" (opens), returning a graceful fallback immediately rather than waiting for a timeout. After a configured period, it enters half-open state and allows limited test requests. Closes again when requests succeed.
JavaScript Example

Saga orchestration + Circuit Breaker in Node.js

JavaScript Example 
// Saga orchestrator for e-commerce order flow
// Order → Payment → Inventory → Shipping (each is a local transaction)

class OrderSaga {
  constructor(services) {
    this.order = services.orderService;
    this.payment = services.paymentService;
    this.inventory = services.inventoryService;
    this.shipping = services.shippingService;
  }

  async execute(orderData) {
    const saga = { orderId: null, paymentId: null, inventoryReserved: false };

    try {
      // Step 1: Create order
      saga.orderId = await this.order.create(orderData);

      // Step 2: Charge payment
      saga.paymentId = await this.payment.charge({
        orderId: saga.orderId,
        amount: orderData.amount,
        userId: orderData.userId,
      });

      // Step 3: Reserve inventory
      await this.inventory.reserve({ orderId: saga.orderId, items: orderData.items });
      saga.inventoryReserved = true;

      // Step 4: Create shipment
      const shipmentId = await this.shipping.create({ orderId: saga.orderId });

      return { success: true, orderId: saga.orderId, shipmentId };

    } catch (err) {
      // Compensating transactions — undo in reverse order
      console.error(`[saga] Step failed: ${err.message} — running compensation`);
      await this._compensate(saga, err);
      throw new Error(`Order saga failed: ${err.message}`);
    }
  }

  async _compensate(saga, originalError) {
    if (saga.inventoryReserved) {
      await this.inventory.release({ orderId: saga.orderId }).catch(console.error);
    }
    if (saga.paymentId) {
      await this.payment.refund({ paymentId: saga.paymentId }).catch(console.error);
    }
    if (saga.orderId) {
      await this.order.cancel({ orderId: saga.orderId, reason: originalError.message }).catch(console.error);
    }
  }
}

// CQRS: separate write and read paths
class OrderCommandService {
  async createOrder(data, eventBus) {
    const order = await db.orders.insert(data);
    // Publish event so read-side projection can update
    await eventBus.publish('order.created', { orderId: order.id, ...data });
    return order.id;
  }
}

class OrderQueryService {
  // Read from denormalised, query-optimised projection
  async getOrderDashboard(userId) {
    return db.order_projections.findAll({ userId, include: ['user', 'items', 'shipment'] });
  }
}
Orchestration vs Choreography: Choreography feels elegant but becomes an untraceable web of events as system complexity grows. Orchestration (explicit saga coordinator) is easier to reason about, test, and monitor — especially for multi-step workflows where partial failure is common. Start with orchestration.

Key Takeaway

These eight patterns address the four core challenges of microservices: data ownership (Database Per Service), client complexity (API Gateway, BFF), state management (CQRS, Event Sourcing, Saga), and operational resilience (Sidecar, Circuit Breaker). They are frequently combined — a production system might use all eight simultaneously. Understand the failure each pattern prevents, then decide which failures are worth spending complexity budget on for your specific system's scale and team size.
