Story · Why a single server always breaks at scale

Every developer's first backend is one server talking to one database. It works. Then the product grows, traffic spikes, and suddenly the single machine can't keep up — every request competes for the same CPU and disk. The author's framing is blunt: most system design knowledge isn't about clever code, it's about knowing which problems have already been solved and which tool to reach for.

The article's strength is sequence. It starts with a literal web request (browser → DNS → IP → port → server) and builds each layer of complexity on top — so by the time you reach Kafka partitions and Raft consensus, you understand exactly why those abstractions exist.

The foundation

Servers, DNS, and how a request actually works

A server is a physical or virtual machine running application code. When a browser requests a URL:

  1. The browser queries DNS to resolve the domain to an IP address.
  2. The browser sends the HTTP request to that IP.
  3. The server uses a port number to route the request to the right application process.

In production, you rent cloud VMs (e.g., AWS EC2) and push your code to them. Understanding this baseline matters because every scaling decision is really a decision about how to handle more of these request flows simultaneously.

Latency vs Throughput

Latency is how long a single request takes (milliseconds). Throughput is how many requests the system handles per second (RPS/TPS). A highway analogy: latency = time for one car to drive A→B; throughput = cars per hour. The goal is always high throughput and low latency simultaneously — they pull in opposite directions under load.

How a DNS resolution + HTTP request works — in code

Node.js — DNS lookup + HTTP request simulation
const dns = require('dns').promises;
const https = require('https');

async function makeRequest(hostname, path = '/') {
  // Step 1: DNS resolution — domain → IP
  const addresses = await dns.lookup(hostname);
  console.log(`DNS resolved ${hostname} → ${addresses.address}`);

  // Step 2: HTTP request to resolved IP (via hostname for TLS SNI)
  return new Promise((resolve, reject) => {
    const options = {
      hostname,
      port: 443,          // HTTPS default port
      path,
      method: 'GET',
      headers: { Host: hostname }
    };

    const req = https.request(options, (res) => {
      let body = '';
      res.on('data', chunk => body += chunk);
      res.on('end', () => {
        console.log(`Status: ${res.statusCode}`);
        console.log(`Latency concept: time from req.end() to this callback = RTT`);
        resolve(body.slice(0, 200)); // first 200 chars
      });
    });

    req.on('error', reject);
    const startTime = Date.now();
    req.end();
    console.log(`Request sent at ${startTime}ms`);
  });
}

// Usage: node server.js
makeRequest('example.com', '/').then(console.log).catch(console.error);

Scaling

Vertical, horizontal, and auto-scaling

Vertical scaling (scale up/down)

Add more RAM, CPU, or storage to the same machine. Simple — no code changes required. Used for SQL databases and stateful services. Has a hard ceiling: you eventually run out of hardware to add.

Horizontal scaling (scale out/in)

Add more machines and distribute load across them. Requires a load balancer as the single contact point for clients. The load balancer routes each incoming request to whichever server is least busy. This is the dominant pattern in modern production systems.

Auto-scaling

Dynamically adjusts server count based on real-time traffic. When CPU usage crosses a threshold (e.g., 90%), new instances spin up automatically and are removed when traffic drops. This avoids paying for idle capacity while surviving traffic spikes — but requires load testing upfront to calibrate the thresholds correctly.

Horizontal scaling with Node.js Cluster module

Node.js — Cluster module for horizontal scaling on one machine
const cluster = require('cluster');
const http = require('http');
const os = require('os');

const NUM_WORKERS = os.cpus().length; // one worker per CPU core

if (cluster.isPrimary) {
  console.log(`Primary PID ${process.pid}: spawning ${NUM_WORKERS} workers`);

  // Spawn workers (horizontal scaling across CPU cores)
  for (let i = 0; i < NUM_WORKERS; i++) {
    cluster.fork();
  }

  // Auto-recovery: restart worker if it crashes
  cluster.on('exit', (worker, code, signal) => {
    console.log(`Worker ${worker.process.pid} died (code=${code}). Restarting...`);
    cluster.fork(); // auto-scale back to target count
  });

  // Simulate auto-scaling signal: if load is high, fork more workers
  function checkLoad() {
    const activeWorkers = Object.keys(cluster.workers).length;
    // In production: check CPU% via os.loadavg() or metrics API
    const load = os.loadavg()[0]; // 1-minute load average
    if (load > 0.8 * NUM_WORKERS && activeWorkers < NUM_WORKERS * 2) {
      console.log(`High load (${load.toFixed(2)}): scaling out — adding worker`);
      cluster.fork();
    }
  }
  setInterval(checkLoad, 10_000); // check every 10s

} else {
  // Worker: runs the actual HTTP server
  http.createServer((req, res) => {
    res.end(`Handled by worker PID ${process.pid}\n`);
  }).listen(3000);

  console.log(`Worker ${process.pid} started`);
}

Interview skill

Back-of-the-envelope estimation

Interviewers expect you to size a system before designing it. Three things to estimate:

  • Load: DAU × actions/day = writes/day. (100M users × 10 tweets = 1B writes/day)
  • Storage: bytes per record × daily writes × retention. (Twitter example: ~1 PB/day including photos)
  • Resources: req/sec × CPU time per request ÷ core capacity = cores needed → server count.

The memory powers-of-2 table is worth memorising: KB = 10³, MB = 10⁶, GB = 10⁹, TB = 10¹², PB = 10¹⁵. Most estimation errors come from off-by-1000x mistakes, not arithmetic.

Back-of-envelope calculator in code

JavaScript — Back-of-envelope estimation calculator
// ── Unit helpers ──────────────────────────────────────────────
const KB = 1_000;
const MB = 1_000 * KB;
const GB = 1_000 * MB;
const TB = 1_000 * GB;
const PB = 1_000 * TB;

function formatBytes(bytes) {
  if (bytes >= PB) return `${(bytes / PB).toFixed(2)} PB`;
  if (bytes >= TB) return `${(bytes / TB).toFixed(2)} TB`;
  if (bytes >= GB) return `${(bytes / GB).toFixed(2)} GB`;
  if (bytes >= MB) return `${(bytes / MB).toFixed(2)} MB`;
  return `${(bytes / KB).toFixed(2)} KB`;
}

// ── Estimation function ───────────────────────────────────────
function estimateSystem({ dau, actionsPerDay, bytesPerRecord, retentionDays, cpuMsPerReq, coresPerServer }) {
  const writesPerDay  = dau * actionsPerDay;
  const writesPerSec  = Math.ceil(writesPerDay / 86_400);
  const storagePerDay = writesPerDay * bytesPerRecord;
  const totalStorage  = storagePerDay * retentionDays;

  // Resource estimation: req/sec × cpuMs per req ÷ 1000ms per core
  const coresNeeded   = Math.ceil(writesPerSec * (cpuMsPerReq / 1000));
  const serversNeeded = Math.ceil(coresNeeded / coresPerServer);

  console.log('═══ Back-of-Envelope Estimation ═══');
  console.log(`DAU:               ${dau.toLocaleString()}`);
  console.log(`Writes/day:        ${writesPerDay.toLocaleString()}`);
  console.log(`Writes/sec (peak): ${writesPerSec.toLocaleString()}`);
  console.log(`Storage/day:       ${formatBytes(storagePerDay)}`);
  console.log(`Total storage:     ${formatBytes(totalStorage)} (${retentionDays}d retention)`);
  console.log(`CPU cores needed:  ${coresNeeded}`);
  console.log(`Servers needed:    ${serversNeeded} (${coresPerServer} cores each)`);
}

// ── Twitter example from the article ─────────────────────────
estimateSystem({
  dau:            100_000_000,   // 100M DAU
  actionsPerDay:  10,            // 10 tweets per user per day
  bytesPerRecord: 500,           // ~500 bytes per tweet (text only)
  retentionDays:  365,           // 1 year retention
  cpuMsPerReq:    10,            // 10ms CPU per write
  coresPerServer: 4,
});

// ── Photo-heavy estimation ─────────────────────────────────────
console.log('\n── Adding photo uploads (10% of tweets have 2MB photos) ──');
const photoUploadsPerDay = 100_000_000 * 10 * 0.10;
const photoStoragePerDay = photoUploadsPerDay * 2 * MB;
console.log(`Photo storage/day: ${formatBytes(photoStoragePerDay)}`);
Distributed systems theory

CAP theorem

In a distributed system (data stored across multiple servers) you can only simultaneously guarantee two of these three properties:

  • Consistency (C): Every read returns the same, most recent value from any node.
  • Availability (A): The system responds even when some nodes fail.
  • Partition Tolerance (P): The system keeps working despite network communication failures between nodes.

Because network partitions are inevitable in real distributed systems, P is non-negotiable. The actual choice is always CP vs AP:

  • CP (consistency + partition tolerance): Banking, payments, stock trading — stale reads are unacceptable.
  • AP (availability + partition tolerance): Social media likes, feeds — temporary inconsistency is fine.

Simulating CP vs AP behavior during a network partition

JavaScript — CAP theorem: CP vs AP node simulation
class DistributedNode {
  constructor(id, strategy) {
    this.id = id;
    this.strategy = strategy; // 'CP' or 'AP'
    this.data = new Map();
    this.partitioned = false; // simulates network partition
    this.primary = null;
  }

  setPrimary(node) { this.primary = node; }
  simulatePartition() { this.partitioned = true; }
  healPartition() {
    this.partitioned = false;
    // On heal: sync from primary (eventual consistency catch-up)
    if (this.primary) {
      for (const [k, v] of this.primary.data) this.data.set(k, v);
    }
  }

  read(key) {
    if (this.partitioned) {
      if (this.strategy === 'CP') {
        // CP: refuse reads during partition — return error to ensure consistency
        throw new Error(`[CP Node ${this.id}] PARTITION: refusing read — consistency cannot be guaranteed`);
      } else {
        // AP: serve stale data — availability over consistency
        console.warn(`[AP Node ${this.id}] PARTITION: serving potentially stale data for key "${key}"`);
        return this.data.get(key) ?? null;
      }
    }
    return this.data.get(key) ?? null;
  }

  write(key, value) {
    if (this.partitioned && this.strategy === 'CP') {
      throw new Error(`[CP Node ${this.id}] PARTITION: refusing write — cannot guarantee consistency`);
    }
    this.data.set(key, value);
    return { ok: true, node: this.id, value };
  }
}

// ── Demonstration ──────────────────────────────────────────────
const cpNode = new DistributedNode('replica-1', 'CP');
const apNode = new DistributedNode('replica-2', 'AP');

cpNode.write('balance', 1000);
apNode.write('likes', 42);

console.log('Before partition:');
console.log('CP read balance:', cpNode.read('balance')); // 1000
console.log('AP read likes:',  apNode.read('likes'));   // 42

// Simulate network partition
cpNode.simulatePartition();
apNode.simulatePartition();

console.log('\nDuring network partition:');
try {
  console.log('CP read:', cpNode.read('balance'));     // throws
} catch (e) { console.error(e.message); }             // CP refuses

console.log('AP read:', apNode.read('likes'));         // 42 (stale but available)

// Heal
apNode.healPartition();
console.log('\nAfter healing: AP node synced, serves fresh data');
Database scaling — step by step

5-step database scaling playbook

Step 1 — Indexing

Without an index, queries do a full table scan: O(N). With a B-tree index on the searched column: O(log N). One SQL line enables it; the database handles the rest. Always index before reaching for bigger solutions.

Step 2 — Partitioning

Splits one large table into smaller sub-tables on the same server. Each partition maintains its own index. The database engine routes queries automatically. Reduces scan size without application-level changes.

Step 3 — Master-slave (read replicas)

One master node handles all writes. Multiple slave nodes handle reads. Writes replicate from master → slaves (synchronously or asynchronously). Use this when read-heavy traffic saturates a single server.

Step 4 — Multi-master

Multiple masters handle writes (e.g., one per geographic region). The challenge is conflict resolution: when the same record has different values on two masters, which wins? Common strategies: last-write-wins, merge, or accept-both.

Step 5 — Sharding

Splits the table across different servers (shards). Unlike partitioning, routing logic must live in application code. The sharding key must distribute data evenly.

  • Range-based: Simple, but skewed if data isn't uniformly distributed.
  • Hash-based: (HASH(key) % num_shards) — even distribution, hard to rebalance.
  • Geographic: Good for geo-distributed systems, hotspot risk per region.
  • Directory-based: Lookup table maps keys to shards — flexible, but the directory itself becomes a bottleneck.

Sharding downsides: complex routing code, expensive cross-shard JOINs, harder data consistency. Decision rule: try vertical first → master-slave for reads → sharding for writes.

Database scaling — SQL examples for each step

SQL — Index, Partition, and Sharding key examples
-- STEP 1: Indexing (O(N) → O(log N))
-- Without index: full scan on 100M rows
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
-- → Seq Scan on users (cost=0..2M rows)

-- Add a B-tree index
CREATE INDEX idx_users_email ON users (email);
-- Now the same query uses the index
EXPLAIN SELECT * FROM users WHERE email = 'alice@example.com';
-- → Index Scan using idx_users_email (cost=0..8)

-- STEP 2: Table Partitioning (PostgreSQL range partitioning)
CREATE TABLE orders (
  id         BIGSERIAL,
  user_id    BIGINT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL,
  total      NUMERIC(10,2)
) PARTITION BY RANGE (created_at);

-- Create monthly partitions — each has its own smaller index
CREATE TABLE orders_2026_01 PARTITION OF orders
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE orders_2026_02 PARTITION OF orders
  FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
-- PostgreSQL routes queries to the right partition automatically

-- STEP 5: Sharding key decision
-- BAD shard key: created_at (all writes go to one "hot" shard)
-- GOOD shard key: user_id (distributes writes evenly)
-- Hash-based: shard_id = HASH(user_id) % 4

Master-slave routing in Node.js

Node.js — Read/write split with master-slave database pool
const { Pool } = require('pg'); // npm install pg

// Master handles all WRITES
const master = new Pool({
  host: 'db-master.internal',
  port: 5432,
  database: 'mydb',
  user: 'app',
  password: process.env.DB_PASS,
  max: 10,
});

// Read replicas handle READ queries (round-robin between replicas)
const replicas = [
  new Pool({ host: 'db-replica-1.internal', port: 5432, database: 'mydb', user: 'app', password: process.env.DB_PASS }),
  new Pool({ host: 'db-replica-2.internal', port: 5432, database: 'mydb', user: 'app', password: process.env.DB_PASS }),
];
let replicaIndex = 0;

function getReadPool() {
  // Round-robin across replicas
  const pool = replicas[replicaIndex % replicas.length];
  replicaIndex++;
  return pool;
}

// Application-level routing
async function dbQuery(sql, params, { write = false } = {}) {
  const pool = write ? master : getReadPool();
  const result = await pool.query(sql, params);
  return result.rows;
}

// Usage
async function run() {
  // Write → goes to master
  await dbQuery(
    'INSERT INTO orders (user_id, total) VALUES ($1, $2)',
    [42, 99.99],
    { write: true }
  );

  // Read → goes to a replica
  const orders = await dbQuery(
    'SELECT * FROM orders WHERE user_id = $1',
    [42]
  );
  console.log('Orders from replica:', orders);
}

run().catch(console.error);

Hash-based sharding router

JavaScript — Hash-based sharding key router
const crypto = require('crypto');

const SHARDS = [
  { id: 0, host: 'shard-0.db.internal' },
  { id: 1, host: 'shard-1.db.internal' },
  { id: 2, host: 'shard-2.db.internal' },
  { id: 3, host: 'shard-3.db.internal' },
];

function getShardForKey(userId) {
  // Convert userId to a 32-bit integer via SHA-256, then mod num_shards
  const hash = crypto.createHash('sha256').update(String(userId)).digest('hex');
  const num  = parseInt(hash.slice(0, 8), 16); // first 32 bits
  return SHARDS[num % SHARDS.length];
}

// Test distribution
const counts = Array(SHARDS.length).fill(0);
for (let userId = 1; userId <= 10_000; userId++) {
  const shard = getShardForKey(userId);
  counts[shard.id]++;
}

console.log('Shard distribution across 10,000 user IDs:');
counts.forEach((count, i) => {
  console.log(`  Shard ${i}: ${count} users (${(count / 100).toFixed(1)}%)`);
});
// Expect roughly 25% each — hash-based gives even distribution
Database selection

SQL vs NoSQL — when to use which

SQL databases

Tabular storage with a predefined schema. Follows ACID (Atomicity, Consistency, Isolation, Durability). Scales primarily vertically. Examples: MySQL, PostgreSQL, SQLite.

NoSQL database types

  • Document (MongoDB) — JSON/BSON records, flexible schema.
  • Key-value (Redis, DynamoDB) — blazing-fast lookups by key.
  • Column-family (Cassandra) — optimized for write-heavy, wide-row access patterns.
  • Graph (Neo4j) — relationships are first-class, ideal for social graphs.

The decision framework

  • Structured, fixed schema with complex joins → SQL
  • Financial transactions, strict data integrity → SQL
  • Flexible/unstructured data at high scale → NoSQL
  • Social media posts, likes, activity feeds → NoSQL
  • High availability with eventual consistency acceptable → NoSQL

SQL vs NoSQL — same query in PostgreSQL and MongoDB

Node.js — PostgreSQL (SQL) vs MongoDB (NoSQL) side-by-side
// ── PostgreSQL (SQL) example ──────────────────────────────────
const { Client } = require('pg');

async function sqlExample() {
  const client = new Client({ connectionString: 'postgresql://user:pass@localhost/mydb' });
  await client.connect();

  // Fixed schema — enforced by the database
  await client.query(`
    CREATE TABLE IF NOT EXISTS users (
      id    SERIAL PRIMARY KEY,
      name  VARCHAR(100) NOT NULL,
      email VARCHAR(255) UNIQUE NOT NULL,
      age   INT CHECK (age > 0)
    )
  `);

  await client.query(
    'INSERT INTO users (name, email, age) VALUES ($1, $2, $3)',
    ['Alice', 'alice@example.com', 30]
  );

  // JOIN across tables — SQL strength
  const result = await client.query(`
    SELECT u.name, COUNT(o.id) AS order_count, SUM(o.total) AS lifetime_value
    FROM users u
    JOIN orders o ON u.id = o.user_id
    WHERE u.age > 25
    GROUP BY u.id, u.name
    ORDER BY lifetime_value DESC
    LIMIT 10
  `);
  console.log('Top customers by lifetime value:', result.rows);
  await client.end();
}

// ── MongoDB (NoSQL) example ───────────────────────────────────
const { MongoClient } = require('mongodb');

async function nosqlExample() {
  const client = new MongoClient('mongodb://localhost:27017');
  await client.connect();
  const db = client.db('mydb');

  // Flexible schema — each document can have different fields
  await db.collection('products').insertMany([
    { name: 'Laptop', category: 'Electronics', specs: { ram: '16GB', storage: '512GB' }, tags: ['sale'] },
    { name: 'T-Shirt', category: 'Clothing', sizes: ['S', 'M', 'L'], color: 'blue' },
    // ↑ Different fields per document — perfect for product catalogs

Architecture patterns

Microservices and the API gateway

Monolith vs microservices

A monolith puts all functionality in one backend process. A microservice architecture splits the system into independent services by domain (User Service, Order Service, Payment Service). Each service has its own database, can use its own tech stack, deploys independently, and fails in isolation.

Most startups begin with a monolith (simpler to build, test, and deploy) and migrate to microservices as the team and scale grow. The trigger is usually team size: when one team per domain makes organizational sense, microservices follow naturally.

API gateway

Clients send all requests to a single API gateway endpoint, which routes to the correct microservice. The gateway also handles cross-cutting concerns: rate limiting, caching, authentication and authorisation. This keeps individual services lean and prevents each one from reimplementing the same middleware.

Traffic distribution

Load balancer algorithms

  • Round robin: Rotate requests sequentially (Server 1 → 2 → 3 → 1…). Simple, assumes equal capacity. Ignores real-time server health.
  • Weighted round robin: Servers assigned static weights proportional to capacity. Higher-weight servers receive more requests. Doesn't adapt to live load.
  • Least connections: Routes to whichever server has the fewest active connections right now. Dynamically adapts to real traffic. Best for mixed request durations.
  • Hash-based: Hashes the client IP or user ID to determine server. Guarantees session persistence (same user → same server). Disrupted when servers are added or removed.
Performance

Caching and Redis

Caching stores precomputed or frequently accessed data in high-speed storage so future requests skip the expensive DB query. A query taking 600ms (500ms DB + 100ms compute) served from Redis takes ~60ms — a 10× improvement.

Where to cache

  • Client-side: Browser cache (HTML, CSS, JS assets).
  • Server-side: Redis or Memcached in server memory.
  • CDN: Geographically distributed edge caches (CloudFront, Cloudflare).
  • Application-level: In-process query result caching.

Cache invalidation

Stale data must be evicted or updated. Two main strategies:

  • TTL (Time to Live): Data auto-expires after a set duration.
  • Write-through: Update cache simultaneously when the database is written.

Redis fundamentals

Redis is an in-memory key-value store. Because data lives in RAM, reads are orders of magnitude faster than disk-based databases — but storage is limited by RAM size. Key Redis data types:

  • String: SET user:1 "Alice" / GET user:1
  • List: LPUSH + RPOP = queue (FIFO); LPUSH + LPOP = stack (LIFO)
  • Hash: Store object fields under one key (e.g., user:1:email)

A cache hit means the data was found in cache and served immediately. A cache miss means it wasn't — the system falls back to the database, then usually populates the cache for next time.

Static and media content

Blob storage and CDNs

Blob storage (AWS S3, Cloudflare R2)

A blob (Binary Large Object) is any file — video, image, PDF — stored as raw binary. Files don't belong in relational databases: a single video can be 1GB+, which makes queries painfully slow. Dedicated blob stores auto-scale, offer 11-nines (99.999999999%) durability, pay-as-you-go pricing, encryption at rest and in transit, and fine-grained access control via pre-signed URLs or IAM policies.

CDN (CloudFront, Cloudflare)

Files stored in one region are slow to serve globally because of physical distance. A CDN caches content on edge servers distributed worldwide.

  1. User requests a file → GeoDNS routes to nearest edge server.
  2. Cache hit: edge server returns file immediately.
  3. Cache miss: edge fetches from origin, caches it, serves the user. Future requests hit cache.

TTL controls how long edge servers hold content before refreshing from origin. CDNs are the primary tool for making static assets (images, JS, CSS) fast globally.

Async communication

Message brokers, Kafka, and event-driven architecture

Synchronous vs asynchronous

In synchronous communication, the client waits for the server to fully process the request before getting a response. For long-running tasks (video transcoding, email sending, PDF generation) this means the client hangs for seconds or minutes.

In asynchronous communication, the server immediately returns "task accepted" and a background worker handles the heavy work. The client is notified later (webhook, email, WebSocket push).

Message queue vs message stream

  • Message queue (RabbitMQ, AWS SQS): one consumer per message type. Message is deleted once processed. Best for task delegation with one worker type.
  • Message stream (Kafka, AWS Kinesis): many consumers can read the same message. Messages persist and are never auto-deleted. Best for "write once, read by many" use cases like analytics, audit logs, and data pipelines.

Apache Kafka internals

Kafka is the standard for high-throughput message streaming. Key terms:

  • Topic: A named category of messages (like a database table).
  • Partition: A topic split into parallel lanes for horizontal throughput.
  • Consumer group: A set of consumers that collectively process a topic. Each partition is owned by exactly one consumer within a group.
  • Producer: Publishes messages. Broker: Kafka server managing topics.

Rule: for horizontal consumer scaling, partitions ≥ consumers. Kafka auto-rebalances assignments when consumers are added or removed. Example: 4 partitions + 3 consumers → one consumer handles two partitions, the others handle one each.

Practical use case: Uber driver location updates every 2 seconds × thousands of drivers. Writing each update directly to the database would overwhelm it. Buffer in Kafka, batch-write to DB every 10 minutes.

Event-driven architecture (EDA)

Non-critical downstream tasks (inventory update, email notification) shouldn't block the response to the user. EDA pattern:

  1. Order placed → Order Service confirms payment → immediately returns success to client.
  2. Order Service publishes an event to the message broker.
  3. Inventory Service and Notification Service consume the event asynchronously at their own pace.

EDA benefits: services are fully decoupled (producer doesn't know about consumers), one service failure doesn't cascade, each service scales independently.

Distributed systems

Leader election and auto-recovery

A distributed system has work performed by multiple cooperating machines that appear as one system to the client. Sharding, horizontal scaling, and big data computation are all forms of distributed execution.

Leader + follower architecture

A common pattern: one leader accepts client requests and coordinates work; followers execute tasks and return results. The leader aggregates and responds. Leader election runs at startup and on leader failure.

Leader election algorithms

  • Bully: O(N) — the highest-ID live node wins.
  • Gossip protocol: O(log N) — nodes exchange heartbeats to propagate state changes. Used by DynamoDB and Cassandra.
  • Raft: Consensus algorithm requiring 50%+ nodes to agree on a leader. Used by Docker Swarm and etcd.

Auto-recoverable orchestrator hierarchy

Manually restarting crashed servers doesn't scale. The solution is a hierarchy:

  • Worker-Orchestrators monitor application servers and restart them on crash.
  • Leader-Orchestrator monitors worker-orchestrators and restarts them.
  • If the leader-orchestrator fails, a worker promotes itself via leader election.

The entire recovery chain is automated — no human intervention required at any level.

Data consistency

Strong consistency vs eventual consistency

Strong consistency

Every read after a write returns the most recent data — all replicas agree before the write is acknowledged. Behaves as if a single copy of data exists. Implementation approaches:

  • Synchronous replication: All replicas updated before write acknowledged (Google Spanner).
  • Quorum-based (W+R > N): Majority acknowledgment required (DynamoDB, Cassandra configurable).
  • Raft consensus: 50%+ nodes must agree (Docker Swarm, etcd).

Use when: banking, payments, stock trading — stale reads are unacceptable.

Eventual consistency

All replicas will eventually converge to the same value, but short-term inconsistency is acceptable in exchange for higher availability and lower write latency. Implementation: async replication, relaxed quorum (R+W ≤ N), gossip protocol. Use when: social media likes/comments, product catalogs, DNS records.

Routing strategy

Consistent hashing

Simple hashing (HASH(key) % num_servers) has a fatal flaw: when you add or remove a server, nearly every key remaps to a different server — causing massive data movement and cache invalidation.

Consistent hashing solves this with a circular ring:

  1. Hash each server's identity (IP or ID) onto a point on the ring.
  2. Hash each data key onto the same ring using the same function.
  3. Each key is assigned to its nearest clockwise server on the ring.

When a server is added or removed, only the keys immediately adjacent to that position need to reassign — all other keys are unaffected. Used by AWS DynamoDB, Apache Cassandra, and Riak.

Network intermediaries

Forward proxy vs reverse proxy

Forward proxy — acts on behalf of the client

The server sees the proxy's IP, not the client's. The client's identity is hidden. Use cases: VPNs, accessing geo-blocked content, corporate internet filtering, caching frequently requested content organisation-wide.

Reverse proxy — acts on behalf of the server

The client sees the proxy, not the actual backend servers. The server's identity is hidden. Use cases: load balancing, SSL termination (handles encryption so backend servers don't have to), caching static content, shielding backend services from direct internet exposure.

In production, Nginx and HAProxy are the standard reverse proxy tools. They are far more efficient than a hand-rolled Node.js proxy — with built-in SSL support, connection pooling, rate limiting, and caching.

Reliability

Data redundancy and recovery

Physical disasters (floods, fires), disk corruption, and hardware failures are inevitable at scale. Two approaches:

  • Periodic backup: Daily or weekly snapshots. Simple, but you lose everything that happened since the last snapshot.
  • Continuous redundancy (modern standard): A live replica server syncs all writes from the main database in real time (synchronously or asynchronously). On main failure, the replica auto-promotes to main. Zero manual intervention.

The replica only syncs — it doesn't serve client reads (that's what read replicas are for in a master-slave setup). Its sole job is to be a warm standby.

Interview framework

How to solve any system design problem in 3 steps

Step 1 — Understand the problem

Clarify functional requirements (what the system does) and non-functional requirements (scale, latency, consistency, availability). Don't design before you know the constraints.

Step 2 — Break into sub-problems

Decompose by domain. For an e-commerce system: Product Listing, Search, Orders, Payments. Resist the urge to solve the whole thing at once.

Step 3 — Address 4 dimensions for each sub-problem

  • Database: SQL or NoSQL? Which specific DB? Schema design?
  • Caching: What to cache? TTL? Invalidation strategy?
  • Scaling & fault tolerance: Horizontal or vertical? Replication strategy?
  • Communication: Synchronous REST API or asynchronous message broker?

The trap: Only create sub-sub-problems when genuinely necessary. Over-engineering in an interview signals unclear thinking, not depth.

Common questions

FAQ

  • Do I need to know all of this before I start building real systems?

    No. Know the basics (servers, scaling, caching, databases) and learn the rest when a real problem demands it. Most teams don't need Kafka or Raft until they're processing millions of events per second. Build, hit the wall, then reach for the next tool.

  • When should I use NoSQL instead of PostgreSQL?

    When your schema is genuinely unpredictable, your write throughput exceeds what a single Postgres master can handle, or you need built-in horizontal sharding. For most applications, Postgres with read replicas and proper indexing handles far more than engineers expect.

  • What's the difference between partitioning and sharding?

    Partitioning splits a table into sub-tables on the same server — the database engine handles routing transparently. Sharding splits data across different servers — your application code must know which shard to route each query to. Partitioning is simpler; sharding is more powerful but far more complex to operate.

  • Should I start with microservices or a monolith?

    Almost always start with a monolith. Microservices solve organisational and scaling problems that don't exist at the beginning. Premature microservices add distributed systems complexity (network calls, partial failures, data consistency) before you have the team size or traffic that justifies it.

70+ System Design Terms Every Beginner Should Know

The vocabulary of system design is the prerequisite for everything else. Interviewers at every level — even for junior roles — expect fluency with these terms. This glossary covers every term you will encounter in an interview, organized by concept area.

Group A: Fundamentals

Latency
Time elapsed from when a client sends a request to when it receives the first byte of the response. P99 latency (99th percentile) matters more than average — if P99 is 2 seconds, 1 in every 100 users waits 2+ seconds on every request. Interviewers always ask: "What latency SLA do you need?" before you start designing.
Throughput
The number of requests or volume of data a system processes per unit of time (req/s, MB/s). A system with low latency but low throughput is like a fast but narrow highway — it handles one car quickly but can't handle 10,000 simultaneously. Distinguish throughput (actual rate achieved) from bandwidth (theoretical maximum capacity).
Availability
The percentage of time a system is operational and responsive. "Five nines" (99.999%) = approximately 5 minutes of downtime per year. Formula: availability = uptime / (uptime + downtime). Achieved through redundancy (multiple servers), automatic failover, and health checks that route around failures. Interviewers often ask you to state a target availability and then design to meet it.
Reliability
A system behaves correctly — returns accurate results — even when some of its components fail. Availability is a subset of reliability: a system can be available (responding to requests) but unreliable (returning wrong data). A reliable system validates inputs, handles partial failures gracefully, and never silently corrupts data.
Scalability
The ability to handle increasing load without degrading performance proportionally. Vertical scaling: add more CPU/RAM to an existing machine. Horizontal scaling: add more machines. The interview test: "how does your design behave at 10× current load?" A scalable design identifies which component becomes the bottleneck first and has a plan for it.
Fault Tolerance
The system continues operating — possibly in a degraded mode — when one or more components fail. Achieved via replication (multiple copies of data), redundancy (multiple instances of services), and graceful degradation (return cached results instead of failing entirely). Different from reliability: a fault-tolerant system expects failures and handles them; a brittle system fails catastrophically at the first component failure.

Group B: Networking and APIs

DNS (Domain Name System)
The distributed system that translates human-readable domain names (google.com) into IP addresses (142.250.80.46). Works like a hierarchical phone book. DNS lookup adds 1–100ms on first visit; cached by the OS and browser after that. TTL (Time To Live) controls how long the cache is valid. DNS is the first component in every system design interview: clients resolve the service's domain before they can connect.
TCP vs UDP
TCP (Transmission Control Protocol): reliable, ordered, connection-oriented. Guarantees delivery and ordering via acknowledgements and retransmissions. Used for: web (HTTP), email, databases. UDP (User Datagram Protocol): fast, unreliable, connectionless. Sends packets and doesn't check if they arrived. Used for: video streaming, gaming, DNS. TCP overhead adds ~1.5× latency vs UDP for the reliability guarantee.
HTTP/HTTPS
The stateless request-response protocol that powers the web. Every request is independent — the server holds no session memory between requests. HTTPS adds TLS encryption. HTTP/2 multiplexes multiple requests over a single TCP connection, solving the "head-of-line blocking" problem of HTTP/1.1. HTTP/3 uses QUIC (UDP-based) for lower latency on lossy connections.
REST (Representational State Transfer)
An architectural style for HTTP APIs using standard verbs (GET = read, POST = create, PUT = update, DELETE = remove) applied to resource URLs (/orders/123). Stateless: every request contains all context needed; no server-side session. Contrast with GraphQL (client specifies exact data shape in a query, avoiding over- and under-fetching) and gRPC (binary protocol, typed contracts, supports streaming — preferred for microservice-to-microservice communication).
WebSocket
A full-duplex communication channel over a single persistent TCP connection. The client sends an HTTP Upgrade request; the server switches protocols. Both sides can send data at any time without the overhead of a new HTTP request per message. Used for: real-time chat, live dashboards, gaming, collaborative editing. Contrast with HTTP long-polling (client holds a request open until the server has data) and SSE (server pushes events, client can't send back).
API Gateway
A single entry point that receives all client requests and routes them to the appropriate backend service. Handles cross-cutting concerns: authentication, rate limiting, SSL termination, request logging, and response caching. Examples: AWS API Gateway, Kong, Nginx. Prevents every microservice from re-implementing auth and rate limiting independently. The tradeoff: a single API Gateway can become a bottleneck and a single point of failure — run multiple instances behind a load balancer.

Group C: Caching

Cache
A fast-access store of precomputed or frequently read data sitting between the client and the primary data source. Cache hit: data found in the cache — fast (<1ms for Redis). Cache miss: must fetch from origin — slow (10–100ms for a DB query). Hit rate = hits / total requests; aim for >90% in production. A cache with 80% hit rate reduces DB load by 5×.
Cache-Aside (Lazy Loading)
The most common caching pattern. On read: check cache first; on miss, fetch from DB and write to cache. On write: update DB and invalidate (or update) the cache entry. The application code manages the cache explicitly. Risk: thundering herd — many concurrent misses on the same key all hit the DB simultaneously. Mitigation: mutex lock on the cache key during population, or probabilistic early expiry.
Write-Through Cache
Every write goes to the cache AND the database synchronously before the write completes. The cache is always in sync with the database — no stale reads after a write. Drawback: writes are slower (must wait for both cache and DB to acknowledge). Best for read-heavy workloads where stale data is unacceptable.
Write-Behind (Write-Back) Cache
Writes go to the cache immediately; a background process flushes them to the database asynchronously. Fastest write path — the caller doesn't wait for the DB. Risk: data loss if the cache node fails before the background flush completes. Use only when occasional data loss is acceptable (e.g., view counts, non-critical metrics).
TTL (Time To Live)
The duration after which a cached entry is considered expired and must be re-fetched from the origin. Short TTL = fresher data but lower hit rate (more origin requests). Long TTL = higher hit rate but potentially stale data. Add random jitter (±10–20% of TTL) to prevent simultaneous expiry of many keys (the thundering herd problem).
Cache Eviction Policy
The algorithm a cache uses to decide which entries to remove when it reaches capacity. LRU (Least Recently Used): remove the entry not accessed for the longest time — assumes recently accessed items will be accessed again soon. LFU (Least Frequently Used): remove the entry accessed the fewest times — better for stable hot-key workloads. Most production caches (Redis, Memcached) default to LRU or a variant.
CDN (Content Delivery Network)
A geographically distributed network of servers (edge nodes) that cache and serve static content (images, JS, CSS, video segments) from the node closest to the user. Reduces latency (content is served from 10ms away instead of 100ms) and reduces load on the origin server. Examples: Cloudflare, AWS CloudFront, Akamai, Fastly. Cache invalidation on content change: use versioned URLs (content hash in filename) so old and new versions can coexist during rollout.

Group D: Databases

SQL vs NoSQL
SQL (relational): fixed schema, tables with rows and columns, ACID transactions, powerful JOINs. Best for: transactional data, complex queries, strict consistency. NoSQL: flexible schema (documents, key-value, graph, time-series), scales horizontally more easily, often sacrifices some ACID properties for throughput. Neither is universally better — choose based on data shape, query patterns, and consistency needs.
ACID Transactions
Atomicity (all operations in a transaction succeed or all are rolled back), Consistency (the database remains in a valid state before and after), Isolation (concurrent transactions don't interfere with each other), Durability (committed data survives crashes). SQL databases provide ACID by default. Many NoSQL databases sacrifice isolation and consistency for higher write throughput and horizontal scale.
Index
A data structure that maintains a sorted reference to one or more columns, enabling fast lookups without scanning every row. B-tree index (the default in PostgreSQL, MySQL): efficient for equality and range queries. Hash index: fastest for equality only. Too many indexes slow down writes (each write must update all indexes). Rule of thumb: index columns that appear in WHERE, JOIN, or ORDER BY clauses of slow queries.
Sharding (Horizontal Partitioning)
Splitting a large database table across multiple database servers, distributing rows by a "shard key." All rows with the same shard key value live on the same shard. Good shard key: high cardinality, even write distribution (user_id works well). Bad shard key: low cardinality or monotonically increasing (timestamps — all new writes go to the last shard). A bad shard key creates a "hot shard" that becomes the bottleneck.
Replication
Maintaining copies of data on multiple servers for fault tolerance and read scale. Primary-replica (leader-follower): all writes go to the primary; replicas asynchronously copy changes. Reads can be served from any replica. Replication lag: replicas may be milliseconds to seconds behind the primary — reading from a replica immediately after writing to the primary may return stale data ("read-your-own-writes" violation).
CAP Theorem
A distributed data store can guarantee at most two of: Consistency (every read reflects the most recent write), Availability (every request gets a non-error response), and Partition Tolerance (the system continues working when network partitions split nodes). In practice, partition tolerance is required in any real distributed system — so you choose CP (consistent but may refuse requests during a partition, e.g., HBase) or AP (always available but may return stale data during a partition, e.g., Cassandra, DynamoDB).
OLTP vs OLAP
OLTP (Online Transaction Processing): row-oriented storage, optimized for frequent small reads/writes (banking transactions, order creation, user authentication). OLAP (Online Analytical Processing): column-oriented storage (Parquet, ORC), optimized for scanning large amounts of data for aggregations (reports, dashboards, ML feature generation). Never use the same database for both at scale — they have opposite storage and query optimization requirements.

Group E: Distributed Systems

Consistent Hashing
A technique for distributing data or requests across servers such that adding or removing a server only remaps ~1/N of keys (instead of all of them). Servers are placed on a virtual ring by hashing their IDs; each key is assigned to the nearest server clockwise on the ring. Virtual nodes (vnodes) give each physical server multiple positions on the ring for even load distribution. Used in: distributed caches (Redis Cluster), CDN routing, database sharding (Cassandra, DynamoDB).
Leader Election
The process by which distributed nodes agree on one node to act as the "leader" (primary) that handles writes or coordinates work; all other nodes are followers that replicate. Algorithms: Raft (understandable, widely used), Paxos (more general, harder to implement), ZooKeeper's ZAB. Critical property: exactly one leader at any time — split brain (two nodes both believe they are leader) causes data inconsistency.
Consensus
Agreement among distributed nodes on a single value, even when some nodes fail or messages are delayed. Required for: leader election, distributed transactions, and replicated state machines. Both Raft and Paxos require a quorum (majority: N/2 + 1 nodes) to agree before committing. A cluster of 3 nodes can tolerate 1 failure; 5 nodes can tolerate 2 failures.
Eventual Consistency
In an AP distributed system, all replicas will converge to the same value given sufficient time and no new updates — but reads during the convergence window may return stale data. DNS is the canonical example (a DNS record change takes minutes to propagate globally). Appropriate for: shopping carts, social media feeds, user profiles, likes/view counts. Not appropriate for: bank balances, inventory levels, appointment booking.
Idempotency
An operation that produces the same result whether performed once or N times. Critical for retry safety — if a payment API call times out (did it go through?), retrying must not double-charge. Implemented via idempotency keys: the client generates a unique key per operation and includes it in the request; the server persists the key + result and returns the stored result on duplicates. GET requests are inherently idempotent; POST requests are not unless explicitly designed to be.
Exactly-Once Delivery
A guarantee that a message is processed exactly once — neither dropped (at-most-once) nor processed multiple times (at-least-once). Extremely hard to achieve in distributed systems because network failures make it impossible to distinguish "message not delivered" from "message delivered but ack lost." The practical solution: at-least-once delivery (guaranteed delivery, possible duplicates) + idempotent message processing (duplicates are safe). Kafka's transactional producers provide this combination.

Group F: Load Balancing and Scaling

Load Balancer
Distributes incoming requests across multiple server instances to prevent any single server from being overwhelmed. Layer 4 (transport-level): routes by TCP/UDP port — fast but cannot inspect request content. Layer 7 (application-level): routes by URL path, HTTP headers, or cookies — enables smart routing (e.g., send /api to API servers, /static to CDN). Algorithms: round-robin (equal distribution), least-connections (route to the least-loaded server), IP hash (same client always reaches the same server — "sticky sessions").
Horizontal Scaling (Scale Out)
Adding more server instances to handle more load. Each instance handles a share of the traffic. Preferred for stateless services (web servers, API servers, worker processes) — any instance can handle any request. Challenge: stateful services (databases, caches with session data) require careful coordination when adding instances because data must be redistributed.
Vertical Scaling (Scale Up)
Adding more CPU, RAM, or storage to an existing server. Simpler operationally (no distributed complexity) but has a hard ceiling (the largest available machine) and creates a single point of failure. Suitable for: databases where horizontal scaling is complex, legacy applications that cannot run on multiple instances. The tradeoff: vertical scaling is bounded; horizontal scaling is not.
Auto-Scaling
Automatically adding or removing server instances based on real-time load metrics (CPU utilization, request rate, queue depth). AWS Auto Scaling Groups, GCP Managed Instance Groups. Key configuration: scale-out threshold (e.g., add instance when CPU >70% for 3 minutes), scale-in threshold (remove instance when CPU <30% for 10 minutes), cooldown period (wait 5 minutes after scaling before scaling again — prevents thrashing).
Stateless vs Stateful Services
Stateless: each request is fully self-contained; any server instance can handle it (REST API servers, web servers). Stateful: the server holds per-client state between requests (WebSocket connections, gaming servers, streaming sessions). Stateless services are trivially horizontally scalable — add more instances, route requests to any of them. Stateful services require sticky routing (same client always reaches the same instance) or externalized state (move state to Redis so any instance can access it).
Reverse Proxy
A server that sits in front of application servers and forwards incoming requests to them. Handles: SSL termination (decrypts HTTPS, forwards HTTP internally), compression, caching of static responses, and load balancing. Nginx and Caddy are the most common. Contrast with a forward proxy (sits in front of clients, not servers — used for corporate internet filtering or anonymization).

Group G: Messaging and Events

Message Queue
An asynchronous buffer between services. The producer writes messages to the queue without waiting for processing; the consumer reads and processes messages independently at its own pace. Decouples services — the producer doesn't need to know which service will consume its messages. Examples: RabbitMQ, Amazon SQS. Key properties: durability (messages persist across broker restarts), ordering (FIFO or priority), delivery guarantee (at-least-once: consumer must ack; at-most-once: no ack).
Pub/Sub (Publish-Subscribe)
A messaging pattern where publishers send events to named "topics" and all subscribers to that topic receive a copy. One-to-many fan-out: one "order placed" event simultaneously reaches the inventory service, billing service, and email service. Contrast with point-to-point queues where each message is consumed by exactly one consumer. Google Pub/Sub and Kafka support pub/sub patterns.
Event Streaming
A persistent, replayable, ordered log of events that consumers can read at their own pace from any offset. Kafka is the canonical example. Unlike message queues (message is deleted after consumption), event streams retain messages for a configurable period (days to weeks). A new consumer can replay from the beginning of the log — useful for rebuilding derived data stores or replaying events after a bug fix.
Dead Letter Queue (DLQ)
A secondary queue that receives messages that have failed processing after N retry attempts. Prevents a single bad message from blocking the entire queue forever (a "poison pill"). Production must-have: monitor DLQ message count — a spike indicates a systematic processing failure. DLQ messages should be inspected, the root cause fixed, and then re-processed.

Group H: Reliability Patterns

Circuit Breaker
A pattern that stops sending requests to a failing downstream service, preventing cascade failures. States: CLOSED (normal operation), OPEN (downstream failing — reject all requests immediately with an error), HALF-OPEN (test: send one request; if it succeeds, close the circuit). Without a circuit breaker, every thread waits for the failing service to timeout, exhausting your thread pool and taking down your own service. Netflix Hystrix popularized this pattern; Resilience4j is the modern Java alternative.
Rate Limiting
Controls the number of requests a client can make in a given time window. Algorithms: token bucket (tokens accumulate up to a maximum; each request consumes one token — allows controlled bursts), leaky bucket (requests are processed at a fixed rate — smooths output but queues bursts), sliding window counter (counts requests in the last N seconds — accurate, implements well in Redis with INCR + EXPIRE). Protects against: DoS attacks, abusive clients, and accidental retry storms from your own services.
Retry with Exponential Backoff
On failure, wait before retrying; double the wait on each attempt (1s → 2s → 4s → 8s). Prevents retry storms where all clients retry simultaneously, amplifying load on a struggling service. Add jitter (random ±50% of wait time) to desynchronize retries from different clients. Always set a maximum retry count — infinite retries can accidentally DDoS your own downstream service.
Bulkhead
Isolate components into separate resource pools (thread pools, connection pools, memory) so one failing component cannot exhaust resources for all others. Named after the watertight compartments in a ship's hull. Example: Netflix's Hystrix gave each downstream service its own thread pool — if the recommendations service was slow, it could not consume the threads reserved for the payment service.
Timeout
The maximum time to wait for a response before treating the request as failed. Always set timeouts on all network calls — a thread waiting indefinitely for a response is a hung thread that never releases its resources, eventually exhausting the thread pool. Set separate timeouts for connection establishment (typically 1–3s) and read completion (depends on operation — typically 5–30s). Combine with retries and circuit breaker for full resilience.
Health Check
A lightweight HTTP endpoint (GET /health or GET /readyz) that load balancers and orchestrators call periodically to verify an instance is alive and ready for traffic. Liveness probe: is the process alive and not deadlocked? Returns 200 if yes, triggers a restart if consistently failing. Readiness probe: is the service ready to accept requests? (DB connection established, warmup complete.) Load balancer removes an instance from rotation until readiness probe passes.

Group I: Storage

Object Storage
Stores unstructured data (files, images, videos, backups) as discrete objects with metadata, addressable by a unique key. Infinitely scalable — no hierarchy (flat namespace, though key prefixes simulate directories). Examples: Amazon S3, Google Cloud Storage. Not suitable for transactional data or frequent byte-range updates. Access latency: tens of milliseconds — slower than block storage but orders of magnitude cheaper per GB.
Block Storage
Raw storage divided into fixed-size blocks (typically 4KB–512KB), addressable by block number. Fast random read/write — databases use block storage because they need to update 4KB pages within large files without rewriting the whole file. Examples: AWS EBS, Google Persistent Disk. Attached to a single VM at a time (unlike object storage, which is shared).
File Storage (NFS/EFS)
A shared filesystem accessible by multiple servers simultaneously via NFS or SMB protocols. Presents a familiar directory tree. Suitable for: legacy applications that expect a filesystem, shared assets that multiple processes need to read/write. Slower than block storage for database workloads. Examples: AWS EFS, Azure Files.
Data Partitioning
Dividing a large dataset into smaller independent subsets stored on separate storage nodes. Vertical partitioning: split columns across tables (e.g., rarely-used large columns in a separate table). Horizontal partitioning (sharding): distribute rows across servers by a key. Done to exceed single-node storage capacity or processing throughput. The partition key choice determines whether queries can be efficiently routed to a single partition (fast) or must fan out to all partitions (slow).

Group J: Security

Authentication vs Authorization
Authentication (AuthN): verifying identity — "who are you?" (login, token validation). Authorization (AuthZ): verifying permissions — "what are you allowed to do?" (role checks, access control lists). Always authenticate before authorizing. OAuth 2.0 is an authorization framework; OpenID Connect (OIDC) adds identity (authentication) on top of OAuth 2.0. Confusing the two is a security design flaw.
JWT (JSON Web Token)
A compact, URL-safe token containing claims (user_id, roles, expiry timestamp) signed with a secret key (HMAC) or private key (RSA/ECDSA). The server validates the signature without a database lookup — enabling stateless, horizontally scalable authentication. Risk: JWTs cannot be revoked before their expiry time without a token blocklist (which reintroduces the database lookup). Keep JWT lifetime short (15–60 minutes); use refresh tokens for longer sessions.
TLS (Transport Layer Security)
The cryptographic protocol providing encrypted and authenticated communication over TCP — "the S in HTTPS." TLS 1.3 is the current standard. Terminates at the load balancer or application server; traffic within the data center may be unencrypted unless you implement mTLS (mutual TLS — both sides authenticate). Always use TLS 1.2+; TLS 1.0 and 1.1 have known vulnerabilities and should be disabled.
SQL Injection
An attack where malicious SQL code is injected into a query through unsanitized user input. Example: SELECT * FROM users WHERE name = '" + userInput + "'" — if userInput is '; DROP TABLE users; --, the database executes a table drop. Prevention: always use parameterized queries or prepared statements — never concatenate user input into SQL strings. SQL injection is one of the oldest vulnerabilities and still appears regularly in production systems.

Group K: Monitoring and Observability

Metrics
Numerical time-series measurements that quantify system health: request rate (req/s), error rate (%), latency percentiles (P50, P95, P99), CPU utilization, memory usage, queue depth. Stored in time-series databases (Prometheus, Datadog). Metrics enable alerting (page on-call when error rate exceeds 1% for 5 minutes) and dashboards for trend analysis.
Logs
Timestamped textual records of individual events. Structured logs (JSON format) are machine-searchable; unstructured text logs are not. Aggregated in ELK stack (Elasticsearch + Logstash + Kibana) or Splunk. Log levels: DEBUG (verbose development output), INFO (normal operations), WARN (unexpected but recoverable), ERROR (failure requiring attention), FATAL (process must exit). Never log PII or secrets.
Distributed Tracing
Tracks a single user request as it flows through multiple microservices. Each service creates a "span" recording the operation name, start/end time, and parent span ID; all spans from one request form a tree called a "trace." Implemented with OpenTelemetry + Jaeger or Zipkin. Answers "why is this specific request slow across 8 services?" — a question that aggregate metrics cannot answer.
SLI / SLO / SLA
SLI (Service Level Indicator): a measured metric quantifying reliability (e.g., request success rate = 99.7%). SLO (Service Level Objective): the internal target (e.g., success rate ≥ 99.9%). Error budget = 100% − SLO = 0.1% of requests may fail. SLA (Service Level Agreement): the contractual commitment to customers with financial penalties for breach. Design systems to meet SLOs with sufficient margin to avoid breaching SLAs.

Group L: Advanced Concepts

Microservices
An architectural style where an application is decomposed into small, independently deployable services, each owning its own data store. Benefits: independent deployment (update one service without touching others), independent scaling, and failure isolation (one service crash doesn't bring down the monolith). Costs: distributed systems complexity — network latency between services, partial failure scenarios, distributed transactions across services.
Service Mesh
An infrastructure layer that handles all service-to-service communication transparently, without requiring changes to application code. Capabilities: mTLS between services, automatic retries, circuit breaking, load balancing, and observability. Implemented with sidecar proxies (Envoy) injected alongside every service pod. Istio and Linkerd are the main implementations. Tradeoff: significant operational complexity and resource overhead — only justified at organizations running dozens or hundreds of microservices.
Backpressure
A mechanism for a consumer to signal to a producer to slow down when the consumer cannot keep up. Without backpressure, a fast producer overwhelms a slow consumer — memory overflows, messages are dropped, or the consumer crashes. Implementations: bounded queues (producer blocks when queue is full), reactive streams protocols (consumer explicitly requests N more items from producer). Critical in stream processing pipelines where ingestion rate can spike unpredictably.
Fan-Out
One event or request triggers parallel work in multiple downstream systems. Example: one "user followed" event triggers: notification service, feed ranking service, and analytics service simultaneously. Fan-out-on-write: when an event occurs, proactively write derived data to all subscribers' stores (fast reads, slow writes at scale for celebrities with millions of followers). Fan-out-on-read: compute derived data at query time (slow reads, simple writes). Hybrid: use write fan-out for regular users, read fan-out for celebrities.
Saga Pattern
A pattern for managing distributed transactions across multiple services without two-phase commit (2PC). Each step in the saga has a compensating transaction (rollback action). If step N fails, steps N-1 through 1 are compensated in reverse order. Two variants: orchestration saga (one central orchestrator calls each step in order) and choreography saga (each service publishes an event that triggers the next service). Used for: order placement (reserve inventory → charge payment → confirm order; if payment fails → release inventory).
CQRS (Command Query Responsibility Segregation)
Separates the write model (commands that change state) from the read model (queries that return data). The write service accepts commands, validates them, and appends events to the event store. Read services maintain optimized view models updated asynchronously from those events. Enables: independent scaling of read and write paths, read models optimized for specific query patterns (e.g., a denormalized "user dashboard" view model). Adds eventual consistency between write and read. Justified only when read and write workloads have drastically different shapes.
Back-of-Envelope Estimation
Quick order-of-magnitude calculations to validate the feasibility of a design before committing to it. Example: "10M daily active users × 5 messages/day × 500 bytes/message = 25 GB/day of writes = ~300 KB/s write throughput — easily handled by a single Kafka partition." Interviewers test whether you can sanity-check your own design. Key numbers to memorize: 1M req/day ≈ 12 req/s; SSD: ~100K IOPS; network within datacenter: ~0.5ms round-trip; 1 Gbps ≈ 125 MB/s.
Heartbeat
A periodic signal a node sends to indicate it is alive. If no heartbeat arrives within a timeout window (e.g., 30 seconds), the coordinator considers the node dead and reassigns its responsibilities. Used in: Kafka broker registration with the controller, Kubernetes kubelet reporting to the control plane, ZooKeeper session maintenance. The heartbeat interval and timeout must be tuned carefully — too short causes false failures during GC pauses; too long causes slow failure detection.
Gossip Protocol
A decentralized peer-to-peer protocol where each node periodically selects a few random peers and exchanges state information. Like a rumor spreading through a social network — it reaches all nodes in O(log N) communication rounds, even if any individual node is unreachable. Used for: cluster membership tracking (who is up?), failure detection, and configuration propagation. Examples: Cassandra, Consul, Amazon S3's internal metadata system. Eventual convergence makes gossip protocols AP (available + partition-tolerant) but not immediately consistent.
Two-Phase Commit (2PC)
A distributed protocol for atomic transactions spanning multiple nodes. Phase 1 (Prepare): a coordinator asks all participant nodes if they are ready to commit. Phase 2 (Commit/Abort): if all replied "yes," the coordinator sends Commit to all; if any replied "no" or timed out, sends Abort. Problems: the coordinator is a single point of failure; participants are blocked (holding locks) while waiting for Phase 2, which can be seconds during network partitions. Not used in modern large-scale systems — replaced by sagas and eventual consistency patterns.
Bloom Filter
A space-efficient probabilistic data structure for testing whether an element is a member of a set. False positives are possible (may say "in set" when it's not); false negatives are impossible (if it says "not in set," it's definitely not in the set). Uses ~10 bits per element to represent a set of 1 billion items in ~1.2 GB. Used in: Cassandra (avoid disk lookup for keys that definitely don't exist), Chrome Safe Browsing (check if a URL is in the malicious URL set without downloading the full list), HBase (skip SSTables that don't contain the requested key).

Key Takeaway

System design is not about memorising components — it's about understanding why each component exists, what problem it solves, and what trade-off it introduces. Start with a single server, understand why it breaks, add the right abstraction, and repeat. The engineer who can articulate the why behind every architectural decision is the one who makes it through the interview and ships systems that last.
