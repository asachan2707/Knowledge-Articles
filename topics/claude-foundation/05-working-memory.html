Working memory is the part of AI behaviour with the sharpest edge: whatever fits in the window is usable, and whatever doesn’t simply doesn’t exist for the model. Inside the window, position matters too.

Core idea: Context is finite and position-sensitive: put critical material at the edges, curate the middle, and re-supply what must persist.

Story · The instruction that vanished on page 11

A team pastes a 20-page policy into a prompt and asks a question whose answer lives on page 11. The assistant answers confidently from the first and last pages. Nothing errored and no warning appeared; the relevant paragraph simply carried less weight sitting in the middle. Later, in a long support chat, the assistant stops following a rule given at the start. Different symptom, same property.

Lesson 8

The context window is a fixed-size workspace

Everything the model attends to lives inside a fixed-size context window: your prompt, uploaded documents, the conversation so far. Content inside is accessible; content outside is not. Unlike the other properties, which fade gradually, this one has a cliff: things work until they don’t, and warnings are not guaranteed.

ZoneLooks like
CapabilityMaterial fits comfortably; session is current; relevant context is provided
LimitationVery long documents or chats; assuming continuity across sessions; key details buried mid-input
  • Typical failure: silent truncation of what no longer fits.
  • The model does not learn from your correction; it only reacts to what is currently in context. A new conversation starts from nothing.
  • Features that push the cliff out: memory, compaction, projects/workspaces, larger windows and multi-agent workflows.
  • 4D link: Working Memory is what Description acts on. It tells you how to structure context, when to put things first, and when to restart.

Using context as leverage

  • Put key material first.
  • Split big jobs into pieces.
  • Re-supply vital context rather than assuming it persists.
Lesson 9 · Try It Out

Context degradation: more context can make things worse

The interactive starts with you. You view a sequence of 15 words, one at a time for about 1.5 seconds each, then type what you can recall and see recall-by-position as a chart. The words in the middle vanish.

The U-shaped curve

That is the serial position effect, studied by psychologists for over a century: early items benefit from primacy (more rehearsal), late items from recency (still fresh), and the middle gets neither.

The lesson’s claim: language models show the same pattern. It cites a 2023 Stanford study (Liu et al., Lost in the Middle) in which accuracy was highest when a key fact sat at the very start or end of the context and dropped by more than 30% when it was in the middle, and attributes it to how transformer attention weights the edges of the window.

The two layouts

Dangerous patternSafer pattern
System prompt → chat 1 → chat 2 → … → key instruction buried here → … → chat 18 → latest messageSystem prompt → key instruction (up front) → chat 1 … chat 18 → latest message → key instruction (repeated)

The advice: put the most important instructions at the beginning and end; state must-follow constraints early in the system prompt and restate them near the end. Every extra piece of context pushes other content toward the middle dead zone, which is the core tension of context engineering: not just what to include, but where to put it and what to leave out.

Key takeaway from the page: more context ≠ better results. Attention is finite, so curate ruthlessly, place strategically and repeat what matters.

Code

Runnable context builder: curate the middle, protect both edges

This assembles a prompt with the must-follow rule at both edges and drops the oldest chat turns first when over budget. The token count is a rough 4-characters-per-token heuristic, not a real tokenizer — use your provider’s token-counting API in production.

JavaScript Example 
// Defend against "lost in the middle": curate, then place critical rules at BOTH edges.
const approxTokens = (s) => Math.ceil(s.length / 4); // rough heuristic: ~4 chars per token

function buildContext({ system, mustFollow, history, latest, budget = 2000 }) {
  // Curate: drop oldest turns first until we fit (edges are protected, the middle is expendable).
  const fixed = approxTokens(system) + 2 * approxTokens(mustFollow) + approxTokens(latest);
  const kept = [...history];
  let used = fixed + kept.reduce((n, m) => n + approxTokens(m), 0);
  while (used > budget && kept.length) used -= approxTokens(kept.shift());

  return [
    system,
    `IMPORTANT: ${mustFollow}`,           // front edge (primacy)
    ...kept,                               // the dead zone: keep it small
    latest,
    `REMINDER: ${mustFollow}`,            // back edge (recency)
  ].join('\n');
}

const history = Array.from({ length: 40 }, (_, i) => `turn ${i + 1}: ${'blah '.repeat(60)}`);
const ctx = buildContext({
  system: 'You are a support assistant.',
  mustFollow: 'Never promise refunds over $100.',
  history,
  latest: 'Customer: refund my $450 order!',
  budget: 800,
});
const lines = ctx.split('\n');
console.log('turns kept:', lines.filter((l) => l.startsWith('turn')).length, 'of', history.length);
console.log('first :', lines[1]);
console.log('last  :', lines.at(-1));
console.log('~tokens:', approxTokens(ctx));
Output (ran under Node.js)

last  : REMINDER: Never promise refunds over $100.

Architect's note

Engineering the cliff

  • Budget explicitly. Reserve tokens for the system prompt, tools, output and safety margin; treat the remainder as the only space for history and documents.
  • Compaction beats truncation. Summarise older turns (decisions, constraints, open questions) instead of dropping them, and pin invariants outside the summarised region.
  • Retrieve, don’t paste. Pull the few relevant chunks per question instead of the whole document; it improves cost, latency and mid-context recall.
  • Order matters. For multi-document prompts, put the question near the end and the most relevant documents at the edges; rerank retrieved chunks accordingly.
  • Long-context ≠ perfect recall. A larger window moves the cliff but does not remove position effects; test recall at your actual lengths with “needle” probes.
  • Persist state outside the window (files, memory features, project knowledge) for anything that must survive a restart.
Exercise

The before-and-after

Pick a task that depends on context only you have (a style guide, a past good example, audience constraints) and write 2–3 lines defining “good output”. Then:

  • Cold start vs context: run the bare request, then rerun it in a fresh conversation with your guide/example first; compare both against your definition of good.
  • Lost in the middle: bury one key instruction mid-document and ask something that hinges on it; then move it to the top.
  • Blank slate: teach it something, open a new conversation and ask as if it remembered; watch it start from nothing.
  • Follow-up: annotate your task list with which tasks need standing context.
  • Stretch: if your tool has memory or projects, set one up with Probe 1’s context and compare effort and quality.
FAQ

Frequently Asked Questions

Why would a larger context window not solve this?

It moves the cliff and raises the ceiling, but position effects, cost and latency still apply, and irrelevant content dilutes attention.

Does the model remember me between chats?

Not by itself. Persistent behaviour comes from memory features, projects or files that inject content into the next window.

Is “repeat the instruction at the end” wasteful?

It costs few tokens and exploits the recency edge; for hard constraints it is cheap insurance.

Key Takeaway

“Give it everything” is a trap. Curate what goes in, place the must-follow rules at the start and repeat them at the end, move durable context into memory or projects, and restart a drifting conversation rather than arguing with it.
