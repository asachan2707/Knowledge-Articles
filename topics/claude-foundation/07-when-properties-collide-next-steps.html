Real failures are collisions. Naming the two properties involved is the difference between a vague “AI is unreliable” and a specific, effective fix.

Core idea: Diagnose the pair, then apply the pair’s fix: verify, retrieve, re-supply, restate, offload, or invite pushback.

Story · One bad answer, two culprits

An assistant produces a beautifully formatted report citing a regulation, complete with a section number and a link, none of which exist. That is not “just hallucination”. The mechanism that invents plausible strings (next token prediction) met a topic where the model’s coverage was thin or stale (knowledge). A fix aimed at only one of them, say “be more careful”, does nothing; a fix aimed at the pair (retrieve the real text, then verify specifics) works.

Lesson 12

Most failures are two properties meeting

The four properties rarely act alone. The skill the lesson teaches is to name the pair, because the pair determines the fix.

Diagnosis is an act of Discernment: you judge output better when you know what kind of wrong it is.

Exercise: the failure diagnosis

  • Recall 2–3 times AI disappointed or surprised you; write what you asked, what you got and what was wrong.
  • Describe each to an AI and ask which properties were likely involved and why.
  • Evaluate the diagnosis yourself and push back if you disagree — remember the sycophancy pattern from Lesson 3.
  • For each, ask for the most targeted fix and test it on a similar task.
  • Revisit your Lesson 1 list with its accumulated annotations (property tags, verification scores, knowledge flags, context needs, goal statements) and name the colliding pair for the most troublesome tasks.
Code

Runnable failure diagnoser: symptoms → property pair → fix

A deliberately simple keyword-signal sketch of the “name the pair” habit. Real triage is a human judgement, but encoding it as a lookup table makes the logic explicit and testable for team runbooks.

JavaScript Example 
// "When properties collide": name the pair, then pick the targeted fix.
const PAIRS = [
  { needs: ['token', 'knowledge'], name: 'Next Token Prediction + Knowledge', symptom: 'hallucinated specifics (citations, dates, URLs)', fix: 'verify specifics; enable search/RAG with citations' },
  { needs: ['memory', 'steer'],    name: 'Working Memory + Steerability',   symptom: 'long-conversation drift',                       fix: 're-supply context; restate the goal; start a fresh session' },
  { needs: ['token', 'steer'],     name: 'Next Token Prediction + Steerability', symptom: 'confidently wrong math / brittle logic',  fix: 'offload to code execution; ask for visible reasoning' },
  { needs: ['character', 'steer'], name: 'Training character + Steerability', symptom: 'agreeable acceptance of a bad premise',      fix: 'invite pushback explicitly; ask for the strongest counter-argument' },
];

const SIGNALS = {
  token: /fake|invented|made up|citation|url|statistic|sounded right/i,
  knowledge: /recent|latest|2025|2026|niche|local|regulation/i,
  memory: /earlier|forgot|long (chat|conversation)|ignored my instruction/i,
  steer: /literal|format|instruction|drift|steps?/i,
  character: /agreed|went along|flattered|never pushed back/i,
};

function diagnose(story) {
  const hit = new Set(Object.keys(SIGNALS).filter((k) => SIGNALS[k].test(story)));
  return PAIRS.filter((p) => p.needs.every((n) => hit.has(n))).map(({ name, symptom, fix }) => ({ name, symptom, fix }));
}

console.log(diagnose('It gave me a made up citation with a URL for a recent 2026 regulation.'));
console.log(diagnose('In a long conversation it forgot my format instruction from earlier.'));
console.log(diagnose('I said my plan was bulletproof and it just agreed with my instruction to polish it.'));

Lesson 13

Next steps: one small model of the machine

The closing lesson’s claim is that fluent AI use does not come from memorising every failure mode. It comes from a compact, clear picture of how the system behaves, so that when something breaks you can identify which kind of wrong it is and respond appropriately.

  • Combine the four properties and the training fingerprints into one usable mental model.
  • See this course and the 4D Framework as two halves of one system: the properties explain what the 4D competencies react to.
  • Practise calibrated trust: place the task on each continuum, then adjust verification and context habits.
  • Expect the boundaries to move while the shape stays useful.

Your commitment

Do a gut-read of each task on your list (where it falls on each continuum, and which mitigation it needs), then pick one task and one change for this week and write it down. The lesson’s examples: a verification step, a standing-context setup, a checkpoint, or the habit of stating the goal rather than only the format. Reflect on the biggest change in how you think about AI behaviour since Lesson 1 and which of the 4Ds sharpened most.

Checklist

Practical checklist

  • When output is wrong, name the property pair before rewording the prompt.
  • Verify specifics, supply knowledge, curate context, state goals — one habit per property.
  • Invite disagreement whenever you want honest evaluation.
  • Offload exact work (math, counts, sorting) to code.
  • Revisit your task list quarterly; boundaries move, properties don’t.

FAQ

Frequently Asked Questions

Why is there so much emphasis on pairs?

Because single-property fixes often miss. Hallucinated citations need both verification and retrieval; drift needs both context management and a restated goal.

Will this stay true as models improve?

The course argues yes: boundaries shift but the properties remain. Re-test your tasks as models change.

Key Takeaway

You don’t need a catalogue of every way AI can fail. Keep four properties in your head, locate your task on each, and when something breaks ask which two collided. That one question picks the fix and keeps working as the models change.
