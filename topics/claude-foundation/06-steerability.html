Steerability is why assistants feel obedient and also why they sometimes obey the wrong thing perfectly. Control is strongest when instructions are short, concrete and checkable, and weakest exactly where meaning, long chains or precision matter.

Core idea: The model follows your words by pattern, not your intent by understanding — so supply the goal, check the checkable, and add checkpoints to long chains.

Story · “Make it shorter”

A colleague forwards a polite email from Jordan Reyes to Marcus Chen about the Q2 roadmap: the team recommends platform consolidation, the mobile redesign slips to Q3, and Jordan wants Marcus’s sign-off before Friday. The instruction is “make it shorter.” A literal shortening can cut the ask, the deadline or the trade-off, leaving a tidy email that no longer gets the sign-off. The words were obeyed; the intent was lost.

Lesson 10

Instruction-following is itself pattern completion

The model follows instructions the way it does everything else: by continuing a pattern. Fine-tuning taught it to treat instructions as something to honour, so it is very steerable, but it matches patterns rather than comprehending intent. The gap between what you say and what you mean is where most failures live.

ZoneLooks like
CapabilityShort, concrete, verifiable instructions: format specs, length limits, explicit roles
LimitationLong reasoning chains, abstract or ambiguous requests, tasks needing native numeric/logical precision

Characteristic failures

  • Reasoning drift — small early errors compound across dependent steps.
  • Letter over spirit — the instruction is honoured but the intent is missed.
  • Brittle arithmetic — exact calculation done by prediction, not computation.

Features that keep intent from diluting

  • System prompts for standing intent and role.
  • Code execution for exact maths and data handling.
  • Visible reasoning so intermediate steps can be checked.
  • Structured outputs that constrain format.

Fix for literal-but-useless results: restate the goal. Repeating the instruction more forcefully does not help. 4D link: steerability is what makes Description powerful and what limits it.

Code

Runnable checkpoints: verify the checkable, gate the multi-step

Format constraints are machine-checkable, so verify them in code. The goal (“get Marcus to sign off by Friday”) is not, so it needs a human checkpoint. The step runner stops at the first failed check instead of letting drift compound.

JavaScript Example 
// Steerability: verify short, checkable constraints in code instead of trusting prose.
const checks = {
  exactlyBullets: (n) => (t) => t.split('\n').filter((l) => /^\s*[-*•]\s+\S/.test(l)).length === n,
  maxWords: (n) => (t) => t.trim().split(/\s+/).length <= n,
  mustMention: (s) => (t) => t.toLowerCase().includes(s.toLowerCase()),
};

function verify(output, spec) {
  return Object.entries(spec).map(([name, check]) => ({ name, ok: check(output) }));
}

// The goal ("get Marcus to sign off by Friday") is not machine-checkable, so keep a human
// checkpoint; the format constraints ARE checkable, so automate them.
const spec = { fiveBullets: checks.exactlyBullets(5), under80Words: checks.maxWords(80), mentionsFriday: checks.mustMention('friday') };

const literalButUseless = '- Q2 roadmap: recommendation ready\n- Need sign-off\n- Platform consolidation\n- Mobile slips to Q3\n- Call?';
console.log(verify(literalButUseless, spec));

// A checkpointed multi-step run: stop at the first failing step instead of letting drift compound.
async function runSteps(steps) {
  const results = [];
  for (const [i, step] of steps.entries()) {
    const r = await step(results);
    results.push(r);
    if (!r.ok) { console.log(`checkpoint: step ${i + 1} failed -> stop and fix before continuing`); break; }
  }
  return results;
}
await runSteps([
  async () => ({ ok: true, value: 12 * 12 }),
  async ([a]) => ({ ok: a.value === 144, value: a.value + 6 }),
  async ([, b]) => ({ ok: b.value === 151, value: b.value * 2 }), // deliberately wrong expectation
  async () => ({ ok: true }),
]);

Architect's note

Designing for the word–intent gap

  • State goal, audience, and constraint — in that order. “Convince the team this timeline is realistic” is a goal; “three bullets” is a format. You usually need both.
  • Checkpoint dependent chains. Error probability multiplies across steps: 95% reliable per step is ~77% over five dependent steps. Insert verifiable checks between steps.
  • Offload exactness. Arithmetic, sorting, date maths and regex matching belong in tools, not in token prediction.
  • Prefer structured output (schemas, enumerations) at system boundaries so downstream code can validate instead of parse prose.
  • Evaluate on intent, not just instruction compliance: add rubric items such as “still contains the ask and deadline”.
Exercise

The goal rewrite

  • Take a multi-step or format-specific task and write a one-sentence goal (not an output shape).
  • Tight control: give a short verifiable instruction (e.g. a three-column table, exactly five bullets, second person) and check it held precisely.
  • Reasoning drift: request a 4–5 step dependent version, check for early errors that propagate, then ask it to pause and show step 2 first and compare.
  • Letter vs spirit: give a literally satisfiable but useless instruction, then re-prompt with the goal stated.
  • Follow-up: mark where to add checkpoints and write goal statements for tasks you only prompt by format.
FAQ

Frequently Asked Questions

Why does “IMPORTANT!!!” not fix a misread instruction?

Emphasis restates the instruction, not the intent. The missing information is the goal, so state that.

If it can follow format rules reliably, why not logic?

Short checkable constraints match patterns it has seen constantly; long chains and exact computation require precision that prediction doesn’t guarantee.

When should I use code execution?

Whenever a number, count, sort or transformation must be exactly right.

Key Takeaway

When a result is literally right and practically useless, don’t shout the instruction louder; change the information. State the goal, verify format in code, run exact calculations in tools, and put a checkpoint wherever errors could compound.
