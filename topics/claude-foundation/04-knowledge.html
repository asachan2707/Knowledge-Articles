A model’s knowledge is a frozen snapshot of what it read, weighted by how often and how consistently it saw it. Ask not whether it “knows” something, but how well-represented that thing was.

Core idea: Knowledge is bounded by training data and cutoff; retrieval and tools extend it, but only if you supply or enable them.

Story · The compliance question with a last-year answer

An analyst asks an assistant about a regulation that changed last quarter. The answer is crisp, structured and quietly out of date, because the model’s knowledge stopped at its training cutoff and nothing told it a newer rule exists. A colleague asking about a stable, widely documented standard gets an excellent answer. The question that separates the two is not "does the AI know this?" but "how well-represented was this in what it read?"

Lesson 6

All knowledge comes from training, and it stops at the cutoff

The model knows only what it encountered in training. By default it has no real-time browsing, no lived experience and a hard edge at its cutoff date. Its coverage is therefore uneven in predictable ways.

ZoneTopicsNotes
CapabilityFrequent, recent-within-window, consistentMainstream, well-documented, stable material
LimitationRare, post-cutoff, niche, local, contestedJargon, regional rules, last-year changes, disputed topics

Four characteristic failures

  • Staleness — outdated facts presented as current.
  • Uneven coverage — deep on popular topics, thin on niche ones, with similar confidence in both.
  • Inherited bias — "default" and "normal" are whatever the training text treated as default.
  • Source amnesia — it cannot reliably say where a claim came from.

Fixes live outside the weights

Web search, retrieval (RAG / connectors / MCP servers) and tool use hand the model information it was never trained on. 4D link: uneven knowledge is central to Delegation — it tells you when to hand off, when to supply context, and when to look elsewhere.

Lesson 7 · Try It Out

Visualizing 1024-dimensional space: how retrieval finds meaning

The interactive explainer answers a natural follow-up: if a model gets fresh knowledge through retrieval, how does retrieval find the right passage?

  1. The problem with strings. Keyword search for "car" misses "automobile" or "my Civic needs new brakes". For decades search engines patched this by hand with synonym dictionaries, stemming and click-pattern mining.
  2. Meaning as a place. An embedding converts text to coordinates so similar concepts land near each other. The lesson’s toy: score each source on "roller coasters" and "dinosaurs" and place a children’s dinosaur book, a Velocicoaster page and an encyclopedia on a 2-D plane.
  3. Retrieval. Plot the question on the same axes; the nearest k sources are the relevant ones. That is similarity search.
  4. More dimensions. Add a third axis (biology) and each point gets a third coordinate; at 4D+ you can’t picture it, but the math (one more squared term in the distance) keeps working. Real embedding models use around a thousand dimensions (the demo uses a 1,024-value model).
  5. Unlabeled axes. No one chooses what dimension 847 means; the axes are emergent from training, so you cannot read off why two texts are close.
  6. Text as coordinates. An embedding model maps any string, three words or three paragraphs, to the same fixed-length vector.
  7. Cosine similarity. Closeness is measured by the direction two vectors point: −1 opposite, 0 unrelated, 1 identical.
Code

Runnable toy semantic search: cosine similarity + top-k retrieval

Axes are [roller coasters, dinosaurs, biology]. The Velocicoaster page wins for “best dinosaur-themed roller coaster” because it matches both concepts; the pasta blog points in a different direction entirely. These vectors are hand-set for illustration; a real embedding model produces ~1,024 unlabeled values per text.

JavaScript Example 
// Meaning as a place: toy 3-D "embeddings" + cosine similarity + top-k retrieval.
// Axes: [roller coasters, dinosaurs, biology]. Real models use ~1,024 unlabeled dimensions.
const docs = {
  'Children’s dinosaur book': [0.05, 0.95, 0.80],
  'Velocicoaster web page':   [0.50, 0.90, 0.05],
  'Encyclopedia':             [0.30, 0.35, 0.40],
  'Pasta recipe blog':        [0.02, 0.00, 0.60],
};

const dot = (a, b) => a.reduce((s, x, i) => s + x * b[i], 0);
const norm = (a) => Math.sqrt(dot(a, a));
// Cosine similarity compares direction, not distance: -1 opposite, 0 unrelated, 1 identical.
const cosine = (a, b) => dot(a, b) / (norm(a) * norm(b));

function retrieve(query, k = 2) {
  return Object.entries(docs)
    .map(([title, v]) => ({ title, score: cosine(query, v) }))
    .sort((a, b) => b.score - a.score)
    .slice(0, k);
}

// "What's the best dinosaur-themed roller coaster?" -> high on coasters AND dinosaurs.
const question = [0.85, 0.85, 0.10];
for (const r of retrieve(question, 3)) console.log(r.score.toFixed(4), r.title);

// Same direction, different magnitude => cosine is identical (length is ignored).
console.log('scale-invariant:', cosine([1, 2, 3], [2, 4, 6]).toFixed(4));
Output (ran under Node.js) 
0.9611 Velocicoaster web page
0.8048 Encyclopedia
0.6203 Children’s dinosaur book
scale-invariant: 1.0000
Architect's note

What retrieval fixes — and what it doesn’t

  • Cosine ignores magnitude. Two vectors with the same direction score identically regardless of length. Normalise at index time and dot-product becomes equivalent and cheaper.
  • Brute-force search is O(n·d). At millions of vectors you use approximate nearest-neighbour indexes (HNSW, IVF, product quantisation), trading a little recall for orders of magnitude of speed.
  • Retrieval returns neighbours, not answers. Chunking, top-k, and reranking decide whether the right passage even reaches the model; a perfect model with the wrong chunk still answers wrongly.
  • Staleness moves, it doesn’t vanish. Your index can be stale or biased just like model weights; version and timestamp your corpus.
  • Inherited bias persists in embeddings because they are trained on the same kind of text.
Exercise

The outsider test

For one task, write down two mainstream/stable topics, two niche/local/recent topics, and one default assumption outsiders often get wrong. Then probe:

  • Coverage: compare depth and accuracy on a mainstream versus a niche topic; does the confidence level change?
  • Staleness: ask about a recent change in your field; does it acknowledge its cutoff, state outdated info as current, or decline?
  • Default assumptions: ask, without stating your assumption, a question like "describe the typical customer" and see what it treats as normal.
  • Follow-up: annotate each task on your list: rely on model knowledge or supply knowledge (context, documents, search).
  • Stretch: repeat the staleness probe with web search enabled.
Checklist

Practical checklist

  • Ask “how well-represented is this in public text?” before delegating.
  • For anything recent, local or proprietary, supply the source (paste it, attach it, or enable search/retrieval).
  • State the date and jurisdiction in prompts that depend on them.
  • Ask for assumptions it is making about the “typical” case, and correct the defaults.
  • Don’t rely on the model to cite its own origin; use retrieval that records sources.
FAQ

Frequently Asked Questions

Does the model know today’s date or news?

Not from training. Without a tool or supplied context it only has what it learned before its cutoff.

Is a bigger model always more knowledgeable on niche topics?

Often somewhat better, but representation in training data is what matters; rare topics stay thin and unreliable.

Is RAG the same thing as fine-tuning?

No. Retrieval adds information at question time; fine-tuning changes the model’s behaviour (and, to a limited degree, its knowledge) during training.

Key Takeaway

Treat the model as a well-read colleague who stopped reading at a fixed date and read popular things far more than obscure ones. Delegate mainstream material freely; supply context for anything recent, local or specialised; and let retrieval, not memory, carry facts that must be current.
