Build a Second Brain in 15 Minutes: Markdown, Git, and an AI Agent

Stop losing knowledge to the entropy of bookmarks, scattered notes, and apps you never re-open. The COG (Cognition + Obsidian + Git) system turns a plain Git repo of Markdown files into a personal knowledge base where an AI agent handles capture, retrieval, and synthesis — no database, no server, no vendor lock-in, and a 15-minute setup.

Domain: AI · Personal Productivity · Knowledge Management Published: 2026-07-29
Story · The knowledge management crisis most engineers live in

You spend 45 minutes researching how Kafka consumer groups handle partition rebalancing. You learn exactly what you needed, solve the problem, close the tabs, and move on. Three months later, a colleague asks you the same question. You remember you researched it. You do not remember what you concluded. You research it again.

Meanwhile your bookmarks folder has 400 links you will never open. Your Notion workspace has 80 pages, half of them stubs. Your Obsidian vault started strong in January and trailed off by March because filing notes felt like homework. Your Apple Notes has the good stuff but no structure. Your phone screenshots folder is the real archive, and it is unsearchable.

This is not a discipline problem. It is a friction problem. Every note-taking system that requires you to decide the right folder, tag, and template before you capture a thought loses to the zero-friction option: do nothing, forget it, re-learn it later. The system that wins is the one where capture is instant and retrieval is intelligent. That is exactly what an AI agent over a Git repo gives you.

Why Not Just Use Notion, Obsidian, or Roam?

None of these tools are bad. The problem is that they all introduce friction at the point that matters most: capture. And they each carry a structural weakness that becomes expensive over time.

Too much structure required upfront

Notion asks you to choose a database, template, and property schema before you write your first word. Roam and Obsidian are more forgiving, but the plugin ecosystem and vault configuration become a productivity project of their own. The system gradually becomes something you maintain rather than something you use.

Vendor lock-in and closed formats

Notion's data lives in Notion. Roam's data lives in Roam. Obsidian stores local Markdown, which is good, but sync requires their paid tier or a separate service. If any of these companies changes pricing, discontinues a feature, or shuts down, you have a migration problem. A Git repo of plain .md files is the most portable format that exists. It works with every editor, every CI pipeline, every AI tool, and will work in 20 years.

No agent-native interaction model

These tools were built for human-driven interaction: click, type, navigate. An AI agent cannot browse a Notion workspace efficiently. It cannot run a semantic search across your Obsidian vault without a plugin and local embedding setup. A flat folder of Markdown files, by contrast, is exactly what every AI coding tool (Claude Code, Cursor, Kiro, Gemini CLI, Codex) is already optimized to read, search, write, and reason over.

The core insight: The best knowledge management system is the one you actually use. Markdown + Git has essentially zero capture friction when an AI agent is the interface. You speak; it files. You ask; it retrieves. The format is too simple to break and too portable to lose.

The COG Architecture

COG (Cognition + Obsidian + Git) is an open-source MIT-licensed project by huytieu/COG-second-brain that establishes the conventions for this setup: a folder structure, a CLAUDE.md that instructs the AI agent, and a handful of templates. The entire thing is a Git repo of Markdown. Nothing more.

Folder structure

my-brain/
├── CLAUDE.md              ← agent instructions (how to file, how to retrieve)
├── daily/                 ← dated daily notes, captures, journal
│   └── 2026-07-29.md
├── projects/              ← one file or subfolder per active project
│   └── payment-service-refactor.md
├── reference/             ← evergreen facts, how-tos, concept summaries
│   ├── redis-patterns.md
│   └── distributed-locking.md
├── people/                ← notes on colleagues, meeting context, 1:1 prep
│   └── alice-zhang.md
└── ideas/                 ← half-baked thoughts, hypotheses, future work
    └── caching-experiment.md

Why Git is the right backend

Git gives you everything a knowledge base needs that a database would have to re-implement:

  • Version history — every change to every note is tracked. You can see what you thought six months ago versus today.
  • Diff — git diff shows exactly what was added or changed since your last review. Your agent can use this as a "what's new" feed.
  • Branches — want to try a different organizational structure? Branch it. Experiment without risk. Merge if it works.
  • Remote backup — git push to a private GitHub/GitLab repo is as reliable a backup as anything. Free, encrypted at rest, with full history.
  • Blame and log — git log --follow reference/redis-patterns.md shows you when you learned something and from what context.

The AI agent is the interface

You do not open the repo to browse files. You open your AI tool (Claude Code, Cursor, Kiro, Gemini CLI, or OpenAI Codex) pointed at the repo directory, and you talk to it in natural language. The CLAUDE.md file tells it the conventions — which folder to file things in, how to format notes, how to tag, and how to respond to standard prompts like "morning brief" or "what do I know about X."

Setup: 15 Minutes

There are two ways to get the repo. Clone the reference implementation directly, or use the npx shortcut that scaffolds a named copy:

Terminal — clone or scaffold 
# Option 1: clone the reference repo
git clone https://github.com/huytieu/COG-second-brain my-brain
cd my-brain

# Option 2: npx shortcut (creates a clean copy named my-brain)
npx create-cog-brain my-brain
cd my-brain

# Push to your own private remote
git remote set-url origin git@github.com:YOUR_USERNAME/my-brain.git
git push -u origin main

Open the repo in your AI tool. For Claude Code:

Terminal — open with Claude Code 
cd my-brain
claude   # opens Claude Code in the repo context; CLAUDE.md is automatically read

The CLAUDE.md file is the configuration layer. It tells the agent the folder conventions, the note format, and the vocabulary of standard commands. You should read through it and adjust it to your workflow — this is the one file you will customize. Everything else is just Markdown files.

CLAUDE.md — default agent instructions (excerpt) 
# COG Second Brain — Agent Instructions

## Your role
You are the interface for this knowledge base. When the user captures a thought,
file it. When the user asks a question, search the repo and synthesize an answer.
When the user says "morning brief", run the daily summary routine.

## Filing conventions
- New factual captures → reference/ (use kebab-case filenames)
- Time-sensitive work notes → daily/YYYY-MM-DD.md (append, never overwrite)
- Project context → projects/<project-name>.md
- Meeting notes and people context → people/<name>.md
- Speculative ideas → ideas/

## Note format
Every note should start with YAML frontmatter:
---
title: <descriptive title>
date: YYYY-MM-DD
tags: [tag1, tag2]
source: <url or "personal">
---

## Standard commands
- "morning brief" → summarize new git commits since yesterday, surface connections
- "what do I know about X" → search reference/ and projects/, synthesize
- "remember that..." → capture to the right folder and confirm where it was filed
- "weekly review" → run the weekly review template

Supported AI tools: Claude Code, Cursor, Kiro, Gemini CLI, and OpenAI Codex. Any tool that can open a directory and read a CLAUDE.md (or equivalent project instructions file) works. The conventions in CLAUDE.md translate naturally to each tool's project memory system.

The 3 Core Operations

1. Capture

You talk to the agent the way you would text a note to yourself, except the agent actually files it. No decision required from you. The agent reads CLAUDE.md, decides the right folder and filename, writes the note with frontmatter, and confirms. 

> Remember that Redis uses sorted sets for leaderboards — ZADD with score as
  timestamp gives you a ranked list where ZRANGE retrieves top N in O(log N + N).

Agent: Filed to reference/redis-sorted-sets-leaderboards.md
  Tags: [redis, data-structures, leaderboards]
  Linked from: reference/redis-patterns.md (added to "see also")

2. Connect (Retrieval and Synthesis)

When you ask a question, the agent searches across all your notes — not just a keyword match, but a semantic synthesis. It can pull from multiple files, follow [[links]], and give you a consolidated answer with citations. 

> What do I know about distributed locking?

Agent: Based on your notes across 3 files:

**reference/distributed-locking.md** (2026-06-12)
  Redlock requires majority quorum across Redis nodes. Martin Kleppmann's
  critique: unsafe under GC pauses. Your note: "for seat booking, GC-pause
  risk acceptable because critical section is just the DB write, not payment."

**reference/redis-patterns.md** (2026-07-01)
  SETNX + PX for atomic lock acquisition. Lua script for atomic
  check-and-delete on release (prevents releasing another process's lock).

**projects/payment-service-refactor.md** (2026-07-15)
  Decided: PostgreSQL advisory locks over Redis for this service — simpler,
  no external dependency, sufficient for our connection pool size.

Connections: These notes relate to → reference/redis-sorted-sets-leaderboards.md,
  reference/consistency-models.md

3. Recall (Morning Brief)

The daily brief is the killer feature of this setup. You run it each morning and the agent synthesizes what you captured yesterday, surfaces connections you may have missed, and prepares you for the day. 

> morning brief

Agent: Good morning. Here is your brief for 2026-07-29:

**Yesterday's captures (3 notes)**
  - reference/kafka-consumer-groups.md — consumer group rebalancing, partition
    assignment strategies (range vs round-robin vs sticky)
  - daily/2026-07-28.md — standup notes, payment-service retries discussion
  - ideas/event-sourcing-for-audit-log.md — rough idea captured

**Connections surfaced**
  Your kafka-consumer-groups note connects to reference/distributed-locking.md
  (partition ownership is itself a distributed lock problem — sticky assignment
  is the "lock with TTL" pattern applied to consumer groups).

**Open threads**
  - payment-service-refactor.md has no decision recorded for the Redis vs PG
    advisory lock choice. Worth finalizing today.

**Today's focus** (from projects/ last-modified dates)
  payment-service-refactor.md was touched most recently — likely your active project.

Linking Notes: Zettelkasten-Lite

Full Zettelkasten implementation is overkill for most engineers. COG borrows the two most valuable ideas: bidirectional links and tag-based navigation.

Wiki-style links

Use [[note-slug]] syntax inside any note to link to another. The agent follows these links during retrieval — when you ask about topic X, it traverses the link graph to find related notes, not just the file you asked about.

reference/kafka-consumer-groups.md — linking example 
---
title: Kafka Consumer Groups and Partition Rebalancing
date: 2026-07-28
tags: [kafka, distributed-systems, messaging]
source: https://kafka.apache.org/documentation/#consumerapi
---

# Kafka Consumer Groups

A consumer group is a set of consumers that cooperatively consume a topic.
Each partition is assigned to exactly one consumer in the group at any time —
this assignment is itself a distributed coordination problem.

See also: [[distributed-locking]] (partition assignment as lock ownership)
See also: [[redis-patterns]] (Redis Streams as alternative to Kafka for small teams)

## Rebalancing triggers
- Consumer joins or leaves the group
- Partition count changes
- Consumer fails heartbeat (session.timeout.ms exceeded)

Tags

Frontmatter tags are the second navigation axis. The agent can answer "show me everything tagged redis" or "what distributed-systems notes do I have from the last 30 days?" without building any index — it reads the YAML frontmatter across the reference/ folder and filters.

Index files per domain

For domains where you have more than five notes, create an index file that lists them. The agent will use the index as a map during retrieval, which speeds up synthesis and avoids missing notes that are not well-linked.

reference/_index-distributed-systems.md — domain index 
---
title: Distributed Systems — Index
tags: [index, distributed-systems]
---

# Distributed Systems Notes

## Consensus and Coordination
- [[distributed-locking]] — Redis Redlock, PG advisory locks, Redlock controversy
- [[kafka-consumer-groups]] — partition assignment, rebalancing strategies

## Data Replication
- [[consistency-models]] — strong, eventual, causal, read-your-writes
- [[raft-consensus]] — leader election, log replication, term numbers

## Patterns
- [[saga-pattern]] — distributed transactions without 2PC
- [[outbox-pattern]] — reliable event publishing from a database

Making It Yours: Customization

CLAUDE.md is the only configuration file that matters. Once you understand what it does — instruct the agent on conventions and define the vocabulary of standard prompts — you can shape the system to your exact workflow.

Daily standup template

Add a standup section to CLAUDE.md and the agent will generate your standup update from your notes each morning:

CLAUDE.md addition — standup template 
## Standup command
When the user says "standup", read daily/<yesterday>.md and any project notes
touched in the last 24 hours (git log --since="24 hours ago"), then output:

**Yesterday**: [1-3 bullet points of what was actually done]
**Today**: [inferred from open threads and project notes]
**Blockers**: [any explicitly mentioned blockers, or "none"]

Keep it to 5 lines max. Engineering standup style.

Weekly review prompt

CLAUDE.md addition — weekly review 
## Weekly review command
When the user says "weekly review", do the following:
1. List all notes created or modified this week (git log --since="7 days ago")
2. Identify the top 3 themes across those notes (by tag frequency)
3. Find any ideas/ notes that are older than 2 weeks with no links — flag for
   deletion or promotion to reference/
4. Check projects/ for any project that has had no activity in 7 days — flag
   as stale
5. Output a summary in the format: themes, connections found, housekeeping needed

Obsidian as a read-only viewer

If you prefer a visual graph view of your notes, open the repo folder in Obsidian. It reads the same [[wiki-link]] syntax and renders the graph view. Use Obsidian purely for visual exploration — all writes go through the AI agent. This gives you the best of both worlds: agent-native interaction for capture and retrieval, visual graph for exploration.

For Engineers Specifically

The general knowledge management use case is well-covered by Notion and its peers. Where COG is uniquely powerful is for software engineers, because the artifact format (Markdown + code blocks + Git history) is native to engineering work.

Capturing learnings from PRs

> Just merged PR #847 — learned that Postgres JSONB GIN indexes only help when
  you query with the @> containment operator, not with ->> text extraction.
  Note this for the future.

Agent: Filed to reference/postgres-jsonb-indexes.md
  Tags: [postgres, indexing, json, performance]
  Linked from: reference/postgres-patterns.md

Architecture Decision Records (ADRs)

ADRs are a natural fit for the projects/ folder. The agent can template them and update the status field as the project evolves.

projects/payment-service-refactor.md — ADR example 
---
title: Payment Service Refactor — ADRs
date: 2026-07-01
tags: [architecture, payment, decisions]
status: in-progress
---

## ADR-001: Distributed Lock Implementation

**Date**: 2026-07-15
**Status**: Decided
**Context**: Payment service needs to prevent double-charge under concurrent retries.
**Options considered**: Redis Redlock, PostgreSQL advisory locks, optimistic locking
**Decision**: PostgreSQL advisory locks
**Rationale**: Simpler operational model (no Redis dependency), sufficient at current
  connection pool size (max 100 concurrent), automatically released on connection close.
**Consequences**: Ceiling at ~100 concurrent lock acquisitions per second. Revisit
  if payment volume exceeds 50 RPS sustained.

Debugging notes that become runbooks

When you debug a hard problem, capture the investigation in the daily note. Later, ask the agent to promote it to a runbook in reference/: 

> The debugging session from yesterday about the Redis connection pool exhaustion —
  that should become a runbook. Write it up properly.

Agent: Created reference/runbook-redis-connection-pool-exhaustion.md
  Extracted: symptoms, diagnosis steps, root cause, fix, prevention
  Added monitoring commands and the specific log patterns to grep for
  Linked from: reference/redis-patterns.md and reference/runbooks-index.md

Key Takeaway

The COG system works because it removes the two failure modes of every knowledge management system: capture friction and retrieval failure. Capture friction goes to zero when an AI agent is the interface — you narrate, it files. Retrieval improves dramatically when the agent can synthesize across notes and follow links rather than returning a keyword-matched list. The underlying format — plain Markdown in a Git repo — is the least fragile data format available: no database to maintain, no vendor to depend on, no migration to dread. The 15-minute setup is real. The compounding value over months and years of captured knowledge is the payoff.
