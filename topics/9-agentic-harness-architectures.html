9 Agentic Harness Architectures Every AI Developer Must Know

The agent loop is just one pattern. Production agentic systems choose from a spectrum of harness architectures — each with distinct token cost profiles, reliability characteristics, and parallelism models. This reference covers all nine patterns with implementation trade-offs, failure modes, and runnable JavaScript examples.

Domain: AI Engineering · Agent Design Published: 2026-09-03

Picking the wrong harness for a task is the most common architectural mistake in agent engineering. A ReAct loop is elegant for tool-heavy research; it is catastrophically expensive and unreliable for a 15-step deployment pipeline. Knowing when each harness applies — and what it costs you in tokens, latency, and reliability — is the difference between a $0.03 agent run and a $12 agent run that still fails.

Core idea: Every agentic harness is a policy that controls how an LLM allocates reasoning budget, interleaves tool use, and decides when to stop. The "best" harness is the one whose reliability/cost trade-off matches your task's error tolerance and complexity.

Separate generator and critic agents. Critic evaluates and rejects or accepts outputs before they proceed.

Story · The $40,000 Agent Incident

In 2024, a well-funded AI startup built a customer support automation agent using a naive ReAct loop for a task that involved orchestrating 12 back-end systems across 8 steps per ticket. The agent worked fine in demos. In production, it burned $40,000 in a single month from retries, context re-inflation, and circular tool-call loops — all because the ReAct loop had no upfront plan and no step budget. Switching to a Plan-and-Execute harness with step budgets reduced monthly cost by 85% and increased task completion rate from 62% to 94%.

The same pattern played out at scale at Cognition AI (Devin), Adept AI, and internally at Google (AlphaCode 2). Each found that for deterministic pipelines, planning before acting consistently outperformed reactive reasoning.

Architecture 1
ReAct Loop · Reason + Act Interleaved

ReAct Loop

Introduced in the 2022 paper ReAct: Synergizing Reasoning and Acting in Language Models (Yao et al., Google Brain), ReAct interleaves chain-of-thought reasoning with tool calls in a single context window. Each turn: the model emits a Thought, then an Action (tool call), then observes the result, then loops. The loop terminates when the model emits a final answer or hits a max-turns guard.

When to use: Single-agent research, tool-augmented QA, interactive data exploration, agentic search pipelines. Ideal when the task structure is unknown upfront and tool results determine the next step organically.

Trade-offs: Simple to implement. Low planning overhead. But context grows linearly with turns, making long tasks expensive. No global plan means the agent can loop or hallucinate a dead-end path. No memory of prior failures.

Failure modes: Circular tool loops (calls the same tool repeatedly with minor variation), context explosion past 200K tokens on long tasks, no error recovery (one bad observation contaminates all future reasoning), and confident wrong final answers when the model pattern-matches too early.

Token cost profile: O(T * N) where T is average tokens per turn and N is number of turns. Grows fast. A 20-turn agent with 2K tokens/turn costs ~40K tokens/run.

Real examples: LangChain's default agent, OpenAI Assistants API default loop, early versions of Perplexity AI's answer engine, Anthropic's Claude tool use documentation examples.

JavaScript Example — ReAct Loop 
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

const tools = [
  {
    name: "web_search",
    description: "Search the web for current information.",
    input_schema: {
      type: "object",
      properties: {
        query: { type: "string", description: "Search query" },
      },
      required: ["query"],
    },
  },
  {
    name: "calculate",
    description: "Evaluate a mathematical expression.",
    input_schema: {
      type: "object",
      properties: {
        expression: { type: "string", description: "Math expression to evaluate" },
      },
      required: ["expression"],
    },
  },
];

async function executeTool(name, input) {
  if (name === "calculate") {
    // Safe eval via Function constructor
    return { result: Function(`"use strict"; return (${input.expression})`)() };
  }
  if (name === "web_search") {
    // Stub: replace with real search API
    return { results: [`Stub result for query: ${input.query}`] };
  }
  throw new Error(`Unknown tool: ${name}`);
}

async function reactLoop(goal, maxTurns = 15) {
  const messages = [{ role: "user", content: goal }];

  for (let turn = 0; turn < maxTurns; turn++) {
    const response = await client.messages.create({
      model: "claude-sonnet-4-6",
      max_tokens: 4096,
      tools,
      messages,
    });

    messages.push({ role: "assistant", content: response.content });

    if (response.stop_reason === "end_turn") {
      const text = response.content.find((b) => b.type === "text");
      return text?.text ?? "(no final answer)";
    }

    if (response.stop_reason === "tool_use") {
      const toolBlocks = response.content.filter((b) => b.type === "tool_use");
      const toolResults = await Promise.all(
        toolBlocks.map(async (block) => ({
          type: "tool_result",
          tool_use_id: block.id,
          content: JSON.stringify(await executeTool(block.name, block.input)),
        }))
      );
      messages.push({ role: "user", content: toolResults });
    }
  }

  throw new Error(`ReAct loop exceeded ${maxTurns} turns`);
}

// Usage
reactLoop("What is 17% of 4200, and search for the latest Claude model?")
  .then(console.log)
  .catch(console.error);
Architecture 2
Plan-and-Execute · Decouple Planning from Execution

Plan-and-Execute

Plan-and-Execute separates the agent run into two distinct phases. In phase 1, a planner LLM produces a structured list of steps (the plan) given the goal. In phase 2, an executor LLM (often lighter-weight) carries out each step sequentially, with tool access. The plan can be re-planned if a step fails with unrecoverable information.

When to use: Complex multi-step pipelines (CI/CD automation, code generation with review, document processing), tasks where the subtask decomposition is stable before execution starts, and any scenario where you want step-level observability and rollback.

Trade-offs: More reliable than ReAct for known task structures. Enables step-level progress tracking and partial retries. Two LLM calls minimum (planner + executor per step). Plans can be wrong if the planner lacks full context, requiring expensive re-plan cycles.

Failure modes: Stale plan (planner made assumptions that execution invalidates), step granularity mismatch (plan steps too coarse for executor), plan hallucination (planner invents tool names or APIs that don't exist), and executor drift (executor ignores the plan and goes rogue on ambiguous steps).

Token cost profile: Plan phase: O(P) tokens once. Execution: O(E * S) where E is tokens per execution step and S is number of steps. Total is often 30-50% cheaper than ReAct for the same task because the executor doesn't need to carry full reasoning in each turn.

Real examples: Devin (Cognition AI) uses a planning phase before code execution. GitHub Copilot Workspace generates a plan before touching files. LangChain's PlanAndExecute agent. AWS Bedrock multi-step workflows.

Architecture 3
Reflexion · Verbal Reinforcement Learning

Reflexion

Introduced in 2023 (Shinn et al.), Reflexion gives agents episodic memory of their own failures. After each trial, the agent writes a verbal self-reflection ("I failed because I searched for the wrong term — next time I should use the vendor's official API docs first"). These reflections are prepended to the system prompt in subsequent trials, creating a feedback loop without gradient updates.

When to use: Tasks with a clear success/failure signal (unit tests pass, API returns expected schema, financial calculation matches ground truth). Iterative code generation, theorem proving, game-playing agents.

Trade-offs: Dramatically improves performance across retries on complex reasoning tasks (22% improvement reported on HotpotQA in original paper). But requires multiple trials, multiplying token cost by the retry count. Reflection quality varies — sometimes the model diagnoses the wrong failure mode.

Failure modes: Compounding hallucination (reflections themselves are wrong, poisoning future trials), reflection bloat (context fills with useless reflections after many failures), and false convergence (agent reflects that the task is impossible and stops trying).

Token cost profile: O(T * R) where R is number of retry trials and T is tokens per trial. Each trial grows slightly as reflections accumulate. Budget for 3-5x base token cost if using Reflexion.

Real examples: AlphaCode used a similar self-correction loop. OpenAI's iterative code interpreter. Cognition's Devin uses self-reflection on test failures before re-editing code.

Architecture 4
Tree of Thought · Parallel Reasoning Branches

Tree of Thought (ToT)

Proposed in 2023 (Yao et al., Princeton + Google DeepMind), ToT generalizes chain-of-thought by treating the reasoning process as a tree rather than a line. At each step the agent generates multiple candidate next thoughts (breadth), evaluates each (a separate LLM call scoring "promising / not promising"), selects the best branch (or explores multiple in parallel), and continues. Backtracking is explicit: the agent can abandon a subtree and re-explore.

When to use: Combinatorial problems (crossword puzzle solving, code refactoring with multiple valid paths, strategic planning with trade-offs), situations where greedy reasoning reliably fails and exploration helps.

Trade-offs: Dramatically better accuracy on tasks where greedy reasoning fails. Quadratic token cost growth (each level multiplies breadth * depth). Evaluator LLM calls are expensive and sometimes uncorrelated with actual correctness.

Failure modes: Evaluator bias (the evaluator scores verbose-sounding wrong paths higher than correct concise paths), exponential blowup if the tree is wide and deep, and incoherent backtracking (the agent backtracks to a node but the context window doesn't reflect the correct state at that node).

Token cost profile: O(B^D * E) where B is branching factor, D is depth, and E is evaluation cost per node. A tree of depth 4, branching 3, costs ~81x a single chain. Use beam search (keep top-k) to constrain cost.

Real examples: GPT-4 ToT used for Game of 24 (arithmetic game). DeepMind's AlphaGeometry uses a tree-search-like reasoning process. Google DeepMind's Gemini Pro for code completion with multi-path exploration.

Architecture 5
LATS · Language Agent Tree Search (MCTS for LLMs)

LATS — Language Agent Tree Search

LATS (Zhou et al., 2023) adapts Monte Carlo Tree Search (MCTS) to LLM agents. Each node is an agent state (message history + tool results). Selection uses UCT (Upper Confidence Bound for Trees) to balance exploring new paths vs. exploiting promising ones. Expansion generates candidate next actions. Simulation runs a fast rollout to a terminal state. Backpropagation updates node values.

When to use: Highest-complexity reasoning tasks where you have a clear reward signal and can afford expensive search. Mathematical proof generation, program synthesis, strategic planning with long horizons.

Trade-offs: Best-performing harness on extremely hard reasoning benchmarks (reported 94.4% on HumanEval vs 70% for ReAct). But 10-100x more expensive than ReAct. Requires a value function (LLM-as-judge or trained reward model). Engineering complexity is high.

Failure modes: Value function misalignment (MCTS optimizes the value estimate, not the actual task outcome — Goodhart's Law), compute budget exhaustion, and node state inconsistency (parallel paths create conflicting tool-call states that can't be merged).

Token cost profile: O(iterations * rollout_depth * tokens_per_state). A budget of 50 MCTS iterations, depth 5, 2K tokens/state costs ~500K tokens per task. Suitable only for high-value, high-complexity tasks.

Real examples: AlphaCode 2 uses a search-based code generation process. Reflexion paper compares against MCTS baselines. OpenAI's research o1/o3 models use an internal search process that resembles LATS at inference time.

Architecture 6
Multi-Agent Orchestrator · Coordinator + Specialists

Multi-Agent Orchestrator

An orchestrator agent decomposes a task into subtasks and delegates each to a specialist subagent. The orchestrator does not execute tools directly — it reasons about task decomposition, routes to the right specialist, and aggregates results. Subagents are narrow experts with domain-specific tools, prompts, and context.

When to use: Tasks that span multiple domains (research + code + data analysis), parallelizable subtasks, scenarios where specialization dramatically improves quality (a dedicated SQL agent beats a generalist for database queries), and high-throughput pipelines that benefit from concurrent execution.

Trade-offs: Parallelism reduces wall-clock latency. Specialization improves per-domain quality. But orchestrator-subagent communication adds latency and token overhead. Subagent failures are harder to debug than single-agent failures. Orchestrator prompt engineering is hard — it must correctly decompose tasks it has never seen.

Failure modes: Orchestrator hallucinating subagent capabilities, subagent result aggregation errors (conflicting outputs from parallel subagents), context loss between orchestrator and subagent (handoffs lose nuance), and infinite delegation loops (orchestrator creates subagents that create more subagents).

Token cost profile: O(O + sum(Si)) where O is orchestrator tokens and Si is each subagent's token cost. With parallelism, wall-clock time is O(max(Si)) but total tokens are additive. Good orchestrators reduce O by being concise in delegation.

Real examples: Anthropic's Claude Code uses orchestrator + subagent architecture internally. OpenAI Swarm framework. AutoGen (Microsoft). CrewAI. AWS Bedrock Multi-Agent Collaboration. LangGraph's supervisor pattern.

JavaScript Example — Multi-Agent Orchestrator 
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

// Specialist subagent: runs a focused task with domain-specific tools
async function runSubagent(role, systemPrompt, task, tools = []) {
  const response = await client.messages.create({
    model: "claude-haiku-4-5",  // cheaper model for specialists
    max_tokens: 2048,
    system: systemPrompt,
    messages: [{ role: "user", content: task }],
    tools,
  });
  const text = response.content.find((b) => b.type === "text");
  return text?.text ?? "";
}

// Orchestrator: decomposes task and delegates to specialists
async function orchestrate(userGoal) {
  // Step 1 — orchestrator creates a plan
  const planResponse = await client.messages.create({
    model: "claude-sonnet-4-6",
    max_tokens: 1024,
    system: `You are an orchestrator. Given a user goal, produce a JSON array of subtasks.
Each subtask has: { "agent": "researcher|analyst|writer", "task": "description" }.
Output ONLY the JSON array, no prose.`,
    messages: [{ role: "user", content: userGoal }],
  });

  let plan;
  try {
    plan = JSON.parse(planResponse.content[0].text);
  } catch {
    throw new Error("Orchestrator failed to produce valid JSON plan");
  }

  // Step 2 — run subagents in parallel
  const agentPrompts = {
    researcher: "You are a research specialist. Find and summarize factual information.",
    analyst:    "You are a data analyst. Interpret data, identify patterns, compute metrics.",
    writer:     "You are a technical writer. Produce clear, structured prose from inputs.",
  };

  const results = await Promise.all(
    plan.map((subtask) =>
      runSubagent(
        subtask.agent,
        agentPrompts[subtask.agent] ?? "You are a general-purpose assistant.",
        subtask.task
      ).then((result) => ({ agent: subtask.agent, task: subtask.task, result }))
    )
  );

  // Step 3 — orchestrator aggregates results
  const aggregatePrompt = results
    .map((r) => `## ${r.agent.toUpperCase()} output\nTask: ${r.task}\nResult: ${r.result}`)
    .join("\n\n");

  const finalResponse = await client.messages.create({
    model: "claude-sonnet-4-6",
    max_tokens: 2048,
    system: "You are an orchestrator. Synthesize the specialist outputs into a final answer.",
    messages: [
      { role: "user", content: `Original goal: ${userGoal}\n\n${aggregatePrompt}` },
    ],
  });

  return finalResponse.content[0].text;
}

// Usage
orchestrate("Analyze the impact of LLM inference costs on startup unit economics in 2024")
  .then(console.log)
  .catch(console.error);
Architecture 7
Swarm / P2P · Decentralized Agent Networks

Swarm / Peer-to-Peer Agents

Swarm architectures eliminate the central coordinator. Agents communicate directly with each other, passing partial results and requests laterally. Each agent has a local policy for deciding which other agent to query or hand off to. Global task completion emerges from local interactions, similar to ant colony optimization.

When to use: Fault-tolerant distributed pipelines, tasks where the routing logic is too complex to encode in a single orchestrator, scenarios where any single agent going down should not halt the entire pipeline.

Trade-offs: High fault tolerance — no single point of failure. Natural load distribution. But debugging is extremely hard (emergent behavior, non-deterministic execution paths). Deadlocks are possible if agents wait on each other. Difficult to trace end-to-end reasoning.

Failure modes: Circular handoffs (agent A sends to B, B sends back to A), message loss in async pipelines, inconsistent agent state across the swarm, and emergent failure modes that don't appear in unit testing but surface under load.

Token cost profile: Highly variable — depends on topology. Star topologies (all agents go through a hub) approach orchestrator costs. Fully decentralized topologies multiply cost by the number of inter-agent messages. Tracing tokens across agents requires a shared trace ID.

Real examples: OpenAI's Swarm (experimental). AutoGen's group chat. Early Salesforce Einstein Copilot used lateral agent handoffs. Bee Agent Framework (IBM Research). Research paper "Communicative Agents for Software Design" (ChatDev).

Architecture 8
HITL · Human-in-the-Loop Checkpoints

Human-in-the-Loop (HITL)

HITL is not a standalone harness — it is a modifier applied to any of the above. At defined checkpoints, the agent pauses execution and requests human approval before proceeding. Checkpoints are typically placed before irreversible actions (database writes, API deploys, financial transactions), high-uncertainty decisions, or steps that exceed a confidence threshold.

When to use: Any agent operating on production systems, financial transactions, legal document generation, medical decision support, or actions where the cost of error exceeds the cost of a human review. Regulatory compliance often mandates HITL for AI-assisted decisions.

Trade-offs: Dramatically reduces catastrophic failure risk. Builds user trust. But adds latency (human approval is not millisecond-fast), breaks the automation value proposition if checkpoints are too frequent, and creates approval fatigue if humans approve blindly.

Failure modes: Automation bias (humans approve without reading), checkpoint fatigue (too many approvals → rubber-stamping), checkpoint gap (dangerous actions happen between checkpoints), and async approval timeout (agent hangs indefinitely waiting for human response).

Production pattern: Use HITL selectively. Apply a risk classifier to each proposed action and escalate to human review only when risk score exceeds a threshold. Default-approve low-risk, reversible actions. Require explicit approval for irreversible or high-impact actions. Build an async approval queue with timeout fallback (reject on timeout).

Real examples: Claude Code's permission prompt system for file writes and shell commands. AWS Config rule change approvals. GitHub Actions environment protection rules. Stripe's fraud review queue for flagged transactions. Palantir's human review loop for automated intelligence analysis.

Architecture 9
Critic-Actor · Generator + Evaluator Separation

Critic-Actor Pattern

The Critic-Actor pattern assigns two distinct roles: the Actor generates a candidate output, and the Critic evaluates it against explicit rubrics. The Actor's output only proceeds if the Critic approves. On rejection, the Critic provides structured feedback that the Actor uses in its next generation attempt. This decouples generation quality from evaluation quality and breaks the self-consistency bias that appears when a model evaluates its own output.

When to use: Code review pipelines, content moderation, factual verification, contract generation, any scenario where generation quality must be independently verified before the output is trusted.

Trade-offs: Catches errors the actor would miss in self-evaluation. Critic can be a different model (cheaper, specialized). But doubles the base token cost. Critic calibration is hard — an over-critical critic loops forever; an under-critical one adds no value. Critic-Actor needs an escape valve (max rejection count).

Failure modes: Critic hallucinating errors (rejecting correct outputs), actor overfitting to critic feedback (produces outputs that satisfy the critic but not the user), infinite rejection loops, and critic blind spots (both actor and critic share the same training biases).

Token cost profile: O((A + C) * R) where A is actor tokens, C is critic tokens, and R is average rejection rounds until acceptance. With a good actor, R ≈ 1.3; with a bad actor, R can exceed 5, multiplying cost 5x.

Real examples: Anthropic's Constitutional AI uses a critic (critique model) to evaluate and revise actor outputs. OpenAI's self-critique pipeline. LinkedIn uses a critic model to evaluate AI-generated job descriptions. Stripe uses a critic layer for AI-generated API documentation.

JavaScript Example — Critic-Actor Pattern 
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

async function actor(task, feedback = null) {
  const messages = [{ role: "user", content: task }];
  if (feedback) {
    messages.push({ role: "assistant", content: "(previous attempt rejected)" });
    messages.push({ role: "user", content: `Critic feedback: ${feedback}\n\nPlease revise.` });
  }
  const response = await client.messages.create({
    model: "claude-haiku-4-5",
    max_tokens: 2048,
    system: "You are an expert technical writer. Produce clear, accurate, concise content.",
    messages,
  });
  return response.content[0].text;
}

async function critic(task, output) {
  const response = await client.messages.create({
    model: "claude-sonnet-4-6",  // stronger model for evaluation
    max_tokens: 1024,
    system: `You are a strict quality critic. Evaluate the output against:
1. Accuracy — is every factual claim correct?
2. Completeness — does it cover all required aspects?
3. Clarity — is it free of jargon and easy to follow?
4. Conciseness — is it appropriately brief with no padding?

Respond with JSON: { "approved": true|false, "feedback": "..." }
If approved, feedback can be empty. If rejected, feedback must be specific and actionable.`,
    messages: [
      {
        role: "user",
        content: `Task: ${task}\n\nOutput to evaluate:\n${output}`,
      },
    ],
  });

  try {
    return JSON.parse(response.content[0].text);
  } catch {
    return { approved: false, feedback: "Critic produced unparseable response" };
  }
}

async function criticActorLoop(task, maxRounds = 5) {
  let output = null;
  let feedback = null;

  for (let round = 1; round <= maxRounds; round++) {
    console.log(`Round ${round}: Actor generating...`);
    output = await actor(task, feedback);

    console.log(`Round ${round}: Critic evaluating...`);
    const verdict = await critic(task, output);

    if (verdict.approved) {
      console.log(`Approved after ${round} round(s).`);
      return output;
    }

    console.log(`Rejected: ${verdict.feedback}`);
    feedback = verdict.feedback;
  }

  console.warn(`Max rounds reached. Returning last output with caveats.`);
  return output;
}

// Usage
criticActorLoop(
  "Write a 3-paragraph explanation of WebSockets for a senior backend engineer."
)
  .then(console.log)
  .catch(console.error);

Failure Modes · What Breaks in Production

Universal Failure Modes Across Harnesses

Regardless of harness, these failures appear in every production agentic system. Design mitigations before you deploy, not after.

  • Context window exhaustion: All harnesses grow context over turns. Set a hard max_tokens budget and implement context compression (summarize and truncate older turns) before the limit is hit.
  • Infinite loops: Agents without a turn/step budget will loop forever on ambiguous tasks. Always enforce a max_turns or max_steps guard with an explicit error.
  • Tool call hallucination: The model calls tools with invalid parameters or calls tools that don't exist. Validate all tool calls at the harness layer before execution. Never trust the model's tool schema adherence in production.
  • Prompt injection via tool results: Tool results (web search, database queries, file reads) can contain adversarial instructions that hijack the agent. Sanitize tool results before returning them to the model context.
  • Cascading subagent failure: In multi-agent systems, one subagent's failure silently produces wrong data that upstream agents use without validation. Implement per-subagent result validation at the orchestration layer.
  • Model version drift: The harness was tuned for one model version. After a silent model update, behavior changes and the harness breaks. Pin model versions in production and test before accepting model updates.
Production Constraints · Scaling and Operational Limits

Scaling Constraints and Production Gotchas

  • Rate limits are per-API-key, not per-agent: In multi-agent systems with parallel subagents, all subagents share the same rate limit. A burst of 20 concurrent subagents will hit the TPM (tokens per minute) limit immediately. Use a token bucket rate limiter in your harness layer, not just at the API call site.
  • Latency amplification in serial architectures: Plan-and-Execute, Reflexion, and Critic-Actor are serial. A 3-step plan with 2s per step is 6s minimum. With retries and critic rejection rounds, p99 latency can be 30-60s. SLA must be set accordingly or async / webhook delivery is required.
  • Observability gaps in multi-agent systems: A single user request spawns N agent runs. Without a shared trace ID propagated through all agent calls, it is impossible to reconstruct what happened for a given user request. Implement W3C Trace Context (traceparent header) across all agent-to-agent calls.
  • Cost explosion on retry storms: Reflexion and Critic-Actor retry on failure. If the task is genuinely impossible (ambiguous goal, missing tools), they will retry at max rounds and burn full token budget every time. Detect early termination conditions (task infeasible signal) and set per-task cost caps.
  • Memory isolation between subagents: In orchestrator patterns, subagents must not share mutable state via side effects (file system, database) without coordination. Concurrent writes from parallel subagents cause data corruption. Use explicit handoff protocols, not shared memory.
  • The cold-start problem for LATS and ToT: Both architectures need a value function or evaluator to score branches. If the evaluator is also an LLM, cold starting the search adds 10-20 evaluator calls just to populate the tree root. Cache evaluator calls aggressively and warm-start with heuristics.
Decision Guide · Which Harness to Use

Harness Selection Decision Guide

Work through these questions sequentially to narrow your selection:

  1. Is the task a single well-scoped question with tool access? → Use ReAct Loop. Simple, cheap, well-understood.
  2. Is the task a multi-step pipeline with known steps upfront? → Use Plan-and-Execute. Better reliability at lower cost than ReAct for pipelines.
  3. Does the task have a clear binary success signal (tests pass/fail)? → Add Reflexion on top of ReAct or Plan-and-Execute.
  4. Does the task require exploring multiple candidate solutions? → Use Tree of Thought (affordable complexity) or LATS (maximum quality, very expensive).
  5. Does the task naturally decompose into independent parallel subtasks? → Use Multi-Agent Orchestrator.
  6. Does the output need independent quality verification? → Add Critic-Actor as a post-processing layer.
  7. Are any actions irreversible or high-stakes? → Add HITL checkpoints before those actions regardless of base harness.
  8. Does the system need fault tolerance without a central coordinator? → Explore Swarm / P2P only if you have excellent distributed systems observability.
Checklist · Production Harness Readiness

Production Harness Readiness Checklist

  • Hard max_turns / max_steps guard on every agent loop
  • Per-run token budget enforced at the harness layer (not just model level)
  • All tool calls validated before execution (schema + allowed-tools allowlist)
  • Tool results sanitized for prompt injection before adding to context
  • Shared trace ID propagated through all agent-to-agent calls
  • Rate limiter (token bucket) wrapping all LLM API calls
  • Per-run cost cap with early termination on budget exceeded
  • Model version pinned; tested before accepting model updates
  • Async approval queue for HITL with timeout-reject fallback
  • Subagent result validation before aggregation in orchestrator
  • Context compression strategy defined for long-running agents
  • Runbook for each known failure mode (circular loop, cost explosion, injection)
FAQ · Common Questions

Frequently Asked Questions

Can you combine harnesses?

Yes, and production systems almost always do. The most common combination is Plan-and-Execute at the outer level, with each execution step using a ReAct loop internally, Critic-Actor wrapping output-generating steps, and HITL before any irreversible action. Think of harnesses as composable layers, not mutually exclusive choices.

When is ReAct not appropriate?

When the task has more than ~7 predictable steps, involves parallel subtasks, requires output quality verification, or has irreversible side effects. ReAct's lack of upfront planning makes it unreliable and expensive for complex pipelines. The $40,000 incident above is a canonical example of ReAct misapplied to a pipeline task.

How do I choose between LATS and Tree of Thought?

ToT is better when you have a reasonable evaluator and the task depth is manageable (3-5 levels). LATS is better when the task is very long horizon, you need principled exploration/exploitation balance (UCT), and you can afford the engineering complexity of implementing MCTS. For most teams, ToT with beam search (keep top-3 branches) is the practical choice. LATS is a research-grade architecture for 2024-2025.

Should the critic always be a stronger model than the actor?

Not necessarily. In Critic-Actor the critic should have a different strength profile from the actor: the actor needs broad generation capability, the critic needs precise evaluation capability. For code review, a smaller model fine-tuned on code quality rubrics often outperforms a larger generalist. Match critic model to the evaluation task, not to general intelligence rank.

What is the minimum viable observability for a multi-agent system?

Three things: (1) a shared trace_id across all agent calls for a single user request, (2) per-agent token consumption logged with the trace_id, and (3) the final input/output for each agent persisted for replay debugging. Without these, production debugging is effectively impossible.

Is Swarm the same as multi-agent?

No. Multi-agent orchestrator has a hierarchical topology: one coordinator, many workers. Swarm is a flat peer-to-peer topology: all agents are equal, routing is emergent. Orchestrator is better for predictable delegated tasks; Swarm is better for fault-tolerant distributed pipelines where no single agent owns the whole workflow. In practice, most teams should start with orchestrator and only move to Swarm when they have strong observability and a genuine need for decentralization.

Key Takeaway

The default agent loop (ReAct) is a good starting point but a poor endpoint. Every production agentic system eventually evolves toward a hybrid harness: planning before executing, criticizing before shipping, and checkpointing before destroying. The frameworks that survive in production are the ones that treat harness architecture as a first-class engineering decision — not an afterthought. Pick the harness before you write the prompt, enforce budgets before you hit rate limits, and instrument before you deploy. The nine architectures in this page give you the vocabulary and the trade-off map to make that decision deliberately.
