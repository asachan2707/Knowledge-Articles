OKF + RAG: The Agent Architecture That Reads First and Searches Second

Agents confidently invent company-specific facts: metric formulas, internal API shapes, runbook steps. RAG returns text that is similar to the question, not text that is authoritative. This page covers the Open Knowledge Format (OKF) idea, a Git-backed set of Markdown files an agent reads directly, and a router design that sends authoritative questions to OKF and exploratory ones to RAG, with working code, failure modes and an honest critique.

Ask an agent "what is our churn rate?" and you will get a fluent, plausible formula. It may not be yours. Does your company exclude trials? Does a downgrade count as a loss? That answer lives in a few people's heads and in a long tail of chat threads, and a model that never saw the rule will happily improvise one. The usual fix is RAG, but RAG answers "what looks like this question?", while a metric definition needs "what is the one blessed answer?". Those are different questions, and they deserve different machinery.

Core idea: RAG retrieves, OKF remembers. Use RAG to go find an answer somewhere in a large messy corpus; use OKF to go read knowledge that someone already wrote down clearly and owns. Put a deterministic router in front so the agent reads first and searches second.

Sourcing note: the OKF details here (its origin, the bundle layout, the frontmatter fields) are as reported by the two articles above. I could not independently confirm the specification, and the second article is member-only, so I used only its headline framing. Treat the format as "an idea worth adopting in spirit" and check the official spec before building tooling that depends on exact field names. The router, failure modes and scaling commentary are my own architecture opinions, not claims from either article.

Story · Hypothetical, for illustration only

Imagine an analytics agent at a mid-sized SaaS company. A new product manager asks it, "What is churn this quarter?" The agent searches the company Slack export. Three threads come back. One says churn is cancellations over active customers. A second, from the finance channel, counts downgrades as churn. A third, two years old, says trials are included because "we want the honest number".

All three are semantically close to the question, and all three score well. The model picks the most fluent one, writes a confident paragraph, and the number goes into a board deck. Nothing here is a model bug. Retrieval did its job: it found related text. What was missing was a single owned page that says "this is the definition, these are the exclusions, this is the source table".

With a knowledge bundle in the loop, the same question hits a file titled "Monthly Churn Rate" before any search runs. The agent quotes the formula, cites the file, and shows who owns it. The Slack threads are still useful, but now as background, not as the authority. (This scenario is invented to make the failure concrete; it is not a report about any real company.)

What OKF is

A wiki the agent can read, kept in Git

According to the article, OKF (Open Knowledge Format) was introduced by Google Cloud in June 2026 as an open, vendor-neutral specification. The mental model is a company wiki, not a search engine: you do not query it for "similar" pages, you open the page for the thing you mean.

Bundle layout

A knowledge bundle is a directory of Markdown files stored in Git. The rule that makes it work is one concept per file: one table, one metric, one endpoint, one runbook. Small single-topic files mean the agent loads exactly the thing asked about and nothing else, and humans can review a change in a few lines.

Frontmatter

Each file starts with YAML frontmatter that describes it: a type (metric, table, endpoint, runbook), a title, a description, an owner, some tags, and a timestamp. The body holds the actual content: the formula, the rules, the source table, and links to related files. Links matter: they let an agent walk from "churn" to "net revenue retention" deliberately instead of by embedding distance.

Example bundle file: metrics/monthly-churn-rate.md 
---
type: metric
title: Monthly Churn Rate
description: Share of customers lost during a calendar month.
owner: analytics-platform
aliases: [churn, churn rate]
tags: [retention, saas]
timestamp: 2026-09-01
---
# Monthly Churn Rate
Formula: customers lost during the month / customers at the start of the month * 100
Rules: exclude trial accounts; do not count downgrades as churn.
Source table: warehouse.subscriptions_monthly
Related: ./metrics/net-revenue-retention.md

I added aliases to the sample frontmatter because lookup by name needs synonyms ("churn", "churn rate"). That field is my addition, not necessarily part of the spec.

Why Git

  • Review: a definition change is a pull request with a reviewer, not a silent edit in a wiki.
  • Audit trail: git blame answers "who changed the churn rule and why" for free.
  • No retrieval infrastructure: no embeddings, no chunking, no vector database, no re-indexing job when a file changes. The agent just reads the file.
  • Ownership by construction: CODEOWNERS can route a metric file to the team that owns the metric.
Where RAG fails

Strong reach, weak authority

The RAG loop is ingest, chunk, embed, store vectors, search, then augment the prompt. It is excellent at reach: it can surface a relevant paragraph from millions of pages nobody could hand-curate. It is weak at precision about truth, because similarity is not correctness.

  • Conflicting sources look identical. Two contradictory definitions embed almost the same. The ranker has no concept of "official".
  • Stale beats right on wording. An old thread phrased exactly like the question can outrank the current doc.
  • Chunking cuts rules in half. "Exclude trials" can land in the next chunk after the formula, and the formula alone is returned.
  • Probabilistic by design. The same question can return different top-k after a re-index or a model change, so answers drift without anyone editing a doc.

For depth on making RAG itself better (hybrid search, re-ranking, evals), see RAG from Scratch to Production. The point here is different: some questions should never go through similarity search at all.

The router

Deterministic precedence, not vibes

The article describes an "intelligent router" that classifies each query. I would not let an LLM classifier make the first decision. A model deciding which source to trust is itself a probabilistic component in the one place you wanted determinism. My design is a precedence chain where the cheap, explainable checks run first:

  1. Exact or entity match against the bundle. If the question names a title or alias ("churn", "orders API"), answer from that file. No model involved in the decision.
  2. Classifier. If nothing matched strongly, a small model labels the query "authoritative" (definition, schema, procedure) or "exploratory" (find discussions, summarise a topic). Authoritative plus a weak bundle hit still goes to OKF.
  3. RAG fallback. Everything else is searched. The answer is labelled as unverified.

Policies that make it trustworthy

  • Conflict policy: OKF wins, and says so. If both sources speak and disagree, the answer uses the OKF file and cites it. The disagreeing RAG snippet can be mentioned as "an older thread says otherwise", and the mismatch should be logged as a prompt to fix or retire the thread.
  • Log which path answered. Every response records the path (entity match, classifier to OKF, classifier to RAG), the cited files, and warnings. Without this you cannot measure misrouting.
  • Staleness and ownership checks. A file with no owner, or whose timestamp is older than your threshold, still answers but carries a warning. Silent staleness is the worst failure of this design.
  • Return a structured result. { source, answer, citations, warnings }, so the UI can show "from the Monthly Churn Rate page, owned by analytics-platform".
Runnable code

A small OKF-plus-RAG router in plain Node

This file has no dependencies. It parses simple frontmatter (key: value and [a, b] lists only; real YAML needs a real parser), loads a bundle, scores lookups by title, alias and tag, and routes with an injected ragSearch and llm. The fakes are deterministic so you can run it immediately; the comments mark where a real model and real vector search plug in. It writes the example bundle file to a temp directory and runs three queries, one per path.

JavaScript · okf-router.mjs · run with: node okf-router.mjs 
// okf-router.mjs  (Node 20+, ES modules, zero dependencies)
import { readdir, readFile, writeFile, mkdir, mkdtemp } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import path from 'node:path';

// ---------- 1. Tiny frontmatter parser: "key: value" and "key: [a, b]" ----------
function parseScalar(raw) {
  const v = raw.trim().replace(/^["']|["']$/g, '');
  return v;
}
export function parseFrontmatter(text) {
  const m = text.match(/^---\r?\n([\s\S]*?)\r?\n---\r?\n?([\s\S]*)$/);
  if (!m) return { meta: {}, body: text };
  const meta = {};
  for (const line of m[1].split(/\r?\n/)) {
    const kv = line.match(/^([A-Za-z_][\w-]*):\s*(.*)$/);
    if (!kv) continue; // ignore comments / unsupported YAML
    const [, key, val] = kv;
    meta[key] = val.startsWith('[') && val.endsWith(']')
      ? val.slice(1, -1).split(',').map(parseScalar).filter(Boolean)
      : parseScalar(val);
  }
  return { meta, body: m[2].trim() };
}

// ---------- 2. loadBundle(dir): walk the tree, parse every .md ----------
export async function loadBundle(dir) {
  const docs = [];
  async function walk(d) {
    for (const entry of await readdir(d, { withFileTypes: true })) {
      const full = path.join(d, entry.name);
      if (entry.isDirectory()) await walk(full);
      else if (entry.name.endsWith('.md')) {
        const { meta, body } = parseFrontmatter(await readFile(full, 'utf8'));
        if (!meta.title) continue; // a file without a title is not addressable
        docs.push({
          id: path.relative(dir, full),
          meta: { ...meta, aliases: meta.aliases ?? [], tags: meta.tags ?? [] },
          body,
        });
      }
    }
  }
  await walk(dir);
  return docs;
}

// ---------- 3. lookup(query): score by title / alias / tag ----------
const norm = (s) => s.toLowerCase().replace(/[^a-z0-9 ]+/g, ' ').replace(/\s+/g, ' ').trim();
const STOP = new Set(['what','is','the','a','an','of','how','do','we','our','does','are','define','calculate','calculated']);
const tokens = (s) => norm(s).split(' ').filter((t) => t && !STOP.has(t));

export function lookup(bundle, query, limit = 3) {
  const q = norm(query);
  const qTokens = new Set(tokens(query));
  const scored = bundle.map((doc) => {
    const title = norm(doc.meta.title);
    const aliases = doc.meta.aliases.map(norm);
    let score = 0;
    if (q === title || aliases.includes(q)) score = 100;           // exact name
    else if (q.includes(title) || aliases.some((a) => q.includes(a))) score = 80; // entity named in question
    for (const t of tokens(doc.meta.title)) if (qTokens.has(t)) score += 15;
    for (const tag of doc.meta.tags.map(norm)) if (qTokens.has(tag)) score += 10;
    return { doc, score };
  });
  return scored.filter((s) => s.score > 0).sort((a, b) => b.score - a.score).slice(0, limit);
}

// ---------- 4. The router ----------
const daysOld = (iso, now) => (now - Date.parse(iso)) / 86_400_000;

export async function route(query, { bundle, ragSearch, llm, now = Date.now(), maxAgeDays = 180, log = console.log }) {
  const hits = lookup(bundle, query);
  const top = hits[0];
  let path_, source;

  if (top && top.score >= 80) { path_ = 'okf-entity-match'; source = 'okf'; }
  else {
    const intent = await llm.classify(query);            // 'authoritative' | 'exploratory'
    if (intent === 'authoritative' && top && top.score >= 25) { path_ = 'classifier->okf'; source = 'okf'; }
    else { path_ = 'classifier->rag'; source = 'rag'; }
  }

  let context, citations, warnings = [];
  if (source === 'okf') {
    const d = top.doc;
    context = d.body;
    citations = [{ kind: 'okf', id: d.id, owner: d.meta.owner, timestamp: d.meta.timestamp }];
    if (d.meta.timestamp && daysOld(d.meta.timestamp, now) > maxAgeDays) warnings.push(`stale: ${d.id} not updated in ${maxAgeDays}+ days`);
    if (!d.meta.owner) warnings.push(`no owner: ${d.id}`);
  } else {
    const chunks = await ragSearch(query);               // your vector / hybrid search goes here
    context = chunks.map((c) => c.text).join('\n---\n');
    citations = chunks.map((c) => ({ kind: 'rag', id: c.id, score: c.score }));
    warnings.push('unverified: answer is based on retrieved documents, not an owned source');
  }

  // Swap point: llm.answer is the only call that should talk to a real model.
  const answer = await llm.answer({ question: query, context, trusted: source === 'okf' });
  log(JSON.stringify({ query, path: path_, source, citations: citations.map((c) => c.id), warnings }));
  return { source, answer, citations, warnings };
}

// ---------- 5. Deterministic fakes so this file runs as-is ----------
export const fakeLlm = {
  async classify(q) {
    return /\b(what is|define|formula|calculated|endpoint|schema|runbook|owner)\b/i.test(q) ? 'authoritative' : 'exploratory';
  },
  async answer({ question, context, trusted }) {
    return `${trusted ? '[authoritative]' : '[best-effort]'} ${context.split('\n').find((l) => l.trim() && !l.startsWith('#')) ?? ''}`;
  },
};
// REAL LLM: keep the same two methods. classify() -> small/cheap model returning one label;
// answer() -> your chat call, with `context` in the prompt, wrapped as DATA when trusted === false.

export const fakeRag = async () => [
  { id: 'slack#C123/1699.2', score: 0.81, text: 'Churn is cancellations divided by all active customers this quarter.' },
  { id: 'slack#C456/1702.9', score: 0.79, text: 'We count downgrades as churn in the finance dashboard.' },
];

const dir = await mkdtemp(path.join(tmpdir(), 'okf-'));
await mkdir(path.join(dir, 'metrics'));
await writeFile(path.join(dir, 'metrics', 'monthly-churn-rate.md'), EXAMPLE);

  console.log((await route(q, deps)).answer, '\n');
}

Two deliberate simplifications: scoring is a hand-tuned heuristic with thresholds (80 and 25) you should calibrate against logged queries, and the "answer" step of the fake model just echoes the first content line. In production, llm.answer calls your model with the OKF body as trusted context or the RAG chunks as untrusted data.

Failure modes

How this architecture breaks

  1. Stale bundle. OKF shifts the risk from "wrong retrieval" to "wrong but official". A confident, cited, outdated formula is more dangerous than a hedged RAG answer, because people trust citations. Mitigate with owners, review-by dates, a CI job that fails on files past their timestamp threshold, and surfacing the age in every answer.
  2. Bundle sprawl and merge conflicts. If every team commits to one repo, you get rename churn, duplicate concepts ("churn", "customer churn", "logo churn") and conflicting PRs. Enforce one concept per file, a naming convention, a lint for duplicate titles and aliases, and CODEOWNERS per directory.
  3. Router misclassification. A definition question phrased casually ("how many people left last month?") bypasses the entity match and goes to RAG. Track the path in logs, sample the RAG-routed "authoritative-looking" queries weekly, and add aliases rather than reaching for a smarter classifier first.
  4. Prompt injection through RAG, trust asymmetry with OKF. Retrieved Slack messages and wikis can contain instructions an attacker planted. OKF files pass through review and are far safer, but only if you keep them separate. Never splice RAG text into the same trusted block as OKF content; wrap it as quoted data, and give it no tool-calling authority.
  5. Permission mixing. A bundle in Git is readable by anyone with repo access, while the Slack corpus has per-channel permissions. If the router merges both into one prompt, a user may see HR or finance content via a "helpful" answer. Enforce ACLs at retrieval time, and split bundles by audience instead of filtering after the fact.
  6. Concept drift between files. Two correct pages can still contradict each other (a metric file and a dashboard runbook). Links help; a nightly check that follows links and flags dead targets helps more.
Scaling constraints

When a bundle outgrows grep

A few hundred small files is comfortable: the router above can scan them in memory in milliseconds. Somewhere in the thousands-of-files range, or when many agent processes need it, a linear scan and title matching stop being enough. But the next step is not automatically embeddings.

  • First, a plain index. Build a title/alias/tag map and an inverted index at CI time, cache it, and rebuild on merge. This keeps lookups exact, explainable and cheap.
  • Then, link and type structure. Use type and the links between files for scoped lookups ("all endpoints owned by payments"). This is the territory of knowledge graphs, discussed in Structuring 40 Million Documents Into an Agentic Knowledge Graph.
  • Only then, semantic search over the bundle. If you do add embeddings, use them to find the right file, then read the whole file. You keep the property that the answer comes from an owned page, not from a stitched chunk.
  • Context budget. A bundle is only useful if the agent loads the relevant few files. Cap how many files and tokens one answer may read, and keep files short.
  • The human limit. The scarce resource is not storage but curation. A bundle only scales as far as owners keep it accurate; the long tail of "nobody wrote this down" stays in RAG territory permanently.

Honest critique

Is "ultimate" earned? Not yet.

Readers pushed back on the article in two fair ways, and I agree with both in part.

  • "The router could just use the curated sources you already have." True. If your company already has a good metrics catalogue, a data dictionary or an API portal, the real work is exposing those through a lookup tool, not adopting a new format. OKF's value is the discipline (one concept per file, owner, Git review), and that discipline can be applied to existing systems. A new spec earns its place only if it gives you interoperability across tools, which I cannot verify.
  • "Calling it ultimate is premature." Hybrid does not remove RAG's problems; it confines them to the exploratory path. Retrieval quality, ranking and stale documents are still there, and now you also own a router, a bundle and a curation process. The hybrid is better for questions with a single right answer, and strictly more to run.

My position: the architecture is sound for a specific class of knowledge (definitions, schemas, procedures) and oversold as a universal fix. Measure it. Take 50 real questions, label the right source, and compare answer accuracy for RAG alone, OKF alone and the hybrid before committing a team to maintaining a bundle.

Practical learning

Checklist for adopting this

  • List the 20 questions where a wrong answer is costly (metrics, schemas, runbooks). Start the bundle with those only.
  • One concept per file; required frontmatter: type, title, owner, timestamp; add aliases for how people actually phrase things.
  • Put the bundle in Git with CODEOWNERS and a CI lint (missing owner, duplicate titles or aliases, dead links, stale timestamp).
  • Route with precedence: entity match, then classifier, then RAG. Keep the first step model-free.
  • On conflict, OKF wins and is cited; log the conflict as a cleanup task.
  • Log the path, citations and warnings on every answer; review RAG-routed definition-style queries weekly.
  • Treat RAG text as untrusted data and OKF as reviewed instructions; never mix them in one trusted block.
  • Apply permissions at retrieval time and split bundles by audience.
  • Build an index before you think about embeddings.
  • Run an A/B on real questions to prove the hybrid beats what you have.
FAQ

Common questions

Does OKF replace RAG? No. The framing from the Towards AI piece is "RAG retrieves, OKF remembers": RAG is "go find it" in a large corpus, OKF is "go read it" for established knowledge. You need both.

Is this just a wiki with extra steps? Largely, yes, and that is the appeal. The new part is that structure (one concept per file, typed frontmatter, links) is designed for an agent to read reliably, and Git gives review and history.

Why not put everything in the prompt? Cost, latency and attention. Loading only the matching file keeps context small and answers traceable.

Can the router be an LLM agent that chooses tools itself? It can, and for exploratory work that is fine. For authoritative facts I prefer a deterministic first step because it is testable and cannot be talked out of the right source.

What if the OKF file is wrong? Then the agent is wrong with a citation. That is why ownership, review dates and age warnings are part of the design, not extras.

Do I need the official spec to start? No. The practice (Markdown, frontmatter, Git, one concept per file) works today. Align with the official spec once you have confirmed it and need tool interoperability.

Key Takeaway

Similarity is not authority. Give your agent a small, owned, Git-reviewed set of Markdown pages for the facts that must be right, and let RAG handle the rest of the world. Put a deterministic, logged router in front, make OKF win on conflict with a citation, and spend your effort on ownership, freshness and permissions, because those, not the retrieval method, decide whether the system stays trustworthy.
