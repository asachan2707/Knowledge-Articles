BookMyShow: Same Seat Sold Twice — System Design Deep Dive on Race Conditions and Distributed Locking

How a seat reservation system can double-sell a seat under concurrent load — and the distributed locking, optimistic concurrency, and seat-state machine design that prevents it. Full deep dive: Redlock, advisory locks in PostgreSQL, the seat lifecycle state machine, seat hold TTLs, payment race conditions, and the reconciliation job that catches the edge cases.

Domain: System Design · Distributed Locking · Concurrency Published: 2026-07-22

A cinema seat is a classic scarce shared resource. Two users see the same seat available, both select it, both pay — one arrives at the theatre to find a stranger in their seat. This is not a booking system bug; it is a fundamental concurrency problem. The seat is a shared mutable state, and without serialisation at the critical section (the reservation), the race condition is guaranteed to manifest at sufficient scale.

Scale context: BookMyShow handles 10–15M bookings/month. On a blockbuster release (Avengers, RRR, KGF), a single show sells out in under 60 seconds, with 100,000+ concurrent users on the same 200-seat hall. At that concurrency:seat ratio, naive locking strategies fail immediately.

Story · Pathaan release: 5,000 duplicate bookings in 4 minutes

When Pathaan released, BookMyShow saw 10M users hit the platform simultaneously at 12:00 AM. For popular halls in Mumbai, a single 300-seat show had 50,000+ concurrent booking attempts. Without effective distributed locking, multiple users completed payment for the same seat. Each duplicate booking required manual detection, refunds, and customer support.

The operational cost per duplicate booking was ₹800–1,200 (refund processing, support, goodwill credit). At 5,000 duplicates, that is ₹4–6M in operational cost from a single film release. The fix was architectural, not just a hotfix.

The Seat State Machine

Every seat in every show follows a strict state machine. No transition is valid unless the seat is in the correct prior state. The state machine is the contract that makes the seat system correct. 

available
  ↓ user selects seat (lock acquired)
held (with TTL: 10 minutes)
  ↓ user completes payment
booked (permanent)

available ← held (TTL expires, lock released)
available ← held (user abandons, explicit release)

The held state is the critical section. Only one user may hold a seat at a time. The distributed lock's job is to ensure the transition available → held is atomic and mutually exclusive.

Distributed Locking: Redlock and Alternatives

Option 1: Redis-based lock (Redlock algorithm)

Redis's SET key value NX PX ttl is an atomic "set if not exists with TTL." Redlock runs this across 3–5 independent Redis nodes; a lock is acquired only if a majority of nodes grant it. This protects against single-node failure.

Redlock is controversial. Martin Kleppmann's 2016 critique showed it is unsafe under GC pauses (lock TTL expires while the lock holder is paused, another process acquires the lock, both proceed). For seat booking — where the consequence of a collision is a duplicate booking, not data corruption — Redlock is widely used in practice and the GC-pause risk is mitigated by keeping the critical section short (just the DB write, not the payment flow).

Option 2: PostgreSQL Advisory Locks

PostgreSQL's pg_try_advisory_lock(seatId) is a session-level mutex stored in the database itself. No external Redis cluster required. Automatically released when the DB connection closes. Horizontally scalable only to the number of PG connections, so it has a ceiling — but for a system that already uses PostgreSQL as the source of truth, it is the simplest correct solution.

Option 3: Optimistic concurrency (version column)

Add a version column to the seat row. On update, include WHERE version = $known_version. If another transaction updated first, the row count is 0 — retry or return conflict. No locks held, high throughput, but requires retry logic and is less suitable for high-contention seats (popular seats = many retries = degraded throughput under load).

JavaScript Example — Seat Hold with Redis Lock + PostgreSQL Write 
// seat-reservation.js — Node.js + ioredis + PostgreSQL
import Redis from 'ioredis';
const redis = new Redis(process.env.REDIS_URL);

const HOLD_TTL_MS = 600_000;  // 10 minutes
const LOCK_TTL_MS = 5_000;    // 5 second lock — just long enough for the DB write

async function holdSeat(showId, seatId, userId) {
  const lockKey = `seat-lock:${showId}:${seatId}`;
  const lockValue = `${userId}-${Date.now()}`; // unique per acquisition attempt

  // 1. Acquire distributed lock (atomic SET NX PX)
  const locked = await redis.set(lockKey, lockValue, 'NX', 'PX', LOCK_TTL_MS);
  if (!locked) {
    throw new Error('Seat is currently being reserved by another user');
  }

  try {
    // 2. Verify seat is still available (under lock — no race possible)
    const seat = await db.query(
      `SELECT status FROM seats WHERE show_id = $1 AND seat_id = $2 FOR UPDATE`,
      [showId, seatId]
    );
    if (!seat.rows[0] || seat.rows[0].status !== 'available') {
      throw new Error('Seat no longer available');
    }

    // 3. Transition to 'held' with TTL metadata
    const holdExpiry = new Date(Date.now() + HOLD_TTL_MS);
    await db.query(
      `UPDATE seats SET status = 'held', held_by = $1, hold_expires_at = $2
       WHERE show_id = $3 AND seat_id = $4 AND status = 'available'`,
      [userId, holdExpiry, showId, seatId]
    );

    // 4. Store hold in Redis for fast TTL-based cleanup
    await redis.set(`seat-hold:${showId}:${seatId}`, userId, 'PX', HOLD_TTL_MS);

    return { held: true, expiresAt: holdExpiry };
  } finally {
    // 5. Release lock — only if we still own it (use Lua for atomic check-and-delete)
    const releaseScript = `
      if redis.call('GET', KEYS[1]) == ARGV[1] then
        return redis.call('DEL', KEYS[1])
      else
        return 0
      end
    `;
    await redis.eval(releaseScript, 1, lockKey, lockValue);
  }
}

async function confirmBooking(showId, seatId, userId, paymentId) {
  // Verify the hold is still valid and belongs to this user
  const seat = await db.query(
    `SELECT status, held_by, hold_expires_at FROM seats
     WHERE show_id = $1 AND seat_id = $2 FOR UPDATE`,
    [showId, seatId]
  );

  const row = seat.rows[0];
  if (!row || row.status !== 'held') throw new Error('Seat hold expired or not found');
  if (row.held_by !== userId) throw new Error('Seat held by different user');
  if (new Date(row.hold_expires_at) < new Date()) throw new Error('Hold expired');

  // Transition to 'booked' (permanent)
  await db.query(
    `UPDATE seats SET status = 'booked', payment_id = $1, booked_at = NOW(),
                      held_by = NULL, hold_expires_at = NULL
     WHERE show_id = $2 AND seat_id = $3 AND held_by = $4`,
    [paymentId, showId, seatId, userId]
  );

  // Remove from Redis hold store
  await redis.del(`seat-hold:${showId}:${seatId}`);

  return { booked: true };
}

// TTL expiry cleanup (runs every minute)
async function releaseExpiredHolds() {
  const expired = await db.query(
    `UPDATE seats SET status = 'available', held_by = NULL, hold_expires_at = NULL
     WHERE status = 'held' AND hold_expires_at < NOW()
     RETURNING show_id, seat_id`
  );
  console.log(`[cleanup] Released ${expired.rowCount} expired holds`);
}

The Payment Race Condition

The hold-to-booked transition has its own race condition: the user's payment succeeds, but the confirmBooking() call arrives after the hold TTL expires and the seat was re-held by another user.

Solution: extend the hold on payment initiation, not on payment completion. When the user clicks "Pay Now," extend the Redis hold TTL to 15 minutes immediately (before redirecting to the payment gateway). The payment can take up to 5 minutes; the extended hold covers it. On payment success, call confirmBooking() which does a final state check.

Seat Display: Eventual Consistency is OK for the Grid

The seat map shown to users does NOT need to be strongly consistent. "Available" vs "held" is a cosmetic distinction for display — what matters is that the actual reservation attempt (the lock acquisition) is strongly consistent.

The seat grid is served from a Redis cache that is refreshed every 2 seconds via a Kafka consumer. A user may see a seat as "available" when it was actually just held by another user — but when they click it, the lock acquisition will fail and they will see "seat taken." The 2-second eventual consistency window is acceptable; the reservation layer is always strongly consistent.

Failure Modes and Production Gotchas

  • Lock TTL shorter than DB write duration — if the PostgreSQL update takes longer than the lock TTL (e.g. during a deadlock or slow query), the lock expires and another user can acquire it while the first user's write is in-flight. Fix: set lock TTL to 5× the p99 DB write duration under load.
  • Redis single-point failure — if using a single Redis node (not Redlock), lock loss on node restart = all seats unlocked simultaneously = potential duplicate booking storm. Fix: Redis Sentinel + AOF persistence; or use PostgreSQL advisory locks as primary mechanism (failsafe at DB level).
  • User refreshes during hold — if a user refreshes the booking page, the client may re-request a hold on the same seat they already hold, consuming a second hold slot (if the system does not dedup by userId). Fix: SETNX keyed by both seatId AND userId; if the user already holds the seat, return the existing hold's TTL.
  • Seat status cache serving stale data after forced release — an admin forcibly releases a hold (fraud case, VIP override), but the Redis cache still shows it as held. Fix: pub/sub invalidation of the seat cache on every admin action, same as the cart invalidation pattern.

Key Takeaway

The BookMyShow duplicate-booking problem is solved by a two-layer strategy: a distributed lock (Redis or PostgreSQL advisory) that serialises the available → held transition, and a seat state machine that makes illegal transitions structurally impossible. The seat display can be eventually consistent — the booking layer must be strongly consistent. The most important engineering insight: holding a lock only for the DB write (milliseconds), not for the entire payment flow (minutes), keeps the system throughput high while still preventing double-sells.
