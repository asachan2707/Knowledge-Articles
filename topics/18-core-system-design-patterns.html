18 Core System Design Patterns Explained in 20 Minutes

CQRS, Event Sourcing, Saga, Circuit Breaker, Bulkhead, Strangler Fig, Sidecar, Ambassador, Anti-Corruption Layer, BFF, Outbox, Inbox, 2PC, Read Replica, Cache patterns, Fanout, Competing Consumers, and Leader Election — every pattern explained from the production failure that motivated it, with when-to-use and when-NOT-to-use guidance and real company examples.

Domain: System Design · Architecture · Distributed Systems Credit: Deep-concept · Medium Published: 2026-09-03

Distributed systems fail in patterned ways: writes split across services lose atomicity, slow dependencies cascade, traffic spikes corrupt shared state, and legacy boundaries leak poison. These 18 patterns are the canonical vocabulary for describing — and solving — those failure modes. Learning them as a vocabulary, not as a checklist, is what separates architects from engineers who read books about architecture.

Core idea: Each pattern here was extracted from a real production incident at scale. The pattern name is shorthand for a context, a force, and a resolution. You cannot apply a pattern correctly unless you understand the force it resolves.

Story · The Great Migration at Shopify

In 2020, Shopify ran a multi-year migration from a Rails monolith to a pod-based architecture. Within that effort they touched nearly every pattern in this list. They used the Strangler Fig to route traffic incrementally. They deployed the Sidecar pattern via Envoy for mTLS between pods. The Anti-Corruption Layer protected new domain models from legacy data shapes. The Outbox Pattern ensured order events reached Kafka atomically. The CQRS model gave their storefront read path its own optimised read replicas. One migration. Eighteen patterns. The ones they skipped cost them production incidents to relearn.

Group 1 — Data Consistency Patterns

Patterns 1–3 · CQRS, Event Sourcing, Saga

1. CQRS — Command Query Responsibility Segregation

Problem: A single data model tries to serve both writes (complex business rules, validation, constraints) and reads (denormalised projections, aggregations, sorting). Under load, read contention slows writes; write-optimised schemas make reads ugly.

Mechanism: Split the model. Commands mutate state through a write model validated by domain logic. Queries read from a separate, purpose-built read model — often a different database engine entirely (Postgres writes, Elasticsearch reads). The two sides stay in sync via events or replication.

When to use: High-read, lower-write systems with complex read projections. DDD-heavy domains. Systems where reads and writes have different latency SLAs.

When NOT to use: Simple CRUD apps. Small teams — the operational overhead (two schemas, sync lag, eventual consistency) outweighs the gains. Do not start with CQRS; extract to it when the pain is concrete.

Failure modes: Read model lag causes stale reads. Sync failures leave read model permanently diverged. Schema migrations must update both sides.

Real example: Microsoft Azure's CosmosDB was designed with CQRS at its change feed, where the change feed acts as the event stream powering downstream read projections. LinkedIn's activity feed similarly separates write ingestion from read fan-out.

JavaScript Example — CQRS Read Model Rebuild 
// cqrs-read-model.js — Command side writes events; read side projects them
class OrderWriteRepository {
  constructor(db, eventBus) {
    this.db = db;
    this.eventBus = eventBus;
  }

  async placeOrder(command) {
    const { userId, items, totalCents } = command;
    // Validate domain rules
    if (!items.length) throw new Error('Order must have items');
    if (totalCents <= 0) throw new Error('Total must be positive');

    const result = await this.db.query(
      `INSERT INTO orders (user_id, total_cents, status, created_at)
       VALUES ($1, $2, 'pending', NOW()) RETURNING id`,
      [userId, totalCents]
    );
    const orderId = result.rows[0].id;

    // Emit domain event — write model does NOT care about read projections
    await this.eventBus.emit('order.placed', {
      orderId, userId, items, totalCents, timestamp: Date.now()
    });
    return orderId;
  }
}

// Read side: subscribes to events, maintains its own projection
class OrderReadProjection {
  constructor(readDb) {
    this.readDb = readDb;
  }

  // Idempotent — can be replayed to rebuild from scratch
  async handleOrderPlaced(event) {
    const { orderId, userId, items, totalCents, timestamp } = event;
    await this.readDb.query(
      `INSERT INTO order_summaries
         (order_id, user_id, item_count, total_cents, status, placed_at)
       VALUES ($1, $2, $3, $4, 'pending', $5)
       ON CONFLICT (order_id) DO NOTHING`,
      [orderId, userId, items.length, totalCents, new Date(timestamp)]
    );
  }

  async getOrdersByUser(userId) {
    // Fast, denormalised read — no joins, no domain logic
    const { rows } = await this.readDb.query(
      `SELECT * FROM order_summaries WHERE user_id = $1 ORDER BY placed_at DESC`,
      [userId]
    );
    return rows;
  }
}

2. Event Sourcing

Problem: You lose the history of how an entity reached its current state. Audit trails are hard. Debugging production state bugs requires time-travel.

Mechanism: Instead of storing current state, store an append-only log of events. Current state is derived by replaying events. The event log is the source of truth.

When to use: Audit-heavy domains (finance, healthcare, legal). Systems that need temporal queries ("what was the state at T-minus-3 days?"). Pairs naturally with CQRS — events power read-model projections.

When NOT to use: Simple CRUD with no audit requirements. Systems where events are not meaningful domain facts. Event stores require snapshots as event counts grow — neglecting this causes O(n) replay costs.

Failure modes: Event schema evolution is painful — you cannot change a past event. Snapshot strategies must be planned upfront. Replay performance degrades without periodic snapshots (every N events).

Real example: Axon Framework (used by ING Bank) centers their core banking platform on Event Sourcing, giving them full transactional audit and the ability to rebuild any account state from the event log.

3. Saga Pattern

Problem: A business transaction spans multiple services. You cannot use a database transaction across service boundaries. If step 3 of 5 fails, steps 1–2 must be compensated.

Two variants:

Choreography Saga: Each service listens for events and decides its own next action, publishing its own result event. No central coordinator. Pros: loose coupling, no single point of failure. Cons: flow is implicit, debugging distributed state is hard.

Orchestration Saga: A central Saga Orchestrator sends commands to services and reacts to their responses. Flow is explicit. Pros: visible, debuggable, testable. Cons: orchestrator becomes a coupling point; must itself be fault-tolerant.

When NOT to use: If you can accomplish the transaction within a single service boundary, do not introduce a Saga. The compensating transaction model only works if all participants implement idempotent compensations.

Real example: Uber uses orchestrated Sagas for trip lifecycle management. Booking a trip involves driver assignment, price locking, notification dispatch, and payment authorization — each service has a compensating action if any step fails.

Group 2 — Resilience Patterns

Patterns 4–6 · Circuit Breaker, Bulkhead, Strangler Fig

4. Circuit Breaker

Problem: A slow or failing downstream dependency causes cascading failure. Every caller waits on timeouts, exhausting thread pools and connection pools across the entire call chain.

Mechanism: A state machine with three states. Closed: calls flow normally; failures are counted. Open: calls fail immediately (fast fail) after a failure threshold is crossed; no downstream call is made. Half-Open: after a timeout, a probe request is allowed through; if it succeeds, the breaker closes; if it fails, it re-opens.

Parameters to tune: failure threshold (e.g. 50% of last 10 requests), open-state timeout (e.g. 30s), probe request count in half-open. Wrong thresholds cause either false positives (breaker trips on normal blips) or false negatives (breaker never trips before cascade).

Real example: Netflix's Hystrix library popularised this pattern for their microservices mesh. Every service-to-service call was wrapped in a circuit breaker with fallbacks, enabling graceful degradation at scale.

JavaScript Example — Circuit Breaker 
// circuit-breaker.js — production-grade state machine
class CircuitBreaker {
  constructor(fn, options = {}) {
    this.fn = fn;
    this.failureThreshold = options.failureThreshold ?? 5;
    this.successThreshold = options.successThreshold ?? 2;
    this.timeout = options.timeout ?? 30_000; // ms before half-open probe
    this.state = 'CLOSED';
    this.failureCount = 0;
    this.successCount = 0;
    this.nextAttempt = Date.now();
  }

  async call(...args) {
    if (this.state === 'OPEN') {
      if (Date.now() < this.nextAttempt) {
        throw new Error(`CircuitBreaker OPEN — fast-fail (retry after ${new Date(this.nextAttempt).toISOString()})`);
      }
      // Transition to half-open for probe
      this.state = 'HALF_OPEN';
    }

    try {
      const result = await this.fn(...args);
      this._onSuccess();
      return result;
    } catch (err) {
      this._onFailure();
      throw err;
    }
  }

  _onSuccess() {
    this.failureCount = 0;
    if (this.state === 'HALF_OPEN') {
      this.successCount++;
      if (this.successCount >= this.successThreshold) {
        this.successCount = 0;
        this.state = 'CLOSED';
        console.log('CircuitBreaker: HALF_OPEN -> CLOSED');
      }
    }
  }

  _onFailure() {
    this.failureCount++;
    this.successCount = 0;
    if (this.state === 'HALF_OPEN' || this.failureCount >= this.failureThreshold) {
      this.state = 'OPEN';
      this.nextAttempt = Date.now() + this.timeout;
      console.warn(`CircuitBreaker: OPEN — next probe at ${new Date(this.nextAttempt).toISOString()}`);
    }
  }
}

// Usage
const breaker = new CircuitBreaker(
  (userId) => fetch(`https://payment-service/users/${userId}`).then(r => r.json()),
  { failureThreshold: 3, timeout: 15_000 }
);

async function getPaymentProfile(userId) {
  try {
    return await breaker.call(userId);
  } catch (err) {
    // Fallback: return cached profile or default
    return { userId, paymentMethod: 'unknown', cached: true };
  }
}

5. Bulkhead

Problem: A surge of traffic to one feature (e.g. search) exhausts the shared thread pool, starving unrelated features (e.g. checkout). One slow tenant degrades all tenants.

Mechanism: Partition resources (thread pools, connection pools, queues) into isolated compartments per service, tenant, or criticality tier. A failure in one bulkhead cannot propagate to another. Named after ship bulkheads that contain flooding to a single compartment.

When to use: Multi-tenant SaaS platforms. Systems with mixed-criticality workloads (payment path must not share resources with analytics).

Real example: AWS isolates different services and customer accounts using bulkhead principles via separate queue groups and per-tenant resource limits in their SQS and DynamoDB capacity management.

6. Strangler Fig

Problem: You need to replace a monolith incrementally without a risky big-bang rewrite. You cannot take the system down; the new system must coexist.

Mechanism: Route all traffic through a facade (reverse proxy, API gateway). Migrate individual capabilities one by one to the new system; redirect routing for each capability as it goes live. The monolith "strangles" as more routes are redirected. Remove the monolith when all routes are migrated.

Key discipline: The facade must not leak monolith internals. Data migration is the hard part — the Anti-Corruption Layer (Pattern 9) protects the new system from legacy data shapes during the transition.

Real example: Shopify, as described above. Also Amazon — their Services Initiative (circa 2002) used Strangler Fig semantics, incrementally peeling services from their retail monolith over a decade.

Group 3 — Service Mesh & Integration Patterns

Patterns 7–10 · Sidecar, Ambassador, ACL, BFF

7. Sidecar

Problem: Cross-cutting concerns (mTLS, logging, metrics, service discovery, retries) are duplicated across every service, each in a different language.

Mechanism: Deploy a helper container alongside each service container in the same pod (Kubernetes) or on the same host. The sidecar handles cross-cutting concerns; the main container focuses on business logic. Communication is local (localhost or Unix socket), so latency is sub-millisecond.

Real example: Envoy Proxy as a sidecar in Istio service mesh. Lyft open-sourced Envoy after building it as the sidecar foundation for their microservices migration. Every Lyft service gets mTLS, distributed tracing, and circuit-breaking without a single line of application code.

8. Ambassador

Problem: A service needs to communicate with complex external systems (load-balanced clusters, services requiring retries, connection pools). The application should not own that complexity.

Mechanism: Deploy an ambassador container (a specialised sidecar) that acts as an out-of-process proxy for the external system. The app calls localhost; the ambassador handles routing, retries, circuit-breaking, and protocol translation.

Distinction from Sidecar: The Sidecar augments your service's own behavior. The Ambassador proxies outbound calls to external dependencies.

Real example: Microsoft's Azure Redis Ambassador pattern — app containers connect to a local Redis ambassador that manages connection pooling and failover to Redis clusters, shielding app code from Redis Cluster topology changes.

9. Anti-Corruption Layer (ACL)

Problem: A new domain model must integrate with a legacy system that uses a different domain language, data format, and semantics. Direct integration pollutes the new model with legacy concepts.

Mechanism: Insert a translation layer at the boundary. The ACL translates between the new domain model (clean, bounded context) and the legacy system's model. The ACL owns the mapping logic; neither side knows about the other's internals.

Failure mode: ACLs tend to accumulate logic over time as the legacy system changes. They must be tested at the contract level, not just unit-tested, otherwise upstream legacy changes silently break translations.

Real example: When Booking.com migrated from a PHP monolith to bounded contexts, ACLs translated legacy inventory structs into clean domain value objects, preventing legacy naming conventions from bleeding into the new hotel inventory domain.

10. Backends for Frontends (BFF)

Problem: A single generic API must serve mobile (slow networks, battery constraints, small screen, different data needs) and web (bandwidth-rich, different UX flows) and third-party partners (different auth, different payloads). One backend cannot optimise for all clients.

Mechanism: Create a dedicated backend per frontend type. Each BFF aggregates downstream services, shapes payloads, and enforces auth models specific to its client. The BFF is owned by the frontend team.

Failure mode: BFFs accumulate business logic that should live in downstream services. They become coupled to UI implementation details. Keep BFFs thin — aggregation and shaping, not business rules.

Real example: SoundCloud's architecture blog (2014) documented their transition to BFF: one backend for the iOS app, one for Android, one for the web player, each owned by the respective frontend team.

Group 4 — Messaging Reliability Patterns

Patterns 11–13 · Outbox, Inbox, Two-Phase Commit

11. Outbox Pattern

Problem: Writing to a database and publishing to a message broker must be atomic — but they are two separate systems. A crash between them causes lost events (if publish fails after DB write) or phantom events (if publish succeeds before DB write commits then rolls back).

Mechanism: Write the event to an outbox table in the same database transaction as the business data. A separate relay process reads the outbox and publishes to the broker, marking events published only after confirmation. Debezium (CDC) or a polling relay both work.

Guarantee: At-least-once delivery. Consumers must be idempotent.

Real example: Stripe's payment processing uses the Outbox pattern to ensure that a charge event is never lost between their database commit and Kafka publish, preventing double-charge confusion in their webhook fanout system.

JavaScript Example — Outbox Pattern 
// outbox-pattern.js — atomic write + relay
async function processPaymentWithOutbox(pgClient, payment) {
  await pgClient.query('BEGIN');
  try {
    // 1. Write business fact
    const { rows } = await pgClient.query(
      `INSERT INTO payments (user_id, amount_cents, status, idempotency_key)
       VALUES ($1, $2, 'captured', $3)
       ON CONFLICT (idempotency_key) DO NOTHING
       RETURNING id`,
      [payment.userId, payment.amountCents, payment.idempotencyKey]
    );
    if (!rows.length) {
      await pgClient.query('ROLLBACK');
      return null; // duplicate — already processed
    }
    const paymentId = rows[0].id;

    // 2. Write event to outbox — same transaction
    await pgClient.query(
      `INSERT INTO outbox_events
         (aggregate_id, event_type, payload, status, created_at)
       VALUES ($1, 'payment.captured', $2, 'pending', NOW())`,
      [paymentId, JSON.stringify({ paymentId, ...payment })]
    );

    await pgClient.query('COMMIT');
    return paymentId;
  } catch (err) {
    await pgClient.query('ROLLBACK');
    throw err;
  }
}

// Relay — runs every 100ms on a dedicated process
async function relayOutboxToKafka(pgPool, kafka) {
  const producer = kafka.producer();
  await producer.connect();

  const { rows } = await pgPool.query(
    `SELECT id, aggregate_id, event_type, payload
     FROM outbox_events
     WHERE status = 'pending'
     ORDER BY created_at
     LIMIT 50
     FOR UPDATE SKIP LOCKED`  // prevents double-processing across relay replicas
  );

  for (const row of rows) {
    await producer.send({
      topic: row.event_type,
      messages: [{ key: row.aggregate_id.toString(), value: row.payload }]
    });
    await pgPool.query(
      `UPDATE outbox_events SET status = 'published', published_at = NOW()
       WHERE id = $1`,
      [row.id]
    );
  }
  await producer.disconnect();
}

12. Inbox Pattern

Problem: Consuming a message and processing it must be idempotent. Message brokers guarantee at-least-once delivery — your consumer will receive duplicate messages. Processing a payment twice, shipping an order twice, or deducting inventory twice are catastrophic.

Mechanism: The consumer writes the message ID to an inbox table before processing. If the message ID already exists, it is a duplicate — skip processing. The inbox check and business processing happen in the same database transaction.

Outbox vs Inbox: Outbox ensures reliable publish (producer side). Inbox ensures idempotent consume (consumer side). They are complementary, not alternatives.

Real example: Shopify's order pipeline uses inbox deduplication on their inventory reservation consumer — a duplicate "reserve inventory" message must not double-decrement stock.

13. Two-Phase Commit (2PC)

Problem: You need a true atomic transaction across multiple databases or services. Either all participants commit or all abort.

Mechanism: Phase 1 (Prepare): the coordinator asks all participants to prepare and vote. Phase 2 (Commit/Abort): if all vote yes, coordinator sends commit; if any vote no, coordinator sends abort.

Blocking hazard: If the coordinator crashes after Phase 1 but before Phase 2, participants are blocked — they have voted but cannot proceed without the coordinator's final decision. This is the fundamental flaw of 2PC.

When NOT to use: Almost never in microservices. Use the Saga pattern instead. 2PC is appropriate for relational database clusters where the coordinator and participants share a failure domain (e.g. XA transactions in a bank's core system within a single data center).

Real example: Google Spanner uses a form of 2PC backed by Paxos groups for distributed transactions, but the coordinator itself is replicated — eliminating the blocking failure mode that makes vanilla 2PC dangerous.

Group 5 — Read Scaling Patterns

Patterns 14–15 · Read Replica, Cache Patterns

14. Read Replica

Problem: Read traffic saturates the primary database. Analytics queries compete with OLTP writes for the same I/O and CPU.

Mechanism: The primary handles all writes. Replicas receive asynchronous log replication (WAL streaming in Postgres, binlog in MySQL). Application reads are directed to replicas. Replication lag means replicas may serve stale data.

Replication lag is a first-class concern: A write followed immediately by a read may not see the write if routed to a replica. Mitigate with read-your-writes consistency (route reads to primary for a short window after a write, or use session consistency tokens).

Real example: GitHub uses read replicas extensively for their repository browsing path. Most reads (file tree, commit history, blame) are served from replicas; writes (commits, PR merges) go to the primary. They document replication lag monitoring as a core SRE responsibility.

15. Cache-Aside / Read-Through / Write-Through

Cache-Aside (Lazy Loading): Application checks cache first. On miss, application fetches from DB, writes to cache, returns result. Cache population is application-driven. Pros: only requested data is cached. Cons: cold start, cache and DB can diverge if DB updates happen outside the app.

Read-Through: Application always reads from cache. On miss, the cache layer (not the application) fetches from DB and populates itself. Pros: simpler application code. Cons: requires a cache that supports read-through semantics (e.g. Redis with a cache module, AWS ElastiCache with write-through cluster mode).

Write-Through: On every write, the application writes to the cache AND the DB synchronously (or the cache writes through to the DB). Cache is always fresh. Cons: write latency doubles; data that is never read is also cached (wasted memory).

Write-Behind (Write-Back): Write to cache only; the cache asynchronously flushes to DB. Lowest write latency; highest risk of data loss if cache fails before flush.

Real example: Twitter's Flock system (social graph service) uses Cache-Aside with Redis. The social graph is too large to fit in RAM; most edges are cold. Cache-Aside means only hot edges (followed accounts of active users) ever enter cache.

Group 6 — Messaging Topology Patterns

Patterns 16–18 · Fanout, Competing Consumers, Leader Election

16. Fanout Pattern

Problem: A single event must trigger actions in many downstream services (notification, analytics, audit, billing). Publishing directly to each service couples the producer to all consumers and doesn't scale.

Mechanism: The producer publishes to one topic or exchange. A fanout mechanism (Kafka with multiple consumer groups, SNS topic with multiple SQS queue subscriptions, RabbitMQ fanout exchange) delivers a copy to every subscriber independently. Consumers are fully decoupled from the producer and from each other.

Failure mode: If one consumer falls behind (slow consumer), its queue fills up. With Kafka, a slow consumer group does not affect other consumer groups. With shared queues, it does. The slow consumer must be backpressure-handled separately.

Real example: AWS SNS+SQS fanout is the canonical implementation. When an S3 object upload event is published to SNS, it fans out to SQS queues for thumbnail generation, virus scanning, and metadata indexing — each independently scaled.

17. Competing Consumers

Problem: A single queue receives more messages than one consumer can process. You need horizontal scale on the consumer side without processing a message twice.

Mechanism: Multiple consumer instances all subscribe to the same queue. The broker delivers each message to exactly one consumer (competing, not broadcasting). Consumers are stateless and interchangeable. Scale by adding consumer instances.

Distinction from Fanout: Fanout delivers every message to every consumer. Competing Consumers delivers each message to exactly one of a pool of consumers.

Failure mode: A consumer that processes a message but crashes before acknowledging it will cause the broker to redeliver the message to another consumer. Consumers must be idempotent (use the Inbox pattern). Message ordering is not guaranteed across competing consumers — if ordering matters, use partition-keyed delivery (Kafka partition by key).

Real example: Netflix's stream processing uses Competing Consumers extensively via Kafka consumer groups. Video encoding jobs are distributed across a pool of encoding worker pods; each pod races to claim the next job from the Kafka topic.

18. Leader Election

Problem: A distributed system needs exactly one node to perform a privileged action at a time (database primary, scheduled job runner, shard coordinator, outbox relay). Multiple nodes performing the same privileged action causes data corruption.

Mechanism: Nodes compete for a distributed lock. The winner is the leader and performs the privileged action. The lock has a TTL (lease); if the leader crashes, the lock expires and a new election occurs. Implementations: ZooKeeper ephemeral nodes, etcd leader election, Postgres advisory locks, Redis SETNX with TTL.

Failure modes: The leader suffers a GC pause longer than the TTL — the lock expires and a new leader is elected while the old leader is still running. Two leaders are active simultaneously (split-brain). Mitigate with fencing tokens: each lease generation has a monotonically increasing token; the storage layer rejects writes with stale tokens.

Real example: Kubernetes uses etcd for leader election of its controller manager, scheduler, and cloud controller. Each component writes a lease object; only the holder of the lease becomes active. etcd's linearizable writes ensure only one node wins.

Pattern Selection Checklist

Practical · Before picking a pattern
  • Identify the specific failure mode first — never pick a pattern by name before naming the problem it solves.
  • CQRS: only if reads and writes have meaningfully different models or scaling requirements. Start with a single model.
  • Event Sourcing: only if you need temporal audit or event-driven projections. The operational cost is real.
  • Saga (Orchestration): prefer over choreography when you need debuggable, testable distributed transaction flow.
  • Circuit Breaker: always wrap synchronous service-to-service calls in production. Tune thresholds on p99 latency, not averages.
  • Bulkhead: identify your critical paths (checkout, payment) and isolate their resource pools from non-critical paths (search, analytics).
  • Outbox: every service that writes to a DB AND publishes to a broker needs this pattern. No exceptions.
  • Inbox: every consumer that has side effects (writes, charges, sends) must deduplicate. Check idempotency key in the same transaction as the business effect.
  • 2PC: do not use in microservices. Use Saga with compensating transactions instead.
  • Leader Election: use fencing tokens. A TTL alone is not sufficient against GC pauses or network partitions.
  • BFF: keep BFFs thin — aggregation and payload shaping only. Business rules belong in domain services.
  • Strangler Fig: invest in the facade/proxy upfront. Data migration is harder than routing migration.

FAQ

CQRS vs Read Replica — what is the difference?

A Read Replica is a copy of the same data model, kept in sync via database replication. A CQRS read model is a purpose-built projection with a different shape, potentially on a different database engine. Read Replicas are simpler and synchronised automatically; CQRS read models are richer but require explicit sync via events.

When should I choose Choreography Saga over Orchestration Saga?

Choreography works well for simple, linear flows with few services. As the number of participants grows or the flow has branching logic, choreography becomes undebuggable. Use orchestration whenever you need to reason about the overall transaction state. Most production systems at scale (Uber, Airbnb) gravitate toward orchestration.

Is the Sidecar the same as a service mesh?

The Sidecar is the pattern. A service mesh (Istio, Linkerd, Consul Connect) is an implementation of that pattern at platform scale. A service mesh deploys sidecars automatically and provides a control plane for configuring them uniformly.

Why is 2PC considered harmful in microservices?

Because it requires all participants to hold locks until the coordinator completes Phase 2. If the coordinator crashes, participants are blocked indefinitely — this is the blocking failure mode. In a distributed system where nodes fail independently, this guarantee cannot be reliably maintained. The Saga pattern replaces 2PC with compensating transactions at the cost of eventual (not immediate) consistency.

Can I combine Event Sourcing and CQRS?

Yes — this is the canonical combination. The event store is the write model. Every event written to the store is also published to downstream projectors that maintain CQRS read models. The event stream serves as the bridge between the two sides. Greg Young, who formalised CQRS, originally presented Event Sourcing as its natural companion.

What is the difference between Outbox and Transactional Messaging?

Transactional messaging is the general requirement: a message must be published if-and-only-if a transaction commits. The Outbox Pattern is the specific implementation: write to an outbox table in the same transaction, relay asynchronously. Kafka Transactions (via the transactional producer API) are an alternative when both writer and broker support transactional semantics.

Key Takeaway

These 18 patterns form a complete vocabulary for distributed systems design. The most important discipline is knowing when NOT to use each one — CQRS is not a default architecture, 2PC does not belong in microservices, Event Sourcing is not a free audit log. Every pattern carries an operational tax. The senior engineer's job is to identify the specific production failure mode first, then reach for the lightest pattern that resolves it. A system that thoughtfully applies five of these patterns in the right places will outperform one that blindly applies all eighteen.
