Two resources, from opposite ends of the crawling problem. The Olston and Najork survey is the academic map of the whole discipline: frontier, politeness, deduplication, freshness, traps. Google's dynamic rendering page is a snapshot of one specific modern pain: the content you want is not in the HTML, it is produced by JavaScript, and someone has to run the browser.

Core idea: a crawler is a scheduler with a conscience. The fetching is easy; deciding what to fetch next, how often, and how politely, while never doing the same work twice, is the engineering.

Resource 1

Web Crawling

What it is

"Web Crawling" by Christopher Olston and Marc Najork, published in Foundations and Trends in Information Retrieval (2010). It is a survey of crawler techniques from the research literature and of the engineering of large crawlers.

Reading note: my fetcher could not extract this PDF, so the points below are the standard topics of the survey and of crawler design, not a summary of its exact text. No quotes or numbers are taken from it.

The core loop

seed URLs -> URL frontier -> fetcher (DNS, robots.txt, HTTP) -> content store ^ | | parser: extract links + text | | +---- URL filter / "seen?" test <----------+ normalise, dedupe, prioritise, assign to host queue

Ideas to extract

  • The frontier is the brain. It has two jobs that pull in opposite directions: prioritise (important and stale pages first) and be polite (one host gets a request at a time, with a delay). The classic design uses front queues for priority feeding back queues, one per host, with a heap keyed on "next allowed time". My code does the simplest version of this.
  • Politeness: obey robots.txt, cap concurrent connections per host, honour crawl delay, and back off on slow responses or 429s. Politeness is also self-interest, since hosts block aggressive crawlers.
  • URL normalisation and "seen" test: lower-case host, remove fragments, resolve relative paths, canonicalise query parameters. A Bloom filter or hash set answers "have I queued this?"; at web scale this is a large distributed structure.
  • Content duplication: exact duplicates by hashing the body; near-duplicates by shingling and similarity sketches (MinHash or SimHash). Mirror sites and boilerplate pages are common.
  • Spider traps: calendars, session IDs in URLs, infinite redirects and query-parameter permutations. Defences: URL length and depth caps, per-host page budgets, pattern detection.
  • Freshness: pages change at different rates. Re-crawl scheduling is an optimisation problem: spend limited fetches where they raise the freshness of the index the most, which is not always the pages that change most often.
  • Distribution: partition by host (not by URL) across crawler nodes, so politeness is enforced locally, using consistent hashing; exchange discovered links between nodes in batches.

Senior commentary

The pragmatic lesson of every real crawler is that the hard parts are not in the happy path. DNS resolution becomes a bottleneck, so you cache it and run your own resolver. robots.txt must be cached with a refresh policy and treated as mandatory. Long-tail hosts are slow, so you need short timeouts and concurrency by hundreds or thousands of in-flight requests per node, not per thread. And you must be able to stop: a kill switch by host or by pattern matters the first time you annoy a site's operators.

Still true: architecture, politeness, deduplication, trap handling. Dated: assumptions that most content is static HTML, and the era-specific scale and storage numbers. Modern crawlers also care about JavaScript rendering, structured data, canonical tags and sitemaps, which the page below picks up.

Resource 2

Google Dynamic Rendering

What it is

A page in Google Search Central documentation. I read it. It describes a workaround and now presents it as a past practice rather than a recommendation.

The idea

Many sites build the page in the browser: the initial HTML is a shell and JavaScript fetches and inserts the content. A crawler that does not run JavaScript sees an empty shell. Dynamic rendering means the server detects a crawler (typically through the user agent) and sends it a pre-rendered, JavaScript-free HTML version, produced by a separate rendering service, while ordinary users keep getting the client-side app.

What the page says

  • Google Search can process JavaScript, but there are limitations, and other search engines may not process it at all.
  • Dynamic rendering is described as a workaround, not a long-term solution; Google points developers to server-side rendering, static rendering, or hydration instead.
  • It adds complexity and resource cost (a rendering server to run and keep in sync).
  • Google generally does not treat it as cloaking as long as the crawler and users receive similar content; serving substantially different content (the page's example is a cat page for users and a dog page for the crawler) is cloaking.

Senior commentary

For a crawler designer this is the other side of the table. Your options are: fetch raw HTML only (fast, cheap, misses client-rendered content), or add a rendering stage using a headless browser (accurate, perhaps ten to a hundred times more expensive per page in CPU and time). The usual pattern is tiered: fetch raw HTML, detect pages that look like empty shells (very little text, a single root element, a heavy script bundle), and send only those to a rendering pool, with strict timeouts, resource blocking and per-host budgets. Rendering is also where you meet infinite scroll, lazy loading, service workers and anti-bot systems.

Operational gotcha: the rendering pool executes untrusted code from the whole internet. Isolate it (containers or microVMs, no access to internal networks, tight egress rules) or you have built an SSRF launchpad.

Still true versus dated

The need to deal with JavaScript content is permanent; the specific technique is described by Google as outdated, so do not propose dynamic rendering for new sites in an interview. Do propose it as a crawler-side rendering stage.

  • Say "frontier" and describe both priority and politeness.
  • Always mention robots.txt and a per-host rate limit.
  • Explain how you detect duplicates at the URL and content level.
  • Mention JavaScript rendering as a costed, optional stage.
Numbers

Back-of-envelope arithmetic

  • Fetch rate: 1 billion pages per month is about 1,000,000,000 / 2,592,000 s, roughly 386 pages per second on average. Plan for peaks of two to three times that.
  • Bandwidth: at an average page of 100 KB, 386 pages per second is about 39 MB/s, about 310 Mbit/s of ingress, before compression.
  • Storage: 1 billion pages at 100 KB is 100 TB per month raw; compression and dropping duplicates commonly bring this down severalfold.
  • Politeness limits throughput per host: with a one second delay, a host yields at most 1 page per second per crawler; 386 pages per second therefore needs at least 386 distinct hosts in flight at all times. That, not CPU, is why large crawls need broad host diversity.
  • Rendering cost: if 10 percent of pages need rendering at 2 CPU-seconds each, that is 39 pages/s x 2 = about 78 cores kept busy, more than the fetch tier itself.
Code

Runnable example

JavaScript Example 
// Polite crawler frontier: per-host queues, crawl-delay, priority, URL dedup, simulated clock.
class Frontier {
  constructor({ delayMs = 1000 } = {}) { this.delay = delayMs; this.hosts = new Map(); this.seen = new Set(); }
  norm(u) { const x = new URL(u); x.hash = ''; x.hostname = x.hostname.toLowerCase(); if (x.pathname.length > 1 && x.pathname.endsWith('/')) x.pathname = x.pathname.slice(0, -1); return x.href; }
  add(u, prio = 5) { const n = this.norm(u); if (this.seen.has(n)) return false; this.seen.add(n);
    const h = new URL(n).host; if (!this.hosts.has(h)) this.hosts.set(h, { q: [], nextOk: 0 });
    const hq = this.hosts.get(h); hq.q.push({ n, prio }); hq.q.sort((a, b) => a.prio - b.prio); return true; }
  next(now) {                         // pick the ready host with the best head priority
    let best = null;
    for (const [h, hq] of this.hosts) if (hq.q.length && hq.nextOk <= now && (!best || hq.q[0].prio < best.hq.q[0].prio)) best = { h, hq };
    if (!best) return null; const item = best.hq.q.shift(); best.hq.nextOk = now + this.delay; return item.n;
  }
  pending() { let c = 0; for (const hq of this.hosts.values()) c += hq.q.length; return c; }
}
const web = {
  'https://a.com/': ['https://a.com/x', 'https://a.com/y/', 'https://b.com/', 'https://A.com/x#frag'],
  'https://a.com/x': ['https://a.com/y', 'https://c.com/'], 'https://a.com/y': [], 'https://b.com/': ['https://a.com/'], 'https://c.com/': [],
};
const f = new Frontier({ delayMs: 1000 }); f.add('https://a.com/', 1);
let now = 0; const fetched = [];
while (f.pending()) {
  const u = f.next(now);
  if (!u) { now += 100; continue; }
  fetched.push(`${now}ms ${u}`);
  for (const l of web[u] ?? []) f.add(l, u.includes('a.com') ? 5 : 3);
}
console.log(fetched.join('\n'));
const aTimes = fetched.filter(s => s.includes('a.com')).map(s => parseInt(s));
console.assert(aTimes.every((t, i) => i === 0 || t - aTimes[i - 1] >= 1000), 'politeness violated');
console.assert(new Set(fetched.map(s => s.split(' ')[1])).size === fetched.length, 'duplicates');
console.log('pages:', fetched.length, '- a.com gaps >= 1000ms:', true);

Prints the order in which pages are fetched with the simulated time; the output shows two pages fetched at once from different hosts, a one-second gap on the same host, and normalisation removing duplicate URLs. Executed with node; asserts pass.

Exercise

What to build

  1. Replace the linear scan in next() with a min-heap keyed on the host\'s next-allowed time.
  2. Add robots.txt support: a per-host cache with TTL and a parser for allow and disallow rules.
  3. Add a Bloom filter in front of the seen set and measure its false-positive rate at different sizes.
  4. Add a shell-page detector (text-to-markup ratio) and route flagged pages to a stub render queue with a concurrency cap.

Key Takeaway

A crawler is mostly a frontier: priority, politeness and duplicate suppression. The fetch loop is trivial, and the modern complication is content that needs a browser. Design for host diversity, make rendering a costed optional stage, and never forget the kill switch.

FAQ · Common Questions

Frequently Asked Questions

Why partition crawler nodes by host?

So all URLs of one host go to one node, which can enforce politeness locally without cross-node coordination.

Bloom filter or hash set for seen URLs?

A Bloom filter is compact and fast but has false positives, so a few new URLs are skipped. At web scale that is usually acceptable; keep an exact store for important sources.

How do you detect near-duplicate pages?

Shingle the text and compare sketches (MinHash or SimHash). Exact duplicates are found cheaply by hashing the normalised body.

Is dynamic rendering what I should propose in an interview?

No for site owners: Google recommends server-side rendering, static rendering or hydration. For a crawler, propose a rendering tier for pages that look like empty shells.

How do you avoid spider traps?

Depth limits, per-host page budgets, URL length caps, and pattern detection for calendars and session IDs, plus monitoring for hosts that generate huge numbers of unique URLs.
