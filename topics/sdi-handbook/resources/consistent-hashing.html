Consistent Hashing: From the Ring to Maglev — Reading Guide

A reading guide to five consistent hashing resources (White, CS168, Cassandra, Discord, Maglev) with commentary, a runnable ring, jump hash, bounded loads and Maglev table.

TypeResource guide · related chapters: Chapters 5, 6
Read time12 min
Core ideasring, vnodes, jump hash, bounded loads, Maglev hashing
Real systemsCassandra, Dynamo, Maglev, memcached/ketama, Discord

Five resources, and they form a ladder: a hands-on blog post that explains the ring, a university lecture that explains why it works, two production systems (Cassandra, Discord) that use it for data and process placement, and Google's Maglev, which shows that for load balancers the right question is not "how do I minimise movement" but "how do I keep every connection on its backend".

Core idea: consistent hashing is a family of techniques for assigning keys to a changing set of nodes with bounded disruption. The ring is one member. Which member you choose depends on whether you value minimal movement, perfect balance, lookup speed, or per-flow stickiness.

Resource 1

Consistent Hashing

What it is

A 2007 blog post by Tom White (author of Hadoop: The Definitive Guide), with a small Java implementation. It is a clear, code-first explanation.

Ideas it presents

  • The problem with mod-N: placing an object on cache hash(o) mod n reshuffles almost everything when n changes, so the origin gets flooded. My simulation: growing from 10 to 11 nodes moves about 91% of keys.
  • The ring: hash both nodes and objects into one circular number space; an object belongs to the first node clockwise. Add a node and it takes a slice from its neighbour; lose one and its keys fall to the next.
  • Hash quality matters: naive built-in hash codes cluster; use a well-mixing function (the post uses MD5, chosen for dispersion, not security).
  • Replicas (virtual nodes): one point per node gives wildly uneven arcs. Hash node + suffix many times. The author's experiment showed spread falling as replicas grow, reaching roughly 5 to 10 percent deviation at one to two hundred replicas.
  • Data structure: a sorted map; lookup is a "first key greater or equal, else wrap to first" query, so O(log V) for V total points.
hash space 0 ... 2^32, wraps n2#1 ● k1 ● n1#0 ● n1#2 k2 ● n3#1 key goes to the next point clockwise k1 -> n1#0 -> owner n1

Senior commentary

My own runs back the post's claim, and show why you must not trust a single point per node: with 1 point per node the busiest of ten nodes held 2.2 times the average; with 10, 1.43 times; with 150, 1.14 times. The cost is memory (V = nodes times vnodes entries to hold and sort) and slower topology changes. Also note the post mentions memcached clients: that is the pattern where only the client knows the ring and servers are oblivious, which is the cheapest deployment of the idea.

Dated: the post stops at plain vnodes. Since then we have jump consistent hash (Lamping and Veach, Google, 2014: no memory, perfect balance, but buckets must be numbered 0..N-1 and you can only add or remove at the end), rendezvous hashing, and bounded-load variants. The core ring idea is still what Cassandra, Dynamo and many caches use.

Connection

This is the whole spine of chapter 5 and the hub page. The chapter's "vnodes fix imbalance" step is exactly the experiment here.

Resource 2

CS168: Introduction and Consistent Hashing:

What it is

Lecture notes from Stanford's CS168 course, "The Modern Algorithmic Toolbox" (spring 2016), taught by Tim Roughgarden and Gregory Valiant. Lecture 1 introduces the course and consistent hashing as the first tool. This is the academic counterpart of the blog post.

What to take from it

The lecture frames consistent hashing as a design problem with two goals at once: spread keys evenly, and change little when the node set changes. From the standard treatment (Karger et al., 1997) the points worth knowing are:

  • Balance is a probabilistic statement. With random placement and a single point per server, the biggest arc is about log n times larger than the average, which is why virtual copies are needed. With about log n copies per server the maximum load is within a constant factor of average with high probability.
  • Movement is the opposite of mod-N: adding the n-th server moves roughly 1/n of the keys, which is the optimum, because the new server must receive at least that much.
  • Replication is a natural extension: store each item on the next several distinct servers clockwise.
Reading note: the PDF text could not be extracted by my fetcher, so the points above are the standard results, not a summary of that specific document's wording or examples. Read it yourself for the proofs and the author's presentation.

Senior commentary

The theory tells you the asymptotics but not the constants you live with. The practical lesson is to measure: simulate your key distribution against your vnode count before choosing. The "log n" result also explains why systems that started with 1 token per node (early Cassandra) later moved to 256 vnodes per node by default, and why later versions reduced that default again: more vnodes improves balance but makes repair, streaming and range queries more expensive.

Connection

It supplies the "why" behind the chapter's claim that vnodes give balance. Use it to answer the interview follow-up "how many virtual nodes, and why".

Resource 3

Google Maglev

What it is

"Maglev: A Fast and Reliable Software Network Load Balancer" (Eisenbud et al., NSDI 2016). It describes the L4 load balancer that fronts Google services, running as software on commodity Linux machines instead of dedicated hardware.

Mechanisms, from the paper as I know it

  • Scale out with ECMP: routers spread packets across many Maglev machines using equal-cost multipath. Any machine can take any packet, so no single machine is a bottleneck.
  • Kernel bypass packet path: the paper describes a user-space networking path to reach line-rate packet processing without per-packet system calls.
  • Flow-based backend choice: hash the connection five-tuple, look up a backend in a table.
  • Connection tracking: each machine remembers recent flows locally. That is a cache, not the source of truth; if routing shifts a flow to another Maglev machine, the consistent hash table should pick the same backend.
  • Maglev hashing: a lookup table of prime size M. Each backend has its own pseudo-random permutation of slots (an offset and a skip derived from its name). Backends take turns claiming their next unclaimed preferred slot until the table is full. Lookup is one array read: table[hash(flow) mod M].
backend preference order (offset + i*skip) mod M be0 3 7 4 1 ... be1 0 2 4 6 ... round 1: be0 takes 3, be1 takes 0, be2 takes ... round 2: ...continue until every slot owned

Senior commentary

This is the instructive counterpoint to the ring. Maglev hashing gives near-perfect balance (my simulation of 10 backends and 65,537 slots: every backend holds 6,553 or 6,554 slots) and O(1) lookup, in exchange for a table rebuild when backends change and slightly more churn than the ideal. In my run, removing one of ten backends reassigned only 0.4% of the surviving backends' slots, though the paper trades a little disruption for the balance. A rebuild is fine when the backend set changes rarely, as it does in a data centre, and not fine for a database with thousands of dynamic partitions.

Also note the philosophy: consistent hashing here is a safety net for connection tracking, not the main mechanism. This is how you design when a wrongly-routed packet means a broken TCP connection.

Still true versus dated

The architecture (ECMP, software forwarding, flow hashing) is standard, and Maglev hashing was reused by Envoy and Katran-style load balancers. Specific throughput numbers in the paper are of 2016 hardware, so do not quote them as current.

Resource 4

Apache Cassandra

What it is

"Cassandra: A Decentralized Structured Storage System" by Avinash Lakshman and Prashant Malik (LADIS 2009), written at Facebook where the system powered inbox search. The repo link points to this paper. It is short, about six pages.

Ideas

  • Partitioning: an order-preserving or random hash of the row key places it on a ring. Each node has a position, and the ring owner and following nodes hold the replicas.
  • Replication: a coordinator forwards writes to N replicas; policies can be rack-aware or datacenter-aware.
  • Membership and failure detection: a gossip protocol spreads cluster state, and an accrual failure detector produces a suspicion level instead of a binary up/down.
  • Storage engine: commit log, in-memory table, immutable on-disk files merged by compaction, a lineage borrowed from Bigtable.
  • Lessons the authors note: the original ring placement was uneven, and they discuss moving nodes along the ring to rebalance, which later evolved into virtual nodes.

Senior commentary

The page I could actually fetch about modern Cassandra (the DataStax 3.0 architecture overview) confirms what survived: peer nodes with no primary, gossip, a partitioner that hashes the primary key into a token (Murmur3 by default), replication factor per datacenter, snitches for topology, and the commit log to memtable to SSTable write path. What changed is the placement: vnodes via num_tokens replaced one-token-per-node and manual rebalancing. If you only read one section, read how a key's token selects the replica set, because that is consistent hashing applied to a database.

Resource 5

Scaling Discord

What it is

A Discord engineering blog post on scaling their Elixir/Erlang-based real-time services (the URL slug says "scaling elixir"). The old blog.discord.com address now redirects, and when I followed it I received the blog index, not the article. I therefore do not summarise the post's specifics or numbers.

What I can say responsibly

Real-time chat platforms in the Erlang family assign each "room" (a Discord server is called a guild) to one long-lived process, and a routing layer must find which node owns it. A consistent hash ring over the node list is the natural answer: any node can compute the owner locally, and membership changes move only a slice of rooms. That is why this link sits in the consistent hashing group. This is a different use from the others: the thing being placed is not data but live state with a single owner, so moving it is far more disruptive than moving a cached key, and you want the slowest possible churn.

Interview angle: distinguish "placement of data" (can be re-fetched, copy in background) from "placement of actors" (state must be handed off or rebuilt, ordering must be preserved). Rings serve both, but the operational cost differs.

Code

Runnable example

JavaScript Example 
import { createHash } from 'node:crypto';
const h32 = s => createHash('md5').update(s).digest().readUInt32BE(0);

class Ring {
  constructor(vnodes = 150) { this.v = vnodes; this.pts = []; this.nodes = new Set(); }
  add(n) { this.nodes.add(n); for (let i = 0; i < this.v; i++) this.pts.push([h32(`${n}#${i}`), n]); this.pts.sort((a, b) => a[0] - b[0]); }
  remove(n) { this.nodes.delete(n); this.pts = this.pts.filter(p => p[1] !== n); }
  _idx(k) { const x = h32(k); let lo = 0, hi = this.pts.length; while (lo < hi) { const m = (lo + hi) >> 1; if (this.pts[m][0] < x) lo = m + 1; else hi = m; } return lo % this.pts.length; }
  get(k) { return this.pts[this._idx(k)][1]; }
  // bounded loads (Mirrokni et al.): cap = ceil(c * avg); walk clockwise past full nodes
  getBounded(k, load, cap) { let i = this._idx(k); for (let s = 0; s < this.pts.length; s++, i = (i + 1) % this.pts.length) { const n = this.pts[i][1]; if ((load.get(n) ?? 0) < cap) return n; } throw new Error('full'); }
}

// Jump consistent hash (Lamping & Veach) using BigInt for 64-bit math
function jump(key, buckets) {
  let k = BigInt(key) & 0xffffffffffffffffn, b = -1n, j = 0n;
  while (j < BigInt(buckets)) { b = j; k = (k * 2862933555777941757n + 1n) & 0xffffffffffffffffn; j = BigInt(Math.floor(Number(b + 1n) * (2 ** 31 / Number((k >> 33n) + 1n)))); }
  return Number(b);
}

const keys = Array.from({ length: 20000 }, (_, i) => `key-${i}`);
const spread = r => { const m = new Map(); for (const k of keys) m.set(r.get(k), (m.get(r.get(k)) ?? 0) + 1); const v = [...m.values()]; const avg = keys.length / r.nodes.size; return (Math.max(...v) / avg).toFixed(2); };

for (const v of [1, 10, 150]) {
  const r = new Ring(v); for (let i = 0; i < 10; i++) r.add(`n${i}`);
  console.log(`vnodes=${v}: max/avg load = ${spread(r)}`);
}
const r = new Ring(150); for (let i = 0; i < 10; i++) r.add(`n${i}`);
const before = new Map(keys.map(k => [k, r.get(k)])); r.add('n10');
const moved = keys.filter(k => r.get(k) !== before.get(k)).length;
console.log(`ring add 11th node: moved ${(100 * moved / keys.length).toFixed(1)}% (ideal 9.1%), mod-N would move ~${(100 * (1 - 1 / 11)).toFixed(0)}%`);
console.assert(moved / keys.length < 0.15 && moved / keys.length > 0.04);

const mod = keys.filter(k => h32(k) % 10 !== h32(k) % 11).length;
console.log(`mod-N 10->11 actually moved ${(100 * mod / keys.length).toFixed(1)}%`);

let jm = 0; for (let i = 0; i < 20000; i++) if (jump(i, 10) !== jump(i, 11)) jm++;
console.log(`jump hash 10->11 moved ${(100 * jm / 20000).toFixed(1)}%`);

const r10 = new Ring(150); for (let i = 0; i < 10; i++) r10.add(`n${i}`);
const unb = new Map(); for (const k of keys) unb.set(r10.get(k), (unb.get(r10.get(k)) ?? 0) + 1);
const load = new Map(); const cap = Math.ceil(1.05 * keys.length / 10);
for (const k of keys) { const n = r10.getBounded(k, load, cap); load.set(n, (load.get(n) ?? 0) + 1); }
console.log(`max load: plain ring = ${Math.max(...unb.values())}, bounded (c=1.05) = ${Math.max(...load.values())}, cap = ${cap}`);
console.assert(Math.max(...load.values()) <= cap);

// Maglev table: each backend walks its own permutation of slots; backends take turns claiming free slots.
function maglev(backends, M = 65537) {              // M must be prime
  const perm = backends.map(b => ({ off: h32(b + ':off') % M, skip: (h32(b + ':skip') % (M - 1)) + 1, next: 0 }));
  const table = new Array(M).fill(-1); let filled = 0;
  while (true) for (let i = 0; i < backends.length; i++) {
    let c; do { c = (perm[i].off + perm[i].next * perm[i].skip) % M; perm[i].next++; } while (table[c] >= 0);
    table[c] = i; if (++filled === M) return table;
  }
}
const names = Array.from({ length: 10 }, (_, i) => `be${i}`);
const t1 = maglev(names), t2 = maglev(names.slice(0, 9));
const slots = new Array(10).fill(0); t1.forEach(i => slots[i]++);
let churn = 0; for (let s = 0; s < t1.length; s++) if (t1[s] !== 9 && t1[s] !== t2[s]) churn++;
console.log(`maglev slots per backend: min ${Math.min(...slots)} max ${Math.max(...slots)}; surviving-slot churn after removing be9: ${(100 * churn / t1.length).toFixed(1)}%`);
console.assert(Math.max(...slots) - Math.min(...slots) <= 1);

Prints the max-to-average load for 1, 10 and 150 vnodes, keys moved by adding a node (ring about 8.5 percent versus mod-N about 91 percent), jump hash movement, a bounded-load cap being honoured, and a Maglev table with near-equal slot counts. Executed with node; asserts pass.

Exercise

What to build

  1. Extend the ring with weights so a node with twice the capacity gets twice the vnodes; verify the share ratio.
  2. Add replica placement: for each key, return the next three distinct nodes clockwise, skipping vnodes of the same node and, optionally, the same rack.
  3. Rebuild the Maglev table with 100 backends and measure how much of the table changes for one removal across several table sizes.
  4. Write a test that proves the bounded-load variant never exceeds ceil(c x average) even while a node is being removed.

Key Takeaway

The ring is the default, but it is not the idea. The idea is a deterministic mapping with bounded disruption, and every resource here picks a different point on the trade-off between balance, movement, speed and stickiness. Know all four corners.

FAQ · Common Questions

Frequently Asked Questions

How many virtual nodes should I use?

Enough that the max-to-average load fits your tolerance. In my simulation 150 per node gave about 1.14 times the average; Cassandra historically defaulted to 256 and later reduced it. More vnodes means better balance but costlier repair and bigger routing tables.

Why not just use mod N with a big prime?

The modulus still changes when N changes. Pre-sharding into many fixed logical partitions (like Redis Cluster 16384 slots) is a good alternative: partitions map to nodes via a table you move explicitly.

When is jump hash better than a ring?

When buckets are numbered contiguously and only grow or shrink at the end, for example sharded storage replicas. It cannot remove an arbitrary node.

How does a hot key interact with consistent hashing?

It does not help: all requests for one key still land on one node. Use replication for reads, key splitting, or local caching.

Why does Maglev use a table instead of a ring?

Lookup speed and balance. Packet forwarding needs a single memory read per packet, and the backend set rarely changes.
