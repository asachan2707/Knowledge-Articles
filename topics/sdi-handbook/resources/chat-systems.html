Chat Systems: Reading Guide

A reading guide to two engineering posts on chat at scale: Discord's bucketed Cassandra message store and Slack's Flannel edge cache for client bootstrap.

TypeResource guide · related chapters: Chapter 12
Read time13 min

Chapter 12 of the handbook asks you to design a chat system on a whiteboard. The two resources attached to it are the opposite of a whiteboard: one is a post-migration report on where a billion-message-scale history store actually hurt, the other is an account of how a client/server contract that was fine for small teams fell over for big ones. Together they teach the two lessons interview answers usually skip: storage layout is decided by access pattern and partition size, not by the logical model, and the biggest cost in a chat product is often the connect/reconnect path, not the steady-state message path.

Core idea: Discord's post is a lesson in choosing a partition key and then bounding partition size; Slack's Flannel post is a lesson in not shipping the world to every client. Read both with the question "what grows without bound here, and who pays for it?"

Resource 1

How Discord stores billions of messages

What it is

An engineering-blog post from Discord describing why they moved their message history out of a single MongoDB replica set and into Cassandra, what the schema looked like, what went wrong in production, and what they changed. It was written about a year after the migration, when the team was still very small (the post mentions four backend engineers and no dedicated ops staff), which is part of why it reads as practical rather than polished.

The story in order

  • Start simple on purpose. The first version kept all messages in one MongoDB collection with a single compound index on channel and creation time. Sharding was deliberately avoided, and a migration was assumed from day one. This is the correct way to start: the point of a v1 is to find out what the workload is.
  • The trigger was memory, not volume. At roughly the hundred-million-message mark, data and index no longer fit in RAM and latency became unpredictable. The lesson is that a B-tree index that stops fitting in memory turns every random read into disk I/O, and chat history is a random-read workload (people jump to old messages, reply links, search results, pins).
  • Requirements were written down before choosing. Linear scalability, automatic failover, low maintenance, proven technology, predictable latency without a separate cache tier, and not being a blob store. Cassandra was the only candidate meeting all of them. Notice the explicit non-goal of putting Redis or Memcached in front: they wanted the database itself to have flat latency.
  • Workload shape drove the design. Three kinds of communities with very different profiles: voice-heavy servers with almost no text history, private friend groups with modest history that rarely stays cached, and giant public servers where recent data is hot. The first two produce cache misses; only the third behaves like a classic cache-friendly workload. A design that works only for the third would have failed the first two.

The schema and the bucketing trick

Cassandra can be thought of as a key-key-value store: the partition key decides which replicas own the data, and the clustering key decides the on-disk order inside the partition. The first design used the channel as partition key and a time-sortable message ID (a Snowflake) as clustering key. That gives you the access path the product needs, "newest N messages in this channel", as a single sequential read on one replica set.

The problem: a partition per channel is unbounded. The post reports early warnings about partitions over about 100 MB and notes that big partitions strain the JVM's garbage collector during compaction and cannot be split across nodes. The fix was to make time part of the partition key: group messages into windows of roughly ten days, so the partition key becomes (channel, bucket). The bucket is derived from the message ID or timestamp, so no lookup table is needed.

  Before:  PK = channel_id                 one ever-growing partition per channel
           CK = message_id (snowflake)

  After:   PK = (channel_id, bucket)       bucket = time window of ~10 days
           CK = message_id  DESC

  read "latest 50":
     bucket(now) --> bucket(now)-1 --> bucket(now)-2 ... until 50 rows found
     (stop at the bucket of the channel's first message)

The cost of bucketing is the read path: a quiet channel might need to walk many empty buckets to collect a page of history. That sets up the post's best story.

Dark launch and the surprises

  • Eventual consistency bit immediately. They double-wrote to Mongo and Cassandra and saw rows with missing authors. Cassandra writes are upserts with last-write-wins per column, so a concurrent edit and delete could resurrect a partial row. Their remedy was to treat such rows as corrupt and delete them, rather than rewriting whole messages, which would risk undeleting content.
  • Nulls are not free. Writing a null column creates a tombstone. Most messages populate only a handful of the sixteen columns, so naive writes created a dozen needless tombstones each. Writing only the populated columns removed that overhead. This is a general Cassandra rule worth memorising: never write "empty" values.
  • Result. Writes were sub-millisecond and reads in the low single-digit milliseconds, steady across a week of testing, including jumps to very old messages in huge channels. They made Cassandra primary and retired Mongo within a week.

The tombstone incident

About half a year later the cluster began suffering repeated multi-second stop-the-world GC pauses. The cause was a public channel that took around twenty seconds to load and contained exactly one message: millions had been deleted via the API, and each read scanned millions of tombstones, generating garbage faster than the JVM could reclaim it. They shortened tombstone lifetime (safe because they ran regular repairs) and changed the reader to remember empty buckets so that a read does not rescan them.

Senior takeaway: in an LSM store, deletes are writes, and a "range scan over deleted data" is the classic failure. Any chat design with delete-heavy channels (bots, moderation purges, retention jobs) must plan for tombstone volume and for reads that skip empty ranges.

Scale numbers the post gives

Message volume grew from tens of millions per day to over a hundred million per day during the time covered. The cluster at publication was twelve nodes, replication factor three, close to a terabyte of compressed data per node. Future plans listed in the post were Cassandra 3's more compact storage format, larger per-node data, and evaluating Scylla for faster repairs.

What still holds, and what is dated

  • Still true: partition key choice is the architecture; bound partition size using time; Snowflake-style IDs give you ordering and a cheap bucket function; tombstones and GC are the operational enemy; test with dual writes before cutover.
  • Dated: the specific cluster size, the Cassandra 2 era GC behaviour, and the hardware choices. Discord has since written publicly about a later generation of this system (a move to a C++ Cassandra-compatible database and a service layer in front of it that coalesces duplicate requests for hot data); I did not re-read that follow-up for this guide, so consider it a pointer rather than a source.

How it connects to Chapter 12

The chapter's message store discussion usually says "use a key-value store with horizontal scaling, because history is huge and read-heavy for recent items". This post gives the missing detail: the key is (conversation, time bucket), ordering within it is by a time-sortable ID, and the ID doubles as the message sequence. It also supplies a realistic answer to "what happens when someone deletes a million messages?" which almost no whiteboard answer addresses.

Resource 2

Flannel: An Application-Level Edge Cache to Make Slack Scale

What it is

A Slack engineering post (published in 2017) about a service called Flannel: a purpose-built cache deployed at edge locations that sits between Slack clients and the main application servers. It exists to solve a problem created by an early product assumption, not a storage problem.

The problem

Slack's client was designed to start by downloading a full snapshot of the team: users, channels, memberships, recent messages. Then it opened a WebSocket for live events. For a small team this is excellent because everything is local and instant. For teams with tens of thousands of members it degrades in four ways the post lists: slow startup, a large in-memory footprint on the client, reconnects that cost almost as much as first load, and reconnection storms in which a whole office loses and regains network at once and the combined load makes everything slower, causing more retries.

The design

  client --> Flannel (edge PoP) --WebSocket--> Slack servers (main region)
                |  caches users, channels, bots
                |  returns a *slim* bootstrap payload
                |  answers queries on demand (e.g. quick switcher autocomplete)
                v
  client lazily asks Flannel for objects it actually needs
  • Slim boot, lazy load, query-on-miss. The client receives minimal data up front and fetches channels or users when the UI needs them. The quick switcher is the example: typing sends prefix queries to Flannel instead of searching a local copy of every user.
  • Proactive push. If an incoming message mentions a user the client has not loaded, Flannel pushes that user's record just ahead of the message, saving a round trip. That is a neat piece of latency engineering: the cache predicts the next query from the stream.
  • Affinity via consistent hashing. Requests from the same team and network region are routed to the same Flannel instance, so cache hit rate is high and memory is not duplicated across the fleet.
  • Freshness. Flannel itself holds a WebSocket to the main-region servers and consumes the same real-time events as a client would. The post does not describe a separate invalidation protocol; the event stream is the consistency mechanism.

Numbers reported

At the time of writing, peaks of about four million simultaneous connections and about six hundred thousand client queries per second. Bootstrap payload shrank by roughly 7x for a team of about 1,500 users and about 44x for a team of about 32,000. The post also says presence events delivered to clients dropped by about 5x after moving presence to a publish/subscribe model, and sketches future work: moving fan-out into Flannel so that one copy per edge server, not one per user, crosses the backbone.

What still holds, and what is dated

  • Still true: do not make clients download whole datasets; subscribe to what is visible; cache close to users; use consistent hashing for affinity; presence is a fan-out amplifier and should be subscription-based.
  • Dated or unstated: exact scale figures; the post says little about failure behaviour of the cache tier itself, so you must reason about it yourself (what happens when an edge node dies and its team is rehashed elsewhere? A cold cache for a large team is another reconnect storm).

How it connects to Chapter 12

The chapter treats presence and online-status fan-out as an add-on. Flannel shows the real cost: with N members in a team, naive presence is O(N) events per change and O(N) state per client. The practical remedies are the ones the post names: lazy loading, subscription scoping, and an edge tier that collapses duplicate work. It also reinforces the chapter's choice of WebSockets for the live channel while pointing out that the initial sync is a separate problem that deserves its own design.

Synthesis

How the Two Resources Fit Together

They cover the two halves of a chat product. Discord's post is the cold path: durable history, read on demand, in bounded partitions. Flannel is the hot path and the connect path: what a client sees at login, how presence and lookups are served, and how to survive everyone reconnecting at once. A complete answer uses both: a bucketed, time-sorted store behind a history API; a WebSocket tier for live delivery; an edge cache for roster-style data; and subscription-scoped presence.

Code

Bucketed Message Store with Snowflake-Style IDs

This example models the schema from Discord's post: partition key (channel, bucket), clustering by a time-sortable ID, and a reader that walks buckets backwards. The second scenario reproduces the quiet-channel problem: with one old message, fetching the latest page must scan every bucket in between, which is exactly what remembering empty buckets avoids.

JavaScript Example 
// Discord-style bucketed message store: partition key (channelId, bucket), clustering key messageId (Snowflake).
const EPOCH = 1420070400000n;           // Discord's public epoch (2015-01-01)
const BUCKET_MS = 10n * 24n * 3600n * 1000n; // ~10 days of time per bucket
let seq = 0n;
const snowflake = (ms) => ((BigInt(ms) - EPOCH) << 22n) | (seq++ & 0x3fffn); // time | sequence (worker bits omitted)
const bucketOf = (id) => (id >> 22n) / BUCKET_MS;

class Store {
  constructor() { this.parts = new Map(); this.bucketReads = 0; this.firstBucket = new Map(); }
  key(ch, b) { return `${ch}:${b}`; }
  write(ch, id, text) {
    const b = bucketOf(id), k = this.key(ch, b);
    if (!this.parts.has(k)) this.parts.set(k, []);
    const rows = this.parts.get(k);
    rows.push({ id, text });
    rows.sort((x, y) => (x.id < y.id ? 1 : -1));   // clustering order: newest first
    if (!this.firstBucket.has(ch) || b < this.firstBucket.get(ch)) this.firstBucket.set(ch, b);
  }
  delete(ch, id) {
    const rows = this.parts.get(this.key(ch, bucketOf(id)));
    const i = rows.findIndex((r) => r.id === id);
    if (i >= 0) rows.splice(i, 1);
  }
  // newest `limit` messages: walk buckets backwards from the bucket of `beforeId`
  latest(ch, nowId, limit) {
    const out = []; this.bucketReads = 0;
    for (let b = bucketOf(nowId); b >= this.firstBucket.get(ch) && out.length < limit; b--) {
      this.bucketReads++;
      for (const r of this.parts.get(this.key(ch, b)) ?? []) { if (out.length < limit) out.push(r); }
    }
    return out;
  }
}

const day = 24 * 3600 * 1000, t0 = Number(EPOCH) + 400 * day;
const s = new Store(), ch = "general";
const ids = [];
for (let d = 0; d < 60; d += 5) { const id = snowflake(t0 + d * day); ids.push(id); s.write(ch, id, `msg day ${d}`); }
const now = snowflake(t0 + 61 * day);
let got = s.latest(ch, now, 3);
console.log("latest 3:", got.map((m) => m.text), "buckets read:", s.bucketReads);
// ordering check: ids strictly increase with time
console.assert(ids.every((v, i) => i === 0 || v > ids[i - 1]), "snowflake order");
console.assert(got[0].text === "msg day 55");
// quiet channel: only one old message -> reader must walk many empty buckets
const quiet = new Store(); quiet.write("q", snowflake(t0), "old one");
const later = snowflake(t0 + 300 * day);
got = quiet.latest("q", later, 50);
console.log("quiet channel:", got.length, "message, buckets scanned:", quiet.bucketReads);
console.assert(got.length === 1 && quiet.bucketReads > 25);

Executed with Node 24. Prints the three newest messages (reading 3 buckets), then shows a quiet channel with a single message forcing 31 bucket reads. The assertions pass silently.

Build exercise

What to Build

  • Extend the store above with delete support that writes a tombstone marker, and add a counter for tombstones scanned per read. Delete 100,000 messages from one channel and measure how reads degrade.
  • Add the "remember empty buckets" optimisation (a per-channel map of the oldest and newest non-empty bucket) and show the scanned-tombstone count drops.
  • Write a toy Flannel: an in-memory cache keyed by team, fed by an event stream, with a boot() that returns a slim payload and a query(prefix) that serves autocomplete. Simulate 1,000 clients reconnecting simultaneously with and without the cache and compare backend calls.

Key Takeaway

Chat storage is a partition-key problem with a bounded-growth rule, and chat clients are a connect-path problem with a bounded-state rule. Both resources show a system that worked until one unbounded thing (a partition, a payload) stopped fitting, and the fix was to bound it.
