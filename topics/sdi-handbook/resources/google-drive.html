Resource 1

Differential Synchronization

What it is

An essay by Neil Fraser (of Google, written around 2009) describing the algorithm that powered collaborative editing in Google's early real-time products. It positions itself against two incumbents: locking and operational transformation, and it proposes something simpler: repeatedly diff, send the diff, patch.

The loop

Each endpoint keeps, besides its live text, a shadow: its copy of what the other side last saw. A sync cycle on one side is: (1) diff the live text against the shadow to get the user's recent edits; (2) copy the live text into the shadow; (3) send the edits; the receiver applies them to its own live text on a best-effort basis and to its shadow strictly. Then the roles swap. Both directions run continuously in the background and never need the document to be quiet.

   Client text --diff vs Client Shadow--> edits ------------------------+
        ^                                                               v
        |                                                      patch Server Shadow (strict)
   patch (fuzzy)                                                patch Server text   (fuzzy)
        ^                                                               |
        +------- edits <--diff vs Server Shadow-- Server text <---------+

Why it works

  • Fuzzy patching. A patch carries context, so it can be applied to text that has changed since. If the context no longer matches, the patch simply fails. That is acceptable: the failed change shows up again in the next diff and is effectively reverted at its origin, so the system converges to a state where both sides agree, even if one edit was lost.
  • Strict shadows. The shadow patch is guaranteed to apply cleanly, because the shadow equals the sender's previous text; only the live-text patch is fuzzy.
  • Semantic diffs. Diffs should be human-meaningful (word-level), not minimal at the character level, or two concurrent edits to one word can blend into nonsense. The essay gives a cat-versus-cut-versus-hag illustration.
  • Any content type works if you have a diff and a fuzzy patch for it.

Reliability: version numbers and the edit stack

Over an unreliable network, each edit batch is tagged with the sender's shadow version, and each message acknowledges the version of the other side's last accepted edit. Unacknowledged edits stay on a stack and are resent every cycle until acknowledged. The server also keeps a backup shadow, the previous version, so it can recover when a response was lost: it sees a version mismatch but a matching backup, rolls back to the backup, discards the already-processed edit, applies the new one, and continues. The essay walks through duplicate, lost-outbound, lost-return and out-of-order packets, and says anything worse should reinitialise rather than loop forever. A checksum accompanies edits; on mismatch the full text is retransmitted.

Design principle: state the invariants (the shadow equals the peer's last known text), make the protocol idempotent with version numbers, and fall back to a full resync. That trio is what you want from any sync protocol, including file sync.

The comparison with other approaches

ApproachEssay's critique
LockingBlocks real-time collaboration; lost unlock messages leave nobody owning the lock.
Event passing / operational transformationNeeds every user action captured and transformed; one lost operation forks the document; not naturally convergent.
Three-way mergeHalf-duplex: if the user edits while a sync is in flight, the incoming version may be discarded.
Differential syncSymmetric, continuous, self-healing, tolerates unreliable networks.

Scaling and limits

Many clients can share one server text; the load can be spread by load-balanced servers over shared storage or by tree-shaped server links. Diff cost grows quadratically with the size of the change, so frequent diffs of small changes are cheap; sync intervals can adapt (shorter when active, longer when idle). Limits per the essay: one packet in flight at a time hurts high-latency links, and edits from different users blend together, so attribution and per-user undo are hard.

What is still true, what is dated

  • Still true: shadow-copy and diff protocols underlie many sync systems (rsync-like delta transfer, Dropbox-style block diffs, git). The self-healing and idempotent-ack design remains good practice.
  • Dated or contested: industry practice for rich collaborative editing moved towards operational transformation (Google Docs later used OT, as widely reported) and CRDTs (Yjs, Automerge), which preserve intent and per-user attribution better. Differential sync's "a failed patch just reverts" is fine for a text box and unacceptable for a spreadsheet cell or a structured document. I am relying on general industry knowledge here, not on the essay.

How it connects to Chapter 15

The chapter's conflict-resolution section (first version wins, the loser is saved as a conflict copy) is the file-level answer: coarse, safe, and loses nothing. Fraser's algorithm is the fine-grained alternative for documents. The chapter's block-level delta sync (send only changed blocks) is the same diff-the-shadow idea at 4 MB granularity instead of words. When an interviewer asks "what about real-time collaboration?", this essay is your answer, plus the OT/CRDT caveat above.

Resource 3

How We've Scaled Dropbox

Video, not read in full. From the title it is a talk about scaling Dropbox, and I will not describe its content. For context, here is what is generally and publicly known about block-based file sync (this is background, not claims about the talk):

  • Files are split into fixed-size blocks (a figure of about 4 MB is widely cited for Dropbox), each block hashed by content. Only blocks the server has never seen are uploaded, which gives both delta sync and cross-user deduplication.
  • The metadata (file tree, versions, block lists) lives in a database that must be strongly consistent per account and is the harder thing to scale; block storage is a comparatively simple content-addressed object store.
  • Clients learn about changes through a notification channel (long polling or a socket) and then fetch metadata deltas.

Chapter 15 covers the same pieces (block servers, metadata DB, notification service, cold storage for old versions). When you watch the talk, check whether and how it addresses metadata sharding, which the chapter treats lightly.

Code

Differential Synchronization with Edit Stack and Fuzzy Patching

A compact implementation of the protocol: word-level LCS diff producing hunks with preceding context, a strict patch for shadows and a fuzzy one for live text, version numbers with acknowledgement, and resend of unacknowledged edits. The scenarios: concurrent non-overlapping edits merge; a lost message is repaired by resending from the stack; a conflicting edit to the same word converges to one side's version.

JavaScript Example 
// Differential synchronization (Fraser): shadow + diff + fuzzy patch, with edits stack & version numbers.
const tok = (s) => s.match(/\s+|[^\s]+/g) ?? [];
function diff(a, b) {           // word-level LCS -> hunks {at (token index in a), del[], ins[], ctx (preceding text)}
  const A = tok(a), B = tok(b), n = A.length, m = B.length;
  const L = Array.from({ length: n + 1 }, () => new Array(m + 1).fill(0));
  for (let i = n - 1; i >= 0; i--) for (let j = m - 1; j >= 0; j--)
    L[i][j] = A[i] === B[j] ? L[i + 1][j + 1] + 1 : Math.max(L[i + 1][j], L[i][j + 1]);
  const hunks = []; let i = 0, j = 0, h = null;
  const flush = () => { if (h) { hunks.push(h); h = null; } };
  while (i < n || j < m) {
    if (i < n && j < m && A[i] === B[j]) { flush(); i++; j++; continue; }
    h ??= { at: i, del: [], ins: [], ctx: A.slice(Math.max(0, i - 3), i).join("") };
    if (j < m && (i >= n || L[i][j + 1] >= L[i + 1][j])) h.ins.push(B[j++]); else h.del.push(A[i++]);
  }
  flush(); return hunks;
}
function patch(text, hunks, strict = false) {   // fuzzy: find ctx+del near expected spot; failed hunks are skipped
  let t = text, failed = 0;
  for (const h of hunks.slice().reverse()) {
    const needle = h.ctx + h.del.join("");
    const pos = t.indexOf(needle);
    if (pos < 0) { failed++; if (strict) throw new Error("shadow mismatch"); continue; }
    t = t.slice(0, pos + h.ctx.length) + h.ins.join("") + t.slice(pos + needle.length);
  }
  return { text: t, failed };
}
class Peer {
  constructor(name, text) { this.name = name; this.text = text; this.shadow = text; this.n = 0; this.m = 0; this.stack = []; }
  // one half-cycle: diff text vs shadow, snapshot, queue edits with version n
  produce() {
    const hunks = diff(this.shadow, this.text);
    if (hunks.length) { this.stack.push({ n: this.n, hunks }); this.n++; }
    this.shadow = this.text;
    return { ack: this.m, edits: this.stack.slice() };      // resend everything unacknowledged
  }
  receive(msg) {
    this.stack = this.stack.filter((e) => e.n >= msg.ack);  // drop acknowledged edits
    for (const e of msg.edits) {
      if (e.n < this.m) continue;                           // duplicate: already applied
      this.shadow = patch(this.shadow, e.hunks, true).text; // shadow patch is strict
      const r = patch(this.text, e.hunks);                  // live text patch is fuzzy
      this.text = r.text; this.m = e.n + 1;
    }
  }
}
const base = "The quick brown fox jumps over the lazy dog today";
const client = new Peer("client", base), server = new Peer("server", base);
client.text = "The quick red fox jumps over the lazy dog today";          // client edit
server.text = "The quick brown fox jumps over the sleepy dog today!";     // concurrent server edit
const sync = (from, to) => to.receive(from.produce());
sync(client, server);      // server gets "red" while it has its own edits
sync(server, client);      // client gets "sleepy" and "!"
sync(client, server);
console.log("client:", client.text);
console.log("server:", server.text);
console.assert(client.text === server.text && client.text === "The quick red fox jumps over the sleepy dog today!");
// lost packet: client's message dropped, edits stay on the stack and are resent
client.text += " Bye"; client.produce(); /* lost */ client.text += "!!";
sync(client, server);
console.log("after loss+resend:", JSON.stringify(server.text), "stack size at client:", client.stack.length);
console.assert(server.text.endsWith("Bye!!"));
sync(server, client);      // ack
console.assert(client.stack.length === 0);
// conflicting edit on the same words: fuzzy patch fails on one side, the next diff converges
const a = new Peer("a", "I like Macs a lot"), b = new Peer("b", "I like Macs a lot");
a.text = "I like Macintoshes a lot"; b.text = "I like Smith & Wesson a lot";
sync(a, b); sync(b, a); sync(a, b);
console.log("conflict converged:", a.text === b.text, "->", a.text);
console.assert(a.text === b.text);

Executed with Node 24. Prints both peers converging to "The quick red fox jumps over the sleepy dog today!", the server catching up after a lost message with a client stack size of 2, and "conflict converged: true". The assertions pass silently.

Key Takeaway

File sync and document sync are different problems. Files: content-hashed blocks, metadata database, conflict copies. Documents: continuous diff against a shadow with fuzzy patches, acknowledged by version numbers. Fraser's design is simple and self-healing; know its limits against OT and CRDTs.
