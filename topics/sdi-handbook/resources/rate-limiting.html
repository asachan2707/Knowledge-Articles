Rate Limiting: Circuit Breakers and Pacers — Reading Guide

A reading guide to Fowler's circuit breaker note and Uber's Go rate limiter, with commentary, a runnable breaker and pacer, and an exercise.

Read time9 min

Real systemsResilience4j, Hystrix, uber-go/ratelimit, Envoy

Two short resources sit under the rate-limiter chapter, and they teach complementary halves of the same discipline. Fowler's circuit-breaker note is about protecting yourself from a dependency that is failing. Uber's ratelimit library is about protecting others (or yourself) from too much traffic by pacing calls. Together they cover both directions of load-shedding.

Core idea: a limiter decides how fast work may flow; a breaker decides whether work should flow at all. Production systems need both, and they should be tuned to fail in different, predictable ways.

How to use this guide

Scope and reading order

The handbook's Rate Limiter chapter covers token bucket, leaky bucket, fixed and sliding windows, and the distributed Redis design. These two resources do not repeat that; they fill gaps the chapter only touches: what a client should do when the server says no, and what an in-process pacing implementation looks like in real code. Read Fowler first (15 minutes, no code needed), then skim the Uber source (10 minutes), then build the exercise at the end.

Resource 1

Circuit Breaker Algorithm

What it is

A short article on Martin Fowler's bliki (2014) describing a pattern popularised by Michael Nygard's book Release It!. I fetched and read the page for this guide.

The mechanism, in my words

Wrap every remote call in an object that counts consecutive failures. While the count is under a threshold the wrapper is transparent. Once the threshold is hit, it stops calling the dependency at all and fails immediately. That is the whole trick: the expensive part of a failing dependency is not the error, it is the waiting for a timeout while threads, sockets and queue slots stay pinned. Failing in microseconds instead of seconds frees those resources and also stops you from hammering a service that is already on its knees.

CLOSED --(failures >= threshold)--> OPEN --(reset timeout elapsed)--> HALF-OPEN ^ | |------------------ trial call succeeds -----------------------| trial call fails: back to OPEN, timer restarts

Three states: closed (normal, success resets the counter), open (reject instantly), and half-open (after a cool-down, let a single probe through; success closes the breaker, failure re-opens it and restarts the timer).

The refinements Fowler lists

  • Trip on an error rate instead of a raw count, or use different thresholds per error class (timeouts versus connection refused).
  • Do not count business errors (a 404, a validation failure) as breaker failures; they say nothing about dependency health.
  • Bound concurrency with a thread pool or semaphore so a flood of slow calls trips the breaker by exhausting the pool, not by exhausting the process.
  • For asynchronous messaging, trip when the outbound queue fills.
  • Log every state change, expose the state to monitoring, and let operators trip or reset it by hand.
  • Decide at the caller what a rejected call means: fail the request, serve stale data, or queue the work for later.

Senior commentary

The article's pseudo-code counts failures; the production versions (Hystrix, Resilience4j, Envoy outlier detection, Polly) use a rolling window with a minimum request volume. Without that minimum, one failure out of two requests looks like a 50% error rate and the breaker flaps. The half-open state is where most home-grown implementations are wrong: if you let all waiting callers through at the moment the timer expires you recreate the thundering herd you were trying to prevent. Allow one probe, or a small percentage, and make the others keep failing fast.

Still true today: everything. The three-state model is unchanged. Dated: the Hystrix reference (Netflix put it into maintenance mode, and the community moved to Resilience4j and service-mesh policies). Today the breaker often lives in the sidecar or gateway, not the application, which shifts tuning from code to configuration.

Connection to the handbook

The rate limiter chapter answers "what do we return when a client is over quota" with HTTP 429 and Retry-After. The breaker is what a well-behaved client does with that signal and with 5xx/timeouts: stop sending. Pair it with exponential backoff plus jitter, otherwise a hundred clients with identical timers reopen in the same millisecond. It also fits beside the API gateway, where per-upstream breakers are a standard feature.

Resource 2

Uber Rate Limiter

What it is

The public API file of uber-go/ratelimit, a small Go library. The page I fetched is the interface layer: the implementation sits in a separate file the page only references, so what follows about internals is limited to what the API and its option names make clear, plus general knowledge of the leaky-bucket technique.

The contract

The caller invokes Take() before each unit of work. Take() blocks until it is time to proceed and returns the time at which the caller was released. There is no "rejected" outcome: this is a pacer, not a gatekeeper. That single design decision is the lesson. A limiter that blocks smooths traffic with no error handling at the call site, but it also ties up the calling goroutine, so it belongs on the client side of an outbound call or in a worker that is allowed to wait. A server-side limiter that blocks would simply convert overload into a growing pile of parked connections; there you want fast rejection.

Options and what they teach

OptionMeaningLesson
New(rate)Rate per second by defaultRate is turned into a fixed spacing between requests (1s divided by rate)
Per(d)Change the time unitRates like 2 per minute still become even spacing
WithSlack(n) / defaultBank unused capacity, default of 10 requests' worthStrict pacing punishes bursty callers; slack allows a bounded catch-up burst
WithoutSlackSlack of zeroPerfectly even spacing, at the cost of throughput after idle periods
WithClockInject a clockTime-dependent code must be testable without sleeping
NewUnlimited()Never blocksA null object so call sites need no if limiter != nil

Senior commentary

The constructor name in the source (an "atomic int64"-based implementation) tells you the state is a single timestamp updated with compare-and-swap, not a mutex-guarded structure. That is the right shape for a hot-path limiter: the entire state of a leaky bucket with a fixed spacing is "when may the next request run", one integer. It is why this library is cheap even under heavy contention, and it is the same insight behind GCRA (the generic cell rate algorithm), which Redis-based limiters such as Redis Cell use for distributed enforcement.

Slack is the bridge to the token bucket from the handbook chapter. A leaky bucket with 10 slack and a token bucket with capacity 10 allow almost the same behaviour: after quiet time, a burst of about ten, then steady spacing. The difference is framing: the bucket models credit for lateness, not tokens. In my example below, after half a second of idleness at 100/s, eleven calls go through instantly and the twelfth waits 10 ms.

Caveat: this is a single-process limiter. Ten replicas each configured for 100/s give 1,000/s against a shared downstream. For global limits use the shared-counter design in the chapter, or divide the quota by instance count and accept some slack in the autoscaling case.

Still true versus dated

The technique is timeless; the library's specifics (default slack, clock abstraction) may have changed since I could verify them, so check the current source before relying on defaults.

Connection to the handbook

It is a concrete instance of the leaky bucket in chapter 4 and complements the algorithm tour on the rate limiting hub page.

Synthesis

How the two resources fit together

Picture a service A calling service B. A uses a pacer (Uber style) to keep its outbound rate under B's published quota, so it rarely gets 429s. B applies a server-side limiter that rejects excess quickly. When B degrades anyway (a bad deploy, a full disk), A's breaker notices timeouts, opens, and A stops adding load while B recovers. The half-open probe finds out B is back. Each layer has a distinct job:

MechanismProtectsFailure signalResponse
Server-side limiterThe server, from too many requestsRequest rate over quota429 + Retry-After, fast
Client-side pacerThe downstream, from this callerLocal rate over budgetBlock briefly
Circuit breakerThe caller, from a sick dependencyErrors and timeoutsFail fast, probe later
Bulkhead / concurrency capThe caller's thread poolIn-flight countReject at the cap

Order of operations on the client: bulkhead check, breaker check, pacer wait, call, record result. Putting the pacer after the breaker avoids spending budget on calls you know will be rejected.

  • Read first: Fowler. Skim: Uber's options. Skip: nothing; both are short.
  • Always send Retry-After (or similar) so clients can back off intelligently instead of guessing.
  • Add jitter to every timer: breaker reset, retry backoff, pacer start.
  • Alert on breaker state changes, not just on error counts.
  • Treat 429 as backpressure, not as a failure that trips the breaker, unless the quota is clearly exhausted for a long period.
Code

Runnable example

JavaScript Example 
// Circuit breaker (closed/open/half-open) guarding a leaky-bucket pacer with slack.
class Clock { constructor(){ this.t = 1_000_000_000n; } now(){ return this.t; } advance(ms){ this.t += BigInt(ms) * 1_000_000n; } }

class Pacer {                       // inspired by the "perRequest + maxSlack" leaky bucket idea
  constructor(clock, ratePerSec, slack = 10) {
    this.c = clock; this.per = 1_000_000_000n / BigInt(ratePerSec);
    this.maxSlack = -BigInt(slack) * this.per; this.last = 0n; this.sleptFor = 0n;
  }
  take() {                          // returns ns the caller must wait (0 = go now)
    const now = this.c.now();
    if (this.last === 0n) { this.last = now; return 0n; }
    this.sleptFor += this.per - (now - this.last);
    if (this.sleptFor > 0n) { const wait = this.sleptFor; this.last = now + wait; this.sleptFor = 0n; return wait; }
    if (this.sleptFor < this.maxSlack) this.sleptFor = this.maxSlack;  // cap banked slack
    this.last = now; return 0n;
  }
}

class CircuitBreaker {
  constructor(clock, { threshold = 3, resetMs = 100 } = {}) {
    this.c = clock; this.threshold = threshold; this.resetNs = BigInt(resetMs) * 1_000_000n;
    this.failures = 0; this.openedAt = 0n; this.trialInFlight = false;
  }
  get state() {
    if (this.failures < this.threshold) return 'closed';
    return this.c.now() - this.openedAt >= this.resetNs ? 'half-open' : 'open';
  }
  call(fn) {
    const s = this.state;
    if (s === 'open') throw new Error('circuit open');
    try { const r = fn(); this.failures = 0; return r; }
    catch (e) { this.failures++; if (this.failures >= this.threshold) this.openedAt = this.c.now(); throw e; }
  }
}

const clock = new Clock();
const pacer = new Pacer(clock, 100, 10);            // 100 req/s => 10ms spacing
const waits = [];
for (let i = 0; i < 5; i++) waits.push(Number(pacer.take() / 1_000_000n));
console.log('burst of 5 at t=0, waits(ms):', waits.join(','));
clock.advance(500);                                  // idle: bank slack
const after = [];
for (let i = 0; i < 12; i++) after.push(Number(pacer.take() / 1_000_000n));
console.log('after idle, 12 back-to-back waits(ms):', after.join(','));

const cb = new CircuitBreaker(clock, { threshold: 3, resetMs: 100 });
let up = false; const dep = () => { if (!up) throw new Error('boom'); return 'ok'; };
const log = [];
for (let i = 0; i < 5; i++) { try { cb.call(dep); } catch (e) { log.push(`${e.message}->${cb.state}`); } }
console.log(log.join(' | '));
clock.advance(120); console.log('after reset timeout:', cb.state);
up = true; console.log('trial call:', cb.call(dep), '->', cb.state);
console.assert(cb.state === 'closed');

Prints a burst that is paced at 10 ms steps, an idle period followed by 11 instant calls using banked slack and then pacing again, and a breaker going closed to open to half-open to closed. Executed with node; the asserts pass.

Exercise

What to build

  1. Wrap the pacer and breaker into one ResilientClient.call(fn) and test it against a fake dependency that fails for the first 2 seconds of simulated time, then recovers.
  2. Replace the consecutive-failure count with a sliding window of the last 20 calls and a 50% threshold with a minimum of 10 calls. Prove with a test that flapping disappears.
  3. Limit half-open probes to one in-flight call; show that concurrent callers during the probe still fail fast.
  4. Honour a Retry-After header by pushing the pacer's next-allowed timestamp forward.
Checklist

Before you ship

  • Every outbound call has a timeout shorter than the caller's own deadline.
  • Breaker state is a metric and a log line.
  • Fallback behaviour is a conscious product decision (stale data, queue, error).
  • Limits are per-dependency, not global.
  • Tests use an injected clock; none of them sleep.

Key Takeaway

Limiting and breaking are two ends of one control loop. Pace what you send, reject what you cannot serve, and stop calling what is already failing. The resources are tiny, but the vocabulary they set (slack, half-open, fail fast) is what you will use in every incident review.

FAQ · Common Questions

Frequently Asked Questions

Why does a breaker need a half-open state?

Without it the breaker either never recovers or reopens for everyone at once. Half-open sends a single probe so recovery is detected without a stampede.

Pacer or token bucket for client-side limiting?

Same family. A pacer with slack is a token bucket expressed as spacing plus credit. Use whichever gives the cleanest code; both need a single timestamp or counter.

Should a 429 trip the breaker?

Usually no. A 429 means the server is healthy but you are over quota, so slow down. Tripping the breaker conflates overload with failure and can cut off a healthy dependency.

Where should the breaker live, app or mesh?

Both exist. A mesh gives uniform policy and metrics; in-app lets you choose fallbacks. Many teams use mesh outlier detection for coarse protection and in-app breakers where a fallback matters.

How do you rate limit across many instances?

Shared counters (Redis with Lua or GCRA), or static per-instance shares. See chapter 4.
