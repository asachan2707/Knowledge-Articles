Key-Value Stores: Dynamo, Bigtable and Cassandra — Reading Guide

A reading guide to the Dynamo and Bigtable papers, Cassandra architecture and two DynamoDB talks, with commentary, a runnable quorum and vector clock demo, and an exercise.

TypeResource guide · related chapters: Chapter 6
Read time10 min
Core ideasquorum, vector clocks, hinted handoff, LSM tree
Real systemsDynamo, DynamoDB, Cassandra, Bigtable, HBase

Six resources about key-value stores that describe two lineages. The Dynamo lineage (Dynamo paper, Vogels' announcement, Cassandra, and the DynamoDB talks) is about availability, partitioning and tunable consistency. The Bigtable lineage is about sorted storage, tablets and the log-structured write path. Cassandra famously borrows from both. Chapter 6 compresses them into one design; this guide un-compresses them.

Core idea: a distributed KV store is two independent decisions: how data is placed and replicated (Dynamo's contribution) and how a single node stores and finds bytes (Bigtable's contribution). Confusing the two is the most common interview mistake.

Resource 1

Amazon Dynamo

What it is

"Dynamo: Amazon's Highly Available Key-value Store" (DeCandia et al., SOSP 2007). It is the single most influential KV paper and the blueprint for the chapter's replication, versioning and failure-handling sections.

Mechanisms

ProblemDynamo's answerChapter 6 name
Spread data, grow incrementallyConsistent hashing with virtual nodesData partition
Survive node lossReplicate each key on N successive nodes (a "preference list")Data replication
Tune consistency vs latencyQuorum parameters N, R, W; typical setting 3, 2, 2Consistency
Accept writes during partitionsSloppy quorum plus hinted handoffTemporary failure handling
Detect concurrent updatesVector clocks; client or application reconcilesInconsistency resolution
Repair permanent divergenceAnti-entropy with Merkle treesPermanent failure handling
Know who is aliveGossip-based membershipFailure detection

Numbers and lessons worth remembering

  • Targets are expressed in the 99.9th percentile (the Dynamo SLA was around 300 ms), not averages.
  • The paper reports that 99.94% of shopping-cart reads returned a single version, so conflicts are rare in practice, and they must still be handled.
  • Partitioning moved from random tokens to fixed equal-size partitions, which improved balance and made bootstrapping and archival easier.
  • Client-driven coordination (the client knows the ring and goes straight to a replica) cut tail latency by tens of milliseconds at the 99.9th percentile.
  • The authors state the design suits a few hundred nodes; they say thousands would be hard because every node tracks full routing state.
client --put(k,v,ctx)--> coordinator (first in preference list) |-> replica 1 ack |-> replica 2 ack W=2: success |-> replica 3 down -> hint stored on node 4 read: ask N, wait R, return all causally-latest versions, repair stale ones

Senior commentary

Three things people get wrong. First, R plus W greater than N is not linearizability; sloppy quorums, concurrent writes and clock-free versioning mean you can still read stale data. Second, vector clocks grow; Dynamo truncates old entries, accepting some loss of precision. Many successors (Riak early on, then Cassandra) moved to timestamps with last-write-wins because pushing merge logic onto developers proved unpopular. Third, "always writeable" is a product decision (a lost cart item is cheaper than a failed checkout), not a universal good.

Dated: Dynamo's own successors dropped several parts. Amazon's DynamoDB service is a different system (see below), and the paper's gossip full-membership model does not scale to thousands. Still true: the vocabulary and trade-offs, which every Dynamo-style system reuses.

Connection

Map one-to-one onto chapter 6, and revisit the CAP theorem and consistency models pages. The code below implements the quorum and vector clock parts.

Cassandra Architecture

What it is

The introduction to the architecture section in DataStax's archived documentation for Cassandra 3.0. I read this page. It is explicitly marked as no longer maintained.

Content

  • Peer-to-peer: every node is equal; any node a client contacts becomes the coordinator for that request.
  • Write path: append to a commit log (durability), update an in-memory memtable, later flush to immutable SSTables; compaction merges SSTables and drops data covered by tombstones.
  • Token-based placement: a partitioner (Murmur3 by default) hashes the primary key to a token; the replica set follows from the token and the replication strategy.
  • Replication factor per datacenter with no primary replica; NetworkTopologyStrategy is the recommended choice.
  • Gossip shares state; snitches teach the cluster where racks and datacenters are; a dynamic snitch steers reads toward better-performing replicas.
  • Repair mechanisms reconcile replicas.

Senior commentary

Cassandra is the proof that you can fuse the two lineages. The ring and quorum story is Dynamo; the commit-log, memtable and SSTable story is Bigtable. The tombstone detail is a real production hazard: deletes are writes, and a read must merge many SSTables, so wide partitions with heavy deletes (the "queue in Cassandra" anti-pattern) degrade badly. Gossip plus a snitch also means topology is configuration you must get right; an incorrect rack mapping silently ruins replica placement.

Still true versus dated

Concepts hold in later versions. Version-specific defaults, tooling names and the DSE-specific parts have moved; verify against the current Apache documentation.

Google BigTable Architecture

What it is

"Bigtable: A Distributed Storage System for Structured Data" (Chang et al., OSDI 2006), the sorted, wide-column store that inspired HBase and, for its storage engine, Cassandra.

Ideas

  • Data model: a sparse, sorted, multi-dimensional map from (row key, column key, timestamp) to bytes. Column families group columns; single-row operations are atomic.
  • Tablets: contiguous row ranges are the unit of distribution; a tablet server hosts many tablets and splits them when they grow.
  • Storage: writes go to a commit log and an in-memory sorted memtable; the memtable is flushed to immutable, indexed SSTable files on a distributed file system; periodic compaction merges them.
  • Coordination: a lock service (Chubby) elects the one active master and tracks tablet-server liveness; the master assigns tablets, but clients read and write against tablet servers directly, so the master is not a data bottleneck.
write -> commit log (sequential, durable) -> memtable (sorted, in RAM) --flush--> SSTable 1, SSTable 2 ... read -> memtable + SSTables (bloom filter skips most) -> merge newest wins compaction merges SSTables, drops overwritten and deleted cells

Senior commentary

The KV chapter's "write path" and "read path" with bloom filters is this paper, nearly verbatim. The strategic difference from Dynamo: Bigtable is consistent (one server owns a tablet at a time, coordinated through the lock service) and sorted, so range scans are cheap; Dynamo is available and hashed, so scans are impossible but writes never block. Pick by access pattern: sorted keys for time series and scans, hashed keys for point lookups and extreme availability.

The design of storing data on a distributed file system and keeping servers stateless over it is the origin of today's disaggregated storage designs; the trade is a network hop per read in exchange for fast recovery.

Amazon Dynamo DB Internals

What it is

Werner Vogels' October 2007 blog post announcing the Dynamo paper. Despite the title in the repo, it is about the Dynamo paper, not the DynamoDB service that launched in 2012. I read this page.

Content

It frames the problem: constant component failure at Amazon's scale, services that mostly need primary-key access, and relational databases that favour consistency over availability and are hard to scale out. It lists the techniques (consistent hashing, vector clocks, quorum, hinted handoff, Merkle trees, gossip) and says Dynamo was among the first production systems to combine them. It reproduces the paper, and stresses that Dynamo was an internal building block, with the shopping cart as the canonical example.

Commentary

Read it as the "why" memo: the paper's argument is about business requirements first. A good interview answer states the requirement ("never reject a cart write") before the mechanism.

Naming trap: Dynamo (2007 paper, internal) and DynamoDB (2012, managed service) share a heritage but differ in design. Public descriptions of DynamoDB (including a USENIX ATC 2022 paper) describe single-leader replication per partition, not leaderless quorums and vector clocks. Do not describe DynamoDB with the Dynamo paper's mechanisms.

  • Always state N, R and W and what they buy; R plus W greater than N reduces staleness, not eliminates it.

  • Explain delete semantics (tombstones) and compaction.
  • Name the failure types: transient (hinted handoff) versus permanent (anti-entropy).
Code

Runnable example

JavaScript Example 
// Dynamo-style N=3, R=2, W=2 with vector clocks, hinted-style sloppy failure and read repair.
const vcInc = (vc, n) => ({ ...vc, [n]: (vc[n] ?? 0) + 1 });
const vcLeq = (a, b) => Object.keys(a).every(k => a[k] <= (b[k] ?? 0));
const vcMerge = (a, b) => { const o = { ...a }; for (const k in b) o[k] = Math.max(o[k] ?? 0, b[k]); return o; };

class Replica { constructor(id){ this.id = id; this.up = true; this.data = new Map(); }
  put(k, ver) { if (!this.up) throw new Error('down'); const cur = this.data.get(k) ?? [];
    const kept = cur.filter(c => !vcLeq(c.vc, ver.vc));           // drop versions dominated by new one
    if (!kept.some(c => vcLeq(ver.vc, c.vc))) kept.push(ver);      // add unless already dominated
    this.data.set(k, kept); }
  get(k) { if (!this.up) throw new Error('down'); return this.data.get(k) ?? []; } }

class Coordinator {
  constructor(reps, { N = 3, R = 2, W = 2 } = {}) { this.reps = reps; this.N = N; this.R = R; this.W = W; }
  put(k, value, ctx = {}, coord = this.reps[0].id) {
    const ver = { value, vc: vcInc(ctx, coord) }; let acks = 0;
    for (const r of this.reps.slice(0, this.N)) { try { r.put(k, ver); acks++; } catch {} }
    if (acks < this.W) throw new Error(`write quorum failed (${acks}/${this.W})`);
    return ver.vc;
  }
  get(k) {
    let resp = 0, all = [];
    for (const r of this.reps.slice(0, this.N)) { try { all.push(...r.get(k)); resp++; } catch {} }
    if (resp < this.R) throw new Error('read quorum failed');
    const uniq = []; for (const v of all) { if (uniq.some(u => vcLeq(v.vc, u.vc))) continue;
      for (let i = uniq.length - 1; i >= 0; i--) if (vcLeq(uniq[i].vc, v.vc)) uniq.splice(i, 1); uniq.push(v); }
    for (const r of this.reps) if (r.up) for (const v of uniq) r.put(k, v);   // read repair
    return uniq;
  }
}

const reps = ['A', 'B', 'C'].map(id => new Replica(id)); const c = new Coordinator(reps);
const ctx1 = c.put('cart', ['book'], {}, 'A');
reps[2].up = false;                                       // C down: W=2 still met
const ctx2 = c.put('cart', ['book', 'pen'], ctx1, 'A');
console.log('after C down, read:', JSON.stringify(c.get('cart').map(v => v.value)));
reps[2].up = true; reps[1].up = false;
// two clients write concurrently from the same context via different coordinators
c.put('cart', ['book', 'pen', 'mug'], ctx2, 'A');
c.put('cart', ['book', 'pen', 'hat'], ctx2, 'C');       // concurrent sibling
reps[1].up = true;
const siblings = c.get('cart');
console.log('siblings:', JSON.stringify(siblings.map(v => v.value)));
console.assert(siblings.length === 2);
const merged = [...new Set(siblings.flatMap(s => s.value))];
const ctx = siblings.map(s => s.vc).reduce(vcMerge, {});
c.put('cart', merged, ctx, 'B');
const fin = c.get('cart'); console.log('after semantic merge:', JSON.stringify(fin.map(v => v.value)));
console.assert(fin.length === 1 && fin[0].value.length === 4);
reps[0].up = reps[1].up = false;
try { c.put('cart', ['x'], ctx, 'C'); } catch (e) { console.log('2 replicas down ->', e.message); }

Prints a read after one replica is down, two concurrent writes becoming siblings, a semantic merge collapsing them into one version, and a write failing when only one replica is up. Executed with node; asserts pass.

Exercise

What to build

  1. Add hinted handoff: when a replica is down, store the write on a fallback node with the intended owner, and replay it on recovery. Write a test showing the replay.
  2. Add a Merkle-tree comparison between two replicas that finds differing keys with O(log n) hash comparisons.
  3. Add a toggle between vector clocks and last-write-wins, and write a test where LWW silently loses a concurrent update.
  4. Extend the replica with a memtable that flushes to sorted runs and a read that merges them, with tombstones.

Key Takeaway

Learn the KV store as a menu of independent choices: placement, replication, conflict handling, storage engine. Dynamo supplied the first three, Bigtable the fourth, and Cassandra shows they combine. Be able to defend each choice against the requirement that motivated it.

FAQ · Common Questions

Frequently Asked Questions

Does R + W > N guarantee strong consistency?

No. With sloppy quorums, concurrent writes and no global ordering you can still read stale or conflicting data. It narrows the window; it does not close it.

Why vector clocks instead of timestamps?

Timestamps need synchronised clocks and silently drop one concurrent write. Vector clocks detect concurrency so nothing is lost, at the cost of metadata and client merge logic.

Is DynamoDB the same as Dynamo?

No. Same company and heritage, different design. The managed service is described publicly as using a leader per partition, not leaderless quorum.

How do deletes work in an LSM-based store?

A delete writes a tombstone marker; compaction later removes both the marker and the covered data, after a grace period so replicas can learn of the delete.

When would you pick a Bigtable-style store over Dynamo-style?

When you need ordered scans and per-row strong consistency, such as time series or lookups by key prefix, and can accept less availability under partition.
