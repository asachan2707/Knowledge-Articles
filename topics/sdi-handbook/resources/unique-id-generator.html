Unique ID Generation: Ticket Servers and Snowflake — Reading Guide

A reading guide to Flickr ticket servers and Twitter Snowflake, with commentary on clocks, worker IDs and trade-offs, plus a runnable ticket server and Snowflake generator.

TypeResource guide · related chapters: Chapter 7
Read time9 min
Core ideasticket server, snowflake, clock skew, worker lease
Real systemsFlickr, Twitter Snowflake, UUIDv7, ULID

Two resources, two philosophies. Flickr's ticket servers say: a database you already operate can hand out sequential integers, so do the dumbest thing that works. Twitter's Snowflake says: nothing in the request path should call a central server, so pack time, machine and sequence into one 64-bit number. Almost every ID scheme you will meet is one of these two with variations.

Core idea: "unique" is cheap; "unique, sortable, compact, available and without coordination on the hot path" is the real requirement. The two resources show the two cheapest ways to meet different subsets of it.

Resource 1

Ticket Servers: Distributed Unique Primary Keys on the Cheap

What it is

A February 2010 Flickr engineering post explaining how they generate primary keys for a database that is sharded across many MySQL servers. I read the page.

The problem as the post frames it

Flickr shards across master-master pairs of MySQL servers. Plain auto-increment columns collide when the same table lives on several shards, and when rows move between shards. Random GUIDs are large and index poorly in MySQL; sequential integers are small, cache-friendly and handy for debugging. The post also dismisses a Dynamo-style consistent-hashing store as a poor fit for a database tuned for fast random reads.

The mechanism

A dedicated "ticket" database contains tables that hold a single row. A table has an auto-increment id and a stub column with a unique index. To get a new ID: run REPLACE INTO Tickets64 (stub) VALUES ('a') and then SELECT LAST_INSERT_ID(). REPLACE deletes the old row sharing the unique key and inserts a new one; the table never grows, but the auto-increment counter keeps rising. The two statements run on one connection, so concurrent clients each see their own last-insert id.

To avoid a single point of failure, Flickr runs two ticket servers, one configured to produce odd numbers and the other even (auto-increment increment 2, with offsets 1 and 2). Clients round-robin. If one dies, the other carries all traffic. They explicitly avoid replication or locking between the two because it would hurt performance. They keep separate tables for different object types so busy types do not inflate counts of rare ones, and the post notes that the two servers drift apart by a few hundred thousand, which "hurts no one".

app --REPLACE INTO Tickets64--> ticket server A (1,3,5,7 ...) app --REPLACE INTO Tickets64--> ticket server B (2,4,6,8 ...) round-robin; if one is down, use the other ids: small integers, roughly increasing, but not strictly ordered across servers

Senior commentary

  • Strengths: trivially simple to operate for a MySQL shop; compact, index-friendly IDs; gaps are not a problem.
  • Costs: a network round trip per ID unless you batch; ticket servers are a dependency on every insert path; two servers give availability but not strict ordering, since A and B drift.
  • Standard fix: allocate IDs in blocks (a "hi/lo" scheme). The app asks for a block of, say, 1,000 numbers and uses them locally, cutting the round trips by three orders of magnitude at the cost of gaps when the app restarts.
  • Odd/even does not scale past two: with N servers you set the increment to N, and changing N later requires care to avoid overlaps.

Still true versus dated

The pattern is alive: database sequences, Redis INCR, and block allocation in ORM libraries are all ticket servers. The dated bit is MySQL REPLACE as the mechanism, and the worry about GUIDs; time-ordered UUIDs (UUIDv7, ULID) now give compact-enough, index-friendly keys with no server.

Connection

It is approach 2 ("multi-master replication") in chapter 7, in its production form. The URL-shortener design also needs unique IDs; see the URL shortener page.

Resource 2

Snowflake

What it is

Twitter's 2010 announcement of Snowflake, a network service for generating unique IDs at high scale, built when Twitter was moving from a single MySQL database to Cassandra-based storage that had no built-in sequence feature. The project repository was later archived.

Reading note: the page returned HTTP 403 to my fetcher, so the description below is the widely documented design, not a reading of the post.

The design

1 bit 41 bits 10 bits 12 bits 0 | milliseconds since custom epoch | worker / datacenter id | per-ms sequence sign ~69.7 years of range 1,024 machines 4,096 ids per ms per machine
  • IDs are 64-bit integers, so they fit a signed long in nearly every language (and a JavaScript double only if you are careful; JSON consumers often need the ID as a string).
  • IDs are roughly time-sortable (k-ordered). Two IDs from different machines in the same millisecond have no defined order; one machine's IDs are strictly increasing.
  • Each machine needs a unique worker ID. Twitter's service used ZooKeeper to coordinate worker identity, not to issue IDs per request.
  • If the sequence for a millisecond overflows (more than 4,096), the generator waits for the next millisecond.

Senior commentary

The design is a tiny distributed system with one hard assumption: the clock must not go backwards. NTP step adjustments, VM migration and leap-second handling can all rewind time; a naive generator then re-issues old timestamps and duplicates IDs. The correct behaviour is to refuse (or wait) when the clock is behind the last issued timestamp; my example throws, which makes an outage visible instead of silently duplicating IDs. The second hazard is worker-ID reuse: if two live processes get the same worker ID (a bad rollout, container restart without lease expiry) you get collisions. Worker ID allocation therefore needs a lease with a fencing property.

Throughput is 4,096 IDs per millisecond per worker, about 4.1 million per second, which is far more than almost any single service needs. The epoch choice matters: the 41-bit field lasts roughly 69.7 years from your epoch, so set it close to launch.

Variants: Instagram shard-ID layouts embed a logical shard ID instead of a machine ID; Sonyflake trades sequence bits for a longer lifespan; UUIDv7 and ULID embed a millisecond timestamp plus randomness, trading the 64-bit size for zero coordination.

Connection

It is the chapter 7 final design: compare the layout with the bit-allocation exercise in chapter 7. Clock skew also relates to the discussion in consistency models.

Snowflake ↗

Numbers

Back-of-envelope arithmetic

  • Snowflake lifetime: 2^41 ms is about 2.2 trillion ms; divided by 31.56 billion ms per year that is about 69.7 years from the chosen epoch.
  • Per-worker rate: 2^12 = 4,096 IDs per millisecond, so 4,096,000 per second per worker. A fleet of 1,024 workers could in theory issue over 4 billion IDs per second, which is why the layout is rarely the bottleneck.
  • Ticket server rate: one MySQL REPLACE plus LAST_INSERT_ID is bounded by one database's write throughput, so a service writing 50,000 rows per second would need block allocation: at 1,000 IDs per block that is 50 block requests per second.
  • Gap cost: with blocks of 1,000 and 100 app servers each restarting once a day, you waste at most about 100,000 IDs per day out of a 64-bit space: irrelevant, but visible if someone expects IDs to be gapless.

Two practical conclusions follow. The bit layout is almost never the limit; the operational controls around it are. And a ticket server needs no cleverness to survive huge growth, only batching.

Reading order: Flickr first (shortest and most clearly argued), then Snowflake; then chapter 7 to see both framed as interview options. Read both because they answer the same question with opposite trade-offs: coordinate once (a tiny, simple service) or never (a clever layout).

  • State the requirements first: ordering, size, rate, whether IDs are exposed to users.
  • Decide what happens on clock regression.
  • Decide how worker IDs are leased and recycled.
  • Remember that sortable IDs leak creation time and volume; do not use them where that is sensitive.
Code

Runnable example

JavaScript Example 
// Flickr-style ticket servers (odd/even) vs Snowflake-style 64-bit ids.
class TicketServer { constructor(offset, inc = 2) { this.next = offset; this.inc = inc; this.up = true; }
  ticket() { if (!this.up) throw new Error('down'); const v = this.next; this.next += this.inc; return v; } }
class Tickets { constructor(servers) { this.s = servers; this.i = 0; }
  get() { for (let t = 0; t < this.s.length; t++) { const sv = this.s[this.i++ % this.s.length]; try { return sv.ticket(); } catch {} } throw new Error('all down'); } }
const a = new TicketServer(1), b = new TicketServer(2), tk = new Tickets([a, b]);
const ids = [tk.get(), tk.get(), tk.get(), tk.get()]; b.up = false; ids.push(tk.get(), tk.get());
console.log('ticket ids (even server down for last two):', ids.join(','));

const EPOCH = 1288834974657n;                      // Twitter epoch (ms)
class Snowflake {
  constructor(workerId, now = () => BigInt(Date.now())) { if (workerId < 0 || workerId > 1023) throw new Error('worker'); this.w = BigInt(workerId); this.now = now; this.last = -1n; this.seq = 0n; }
  next() {
    let t = this.now();
    if (t < this.last) throw new Error(`clock moved back ${this.last - t}ms`);
    if (t === this.last) { this.seq = (this.seq + 1n) & 4095n; if (this.seq === 0n) { while (t <= this.last) t = this.now(); } } else this.seq = 0n;
    this.last = t; return ((t - EPOCH) << 22n) | (this.w << 12n) | this.seq;
  }
}
const decode = id => ({ ms: Number(id >> 22n) + Number(EPOCH), worker: Number((id >> 12n) & 1023n), seq: Number(id & 4095n) });
let fake = 1700000000000n; const sf = new Snowflake(7, () => fake);
const out = [sf.next(), sf.next(), (fake++, sf.next())];
console.log(out.map(String).join(' '));
console.log(JSON.stringify(decode(out[2])));
console.assert(out[0] < out[1] && out[1] < out[2] && decode(out[2]).worker === 7 && decode(out[1]).seq === 1);
const real = new Snowflake(1); const set = new Set(); for (let i = 0; i < 100000; i++) set.add(real.next());
console.log('100k unique ids:', set.size === 100000);
fake -= 5n; try { sf.next(); } catch (e) { console.log('guard:', e.message); }
console.log('max sustained per worker:', 4096 * 1000, 'ids/s; timestamp bits last ~', (2 ** 41 / 31557600000).toFixed(1), 'years');

Prints ticket IDs from an odd/even pair with one server down, three Snowflake IDs with a decoded fields, a check that 100,000 IDs are unique, and the clock-rewind guard firing. Executed with node; asserts pass.

Exercise

What to build

  1. Add block allocation to the ticket client (grab 100 IDs per call) and compare the number of server calls.
  2. Persist the Snowflake generator's last timestamp and refuse to start if the wall clock is behind it.
  3. Implement a worker-ID lease with an expiry, and a test that two live workers can never hold the same ID.
  4. Write a UUIDv7 generator from the spec and measure how often two IDs generated in the same millisecond sort in creation order.

Key Takeaway

Pick between "one tiny coordinator" and "no coordinator plus clock discipline", and be explicit about the failure each one introduces. The interesting engineering is never the bit layout; it is clock rewinds, worker-ID leases and what happens when the coordinator is down.

FAQ · Common Questions

Frequently Asked Questions

Why not use UUIDs?

They are 128 bits, random UUIDv4 values fragment B-tree indexes, and they carry no order. Time-ordered variants fix the last two at the cost of the first.

What if the clock goes backwards?

Reject or wait until the clock passes the last issued timestamp, and alert. Never emit IDs with an older timestamp and a fresh sequence; that is how duplicates appear.

How are worker IDs assigned safely?

Through a lease from a coordination service such as ZooKeeper or etcd, with expiry and, ideally, a fencing token, so a restarted process cannot share an ID with a ghost of itself.

Is Snowflake strictly ordered?

Only within a single worker. Across workers IDs are roughly ordered by millisecond; for causal ordering you need a logical clock or a log.

Can I give IDs to JavaScript clients?

Not as numbers: a 64-bit integer exceeds the 53-bit safe range of a double. Send them as strings.
