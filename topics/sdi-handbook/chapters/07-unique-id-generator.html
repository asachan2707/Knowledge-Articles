Design a Unique ID Generator in Distributed Systems

Auto-increment dies the moment you have more than one database writer. This chapter walks the four classic options, then builds the Snowflake layout bit by bit and covers what actually breaks in production: clocks that go backwards, worker-ID collisions, and ids that JavaScript silently corrupts.

Every row you ever insert needs a name. On one database the name is a counter. On fifty independent machines, there is no shared counter, and the moment you invent one you have built a bottleneck, a single point of failure, or a coordination protocol. A unique ID generator is the small service (or library) that hands out those names without anyone asking permission.

Core idea: Make the id a concatenation of independent coordinates: when (time), where (worker), and which one in that instant (sequence). If each coordinate is unique within its parent, the whole is unique without any runtime agreement between machines. The only things you must coordinate are the worker numbers, once, at startup.

A well-known design

Why Twitter wrote Snowflake

Around 2010 Twitter was moving its tweet storage off a single MySQL master with auto-increment keys toward a sharded, partly Cassandra-backed store. Sharded stores have no global counter, yet the product needed ids that were roughly time-ordered (timeline merges sort by id) and that fit in the 64-bit integers the existing code and databases used. Twitter's published answer was Snowflake: a small network service in which every node mints ids locally from the clock, a worker number and a per-millisecond counter. The idea has since been copied everywhere (Discord, Instagram's variant inside PostgreSQL, Sonyflake, many in-house libraries) because it removes the one thing that does not scale: a shared mutable counter.

Requirements and numbers

What we are actually building

  • Unique: no two ids ever collide, across all machines and data centers, forever.
  • Numeric and 64-bit: fits a signed BIGINT, which keeps indexes small and comparisons cheap.
  • Roughly time-sorted: sorting by id approximates sorting by creation time. Not necessarily +1 per call.
  • Fast: at least 10,000 ids/second system-wide; the real design handles millions.
  • Highly available: if ids stop, writes stop. This is a tier-0 dependency.

The headroom is absurd compared to the 10k/s target, which is the point: you are not buying throughput, you are buying independence. That headroom is also what lets you trade bits between fields later.

Four candidate designs

The options, and why three of them lose

1. Multi-master auto-increment

Run k databases; server i hands out i, i+k, i+2k, and so on (auto_increment_increment = k, auto_increment_offset = i). It reuses boring technology, and ids stay numeric.

  app ──► DB-1 : 1, 3, 5, 7 ...    (step 2, offset 1)
  app ──► DB-2 : 2, 4, 6, 8 ...    (step 2, offset 2)

  add DB-3 tomorrow?  step must become 3  → existing ranges collide
  ordering: id 7 (DB-1) may be created before id 4 (DB-2)

Problems: the step is baked into every server, so adding or removing one is a migration rather than a deploy. Ids do not follow time across servers (one lagging server issues "old" numbers). Cross-datacenter use is painful because each DC needs its own non-overlapping offsets, and every id costs a database round trip and a durable write.

2. UUID (v4)

128 random bits, generated anywhere with zero coordination. Collision probability is negligible (for 2122 random bits you would need on the order of 1018 ids before a collision gets likely). It scales with the web tier because the generator is a library call. Costs: twice the width of a BIGINT, no time order, and in a B-tree primary key every insert lands on a random leaf page, which wrecks write locality, bloats the buffer pool and fragments the index. In InnoDB the clustered key is copied into every secondary index, so a 16-byte key penalizes every index.

3. Ticket server

One dedicated database whose only table has an auto-increment column; clients run REPLACE INTO tickets (stub) VALUES ('a') and read LAST_INSERT_ID(). Flickr published this pattern: it is simple, numeric and strictly increasing. But a single server is a SPOF and a throughput ceiling. Flickr's own mitigation was two ticket servers, one issuing odd and one even, with clients round-robining; that is multi-master again, with the same ordering weakness.

  web-1 ─┐                  ┌─────────────┐
  web-2 ─┼── "give me id" ─►│ ticket DB   │ auto_increment
  web-3 ─┘                  └─────────────┘
              every insert in the company waits on one box

A common refinement is range allocation ("ID block" or "HiLo"): a worker leases a block of, say, 10,000 ids from the ticket server and serves them from memory, going back only when the block is exhausted. That cuts ticket-server QPS by 10,000x. The costs are gaps after crashes (unused block is lost) and ids that are ordered within a worker but not across workers.

4. Snowflake-style composition

Split 64 bits into fields and let each machine fill them itself. This is the winner because it gives uniqueness (by construction), rough time order (timestamp occupies the high bits), numeric 64-bit width, and no runtime dependency on any other machine.

The bit layout

Anatomy of a Snowflake id

   63   62                              22 21    17 16     12 11            0
  ┌───┬──────────────────────────────────┬────────┬────────┬───────────────┐
  │ 0 │ timestamp (41 bits)             │ dc (5)  │ mach(5)│ sequence (12)  │
  └───┴──────────────────────────────────┴────────┴────────┴───────────────┘
   sign   ms since custom epoch          0..31    0..31     0..4095 per ms

  id = (ts - EPOCH) << 22  |  dc << 17  |  machine << 12  |  seq
  • Sign bit (1): always 0 so the value stays positive in signed 64-bit columns and signed comparisons order correctly. It also leaves a spare bit you could reclaim if you were willing to use unsigned types.
  • Timestamp (41): milliseconds since a custom epoch you choose. Twitter's was 1288834974657, which is 2010-11-04 01:42:54.657 UTC. Using your launch date instead of 1970 is what gives you the full 69.7 years rather than having burned 40 of them.
  • Datacenter (5) and machine (5): together a 10-bit worker identity, 1,024 workers. The 5/5 split is cosmetic; the generator only cares that the 10 bits are unique per live process.
  • Sequence (12): counter within one millisecond on one worker; resets to 0 when the millisecond changes. If you hit 4,096 in the same ms you must wait for the next tick, a deliberate throttle.

Because the timestamp is in the most significant bits, ids sort by time down to the millisecond; within one millisecond, ids from different workers order by worker bits, which is arbitrary but stable. That property is called k-sortable (sorted within a small window of k), and it is what makes ORDER BY id DESC LIMIT 20 work as a "latest" query and keeps inserts append-mostly in a B-tree.

Insight: Ordering is only as good as your clocks. Two events 1 ms apart on machines whose clocks differ by 5 ms can get ids in the "wrong" order. Treat id order as approximate causality, never as a source of truth for "A happened before B". If you need real ordering, use a per-entity version number or a consensus log.
Deep dive

Clocks: the part everyone underestimates

The generator is a pure function of (clock, worker, counter). Break the clock assumption and you break uniqueness, not just ordering. Three distinct hazards:

HazardWhat happensDefence
Clock drift between machinesIds from different workers interleave out of real-time order.NTP (or chrony) with monitoring; in clouds, the provider's time service (AWS Time Sync, Google's leap-smeared NTP). Accept ms-level disorder.
Clock steps backwards on one machine (NTP step, VM migration, leap second, operator error)Same (ts, worker) pair repeats; sequence restarts at 0, so duplicate ids.Remember lastTs; if now < lastTs, refuse. For tiny regressions spin-wait; for larger ones fail loudly and take the node out of rotation.
Restart after crashProcess loses lastTs; if the clock regressed while down, duplicates become possible.Persist the high-water mark periodically and on shutdown; on boot, wait until the clock is past it. Or add a few "epoch generation" bits bumped on every restart.

Use a monotonic source for deltas when you can. Node's process.hrtime and Java's System.nanoTime never go backwards but are not wall-clock; a common trick is to read wall-clock once at boot and advance it with the monotonic clock, re-syncing slowly. NTP slewing (gradually speeding or slowing the clock) is safe; stepping is what bites. Configure chrony with makestep limited to boot, and prefer leap-second smearing.

Production gotcha: A "temporary" -2 s step on one host with no guard produces up to two seconds of duplicate ids, which show up weeks later as unique-constraint violations on the replica or as silently overwritten rows in a key-value store. Always include the clock-regression check, and alert on it.
Deep dive

Who gets which worker id?

The 10 worker bits must be unique among live generators. This is the only coordination Snowflake needs, and it is a startup concern, not a per-id one. Options, from simplest to most robust:

  • Static config: bake the id into the deploy (machine number from a host inventory). Works for pet servers; fragile for autoscaled fleets.
  • Lease from a coordinator: on boot, create an ephemeral/sequential node in ZooKeeper or etcd (or a TTL'd row in a database or a Redis key with SET NX PX); the lease number is the worker id; renew periodically, relinquish on shutdown. If the lease lapses (GC pause, partition), the process must stop issuing ids before the lease expires from the coordinator's point of view.
  • Derive from stable identity: for Kubernetes StatefulSets the pod ordinal is already unique and stable; for others hash an IP/MAC (risk of collisions: with only 1,024 values the birthday paradox bites at around 40 nodes, so never hash blindly).

Reusing a worker id too quickly is also a trap: if worker 17 dies and its replacement takes 17 while the replacement's clock is behind, you recreate the clock-regression scenario across processes. Keep a cooling period of at least the maximum expected clock offset.

Deep dive

Tuning the bit budget

The 41/10/12 split is a default, not a law. Redo the arithmetic for your workload:

SituationAdjustmentCost
Few workers, enormous per-worker burstFewer worker bits (e.g. 3), more sequence bits (e.g. 19)Max 8 workers
Thousands of small stateless podsMore worker bits (13) and fewer sequence bits (9 → 512/ms/worker)Per-worker burst cap drops 8x
Want a century of lifeSeconds instead of milliseconds for the timestamp (Sonyflake uses 10 ms units: 39 bits time, 8 bits sequence, 16 bits machine)Coarser order, lower per-worker rate (256 per 10 ms)
Low volume, long lifeReduce sequence bits, keep time bitsThroughput cap

Instagram published a variant implemented inside PostgreSQL: 41 bits of time, 13 bits of logical shard id and 10 bits from a per-table sequence. Because the shard id is embedded in the id, you can route a lookup to the right shard without a directory. That is a real design lever: ids that carry routing information. The flip side is that re-sharding is harder, since the id is a permanent address.

Modern alternatives and how to choose

My opinion: if you do not specifically need a 64-bit integer, UUIDv7 is the lowest-regret choice today. You get time-ordered inserts, no worker-id service and a native column type. Pick Snowflake when ids appear in URLs, are stored by the billion in narrow rows, or must be JSON-safe as strings, and the 8-byte saving across indexes matters.

Snowflake wins

  • 8 bytes: half the index and foreign-key footprint of a UUID
  • Embeds creation time; decodable for debugging
  • Tunable bit budget; can embed shard routing

Snowflake costs

  • Worker-id assignment is operational burden
  • Clock regression can silently corrupt uniqueness
  • Predictable and enumerable: leaks creation time and rate
Runnable code

A Snowflake generator you can break on purpose

The implementation below uses BigInt because 64-bit ids exceed the 253 safe-integer limit of a JavaScript Number. The clock is injectable, which lets the test drive the sequence-rollover and clock-regression paths deterministically. It then measures real-clock throughput on a single worker.

JavaScript Example 
// Snowflake-style 64-bit ID generator: 1 sign | 41 time | 5 dc | 5 machine | 12 seq
const EPOCH = 1288834974657n; // Twitter's custom epoch (ms)
const TS_BITS = 41n, DC_BITS = 5n, M_BITS = 5n, SEQ_BITS = 12n;
const MAX_SEQ = (1n << SEQ_BITS) - 1n;
const M_SHIFT = SEQ_BITS, DC_SHIFT = SEQ_BITS + M_BITS, TS_SHIFT = SEQ_BITS + M_BITS + DC_BITS;

class Snowflake {
  constructor({ dc, machine, now = () => BigInt(Date.now()), sleep = null, maxBackwardWaitMs = 5n }) {
    if (dc < 0 || dc >= 32 || machine < 0 || machine >= 32) throw new RangeError('dc/machine must be 0..31');
    this.dc = BigInt(dc); this.machine = BigInt(machine);
    this.now = now; this.maxWait = maxBackwardWaitMs;
    this.lastTs = -1n; this.seq = 0n;
  }
  next() {
    let ts = this.now();
    if (ts < this.lastTs) {
      const drift = this.lastTs - ts;
      // small regression: refuse to go backwards; spin until the clock catches up
      if (drift > this.maxWait) throw new Error(`clock moved backwards by ${drift}ms, refusing to issue ids`);
      while (ts < this.lastTs) ts = this.now();
    }
    if (ts === this.lastTs) {
      this.seq = (this.seq + 1n) & MAX_SEQ;
      if (this.seq === 0n) { // sequence exhausted this ms: wait for next ms
        while (ts <= this.lastTs) ts = this.now();
      }
    } else this.seq = 0n;
    this.lastTs = ts;
    return ((ts - EPOCH) << TS_SHIFT) | (this.dc << DC_SHIFT) | (this.machine << M_SHIFT) | this.seq;
  }
}
const decode = (id) => ({
  timestamp: Number((id >> TS_SHIFT) + EPOCH),
  dc: Number((id >> DC_SHIFT) & 31n),
  machine: Number((id >> M_SHIFT) & 31n),
  seq: Number(id & MAX_SEQ),
});

// --- self-test with a fake clock so results are deterministic ---
let fake = 1700000000000n;
const gen = new Snowflake({ dc: 3, machine: 17, now: () => fake });
const a = gen.next(), b = gen.next();
console.log('a =', a.toString(), decode(a));
console.log('b =', b.toString(), decode(b));
console.assert(b > a, 'same-ms ids must increase');
console.assert(decode(a).dc === 3 && decode(a).machine === 17, 'fields round-trip');
console.assert(decode(a).timestamp === 1700000000000, 'timestamp round-trips');

// sequence rollover: issue 4097 ids in one fake ms; the clock must tick forward once
let calls = 0;
const g2 = new Snowflake({ dc: 0, machine: 1, now: () => { calls++; return calls > 4200 ? 1700000000001n : 1700000000000n; } });
const ids = new Set(); let prev = -1n;
for (let i = 0; i < 4097; i++) { const id = g2.next(); ids.add(id); console.assert(id > prev); prev = id; }
console.log('4097 ids, unique =', ids.size, ' last decoded =', decode(prev));
console.assert(ids.size === 4097 && decode(prev).seq === 0 && decode(prev).timestamp === 1700000000001);

// clock regression: small drift waits, large drift throws
let t = 1700000005000n;
const g3 = new Snowflake({ dc: 1, machine: 1, now: () => t });
g3.next();
t = 1700000004999n; // 1ms back
let spins = 0; const g3now = g3.now; g3.now = () => { if (++spins > 3) t = 1700000005000n; return g3now(); };
console.log('after 1ms regression id ok:', g3.next() > 0n);
t = 1700000004000n; g3.now = g3now;
try { g3.next(); } catch (e) { console.log('large drift ->', e.message); }

// throughput on the real clock
const real = new Snowflake({ dc: 1, machine: 2 });
const N = 200000, t0 = process.hrtime.bigint(); const seen = new Set();
for (let i = 0; i < N; i++) seen.add(real.next());
const ms = Number(process.hrtime.bigint() - t0) / 1e6;
console.log(`generated ${N} unique=${seen.size === N} in ${ms.toFixed(0)}ms (~${Math.round(N / ms * 1000)} ids/s, capped at 4096/ms = 4.096M/s)`);
console.assert(seen.size === N);
// 41-bit range
console.log('41-bit lifetime (years):', (Number(2n ** 41n) / (1000 * 3600 * 24 * 365.25)).toFixed(1));

Prints two decoded ids from one millisecond (sequence 0 then 1), a 4,097-id burst that rolls the sequence over and advances the timestamp by exactly one ms, a spin-wait over a 1 ms regression, a refusal on a 1,000 ms regression, and a ~200k-id uniqueness run with measured throughput (about 2 M ids/s on a laptop).

Gotcha, the 253 trap: Snowflake ids are ~1.7 × 1018, far above Number.MAX_SAFE_INTEGER (≈ 9.007 × 1015). JSON.parse in a browser will round them and two different ids can become the same number. This is why Twitter's API returns both id and id_str. Always serialize 64-bit ids as strings across JS boundaries.

Scaling and production

Deployment shape and gotchas

  • Library vs service. A library has zero network hops and no extra SPOF, but needs worker ids for every app process. A service concentrates the worker-id problem in few nodes at the price of an RPC (sub-millisecond in-DC). Large shops typically do the library variant when processes are long-lived, service when they are short-lived (functions, batch).
  • Batching. Let callers request n ids at once (nextBatch(1000)); amortizes RPC cost and reduces lock contention on the generator.
  • Thread safety. The (lastTs, seq) update must be atomic; use a mutex or a single-threaded actor. In Node, a synchronous function is naturally atomic per process, but cluster/worker-threads need distinct worker ids.
  • Observability. Export: ids/s, sequence-exhaust waits, clock-regression refusals, lease renewals, and max observed clock offset from NTP. The regression counter is the one that should page someone.
  • Security. Ids are guessable. Never use them as an authorization token; use per-object authorization, and expose opaque tokens externally if enumeration is a problem.
  • Multi-region. Allocate disjoint worker-id ranges per region (e.g. dc bits = region) so there is no cross-region lease. Ordering across regions is only as good as inter-region clock skew.
  • Hot-key avoidance. Monotonic ids concentrate inserts on the right edge of a B-tree (good locality) but create a hot shard in range-partitioned stores like HBase or Bigtable. Hash or reverse the key, or prefix a salt, if you range-partition on the id.
Checklist

Interview and design checklist

  • Stated requirements: unique, numeric, 64-bit, time-sortable, 10k+/s, highly available.
  • Rejected multi-master (step coupling), UUID (128-bit, unordered), single ticket server (SPOF) with reasons.
  • Drew the 1/41/5/5/12 layout and computed lifetime (~69.7 years) and per-worker rate (4,096/ms).
  • Explained how worker ids are assigned (static, lease, ordinal) and their failure behaviour.
  • Covered clock sync (NTP), regression handling, and restart safety.
  • Discussed tuning bit sections (more sequence for bursty, more time for long-lived).
  • Mentioned HA: multiple generators, library embedding, no runtime coordination.
  • Called out string serialization for JS clients and the guessability of ids.
FAQ · Common Questions

Frequently Asked Questions

Are Snowflake ids strictly increasing?

Per worker, yes, as long as the clock never regresses. Globally, no: they are ordered by millisecond then by worker bits, so two workers inside the same millisecond produce ids ordered by worker number, and clock skew can reorder events across machines. They are k-sortable, not totally ordered.

What if I need more than 4,096 ids per millisecond on one machine?

Shift bits: cut machine bits or timestamp precision (Sonyflake-style 10 ms units) to widen the sequence, or run several generators per machine with distinct worker ids. At 4 million ids per second per worker you are usually limited by the database, not the generator.

Why not just use a database sequence with large caching?

That is the block-lease design and it is fine for moderate scale. You get dense ints and an easy mental model, but you keep a stateful central dependency, ids are not time-ordered across workers, and a crash burns the cached block. It is a good answer if you are already on one PostgreSQL primary and not sharded yet.

How do you guarantee uniqueness across data centers?

By construction: dc and machine bits make every (worker, ms, seq) tuple distinct. The only global requirement is that each worker id is held by one live process at a time, which you enforce at startup with a lease or static allocation, not on the hot path.

Should ids be sortable at all? Does it leak information?

Sortability gives index locality and cheap "recent first" queries. It leaks creation time and, with sequence values, approximate volume. For public identifiers where that matters, store the sortable id internally and expose a separate random public id.

Snowflake or UUIDv7 today?

If you control the schema and 16 bytes is fine, UUIDv7 gives most of the benefits with no worker-id service. Choose Snowflake when you need an 8-byte integer, JSON-friendly decoding of time, or routing bits inside the id.

Key Takeaway

Do not share a counter; share a convention. Time in the high bits gives order, a leased worker number gives uniqueness, and a local sequence gives burst capacity. The whole design is safe exactly as long as one assumption holds, that no worker ever sees time go backwards, so the interesting engineering is the guard around the clock, not the bit shifting.
