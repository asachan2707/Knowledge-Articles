Design a Proximity Service

Find the restaurants within 500 metres of me. The problem is a read-heavy, slowly changing geospatial index, and the whole chapter is the question of how to turn two-dimensional distance into something a database or an in-memory structure can answer fast.

"Find nearby" sounds like a WHERE clause. It is actually a mismatch between the shape of the question (a disc on a sphere) and the shape of every ordinary index (a one-dimensional sorted order). Every algorithm in this chapter is a different way to flatten the plane into a line while keeping near things near.

Core idea: map each point to a cell identifier such that nearby points share identifier prefixes (or tree paths), then answer a radius query as "look up my cell and its neighbours, fetch candidates, filter by exact distance". The index narrows; the exact maths decides.

A public design to anchor on

Geospatial indexes in the wild

Redis GEOADD stores each member in a sorted set using a 52-bit integer geohash as its score, so GEOSEARCH is a handful of range scans on a skip list plus an exact distance filter. MongoDB's 2dsphere index and Google's S2 library use hierarchical cell IDs on a cube mapped sphere. PostGIS uses an R-tree (GiST) over bounding boxes, and Lucene and Elasticsearch use BKD trees for geo points. Four products, four structures, one pattern: reduce 2D to an ordered key, scan a few ranges, then filter exactly. Knowing this is what lets you say "I would use Redis GEO or PostGIS in practice, but here is what is inside".

Requirements and numbers

Scope and sizing

  • Search: given (lat, lon, radius) return businesses within that radius; default 5 km, user-selectable from 0.5 km to 20 km.
  • Business CRUD: owners add, edit, delete. Changes need not be visible instantly; next-day is acceptable.
  • Detail view: full business info by ID.
  • Non-functional: low latency (users are standing on a street), availability through lunchtime spikes in dense areas, and privacy compliance (GDPR/CCPA) for any stored user location.

High-level design

Two services with opposite personalities

client ──▶ Load balancer ─┬─▶ Location-Based Service (LBS) read-only, stateless, hot │ │ geohash/quadtree lookup, distance filter, rank │ ▼ │ Geospatial index (cache + read replicas) │ └─▶ Business Service CRUD + detail views, write path │ ▼ Primary DB ──▶ replicas (business table, geo index table) │ nightly job: rebuild/patch geo index

The LBS handles only search. It is read-only, stateless and absorbs the spiky load, so it autoscales horizontally with no coordination. The Business Service owns writes and detail reads at far lower volume. Splitting them lets each scale on its own signal and lets you deploy a risky index change to the LBS without touching CRUD. The database runs one primary with many replicas; replication lag of seconds is acceptable because business data is not real-time.

Deep dive 1

Why the naive query fails, and the index family

The first idea is a bounding box: WHERE lat BETWEEN a AND b AND lon BETWEEN c AND d. Even with an index on each column this is slow. A B-tree on lat returns every business in a horizontal band around the whole globe, a B-tree on lon returns a vertical band, and the database must intersect two huge sets. A composite index (lat, lon) is only effective on the first column. That is the "one-dimensional index" problem.

All fixes convert 2D location to a 1D key (hash-based) or a tree that prunes in both dimensions at once.

Geohash is the interview default because you can implement it in ten lines and run it in plain SQL or Redis. The rest of this chapter treats it as the primary and compares quadtree and S2 against it.

Deep dive 2

Geohash in detail

Construction. Start with the interval lon in [-180, 180]. Ask whether the point is in the upper or lower half: that is bit 1. Then lat in [-90, 90]: bit 2. Alternate lon and lat, halving each time. Group every 5 bits into one base32 character (digits and letters excluding a, i, l, o). The code is executable below; the reference vector (57.64911, 10.40744) → u4pruydqqvj is checked in the tests. Because bits alternate, the sequence of cells is a Z-order curve (a Morton code).

Prefix property. Two points that share a prefix lie inside the same ancestor cell, so a prefix LIKE '9q8yy%' on a B-tree is a range scan. The converse does not hold: two points can be metres apart and share no prefix, because a cell boundary (such as the equator, the prime meridian, or the edge of any parent cell) cuts between them.

Cell widths shrink towards the poles because longitude lines converge, so a "length 6" cell is physically narrower at 60 degrees north than at the equator. The sample code derives precision from actual cell dimensions at the query latitude rather than a fixed table.

Choosing precision and covering the circle

Pick the longest geohash whose cell is at least as large as the search radius. The query disc then can overlap at most the home cell and its eight neighbours, so the candidate set is those nine cells. For a 500 m radius that is length 6. Fetch the IDs in all nine cells in parallel, compute exact great-circle (haversine) distance, drop anything outside the radius, sort, paginate.

┌────────┬────────┬────────┐ │ NW │ N │ NE │ candidate cells = home + 8 neighbours ├────────┼────────┼────────┤ │ W │ HOME │ E │ the search circle (radius r ≤ cell size) can never │ │ ●─r─╮│ │ reach beyond this 3×3 block ├────────┼────────┼────────┤ │ SW │ S │ SE │ but 3×3 may hold ~10x more points than the circle needs → exact filter └────────┴────────┴────────┘

Boundary issues

  • Close but different prefixes. Solved by the 3x3 neighbour query above. Compute neighbours by stepping one cell width/height from the cell centre and re-encoding, as in the example. Handle longitude wrap at the antimeridian and clamp at the poles.
  • Long shared prefix, different cell. Two points sharing five characters can still lie in distinct length-6 cells; the neighbour query again covers it. Never assume "same prefix means close" without the exact distance filter.
  • Not enough results. In sparse areas the 3x3 block may hold fewer than the wanted count. Drop one character (cell grows 32x in area) and query again, repeating until enough or until a cap. The product behaviour "widen the search" maps cleanly onto "shorten the prefix".
Gotcha: the 3x3 block is a superset, so you must always do the exact distance filter and you must over-fetch for ranking. Also remember a geohash cell is not a circle; at the corners the true circle includes noticeably less area than the block, which is why post-filtering removes a large fraction of candidates.

Storing it

The geospatial index table is just (geohash, business_id), with one row per business per supported precision (for example 4, 5, 6) or a single 12-character hash queried with prefix ranges. Prefer separate rows per precision for key-value stores, where range scans are weaker than point lookups: GET geohash:6:9q8yym → {ids}. In SQL, a composite primary key (geohash, business_id) turns every lookup into an index range scan. Updates are cheap: insert or delete one row per precision. Avoid keeping a precision in a single column that is then updated in place; with per-precision rows there is nothing to compute at read time.

Deep dive 3

Quadtree and S2

Quadtree. Start with one node covering the world. While a node holds more than N businesses (the chapter uses 100), split it into four equal quadrants and push points down. The result has tiny cells in downtown Tokyo and enormous ones over the Pacific, so every leaf holds a bounded number of points regardless of density. That bound is the point: query cost is proportional to the result, not to cell area.

Searching: descend to the leaf containing the query point, collect its candidates, then expand to sibling and neighbour leaves in best-first order of box distance until the k-th best distance is smaller than the next box's distance. That prune rule is what makes k-nearest queries ("the three closest petrol stations, however far") natural here and awkward with geohash, where you would loop over shrinking prefixes. The example implements it and verifies against brute force.

Memory and build arithmetic

200 M businesses with at most 100 per leaf gives at least 2 M leaves. A leaf holds up to 100 eight-byte IDs plus a bounding box (say 32 bytes): about 830 bytes. 2 M × 830 B ≈ 1.7 GB, and internal nodes add roughly a third as many nodes with only child pointers, tens of megabytes. Real trees are less full than the maximum (splits create half-empty children), so budget 2 to 4x. Everything fits comfortably on one commodity server. Construction is O(n log n) in practice, which for 200 M points is minutes.

Operational consequences

  • Start-up time. A fresh LBS node cannot serve until the tree is built (or loaded from a snapshot). Do not restart the fleet at once. Roll out in small waves, keep capacity for the nodes that are building, and prefer loading a serialised snapshot over rebuilding from the database.
  • Updates. Simple approach: every node rebuilds periodically (nightly) from the source of truth, which matches the "next-day visibility" requirement. In-place updates are possible but need fine-grained locking or copy-on-write subtrees, and a deletion that merges nodes is fiddly. Prefer immutable snapshots swapped atomically with a pointer flip.
  • Consistency between nodes. Nodes rebuilt at different moments disagree for a while. For a search service this is fine; for a booking service it would not be.

Google S2. The sphere is projected onto the six faces of a cube, each face is recursively quartered into cells (levels 0 to 30, level 30 is about a centimetre), and cells are numbered along a Hilbert space-filling curve. Hilbert has better locality than Z-order: it never makes the long diagonal jumps of Morton order, so a region maps to fewer contiguous ID ranges. Two further advantages: a region coverer can approximate any shape (circle, polygon, geofence) with a set of cells of mixed levels given min level, max level and max cell count, and the projection keeps cell areas roughly uniform. This is why S2 is the choice for geofencing, and it underlies MongoDB's 2dsphere. The cost is conceptual weight and a library dependency.

Trade-offs

Geohash vs quadtree vs S2

Geohash strengths

  • Stateless: just a key into a DB or Redis
  • Updates are single-row inserts and deletes
  • Fixed-radius search is a 9-key fetch
  • Trivial to shard or cache

Geohash weaknesses

  • Cell size cannot follow population density
  • Boundary handling needed
  • k-nearest is indirect
  • Z-order jumps reduce locality

Quadtree strengths

  • Bounded points per leaf in any region
  • Natural k-nearest and variable radius
  • Excellent in-memory speed

Quadtree weaknesses

  • Build time and cold start
  • Updates require rebuild or locks
  • Each node holds a full copy

Scaling and caching

Database, cache, regions

The business table

200 GB is small enough for one primary, but concentrated read traffic and operational limits push toward sharding by business_id. Sharding by ID spreads rows evenly and keeps detail lookups to one shard. Sharding by location sounds attractive for locality but creates hot shards (Manhattan) and awkward neighbour queries across shard borders, so avoid it for the business table.

The geospatial index

About 5 GB does not need sharding. Use one primary and as many read replicas as the QPS demands. If you do want to cache aggressively, put the index in Redis (geohash:6:9q8yym → set of IDs) in front of the SQL table, or just embed it in the LBS process memory. Redis cluster by key hash spreads cells evenly.

Cache keys

Raw GPS coordinates are a poor cache key: they are noisy at the metre level and change continuously as the user moves, so the hit rate approaches zero. The geohash cell is a natural quantisation: everyone standing in the same 1.2 km by 0.6 km cell reuses the same entry. Two caches work in tandem: geohash → [business_ids] (tiny, extremely hot, long TTL since data changes daily) and business_id → detail (larger, TTL by volatility). Note ranking by distance cannot be cached per cell, since it depends on the exact origin, so the LBS sorts at request time over at most a few hundred candidates, which costs microseconds.

Regions and availability

Deploy the LBS in several regions and route users to the closest. Replicas of the index are read-only copies, so there is no cross-region write path to worry about. Business writes go to a single primary region and replicate asynchronously; the daily batch rebuild distributes new snapshots. Because tolerance for staleness is high, you can serve from the stale copy during a primary-region outage.

Business updates

A write lands in the primary; a nightly job (or a stream consumer for fresher updates) recomputes affected geohash rows and refreshes caches. Handling an update that moves a business (new lat/lon) means removing it from the old cell's rows and adding to the new; do both in one transaction. Cache invalidation then needs only the old and new cell keys.

Final request path

Putting it together

1. client → LB: lat=37.77672, lon=-122.41673, radius=500 m 2. LB → LBS (any node, stateless) 3. LBS: radius 500 m → geohash length 6; home = 9q8yym 4. LBS: neighbours(9q8yym) → 8 cells → list of 9 keys 5. LBS → Redis (geohash index), 9 GETs in parallel → candidate business_ids 6. LBS: exact haversine filter ≤ 500 m; sort by distance (or rating-weighted rank) 7. LBS → Redis (business info), MGET top page → names, photos, ratings 8. LBS → client: ranked page + cursor typical budget: tens of ms

The two latency levers are the parallel fan-out in step 5 and the fact that the only mutable state the LBS touches is cache. If both Redis tiers fail, the LBS can fall back to the SQL replicas (slower but correct), which is a nicely cheap degradation path.

Runnable code

Geohash with neighbours and a quadtree k-NN

The example implements geohash encode, decode, neighbour computation (with wraparound and clamping) and precision selection from actual cell size. It indexes 20,000 random San Francisco points, runs the 500 m search through the nine-cell method, and asserts the result is identical to brute-force haversine. It then builds a capped-leaf quadtree and checks its 5-nearest answer against brute force.

JavaScript Example 
// Geohash (encode/decode/neighbours/cover-radius) + bucket-capped quadtree kNN, validated vs brute force.
import assert from 'node:assert/strict';
const B32 = '0123456789bcdefghjkmnpqrstuvwxyz';

function encode(lat, lon, len = 9) {
  let latR = [-90, 90], lonR = [-180, 180], bits = 0, ch = 0, even = true, out = '';
  while (out.length < len) {
    const r = even ? lonR : latR, v = even ? lon : lat, mid = (r[0] + r[1]) / 2;
    ch <<= 1; if (v >= mid) { ch |= 1; r[0] = mid; } else r[1] = mid;
    even = !even;
    if (++bits === 5) { out += B32[ch]; bits = 0; ch = 0; }
  }
  return out;
}
function bounds(hash) {
  let latR = [-90, 90], lonR = [-180, 180], even = true;
  for (const c of hash) {
    const v = B32.indexOf(c);
    for (let b = 4; b >= 0; b--) {
      const r = even ? lonR : latR, mid = (r[0] + r[1]) / 2;
      if ((v >> b) & 1) r[0] = mid; else r[1] = mid;
      even = !even;
    }
  }
  return { latR, lonR };
}
const decode = h => { const { latR, lonR } = bounds(h); return { lat: (latR[0] + latR[1]) / 2, lon: (lonR[0] + lonR[1]) / 2 }; };

// neighbours by decoding the cell centre and stepping one cell height/width (wraps in lon, clamps in lat)
function neighbours(hash) {
  const { latR, lonR } = bounds(hash);
  const h = latR[1] - latR[0], w = lonR[1] - lonR[0];
  const c = decode(hash), out = [];
  for (const dy of [-1, 0, 1]) for (const dx of [-1, 0, 1]) {
    if (!dx && !dy) continue;
    const lat = c.lat + dy * h; if (lat > 90 || lat < -90) continue;
    let lon = c.lon + dx * w; if (lon > 180) lon -= 360; if (lon < -180) lon += 360;
    out.push(encode(lat, lon, hash.length));
  }
  return [...new Set(out)];
}

const R = 6371008.8;
const rad = d => d * Math.PI / 180;
function haversine(a, b) {
  const dLat = rad(b.lat - a.lat), dLon = rad(b.lon - a.lon);
  const s = Math.sin(dLat / 2) ** 2 + Math.cos(rad(a.lat)) * Math.cos(rad(b.lat)) * Math.sin(dLon / 2) ** 2;
  return 2 * R * Math.asin(Math.sqrt(s));
}
// pick the longest precision whose cell is still at least as big as the radius (both dims)
function precisionFor(radiusM, lat) {
  for (let len = 12; len >= 1; len--) {
    const { latR, lonR } = bounds(encode(lat, 0, len));
    const hM = rad(latR[1] - latR[0]) * R, wM = rad(lonR[1] - lonR[0]) * R * Math.cos(rad(lat));
    if (Math.min(hM, wM) >= radiusM) return len;
  }
  return 1;
}

class GeoIndex { // the "geospatial index table": geohash -> set of business ids
  cells = new Map(); pts = new Map(); len = 6;
  constructor(len) { this.len = len; }
  add(id, lat, lon) {
    this.pts.set(id, { lat, lon });
    const k = encode(lat, lon, this.len);
    (this.cells.get(k) ?? this.cells.set(k, new Set()).get(k)).add(id);
  }
  search(lat, lon, radiusM) {
    const me = { lat, lon }, home = encode(lat, lon, this.len);
    const cand = [];
    for (const cell of [home, ...neighbours(home)]) for (const id of this.cells.get(cell) ?? []) cand.push(id);
    return cand.map(id => ({ id, d: haversine(me, this.pts.get(id)) })).filter(x => x.d <= radiusM).sort((a, b) => a.d - b.d);
  }
}

class Quadtree {
  constructor(box, cap = 100, depth = 0) { this.box = box; this.cap = cap; this.pts = []; this.kids = null; this.depth = depth; }
  insert(p) {
    if (this.kids) return this.kids[this.#q(p)].insert(p);
    this.pts.push(p);
    if (this.pts.length > this.cap && this.depth < 24) {
      const { x0, y0, x1, y1 } = this.box, mx = (x0 + x1) / 2, my = (y0 + y1) / 2;
      this.kids = [{ x0, y0, x1: mx, y1: my }, { x0: mx, y0, x1, y1: my }, { x0, y0: my, x1: mx, y1 }, { x0: mx, y0: my, x1, y1 }]
        .map(b => new Quadtree(b, this.cap, this.depth + 1));
      const old = this.pts; this.pts = [];
      old.forEach(q => this.kids[this.#q(q)].insert(q));
    }
  }
  #q(p) { const mx = (this.box.x0 + this.box.x1) / 2, my = (this.box.y0 + this.box.y1) / 2; return (p.x >= mx ? 1 : 0) + (p.y >= my ? 2 : 0); }
  // k nearest in planar space with best-first pruning on box distance
  knn(x, y, k) {
    const best = []; // sorted ascending, max k
    const boxD = b => { const dx = Math.max(b.x0 - x, 0, x - b.x1), dy = Math.max(b.y0 - y, 0, y - b.y1); return dx * dx + dy * dy; };
    const visit = n => {
      if (best.length === k && boxD(n.box) > best[k - 1].d) return;
      if (!n.kids) { for (const p of n.pts) { const d = (p.x - x) ** 2 + (p.y - y) ** 2; best.push({ ...p, d }); } best.sort((a, b) => a.d - b.d); best.length = Math.min(best.length, k); return; }
      [...n.kids].sort((a, b) => boxD(a.box) - boxD(b.box)).forEach(visit);
    };
    visit(this); return best;
  }
  leaves() { return this.kids ? this.kids.reduce((s, c) => s + c.leaves(), 0) : 1; }
}

console.log('SF 37.77672,-122.41673 ->', encode(37.77672, -122.41673, 6));
console.log('neighbours of 9q8yyk:', neighbours('9q8yyk').join(' '));

let s = 42; const rand = () => (s = (s * 1664525 + 1013904223) >>> 0) / 2 ** 32;

const kx = Math.cos(rad(37.78));
const proj = p => ({ id: p.id, x: p.lon * kx, y: p.lat });
const qt = new Quadtree({ x0: -123 * kx, y0: 37, x1: -122 * kx, y1: 38 }, 100);

const q = proj(me), near = qt.knn(q.x, q.y, 5);

console.log('quadtree leaves:', qt.leaves(), '| 5-NN ids:', near.map(n => n.id).join(','));

Production gotchas

Things that bite after launch

  • Distance on a sphere. Use haversine (or Vincenty for high accuracy). Euclidean on raw degrees is wrong because a degree of longitude shrinks with the cosine of latitude, which the quadtree example corrects for with a projection factor.
  • Latitude/longitude order. GeoJSON and many databases use (lon, lat); most mobile APIs use (lat, lon). Mixing them puts San Francisco in Antarctica. Write the test.
  • Privacy. The query contains the user's location. Log at geohash-length-5 granularity, not raw coordinates; set retention; honour deletion requests; coarsen before sending to analytics.
  • Ranking beyond distance. Real products blend distance, rating, open-now, popularity, personalisation. Retrieval (this chapter) gives a candidate set; a separate ranker orders it. Do not push ranking into the index.
  • Categories and filters. Filtering "open now AND vegetarian" after retrieval wastes work in dense areas. At scale, include category in the index key (or use a search engine such as Elasticsearch that combines geo and attribute filters).
  • Pagination stability. Distance-sorted results shift as the user moves; use a cursor that pins the origin snapshot.
  • Test data skew. Uniform random test data hides every density problem. Load-test with real city clustering.

FAQ · Common Questions

Frequently Asked Questions

Why not just use a database with a spatial index?

Often you should: PostGIS with a GiST index answers this directly and handles polygons, joins and filters. The interview asks you to explain what is inside, and at extreme read QPS an in-memory or Redis-backed cell lookup is cheaper per query than a disk-based spatial index.

What if a geohash cell contains millions of businesses?

You chose too coarse a precision for that region. Use adaptive precision: split hot cells into longer prefixes, or serve dense regions from a quadtree. A skewed distribution is the textbook reason quadtrees exist.

How do you support "open now" or "category" filters efficiently?

Small result sets: post-filter. Large: add the category to the index key, or push everything to a search engine that supports geo plus filter queries in one pass.

How would you handle a moving user, such as someone driving?

Re-query when the user leaves their current cell or moves more than a fraction of the radius, rather than every GPS tick. Cache neighbours of the current cell client-side. Truly continuous tracking is the next chapter's problem.

Geohash versus S2: which would you really pick?

For a fixed-radius lookup with a key-value store, geohash for simplicity. For anything involving regions, high latitude accuracy, variable-size coverings or a need for locality-preserving ranges, S2 (or H3, Uber's hexagonal grid, which has uniform neighbour distances).

How fresh must the index be?

The requirement says daily. If the product later wants minutes, stream changes from the primary (CDC) into index updates and invalidate the specific cell keys; the architecture already supports this because the index is derived data.

Key Takeaway

Proximity search is "flatten the plane, scan a few ranges, filter exactly". Geohash with a 3x3 neighbour query is the simple, update-friendly default; a quadtree wins when density varies or you need k-nearest; S2 wins for regions. The index is small enough to replicate rather than shard, and the cache key is the cell, never the raw coordinate.
