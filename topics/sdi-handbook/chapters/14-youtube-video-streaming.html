Design YouTube (Video Streaming)

A video platform is two separate systems glued by a blob store: a slow, CPU-hungry, asynchronous ingest pipeline and a fast, bandwidth-hungry, CDN-fronted playback path. This page walks through both, with the transcoding DAG as the centrepiece.

Video looks like a storage problem and behaves like a money problem. A 300 MB upload becomes a dozen renditions, each cut into seconds-long segments, and then gets pulled across the planet thousands of times. The design question is not "where do the bytes live" but "how few times do we pay to move and compute them".

Core idea: split the product at the blob store. Everything left of it (upload, transcode, package) is asynchronous, parallel, retryable batch work. Everything right of it (playback) is a static-file delivery problem that a CDN solves. Neither side should ever wait on the other.

A public design to anchor on

What Netflix and YouTube publicly describe

Netflix has written openly about its encoding pipeline: a source file is cut into chunks, each chunk is encoded independently on a farm of workers, and the results are stitched and validated. They later moved to shot-based encoding, where chunk boundaries follow scene cuts so each shot can be given its own bitrate budget. YouTube's public material shows the same shape: upload, fan out to many encoders, publish a ladder of resolutions. The shared lesson is that chunk-level parallelism turns a job that would take longer than the video itself into one that finishes in a fraction of the runtime.

Requirements and numbers

Scope and back-of-envelope

Functional scope is deliberately two verbs: upload a video, watch a video, on phones, browsers and TVs. The non-functional list is what drives the architecture: fast uploads, smooth playback, the ability to switch quality mid-stream, low infrastructure cost, and high availability. Notice that "low cost" sits next to "fast"; at this scale they are in tension and you must say which wins where.

Sizing (assumptions: 5 M DAU, 10% upload one video a day, 300 MB average, 5 videos watched per user per day, 1 GB cap)

Read the table: storage is a rounding error next to delivery. A petabyte of S3 costs tens of thousands per month; a petabyte of CDN egress at list price costs twenty thousand dollars per petabyte served, every day. Every optimisation worth discussing in this chapter eventually points at egress.

Note that the quoted $150 K/day is a list-price figure. Large publishers negotiate committed-use pricing, peer directly with ISPs and run their own caches, which is exactly the last cost lever discussed below.

High-level design

Components and the two flows

UPLOAD PATH (async, write-heavy, CPU-heavy) client ──(1) pre-signed PUT, chunked──▶ Original storage (blob) │ │ object-created event │(2) metadata: title, size, format ▼ ▼ Transcoding pipeline API servers ──▶ Metadata DB (+cache) │ preprocess → DAG → workers ▲ ├──▶ Transcoded storage ──▶ CDN (push / warm) │ └──▶ completion queue ──▶ handlers └───── status = READY, notify uploader ◀──────────┘ PLAYBACK PATH (sync, read-heavy, bandwidth-heavy) player ──▶ API (fetch manifest URL) ──▶ metadata player ══▶ CDN edge ══ segment GETs (.m4s / .ts) ══▶ cache hit; miss → origin ABR logic in the player picks the rung per segment

Component roles

  • Client: phone, laptop, smart TV. It owns the adaptive-bitrate decision, so the server stays dumb and cacheable.
  • API servers: everything except the video bytes: auth, feed, metadata edits, issuing upload URLs. Stateless, horizontally scaled.
  • Metadata DB and cache: title, description, owner, renditions available, processing state. Sharded, replicated; read-heavy so a cache fronts hot videos.
  • Original storage: blob store holding exactly what the user sent. Keep it: re-encoding for a new codec years later needs the source.
  • Transcoding servers: the compute farm, the focus of the deep dive.
  • Transcoded storage and CDN: the distributable outputs, and the edge caches that actually serve viewers.
  • Completion queue and handlers: decouple "encoding finished" from "update the database and tell the user".

Upload flow, step by step

The client does two things in parallel. It streams the video to blob storage, and it posts the metadata (file name, size, declared format) to an API server, which inserts a row in state UPLOADING. When the blob lands, an event kicks off transcoding. Each finished output is written to transcoded storage, and when the last one is done a completion event goes on a queue. A handler flips the metadata row to READY, pushes the assets towards the CDN and notifies the uploader. The row state machine (UPLOADING → PROCESSING → READY | FAILED) is the contract between the two halves, and it is the only thing the playback side needs to trust.

Streaming flow

"Streaming" here does not mean a long-lived socket from the server. The player fetches a small manifest that lists renditions and segment URLs, then issues ordinary HTTP GETs for consecutive segments, typically two to ten seconds each. Because segments are plain static objects, any CDN can cache them and any HTTP stack can retry them. The two dominant protocols are Apple's HLS (m3u8 playlists, historically MPEG-TS segments, now commonly fragmented MP4) and MPEG-DASH (an XML .mpd manifest with fMP4 segments). Common Media Application Format (CMAF) lets one set of fMP4 segments satisfy both, which halves storage and CDN cache footprint for operators who serve both ecosystems. Older protocols such as Adobe HDS have faded with Flash; if an interviewer names one, say it exists and that your player stack decides the choice.

Do not stream from your API tier. Putting bytes through application servers couples your stateless fleet to the heaviest bandwidth in the system and gives up edge caching. Video bytes should never touch the API servers in either direction; they carry URLs and signatures, not payloads.
Deep dive 1

Why transcode at all, and what a video file really is

Three reasons, in order of importance. First, raw camera or screen-recorder output is enormous; modern codecs compress by one to two orders of magnitude. Second, devices differ: a ten-year-old TV and a new phone support different codecs, profiles and containers. Third, networks differ and change: a viewer on a train needs a 400 kbps rung one minute and a 5 Mbps rung the next.

ConceptWhat it isExamples
ContainerThe wrapper that interleaves video, audio, subtitles and timing metadataMP4, MKV, WebM, MPEG-TS, fMP4
CodecThe compression algorithm for one stream inside the containerH.264/AVC, H.265/HEVC, VP9, AV1; AAC and Opus for audio
Bitrate and resolutionThe quality/size knobs applied per rendition240p at about 0.4 Mbps up to 4K at 15+ Mbps
GOPGroup of Pictures: a keyframe (I-frame) followed by dependent P/B frames until the next keyframetypically 1 to 4 seconds

The GOP is the unit that matters architecturally. A GOP starts with a keyframe that can be decoded alone, so it is the smallest chunk you can hand to a worker, and also the smallest segment a player can switch quality on. If you cut a file in the middle of a GOP you either re-encode more than needed or produce a segment that cannot start playback. This is why the preprocessor aligns splits to GOP boundaries.

Compute is the real cost of codecs. AV1 saves bandwidth over H.264 at equal quality but costs far more CPU per second of video to produce. That flips the economics for popular content (encode once, serve a million times: spend the CPU) versus the long tail (watched twice: do not).

Adaptive bitrate (ABR) in one paragraph

The encoder produces a ladder: the same content at several resolution/bitrate pairs, all cut at identical segment boundaries. The player measures recent throughput and buffer level, and before each segment request picks the highest rung it expects to download faster than it plays. Switching is seamless precisely because every rung has keyframes at the same timestamps. Throughput-based rules are simple but jittery; buffer-based rules are more stable; production players blend both and add a safety margin (the code below uses 80% of measured throughput). Per-title or per-shot ladders, as Netflix publishes, replace the fixed ladder with one tuned to how hard each piece of content is to compress.

Deep dive 2

The transcoding pipeline as a DAG

One upload fans out into many independent jobs: split the container into video, audio and metadata streams; encode the video into several resolutions and codecs; generate thumbnails; burn or overlay a watermark; transcode audio; run content-safety and copyright checks; and finally package manifests. Different creators or product tiers want different subsets. Hard-coding a pipeline for each does not survive contact with product managers, so the pipeline is expressed as a directed acyclic graph of tasks that a configuration file declares.

┌──────────┐ │ split │ stage 0 └────┬─────┘ ┌──────────────┼───────────────┐ ┌───▼───┐ ┌───▼───┐ ┌───▼───┐ │ video │ │ audio │ │ meta │ stage 1 └───┬───┘ └───┬───┘ └───┬───┘ ┌───────┼────────┬─────┘ │ ┌─▼──┐ ┌──▼───┐ ┌──▼────┐ ┌──────────┐ │ │720p│ │1080p │ │thumb │ │watermark │ │ stage 2 (parallel) └─┬──┘ └──┬───┘ └──┬────┘ └────┬─────┘ │ └───────┴────────┴───────────┴─────────┘ ▼ ┌─────────┐ │ package │ manifests + segment index stage 3 └─────────┘

A DAG buys you three things: parallelism (anything with satisfied dependencies runs now), partial retry (a failed 1080p encode does not redo the audio), and configurability (add a task by adding a node and edges). Execution is by topological layers, called stages: stage 0 has no dependencies, stage N depends only on earlier stages. The executable example below computes exactly this layering with Kahn's algorithm and rejects cycles.

The five moving parts

ComponentJobDesign notes
PreprocessorSplits the video into GOP-aligned chunks, generates the DAG from the config, writes chunks and metadata to temporary storagePersisting chunks first is what makes retries cheap. Splitting to GOP boundaries also helps legacy clients that cannot split themselves.
DAG schedulerBreaks the graph into stages and enqueues each stage's tasksA stage is released only when every task of the previous stage reports success, or the dependency edges are tracked per task for finer-grained release.
Resource managerMatches tasks to workers using three queues: a task priority queue, a worker queue ordered by utilisation, and a running queue of (task, worker) pairsPicks the highest-priority task and the best-fit worker, records the pair in the running queue, and moves it back on completion or timeout.
Task workersRun one kind of task each: encode, thumbnail, watermark, mergePools are specialised: GPU or high-core machines for encodes, small ones for thumbnails. Scale each pool on its own queue depth.
Temporary storageChunks and intermediate outputsSmall metadata in memory or a fast KV store; large chunks in blob storage with a short lifecycle rule. Delete once the job is final.

In production you would not hand-write the scheduler. This shape maps onto Temporal, AWS Step Functions with Batch or MediaConvert, or a Kubernetes job controller, and the interview answer should say so while still explaining what those tools do for you. Whichever you choose, tasks must be idempotent: given the same input chunk and parameters, writing the same output key a second time must be harmless. That one property is what lets the scheduler retry blindly. See Idempotency.

Queues between stages

Rather than module A calling module B, put a message queue between each pair: upload to preprocessor, preprocessor to scheduler, workers to completion handler. The benefit is back-pressure and independent scaling. If encoders fall behind during a viral surge, the queue grows (an alarm, not an outage) while uploads keep succeeding. Priority matters here: a creator's 30-second clip should not wait behind a 4-hour livestream archive, and retried tasks should jump the line so a nearly finished job completes. See Message Queues.

Speed, safety, cost

System optimisations

Speed

  • Parallel, resumable uploads. The client slices the file by GOP or fixed size and uploads slices concurrently using multipart upload. A dropped connection resumes from the last acknowledged slice rather than from zero. S3 multipart, the tus protocol and GCS resumable upload sessions all work this way.
  • Upload close to the user. Terminate uploads at the nearest edge or regional ingest point, then move bytes over the provider backbone. Round-trip time to a far region dominates TCP throughput for a single stream.
  • Pipeline parallelism through queues. Because each stage reads from a queue, the encoder can start on the first chunks while later chunks are still uploading, instead of waiting for a complete file.

Safety

  • Pre-signed URLs. The client first asks the API for an upload target. The API authenticates the user, then returns a time-limited, single-object URL signed with the storage provider's credentials. The client uploads straight to blob storage; no credentials leak and no bytes cross the API tier.
  • Content protection. Encrypt segments (AES-128 in HLS, CENC in DASH) and gate the key through a DRM licence server: Widevine on Chrome/Android, FairPlay on Apple, PlayReady on Microsoft. Visible and forensic watermarking deter and trace leaks. Be honest that DRM raises the bar but does not make piracy impossible.
  • Upload validation. Scan the container header, enforce size/duration limits, and run the transcoder in a sandbox: media parsers are a classic source of memory-safety bugs, and you are decoding hostile files.

Cost

  • Pareto the catalogue. Views follow a heavy tail. Keep popular videos in the CDN; serve the tail from regional origin storage with a lower-cost tier and let the first viewer warm the edge.
  • Encode lazily for the tail. Always make the cheap rungs; produce the expensive codecs or 4K rung only after a video crosses a view threshold.
  • Regionalise. A video popular in one country does not need replicas in all points of presence.
  • Own the edge. At sufficient volume, deploy caches inside ISP networks (Netflix Open Connect is the public example) so the traffic never crosses a paid transit link.

Runnable code

DAG stage planner, resource manager, and ABR picker

The example does three things. It layers a transcoding DAG into stages with Kahn's algorithm and detects cycles. It runs the stages through a small resource manager: a binary-heap task queue (encodes outrank other work, retried tasks outrank everything), a worker pool where each job goes to the least-loaded worker, and bounded retries. Finally it picks an ABR rung from measured throughput.

JavaScript Example 
// Video transcoding DAG: stage planning (Kahn layering) + resource manager
// with a priority task queue, least-loaded worker choice and retry on failure.
import assert from 'node:assert/strict';

// 1. DAG -> stages -------------------------------------------------------
function planStages(dag) {
  const indeg = new Map(Object.keys(dag).map(k => [k, 0]));
  for (const deps of Object.values(dag)) for (const d of deps) {
    if (!indeg.has(d)) throw new Error(`unknown dependency ${d}`);
  }
  for (const [task, deps] of Object.entries(dag)) indeg.set(task, deps.length);
  const stages = [];
  let ready = [...indeg].filter(([, n]) => n === 0).map(([k]) => k);
  let seen = 0;
  while (ready.length) {
    stages.push(ready);
    seen += ready.length;
    const next = [];
    for (const done of ready)
      for (const [task, deps] of Object.entries(dag))
        if (deps.includes(done) && indeg.set(task, indeg.get(task) - 1).get(task) === 0) next.push(task);
    ready = next;
  }
  if (seen !== Object.keys(dag).length) throw new Error('cycle detected');
  return stages;
}

// 2. Tiny binary heap used as priority queue -------------------------------
class Heap {
  constructor(cmp) { this.a = []; this.cmp = cmp; }
  get size() { return this.a.length; }
  push(x) {
    const a = this.a; a.push(x); let i = a.length - 1;
    while (i > 0) { const p = (i - 1) >> 1; if (this.cmp(a[i], a[p]) >= 0) break; [a[i], a[p]] = [a[p], a[i]]; i = p; }
  }
  pop() {
    const a = this.a; const top = a[0]; const last = a.pop();
    if (a.length) {
      a[0] = last; let i = 0;
      for (;;) {
        let l = 2 * i + 1, r = l + 1, m = i;
        if (l < a.length && this.cmp(a[l], a[m]) < 0) m = l;
        if (r < a.length && this.cmp(a[r], a[m]) < 0) m = r;
        if (m === i) break; [a[i], a[m]] = [a[m], a[i]]; i = m;
      }
    }
    return top;
  }
}

// 3. Resource manager: run stage by stage, tasks in a stage in parallel ----
async function run(dag, { workers = 3, maxAttempts = 3, flaky = {} } = {}) {
  const log = [];
  const load = new Array(workers).fill(0);              // "worker queue"
  const attemptsSeen = {};
  const exec = async (task, w) => {
    attemptsSeen[task] = (attemptsSeen[task] ?? 0) + 1;
    await new Promise(r => setTimeout(r, 5));
    if ((flaky[task] ?? 0) >= attemptsSeen[task]) throw new Error(`${task} crashed on worker ${w}`);
  };
  const stages = planStages(dag);
  for (const [si, stage] of stages.entries()) {
    const taskQ = new Heap((x, y) => y.prio - x.prio || x.name.localeCompare(y.name));
    stage.forEach(name => taskQ.push({ name, prio: name.startsWith('encode') ? 2 : 1 }));
    const running = new Set();
    const pending = [];
    const dispatch = async () => {
      while (taskQ.size) {
        while (running.size >= workers) await Promise.race(running);
        const t = taskQ.pop();
        const w = load.indexOf(Math.min(...load));      // least-loaded worker
        load[w]++;
        const p = exec(t.name, w).then(
          () => log.push(`stage${si} ${t.name} ok on w${w} (attempt ${attemptsSeen[t.name]})`),
          err => {
            if (attemptsSeen[t.name] >= maxAttempts) throw err;
            log.push(`stage${si} ${t.name} FAILED -> requeue`);
            taskQ.push({ ...t, prio: t.prio + 10 });      // retried work jumps the queue
          }
        ).finally(() => { load[w]--; running.delete(p); });
        running.add(p); pending.push(p);
      }
    };
    await dispatch();
    while (running.size) { await Promise.all(running); await dispatch(); }
    await Promise.all(pending);
  }
  return { stages, log };
}

// 4. Adaptive-bitrate ladder pick -------------------------------------------
const ladder = [ // height, kbps (illustrative ladder)
  { h: 240, kbps: 400 }, { h: 360, kbps: 800 }, { h: 480, kbps: 1400 },
  { h: 720, kbps: 2800 }, { h: 1080, kbps: 5000 },
];
const pickRung = (throughputKbps, safety = 0.8) =>
  [...ladder].reverse().find(r => r.kbps <= throughputKbps * safety) ?? ladder[0];

// ---- demo + self test -------------------------------------------------------
const dag = {
  split: [],
  video: ['split'], audio: ['split'], meta: ['split'],
  encode_720p: ['video'], encode_1080p: ['video'], thumbnail: ['video'], watermark: ['video'],
  package: ['encode_720p', 'encode_1080p', 'audio', 'meta', 'thumbnail', 'watermark'],
};
const stages = planStages(dag);
console.log('stages:', JSON.stringify(stages));
assert.deepEqual(stages[0], ['split']);
assert.equal(stages.at(-1)[0], 'package');
assert.throws(() => planStages({ a: ['b'], b: ['a'] }), /cycle/);

const { log } = await run(dag, { workers: 2, flaky: { encode_1080p: 2 } });
log.forEach(l => console.log(l));
assert.ok(log.some(l => l.includes('encode_1080p FAILED')));
assert.ok(log.some(l => l.includes('encode_1080p ok') && l.includes('attempt 3')));
assert.equal(log.filter(l => l.includes(' ok ')).length, Object.keys(dag).length);

console.log('3 Mbps ->', pickRung(3000).h + 'p', '| 0.4 Mbps ->', pickRung(400).h + 'p', '| 20 Mbps ->', pickRung(20000).h + 'p');
assert.equal(pickRung(3000).h, 480);
assert.equal(pickRung(20000).h, 1080);
console.log('all assertions passed');

Prints the four stages (split; video/audio/meta; four parallel tasks; package), shows encode_1080p failing twice and succeeding on attempt 3, then 480p for 3 Mbps, 240p for 0.4 Mbps, 1080p for 20 Mbps, and "all assertions passed". Executed with Node 20+.

Failure modes

Error handling

FailureClassResponse
Upload connection dropsRecoverableResume from last acknowledged part; abort multipart uploads that sit idle for a day so orphans do not accrue storage cost.
Worker crashes mid-encodeRecoverableRunning-queue entry times out, task requeued at higher priority; the chunk is still in temporary storage so nothing upstream reruns.
Resource shortageRecoverableTasks wait in the queue; autoscale on queue age, not CPU, since idle workers waiting on I/O look healthy.
Corrupt or malformed fileNon-recoverableStop at preprocessing, mark FAILED, surface a specific error to the uploader. Retrying a bad file only burns compute.
Poison task (crashes every worker)Non-recoverableCap attempts, move to a dead-letter queue, alert. One bad title must not starve the fleet.
Metadata DB failover during completionRecoverableCompletion handler is idempotent; redelivered messages set READY again harmlessly.
CDN origin overloaded by a cold viral videoRecoverableOrigin shield / request coalescing so one miss fans in to one origin fetch.
Scaling and production

Where it bends, and gotchas

  • The knee is egress, then transcode throughput. The metadata tier scales like any read-heavy sharded service. The first thing to hurt is the CDN bill; the second is encode latency for long uploads, solved by chunk-level parallelism.
  • Thundering herd on a premiere. A scheduled launch means every viewer asks for the first segments of the same asset at once. Pre-warm the edge and use origin shielding.
  • Keyframe alignment bugs. If rungs are cut at slightly different timestamps, ABR switching produces glitches or audio drift. Enforce fixed GOP duration across all rungs.
  • Audio is a separate track. Encode and package it once and reuse across all video rungs; do not duplicate it per resolution.
  • Manifest staleness. Cache manifests briefly (or not at all for live) while caching segments for a long time; segments are immutable, manifests are not.
  • Thumbnails and metadata search deserve their own path. Sprite sheets for hover preview and a search index fed by the completion event keep the playback path clean. See Elasticsearch.
  • Hot metadata. View counters written per play will melt a row; batch them through a stream and aggregate, as in YouTube video processing pipeline and the ad-click chapter later in this handbook.

FAQ · Common Questions

Frequently Asked Questions

Why not transcode on the client before uploading?

You cannot trust the client's output (codec profile, keyframe cadence, malicious payloads), phones are battery-constrained, and you still need the full ladder. Light client-side work such as trimming or compressing a very large source is fine, but the authoritative encode runs server-side.

How do you keep upload fast for a 1 GB file on a bad mobile network?

Chunked multipart upload with small parts (a few MB), parallel part uploads, per-part retry and resume, and an endpoint close to the user. Compute a checksum per part so the server detects corruption without re-reading the whole file.

What happens if the user opens the video while it is still processing?

The metadata row says PROCESSING. A common approach is to publish the lowest rung first as soon as it is ready and add higher rungs as they finish, because the manifest can grow. The uploader sees "available in SD, HD processing".

How would you add live streaming?

Ingest over RTMP or SRT, transcode in near real time into a short-segment ladder, publish a rolling manifest with low-latency HLS or DASH, and accept 3 to 10 seconds of glass-to-glass delay. There is no time for a big DAG: encoding is per-segment and pipelined, and the CDN must refresh manifests every segment.

How do you decide which videos stay in the CDN?

Let the cache decide with LRU or a frequency-aware policy (TinyLFU style), and tier it: edge, regional shield, origin. Add explicit pre-positioning for predicted hits such as a scheduled release. Watching the hit ratio per tier tells you whether to resize.

How do you handle copyright and abuse?

Add scanning tasks into the DAG (audio and video fingerprint matching, hash lists for known illegal content, ML classifiers) that gate the transition to READY. Placing them in the DAG reuses the retry and scaling machinery.

Key Takeaway

Treat video as two products: an asynchronous, DAG-driven factory that turns one upload into many GOP-aligned, adaptively switchable renditions, and a dumb static-file delivery path that a CDN serves. Make every task idempotent so retries are free, and spend your design effort where the money is: egress, not storage.
