Design a Rate Limiter

A rate limiter caps how much traffic a client can send, protecting services from abuse, overload and runaway cost. This chapter compares the five classic algorithms (token bucket, leaky bucket, fixed window, sliding log, sliding counter), then covers placement, rules, Redis-backed distributed counting, race conditions, multi-region sync, and what clients should do when throttled.

A rate limiter answers one question millions of times per second: "has this caller used up their share?" It must answer in microseconds, with almost no memory per caller, correctly across a fleet of servers, and without becoming the outage it was built to prevent.

Core idea: rate limiting is admission control. Choose a client identity, a rule (limit, window, burst), an algorithm that approximates the rule cheaply, and a shared atomic counter. Everything else (headers, retries, multi-region) is detail around those four decisions.

A well-known public design

Why the big API providers all throttle, and how they say they do it

Payment, source-hosting and cloud providers publish their limits because the limiter is part of the product contract. Stripe has described, in public engineering writing, layering several limiters, including a request-rate limiter based on a token bucket and separate limiters that protect concurrent requests and load. GitHub documents hourly request budgets with response headers that report remaining quota. Cloudflare has written about approximating a sliding window with two counters. The common thread: no single algorithm is used everywhere; production systems stack a cheap global limit, per-endpoint limits, and load-shedding behind them.

Why it exists

What rate limiting protects

  • Availability. A single misbehaving client, buggy retry loop, or DoS attempt can starve everyone else. Limiting prevents resource starvation.
  • Cost. Calls to paid third-party APIs, expensive queries or ML inference cost real money; a cap bounds the bill. It also lets you size servers for a defined load rather than an unbounded one.
  • Fairness and tiering. Free tier gets 100 requests per minute, paid tier gets 10,000. The limiter is how you sell capacity.
  • Abuse containment. Credential stuffing, scraping, SMS pumping and signup spam are rate problems before they are anything else.

Rate limiting is related to but distinct from backpressure, load shedding and circuit breaking. A limiter enforces a policy per caller regardless of current health; load shedding reacts to current overload regardless of caller; a circuit breaker protects a caller from a failing dependency. A mature system has all three.

Back-of-envelope: how big is the state?

1M active callers, one rule each counter-based (fixed window / token bucket): ~100 B per key in Redis → ~100 MB sliding log, limit 500 per minute, caller at the limit: 500 timestamps x 8 B = 4 KB raw → ~4 GB for 1M callers Redis sorted-set overhead is several times higher → tens of GB Verdict: log-based limiting is affordable for low limits (login attempts) and not for high ones.

Guidance: in a microservices environment, put the general limits in the gateway (or a sidecar such as Envoy with a rate-limit service) and keep specific, business-aware limits (for example "five password attempts per account per hour") in the owning service. If you lack the staff to run the limiter, buy it: cloud gateways, CDNs and WAFs include one. Match algorithm to business need rather than defaulting to your favourite.

client ──▶ [ rate-limit middleware ] ──allowed──▶ API servers │ ▲ counters ▼ │ rules (cached from config store) [ Redis ] [ rules store ] │ over limit: HTTP 429 + Retry-After (or queue / drop, per policy)

Rules and responses

  • Rules as configuration, loaded from files or a config service and cached in the middleware, for example: "domain=messaging, descriptor=(key=message_type, value=marketing): 5 per day" (the shape used by Lyft's open-source rate-limit service). Keep a version and an audit trail; a bad rule is a production incident.
  • Reject with HTTP 429 Too Many Requests. Include headers telling the client what happened: the allowed limit, the remaining quota and either how long to wait (Retry-After) or when the window resets. The classic de facto names are X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset; a standardised RateLimit header family is in progress at the IETF.
  • Hard vs soft limits. Hard: never exceed. Soft: allow short overshoot, or log and alert without blocking, which is how you roll out a new rule safely.
  • Queue or drop. Rate-limited requests may be dropped, delayed (leaky bucket) or sent to a lower-priority queue for later, depending on semantics.
Step 3 · algorithms

The five algorithms

1. Token bucket

A bucket of capacity B holds tokens, refilled at rate r per second up to B. A request spends one token (or more, for expensive operations); no token, no service. State per caller: two numbers (token count and last-refill time). Refill is computed lazily on each request, so no timers are needed: tokens = min(B, tokens + (now - last) x r).

B=10, r=2/s t=0: [##########] 10 burst of 10 allowed → 0 left, 11th rejected t=1s: [##........] 2 refill 2 → two more allowed, then rejected again long-run average ≤ 2 req/s, burst ≤ 10

Pros

  • Tiny state; O(1).
  • Explicitly allows bursts, which matches human traffic.
  • Cost-weighted requests are natural.

Cons

  • Two parameters to tune.
  • Bursts of B are allowed on every refill period, which may exceed what a fragile backend tolerates.

You usually keep several buckets: per user, per IP, per endpoint, and one global bucket protecting the backend (for example a user may burst on search but all users together cannot exceed the cluster's capacity).

2. Leaky bucket

Requests enter a FIFO queue of fixed size and are processed at a constant outflow rate. A full queue drops new requests. Conceptually it is a traffic shaper: arbitrary input, steady output. There are two common implementations. The queue form actually buffers and delays requests (good for smoothing writes to a fragile downstream). The meter form tracks a "water level" that drains at the leak rate and rejects when it would overflow; that is arithmetically a token bucket with the roles inverted, and it is what Uber's open-source Go limiter approximates by spacing calls rather than queuing them.

Pros

  • Smooth, predictable output rate.
  • Memory-efficient with a bounded queue.

Cons

  • A burst fills the queue with old requests; recent ones wait or drop (latency).
  • Two parameters (queue size, leak rate).

3. Fixed window counter

Time is divided into windows (for example one minute). Each caller has a counter keyed by window id; increment per request, reject when it exceeds the limit. It is the simplest possible limiter and maps to Redis INCR plus EXPIRE. The flaw is the boundary effect: with a limit of 5 per second, a caller can send 5 at the end of one window and 5 at the start of the next, so 10 requests flow in roughly 100 ms, double the quota. In the worst case the burst is 2x the limit.

limit 5 / 1000 ms |---------------- window 0 ----------------|---------------- window 1 ----------------| ##### (t=900..980) ##### (t=1000..1080) 10 requests in 180 ms: each window saw only 5 → all allowed

4. Sliding window log

Keep a timestamp for every accepted request. On a new request, drop timestamps older than now - window, count what remains, and accept only if the count is under the limit. It is exact: in any rolling window the limit holds. The price is memory proportional to the limit (see the arithmetic above). Decide whether rejected requests are logged; not logging them lets a client keep hammering without extending its own penalty.

5. Sliding window counter

A hybrid. Keep counts for the current and previous fixed windows, and estimate the rolling count by weighting the previous window by how much of it still overlaps the rolling window:

estimate = previous_count x (1 - fraction_of_current_window_elapsed) + current_count example: limit 100/min, previous window 84, current window 36, we are 25% into the current window estimate = 84 x 0.75 + 36 = 99 → request allowed (new estimate 100) the next request: 84 x 0.75 + 37 = 100 → at the limit, reject

It assumes requests in the previous window were evenly spread, so it is an approximation, but a very good one on real traffic (Cloudflare reported negligible error when they adopted it), and it needs only two counters per caller. For most public APIs this is the best default.

Step 4 · distributed design

Counters in Redis, and why races matter

Per-server counters undercount: with ten API servers and a limit of 100, a caller routed round-robin could get 1,000. So counters live in a shared, fast store; Redis is the usual choice because it is in-memory, supports atomic increments and expiry, and handles hundreds of thousands of operations per second per node. The middleware flow is: build the key (for example rl:{user}:{endpoint}), fetch or update the counter, decide, and either forward or return 429.

The race condition

The naive sequence "GET count, check, SET count+1" is a read-modify-write across the network. Two servers can both read 99, both decide "allowed", and both write 100, letting 101 requests through. Fixes, from least to most robust:

  1. Atomic primitives. For fixed window, INCR is atomic: increment first, then compare. Set the expiry only when the returned value is 1.
  2. Lua scripts. Redis executes a script atomically, so refill-and-take for a token bucket (below) is race-free and costs one round trip. This is the standard production answer.
  3. Sorted sets for the sliding log: ZREMRANGEBYSCORE (drop old), ZCARD (count), ZADD (record), wrapped in a MULTI or a script.
  4. Locks work but serialise every request and add failure modes; avoid.
Use the store's clock. If each API server passes its own timestamp, clock skew between servers corrupts refill maths. In a Redis script, read TIME inside the script (or tolerate skew by design). Also give every key a TTL, or abandoned callers leak memory forever.

Scaling the limiter itself

  • Shard keys across a Redis cluster by caller id (consistent hashing, chapter 5); a single caller always maps to one node, so atomicity is preserved.
  • Reduce traffic with local pre-aggregation: each API node keeps a small local allowance and syncs with Redis in batches. This trades accuracy (callers can overshoot by up to the sum of local allowances) for far fewer network calls. Good for high-volume tiers; avoid for strict security limits.
  • Use pipelining or connection pooling and keep Redis in the same availability zone; a cross-zone hop can cost more than the whole limiter budget.
Deep dive

Multi-data-center, failure policy and monitoring

Multiple regions. A global limit requires cross-region coordination, which is slow (tens to hundreds of milliseconds) and itself a failure risk. Common choices: (a) enforce limits per region with each region given a share of the budget, (b) route a caller to a home region by key so one region owns their counter, or (c) replicate counters asynchronously and accept brief overshoot (eventual consistency). Most systems pick (a) or (c); true global linearisable limits are rarely worth the latency.

Fail open or closed. When Redis is unreachable, you must choose. Fail open (let traffic through) preserves availability but removes protection exactly when something is wrong; fail closed (reject) preserves protection but turns a limiter outage into a site outage. Typical practice: fail open for ordinary API quotas, fail closed for security-sensitive limits (login, OTP, payments), and give the client library a short timeout and a local fallback bucket. Make the middleware deliberately cheap to bypass, and alert loudly when it does.

Rollout and tuning. Ship new rules in log-only (shadow) mode first; compare predicted rejections with real traffic; then enforce. Monitor the rejection rate per rule, the tail latency of the limiter, and the top-N throttled callers. A sudden rise in rejections is either an attack or a rule that is too tight after a traffic pattern change (a new marketing campaign, a flash sale), and you need the data to tell which.

Layers. The chapter focuses on layer 7 (HTTP), but the same ideas apply at layer 3 and 4 (connection and packet rate via firewall rules such as iptables or cloud security tooling), at the database (connection and statement limits), and in queues (consumer concurrency). Defence works best in layers.

Client best practice. Well-behaved clients cache responses to avoid redundant calls, respect Retry-After, back off exponentially with jitter, avoid retry storms, and handle 429 gracefully in the UI. A server can only protect itself so far; clients that retry instantly turn a limit into a thundering herd.

Code

Runnable example: all five algorithms with an injectable clock

Every limiter takes a now() function so the tests are deterministic. The demo sends five requests just before a window boundary and five just after, and shows the fixed-window flaw: with a limit of 5 per second, fixed window admits all 10, while the sliding log and sliding counter admit only 5.

JavaScript Example 
import assert from 'node:assert/strict';

// All limiters take an injectable clock (ms) so behaviour is deterministic.
export class TokenBucket {
  constructor(capacity, refillPerSec, now) { Object.assign(this, { capacity, refillPerSec, now });
    this.tokens = capacity; this.last = now(); }
  allow(cost = 1) {
    const t = this.now();
    this.tokens = Math.min(this.capacity, this.tokens + (t - this.last) / 1000 * this.refillPerSec);
    this.last = t;                       // lazy refill: no timer needed
    if (this.tokens >= cost) { this.tokens -= cost; return true; }
    return false;
  }
}
export class LeakyBucket {               // queue drained at a constant rate (meter variant, no real queue)
  constructor(capacity, leakPerSec, now) { Object.assign(this, { capacity, leakPerSec, now });
    this.level = 0; this.last = now(); }
  allow() {
    const t = this.now();
    this.level = Math.max(0, this.level - (t - this.last) / 1000 * this.leakPerSec); this.last = t;
    if (this.level + 1 <= this.capacity) { this.level += 1; return true; }
    return false;
  }
}
export class FixedWindow {
  constructor(limit, windowMs, now) { Object.assign(this, { limit, windowMs, now }); this.win = -1; this.count = 0; }
  allow() {
    const w = Math.floor(this.now() / this.windowMs);
    if (w !== this.win) { this.win = w; this.count = 0; }
    return this.count < this.limit ? (this.count++, true) : false;
  }
}
export class SlidingLog {
  constructor(limit, windowMs, now) { Object.assign(this, { limit, windowMs, now }); this.log = []; }
  allow() {
    const t = this.now();
    while (this.log.length && this.log[0] <= t - this.windowMs) this.log.shift();
    if (this.log.length < this.limit) { this.log.push(t); return true; }  // rejected requests are not logged
    return false;
  }
}
export class SlidingCounter {            // weighted blend of previous and current fixed windows
  constructor(limit, windowMs, now) { Object.assign(this, { limit, windowMs, now }); this.win = -1; this.cur = 0; this.prev = 0; }
  allow() {
    const t = this.now(), w = Math.floor(t / this.windowMs);
    if (w !== this.win) { this.prev = (w === this.win + 1) ? this.cur : 0; this.cur = 0; this.win = w; }
    const overlap = 1 - (t % this.windowMs) / this.windowMs;
    const est = this.prev * overlap + this.cur;
    if (est + 1 <= this.limit) { this.cur++; return true; }
    return false;
  }
}

// ---- demo: the fixed-window boundary burst --------------------------------
const run = (mk, times) => { let t = 0; const l = mk(() => t); return times.map(x => (t = x, l.allow())); };
const count = a => a.filter(Boolean).length;
// limit 5 per 1000 ms; send 5 requests at t=900..990 and 5 more at t=1000..1090
const burst = [900, 920, 940, 960, 980, 1000, 1020, 1040, 1060, 1080];
const fw = count(run(n => new FixedWindow(5, 1000, n), burst));
const sl = count(run(n => new SlidingLog(5, 1000, n), burst));
const sc = count(run(n => new SlidingCounter(5, 1000, n), burst));
console.log(`burst across boundary -> fixed:${fw} log:${sl} slidingCounter:${sc} (limit 5 per 1000ms)`);
assert.equal(fw, 10); assert.equal(sl, 5); assert.ok(sc <= 6);

// token bucket: burst of 10 allowed, then ~2/s sustained
{ let t = 0; const tb = new TokenBucket(10, 2, () => t);
  const first = Array.from({ length: 12 }, () => tb.allow());
  assert.equal(count(first), 10);
  t = 1000; assert.equal(count([tb.allow(), tb.allow(), tb.allow()]), 2);
  console.log('token bucket: burst 10 then', 2, 'per second -> ok'); }
// leaky bucket: steady drain
{ let t = 0; const lb = new LeakyBucket(3, 1, () => t);
  assert.equal(count([1, 2, 3, 4].map(() => lb.allow())), 3);
  t = 1000; assert.equal(lb.allow(), true); assert.equal(lb.allow(), false);
  console.log('leaky bucket: capacity 3, drain 1/s -> ok'); }
console.log('all checks passed');

Prints "burst across boundary -> fixed:10 log:5 slidingCounter:5 (limit 5 per 1000ms)", then confirms that the token bucket allows a burst of 10 then 2 per second and that the leaky bucket drains at 1 per second, ending with "all checks passed". Executed with node.

In production the check-and-update must be one atomic step against shared state. This Redis Lua script performs a token-bucket refill and spend in a single round trip (shown for reference; the JavaScript above is what was executed here).

Redis Lua (reference, not run in this page) 
-- KEYS[1] = bucket key; ARGV = capacity, refill_per_sec, now_ms, cost
local d = redis.call('HMGET', KEYS[1], 't', 'ts')
local tokens = tonumber(d[1]) or tonumber(ARGV[1])
local ts = tonumber(d[2]) or tonumber(ARGV[3])
tokens = math.min(tonumber(ARGV[1]), tokens + (tonumber(ARGV[3]) - ts) / 1000 * tonumber(ARGV[2]))
local ok = 0
if tokens >= tonumber(ARGV[4]) then tokens = tokens - tonumber(ARGV[4]); ok = 1 end
redis.call('HSET', KEYS[1], 't', tokens, 'ts', ARGV[3])
redis.call('PEXPIRE', KEYS[1], math.ceil(tonumber(ARGV[1]) / tonumber(ARGV[2]) * 1000) * 2)
return ok

Invoke with EVALSHA, passing the key, then capacity, refill rate per second, current time in milliseconds and cost. Returns 1 for allowed, 0 for rejected. Prefer redis.call('TIME') inside the script over a client-supplied time.

Scaling and production

Gotchas worth knowing

  • Latency budget. One Redis round trip inside a zone is typically sub-millisecond to low milliseconds; across zones it can double or triple. Count it in your SLO.
  • Memory with TTL. Set expiry to roughly twice the window so idle callers vanish.
  • Cost-based limiting. Not all requests cost the same; a search may cost 10 tokens and a ping 1. Token bucket handles this directly.
  • Concurrency limits are different. "At most 10 in-flight requests" is a semaphore, not a rate. Many outages are fixed by a concurrency limiter (as in adaptive concurrency in Envoy) rather than a rate one.
  • Return limits in headers on success too, so well-behaved clients can pace themselves before they are throttled.
  • Test at the boundary. Fuzz the window edge, DST and leap-second behaviours, and process restarts; most limiter bugs live there.
Checklist

Design checklist

  • Identity chosen (user, key, IP, device) and spoofing considered.
  • Algorithm justified against burst tolerance and memory.
  • Rules in versioned config; shadow mode before enforce.
  • Atomic check-and-update; store-side clock; TTL on every key.
  • 429 with Retry-After and quota headers.
  • Fail-open versus fail-closed decided per rule class.
  • Multi-region strategy explicit (per-region share or home region).
  • Metrics: rejections by rule, limiter latency, top throttled callers.
FAQ · Common Questions

Frequently Asked Questions

Token bucket or sliding window counter for a public API?

If you want to allow short bursts while bounding average rate (typical for humans and SDKs), token bucket. If you want the simple promise "no more than N in any 60 seconds" with minimal state, sliding window counter. Many platforms use both: a sliding window for the headline quota and a token bucket for burst control.

How do you rate-limit across many servers without a central Redis?

Split the budget (each node gets limit / N and adjusts as nodes change), or route requests for the same caller to the same node with consistent hashing (chapter 5), or use gossip-style approximate counting. All trade strictness for independence. A central store is simplest when you need accuracy.

What do you do with requests that exceed the limit: drop or queue?

Drop with 429 for interactive APIs, because queuing hides overload and increases latency. Queue (leaky bucket style) for background or batch traffic where delay is acceptable. In both cases, bound the queue.

How do you rate-limit by IP when users share NAT or use IPv6?

Prefer authenticated identity; use IP only as a coarse outer limit with a generous threshold. For IPv6, limit by prefix (for example /64) because a single host controls billions of addresses within it.

Where does idempotency fit in?

Throttled clients will retry. If the first attempt partially succeeded, a retry could duplicate work; idempotency keys make retries safe. See the hub's idempotency page.

How do you test a rate limiter?

Unit-test each algorithm against a fake clock (as in the code above), property-test that no window ever exceeds the limit (for the exact algorithms), and run a concurrent load test against the real Redis path to catch races and measure tail latency.

Key Takeaway

Pick the algorithm by the failure you can least afford. Token bucket for bursty clients with a long-term average, leaky bucket for a smooth downstream rate, sliding counter for cheap near-exact windows, and fixed window only when edge bursts are acceptable. In a cluster, correctness lives in a single atomic operation against a shared store, and you must decide in advance whether the limiter fails open or closed.
