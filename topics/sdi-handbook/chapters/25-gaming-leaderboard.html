Design a Real-time Gaming Leaderboard

A leaderboard is a ranking query that must stay fast while scores change thousands of times per second. Learn why relational databases struggle, how Redis sorted sets and skip lists solve it, and how to shard when one node is no longer enough.

Every competitive game has the same screen: the top ten players, and "you are number 357,812". The first is a top-K query; the second is a rank query, which is harder than it looks. Rank is a global property, since it depends on the score of every other player, yet users expect it to update the moment they win a match.

This chapter is a good lesson in choosing a data structure before choosing a database. The problem is almost entirely solved by one structure, the order-statistic sorted collection, and the rest of the design is about making that structure durable, secure and scalable.

Core idea: Keep the ranking in a structure that is always sorted and can answer "how many items are above this one" in logarithmic time. Redis sorted sets (hash map plus skip list with span counts) do exactly that. Use a relational store as the durable record of match results, and shard the sorted set only when a single node's memory or throughput really requires it.

Background · Where the skip list came from

William Pugh's 1990 trick, and why Redis picked it

Skip lists were published by William Pugh in 1990 as a probabilistic alternative to balanced trees: a sorted linked list with extra "express lane" levels, where each node is promoted to the next level with a fixed probability. Search, insert and delete are O(log N) in expectation with no rebalancing logic. Redis uses a skip list for sorted sets (alongside a hash table) and its author has explained the choice publicly: skip lists are simpler to implement and debug than balanced trees, and range walks are just pointer chasing along the bottom level. Redis stores a "span" on every forward pointer, which turns the skip list into an order-statistic structure: the sum of spans along a search path is the element's rank. That small addition is what makes ZRANK logarithmic instead of linear.

Step 1 · Scope and Requirements

What the interviewer pins down

  • A player earns one point for each match won. Everyone participates.
  • A tournament runs per calendar month and starts a fresh leaderboard.
  • Display the top 10 plus the caller's own rank; bonus: show the four players above and below the caller.
  • Scale: 5 million DAU, 25 million MAU, about 10 matches per player per day.
  • Equal scores share a rank (tie-breaking is a stretch topic).
  • Real time: a win shows up on the leaderboard immediately or nearly so. Batch-refreshed results are explicitly not acceptable.

A subtle inconsistency to avoid. The source notes mention both 5 million and 50 million DAU in the estimate section; the 50-users-per-second figure only matches 5 million. What the numbers say: reads and writes are tiny, a few thousand operations per second against about a gigabyte of data. The problem is not throughput, it is the shape of the query (rank), and the single-node solution fits comfortably in memory. Do not shard on day one; design the shard path, but build the simple version first.

Step 2 · High-Level Design

API and architecture

                      |                                     |
                      +-- insert match result --> MySQL (durable truth; rebuild source)
 Player --GET top10 / my rank--> Leaderboard service --> Redis ZREVRANGE / ZREVRANK  (+ user profile cache)

A player wins; the game server validates it and calls the leaderboard service; the leaderboard service updates the store; clients read through the same service. The rejected alternative is letting the client report its own win. That is insecure: anyone with a proxy can alter requests and post any score. For games where the server already owns the game logic, the server records the result without the client asking, which also removes a whole attack surface. Authentication of the game-server-to-leaderboard hop (mutual TLS or signed requests) completes the picture.

Should a message queue sit between the game server and the leaderboard? Not required by the stated scope, so the baseline omits it. It becomes worthwhile the moment a second consumer exists (achievements, analytics, anti-cheat, push notifications), or when you want to absorb bursts and replay history. A log such as Kafka also gives you the cleanest recovery story: the leaderboard is a materialized view of the stream of match results.

Data Models

Relational first: where it breaks

With few users, a relational table works. The source notes suggest one table per month; a better modeling is a single table with a (tournament, user_id) key, so you never create tables on a schedule and rollover is just a new tournament id.

 leaderboard(tournament TEXT, user_id TEXT, score INT, PRIMARY KEY (tournament, user_id),  INDEX (tournament, score DESC))

 win:   INSERT ... ON DUPLICATE KEY UPDATE score = score + 1
 top10: SELECT user_id, score FROM leaderboard WHERE tournament=? ORDER BY score DESC LIMIT 10      -- fast with the index
 rank:  SELECT COUNT(*) + 1 FROM leaderboard WHERE tournament=? AND score > (my score)             -- O(rank) index entries

Top ten is easy with an index on score and LIMIT 10. The problem is rank. A B-tree index is ordered but it does not know how many entries sit before a given key; the database has to count them, walking index entries, so the cost grows with the number of players ahead of you. A player at rank 4 million forces a four-million-entry count, on a hot table that is also absorbing updates, and the secondary index on score is rewritten on every change. Shortcuts such as session variables numbering rows (@rownum) force a scan of everything. You could add periodic materialized ranks, but then it is no longer real time. You need a structure that stores subtree sizes or spans.

Redis solution

Sorted sets

A Redis sorted set (ZSET) maps each unique member to a floating-point score and keeps members ordered by (score, member). Internally, for sets above a small size, it is two structures sharing the same elements: a hash table for O(1) member-to-score lookup, and a skip list ordered by score for range and rank queries. Small sets use a compact listpack encoding instead.

How the skip list gives rank in O(log N)

 L3:  H ---------------------------------> 40 --------------------------> nil       span: elements skipped
 L2:  H ---------> 15 -------------------> 40 -------------> 70 ---------> nil
 L1:  H ----> 8 -> 15 -----> 25 -------> 40 ----> 55 -> 70 -> 90 -> nil
 L0:  H -> 3 -> 8 -> 15 -> 21 -> 25 -> 33 -> 40 -> 48 -> 55 -> 63 -> 70 -> 81 -> 90
 Each node gets level L with probability p^(L-1) (p = 1/4 in Redis). Search drops down when the next hop overshoots.
 Rank(x) = sum of spans of the forward hops taken from the head to x.

Search starts at the top level and moves right while the next node is smaller than the target, dropping a level otherwise. On average this visits O(log N) nodes; the chapter's 64-node illustration needs about 11 steps against 62 for a plain linked list. Because every forward pointer stores how many bottom-level nodes it skips, summing spans while descending yields the position. Accessing the k-th element uses the same walk in reverse.

  • Around me: take the rank r, then ZREVRANGE key r-4 r+4 (clamp at zero). Two cheap calls, or one Lua script to make the pair atomic.

Ties

The requirement says equal scores share a rank. A ZSET gives each member a distinct position (ties are ordered by member bytes), so for "competition ranking" compute the rank as the count of players with a strictly higher score plus one: ZCOUNT key (score +inf plus 1. If you instead want deterministic ordering that rewards whoever reached the score first, fold a time component into the score. A double has 53 bits of integer precision, so pack points × 2^32 + (MAX_T − t_seconds) and keep points below 221. The example does this. Decode with a floor-divide.

Durability and the system of record

  • Redis persistence (RDB snapshots plus AOF) and a replica protect against a process crash, but failover with asynchronous replication can lose the last writes.
  • Keep the match-result history in MySQL (or the Kafka log) as the source of truth; this also stores timestamps and match ids for audits and tie-breaks. The leaderboard in Redis is a derived index that can be rebuilt by replaying results.
  • Two writes (database and Redis) can diverge. Make the match insert the commit point, publish an event (transactional outbox), and let the consumer apply ZINCRBY idempotently, for example by recording processed match ids in a Redis set, or by writing absolute scores with ZADD computed from the database instead of increments.
  • Cache profile data (name, avatar) for the top ten in a Redis hash or small cache; it is read far more often than it changes.
  • Monthly rollover: new key per tournament. At month end, snapshot the final top N and write them to durable storage for awards and history, keep the old key readable for a while, then expire it. Decide explicitly which clock (UTC) defines the boundary and assign matches by their completion event time, so a game ending at 00:00:03 does not land in the wrong tournament.
Deep Dive 1

Manage it yourself, or go serverless?

Self-managed means API servers, Redis (primary and replica), MySQL for profiles and match history, and a cache for hot profile data. Managed or serverless means something like API Gateway routing to Lambda functions that talk to a managed Redis (for example ElastiCache) and a managed database. Lambda runs code on demand and scales out automatically, and you never patch servers. The source recommends this route for a brand-new game.

Self-managedServerless / managed

Cost shapeCheaper at steady high loadPay per request; great for spiky or small games, pricey at sustained volume

Lock-inPortableTied to a cloud's primitives

Serverless is a good fit for the stateless leaderboard API tier. The stateful Redis tier is still a long-running service wherever you host it, so the real gain is operational convenience for the stateless parts.

Deep Dive 2

Scaling Redis when one node is not enough

At 500 million DAU, the estimates reach 65 GB and 250k QPS, which exceeds a comfortable single instance. Also keep in mind that a fork-based snapshot of a write-heavy node can temporarily need up to twice the memory, so provision for it, and benchmark with redis-benchmark on your actual instance type rather than trusting estimates.

Option A: partition by score range (fixed partitions)

 Shard 1: scores 900-1000 (top)   Shard 2: 800-899   ...   Shard 10: 0-99
 user -> shard mapping kept in app (MySQL or a cache): user_id -> current shard
 Top 10:     read from Shard 1 only (fall to Shard 2 if it holds fewer than 10)
 My rank:    ZREVRANK within my shard  +  sum(ZCARD of every higher-score shard)

Top-K is a single read of the top shard. Exact global rank is cheap: rank inside the shard plus the cardinalities of all higher shards, which are O(1) each and can be cached. The costs are operational. When a score crosses a range boundary the user must move shards, which is a two-step move (remove from one set, add to another) that needs care for atomicity. Score distributions are rarely uniform (a long tail of low scores, a thin crowd at the top), so ranges must be chosen from the actual distribution and rebalanced. The mapping from user to shard is itself a store to maintain.

Option B: hash partition (Redis Cluster)

Redis Cluster hashes each key (not each member) into 16,384 slots spread across nodes. It is not a proxy: clients are cluster-aware and follow redirect replies, and slot-to-node assignment is not consistent hashing even though the goal is similar. Crucially a single ZSET key lives on one node, so a cluster does not automatically split a leaderboard. To spread one logical leaderboard you create N keys such as lb:2026-10:{0..N-1} and place each user in hash(user) mod N.

 Top-K:  scatter ZREVRANGE 0..K-1 to every partition  ->  gather k-way merge  ->  global top K
 Rank:   no cheap answer: need count of players above me in EVERY partition (N ZCOUNT calls, summed)

The global top K is guaranteed to lie inside the union of each partition's top K, so a K-way merge is correct, and the example proves it against a single set. Costs: latency grows with partition count (you wait for the slowest), large K drags large payloads from every partition, and rank requires N counts. With N in the tens that is acceptable for top ten; for "show me my exact rank" it is the weak spot, which is why the chapter leans toward fixed score partitions for Redis.

A pragmatic hybrid: hash-partition the full population for writes and per-user rank within partition, maintain a small global "elite" ZSET (the top few thousand players) updated only when a score exceeds the elite threshold, and report approximate percentile for everyone below. Most players neither need nor can interpret the difference between rank 3,412,118 and 3,412,121.

Deep Dive 3

The NoSQL alternative: DynamoDB (or Cassandra, MongoDB)

If you want a fully managed, horizontally scaling store that sorts within a partition, DynamoDB fits: heavy writes, a sort key for ordering, and global secondary indexes for other access paths. The modeling steps are instructive.

  1. First try: partition key = game_name#month, sort key = user_id. Lookups by user are easy, but nothing is ordered by score.
  2. Score as the sort key: partition key = game#month, sort key = score. Now a descending query returns the top ten. Two catches: a key attribute cannot be updated in place, so a score change is a delete plus a put in one transaction; and the whole month lives in one partition key, which is a hot partition because every write for the current month hits it.
  3. Write sharding: append a shard number to the partition key: game#month#(user_id mod N). Writes now spread across N partitions. The trade-off is explicit: more shards means more write throughput but every leaderboard read has to query all N and merge (scatter-gather), so N is a tunable that needs benchmarking.

The remaining weakness is exact rank. Computing it needs a count of items above a score across all shards, which DynamoDB cannot do cheaply. Once the player base is large, an acceptable product answer is a percentile: a periodic job samples or histograms score distribution (for example, "score under 100: 10th percentile, under 500: 20th, ..., under 6,500: 90th") and the API maps a user's score to a percentile band. Exact rank is shown only for the top few thousand. See also DynamoDB hot partition sharding.

Trade-offs

Decisions and what they cost

Redis sorted set as the index

  • Rank, top-K and neighbors in O(log N)
  • Atomic ZINCRBY, no read-modify-write
  • Fits one node for tens of millions of players

What it costs

  • Memory-bound, so cost scales with players
  • Needs a database of record and a rebuild path
  • Sharding sacrifices cheap exact rank or cheap top-K

Server-authoritative scoring

  • Clients cannot forge wins
  • One place for anti-cheat and idempotency

What it costs

  • Game servers become a dependency of the score path
  • Needs service-to-service auth and key rotation

Scaling and Production Gotchas

Things that bite after launch

  • Big keys: a single ZSET with hundreds of millions of members makes DEL, persistence forks and replica resyncs slow; expire old tournaments with UNLINK (asynchronous free) rather than DEL.
  • Deep pagination: ZREVRANGE key 5000000 5009999 is O(log N + M) and fine, but a naive loop paginating by offset while scores change shows duplicates or gaps. Use rank windows only for display and cursor on (score, member) for exports.
  • Float scores: doubles have 53 bits of integer precision; packing time into the score caps your maximum points. Verify bounds, and test decode.
  • Rank is a moving target: between a client reading its rank and displaying it, others overtake. Show a timestamp or just accept slight staleness; do not build features requiring a stable rank across requests.
  • Hot player or hot key: a streamer's profile is read constantly; cache profile hydration separately from rank queries.
  • Clock and region: a global game with regional boards needs one ZSET per region plus a global one, or you must decide that rank is per region. Cross-region replication of a sorted set is a product decision as much as a technical one.
  • Operational visibility: alert on replica lag, memory fragmentation, fork duration, command latency percentiles, and reconciliation drift.
Wrap-up

Extra talking points

  • Faster retrieval: cache user objects in a Redis hash keyed by user id so rendering the top ten does not hit MySQL.
  • Tie-breaking: order equal scores by who reached the score first (last-played timestamp as in the source notes, or the time they reached it); implement via score packing or a secondary comparator.
  • Failure recovery: a large Redis outage is recoverable by re-deriving the board from durable match records. The source suggests replaying database log entries with a script; a purpose-built match-results table or an event stream is sturdier than relying on a binary log.
  • Neighbors: four above and four below is two calls once you know the rank, as in the example.
Code · Runnable

A sorted set with O(log N) rank, built from scratch

This implementation is a skip list with spans, ordered by (score, member), plus a hash map for member lookups: the same shape as a Redis ZSET. It provides zincrby, zrevrank and zrevrange (which together give top-K, rank and "around me"), a score-packing helper for time-based tie-breaking, and a scatter-gather top-K across hash shards. The test replays 20,000 random wins against a brute-force sort and compares top-10, ranks and the sharded merge.

JavaScript Example 
// Redis-style sorted set from scratch: skip list with spans (O(log N) rank),
// ZINCRBY / ZREVRANK / ZREVRANGE, tie-break by earliest achiever, plus scatter-gather top-K across shards.
import assert from 'node:assert/strict';

const MAXLVL = 16;
class Node { constructor(member, score, lvl) { this.member = member; this.score = score; this.next = new Array(lvl).fill(null); this.span = new Array(lvl).fill(0); } }

class SortedSet {
  // Ordering key: score ascending, then member ascending (same as Redis). A hash map gives O(1) member->score.
  constructor(rnd = Math.random) { this.head = new Node(null, -Infinity, MAXLVL); this.level = 1; this.len = 0; this.scores = new Map(); this.rnd = rnd; }
  #lt(n, score, member) { return n.score < score || (n.score === score && n.member < member); }
  #randLevel() { let l = 1; while (l < MAXLVL && this.rnd() < 0.25) l++; return l; }   // p = 1/4 as in Redis
  #insert(member, score) {
    const update = new Array(MAXLVL), rank = new Array(MAXLVL).fill(0);
    let x = this.head;
    for (let i = this.level - 1; i >= 0; i--) {
      rank[i] = i === this.level - 1 ? 0 : rank[i + 1];
      while (x.next[i] && this.#lt(x.next[i], score, member)) { rank[i] += x.span[i]; x = x.next[i]; }
      update[i] = x;
    }
    const lvl = this.#randLevel();
    if (lvl > this.level) { for (let i = this.level; i < lvl; i++) { rank[i] = 0; update[i] = this.head; update[i].span[i] = this.len; } this.level = lvl; }
    const n = new Node(member, score, lvl);
    for (let i = 0; i < lvl; i++) {
      n.next[i] = update[i].next[i]; update[i].next[i] = n;
      n.span[i] = update[i].span[i] - (rank[0] - rank[i]);
      update[i].span[i] = rank[0] - rank[i] + 1;
    }
    for (let i = lvl; i < this.level; i++) update[i].span[i]++;
    this.len++;
  }
  #remove(member, score) {
    const update = new Array(MAXLVL); let x = this.head;
    for (let i = this.level - 1; i >= 0; i--) { while (x.next[i] && this.#lt(x.next[i], score, member)) x = x.next[i]; update[i] = x; }
    const t = x.next[0]; assert(t && t.member === member);
    for (let i = 0; i < this.level; i++) {
      if (update[i].next[i] === t) { update[i].span[i] += t.span[i] - 1; update[i].next[i] = t.next[i]; } else update[i].span[i]--;
    }
    while (this.level > 1 && !this.head.next[this.level - 1]) this.level--;
    this.len--;
  }
  zadd(member, score) { if (this.scores.has(member)) this.#remove(member, this.scores.get(member)); this.#insert(member, score); this.scores.set(member, score); }
  zincrby(member, by) { const s = (this.scores.get(member) ?? 0) + by; this.zadd(member, s); return s; }
  zrankAsc(member) {                       // 0-based rank ascending, O(log N) by summing spans
    const score = this.scores.get(member); if (score === undefined) return null;
    let x = this.head, r = 0;
    for (let i = this.level - 1; i >= 0; i--) while (x.next[i] && (this.#lt(x.next[i], score, member) || x.next[i].member === member)) { r += x.span[i]; x = x.next[i]; }
    return r - 1;
  }
  zrevrank(member) { const r = this.zrankAsc(member); return r === null ? null : this.len - 1 - r; }
  #at(rankAsc) {                           // node at 0-based ascending rank, via span walk
    let x = this.head, r = -1;
    for (let i = this.level - 1; i >= 0; i--) while (x.next[i] && r + x.span[i] <= rankAsc) { r += x.span[i]; x = x.next[i]; }
    return x;
  }
  zrevrange(start, stop) {                 // O(log N + M)
    const out = []; stop = Math.min(stop, this.len - 1);
    for (let k = start; k <= stop; k++) { const n = this.#at(this.len - 1 - k); out.push([n.member, n.score]); }
    return out;
  }
}

// Tie-break: pack (score, time) into one number so the earlier achiever ranks higher at equal points.
// 2^53 mantissa: score < 2^21 (2M points), remaining 32 bits hold (MAX_T - t) in seconds.
const MAX_T = 2 ** 32 - 1, packScore = (points, tSec) => points * 2 ** 32 + (MAX_T - tSec);
const unpackPoints = (packed) => Math.floor(packed / 2 ** 32);

// Scatter-gather for hash-partitioned shards: global top K is inside the union of per-shard top K.
function topKAcrossShards(shards, k) {
  return shards.flatMap((s) => s.zrevrange(0, k - 1)).sort((a, b) => b[1] - a[1] || (a[0] < b[0] ? 1 : -1)).slice(0, k);   // same tie order as zrevrange
}
// Global rank when sharded by score range: users strictly above me in higher shards + my rank in my shard.
const rangeShardRank = (shardsHighToLow, idx, member) =>
  shardsHighToLow.slice(0, idx).reduce((s, sh) => s + sh.len, 0) + shardsHighToLow[idx].zrevrank(member);

// ---------------- self-test vs brute force ----------------
let seed = 42; const rnd = () => ((seed = (seed * 1664525 + 1013904223) >>> 0) / 2 ** 32);
const zs = new SortedSet(rnd), truth = new Map();
for (let i = 0; i < 20000; i++) { const u = 'u' + Math.floor(rnd() * 3000); zs.zincrby(u, 1); truth.set(u, (truth.get(u) ?? 0) + 1); }
const order = [...truth].sort((a, b) => b[1] - a[1] || (a[0] < b[0] ? 1 : -1));   // score desc; member desc within tie (reverse of asc order)
assert.deepEqual(zs.zrevrange(0, 9), order.slice(0, 10));
for (const u of ['u7', 'u1500', 'u2999']) if (truth.has(u)) assert.equal(zs.zrevrank(u), order.findIndex(([m]) => m === u));
assert.equal(zs.len, truth.size);
console.log('top 3 of', zs.len, 'players:', JSON.stringify(zs.zrevrange(0, 2)));
const me = order[1234][0];
console.log(`rank of ${me}: ${zs.zrevrank(me)}; window +-4:`, zs.zrevrange(zs.zrevrank(me) - 4, zs.zrevrank(me) + 4).map(([m]) => m).join(' '));

// tie-break demo
const t = new SortedSet(rnd);
t.zadd('late', packScore(10, 2000)); t.zadd('early', packScore(10, 1000)); t.zadd('leader', packScore(11, 5000));
console.log('tie-break order:', t.zrevrange(0, 2).map(([m, s]) => `${m}(${unpackPoints(s)})`).join(' > '));
assert.deepEqual(t.zrevrange(0, 2).map(([m]) => m), ['leader', 'early', 'late']);

// sharded: hash partition scatter-gather must equal the single-set answer
const shards = [new SortedSet(rnd), new SortedSet(rnd), new SortedSet(rnd), new SortedSet(rnd)];
const h = (s) => [...s].reduce((a, c) => (a * 31 + c.charCodeAt(0)) >>> 0, 7) % 4;
for (const [u, s] of truth) shards[h(u)].zadd(u, s);
assert.deepEqual(topKAcrossShards(shards, 10), zs.zrevrange(0, 9));
console.log('scatter-gather top-10 across 4 hash shards == single sorted set');
// updating existing member keeps invariants
zs.zincrby('u7', 1000); assert.equal(zs.zrevrank('u7'), 0);
console.log('all assertions passed');

Prints the top three of roughly 3,000 simulated players, the rank of one mid-table player with the nine-player window around it, the tie-break order "leader(11) > early(10) > late(10)", a confirmation that the 4-shard scatter-gather top 10 equals the single-set top 10, and "all assertions passed". FAQ · Common Questions

Frequently Asked Questions

Why not just keep an index on score in MySQL?

It makes top-K cheap but rank still requires counting entries before the target, which is linear in the player's position, and every score change rewrites the index. At 25 million rows with constant updates, rank queries from low-ranked players are the expensive ones, and those are most players. A structure that tracks subtree sizes or spans gives logarithmic rank; Redis ZSET is the off-the-shelf version.

How do you show the players around me?

Get my rank r with ZREVRANK, then ZREVRANGE from max(0, r-4) to r+4 with scores, hydrate names from the profile cache. If the board is score-range sharded and my window straddles two shards, issue a second small range on the neighbouring shard.

What if two people have the same score?

For display, give them the same rank: rank equals one plus the number of players with a strictly higher score (ZCOUNT with an exclusive lower bound). For stable ordering, encode a tie-break in the score such as earliest time to reach it, or sort by last-won timestamp.

How would you support daily, weekly and all-time boards at once?

One sorted set per window, each updated by the same event (multiple ZINCRBY in a pipeline or Lua script). Expire daily and weekly keys after their window plus a grace period. All-time is the largest key, so it is the first candidate for sharding. ZUNIONSTORE can build derived boards (for example, last-7-days from daily keys) but is O(N) and should be run offline.

Can a client call the leaderboard directly to report a win?

No. A proxy can alter requests, so scores must come from a trusted server that has seen the match result. Where the game server owns the logic, it records the outcome without any client call.

How do you rebuild after losing Redis?

Aggregate points per user from the durable match results for the tournament (SQL group-by, or replay the event stream), bulk-load with pipelined ZADD into a new key, then switch the service to it atomically (RENAME or a pointer in config). Keep serving a cached last-known top ten while the rebuild runs, and replay events received during the rebuild.

Key Takeaway

A leaderboard is an order-statistic problem: pick a structure that is always sorted and can count what is above you. Use a Redis sorted set for serving, a durable database or log for truth, authoritative servers for scoring, and delay sharding until the numbers demand it. When you do shard, decide up front whether you are protecting cheap top-K or cheap exact rank, because the partitioning scheme cannot give you both for free.
