Design Nearby Friends

Proximity search over points that move every thirty seconds. Where the last chapter's index could be rebuilt nightly, this one has hundreds of thousands of writes per second and a fan-out problem, so the design shifts from indexes to messaging.

"Show me which friends are within five miles, live." Notice what is absent: nobody asked to search a map. The geometry is a one-line distance formula between two known people. The hard part is that every person's position changes constantly and every change must reach a few dozen others quickly, which makes this a messaging system wearing a location costume.

Core idea: give every user a pub/sub channel carrying their location. Each connected user subscribes to the channels of their friends. A location update is one publish, delivered to whichever WebSocket servers hold subscribers, which compute the distance and forward only when it is under the threshold. The scale problem is entirely in the pub/sub tier.

A public design to anchor on

Why Erlang and Elixir keep appearing

WhatsApp has publicly described running its messaging servers on Erlang, with a very large number of concurrent connections per machine, and Discord has written about using Elixir (also on the BEAM virtual machine) for its real-time presence and guild fan-out. The reason is structural: BEAM gives cheap isolated processes, message passing between them, and supervised restart, which is exactly the shape of "a connection per user and a mailbox per channel". The chapter's Erlang alternative is this same observation. See the neighbouring page on Discord presence for a related fan-out problem.

Requirements and numbers

Scope and sizing

The interview dialogue pins down the scope: "nearby" means straight-line distance within a configurable five miles; the app has one billion users of which ten percent use this feature; inactive friends drop off the list after about ten minutes; history is stored for analytics and machine learning; privacy law is out of scope for the exercise (in the real product it absolutely is not, see gotchas). Functional needs: a list of nearby friends, each with distance and a "last updated" timestamp, refreshed every few seconds. Non-functional: low latency delivery, tolerance for occasional lost updates, and eventual consistency for location data.

The 100 K per node figure is an assumption (Redis pub/sub delivery cost grows with subscriber count and message size); in an interview, state it, then say you would benchmark.
High-level design

Why not peer to peer, and why not pull

Phones sit behind carrier NAT, lose connectivity in lifts, and must conserve battery. Direct device-to-device messaging is therefore impractical; a shared backend acts as the fan-out point. It receives every active user's location, finds recipients, and forwards a message only when the pair is within the radius.

A pull design is the other obvious option: every thirty seconds each client asks "where are my friends". With 10 M concurrent users, even if the server only looks up online friends (about 40 each), that is 10 M × 40 ÷ 30 ≈ 13 M cache reads per second, equal in volume to push, but with an extra request round trip, no early out when nobody has moved, and constant polling of friends who are far away. Push is better because a quiet user generates no work. Both designs have the same asymptotic cost; push has the better constants and the lower delay.

  • Load balancer fronts both REST and WebSocket traffic. For WebSockets it only picks a server at connection time; after that the connection is sticky by nature.
  • REST API servers are ordinary stateless services for friend management and profile.
  • WebSocket servers hold the live connection, accept the periodic update, publish it, and receive friends' updates to forward. They are stateful (they remember each connected user's latest location and their subscriptions in memory for distance maths).
  • Location cache (Redis) maps user_id → (lat, lon, timestamp) with a TTL of about ten minutes. Expiry is the definition of "inactive": no key, not nearby. Each update refreshes the TTL.
  • Location history (Cassandra, partition by user, cluster by time) is write-only from this feature's view and feeds analytics and ML. It must not be in the hot path.
  • Redis pub/sub is the message bus. A channel costs almost nothing when nobody subscribes, so every user's channel can exist implicitly.

One periodic update, end to end

  1. Phone sends {lat, lon, ts} over its WebSocket every 30 s.
  2. WS server appends to history (async), writes the cache (refreshing the TTL) and updates its own in-memory copy for that user.
  3. It publishes the update on the user's channel.
  4. Every WS server with at least one subscriber on that channel receives it.
  5. For each local subscriber it computes the distance between the subscriber's last known location and the published one. If within the radius it pushes {friend_id, lat, lon, ts} to the subscriber's socket; otherwise it drops it silently.

The distance check sits on the receiving side because the sender's channel is shared by all friends; the sender does not know each friend's position. On average there are about 40 deliveries per update, which is where the 14 M/s comes from.

Client initialisation

When a client connects, the WS server loads that user's friend list, subscribes to every friend's channel, reads each friend's last location from the cache, filters by distance, and returns the initial list. Without the cache read the user would wait up to 30 s before seeing anyone. Subscription is idempotent, so a reconnect simply repeats the process.

Deep dive 2

Distributing the pub/sub tier

Two Redis nodes would hold the 200 GB, but 140 are needed for delivery throughput, so the channel space must be partitioned. Partition by channel: each user's channel lives on exactly one pub/sub node. All publishers and subscribers must agree on which node that is, or messages vanish. That agreement is a consistent hash ring over the channel name, distributed via service discovery.

ZooKeeper / etcd key: /pubsub/ring → { vnodes: [(hash, node)...], version: 42 } ▲ watch ▲ watch ┌─────┴───────┐ ┌──────┴──────┐ │ WS server A │ │ WS server B │ both cache the ring locally └──────┬──────┘ └──────┬──────┘ │ publish(chan:bob) → ring.get("chan:bob") = redis-17 ▼ │ subscribe(chan:bob) → same ring → redis-17 redis-17 ◀────────────────────────────────┘
  • Ring in service discovery. ZooKeeper or etcd stores the authoritative ring and which Redis nodes are alive. WS servers watch it and cache it in memory so a publish costs a local binary search, not a network hop. See Service Discovery and Consistent Hashing.
  • Virtual nodes. Each physical node owns many positions on the ring so channels spread evenly and a join or leave moves only about 1/N of the keys. The example below measures this: adding the fifth shard moves 20.4 percent of channels, close to the 20 percent ideal.
  • Treat the cluster as stateful. A channel's subscriber list lives on its node. When a channel moves, every WS server with subscribers must re-subscribe on the new node. Pub/sub state is not replicated; a node that dies takes its subscriptions with it, and clients/WS servers must detect that and resubscribe.
  • Resizing procedure. Publish a new ring version, WS servers resubscribe the moved channels, then retire old subscriptions. Messages in flight during the cutover may be lost, which this application tolerates (the next update is 30 s away). Do it at the daily traffic trough; schedule growth from historical data and over-provision for spikes, since a sudden unplanned resize is the riskiest operation in the system.
  • Why not Redis Cluster? Classic Redis Cluster broadcasts PUBLISH to every node, which turns publish cost into O(nodes). Redis 7 added sharded pub/sub (SPUBLISH/SSUBSCRIBE) that routes by hash slot and fixes this, which is the modern way to get the same effect; the chapter's explicit ring is the pre-7 answer and also what you would build with a different bus.
Delivery semantics. Redis pub/sub is at-most-once and non-durable: a subscriber that is disconnected misses messages and there is no replay. That is a deliberate fit here because a location is stale in thirty seconds. If you swapped in Kafka for durability you would pay for log storage you never read and add per-partition fan-out limits; pub/sub is the right tool when "latest value wins and missing one is fine".
Deep dive 3

Friends, whales, strangers, alternatives

Adding and removing friends

When the friend graph changes, the affected user's WS server must subscribe or unsubscribe from the new friend's channel. The feature lives in a larger app, so the app already emits a friend-added event; the client forwards it over the socket and the server acts. Server-side, a message from the social graph service (published on the same bus or a stream) is more robust than trusting clients. When a friend first appears online, the server tells the client to start tracking them; when the friend's TTL expires, it tells the client to drop them.

Users with many friends

Cap the friend count (some networks use 5,000). The WS server of a user with 5,000 friends holds 5,000 subscriptions and receives about ten times the average traffic, but that is a single connection's worth; spread over a large fleet it is not a bottleneck. The inverse case is the publishing side: one update by a user with 5,000 subscribers produces up to 500 deliveries (with 10 percent online). Both are fine, but monitor the tail: p99 fan-out size determines p99 latency. If you remove the cap you need a different mechanism for celebrity accounts, such as sampling or opt-in only.

Showing a random nearby person

A product twist: occasionally surface a non-friend nearby. Friend channels cannot do this because the subscriber does not know whom to subscribe to. Introduce channels keyed by geohash cell: every active user publishes to the channel of the geohash cell they stand in, and every user subscribes to their own cell plus the eight neighbours (the boundary solution from the previous chapter). Pick a coarse precision such as length 5 so a cell holds a manageable crowd, and sample at the receiver to avoid flooding in dense places. These channels are distributed over the same ring (key = geo:<hash>). Privacy is the real constraint here: only show users who opted in, and show a rounded location.

Erlang or Elixir instead of Redis

On BEAM you can spawn a lightweight process per connection and per channel, so the WS server and the pub/sub layer are one distributed application with in-process routing and no separate bus. It removes the Redis hop and the ring bookkeeping (distributed Erlang or a process registry handles placement). The cost is organisational: Erlang/Elixir skills are scarcer, and you take on operating a distributed runtime. Worth naming as an option; choosing it depends on the team.

Why this design holds

  • Cost is proportional to active movers, not total users
  • Idle channels are free
  • Failures lose only a stale sample

What it pays

  • Stateful WS and Redis tiers need careful draining and resizing
  • No replay: reconnecting clients rebuild from the cache
  • High fan-out per update drives cost
Runnable code

Consistent hash ring, pub/sub shards, and WebSocket fan-out

The example builds a hash ring with virtual nodes and measures balance and movement when a shard joins. It then simulates a small cluster: three pub/sub shards chosen by the ring, a WebSocket server that subscribes each connecting user to friends' channels, seeds initial state from the location cache, filters deliveries by haversine distance in miles, and expires presence via a TTL.

JavaScript Example 
// Nearby friends: consistent-hash ring (vnodes) placing per-user pub/sub channels on shards,
// an in-process pub/sub "Redis", websocket-server fan-out with distance filtering and TTL presence.
import { createHash } from 'node:crypto';
import assert from 'node:assert/strict';

const h32 = s => createHash('md5').update(s).digest().readUInt32BE(0);
class Ring {
  points = []; // sorted [hash, node]
  constructor(vnodes = 100) { this.vnodes = vnodes; }
  add(node) { for (let i = 0; i < this.vnodes; i++) this.points.push([h32(`${node}#${i}`), node]); this.points.sort((a, b) => a[0] - b[0]); }
  remove(node) { this.points = this.points.filter(p => p[1] !== node); }
  get(key) {
    const h = h32(key); let lo = 0, hi = this.points.length;
    while (lo < hi) { const m = (lo + hi) >> 1; if (this.points[m][0] < h) lo = m + 1; else hi = m; }
    return this.points[lo % this.points.length][1];
  }
}

class PubSubShard { // channel -> subscribers (each shard is "one Redis node")
  chans = new Map(); published = 0;
  subscribe(ch, fn) { (this.chans.get(ch) ?? this.chans.set(ch, new Set()).get(ch)).add(fn); }
  unsubscribe(ch, fn) { this.chans.get(ch)?.delete(fn); }
  publish(ch, msg) { this.published++; for (const fn of this.chans.get(ch) ?? []) fn(msg); }
}

const R = 3958.7613; // miles
const rad = d => d * Math.PI / 180;
const miles = (a, b) => {
  const s = Math.sin(rad(b.lat - a.lat) / 2) ** 2 + Math.cos(rad(a.lat)) * Math.cos(rad(b.lat)) * Math.sin(rad(b.lon - a.lon) / 2) ** 2;
  return 2 * R * Math.asin(Math.sqrt(s));
};

class Cluster {
  now = 0; ttl = 600; // seconds
  cache = new Map();  // location cache: user -> {lat,lon,ts}
  constructor(shardNames, vnodes) {
    this.ring = new Ring(vnodes); this.shards = new Map();
    shardNames.forEach(n => { this.ring.add(n); this.shards.set(n, new PubSubShard()); });
  }
  shardFor(user) { return this.shards.get(this.ring.get(`chan:${user}`)); }
  alive(user) { const l = this.cache.get(user); return l && this.now - l.ts <= this.ttl ? l : null; }
}

class WsServer {
  constructor(cluster, friendsOf, radiusMiles = 5) { this.c = cluster; this.friendsOf = friendsOf; this.radius = radiusMiles; this.users = new Map(); }
  connect(user, loc, inbox) {
    this.users.set(user, { loc, inbox, subs: [] });
    this.c.cache.set(user, { ...loc, ts: this.c.now });
    for (const f of this.friendsOf(user)) {                 // subscribe to every friend's channel
      const fn = msg => this.#deliver(user, msg);
      this.c.shardFor(f).subscribe(`chan:${f}`, fn);
      this.users.get(user).subs.push([f, fn]);
      const fl = this.c.alive(f);                           // seed initial view from the cache
      if (fl && miles(loc, fl) <= this.radius) inbox.push({ from: f, miles: +miles(loc, fl).toFixed(2), ts: fl.ts, seed: true });
    }
  }
  disconnect(user) { for (const [f, fn] of this.users.get(user).subs) this.c.shardFor(f).unsubscribe(`chan:${f}`, fn); this.users.delete(user); }
  update(user, loc) {                                       // periodic location update
    this.users.get(user).loc = loc;
    this.c.cache.set(user, { ...loc, ts: this.c.now });
    this.c.shardFor(user).publish(`chan:${user}`, { from: user, ...loc, ts: this.c.now });
  }
  #deliver(to, msg) {                                       // receiving side does the distance filter
    const u = this.users.get(to); if (!u) return;
    const d = miles(u.loc, msg);
    if (d <= this.radius) u.inbox.push({ from: msg.from, miles: +d.toFixed(2), ts: msg.ts });
  }
}

// ---------- tests ----------
// 1. ring balance + minimal movement when adding a shard
const ring = new Ring(200); ['r1', 'r2', 'r3', 'r4'].forEach(n => ring.add(n));
const keys = Array.from({ length: 20000 }, (_, i) => `chan:u${i}`);
const before = keys.map(k => ring.get(k));
const counts = {}; before.forEach(n => counts[n] = (counts[n] ?? 0) + 1);
console.log('channels per shard:', JSON.stringify(counts));
for (const n of Object.values(counts)) assert.ok(n > 3500 && n < 6500);
ring.add('r5');
const moved = keys.filter((k, i) => ring.get(k) !== before[i]).length;
console.log(`adding 1 of 5 shards moved ${(100 * moved / keys.length).toFixed(1)}% of channels (ideal 20%)`);
assert.ok(moved / keys.length < 0.30);
assert.ok(keys.every((k, i) => ring.get(k) === before[i] || ring.get(k) === 'r5'));

// 2. end-to-end fan-out
const friends = { alice: ['bob', 'carol'], bob: ['alice'], carol: ['alice'] };
const cl = new Cluster(['s1', 's2', 's3'], 100);
const ws = new WsServer(cl, u => friends[u]);
const inbox = { alice: [], bob: [], carol: [] };
ws.connect('bob', { lat: 37.78, lon: -122.41 }, inbox.bob);          // ~0.6 mi away from alice
ws.connect('carol', { lat: 37.33, lon: -121.89 }, inbox.carol);      // San Jose ~ 42 mi

console.log('alice seeded view:', JSON.stringify(inbox.alice));

ws.update('bob', { lat: 37.79, lon: -122.40 });
cl.now = 30; ws.update('carol', { lat: 37.34, lon: -121.88 });
console.log('alice after updates:', JSON.stringify(inbox.alice.slice(1)));
assert.equal(inbox.alice.length, 2);                                   // carol filtered (too far)
assert.equal(inbox.bob.length, 0);                                 // bob only hears alice, who has not moved

ws.update('alice', { lat: 37.7750, lon: -122.4190 });
assert.equal(inbox.bob.length, 1);

// 3. TTL presence

assert.equal(cl.alive('bob'), null);
console.log('bob expired from presence after 10 min of silence: true');
console.log('all assertions passed');

Scaling and production

Gotchas

  • Privacy is the product risk. Opt-in, mutual-friend-only visibility, a visible "sharing with" indicator, a "pause" switch, rounding location to a coarse precision when displayed, and blocked-user filtering at the receiver. Location history is sensitive personal data and subject to GDPR/CCPA in real deployments, however the interview waived it. Set retention limits and let users delete history.
  • Battery. The biggest cost sits on the phone. Adaptive reporting (more often when moving fast, back off when stationary, suppress when the app is backgrounded), significant-change location APIs, and batching radio use all matter more than server tuning.
  • Mass reconnect after an outage. Millions of clients reconnect together and each triggers a friend-list read plus hundreds of subscribes. Use connection admission control, exponential backoff with jitter, and a cached friend list.
  • Subscription accounting. Each connection costs 400 subscribe calls in the worst case. Subscribe lazily to online friends only, and learn presence from the cache (a pipelined multi-get) before subscribing.
  • Distance on a sphere. Haversine per delivery is cheap, but at 14 M/s it is millions of trig calls per second; precompute cosine of the receiver's latitude and short-circuit with a bounding-box test.
  • Backpressure. A hotspot such as a stadium turns many friends co-located, so every update passes the distance test and fan-out goes from 40 to nearly 400. Plan for the worst case, not the mean.
  • Observability. Track end-to-end delivery latency (publish timestamp to client receipt), fan-out size histogram, subscription counts per node, and ring version skew. See Observability.

FAQ · Common Questions

Frequently Asked Questions

Why subscribe to friends' channels instead of publishing to each friend's channel?

Publishing to each friend multiplies publisher work by 400 on every update, even for offline friends. Subscribing moves the fan-out cost into the pub/sub node and, because subscriptions exist only for online friends, you pay only for friends who can actually receive.

Could you use the geohash approach for friends too?

Yes: everyone publishes to their cell channel and receivers filter to friends. It scales with cells not friends, but each receiver sees all strangers in nearby cells, which at city density is far more traffic than 40 friends. Friend channels are more selective.

What if Redis pub/sub is too slow?

Shard further, batch multiple updates per publish per destination node, drop precision (cheaper payloads), reduce update frequency, or move to in-process routing as in the Erlang design. First measure whether the limit is CPU on subscribers or network egress.

How do you avoid showing a stale friend?

Every update carries a timestamp, the cache TTL removes inactive users, and the UI displays "last updated". A friend not heard from in ten minutes disappears; the server sends an unsubscribe hint to the client.

How would you make the radius configurable per user?

Store the radius with the receiver; the receiving WS server applies it during the distance check. No change to publishing is needed, which is a benefit of receiver-side filtering.

How do you test this at scale?

Synthetic load generators holding millions of sockets with realistic movement models, ring-resize game days, and chaos tests that kill pub/sub nodes while measuring delivery gaps. Watch delivery latency percentiles, not averages.

Key Takeaway

When points move, stop thinking in indexes and start thinking in message rates. One channel per user, subscribers filter by distance, a TTL cache defines presence, and a consistent-hash ring spreads channels over enough pub/sub nodes to carry fourteen million deliveries a second. Because stale locations are worthless, an ephemeral at-most-once bus is exactly right.
