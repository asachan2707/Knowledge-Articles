Design a Web Crawler

A crawler is a graph traversal over the public web that must be fast, but above all polite and robust. The core component is the URL frontier, which has to prioritise important pages while guaranteeing that no single host is hammered.

Every search engine begins with a crawler. Before anything can be indexed or ranked, someone has to fetch billions of pages from servers they do not control, without knocking those servers over, without falling into infinite loops, and without storing the same content twice. Crawlers also serve web archiving, data mining and brand-monitoring jobs, but the search-index case sets the hardest requirements.

Core idea: the web is a directed graph, and crawling is breadth-first search with two twists. The queue is not a simple FIFO: it is a two-level structure that orders work by importance and spaces out requests per host. And two membership tests, "have I seen this URL" and "have I seen this content", keep the traversal finite.

A well-known design

Mercator and its descendants

The published design that most crawler architectures descend from is Mercator, the crawler built at Compaq/AltaVista and described in the late 1990s. Its blueprint will look familiar after this chapter: a frontier that is really two sets of queues (priority "front" queues feeding per-host "back" queues), a fetch stage with a DNS cache, a duplicate-content fingerprint check, and a URL-seen set kept mostly on disk with an in-memory cache in front. Open-source crawlers such as Heritrix (used by the Internet Archive) and Apache Nutch follow the same structure, and Common Crawl publishes monthly snapshots of this kind of output. The notes' diagram is a modernised Mercator.

Workflow

  1. Seed URLs enter the frontier.
  2. The downloader takes URLs from the frontier, resolves DNS and fetches.
  3. The parser validates the page; content-seen checks its fingerprint.
  4. New content is stored and its links extracted.
  5. Links pass the filter, then URL-seen, and the survivors return to the frontier.
Traversal

BFS, not DFS, and why plain BFS is not enough

Depth-first search on the web can descend arbitrarily deep into one site's link structure (or a generated trap) before returning, which is both slow to cover the graph and unfair to other hosts. Breadth-first with a FIFO queue is the natural default. But a pure FIFO has two flaws on the real web: it ignores that pages differ wildly in value, and because a page tends to link many URLs on its own host, FIFO order releases bursts of same-host URLs back-to-back, which is exactly the traffic pattern that gets crawlers banned.

The fix is to make the frontier smarter, not to abandon BFS.

The URL frontier

Two tiers: priority in front, politeness behind

   incoming URLs
        |
   [ Prioritizer ] -- score by PageRank-like signal, domain authority, change rate
        |
   +----+-----+-----+            FRONT queues f1..fn  (priority)
   | f1 | f2  | ... | fn         selector picks f_i with probability biased to high priority
   +----+-----+-----+
        |   (route by host)
   [ Back-queue router ] -- mapping table: host -> back queue
        |
   +----+-----+-----+            BACK queues b1..bm  (politeness)
   | b1 | b2  | ... | bm         each queue holds URLs of ONE host at a time
   +----+-----+-----+
        |    |           |
     worker1 worker2 ... workerM   one worker per back queue, sleeps between fetches

Politeness

The rule: at most one in-flight request per host, with a gap between consecutive requests. Implement it by routing all URLs of a host into one FIFO back queue (the mapping table records host to queue), assigning each queue to one worker, and having that worker wait out a delay before taking the next URL. A common refinement, used in Mercator, keeps a heap keyed by "earliest time this host may be hit again" so the scheduler always picks the host that is ready soonest, which keeps workers busy even when many hosts are cooling down. Honour the site's Crawl-delay if given (Google ignores that directive, but many crawlers respect it), and adapt dynamically: back off when latency or 5xx rates rise, since the server's response time is a good signal of its load.

Priority

The prioritizer assigns each URL a score from signals such as a PageRank estimate, the domain's observed quality, how often the page changes, and depth from a seed. URLs land in front queues f1..fn, one per priority band. The selector draws from the higher bands more often but never starves the lower ones, because a strictly highest-first policy would leave the long tail forever uncrawled. The front queues decide what matters; the back queues decide when it is safe.

Freshness

A crawl is never finished; pages change. Recrawl using the page's own history: a news front page may change every few minutes, an archived article never. Estimate each page's change rate from past visits (if it changed in 4 of the last 5 fetches, revisit soon) and use HTTP validators (ETag, If-Modified-Since) so an unchanged page costs a 304 rather than 500 KB. Prioritise recrawls by importance times staleness, otherwise the cheap, frequently changing pages crowd out discovery of new ones.

Storage of the frontier

The frontier holds hundreds of millions of URLs, too many for memory, but it needs low-latency dequeue. The standard split is a disk-backed queue with a small in-memory buffer at the head and tail of each queue: workers read and write the memory buffers and a background process spills and refills from disk in batches. Sequential disk I/O keeps that cheap.

Politeness is a correctness property, not a nicety. A mis-bucketed URL (for example, treating www.example.com and example.com as different hosts, or ignoring that many hostnames share one IP) lets you send parallel requests to one machine. Key politeness on the registered domain and, where cheap to know, the resolved IP.

HTML Downloader

Fetching fast without being rude or fragile

  • robots.txt. Before fetching from a host, retrieve and cache its /robots.txt (refresh periodically, for example daily) and obey Disallow and Allow rules, using the longest matching path. Treat a 4xx as "no restrictions" and a persistent 5xx as "stay away for now", which is what Google's documented behaviour does.
  • DNS cache. DNS lookups can take tens to hundreds of milliseconds and many resolvers serialise requests. Keep an in-process map of host to IP with a TTL, refresh in the background, and use an asynchronous resolver.
  • Distribute. Run many crawler servers, assign hosts to servers by hashing the host, and place crawlers near the content (regional data centres) to cut latency and cross-ocean bandwidth. See consistent hashing so adding a server remaps only a fraction of hosts.
  • Short timeouts. Set connect, first-byte and total timeouts, and cap response size. A slow host should cost you a few seconds of one worker, not a thread forever; count repeated timeouts and deprioritise the host.
  • Be identifiable. Send a descriptive User-Agent with a contact URL, and honour requests to stop.
  • Conditional GET and compression. Send Accept-Encoding: gzip and validators to save bandwidth on both sides.
Dedup

Two membership tests keep the crawl finite

URL seen

Without it, any cycle in the link graph (and the web is full of them) loops forever. Normalise first, since otherwise the same page appears under many spellings: lowercase the host, drop the fragment, remove default ports, sort query parameters, collapse duplicate slashes and trailing slashes, resolve relative paths. Then test membership in a Bloom filter (a miss is definitive; a hit has a small chance of being wrong, which here means a rare page is skipped, an acceptable loss) or an exact hash set of 64-bit URL fingerprints on disk with a memory cache. Strip tracking parameters (utm_*) per site rules where safe.

Content seen

Many distinct URLs serve identical bodies: mirrors, session-id variants, print views. Comparing page text directly is far too costly, so store a fingerprint per page: a cryptographic or 64-bit hash for exact duplicates, and a locality-sensitive hash like simhash for near-duplicates, where two pages that differ by a banner or timestamp land within a few bits of Hamming distance. The code below implements simhash on three-word shingles and shows a near-duplicate scoring distance 0 against an unrelated page at 31.

Exact-hash trap: a hash of the full HTML fails on near-duplicates, since any dynamic fragment (a timestamp, a rotating ad id) changes it. Hash the extracted main text, not the raw markup, for the exact-match test.

Hostile web

Spider traps, noise and dynamic pages

  • Spider traps. Infinite link structures: a calendar that links to the next month forever, a relative link bug producing /a/a/a/a/..., session ids in URLs that make every visit a new URL. Defences: cap URL length (say 2,000 characters), cap path depth, cap the number of pages per host or per directory pattern, detect repeating path segments, and flag hosts whose URL count explodes without new content. A person can then whitelist or blacklist the offender; fully automatic trap detection is an unsolved problem.
  • Data noise. Advertising, boilerplate navigation, spam and auto-generated pages add storage cost and pollute the index. Filter by content quality signals and exclude known spam domains.
  • Server-side rendering. Many modern sites build their content in the browser with JavaScript, so the raw HTML contains almost nothing. Rendering every page in a headless browser costs orders of magnitude more CPU than a plain fetch, so do it selectively: render only pages that look like empty shells, in a separate, lower-throughput pool. Google documents this as its "rendering" stage following crawl.
  • Malformed and malicious content. Parsers must tolerate broken HTML, enormous documents, decompression bombs and zip links. Sandbox parsing, set size limits, and never execute fetched content on the fetch workers.
Robustness and extensibility

Surviving failure, and adding new content types

  • Consistent hashing of hosts across crawler servers spreads load and means a server failure remaps only its share.
  • Checkpoint the frontier and the URL-seen set periodically so a crashed crawler resumes rather than restarting. A message queue between stages decouples them and absorbs bursts (message queues).
  • Handle exceptions per URL. One bad page must never crash a worker; catch, record, move on, and count failures per host.
  • Validate data at every stage boundary (status codes, MIME type, encoding, size).
  • Extensibility. Treat the pipeline as pluggable stages after the parser: a PNG downloader, a web monitor that checks for copyright or trademark misuse, a link-graph exporter for PageRank. Each module reads from the same stream of fetched pages and is added without touching the fetch core.

Partition by host

  • All rate state for a host lives on one server.
  • robots.txt and DNS cache locality.
  • Easy to enforce one-request-at-a-time.

Cost of partition by host

  • Extracted links must be forwarded to the owner server of each target host.
  • A giant host (a large social site) is a hot partition.
  • Rebalancing moves politeness state.
Hands-on

Normalisation, robots rules, a politeness frontier and simhash

The script crawls a tiny simulated web with a virtual clock. It normalises URLs, applies robots.txt with longest-match semantics and a Crawl-delay of two seconds for one host, uses a two-tier frontier (priority in front, per-host queues behind), caps depth to stop a trap, deduplicates by content hash, and finishes with a simhash demonstration. Assertions verify that the delay was honoured, the private path never fetched, and equivalent URLs collapsed.

JavaScript Example 
import assert from 'node:assert/strict';
import { createHash } from 'node:crypto';

// ---- URL normalization (dedup key) ----
export function normalize(raw) {
  const u = new URL(raw);
  u.hash = '';
  u.hostname = u.hostname.toLowerCase();
  if ((u.protocol === 'http:' && u.port === '80') || (u.protocol === 'https:' && u.port === '443')) u.port = '';
  u.searchParams.sort();
  let p = u.pathname.replace(/\/{2,}/g, '/');
  if (p.length > 1 && p.endsWith('/')) p = p.slice(0, -1);
  u.pathname = p;
  return u.toString();
}

// ---- robots.txt (minimal: longest-match Allow/Disallow for one agent group) ----
export function parseRobots(text, agent = '*') {
  const rules = []; let applies = false, delay = 0;
  for (const line of text.split('\n').map(l => l.split('#')[0].trim()).filter(Boolean)) {
    const [k, ...r] = line.split(':'); const key = k.toLowerCase(), val = r.join(':').trim();
    if (key === 'user-agent') applies = val === '*' || val === agent;
    else if (applies && key === 'disallow' && val) rules.push({ allow: false, path: val });
    else if (applies && key === 'allow' && val) rules.push({ allow: true, path: val });
    else if (applies && key === 'crawl-delay') delay = Number(val) * 1000;
  }
  return { delay, allowed(path) {
    let best = null;
    for (const r of rules) if (path.startsWith(r.path) && (!best || r.path.length > best.path.length)) best = r;
    return best ? best.allow : true;
  } };
}

// ---- URL frontier: prioritizer (front queues) + politeness (back queues per host) ----
export class Frontier {
  constructor({ priorities = 3, defaultDelay = 1000, now = () => Date.now() } = {}) {
    this.front = Array.from({ length: priorities }, () => []);
    this.back = new Map();      // host -> FIFO of urls
    this.nextOk = new Map();    // host -> earliest next fetch time
    this.delays = new Map();    // host -> crawl-delay override
    this.defaultDelay = defaultDelay; this.now = now;
  }
  add(url, priority = 1) { this.front[Math.min(priority, this.front.length - 1)].push(url); }
  setDelay(host, ms) { this.delays.set(host, ms); }
  // move from front queues (high priority first, biased) into per-host back queues
  #refill() {
    for (const q of this.front) {
      while (q.length) { const url = q.shift(); const h = new URL(url).host;
        if (!this.back.has(h)) this.back.set(h, []); this.back.get(h).push(url); }
    }
  }
  // returns {url} when some host is ready, or {waitMs} when all hosts are cooling down, or null if empty
  next() {
    this.#refill();
    let minWait = Infinity;
    for (const [host, q] of this.back) {
      if (!q.length) continue;
      const wait = (this.nextOk.get(host) ?? 0) - this.now();
      if (wait <= 0) {
        this.nextOk.set(host, this.now() + (this.delays.get(host) ?? this.defaultDelay));
        return { url: q.shift() };
      }
      minWait = Math.min(minWait, wait);
    }
    return minWait === Infinity ? null : { waitMs: minWait };
  }
}

// ---- content-seen: exact hash + simhash for near-duplicates ----
export const contentHash = t => createHash('sha256').update(t).digest('hex');
export function simhash(text) {
  const v = new Array(64).fill(0);
  const words = text.toLowerCase().match(/\w+/g) ?? [];
  for (let i = 0; i + 2 < words.length + 1; i++) {                  // 3-word shingles
    const sh = words.slice(i, i + 3).join(' ');
    const h = createHash('md5').update(sh).digest().readBigUInt64BE(0);
    for (let b = 0; b < 64; b++) v[b] += (h >> BigInt(b)) & 1n ? 1 : -1;
  }
  return v.reduce((acc, x, b) => (x > 0 ? acc | (1n << BigInt(b)) : acc), 0n);
}
export function hamming(a, b) { let x = a ^ b, n = 0; while (x) { n += Number(x & 1n); x >>= 1n; } return n; }

  if (!robots[u.hostname]?.allowed(u.pathname)) { log.push(`t=${clock} SKIP robots ${url}`); continue; }

  }
}

Scaling and production gotchas

Where it hurts at scale

  • The crawl is I/O bound, not CPU bound, until you add parsing and rendering; size fetchers by concurrent connections, parsers by CPU.
  • The URL-seen set grows with every discovered URL, not every fetched page. Discovery outpaces fetching by a large factor, so cap or sample links from low-value pages.
  • Hostnames lie: wildcard DNS makes infinite subdomains. Limit subdomains per registered domain.
  • Character encodings and redirect chains (limit to a handful of hops) account for many silent losses; record the final URL and canonical link element.
  • Respect noindex, nofollow and the legal environment (terms of use, privacy law) per jurisdiction. Keep an operator-facing abuse contact and a way to blocklist a domain instantly.
  • Store raw responses compressed in large append-only container files (WARC is the archiving standard) rather than one object per page, to avoid small-file overhead at billions of pages.
  • Shard storage and the URL database by host; use replication for durability. Collect crawl metrics (pages per second per host, error rate, queue depth, duplicate ratio) to tune the whole system.

FAQ · Common Questions

Frequently Asked Questions

Why not simply use a single FIFO queue?

It cannot express priority, and it produces bursts of same-host requests since linked pages cluster by host. The two-tier frontier separates the two concerns cleanly.

How do you decide the delay between requests to a host?

Start from the robots.txt Crawl-delay if present, else a default of a second or more, and scale by the measured response time of the host (a common heuristic is a multiple of the last fetch time). Back off further on errors or timeouts.

A Bloom filter can skip pages. Is that acceptable?

Usually yes: with a 1% false-positive rate you miss about one new URL in a hundred in that epoch, and most are re-discovered via other links or the next crawl. For critical hosts keep an exact set. The benefit is memory: roughly 12 GB for 10 billion URLs versus over 100 GB for exact 8-byte fingerprints.

How do you detect that a page changed?

Conditional GET with ETag or Last-Modified is the first, cheap signal. If the server does not support it, compare the content fingerprint with the stored one. Record the change history to drive recrawl frequency.

How would you crawl a site that is entirely JavaScript?

Detect an empty shell (very little text, a root div and script tags), send it to a separate rendering pool running a headless browser, set a strict time and resource budget, and extract links from the rendered DOM. It is expensive, so do it for a small fraction of pages.

How do you scale the crawl past one data centre?

Partition hosts across regional crawler clusters by consistent hash on the host; forward discovered URLs to the owning cluster through a queue; keep content storage regional and replicate only the index inputs. Because politeness state is per host, partitioning by host keeps it local.

Key Takeaway

A crawler is BFS over the web with a smart queue. Build the frontier as priority queues feeding one-host-per-queue back queues, obey robots.txt, filter URLs and content twice (normalised URL-seen, fingerprinted content-seen), and defend against traps with hard limits. Shard by host so politeness state stays local, checkpoint everything, and keep the pipeline pluggable.
