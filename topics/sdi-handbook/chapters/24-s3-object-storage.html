Design an S3-like Object Storage

Object storage trades latency for durability, capacity and cost. This chapter separates metadata from bytes, packs small objects into big append-only files, protects data with erasure coding across failure domains, and handles listing, versioning, multipart uploads and garbage collection.

Almost every large system eventually produces a pile of immutable blobs: photos, videos, backups, logs, model checkpoints, email attachments. Putting them in a database is wasteful, putting them on a network file system does not scale, and putting them on raw disks makes you reinvent durability every time. Object storage is the shared answer: a flat namespace of immutable objects, addressed by key over HTTP, built to be nearly impossible to lose.

The interesting part of this chapter is not the REST API, which is trivial. It is how you pack billions of objects of wildly different sizes onto commodity disks, keep six or more nines of durability without tripling your hardware bill, and still make listing, versioning and giant uploads work.

Core idea: Split the system into a small, strongly consistent, sharded metadata plane (names, versions, locations) and a huge, dumb, append-only data plane (bytes on disks, protected by replication or erasure coding and verified by checksums). Everything else is bookkeeping around that split.

Background · Public designs worth knowing

Why "pack small files into big ones" is the oldest trick in the book

Facebook's Haystack paper (OSDI 2010) is the canonical public account of the small-object problem. Serving billions of photos from a conventional file system meant several disk operations per photo, mostly spent reading directory and inode metadata. Haystack's fix was to append many photos into very large files and keep a compact in-memory index of offsets, so a read costs one disk seek. Google's GFS, HDFS and today's S3-class systems all share the same instinct: avoid one-file-per-object on the underlying file system.

The other public landmark is Amazon S3 itself, launched in 2006. It exposes a bucket/key API, publishes eleven nines of annual durability for its standard classes, and, since late 2020, provides strong read-after-write consistency for all operations. Backblaze's open durability analysis and the Reed-Solomon coding literature are the public foundations for the erasure-coding discussion below.

Background · Storage Types

Block, file and object storage

Block storage (HDD, SSD, SAN volumes, cloud volumes such as EBS) exposes fixed-size blocks to a server, which formats them with a file system or hands them to a database that manages raw blocks. File storage adds hierarchy and POSIX-like semantics (directories, permissions, in-place edits) on top of block storage and is shared over NFS or SMB. Object storage drops the hierarchy and in-place mutation in exchange for scale, cost and durability: you PUT a whole object, GET it back, or DELETE it.

Vocabulary: a bucket is a globally unique container; an object is data plus metadata addressed by key inside a bucket; versioning keeps multiple variants of the same key; the URI is /bucket/key; an SLA states durability and availability promises. Note that there is no real directory tree: photos/2024/cat.jpg is one key that happens to contain slashes.

Step 1 · Scope and Requirements

Targets and the estimate

Scope: create buckets, upload and download objects, versioning, list objects in a bucket. Objects range from tiny to huge and both must be efficient. Capacity: about 100 PB. Durability: six nines, availability: four nines. The extra requirement that decides the architecture is storage efficiency: lower the cost per stored byte without giving up reliability or performance.

With six nines of durability, you expect to lose roughly one object in a million per year. With four nines of availability you may be unavailable about 52 minutes per year (365 × 24 × 60 × 0.0001 ≈ 52.6 min). Note that durability and availability are different promises: an object can be perfectly safe while the service is temporarily down.

Two takeaways. First, the metadata is tiny compared with the data (0.68 TB against 40 PB, a ratio of about 1 in 60,000), so it fits in a modest sharded database and can be engineered separately. Second, small objects are 20% of the count but only about 0.2% of the bytes (0.1 of 59.3 MB); they are the IOPS problem while large objects are the bandwidth problem. A 7200 rpm disk gives only 100-150 random IOPS, so one object per random seek would be ruinous. That is what pushes us toward sequential, append-only layouts. The drive counts above ignore headroom, rebuild spare capacity and growth, but the 2x gap between replication and erasure coding is the point.

Step 2 · High-Level Design

Properties that shape the design

  • Immutability: objects are never edited in place. A "modification" is a new object (or new version) under the same key. This kills a huge class of consistency and locking problems and makes erasure coding and caching safe.
  • Key-value shape: the key is the URI; the value is the bytes.
  • Write once, read many: published workload numbers put reads far above writes (one often-quoted figure is around 95% reads), so read paths and caches matter.
  • Mixed sizes: the system must be efficient for kilobytes and for multi-gigabyte objects.

The design mirrors a UNIX file system. A file has an inode (metadata and a list of block pointers) and data blocks scattered on disk; reading means looking up the inode first. Object storage does the same at datacenter scale: the metadata store plays the inode table (name to object id, size, owner, version, tags), the data store holds the blocks. Separating them lets each scale on its own axis: metadata is small and query-heavy, data is huge and throughput-heavy.

 Client --HTTP--> Load balancer --> API service (stateless) ---+--> IAM: authn / authz / bucket policy
                                                +--> Metadata store: bucket + object tables (sharded)
                                                +--> Data store: bytes addressed by object_id (UUID)

Upload path

  1. PUT /bucket-to-share creates a bucket. The API service asks IAM whether the caller may write, then inserts a bucket row in the metadata store and returns success.
  2. PUT /bucket-to-share/script.txt uploads an object. The API service re-checks authorization, then streams the payload to the data store, which persists it and returns a fresh object_id (a UUID).
  3. Only after the data store acknowledges does the API service insert the object row (object_id, bucket_id, name, size, checksum, ...) into the metadata store. Order matters: writing data first means a crash leaves an orphan blob (garbage collected later) rather than a metadata row pointing at nothing.

Download path

  1. GET /bucket-to-share/script.txt reaches the API service through the load balancer.
  2. IAM checks read permission. The metadata store resolves bucket and name to object_id (and the current version).
  3. The data store returns the bytes for that id, which are streamed back. Range requests (Range: bytes=...) must be supported, since large-object clients depend on them.

The folder illusion. Because the namespace is flat, "folders" are a naming convention plus a listing feature: list with prefix abc/ and delimiter / to get one level at a time. Consequently renaming a "folder" means copying every object under the prefix and deleting the originals; there is no O(1) rename.

The data store

Persistence flow with replication

  1. The API service sends the object to the data routing service.
  2. The router generates the object id and picks the replication group for that id deterministically (consistent hashing over the cluster map), then sends the data to the group's primary.
  3. The primary writes locally and replicates to two secondaries.
  4. Once the replicas have acknowledged, the primary responds and the object id returns up the chain.

The primary waits for replication before acknowledging, trading latency for consistency. There is a spectrum: acknowledge after all replicas (strongest, slowest), after a quorum of two out of three (usual compromise: survives one slow or dead replica), or after the primary alone (fast, but a primary crash loses data that no one else has). For an object store whose headline promise is durability, wait for at least a quorum, and make "no ack until durable on disk" literal by calling fsync or using O_DSYNC-style writes on the commit path.

How bytes are laid out on disk

Storing one file per object is the obvious approach and breaks at scale for two reasons. Every file wastes the tail of its last block (a 4 KB block size makes a 1 KB object occupy 4 KB), and every file consumes an inode; file systems slow down and eventually run out of inodes with hundreds of millions of tiny files.

The fix is to append objects into large files, much like a write-ahead log: open a file, append records one after another, and when the file reaches a few gigabytes seal it and start a new one. Only one file per core or per disk is writable at a time, because appends to one file must be serialized; pinning writable files to cores (or giving each writer its own active file) removes lock contention. Sealed files are immutable, which makes them trivially cacheable, checksummable and replicable.

 /data/f0 (sealed)  [obj A][obj B][obj C][obj D] ...            immutable, a few GB
 /data/f1 (active)  [obj E][obj F][obj G] --> append here          single writer per file

 object_mapping table (per data node)
   object_id | file   | offset | size
   ----------+--------+--------+-----
   uuid-F    | f1     | 4_096  | 1_024        -> read = open file, pread(offset, size), verify checksum

Finding an object inside a file

Each data node keeps an object_mapping table: object id, file name, offset, size. The access pattern is point lookups with relatively few writes, so a B-tree style engine suits it, and an embedded relational database such as SQLite is a good fit (an LSM engine such as RocksDB is the alternative when write rates are very high). The key design choice is where the mapping lives. A separate shared database cluster would need aggressive scaling and adds a network hop on every read. Because a data node only ever needs the mappings for its own objects, embed the database on the node itself. Losing the node means losing its mapping, but the replicas have their own copies, and in a pinch the table can be rebuilt by scanning the self-describing records in the sealed files, which is why each record on disk should carry its id, length and checksum.

The updated write path on a data node is therefore: append the object to the active file, then insert the mapping row. Reads look up the row and issue one positional read. With the mapping in memory or in the page cache, a read costs a single disk access.

Deep Dive 2

Durability: replication, failure domains, erasure coding

Six nines is a statement about probabilities across every failure you can name: a disk dies, a machine dies, a rack loses power, a top-of-rack switch fails, an availability zone burns down, a firmware bug corrupts a batch of drives, an operator deletes the wrong thing. Plan against each.

Replication and the naive math

Take an annual failure rate of about 0.81% per disk. If three copies lived on independent disks and a lost copy were never repaired within the year, you would lose an object with probability 0.00813 ≈ 5.3×10-7, i.e. about 99.99995%, a bit over six nines. That is the back-of-envelope that makes three copies look "enough". It is optimistic on two counts. Failures are not independent (same rack, same batch, same power feed), and the real risk is about overlapping failures during the repair window. In practice the repair time, not the annual rate, drives the number: faster re-replication after a failure shortens the exposure window and raises durability dramatically.

 Failure-domain isolation
   AZ-1: rack1 [A] ........ rack2 [ ]
   AZ-2: rack3 [B] ........ rack4 [ ]       one replica per domain
   AZ-3: rack5 [C] ........ rack6 [ ]
   A rack, a switch or an entire AZ failing costs at most one copy.

So place replicas across racks, power domains, and ideally AZs or datacenters. The placement service's virtual cluster map exists precisely to encode these boundaries. Separate replicas by software-version and hardware-batch diversity if you can, since correlated bugs are a real source of data loss.

Erasure coding

Replication stores whole copies, so three copies cost 200% overhead (3x raw for 1x data). Erasure coding splits the object into k data chunks and computes m parity chunks so that any k of the k+m chunks reconstruct the original. With 8+4 you store 12 chunks for 8 chunks of data: 1.5x raw, 50% overhead, yet you survive the loss of any four chunks, which is better fault tolerance than three-way replication (which survives two). The chunks are spread over 12 different failure domains.

 object (e.g. 64 MB)  --split-->  d1 d2 d3 d4 d5 d6 d7 d8     8 data chunks of 8 MB
                      --encode--> p1 p2 p3 p4                   4 parity chunks
 12 chunks on 12 nodes in 12 failure domains.
 Read: fetch any 8 (fastest 8 win)  |  Lose up to 4: rebuild from survivors.

The mathematics is Reed-Solomon coding over a finite field such as GF(28), where each byte position is treated as a polynomial evaluation or a row combination with a generator matrix. The runnable example below builds a Cauchy-matrix code and recovers a payload after dropping four of twelve shards.

Rule of thumb used in practice: replicate hot and small objects for latency and simplicity, erasure-code large and cold objects for cost. Many systems write replicas first and convert to erasure-coded stripes in the background once an object is sealed and cooling (Azure Storage's "lazy" erasure coding with local reconstruction codes is the public example; Ceph and HDFS also offer both modes).

Correctness verification

Disks fail loudly (a dead drive is obvious) and quietly (a flipped bit, a misdirected write, a torn sector). The defense is checksums: compute a hash of the bytes when you receive them, store it with the object, and verify on read and in a background scrubber that walks sealed files at low priority. Keep checksums at two levels: per object (end-to-end, so the client can compare too) and per file or chunk (so the scrubber can verify without parsing). With 8+4 coding, each chunk carries its own checksum, a read verifies the 8 chunks it fetched, and any mismatch is treated as an erasure: drop that chunk, decode from the others, and queue a repair. Use a fast non-cryptographic or hardware-assisted CRC for the scrubber and a stronger hash such as SHA-256 or an MD5 compatibility etag at the API layer. Checksum the request payload at the edge as well, since corruption can occur before the data store ever sees the bytes.

Deep Dive 3

The metadata store

Two logical tables carry the whole namespace: bucket (bucket id, name, owner, region, policy) and object (bucket id, object name, object id, version, size, checksum, creation time, user metadata). Queries to support: look up an object id by bucket and name; insert and delete by name; list objects in a bucket sharing a prefix.

Buckets per account are capped by policy, so the bucket table is small. A single replicated database handles it; scale read throughput with read replicas and caching. The object table is the one that explodes (billions of rows) and must be sharded.

Choosing the shard key

Shard keyUpsideDownside
bucket_idListing a bucket hits one shardHot-spot: one popular bucket may hold billions of objects and most of the traffic
object_idEven distributionAlmost every query is by name, not id, so we cannot route
hash(bucket_name, object_name)Even distribution; the dominant queries (get, put, delete by name) route to exactly one shardListing now spans all shards

The chosen key is the hash of bucket name plus object name, ideally with consistent hashing or a directory of virtual shards so you can split shards without rehashing everything.

Listing objects

On one database the listing is a range scan, WHERE bucket_id = ? AND object_name LIKE 'abc/%' ORDER BY object_name. When the table is hash-sharded, matching names are scattered everywhere, so a prefix listing means querying every shard and merging. Pagination gets ugly because each shard has a different number of matching rows; you need per-shard cursors and a k-way merge to return a globally sorted page. Two ways out:

  • Accept slow listing: object stores are not optimized for it and real services document listing as eventually heavier than point reads. Return keys in lexicographic order, max 1,000 per page, with a continuation token, which is how S3 does it.
  • Maintain a second, denormalized listing index sharded by bucket_id and sorted by name, updated asynchronously or in the same write path. A hot bucket becomes a hot shard for listing only, which is much cheaper than for gets. Split such a bucket's index by key range when it grows.

Hot key ranges. Sequential keys (timestamps, incrementing ids) concentrate writes on one shard of a range-partitioned index. Public S3 guidance has long advised spreading key prefixes for exactly this reason, and documents per-prefix request-rate limits that the service scales to as load grows. Hashing in the primary table avoids this; the sorted listing index is where it re-appears.

Versioning

With versioning on, the object table gains an object_version column, typically a time-ordered id (TIMEUUID or ULID), so a key's versions sort newest-first. Each PUT creates a new row with a new object id; the older versions stay. A plain GET returns the latest version; a GET with a version id returns that one. DELETE does not remove data: it inserts a delete marker as the newest version, a row pointing at a special tombstone object id, and a plain GET that hits it returns 404. Deleting a specific version id permanently removes that version. Undeleting is just removing the marker. Lifecycle rules then expire old versions to bound cost.

 key: report.pdf
   v3 (newest) : DELETE MARKER     -> GET report.pdf => 404
   v2          : object_id=9b1e...
   v1          : object_id=41ac...         -> GET report.pdf?versionId=v1 => 200
Deep Dive 4

Large uploads, garbage collection and compaction

Multipart upload

Uploading a 50 GB object in one HTTP request is fragile (any hiccup restarts everything) and slow (one TCP stream). Multipart upload splits the work:

  1. The client calls initiate; the service returns an upload_id.
  2. The client slices the file into parts and uploads them independently and in parallel, each tagged with the upload id and a part number. Each response carries an etag, a checksum of that part.
  3. The client calls complete with the upload id and the ordered list of (part number, etag).
  4. The service verifies the etags, stitches the parts into one logical object (often by recording an ordered list of part locations in the metadata rather than copying bytes, though finalizing can still take some time), writes the object row, and returns success.

For S3 specifically, parts are 5 MB to 5 GB (the last part may be smaller), up to 10,000 parts, and the final etag is the MD5 of the concatenated binary MD5s of the parts followed by a dash and the part count. The example computes exactly that. A failed part is retried alone; abandoned uploads leave orphan parts, which is where garbage collection comes in. Always add a lifecycle rule to abort incomplete multipart uploads after a few days; they silently accrue storage cost.

Garbage collection

Three kinds of garbage accumulate: lazily deleted objects (marked deleted but still occupying disk), orphans (bytes written for an upload that never got a metadata row, abandoned multipart parts, data from a crash between the data write and the metadata insert), and corrupted chunks that failed verification and were superseded by repaired copies. The collector also reclaims space on replicas: with three-way replication delete from the primary and both secondaries; with 8+4 coding delete all 12 chunks.

Compaction

Because data files are append-only and sealed, deleting an object cannot punch a hole in the middle of a file cheaply. Compaction rewrites files instead. The collector picks sealed files with a high garbage ratio, copies the live objects into a new file, updates the mapping rows to the new file and offsets in one database transaction, and only then deletes the old files. Run it in the background with an IO budget, and set a threshold so you do not keep producing lots of small files. Crash safety falls out of ordering: the new file is complete before the mapping commits, and until the commit the old file is still valid.

 before:  f1 [A][B][C][D]     B, D deleted        mapping: A,C -> f1
 copy:    f9 [A][C]                                         mapping: A,C -> f9   (txn commit)
 after:   f1 deleted, space reclaimed
Trade-offs

Decisions and what they cost

Metadata / data split

  • Scale each plane independently
  • Immutable data is simple to replicate and cache
  • Metadata fits a conventional sharded DB

What it costs

  • Two-step commit with an ordering to get right
  • Orphans and dangling pointers need GC and repair jobs
  • Metadata is the availability bottleneck

Append-only packed files

  • Sequential I/O, few inodes, no block waste
  • One seek per read with an index
  • Sealed files are easy to checksum and copy

What it costs

  • Deletes need compaction (write amplification)
  • Single writer per file needs core pinning
  • Index loss needs rebuild-by-scan support

Scaling and Production Gotchas

Things that bite after launch

  • Repair storms: when a rack disappears, naive re-replication can saturate the network and hurt customers. Prioritize groups with the fewest remaining copies and throttle the rest.
  • Erasure-coded read tail: a read of 8 chunks is as slow as the slowest. Hedged requests (ask 9 or 10, use the first 8) cut p99.
  • Small objects at scale: metadata cost per object is fixed, so a bucket with billions of 1 KB objects is expensive in metadata and request count even if it is tiny in bytes. Batching or aggregating in the application is often the right advice.
  • Pre-signed URLs and direct upload: push bytes straight to the data plane with a time-limited signed URL so the API tier is not a bandwidth proxy.
  • Hot objects: a viral object hammers three disks. Put a CDN or an object cache in front, and replicate hot data more widely.
  • Encryption: server-side encryption with per-object data keys wrapped by a KMS key; make sure crypto-erase is possible for compliance deletes.
  • Rolling upgrades and format evolution: data file and record formats outlive many software versions. Version every on-disk structure.
  • Cost control: lifecycle policies (transition to colder tiers, expire old versions, abort stale multipart uploads) matter as much as raw efficiency.
  • Bucket names and DNS: bucket names are a global namespace, so you need a strongly consistent create path (a single source of truth for names) and DNS-compatible naming rules if you support virtual-hosted-style URLs.
Wrap-up

What the design covered

We compared block, file and object storage; settled the API flows for bucket creation, upload, download, listing and versioning; and went deep on the data store (routing, placement, nodes, append-only files, object mapping), durability (replication, failure domains, erasure coding, checksums), the sharded metadata store, multipart upload, garbage collection and compaction. Code · Runnable

A data node, a Reed-Solomon code, and a multipart etag

One file, three ideas. DataNode appends objects into size-bounded files, keeps an offset index with a checksum per object, detects a flipped bit on read, and compacts sealed files by copying live records into a new file and swapping the index. rsEncode and rsDecode implement a true Reed-Solomon style erasure code over GF(28) with a Cauchy matrix (any k shards recover the data) and are exercised with the chapter's 8+4 layout. multipartEtag shows how the combined etag of a multipart object is derived. Only node:crypto and node:assert are used.

JavaScript Example 
// Object-store core: (1) append-only data files + offset index + checksums + compaction,
// (2) Reed-Solomon erasure coding over GF(256), (3) multipart etags.
import assert from 'node:assert/strict';
import { createHash, randomUUID } from 'node:crypto';

const md5 = (b) => createHash('md5').update(b).digest('hex');
const sha = (b) => createHash('sha256').update(b).digest('hex');

// ===== 1. Log-structured data node =====
class DataNode {
  constructor(maxFile = 64) { this.maxFile = maxFile; this.files = new Map(); this.active = 'f0'; this.files.set('f0', []); this.index = new Map(); this.n = 0; }
  put(bytes) {
    let f = this.files.get(this.active);
    if (f.reduce((s, r) => s + r.data.length, 0) + bytes.length > this.maxFile && f.length) {   // roll to a new file
      this.active = `f${++this.n}`; this.files.set(this.active, []); f = this.files.get(this.active);
    }
    const id = randomUUID();
    const offset = f.reduce((s, r) => s + r.data.length, 0);
    f.push({ id, data: Buffer.from(bytes), deleted: false });            // sequential append only
    this.index.set(id, { file: this.active, offset, size: bytes.length, sum: sha(bytes) });
    return id;
  }
  get(id) {
    const m = this.index.get(id); if (!m) return null;
    const rec = this.files.get(m.file).find((r) => r.id === id);
    if (sha(rec.data) !== m.sum) throw new Error('checksum mismatch: ' + id);   // bit-rot detection
    return rec.data;
  }
  delete(id) { const m = this.index.get(id); this.files.get(m.file).find((r) => r.id === id).deleted = true; this.index.delete(id); }
  compact() {                       // copy live records of sealed files into a fresh file, then swap the index
    const sealed = [...this.files.keys()].filter((k) => k !== this.active);
    const out = []; let off = 0;
    const name = `c${++this.n}`;
    for (const k of sealed) for (const r of this.files.get(k)) if (!r.deleted && this.index.has(r.id)) {
      out.push(r); this.index.set(r.id, { ...this.index.get(r.id), file: name, offset: off }); off += r.data.length;
    }
    sealed.forEach((k) => this.files.delete(k)); this.files.set(name, out);   // "transaction" commit
    return { reclaimedFiles: sealed.length, liveRecords: out.length };
  }
}

// ===== 2. Reed-Solomon (k data + m parity) over GF(2^8), poly 0x11d =====
const EXP = new Uint8Array(512), LOG = new Uint8Array(256);
for (let i = 0, x = 1; i < 255; i++) { EXP[i] = x; LOG[x] = i; x <<= 1; if (x & 256) x ^= 0x11d; }
for (let i = 255; i < 512; i++) EXP[i] = EXP[i - 255];
const mul = (a, b) => (a && b ? EXP[LOG[a] + LOG[b]] : 0);
const inv = (a) => EXP[255 - LOG[a]];
// Cauchy matrix rows: every square submatrix of [I; C] is invertible => any k shards rebuild the data.
const cauchy = (k, m) => Array.from({ length: m }, (_, i) => Array.from({ length: k }, (_, j) => inv((i + k) ^ j)));

function rsEncode(data, k, m) {                         // returns k+m equal-length shards
  const len = Math.ceil(data.length / k), shards = [];
  for (let i = 0; i < k; i++) { const s = Buffer.alloc(len); data.copy(s, 0, i * len, Math.min(data.length, (i + 1) * len)); shards.push(s); }
  for (const row of cauchy(k, m)) {
    const p = Buffer.alloc(len);
    for (let j = 0; j < k; j++) for (let b = 0; b < len; b++) p[b] ^= mul(row[j], shards[j][b]);
    shards.push(p);
  }
  return shards;
}
function rsDecode(shards, k, m, size) {                  // shards: array with `null` for lost ones
  const rows = [...Array(k).keys()].map((i) => Array.from({ length: k }, (_, j) => (i === j ? 1 : 0)));
  const C = cauchy(k, m); C.forEach((r) => rows.push(r));
  const have = shards.map((s, i) => (s ? i : -1)).filter((i) => i >= 0).slice(0, k);
  assert(have.length === k, 'not enough shards');
  const A = have.map((i) => [...rows[i]]), Y = have.map((i) => Buffer.from(shards[i]));
  const len = Y[0].length;
  for (let c = 0; c < k; c++) {                          // Gauss-Jordan elimination in GF(256)
    let p = c; while (A[p][c] === 0) p++;
    [A[c], A[p]] = [A[p], A[c]]; [Y[c], Y[p]] = [Y[p], Y[c]];
    const iv = inv(A[c][c]);
    A[c] = A[c].map((v) => mul(v, iv)); for (let b = 0; b < len; b++) Y[c][b] = mul(Y[c][b], iv);
    for (let r = 0; r < k; r++) if (r !== c && A[r][c]) {
      const f = A[r][c];
      A[r] = A[r].map((v, j) => v ^ mul(f, A[c][j])); for (let b = 0; b < len; b++) Y[r][b] ^= mul(f, Y[c][b]);
    }
  }
  return Buffer.concat(Y).subarray(0, size);
}

// ===== 3. Multipart upload: object etag = md5(concat(part md5 digests)) + "-" + partCount =====
function multipartEtag(parts) {
  const digests = Buffer.concat(parts.map((p) => createHash('md5').update(p).digest()));
  return `${md5(digests)}-${parts.length}`;
}

FAQ · Common Questions

Frequently Asked Questions

Why not store objects in a database or distributed file system?

A database makes every byte pass through a general-purpose engine tuned for small rows, and a distributed file system pays for hierarchical namespace semantics and in-place mutation you do not need. By restricting the model to immutable blobs and flat keys you unlock append-only layouts, erasure coding and trivially partitionable metadata, which is where the cost and scale advantage comes from.

How do you make sure an upload is either fully visible or not at all?

Write the data and make it durable first, then insert the metadata row as the single commit point. Readers only discover objects via metadata, so a half-finished upload is invisible. Crashes leave orphan bytes which a reconciliation job and the garbage collector remove after a safety delay.

Can you update part of an object?

Not in place. Objects are immutable. You upload a new object or version. For large objects, applications use multipart upload with a server-side copy of unchanged ranges, or they split data into many smaller objects so rewrites are cheap.

How would you handle a 5 TB object?

Multipart upload with, say, 10,000 parts of about 500 MB uploaded in parallel and retried individually. On the data side the object is stored as many chunks across many replication groups; the object row records the ordered chunk list, so reads can fetch ranges in parallel. Erasure code each chunk or stripe independently.

How do you rebalance when new nodes are added?

The placement service updates the cluster map and assigns new replication groups to the new nodes; existing groups can be migrated gradually by copying sealed files (immutable, so safe to copy while serving) and flipping the group membership. Consistent hashing with virtual nodes bounds how much moves.

Why is erasure coding hard in practice?

The math is the easy part. The cost is operational: partial-stripe writes, small objects, repair read amplification, hedged reads, placement constraints across 12 domains, and the CPU for encoding. That is why systems often start with replication and move cold data to erasure-coded stripes later.

Key Takeaway

Object storage is a metadata database married to a pile of append-only files. Commit metadata last, pack small objects together, spread copies or erasure-coded chunks across failure domains, checksum everything and scrub continuously, shard metadata by name hash with a separate listing index, and let compaction and garbage collection pay the deferred cost of immutability.
