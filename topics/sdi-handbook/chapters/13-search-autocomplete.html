Design a Search Autocomplete System

Typeahead has a brutal latency budget and a deceptively simple data structure. This chapter builds a system that returns the five most popular completions for a prefix in well under 100 ms, keeps the ranking fresh without updating anything in the hot path, and shards the index sensibly.

Every keystroke in a search box is a read request, and users abandon boxes that lag. Autocomplete is therefore a read-optimized system with an enormous read-to-write ratio: billions of lookups against a ranking that changes slowly. That asymmetry dictates the whole design: precompute the answer for every prefix, serve it from memory, and refresh the precomputation offline.

Core idea: split the system in two. A data gathering pipeline turns raw query logs into aggregated counts and builds a trie snapshot offline; a query service answers prefix lookups from an in-memory copy where each trie node already stores its own top-k list, so a lookup costs O(prefix length), not O(subtree size).

A public design to anchor on

Prefixy and the prefix hash tree

Two sources from the repo's reading list frame the problem space. The Prefixy engineering write-up describes a prefix-search service that stores completions in a key-value layer (MongoDB) keyed by prefix instead of keeping a literal tree in memory, trading a bit of space for horizontal scalability and simple operations. The Prefix Hash Tree paper (Berkeley) shows how to run prefix and range queries over a distributed hash table by hashing trie nodes onto the DHT. Both land on the same insight this chapter reaches: a trie is a logical model, and the physical layout can be a flat map from prefix to precomputed result.

Requirements

Scope and numbers

  • Match on the beginning of the query only (prefix match, not fuzzy or mid-string).
  • Return 5 suggestions, ranked by historical popularity.
  • Lowercase English letters to start; no spell correction.
  • Response in under roughly 100 ms; highly available and scalable.

Two honest observations. First, the 20-requests-per-search figure is an upper bound: clients debounce (wait 100 to 150 ms after the last keystroke) and cancel superseded requests, which commonly removes a large fraction of the traffic. Second, 0.4 GB/day of genuinely new query text is tiny; the index is small enough to fit comfortably in RAM on a handful of machines. The challenge is latency and QPS, not capacity.

High-level design

Two services, one precomputed table

WRITE PATH (offline, minutes to days) search logs ──▶ aggregators ──▶ frequency table ──▶ trie workers ──▶ trie DB │ snapshot READ PATH (online, tens of ms) ▼ keystroke ──▶ LB ──▶ API ──▶ trie cache (memory) ◀──── load/refresh ───── trie DB └─▶ filter layer ──▶ top-5 JSON ──▶ browser cache

The naive first version keeps one table of (query, frequency). Given a prefix tw, run SELECT query FROM freq WHERE query LIKE 'tw%' ORDER BY frequency DESC LIMIT 5. It works at small scale, and it is a good thing to say out loud first, because it makes the problem visible: with an index it still scans every match of a short prefix like t before sorting, and at 48,000 QPS that is a disaster. The fix is to stop computing the answer at request time.

Deep dive

The trie and the top-k trick

A trie stores strings by sharing prefixes: each edge is a character, each root-to-node path is a prefix, and nodes marking a complete query hold its frequency. Finding the prefix node is O(p) for prefix length p. The original approach then walks the whole subtree under that node collecting valid queries and sorts them to pick the top 5. For short prefixes the subtree is a large fraction of all queries, so the cost is O(p + c + c log c) where c is the number of descendants.

root ┌───┴───┐ t w ┌──┴──┐ └─ i ─ s ─ h wish o w │ ┌─┴──┐ y e i │ ┌─┴─┬──┐ e t n s t ├─ t─ e─ r ... twitter, twitch, twin, twist node "tw" caches: [ twitter 80, tweet 60, twitch 40, twilight 30, twin 22 ] ← answer is already here

Two optimizations remove the subtree walk entirely.

  • Cap the prefix length. Real queries are short; clamp stored and looked-up prefixes to a small constant such as 50 characters. Then finding the node is O(1) in effect, because p is bounded.
  • Cache the top-k at every node. During the offline build, each node stores the best five queries in its subtree. A lookup becomes: walk p characters, return the node's list. Time is O(p), and no sorting happens online.

The price is space. Each node holds up to k references, so memory grows by roughly a factor of k times the node count. Mitigations: store query ids instead of strings (the strings live once in a side table), and prune low-frequency leaves so rare queries are not indexed at all. A rare query will never be in any top-5 list except for its own very specific prefix, so you can often keep it out of the structure and fall back to a slower path or no suggestion.

Complexity summary: build is O(N · L · k) for N queries of length L (each insertion offers the query to L+1 ancestors, each keeps k entries sorted); lookup is O(p); memory is O(total nodes × k). The expensive work all lives in the offline build, which is exactly where you want it.

A subtle correctness point: when merging a child's top-k into its parent during a bottom-up build you can take the top-k of the union of the children's lists plus the node's own query. This is exact, not approximate, because anything in the parent's top-k must be in the top-k of the child subtree it came from.

Deep dive

Data gathering: why not update the trie live?

The simple design bumps a counter on every search. That is impractical for three reasons: billions of queries per day would hammer the structure with writes; the top five for a prefix rarely change between consecutive queries, so most updates are wasted; and a mutable shared trie under concurrent update is a lock-contention nightmare. Instead, the pipeline is batch:

  1. Analytics logs. Raw (query, timestamp) records appended in time order. Append-only, not indexed.
  2. Aggregators. Roll the logs into (query, time bucket, count). The bucket size depends on the product: a news or social app wants hourly or finer; a shopping site is fine with weekly. Use MapReduce, Spark or a streaming job such as Flink for the roll-up.
  3. Workers. Build a fresh trie from the aggregated counts and write it to the trie database.
  4. Trie cache. A distributed in-memory tier (Redis, Memcached or a process-local copy) loads the new snapshot and serves reads.

Rebuilding rather than mutating gives you immutable snapshots: the serving fleet loads version N+1 beside version N and flips a pointer, and rollback is a pointer flip back. It also means a bad build never corrupts the live index.

How the trie is stored durably

I favour the key-value form for serving. It turns the "tree" into a flat map, which is trivially shardable, cacheable and mirrors the Prefixy approach. The tree shape then exists only during the build.

Query service

The online request path

  1. The client sends the current prefix, for example GET /autocomplete?q=tw, to a load balancer.
  2. The API server looks up the prefix in the trie cache. A hit returns the stored top five immediately.
  3. On a miss it reads from the trie database and populates the cache.
  4. The filter layer removes suggestions that must not be shown.
  5. The five strings are returned as a small JSON array.

Client-side tricks that are worth as much as the server work

  • Asynchronous requests (XHR/fetch) so typing is never blocked.
  • Debounce and cancel in-flight calls when a new character arrives; drop out-of-order responses by tagging each request with the prefix it was for.
  • Browser caching. Autocomplete results for a prefix are stable, so a response header such as Cache-Control: private, max-age=3600 lets the browser answer repeated prefixes locally. Google's own suggestions are cached this way for about an hour.
  • Data sampling. At very high volume you can log only one in N requests for analytics; counts are statistically still correct and you save pipeline cost.
  • Prefetch on focus: serve the empty-prefix list (popular or personal recents) instantly.

Removing unwanted suggestions

Hateful, dangerous, legally contested or simply wrong suggestions must be removable quickly, and a weekly rebuild is far too slow. Put a filter layer between the trie cache and the client: a blocklist keyed by query (and pattern rules) that is checked on every response. The trie itself is cleaned later, asynchronously, when the next build excludes those entries. The filter layer also gives you per-region and per-policy rules without rebuilding anything. Because it can drop entries from a list of exactly k, store a few extra candidates per node (say k+3) so the response is still full after filtering; the code below shows the filtering step.

Code

Runnable core: trie with cached top-k, filter and decayed trending

The implementation builds a trie where every node keeps a sorted top-k list, answers prefix queries in O(prefix length), applies a read-time blocklist, rebuilds with an exponentially decayed score so recent surges outrank stale volume, and repeats the QPS arithmetic from above.

JavaScript Example 
// Autocomplete trie with top-k cached per node, weekly rebuild, filter layer, and decayed trending score.
import assert from 'node:assert/strict';

class Node { constructor() { this.kids = new Map(); this.top = []; } }  // top: [{q, score}] sorted desc, len<=k

class AutocompleteTrie {
  constructor(k = 5, maxPrefix = 50) { this.root = new Node(); this.k = k; this.maxPrefix = maxPrefix; }
  static build(freq, k = 5) {                                          // freq: Map(query -> count)
    const t = new AutocompleteTrie(k);
    for (const [q, c] of freq) t.#insert(q, c);
    return t;
  }
  #insert(q, score) {
    q = q.slice(0, this.maxPrefix);
    let n = this.root;
    this.#offer(n, q, score);
    for (const ch of q) {
      if (!n.kids.has(ch)) n.kids.set(ch, new Node());
      n = n.kids.get(ch);
      this.#offer(n, q, score);                                        // every ancestor keeps its own top-k
    }
  }
  #offer(n, q, score) {
    n.top.push({ q, score });
    n.top.sort((a, b) => b.score - a.score || (a.q < b.q ? -1 : 1));
    if (n.top.length > this.k) n.top.length = this.k;
  }
  suggest(prefix, blocked = () => false) {
    let n = this.root;
    for (const ch of prefix.slice(0, this.maxPrefix)) { n = n.kids.get(ch); if (!n) return []; }
    return n.top.filter(e => !blocked(e.q)).map(e => e.q);             // O(len(prefix) + k)
  }
}

const freq = new Map(Object.entries({
  tree: 10, try: 29, true: 35, toy: 14, wish: 25, win: 15, twitter: 80, twitch: 40, twilight: 30,
  twin: 22, twist: 12, tweet: 60, twelve: 9, tw: 5,
}));
const trie = AutocompleteTrie.build(freq);
console.log('tw   ->', trie.suggest('tw'));
console.log('twi  ->', trie.suggest('twi'));
console.log('t    ->', trie.suggest('t'));
assert.deepEqual(trie.suggest('tw'), ['twitter', 'tweet', 'twitch', 'twilight', 'twin']);
assert.deepEqual(trie.suggest('twi'), ['twitter', 'twitch', 'twilight', 'twin', 'twist']);
assert.deepEqual(trie.suggest('zzz'), []);

// filter layer: hide a query immediately at read time; physical delete happens at next rebuild
const hideTwitch = q => q === 'twitch';
console.log('tw (filtered) ->', trie.suggest('tw', hideTwitch));
assert.ok(!trie.suggest('tw', hideTwitch).includes('twitch'));

// weekly rebuild with exponential decay so recent queries outrank stale ones
const halfLifeDays = 7, decay = d => 0.5 ** (d / halfLifeDays);
const daily = [ // [query, ageDays, count]
  ['election results', 30, 1000], ['election results', 1, 50], ['eclipse today', 0, 400], ['eclipse today', 1, 300],
];
const scored = new Map();
for (const [q, age, c] of daily) scored.set(q, (scored.get(q) ?? 0) + c * decay(age));
const trending = AutocompleteTrie.build(scored);
console.log('e -> ', trending.suggest('e'), [...scored].map(([q, s]) => `${q}=${s.toFixed(1)}`));
assert.equal(trending.suggest('e')[0], 'eclipse today');

// back-of-envelope
const dau = 10e6, queriesPerUser = 10, charsPerQuery = 20, qps = dau * queriesPerUser * charsPerQuery / 86400;
console.log('avg QPS', Math.round(qps), 'peak', Math.round(qps * 2));
assert.equal(Math.round(qps * 2), 46296);
console.log('all assertions passed');

Run with node trie.mjs (Node 20+, no dependencies). It prints the top five for tw, twi and t, the filtered result with "twitch" hidden, the trending ranking (eclipse today beats the older, larger election volume), the average and peak QPS (23,148 and 46,296) and "all assertions passed". Executed and verified.

Scaling

Sharding the trie

Even though the data fits in memory on a few boxes, QPS and availability push you to replicate and shard. The obvious scheme is range sharding by first letters: a-m on one shard, n-z on another. It breaks quickly because letters are not evenly popular; far more queries begin with s than with x. Refine it in two steps.

  • Multi-letter ranges. Shard on the first two or three characters (aa-ag, ah-an), choosing boundaries from historical traffic so each shard receives similar load.
  • Shard map manager. A small, cached routing table maps prefix ranges to servers; the API tier consults it per request. Rebalancing means updating the map and moving the affected key range, which is much cheaper than rehashing everything.
request "tw…" ──▶ API ──▶ shard map: a-ag→S1 ah-an→S2 … t-tm→S9 tn-tz→S10 … │ ▼ S9 (replicas R1, R2, R3) ──▶ top-5 for "tw"

One catch: every prefix of a query lives on the shard that owns the query's early characters, so all prefixes of twitter land on the same shard and lookups never fan out. That is why sharding by leading characters is right here, whereas hashing the full query would scatter a single query's prefixes across the cluster. Hash-based placement (see consistent hashing) works only if you hash the prefix key itself, in which case each key lookup hits one node but hot short prefixes like a become single-key hot spots. Replicate or locally cache the first few levels everywhere; they are tiny and extremely hot.

Extensions

Multi-language and trending

Other languages. Store Unicode, not ASCII, which immediately changes the branching factor: a trie node over Chinese characters can have thousands of children, so use a map per node (or a compact radix tree) rather than a 26-slot array. Normalise input first (case folding, Unicode normalization form, accent stripping where appropriate) and decide whether to tokenise at the character, grapheme or word level; for scripts without spaces you may need a segmenter. Build separate tries per country or language so suggestions reflect local popularity, and route by the user's locale.

Real-time and trending queries. A weekly batch cannot surface an event that started an hour ago. Layer three techniques: shorten the aggregation window for a "recent" index; weight counts by recency with exponential decay (as the code does); and, for sharp surges, stream the logs through Kafka into a stream processor that maintains approximate counts (count-min sketch plus a top-k heap) and merges the trending list into the trie answer at read time. Capping how fast a query can climb prevents a spam burst from owning the box.

Personalization and relevance. Frequency is only a baseline. Mix in the user's own history, location, language and time of day, then re-rank the shortlist of candidates; keep personalization out of the trie and apply it as a small second stage so the shared index stays cacheable.

Production gotcha: privacy. Autocomplete is built from other people's queries, so a rare query typed by one person can leak. Apply a minimum-count threshold before a query enters the index, and never index queries that look like personal data (emails, phone numbers, ID numbers).

For a very different serving option, a search engine with a built-in completion suggester (an FST-based structure in Elasticsearch, see the existing Elasticsearch page) is a pragmatic choice when you already run one and do not need extreme QPS from a bespoke service.

Checklist

Before you leave the whiteboard

  • QPS computed with the arithmetic shown: 24,000 average, 48,000 peak.
  • Two services: offline data gathering and online query.
  • Trie with top-k cached at each node; prefix length capped.
  • Weekly (or shorter) rebuild into an immutable snapshot with rollback.
  • Trie stored as a snapshot or a prefix key-value map; cache in front.
  • Filter layer for takedowns; physical removal during rebuild.
  • Client debounce, cancellation and browser caching.
  • Range sharding with traffic-based boundaries and a shard map.
  • Plan for Unicode, per-locale tries and trending.
FAQ · Common Questions

Frequently Asked Questions

Why not just use a database index with LIKE 'prefix%'?

An ordered index handles the match, but you still have to rank every match by popularity, and short prefixes match a huge share of rows. At tens of thousands of QPS that sort is the bottleneck. Precomputing the answer per prefix moves the work offline.

How much memory does the cached top-k add?

Roughly k references per node. If you store 4-byte query ids rather than strings, k=5 adds about 20 bytes per node plus list overhead, which is modest compared to storing the strings themselves. Pruning rare queries from deep nodes shrinks it further.

How do you make suggestions fresh without rebuilding constantly?

Keep the big trie on a slow cadence and add a small, fast "recent" structure covering the last hour or so; merge its top results with the trie's at read time. This is the pattern used by lambda-style architectures: batch for accuracy, speed layer for freshness.

What if the user types a typo?

Prefix matching cannot recover. Add a spell-correction stage (edit distance over a dictionary, or learned from query reformulations in the logs) as a separate component that proposes corrected prefixes to look up. It is outside this chapter's scope but is the usual first follow-up.

Why shard by leading characters rather than hash the whole query?

All prefixes of a query share leading characters, so they stay together on one shard and each keystroke goes to one node. Whole-query hashing would scatter prefixes and force fanout. The cost is skew, handled by traffic-based boundaries.

How do you handle a suggestion that must disappear right now?

Add it to the blocklist consulted by the filter layer, which takes effect in seconds across the fleet. The next trie build omits it permanently and you can then drop the blocklist entry.

Key Takeaway

Autocomplete is a read-heavy problem solved by moving all computation offline. Aggregate logs into counts, bake the top-k answer into every trie node, serve a flat prefix-to-suggestions map from memory, shard by leading characters with traffic-aware boundaries, and use a filter layer plus a small recency index to cover the two things batch rebuilds cannot: takedowns and trending.
