Design Google Maps

Three systems in one: a write-heavy GPS ingest pipeline, a read-heavy static image (or vector) delivery network, and a graph search service that must answer in a second over a planet-sized road network. The unifying trick is tiling, applied to pixels, to roads and to cache keys alike.

A maps product looks like one application and is really three unrelated workloads sharing a coordinate system. Ingesting a billion people's positions is a streaming problem. Showing a map is a CDN problem. Finding a route is a graph problem. The skill the interviewer wants to see is whether you can tell them apart and give each its own storage and scaling model.

Core idea: divide the world into tiles at multiple zoom levels and use the tile ID as the universal key. Image tiles go to the CDN, routing graph tiles go to object storage and are loaded on demand by the pathfinder, and an in-flight trip is indexed by the tiles it crosses so that a traffic event can be matched to affected drivers with a key lookup.

A public design to anchor on

OpenStreetMap, Valhalla and slippy tiles

The open ecosystem makes the pieces visible. OpenStreetMap supplies raw road data as nodes, ways and tags. Open routers such as Valhalla preprocess it into hierarchical routing tiles (levels for highways, arterial roads and local streets) and load only the tiles a query touches, while OSRM uses contraction hierarchies instead. Rendering servers produce slippy-map tiles addressed as /{z}/{x}/{y}, increasingly as vector tiles (the Mapbox Vector Tile format is protobuf-encoded geometry) that the client draws. Google has said publicly that its ETA predictions combine historical and live traffic with machine-learning models, including graph neural networks. None of these systems routes over one global graph in memory; they all slice.

Map 101

The geography you need before designing

Coordinates and projection

Positions are latitude (north-south, -90 to 90) and longitude (east-west, -180 to 180). To draw on a flat screen you project the sphere onto a plane, and every projection distorts something: area, shape, distance or direction. Web Mercator, the variant used by Google and virtually every web map, preserves local shape (so streets look right at every zoom) but inflates area toward the poles, and it cuts off at about ±85.05 degrees latitude, which is why the map is a clean square. Never compute distances in projected coordinates; use great-circle maths for that.

Geocoding and reverse geocoding

Geocoding converts an address into coordinates; reverse geocoding does the opposite. Providers combine address-range interpolation along street segments (house 100 to 198 on this block, so number 150 lies about halfway along it), authoritative parcel or building data, and place databases. The output carries a precision class: rooftop, interpolated, street, locality. Surface that class; a "locality"-level match is not an address.

Geohash (and what maps actually use)

The chapter introduces geohashing as a recursive four-way split of the plane into a string (see the previous chapters). Strictly, web maps address tiles with the z/x/y scheme of the Mercator square (or an equivalent quadkey string where each digit 0 to 3 is a quadrant), not a base32 geohash. They are the same idea, recursive quartering with a prefix hierarchy, but the details differ and a client must reproduce them exactly. The example below uses z/x/y and quadkeys.

Tiles

Rendering the whole planet as one image is impossible, so it is cut into 256 by 256 pixel tiles per zoom level. Zoom 0 is one tile for the world; each zoom level doubles the resolution along each axis and so quadruples the tile count: 4z tiles at level z. The client downloads only the handful covering its viewport at its zoom and stitches them. Many modern clients use 512-pixel tiles at a lower zoom number to cut request counts on high-density screens.

Roads as a graph

Intersections are nodes; road segments are directed edges with attributes: length, speed limit, road class, turn restrictions, one-way flags, tolls, and a live traffic multiplier. Real routers add turn costs by modelling edges between edges, since a left turn across traffic takes longer than going straight. Dijkstra and A* are the base algorithms, but both degrade as the graph grows, which forces the tiling and hierarchy ideas below.

Requirements and numbers

Scope and sizing

Scope fixed by the interview: one billion daily active users; features are location updates, navigation with ETA, and map rendering; road data is terabytes from multiple sources and is available; traffic must be considered; modes include driving, walking and cycling; multi-stop routes, business listings and photos are out. Non-functional: accuracy (never send someone the wrong way), smooth rendering, low data and battery use on the client, plus ordinary availability and scale.

Location service

Clients record GPS fixes locally and send a batch every few seconds (the sizing used 15), as POST /v1/locations with an array of (lat, lon, timestamp) tuples. Batching saves radio wake-ups and battery, a stated non-functional goal, at the cost of delaying traffic data by up to one batch. For navigation this is acceptable because the on-device blue dot is driven by the local GPS stream; the server copy matters for aggregate traffic.

The storage requirement is extreme write throughput with no need for transactions or read-your-writes. Cassandra fits: partition key user_id, clustering key timestamp, so one user's trail is contiguous and time-ordered; availability is favoured over consistency since a newer ping makes the older one stale anyway. In parallel the same pings go to Kafka, which fans them out to independent consumers: a traffic updater, a routing-data improver (new roads appear as unmapped traces), a personalisation/ML pipeline, and analytics. Writing to Kafka first and consuming into Cassandra is an equally valid arrangement and makes ordering and replay uniform.

Navigation service

GET /v1/nav?origin=…&destination=…&mode=driving returns distance, duration, step-by-step instructions, an encoded polyline for drawing, and the geocoded waypoints (with a status and a "partial match" flag so the client can ask for disambiguation). Latency of a second or so is acceptable, accuracy is paramount. Traffic-aware rerouting while driving is handled in the deep dive.

Map rendering

The full tile set is petabytes, so clients fetch on demand according to position and zoom, when the user pans, zooms or drives into a new tile. There are two serving models: render per request (huge CPU, poor cache behaviour) or pre-render once and serve static objects with deterministic URLs. The chapter picks the second: tiles are named by z/x/y (the chapter says geohash, the principle is identical), stored in object storage and served through the CDN from a point of presence near the user. There are two ways for a client to find the URL:

  • Client computes the tile ID from lat/lon and zoom. Zero extra round trips and perfect cacheability, but the algorithm is baked into every shipped app for years because forcing upgrades is hard. Choose a standard scheme (z/x/y Web Mercator) you will never want to change.
  • Server computes it via a small tile-URL API. One extra call, but you can change schemes, shards and CDN hostnames at will. Fine as a hybrid: standard scheme with a server-provided URL template and version.

Zoom levels and tile counts

At the smallest zoom the whole world is a single 256 by 256 tile. Every increase by one splits each tile into four, so the count grows by 4x and the ground covered per pixel halves. Ground width of a tile at the equator is about 40,075 km divided by 2z: roughly 1.2 km at zoom 15, 305 m at zoom 17. Driving at 60 km/h (16.7 m/s), a driver crosses a zoom-17 tile in about 18 seconds, so a navigation client continuously prefetches the tiles ahead of the heading, and a client cache keyed on tile ID with LRU eviction avoids refetching on reverse and revisit.

Vector tiles

Instead of shipping rendered pictures, send geometry: roads as polylines, buildings as polygons, labels as points, packed in a compact binary format (for example protobuf), and let the client rasterise on the GPU. Benefits: far less bandwidth (paths compress much better than anti-aliased pixels), crisp rendering at any device density, smooth zoom between levels, rotation and tilt, and restyling (dark mode, route highlighting) with no new tiles. Costs: more client CPU/GPU work, a style engine on every platform, and harder debugging than "look at the PNG". Most modern map products use vector tiles for the base map and keep raster tiles for satellite imagery.

Deep dive 2

Routing: graph, tiles, hierarchy, A*

A planet-wide road network has hundreds of millions of nodes. Running Dijkstra from a source explores a disc of roads out to the destination's distance, which for cross-country trips is almost everything. Three standard techniques bring this under control.

  1. A* with an admissible heuristic. Prioritise nodes by cost_so_far + estimate_to_goal where the estimate is straight-line distance divided by the maximum plausible speed. Because it never over-estimates, the result is still optimal while the search is pulled toward the destination. The quality of the heuristic dominates: the example assumes 130 km/h while its toy grid streets run at about 60 km/h, so the estimate is loose and the 12 by 12 city still expands every node. A tighter per-region speed bound prunes far more.
  2. Partition the graph into routing tiles. Each tile stores the nodes and edges within a geographic cell plus references to neighbouring tiles at its borders. The pathfinder loads a tile only when the search reaches it, so memory and I/O are proportional to the corridor of the trip, not to the planet.
  3. Hierarchy of tile levels. A long journey does not need every residential street. Maintain several graphs: a fine level with all roads, a middle level of arterials, and a coarse level of highways. Search at fine detail near the origin and destination, and at coarse detail in between, switching down as the search approaches the ends. Valhalla builds exactly such a three-level tile set. Contraction hierarchies (used by OSRM) reach the same goal by adding precomputed shortcut edges.

The routing tiles are generated offline by a pipeline that ingests the raw road sources, cleans and merges them, builds the graph, assigns edges to tiles and levels, serialises each tile into compact binary form (adjacency lists compress well) and uploads the result to object storage. Hot tiles stay in memory on the pathfinder nodes via an LRU cache; cold ones are fetched from S3. Version tiles by build number so a deployment switches atomically.

The navigation pipeline

Route plannerOrchestrates: asks the shortest-path service for several candidate routes, asks the ETA service to price each under current traffic, and gives the set to the ranker.

ETA servicePredicts travel time per candidate using ML over live and historical traffic by road segment, time of day and day of week. Edge weights in the path search are the same travel-time estimates.

Two real-world details the notes skip. First, map matching: raw GPS is noisy by many metres, so the server (and client) snap traces onto the most probable road sequence using a hidden Markov model with Viterbi decoding; without this, traffic speeds are attributed to the wrong road, notably on parallel highway frontage roads. Second, traffic as an aggregate: a stream job groups matched points by road segment over a short window, takes a robust statistic (a median or trimmed mean, to resist the single parked phone), and publishes a speed to the traffic store; sparse segments fall back to historical profiles.

Deep dive 3

Adaptive ETA and rerouting

A route computed at departure goes stale: an accident, a closure or a sudden slowdown ahead changes the best path. To react without scanning every active trip, index the trips. A naive index stores, per navigating user, the list of every routing tile on the path (user_1: r1, r2, … rk). When an incident hits tile r2, query "who has r2" and recompute their routes. With millions of concurrent trips the lists are large.

The chapter's compression: store only the user's origin tile and its ancestors at progressively coarser levels, up to the level whose tile contains the destination: user_1: r1, super(r1), super(super(r1)), …. A user is possibly affected by an incident if the incident's tile lies inside the topmost stored ancestor (a super-tile containing the whole trip). That is a cheap necessary test with few false positives for long trips, then confirm with the actual path. In a quadkey scheme this is delightfully simple, because a tile's ancestors are the prefixes of its key. The example indexes each trip under every prefix of every path tile, which is the dual: look up the accident tile's key and you get exactly the trips whose paths cross it.

incident in tile 0230102033|3231 │ lookup keys: that tile and each ancestor prefix ▼ index[ "02301020333231" ] → {u1} (trip passes through this exact tile) index[ "0230102033" ] → {u1, u7, …} (trips touching the parent region: coarser candidates) │ for each candidate: re-run A* from current position with new weights ▼ push new route / "faster route available" over WebSocket

Beyond closures, a service can retain each navigating user's alternatives and notify them when a better one appears. Throttle: rerouting every minute is exhausting; require a minimum time gain (for example two minutes, or ten percent) before interrupting.

How to push the update to the phone

  • Mobile push notifications: payload limits are small (a few KB), delivery is not instantaneous, and web clients cannot use them. Fine for "your route changed", not for carrying a route.
  • Long polling: works anywhere but holds a server request per user and wastes resources at this scale.
  • WebSocket: bidirectional, lowest overhead per message; the chapter's preference, useful also for last-mile delivery features that need upstream messages.
  • Server-sent events: simpler (one-way, HTTP-based, auto-reconnect), a fine fit when only the server speaks; chosen against because bidirectional capability is valuable.

Why tiling everywhere works

  • Cache keys are deterministic
  • Work is proportional to the trip, not the planet
  • Hierarchy comes free from prefixes
  • Parallel, independent tile build jobs

What tiling costs

  • Edge effects at tile borders (features cut, paths cross tiles)
  • Format lock-in on clients
  • Rebuild and invalidate when data changes
  • Hierarchical routing can miss exact optimum
Runnable code

Tile math, tiled A*, and affected-user rerouting

The example implements Web Mercator lat/lon to z/x/y and quadkey conversion (checked against well-known reference values), builds a small grid city road graph with node coordinates, runs A* with an admissible great-circle heuristic, and then builds the prefix-based tile index over an active trip. A simulated accident is mapped to affected users by key lookup, edge weights are updated, and the reroute from the current position avoids the jam.

JavaScript Example 
// Map tiles (Web Mercator z/x/y + quadkeys), tile-partitioned A* routing, and affected-user lookup for rerouting.
import assert from 'node:assert/strict';

const TILE = 256;
const clampLat = lat => Math.max(-85.0511287798, Math.min(85.0511287798, lat));
function latLonToTile(lat, lon, z) {                       // slippy-map convention, Web Mercator
  const n = 2 ** z, x = Math.floor(((lon + 180) / 360) * n);
  const r = clampLat(lat) * Math.PI / 180;
  const y = Math.floor((1 - Math.asinh(Math.tan(r)) / Math.PI) / 2 * n);
  return { z, x: Math.min(x, n - 1), y: Math.min(y, n - 1) };
}
const quadkey = ({ z, x, y }) => { let q = ''; for (let i = z; i > 0; i--) { const m = 1 << (i - 1); q += ((x & m ? 1 : 0) + (y & m ? 2 : 0)); } return q; };
const tileUrl = t => `/tiles/${t.z}/${t.x}/${t.y}.pbf`;

// --- road graph: nodes carry coordinates; each node belongs to a leaf routing tile via quadkey ---
class RoadGraph {
  adj = new Map(); xy = new Map();
  node(id, lat, lon) { this.xy.set(id, { lat, lon }); this.adj.set(id, []); }
  road(a, b, seconds) { this.adj.get(a).push({ to: b, w: seconds }); this.adj.get(b).push({ to: a, w: seconds }); }
  setWeight(a, b, seconds) { for (const [u, v] of [[a, b], [b, a]]) this.adj.get(u).find(e => e.to === v).w = seconds; }
  tileOf(id, z = 14) { const p = this.xy.get(id); return quadkey(latLonToTile(p.lat, p.lon, z)); }
}
const rad = d => d * Math.PI / 180;
const km = (a, b) => 6371 * 2 * Math.asin(Math.sqrt(Math.sin(rad(b.lat - a.lat) / 2) ** 2 + Math.cos(rad(a.lat)) * Math.cos(rad(b.lat)) * Math.sin(rad(b.lon - a.lon) / 2) ** 2));

function astar(g, src, dst, maxKmh = 130) {                // admissible heuristic: straight line at top speed
  const h = n => km(g.xy.get(n), g.xy.get(dst)) / maxKmh * 3600;
  const dist = new Map([[src, 0]]), prev = new Map(), open = [[h(src), src]], closed = new Set(); let expanded = 0;
  while (open.length) {
    open.sort((a, b) => a[0] - b[0]); const [, u] = open.shift();
    if (closed.has(u)) continue; closed.add(u); expanded++;
    if (u === dst) break;
    for (const { to, w } of g.adj.get(u)) {
      const nd = dist.get(u) + w;
      if (nd < (dist.get(to) ?? Infinity)) { dist.set(to, nd); prev.set(to, u); open.push([nd + h(to), to]); }
    }
  }
  if (!dist.has(dst)) return null;
  const path = [dst]; while (path[0] !== src) path.unshift(prev.get(path[0]));
  return { path, seconds: dist.get(dst), expanded };
}

// grid city: 12x12 intersections, ~1 km apart, 60 s per block
const g = new RoadGraph(), N = 12, id = (r, c) => `n${r}_${c}`;
for (let r = 0; r < N; r++) for (let c = 0; c < N; c++) g.node(id(r, c), 37.70 + r * 0.009, -122.50 + c * 0.0113);
for (let r = 0; r < N; r++) for (let c = 0; c < N; c++) { if (c + 1 < N) g.road(id(r, c), id(r, c + 1), 60); if (r + 1 < N) g.road(id(r, c), id(r + 1, c), 60); }

// --- tests ---
const sf = latLonToTile(37.7749, -122.4194, 10);
console.log('SF z10 tile:', JSON.stringify(sf), tileUrl(sf), 'quadkey', quadkey(sf));
assert.deepEqual(sf, { z: 10, x: 163, y: 395 });                       // well-known slippy-map value
assert.deepEqual(latLonToTile(0, 0, 1), { z: 1, x: 1, y: 1 });
assert.equal(quadkey({ z: 3, x: 3, y: 5 }), '213');                    // Bing quadkey docs example
// ancestors are string prefixes -> hierarchy comes for free
const k14 = quadkey(latLonToTile(37.7749, -122.4194, 14));
assert.ok(k14.startsWith(quadkey(sf)));
// tile counts: 4^z; z21 pixel world
console.log('tiles at z21:', (4 ** 21).toLocaleString('en-US'), '| sum z0..z21 factor:', ((4 ** 22 - 1) / 3 / 4 ** 21).toFixed(3));

const r1 = astar(g, id(0, 0), id(N - 1, N - 1));
console.log(`route: ${r1.path.length} nodes, ${r1.seconds}s, expanded ${r1.expanded}/${N * N}`);
assert.equal(r1.seconds, 60 * 2 * (N - 1));

// register an active navigation: store origin tile + ancestor tiles at coarser zoom, per the "super tile" trick
const nav = { user: 'u1', path: r1.path };
const tileSet = new Set(); r1.path.forEach(n => { const k = g.tileOf(n, 14); for (let l = k.length; l >= 8; l--) tileSet.add(k.slice(0, l)); });
const index = new Map(); tileSet.forEach(t => (index.get(t) ?? index.set(t, new Set()).get(t)).add(nav.user));

// accident on a mid-route edge: jam it and find who is affected via the tile index
const [a, b] = [r1.path[10], r1.path[11]];
const hot = g.tileOf(a, 14);
const affected = [...(index.get(hot) ?? [])];
console.log('accident tile', hot, '-> affected users:', affected);
assert.deepEqual(affected, ['u1']);
g.setWeight(a, b, 3600);
const r2 = astar(g, r1.path[10], id(N - 1, N - 1));
console.log(`reroute from mid-trip: ${r2.seconds}s (was ${60 * (2 * (N - 1) - 10)}s clear) avoids jam:`, !r2.path.includes(b) || r2.path[1] !== b);
assert.ok(r2.seconds < 3600 && r2.path[1] !== b);
// a user in a far corner is not indexed under the jammed tile
assert.equal((index.get(g.tileOf(id(0, N - 1), 14)) ?? new Set()).size, 0);
console.log('all assertions passed');

Scaling and production

Knees and gotchas

  • Egress dominates again. Tile bytes, not routes, are the cost centre. Vector tiles, aggressive client caching, long TTL on immutable versioned URLs, and HTTP/2 or HTTP/3 multiplexing for the many small requests matter more than server optimisation.
  • Antimeridian and poles. Tiles wrap in x and are clamped in y; routes that cross longitude ±180 must handle wrap in both the heuristic and tile lookup.
  • Heuristic admissibility. A* with a heuristic that overestimates (for example assuming a top speed lower than some real road allows) silently returns suboptimal routes. Derive the speed bound from the data, per region.
  • Time-dependent edges. A road's cost depends on the hour, so true shortest path is on a time-dependent graph; predicted arrival time at each edge selects its weight. Many systems approximate with the departure-time profile.
  • Turn restrictions and one-ways are data bugs that become user-facing hazards. Treat road data quality as a first-class system with feedback from the location stream (many traces on a "one-way" the wrong way suggest an error).
  • Privacy. Location trails identify home and work. Aggregate for traffic, strip or rotate identifiers, apply k-anonymity thresholds on published speeds, and keep personal history opt-in with retention.
  • Battery and data. Sensor fusion, batching, adaptive GPS duty-cycling, delta-encoded polylines and compressed protobuf all serve the stated non-functional goal.
  • Multi-modal routing (walk, bike, transit) uses different graphs and weights; keep modes as separate tile sets rather than flags on one graph so each can evolve independently.
  • Multi-stop routing is the travelling salesman problem in disguise; heuristics (nearest neighbour, 2-opt, or OR-tools-style solvers) over a matrix of pairwise ETAs. It is the natural enterprise extension the chapter closes with, selling optimal ordering to delivery and ride-hailing platforms.

FAQ · Common Questions

Frequently Asked Questions

Why not store the road graph in a graph database?

The access pattern is "load a tile by key, run an in-memory search", not ad hoc traversals. Binary tiles in object storage are cheaper, trivially cacheable and faster to load. A graph database adds a query layer you never use and struggles at planetary size.

How is traffic incorporated into routing?

Streams of map-matched location points yield per-segment speeds that multiply or replace the static travel time on edges. The ETA service uses these plus historical patterns and predicts speeds for when the driver will actually be on each segment, not just now.

What happens to tiles when the road data changes?

An offline pipeline rebuilds only changed tiles, publishes a new data version, and the CDN URLs include the version, so new loads pick up fresh tiles while old clients keep working until their cache expires. No mass invalidation is needed.

How would you design offline maps?

Let users download region bundles: vector tiles for chosen bounding boxes and zoom ranges plus the routing tiles for the region and a geocoding index. Routing then runs on-device with static speed profiles, no live traffic.

Why is A* not enough by itself?

It reduces exploration but still scales with route length. Continental routes require hierarchy or precomputed shortcuts (contraction hierarchies, transit nodes) that answer in milliseconds after heavy preprocessing. The hierarchical tile levels in the chapter are the lightweight version of that.

How do you keep location batching from hurting rerouting?

Rerouting decisions use the server's latest batch plus on-device logic. The device itself detects that it left the route (off-route detection within a few seconds) and asks for a fresh route, so server-side reroute is only for incidents the device cannot know about.

Key Takeaway

Tile the world and reuse the tile ID everywhere: as the CDN key for map pictures, as the unit of routing-graph loading, as the hierarchy for coarse-to-fine path search, and as the index that finds drivers affected by an incident.
