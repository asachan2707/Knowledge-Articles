Design a Distributed Email Service

A Gmail-class mail system is mostly a storage and queueing problem wearing a protocol costume. Learn the send and receive pipelines, why the mailbox is partitioned by user, how search and deliverability fit in, and where the real cost lives.

Real systemsGmail, Bigtable, HBase, Cassandra, Elasticsearch, Kafka, S3, Postfix, Dovecot

Email is the oldest federated, store-and-forward messaging system still in daily use. Anyone can run a server, any server can talk to any other, and the whole thing works because of a handful of 1980s protocols that nobody dares break. Designing a Gmail-scale service means keeping that protocol surface at the edge and building a modern, partitioned, queue-driven backend behind it.

The interview framing is deceptively simple: users send, receive, fetch, filter, and search mail, with attachments. The depth is in three questions. How do you store a billion mailboxes so that reads are cheap and nothing is ever lost? How do you move mail between organizations reliably when the other side is flaky, hostile, or both? And how do you make sure the mail you send lands in an inbox rather than a spam folder?

Core idea: Every user's mailbox is an independent unit. Partition everything (metadata, search index, cache, real-time connections) by user_id, put durable queues between every stage of the send and receive pipelines, keep large blobs in object storage, and treat deliverability as a first-class product problem rather than an afterthought.

Background · How mail storage evolved

From one file per message to purpose-built mailbox stores

The classic Unix mail stack stored a mailbox either as a single append-only file (the mbox format) or as a directory with one file per message (D. J. Bernstein's Maildir, designed to avoid locking). Servers such as Postfix (SMTP) and Dovecot (IMAP) run happily on this for thousands of users per machine. Maildir fixed concurrency, but every message is still a file: an inbox with 100,000 messages is 100,000 inodes, listing requires directory scans, and a dead disk means dead mail unless you bolt on RAID and backups.

Large providers abandoned this model. Facebook publicly described building its Messages product on HBase (an open-source Bigtable clone) with attachments in a separate blob tier, and Google has described Bigtable as a general substrate for user-facing products. The common thread in these public designs is exactly what this chapter recommends: a wide-column, strongly consistent store keyed by user, with small hot metadata separated from large cold bytes.

Step 1 · Scope and Requirements

What we are building

The interviewer sets the target at one billion users. Functional scope: send and receive mail, fetch mail, organize into folders and filter by attributes (read or unread), full-text search, anti-spam and anti-virus, and attachments. Authentication is waved away, and clients talk HTTP to our servers rather than SMTP, IMAP or POP. We still speak SMTP between servers, because that is how the rest of the world delivers mail to us.

Non-functionalWhat it forces
ReliabilityOnce we acknowledge a message we must never lose it. Durable queue plus synchronous replication before the SMTP 250 OK.
AvailabilityReplicas everywhere, partial failure tolerated: a dead shard hurts only the users on it, never everyone.
ScalabilityMailboxes are independent, so horizontal partitioning by user works almost without cross-shard traffic.
FlexibilityHTTP/JSON between client and backend lets us add labels, snooze, smart replies, without negotiating a protocol extension with every mail client on earth.

Back-of-the-envelope

Read the numbers: the system is write-heavy in bytes but the writes are small and sequential per user. Attachments dominate raw capacity, which is why they live in an object store with erasure coding (see chapter 24). With 3x replication the footprint is north of 6 EB per year, which is why deduplicating identical attachments and tiering old mail to cold storage show up in every real design. Also note that the 50 KB figure per mail includes headers and bodies, and that inbound counts include mail you accept before spam filtering rejects it.

Step 2 · Email 101

Protocols and DNS you must know

ProtocolRoleNotes
SMTPServer-to-server transfer and client submissionPort 25 between MTAs, 587 (STARTTLS) or 465 (implicit TLS) for authenticated submission. Store-and-forward: a relay owns the message once it replies 250.
POP3Download mail from a serverTraditionally downloads and deletes. Single-device mindset.
IMAPRemote access to a server-side mailboxMail stays on the server; folders, flags, and server-side search; IDLE gives push-like notification.
HTTPSWeb and mobile clientsNot a mail protocol but the right choice for rich clients. This is our client API.

To find where to deliver mail for bob@gmail.com, a sending server queries DNS for the domain's MX records. Each record carries a hostname and a preference number; the sender tries the lowest number first and falls back to higher numbers. If no MX exists, SMTP falls back to the domain's A record. The code example below implements exactly this selection plus retry.

Alice (outlook.com client)          outlook.com MTA                gmail.com MTA             Bob
   |  SMTP submit                    |                              |                      |
   |------------------------------>|  DNS: MX gmail.com ?             |                      |
   |                               |  -> 5 gmail-smtp-in.l.google.com             |
   |                               |  SMTP: MAIL FROM / RCPT TO / DATA |                      |
   |                               |----------------------------->|  250 queued (durable)  |
   |                               |<-----------------------------|                      |
   |                               |                              |  store in Bob's box  |
   |                               |                              |<----- IMAP/HTTPS ----|

Three protocol facts shape the design. First, SMTP carries an envelope (MAIL FROM, RCPT TO) that is separate from the visible headers; Bcc recipients exist only in the envelope, so the sending pipeline must expand To, Cc and Bcc into one envelope recipient list and then strip Bcc from the stored copy that other recipients see. Second, attachments travel base64-encoded inside the MIME body, which inflates them by about one third, so a 25 MB cap on the encoded message means about 18 MB of actual file. Third, temporary failures (4xx) and permanent failures (5xx) must be told apart: the former are retried for days, the latter generate a bounce.

Step 2 · High-Level Design

From a single mail server to a distributed one

A traditional server bundles SMTP, mailbox storage on local disk, and IMAP/POP in one process on one machine. Disk I/O becomes the bottleneck as users grow, and the machine is a single point of failure. The distributed version keeps SMTP at the edge (other servers still deliver mail to us that way), replaces local files with a partitioned replicated store, and exposes a REST API for our own clients.

EndpointPurpose

GET /v1/folders/{id}/messagesPaginated message list of one folder; use a keyset cursor (the last email id), not offset
GET /v1/messages/{id}One message with headers, body, read flag, attachment references

Components and what each one owns

  • Web servers: stateless request/response tier for login, signup, profile, folder and message APIs. Scale by adding boxes behind the load balancer.
  • Real-time servers: hold WebSocket connections and push new-mail and state-change events. Fall back to long polling for clients that cannot upgrade. See WebSockets.
  • Metadata DB: headers, body text, flags, folder membership. Strongly consistent, partitioned by user.
  • Attachment store: an object store such as S3. Metadata rows keep only a reference.
  • Distributed cache: recently received and recently opened mail, because recency dominates access.
  • Search store: a per-user full-text index, fed asynchronously.

Email sending flow

  1. The client posts the message; the load balancer applies per-account rate limits (a compromised account is the number one source of outbound spam).
  2. A web server validates the payload: size, address syntax, attachment references already uploaded to object storage. It runs a cheap spam and abuse check on the way out.
  3. If every recipient is on our own domain, we short-circuit: skip SMTP entirely and drop the message into the incoming path (the receive pipeline) for those recipients. This is both faster and keeps internal mail off the public internet.
  4. Otherwise the message goes onto the outgoing queue; validation failures go to an error queue for inspection or an immediate bounce to the sender.
  5. SMTP out workers pull from the queue, run deeper spam and virus scanning, sign with DKIM, resolve MX, and open an SMTP session to the recipient's server. A copy is written to the sender's Sent folder.

Watch the queue depth. A growing outgoing queue means either the destination servers are down or throttling you (retry with exponential backoff and jitter, per-destination concurrency caps) or you simply have too few consumers (autoscale workers). Per-domain queues or per-domain concurrency limits prevent one slow destination from head-of-line blocking everything else.

Email receiving flow

  1. Inbound SMTP connections arrive at an SMTP load balancer and are spread across SMTP servers.
  2. The SMTP server applies the acceptance policy at connection time: unknown recipient, blocklisted IP, failed SPF, over-size message. Rejecting during the SMTP dialogue is far cheaper than accepting and bouncing later, and avoids backscatter.
  3. Large attachments are written straight to object storage; the rest of the message is enqueued on the incoming queue. Only after the queue write is durable does the server reply 250.
  4. Mail processing workers consume the queue: virus scan, spam classification, user filters and labels. They then write to the metadata DB, the cache, the search pipeline, and notify the real-time tier.
  5. Online users get a push; offline users pick the mail up via the HTTP API on next sign-in.

At-least-once consumption means workers may process a message twice after a crash, so processing must be idempotent: derive the mail's id deterministically from the envelope id and recipient, and make inserts upserts. See idempotency.

Deep Dive 1

The metadata database

Workload characteristics

  • Headers are small and read constantly (every inbox render). Bodies range from a line to megabytes but are typically opened once.
  • Almost every operation touches one user's data only: fetch, mark read, move, search. There is essentially no cross-user transaction.
  • Recency drives access: the last few weeks of mail get nearly all the reads, so hot and cold tiers pay off.
  • Durability requirement is absolute. A lost email is a headline.

Choosing a store

OptionFitsMisses
Relational (sharded MySQL/Postgres)Rich indexes and transactions; trivial to filter unreadTuned for small rows; multi-MB bodies hurt buffer pools and replication; resharding a billion accounts is painful
Distributed object storeCheap, durable, great for blobs and backupsNo cheap "mark as read", no ordered folder listing, no per-message mutation
Wide-column NoSQL (Bigtable, HBase, Cassandra)Partition by user, sort by time, massive write throughput, LSM-friendlyLimited secondary indexes; filtering on non-key columns is off the table; Cassandra is tunable-consistency, Bigtable and HBase are strongly consistent per row

No off-the-shelf product ticks every box, which is why the biggest providers build their own. In an interview you do not design a database; you state the properties you need: values up to a few MB per cell, strong consistency, minimal disk I/O per operation, high availability with fault tolerance, and easy incremental backup. Then you use a wide-column model as the working assumption.

Data model

The partition key is user_id, so a mailbox is co-located and every query is single-partition. The clustering key orders rows inside the partition. The price is that you cannot share one stored copy of a message among multiple users; each recipient gets their own row. That is a deliberate choice: a mailbox is private state (read flags, labels, deletion are per user), and copy-per-recipient keeps deletion and legal holds simple.

folders        PK ((user_id), folder_id)          name, ...
emails         PK ((user_id), folder_id, email_id)   email_id = timeuuid, sorted DESC
                 from, to[], subject, body, is_read, preview, attachment_count, headers
attachments    PK ((email_id), filename)             size, object_key (-> object store)
read_emails    PK ((user_id), folder_id, email_id)   denormalized copy
unread_emails  PK ((user_id), folder_id, email_id)   denormalized copy
  • timeuuid for the email id: embeds the creation timestamp, so the clustering order is "newest first" for free and a page cursor is just the last id seen.
  • Read/unread denormalization: a wide-column store forbids filtering on a non-key column (or makes it a scan). Instead of scanning a folder and filtering in memory, maintain two tables and move a row between them when the flag flips. Both live in the same partition, so the pair of writes is a cheap single-partition batch. The runnable example mirrors this with two sets.
  • Threads: clients rebuild conversations from the Message-Id, In-Reply-To and References headers. Store those, and compute the thread grouping either at read time (cheap for one folder page) or at ingest by resolving to a thread id (better for counts).
  • Label model: the folders table is the simple answer. Gmail-style multi-label means one message is in several "folders", which in this model is several clustering rows pointing at one body; mention it as an extension.

Hot and huge partitions. One user with ten years of mail is a very wide partition, and compaction and repair on wide partitions are painful. Practical mitigations: bucket the clustering key by time ((user_id, month)), keep bodies above a size threshold in the object store and only a pointer in the row, and cap list endpoints. Also expect a few shared mailboxes (support@, newsletters) that are orders of magnitude hotter than normal users.

Consistency versus availability

By the CAP trade-off we pick consistency. A user who marks a message read, refreshes, and sees it unread again perceives a bug; a deleted mail reappearing is worse. The cost is that during a failover or partition, writes for the affected partitions are briefly unavailable. Because partitions are per user, the blast radius is a slice of users, not the service. Put the leader of each partition in a datacenter close to the user, replicate synchronously to at least one other failure domain before acknowledging, and replicate asynchronously across regions. See CAP theorem and consistency models.

Deep Dive 2

Email deliverability

Standing up an SMTP server is an afternoon of work. Getting a major provider to put your mail in the inbox is a reputation game. Recipient systems assume unknown senders are spammers until proven otherwise.

LeverWhat it does
Dedicated sending IPsReputation is tracked per IP and per domain. Shared IPs inherit their worst neighbour's sins.
Traffic segregationPut transactional mail (password resets, receipts) on separate IPs and subdomains from marketing blasts so complaint rates on one do not poison the other.
IP warm-upRamp volume gradually over roughly two to six weeks so large providers learn you are consistent and wanted.

Interview posture: you are not expected to recite the RFCs. Name the families (reputation, authentication, feedback, hygiene), show that you know a cold IP lands in spam, and say the service needs a dedicated deliverability function with dashboards and a bounce-processing pipeline.

Deep Dive 3

Search

Email search differs from web search in ways that change the architecture. It is scoped to a single mailbox; results are sorted by attributes such as date rather than relevance; users expect their newest mail to be searchable immediately and results to be accurate; and the write-to-read ratio is inverted: every incoming mail, label change and read flag causes an index update, yet most users search rarely.

Web searchMailbox search
ScopeThe whole webOne user's mail
SortingRelevanceTime and attributes (from, to, subject, unread, has attachment)
FreshnessMinutes to hours is fineNear-instant and precise
WorkloadRead-heavyWrite-heavy, with spiky reads

Option A: Elasticsearch

Run an Elasticsearch cluster and route documents by user_id (custom routing) so one user's documents sit in one shard and a query hits a single shard instead of fanning out. Mutations are written to the primary metadata DB first and then published to Kafka; an indexer consumes the stream and updates Elasticsearch asynchronously, decoupling mail ingestion latency from index health. Queries go to the index synchronously. Typical gotchas: index lag means "I just got that mail, why can't I find it?" (mitigate by also checking the last few minutes of mail in the primary store), and mapping many users into shared indices needs care so one giant tenant does not become a hot shard. See Elasticsearch.

Option B: a custom engine on an LSM tree

Because the workload is write-dominated, a log-structured merge tree is a natural fit. Writes go to an in-memory memtable (plus a write-ahead log), the memtable is flushed to immutable sorted files when it fills, and background compaction merges levels. All disk writes are sequential. This is the design behind Bigtable, Cassandra, and RocksDB. A custom index can even live inside the mailbox store itself, so a single system holds both mail and its index with no sync pipeline.

DimensionElasticsearchCustom LSM-based
Time to buildDays, off the shelfMany engineer-years
Operational surfaceAnother cluster to run, upgrade, and keep consistent with the DBOne system; the index is part of the store
Scale ceilingHigh but eventually hits cluster-state and shard-count limitsTuned for per-user shape, scales further
Consistency with source of truthEventual via the Kafka pipeline; needs reconciliation jobsCan be transactional with the mail row

The sensible recommendation: start with Elasticsearch, keep the indexing pipeline replayable from the mail log, and revisit a custom engine only when cost or latency data justify it.

Deep Dive 4

Scalability, availability and real-time delivery

Because users do not interact with each other's stored data, almost every tier scales independently: web servers are stateless, queues are partitioned, workers are stateless consumers, the DB and search index are keyed by user, and the cache is sharded by user. Compose them into cells: a cell is a self-contained slice (a few million users with their own DB shard, cache, index and workers). A directory service maps user_id to a cell. Cells give you a bounded blast radius, a unit of capacity planning, and an easy way to move users when you rebalance.

          Global router: user_id -> (primary DC, cell)
                   |                         |
          DC-East (leader)              DC-West (follower)
      DB shard A  ---- sync/async repl ---->  DB shard A'
      Search idx  ---- rebuilt from log ----> Search idx'
      Queues      ---- mirrored ------------> Queues'
         failover: promote follower, route users of the failed cell, accept brief write unavailability

For the real-time path, a user holds one persistent connection to some real-time server. A small presence map (user to server) lets a mail-processing worker publish "new mail for user X" to the right box; if the user is offline nothing is pushed and the next HTTP sync catches up using the last-seen email id as cursor. Keep push payloads tiny (a signal, not the mail) so a lost event is harmless: the client always reconciles through the API.

Cache policy: write-through the newest few hundred headers per user into Redis at ingest, evict with LRU, and treat the cache as disposable since the DB is authoritative. See caching.

Trade-offs

Decisions and what they cost

Partition by user_id

  • Every query is single-partition
  • Search, cache and connections shard the same way
  • Failure and migration blast radius is small
  • Simple per-user export, delete, and legal hold

What it costs

  • No shared single copy of a mail sent to many recipients (storage amplification)
  • Hot and huge mailboxes need special handling
  • Cross-user features (shared inbox, delegated access) need extra modeling

Queues between every stage

  • Absorbs spikes and destination outages
  • Independent scaling of workers
  • Natural retry and dead-letter handling

What it costs

  • At-least-once means idempotent consumers
  • Latency from queueing and multi-stage scanning
  • More moving parts to monitor

Scaling and Production Gotchas

Things that bite after launch

  • The 250 OK contract: after you reply 250 to a sender you are responsible for the message. Replicate it durably before replying, and if you must shed load return a 4xx before accepting, never drop after.
  • Greylisting and retry storms: many senders retry on fixed schedules, producing synchronized thundering herds when you recover from an outage. Rate-limit accepting and let the senders' own backoff spread.
  • Mailbox size distribution is heavy-tailed: median users are small, the top 0.1% are enormous. Plan for them explicitly with bucketed partitions and quota enforcement.
  • Deletion is a pipeline: removing a message touches metadata, cache, search, object store, and backups. Use tombstones and an asynchronous reaper, and keep a recoverable window (trash for 30 days is a common product choice).
  • MIME is hostile input: nested multipart bombs, malformed encodings, giant headers. Parse in sandboxed workers with strict limits, and never render HTML mail without sanitization (remote images are a tracking and exploit vector).
  • Unicode and addresses: internationalized addresses, case-insensitive local parts by convention, plus-addressing; normalize before keying anything.
  • Migration cost: moving a user between cells means copying a possibly multi-GB mailbox while it is live. Do it with dual-writes and a catch-up log, not a stop-the-world copy.
Wrap-up Topics

Extras worth mentioning if time allows

  • Fault tolerance: walk through each box and say what happens when it dies. Queues and replicated stores should make every answer "retry, no loss".
  • Compliance: mail is full of personal data. Under GDPR-style rules you need deletion that reaches every copy (including search indexes, caches and backups), data residency by region, and audit logging for access.
  • Security: TLS in transit, encryption at rest with per-user or per-tenant keys, phishing and malware detection, safe-browsing link checks, account-takeover detection.
  • Optimizations: deduplicate identical attachments by content hash (a mail sent to a mailing list should store one blob with a reference count), compress old mail, tier cold mail to cheaper storage, and pre-compute thread and preview data at ingest.
Code · Runnable

A mailbox core you can run

The example below implements four ideas from the chapter: a per-user partitioned store with time-ordered ids and keyset pagination, the denormalized unread view, thread reconstruction from Message-Id/In-Reply-To/References using union-find, and outbound delivery that tries MX hosts by preference with full-jitter exponential backoff between rounds. It uses only Node built-ins.

JavaScript Example 
// Mini mail core: per-user partitioned mailbox, denormalized read/unread views,
// thread reconstruction from headers, and MX-priority delivery with backoff.
import assert from 'node:assert/strict';

// ---- 1. Time-ordered ids (stand-in for Cassandra timeuuid): ms timestamp + sequence.
let seq = 0;
const timeId = (ts) => `${String(ts).padStart(13, '0')}-${String(seq++).padStart(6, '0')}`;

// ---- 2. Mailbox store. Partition key = userId, clustering key = emailId (newest first).
class MailStore {
  constructor() { this.byUser = new Map(); }
  #p(u) {
    if (!this.byUser.has(u)) this.byUser.set(u, { emails: new Map(), unread: new Set(), read: new Set(), folders: new Map() });
    return this.byUser.get(u);
  }
  put(userId, folder, msg, ts) {
    const p = this.#p(userId);
    const id = timeId(ts);
    p.emails.set(id, { id, folder, isRead: false, ...msg });
    // denormalized "tables": (folder, read-state) -> ids, so no filter-on-read is needed
    p.unread.add(id);
    if (!p.folders.has(folder)) p.folders.set(folder, new Set());
    p.folders.get(folder).add(id);
    return id;
  }
  markRead(userId, id) {            // batch of 2 writes, both inside ONE partition
    const p = this.#p(userId);
    p.emails.get(id).isRead = true;
    p.unread.delete(id); p.read.add(id);
  }
  list(userId, folder, { unreadOnly = false, limit = 50, before = '\uffff' } = {}) {
    const p = this.#p(userId);
    const ids = [...(p.folders.get(folder) ?? [])]
      .filter((id) => id < before && (!unreadOnly || p.unread.has(id)))
      .sort().reverse().slice(0, limit);       // newest first, keyset pagination via `before`
    return ids.map((id) => p.emails.get(id));
  }
  get(userId, id) { return this.#p(userId).emails.get(id); }
}

// ---- 3. Thread reconstruction using Message-Id / In-Reply-To / References.
function buildThreads(messages) {
  const parent = new Map();                          // union-find over message-ids
  const find = (x) => { while (parent.get(x) !== x) { parent.set(x, parent.get(parent.get(x))); x = parent.get(x); } return x; };
  const add = (x) => { if (!parent.has(x)) parent.set(x, x); };
  for (const m of messages) {
    add(m.messageId);
    for (const ref of [m.inReplyTo, ...(m.references ?? [])].filter(Boolean)) {
      add(ref); parent.set(find(ref), find(m.messageId));
    }
  }
  const threads = new Map();
  for (const m of messages) {
    const root = find(m.messageId);
    (threads.get(root) ?? threads.set(root, []).get(root)).push(m.subject);
  }
  return [...threads.values()];
}

// ---- 4. Outbound delivery: try MX hosts by ascending priority, exponential backoff w/ full jitter.
async function deliver(mxRecords, send, { maxAttempts = 5, base = 100, cap = 5000, rand = Math.random, sleep } = {}) {
  const hosts = [...mxRecords].sort((a, b) => a.pref - b.pref);
  const waits = [];
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    for (const mx of hosts) {
      try { await send(mx.host); return { ok: true, host: mx.host, attempt, waits }; }
      catch { /* try next MX in the same round */ }
    }
    const w = Math.floor(rand() * Math.min(cap, base * 2 ** attempt)); // full jitter
    waits.push(w); await sleep(w);
  }
  return { ok: false, waits };                       // caller moves it to the dead-letter / bounce path
}

FAQ · Common Questions

Frequently Asked Questions

Why not store each recipient's mail as a reference to one shared copy?

It saves space for mailing lists but couples users: read state, labels and deletion are per user, retention and legal holds differ, and a shared row becomes a hot spot. The usual compromise is per-recipient metadata rows with shared immutable blobs (attachments, large bodies) deduplicated in the object store by content hash with reference counting.

How do you guarantee an email is never lost?

Define the ownership hand-offs. Inbound: do not reply 250 until the message is persisted to a replicated queue or store. Internal stages: acknowledge a queue message only after the next durable write. Outbound: keep retrying with backoff for days, and generate a bounce if you give up. Storage: synchronous replication in the shard plus asynchronous cross-region copies and periodic verified backups.

How do you make the pipelines idempotent?

Derive a stable id from the envelope (for example a hash of the queue message id and recipient) and use it as the clustering key or an upsert key. Re-running the worker overwrites the same row. For the outbound side, keep the message id in the send record so a retry after a lost acknowledgment does not enqueue a second SMTP delivery.

How do you show unread counts cheaply?

Keep a counter per (user, folder) updated when messages move between the read and unread tables, or count the unread partition slice with a cap (show "99+"). Counters drift under retries, so recompute periodically from the table as the source of truth.

Why use Kafka for indexing rather than writing to Elasticsearch directly?

The index is a derived view. Writing it from the request path ties mail acceptance to index health and gives you dual-write inconsistency. A log decouples them, lets you rebuild indexes by replay, and absorbs reindex storms (for example after a mapping change).

How would you add conversation view and labels?

Store thread id at ingest (resolve via References/In-Reply-To, fall back to normalized subject plus participants), and model labels as additional clustering rows or a set column plus a denormalized per-label table. Every extra index is another write, so budget write amplification before adding it.

Key Takeaway

A distributed email service is a set of independent per-user mailboxes joined by durable queues. Partition by user, keep blobs in object storage, choose consistency for mailbox state, index asynchronously, and invest as much in sender reputation as in storage. The protocol work is at the edge; the engineering work is in never losing a message you have acknowledged.
