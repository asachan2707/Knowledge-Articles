Design a Chat System

A chat system is a connection-management problem wearing a messaging costume. This chapter builds 1:1 and group chat for 50M daily users with durable history, multi-device sync and presence, and spends its depth where the real difficulty is: millions of long-lived sockets, ordering, and fanout.

Almost every other system in this handbook is request/response: the client asks, the server answers, and you can scale by adding stateless boxes. Chat breaks that model. Messages must be pushed to a receiver who never asked, and to push you must remember which of millions of sockets belongs to which user. The whole design is about taming that statefulness.

Core idea: keep exactly one tier stateful (the chat servers holding WebSocket connections), make everything else stateless, give every channel its own monotonically increasing message id, and let each device pull "everything after my last id" so that delivery, reconnects and multi-device sync collapse into a single mechanism.

A public design to anchor on

How Discord stores billions of messages

Discord has written publicly about moving its message store from MongoDB to Cassandra and later to ScyllaDB. The shape of the data is the lesson: messages are partitioned by channel (plus a time bucket so a busy channel does not create one unbounded partition) and clustered by a time-sortable id, so "the latest 50 messages in this channel" is a single-partition range read. That is exactly the (channel_id, message_id) key this chapter arrives at, and the reason a wide-column or key-value store beats a relational table with a giant secondary index for this workload. Slack's Flannel, listed in the sources below, solves the other half: an application-level edge cache so a client booting into a huge workspace does not fetch the whole member list.

Requirements

What we are building

  • One-on-one chat and group chat capped at 100 members.
  • Text messages, up to 100,000 characters each (large enough that you must think about row size and not assume tiny payloads).
  • Online/offline presence indicator.
  • Multiple devices per user, all converging on the same history.
  • Push notification when the recipient is not connected.
  • 50 million daily active users; chat history stored permanently; low latency delivery.

The shape matters more than the digits. Write rate is modest by internet standards; the hard numbers are 10 million idle-but-open connections and the fanout multiplier on groups. A single well-tuned box can hold hundreds of thousands of idle sockets, but keeping headroom for reconnect storms is why you plan at a fraction of that.

Transport

Getting messages to the receiver

Sending is easy: an ordinary HTTP request over a keep-alive connection works, and plenty of production systems send over plain HTTPS. Receiving is the problem, because HTTP is client-initiated. Three options exist.

TechniqueHow it worksCostVerdict
Short pollingClient asks "anything new?" every N secondsMost responses empty; latency up to N seconds; huge request volume from idle usersFine for a prototype, wasteful at scale
Long pollingServer holds the request open until a message arrives or a timeout firesEach delivery needs a re-request; the sender and receiver often land on different servers; connection churn even for silent usersReasonable fallback behind restrictive proxies
WebSocketOne HTTP Upgrade handshake, then a bidirectional framed TCP channelStateful: server must track every open socketDefault choice for both directions
Short poll C ──?──▶ S ──none──▶ C ──?──▶ S ──none──▶ C ──?──▶ S ──msg──▶ C Long poll C ──?──▶ S ·········(held)·········──msg──▶ C ──?──▶ S ··· WebSocket C ══ Upgrade ══▶ S ◀══ msg ══ ══ msg ══▶ ◀══ msg ══ (one TCP connection)

WebSocket's cost is operational, not conceptual. The connection is long-lived, so deploys, load balancer idle timeouts and NAT timeouts all become your problem. Run application-level pings so intermediaries do not silently drop a quiet socket, and have the client reconnect with jittered exponential backoff; without jitter, a chat-server restart turns into a synchronized reconnect stampede from every client it held.

Practical note: ship a long-polling or HTTP fallback anyway. Some corporate proxies still break Upgrade, and mobile OSes aggressively kill background sockets, which is why push notifications are not optional but a core part of the delivery path.
High-level design

Stateless where possible, stateful where forced

Split the system by whether it needs to remember a connection.

  • Stateless tier (behind a normal load balancer): signup, login, profile, friend and group management. These are ordinary REST services and scale by adding instances. A service-discovery component also lives here; it hands a freshly logged-in client the address of a chat server.
  • Stateful tier: the chat servers. Each holds the WebSocket connections of the users assigned to it and a local map from user id to socket.
  • Presence servers: track who is online.
  • Notification path: hands messages for offline users to APNs/FCM (see the notification system chapter).
  • Message store: a key-value or wide-column database holding all history.
stateless stateful client ──HTTPS──▶ LB ──▶ API servers (login, profile, groups) │ │ │ service discovery ──▶ "use chat-server-17" │ └────WebSocket────────────▶ chat servers ◀─────▶ message KV store │ │ │ └────▶ presence servers └───────────▶ push notification (APNs / FCM) when offline

Why a key-value or wide-column store for history

The access pattern is overwhelmingly "append to a channel" and "read the tail of a channel, occasionally page backwards." There are no joins and no ad hoc queries on the hot path. Relational databases can do this, but the long tail hurts: months-old conversations are rarely read, so their index pages are cold, and a random read against a very large B-tree index becomes a disk seek. A partitioned store like Cassandra or HBase keeps each channel's messages contiguous on disk, scales by adding nodes, and gives predictable single-partition latency. Messenger and Discord both run on stores of this family. Search over history is a separate concern; feed messages into an inverted index such as Elasticsearch rather than abusing the primary store.

The message id has two jobs: be unique and encode order, because created_at alone is unsafe (two messages can share a millisecond). How global does the id have to be? Not at all. You only need a total order within a channel; no one compares message 7 of channel A with message 9 of channel B. So a per-channel counter is sufficient, and it is cheaper than a globally coordinated Snowflake-style id (see the unique-id chapter), though a Snowflake id works too and gives you a time-sortable key without a per-channel sequencer. The trade is below.

Id strategyProsCons
Per-channel counterDense, small ids; gaps are detectable (a client can see that id 8 is missing); cheap ordering proofNeeds a single writer per channel (or a CAS) to hand out the next number; counter state to recover
Global time-sortable id (Snowflake)No coordination on the hot path; any chat server can mint oneOrder within a channel depends on clock quality; cannot detect gaps; larger ids
Deep dive

Service discovery: which chat server do I talk to?

After login the client needs one chat server. A discovery service (the classic answer is Apache ZooKeeper, with etcd and Consul as modern equivalents) maintains a registry of live chat servers and picks one using geography and current load. The flow is: client authenticates, the API tier asks discovery for the best server, the client opens a WebSocket to it. If that server dies, the client asks again.

An opinionated note: do not pick by pure round-robin, because connection count and bandwidth, not request rate, define load for a socket server. Pick by connection count with some randomness (power-of-two-choices works well), and drain a server by refusing new assignments before a deploy so connections migrate gradually. See the service discovery and load balancing pages.

One-on-one flow

A's device ──ws──▶ Chat server 1 │ 1 assign message id (per channel) │ 2 persist to KV store ◀ persist BEFORE you deliver │ 3 publish to B's inbox / message-sync queue ▼ B online? ──yes──▶ Chat server 2 ══ws══▶ B's device └───no───▶ push notification service ──▶ APNs / FCM

The ordering of steps is the reliability guarantee. If you deliver before persisting and the server dies between the two, the receiver saw a message the history never recorded. Persist first, then deliver; if delivery fails, the message is still there for the receiver's next sync. Aim for at-least-once delivery with client-side de-duplication on (channel_id, message_id), because exactly-once over an unreliable network is not on offer. The client also attaches a client-generated id to each outgoing message so a retry after a lost acknowledgment is idempotent (the same trick as in the idempotency page).

How does server 1 know B is on server 2? Either a lookup in a shared session registry (user id to server id, in Redis, with a TTL refreshed by the socket's pings), or a pub/sub topic per user or per server. The registry is simple and precise; pub/sub removes the lookup but adds a broker on the hot path. Both are used in practice.

Group chat flow

A sends to group G (members A, B, C) Chat server ──▶ persist once in (channel=G, id) │ ├──▶ B's inbox queue ──▶ B's chat server ──▶ B's devices └──▶ C's inbox queue ──▶ C's chat server ──▶ C's devices

The chapter's approach is to copy the message into every recipient's inbox (a per-user message sync queue). Reading becomes trivial: each device drains one queue regardless of how many senders or groups feed it. The cost is write amplification of N−1 per message, which is why the group size is capped at 100 here. Be careful to separate two things: the message body is stored once in the channel table; the inbox holds only pointers (channel id plus message id), so the amplification is in small index entries, not full text.

This is the same push-versus-pull choice you meet in the news feed chapter. For groups of 100, push (fanout on write) is correct. For a 100,000-member community channel, per-recipient inboxes are absurd; those systems store once per channel and have clients fetch by cursor, pushing only a lightweight "channel has new messages" signal to members who are currently looking at it. That is the architecture behind large Discord and Slack channels.

Multi-device sync

Each device remembers cur_max_message_id: the highest message id it has seen. To sync, the device asks for messages in its channels with id greater than that value. A message is "new" for a device exactly when it was addressed to the logged-in user and its id exceeds the device's cursor. Because each device owns its own cursor, a phone that was off for a week and a laptop that was on all day each get the right delta with no per-device bookkeeping on the server. With per-channel ids, the cursor is really a map: channel to last seen id (the code below does this), and a cold-started device with an empty map simply fetches recent history per channel.

Insight: live delivery and reconnect catch-up are the same code path. The server never "sends a message"; it tells the connected device "your channel advanced, pull from your cursor." Dropped packets, a socket that died mid-delivery and a brand-new device all heal identically.
Deep dive

Online presence

On login the client connects and the presence server records the user as online with a timestamp; on a clean logout it records offline. The hard part is the unclean case: a phone enters a tunnel, the TCP connection never sends a FIN, and the server believes the user is online forever. Closing that gap is why presence is built on heartbeats rather than on socket state alone.

  • The client sends a heartbeat every few seconds (say every 5).
  • The presence server stores last_active. If no heartbeat arrives within a timeout (the notes use 30 seconds), the user is considered offline.
  • The timeout must exceed several heartbeat intervals so one dropped packet, or a user flicking between Wi-Fi and cellular, does not make the status flap.

Presence fanout is where this gets expensive. The chapter's design uses a publish/subscribe channel per friend pair: when A's status changes, A publishes on channels A-B, A-C and A-D, and B, C and D are each subscribed to their channel with A. That is fine for a small friend list but costs one publish per friend per transition, and every login, logout and flap is a transition. For large groups or big social graphs, do not push. Instead, fetch presence lazily: clients request status only for users currently visible on screen, and the server returns a cached last-seen value. Discord's public writing on presence describes bounding exactly this fanout; see the existing Discord presence design page for a worked treatment.

Gotcha: debounce presence. Publishing "offline" the instant one heartbeat is missed, then "online" two seconds later, burns fanout capacity and makes the UI blink. Require the timeout to elapse before announcing offline, and consider announcing online immediately but offline only after the grace period.
Code

Runnable core: per-channel ids, cursor sync, presence

This model captures the mechanics that matter: persist-first delivery, per-channel sequence ids, per-device cursors that make reconnect and multi-device identical, heartbeat expiry using an injected clock, and an offline push queue. The WebSocket layer is deliberately replaced with callbacks; the algorithms are the same.

JavaScript Example 
// Mini chat core: per-channel sequence ids, durable store, inbox sync by cur_max_message_id, heartbeat presence.
import assert from 'node:assert/strict';

class MessageStore {                       // stands in for a KV store keyed (channel_id, message_id)
  #rows = new Map();                       // channel -> array of {id, from, text}
  #seq = new Map();                        // channel -> last id (local sequence per channel)
  append(channel, from, text) {
    const id = (this.#seq.get(channel) ?? 0) + 1;
    this.#seq.set(channel, id);
    if (!this.#rows.has(channel)) this.#rows.set(channel, []);
    const row = { channel, id, from, text };
    this.#rows.get(channel).push(row);
    return row;
  }
  since(channel, afterId) { return (this.#rows.get(channel) ?? []).filter(r => r.id > afterId); }
}

class Presence {
  constructor(timeoutMs, now) { this.timeoutMs = timeoutMs; this.now = now; this.last = new Map(); }
  heartbeat(user) { this.last.set(user, this.now()); }
  isOnline(user) { const t = this.last.get(user); return t !== undefined && this.now() - t <= this.timeoutMs; }
}

class ChatService {
  constructor(store, presence) {
    this.store = store; this.presence = presence;
    this.members = new Map();              // channel -> Set(users)
    this.sockets = new Map();              // user -> [{device, cursor: Map(channel->curMax), push(msg)}]
    this.pushQueue = [];                   // offline push notifications
  }
  join(channel, users) { this.members.set(channel, new Set(users)); }
  connect(user, device, onMessage) {
    const dev = { device, cursors: new Map(), push: onMessage };
    (this.sockets.get(user) ?? this.sockets.set(user, []).get(user)).push(dev);
    this.presence.heartbeat(user);
    // reconnect: pull everything newer than this device's cursor for each channel
    for (const [channel, users] of this.members) if (users.has(user)) this.sync(user, dev, channel);
    return dev;
  }
  sync(user, dev, channel) {
    const after = dev.cursors.get(channel) ?? 0;
    for (const m of this.store.since(channel, after)) { dev.push(m); dev.cursors.set(channel, m.id); }
  }
  send(channel, from, text) {
    const row = this.store.append(channel, from, text);       // persist first, then deliver
    for (const u of this.members.get(channel)) {
      if (u === from) continue;
      const devs = this.sockets.get(u) ?? [];
      if (this.presence.isOnline(u) && devs.length) devs.forEach(d => this.sync(u, d, channel));
      else this.pushQueue.push({ to: u, channel, id: row.id });
    }
    return row;
  }
}

let clock = 0;
const store = new MessageStore(), presence = new Presence(30_000, () => clock);
const svc = new ChatService(store, presence);
svc.join('dm:a-b', ['a', 'b']); svc.join('grp:1', ['a', 'b', 'c']);

const phone = [], laptop = [];
svc.connect('b', 'phone', m => phone.push(`${m.channel}#${m.id}:${m.text}`));
presence.heartbeat('a');
svc.send('dm:a-b', 'a', 'hi');
svc.send('grp:1', 'a', 'hello group');
assert.deepEqual(phone, ['dm:a-b#1:hi', 'grp:1#1:hello group']);
assert.equal(svc.pushQueue.length, 1);                         // c was never online -> push notification
assert.equal(svc.pushQueue[0].to, 'c');

// laptop logs in later and catches up from cursor 0; ids are per-channel so they restart at 1
svc.connect('b', 'laptop', m => laptop.push(`${m.channel}#${m.id}`));
assert.deepEqual(laptop, ['dm:a-b#1', 'grp:1#1']);

// presence: b stops heartbeating
clock = 20_000; assert.equal(presence.isOnline('b'), true);
clock = 31_000; assert.equal(presence.isOnline('b'), false);
svc.send('dm:a-b', 'a', 'are you there?');
assert.equal(svc.pushQueue.at(-1).to, 'b');                    // offline -> push
// b reconnects: only the missed message is replayed
const phone2 = []; svc.connect('b', 'tablet', m => phone2.push(m.text));
assert.deepEqual(phone2, ['hi', 'are you there?', 'hello group']);   // new device replays every channel from cursor 0
console.log('phone:', phone); console.log('laptop:', laptop);
console.log('push queue:', svc.pushQueue); console.log('tablet replay:', phone2);
console.log('all assertions passed');

Run with node chat.mjs (Node 20+, no dependencies). It prints what each device received, the offline push queue (user c on first send, user b after its heartbeat expires) and the tablet's full replay, then "all assertions passed". Executed and verified.

Stateful chat servers: wins

  • Instant push with no polling overhead
  • Per-connection state enables backpressure and batching
  • Cheap per-message cost once connected

Stateful chat servers: costs

  • Deploys and crashes drop thousands of sockets
  • Sticky routing; load balancing by connections, not requests
  • Reconnect storms need jitter and rate limits

Scaling and production

Where the knees are

  • File descriptors and memory, not CPU. Raise ulimits, tune kernel socket buffers and keep per-connection state tiny. Idle connection memory is dominated by buffers; trim them for quiet sockets.
  • Sharding the message store. Partition by channel id, using consistent hashing so adding nodes moves little data; see consistent hashing and sharding.
  • Cache the tail. Most reads are the latest page of an active channel; keep it in a cache and let the store serve scrollback.
  • Flannel-style edge caching. Large workspaces should not ship their full member list to every client; serve lazily from a regional cache close to the user.
  • Media. Do not send photos through the chat server: upload to object storage, compress and thumbnail, and send a reference in the message.
  • Privacy. End-to-end encryption moves the trust boundary to the devices, which means the server can no longer search or moderate content, and multi-device sync needs per-device keys. Decide early; retrofitting is painful.
  • Observability. Track connected sockets per server, delivery latency from persist to device ack, sync-delta sizes, push failure rate and reconnect rate. A rising reconnect rate is the earliest warning of a bad deploy or a network event.
Checklist

Before you leave the whiteboard

  • WebSocket chosen with a fallback, and the reconnect behaviour (jitter, cursors) stated.
  • Stateless and stateful tiers clearly separated; discovery assigns chat servers.
  • Persist-then-deliver ordering explained; at-least-once with de-dup.
  • Per-channel id and why a global order is unnecessary.
  • Group size limit tied to inbox write amplification, with the large-channel alternative.
  • Device cursor sync handles multi-device and reconnect with one mechanism.
  • Heartbeat presence with timeout and a plan for fanout cost.
  • Offline path through push notifications; media via object storage.
FAQ · Common Questions

Frequently Asked Questions

Why not use Kafka as the message store?

Kafka is excellent as the transport between chat servers, the persistence worker and the search indexer, but it is a log, not a random-access store. Reading the last 50 messages of one of millions of channels would mean one partition per channel, which Kafka does not tolerate. Use it as a pipe and use a partitioned KV or wide-column database as the system of record.

How do you guarantee ordering when two people type at once?

Ordering is defined by the sequencer for that channel, not by wall-clock time. Whichever message reaches the channel's single writer first gets the lower id, and every client renders by id. Both senders may briefly see their own message first (optimistic UI) and then reorder once the server ids arrive.

What happens when the recipient is connected to a different data center?

Route through an inter-region bus: the sending region persists, then publishes to the region where the recipient's session lives, or the recipient's region pulls from a replicated store. Keep a home region per channel to preserve a single sequencer, and accept extra latency for cross-region conversations.

Why is a read receipt harder than delivery?

It is another event type flowing the other way, with its own fanout (in a group, up to N receipts per message). Store it as a per-user read cursor per channel, not per message, so "read up to id 40" is one tiny write and receipts compress dramatically.

How would you add message search?

Stream persisted messages to a search cluster (Elasticsearch or similar) partitioned by workspace or user. Keep it eventually consistent and out of the send path; the primary store never serves full-text queries.

Why cap group size at 100 here?

Because the design pushes a pointer into every member's inbox, so write cost per message is proportional to membership. The cap is a design constraint, not a product statement; beyond it you switch to shared-channel cursors.

Key Takeaway

Chat is a statefulness problem. Confine state to a thin tier of WebSocket servers, persist every message under a per-channel sequence before delivering it, and let each device pull from its own cursor so that delivery, reconnects and new devices are one mechanism. Treat presence as an expensive, lossy, lazily-fetched signal and you will not drown in fanout.
