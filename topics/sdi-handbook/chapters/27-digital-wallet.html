Design a Digital Wallet

Scaling balance transfers to a million per second: sharded state, 2PC vs TC/C vs Saga, event sourcing with replay and snapshots, Raft-replicated logs, and CQRS with push.

ChapterChapter 27 of 28 · Part 6 Transactional Systems
Read time22 min
Core ideas2PC vs TC/C vs Saga, event sourcing, CQRS, Raft, snapshots, deterministic state machine
Real systemsLMAX, Raft (etcd), RocksDB, Kafka, ZooKeeper, Redis, Spanner, TigerBeetle

A digital wallet lets users hold a balance inside a platform and move it to other users instantly and cheaply, without touching card networks or bank rails for every transfer. The specification sounds trivial, subtract here and add there, until you demand one million transfers per second, four nines of availability, strict correctness, and the ability to prove after the fact that every balance is right.

Core idea: Scale comes from raising per-node throughput (local append-only logs, in-memory state, a single-threaded deterministic state machine) and from sharding; correctness comes from an immutable event log you can replay; cross-shard atomicity comes from compensation (TC/C or Saga) rather than lock-holding two-phase commit.

A well-known public design

LMAX and the single-threaded business logic processor

Martin Fowler's well-known write-up of the LMAX Architecture describes a retail financial exchange that processed on the order of six million orders per second on one thread. The recipe is the one this chapter converges on: journal every input event to disk, keep all state in memory, run the business logic on a single thread so there are no locks, and recover by replaying the journal over a snapshot. Replicas apply the same input sequence and therefore reach the same state. Wallets are not exchanges, but the lesson transfers directly: a deterministic state machine fed by an ordered log is dramatically faster and easier to reason about than a pile of row locks.

Scope & Requirements

Problem statement and the estimate that drives everything

Scope is deliberately narrow: balance transfer between two wallets in the same currency (no foreign exchange). The service must support 1M TPS, 99.99% availability (about 52 minutes of downtime a year, or 8.6 seconds a day), transactional guarantees, and reproducibility. The last one is the interesting requirement. Reconciliation can tell you that numbers disagree; reproducibility lets you replay history from the first event to find out why.

Back-of-envelope

  • A cloud-hosted relational database node handles roughly 1,000 simple transactional TPS (a rough planning number; tuned hardware does better, contended rows do worse).
  • 1,000,000 transfers/s / 1,000 per node = 1,000 nodes. But a transfer has two legs (debit and credit), each a write, so the real load is 2,000,000 balance updates/s, i.e. 2,000 nodes.
  • Per-node throughput is the lever that dominates cost:
Per-node TPSNodes for 2M updates/sImplication
10020,000Absurd to operate
1,0002,000Conventional SQL; huge cross-shard transaction surface
10,000200Achievable with an in-memory state machine and append-only log

So the design goal is stated for us: make one node fast enough that you need hundreds of nodes, not thousands. A hundred-fold more per node is also a hundred-fold fewer network hops and cross-shard transactions.

High-Level Design · Attempt 1

API and the in-memory sharded key-value store

One endpoint is enough: POST /v1/wallet/balance_transfer with from_account, to_account, amount (string or integer minor units, never float), currency, and transaction_id, which is the idempotency key. The response returns a status and the transaction id.

The first instinct is a map<user_id, balance> held in Redis, partitioned across nodes because one node cannot take 1M TPS. Pick the partition with hash(account_id) mod N. Store N and the node addresses in ZooKeeper (or etcd), which gives the stateless wallet-service fleet a consistent, highly available view of the topology. Wallet servers are interchangeable and scale horizontally.

ATTEMPT 1: SHARDED IN-MEMORY BALANCES client ──▶ [ wallet service ] x many (stateless) │ partition = hash(account) mod N N + node list from ZooKeeper / etcd ┌─────────┼─────────┐ ▼ ▼ ▼ redis-0 redis-1 redis-2 ... balances: A→100, B→50 ... transfer A→C where A on redis-0, C on redis-2: DECRBY A 1 ✔ process dies here INCRBY C 1 ✘ => $1 destroyed

This scales but fails two requirements. The two updates land on different nodes and nothing makes them atomic. And an in-memory store with asynchronous persistence is not a system of record. Also, plain modulo hashing remaps most keys when N changes; real deployments use a fixed large number of logical partitions mapped to nodes, or consistent hashing.

Distributed Transactions

Three ways to make a cross-shard transfer atomic

Option A: Two-phase commit over relational shards

Replace Redis with sharded relational databases. A coordinator (the wallet service) reads and writes on each database as in normal transactions. When ready to commit it asks every participant to prepare, meaning "durably promise you can commit and hold your locks". If all vote yes, the coordinator tells everyone to commit; any no, or a timeout, means abort.

2PC coordinator DB-A (A-1) DB-C (C+1) │──prepare──────────▶│ │ │──prepare───────────────────────────────▶│ │◀──yes──────────────│ │ both now hold row locks, in doubt │◀──yes───────────────────────────────────│ │──commit───────────▶│ │ │──commit────────────────────────────────▶│ If the coordinator dies between prepare and commit, participants block holding locks.

Downsides: locks are held across network round trips, so contention collapses throughput on hot accounts; and the coordinator is a blocking single point of failure. 2PC is also tied to databases that implement XA-style prepare, which many NoSQL and microservice stores do not.

Option B: Try-Confirm/Cancel (TC/C)

TC/C turns one distributed transaction into two independent, local transactions per participant. Nothing is held open between them; the "lock" is a business-level reservation.

PhaseOperationAccount A (debit)Account C (credit)
1TryBalance -$1 (committed locally)NOP
2aConfirm (all tries said yes)NOPBalance +$1
2bCancel (any try failed)Balance +$1 (undo)NOP
TC/C TIMELINE coordinator DB-A DB-C │──try: A-1────▶ txn{ bal-=1 }✔ │──try: NOP─────────────────────────▶ ✔ │ --- all yes ---> │──confirm: NOP─▶ ✔ │──confirm: C+1─────────────────────▶ txn{ bal+=1 }✔ CONFIRMED try fails (e.g. A has insufficient funds) ──▶ cancel both: │──cancel: A+1─▶ (only if try had applied) cancel: NOP CANCELLED

The sharp difference from 2PC: after phase one every local transaction is already committed, and phase two either executes a further transaction (confirm) or reverses the committed one (cancel). 2PC's first phase leaves work uncommitted and locked.

Phase 1Phase 2 successPhase 2 failure
2PCTransactions prepared but not committedCommit allAbort all
TC/CTransactions committed or cancelled locallyRun the confirm transactionsRun compensating transactions

TC/C failure handling

  • Coordinator crash. Persist a phase status table alongside the shards: transaction id and content, try status per participant (not sent / sent / response received), the chosen second phase (confirm or cancel) and its status, plus the out-of-order flag. The status row is written atomically with each step so a restarted coordinator resumes rather than guesses.
  • Visible intermediate state. Between try and confirm, A has lost $1 and C has not gained it, so the system's total looks short. That is tolerable provided it is always repaired and nobody can spend the in-flight amount. The rule: the try phase deducts and the confirm phase adds. Deduct-first means the worst case is temporary under-count, never money from nowhere. Adding in try (choice 2) lets C spend funds that may be cancelled; doing both in try (choice 3) needs cross-database atomicity, which is exactly what we lack.
  • Out-of-order delivery. A cancel can overtake a try (the try was delayed by the network and the coordinator timed out and cancelled). If the shard then processes the late try, it deducts for a transaction already declared dead. Defence: on cancel with no matching try, record a tombstone (the out-of-order flag); a later try consults the flag and refuses.
  • Idempotency. Try, confirm and cancel can each be redelivered. Key every phase by transaction id and ignore repeats.

Option C: Saga

A saga (originally from Garcia-Molina and Salem, 1987, for long-lived database transactions, later popularised for microservices) is a linear sequence of local transactions, each in its own database. If step k fails, run compensating actions for steps k-1 down to 1. For a transfer: step 1 debit A; step 2 credit C; if step 2 fails, compensate by crediting A back.

Two ways to coordinate: choreography, where each service reacts to events and emits the next, so the workflow is implicit and scattered across services; and orchestration, where a central coordinator tells each participant what to do and tracks progress. For money, prefer orchestration: the workflow is in one place, one status record per saga, easy to inspect and to resume.

DimensionTC/CSaga
CompensationIn the cancel phaseIn the rollback sequence
Central coordinatorYesYes when orchestrated
Execution orderAnyLinear
ParallelismYes: tries run concurrentlyNo: step by step
Partial inconsistency visibleYesYes
Where the logic livesApplicationApplication
Choosing: if latency is the constraint, use TC/C because tries can fan out in parallel and you wait for the slowest rather than the sum. If you have long multi-step business flows across many services, Saga's linear, readable orchestration is easier to build. Neither removes the need for an audit trail, which brings us to event sourcing.
Event Sourcing

From "what is the balance" to "what happened"

An audited wallet must answer three questions: what was any account's balance at a past instant; how do we know current and historical balances are correct; and after a code change, how do we prove the new logic still computes the same results? A table that stores only current balances cannot answer any of them. Event sourcing can, because it stores the transitions, not the result.

ConceptMeaningProperties
CommandIntent from the outside world: "transfer $1 from A to B"Globally ordered in a FIFO queue; may be rejected; may involve I/O or randomness; yields zero or more events
EventA fact that already happened: "A debited $1, B credited $1"Immutable, ordered, cannot fail
StateWhat the events add up to, e.g. map account → balanceDerived; can always be rebuilt
State machineValidates a command against state, emits events, applies events to stateMust be deterministic: no clock reads, randomness, or external I/O
EVENT-SOURCED WALLET clients ──▶ [ command queue (FIFO) ] ──▶ state machine ──validate(cmd, state)──▶ events │ ▲ │ │ └────── read balances ─────────┘ ▼ [ event log (immutable, ordered) ] │ apply ▼ [ state: balances ] one command A→B $1 produces two events: DEBITED(A,1), CREDITED(B,1)

Since commands may have side effects but events are facts, the non-determinism is confined to the step that turns a command into events (which is also where you capture any externally obtained value, such as an exchange rate or a fraud score, into the event). Replaying events then needs no I/O and always yields the same state.

How it answers the audit questions

  • Balance at time T: replay events up to T.
  • Correctness: replay everything from event zero and compare with live state; any divergence is a bug or tampering, and you know the first event where it appears.
  • Code change safety: run old and new state-machine versions against the same event history and diff the results (a regression test using production data).

CQRS for reads

The write path (commands to events) is optimised for ordering and durability. Read queries ("what is my balance? show my history") go to separate read-only state machines that consume the same event stream and maintain query-friendly views. This is CQRS: Command Query Responsibility Segregation. It lets reads scale independently and be shaped differently (balances, statements, per-merchant aggregates) at the price of staleness: a read model lags the write model by some milliseconds.

Deep Dive · Performance

High-performance event sourcing on one node

If commands and events live in an external Kafka and state lives in an external database, every transfer pays several network round trips. The deep dive peels those off one by one.

  1. Local append-only files for commands and events. Sequential appends are the fastest thing a disk does, even a spinning one, and there is no network hop.
  2. Recent entries cached in memory with mmap. Mapping the file into the process address space makes appends and reads of the hot tail memory operations, with the OS page cache flushing to disk. Reads of recent events never hit the disk path at all.
  3. State in a local embedded store. SQLite is a file-backed relational option; RocksDB, an LSM-tree engine, turns random updates into sequential writes (memtable then SST files, compacted in the background) and serves reads from block cache and bloom filters. For a write-heavy balance map RocksDB is the better fit.
  4. Snapshots. Replaying from event zero gets slower forever. Periodically dump the state at a known event offset to durable storage (a large binary blob in HDFS or S3). Recovery becomes: load latest snapshot, replay only events after its offset.
ONE WALLET NODE (after optimisation) cmd ──▶ [mmap command log] ──▶ state machine (single thread) ──▶ [mmap event log] ──▶ apply │ │ reads from writes to └─────────────▶ [ RocksDB state ] ◀───────────────┘ every N events / T minutes ──▶ snapshot(state, offset) ──▶ HDFS / object storage
Caution on durability: mmap'd data in the page cache is not durable until flushed. Whether you msync / fsync per batch or rely on replication for durability (next section) is a core latency-versus-safety decision. Batching many commands per fsync (group commit) is how single nodes reach tens of thousands of durable ops per second.
Deep Dive · Reliability

Replicating only what must survive

Local files and in-memory state make the node stateful: lose the machine, lose the wallet. Rather than replicating everything, reason about what is irreplaceable.

DataRebuildable?Reliability need
State (balances)Yes, replay eventsLow: a cache of the log
SnapshotsYes, replay eventsLow: an optimisation
CommandsNo, if command handling had non-deterministic parts you cannot regenerate the events from commands aloneModerate: they are inputs, but events are the truth
EventsNo: they are the source of truthHighest

So the event log is what we replicate, and we need two properties: no acknowledged event is lost, and every replica holds the same events in the same order. That is precisely state-machine replication via a consensus protocol. Raft is the pragmatic choice: a leader accepts appends and replicates them to followers; an entry is committed once a majority has persisted it; if the leader fails, followers elect a new one among those with the most up-to-date log. With 2f+1 nodes the group tolerates f failures, so a three-node group survives one, five survive two. Followers apply the same events to build identical state, so any follower is a hot standby.

RAFT GROUP (3 nodes) ┌────────── append(event 42) ──────────┐ client ─▶│ LEADER log: …,41,42 │ └───┬───────────────────────────┬──────┘ replicate replicate ▼ ▼ FOLLOWER-1 log: …,41,42 FOLLOWER-2 log: …,41 (lagging, catches up) commit index advances when 2 of 3 have persisted 42 → ack to client; leader dies → follower with log through 42 can win election

Cost: one network round trip (to the nearest majority) per commit, amortised by batching entries per round trip. Production implementations include etcd's raft library, HashiCorp Raft, and TiKV's Raft groups.

Deep Dive · Scale-out

Many Raft groups, a reverse proxy, and push instead of poll

Two limits remain. One Raft group's capacity is bounded by its leader, so we must shard into many groups, and transfers between accounts in different groups need distributed transactions again (now over fast, replicated, deterministic participants rather than slow SQL). And the CQRS read path is asynchronous: a client that submitted a transfer does not know when the read model has caught up, so naive clients poll, which is both slow to notice and a load multiplier.

  1. Polling: client repeatedly queries the read side. Simple, laggy, and heavy under load.
  2. Reverse proxy: a gateway submits the command on the user's behalf and does the polling itself, batching lookups for many users into fewer queries. Lower load, still not real time.
  3. Push: the read-only state machines push completion to the proxy once they apply the relevant event; the proxy answers the waiting client (long-poll, WebSocket, or SSE; see WebSockets). Users perceive the system as synchronous even though it is not.
FINAL ARCHITECTURE user ──▶ [ reverse proxy ] ──▶ [ Saga / TC-C coordinator + phase status table ] ▲ │ 1. A-1 → partition P1 2. C+1 → partition P2 │ push result ▼ ▼ │ ┌─ Raft group P1 ─┐ ┌─ Raft group P2 ─┐ │ │ leader+2 follow │ │ leader+2 follow │ │ │ cmd→event→state │ │ cmd→event→state │ │ └───────┬─────────┘ └───────┬─────────┘ └──── read-only state machines (CQRS) notice applied events ─────┘

Lifecycle of one transfer in the final system

  1. User A submits a distributed transaction with two operations, A-1 and C+1, to the coordinator.
  2. The coordinator writes a phase-status record for the transaction.
  3. It resolves which partition owns each account.
  4. Partition 1's Raft leader receives A-1, validates it against state, produces an event, replicates it to a majority.
  5. The read state machine applies the event and pushes the outcome to the coordinator.
  6. The coordinator records success for step 1 and proceeds to C+1 in partition 2, the same way.
  7. After step 2 is recorded the coordinator tells the client. On any failure it runs the compensations instead.
Idempotency & Invariants

The details that keep it honest

  • Dedup in the state machine. The transaction id is checked inside the deterministic apply path, so redelivered commands (client retry, coordinator resume, Raft re-proposal after leader change) produce no second effect. The dedup set is part of replayed state; bound it by retaining ids for the retry horizon plus snapshot it.
  • No negative balances. Validation happens in the shard that owns the account, on the single writer, so check-then-debit has no race. Reservation-style debits (try) must be visible to subsequent validations.
  • Conservation. The sum of all balances plus in-flight reservations is constant. Run it as a continuous invariant check and as part of snapshot verification.
  • Hot accounts. A single merchant receiving most transfers makes one partition's single thread the bottleneck. Split the account into sub-accounts (sharded counters) that are summed on read, or aggregate credits in batches.
  • Resharding. Moving an account between groups is itself a distributed transaction plus an event-log handoff. Use many more logical partitions than nodes so rebalancing moves whole partitions.
  • Event schema evolution. Events live forever. Version them, and keep old-version handlers in the replay path, otherwise replay breaks when code changes. Upcasters that translate old events on read are a common approach.

Event-sourced core

  • Complete, tamper-evident history
  • Deterministic replay for debugging and regression testing
  • Natural fit for single-threaded high throughput

Event-sourced core

  • Unfamiliar model; needs discipline
  • Log and snapshot management are your job
  • Hard to delete data (privacy law): crypto-shredding or tombstone events needed

It is worth saying aloud in an interview that a mature alternative exists: just use a distributed SQL database (Spanner, CockroachDB, YugabyteDB) with serializable transactions and accept the lower ceiling. Purpose-built ledger databases such as TigerBeetle target exactly this debit-credit workload at very high throughput. The chapter's route is the do-it-yourself version of the same ideas.

Code

Deterministic wallet state machine, replay, snapshots, and TC/C

The program implements the core mechanics: a pure decide / apply pair, an event log with idempotent command handling and periodic snapshots, time-travel replay, and a TC/C coordinator over two shards with the out-of-order-cancel tombstone. Executed; assertions pass.

JavaScript Example 
// Event-sourced wallet: deterministic state machine + replay + snapshot, and a TC/C coordinator over two shards.
import assert from 'node:assert/strict';

// ---------- 1. Event sourcing: commands -> events -> state ----------
// The state machine is PURE: same event list => same state. No clock, no randomness, no I/O.
function decide(state, cmd) {                    // validate a command, return events (or a rejection)
  if (cmd.type !== 'TRANSFER') return { error: 'UNKNOWN' };
  const { from, to, amount, id } = cmd;
  if (amount <= 0n) return { error: 'BAD_AMOUNT' };
  if ((state.get(from) ?? 0n) < amount) return { error: 'INSUFFICIENT_FUNDS' };
  return { events: [{ id, type: 'DEBITED', acct: from, amount }, { id, type: 'CREDITED', acct: to, amount }] };
}
function apply(state, ev) {                      // fold one event into state
  const d = ev.type === 'DEBITED' ? -ev.amount : ev.amount;
  state.set(ev.acct, (state.get(ev.acct) ?? 0n) + d);
}
class WalletLog {
  commands = []; events = []; state = new Map(); snapshots = []; seenIds = new Set();
  constructor(opening = {}) { for (const [k, v] of Object.entries(opening)) { this.events.push({ id: `open:${k}`, type: 'CREDITED', acct: k, amount: v }); apply(this.state, this.events.at(-1)); } }
  submit(cmd) {
    this.commands.push(cmd);
    if (this.seenIds.has(cmd.id)) return { duplicate: true };       // idempotency by transaction_id
    const r = decide(this.state, cmd);
    if (r.error) return r;
    this.seenIds.add(cmd.id);
    for (const ev of r.events) { this.events.push(ev); apply(this.state, ev); }
    if (this.events.length - (this.snapshots.at(-1)?.upto ?? 0) >= 8) this.snapshots.push({ upto: this.events.length, state: new Map(this.state) });
    return { ok: true };
  }
  static replay(events, upto = events.length, snap = null) { // rebuild any historical state
    const s = snap ? new Map(snap.state) : new Map();
    for (let i = snap ? snap.upto : 0; i < upto; i++) apply(s, events[i]);
    return s;
  }
}

const log = new WalletLog({ A: 100n, B: 50n, C: 0n });
assert.deepEqual(log.submit({ id: 't1', type: 'TRANSFER', from: 'A', to: 'C', amount: 30n }), { ok: true });
assert.deepEqual(log.submit({ id: 't1', type: 'TRANSFER', from: 'A', to: 'C', amount: 30n }), { duplicate: true });
assert.equal(log.submit({ id: 't2', type: 'TRANSFER', from: 'B', to: 'A', amount: 80n }).error, 'INSUFFICIENT_FUNDS');
for (let i = 0; i < 10; i++) log.submit({ id: `x${i}`, type: 'TRANSFER', from: 'A', to: 'B', amount: 1n });

const rebuilt = WalletLog.replay(log.events);
assert.deepEqual([...rebuilt], [...log.state]);                       // full replay == live state
const snap = log.snapshots[1]; // a mid-history snapshot; replay only the tail
assert.deepEqual([...WalletLog.replay(log.events, log.events.length, snap)], [...log.state]); // snapshot + tail
const afterT1 = WalletLog.replay(log.events, 5);                       // time travel: balances after 5 events
console.log('live state     :', [...log.state].map(([k, v]) => `${k}=${v}`).join(' '));
console.log('state @event 5 :', [...afterT1].map(([k, v]) => `${k}=${v}`).join(' '));
console.log('snapshot used  : upto', snap.upto, 'of', log.events.length, 'events');
let sum = 0n; for (const v of log.state.values()) sum += v; assert.equal(sum, 150n); // money conserved

// ---------- 2. TC/C across two shards, with out-of-order cancel protection ----------
class Shard {
  balances = new Map(); phase = new Map(); // txId -> 'TRIED' | 'CONFIRMED' | 'CANCELLED' | 'CANCEL_FIRST'
  constructor(name, init) { this.name = name; for (const [k, v] of Object.entries(init)) this.balances.set(k, v); }
  try_(tx, acct, delta) {               // local ACID txn #1: reserve (deduct) now; credits are NOP in try
    if (this.phase.get(tx) === 'CANCEL_FIRST') return false;      // cancel overtook try -> refuse
    if (this.phase.has(tx)) return true;                           // idempotent
    if (delta < 0n && (this.balances.get(acct) ?? 0n) + delta < 0n) return false;
    if (delta < 0n) this.balances.set(acct, this.balances.get(acct) + delta);
    this.phase.set(tx, 'TRIED'); return true;
  }
  confirm(tx, acct, delta) {            // local ACID txn #2 (success path)
    if (this.phase.get(tx) === 'CONFIRMED') return;
    if (delta > 0n) this.balances.set(acct, (this.balances.get(acct) ?? 0n) + delta);
    this.phase.set(tx, 'CONFIRMED');
  }
  cancel(tx, acct, delta) {             // compensating txn: undo the try, or leave a tombstone if try never arrived
    const p = this.phase.get(tx);
    if (p === undefined) { this.phase.set(tx, 'CANCEL_FIRST'); return; }
    if (p === 'TRIED' && delta < 0n) this.balances.set(acct, this.balances.get(acct) - delta);
    if (p === 'TRIED') this.phase.set(tx, 'CANCELLED');
  }
}
function tcc(tx, legs) {                // legs = [{shard, acct, delta}], deductions first
  const ordered = [...legs].sort((a, b) => Number(a.delta - b.delta));
  const tried = [];
  for (const l of ordered) { if (l.shard.try_(tx, l.acct, l.delta)) tried.push(l); else { for (const t of legs) t.shard.cancel(tx, t.acct, t.delta); return 'CANCELLED'; } }
  for (const l of legs) l.shard.confirm(tx, l.acct, l.delta);
  return 'CONFIRMED';
}
const s1 = new Shard('s1', { A: 100n }), s2 = new Shard('s2', { C: 5n });
assert.equal(tcc('T1', [{ shard: s1, acct: 'A', delta: -40n }, { shard: s2, acct: 'C', delta: 40n }]), 'CONFIRMED');
assert.equal(tcc('T2', [{ shard: s1, acct: 'A', delta: -500n }, { shard: s2, acct: 'C', delta: 500n }]), 'CANCELLED');
assert.equal(s1.balances.get('A'), 60n); assert.equal(s2.balances.get('C'), 45n);
s2.cancel('T3', 'C', 10n);              // cancel arrives BEFORE try (network reordering)
assert.equal(s2.try_('T3', 'C', 10n), false);
console.log('TC/C result    : A=' + s1.balances.get('A') + ' C=' + s2.balances.get('C') + ', late try after cancel rejected');
console.log('all assertions passed');

Prints the live balances (A=60 B=60 C=30), the balances after the first 5 events (A=70 B=50 C=30), the snapshot offset used for a partial replay (17 of 25 events), the TC/C outcome (A=60 C=45, late try after cancel rejected), then "all assertions passed".

Scaling & Production Gotchas

Knees in the curve

  • Raft round trip bounds latency. Put replicas in the same region (or at least metro), batch entries per round trip, and use pipelining. Cross-region synchronous replication makes every transfer cost tens of milliseconds.
  • Single-threaded does not mean single-core wasteful. Run many partitions per machine, one pinned thread each. The unit of parallelism is the partition.
  • Cross-partition ratio is the hidden cost. If 30% of transfers cross partitions, the effective TPS is dominated by coordinator work. Partition so that likely counterparties colocate where the domain allows.
  • Snapshot cadence trades recovery time against write amplification. Choose it from your recovery-time objective: replay speed (events/s) times allowed seconds gives the maximum tail length.
  • Log retention. Events are forever in principle; in practice archive cold segments to object storage and keep a verifiable hash chain (each batch includes the hash of the previous) so archived history remains tamper-evident.
  • Back-pressure. The command queue must be bounded; shed load at the proxy with explicit errors rather than letting queues grow until latency is useless.
  • Observability. Per-partition queue depth, apply lag of read models, Raft commit latency, election count, coordinator in-flight ages, invariant checker output. See observability.
Checklist

Design-review checklist

  • Transfer API is idempotent via transaction id, enforced inside the state machine
  • State machine is deterministic; external values are captured in events
  • Event log is replicated by consensus; state and snapshots are rebuildable
  • Cross-partition transfers use TC/C or orchestrated Saga with a persisted status table
  • Deduct first, add later; confirm and cancel are idempotent and retried until done
  • Out-of-order cancel handled with a tombstone/flag
  • CQRS read models with push notification to the waiting client
  • Periodic snapshots, tested restores, replay-based regression tests in CI
  • Hot account strategy and resharding plan
  • Continuous conservation check and nightly full replay verification
FAQ · Common Questions

Frequently Asked Questions

Why not just use 2PC across sharded SQL databases?

It works and is the simplest correct answer, but locks are held across network round trips and the coordinator is a blocking point of failure, so throughput per node stays near the 1,000 TPS class and you would need thousands of nodes. TC/C and event sourcing trade simplicity for much higher per-node throughput.

TC/C leaves a window where money has left A but not arrived in C. Is that acceptable?

Yes, if three conditions hold: the in-flight amount cannot be spent by anyone, the transaction always completes or compensates (persisted coordinator state, indefinite retry of confirm), and the window is visible in monitoring. Deducting in the try phase guarantees the system never over-credits.

Why are events replicated but not commands?

State is derivable from events. Events are derivable from commands only if processing is deterministic, but command handling may involve I/O and randomness, so events are the true record. Commands are inputs worth keeping for debugging, but events are what must never be lost.

How do you prove correctness after a code change?

Replay the entire production event history through both the old and new state machine versions and compare every resulting balance (and every emitted event for commands re-run). Because the machine is deterministic, any difference is attributable to the code change.

Saga or TC/C for a wallet?

A two-leg transfer is a natural TC/C case: both tries run in parallel for lower latency. Saga fits longer flows (debit, fee, rewards, notification) where sequential steps with compensations read naturally. Both need an orchestrator and persisted status.

What if a user's account is on a partition whose Raft group has lost quorum?

That slice is unavailable by design (CP behaviour). Transfers touching it are rejected or cancelled via compensation; other partitions continue. This is why the 99.99% target is reasoned per partition and why replica placement across failure domains matters. See CAP.

Key Takeaway

Do not scale a wallet by making a database do distributed locking faster; scale it by making each node a deterministic, single-writer state machine over a replicated append-only log, then glue partitions together with compensating transactions. You get throughput, an audit trail, and replayable proof of correctness from the same decision.
