Design Google Drive (File Sync)

A sync service is a metadata database with a very large, very dumb blob store behind it. The interesting engineering is in cutting files into blocks so that uploads are resumable, edits are cheap, duplicates cost nothing and conflicts are detectable.

Everyone's first answer is "S3 plus a database". That is correct and not yet an answer. The questions that separate designs are: what happens when someone changes one line in a 2 GB file, when two laptops edit the same document offline, when the upload dies at 97 percent, and when a million users upload the same installer.

Core idea: never treat a file as the unit of storage or transfer. Treat it as an ordered list of immutable, content-addressed blocks. A file version is then just a row pointing at a list of hashes, and almost every feature (resume, delta sync, dedup, cheap history, integrity checks) falls out of that one choice.

A public design to anchor on

Dropbox's block-and-metadata split

Dropbox has described its architecture in public talks: the desktop client chunks files into blocks of up to 4 MB, hashes each with SHA-256, asks the server which hashes it already has, and uploads only the missing ones. A separate metadata service tracks namespaces, file lists and which blocks make up each revision, and a notification channel (long-lived HTTP polling) tells devices that something changed. Block storage began on S3 and was later moved to an in-house system Dropbox calls Magic Pocket. The block/metadata separation is the part to copy; the storage back end is a swappable implementation detail.

Requirements and numbers

Scope and sizing

Functional: upload and download files, sync across devices, share with permissions, keep revision history, notify on edit/delete/share. Out of scope here: collaborative real-time editing as in Google Docs, which uses operational transforms or CRDTs on top of a different pipeline. Non-functional priorities, in order: reliability (losing a customer's file is the one unforgivable failure), sync speed, bandwidth efficiency (mobile data costs the user), scalability and availability.

If you multiply the 10 M DAU by 10 GB you get 100 PB; people lose marks on exactly this. The write rate (240 QPS) is tiny; capacity and the metadata path are the real problems, so the design optimises bytes and consistency rather than raw request throughput.
High-level design

From one box to a sync platform

Day one: one server

A web server, a database for users and file metadata, and a directory tree with one folder per namespace (a namespace is the root of a user's or shared-folder's tree). A file is identified by namespace plus relative path. It works, and it fails on three axes: disk fills, the box is a single point of failure, and no one can resume a broken upload.

All of these require auth and run over TLS. A resumable session is just state: (upload_id, expected_size, received_ranges). Keep the session record in the metadata store or cache with a TTL so abandoned uploads expire.

Scaling the single box

  • Object storage (S3-class) for the bytes, replicated across zones and optionally regions. You get eleven nines of designed durability for nothing you have to operate.
  • Load balancer plus stateless web/API servers so failure of any one is invisible.
  • Metadata DB sharded and replicated, ideally by namespace/user, with a cache in front.

Why block servers exist

You could let the client write whole files to object storage. Block servers (or an equivalent client library) add the logic that makes this a sync product: split into blocks, compress each (text compresses well, JPEG and video do not, so choose per type or skip), encrypt, hash, and store by hash. Block size is a trade-off. Small blocks (say 256 KB) give finer deltas and better dedup but multiply metadata rows and request overhead. Large blocks (4 to 8 MB) amortise per-request cost but retransmit more on a small edit. A fixed 4 MB maximum is a defensible default; content-defined chunking (below) lets you hit an average size while still resynchronising after inserts.

Deep dive 1

The metadata database

Metadata is small, relational and must be consistent: a path must resolve to exactly one current version, and a rename or move must be atomic. That argues for an ACID store (MySQL or Postgres, or a globally consistent system such as Spanner) rather than an eventually consistent NoSQL store. Reads dominate, so replicas plus a cache take pressure off the primary; the cache must be invalidated on commit, and clients that just wrote should read from the primary to avoid seeing their own change vanish.

Sharding by namespace_id keeps a user's whole tree on one shard, so listing a folder and renaming inside it are single-shard transactions. Shared folders complicate this (a namespace has many members), which is why namespaces rather than users are the sharding key. Cross-namespace moves need a short two-phase operation, usually done as copy-then-delete under a saga. See Sharding.

A change log is the other essential structure: an append-only per-namespace sequence of events (cursor, file_id, op, version). A device stores the last cursor it processed and asks "give me everything after cursor N". This turns sync from a diff of two trees (expensive) into reading a log tail (cheap), and it is what the offline queue really is.

Deep dive 2

Upload, download and sync flows

Upload

client API server block server object store │ ── (A) add-file metadata ─▶│ INSERT file_version (status=PENDING) │ ── (B) which blocks do you lack? hashes[] ──────▶│ answer: [h7, h9] │ ── (B) PUT block h7, h9 (compressed+encrypted) ─▶│ ───────────────▶ put (idempotent by hash) │ │◀──── commit (all blocks present) ─────│ │ │ status = UPLOADED ; append change-log entry │ │ ──▶ notification service ──▶ other devices │◀── ack(version=N) ─────────│

The metadata and block uploads run in parallel for latency, but the version only becomes visible when every referenced block exists. A PENDING row is invisible to readers; a janitor aborts and cleans stale pending rows. Because block keys are hashes, retries are idempotent by construction: re-uploading a block that already exists is a no-op. S3-style event callbacks (or the block server's own acknowledgement) flip the status, which in turn publishes the change event.

Download and sync

A device learns about a change in one of two ways. If it is online, the notification service tells it. If it is offline, the change-log entries wait, and on reconnect the device reads the log from its last cursor. Either way the next steps are identical: fetch the new metadata from the API tier, diff the block list against the blocks it already holds, download only the missing ones from the block servers (ideally via a CDN or signed URLs), and reassemble in order. Verify each block's hash on arrival; a mismatch is a corrupted download, not a conflict.

Delta sync and chunking

With fixed-size blocks, editing the middle of a file leaves most blocks unchanged and only the touched ones are re-uploaded, which is great for in-place edits (databases, disk images, big spreadsheets). Inserting bytes shifts every later block boundary and defeats dedup. The fix, used by rsync (rolling checksum), backup tools and Dropbox-style systems, is content-defined chunking: slide a rolling hash over the bytes and cut wherever the hash satisfies a rule such as "low 13 bits are zero". Boundaries now depend on local content, so inserting 100 bytes disturbs one or two chunks and the rest realign. The example below does exactly this and shows a 600 KB file edited near the front re-uploading under 2 percent of its bytes.

Archives such as zip, and many office formats, are themselves compressed containers where a tiny edit changes everything after it. Mature clients special-case these by chunking inside the container or accepting the cost. Mention it, because it shows you have met real files.

Conflicts

Two devices edit version 5 independently. The first commit that reaches the server creates version 6. The second commit carries base_version = 5, which no longer equals the latest, so the server rejects it (this is optimistic concurrency, a compare-and-set on the version). The server does not guess. It keeps the winner as the canonical file and stores the loser as a sibling, such as "report (conflicted copy from tablet)", and tells the user. For plain files this is the honest behaviour; for structured documents a merge is possible but requires format knowledge, and for live collaborative text you leave this layer entirely and use OT/CRDTs. Neil Fraser's differential synchronization, listed in the references, is a third model: continuously diff and patch a shared text between client and server shadow copies.

Deep dive 3

Notification service, storage economics, security

Telling devices something changed

The need is one-way and low frequency per device: "namespace X has a new cursor". Long polling does that well. The client holds an HTTP request open; the server answers when there is a change or after roughly a minute with "nothing", and the client immediately re-issues it. That works through corporate proxies, needs no special protocol and is simple to scale. WebSockets give bidirectional, lower-overhead messaging, which matters more in chat than here. Either way, treat the notification as a hint containing the namespace and cursor, never as the data; the log is the source of truth, and a missed hint costs only latency because devices also poll on a timer. At scale each notification server holds many thousands of idle connections, so use epoll-based servers, tune file-descriptor limits, and shard subscribers by namespace through a pub/sub layer. See WebSockets and Pub/Sub.

Storage optimisation

  • Deduplication. Identical hashes are stored once. Do it per account, not globally: global dedup lets an attacker probe whether someone else holds a particular file by seeing whether the upload "completes instantly", a real attack on early cloud storage services. Per-account dedup still wins the common case of repeated copies and versions.
  • Version retention. Unbounded history is unbounded cost. Cap the number of versions or the age, and thin older ones (keep daily, then weekly) while keeping recent edits dense. Versions share blocks, so ten versions of a large file with small edits cost far less than ten copies.
  • Cold storage. Blocks not referenced by any current version, or belonging to files untouched for months, migrate to infrequent-access or archive tiers (S3 Glacier class). Retrieval is slower and costs money, so keep a small hot cache and have the UI set expectations.
  • Garbage collection. With refcounts, deleting a version decrements its blocks and a sweeper reclaims zeros after a grace period. Mark-and-sweep is safer against refcount drift; run it offline and never delete a block newer than the longest upload session.

Security

Encrypt in transit and at rest. Server-side keys per block or per namespace via a KMS is standard; client-side end-to-end encryption is stronger but breaks server-side dedup across users, preview generation and search, so it is a product decision. Sharing is a metadata operation (an ACL row), never a data copy, so revocation is instant. Signed, short-lived block URLs prevent hot-linking.

Block-based design wins

  • Resumable by default
  • Edits cost kilobytes, not gigabytes
  • Cheap history and dedup
  • Integrity via hashes

It costs

  • Reassembly latency on first open
  • More metadata to keep consistent
  • Garbage collection complexity
  • CPU for hashing/chunking on the client
Runnable code

Content-defined chunking, dedup, delta upload, and conflicts

The example implements a gear-hash content-defined chunker, a content-addressed block store with dedup, a metadata service whose commit is a compare-and-set on the base version, and a client that uploads only blocks the store lacks. It then demonstrates a 100-byte insert, a concurrent two-device conflict producing a conflicted copy, and dedup of an identical file.

JavaScript Example 
// Content-defined chunking + block dedup + delta sync + optimistic-concurrency conflicts.
import { createHash, randomBytes } from 'node:crypto';
import assert from 'node:assert/strict';

// --- gear table (deterministic so runs are reproducible) ---
let seed = 0x9e3779b9;
const rnd32 = () => (seed = (Math.imul(seed ^ (seed >>> 15), 0x2c1b3c6d) + 0x297a2d39) >>> 0);
const GEAR = Array.from({ length: 256 }, () => rnd32());

// Content-defined chunking: boundary where the rolling gear hash has `bits` low zero bits.
function chunk(buf, { minSize = 2048, maxSize = 65536, bits = 13 } = {}) {
  const mask = (1 << bits) - 1, out = [];
  let start = 0, h = 0;
  for (let i = 0; i < buf.length; i++) {
    h = ((h << 1) + GEAR[buf[i]]) >>> 0;
    const len = i - start + 1;
    if ((len >= minSize && (h & mask) === 0) || len >= maxSize) {
      out.push(buf.subarray(start, i + 1)); start = i + 1; h = 0;
    }
  }
  if (start < buf.length) out.push(buf.subarray(start));
  return out;
}
const sha = b => createHash('sha256').update(b).digest('hex');

// --- block server: account-level dedup store ---
class BlockStore {
  blocks = new Map(); bytesStored = 0; bytesUploaded = 0;
  has(h) { return this.blocks.has(h); }
  put(h, data) { this.bytesUploaded += data.length; if (!this.blocks.has(h)) { this.blocks.set(h, data); this.bytesStored += data.length; } }
}

// --- metadata service: versions with compare-and-set on base version ---
class Metadata {
  files = new Map(); // path -> { version, blocks:[hash], history:[] }
  commit(path, baseVersion, blockList, client) {
    const f = this.files.get(path) ?? { version: 0, blocks: [], history: [] };
    if (f.version !== baseVersion) return { ok: false, conflict: `${path} (conflicted copy from ${client})`, serverVersion: f.version };
    f.version++; f.blocks = blockList; f.history.push(blockList); this.files.set(path, f);
    return { ok: true, version: f.version };
  }
}

// --- client: delta upload = only blocks the server lacks ---
function push(client, store, meta, path, data, baseVersion) {
  const chunks = chunk(data), list = [];
  let sent = 0;
  for (const c of chunks) {
    const h = sha(c); list.push(h);
    if (!store.has(h)) { store.put(h, c); sent += c.length; }   // delta: skip known blocks
  }
  const res = meta.commit(path, baseVersion, list, client);
  if (!res.ok) { // keep both copies: save the loser under a conflicted name
    const r2 = meta.commit(res.conflict, 0, list, client);
    return { ...res, sent, savedAs: res.conflict, r2 };
  }
  return { ...res, sent, blocks: chunks.length };
}
const pull = (store, meta, path) => Buffer.concat(meta.files.get(path).blocks.map(h => store.blocks.get(h)));

// ---------------- demo + self test ----------------
const store = new BlockStore(), meta = new Metadata();
const v1 = randomBytes(600_000);
const r1 = push('laptop', store, meta, '/docs/big.bin', v1, 0);
console.log(`v1: ${r1.blocks} blocks, uploaded ${r1.sent} bytes, version ${r1.version}`);
assert.ok(r1.blocks > 20 && r1.blocks < 400);
assert.deepEqual(pull(store, meta, '/docs/big.bin'), v1);

// insert 100 bytes near the front: fixed-size blocks would shift everything, CDC resyncs after one or two blocks.
const v2 = Buffer.concat([v1.subarray(0, 1000), randomBytes(100), v1.subarray(1000)]);
const r2 = push('laptop', store, meta, '/docs/big.bin', v2, 1);
console.log(`v2 (insert 100B): uploaded ${r2.sent} bytes of ${v2.length} (${(100 * r2.sent / v2.length).toFixed(2)}%)`);
assert.ok(r2.sent < v2.length * 0.1, 'delta must be tiny');
assert.deepEqual(pull(store, meta, '/docs/big.bin'), v2);

// two devices edit from version 2 concurrently; first commit wins, second gets a conflicted copy
const a = Buffer.concat([v2, Buffer.from('phone edit')]);
const b = Buffer.concat([v2, Buffer.from('tablet edit')]);
const ra = push('phone', store, meta, '/docs/big.bin', a, 2);
const rb = push('tablet', store, meta, '/docs/big.bin', b, 2);
console.log('phone:', ra.ok, '| tablet:', rb.ok, '->', rb.savedAs);
assert.ok(ra.ok && !rb.ok && rb.r2.ok);
assert.deepEqual(pull(store, meta, rb.savedAs), b);

// dedup: another user (same account namespace) uploads the same bytes -> zero new storage
const before = store.bytesStored;
push('desktop', store, meta, '/copy/big.bin', v2, 0);
console.log('extra bytes stored for identical copy:', store.bytesStored - before);
assert.equal(store.bytesStored, before);
console.log('versions kept for big.bin:', meta.files.get('/docs/big.bin').history.length);
console.log('all assertions passed');

Prints the block count of v1, the tiny percentage re-uploaded after a 100-byte insert (about 2 percent, a few kilobytes of 600 KB), the phone commit succeeding and the tablet commit becoming a "(conflicted copy from tablet)", 0 extra bytes for an identical copy, and "all assertions passed". Executed with Node 20+.

Scaling and production

Knees and gotchas

  • Many small files break the model. A node_modules folder with 50,000 tiny files makes metadata, not bytes, the bottleneck. Batch metadata commits, pack small files into one block, and let clients ignore patterns.
  • Hot shared namespaces. A company-wide shared folder concentrates writes and notifications in one shard. Shard its change log separately or fan out notifications through pub/sub.
  • Initial sync stampede. New devices pull a whole tree. Rate-limit and prioritise recently modified files so the user sees something useful fast.
  • File-watcher races. OS file events fire before a program finishes writing, and "save" is often write-temp, rename. Debounce, hash after quiesce, handle atomic renames as moves, not delete plus create.
  • Case-insensitive file systems. "Report.doc" and "report.doc" are the same on macOS and Windows, different on Linux. Your path uniqueness rule has to pick one and detect collisions.
  • Per-request billing. Object stores charge per PUT/GET; very small blocks can cost more in requests than in bytes. Another reason to pick 1 to 4 MB over 64 KB.
  • Quota accounting should count unique referenced bytes per account, updated asynchronously, with a soft grace so a failed counter never blocks a save.
Checklist

Interview checklist

  • State the sizing correctly: 500 PB allocated from 50 M users × 10 GB; about 240 upload QPS.
  • Separate metadata (consistent, relational) from blocks (immutable, content-addressed).
  • Block servers: split, compress, encrypt, hash; 4 MB max; deduplicate per account.
  • Resumable upload sessions; pending versus uploaded state; change log with cursors.
  • Delta sync via block diff; mention content-defined chunking for insert robustness.
  • Conflict handling: version compare-and-set, keep both copies.
  • Notification by long poll as a hint, with polling as the safety net.
  • Cold tier, version limits, garbage collection.
  • Failure matrix: LB, block server, metadata, storage, notifications.
  • Security: TLS, encryption at rest, ACL-based sharing, side channel in global dedup.
FAQ · Common Questions

Frequently Asked Questions

Why not use the object store directly with whole files?

You lose resumability past a certain size, pay full-file transfer for tiny edits, store every version in full, and cannot dedup. Block granularity solves all four with one mechanism. For tiny files it degenerates to one block, so the cost is nil.

How do you ensure the client never sees a half-written file?

Versions are immutable and become visible only after every referenced block is durable. Clients download into a temp file, verify hashes, then atomically rename into place.

What if two users edit a shared document at once?

For ordinary files, the second writer receives a conflicted copy. For real-time co-editing, route to a collaborative editing service using OT or CRDTs and snapshot the result back into the file store periodically.

How would you reduce sync latency for large files?

Parallel block transfers, block-level delta, a nearby upload endpoint, LAN sync between devices on the same network, and starting downloads on other devices as soon as the first blocks commit rather than at file completion.

How do you support version history without exploding storage?

Versions share blocks, so cost is the changed blocks only. Add retention rules, thin older versions, and move unreferenced or old blocks to cold storage. Keep the metadata rows forever; they are tiny.

Where does consistency matter and where not?

Strongly consistent for path-to-version resolution, rename and permission changes. Eventual is fine for notifications, replicas of block data (since content-addressed blocks are immutable, a replica either has the block or does not), and quota counters. See Consistency Models.

Key Takeaway

Model a file as an ordered list of immutable content-hashed blocks plus a strongly consistent metadata row per version. Resume, delta sync, dedup, history and integrity all follow, conflicts become a simple compare-and-set on the base version, and change notification is just a hint over an append-only log.
