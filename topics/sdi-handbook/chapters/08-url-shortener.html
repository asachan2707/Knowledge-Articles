Design a URL Shortener

A URL shortener is a deceptively small system: one write path that mints a unique short code and one very hot read path that redirects. The interesting decisions are how you mint codes, which redirect status you return, and how you keep the read path in memory.

Long URLs are awkward: they break in emails, blow past SMS limits, look ugly in print, and cannot be typed from a poster. A shortener trades a tiny lookup table for a compact, shareable alias. It also quietly becomes a click-analytics and link-management product, which is where most of the commercial value sits.

Core idea: the system is a giant, append-mostly key-value map from a short code to a long URL. Everything hard is about (1) generating a code that is unique without a global bottleneck, and (2) serving roughly ten reads per write at memory speed with a redirect that the browser may or may not cache.

A well-known design

TinyURL, Bitly and the "id to base62" pattern

Public services such as TinyURL and Bitly popularised the simple trick that this chapter leans on: store every link under an integer primary key, then render that integer in a URL-safe alphabet. The database hands out dense integers, the encoder turns them into short strings, and decoding is the inverse arithmetic, so in principle you do not even need to index the code column. Most open-source shorteners and many internal "go/" link services follow the same shape. The variants differ mainly in where the integer comes from, which is why the previous chapter on unique-id generation is a prerequisite for this one.

Requirements and estimates

Pin the numbers before drawing boxes

Functional

  • Shorten: given a long URL, return a short URL. The same long URL may or may not map to the same code (decide, and say so).
  • Redirect: given a short URL, send the browser to the long URL.
  • Codes are as short as possible, made of URL-safe characters, and never collide.
  • Highly available, low latency on redirect, and tolerant of abusive traffic.

Back-of-envelope

Correction to the source notes: they quote 365 TB for ten years. With 365 billion records the figure only reaches 365 TB if each row is about 1 KB. A row is a 7-byte code, a long URL averaging a hundred-odd bytes, a timestamp and an owner id; 100 bytes per record gives 36.5 TB, and even a pessimistic 300 bytes with index overhead is about 110 TB. It is a ten-fold difference that decides whether you need a sharded cluster on day one or merely a replicated pair, so show your arithmetic in the interview.

The read side is the one that matters. About one billion redirects per day at roughly 100 bytes each is 100 GB of hot payload per day. Real traffic follows a power law (a few viral links take most clicks), so a cache holding the hottest 20% of a day, about 20 GB, fits comfortably in a single Redis node and gives you a very high hit ratio.

API design

Two endpoints, one important status code

RedirectGET /{shortCode}301 or 302 with a Location header; 404 if unknown; 410 if expired

Putting the code at the root path keeps the public URL as short as the domain permits. The redirect is the whole product, so it should be served by a thin stateless tier with nothing between it and the cache.

301 vs 302

The redirect status decides who gets the traffic

301 Moved Permanently

  • Browsers and intermediaries cache it, so repeat clicks never reach you.
  • Cuts server load and bandwidth for popular links.
  • Good when the link is truly immutable and you do not need per-click data.

302 Found (temporary)

  • Every click comes back to your servers, so you can count it, geo-tag it and A/B it.
  • You can change or revoke the destination later and users will see it.
  • Costs more traffic; you must size the redirect tier for the full click rate.

For a commercial shortener the answer is almost always 302 (or 307 when you want to preserve the HTTP method), because analytics and the ability to disable a malicious link are the product. A 301 is correct for an internal vanity-link service whose targets never change. Be aware that a 301 you shipped by mistake is effectively irreversible for clients that already cached it.

Code generation

Strategy A: unique id, then base62

Each new row gets a globally unique integer (from a ticket server, a database sequence with range allocation, or a Snowflake-style generator as in chapter 7). The integer is written in base 62 using [0-9a-zA-Z]. Decoding is the reverse sum of digit times 62 to the power of its position. The notes' worked example, id 2,009,215,674,938, comes out as zn9edcu; the code below reproduces it, so the arithmetic is verified.

 repeated division by 62, collecting remainders (least significant digit first):
  2009215674938 / 62 =  32406704434  remainder 30 -> u
    32406704434 / 62 =    522688781  remainder 12 -> c
      522688781 / 62 =      8430464  remainder 13 -> d
        8430464 / 62 =       135975  remainder 14 -> e
         135975 / 62 =         2193  remainder  9 -> 9
           2193 / 62 =           35  remainder 23 -> n
             35 / 62 =            0  remainder 35 -> z
 read the remainders bottom-up:  zn9edcu  (7 chars, since 62^6 <= id < 62^7)

Properties

  • Collisions are impossible by construction, so no read-before-write is needed to guarantee uniqueness.
  • Length grows with the id: under 62^6 (about 56.8 billion) codes are six characters, then seven. Seven characters covers 3.52 trillion codes, roughly ten times the ten-year need of 365 billion.
  • Needs a distributed id source, and the id source becomes a dependency of the write path.
  • Codes are sequential, hence guessable. Anyone can walk zn9edcu, zn9edcv, ... and enumerate other people's links. For unlisted or private links that is a real leak.

Hide the sequence without losing uniqueness. Multiply the id by a large constant coprime to 62^7 and take the result modulo 62^7 before encoding. Multiplication by a unit is a bijection on the residues, so uniqueness is preserved, the output looks random, and decoding uses the modular inverse. A Feistel network does the same job. Unlike truncating a hash, this cannot collide. If the links are security-sensitive, also add a random or signed component; obscurity alone is not authorization.

Getting ids without a hot spot

A single counter row is a bottleneck and a single point of failure. The practical pattern is range leasing: a small coordination service (ZooKeeper, etcd, or one database row updated with UPDATE ... SET next = next + 1000) hands each app server a block of, say, 1,000 ids. The server mints codes from its block in memory and only returns to the coordinator when the block runs out. Coordination traffic drops by three orders of magnitude, and a crash merely wastes the unused remainder of a block, which is harmless given the code space. Flickr's ticket servers (two databases handing out odd and even ids) are the classic precursor.

Code generation

Strategy B: hash the URL and handle collisions

Compute a hash such as CRC32, MD5 or SHA-1 of the long URL and keep the first seven characters of its base62 (or hex) form. The output is a fixed length and needs no id service. The problem is the pigeonhole principle: a truncated hash has far fewer bits than the digest.

CRC32 is only 32 bits, so its base62 form is about six characters and the collision rate is unacceptable at this scale. A truncated MD5 or SHA-1 can fill seven characters but still collides. The birthday arithmetic is unforgiving: once the table holds 10% of the 3.52 trillion code space (352 billion rows, which is where our ten-year plan ends), roughly one in ten new insertions hits an existing code, so the retry loop is a steady-state path, not an edge case.

  longURL --hash--> first 7 chars --> Bloom filter says "definitely new"?
                                         |yes                  |"maybe present"
                                         v                     v
                                   INSERT (code, long)    SELECT long WHERE code=?
                                                                |
                                           same long URL? return it | different? salt + rehash

Resolving collisions by appending a predefined string and rehashing works but costs a database lookup per attempt. A Bloom filter in front removes most of those lookups: if the filter says the code is absent, it is absent for certain, and you insert immediately. If it says "maybe present" you pay one read to disambiguate. Sizing is the usual rule: about 10 bits per element for a 1% false positive rate, so a filter over all 365 billion codes would be about 456 GB, which is why in practice you shard it or lean on the database's unique index and just retry on a duplicate-key error.

The cleanest correctness mechanism is not the filter at all, it is a unique constraint on the code column and an insert that retries with a salt on violation. The Bloom filter is an optimisation; the database is the arbiter. Two concurrent shortens of different URLs that hash to the same code cannot both succeed.

Trade-offs

Which strategy should you pick

DimensionCounter + base62Hash + collision handling
Code lengthGrows with the id (6 then 7 chars)Fixed
Needs an id generatorYesNo
CollisionsImpossibleFrequent at scale; must retry
Write path costOne insertHash, filter probe, maybe a read, insert, maybe retry
GuessableYes unless permutedNo, looks random
Same URL gives same codeOnly with an extra lookup indexNaturally, if you do not salt
Custom aliasesReserve in the same tableSame

My default is counter plus a keyed permutation plus base62: no collisions, one write, constant-time encode, and the one genuine weakness (enumeration) is closed cheaply. Choose the hash route only when you cannot operate any central id source, or you want idempotent shortening of identical URLs for free.

High-level design

Shorten and redirect flows

   WRITE (about 1.2K/s)                                         READ (about 12K/s, peak 23K/s)
   client                                                       client
     | POST longUrl                                               | GET /code
     v                                                            v
  [Rate limiter] -> [API server] --1. lookup longUrl?--> [DB / index]      [LB] -> [Redirect server]
                        | 2. new id (leased block)                             |  1. cache GET code
                        | 3. base62(id) = code                                  |  2. miss: DB read replica
                        | 4. INSERT (id, code, longUrl)                         |  3. fill cache, 302
                        v                                                       v
                    [DB primary] ---replicate--> [replicas]  --> [Redis]   [Kafka: click events -> analytics]

Shorten flow

  1. Check whether the long URL already exists (needs an index on the long URL or on its hash; skip this if you accept duplicates).
  2. If it exists, return the stored code.
  3. Otherwise take the next id, encode it, and persist the mapping.

Redirect flow

  1. Look up the code in the cache.
  2. On a miss read the database (a replica is fine; links are immutable after creation), then populate the cache.
  3. Return the redirect, and publish a click event to a queue off the critical path.

Because the data is write-once, the cache can be a plain read-through LRU with a long TTL and almost no invalidation problem. The only invalidations are deletes, expiry and edits, and those are rare enough to handle with an explicit cache delete plus a short TTL as a safety net.

Data model

Storage choice and sharding

The access pattern is a pure point lookup by code. The schema is tiny: code (primary key), long_url, created_at, optional expires_at and owner_id. If you use strategy A the integer id can be the primary key and the code is derived, so no secondary index on the code is needed at all. A relational database is fine at 36 TB with sharding, but a wide-column or key-value store (Cassandra, DynamoDB) matches the workload better: no joins, no cross-row transactions, easy horizontal scale.

Shard by the code (or its hash), not by creation time. Range-sharding on a sequential id sends every new write to the newest shard, the classic hot-partition problem; hashing the code spreads both writes and the viral-link reads. See DynamoDB hot partition sharding for what happens when one key is much hotter than the rest, which for a shortener is a single viral link: cache it, and consider replicating very hot keys in the cache tier.

Deep dive

Abuse, analytics, expiry and availability

  • Rate limiting. Limit shorten calls per IP and per API key, since otherwise one actor can exhaust the code space or host phishing at scale. Details in the rate limiter chapter.
  • Malicious destinations. A shortener hides where a link goes, which phishers love. Check submitted URLs against a safe-browsing style list, re-scan periodically, and keep the ability to disable a code instantly (another reason for 302).
  • Analytics. Emit an event per redirect (code, timestamp, user agent, coarse geo, referrer) to a log such as Kafka, aggregate asynchronously. Never let the analytics write sit in the redirect latency path.
  • Expiry. Store an optional expiry; enforce it at read time and reclaim rows in a background sweep. Do not recycle codes quickly, or stale links on printed material will point at someone else's content.
  • Custom aliases. Share the same namespace, validate the alphabet, and use the unique constraint to arbitrate races. Reserve system words such as api and admin.
  • Availability. The write tier can degrade; the read tier must not. Replicate across zones, keep a warm cache in each, and allow the redirect service to serve from cache if the database is down.
Hands-on

Base62, counter shortener, hash shortener and LRU in one file

This file implements both strategies end to end. It asserts the notes' base62 example, shows when 7 characters stop being enough, forces collisions by deliberately shrinking the hash code to 4 characters across 20,000 URLs, and verifies that retries still yield unique codes. The Bloom filter uses SHA-256 slices as its hash family, and the LRU uses a Map's insertion order.

JavaScript Example 
import assert from 'node:assert/strict';
import { createHash } from 'node:crypto';

const ALPHABET = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';

export function encode62(n) {
  let x = BigInt(n);
  if (x === 0n) return '0';
  let out = '';
  while (x > 0n) { out = ALPHABET[Number(x % 62n)] + out; x /= 62n; }
  return out;
}
export function decode62(s) {
  let x = 0n;
  for (const ch of s) {
    const d = ALPHABET.indexOf(ch);
    if (d < 0) throw new Error('bad char ' + ch);
    x = x * 62n + BigInt(d);
  }
  return x;
}

// Bloom filter for the "hash + collision" strategy
class Bloom {
  constructor(bits = 1 << 16, k = 4) { this.bits = new Uint8Array(bits >> 3); this.m = bits; this.k = k; }
  #idx(s) {
    const h = createHash('sha256').update(s).digest();
    return Array.from({ length: this.k }, (_, i) => h.readUInt32BE(i * 4) % this.m);
  }
  add(s) { for (const i of this.#idx(s)) this.bits[i >> 3] |= 1 << (i & 7); }
  has(s) { return this.#idx(s).every(i => this.bits[i >> 3] & (1 << (i & 7))); }
}

// Strategy A: counter -> base62 (permuted to avoid guessable sequence)
export class CounterShortener {
  constructor() { this.next = 1_000_000_000n; this.byShort = new Map(); this.byLong = new Map(); }
  shorten(longUrl) {
    if (this.byLong.has(longUrl)) return this.byLong.get(longUrl);
    const id = this.next++;
    const short = encode62(id);
    this.byShort.set(short, longUrl); this.byLong.set(longUrl, short);
    return short;
  }
  resolve(s) { return this.byShort.get(s); }
}

// Strategy B: hash prefix + salt-on-collision (DB is source of truth, bloom is a fast negative check)
export class HashShortener {
  constructor(len = 7) { this.len = len; this.db = new Map(); this.bloom = new Bloom(); this.dbLookups = 0; }
  shorten(longUrl) {
    for (let attempt = 0; ; attempt++) {
      const digest = createHash('sha256').update(longUrl + (attempt ? '#' + attempt : '')).digest();
      const short = encode62(BigInt('0x' + digest.subarray(0, 6).toString('hex'))).padStart(this.len, '0').slice(0, this.len);
      if (!this.bloom.has(short)) { this.db.set(short, longUrl); this.bloom.add(short); return short; }
      this.dbLookups++; // possible collision: confirm in DB
      const existing = this.db.get(short);
      if (existing === longUrl) return short; // same URL already stored
      // true collision -> retry with salt
    }
  }
}

// LRU cache for the redirect path
export class LRU {
  constructor(cap) { this.cap = cap; this.m = new Map(); }
  get(k) { if (!this.m.has(k)) return undefined; const v = this.m.get(k); this.m.delete(k); this.m.set(k, v); return v; }
  set(k, v) { this.m.delete(k); this.m.set(k, v); if (this.m.size > this.cap) this.m.delete(this.m.keys().next().value); }
}

// ---- self test ----
assert.equal(encode62(2009215674938n), 'zn9edcu');
assert.equal(decode62('zn9edcu'), 2009215674938n);
assert.equal(62n ** 7n, 3521614606208n);
assert.equal(encode62(62n ** 7n - 1n).length, 7);
assert.equal(encode62(62n ** 7n).length, 8);
console.log('base62(2009215674938) =', encode62(2009215674938n));
console.log('62^7 =', 62n ** 7n, ' 100M/day * 365 * 10 =', 100_000_000n * 3650n, 'urls ->', encode62(100_000_000n * 3650n).length, 'chars');

const c = new CounterShortener();
const a = c.shorten('https://example.com/a'), b = c.shorten('https://example.com/b');
assert.notEqual(a, b); assert.equal(c.shorten('https://example.com/a'), a);
console.log('counter:', a, b, '->', c.resolve(a));

const h = new HashShortener(4); // tiny length to force collisions
const seen = new Set();
for (let i = 0; i < 20000; i++) seen.add(h.shorten('https://example.com/page/' + i));
assert.equal(seen.size, 20000);
console.log('hash(4 chars): 20000 urls, all unique codes:', seen.size, ', collision DB checks:', h.dbLookups);

const cache = new LRU(2); cache.set('x', 1); cache.set('y', 2); cache.get('x'); cache.set('z', 3);
assert.equal(cache.get('y'), undefined); assert.equal(cache.get('x'), 1);

Run with node shortener.mjs. Prints base62(2009215674938) = zn9edcu, the 7-character capacity check (365 billion fits in 7 chars), two counter-issued codes, 20,000 unique 4-character hash codes with about 2,200 collision database checks, and "LRU ok". All assertions pass.

Scaling and production gotchas

Where the knees are

  • Redirect tier scales linearly and statelessly; the first real limit is cache memory and network, not CPU.
  • The write path is 10x smaller than reads, so a modest primary with replicas carries it far; shard the database when storage, not QPS, forces you, around the tens of terabytes.
  • URL validation matters: reject non-http schemes (javascript:, file:), normalise, cap length, and block your own domain to prevent redirect loops.
  • Case-sensitive codes (aB vs ab) bite when someone reads the code aloud or the storage layer is case-insensitive. Decide up front; some services drop to base36 or remove look-alike characters (0/O, 1/l) to trade length for legibility.
  • Never reuse a deleted code immediately, and keep a tombstone so you can return 410 instead of silently redirecting somewhere new.
  • Time-to-first-byte of the redirect is the metric to watch; measure the 99th percentile including cache misses.
Checklist

Interview checklist

  • State write QPS, read QPS, record count and storage with arithmetic, and justify 7 characters.
  • Choose 301 or 302 and give the reason (caching vs analytics and control).
  • Pick a code strategy, name its failure (collisions or guessability) and its fix.
  • Explain how uniqueness is enforced under concurrency (unique constraint, not just a filter).
  • Put a cache in front of reads, and shard by code hash not by time.
  • Cover rate limiting, malicious links, analytics off the hot path, expiry and availability.
FAQ · Common Questions

Frequently Asked Questions

Why base62 and not base64?

Standard base64 includes + and /, which have meaning in URLs and need escaping, and pads with =. URL-safe base64 swaps in - and _ and works fine too; base62 is simply the largest purely alphanumeric alphabet, which avoids any encoding ambiguity and survives copy-paste, word-wrapping and voice dictation better.

Should the same long URL always give the same short code?

Not necessarily. Deduplication saves space and makes the call idempotent, but costs an index on the long URL and prevents per-user links (two people shortening the same page want separate click statistics). Many commercial services create a new code per request and dedupe only within an account.

How do I stop people guessing other codes?

Permute the id with a keyed bijection before encoding, or use random codes with a collision check. For genuinely private content do not rely on code secrecy at all: require authentication, or embed a signed token.

What happens if two servers generate the same code?

With leased id blocks it cannot happen because blocks are disjoint. With hashing it can; the unique constraint rejects the second insert and the writer retries with a salt. That is why the database, not the Bloom filter, is the source of truth.

How would you add expiring links and click limits?

Store expires_at and an optional remaining-clicks counter. Expiry is a read-time check plus a background delete. A click budget needs an atomic decrement (a Redis DECR or a conditional database update) and forces you onto a 302 so every click is observed.

How do you scale the cache for a billion reads a day?

One billion reads is only about 12K per second on average, trivial for Redis. Use a replicated cache for availability, consistent hashing if you outgrow one node, a small in-process cache for the hottest handful of codes, and coalesce simultaneous misses on the same key to avoid a stampede.

Key Takeaway

A URL shortener is a write-once key-value map with a hot read path. Mint codes from unique integers rendered in base62 (permute them if guessability matters), enforce uniqueness in the database, serve redirects from a read-through cache, and choose 302 when you want to keep control and analytics. Fix the storage arithmetic: 365 billion rows at about 100 bytes is roughly 36.5 TB, not 365 TB.
