Design a Key-Value Store

A distributed key-value store combines a partitioning ring, N-way replication, tunable quorums, vector-clock versioning, gossip failure detection, hinted handoff, Merkle-tree repair and an LSM-style storage engine. This chapter assembles those pieces into a Dynamo-style, leaderless, highly available design and explains the consistency trade-off behind each one.

A key-value store is the simplest database interface that still matters: put(key, value) and get(key). Because the interface is tiny, a distributed implementation can spend all its complexity budget on the hard parts: staying up when machines die, staying fast under load, and staying roughly consistent when the network misbehaves. This chapter is where most of the distributed-systems vocabulary of the whole handbook is introduced.

Core idea: partition with a consistent-hash ring, replicate each key to N nodes, let clients pick how many acknowledgements (W for writes, R for reads) they need, version values with vector clocks, and use background repair (hinted handoff, Merkle trees) so that replicas converge. No node is special, so no node is a single point of failure.

A well-known public design

The Dynamo paper

In 2007 Amazon engineers published "Dynamo: Amazon's Highly Available Key-value Store". The motivating requirement, stated in the paper, was that shopping-cart-style workloads should always accept writes, even during failures, and that an "always writeable" store was worth the price of occasionally returning conflicting versions that the application must merge. Dynamo combined consistent hashing, vector clocks, sloppy quorums with hinted handoff, Merkle-tree anti-entropy and gossip membership. Cassandra and Riak adopted large parts of that design (Cassandra grafted it onto a Bigtable-style storage engine). Note that today's managed DynamoDB service shares the name and the spirit but not the leaderless internals: it uses per-partition replication groups with a leader. When someone says "Dynamo-style", they mean the paper.

The single-server baseline

Start with a hash table in memory: O(1) get and put. Squeeze it by compressing values and keeping cold data on disk, but you quickly hit the limits of one machine's memory, one machine's failure, and one machine's network card. Hence the distributed design. The rest of this chapter makes explicit what we give up to get there.

Theory

CAP, stated carefully

The CAP theorem says that when a network partition splits a replicated system, you must choose between consistency (every read sees the latest write, linearizably) and availability (every non-failed node answers). Partition tolerance is not an option you can decline: networks do partition, so the real decision is "when the partition happens, which one do I give up?".

n1 ──── n2 ──── n3 partition: [n1 n2] |X| [n3] CP choice: refuse writes (and maybe reads) on the minority side → consistent, but unavailable there AP choice: keep serving both sides → available, replicas diverge, reconcile after the heal
  • CP systems (etcd, ZooKeeper, Spanner-style systems; ledgers) sacrifice availability in the minority partition. Right for locks, configuration, money.
  • AP systems (Dynamo, Cassandra at low consistency levels, Riak) keep accepting requests and reconcile later. Right for carts, sessions, feeds, counters of low stakes.
  • "CA" is a mirage for distributed systems. A single-node database is CA only because there is no network between replicas to partition. Once data lives on several nodes, partitions will happen.
CAP is only the partition-time story. The more useful framing is PACELC: if there is a Partition choose A or C; Else, even with no failure, you still trade Latency for Consistency, because waiting for more replicas costs time. A Dynamo-style system is PA/EL: available during partitions, low-latency otherwise. The N/W/R dial below is how you move along that second axis.

This chapter builds an AP, leaderless design. That is a decision to be defended in an interview by naming the workload: "we accept stale reads and application-level conflict resolution because blocking writes would cost more than occasional conflicts."

Component 1

Data partitioning

Keys are spread over nodes using the consistent-hash ring from chapter 5. Properties we need and get: automatic scaling (add a node and it takes over only its arcs), and heterogeneity via virtual nodes (a bigger machine takes more vnodes, so more data). Because the key's position determines its home, any node can compute where a key lives without a central directory, which is what makes the design decentralised.

ring positions (vnodes of 5 physical nodes: n1..n5) get("cart:7") → hash → position p → first vnode clockwise → coordinator all nodes can compute this locally; clients may be ring-aware or contact any node
Component 2

Data replication

To survive failures, each key is stored on N nodes (commonly N = 3). The rule is the preference list from chapter 5: starting from the key's position, walk clockwise and take the first N distinct physical nodes, skipping vnodes that belong to a machine already chosen. Better, spread replicas across racks and availability zones, and (for disaster tolerance) across data centers, so that a single power or network domain cannot hold all copies.

key k at position p, N = 3 ring → [ n1 ] [ n2 ] [ n3 ] [ n4 ] ... k → n1 (coordinator) , n2 , n3 hold copies n4 takes over the 3rd copy if n3 is down (sloppy quorum, below)
Component 3

Consistency: quorum consensus

Replicas must agree "enough". The knobs are:

  • N: number of replicas per key.
  • W: replicas that must acknowledge a write before it is reported successful.
  • R: replicas that must answer a read before the coordinator returns.

The coordinator sends each request to all N replicas in parallel and returns as soon as the W-th (or R-th) response arrives. This is a latency optimisation: you wait for the W-th fastest of N, which cuts the tail compared with waiting for a specific node.

Setting (N=3)BehaviourTypical use
W=1, R=1Fastest, weakest: stale reads likelyMetrics, caches, session data
W=2, R=2W + R > N: read set overlaps write set; tolerates one failure on either pathThe default balanced choice
W=N, R=1Fast reads, slow and fragile writesRead-heavy data
W=1, R=NFast writes, slow readsWrite-heavy ingest read rarely
W + R ≤ NNo guaranteed overlap; eventual consistency onlyAvailability-first workloads
W + R > N is necessary, not sufficient, for strong consistency. It guarantees that a read quorum contains at least one replica that saw the latest acknowledged write, but it does not give linearizability on its own. Sloppy quorums can write to stand-in nodes outside the preference list so the overlap disappears; concurrent writes can still conflict; a failed write that reached fewer than W replicas can be observed by some readers and not others; and last-write-wins resolution depends on clocks. Call it "strongly consistent in the absence of failures and concurrency", not linearizable.

Consistency models, in plain terms

  • Strong (linearizable): every read returns the most recent completed write. Requires consensus or a single leader per key.
  • Weak: after a write, reads may or may not see it, with no promise about when.
  • Eventual: a special weak form; if writes stop, all replicas converge. Dynamo-style stores target this, and add session guarantees (read-your-writes through sticky coordinators or higher R).
Component 4

Inconsistency resolution with vector clocks

With replicas accepting writes independently, two clients can update the same key at the same time through different coordinators. There is no single correct order, so the system must detect that the writes were concurrent rather than silently pick one. Treat every update as an immutable new version and attach a vector clock.

How a vector clock works

  • A clock is a map from node id to counter, written D([S1, 2], [S2, 1]).
  • When node Si coordinates a write, it takes the clock from the version the client read (the context), increments its own entry (adding it as 1 if absent), and stores the new version.
  • Comparison. Clock X is an ancestor of Y (X happened before Y, Y supersedes X) if every counter in X is less than or equal to its counterpart in Y (missing counts as 0). If neither dominates, the versions are concurrent, called siblings. Equal clocks are the same version.
v1 = D([S1,1]) client A reads v1, writes via S1 → v2 = D([S1,2]) v1 → read by B too, B writes via S2 → v3 = D([S1,1],[S2,1]) compare v2 vs v3: S1: 2 > 1 (v2 ahead) S2: 0 < 1 (v3 ahead) → CONCURRENT (siblings) client reads both, merges, writes via S3 with merged context: v4 = D([S1,2],[S2,1],[S3,1]) dominates v2 and v3 → siblings collapse

On reads, the coordinator gathers R responses, discards any version that is an ancestor of another, and returns all remaining siblings with their clocks. The application merges them (union the carts, keep the later edit of a document, apply a domain rule) and writes back with the combined clock as context, which supersedes both. If the application does not merge, siblings accumulate.

ApproachProsCons
Vector clocks + client mergeNever silently loses a write; correct causalityComplexity pushed to clients; sibling explosion; clock growth
Last-write-wins by timestamp (Cassandra's default per-cell)Trivial; no siblings; bounded metadataSilently drops concurrent writes; clock skew can make an older write win
CRDTs (counters, sets, registers)Automatic, mathematically convergent mergeOnly for data types that fit the merge model

Clock growth

Entries accumulate as more nodes coordinate writes for a key, so the clock can grow without bound. Dynamo stores a timestamp with each entry and drops the oldest once the clock exceeds a threshold (for example 10 entries). That can in principle lose causality information and turn a true ancestor into an apparent sibling, but the paper reports that it did not matter in production. Riak later moved to dotted version vectors to control sibling explosion.

Component 5

Handling failures

a. Failure detection: gossip

One node declaring another dead is a rumour, not a fact; the link between them may be at fault. Systems require corroboration. In a gossip protocol each node keeps a membership list with a heartbeat counter per member, increments its own counter periodically, and every second or so sends its list to a few random peers, who merge it (taking the higher counter per member). If a member's counter has not advanced for a configured period, it is suspected down; if several nodes agree, it is marked down. Gossip needs no central monitor, scales logarithmically in rounds to spread information (about log N rounds), and tolerates its own failures. Practical systems refine the binary alive/dead question into a suspicion level, for example the phi-accrual detector used by Cassandra, which adapts to network jitter.

n1 table: {n1:104, n2:98, n3:77, n4:101} ← n3 hasn't advanced in a while every tick: n1 bumps its own counter, sends the table to 2-3 random peers peers merge by max(); n3 stale across several nodes' views → marked down

b. Temporary failures: sloppy quorum and hinted handoff

A strict quorum would block writes if too many of the N designated nodes are unreachable. A sloppy quorum relaxes this: use the first W (or R) healthy nodes found walking the ring, skipping unreachable ones. If n3 is down, the replica write goes to n4 instead, tagged with a hint saying "this belongs to n3". When failure detection sees n3 return, n4 hands the data back (hinted handoff) and deletes its temporary copy. This keeps the store always writeable. The cost: during the outage, the quorum overlap guarantee is gone, which is exactly the availability-over-consistency choice.

strict: put → n1 n2 n3(down) → W=2 achieved by n1,n2 only if both up sloppy: put → n1 n2 [n4 holds hint for n3] → W met even if n1 or n2 also down n3 returns → n4 streams hint to n3 → n4 drops it

Operational limits: hints are stored for a bounded time (hours), because a node that is down for days must be rebuilt, not replayed. And hints add write load on stand-ins at the worst time.

c. Permanent failures: anti-entropy with Merkle trees

Hinted handoff cannot repair a node that was gone too long, or a replica that silently lost or corrupted data. Anti-entropy compares replicas and copies only differences. Comparing every key is too expensive, so each replica builds a Merkle (hash) tree over its key range:

  1. Divide the key space into buckets (for example 1,024).
  2. Hash each key-value pair, then hash the pairs in a bucket into one leaf hash.
  3. Hash pairs of children upward until a single root hash summarises the range.
root = H(h12 + h34) / \ h12 = H(b1+b2) h34 = H(b3+b4) / \ / \ hash(b1) hash(b2) hash(b3) hash(b4) leaf = hash of the keys in that bucket compare roots: equal → replicas identical, stop. differ → compare children, recurse only into mismatching subtrees → find bad buckets → sync those keys

Cost is proportional to the amount of divergence, not the data size: with one bad bucket among 1,024 you exchange about log2(1024) = 10 levels of hashes and then one bucket's keys. Practical issue: when a node joins or leaves, the key ranges change, so trees must be recomputed; Dynamo noted this as a drawback and Cassandra runs repair as an explicit, rate-limited operation. The example code below uses 8 buckets to keep the output readable.

d. Data-centre outages

Replicate across multiple data centers (the preference list is chosen to span them), so a whole site can go dark and quorums can still be met elsewhere. Consistency levels like "local quorum" (acknowledge within the local DC, replicate asynchronously to the others) keep latency low and make cross-DC failures a repair problem rather than a request-path problem.

Storage engine

Write path, read path and compaction

Each node stores its share using a log-structured merge (LSM) design, the Bigtable and Cassandra approach. The goal is to turn random writes into sequential ones.

Write path

  1. The coordinator forwards the write to the replicas.
  2. Each replica appends to a commit log on disk (sequential, fsynced per policy). This gives durability across crashes.
  3. It inserts the entry into an in-memory sorted structure, the memtable.
  4. When the memtable fills, it is flushed to an immutable sorted file on disk, an SSTable (sorted string table), and the corresponding commit-log segment is retired.
put ──▶ [commit log] (sequential append, durable) └──▶ [memtable] (in RAM, sorted) ── full → flush ──▶ SSTable-1, SSTable-2, SSTable-3 ... (immutable, sorted, on disk) background compaction merges SSTables, drops overwritten values and tombstones

Read path

  1. Check the memtable (and any memory cache). A hit is the freshest data.
  2. On a miss, consult each SSTable's Bloom filter, a compact probabilistic set that can say "definitely not here" or "maybe here". Only SSTables that answer "maybe" are read, via a sparse index to the right block.
  3. Merge the results (newest timestamp or clock wins, or siblings are returned) and answer.
get ──▶ memtable ──miss──▶ for each SSTable: Bloom filter ──no──▶ skip └──maybe──▶ index → block read ──▶ merge newest

A Bloom filter with about 10 bits per key and 7 hash functions gives roughly a 1 percent false-positive rate, so a read for an absent key touches an SSTable in only about 1 of 100 cases per file instead of every file. Without filters, read amplification would be one disk seek per SSTable.

  • Compaction merges SSTables to bound read amplification and reclaim space. Strategies trade write amplification (rewriting data repeatedly) for read performance: size-tiered favours write throughput, leveled favours reads and space.
  • Deletes are writes. A delete inserts a tombstone that must be replicated and kept longer than the maximum repair interval; otherwise a replica that missed the delete can resurrect the data ("zombie" values).
  • Why LSM? Appends and flushes are sequential, which suits SSDs and especially HDDs (see the latency numbers in chapter 2). The price is read and compaction complexity.

The coordinator is a role, not a server: whichever node receives the request (or the ring-aware client library, which avoids an extra hop) plays it for that operation. Every node therefore has the same responsibilities, which is what removes the single point of failure and lets membership change automatically.

Trade-offs

Leaderless versus leader-based, and when to choose which

Leaderless (Dynamo-style)

  • Always writeable; no failover pause.
  • Latency tail cut by quorum of fastest replicas.
  • Natural multi-DC.
  • Elastic scaling.

Costs

  • Conflicts surface to the application.
  • No transactions or secondary indexes by default.
  • Read repair, hints and anti-entropy to operate.
  • Hard to reason about stale reads.

If your data needs uniqueness constraints, transactions, or strictly ordered updates (payments, inventory), pick a leader-based, consensus-backed store (Spanner-style systems, etcd, a relational primary with replicas). If you need massive, always-on, low-latency key access with tolerable staleness (carts, profiles, session, feature flags at scale, time-series events), the leaderless design shines. Many companies use both.

Code

Runnable example: a mini-Dynamo

One file, no dependencies: a consistent-hash ring with vnodes, N/W/R quorum put and get, vector clocks with sibling detection and client merge, sloppy quorum with hinted handoff, and Merkle-tree anti-entropy that repairs only the divergent bucket. Network failures are simulated by flipping a node's up flag.

JavaScript Example 
import assert from 'node:assert/strict';
import { createHash } from 'node:crypto';

const h32 = s => createHash('sha1').update(s).digest().readUInt32BE(0);

// ---------- vector clocks ----------
const vcInc = (vc, node) => ({ ...vc, [node]: (vc[node] ?? 0) + 1 });
export function vcCompare(a, b) {            // 'before' | 'after' | 'equal' | 'concurrent'
  let aLess = false, bLess = false;
  for (const k of new Set([...Object.keys(a), ...Object.keys(b)])) {
    const x = a[k] ?? 0, y = b[k] ?? 0; if (x < y) aLess = true; if (x > y) bLess = true;
  }
  return aLess && bLess ? 'concurrent' : aLess ? 'before' : bLess ? 'after' : 'equal';
}
const vcMerge = (a, b) => { const o = { ...a }; for (const [k, v] of Object.entries(b)) o[k] = Math.max(o[k] ?? 0, v); return o; };
// keep only versions not dominated by another (the "siblings")
function reconcile(versions) {
  return versions.filter((v, i) => !versions.some((w, j) => i !== j && vcCompare(v.vc, w.vc) === 'before'))
    .filter((v, i, arr) => arr.findIndex(w => vcCompare(w.vc, v.vc) === 'equal') === i);
}

// ---------- Merkle tree over key buckets ----------
const sha = s => createHash('sha1').update(s).digest('hex');
export function merkle(store, buckets = 8) {
  const leaves = Array.from({ length: buckets }, (_, b) => {
    const items = [...store].filter(([k]) => h32(k) % buckets === b).sort().map(([k, v]) => k + '=' + JSON.stringify(v.map(x => x.value)));
    return sha(items.join('|'));
  });
  const levels = [leaves];
  while (levels.at(-1).length > 1) {
    const cur = levels.at(-1), next = [];
    for (let i = 0; i < cur.length; i += 2) next.push(sha(cur[i] + (cur[i + 1] ?? '')));
    levels.push(next);
  }
  return levels;                                  // levels.at(-1)[0] is the root
}
export function diffBuckets(a, b, level = a.length - 1, idx = 0, out = []) {
  if (a[level][idx] === b[level][idx]) return out;          // identical subtree: stop
  if (level === 0) { out.push(idx); return out; }
  diffBuckets(a, b, level - 1, idx * 2, out);
  if (idx * 2 + 1 < a[level - 1].length) diffBuckets(a, b, level - 1, idx * 2 + 1, out);
  return out;
}

// ---------- the cluster: ring + quorum + sloppy quorum + hinted handoff ----------
export class Cluster {
  constructor(names, { N = 3, W = 2, R = 2, vnodes = 64 } = {}) {
    Object.assign(this, { N, W, R });
    this.nodes = Object.fromEntries(names.map(n => [n, { up: true, store: new Map(), hints: [] }]));
    this.ring = names.flatMap(n => Array.from({ length: vnodes }, (_, i) => [h32(`${n}#${i}`), n])).sort((a, b) => a[0] - b[0]);
  }
  walk(key) {                                      // all distinct nodes clockwise from the key
    const p = h32(key); let i = this.ring.findIndex(([pos]) => pos >= p); if (i < 0) i = 0;
    const out = [];
    for (let s = 0; s < this.ring.length && out.length < Object.keys(this.nodes).length; s++)
      { const n = this.ring[(i + s) % this.ring.length][1]; if (!out.includes(n)) out.push(n); }
    return out;
  }
  put(key, value, ctx = {}, { sloppy = true } = {}) {
    const walk = this.walk(key), home = walk.slice(0, this.N), coord = walk.find(n => this.nodes[n].up);
    const vc = vcInc(ctx, coord), ver = { value, vc };
    let acks = 0; const stand = walk.slice(this.N).filter(n => this.nodes[n].up);
    for (const n of home) {
      if (this.nodes[n].up) { this.#apply(n, key, ver); acks++; }
      else if (sloppy && stand.length) { this.nodes[stand.shift()].hints.push({ for: n, key, ver }); acks++; }
    }
    if (acks < this.W) throw new Error(`write quorum failed (${acks}/${this.W})`);
    return vc;
  }
  get(key) {
    const home = this.walk(key).slice(0, this.N).filter(n => this.nodes[n].up);
    if (home.length < this.R) throw new Error('read quorum failed');
    const seen = home.slice(0, this.R).flatMap(n => this.nodes[n].store.get(key) ?? []);
    return reconcile(seen);                        // >1 result means siblings -> client must merge
  }
  #apply(n, key, ver) { const s = this.nodes[n].store; s.set(key, reconcile([...(s.get(key) ?? []), ver])); }
  recover(name) {                                  // node returns; stand-ins hand hints back
    this.nodes[name].up = true;
    for (const o of Object.values(this.nodes)) {
      const keep = []; for (const hnt of o.hints) hnt.for === name ? this.#apply(name, hnt.key, hnt.ver) : keep.push(hnt);
      o.hints = keep;
    }
  }
  antiEntropy(a, b) {                              // Merkle-guided repair; returns buckets repaired
    const ta = merkle(this.nodes[a].store), tb = merkle(this.nodes[b].store), bad = diffBuckets(ta, tb);
    for (const [k] of new Map([...this.nodes[a].store, ...this.nodes[b].store]))
      if (bad.includes(h32(k) % 8)) { const m = reconcile([...(this.nodes[a].store.get(k) ?? []), ...(this.nodes[b].store.get(k) ?? [])]);
        this.nodes[a].store.set(k, m); this.nodes[b].store.set(k, m); }
    return bad;
  }
}

// ---------- tests ----------
// vector clocks
assert.equal(vcCompare({ s1: 1 }, { s1: 2 }), 'before');
assert.equal(vcCompare({ s1: 2, s2: 1 }, { s1: 2, s3: 1 }), 'concurrent');
assert.equal(vcCompare(vcMerge({ s1: 2, s2: 1 }, { s1: 2, s3: 1 }), { s1: 2, s2: 1 }), 'after');

const c = new Cluster(['n1', 'n2', 'n3', 'n4', 'n5']);
const ctx1 = c.put('cart:7', ['milk']);
let r = c.get('cart:7'); assert.equal(r.length, 1);
// two clients write concurrently from the same context -> siblings
const home = c.walk('cart:7').slice(0, 3);
// simulate two replicas that each accepted a different write (e.g. during a partition):
c.nodes[home[0]].store.set('cart:7', [{ value: ['milk', 'eggs'], vc: { ...ctx1, a: 1 } }]);
c.nodes[home[1]].store.set('cart:7', [{ value: ['milk', 'bread'], vc: { ...ctx1, b: 1 } }]);
c.nodes[home[2]].store.set('cart:7', []);
r = c.get('cart:7'); assert.equal(r.length, 2); console.log('siblings detected:', r.map(x => x.value.join('+')));
const merged = c.put('cart:7', ['milk', 'eggs', 'bread'], r.reduce((m, x) => vcMerge(m, x.vc), {}));
assert.equal(c.get('cart:7').length, 1); console.log('after client merge ->', c.get('cart:7')[0].value.join('+'));

// sloppy quorum + hinted handoff
const key = 'user:99', w = c.walk(key), down = w[0];
c.nodes[down].up = false;
c.put(key, 'v1');                                              // still succeeds (W=2 of 3 live)
assert.equal(c.get(key)[0].value, 'v1');
const standIn = w.slice(3).find(n => c.nodes[n].hints.length);
console.log(`${down} down; hint parked on ${standIn}`);
assert.ok(standIn);
c.recover(down); assert.equal(c.nodes[down].store.get(key)?.[0].value, 'v1');

// quorum failure when too many replicas die (strict mode)
const d = new Cluster(['a', 'b', 'c'], { N: 3, W: 2, R: 2 });
const dw = d.walk('k'); d.nodes[dw[0]].up = d.nodes[dw[1]].up = false;
assert.throws(() => d.put('k', 1, {}, { sloppy: false }), /write quorum failed/);

// Merkle anti-entropy: replicas diverge in one key; repair touches only that bucket
const x = new Cluster(['p', 'q', 'r']); for (let i = 0; i < 200; i++) x.put('k' + i, i);
x.nodes.p.store.delete('k17');
const bad = x.antiEntropy('p', 'q'); console.log('anti-entropy repaired buckets:', bad);
assert.ok(bad.length >= 1 && bad.length <= 3);
assert.deepEqual(merkle(x.nodes.p.store).at(-1), merkle(x.nodes.q.store).at(-1));
console.log('all checks passed');

Prints "siblings detected: [ 'milk+eggs', 'milk+bread' ]" and "after client merge -> milk+eggs+bread", then which stand-in node holds the hint while n1 is down, which Merkle bucket was repaired, and "all checks passed". Executed with node.

Failure modes

What goes wrong in a Dynamo-style store

Scaling and production

Gotchas

  • Read repair. When the coordinator sees that some of the R replicas returned stale data, it should write the newest version back to them in the background. It is cheap and heals hot keys quickly.
  • Speculative retries. If one replica is slow, send the request to another after a percentile-based delay, rather than waiting for a timeout. This tames tail latency.
  • Idempotent writes. Clients retry. Use idempotent operations or request ids so a retried put does not create a spurious sibling.
  • Size limits. Keep values small. Large values blow up memtable flushes, repair streams and sibling payloads.
  • Capacity headroom. Keep disks well under full: compaction needs scratch space, and a failed node's data must be re-replicated onto survivors.
  • Consistency level per call. Use stronger levels for rare critical reads, and weaker for bulk. Document which paths use which.
  • Upgrades and membership churn. Do rolling restarts one node at a time and wait for gossip to settle and hints to drain before the next.
Checklist

Design checklist

  • State the CAP/PACELC position and the workload that justifies it.
  • Ring with vnodes; replicas on distinct nodes, racks and DCs.
  • N, W, R chosen with the latency/consistency reasoning; limits of W + R > N acknowledged.
  • Conflict strategy: vector clocks plus merge, LWW, or CRDT, and why.
  • Failure detection (gossip), temporary (sloppy quorum, hints) and permanent (Merkle anti-entropy) handling.
  • Write path (commit log, memtable, SSTable), read path (cache, Bloom filter), compaction and tombstones.
  • Coordinator role, symmetric nodes, no SPOF, multi-DC story.
FAQ · Common Questions

Frequently Asked Questions

Does W + R > N give me strong consistency?

Only a weaker, conditional form. Overlap ensures a read quorum intersects the latest acknowledged write's quorum, but sloppy quorums, concurrent writers, partial writes and clock-based resolution break linearizability. If you need it, use a consensus-based store (Raft or Paxos per partition) or a single leader per key.

Why vector clocks instead of timestamps?

Timestamps from different machines cannot establish causality reliably and force silent loss of concurrent writes. Vector clocks say precisely whether one write saw the other. The price is larger metadata and client merging, so many systems choose LWW deliberately for data where last-writer-wins is acceptable.

What is the difference between hinted handoff and anti-entropy?

Hinted handoff is a fast path for short outages: a stand-in holds writes the downed replica missed. Anti-entropy with Merkle trees is the slow, thorough path that detects any divergence (long outages, lost hints, bit rot) by comparing hashes. A robust system needs both.

How does a read differ from a write when R=2, W=2, N=3?

A write goes to all three replicas and succeeds on two acknowledgements. A read asks all three (or two plus a background third), returns after two answers, picks the newest by clock, and repairs stale replicas in the background. Because any 2 of 3 overlap with any other 2 of 3, a read sees at least one copy of the last acknowledged write.

How do you add a node without downtime?

The new node joins the ring, claims its vnodes, learns the membership via gossip, streams the data for its ranges from the current owners, and only then begins to serve reads for those ranges. Existing owners keep serving until the handover completes, then discard moved data. Bootstrapping one node at a time keeps load bounded.

Why are Bloom filters safe to use in the read path?

They have no false negatives: if the filter says a key is absent from an SSTable, it truly is. False positives only cost one unneeded read. That asymmetry makes them ideal for skipping files.

Key Takeaway

A Dynamo-style store is a chain of deliberate availability-over-consistency choices, each paired with a repair mechanism: sloppy quorums with hinted handoff, vector clocks with client reconciliation, Merkle trees for anti-entropy. The tunable N, W, R dial lets you move along the latency and consistency spectrum per request, but quorum overlap alone never gives you linearizability, so decide explicitly what your callers can tolerate.
