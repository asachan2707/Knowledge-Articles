Scale From Zero to Millions of Users

Every large system started as one box. This chapter walks the standard growth path tier by tier (split the database, add a load balancer, replicas, cache, CDN, stateless web tier, multiple data centers, queues, sharding) and explains what each step buys and what new problem it creates.

Nobody designs for ten million users on day one, and nobody should. The interesting skill is knowing which problem arrives next, and which component answers it. This chapter is the master map for the rest of the handbook: nearly every later chapter is a deep dive into one box on this map.

Core idea: scaling is a sequence of bottleneck removals. Each component (load balancer, replica, cache, CDN, queue, shard) exists because a specific resource ran out. If you cannot name the resource, you do not need the component yet.

A well-known pattern

The "one box to many tiers" path is the public record of most web companies

Engineering write-ups from Instagram, Pinterest, Stack Overflow and many others tell a strikingly similar story: start with a monolith and one relational database, add a cache when reads dominate, add read replicas, then finally shard when a single primary cannot keep up. Pinterest and Instagram both described sharding MySQL or PostgreSQL by a user or object identifier rather than moving to an exotic datastore. The lesson is not that those choices are universal. It is that the path is incremental, and the early steps are cheap, boring and reversible.

Step 0

The single-server stage and what a request really does

On day one the web app, database, and maybe a cache all run on one machine. That is a perfectly good architecture for a prototype and even for a modest product: there are no network hops between tiers, no distributed failure modes, and deployment is one command. A request goes through four moves.

  1. The client resolves a domain name through DNS. DNS is a paid, third-party lookup service run outside your data center; it returns an IP address and caches it according to the record's TTL.
  2. The browser or mobile app sends HTTP to that address.
  3. The web server runs business logic, reads or writes the database, and returns HTML (for browsers) or JSON (for mobile and single-page clients).
  4. The client renders the response.

Two traffic sources exist: web clients (server-rendered pages plus JavaScript) and mobile apps (JSON over HTTP, usually behind a versioned API). Design the API as the product boundary from the start, because the mobile app version in the wild is something you can never force to upgrade.

user ──DNS lookup──▶ DNS ──▶ 203.0.113.9 │ └─────── HTTP ──────▶ [ one box: web app + DB + cache ] ◀──── HTML / JSON ───
Gotcha. DNS TTL is your slowest failover knob. If you set a 24 hour TTL and the box dies, clients keep sending traffic to the dead IP for hours. Use short TTLs (tens of seconds to minutes) on records you may need to move, and remember that some resolvers ignore low TTLs.
Step 1

Split the database from the web tier

The first split is separating the data tier from the stateless compute tier. The two have opposite scaling profiles: web servers are cheap, CPU-bound and replaceable; databases are stateful, memory- and IO-bound and precious. Splitting lets you scale each independently and gives the database its own hardware, backup schedule and security zone (no public IP).

Relational vs non-relational

The default for a new product is a relational database (PostgreSQL, MySQL). You get joins, transactions, constraints and thirty years of tooling. Reach for a non-relational store when one of these is genuinely true:

  • You need very low, predictable latency on simple lookups (key-value stores such as DynamoDB or Redis).
  • The data is unstructured or semi-structured and you mostly serialise and deserialise it (document stores such as MongoDB).
  • The data is huge and accessed by key or time range (wide-column stores such as Cassandra or Bigtable).
  • The data is a graph and traversals are the product (graph databases).

"NoSQL scales better" is a lazy answer. Relational databases scale a long way with replicas and sharding. NoSQL stores scale easily because they give up joins and multi-row transactions, and you must be willing to give them up too.

Step 2

Vertical vs horizontal scaling, and the load balancer

Vertical (scale up)

  • Zero code change; the simplest fix when traffic is small.
  • No distributed-systems problems.

Vertical limits

  • A hard ceiling: the biggest machine you can buy.
  • Cost grows faster than capacity at the top end.
  • One machine is still one failure domain: no redundancy.

Horizontal scaling (add more machines) is the only path past the ceiling, and it requires something to spread requests across them. That something is the load balancer. Clients talk to the balancer's public IP; the web servers sit on private IPs reachable only from the balancer. If one server dies, the balancer stops routing to it (via active health checks, not wishful thinking), and if traffic spikes you add servers behind it. This one component delivers both redundancy and elasticity.

Depth: what the balancer actually does

  • Layer 4 vs layer 7. An L4 balancer forwards TCP connections without reading HTTP; it is fast and protocol-agnostic. An L7 balancer parses HTTP, so it can route by path or header, terminate TLS, retry idempotent requests and do canary splits. Most product teams want L7 at the edge and L4 inside.
  • Algorithms. Round robin is fine for uniform requests; least-connections or least-request is better when request cost varies; consistent hashing (chapter 5) is used when requests should stick to a backend for cache locality.
  • The balancer itself must not be a single point of failure. Run it as an active-passive pair with a floating IP, or as a managed service that spans zones.
Step 3

Database replication

With a web tier that can grow, the database becomes the next ceiling. The standard answer is a primary (formerly called master) that accepts all writes and several replicas that copy its changes and serve reads. Because most applications read far more than they write, a typical system has one primary and many replicas, and read capacity scales almost linearly with replica count.

writes ──▶ [ PRIMARY ] ──replication log──┬──▶ [ replica 1 ] ◀── reads ├──▶ [ replica 2 ] ◀── reads └──▶ [ replica 3 ] ◀── reads

Failure handling, with the real-world caveats

FailureResponseCatch
One replica dies (others alive)Router stops sending reads to it; a replacement is provisioned and catches up.Remaining replicas absorb its load; watch for cascading overload.
The only replica diesReads temporarily fall back to the primary.Primary now carries read+write; it may not survive.
Primary diesA replica is promoted (manually, or by an orchestrator such as Patroni, Orchestrator, or a managed service).Replication is usually asynchronous, so the promoted replica may be missing the last few committed writes. Those need reconciliation.

Asynchronous replication gives low write latency but allows data loss on failover; synchronous replication to at least one replica removes that loss window at the cost of write latency and write availability if that replica is down. Many production setups use semi-synchronous replication as a compromise. Multi-primary and circular replication exist but make write conflicts your problem; avoid them until you must.

Replication lag is a product bug, not a database detail. A user edits their profile, the page reloads from a lagging replica, and their edit appears lost. The usual cure is read-your-writes routing: for a short window after a write (or for the user's own data), read from the primary, or from a replica whose replication position has passed the write's position. Step 4

Cache tier

A cache is a fast, usually in-memory, store in front of the database for data that is read often and changed rarely. Memory access is hundreds of times faster than a disk-backed query, and every cache hit is a query the database never sees. The most common pattern is cache-aside: the application checks the cache; on a miss it reads the database and populates the cache; on a write it updates the database and invalidates the key. Redis and Memcached are the common engines.

DecisionGuidance
What to cacheRead-heavy, rarely-changing, expensive-to-compute data. Not data that must be exact on every read (balances, inventory at checkout).
ExpirationAlways set a TTL. Without one, stale or orphaned entries live until eviction, and bugs in invalidation become permanent bugs. Too short a TTL gives a low hit ratio; too long gives staleness.
ConsistencyThe database write and the cache invalidation are not one transaction. Delete after the DB commit, keep TTLs as a safety net, and accept a small stale window. Updating (rather than deleting) the cache on write is more race-prone.
EvictionLRU is the default and usually right; LFU suits skewed, stable popularity. The cache is full by design, so eviction is routine, not an error.
AvailabilityOne cache node is a single point of failure and a cold-start cliff. Use several nodes, ideally across zones, and over-provision memory so a lost node does not melt the database.
Cache stampede. When a hot key expires, thousands of concurrent requests miss together and all hit the database. Mitigate with request coalescing (single flight: one loader, the others wait), jittered TTLs, early refresh, or a short-lived lock. See the related caching page for the full catalogue.
Step 5

CDN for static content

A content delivery network is a geographically distributed set of cache servers for static assets (images, video segments, CSS, JavaScript, downloads). A user's request goes to the nearest edge; on a miss the edge pulls from your origin once and then serves everyone nearby. Latency drops because the speed of light is a hard floor: a cross-ocean round trip is on the order of 100+ ms before any server work.

  • Cost. You pay for egress. Cache aggressively; do not serve rarely-requested content through a paid CDN.
  • Expiry. Too long and users see stale assets; too short and the origin takes the load. The best practice is content-addressed (fingerprinted) filenames such as app.3f9a1c.js with year-long TTLs, so you never need invalidation for them.
  • Invalidation. For URLs that must stay stable, use vendor purge APIs or versioned query/path segments.
  • Fallback. Clients should be able to fall back to the origin if the CDN has an outage, and the origin must be sized for that worst case.
Step 6

Make the web tier stateless

If a web server stores the user's session in its own memory, then user A's next request must reach the same server (sticky sessions), which defeats load balancing, makes deployments disruptive, and loses sessions when the server dies. The fix is to move shared state out of the web tier into a shared store such as Redis, a database, or a signed token (JWT or an encrypted cookie) carried by the client. Now any server can handle any request, so servers become interchangeable and disposable.

STATEFUL (fragile) STATELESS (elastic) user A ─▶ server 1 (has A's session) user A ─▶ any server ─┐ user B ─▶ server 2 (has B's session) user B ─▶ any server ─┼─▶ [ shared session store ] server 1 dies = A is logged out a server dies = nobody notices

Statelessness is what makes autoscaling safe: scale out on CPU or request rate, scale in without draining sessions. It is the cheapest, highest-leverage change in this chapter, so do it before you need it. The trade-off is that you have introduced a dependency (the session store) that must itself be replicated and kept fast; a signed token avoids the dependency but makes immediate revocation harder.

Step 7

Multiple data centers

One region is one blast radius, and users far away pay a latency tax. The next step is a second data center. GeoDNS (for example latency-based or geolocation routing in Route 53 or similar) resolves the same hostname to the nearest healthy site. In a normal day traffic is split by geography; if one site fails, DNS or a global load balancer shifts everyone to the survivor.

┌── GeoDNS ──┐ US users ─┤ ├─ EU users ▼ ▼ [ DC-US ]◀─async replication─▶[ DC-EU ] web+cache+DB web+cache+DB

The hard parts are not routing but state:

  • Traffic redirection. You need health checks and a tested failover path. A failover you have never exercised is a hypothesis.
  • Data synchronisation. Cross-region replication is asynchronous (the speed of light again), so a failover can lose recent writes and a user routed to another site may briefly see old data. Decide per dataset: active-passive with one write region, or active-active with explicit conflict handling (chapter 6 covers the tools).
  • Deployment consistency. The same build, config and schema must roll out to every site, usually through automated pipelines and staged rollouts.
  • Capacity. Each site must survive taking the other's traffic, or you have only moved the outage.
Step 8

Message queues: decouple producers from consumers

Some work should not happen inside the request: image resizing, email, report generation, fan-out to followers. A message queue lets the web tier publish a task and return immediately while workers consume at their own pace. Producers and consumers scale and fail independently, and the queue absorbs bursts: if the queue depth grows you add workers; if workers die the messages wait.

One correction to a common description: queues are not "stored in memory" by definition. Production brokers (Kafka, RabbitMQ with durable queues, SQS) persist messages so that a broker restart does not lose them. What the queue gives you is at-least-once delivery in most systems, which means consumers must be idempotent. The handbook's message-queue chapter (19) builds one from scratch.

Use a queue whenDo not use one when
The caller does not need the result now; load is bursty; a downstream service is slow or flaky; you want retry and dead-letter handling.The caller needs a synchronous answer; ordering and exactly-once semantics are required but nobody has designed for them; the added operational surface outweighs the benefit.
Step 9

Logging, metrics and automation

Once there are dozens of moving parts you cannot debug by SSH. Treat observability and automation as part of the architecture, not polish.

  • Logs. Emit structured (JSON) logs with a request id, aggregate them centrally, and make them searchable. Per-server logs are useless the moment a request crosses a tier.
  • Metrics. Collect host metrics (CPU, memory, disk), per-tier metrics (cache hit ratio, replication lag, queue depth, p99 latency, error rate) and business metrics (sign-ups, orders per minute). Alert on symptoms users feel, not on every cause.
  • Automation. Continuous integration, automated deploys, infrastructure as code, and automatic scaling remove the human from the repeatable parts, which is where outages breed.
Step 10

Scaling the data tier: sharding

Replicas scale reads but every replica holds the full data set and the primary still takes every write. When the write rate or the data size exceeds one machine, you partition the data: sharding. Each shard is an independent database with the same schema holding a disjoint slice of rows, selected by a sharding key such as user_id. A router computes shard = hash(user_id) mod N (or consults a directory) and sends the query to the right place.

app ─▶ shard router: shard = hash(user_id) mod 4 ├─▶ shard 0 (users 0,4,8..) + its own replicas ├─▶ shard 1 ├─▶ shard 2 └─▶ shard 3

Choosing the key is the whole game

A good key has high cardinality, spreads load evenly, and keeps the common query on one shard. Sharding by user_id puts all of one user's data together; sharding by created_at sends all new writes to one hot shard. Once chosen, the key is very hard to change.

ProblemWhy it happensMitigation
ReshardingA shard fills up, or data is skewed. With mod N, changing N remaps most keys (see the code below).Consistent hashing (chapter 5), or many logical shards mapped onto fewer physical nodes so you move whole logical shards.
Celebrity / hot keyOne entity gets orders of magnitude more traffic, overloading its shard.Dedicate a shard or split the entity (key suffix salting), add a cache in front, replicate hot rows.
Cross-shard joins and transactionsData for one query now lives on several machines.Denormalise so common queries are single-shard; use application-level joins; use sagas instead of distributed transactions. Middleware such as Vitess or Citus hides routing.

Code

Runnable example: cache-aside, replication lag and why modulo sharding hurts

This single file implements a TTL plus LRU cache using a Map (insertion order gives O(1) recency updates), a primary with lagging replicas, and a cache-aside service on top. It then measures how many keys move when a modulo-sharded fleet grows from 4 to 5 shards. It runs with Node 20+ and no dependencies.

JavaScript Example 
import assert from 'node:assert/strict';
import { createHash } from 'node:crypto';

// 1) LRU cache with TTL (Map preserves insertion order -> O(1) LRU)
class TtlLru {
  constructor(capacity, ttlMs, now = () => Date.now()) {
    this.cap = capacity; this.ttl = ttlMs; this.now = now; this.m = new Map();
  }
  get(k) {
    const e = this.m.get(k);
    if (!e) return undefined;
    if (e.exp <= this.now()) { this.m.delete(k); return undefined; }
    this.m.delete(k); this.m.set(k, e);           // refresh recency
    return e.v;
  }
  set(k, v) {
    this.m.delete(k);
    this.m.set(k, { v, exp: this.now() + this.ttl });
    if (this.m.size > this.cap) this.m.delete(this.m.keys().next().value); // evict LRU
  }
  del(k) { this.m.delete(k); }
}

// 2) Primary + replicas with asynchronous replication lag
class ReplicatedDb {
  constructor(replicas) {
    this.primary = new Map();
    this.replicas = Array.from({ length: replicas }, () => new Map());
    this.queue = [];                               // pending replication log
    this.rr = 0; this.reads = { primary: 0, replica: 0 };
  }
  write(k, v) { this.primary.set(k, v); this.queue.push([k, v]); }
  replicate() { for (const [k, v] of this.queue) this.replicas.forEach(r => r.set(k, v)); this.queue = []; }
  read(k, { fresh = false } = {}) {
    if (fresh || this.replicas.length === 0) { this.reads.primary++; return this.primary.get(k); }
    this.reads.replica++;
    return this.replicas[this.rr++ % this.replicas.length].get(k);
  }
}

// 3) Cache-aside service on top of both
let t = 0; const clock = () => t;
const cache = new TtlLru(2, 1000, clock);
const db = new ReplicatedDb(2);
const get = k => {
  let v = cache.get(k);
  if (v === undefined) { v = db.read(k); if (v !== undefined) cache.set(k, v); }
  return v;
};
const put = (k, v) => { db.write(k, v); cache.del(k); };   // invalidate, don't update

put('user:1', 'alice'); db.replicate();
assert.equal(get('user:1'), 'alice');                // miss -> replica -> fill
assert.equal(get('user:1'), 'alice');                // hit
assert.equal(db.reads.replica, 1);
put('user:1', 'alicia');                             // replica not yet caught up
assert.equal(db.read('user:1'), 'alice');            // stale replica read (lag)
assert.equal(db.read('user:1', { fresh: true }), 'alicia'); // read-your-writes via primary
db.replicate();
assert.equal(get('user:1'), 'alicia');
t += 1500; assert.equal(cache.get('user:1'), undefined);   // TTL expiry
cache.set('a', 1); cache.set('b', 2); cache.get('a'); cache.set('c', 3);
assert.equal(cache.get('b'), undefined);             // LRU victim was b
assert.equal(cache.get('a'), 1);

// 4) Why modulo sharding hurts: fraction of keys that move when shards go 4 -> 5
const h = s => createHash('md5').update(s).digest().readUInt32BE(0);
let moved = 0; const K = 100000;
for (let i = 0; i < K; i++) { const x = h('user:' + i); if (x % 4 !== x % 5) moved++; }
console.log('modulo 4->5 moved:', (100 * moved / K).toFixed(1) + '% of keys (ideal 20%)');
assert.ok(moved / K > 0.7);
console.log('replica reads:', db.reads.replica, 'primary reads:', db.reads.primary);
console.log('all checks passed');

Prints: "modulo 4->5 moved: ~80% of keys (ideal 20%)", the replica/primary read counts, and "all checks passed" after the assertions on cache hits, TTL expiry, LRU eviction, stale replica reads and read-your-writes pass. Executed with node.

Scaling and production

Scaling knees and gotchas

  • Connections are a resource. Every web server opening a pool to the database multiplies connections; a few hundred servers can exhaust a primary. Use a pooler (PgBouncer, ProxySQL).
  • Autoscaling lags. New instances take minutes to start and warm caches; scale on leading indicators and keep headroom for spikes.
  • Cold caches are outages. A restart or a new region begins with a zero hit ratio; pre-warm or throttle.
  • Backups are not replicas. A replica faithfully replicates a bad DELETE. Keep point-in-time-recovery backups and test restores.
  • Schema changes get harder with scale. Use expand-then-contract migrations so old and new code coexist.
  • Prefer boring. Each new component is a new on-call burden; defer it until a metric demands it.
Checklist

Before you say "it scales"

  • Web tier is stateless; sessions live in a shared store or signed token.
  • No single point of failure at LB, cache, queue, primary or DNS.
  • Reads are absorbed by cache and replicas; read-your-writes is handled.
  • Static assets are on a CDN with fingerprinted names.
  • Slow work is asynchronous and consumers are idempotent.
  • Logs, metrics and alerts exist for every tier; deploys are automated.
  • Sharding key chosen deliberately, with a resharding plan.
  • Failover has been rehearsed, not just designed.
FAQ · Common Questions

Frequently Asked Questions

When should I shard instead of just buying a bigger database?

Shard when the write rate or data volume outgrows the largest primary you can run reliably, or when the cost curve of bigger machines turns steep. Before that, replicas, caching, query tuning, archiving old data and partitioning inside one database (table partitioning) are cheaper and reversible. Sharding is a one-way door because it changes your query model.

Cache-aside, write-through or write-back?

Cache-aside is the safe default: the database stays the source of truth and cache failure only costs speed. Write-through keeps the cache fresher but adds write latency and still needs eviction. Write-back (buffer writes in cache, flush later) is fastest but risks losing acknowledged writes; reserve it for data you can afford to lose or rebuild.

How do you keep a cache consistent with the database?

You cannot make them atomic without a transaction spanning both. In practice: write the database, then delete the cache key; keep a TTL as a backstop; for stricter needs, subscribe to the database change log (CDC) and invalidate from there. Accept and document a small staleness window.

What breaks first if I add replicas but my users write right before reading?

Replication lag shows up as lost updates in the UI. Route the writer's own reads to the primary for a short window, or track the write's log position and read only from replicas that have reached it.

Active-active across regions: easy win or trap?

Mostly a trap for stateful data. It halves latency and survives region loss, but you must resolve write conflicts (last-write-wins loses data; CRDTs or per-record home regions help). Start active-passive for the database, active-active for the stateless tier, and graduate deliberately.

Is a message queue the same as a cache or a database?

No. A queue moves work; a cache accelerates reads; a database stores truth. A durable log such as Kafka blurs the line with a database, but the access pattern (append, read in order, consume by offset) is what defines it.

Key Takeaway

Scale in the order your bottleneck appears, not the order a diagram suggests. Make the web tier stateless first because it is nearly free and unlocks everything else. Absorb reads with replicas, cache and CDN before you touch writes, and only shard when a single primary truly cannot hold the write rate or the data. Every tier you add trades simplicity for capacity, so add it only when the numbers force you.
