Design Ad Click Event Aggregation

A billing-grade stream pipeline that turns a billion raw ad clicks a day into per-minute counts and a top-100 leaderboard that advertisers can trust to the cent. The hard parts are not throughput; they are late events, duplicates, crashes and proving the numbers are right.

Real systemsKafka, Flink, Spark, Cassandra, ClickHouse, Druid, Hive, S3/Parquet, YARN, Debezium-style CDC

Every time someone taps a sponsored result, a small event is born. Advertisers are charged per click (or use click counts to judge a campaign), so those events are literally money. The design question is how to count a billion of them a day, per ad, per minute, per filter, and keep the answer provably correct while machines die, networks lag and clients lie.

Core idea: treat the click stream as an append-only log, aggregate it in small event-time windows with a bounded tolerance for lateness, make every step replayable and idempotent, and then run an independent batch job that recomputes the truth from raw data to catch whatever the real-time path got wrong. Speed comes from streaming; trust comes from replay plus reconciliation.

A public design this echoes

Lambda vs Kappa, and why the argument exists

Nathan Marz popularised the Lambda architecture: a slow-but-exact batch layer (Hadoop, later Spark) plus a fast-but-approximate speed layer, merged at query time. It worked, but teams ended up maintaining two implementations of the same business logic that drifted apart. Jay Kreps (then at LinkedIn, co-creator of Kafka) answered with the Kappa architecture: keep the log as the source of truth and reprocess by replaying it through the same streaming job. Apache Flink's design (checkpointed state, event-time watermarks, exactly-once sinks) is what made Kappa credible for money-grade counting. This chapter lands on Kappa for its main path and keeps a batch reconciler as an auditor, which is the pragmatic hybrid most ad-tech shops end up with.

Why it exists

The business context: ads are sold in milliseconds, billed in minutes

Digital advertising has two very different clocks. Real-time bidding (RTB) is the auction that decides which ad is shown when a page loads: an exchange asks bidders, picks a winner and returns a creative, all inside roughly a second (typically well below 100-200 ms per bidder). That path is latency-critical and lives in its own serving stack. This chapter is about the other clock: the reporting and billing path, where a few minutes of delay is fine but a wrong number is not.

The consumers of this system are advertisers and analysts looking at dashboards (how many clicks did ad X get in the last 30 minutes; which are the hottest 100 ads right now), the billing system that invoices per click, and fraud/optimisation systems that tune targeting. A one percent error at this scale is millions of dollars of disputed invoices. So the non-functional priority order is: correctness, then fault tolerance and replayability, then freshness (minutes), and only then cost.

Step 1 · Scope and requirements

Requirements and back-of-the-envelope maths

Functional

  • Return the number of clicks for ad_id over the last Y minutes (a range query).
  • Return the top 100 most clicked ad_ids over a configurable recent window, refreshed every minute.
  • Support filtering of both queries by attributes such as ip, user_id, country.
  • Handle late events, duplicate events and partial failures with a recovery story.

Non-functional

  • Correctness over speed: results feed billing.
  • End-to-end latency of a few minutes for the aggregate; no sub-second requirement here.
  • Resilient to node, broker and network failures with automatic recovery and no manual reconciliation of the happy path.
  • Scale: 1 billion clicks per day, 2 million ads, click volume growing about 30% year over year.

The number to state out loud is the multiplier on aggregates: every extra filter dimension multiplies row count.
Step 2 · API and data model

Query API and the three tables you actually need

Clients here are dashboards, not end users, so a small read-only REST API is enough. Ingest does not go through it: clicks arrive from the ad-serving tier or click-redirect service straight into the log.

Two design remarks. First, filter is an opaque id and not free-form predicates; this is deliberate, because it ties the API to what has been pre-aggregated (more below). Second, the top-N endpoint is a lookup into a precomputed table, never a scan: its latency is O(1) in data size.

The filter_id indirection is a tiny dimension table mapping an id to a predicate (region = US, ip = 123.1.2.3, user_id = *). That is exactly a data-warehouse star schema: a fact table (counts) keyed by dimensions. Pre-computing every requested combination makes reads trivial but means each dimension multiplies row count, so you cap the allowed filters and make adding one a deliberate, reviewed event.

Why store both raw and aggregated

Keep raw events

  • Recompute after a logic bug or new dimension.
  • Audit and dispute resolution: "show me the clicks you billed".
  • Feeds reconciliation and ML/fraud training.
  • Cheap if parked in cold storage as columnar files.

Raw alone is not enough

  • Scanning terabytes per dashboard refresh is slow and costly.
  • Cannot serve top-N in milliseconds.
  • Aggregates are derived and lossy, so they cannot be the only copy either.

Storage choices follow the access pattern, not fashion. Raw writes are 10-50K/s, append-only, rarely read: Cassandra (LSM-tree, write-optimised, scales linearly) or object storage with Parquet/ORC are natural. The aggregate table is both write-heavy (rewritten each minute) and read-heavy (dashboards, alerts) with simple key lookups by (ad_id, minute range): Cassandra again works, partitioned by (ad_id, filter_id) with click_minute as a clustering column so a range query is a contiguous slice. See the Cassandra page for the LSM and partitioning model.

High-level design

Log in, DAG out

Dumping clicks synchronously into the aggregator couples two systems with very different failure behaviours: if the consumer stalls, producers back up and you start dropping money. A durable log between them absorbs bursts and lets each side fail independently. We use two logs: one for raw clicks, one for aggregation output.

Ad click sources (log watchers / click-redirect svc) │ at-least-once, key = ad_id ▼ ┌────────────────────┐ ┌────────────────────────┐ │ Kafka topic #1 │──────► │ Raw event store (Cassandra │ cold: Parquet on S3 │ raw ad_click │ sink │ or object store) │ └─────────┬──────────┘ └───────────▲────────────┘ │ │ batch read ▼ │ ┌──────────────────────────────┐ ┌──────┴────────────┐ │ Aggregation service (DAG) │ │ Recalculation / │ │ map ─► aggregate ─► reduce │ │ reconciliation │ └─────────┬────────────────────┘ └──────┬────────────┘ ▼ │ results ┌────────────────────┐ ◄──────────────────┘ │ Kafka topic #2 │ (per-minute counts, top-N) │ aggregated results │ └─────────┬──────────┘ │ sink (idempotent / transactional) ▼ ┌────────────────────┐ ┌────────────────────┐ │ Aggregate DB │ ◄────│ Query service / API │ ◄── dashboards, billing └────────────────────┘ └────────────────────┘

Topic one carries (ad_id, click_timestamp, user_id, ip, country). Topic two carries two shapes: (ad_id, click_minute, count) and (update_time_minute, most_clicked_ads). The second topic exists for a subtle reason: it lets the final write to the database be the last step of an exactly-once chain. The DB sink reads a topic of already-final results, and its offset commit and DB write can be reconciled atomically, or made idempotent, in isolation from the heavy computation upstream.

The aggregation service as a map / aggregate / reduce DAG

Think of the service as a small directed acyclic graph of single-purpose operators, with intermediate data in memory and shuffles over TCP or shared memory, the same dataflow idea Flink, Spark Streaming and Beam use.

  • Map reads from Kafka, validates, normalises (strip bad timestamps, resolve country from IP, drop bot traffic) and routes each event by hash(ad_id) mod K to aggregator K. You can skip it by key-partitioning the topic by ad_id and letting aggregators consume partitions directly, but a map stage earns its keep when you do not control the producers (events for one ad may land on any partition) or need a transformation stage.
  • Aggregate keeps an in-memory hash map ad_id -> count per window, plus a bounded min-heap of size N for the local top N. At each minute boundary it emits its counts and local top-N downstream.
  • Reduce merges the per-node top-N lists into the final global top 100 and writes topic two.
use-case 1: count of ad_id (3 aggregators, ad_id mod 3) Kafka ─► Map ─┬─► Agg0 {ad0:9, ad3:4 ...} ─┐ ├─► Agg1 {ad1:7, ad4:2 ...} ─┼─► (write per-minute counts) └─► Agg2 {ad2:5, ad5:8 ...} ─┘ use-case 2: top-N (each Agg keeps a size-N min-heap) Agg0 top3 [ad3:40, ad9:35, ad0:30] ─┐ Agg1 top3 [ad1:90, ad4:20, ad7:18] ─┼─► Reduce: merge 3x3 candidates ─► global top3 Agg2 top3 [ad2:55, ad5:50, ad8:48] ─┘
Why local top-N is enough: because events are partitioned by ad_id, every ad's complete count lives on exactly one aggregator. So each ad in the global top N is necessarily in the top N of its own node, and the reducer only has to merge K lists of N. Partition by anything else (user, region) and the counts of one ad are split across nodes, local top-N lists are no longer sufficient, and the answer silently goes wrong. The reduce step costs O(K N log N) per minute, microseconds.

Filtering via pre-aggregation (star schema)

To answer "clicks for ad X from the US" instantly, the aggregator emits one counter per (ad, minute, dimension value): (ad001, 202101010001, USA, 100), (ad001, 202101010001, GBR, 200), (ad001, 202101010001, others, 3000). Reads become a key lookup. The price is write amplification: with D enabled dimension combinations each click increments up to D counters, and cardinality can explode (ip as a dimension is nearly unbounded). Mitigations that work in practice: cap dimensions to low-cardinality columns (country, device, placement), bucket long tails into an "others" row as above, push high-cardinality filtering (arbitrary ip or user) to the raw store or an OLAP engine, and use sketches (HyperLogLog) when the question is "unique users", not clicks.

Deep dive · Batch vs stream

Streaming, batching, Lambda and Kappa

Online serviceBatchStreaming
InputUser requestsBounded, finite datasetUnbounded stream
OutputResponsesMaterialised views, reportsMaterialised views, running aggregates
Measured byAvailability, latencyThroughputThroughput and latency
ExampleCheckout APIMapReduce, Spark batchFlink, Kafka Streams

Our hot path is streaming, and historical correction is batch. Lambda keeps those as two separate code paths whose results are reconciled at query time. Kappa runs everything through one streaming engine: to reprocess, point a second instance of the same job at the stored raw data (or replay the Kafka topic if retention allows), write to a fresh output, then swap. The chapter's design is Kappa: a recalculation service reads raw events from storage, feeds them to a dedicated aggregation cluster (so live traffic is not slowed down), and publishes results to topic two, which flows through the same sink.

Kappa

  • One codebase for live and replay: no semantic drift.
  • Fix-and-reprocess is an ordinary deploy.
  • Replay is the same code path used every minute, so it is exercised constantly.

Kappa costs

  • Needs a streaming engine strong in state, event time and exactly-once.
  • Reprocessing months of data through a stream job is slower than a native batch scan.
  • Retention of a replayable source must be paid for.
Deep dive · Time

Event time, processing time and the watermark

Each click has two times: event time (when the user clicked, stamped by the client or edge) and processing time (when the aggregator sees it). Between them sit mobile radio sleeps, retries, queue lag, a consumer restart. If you bucket by processing time, a click that happened at 12:00:59 but is processed at 12:01:02 is billed in the wrong minute, and a catch-up after an outage would pile an hour of clicks into one bucket. For billing and reporting that is wrong, so we use event time.

ProsCons
Event timeMatches reality; replay gives identical results; outages do not distort bucketsClient clocks lie; malicious clients can forge times; late events exist and need a policy
Processing timeTrivial; server clock is trustworthy; never lateWrong buckets on any delay; replay gives different numbers; bills the wrong period
Do not trust the device clock raw. Production systems stamp the click at a server-side edge (the click-redirect hop) and carry that as event time, or record both client and server timestamps and clamp the client value to a sane band around the server value. Reject or quarantine events whose event time is far in the future or older than your maximum allowed lateness.

Watermarks, in plain terms

With event time, "when is minute 12:00 complete?" is unanswerable with certainty: a straggler might still be in flight. A watermark is the system's running estimate: "I believe I have now seen every event with event time up to W". A simple, robust heuristic is watermark = max_event_time_seen - allowed_lateness. A window [t, t+1min) is closed, its result emitted, and its state freed when the watermark passes t+1min. The chapter draws this as extending the window: a window "waits" an extra period so that stragglers can still land in it.

1-minute tumbling windows, allowed lateness = 15 s event time ─► 12:00 12:01 12:02 │ win A │ win B │ win C arrivals: e1(12:00:10) e2(12:00:58) e3(12:01:04) e2'(12:00:59, delivered late) e4(12:01:20) maxEventTime: 12:00:10 ...12:00:58...12:01:04.......12:01:04.........12:01:20 watermark : 11:59:55 ...12:00:43...12:00:49.......12:00:49.........12:01:05 late e2' still lands in win A (A is open) win A closes here: wm 12:01:05 ≥ 12:01:00 a straggler arriving after this is "late data": drop, side-output, or correct downstream
  • Short watermark: low latency, more late events dropped from the real-time result.
  • Long watermark: fewer misses, higher latency and more open-window state in memory.
  • Whatever you choose some events arrive later. Do not chase the 0.001% tail with a 30-minute watermark; ship the tail to a side output and let the nightly reconciler or a corrective update fix it.

Flink offers all three options (drop, allowedLateness that re-fires the window with an updated result, or a side output) and bounded-out-of-orderness watermark generators that implement exactly the heuristic above. A subtle production issue: in a multi-partition source, the operator watermark is the minimum across input partitions, so one idle or stuck partition freezes every window in the job. Configure idleness detection, and alert on watermark lag (processing time minus watermark), which is the single most useful health signal in an event-time pipeline.

Deep dive · Windows

Which window for which query

WindowShapeUse here
Tumbling (fixed)Non-overlapping equal slices: [0,1), [1,2)...; every event in exactly one windowThe per-minute click count. Cheap: one counter per (ad, window).
HoppingFixed length, advances by a smaller hop, so windows overlap (length 5 min, hop 1 min)Smoothed series; each event lands in length/hop windows, so cost multiplies.
SlidingWindow ends at "now" and moves continuously or on each eventTop N in the last M minutes.
SessionGap-based; closes after inactivityNot needed for ad counts; relevant for user-journey analytics.

Implementation trick that saves enormous cost: do not recompute the M-minute top-N from raw events. Pre-aggregate in 1-minute tumbling buckets and let the sliding window be a sum of the last M minute buckets. When the window advances one minute you add the newest bucket and subtract the expired one, because counting is invertible, which makes the update O(distinct ads touched), not O(events). Top-N itself is not invertible (you cannot remove an expired minute from a heap), so keep the per-ad totals map for the window, update it incrementally, and rebuild the size-N heap from it each minute: O(A log N) for A active ads, trivial for 2M ads once a minute.

Deep dive · Delivery semantics

Exactly-once: what it really means and how to get it

Three guarantees: at-most-once (may lose), at-least-once (may duplicate), exactly-once (neither). At-least-once is the right default for logs and metrics, where a 0.1% duplicate rate is noise. Here a 0.1% error on a billion clicks a day is a million disputed clicks, so we need the effect of exactly-once, even if the transport is at-least-once.

Where duplicates come from

  • Client / upstream retries: a user double-taps; a mobile SDK resends after a timeout; an ad server retries a produce call that actually succeeded. Mitigation is a stable event_id (a UUID or deterministic hash of ad, user, impression id) assigned at the source plus dedup downstream. Deliberate fraud (click farms, scripts) is a different problem for a risk engine, not for the aggregator.
  • Consumer crash between "process" and "ack": the aggregator emits a count downstream but dies before committing the Kafka offset, so a replacement re-reads from the last committed offset and emits again.
Failure on the last hop (offset 100) Kafka offset: ... 98 99 100 101 Aggregator A: process(100) ─► emit downstream OK ─► ✗ crash before commit offset Aggregator B: resumes from committed offset 99 ─► process(100) again ─► emit duplicate

Three fixes, in increasing correctness:

  1. Save the offset in external storage (HDFS/S3) after emitting. If you crash between emit and save you re-emit (duplicate); if you save first and crash before emitting, the result is lost forever. Neither order is correct, because two different systems are updated non-atomically.
  2. Atomic commit of offset + output. Make "write result to downstream" and "advance input offset" a single transaction. In Kafka this is the transactional API: idempotent producers (producer id + sequence numbers reject duplicate retries per partition), transactional.id for fencing zombie instances, sendOffsetsToTransaction to include the consumer offset in the same atomic commit as the output records, and consumers reading with isolation.level=read_committed. Flink achieves the equivalent with periodic checkpoints (Chandy-Lamport style barriers snapshot operator state plus source offsets consistently) and a two-phase-commit sink.
  3. Make the sink idempotent. If every output row has a deterministic natural key (ad_id|window_start|filter) and the value is the final computed number for that window, writing it twice is a no-op overwrite (an upsert). Then replays, restarts and the nightly recompute all converge on the same state with no distributed transaction at all. This is the best practical answer for the database hop.
Gotcha: Cassandra counter columns (UPDATE ... SET c = c + 1) are not idempotent: a retry after a timeout may or may not have been applied, and replays double count. Write computed totals into ordinary columns keyed by (ad, minute) and overwrite them. Likewise "increment by delta" messages are fragile; "set to value" messages are safe.

So the end-to-end recipe: at-least-once ingest with event ids, in-job dedup (or Kafka idempotence on the producer side), checkpointed state with transactional offset commits inside the stream engine, and an idempotent upsert into the serving DB. Exactly-once is a property of the whole chain, and any one non-idempotent hop breaks it.

Deep dive · Scale

Scaling the three decoupled tiers

1. The message queue

  • Producers scale freely: add more, no coordination.
  • Consumers scale by joining a consumer group, but parallelism is capped by partition count. Over-provision partitions up front (partition count is painful to change: it breaks key-to-partition mapping and per-key ordering). For 50K events/s peak, a few dozen partitions already leave generous headroom; hundreds are common to allow future growth.
  • Rebalancing with thousands of consumers is slow and can stall consumption; use cooperative/incremental rebalancing, static membership, and schedule capacity changes off-peak.
  • Partition by ad_id so one aggregator owns an ad. Optionally split topics by geography (topic_na, topic_eu) to keep traffic regional and shrink blast radius.
  • Size retention for your worst-case outage plus replay needs (days), and watch consumer lag as the primary autoscaling signal.

2. The aggregation service

Map and reduce nodes are stateless or lightly stateful and scale by adding nodes. Per-node throughput scales via multi-threading (simple, bounded by one machine) or via multi-process under a resource manager such as YARN or Kubernetes (more scalable and isolating; more operational surface). Production stacks pick the second and let the engine (Flink task slots, Spark executors) own it.

3. The database

Cassandra scales horizontally by consistent hashing with virtual nodes: add a node and it takes over token ranges automatically, no manual resharding. Design the partition key so a hot ad does not create a hot partition (include a time bucket in the partition key, for example (ad_id, day), and cluster by minute). The aggregate table is small compared with raw data, so write amplification from filters is the main sizing driver.

The hot-key problem

A Super Bowl ad can draw orders of magnitude more clicks than the median ad, and key partitioning sends them all to one aggregator, which becomes the straggler that holds the window open for everyone. Remedies:

TechniqueHowTrade-off
Elastic helpersOverloaded node asks the resource manager for extra workers; splits its events into groups, each helper counts one group, partial sums returned to the ownerReactive; needs resource headroom and a fast scheduler
Global-local (two-stage) aggregationStage 1 pre-aggregates locally on every node before the shuffle (like a MapReduce combiner); stage 2 merges the few partial sums per keyShuffle volume drops from events to nodes x keys; only works for decomposable aggregates (count, sum, max)
Key saltingAppend a random salt 0..s to hot keys (ad9#3), count per salted key, then merge in a second stageExtra stage; need to know which keys are hot (detect via sampling)
Split distinct aggregationFor count-distinct, hash the user id into buckets, aggregate per bucket, then sumOnly for distinct counts; more complexity

Counting is a commutative monoid (associative, with identity zero), which is precisely why pre-aggregation and salting are safe here. Plan the same thinking for any new metric: if it cannot be merged from partials (exact median, for example), hot keys will hurt more.

Deep dive · Fault tolerance

Surviving a dead aggregator

Aggregators hold windows in memory. Kafka offsets alone are not enough to recover: if the node dies at 12:04:30 holding 4.5 minutes of partial state for a 5-minute top-N window, restarting from the last committed offset would require re-reading everything since the window began, which is slow, and you also cannot trivially know which events were already counted.

The standard answer is a consistent snapshot of (input offset, operator state), taken periodically (every few seconds to a minute) and stored on durable storage (HDFS, S3, a state backend like RocksDB with incremental checkpoints). Recovery: a replacement node loads the latest snapshot and resumes consuming from the offset recorded in that same snapshot. Everything after the snapshot is replayed deterministically, and because replayed output is idempotent the world converges.

t0 ────────── t1 ────────── t2 ──────── ✗ crash offset 1000 offset 1800 offset 2600 [snapshot S1] [snapshot S2] work since S2 is lost (in memory only) recovery: load S2 (state + offset 1800) ─► re-read 1800..now from Kafka ─► continue outputs for already-emitted windows are re-upserted by key: no double count

Snapshot frequency is a classic trade-off: frequent snapshots shorten replay and RTO but cost IO and (if synchronous) latency; asynchronous, incremental checkpoints make high frequency cheap. Also snapshot the dedup set or make it TTL-bound, otherwise a replay can double count events in the gap. Test recovery for real: kill -9 an aggregator during a game-day and diff the outputs; the runnable example below does exactly this in miniature.

Deep dive · Correctness

Monitoring and reconciliation

Because the output is revenue, you do not merely hope the pipeline is right; you measure it and audit it.

SignalWhat it tells youAction
End-to-end latency (event time to visible-in-DB)Freshness; derive by propagating timestamps through stagesPage if p99 exceeds the few-minute budget
Consumer lag (records-lag per partition)Aggregators falling behind; Kafka queue "size" is meaningless on a log, so use lag, not depthAutoscale consumers; check hot partitions
Watermark lag, late-event rateClock skew, upstream delays, stuck partitionInvestigate source; raise lateness only if justified
Dedup hit rateRetry storms or a producer bugSudden jump means upstream incident
CPU, memory, GC, disk on aggregatorsCapacity and state growthScale or tune state backend
Events in vs events out, per minuteConservation check: clicks in = sum of counts + dropped late + dropped dupesAlert on any non-zero residual

The reconciliation job is a nightly (or hourly for the previous hour) batch that recomputes per-minute counts directly from the raw store, with no lateness cut-off, and diffs them against the aggregate database. Mismatches are repaired by re-emitting the corrected values through topic two (idempotent upsert), and the size and cause of the diff become a data-quality metric. Typical findings: late events beyond the watermark, a bad deploy, a poisoned partition. This is the safety net that justifies a short watermark in the first place.

Alternative design

Buy instead of build: Hive plus OLAP

The generic DAG is what you describe in an interview to show understanding. In 2026 many teams would assemble it from products: ingest to Kafka, land raw data on object storage (queryable via Hive/Trino/Spark), and send a second stream into an OLAP store such as ClickHouse or Apache Druid, which natively roll up on ingest (Druid's rollup, ClickHouse's SummingMergeTree/AggregatingMergeTree and materialized views) and answer "group by ad, filter by country, last 30 minutes" in tens of milliseconds over billions of rows. Elasticsearch on top of Hive is the older variant of this idea.

OLAP-engine approach

  • Ad-hoc filters and group-bys without pre-declaring dimensions.
  • Far less custom code to run and debug.
  • Built-in rollup, approximate distinct (HLL), columnar compression.

Where it hurts

  • Exactly-once and late-data semantics vary by engine and need careful ingest configuration.
  • Expensive for the very high cardinality combos you can pre-aggregate away.
  • Another cluster family to operate; correctness proof still needs raw data and reconciliation.

Stuck or idle partitionWatermark frozen, no windows closeIdleness timeout, alert on watermark lag

Scaling and production gotchas

Things that bite after launch

  • Partition count is a one-way door. Pick it for next year's volume (30% yearly growth compounds to 3.7x in five years), not today's.
  • Rebalances are stop-the-world for a group. A flapping consumer causes continual rebalances; use static membership and tune session timeouts.
  • State size grows with lateness. Every extra minute of allowed lateness keeps another window of 2M-key state alive; and the dedup set grows with the dedup horizon.
  • Back-pressure beats data loss. When the sink slows, the engine should throttle reads from Kafka; do not buffer unbounded in memory.
  • Reprocessing storms. Replaying a week of events can saturate shared brokers and DB; run recalculation on an isolated cluster and rate-limit the write-back.
  • Time zones and minute keys. Always store UTC epoch minutes; format only at the edge. Daylight-saving bugs in billing are a rite of passage.
  • Schema evolution. Use a registry (Avro/Protobuf) with compatibility checks; a new nullable field must not break replay of last month's events.
  • Privacy. IP and user id are personal data under GDPR-style regimes; set retention and hashing policy for the raw store.
  • Query-side caching. Dashboards poll; cache top-N results for the minute they are valid, keyed by (window, filter).
Runnable code

A miniature exactly-once aggregator

The program below is a single-file model of the core: event-time tumbling windows with a lateness watermark, id-based dedup, an idempotent keyed sink, a snapshot of (offset, state) with crash recovery, a bounded min-heap for top-N, and a reconciliation pass that proves the only discrepancy is the late events. It is deterministic (seeded generator): 3,000 unique clicks with jitter, about 2% arriving three minutes late, plus 100 duplicate retries.

JavaScript Example 
// Ad-click aggregation: event-time tumbling windows, watermark, dedup,
// snapshot+offset recovery, top-N via min-heap over a sliding window, reconciliation.
import assert from 'node:assert/strict';

const MIN = 60_000;
const minuteOf = (ts) => Math.floor(ts / MIN) * MIN;

class MinHeap {                       // bounded heap keeps the N largest counts
  #a = []; #cmp;
  constructor(cmp) { this.#cmp = cmp; }
  get size() { return this.#a.length; }
  peek() { return this.#a[0]; }
  push(x) {
    const a = this.#a; a.push(x);
    let i = a.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.#cmp(a[i], a[p]) >= 0) break;
      [a[i], a[p]] = [a[p], a[i]]; i = p;
    }
  }
  pop() {
    const a = this.#a, top = a[0], last = a.pop();
    if (a.length) {
      a[0] = last; let i = 0;
      for (;;) {
        let l = 2 * i + 1, r = l + 1, m = i;
        if (l < a.length && this.#cmp(a[l], a[m]) < 0) m = l;
        if (r < a.length && this.#cmp(a[r], a[m]) < 0) m = r;
        if (m === i) break;
        [a[i], a[m]] = [a[m], a[i]]; i = m;
      }
    }
    return top;
  }
  toSortedDesc() { return [...this.#a].sort((x, y) => this.#cmp(y, x)); }
}

function topN(counts, n) {            // counts: Map adId -> count
  const cmp = (x, y) => x[1] - y[1] || (y[0] < x[0] ? -1 : 1); // tie-break: smaller id wins
  const h = new MinHeap(cmp);
  for (const e of counts) { h.push(e); if (h.size > n) h.pop(); }
  return h.toSortedDesc().map(([ad, c]) => `${ad}:${c}`);
}

class Aggregator {
  constructor({ lateness = MIN, sink }) {
    this.lateness = lateness; this.sink = sink;
    this.offset = 0;                 // next log offset to read
    this.open = new Map();           // windowStart -> Map(adId -> count)
    this.seen = new Set();           // dedup ids (production: TTL'd store keyed by event id)
    this.maxEventTime = 0;
    this.closedBefore = 0;           // windows with start < closedBefore are final
    this.lateDropped = 0; this.dupes = 0;
  }
  process(log, limit = Infinity) {
    let n = 0;
    while (this.offset < log.length && n++ < limit) {
      const ev = log[this.offset++];
      if (this.seen.has(ev.id)) { this.dupes++; continue; }
      this.seen.add(ev.id);
      const w = minuteOf(ev.ts);
      if (w < this.closedBefore) { this.lateDropped++; continue; } // too late: reconcile later
      if (!this.open.has(w)) this.open.set(w, new Map());
      const m = this.open.get(w); m.set(ev.ad, (m.get(ev.ad) ?? 0) + 1);
      this.maxEventTime = Math.max(this.maxEventTime, ev.ts);
      this.#closeReady();
    }
  }
  #closeReady() {
    const watermark = this.maxEventTime - this.lateness;
    for (const w of [...this.open.keys()].sort((a, b) => a - b)) {
      if (w + MIN <= watermark) {
        for (const [ad, c] of this.open.get(w)) this.sink.upsert(`${ad}|${w}`, c); // idempotent key
        this.open.delete(w); this.closedBefore = Math.max(this.closedBefore, w + MIN);
      }
    }
  }
  flush() { this.maxEventTime += 10 * MIN; this.#closeReady(); }
  snapshot() {
    return structuredClone({ offset: this.offset, open: [...this.open].map(([w, m]) => [w, [...m]]),
      seen: [...this.seen], maxEventTime: this.maxEventTime, closedBefore: this.closedBefore,
      lateDropped: this.lateDropped, dupes: this.dupes });
  }
  static restore(s, opts) {
    const a = new Aggregator(opts); s = structuredClone(s);
    a.offset = s.offset; a.open = new Map(s.open.map(([w, m]) => [w, new Map(m)]));
    a.seen = new Set(s.seen); a.maxEventTime = s.maxEventTime; a.closedBefore = s.closedBefore;
    a.lateDropped = s.lateDropped; a.dupes = s.dupes; return a;
  }
}

class Sink {                          // keyed upsert => replays are harmless (idempotent sink)
  rows = new Map(); writes = 0;
  upsert(k, v) { this.rows.set(k, v); this.writes++; }
  countFor(ad, fromMin, toMin) {      // answers GET /ads/{id}/aggregated_count
    let t = 0;
    for (const [k, v] of this.rows) { const [a, w] = k.split('|'); if (a === ad && +w >= fromMin && +w < toMin) t += v; }
    return t;
  }
  topInWindow(fromMin, toMin, n) {    // sliding-window top-N built from per-minute rows
    const agg = new Map();
    for (const [k, v] of this.rows) { const [a, w] = k.split('|'); if (+w >= fromMin && +w < toMin) agg.set(a, (agg.get(a) ?? 0) + v); }
    return topN(agg, n);
  }
}

// ---- deterministic workload ----
let seed = 42; const rnd = () => (seed = (seed * 1664525 + 1013904223) >>> 0) / 2 ** 32;
const base = Date.UTC(2021, 0, 1);
const log = []; let id = 0;
for (let i = 0; i < 3000; i++) {
  const ad = 'ad' + (rnd() < 0.4 ? 1 : 2 + Math.floor(rnd() * 8));   // ad1 is a hot key
  const ts = base + i * 40 + Math.floor(rnd() * 3000) - (rnd() < 0.02 ? 3 * MIN : 0); // jitter + some very late
  log.push({ id: 'e' + id++, ad, ts, country: rnd() < 0.5 ? 'US' : 'GB' });
}
for (let i = 0; i < 100; i++) log.push(log[Math.floor(rnd() * log.length)]); // producer retries => duplicates

// run A: uninterrupted
const sinkA = new Sink(); const A = new Aggregator({ sink: sinkA }); A.process(log); A.flush();
// run B: crash after 2800 events, recover from the snapshot taken at 1000, replay from its offset
const sinkB = new Sink(); let B = new Aggregator({ sink: sinkB });
B.process(log, 1000); const snap = B.snapshot(); B.process(log, 1800); // work after snapshot is lost on crash
B = Aggregator.restore(snap, { sink: sinkB }); B.process(log); B.flush();
assert.deepEqual([...sinkB.rows].sort(), [...sinkA.rows].sort()); // same result despite crash + replayed upserts
assert.ok(sinkB.writes > sinkA.writes);                            // replay re-wrote some keys (idempotent)

// reconciliation: batch recompute from raw using event time, dedupe by id, no lateness cut-off
const truth = new Map(); const ids = new Set();
for (const e of log) { if (ids.has(e.id)) continue; ids.add(e.id); const k = `${e.ad}|${minuteOf(e.ts)}`; truth.set(k, (truth.get(k) ?? 0) + 1); }
let diff = 0; for (const [k, v] of truth) diff += v - (sinkA.rows.get(k) ?? 0);
assert.equal(diff, A.lateDropped);   // the only discrepancy is exactly the events beyond the watermark
const total = [...sinkA.rows.values()].reduce((s, v) => s + v, 0);
assert.equal(total + A.lateDropped, ids.size);

const end = base + 3 * MIN;
console.log('unique events      :', ids.size, '| duplicates dropped:', A.dupes, '| late dropped:', A.lateDropped);
console.log('crash-recovery ok  :', true, '| sink writes A/B:', sinkA.writes, sinkB.writes);
console.log('reconciliation gap :', diff, '(= late events, repaired by batch)');
console.log('ad1 clicks min0-3  :', sinkA.countFor('ad1', base, end));
console.log('top-3 over 3 min   :', sinkA.topInWindow(base, end, 3).join(', '));

Prints unique-event, duplicate and late counts (3000 / 100 / 70), confirms the crash-and-restore run produces byte-identical sink contents (28 writes vs 29 because one key was rewritten idempotently), shows the reconciliation gap of 70 equal to the late drops, the ad1 count over three minutes, and the top-3 ads. All assertions pass under Node 20+.

Read the output as a proof sketch: the assertion that crash-recovery equals the uninterrupted run is the property you actually care about. If it ever fails in your real pipeline, you have found a non-idempotent hop or state that was not part of the snapshot.

FAQ · Common Questions

Frequently Asked Questions

Why not just use processing time? It is simpler and never late.

Because the bucket would depend on infrastructure health. After a two-minute consumer stall every click would be billed to the recovery minute, and replaying yesterday's data would produce different numbers than the first run. Event time makes the result a pure function of the data, which is what you need to reprocess and to audit.

How long should the watermark be?

Look at the measured distribution of (arrival time minus event time) for your traffic and set lateness near the 99th or 99.9th percentile; typically seconds to a couple of minutes. Then rely on reconciliation for the rest. Making it longer buys diminishing completeness for linearly growing latency and state.

Does Kafka give me exactly-once for free?

Only inside Kafka-to-Kafka pipelines using idempotent producers and transactions with read_committed consumers. The moment you write to an external database you need either a transactional/two-phase sink or an idempotent upsert. In this design the upsert by (ad, minute, filter) is the simpler and more robust choice.

A single ad gets 30% of all traffic. What now?

That is the hot-key problem. Detect it (per-key rate sampling), then salt that key into s sub-keys for stage-one counting and merge in stage two; or use a combiner so each node ships one partial sum per minute. Because counting is associative and commutative this is exact, not approximate.

How do you answer "unique users who clicked" instead of clicks?

Exact distinct counts do not merge cheaply across partitions. Use a HyperLogLog sketch per (ad, minute), which merges by register-wise max and costs a few KB with about 1% error, or aggregate exact distincts only for a small whitelist of high-value ads. State the accuracy trade-off explicitly because billing generally needs exact click counts, while reach metrics tolerate error.

What if the reconciliation job disagrees with the stream result?

The raw log is the truth by definition. Treat the diff as an incident: classify (late data, bug, dropped partition), re-emit corrected values through the normal idempotent path so downstream consumers see a normal update, and fix the root cause. If invoices already went out, a credit note process covers the delta.

Key Takeaway

An ad click aggregator is a correctness problem wearing a throughput costume. Partition by ad_id, bucket by event time with a bounded watermark, make every write idempotent and every stage replayable from a snapshot, and then audit the whole thing nightly against raw data. If you can replay it and reconcile it, you can trust it.
