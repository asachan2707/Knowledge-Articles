System design interviews test whether you can reason about trade-offs under constraints — not whether you can recite architecture diagrams. The pattern that separates good answers from great ones: start with the scale numbers, derive the bottleneck, then choose the architecture that solves that specific bottleneck and nothing more.

Core idea: Every system design problem is a capacity planning problem in disguise. Size the load first, find what breaks at that load, and pick the minimal architecture that prevents that breakage while leaving room to scale further.

Story · The "just use Kafka" trap

A candidate in a system design round was asked how to send 1M notifications. He immediately said "Use Kafka." The interviewer waited. He kept describing the Kafka cluster configuration. The interviewer finally asked: "What happens when Firebase throttles you at 500 req/s?" Silence. The candidate had answered a different question — how to queue messages — and never addressed the actual constraint: provider rate limits.

The correct architecture wasn't just "add a queue." It was: rate-limited consumer workers + per-provider concurrency control + exponential backoff + delivery status tracking. Knowing why each piece exists is what separates a passing answer from a failing one.

Problem 1

Send 1 Million Notifications Without Overwhelming Your Servers

Problem · Scale: 1M users · Time constraint: Black Friday campaign burst · Provider: Firebase (rate limited)
Requirements: - Send personalized push/email to 1M users within 1 hour - Firebase rate limit: ~500 req/s per key - Workers may crash mid-campaign → must be fault-tolerant - Delivery status must be trackable - Must scale to 100M users in future Architecture: API → Kafka topic: notifications → Rate-limited Workers → Firebase / Email Provider ↓ Dead Letter Queue (failed deliveries) ↓ Status Webhook → DB (tracking)

Key layers and why each exists:

ChallengeSolutionWhy
Provider rate limitsRate-limited Kafka consumers (token bucket)Firebase throttles at 500/s — without control your workers get 429s and waste time on retries
Worker crashesKafka manual offset commit after successful sendUncommitted offsets replay on restart — at-least-once delivery
PersonalizationPer-user message rendering in worker, not at APIKeeps API fast; rendering is CPU work, done asynchronously
Delivery trackingProvider callback webhook → status DBFirebase and SendGrid both offer delivery callbacks — wire them up from day one
Scale to 100MPartition Kafka topic by user_id hashN workers consume N partitions in parallel — linear scale
JavaScript Example 
// Rate-limited Kafka consumer for notification delivery
import { Kafka } from "kafkajs";

const kafka = new Kafka({ brokers: ["kafka:9092"] });
const consumer = kafka.consumer({ groupId: "notification-workers" });

// Token bucket — enforces Firebase's 500 req/s limit
class TokenBucket {
  constructor(rate, capacity) {
    this.tokens = capacity;
    this.capacity = capacity;
    setInterval(() => { this.tokens = Math.min(this.capacity, this.tokens + rate / 10); }, 100);
  }
  async consume() {
    while (this.tokens < 1) await new Promise((r) => setTimeout(r, 50));
    this.tokens -= 1;
  }
}

const bucket = new TokenBucket(500, 500); // 500 tokens/sec

await consumer.connect();
await consumer.subscribe({ topic: "notifications", fromBeginning: false });

await consumer.run({
  eachMessage: async ({ message, heartbeat, commitOffsetsIfNecessary }) => {
    const notification = JSON.parse(message.value.toString());

    // Render personalised message
    const body = renderTemplate(notification.templateId, notification.userId);

    // Wait for a rate-limit token
    await bucket.consume();

    try {
      await sendToFirebase(notification.deviceToken, body);
      // Only commit offset AFTER successful send
      await commitOffsetsIfNecessary();
    } catch (err) {
      if (err.status === 429) {
        // Back off and retry — do NOT commit offset
        await new Promise((r) => setTimeout(r, 2000));
      } else {
        await sendToDeadLetterQueue(notification, err.message);
        await commitOffsetsIfNecessary();
      }
    }
    await heartbeat();
  },
});
Problem 2

Resumable Large File Upload (Disconnect-Safe)

Problem · Files up to 10 GB · Mobile clients on flaky connections · Must resume from exact byte offset
Core mechanism: Chunked multipart upload with server-side chunk manifest 1. Client → POST /upload/init → receives session_id 2. Client splits file into 10 MB chunks 3. Client → PUT /upload/{session_id}/chunk/{n} (with SHA-256 checksum) 4. On disconnect → GET /upload/{session_id}/status → { received: [0,1,3], missing: [2,4,5...] } 5. Client re-uploads only missing chunks 6. Client → POST /upload/{session_id}/complete → server assembles + finalises
JavaScript Example 
// Client-side chunked upload with resume
async function uploadWithResume(file, options = {}) {
  const CHUNK_SIZE = 10 * 1024 * 1024; // 10 MB
  const totalChunks = Math.ceil(file.size / CHUNK_SIZE);

  // Step 1: Initialise session
  const { sessionId } = await fetch("/upload/init", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ name: file.name, size: file.size, totalChunks }),
  }).then((r) => r.json());

  // Step 2: Check what the server already has (resume support)
  const { received } = await fetch(`/upload/${sessionId}/status`).then((r) => r.json());
  const receivedSet = new Set(received);

  // Step 3: Upload only missing chunks
  for (let i = 0; i < totalChunks; i++) {
    if (receivedSet.has(i)) continue; // already uploaded

    const start = i * CHUNK_SIZE;
    const chunk = file.slice(start, start + CHUNK_SIZE);
    const checksum = await sha256(chunk);

    const form = new FormData();
    form.append("chunk", chunk);

    await fetch(`/upload/${sessionId}/chunk/${i}`, {
      method: "PUT",
      headers: { "X-Checksum": checksum },
      body: form,
    });

    options.onProgress?.(Math.round(((i + 1) / totalChunks) * 100));
  }

  // Step 4: Finalise
  return fetch(`/upload/${sessionId}/complete`, { method: "POST" }).then((r) => r.json());
}

async function sha256(blob) {
  const buf = await blob.arrayBuffer();
  const hash = await crypto.subtle.digest("SHA-256", buf);
  return Array.from(new Uint8Array(hash)).map((b) => b.toString(16).padStart(2, "0")).join("");
}
Server side: Store received chunks in Redis as a Set keyed by session_id. Use S3 multipart upload API — it natively handles chunk assembly and the CompleteMultipartUpload call. TTL sessions after 24h of inactivity to reclaim storage.

Instagram System Design at 500M DAU

Scale targets: 175K feed reads/sec · 350K like/comment writes/sec · 750 TB/day storage ingestion

LayerTechnologyKey decision
Feed generationHybrid fan-outFan-out on write for regular users (pre-built feed); fan-in on read for celebrities (>1M followers) to avoid write amplification
Media storageBlob store (S3) + CDNPre-signed upload URLs bypass app servers. CDN reduces origin traffic by 90–95%. Hot/cold tiering migrates aging content automatically.

Problem 4

Google L5: Optimize a 10-Table SQL JOIN

Joining 10 tables naively produces a query that PostgreSQL cannot execute in under a second at any meaningful scale. The optimization layers, applied in order:

  1. Indexes on join columns — every foreign key and every column in a WHERE clause used in the join needs an index. Without this, each join is a sequential scan.
  2. Filter early with CTEs or subqueries — push the most selective filter closest to the raw table scan. If only 0.1% of orders are in status DISPUTED, filter that before joining to users, products, and shipping.
  3. Avoid SELECT * — retrieve only the columns you need. Fewer bytes → smaller memory footprint for hash joins → faster execution.
  4. EXPLAIN ANALYZE before optimizing — read the actual row estimates vs actual rows. Stale table statistics (run ANALYZE) cause the query planner to pick wrong join orders.
  5. Materialise expensive subqueries — use WITH MATERIALIZED in PostgreSQL to force a CTE to materialise once rather than being re-evaluated per outer row.
  6. Consider denormalisation for read-heavy paths — if this query runs 10K times/second, maintaining a pre-joined summary table via a trigger or CDC pipeline is often the right answer.
JavaScript Example 
// Node.js: push filtering to the DB, don't pull everything and filter in memory
const { rows } = await db.query(`
  -- Filter first (most selective condition), join after
  WITH disputed_orders AS MATERIALIZED (
    SELECT id, user_id, product_id, amount
    FROM orders
    WHERE status = 'DISPUTED'           -- ~0.1% of rows
      AND created_at > NOW() - INTERVAL '30 days'
  )
  SELECT
    u.name, u.email,
    p.title AS product,
    do.amount,
    s.carrier, s.tracking_number
  FROM disputed_orders do
  JOIN users u         ON u.id = do.user_id
  JOIN products p      ON p.id = do.product_id
  LEFT JOIN shipments s ON s.order_id = do.id
  -- Only 2 more joins after filtering to ~0.1% of data
  ORDER BY do.created_at DESC
  LIMIT 100;
`);
Practical checklist

How to approach any system design interview

  • Always start with scale numbers — DAU, writes/sec, reads/sec, data size — before drawing any boxes.
  • Identify the single bottleneck at that scale. Every architecture decision should trace back to relieving that bottleneck.
  • Say "for now I'd start with X; here's when I'd upgrade to Y" — interviewers reward awareness of over-engineering.
  • Address failure modes explicitly: what happens when a service is down? How do you detect it? How do you recover?
  • Never forget delivery guarantees — at-least-once vs exactly-once, and the idempotency keys you'd need for each.

Key Takeaway

The four problems here — notification fan-out, resumable upload, Instagram architecture, SQL join optimization — share one underlying skill: capacity reasoning under constraints. Know the numbers, find the bottleneck, solve exactly that. A simple, correctly-sized architecture beats a sophisticated one that solves the wrong problem. In interviews and in production.
