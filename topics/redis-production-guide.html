Redis — The Complete Production Guide

Everything you need to run Redis confidently in production: the full data-structure toolkit (String to Stream), persistence trade-offs (RDB vs AOF), cluster vs Sentinel HA, eviction policies, pipelining and transactions, and the six canonical use-cases — caching, session store, rate limiter, leaderboard, pub/sub, and job queue — each with a working JavaScript implementation.

Source: Redis Docs · Antirez Blog · ByteByteGo Domain: Backend / Infrastructure Published: 2026

Redis is deceptively simple to start — SET key value, GET key, done. But the gap between "it works on my laptop" and "it handles 500k ops/sec in production with zero data loss" is enormous. This guide covers the data structures, durability options, high-availability topologies, memory management, and six concrete use-case patterns you will encounter on any serious backend.

Core idea: Redis is a data structure server, not just a cache. Picking the right data type for each problem is the single biggest lever for both correctness and performance — a naive String-encoded JSON blob where a Hash or Sorted Set belongs can cost 10–100× more memory and latency.

Story · The midnight alert

At 2 AM an on-call engineer receives a PagerDuty alert: Redis memory at 98%, eviction policy is allkeys-lru, and the leaderboard service is returning stale scores. The root cause turns out to be three separate mistakes made months apart: a developer stored session data as JSON strings instead of Hashes (3× the memory), a cron job wrote full sorted-set dumps instead of incrementing scores, and nobody had set maxmemory-policy deliberately — it defaulted to noeviction until someone changed it to allkeys-lru without understanding that it would silently evict leaderboard keys under pressure.

Understanding Redis data structures, eviction semantics, and persistence modes before you hit production is far cheaper than learning them during an incident.

Data Structures

The Seven Data Types and When to Use Each

String

The most versatile type. Stores any binary-safe value up to 512 MB. Used for simple key-value caching, counters (INCR, INCRBY), distributed locks (SET … NX PX), and feature flags. Internally Redis auto-encodes short integers as integers (O(1) INCR without string parsing) and short strings as embstr (single allocation, cache-friendly).

Hash

A map of field → value pairs. Ideal for objects (user profiles, product records) because you can HGET a single field without deserialising the entire object. Redis uses a compact ziplist encoding when a Hash has fewer than 128 fields and all values are under 64 bytes — this can be 5–10× more memory-efficient than storing the same data as a JSON string.

List

A doubly-linked list of strings. LPUSH/RPUSH and LPOP/RPOP are O(1). LRANGE is O(N) for the returned slice. Lists are the natural fit for job queues, activity feeds, and recent-events windows. BLPOP/BRPOP provide blocking pop for consumer workers without polling.

Set

An unordered collection of unique strings. O(1) for add/remove/membership. Set operations (SUNION, SINTER, SDIFF) are powerful for tag intersection, mutual-friend calculations, and deduplication pipelines.

Sorted Set (ZSet)

Like a Set, but every member has a floating-point score. Members are stored in sorted order by score. ZADD is O(log N). ZRANGE/ZREVRANGE let you page through top-N leaderboards in O(log N + M). ZRANGEBYSCORE is perfect for time-window queries. This is the canonical structure for leaderboards, rate limiters, and delayed job queues.

Stream

Append-only log of entries (Redis 5+). Each entry has an auto-generated or custom ID and a set of field-value pairs. Streams support consumer groups — multiple independent consumers each processing different entries, with acknowledgement and redelivery of unacked messages. Think of it as a lightweight, in-process Kafka.

HyperLogLog / Bloom Filter / Geospatial (Redis Stack)

The extended Redis Stack types: HyperLogLog gives approximate cardinality counts (unique page views) with O(1) memory; Bloom Filter answers "have I seen this?" with configurable false-positive rate; GEOADD / GEODIST / GEORADIUS handle geospatial indexing built on Sorted Sets. These require the RedisBloom / RediSearch modules or Redis Stack.

Persistence

RDB vs AOF — Choosing Your Durability Guarantee

RDB (Redis Database Snapshots)

RDB creates a point-in-time binary snapshot of the dataset at configurable intervals (e.g., save 900 1 = save if at least 1 key changed in 900 seconds). The child process does the fork-and-write, so the parent keeps serving requests. RDB files are compact and fast to load on restart — startup time for a 10 GB dataset is typically under 30 seconds.

Trade-off: You can lose up to the interval's worth of writes. If Redis crashes between snapshots, those writes are gone. RDB is appropriate when you can tolerate a few minutes of data loss (e.g., a pure cache with a warm-up fallback).

AOF (Append-Only File)

Every write command is appended to a log file. On restart Redis replays the log to rebuild state. Three appendfsync policies control durability vs. performance:

  • always — fsync after every command. Maximum durability, ~10× slower writes.
  • everysec — fsync once per second. At most 1 second of data loss. Recommended for most production deployments.
  • no — let the OS decide. Fastest, but data loss on crash is up to the OS flush interval (typically 30 s).

AOF files grow over time. Redis periodically rewrites them via BGREWRITEAOF (or automatically when the file exceeds a size threshold), compacting the log to the minimal set of commands needed to recreate current state.

RDB + AOF hybrid (recommended)

Redis 4+ supports aof-use-rdb-preamble yes — the AOF file starts with an RDB snapshot and then appends subsequent writes. Fast restart (RDB loading speed) plus near-zero data loss (AOF granularity). This is the recommended production default for data-sensitive workloads.

Rule of thumb: For a pure cache layer, disable persistence entirely (save "" and appendonly no) — it eliminates fork overhead and disk I/O. For anything that must survive a restart (sessions, rate-limiter state, leaderboards), use RDB + AOF hybrid with everysec.

High Availability

Redis Sentinel vs Redis Cluster

Redis Sentinel

Sentinel is a separate process that monitors a primary + one or more replica setup. If the primary goes down, Sentinels elect a new primary through a quorum vote. Clients query Sentinels to discover the current primary address. No data sharding — the entire dataset lives on one shard. Use Sentinel when your dataset fits on one node and you need automatic failover with minimal complexity.

  • Minimum: 3 Sentinel processes for a stable quorum.
  • Failover time: typically 10–30 seconds.
  • Client requirement: client must support Sentinel discovery (ioredis and node-redis both do).

Redis Cluster

Cluster shards data across up to 1000 nodes using 16384 hash slots. Each primary node owns a range of hash slots; replicas provide HA for their primary. Clients route commands based on the slot of the key — cluster-aware clients cache the slot map and redirect on MOVED/ASK responses.

  • Required when dataset exceeds a single node's RAM.
  • Multi-key commands (MGET, SUNION) only work when all keys hash to the same slot — use hash tags ({user:123}:session) to force co-location.
  • Minimum recommended: 3 primaries × 1 replica each = 6 nodes.

Decision rule: Dataset < node RAM → Sentinel. Dataset requires horizontal sharding → Cluster. Don't add Cluster complexity you don't need; Sentinel handles most production use-cases cleanly.

Memory Management

Eviction Policies, TTLs, and Avoiding Hot Keys

maxmemory and eviction policies

Set maxmemory to leave headroom for replication buffers and AOF rewrites (typically 70–80% of physical RAM). When the limit is reached, Redis applies the configured maxmemory-policy:

  • noeviction — return errors on new writes. Safe for primary data stores where silent loss is unacceptable.
  • allkeys-lru — evict any key using LRU. Good for pure caches where any key can be regenerated.
  • volatile-lru — evict only keys with a TTL set. Good when you want to protect keys without TTLs.
  • allkeys-lfu — evict least-frequently used keys (Redis 4+). Better than LRU for skewed access patterns.
  • volatile-ttl — evict the key with the shortest remaining TTL first.

TTL best practices

Always set TTLs on cache keys. Use EXPIRE or the EX/PX options on write. Avoid setting all keys to the same TTL — spread them with jitter (ttl + Math.random() * jitterMs) to prevent cache stampedes where all keys expire simultaneously.

Hot keys and big keys

A hot key is a single key receiving a disproportionate share of traffic. Since a single Redis node is single-threaded for command execution, one hot key can saturate CPU. Solutions: local in-process caching for the hot key; read replicas + randomised replica routing; or sharding the key across N keys with a client-side aggregation step.

A big key is a value that takes >10 ms to serialise/deserialise or occupies >1 MB. Big keys block the event loop during serialisation. Detect them with redis-cli --bigkeys or OBJECT ENCODING key. Mitigation: split into multiple smaller keys, use HSCAN/SSCAN/ZSCAN for iterative access.

JavaScript Example

Six Canonical Use-Cases with ioredis

JavaScript Example 
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL ?? 'redis://localhost:6379');

// ── 1. Cache-aside pattern ──────────────────────────────────────────────────
async function getCachedUser(userId) {
  const key = `user:${userId}`;
  const cached = await redis.get(key);
  if (cached) return JSON.parse(cached);

  const user = await db.findUser(userId); // hypothetical DB call
  // Cache for 5 min with jitter to prevent stampede
  const ttl = 300 + Math.floor(Math.random() * 60);
  await redis.set(key, JSON.stringify(user), 'EX', ttl);
  return user;
}

// ── 2. Distributed lock (SET NX PX) ────────────────────────────────────────
async function withLock(resource, ttlMs, fn) {
  const lockKey = `lock:${resource}`;
  const token = crypto.randomUUID();
  const acquired = await redis.set(lockKey, token, 'PX', ttlMs, 'NX');
  if (!acquired) throw new Error(`Could not acquire lock on ${resource}`);

  try {
    return await fn();
  } finally {
    // Lua script for atomic check-and-delete
    const script = `
      if redis.call("get", KEYS[1]) == ARGV[1] then
        return redis.call("del", KEYS[1])
      else return 0 end`;
    await redis.eval(script, 1, lockKey, token);
  }
}

// ── 3. Fixed-window rate limiter ────────────────────────────────────────────
async function rateLimit(userId, limitPerMinute) {
  const window = Math.floor(Date.now() / 60_000); // 1-minute window
  const key = `rl:${userId}:${window}`;
  const count = await redis.incr(key);
  if (count === 1) await redis.expire(key, 60); // set TTL on first write
  return { allowed: count <= limitPerMinute, count, limit: limitPerMinute };
}

// ── 4. Leaderboard (Sorted Set) ─────────────────────────────────────────────
async function addScore(gameId, userId, score) {
  await redis.zadd(`lb:${gameId}`, score, userId);
}
async function getTopN(gameId, n = 10) {
  // ZREVRANGE returns members highest score first
  const members = await redis.zrevrange(`lb:${gameId}`, 0, n - 1, 'WITHSCORES');
  const result = [];
  for (let i = 0; i < members.length; i += 2) {
    result.push({ userId: members[i], score: Number(members[i + 1]) });
  }
  return result;
}

// ── 5. Session store (Hash) ─────────────────────────────────────────────────
async function saveSession(sessionId, fields, ttlSeconds = 3600) {
  const key = `sess:${sessionId}`;
  await redis.hset(key, fields); // { userId: '42', role: 'admin', ... }
  await redis.expire(key, ttlSeconds);
}
async function getSessionField(sessionId, field) {
  return redis.hget(`sess:${sessionId}`, field);
}

// ── 6. Job queue (List + BLPOP) ─────────────────────────────────────────────
async function enqueue(queueName, job) {
  await redis.rpush(`q:${queueName}`, JSON.stringify(job));
}
async function workerLoop(queueName) {
  while (true) {
    // BLPOP blocks up to 5 s; returns [key, value] or null on timeout
    const result = await redis.blpop(`q:${queueName}`, 5);
    if (!result) continue;
    const job = JSON.parse(result[1]);
    await processJob(job).catch(console.error);
  }
}

async function processJob(job) { console.log('Processing', job); }
async function db_findUser(id) { return { id, name: 'Alice' }; }
Transactions & Scripting

MULTI/EXEC, Lua Scripts, and Pipelining

Pipelining

Pipelining batches multiple commands into a single network round-trip. The client sends N commands without waiting for replies, then reads all N replies at once. This doesn't change atomicity (commands can still interleave with other clients), but it dramatically reduces round-trip overhead for bulk operations. In ioredis, use redis.pipeline() or send an array of commands.

MULTI / EXEC (transactions)

Commands between MULTI and EXEC are queued and executed atomically as a block — no other client's commands interleave. However, Redis transactions do not roll back on runtime errors (only on syntax errors queued before EXEC). Use WATCH before MULTI to implement optimistic locking: if the watched key changes before EXEC, the transaction aborts and returns nil.

Lua scripting (EVAL)

Lua scripts execute atomically on the Redis server — no commands from other clients run while a script is executing. This is stronger than MULTI/EXEC and avoids the check-then-act race condition. Use Lua for complex atomic operations like the lock-release pattern above, or for conditional updates that would otherwise require a WATCH loop. Cache scripts with SCRIPT LOAD + EVALSHA to avoid re-sending the script body on every call.

Atomic operations hierarchy: Single command (always atomic) > Lua script (atomic, no rollback needed) > MULTI/EXEC (atomic block, no rollback) > Pipeline (not atomic, but fast). Match the tool to the consistency requirement.

Pub / Sub & Streams

Pub/Sub, Keyspace Notifications, and Streams

Pub/Sub

PUBLISH channel message broadcasts to all current subscribers. Subscriptions are ephemeral — if a subscriber is disconnected, messages are lost. Redis pub/sub is appropriate for real-time fan-out (chat, live updates) where occasional message loss is acceptable and persistence is not required.

Keyspace notifications

Enable with notify-keyspace-events KEA in redis.conf (or CONFIG SET at runtime). Subscribers receive notifications when keys expire, are deleted, or are written. Useful for cache invalidation triggers, TTL-based workflows, and audit logging — but generates significant internal pub/sub traffic at high key churn.

Streams for reliable messaging

Unlike pub/sub, Streams persist messages and support consumer groups. A consumer group tracks which entries each consumer has acknowledged. Unacknowledged entries can be reclaimed with XAUTOCLAIM after a timeout — providing at-least-once delivery semantics. Use Streams when you need message persistence and ordered, at-least-once processing; use pub/sub for fire-and-forget fan-out.

Practical Checklist

Redis Production Readiness — What to Nail

  • Set maxmemory to 70–80% of RAM and choose maxmemory-policy deliberately — never rely on the default (noeviction) in a cache.
  • Use RDB + AOF hybrid with appendfsync everysec for any data that must survive a restart.
  • Always set TTLs on cache keys. Add random jitter to avoid simultaneous expiry stampedes.
  • Use Hash instead of JSON-serialised strings for objects with many fields — leverage ziplist compression for small hashes.
  • Use Sorted Sets for leaderboards and time-window rate limiters, not Lists — O(log N) range queries are worth it.
  • Prefer Lua scripts over MULTI/EXEC for complex atomic operations to avoid check-then-act races.
  • Deploy at least 3 Sentinel processes for quorum; use Redis Cluster only when you need horizontal sharding.
  • Monitor redis-cli info memory fields: mem_fragmentation_ratio > 1.5 indicates fragmentation; restart or active defrag may be needed.
  • Run redis-cli --hotkeys in production periodically to detect hot-key concentration before it causes latency spikes.
  • For Node.js, use ioredis over node-redis for cluster-aware client routing and built-in reconnection logic.

Key Takeaway

Redis mastery is 80% choosing the right data structure for the problem. Strings for counters and locks, Hashes for objects, Lists for queues, Sorted Sets for ordered collections and leaderboards, Streams for reliable messaging — each type unlocks a compact and efficient implementation that a generic "store it as JSON" approach can never match. Layer in the right persistence mode and HA topology for your durability requirements, set maxmemory and eviction policy deliberately, and use Lua scripts for atomic compound operations. Done right, Redis handles hundreds of thousands of operations per second on a single node with sub-millisecond latency and a memory footprint that would surprise you.
