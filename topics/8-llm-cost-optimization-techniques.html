LLM API costs follow a simple but counterintuitive structure: you pay for every token the model reads and every token it writes, on every request. Teams that focus on shortening prompts optimise the cheapest part of the bill. The real cost drivers are uncontrolled output length (3–5x the price of input per token), context repetition (re-sending the same multi-thousand-token context on every request), and model overqualification (using Opus for tasks Haiku handles identically). Fix these three and you typically see a 60–80% reduction with no measurable quality change; the eight techniques below cover all the layers.

Cost structure primer (2026 pricing, approximate):
Input tokens: $3–15 per million (varies by tier; Haiku ~$0.80, Sonnet ~$3, Opus ~$15)
Output tokens: $15–75 per million (3–5x input cost)
Cached input tokens: ~10% of uncached input
Priority order: output control > prompt caching > model routing > input compression. Context management matters more than prompt length, and output control matters most of all.

Story · The $14,000 Month Nobody Planned For

How a $800 Prototype Became a $14,000 Monthly Bill

Formly, a B2B SaaS for automating contract review, integrated Claude Opus into their document analysis flow. The prototype was impressive — Opus understood complex legal language beautifully. The prototype handled 200 documents per day with an average of 8 API calls per document. The bill was $800/month. Totally manageable. They shipped to production.

Three months later: 2,400 documents per day, 12× more API calls per document than expected (because the production flow had more steps than the prototype), and an average output of 3,200 tokens per analysis (the prototype outputs had been manually curated, not representative). The monthly bill hit $14,000.

Post-analysis revealed three root causes: (1) Claude Opus was being used for every step — including steps that were effectively just text classification ("is this a termination clause?") where Haiku would have performed identically. (2) A 6,000-token system prompt (including full legal clause glossary) was being sent fresh on every API call — no caching. (3) The output format was not constrained — the model was generating 2,000–4,000 token explanations when a 150-token structured JSON response was all the application needed.

The optimized pipeline: Haiku for classification steps, Sonnet for extraction steps, Opus only for the final analysis requiring deep reasoning. Prompt caching on the static system prompt. JSON output with explicit max_tokens. Result: $2,800/month for the same workload — an 80% reduction. Quality was unchanged; they measured it with an LLM-as-judge evaluation over 500 documents.

Foundation

Understanding the LLM Cost Structure Before Optimizing

LLM pricing is per token. Every optimization decision should be evaluated against the token cost it targets. The typical production cost breakdown for a document analysis system (before optimization) looks like this:

Cost component% of billOptimization leverAchievable reduction
Output token generation50–65%max_tokens + structured output50–70%
Repeated uncached input20–35%Prompt caching85–90% of that component
Model overqualification10–30%Model routing by task type60–90% of that component
User input (variable)5–15%Truncation, chunking20–40%

The most common mistake: spending engineering time compressing user input (15% of the bill, 20–40% reducible = 3–6% total savings) while ignoring output length (60% of the bill, 50–70% reducible = 30–42% total savings). Always attack the largest cost component first.

Technique 1

Output Length Control: The Highest-Leverage Technique

Output tokens cost 3–5× more than input tokens. An LLM that generates 3,000 tokens when you need 200 is wasting your money at the highest possible rate. Two mechanisms control output length:

1. max_tokens Parameter

Every LLM API accepts a max_tokens parameter that hard-stops generation. Set it to approximately 120% of your expected maximum response length. For a classification task with a JSON output of 5 fields, max_tokens=150. For a document summary, max_tokens=400. For a full analysis, measure your p95 output length from logs and set max_tokens to p95 + 20%.

Not setting max_tokens explicitly is the most expensive single mistake in LLM deployments. Without it, some requests will generate 4,000+ tokens of explanation when the application uses only the first 200 tokens. You pay for all 4,000.

2. Format Instructions and Structured Output

Explicit length instructions in the system prompt ("Reply in 2-3 sentences maximum", "Output only the JSON object, no explanation") are followed reliably. JSON Schema-constrained outputs are consistently shorter than free text conveying the same information, so use them wherever the consuming code already parses the response.

Asking the model to return JSON with specific fields is dramatically cheaper than asking for a narrative explanation that happens to contain the same information. Compare:

Expensive: "Analyze this contract and explain whether it contains a termination clause, what the notice period is, and whether there are any unusual terms."
→ Typical output: 800–1,500 tokens of prose.

Cheap: "Return JSON: {has_termination_clause: bool, notice_period_days: int|null, unusual_terms: string[]}"
→ Typical output: 50–120 tokens of JSON.

JavaScript — Output-Constrained API Call with Structured Schema 
// cost-optimized-analysis.js
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();

// Output schema enforces structured, minimal responses
const ANALYSIS_SCHEMA = {
  type: 'object',
  properties: {
    has_termination_clause: { type: 'boolean' },
    notice_period_days: { type: ['integer', 'null'] },
    auto_renewal: { type: 'boolean' },
    governing_law: { type: ['string', 'null'] },
    unusual_terms: {
      type: 'array',
      items: { type: 'string', maxLength: 100 }, // Constrain item length too
      maxItems: 5, // Cap the array size
    },
    risk_level: { type: 'string', enum: ['low', 'medium', 'high'] },
  },
  required: ['has_termination_clause', 'auto_renewal', 'risk_level'],
};

export async function analyzeContract(contractText) {
  const response = await client.messages.create({
    model: 'claude-haiku-4-5-20251001', // Haiku for structured extraction
    max_tokens: 256,                      // Explicit cap — JSON response is ≤200 tokens
    system: SYSTEM_PROMPT,               // Cached (see prompt caching section)
    messages: [{
      role: 'user',
      content: `Analyze this contract. Return ONLY valid JSON matching the schema. No explanation.\n\n${contractText.slice(0, 8000)}`, // Truncate input
    }],
    // Force JSON output via tool use (most reliable structured output method)
    tools: [{
      name: 'contract_analysis',
      description: 'Return contract analysis as structured data',
      input_schema: ANALYSIS_SCHEMA,
    }],
    tool_choice: { type: 'tool', name: 'contract_analysis' },
  });

  const toolUse = response.content.find(b => b.type === 'tool_use');
  return toolUse?.input ?? null;
}

// Cost comparison (per 1000 documents):
// Before: prose output ~1500 tokens × $15/M = $22.50/1000 docs
// After:  JSON output ~150 tokens × $15/M = $2.25/1000 docs
// Savings: 90% on output alone, before model routing
Technique 2

Prompt Caching: 90% Cheaper Repeated Context

Prompt caching stores a prefix of your input (typically the system prompt) on the provider's servers and reuses it across requests, charging 10% of the normal input token price for cached tokens. The savings are dramatic for workflows with large, static system prompts.

Example arithmetic for a 2,000-token system prompt across 1M requests: uncached 2,000 x $0.000003 x 1M = $6,000; cached 2,000 x $0.0000003 x 1M = $600. Implementation is one line: add "cache_control": {"type": "ephemeral"} to the last block of the static prefix. The cache persists for 5 minutes (Claude); a keepalive request before expiry avoids re-caching overhead on high-traffic apps. 

{
  "system": [
    {
      "type": "text",
      "text": "You are a helpful assistant for Acme Corp. [2000 tokens of context]",
      "cache_control": { "type": "ephemeral" }
    }
  ]
}

When Caching Saves Money

  • Large, static system prompt — A 4,000-token legal clause glossary sent with every document. Without caching: 4,000 tokens × $3/M = $0.012 per request. With caching: $0.0012 per request after the first call that populates the cache. 90% reduction.
  • Few-shot examples in the prompt — 20 annotated examples totaling 8,000 tokens. Same economics: cached reads cost 90% less.

When Caching Does NOT Save Money

  • Short system prompts (<1000 tokens). The engineering overhead of caching plus the minimum cache block size means there is little saving on short prompts.
  • Prompts that change per user or per request. If your system prompt includes the user's name, preferences, or current context, caching is impossible — the cached prefix must be identical across requests.
  • Low-volume applications. Cache TTLs are typically 5 minutes. If you send fewer than 20 requests per 5 minutes, the cache will expire between your requests and you will pay uncached prices on most calls.
JavaScript — Prompt Caching with Anthropic SDK 
// prompt-caching.js
// Splits system prompt into cacheable static prefix + dynamic suffix.
// Static prefix (legal glossary, instructions) → cache_control: ephemeral
// Dynamic suffix (per-request context) → no cache control

import Anthropic from '@anthropic-ai/sdk';
const client = new Anthropic();

// Static: the full legal clause glossary — 4,000 tokens, same on every call
const LEGAL_GLOSSARY = `You are a contract analysis assistant...
[Full glossary here — 4,000 tokens]`;

// Dynamic: per-request instructions — 200 tokens, varies per request type
function buildSystemPrompt(analysisType) {
  return `Analysis type: ${analysisType}. Focus on clauses relevant to ${analysisType}.`;
}

export async function analyzeWithCaching(contractText, analysisType) {
  return client.messages.create({
    model: 'claude-sonnet-5',
    max_tokens: 512,
    system: [
      {
        type: 'text',
        text: LEGAL_GLOSSARY,
        cache_control: { type: 'ephemeral' }, // Cache this prefix for 5 minutes
      },
      {
        type: 'text',
        text: buildSystemPrompt(analysisType), // NOT cached — changes per request
      },
    ],
    messages: [{
      role: 'user',
      content: contractText,
    }],
  });
}

// Cost math — 1000 requests per hour:
// Without caching: 4,000 tokens × $3/M × 1000 = $12/hour just for system prompt
// With caching (99% cache hit rate): $12 × 0.10 = $1.20/hour
// Savings: $10.80/hour = $7,776/month on the system prompt alone

// Cache hit rate monitoring:
// response.usage.cache_read_input_tokens  → tokens served from cache (cheap)
// response.usage.cache_creation_input_tokens → tokens used to populate cache (normal price)
// response.usage.input_tokens → uncached input tokens
Technique 3

Model Routing: Match Task Complexity to Model Tier

Not every task needs the most capable model. Sending a "classify this email as spam or not spam" request to Claude Opus is like hiring a senior staff engineer to sort the mail. The 2026 model tier economics roughly look like this:

Model tierRelative costBest forNot ideal for
Haiku (small/fast)1×Classification, extraction, formatting, simple Q&AComplex reasoning, nuanced writing, multi-step analysis
Sonnet (mid)5–8×Multi-step reasoning, code generation, extraction from complex documentsTasks Haiku handles; tasks needing Opus-level depth
Opus/large (flagship)15–30×Complex analysis, creative synthesis, nuanced judgment callsTasks cheaper models handle equivalently

In absolute terms the gap between tiers is 10–20x: Haiku 4.5 ~$0.80 / 1M input tokens, Sonnet 4.6 ~$3.00, Opus 4.8 ~$15.00. A routing classifier (itself a fast, cheap model call) can categorise each request and dispatch it to the right tier. The overhead is negligible: a Haiku classification call costs about $0.0001 and saves $0.01–$0.15 per mis-routed request.

def route_query(query: str) -> str:
    classification = haiku.classify(
        query,
        categories=["simple_faq", "standard_task", "complex_reasoning"]
    )
    return {
        "simple_faq": "claude-haiku-4-5",
        "standard_task": "claude-sonnet-4-6",
        "complex_reasoning": "claude-opus-4-8"
    }[classification]

Routing Decision Framework

The key is identifying which steps in your pipeline genuinely require flagship model capability versus which steps are effectively structured data extraction. A contract analysis pipeline has multiple steps — each with different complexity:

  • Step: "Does this document contain a termination clause?" → Binary classification. Haiku.
  • Step: "Extract all date-based obligations from this clause." → Structured extraction. Haiku or Sonnet.
  • Step: "Identify the top 3 business risks in this contract." → Reasoning + judgment. Sonnet.
  • Step: "Write a risk memo for the board explaining the unusual liability structure." → Complex synthesis. Opus.
JavaScript — Automatic Model Router by Task Type 
// model-router.js
// Routes API calls to the cheapest model that meets quality requirements.
// Uses a task taxonomy to determine model tier.

import Anthropic from '@anthropic-ai/sdk';
const client = new Anthropic();

const MODEL_TIERS = {
  haiku:  'claude-haiku-4-5-20251001',
  sonnet: 'claude-sonnet-5',
  opus:   'claude-opus-5',
};

// Task taxonomy → model tier mapping
const TASK_TIER_MAP = {
  // Classification: binary or small-N labels — Haiku always
  classification: 'haiku',
  sentiment: 'haiku',
  routing: 'haiku',
  tagging: 'haiku',
  formatting: 'haiku',

  // Extraction: pull structured data from text — Haiku for simple, Sonnet for complex
  simple_extraction: 'haiku',
  complex_extraction: 'sonnet',
  code_extraction: 'sonnet',

  // Generation: write new content — Sonnet for most, Opus for high-stakes
  summary: 'sonnet',
  draft: 'sonnet',
  analysis: 'sonnet',
  code_generation: 'sonnet',

  // Reasoning: requires deep judgment — Opus
  legal_analysis: 'opus',
  risk_assessment: 'opus',
  architecture_review: 'opus',
  complex_debugging: 'opus',
};

export async function routedApiCall({ taskType, prompt, systemPrompt, maxTokens }) {
  const tier = TASK_TIER_MAP[taskType] ?? 'sonnet'; // Default to Sonnet if unknown
  const model = MODEL_TIERS[tier];

  const start = Date.now();
  const response = await client.messages.create({
    model,
    max_tokens: maxTokens,
    system: systemPrompt,
    messages: [{ role: 'user', content: prompt }],
  });

  const latencyMs = Date.now() - start;
  const inputTokens = response.usage.input_tokens;
  const outputTokens = response.usage.output_tokens;

  // Log for cost observability (see monitoring section)
  console.log(JSON.stringify({
    event: 'llm_call',
    taskType,
    model,
    tier,
    inputTokens,
    outputTokens,
    latencyMs,
    // Cost estimate (rough, update with actual pricing):
    estimatedCostUsd: (inputTokens / 1_000_000 * TIER_COSTS[tier].input) +
                      (outputTokens / 1_000_000 * TIER_COSTS[tier].output),
  }));

  return response;
}

const TIER_COSTS = {
  haiku:  { input: 0.80,  output: 4.00  },
  sonnet: { input: 3.00,  output: 15.00 },
  opus:   { input: 15.00, output: 75.00 },
};
Technique 4

Context window management

For multi-turn conversations, the full conversation history is re-sent with every request. A 20-turn conversation where each turn averages 500 tokens sends 10,000 tokens of history on every request — even though the last 2–3 turns are almost always sufficient for the model to answer correctly.

Strategies in ascending cost savings

  • Sliding window: Keep only the last N turns in context. Easiest to implement; loses long-term session context.
  • Progressive summarisation: Summarise older turns into a compressed summary and keep recent turns verbatim. Preserves relevant context while reducing token count by 60–80%.
  • Semantic retrieval: Store all turns as embeddings; retrieve only the most relevant turns for each request. Near-lossless context at O(1) token count per turn.
Technique 5

Batch API for async workloads

Most LLM providers offer a batch API that processes requests asynchronously (within 24 hours) at 50% of the synchronous price. If you have workloads that don't need immediate responses — nightly report generation, bulk classification, embedding refreshes, offline content processing — use batch mode exclusively. 

from anthropic import Anthropic

client = Anthropic()

# Batch: 50% cheaper, 24hr SLA
batch = client.messages.batches.create(
    requests=[
        {"custom_id": f"req_{i}", "params": {"model": "claude-haiku-4-5", "messages": [...]}}
        for i, item in enumerate(bulk_items)
    ]
)
# Poll for completion; retrieve results batch
print(f"Batch ID: {batch.id}  Status: {batch.processing_status}")
Technique 6

RAG instead of context stuffing

The instinct when building a knowledge-base application is to put all the relevant documents in the system prompt. At scale, this is prohibitively expensive — and the model's performance degrades when the context is packed with documents only partially relevant to the query.

Retrieval-Augmented Generation (RAG) replaces context stuffing with retrieval: embed the knowledge base, retrieve only the top-K relevant chunks for each query, and inject only those chunks into the context. Typical result: 80% context token reduction with equal or better accuracy because the injected context is more targeted.

The cost of the embedding + retrieval step is typically $0.0001 per query — negligible against the token savings.

Technique 7

Response caching for repeated queries

Many production LLM applications receive a small set of high-frequency queries. Caching the responses to these queries eliminates API calls entirely for cache hits. Implementation:

  • Exact match caching: Hash the full request (system prompt + user message) and cache the response in Redis with a TTL. Trivial to implement; effective for FAQ-style applications where users repeat common queries.
  • Semantic caching: Embed the user query and check for high-similarity prior queries in a vector store. Cache hit if similarity exceeds threshold (typically 0.95). Handles paraphrases and spelling variants.

Real-world cache hit rates for customer support applications: 30–60%. That fraction of requests costs zero API tokens.

Technique 8

Fine-tuning to reduce prompt overhead

When a system prompt contains more than 500 tokens of instructions that apply to every request — persona, output format, constraints, examples — fine-tuning bakes those instructions into the model weights. Post-fine-tuning, the system prompt can be reduced to a few sentences.

The break-even calculation: fine-tuning cost (one-time) vs. token savings per request × request volume. For high-volume applications (1M+ requests/month) with large system prompts (1000+ tokens), fine-tuning pays back the one-time cost in days. For low-volume applications, it rarely makes sense.

Priority order

Which techniques to apply first

Apply in priority order: Output length control → prompt caching → model routing → context window management → batch API → RAG → response caching → fine-tuning. Each technique has diminishing returns and rising complexity; start with the first three before considering the rest. And always attack the largest cost component first, which you can only know by measuring (next section).

Monitoring

Cost Observability: Alert Before the Bill Arrives

The Formly team did not notice their cost explosion until three months in, because they had no per-feature cost tracking. The bill was one big number. They had no idea whether the document classifier or the risk memo generator was responsible for the spike.

Every LLM call should emit a structured log event with: task type, model used, input tokens, output tokens, cache hit/miss, and estimated cost. These events can be aggregated in any time-series store (Datadog, Grafana, ClickHouse) to show:

  • Cost per feature — which pipeline step drives spend
  • Cost per user — identify power users or abuse patterns
  • Output token distribution — p50/p95/p99 output lengths per task type
  • Cache hit rate — prompt cache effectiveness over time
  • Model routing distribution — are the right tasks hitting the right models?
JavaScript — Cost Budget Alert System 
// cost-budget-alerter.js
// Tracks rolling 24-hour LLM spend and alerts before daily budget is exceeded.
import Redis from 'ioredis';
const redis = new Redis(process.env.REDIS_URL);

const DAILY_BUDGET_USD = parseFloat(process.env.LLM_DAILY_BUDGET ?? '500');
const ALERT_THRESHOLD = 0.80; // Alert at 80% of budget

export async function recordLlmCost({ taskType, model, inputTokens, outputTokens, cacheHit }) {
  const costs = {
    'claude-haiku-4-5-20251001': { input: 0.80, output: 4.00, cachedInput: 0.08 },
    'claude-sonnet-5':           { input: 3.00, output: 15.00, cachedInput: 0.30 },
    'claude-opus-5':             { input: 15.00, output: 75.00, cachedInput: 1.50 },
  };

  const pricing = costs[model] ?? costs['claude-sonnet-5'];
  const inputCost = cacheHit
    ? (inputTokens / 1_000_000) * pricing.cachedInput
    : (inputTokens / 1_000_000) * pricing.input;
  const outputCost = (outputTokens / 1_000_000) * pricing.output;
  const totalCost = inputCost + outputCost;

  // Increment rolling 24-hour counter (in microdollars for integer precision)
  const dayKey = `llm:cost:${new Date().toISOString().slice(0, 10)}`;
  const taskKey = `llm:cost:task:${taskType}:${new Date().toISOString().slice(0, 10)}`;

  const [total] = await redis.pipeline()
    .incrbyfloat(dayKey, totalCost)
    .expire(dayKey, 86400 * 2)
    .incrbyfloat(taskKey, totalCost)
    .expire(taskKey, 86400 * 2)
    .exec();

  const currentDaySpend = parseFloat(total[1]);

  // Alert at threshold
  if (currentDaySpend >= DAILY_BUDGET_USD * ALERT_THRESHOLD) {
    const alreadyAlerted = await redis.set(
      `llm:alert:${dayKey}`, '1', 'NX', 'EX', 3600
    );
    if (alreadyAlerted) {
      await sendAlert({
        title: 'LLM Daily Budget Alert',
        message: `Spent $${currentDaySpend.toFixed(2)} of $${DAILY_BUDGET_USD} daily budget (${Math.round(currentDaySpend/DAILY_BUDGET_USD*100)}%)`,
        severity: currentDaySpend >= DAILY_BUDGET_USD ? 'critical' : 'warning',
      });
    }
  }

  return { totalCost, currentDaySpend };
}

async function sendAlert({ title, message, severity }) {
  // Hook into your alerting system (PagerDuty, Slack, email)
  console.error(`[${severity.toUpperCase()}] ${title}: ${message}`);

}
Production Gotchas

LLM Cost Failure Modes Engineers Miss

  • Streaming responses counted at generation, not consumption. If you stream a response and the user closes the browser after 100 tokens, you are billed for all tokens generated — not just the tokens the user received. For streaming use cases, set max_tokens aggressively and monitor generation vs. consumption rates.
  • Tool call overhead. Using the tools API adds tokens for the tool definition schema on every call. A complex tool with 10 parameters may add 400+ tokens to every request. If you use tools for structured output, measure the token overhead of the schema and factor it into your cost model.
  • Retry amplification of expensive calls. If a retry policy retries expensive Opus calls on timeout or error, each retry doubles your cost for that request. For expensive model tiers, retry with exponential backoff and a maximum of 2 retries — not 5.
  • Prompt caching cold starts on new deployments. When you deploy a new version of the system prompt, the cache is invalidated. The first N requests after deployment (until the cache warms up) are billed at uncached rates. For high-volume systems, stagger deployments and pre-warm the cache with a synthetic request immediately after deploy.
  • Long-context documents sent in full when chunking would suffice. Sending a 50-page contract as a single 80,000-token context costs 8× more than processing it in 10,000-token chunks with a final synthesis step. For most document analysis tasks, chunking with a final aggregation is cheaper and often produces better results (less relevant context diluting the important sections).
Checklist

LLM Cost Optimization Checklist

  • max_tokens set explicitly on every API call (never relying on model default).
  • Structured output (JSON via tool use) used wherever possible instead of prose.
  • System prompt split into static prefix (cached) + dynamic suffix (uncached).
  • Prompt cache hit rate >90% for high-frequency API call paths.
  • Model tier assigned per task type; Haiku used for classification and extraction steps.
  • Cost per call logged as a structured event with task type, model, tokens, and USD estimate.
  • Daily cost budget configured; alerts at 80% and 100% of budget.
  • Cost per feature/pipeline step tracked in a time-series dashboard.
  • Long documents chunked before sending; no context over 50K tokens unless necessary.
  • Retry policy for expensive tiers capped at max 2 retries with backoff.
  • Multi-turn contexts bounded (sliding window, summarisation or semantic retrieval).
  • Non-urgent workloads moved to the batch API; RAG used instead of context stuffing.
  • Exact and semantic response caching in place for high-frequency queries.
  • Fine-tuning evaluated (break-even) for high-volume apps with 1000+ token system prompts.
Common questions

FAQ

  • Which technique has the best ROI for a new application?

    Prompt caching + model routing. Prompt caching requires one line of configuration and reduces input token costs by 90% for repeated system prompts. Model routing requires a classifier but reduces per-request model cost by 75–90% for simple queries. Together they address the two largest cost drivers before you've written 50 lines of optimisation code.

  • Does context window management affect output quality?

    Sliding window does — it loses long-term context. Progressive summarisation is nearly lossless for most use cases because the summary captures the key decisions and established facts. Semantic retrieval is lossless by design but adds latency. For a chatbot, progressive summarisation is the standard starting point.

  • Is the 70% cost reduction claim realistic for all applications?

    70% is achievable when starting from zero optimisation and applying all eight techniques. The specific savings depend heavily on application structure: a simple FAQ bot gets more from response caching; a complex agentic application gets more from model routing and context management. Measure first — find your largest cost driver and optimise that specifically.

Key Takeaway

LLM cost spikes are almost always the same story: a prototype with careful prompts and eyeballed outputs shipped to production without output constraints, model routing, or cost instrumentation. Cost is driven by uncontrolled output length, input token repetition (system prompt, conversation history) and over-qualified model selection, not by prompt length. Setting max_tokens on every call, caching the static system prompt, and routing classification and extraction to Haiku instead of Opus are configuration changes that take a day and reliably cut spend 40–80%. Cost observability at the feature and task level is what stops the problem recurring: it tells you immediately which new feature caused the next spike instead of waiting three months for the bill.
