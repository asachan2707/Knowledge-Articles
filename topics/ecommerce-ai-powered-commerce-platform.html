E-Commerce System Design Interview: Building an AI-Powered Commerce Platform (From MVP to GenAI)

A complete walkthrough of designing an Amazon-scale e-commerce platform in a system design interview — starting with the correct MVP architecture, identifying where it fails at scale, and then placing GenAI exactly where the system is already weak: semantic search, contextual recommendations, AI-assisted fraud detection, and LLM-powered customer service. The core principle: generative AI is a layer you place precisely where a system is already weak, not a feature you bolt on for optics.

Domain: System Design · AI Architecture · Interview Prep Published: 2026-08-23

An AI-powered commerce platform is not an e-commerce system with a chatbot bolted on. It is a system where the core commerce flows — discovery, personalization, service, fraud prevention — are fundamentally more intelligent because generative models are embedded into the data paths that power them. Getting there requires first building the commerce foundation correctly, then identifying the specific points where that foundation breaks, and then deploying GenAI precisely at those failure points.

Interview principle: "Generative AI is not a product. It is a layer you place exactly where a system is already weak." Design the core system first. Identify where it fails to interpret rather than just store. Only then introduce generative capabilities — with a budget, a latency constraint, and a fallback.

Interview scenario · Senior backend engineer, Meera Iyer

The interviewer, Daniel Cole, opens: "We're building a large-scale marketplace. Think Amazon scale. Walk me through how you'd design it, and tell me where you'd introduce AI."

A weak answer: "I'd use a recommendation engine and a search bar and maybe add a chatbot." This describes features, not architecture. It does not answer why AI is needed, where traditional approaches break, or what the cost/latency/accuracy tradeoffs look like.

The correct answer: scope the MVP, build it, name the failure points at scale, then evolve. "Let me design the core commerce flows first. Then I'll show you exactly where they break — and that will tell us where AI belongs."

Step 1 — Scope & Constraints

Define the Problem Before Designing the Solution

A senior engineer asks clarifying questions before drawing a single box:

  • Scale: 100M registered users, 10M products, 500K orders/day, 50K concurrent users at peak (flash sales: 5× peak = 250K).
  • Consistency requirements: Inventory must be strongly consistent (double-selling a limited item is catastrophic). Order status can be eventually consistent.
  • Read/write ratio: Product catalog: ~100:1 read-heavy. Orders: write-heavy during checkout. Recommendations: read-only.
  • SLA: Search latency P99 < 200ms. Product page load P99 < 500ms. Checkout API P99 < 2s.
  • AI scope: Which flows need GenAI? Search, recommendations, customer service, fraud — all are candidates but have different ROI and complexity.
  • Budget for AI inference: LLM calls are 50–200× more expensive than a cache lookup. Every AI component needs a cost justification.

The MVP is five services, each with a well-defined data model and a clear failure mode. Do not skip this step — the AI integration points emerge directly from the MVP's weaknesses.

Data model highlights

// Core tables (PostgreSQL)

// products — catalog, read-heavy, denormalized for search
CREATE TABLE products (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  seller_id   UUID NOT NULL REFERENCES sellers(id),
  title       TEXT NOT NULL,
  description TEXT,
  category_id INT NOT NULL REFERENCES categories(id),
  price_cents BIGINT NOT NULL,          -- store money as integer cents, never FLOAT
  attributes  JSONB,                    -- flexible product attributes (color, size, material)
  created_at  TIMESTAMPTZ DEFAULT now(),
  search_tsv  TSVECTOR GENERATED ALWAYS AS (
    to_tsvector('english', title || ' ' || coalesce(description, ''))
  ) STORED                              -- full-text search index, auto-maintained
);

-- inventory — strong consistency required; no over-selling
CREATE TABLE inventory (
  product_id   UUID PRIMARY KEY REFERENCES products(id),
  quantity     INT NOT NULL CHECK (quantity >= 0),
  reserved     INT NOT NULL DEFAULT 0,
  version      BIGINT NOT NULL DEFAULT 1  -- optimistic locking version counter
);

-- reserve inventory atomically (Lua script in Redis for pre-check, SQL for authoritative write)
-- Redis: DECRBY product:stock:{id} quantity → check >= 0; if yes, proceed to SQL
-- SQL:   UPDATE inventory SET quantity = quantity - ?, reserved = reserved + ?
--        WHERE product_id = ? AND quantity >= ? -- prevents negative stock at DB level

-- orders — event-driven state machine
CREATE TABLE orders (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     UUID NOT NULL REFERENCES users(id),
  status      TEXT NOT NULL DEFAULT 'PENDING'  -- PENDING→CONFIRMED→SHIPPED→DELIVERED→CANCELLED
               CHECK (status IN ('PENDING','PAYMENT_INITIATED','CONFIRMED','SHIPPED','DELIVERED','CANCELLED')),
  total_cents BIGINT NOT NULL,
  created_at  TIMESTAMPTZ DEFAULT now()
);

-- payments — idempotency is the most critical property
CREATE TABLE payments (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id        UUID NOT NULL REFERENCES orders(id),
  idempotency_key UUID NOT NULL UNIQUE,      -- client-generated; prevents duplicate charges
  amount_cents    BIGINT NOT NULL,
  status          TEXT NOT NULL DEFAULT 'PENDING'
                  CHECK (status IN ('PENDING','AUTHORIZED','CAPTURED','FAILED','REFUNDED')),
  psp_reference   TEXT,                      -- Stripe charge ID, Razorpay payment ID
  created_at      TIMESTAMPTZ DEFAULT now()
);

Checkout flow: distributed transaction with the Saga pattern

The checkout flow spans three services (Inventory, Payment, Order). A distributed transaction cannot use 2PC (two-phase commit) at this scale — it holds locks across services, creating a latency and availability failure mode. The Saga pattern replaces 2PC: each step in the sequence executes locally and, on failure, triggers a compensating transaction to undo prior steps.

  1. Reserve inventory (Inventory Service) — decrement stock, create reservation with TTL. Compensating action: release reservation.
  2. Authorize payment (Payment Service) — call PSP, hold funds. Compensating action: void authorization.
  3. Confirm order (Order Service) — write CONFIRMED status, publish order.confirmed event to Kafka. Compensating action: cancel order, emit order.cancelled.
  4. Capture payment (Payment Service) — finalize charge after order is confirmed.

If step 2 (payment authorization) fails, the Saga executes step 1's compensating action (release reservation). The customer sees "payment failed"; the inventory is correctly restored. No cross-service transaction lock is held.

Step 3 — Where the MVP Fails

The Three Failure Modes That GenAI Fixes

The MVP handles commerce correctly. But "handling commerce correctly" is the table stakes for any marketplace. At Amazon scale, the systems that drive growth — search, recommendations, customer service — all hit fundamental limits with traditional approaches:

Failure 1: Search cannot understand intent

Elasticsearch's inverted index matches query terms to product field terms. A user who searches "comfy shoes for long walks" gets results for products with those exact words. Products titled "ergonomic hiking sneakers for plantar fasciitis" and "orthopedic walking footwear" are not matched. Keyword search is syntactic; human intent is semantic. At 10M products, the mismatch between what users type and what products are titled is the primary driver of failed searches — Amazon's internal research consistently showed that 15–25% of searches return zero results or irrelevant first-page results using keyword-only ranking.

Failure 2: Recommendations are rule-based and generic

Collaborative filtering ("customers who bought X also bought Y") requires a critical mass of purchase history. For new products, new users, and long-tail catalog items, there is no history. Rule-based fallbacks ("show best-sellers in the same category") are not personalized — they ignore the current browsing session, the user's stated intent, and the product's specific attributes. Netflix's recommendation research showed that rule-based systems underperform collaborative filtering by 15–30% on engagement metrics, and collaborative filtering underperforms session-aware models by another 10–20%.

Failure 3: Customer service is slow and expensive

At 500K orders/day, even a 2% contact rate means 10,000 customer service queries per day. Human agents cost $8–15 per interaction in India/Southeast Asia, $20–40 in the US/EU. At 10,000 interactions/day, the pure labor cost is $80K–$150K/day just for reactive support. Traditional rule-based chatbots handle only the most templated queries (order status, return initiation) and escalate everything else, failing customers on the questions where self-service would actually add value.

Step 4 — GenAI Integration Layer

Four AI Components, Each Targeting a Specific Failure Mode

AI Component 1: Semantic Search with Vector Embeddings

Replace (or augment) keyword search with semantic similarity search. Every product's title + description is embedded into a high-dimensional vector using a text embedding model (OpenAI text-embedding-3-large, Anthropic's embeddings, or a self-hosted sentence-transformers model for cost control). At query time, the user's query is embedded using the same model, and the top-K products by cosine similarity are retrieved from a vector database.

"Comfy shoes for long walks" now retrieves "ergonomic hiking sneakers for plantar fasciitis" because their vector representations are close in embedding space — both encode concepts related to walking comfort and foot support — even though they share no keywords.

ApproachLatencyCostAccuracySuitable for
Pure keyword (Elasticsearch BM25)<50ms~$0.0001/queryMedium (syntactic)Exact term match, SKU lookup
Semantic (vector similarity)20–100ms~$0.001–0.01/queryHigh (semantic)Natural language intent, long-tail queries
Hybrid (BM25 + vector RRF fusion)50–150ms~$0.005/queryHighestProduction: best of both worlds

Architecture: Product embeddings are generated offline in an ingestion pipeline (when a product is created or updated) and stored in a vector database (Pinecone, Weaviate, pgvector). At query time, the Search Service embeds the query (online inference, <20ms with a small embedding model), retrieves top-500 vectors from the vector DB, reranks by combining BM25 score and cosine similarity (Reciprocal Rank Fusion), and returns top-20 results. The LLM is NOT in the search hot path — only the embedding model (small, fast, cheap) is.

Scaling constraint: A 10M-product catalog with 1536-dimensional embeddings (float32) requires 10M × 1536 × 4 bytes = ~61 GB of storage in the vector index. This fits in memory for a single large Pinecone pod or a pgvector instance on a 128 GB node. At 100M products, sharding the vector index by category is required.

JavaScript Example — Search Service: Hybrid Search 
import { OpenAI }    from 'openai';
import { Pinecone }  from '@pinecone-database/pinecone';
import esClient      from './elasticsearch-client.js';

const openai   = new OpenAI();
const pinecone = new Pinecone({ apiKey: process.env.PINECONE_KEY });
const index    = pinecone.index('products');

/**
 * Hybrid search: combine semantic similarity (vector) with keyword BM25 score.
 * Returns top-20 product IDs ranked by Reciprocal Rank Fusion.
 */
export async function hybridSearch(query, { topK = 20, categoryId } = {}) {
  // Step 1: embed the query (small embedding model, ~15ms)
  const embeddingResponse = await openai.embeddings.create({
    model: 'text-embedding-3-small',    // faster + cheaper than 3-large, adequate for search
    input: query,
  });
  const queryVector = embeddingResponse.data[0].embedding;

  // Step 2: vector similarity search (Pinecone ANN, ~30ms)
  const vectorFilter = categoryId ? { categoryId: { $eq: categoryId } } : undefined;
  const vectorResults = await index.query({
    vector: queryVector,
    topK: 100,
    filter: vectorFilter,
    includeMetadata: true,
  });

  // Step 3: keyword BM25 search (Elasticsearch, ~30ms) — runs in parallel with vector
  const [_, esResponse] = await Promise.all([
    Promise.resolve(),          // vector search already fired above
    esClient.search({
      index: 'products',
      body: {
        query: {
          multi_match: {
            query,
            fields: ['title^3', 'description', 'attributes.*'],  // title boosted 3×
            type: 'best_fields',
            fuzziness: 'AUTO',
          },
        },
        _source: ['id'],
        size: 100,
        ...(categoryId && { post_filter: { term: { category_id: categoryId } } }),
      },
    }),
  ]);

  // Step 4: Reciprocal Rank Fusion — combine both result sets
  // RRF score = Σ 1/(k + rank_i), k=60 (standard constant)
  const K = 60;
  const scores = new Map();

  vectorResults.matches.forEach((match, rank) => {
    const id = match.id;
    scores.set(id, (scores.get(id) ?? 0) + 1 / (K + rank + 1));
  });

  esResponse.hits.hits.forEach((hit, rank) => {
    const id = hit._source.id;
    scores.set(id, (scores.get(id) ?? 0) + 1 / (K + rank + 1));
  });

  // Sort by combined RRF score, return top-K IDs
  return [...scores.entries()]
    .sort(([, a], [, b]) => b - a)
    .slice(0, topK)
    .map(([id]) => id);
}

AI Component 2: LLM-Powered Personalization Engine

Recommendations evolve from "static collaborative filtering" to "session-aware contextual recommendation" using a two-stage pipeline:

  1. Candidate generation (offline, collaborative filtering + embeddings): For each user, pre-compute a set of 500 candidate products using matrix factorization (ALS — Alternating Least Squares) on purchase/view history. Store in Redis as a scored list with 24-hour TTL. This handles the cold-start problem for existing users.
  2. Session-aware re-ranking (online, LLM-assisted): At page-load time, pass the user's current session context (last 5 viewed products, current cart contents, current page type) to a lightweight LLM (GPT-4o-mini or Claude Haiku — fast, cheap) to re-rank the 500 candidates by relevance to the current session. This addresses the "I'm currently shopping for office furniture, stop showing me camping gear" problem.

Cost control: The LLM re-ranking call happens at most once per session start, cached for the session duration. Cost per session: ~$0.001–0.005 using Claude Haiku or GPT-4o-mini. At 50K concurrent sessions, this is $50–$250/hour in inference cost — significant but justified by recommendation CTR lift (typically 20–40% improvement in session-aware models).

AI Component 3: Multimodal Product Intelligence

Sellers upload 5–10 images per product. Traditional systems store images as files and index only the text metadata the seller provides. AI-powered product intelligence adds:

  • Automatic attribute extraction: A vision model (GPT-4o vision, or a fine-tuned BLIP-2) analyzes product images and extracts structured attributes — color (#4A90D9 → "steel blue"), material ("appears to be genuine leather"), style ("minimalist, suitable for formal occasions"), condition ("new, packaging intact"). These extracted attributes enrich search, reduce seller onboarding friction, and improve matching quality for attribute-filtered searches.
  • Automated description enrichment: For products where the seller provided only a title and images, an LLM generates a complete product description in the marketplace's standard format. This reduces catalog incompleteness — a major SEO and conversion driver — at scale.
  • Visual similarity search: Users can upload a photo ("find products that look like this") and retrieve visually similar items from the catalog. The product's image embedding (from a vision model) enables this without keyword search at all.

AI Component 4: LLM-Powered Customer Service Agent

The customer service layer is the highest-ROI GenAI application in commerce because it replaces human labor directly. The architecture:

  1. Structured data access tools: The LLM is given function-calling tools that query live data — order status, return eligibility, refund status, product availability. It does not hallucinate these; it calls the tools and presents factual results in natural language.
  2. RAG over policy and FAQ documents: The LLM has a retriever for the marketplace's return policy, warranty terms, and FAQ corpus. Queries about policy ("can I return this after 45 days?") are answered from retrieved policy text, not from the model's parametric knowledge. This makes the agent auditable and updatable — change the policy document and the agent's answers change without retraining.
  3. Escalation to human agents: The LLM classifies each interaction on a confidence score and complexity axis. High-confidence, low-complexity queries (order tracking, return initiation) are fully resolved autonomously. Low-confidence or high-complexity queries (payment disputes, fraud claims, legal notices) are escalated to a human agent with a full context summary pre-generated by the LLM. The human receives a one-paragraph brief, not a raw chat transcript.

// Agentic loop — Claude drives the conversation and decides which tools to call
export async function handleCustomerQuery(userId, userMessage, conversationHistory = []) {
  const messages = [
    ...conversationHistory,
    { role: 'user', content: userMessage },
  ];

  const systemPrompt = `You are a helpful customer service agent for ShopAI marketplace.
You have access to order management tools. Always look up live data before answering
questions about orders, returns, or policies — never guess. If a query is outside
your tools' capabilities or involves a financial dispute over $100, respond with
ACTION_REQUIRED:ESCALATE and a one-paragraph summary for the human agent.`;

  // Agentic loop: Claude may call multiple tools before producing the final answer
  while (true) {
    const response = await client.messages.create({
      model:      'claude-haiku-4-5-20251001',  // fast + cheap for customer service
      max_tokens: 1024,
      system:     systemPrompt,
      tools,
      messages,
    });

    if (response.stop_reason === 'end_turn') {
      // Final answer — extract text and return
      const textBlock = response.content.find(b => b.type === 'text');
      return { answer: textBlock?.text, requiresEscalation: textBlock?.text?.includes('ACTION_REQUIRED:ESCALATE') };
    }

    if (response.stop_reason === 'tool_use') {
      // Execute all tool calls and add results to the message loop
      const toolResults = await Promise.all(
        response.content
          .filter(b => b.type === 'tool_use')
          .map(async (toolUse) => ({
            type:        'tool_result',
            tool_use_id: toolUse.id,
            content:     JSON.stringify(await executeTool(toolUse.name, toolUse.input)),
          }))
      );

      // Append Claude's tool-use turn and the tool results to the message history
      messages.push({ role: 'assistant', content: response.content });
      messages.push({ role: 'user',      content: toolResults });
      // Loop continues — Claude sees the tool results and decides the next action
    }
  }
}
Step 5 — Fraud Detection

AI-Assisted Fraud Prevention: Rules + Behavioral Anomaly Detection

Payment fraud at marketplace scale cannot be handled by rules alone. Rules are public knowledge to sophisticated fraudsters who probe the thresholds and adapt. The effective architecture combines deterministic rules (fast, cheap, handles obvious fraud) with ML-based behavioral anomaly detection (catches novel patterns).

Layer 1 — Deterministic rules (milliseconds, synchronous in checkout): Velocity checks (more than 3 orders from the same IP in 10 minutes), card BIN block list, address mismatch (shipping to an address that does not match the billing ZIP), impossible geography (order from NYC, previous order 5 minutes ago from Jakarta). These rules run synchronously in the checkout flow — a failed rule blocks the order immediately.

Layer 2 — ML behavioral model (100–200ms, synchronous): A gradient-boosted tree model (XGBoost) trained on historical labeled transactions outputs a fraud score 0–1. Features: user tenure, typical order value for this user, deviation from the user's normal shopping hour, number of distinct addresses used in last 30 days, device fingerprint mismatch. Score > 0.8: block. Score 0.5–0.8: require additional verification (2FA, OTP). Score < 0.5: approve. The ML model adds <100ms to checkout latency on a GPU inference endpoint.

Layer 3 — LLM review for borderline cases (async, post-transaction): For transactions scored 0.5–0.7 (borderline), an LLM reviews the full transaction context — browsing history leading to purchase, shipping address patterns, communication history, product category risk — and generates a free-text risk assessment for the fraud team's review queue. This is not in the checkout hot path; it runs async and flags the transaction for human review within 5 minutes. LLM cost is justified here: $0.01–0.05 per borderline transaction, against an average fraud loss of $200–$5,000 per successful fraudulent order.

Full Architecture

The Complete System: MVP + GenAI Integration Points

The following describes the data flow through the full system at request time:

Search request path: Client → API Gateway → Search BFF → [Embedding Service (online, 15ms) + Elasticsearch (30ms) in parallel] → Pinecone vector DB (30ms) → RRF fusion → Product Catalog (fetch full product data for top-20 IDs) → Response. Total P99: ~120ms.

Home page / recommendations path: Client → API Gateway → Recommendation BFF → Redis (pre-computed candidates, <5ms) → [if cache miss: LLM re-ranker (Claude Haiku, 200–400ms) + session context] → CDN-cached product cards → Response. Total P99: ~500ms (first session load), <20ms (cached).

Checkout path: Client → API Gateway → Checkout Orchestrator → [Rule engine (sync, <10ms) + Fraud ML model (sync, <100ms)] → if approved: Saga [Inventory reserve → Payment authorize → Order confirm] → Kafka event (order.confirmed) → Response. Total P99: ~1.5s.

Infrastructure and scaling decisions

  • API Gateway: Kong or AWS API Gateway. Handles auth (JWT validation), rate limiting (per-user token bucket), routing, and SSL termination. The gateway is the first choke point — its availability directly determines platform availability. Deploy across 3 AZs, auto-scale on request rate.
  • Kafka for async event processing: order.confirmed triggers: inventory deduction (permanent), notification service (email/push), fulfillment handoff, analytics event. Decouples the order write path from downstream processing. Kafka partition key = order_id for ordering guarantees within an order's lifecycle.
  • PostgreSQL with read replicas: Write traffic goes to primary. Read traffic (product page loads, order history) goes to read replicas. Product Catalog uses a separate PostgreSQL cluster from Orders — blast radius isolation. Connection pooling via PgBouncer in front of both clusters.
  • Redis tiering: L1 (hot) Redis: inventory counts, session cache, idempotency keys — all require sub-millisecond latency, stored in-memory. L2 (warm) Redis: pre-computed recommendation lists, search suggestion caches — can use disk-backed Redis with AOF persistence.
  • CDN: Product images and static assets on Cloudflare or AWS CloudFront. ISR-style revalidation for product pages — edge-cached HTML, invalidated on price/stock change via edge KV store.
  • AI inference: Embedding model deployed on GPU inference endpoint (AWS SageMaker, Modal, or self-hosted with NVIDIA Triton). Serves search embedding requests at <20ms P99. LLM calls (customer service agent, fraud review) use the Anthropic/OpenAI API — no self-hosting justified at this scale.
Failure Modes & Production Gotchas

Where This Architecture Breaks — and How to Defend Against It

  • Vector DB cold start for new products: A new product has no embedding until the ingestion pipeline runs. During the window between product creation and embedding generation (typically 1–30 seconds for async ingestion), the product is invisible to semantic search. Mitigation: synchronous embedding on product create (add <100ms to the create API), or a hybrid fallback where new products surface via keyword-only search until the vector is available.
  • LLM API unavailability in the checkout hot path: The LLM is deliberately NOT in the checkout flow — only the rule engine and the ML model are. Both have fallbacks (fail-open with flagging for async review). If the LLM API is down, checkout continues normally; borderline fraud cases are queued for manual review. Never put an external LLM API in a synchronous checkout critical path.
  • Inventory race condition at flash sale scale: At 250K concurrent users hitting the same product in a flash sale, optimistic locking on PostgreSQL generates massive retry storms. The correct architecture: Redis DECRBY as a pre-check (atomic, sub-millisecond, handles 100K+ ops/sec), with PostgreSQL as the authoritative write after Redis succeeds. Redis pre-check prevents most requests from ever hitting PostgreSQL under flash sale load.
  • Embedding model version skew: If the embedding model version changes (e.g., migrating from text-embedding-3-small to a fine-tuned domain model), all existing product embeddings must be regenerated before the new model is used for query embeddings. Querying with a v2 embedding against a v1 index produces meaningless similarity scores. Maintain a model_version field on each embedding record and enforce version consistency in the search service.
  • LLM hallucination in customer service: Without RAG, the LLM will confidently state wrong return policies, incorrect shipping timelines, and invented warranty terms. The fix: every factual claim the LLM makes must come from a tool call (live data) or a retrieved policy document (RAG). The system prompt explicitly prohibits the model from stating facts it cannot source. Add a citation requirement: every policy statement must include the policy document section it was drawn from.
  • Recommendation feedback loop amplification: If recommendations are based solely on what users click, popular items get shown more, get clicked more, get shown more — the "rich get richer" feedback loop reduces catalog diversity over time. Mitigation: inject exploration factor (ε-greedy: 10% of recommendations are random from outside the pre-computed set), diversity constraint (no more than 3 products from the same seller in a recommendations row), and periodic rebalancing of the collaborative filtering model.

Interview Checklist

What a Strong Answer Must Include

  • Scope the problem with explicit numbers (users, products, orders/day, concurrency) before drawing any boxes.
  • Design the MVP: 5 core services (Catalog, Inventory, Order, Payment, User), their datastores, and their failure modes.
  • Explain the Saga pattern for distributed checkout — why not 2PC, what the compensating transactions are.
  • Name the three MVP failure modes: keyword search intent mismatch, cold-start recommendations, customer service cost at scale.
  • Introduce AI at each failure mode, with a specific technology choice (vector DB for semantic search, LLM re-ranker for recommendations, tool-calling agent for customer service).
  • State the cost and latency for each AI component — never introduce AI without a budget.
  • Keep the LLM out of the synchronous checkout path — latency and availability are non-negotiable there.
  • Name the failure modes of the AI components: embedding version skew, LLM hallucination without RAG, recommendation feedback loop amplification.
  • Describe the fraud prevention layering: rules → ML model → LLM async review.
  • Mention the flash-sale inventory protection: Redis atomic pre-check + PostgreSQL authoritative write.
FAQ

Common questions

Should I use a dedicated vector database or just pgvector?

At 10M products and query volume under 5K queries/second, pgvector with an HNSW index in PostgreSQL is a viable and operationally simpler choice — one fewer system to manage. Above 50M products or 10K queries/second, dedicated vector databases (Pinecone, Weaviate, Qdrant) provide better performance through purpose-built ANNS (Approximate Nearest Neighbor Search) algorithms, GPU-accelerated indexing, and horizontal scaling. The interview answer: start with pgvector for operational simplicity; migrate to a dedicated vector DB when query latency or index rebuild time becomes a bottleneck.

Why not just use a full-featured AI search platform (Algolia, Elastic AI)?

Managed AI search platforms abstract the embedding model, vector index, and BM25 fusion into a single API. This is the right choice for many products — less engineering investment, faster time to market, SLA-backed latency. The interview answer should acknowledge this option. The tradeoff: cost at scale (Algolia and Elastic AI price per search unit, which becomes significant at hundreds of millions of queries/month), and reduced control over the embedding model (critical if domain-specific product nomenclature matters).

How do you handle the cold-start problem for new users in recommendations?

Three approaches: (1) Popularity-based defaults — show top-selling items in the user's first-session geography and device category. (2) Onboarding preference signal — ask two questions at registration ("What brings you here today?") and use the answers to bootstrap a preference profile. (3) Session-level inference — within the first session, the LLM re-ranker uses current browsing behavior (clicked items, search queries) as the context signal, even with no purchase history. The LLM approach is particularly powerful for new users because it does not require historical data — intent is inferred from the current session alone.

What is the right AI spend as a percentage of GMV?

Industry benchmarks for large marketplaces put AI infrastructure at 0.1–0.5% of GMV. At $1B GMV, that is $1M–$5M/year in AI inference costs. The biggest cost items are LLM APIs (customer service, fraud review), followed by embedding infrastructure (search), followed by recommendation model serving. Tracking cost per AI component as a line item in your P&L — not as an undifferentiated "cloud infrastructure" cost — is necessary for making rational decisions about which AI investments pay off.

Key Takeaway

The difference between an AI-powered e-commerce platform and an e-commerce platform with AI features bolted on is the design sequence: build the commerce foundation correctly, identify precisely where it fails to understand intent rather than just store data, and deploy GenAI at exactly those failure points with a budget, a latency constraint, and a fallback. Semantic search replaces keyword search because language models understand intent. Session-aware LLM re-ranking replaces static collaborative filtering because context changes what is relevant in real time. Tool-calling agents replace scripted chatbots because language models can reason about policy and compose multiple data sources into coherent answers. Fraud detection layers rules and ML in the hot path with LLM analysis async for the edge cases where the cost of a mistake justifies the inference spend. None of these components belong in the checkout critical path — the system must be able to complete a purchase even if every AI component is unavailable. Commerce comes first; AI makes it better.
