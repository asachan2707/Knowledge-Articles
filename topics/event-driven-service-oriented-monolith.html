Event-Driven Service-Oriented Monolith: PoC with RabbitMQ

A proof-of-concept architecture that uses internal RabbitMQ pub/sub inside a Python monolith to decouple modules without splitting into microservices. Built with FastAPI, CouchDB, and Pydantic — demonstrating how event-driven communication can work within a monolith as a stepping stone to full microservices decomposition.

SourceArmando Baratti · LinkedIn · 2024
TagsArchitecture, Engineering, Event-Driven, Monolith
JS Example✓ Event bus inside a modular monolith in Node.js

Most event-driven architecture discussions assume you're building microservices. But event-driven communication is equally valuable inside a monolith — it decouples modules, makes cross-cutting concerns like audit logging trivially composable, and creates the seams you'll need if you later split into services.

Core idea: An event-driven service-oriented monolith is a monolith whose internal modules communicate only through events rather than direct function calls. Each module publishes events; other modules subscribe. The modules are independently deployable in theory — and when the time comes to extract them, the event contracts already exist.

The architecture

What the PoC looks like

Stack in the original PoC: Python · FastAPI · RabbitMQ (internal pub/sub) · CouchDB (document store) · Pydantic (schema validation). The JavaScript equivalent below uses Node.js with an EventEmitter as the internal bus — no external broker required for a monolith.

The system is divided into modules:

  • API Layer — FastAPI routes receive HTTP requests and dispatch commands to the event bus
  • Order Module — handles order creation, subscribes to payment events
  • Payment Module — processes payment requests, publishes payment results
  • Notification Module — subscribes to any event it cares about (order created, payment failed, etc.) and sends notifications — with no knowledge of other modules
  • Audit Module — subscribes to all events and writes an immutable audit log — completely decoupled, can be added/removed without touching any other module
Key trade-off: Modules communicate via events, not return values. This means a module publishing an event has no direct knowledge of what happens next. The flow is traceable only through logs/tracing — not by reading the call stack. This is the same trade-off as full microservices, just without the network overhead.
JavaScript Example

Internal event bus in a Node.js modular monolith

JavaScript Example 
import EventEmitter from 'events';

// Internal event bus — same process, no network
// When ready to split to microservices, replace this with a Kafka/RabbitMQ client
class InternalEventBus extends EventEmitter {
  publish(eventType, payload) {
    const envelope = {
      eventType,
      payload,
      timestamp: new Date().toISOString(),
      eventId: Math.random().toString(36).slice(2),
    };
    console.log(`[bus] publish: ${eventType}`, envelope.eventId);
    this.emit(eventType, envelope);
    this.emit('*', envelope); // wildcard for audit/logging
  }

  subscribe(eventType, handler) {
    this.on(eventType, handler);
    return () => this.off(eventType, handler); // returns unsubscribe fn
  }
}

const bus = new InternalEventBus();

// ── Order Module ──
class OrderModule {
  constructor(db, bus) {
    this._db = db;
    this._bus = bus;
    // React to payment results
    bus.subscribe('payment.completed', this._onPaymentCompleted.bind(this));
    bus.subscribe('payment.failed',    this._onPaymentFailed.bind(this));
  }

  async createOrder(data) {
    const order = await this._db.orders.insert({ ...data, status: 'pending' });
    // Publish — doesn't know or care who handles this
    this._bus.publish('order.created', { orderId: order.id, amount: data.amount, userId: data.userId });
    return order;
  }

  async _onPaymentCompleted({ payload }) {
    await this._db.orders.update(payload.orderId, { status: 'confirmed' });
    this._bus.publish('order.confirmed', { orderId: payload.orderId });
  }

  async _onPaymentFailed({ payload }) {
    await this._db.orders.update(payload.orderId, { status: 'payment_failed' });
    this._bus.publish('order.cancelled', { orderId: payload.orderId, reason: 'payment_failed' });
  }
}

// ── Payment Module ──
class PaymentModule {
  constructor(paymentGateway, bus) {
    this._gateway = paymentGateway;
    this._bus = bus;
    bus.subscribe('order.created', this._onOrderCreated.bind(this));
  }

  async _onOrderCreated({ payload }) {
    const result = await this._gateway.charge(payload.amount, payload.userId)
      .catch(err => ({ success: false, error: err.message }));

    const eventType = result.success ? 'payment.completed' : 'payment.failed';
    this._bus.publish(eventType, { orderId: payload.orderId, ...result });
  }
}

// ── Notification Module — knows nothing about Order or Payment modules ──
class NotificationModule {
  constructor(mailer, bus) {
    this._mailer = mailer;
    bus.subscribe('order.confirmed', ({ payload }) =>
      this._mailer.send(payload.userId, 'Order confirmed', `Order ${payload.orderId} is confirmed`));
    bus.subscribe('order.cancelled', ({ payload }) =>
      this._mailer.send(payload.userId, 'Order cancelled', `Order ${payload.orderId} was cancelled: ${payload.reason}`));
  }
}

// ── Audit Module — subscribes to everything via wildcard ──
class AuditModule {
  constructor(auditDb, bus) {
    bus.subscribe('*', (envelope) => {
      auditDb.insert({ ...envelope, receivedAt: new Date().toISOString() });
    });
  }
}
Migration path to microservices: When ready to extract the Payment Module to a separate service, replace bus.subscribe('order.created', ...) with a Kafka consumer and replace bus.publish('payment.completed', ...) with a Kafka producer. The event schema is already defined — the only change is the transport layer. This is why building event-driven inside the monolith first pays off: the contracts exist before the split.
Pydantic schema validation

Why schema validation on events matters

In the original Python PoC, every event payload was validated with a Pydantic model. In JavaScript, this maps to validating event payloads with Zod or similar. The benefit: an event published with the wrong shape fails immediately at the publisher, not silently at the subscriber — and the error appears in the right place in the stack trace.

JavaScript Example 
// Event schema validation with simple runtime checks
const eventSchemas = {
  'order.created': (p) => {
    if (!p.orderId || !p.amount || !p.userId)
      throw new Error('order.created missing required fields: orderId, amount, userId');
    if (typeof p.amount !== 'number' || p.amount <= 0)
      throw new Error('order.created: amount must be a positive number');
  },
  'payment.completed': (p) => {
    if (!p.orderId) throw new Error('payment.completed missing orderId');
  },
};

class ValidatedEventBus extends InternalEventBus {
  publish(eventType, payload) {
    const validate = eventSchemas[eventType];
    if (validate) validate(payload); // throws immediately if invalid
    super.publish(eventType, payload);
  }
}

Key Takeaway

An event-driven modular monolith is not a halfway measure — it's a legitimate architecture pattern that combines the operational simplicity of a monolith with the decoupling benefits of event-driven design. Modules that communicate only through published events are independently testable, independently replaceable, and — when the time is right — independently extractable to microservices. The Notification and Audit modules in particular become trivially composable: any new concern subscribes to existing events without touching any other module's code.
