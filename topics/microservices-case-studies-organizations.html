Microservices Architecture & Case Studies from Netflix, Uber, Amazon, Spotify

How the world's largest platforms actually decomposed their monoliths: Netflix's chaos engineering approach, Uber's domain decomposition, Amazon's "two-pizza teams" mandate, and Spotify's squad model — each with the key architectural decision that made or broke the migration.

Reading microservices theory is necessary but not sufficient. Understanding how real organisations at massive scale actually made the transition — what they got wrong first, what forced the architectural rethink, and what made their approach specific to their team structure — is what separates cargo-culting patterns from applying them correctly.

Core idea: Every successful large-scale microservices migration had one thing in common: organisational structure drove the service boundaries, not the reverse. Conway's Law is not optional — your architecture will eventually match your communication structure whether you plan it or not.

What microservices actually are

The architecture and its traits

Microservices are small, independent services each responsible for a specific business function. They communicate over well-defined APIs (REST, gRPC, or message queues) and are deployed independently. The key traits:

  • Independent deployment — a change to the payment service doesn't require deploying the order service
  • Own database per service — each service manages its own data store; no shared schemas
  • Technology agnostic — the recommendation service can be Python; the payment service can be Go
  • Failure isolation — a crash in the review service doesn't cascade to the checkout service
  • Team-aligned boundaries — one team owns one service (or a small set of related services)
Case studies

How real companies did it

Netflix Chaos as architecture discipline

Problem: A 2008 database corruption incident took Netflix down for 3 days. The monolith had no failure isolation.

Decision: Migrated to AWS + microservices over 7 years. Introduced Chaos Monkey — a tool that randomly kills production instances — to force every service to be resilient to failure by default rather than by choice.

Key insight: You cannot build resilient services without testing failure in production. Chaos engineering isn't optional at Netflix's scale — it's the quality gate.

Technology: Hystrix (circuit breaker), Eureka (service discovery), Zuul (API gateway), Ribbon (client-side load balancing).

Uber Domain decomposition under hypergrowth

Problem: A single Node.js monolith handling all ride requests globally. As Uber expanded to 60+ countries, any deployment touched every geography simultaneously.

Decision: Decomposed by domain: trips, drivers, payments, notifications, maps, pricing — each an independent service with dedicated teams. Built an internal DOSA (Domain-Oriented Microservice Architecture) framework to standardise inter-service communication.

Key insight: Domain decomposition should follow the business domains in your org chart. Uber's engineering org was structured around domains before the services were — the migration made the architecture match what was already true organisationally.

Amazon Two-pizza team mandate

Problem: In 2002, Bezos mandated that all internal systems expose their functionality only through service interfaces — not shared libraries, not direct DB access. Any team that didn't comply would be fired.

Decision: Every team must own a service; every service interface must be externalizable. The "two-pizza team" rule: if you need more than two pizzas to feed the team, the service scope is too large.

Key insight: Amazon's microservices adoption was a management mandate, not an engineering decision. The technology followed the org structure. AWS itself grew from this — the teams that built internal services for Amazon eventually exposed them externally as S3, EC2, SQS.

Spotify Squad model and autonomous services

Problem: As Spotify scaled to hundreds of engineers, feature development became bottlenecked by cross-team dependencies and integration testing overhead.

Decision: Introduced the Squad model — small cross-functional teams (Squads) own an end-to-end feature area and its services. Squads coordinate via Tribes; shared practices via Guilds. Each Squad deploys independently without coordinating with other Squads.

Key insight: The Squad model only works if each Squad genuinely owns its entire stack including production operations. Squads that don't own operations don't feel the pain of poor architecture choices — and they'll make more of them.

JavaScript Example

Service health check + registration (Netflix/Eureka pattern)

JavaScript Example 
// Service discovery pattern: services self-register on startup,
// heartbeat to stay visible, and are removed when they stop heartbeating
// Simplified version of the Eureka client pattern used by Netflix

class ServiceRegistry {
  constructor() {
    this.services = new Map(); // name → { url, lastHeartbeat, metadata }
    this._startReaper();
  }

  register(name, url, metadata = {}) {
    this.services.set(name, { url, lastHeartbeat: Date.now(), metadata });
    console.log(`[registry] ${name} registered at ${url}`);
  }

  heartbeat(name) {
    const svc = this.services.get(name);
    if (svc) svc.lastHeartbeat = Date.now();
  }

  discover(name) {
    const svc = this.services.get(name);
    if (!svc) throw new Error(`Service not found: ${name}`);
    return svc.url;
  }

  _startReaper() {
    setInterval(() => {
      const TTL_MS = 30_000; // deregister after 30s without heartbeat
      for (const [name, svc] of this.services) {
        if (Date.now() - svc.lastHeartbeat > TTL_MS) {
          this.services.delete(name);
          console.log(`[registry] ${name} deregistered (missed heartbeats)`);
        }
      }
    }, 10_000);
  }
}

// Service client with health check loop
class MicroserviceClient {
  constructor(serviceName, registry) {
    this.name = serviceName;
    this.registry = registry;
  }

  async start(port) {
    const url = `http://localhost:${port}`;
    this.registry.register(this.name, url);

    // Send heartbeat every 10 seconds
    this._heartbeatTimer = setInterval(() => {
      this.registry.heartbeat(this.name);
    }, 10_000);

    console.log(`[${this.name}] started on ${url}`);
  }

  stop() {
    clearInterval(this._heartbeatTimer);
    // Registry reaper will remove it automatically within TTL
  }
}

// API Gateway uses the registry to route requests
class ApiGateway {
  constructor(registry) {
    this.registry = registry;
  }

  async forward(serviceName, path, options = {}) {
    const baseUrl = this.registry.discover(serviceName);
    const res = await fetch(`${baseUrl}${path}`, options);
    return res.json();
  }
}

// Usage
const registry = new ServiceRegistry();
const gateway = new ApiGateway(registry);
const paymentService = new MicroserviceClient('payment-service', registry);
await paymentService.start(3001);

Key Takeaway

Every large-scale microservices success story had one common thread: the organisation restructured teams around service boundaries first, or the services were restructured to match existing teams. Technology alone cannot fix a monolith whose failure is organisational. Netflix's chaos engineering, Uber's domain decomposition, Amazon's two-pizza mandate, and Spotify's squad model are all different answers to the same question: how do you build software at scale without coordination overhead killing delivery speed?
