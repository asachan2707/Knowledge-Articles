System Design Interview: Real-Time Leaderboard for Millions of Users

Designing a leaderboard for 50M players and 2M concurrent users isn't a SQL problem — it's a data structure problem. This guide walks through why relational sorting breaks, how Redis Sorted Sets solve ranking in O(log N), how to handle write amplification at 100k updates/second, and how to scope global vs regional vs friend leaderboards.

Source: System Design Interview Prep · Redis Documentation Domain: Backend Engineering / Gaming Infrastructure
Story · The Tournament That Broke the Database

Free Fire India Tournament, 2026

Fifty million registered players. The top 100 will win cash prizes. The tournament starts at 12:00 PM and 2 million players are competing concurrently, each completing a match roughly every 8 minutes and submitting their updated score. Do the arithmetic: 2,000,000 players divided by an 8-minute match cycle equals 250,000 score updates per minute — roughly 4,167 per second at steady state. At match-end spikes, when thousands of games conclude in the same 10-second window, the update rate breaches 100,000 per second.

The engineering team had shipped the naive implementation: a PostgreSQL table with columns (user_id BIGINT, score BIGINT, updated_at TIMESTAMPTZ), indexed by score DESC. The write path was a single UPDATE: UPDATE scores SET score = score + $points WHERE user_id = $uid. The read path for the leaderboard page was an ORDER BY: SELECT user_id, score FROM scores ORDER BY score DESC LIMIT 100. Both queries looked fine in staging with 10,000 rows.

With 50 million rows, the B-tree index on score is enormous. Every score update requires the database to locate the old index entry, remove it, compute the new score, and insert a new entry at the correct sorted position. At 4,000 writes per second, the index is under constant restructuring. Pages split and merge. Write-ahead log (WAL) volume explodes. The index is never in a stable state long enough for VACUUM to reclaim space efficiently.

The ORDER BY reads make things catastrophically worse. Even with the index, PostgreSQL must traverse the index from the highest-scored entry downward, collecting row pointers, then fetch the actual heap rows — a process that competes with write transactions for buffer pool space. With 50M rows, the query planner estimates 50M index entries to scan. At the load of a live tournament, the leaderboard SELECT starts taking 8 seconds. The index is being simultaneously modified by thousands of concurrent writes. Read-write lock contention escalates. The DB CPU climbs to 95%. The connection pool fills. Application servers start timing out.

Players see their rank update 3 minutes after their match ends. Refresh after refresh returns a spinner. Forty minutes into the tournament, the leaderboard page stops loading entirely. PostgreSQL's autovacuum kicks in and consumes the remaining I/O headroom. The primary database becomes unresponsive. The tournament is suspended.

The root cause is not a missing index or a poorly tuned query. The root cause is using a relational database for a problem it was never designed to solve: maintaining a continuously updated global ranking over 50 million entries with sub-second read and write latency.

Requirements

What We Are Building

Functional

  • Update a user's score (additive, not absolute replacement)
  • Get the rank of a specific user in real time
  • Get the top-N leaderboard with scores
  • Time-windowed leaderboards: daily, weekly, tournament-specific
  • Friend leaderboard: rank among a user's social graph only
  • Regional leaderboard: filter by country or region

Non-Functional

  • 50M registered players in the system
  • 2M concurrent users during peak tournaments
  • 100k score updates per second at peak
  • Rank reads: p99 latency under 100ms
  • Score visible in rank within 500ms of match end
  • Leaderboards are eventually consistent (~1s lag acceptable)
  • 99.9% availability (no more than ~8.7 hours downtime/year)

Interview tip: The single most important thing to establish early is the consistency model. "Eventually consistent with up to 1 second of lag" unlocks a completely different (and much more scalable) architecture than "strongly consistent ranking." In a real gaming leaderboard, players tolerate a 1-second lag; they do not tolerate a 3-minute lag.

Root Cause Analysis

Why the Naive Database Approach Fails

To understand why PostgreSQL (or MySQL, or any RDBMS) cannot serve this workload, it helps to examine each failure mode independently.

Full table sort on every read. The query ORDER BY score DESC requires the database to produce a globally sorted result set. Even with a B-tree index on score, this is not a simple key lookup — it is a range scan from the highest value downward. For 50M rows, this means traversing 50M index entries per query. With thousands of concurrent leaderboard page views, the database performs this scan thousands of times per second.

Index thrash under writes. A B-tree index is a balanced tree whose structure is determined by the values it indexes. Every time a user's score changes, the index must delete the old entry (at the old score position) and insert a new entry (at the new score position). With 100,000 updates per second, the index is subject to 100,000 deletions and 100,000 insertions per second. Index pages split continuously. The tree rebalances constantly. This is not just CPU — it generates enormous I/O and WAL write volume.

SQL window functions offer no relief. The SQL RANK() window function computes rank at query time over the result set. It does not cache anything between calls. Every invocation is an O(N) sort pass. For a single user asking "what is my rank," the database must sort all 50M rows to find the position of that one user.

Read-write lock contention. Rank reads and score writes both require access to the same index. Under the default MVCC model, writes do not block reads, but they do generate dead tuples that VACUUM must reclaim. At 100k writes/sec, the table bloats faster than VACUUM can clean it. Additionally, any query that needs a consistent snapshot of the entire sorted set while writes are in flight must use a transaction isolation level that causes lock escalation at scale.

Core insight: A leaderboard is fundamentally a sorted set problem, not a relational database problem. SQL was not designed for this access pattern. The correct tool is a data structure that was designed from the ground up for O(log N) sorted insertion and O(log N) rank queries: a skip list.

Core Data Structure

Redis Sorted Set (ZSET): The Right Tool for the Job

A Redis Sorted Set (ZSET) is a collection of unique string members, each associated with a floating-point score. Members are always stored in order of their score. Redis implements the ZSET using two internal data structures simultaneously: a skip list (for ordered operations) and a hash table (for O(1) score lookups by member). This dual representation is what gives ZSETs their uniquely strong performance profile for leaderboard workloads.

The key operations and their time complexities are:

Command Complexity Description
ZINCRBY key incr member O(log N) Atomically increment score — the correct command for additive scoring
ZADD key score member O(log N) Add or update member with absolute score
ZREVRANK key member O(log N) Return 0-indexed rank of member (highest score = rank 0)
ZREVRANGE key start stop [WITHSCORES] O(log N + M) Return top M members by descending score — the leaderboard query
ZSCORE key member O(1) Return the score of a specific member (hash table lookup)
ZCARD key O(1) Return the total number of members in the set
ZMSCORE key member [member ...] O(N) Return scores for multiple members in one round-trip (Redis 6.2+)

Memory estimate. Each ZSET entry consumes approximately 60 bytes: 8 bytes for the score (IEEE 754 double), variable bytes for the member string (a user ID like "user:42000000" is about 14 bytes), and the skip list node with forward pointers (roughly 32 bytes on average). For 50 million entries: 50,000,000 × 60 bytes = 3,000,000,000 bytes = approximately 3 GB. A single Redis instance with 8 GB of RAM can comfortably hold the entire global leaderboard with room for other keys.

Redis Commands — Core Leaderboard Operations 
# User 42 scored 150 points in a match — increment their cumulative score
ZINCRBY leaderboard:global 150 "user:42"
# Returns the new total score as a string, e.g. "3450"

# Get user 42's rank (0-indexed; rank 0 = first place)
ZREVRANK leaderboard:global "user:42"
# Returns an integer, e.g. 1847 (means user:42 is in 1848th place)

# Get user 42's exact score
ZSCORE leaderboard:global "user:42"
# Returns "3450"

# Get the top 100 players with their scores
ZREVRANGE leaderboard:global 0 99 WITHSCORES
# Returns alternating list: ["user:99", "9800", "user:7", "9750", ...]

# How many total players are on the leaderboard?
ZCARD leaderboard:global
# Returns 50000000

Why the skip list is fast: Redis's skip list implementation gives O(log N) for all rank operations. For 50 million users, log base 2 of 50,000,000 is approximately 26. That means ZINCRBY and ZREVRANK require at most 26 pointer comparisons. At modern CPU speeds operating on data in RAM, 26 comparisons takes under a microsecond. Compare that with PostgreSQL's 8-second ORDER BY on 50M rows under write contention.

Architecture

Write Path: From Game Server to Leaderboard

The write path must handle 100,000 score updates per second at peak without dropping updates or overwhelming the Redis instance. Direct writes from game servers to Redis would work at moderate scale, but introducing Kafka as a buffer between game servers and the score processing layer provides crucial benefits for burst handling and durability.

The flow is: Game Server publishes a score event to the Kafka topic score-events (partitioned by user_id to preserve per-user ordering) — the Score Processor service consumes events and issues ZINCRBY commands to Redis — asynchronously, the Score Processor also writes the final score to PostgreSQL as the durable source of truth.

Why Kafka in the middle. Kafka decouples the game servers from the score processing layer. During the tournament match-end spike at 100k updates/sec, game servers publish to Kafka without waiting for Redis to acknowledge. Kafka absorbs the burst. The Score Processor consumes at whatever rate Redis can handle, with Kafka managing the backpressure. Crucially, Kafka's log provides a durable, replayable record of every score event — if Redis data is lost (node failure, accidental key deletion), the entire leaderboard can be rebuilt by replaying Kafka from offset 0.

Redis pipeline batching. Even though ZINCRBY is O(log N), the network round-trip cost dominates at 100k commands/sec. Redis pipelining batches multiple commands into a single TCP write, eliminating per-command round-trip overhead. The Score Processor accumulates incoming score events over a 5ms window and flushes them as a pipeline: 100k ops/sec divided into 200 pipeline flushes per second, each containing ~500 ZINCRBY commands. Pipeline throughput on Redis typically runs 10-20x higher than individual command throughput because the Redis event loop processes the entire batch before returning to I/O.

PostgreSQL as source of truth. Redis holds the live, queryable ranking state. PostgreSQL holds the authoritative, durable record. The user_scores table records the latest total score per user per window. After the Score Processor writes to Redis, it asynchronously upserts to PostgreSQL. If Redis is rebuilt from scratch (disaster recovery), the Score Processor reads all rows from PostgreSQL and re-hydrates the ZSET. PostgreSQL is never queried on the rank read hot path.

Partition key matters: Partitioning the Kafka topic by user_id ensures all score events for a given user land on the same partition and are processed in order by the same Score Processor consumer. This prevents a race condition where two match results for the same user arrive out of order and result in an incorrect final score.

Architecture

Read Path: Serving Rank with Zero Database Calls

The read path serves two distinct query patterns with very different shapes. Both must complete in under 100ms at p99 and must never touch the PostgreSQL database on the hot path.

Pattern A: Top-N Leaderboard. A player opens the global leaderboard page and wants to see the current top 100. The API handler issues a single Redis command: ZREVRANGE leaderboard:global 0 99 WITHSCORES. Redis returns 100 (member, score) pairs from its skip list in O(log N + 100) time — effectively O(log 50M) + 100 pointer traversals, completing in under 1ms. The API server then enriches the response by fetching display names and avatars from a Redis Hash (pre-populated by the user profile service) using HGETALL user:profile:{id} for each of the 100 entries, or batched with a single pipeline. The final JSON is returned to the client in well under 100ms total.

For the public top-100 leaderboard (the same view that appears on the tournament homepage), the API response is cached at the CDN edge with a 5-second TTL. With 2M concurrent users potentially refreshing the leaderboard page every few seconds, CDN caching reduces the Redis request rate for this query from potentially millions per minute to approximately 12 per minute (one cache fill per 5 seconds per CDN edge node). The 5-second staleness is well within the acceptable 1-second eventual consistency window for the non-top-100 positions.

Pattern B: My Rank. A player wants to know their own current rank. The API issues two Redis commands in a pipeline: ZREVRANK leaderboard:global "user:42" and ZSCORE leaderboard:global "user:42". Both complete in O(log N) and O(1) respectively, in a single network round-trip. The response includes rank (1-indexed for display), score, and the total player count from ZCARD leaderboard:global (which is O(1)). Zero database reads. Total Redis time under 1ms.

Rate limiting on rank reads. Leaderboard data is valuable for automated scraping (competitors harvesting all 50M ranks). Apply a per-user rate limit on rank reads — for example, 60 requests per minute per authenticated user. This prevents scraping without impacting legitimate gameplay.

Edge Case

Tie-Breaking: When Two Players Have Identical Scores

In a tournament with 50 million players accumulating discrete integer scores (kills, points, objectives), large numbers of ties are mathematically guaranteed. If 100,000 players all finish a round at exactly 5,000 points, which one of them holds rank 10,001? The answer matters when prize money is on the line.

Naive approach: arbitrary ordering. Redis, by default, breaks score ties lexicographically by member string. For user IDs like "user:42" and "user:43", this produces a consistent (deterministic) but arbitrary (meaningless) ordering. This is acceptable for casual leaderboards but not for prize-bearing tournaments.

Tournament-fair approach: earlier achiever ranks higher. The player who reached a score first should hold the higher rank. To encode this in the Redis score, use fractional encoding. Redis ZSET scores are IEEE 754 double-precision floats, which provide 15-16 significant decimal digits. If scores are integers in the range 0 to 999,999, we have many spare digits for a time-based tie-breaker.

The encoding: redisScore = integerScore * 1_000_000 + (1_000_000 - timestampOffset) where timestampOffset is derived from the Unix timestamp of when the player reached that score, modulo 1,000,000. Because Redis sorts by ascending score but we want descending rank, we subtract the timestamp from a constant: an earlier timestamp produces a larger offset, which produces a larger effective score, which produces a higher rank for equal integer scores.

Using ZADD with flags to prevent score rollback. During a tournament, scores should only ever increase. If a network glitch causes a stale score event to be replayed, a naive ZINCRBY could still over-apply points. The safer pattern for absolute score updates: ZADD leaderboard:global GT encodedScore "user:42". The GT flag (Redis 6.2+) only updates the score if the new value is greater than the existing value. Combined with idempotency keys in the Kafka event (to deduplicate exact duplicate events), this makes the write path safe against replays and out-of-order delivery.

Double precision range check: IEEE 754 doubles have 53 bits of integer mantissa, representing integers exactly up to 2^53 = 9,007,199,254,740,992. A score of 999,999 multiplied by 1,000,000 equals 999,999,000,000 — well within the safe integer range for exact representation. The tie-breaking encoding is numerically safe for all realistic game scores.

Feature Design

Windowed Leaderboards: Daily, Weekly, and Tournament

Players engage more deeply with leaderboards that reset periodically. A player ranked 47,000th globally has no chance of winning the all-time leaderboard, but they might be competitive on today's daily board. Windowed leaderboards require separate ZSET keys per time window.

The key naming convention:

  • leaderboard:global — all-time cumulative scores
  • leaderboard:daily:2026-07-16 — scores earned on July 16 only
  • leaderboard:weekly:2026-W29 — scores earned in ISO week 29
  • leaderboard:tournament:finals-2026 — scores for a specific tournament
  • leaderboard:region:india — global scores filtered to India players

When the Score Processor consumes a score event, it issues ZINCRBY commands to all relevant window ZSETs simultaneously within a single Redis pipeline. A score event from a player in India playing in the July 16 daily window of the Finals tournament would update four ZSETs in one pipeline flush.

Automatic expiry. Daily leaderboard keys are set to expire at midnight using EXPIREAT leaderboard:daily:2026-07-16 <next-midnight-unix-timestamp>. Redis deletes the key automatically. Weekly keys expire at end-of-week. This requires no scheduled cleanup jobs — Redis handles garbage collection automatically.

Memory estimate for multiple windows. Four active window ZSETs (global, daily, weekly, tournament) at 50M players each: 4 × 50,000,000 × 60 bytes = 12 GB. This fits in a single Redis instance with 16 GB of RAM, or across two replicas in a Redis Cluster setup.

Tournament close-out. When a tournament window ends, the top-N results are promoted to a permanent, read-only snapshot in PostgreSQL: SELECT * FROM leaderboard_snapshots WHERE tournament_id = 'finals-2026' LIMIT 1000. The ZSET is then deleted. Future prize dispute resolution uses the PostgreSQL snapshot, not Redis. Redis is for live ranking; PostgreSQL is for historical records.

Feature Design

Friend Leaderboard: Ranking Among Your Social Graph

The friend leaderboard answers: "Among my 500 friends, where do I rank right now?" It is fundamentally a subset-ranking problem: given a global ZSET of 50M members and a set of specific member IDs, return those members sorted by score with their ranks within that subset.

The ZINTERSTORE approach (avoid for this use case). Redis provides ZINTERSTORE dest numkeys key [key ...] [WEIGHTS weight ...] [AGGREGATE SUM|MIN|MAX] to produce a new ZSET containing only members present in all input keys. Creating a temporary ZSET of friends requires first maintaining the friend list as a ZSET itself (awkward — friends have no natural score), then intersecting it with the global leaderboard. Each ZINTERSTORE writes a new key to Redis and must be explicitly deleted after use. For 2M concurrent users each with 500 friends, the volume of temporary keys becomes unmanageable.

The ZMSCORE approach (recommended). Redis 6.2 introduced ZMSCORE key member [member ...], which returns the scores of multiple members in a single O(N) command where N is the number of requested members. For user 42 with 500 friends, the API issues one command: ZMSCORE leaderboard:global friend1 friend2 ... friend500. Redis returns 500 scores (or nil for friends not yet on the board) in a single round-trip. The API layer sorts the 500-element array in memory (microseconds) and returns the friend leaderboard with computed ranks within the subset.

Social graph storage. Each user's friend list is stored in a Redis Set: SMEMBERS friends:42 returns the set of all friend user IDs. Redis Sets support O(1) member lookup and O(N) enumeration. Friend lists are small (typically under 1000 members) and change infrequently, so they can be cached aggressively.

Caching the friend leaderboard. Computing the friend leaderboard requires fetching the friend list and querying 500 scores — an inexpensive operation but one that happens millions of times per second at tournament scale. Cache the computed friend leaderboard result per user: SET leaderboard:friends:42 "[serialized JSON]" EX 30. A 30-second TTL means the friend leaderboard is at most 30 seconds stale — acceptable for social features.

Why not a per-user ZSET? Maintaining a separate ZSET per user for their friend leaderboard would require updating 500 ZSETs on every score event (once per friend of the scoring user). A player with 500 friends scoring 100k times per second would generate 50M additional ZINCRBY calls per second — a 50x write amplification. The ZMSCORE approach pushes the fan-out cost to read time, where it can be cached, rather than write time.

Scaling

Sharding for Massive Write Throughput

Redis is single-threaded for command processing. A single Redis instance can execute roughly 100,000 simple GET/SET commands per second; for ZINCRBY on a 50M-member ZSET, where the skip list traversal is heavier, practical throughput may be closer to 50,000 to 70,000 operations per second. At a sustained 100k score updates per second with a 50M-member ZSET, a single Redis instance may become the bottleneck.

Sharding Strategy A: Shard by region or game mode. Partition the global leaderboard by a natural boundary: leaderboard:global:india, leaderboard:global:asia-pacific, leaderboard:global:europe. Each shard is a separate Redis instance serving a geographically co-located set of players. Regional leaderboards are trivially available at each shard. A "true global" leaderboard requires a fan-out read across all shards (merge and sort), but this can be done at low frequency (every 30 seconds) and cached.

Sharding Strategy B: Hash sharding for write distribution. Route writes based on userId % N to N Redis instances, each holding a ZSET named leaderboard:shard:{0..N-1}. Write throughput scales linearly with the number of shards. The cost: global rank requires merging N sorted lists and computing a combined rank — a non-trivial operation that must be done offline or approximated.

Approximate ranking for hyper-scale. For players outside the top 10,000, an exact rank of 2,847,332 versus 2,847,401 carries no meaningful information. Use rank buckets: top 100 (exact), top 1,000 (exact), top 10,000 (exact), top 1% (~500,000), top 10% (~5,000,000), top 25%, top 50%, bottom 50%. These thresholds can be computed by sampling the ZSET at known percentile positions using ZREVRANGE — a lightweight operation that runs in O(log N + 1) per threshold.

HyperLogLog for unique active player counts. The tournament dashboard needs to display "X players active today" without a full ZCARD on every daily ZSET. Use Redis HyperLogLog: PFADD active_players:today user:42 on each score event. PFCOUNT active_players:today returns an approximate count with less than 1% error in O(1) time. HyperLogLog uses only 12 KB of memory regardless of cardinality, versus 3 GB for the full ZSET.

Reservoir sampling for percentile estimates. To answer "what score puts a player in the top 10%?" without scanning the entire ZSET, maintain a random sample of 10,000 scores in a separate data structure (a sorted list updated via random eviction). The sample provides an accurate estimate of any percentile boundary in O(log 10,000) = O(1) time for practical purposes.

Implementation

JavaScript: Full Leaderboard Service

The following service implements all core leaderboard operations using the ioredis client. It includes pipeline batching for write throughput, ZMSCORE-based friend leaderboards, and windowed leaderboard support.

JavaScript Example 
import Redis from 'ioredis';

const redis = new Redis({
  host: process.env.REDIS_HOST || 'localhost',
  port: 6379,
  // Enable auto-pipelining: ioredis automatically batches commands
  // that arrive within the same event loop tick into a single pipeline.
  enableAutoPipelining: true,
});

// ─── Key helpers ─────────────────────────────────────────────────────────────

function globalKey() {
  return 'leaderboard:global';
}

function windowKey(window) {
  // window: 'global' | 'daily:2026-07-16' | 'weekly:2026-W29' | 'tournament:finals-2026'
  if (window === 'global') return 'leaderboard:global';
  return `leaderboard:${window}`;
}

function friendsKey(userId) {
  return `friends:${userId}`;
}

function friendLeaderboardCacheKey(userId) {
  return `leaderboard:friends:${userId}`;
}

// ─── Write path ──────────────────────────────────────────────────────────────

/**
 * Increment a user's score on one or more leaderboard windows.
 * Called by the Score Processor after consuming a Kafka score event.
 *
 * @param {string} userId  - e.g. "user:42"
 * @param {number} points  - points to add (always positive)
 * @param {string[]} windows - leaderboard windows to update
 */
async function updateScore(userId, points, windows = ['global']) {
  // Use a manually created pipeline to batch all ZINCRBY calls for this
  // score event into a single TCP write regardless of autoPipelining.
  const pipeline = redis.pipeline();

  for (const window of windows) {
    pipeline.zincrby(windowKey(window), points, userId);
  }

  // Invalidate the cached friend leaderboard for this user's friends.
  // In production, this fan-out would be done asynchronously via a separate
  // Kafka event to avoid adding latency to the score write path.
  pipeline.del(friendLeaderboardCacheKey(userId));

  await pipeline.exec();
}

// ─── Read path: my rank ───────────────────────────────────────────────────────

/**
 * Get the rank and score of a specific user.
 * Returns { rank: number (1-indexed), score: number, totalPlayers: number }
 *
 * @param {string} userId
 * @param {string} window
 */
async function getRank(userId, window = 'global') {
  const key = windowKey(window);
  const pipeline = redis.pipeline();

  pipeline.zrevrank(key, userId);   // 0-indexed rank (null if not present)
  pipeline.zscore(key, userId);     // score as string (null if not present)
  pipeline.zcard(key);              // total members

  const [[, rankIdx], [, scoreStr], [, total]] = await pipeline.exec();

  if (rankIdx === null) {
    return { rank: null, score: 0, totalPlayers: total };
  }

  return {
    rank: rankIdx + 1,          // convert to 1-indexed for display
    score: parseFloat(scoreStr),
    totalPlayers: total,
  };
}

// ─── Read path: top-N leaderboard ─────────────────────────────────────────────

/**
 * Get the top N players with their scores.
 * Returns [{ userId, score, rank }]
 *
 * @param {number} n       - how many entries to return (e.g. 100)
 * @param {string} window  - which leaderboard window
 */
async function getTopN(n, window = 'global') {
  const key = windowKey(window);

  // ZREVRANGE returns alternating [member, score, member, score, ...]
  const raw = await redis.zrevrange(key, 0, n - 1, 'WITHSCORES');

  const results = [];
  for (let i = 0; i < raw.length; i += 2) {
    results.push({
      userId: raw[i],
      score: parseFloat(raw[i + 1]),
      rank: i / 2 + 1,  // 1-indexed
    });
  }

  return results;
}

// ─── Read path: friend leaderboard ────────────────────────────────────────────

/**
 * Get the leaderboard ranking among a user's friends.
 * Uses ZMSCORE (Redis 6.2+) to fetch all friend scores in one round-trip,
 * then sorts in the application layer.
 *
 * @param {string} userId
 * @param {string[]} friendIds  - array of friend user IDs
 * @param {string} window
 */
async function getFriendLeaderboard(userId, friendIds, window = 'global') {
  const cacheKey = friendLeaderboardCacheKey(userId);

  // Check the 30-second cache first.
  const cached = await redis.get(cacheKey);
  if (cached) return JSON.parse(cached);

  if (!friendIds || friendIds.length === 0) return [];

  const key = windowKey(window);

  // Include the requesting user themselves in the leaderboard.
  const allIds = [userId, ...friendIds];

  // ZMSCORE returns an array of scores (strings or null) in the same order
  // as the requested member list. One round-trip for up to 500 members.
  const scores = await redis.zmscore(key, ...allIds);

  const entries = allIds
    .map((id, idx) => ({
      userId: id,
      score: scores[idx] !== null ? parseFloat(scores[idx]) : 0,
      isMe: id === userId,
    }))
    .filter((e) => e.score > 0)                  // exclude players not yet on board
    .sort((a, b) => b.score - a.score)             // sort descending by score
    .map((entry, idx) => ({ ...entry, rank: idx + 1 }));

  // Cache the result for 30 seconds to reduce repeated computation.
  await redis.set(cacheKey, JSON.stringify(entries), 'EX', 30);

  return entries;
}

// ─── Windowed leaderboard convenience wrapper ─────────────────────────────────

/**
 * Get the top N entries for any named window.
 * Example: getWindowedLeaderboard('daily:2026-07-16', 50)
 *
 * @param {string} window
 * @param {number} n
 */
async function getWindowedLeaderboard(window, n = 100) {
  return getTopN(n, window);
}

export {
  updateScore,
  getRank,
  getTopN,
  getFriendLeaderboard,
  getWindowedLeaderboard,
};
Checklist

Implementation Checklist

  • Never use ORDER BY score DESC on a 50M+ row relational table for real-time ranking
  • Use ZINCRBY for atomic, additive score updates — not ZADD which overwrites the absolute score
  • Use ZADD ... GT flag when setting absolute scores to ensure scores only increase and cannot roll back
  • Create a separate ZSET key per time window; set EXPIREAT to midnight or end-of-week for automatic key cleanup
  • Batch score updates via Redis pipeline (or enable enableAutoPipelining in ioredis) to handle burst traffic efficiently
  • Cache the public top-100 leaderboard at the CDN edge with a 5-second TTL to reduce Redis read pressure at scale
  • Use ZMSCORE (Redis 6.2+) for friend leaderboard to fetch all friend scores in one round-trip
  • Back Redis with PostgreSQL as the source of truth for disaster recovery; rebuild from Kafka replay if Redis data is lost
  • Alert when ZSET memory exceeds 70% of available Redis RAM; plan for additional shards or a larger instance
  • Use ZADD NX for first-time score creation (only add if not exists), then ZINCRBY for all subsequent updates
FAQ

Frequently Asked Questions

  • What happens if Redis crashes and we lose all leaderboard data?

    Redis replication (AOF persistence) writes every write command to disk on each node. Replica promotion happens in under 30 seconds via Redis Sentinel or Redis Cluster automatic failover. In the absolute worst case — simultaneous loss of all Redis nodes before a replica can be promoted — the leaderboard can be rebuilt by replaying the score event log from Kafka. The Score Processor replays events from offset 0, issuing ZINCRBY commands as it goes. For 50M players with an average of 20 score events each, this is 1 billion Kafka events. At 100,000 events/sec processing rate, full rebuild takes roughly 3 hours. During the rebuild, serve approximate rankings from PostgreSQL's user_scores table using a pre-computed snapshot.

  • Can a Redis ZSET actually handle 50 million members in a single key?

    Yes. Redis has no practical member count limit on ZSETs. The skip list implementation scales to hundreds of millions of members. At 50M members, ZADD and ZREVRANK still run in O(log N) — approximately 26 steps. The only real constraint is memory: at roughly 60 bytes per entry, 50M members consume about 3 GB of RAM. Redis documentation explicitly supports large ZSETs; production deployments at major gaming companies use ZSETs with tens of millions of members as standard practice.

  • How do you prevent leaderboard manipulation via fake scores?

    The architecture is server-authoritative: score events originate from the game server, not the client. The game client sends match results to the game server, which validates them against the server-side game state before publishing a score event to Kafka. Score events are signed with an HMAC using a server secret and validated by the Score Processor before any Redis write. The client never calls the leaderboard write API directly. Anomaly detection runs as a Kafka Streams job alongside the Score Processor, flagging users whose score velocity exceeds a configurable statistical threshold (e.g., more than 5 standard deviations above the mean for their game mode). Flagged accounts are reviewed and potentially suspended before their scores are persisted.

  • How is rank defined when many users have the same score?

    Tie-breaking is encoded into the Redis score using fractional score encoding: the stored Redis score equals the integer game score multiplied by a large constant plus a time-based offset that makes earlier achievers rank higher. Because every effective score value is unique (the timestamp component distinguishes between any two users who reached the same integer score), ZREVRANK always returns a strict total ordering with no ties. The integer game score is recovered by dividing the Redis score by the same large constant and taking the floor.

Takeaways

Key Takeaways

A real-time leaderboard at scale is an exercise in choosing the right data structure for the access pattern. SQL was designed for flexible ad-hoc queries over relational data; it was not designed for continuously updated global rankings over 50 million rows. Attempting to force a leaderboard workload onto a relational database results in the failure described in the opening story: index thrash, read-write contention, and eventual unavailability under peak load.

Redis Sorted Set provides O(log N) rank operations for 50 million users in microseconds. The skip list implementation means that ZINCRBY, ZREVRANK, and ZREVRANGE all perform the same number of steps regardless of whether the set has 10 members or 100 million. This constant-time characteristic is what makes Redis the correct tool.

The four critical architectural decisions are: Kafka as a score event buffer to absorb the 100k/sec burst without losing events; Redis ZSET as the live ranking engine; PostgreSQL as the durable source of truth for recovery and audit; and separate ZSET keys per time window for daily, weekly, and tournament leaderboards with automatic expiry. Adding friend leaderboards via ZMSCORE pushes fan-out cost to read time where caching absorbs it.

For extreme scale beyond a single Redis instance, approximate rank via percentile buckets and HyperLogLog active player counts makes the system economical without sacrificing the user experience that matters: exact ranks at the top and competitive buckets everywhere else.
