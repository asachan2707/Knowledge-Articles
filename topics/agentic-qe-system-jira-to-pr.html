Agentic QE: From JIRA Ticket to Pull Request

A 9-agent system that takes a JIRA ticket and produces tested, CI-gated Playwright TypeScript tests committed to a feature branch — from requirement analysis through code generation, live execution, evidence reporting, and release gate enforcement. The architectural principle: AI provides intelligence, rules provide control.

The Full Pipeline

The system moves beyond simple test generation to a full pipeline with explicit human-readable artifacts at every stage and strict gate conditions that stop the workflow when quality standards are not met.

JIRA Ticket → jira_data.json → test_requirements.md → APP-5_test_cases.md → coverage_matrix.md → APP-5.spec.ts → execution_report.md → final_report.md → PR + feature branch
Why file-based artifacts? Each agent writes files to disk; the next agent reads them. This makes every decision inspectable by humans, not just trusted on faith. Debugging is O(1): open the artifact, read what the agent decided.

9 Specialized Agents

Each agent has a narrow, well-defined responsibility and reads from / writes to a specific artifact.

Agent 1

jira_extractor

Parse and understand JIRA ticket requirements, extract acceptance criteria, write jira_data.json.

Agent 2

test_case_generation

Design test scenarios using 4 lenses: ecosystem context, user reality, system integration, value delivery.

Agent 3

e2e_validation_agent

Check existing framework coverage. Search Page Objects and fixtures. Stop if required capability is absent.

Agent 4

e2e_code_generation_agent

Write Playwright TypeScript tests matching framework conventions (fixtures, page objects, tagging).

Agent 5

e2e_quality_check_agent

Run TSC + ESLint. Zero errors required. Attempt auto-repair on failure. Stop if repair fails.

Agent 6

e2e_test_executor_agent

Execute tests against live application. Sanity-check beyond exit code: assertion coverage, timing plausibility.

Agent 7

report_generation_agent

Synthesize all artifacts into final_test_generation_report.md — full evidence trail.

Agent 8

pr_submitter_agent

Enforce release gate. Strict policy: anything less than clean PASSED blocks the PR.

Agent 9

workflow_orchestrator

Coordinate the full sequence. Manage inter-agent state. Surface ambiguities as warnings, never hide them.

Framework-Aware Test Generation

Before generating code, the validation agent searches existing Page Objects and fixtures. Tests that reference non-existent framework methods are blocked — AI respects boundaries of the real engineering system.

// Quality check agent — runs TypeScript compiler + ESLint before execution
const { execSync } = require("child_process");
const path = require("path");

class QualityCheckAgent {
  constructor(projectRoot) {
    this.projectRoot = projectRoot;
  }

  async check(specFile) {
    const issues = [];

    // Step 1: TypeScript compilation check
    try {
      execSync(`npx tsc --noEmit --strict`, { cwd: this.projectRoot, stdio: "pipe" });
    } catch (err) {
      const tsErrors = err.stdout.toString().split("\n").filter(Boolean);
      issues.push(...tsErrors.map(e => ({ type: "typescript", message: e })));
    }

    // Step 2: ESLint check
    try {
      execSync(`npx eslint ${specFile} --format json`, { cwd: this.projectRoot, stdio: "pipe" });
    } catch (err) {
      const lintResults = JSON.parse(err.stdout.toString() || "[]");
      lintResults.forEach(file =>
        file.messages.forEach(m =>
          issues.push({ type: "eslint", rule: m.ruleId, message: m.message, line: m.line })
        )
      );
    }

    if (issues.length > 0) {
      return { status: "FAILED", issues, gate: "STOP" };
    }
    return { status: "PASSED", issues: [], gate: "PROCEED" };
  }
}

// Gate policy: zero tolerance on quality check failures
const checker = new QualityCheckAgent("/path/to/project");
checker.check("tests/APP-5.spec.ts").then(result => {
  if (result.gate === "STOP") {
    console.error("Quality gate FAILED — workflow stopped");
    console.error(result.issues);
    process.exit(1);
  }
  console.log("Quality gate PASSED — proceeding to execution");
});

Release Gate Policy

The PR submitter agent enforces a strict binary gate. Ambiguity surfaces as STOPPED, never hidden.

Test Execution StatusGate Decision
PASSEDProceed to PR
PASSED WITH WARNINGSSTOP — do not submit
FAILEDSTOP — do not submit
BLOCKEDSTOP — do not submit
 
// PR Submitter Agent — strict gate enforcement
class PRSubmitterAgent {
  constructor(gitClient) {
    this.git = gitClient;
  }

  async submit(finalReport, branchName) {
    const { testStatus, warnings, failures } = finalReport;

    // Strict gate: only clean PASSED proceeds
    if (testStatus !== "PASSED" || warnings.length > 0) {
      return {
        action: "BLOCKED",
        reason: this._buildBlockReason(testStatus, warnings, failures),
        prCreated: false
      };
    }

    // All gates passed — create feature branch and PR
    await this.git.createBranch(branchName);
    await this.git.commitAll(`feat(test): add E2E tests for ${finalReport.ticketId}`);
    const pr = await this.git.createPR({
      title: `[${finalReport.ticketId}] Automated E2E tests`,
      body:  this._buildPRBody(finalReport),
      branch: branchName
    });

    return { action: "PR_CREATED", prUrl: pr.url, prCreated: true };
  }

  _buildBlockReason(status, warnings, failures) {
    if (status === "PASSED WITH WARNINGS") return `Warnings detected: ${warnings.join(", ")} — manual review required`;
    if (status === "FAILED")               return `Test failures: ${failures.length} test(s) failed`;
    return `Execution blocked: ${status}`;
  }

  _buildPRBody(report) {
    return [
      `## Automated E2E Tests — ${report.ticketId}`,
      `\n### Test Results`,
      `- Status: **${report.testStatus}**`,
      `- Tests: ${report.testCount} (${report.passCount} passed, ${report.failCount} failed)`,
      `- Coverage: ${report.coverageAreas.join(", ")}`,
      `\n### Evidence`,
      `- JIRA requirements: ✅ extracted`,
      `- Framework coverage: ✅ validated`,
      `- TypeScript: ✅ 0 errors`,
      `- ESLint: ✅ 0 violations`,
      `- Live execution: ✅ all tests passed`
    ].join("\n");
  }
}
Key lesson from testing APP-2 (warning path): PASSED WITH WARNINGS blocks the PR — always. The warning path scenario was more instructive than the clean path. Ambiguity must never be hidden; it surfaces immediately as a blocked workflow.

Agent Instructions in Plain Markdown

Each agent is defined in config/agents/*.md — readable English descriptions of role, inputs, steps, rules, and outputs. This is the cleanest form of "rules as code": auditable, version-controlled, and modifiable without touching runtime code. 

# Agent: e2e_validation_agent

## Role
Validate whether the existing Playwright test framework contains the Page Objects,
fixtures, and utilities required to implement the test cases specified in
`APP-5_test_cases.md`.

## Inputs
- `APP-5_test_cases.md` — test cases to validate
- `src/pages/` — existing Page Object files
- `src/fixtures/` — existing fixture files

## Steps
1. Parse each test case and extract required capabilities
2. Search `src/pages/` for matching Page Objects by method name
3. Search `src/fixtures/` for required fixture types
4. For each capability, record: file path, line number, confidence

## Rules
- NEVER invent or assume a framework capability exists without finding it in the codebase
- If a required capability is absent, set status = BLOCKED and record what is missing
- Evidence must be explicit: file path + line number, not "I believe it exists"
- A partial match (similar method name) is a WARNING, not a CONFIRMED capability

## Output
Write `test_coverage_matrix.md` with:
- status: COVERED | PARTIAL | MISSING | BLOCKED
- For each capability: evidence (file:line) or missing reason

Five Design Principles

  • AI provides intelligence, rules provide control. AI understands requirements and generates code; rules define what agents can do, when to stop, when humans intervene.
  • File-based artifact persistence. Every agent decision is written to disk — inspectable, auditable, debuggable without replay.
  • Framework-first generation. Search before generating. Non-existent framework methods stop the workflow — AI never invents plausible-looking but broken code.
  • Small specialized agents over large general ones. A narrow agent with explicit inputs/outputs is far more trustworthy than one agent "do everything" prompt.
  • Warnings block; they never hide. PASSED WITH WARNINGS is a stop condition, not a "close enough." Semantic correctness matters beyond compilation and execution.

Key Takeaway

A stable existing framework is a prerequisite — AI exposes weaknesses, it doesn't fix them. The architecture that makes this system trustworthy is not the AI capability; it's the separation of intelligence (AI understands requirements, writes tests) from control (rules define when to stop, what counts as passing). Artifact-based state makes every decision inspectable. The warning-path scenario — where the workflow correctly blocks a PR despite technically passing tests — is the hardest case to implement correctly and the most important one to test. "A passing test isn't automatically a good test" is the system's guiding invariant.
