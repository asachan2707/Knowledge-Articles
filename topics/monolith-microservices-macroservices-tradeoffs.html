Monolith vs Microservices vs Macroservices: Choosing the Right Architecture

A clear decision framework for choosing between monolithic, microservices, and macroservices architectures — including what macroservices are, when to choose each, what "start with a monolith" actually means in 2026, and how Amazon, Netflix, and Shopify each chose differently for good reasons.

The question "should we use microservices?" is asked at the wrong stage in most organisations. The right question is: "what problems are we solving, what team structure do we have, and what operational maturity do we have to support distributed systems?" The answer determines the architecture; the architecture doesn't determine the answer.

Core idea: Macroservices are the underappreciated middle ground. They give you module-level boundary enforcement without the distributed systems complexity of microservices. Many large-scale applications that describe themselves as "microservices" are actually macroservices.

The three architectures compared

Monolith

All code in one codebase, one deployment unit

  • Simple to develop, test, debug
  • Low operational overhead
  • Easy refactoring (compile-time boundaries)
  • Transactions are local — no distributed coordination
  • Scales as a unit — can't scale hot paths independently
  • One component's bug can crash everything
  • Deployment risk grows with codebase size

Macroservices

Modular monolith: strict module boundaries, single deploy or limited services

  • Module isolation without network overhead
  • Enforced boundaries — no accidental coupling
  • Can split into true microservices later along existing seams
  • Lower operational complexity than microservices
  • Still a single deployment unit per macroservice
  • Requires module discipline to maintain boundaries

Microservices

Small independent services, each with own process and database

  • Independent deployment per service
  • Independent scaling per service
  • Fault isolation — one service crash doesn't cascade
  • Technology freedom per service
  • Distributed systems complexity (latency, partitions, eventual consistency)
  • High operational overhead (observability, service discovery, CI/CD per service)
  • Distributed transactions require Saga or CQRS
Decision framework

Which architecture to choose, and when

Q1
Team size < 10 engineers and domain is not fully understood? → Monolith. You don't have the domain knowledge yet to draw correct service boundaries. Wrong microservice splits are expensive to fix.
Q2
Growing team (10–50 engineers), domain is well-understood, but you lack a platform team for observability/CI? → Macroservices (Modular Monolith). Enforce module boundaries in code; split into microservices when you've proven each boundary is correct and have the ops maturity.
Q3
50+ engineers, distinct domains with independent scaling requirements, platform team exists, teams already structured around domains? → Microservices. You have the team structure and operational maturity to make the complexity pay off.
Q4
Existing monolith that's painful but you can't rewrite from scratch? → Strangler Fig: extract individual services from the edges of the monolith using a façade, while the core remains until the last module migrates.
Real-world choices

How large companies chose

  • Shopify (2022) — explicitly moved from microservices back toward a "modular monolith" (macroservices). The distributed overhead was slowing feature delivery for their team size and problem domain. Rails modules with enforced boundaries delivered the isolation benefit at lower cost.
  • Amazon (2002) — Bezos mandate forced microservices; their team structure (two-pizza teams) was already aligned. The architecture matched the org.
  • Netflix — started with a DVD-shipping monolith, migrated to AWS microservices over 7 years. The migration was the right call — their scale and team size demanded independent deployment and fault isolation.
  • Stack Overflow — runs on a monolith serving millions of requests per day. Proved that a well-optimised monolith with vertical scaling can outperform poorly-implemented microservices at most scales.
JavaScript Example

Macroservice: enforcing module boundaries in Node.js

JavaScript Example 
// Macroservice pattern: modules communicate ONLY through explicit public APIs
// No direct imports across module boundaries — enforced via eslint-plugin-boundaries or similar

// ── modules/orders/index.js (public API of the orders module) ──
export class OrderModule {
  constructor(db, paymentModule) {
    this._db = db;
    this._payment = paymentModule; // declared dependency — not an import
  }

  async createOrder(data) {
    const order = await this._db.orders.insert(data);
    // Call the payment module only through its public API
    const payment = await this._payment.charge({
      orderId: order.id,
      amount: data.amount,
    });
    return { order, payment };
  }

  // Only these methods are exposed to other modules
  async getOrder(id) { return this._db.orders.findById(id); }
  async listOrdersByUser(userId) { return this._db.orders.findAll({ userId }); }
}

// ── modules/payments/index.js (public API) ──
export class PaymentModule {
  constructor(db) { this._db = db; }

  async charge({ orderId, amount }) {
    const payment = await this._db.payments.insert({ orderId, amount, status: 'charged' });
    return payment;
  }

  async refund(paymentId) {
    return this._db.payments.update(paymentId, { status: 'refunded' });
  }
}

// ── app.js (composition root — wires modules together) ──
import { OrderModule } from './modules/orders/index.js';
import { PaymentModule } from './modules/payments/index.js';

const payment = new PaymentModule(db);
const orders = new OrderModule(db, payment);

// ── ESLint rule to enforce no cross-module internal imports ──
// "boundaries/no-private": ["error", { allow: [] }]
// Prevents: import { insertOrder } from '../orders/repository.js'
// Forces: import { OrderModule } from '../orders/index.js'

// When to split to microservices: when orders or payments teams need
// independent deployment cycles, not before.
The "start with a monolith" advice explained: This doesn't mean "never use microservices." It means: build the system until you understand its domain boundaries with confidence, enforce those boundaries as module interfaces, and then — and only then — extract them to independent services. Modules that have been stable and independently evolving for 6+ months are good microservice candidates. Modules that keep changing together are not.

Key Takeaway

Monolith, macroservices, and microservices are not a spectrum from "bad" to "good" — they are different tools for different contexts. The key driver is not technical sophistication but team size, domain clarity, and operational maturity. Macroservices (modular monoliths) are the most under-used option: they provide module isolation without distributed systems overhead, they're easy to evolve from a monolith, and their seams become the natural split points if microservices are eventually needed.
