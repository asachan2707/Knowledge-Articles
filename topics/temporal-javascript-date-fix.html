Temporal: The JavaScript Date Problem Is Finally Being Fixed

JavaScript's Date object has been broken since 1995 — mutable, timezone-unaware, zero-indexed months, locale-dependent parsing, and silent DST bugs that only surface in production. Temporal, now at TC39 Stage 4 and shipping in Chrome 144, replaces it entirely with nine immutable types that force explicit timezone handling and provide nanosecond precision.

Source: lets-code-future · Medium Domain: JavaScript / Web Standards Published: 2026-09-03

Every senior JavaScript engineer has a war story involving Date. A billing system that charged wrong amounts across daylight saving transitions. A scheduler that skipped tasks because new Date("2024-03-10") resolved to a different day depending on the server's local timezone. A data pipeline where date.getMonth() === 0 meant January and nobody remembered. These are not edge cases — they are the predictable consequences of a 29-year-old API copied from Java 1.0 before the web knew what timezones were.

Core idea: Date is a single mutable type that conflates exact time, local wall-clock time, and calendar date into one ambiguous object. Temporal separates those concerns into nine distinct immutable types, making the wrong thing impossible to express accidentally.

Story · The DST billing outage

In March 2019, a European e-commerce platform processed recurring subscriptions using Date. The renewal logic calculated the next billing date by adding 30 days to new Date(). On the night clocks moved forward, two time zones in the customer database interpreted the epoch millisecond threshold differently — the server ran UTC, customer records stored local dates as strings, and new Date("2019-03-31") silently shifted by one hour when parsed on the server. Roughly 4 000 subscriptions renewed a day early or were skipped entirely. Finance noticed the revenue gap 48 hours later. The root cause: Date.parse() treats bare date strings as UTC in modern engines but as local time in older ones — and the production fleet had mixed Node versions.

A rewrite using Temporal.PlainDate three months later eliminated the class entirely. PlainDate carries no timezone at all — it is just a calendar date. The conversion to an exact moment happens at a clearly marked boundary, with an explicit timezone argument the compiler will not let you omit.

The Seven Deadly Sins of JavaScript Date

Root cause analysis

1. Months are zero-indexed, days are not

new Date(2024, 0, 1) is January 1st. new Date(2024, 1, 1) is February 1st. But date.getDate() returns 1 for the first day. There is no justification — it was copied from the Java 1.0 java.util.Date API which itself had this bug. ESLint rules like no-restricted-syntax can catch it, but thousands of codebases have latent off-by-one errors in their month arithmetic.

2. Mutable by default

Every set* method mutates the original object. Passing a Date to a function and calling date.setHours(0) inside it changes the caller's value. Libraries like Moment.js inherited this design and spent years adding .clone() calls everywhere. Temporal objects have no setters — with(), add(), and subtract() always return new instances.

3. No "date without time" concept

When you need to represent "the user's birthday" or "the invoice date", you want a pure calendar date with no time component. Date cannot express this — you get 2024-01-15T00:00:00.000Z at best, which carries an implicit UTC midnight that shifts the displayed date across timezones.

4. toString() output is implementation-defined

new Date().toString() produces different strings across browsers, Node versions, and operating system locales. V8 on macOS, Spidermonkey on Linux, and Hermes on React Native each produce subtly different formats. Code that splits on this string is silently locale-fragile.

5. Date.parse() is unreliable for non-ISO strings

The spec only requires Date.parse() to handle ISO 8601. Everything else — "March 15, 2024", "15/03/2024" — is implementation-dependent. MDN recommends never using Date.parse() outside ISO strings. In practice, production code is full of it.

6. DST arithmetic is silently wrong

Adding 24 hours to a Date near a daylight saving boundary does not always produce "tomorrow". If the clocks skip forward at 2 AM, that day has only 23 hours. date.setDate(date.getDate() + 1) is the correct approach — but the difference between "add 1 day" and "add 24 hours" is not obvious and Date provides no type-level distinction.

7. Millisecond precision only

High-frequency trading systems, distributed tracing, and database timestamps routinely need microsecond or nanosecond precision. Date stores only milliseconds. Temporal.Instant stores nanoseconds as a BigInt (epochNanoseconds), making it suitable for any precision requirement.

// Sorted by exact moment, not string, not locale, not coercion

The Temporal API: Nine Types, One Right Tool Each Time

Type system design

Temporal's design principle: each type represents exactly one concept, and conversion between types is explicit. You cannot accidentally treat an exact moment as a wall-clock time. The type lattice enforces this at the API level — calling .year on a Temporal.Instant throws a TypeError, forcing you to first convert it to a timezone-aware type.

Type What it represents Has timezone? Has time?
Temporal.Instant A unique point in time (nanoseconds from epoch) No Implicit (UTC)
Temporal.ZonedDateTime Date + time + timezone + calendar Yes (IANA) Yes
Temporal.PlainDateTime Date + wall-clock time, no timezone No Yes
Temporal.PlainDate Calendar date only (year/month/day) No No
Temporal.PlainTime Wall-clock time only No Yes
Temporal.PlainYearMonth Year + month (e.g., "October 2024") No No
Temporal.PlainMonthDay Month + day (e.g., recurring birthday) No No
Temporal.Duration A length of time for arithmetic N/A N/A
Temporal.Now Utility namespace for current time — —

Which Type Do You Actually Need?

Decision guide

Use Temporal.Instant when:

You need an exact point in time that is unambiguous regardless of timezone — log timestamps, event sourcing records, created_at database fields, payment timestamps. Store as epochNanoseconds (BigInt) or ISO string with UTC offset. Never display to users without first converting to their timezone.

Use Temporal.ZonedDateTime when:

You need to do arithmetic that must respect DST rules — scheduling recurring events, calculating "the next Sunday at 9 AM in Tokyo", showing a user-facing datetime for a calendar event. This is the type to use when both "what exact moment" and "what wall-clock time in what place" both matter.

Use Temporal.PlainDate when:

The timezone is irrelevant — invoice dates, birthdays, business logic that operates purely on calendar days ("expire in 30 days", "bill on the 15th of each month"). Converting to a timezone-aware instant happens at the boundary (e.g., "expire at midnight in the customer's timezone") and should be an explicit step.

Use Temporal.PlainDateTime when:

You have date and time but the timezone is unknown or not yet decided — user input forms before the user has confirmed their timezone, database rows that store local time without offset. Be careful: PlainDateTime arithmetic does not account for DST; use ZonedDateTime if DST matters.

Use Temporal.Duration when:

You need to represent a span of time: "2 hours 30 minutes", "3 months", "P1Y2M3DT4H". Durations are not normalized automatically — { hours: 90 } stays as 90 hours unless you call .round(). This is intentional; "3 months" and "90 days" are semantically different near month boundaries.

Migrating from Date to Temporal

Before / after patterns JavaScript Example — Migration: common Date patterns 
import { Temporal } from "@js-temporal/polyfill";

// ─── Current time ─────────────────────────────────────────────────────────────
// BEFORE
const nowDate = new Date();
const epochMs = nowDate.getTime();
const isoString = nowDate.toISOString();

// AFTER
const nowInstant   = Temporal.Now.instant();           // exact time, no TZ
const nowZdt       = Temporal.Now.zonedDateTimeISO();  // current TZ from system
const nowPlainDate = Temporal.Now.plainDateISO();      // today as PlainDate
const nowEpochMs   = nowInstant.epochMilliseconds;     // same as Date.now()

// ─── Parse a date-only string ──────────────────────────────────────────────────
// BEFORE: BUG — "2024-01-15" is parsed as UTC midnight, so in UTC-5 it becomes Jan 14
const wrong = new Date("2024-01-15").toLocaleDateString(); // May show "1/14/2024"!

// AFTER: PlainDate has no timezone, so "2024-01-15" is always January 15
const correct = Temporal.PlainDate.from("2024-01-15");
console.log(correct.toString()); // "2024-01-15" — always

// ─── Interop: Date ↔ Temporal ──────────────────────────────────────────────────
// From legacy Date to Temporal
const legacyDate = new Date("2024-06-15T10:30:00Z");
const asInstant = legacyDate.toTemporalInstant();               // built-in bridge
const asZdt     = asInstant.toZonedDateTimeISO("America/New_York");
const asPlain   = asZdt.toPlainDate(); // "2024-06-15"

// From Temporal back to Date (when you need legacy compatibility)
const backToDate = new Date(asInstant.epochMilliseconds);

// ─── Format for display ────────────────────────────────────────────────────────
// BEFORE: locale-dependent
new Date().toLocaleDateString("en-US", { year: "numeric", month: "long", day: "numeric" });

// AFTER: same Intl integration, but source is unambiguous
Temporal.Now.plainDateISO().toLocaleString("en-US", { dateStyle: "long" });
// "September 3, 2026"
JavaScript Example — Duration arithmetic 
import { Temporal } from "@js-temporal/polyfill";

// ─── Adding months (respects month-end overflow) ──────────────────────────────
const jan31 = Temporal.PlainDate.from("2024-01-31");
const oneMonthLater = jan31.add({ months: 1 });
console.log(oneMonthLater.toString()); // "2024-02-29" (2024 is leap year)

const jan31NonLeap = Temporal.PlainDate.from("2023-01-31");
console.log(jan31NonLeap.add({ months: 1 }).toString()); // "2023-02-28" — clamped!

// BEFORE with Date: you had to handle this manually
const wrongFeb = new Date(2023, 0, 31);
wrongFeb.setMonth(wrongFeb.getMonth() + 1);
console.log(wrongFeb.toISOString()); // "2023-03-03T..." — WRONG! overflowed into March

// ─── Difference between two dates ─────────────────────────────────────────────
const start = Temporal.PlainDate.from("2024-01-15");
const end   = Temporal.PlainDate.from("2024-09-03");
const diff  = start.until(end, { largestUnit: "month" });
console.log(diff.toLocaleString()); // "P7M19D" — 7 months and 19 days

// In specific units
const inDays  = start.until(end).days; // just days component
const inTotal = start.until(end, { largestUnit: "day" }).days; // total days: 232

// ─── Flight duration across timezones ─────────────────────────────────────────
const departure = Temporal.ZonedDateTime.from("2024-06-15T09:30:00+08:00[Asia/Hong_Kong]");
const arrival   = Temporal.ZonedDateTime.from("2024-06-15T08:20:00-07:00[America/Los_Angeles]");
const flightDuration = departure.until(arrival, { largestUnit: "hour" });
console.log(`Flight: ${flightDuration.hours}h ${flightDuration.minutes}m`);
// "Flight: 14h 50m" — correct regardless of timezone difference

// ─── Countdown timer (human-readable) ─────────────────────────────────────────
function countdown(targetISO) {
  const target = Temporal.Instant.from(targetISO);
  const now    = Temporal.Now.instant();
  const diff   = now.until(target, { largestUnit: "hour" });
  return `${diff.hours}h ${diff.minutes}m ${diff.seconds}s`;
}
console.log(countdown("2026-12-31T23:59:59Z"));

Timezone-Aware Scheduling: The Real-World Use Case

ZonedDateTime in production

Building a calendar scheduler (think Google Calendar, Calendly, or a cron-based task runner) is where Temporal.ZonedDateTime earns its complexity. The key insight: store future events as wall-clock time + IANA timezone identifier, not as an epoch millisecond. DST rules can and do change — countries periodically abolish or modify their clocks — and storing an epoch locks in the old rule.

JavaScript Example — Timezone-aware recurring events 
import { Temporal } from "@js-temporal/polyfill";

// Daily standup at 9 AM in user's timezone, DST-safe
// Store this as a PlainTime + IANA timezone string, not an epoch offset
function* dailyStandupInstants(startDate, localHour, timeZone, count) {
  let date = Temporal.PlainDate.from(startDate);
  const time = new Temporal.PlainTime(localHour, 0, 0);

  for (let i = 0; i < count; i++) {
    // toZonedDateTime converts local time to exact moment accounting for DST
    const zdt = date.toZonedDateTime({ plainTime: time, timeZone });
    yield zdt.toInstant().epochMilliseconds; // store in DB as epoch ms
    date = date.add({ days: 1 });
  }
}

// Generate next 5 standup times for a NY team
const standups = [...dailyStandupInstants("2024-03-09", 9, "America/New_York", 5)];
// March 10 is DST spring forward — the 9 AM on that day maps to a different offset
// Temporal handles this automatically

// ─── Convert event time across timezones for participants ─────────────────────
function convertMeetingTime(zdtString, participantTimezone) {
  const original = Temporal.ZonedDateTime.from(zdtString);
  const converted = original.withTimeZone(participantTimezone);
  return {
    original: original.toLocaleString("en-US", {
      dateStyle: "short",
      timeStyle: "short",
      timeZone: original.timeZoneId,
    }),
    converted: converted.toLocaleString("en-US", {
      dateStyle: "short",
      timeStyle: "short",
      timeZone: participantTimezone,
    }),
    sameInstant: Temporal.Instant.compare(original.toInstant(), converted.toInstant()) === 0,
  };
}

const result = convertMeetingTime(
  "2024-06-20T14:00:00-04:00[America/New_York]",
  "Asia/Kolkata"
);
console.log(result);
// { original: "6/20/24, 2:00 PM", converted: "6/20/24, 11:30 PM", sameInstant: true }

// ─── Check if business is currently open (overnight hours handled) ─────────────
function isOpen(openTime, closeTime, timeZone) {
  const now       = Temporal.Now.zonedDateTimeISO(timeZone).toPlainTime();
  const open      = Temporal.PlainTime.from(openTime);
  const close     = Temporal.PlainTime.from(closeTime);
  const overnight = Temporal.PlainTime.compare(close, open) < 0;

  if (overnight) {
    // e.g., 22:00 to 06:00 — wraps midnight
    return Temporal.PlainTime.compare(now, open) >= 0 ||
           Temporal.PlainTime.compare(now, close) < 0;
  }
  return Temporal.PlainTime.compare(now, open) >= 0 &&
         Temporal.PlainTime.compare(now, close) < 0;
}

console.log(isOpen("09:00", "17:00", "America/Chicago")); // regular hours
console.log(isOpen("22:00", "06:00", "Asia/Tokyo"));       // overnight restaurant

Current Status and Polyfill Setup

TC39 Stage 4 · Chrome 144 · polyfill available

Temporal reached TC39 Stage 4 and shipped natively in Chrome 144 (released 2025). Firefox and Safari implementations are underway. For production use today, there are two mature polyfills:

  • @js-temporal/polyfill — maintained by the TC39 Temporal champions. Full spec compliance. Use for greenfield projects.
  • temporal-polyfill — by the FullCalendar team. Optimized for bundle size. Good for frontend apps where every KB matters. 
// Install
// npm install @js-temporal/polyfill
// or
// npm install temporal-polyfill

// Usage (polyfill does not auto-install on globalThis in all environments)
import { Temporal, Intl, toTemporalInstant } from "@js-temporal/polyfill";

// In environments where Temporal is native (Chrome 144+), skip the import:
// const now = Temporal.Now.instant(); // works natively

// Feature detection
const hasNativeTemporal = typeof globalThis.Temporal !== "undefined";
if (!hasNativeTemporal) {
  // load polyfill dynamically
  const { Temporal: TPolyfill } = await import("@js-temporal/polyfill");
  globalThis.Temporal = TPolyfill;
}

Performance note: The @js-temporal/polyfill is ~50 KB minified+gzipped. For a frontend app serving 10 M users, you will want to tree-shake it or use temporal-polyfill (roughly 15 KB). On Node.js 22+, run with the native V8 Temporal when available to eliminate the polyfill cost entirely.

Migrating from date-fns, Moment.js, Luxon, and Day.js

Library migration path

Temporal does not immediately make these libraries obsolete — they will remain valuable for utilities (formatting, locale-aware display) that Temporal intentionally delegates to Intl. The migration strategy is incremental:

  1. Stop adding new Date objects; use Temporal for all new date logic.
  2. Replace arithmetic and comparison calls (the most bug-prone category).
  3. Keep library formatting calls short-term, replace with .toLocaleString().
  4. Remove the library when no more calls remain.
Library pattern Temporal equivalent
moment().add(1, 'month') Temporal.Now.plainDateISO().add({ months: 1 })
moment(a).diff(b, 'days') a.until(b, { largestUnit: 'day' }).days
moment.tz(str, tz) Temporal.ZonedDateTime.from({ ...fields, timeZone: tz })
dayjs().isBefore(other) Temporal.Instant.compare(a, b) < 0
dateFns.addMonths(date, 2) date.add({ months: 2 })
dateFns.startOfDay(date) zdt.startOfDay()
luxon.DateTime.local() Temporal.Now.zonedDateTimeISO()
luxon.Duration.fromObject() Temporal.Duration.from()

Moment.js is in maintenance mode — the team officially recommends migrating to alternatives. Temporal is the long-term answer for pure date logic; date-fns remains useful for its extensive locale-aware formatting helpers while Intl.DateTimeFormat continues to mature.

Temporal Failure Modes and Gotchas

What can still go wrong

Disambiguation ambiguity during DST

When clocks fall back, wall-clock times in the skipped hour are ambiguous — 1:30 AM exists twice. ZonedDateTime.from() defaults to disambiguation: 'compatible' which picks the earlier offset. For scheduling code, use 'reject' to throw on ambiguous times and force explicit resolution.

Duration month arithmetic is relative, not absolute

Temporal.Duration.from({ months: 1 }) is not "30 days". It means "one calendar month". jan31.add({ months: 1 }) gives Feb 28/29, not Mar 2. This is usually the right behavior, but duration total calculations require a reference date: duration.total({ unit: 'day', relativeTo: someDate }).

PlainDateTime arithmetic ignores DST

Adding { days: 1 } to a PlainDateTime always adds exactly 24 hours. If you then convert to a ZonedDateTime near a DST boundary, you may end up at the wrong local hour. Use ZonedDateTime from the start for any arithmetic that must produce correct wall-clock results.

valueOf() throws intentionally

Temporal objects throw TypeError when coerced to a primitive. This means date > otherDate will throw — you must use Temporal.PlainDate.compare(a, b) or a.until(b). This is by design to prevent the silent type coercion bugs that plague Date, but it will break naive code that uses comparison operators.

Polyfill bundle size

The reference polyfill includes timezone data. If you use IANA timezones and are bundling for the browser, ensure you are not double-including timezone data from both the polyfill and another library like Luxon or date-fns-tz.

Production Checklist: Adopting Temporal

  • Install @js-temporal/polyfill or temporal-polyfill and add feature detection for native support in Chrome 144+.
  • Replace all new Date("YYYY-MM-DD") with Temporal.PlainDate.from("YYYY-MM-DD") to eliminate the UTC midnight bug.
  • Replace month arithmetic (setMonth(getMonth() + 1)) with date.add({ months: 1 }) to get correct end-of-month behavior.
  • Store database timestamps as epoch milliseconds or ISO 8601 with UTC offset; use Temporal.Instant as the canonical in-memory type.
  • Store future scheduled events as PlainDateTime + IANA timezone string, not as epoch milliseconds, to survive government DST rule changes.
  • Use disambiguation: 'reject' in scheduling code to detect ambiguous DST times at insertion rather than silently picking one.
  • Replace all .sort((a,b) => a - b) on dates with the static Temporal.*.compare method.
  • Add ESLint rule to ban new Date(string) in the codebase (except for Temporal interop bridge calls).
  • For duration display, use Intl.DurationFormat (Stage 4) rather than manual string concatenation.
  • Test DST transitions explicitly: US spring-forward (March), US fall-back (November), and any timezone your users are in.

Frequently Asked Questions

Is Temporal safe to use in production today?

Yes, with a polyfill. @js-temporal/polyfill is production-ready and used by large applications. Natively it ships in Chrome 144. For Node.js, use the polyfill on any version; native support will arrive with V8 updates. The polyfill is spec-compliant and regularly fuzz-tested against the spec test suite.

Does Temporal replace Intl.DateTimeFormat?

No. Temporal handles the logic side (arithmetic, storage, comparison). Display (localized formatting, relative time) is still delegated to Intl. Temporal objects implement .toLocaleString() which uses Intl.DateTimeFormat internally. Think of them as complementary.

Should I migrate an existing codebase all at once?

No. The incremental strategy works well: start with new features using Temporal, migrate arithmetic code first (the highest-risk category), and leave display code for last. The interop bridge date.toTemporalInstant() and new Date(instant.epochMilliseconds) makes mixing old and new code straightforward.

What happened to Moment.js and Luxon?

Moment.js is in long-term maintenance mode — no new features, security fixes only. Luxon (by a Moment.js author) is well-maintained and a good bridge today. Both will remain useful for formatting, but Temporal handles the core date logic more correctly. The Luxon author has stated Temporal is the right long-term answer.

Does Temporal support non-Gregorian calendars?

Yes. All Temporal date types accept an optional calendar parameter supporting ISO 8601, Hebrew, Islamic, Persian, Chinese, Buddhist, and others via the Intl.Calendar identifiers. Date arithmetic respects the calendar's rules for month lengths and year boundaries.

What is the RFC 9557 string format?

It extends ISO 8601 with a bracket notation for IANA timezone identifiers and calendar annotations: 2024-01-15T10:30:00+05:30[Asia/Kolkata][u-ca=hebrew]. This ensures the string carries both the exact offset (for the stored moment) and the IANA identifier (for future DST calculations), preventing the class of bugs where a stored UTC offset becomes wrong after a government DST rule change.

Key Takeaway

The fundamental mistake in Date is conflating three separate concepts — an exact moment in time, a wall-clock reading, and a calendar date — into one mutable object with no type-level distinction. Every DST bug, every off-by-one-day error in UTC parsing, every "works in staging, breaks in production" date issue traces back to this conflation. Temporal enforces the distinction at the type level: you cannot accidentally read .year off an Instant; you cannot skip specifying a timezone when you need DST-correct arithmetic. The API is larger, but each additional type is a bug class made unrepresentable. Adopt Temporal incrementally, starting with the highest-risk arithmetic: month addition, DST-spanning date ranges, and any code where a Date string parse result gets stored in a database. Those three patterns account for the vast majority of production date bugs in JavaScript applications.
