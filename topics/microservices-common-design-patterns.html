Exploring Common Design Patterns in Microservice Architecture

Nine essential microservices patterns explored in depth: Decomposition (by Domain, Subdomain), Database Per Service, API Composition, CQRS, API Gateway, Event-Driven, Saga, Service Registry, and Bulkhead — with the specific problem each one solves and where it fits in a real system.

Microservice design patterns aren't a checklist to apply wholesale — they're a vocabulary of solutions to specific recurring problems. The trap is adopting a pattern because it sounds sophisticated rather than because you're experiencing the specific problem it solves. This guide maps each pattern to its forcing function.

Core idea: Before adopting any pattern, name the specific problem you're experiencing. If you can't name it precisely, you're not ready to apply the pattern. Every pattern here came from someone experiencing a specific, painful failure mode at scale.

The 9 patterns

Pattern library with forcing functions

Decomposition by Domain

Split services along business domain boundaries using Domain-Driven Design. The forcing function: a change in one business domain should not require changes in another. Apply when your monolith has distinct ownership areas with different change frequencies.

Decomposition by Subdomain

Within a domain, separate core subdomain (differentiator), supporting subdomain (needed but not differentiating), and generic subdomain (commodity). Don't build microservices for generic subdomains — use off-the-shelf. Only build what differentiates.

Database Per Service

Each service owns its schema and no other service queries it directly. Forcing function: a schema change by one team broke five other services. Apply as the default — exceptions require explicit justification and a migration plan.

API Composition

When a query requires data from multiple services, an API composer (gateway or dedicated service) fetches in parallel and aggregates. Avoids the N+1 problem of sequential service calls. Use when response time matters more than backend load.

CQRS

Separate the write model (commands) from the read model (queries). Forcing function: read-heavy workloads are contending with write-heavy workloads on the same database. Enables read replicas, materialized views, and separate scaling strategies.

API Gateway

Single entry point. Cross-cutting concerns (auth, rate limiting, request tracing, response caching) live here rather than in every service. Forcing function: every service reimplementing auth in slightly different ways.

Event-Driven / Messaging

Services communicate via events over a broker (Kafka, RabbitMQ). Producers don't know about consumers. Forcing function: synchronous service calls are creating cascading timeouts and tight coupling. Apply when decoupling matters more than immediate consistency.

Saga

Distributed transaction across services using coordinated local transactions with compensating rollback. Forcing function: you need ACID-like guarantees across service boundaries but can't use a shared database. Use orchestration (coordinator) over choreography (events) for traceability.

Service Registry

Services self-register their network location on startup; clients discover service addresses dynamically. Forcing function: hardcoded service URLs in container environments that change IP addresses on every deploy.

Bulkhead

Isolate resource pools so that a failure in one pool doesn't exhaust resources for all services. Named after ship bulkheads: flooding one compartment doesn't sink the ship. Forcing function: one slow downstream service was consuming all thread pool slots, making the entire service unresponsive.

JavaScript Example

Bulkhead pattern + API Composition in Node.js

JavaScript Example 
// Bulkhead: separate concurrency limits per downstream service
// Prevents one slow service from consuming all request capacity

class Bulkhead {
  constructor(name, maxConcurrent) {
    this.name = name;
    this.maxConcurrent = maxConcurrent;
    this.active = 0;
    this.queue = [];
  }

  async execute(fn) {
    if (this.active >= this.maxConcurrent) {
      // Queue the request rather than reject immediately
      await new Promise((resolve, reject) => {
        this.queue.push({ resolve, reject });
        // Timeout after 5 seconds to prevent indefinite queueing
        setTimeout(() => reject(new Error(`[bulkhead:${this.name}] queue timeout`)), 5_000);
      });
    }

    this.active++;
    try {
      return await fn();
    } finally {
      this.active--;
      const next = this.queue.shift();
      if (next) next.resolve();
    }
  }
}

// Each downstream service gets its own bulkhead — they don't share capacity
const inventoryBulkhead = new Bulkhead('inventory', 10);
const pricingBulkhead   = new Bulkhead('pricing', 20);
const reviewsBulkhead   = new Bulkhead('reviews', 5);  // external, slow service

// API Composition: fetch from multiple services in parallel with bulkhead isolation
async function getProductPage(productId) {
  const [inventory, pricing, reviews] = await Promise.allSettled([
    inventoryBulkhead.execute(() => fetchInventory(productId)),
    pricingBulkhead.execute(() => fetchPricing(productId)),
    reviewsBulkhead.execute(() => fetchReviews(productId)),
  ]);

  return {
    productId,
    // Degrade gracefully — a failed reviews service doesn't break the product page
    inventory: inventory.status === 'fulfilled' ? inventory.value : null,
    pricing:   pricing.status === 'fulfilled'   ? pricing.value   : null,
    reviews:   reviews.status === 'fulfilled'   ? reviews.value   : [],
    degraded:  [inventory, pricing, reviews].some(r => r.status === 'rejected'),
  };
}

// Stub downstream fetchers
async function fetchInventory(id) { return { id, stock: 24 }; }
async function fetchPricing(id)   { return { id, price: 29.99, currency: 'USD' }; }
async function fetchReviews(id)   { return [{ rating: 4, text: 'Great product' }]; }
Bulkhead + Circuit Breaker = complete failure isolation: The Bulkhead limits concurrent load to a slow service; the Circuit Breaker stops sending requests when the service is failing. Used together, they prevent a downstream failure from consuming resources (bulkhead) and prevent wasted calls to a known-bad service (circuit breaker). Apply both together for any third-party or latency-variable downstream service.

Key Takeaway

Each pattern in this list solves a specific, observable problem. Decomposition by Domain addresses ownership confusion. Database Per Service prevents cross-team schema coupling. API Composition solves the data aggregation problem across services. Bulkhead prevents one slow downstream from collapsing the entire system. Apply them against the specific problem you're experiencing — and resist the pressure to apply all of them up front before you've experienced the problems they solve.
