Design a Thread Pool to Send 10 Million SMS Messages in One Hour

A complete system design interview answer: thread pool sizing maths, work queue architecture, back-pressure, dead-letter queues, provider rate limit management, retry strategy, and the distributed scaling path when a single machine is not enough.

Domain: System Design · Backend Engineering · Interview Prep Published: 2026-07-22

10 million messages in one hour is 2,778 messages per second. At an average SMS API call latency of 200ms, a single thread can dispatch 5 messages per second. That means you need at minimum 556 concurrent threads to hit the target — before accounting for retries, rate limits, and failure overhead. The interview is testing whether you can translate a volume requirement into a concrete concurrency model, then explain what breaks at each layer.

The interviewer's real question: Can you design a system that is reliably fast, not just theoretically fast? A naive thread pool that ignores provider rate limits, back-pressure, and retry storms will be slower than a well-designed one with half the threads.

Story · The marketing blast that bricked three servers

A SaaS company needed to send a promotional SMS to 10M users at noon. They spun up 2,000 threads, each pulling from a database queue. By 12:01, their SMS provider was returning 429 (Too Many Requests) for 80% of calls. The retry logic kicked in — all 2,000 threads retried simultaneously. Provider connections exhausted. Database connection pool saturated. The app servers went OOM. Zero messages sent. Marketing missed their noon window.

The root problems: no rate limiting, no back-pressure, and exponential retry without jitter. This design solves all three.

Step 2 — Architecture Overview

Five components:

  1. Job Store — PostgreSQL or Redis with the full list of phone numbers and message templates. Partitioned for parallel consumption.
  2. Work Queue — an in-memory bounded queue feeding the thread pool. Bounded size = back-pressure mechanism.
  3. Thread Pool — fixed-size pool of worker threads. Each thread pulls from the work queue, calls the SMS API, handles the result.
  4. Rate Limiter — token bucket shared across all threads, capped at provider's limit (e.g., Twilio: 1,000 msg/s per account).
  5. Dead-Letter Queue (DLQ) — failed messages after max retries land here for manual review or offline retry.

Step 3 — Thread Pool Implementation

JavaScript Example — Thread Pool with Work Queue and Back-Pressure 
// sms-dispatcher.js — Node.js (worker_threads equivalent using async workers)
// Note: In Node.js we achieve concurrency with async I/O rather than OS threads,
// but the logical model is identical to a Java/Python thread pool.

import { Semaphore } from 'async-mutex'; // npm: async-mutex

const CONCURRENCY = 800;          // max concurrent API calls
const RATE_LIMIT = 1000;          // calls per second (provider limit)
const MAX_RETRIES = 3;
const semaphore = new Semaphore(CONCURRENCY);

// Token bucket for rate limiting
class TokenBucket {
  constructor(rate) {
    this.tokens = rate;
    this.rate = rate;
    this.lastRefill = Date.now();
  }
  async acquire() {
    while (true) {
      const now = Date.now();
      const elapsed = (now - this.lastRefill) / 1000;
      this.tokens = Math.min(this.rate, this.tokens + elapsed * this.rate);
      this.lastRefill = now;
      if (this.tokens >= 1) { this.tokens -= 1; return; }
      await new Promise(r => setTimeout(r, 10)); // wait 10ms, re-check
    }
  }
}

const rateLimiter = new TokenBucket(RATE_LIMIT);

async function sendSmsWithRetry(phone, message, attempt = 0) {
  try {
    await rateLimiter.acquire(); // honour provider rate limit
    const response = await fetch('https://api.twilio.com/sms', {
      method: 'POST',
      headers: { 'Authorization': `Bearer ${process.env.TWILIO_TOKEN}` },
      body: JSON.stringify({ to: phone, body: message })
    });
    if (!response.ok) {
      const err = await response.json();
      throw Object.assign(new Error(err.message), { status: response.status });
    }
    return { phone, success: true };
  } catch (err) {
    if (attempt >= MAX_RETRIES) {
      return { phone, success: false, error: err.message, final: true }; // → DLQ
    }
    // Exponential backoff with jitter: 100ms, 200ms, 400ms ± 50%
    const delay = 100 * Math.pow(2, attempt) * (0.5 + Math.random() * 0.5);
    await new Promise(r => setTimeout(r, delay));
    return sendSmsWithRetry(phone, message, attempt + 1);
  }
}

async function dispatchBatch(recipients, message) {
  const results = { sent: 0, failed: 0, dlq: [] };
  const start = Date.now();

  // Process all recipients with bounded concurrency (semaphore = back-pressure)
  await Promise.all(recipients.map(async (phone) => {
    const [, release] = await semaphore.acquire();
    try {
      const result = await sendSmsWithRetry(phone, message);
      if (result.success) results.sent++;
      else { results.failed++; results.dlq.push(result); }
    } finally {
      release(); // release slot back to pool
    }
  }));

  const elapsed = (Date.now() - start) / 1000;
  console.log(`Dispatched ${results.sent} OK, ${results.failed} failed in ${elapsed.toFixed(1)}s`);
  console.log(`Throughput: ${(results.sent / elapsed).toFixed(0)} msg/s`);
  return results;
}

Step 4 — Distributed Scaling (when 1 machine is not enough)

If the provider raises the limit to 10,000 msg/s or the volume grows to 100M messages, a single machine becomes the bottleneck. The distributed extension:

  1. Partition the job store — divide phone numbers into N shards (e.g., by hash of phone number mod N). Each worker node claims one or more shards.
  2. Distributed work queue — replace the in-memory queue with SQS, Kafka, or Redis Streams. Workers consume independently; visibility timeout prevents double-processing.
  3. Distributed rate limiter — replace the in-process token bucket with a Redis-backed distributed rate limiter (Lua script or Redlock). All nodes share the same rate limit against the provider.
  4. Coordinator — a lightweight orchestrator (Temporal, Airflow, or a simple cron) monitors progress, rebalances shards if a node dies, and triggers the DLQ retry job.

Step 5 — Failure Modes and Production Gotchas

  • Provider throttle without 429 — some providers silently drop messages instead of returning 429 under extreme load. Build end-to-end delivery confirmation (delivery receipts / DLR) and treat no-receipt-in-60s as a failure.
  • Retry storm — without jitter, all retries fire at the same instant. The jitter formula above (0.5 + 0.5*random) ensures spread.
  • Memory growth under backlog — if the work queue is unbounded and the provider is slow, you'll queue millions of jobs in memory and OOM. Always bound the queue. When full, apply back-pressure (block the producer or drop to disk).
  • Invalid phone numbers — pre-validate with a regex or E.164 library before dispatching. A 10% invalid rate wastes 1M API calls and occupies threads that could be sending real messages.
  • Partial success reporting — at 10M messages, you need a way to know exactly which numbers succeeded and which failed. Write results to a columnar store (Parquet on S3) partitioned by outcome; never keep 10M rows in a single DB table.
  • Opt-out compliance — query a DNC (Do Not Call) list before dispatching. At 2,778 msg/s, a missed opt-out can generate thousands of regulatory violations before anyone notices.

Key Takeaway

The answer to "design a thread pool for 10M SMS" is not a thread count — it is a system with four interlocking components: a bounded work queue that provides back-pressure, a semaphore that limits concurrency, a rate limiter that respects the provider's ceiling, and a dead-letter queue that ensures no message is silently lost. The thread count follows from the maths; the architecture follows from the failure modes.
