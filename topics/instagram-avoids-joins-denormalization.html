Why Instagram Avoids JOINs at Scale: Denormalization and Read Optimization at 2 Billion Users

At 2 billion monthly active users, a naively normalized Instagram feed requires 4+ table JOINs across billions of rows on every render — an operation that shatters under horizontal sharding. This deep dive covers why JOINs become a structural bottleneck at scale, what denormalization actually means in a production system, how pre-computed aggregates and materialized feed views eliminate joins entirely, and how Instagram handles the write amplification trade-off when a celebrity's post fans out to 300 million followers.

Domain: System Design · Database · Read Optimization Published: 2026-07-29 Source: towardsdev.com

Database normalization is taught as a virtue: eliminate redundancy, enforce referential integrity, keep data consistent through a single source of truth. At a startup with 10,000 users it is the right call — clean schemas, easy migrations, no anomalies. At 2 billion users with 500 million daily active sessions, normalization becomes a liability. The JOIN that was free at small scale becomes a distributed scatter-gather across sharded nodes, adding 10–50 ms to every feed render. Multiply that by 500 million daily sessions and you have hundreds of millions of dollars in infrastructure cost from a single SQL keyword.

Scale context: Instagram serves 100 million stories and 95 million photos per day. At peak, feed rendering happens at ~500,000 requests/second. A single feed page requires assembling 10–20 posts, each needing user data, like counts, comment counts, and media metadata. Without pre-computation, each feed render triggers 40–80 individual database lookups or one massive JOIN. Neither is acceptable at this scale.

Story · The JOIN that works fine in staging and melts in production

Imagine Instagram's feed query in its simplest normalized form. The posts table stores post records keyed by post_id. The users table stores profile data keyed by user_id. The likes table is a join table between users and posts. The comments table links comments to posts. A feed render for 20 posts requires joining all four: 

-- Naive normalized feed query
SELECT
  p.id, p.caption, p.media_url, p.created_at,
  u.username, u.display_name, u.profile_pic_url,
  COUNT(DISTINCT l.user_id)  AS like_count,
  COUNT(DISTINCT c.id)       AS comment_count
FROM posts p
JOIN users u       ON u.id = p.user_id
LEFT JOIN likes l  ON l.post_id = p.id
LEFT JOIN comments c ON c.post_id = p.id
WHERE p.id = ANY($1::bigint[])   -- array of 20 post IDs from feed
GROUP BY p.id, u.id;

In staging with 10,000 posts, this query runs in 3 ms. In production with 50 billion posts, the likes table alone has 500 billion rows. The COUNT aggregation scans billions of rows. The JOIN requires all four tables to be on the same database node — which is impossible once you shard by user_id, because a post's author lives on a different shard from the post's likers. The query that was free at small scale is architecturally impossible at large scale.

Why JOINs Fail at Scale

JOINs fail at scale for four distinct reasons. Understanding each one separately is important because each requires a different mitigation strategy.

1. Horizontal sharding breaks co-location

A SQL JOIN requires rows from multiple tables to be accessible in the same query execution context. On a single database node, that is trivially true. But once you shard — splitting data across multiple database nodes by a partition key — different tables are on different nodes. A JOIN between posts (sharded by post_id) and users (sharded by user_id) requires data from two separate machines. The database cannot execute this JOIN natively; it becomes an application-level scatter-gather. 

-- What the application must do instead of a single JOIN:

// Step 1: Fetch post records from Posts DB shard (sharded by post_id)
const posts = await postsDb.query(
  `SELECT id, user_id, caption, media_url, created_at FROM posts WHERE id = ANY($1)`,
  [postIds]
);

// Step 2: Extract all unique user IDs from results
const userIds = [...new Set(posts.map(p => p.user_id))];

// Step 3: Fetch user data from Users DB shard (different shard cluster!)
const users = await usersDb.query(
  `SELECT id, username, display_name, profile_pic_url FROM users WHERE id = ANY($1)`,
  [userIds]
);

// Step 4: Join in application memory
const userMap = Object.fromEntries(users.map(u => [u.id, u]));
const enrichedPosts = posts.map(p => ({ ...p, user: userMap[p.user_id] }));

This application-level join involves two network round trips (Posts DB + Users DB), two query executions, and in-memory assembly. If the feed page shows 20 posts from 20 different users across 8 shards, the scatter-gather requires 8+ parallel queries before the page can render.

2. Aggregation on high-cardinality tables

COUNT(DISTINCT l.user_id) on a likes table with 500 billion rows is a full-table scan unless perfectly indexed — and even with an index, a post with 10 million likes requires reading 10 million index entries to count them. At 500,000 feed renders/second, this aggregation load is untenable. The solution is pre-computed aggregates: store the count directly on the post row and maintain it with increments/decrements, never computing it at read time.

3. Lock contention under mixed read-write workloads

A heavily-read table like likes receives both read queries (COUNT aggregations for display) and write queries (new likes, unlikes) simultaneously. Under InnoDB or PostgreSQL MVCC, concurrent writes create row-level locks and version chains that degrade read performance. At Instagram's write rate (millions of new likes per minute), this contention is severe. Pre-computed counters on a separate counter service isolate the write workload from the read workload.

4. Index efficiency degrades with JOIN depth

Each additional JOIN table in a query multiplies the optimizer's search space for an execution plan. A 4-table JOIN on billion-row tables often results in the optimizer choosing a full-table scan on one table because the index selectivity across join conditions makes a nested-loop join more expensive than a hash join with a full scan. At scale, query plan stability becomes critical — and complex JOINs are notoriously unstable: a statistics refresh can flip the execution plan from 2 ms to 2 seconds.

What Denormalization Means in Practice

Denormalization is the intentional duplication of data to eliminate JOINs at read time. It is not abandoning data integrity — it is making a deliberate trade: accept higher write complexity in exchange for dramatically simpler reads.

Normalized schema (JOIN required on every read)

-- NORMALIZED: clean, no redundancy, JOIN required
CREATE TABLE users (
  id            BIGINT PRIMARY KEY,
  username      VARCHAR(30) UNIQUE NOT NULL,
  display_name  VARCHAR(60),
  profile_pic_url TEXT,
  updated_at    TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE posts (
  id          BIGINT PRIMARY KEY,
  user_id     BIGINT NOT NULL REFERENCES users(id),  -- FK, JOIN required
  caption     TEXT,
  media_url   TEXT NOT NULL,
  created_at  TIMESTAMPTZ DEFAULT NOW()
);

-- Every read: SELECT ... FROM posts JOIN users ON users.id = posts.user_id

Denormalized schema (no JOIN needed on read)

-- DENORMALIZED: redundant data stored inline, zero JOIN on read
CREATE TABLE posts (
  id              BIGINT PRIMARY KEY,
  user_id         BIGINT NOT NULL,       -- kept for writes/updates
  -- Denormalized user fields (duplicated from users table)
  username        VARCHAR(30) NOT NULL,  -- duplicated!
  display_name    VARCHAR(60),           -- duplicated!
  profile_pic_url TEXT,                  -- duplicated!
  -- Denormalized aggregates
  like_count      INT NOT NULL DEFAULT 0,
  comment_count   INT NOT NULL DEFAULT 0,
  -- Post-specific fields
  caption         TEXT,
  media_url       TEXT NOT NULL,
  created_at      TIMESTAMPTZ DEFAULT NOW()
);

-- Every read: SELECT * FROM posts WHERE id = ANY($1)
-- No JOINs. One table. One query.

The cost is write amplification: when a user changes their username, you must update not just the users row but every post row that duplicated the username. Instagram handles this with an async background update via Kafka — the username update is eventually consistent across post copies, which is acceptable because a username change is a rare event and a brief display inconsistency is tolerable.

The denormalization rule: Duplicate fields that are frequently read and rarely updated. Never duplicate fields that are high-churn (prices, availability, live counters). Instagram duplicates: username, display_name, avatar URL. Instagram does NOT duplicate: follower counts (updated constantly), story availability (changes every 24 hours).

Pre-Computed Aggregates

Like counts and comment counts are the canonical example of read-time aggregation that does not scale. Instagram stores these as integer columns directly on the post row and maintains them through a dedicated counter service rather than computing them on reads.

JavaScript Example — Counter Service with Atomic Increments 
// counter-service.js — Node.js + Redis + PostgreSQL
// Handles like/unlike with atomic Redis increment and async DB sync

import Redis from 'ioredis';
const redis = new Redis(process.env.REDIS_URL);

const COUNTER_SYNC_INTERVAL_MS = 5_000;  // flush to DB every 5 seconds

// When a user likes a post
async function likePost(postId, userId) {
  const likeKey = `likes:${postId}`;
  const userLikeKey = `user-liked:${userId}:${postId}`;

  // Idempotency: prevent double-like
  const alreadyLiked = await redis.set(userLikeKey, '1', 'NX', 'EX', 86400 * 30);
  if (!alreadyLiked) return { status: 'already_liked' };

  // Atomic increment in Redis (fast, no DB write on hot path)
  const newCount = await redis.incr(likeKey);

  // Async: write the like event to Kafka for durable storage
  await kafka.produce('like-events', { postId, userId, action: 'like', ts: Date.now() });

  return { status: 'liked', likeCount: newCount };
}

// Background job: flush Redis counters to PostgreSQL
async function flushCountersToDB() {
  // Scan for all counter keys
  const keys = await redis.keys('likes:*');

  for (const key of keys) {
    const postId = key.split(':')[1];
    const redisCount = await redis.get(key);
    if (redisCount === null) continue;

    // Update the denormalized counter on the post row
    await db.query(
      `UPDATE posts SET like_count = $1 WHERE id = $2`,
      [parseInt(redisCount, 10), postId]
    );
  }
}

setInterval(flushCountersToDB, COUNTER_SYNC_INTERVAL_MS);

// READ PATH: serve from Redis (fast, ~1ms) with DB fallback
async function getLikeCount(postId) {
  const cached = await redis.get(`likes:${postId}`);
  if (cached !== null) return parseInt(cached, 10);

  // Cache miss: load from DB and warm cache
  const row = await db.query(`SELECT like_count FROM posts WHERE id = $1`, [postId]);
  const count = row.rows[0]?.like_count ?? 0;
  await redis.set(`likes:${postId}`, count, 'EX', 3600);
  return count;
}

The critical design choice: the read path never touches the likes join table. It reads a single integer from Redis (sub-millisecond) or from the post row itself. The trade-off is eventual consistency — during a viral spike, the displayed count may lag the true count by a few seconds while Redis flushes to PostgreSQL. Instagram accepts this: users do not notice a count of "2,341,892" vs "2,341,900."

Cassandra counter columns are the NoSQL equivalent. Cassandra provides a native COUNTER column type with atomic increment/decrement semantics, designed exactly for this use case. A Cassandra counter write is a CAS operation distributed across replicas — no full-table COUNT aggregation ever runs.

-- Cassandra counter column example
CREATE TABLE post_counters (
  post_id    BIGINT PRIMARY KEY,
  like_count COUNTER,
  comment_count COUNTER,
  share_count COUNTER
);

-- Increment on like (atomic, distributed)
UPDATE post_counters SET like_count = like_count + 1 WHERE post_id = 123456789;

-- Read (no aggregation, direct counter read)
SELECT like_count, comment_count FROM post_counters WHERE post_id = 123456789;

Materialized Views for Feed: Fan-Out on Write

The feed itself is the most read-heavy data structure in Instagram. Every session begins with a feed render. Building the feed at read time — even with all the denormalization above — still requires fetching post IDs for everyone the user follows, then batch-fetching post data. At 500M daily active users, "fetching post IDs for everyone you follow" is a fan-in aggregation across billions of follow relationships.

Instagram's solution is fan-out on write: when a user posts, Instagram pushes the post ID into every follower's personal feed list at write time, not at read time. The feed list is a pre-materialized view maintained in Redis.

JavaScript Example — Fan-Out on Write with Redis Sorted Sets 
// feed-service.js — Fan-out on write
// Redis sorted set: ZADD feed:{userId} score postId
// score = post timestamp (enables chronological ordering)

import Redis from 'ioredis';
const redis = new Redis(process.env.REDIS_URL);

const MAX_FEED_SIZE = 1000;  // Instagram keeps ~1000 recent post IDs per user

// Called when a user creates a new post
async function fanOutPost(authorId, postId, createdAtMs) {
  // Fetch all followers of this author from the follow graph DB
  // (sharded by author_id for efficient fan-out queries)
  const followers = await followGraphDb.query(
    `SELECT follower_id FROM follows WHERE followed_id = $1`,
    [authorId]
  );

  // Fan out to each follower's Redis feed list in parallel batches
  const BATCH_SIZE = 1000;
  for (let i = 0; i < followers.length; i += BATCH_SIZE) {
    const batch = followers.slice(i, i + BATCH_SIZE);

    const pipeline = redis.pipeline();
    for (const { follower_id } of batch) {
      const feedKey = `feed:${follower_id}`;
      // ZADD feed:userId timestamp postId
      pipeline.zadd(feedKey, createdAtMs, postId.toString());
      // Trim feed to MAX_FEED_SIZE most recent items
      pipeline.zremrangebyrank(feedKey, 0, -(MAX_FEED_SIZE + 1));
      // Set TTL on feed key (30 days of inactivity = evict)
      pipeline.expire(feedKey, 86400 * 30);
    }
    await pipeline.exec();
  }

  console.log(`[fanout] Post ${postId} distributed to ${followers.length} followers`);
}

// READ PATH: serving a user's feed (zero JOINs, zero aggregations)
async function getFeed(userId, page = 0, pageSize = 20) {
  const feedKey = `feed:${userId}`;
  const start = page * pageSize;
  const end = start + pageSize - 1;

  // Step 1: Get postIds from sorted set (newest first = reverse range)
  const postIds = await redis.zrevrange(feedKey, start, end);

  if (postIds.length === 0) return [];

  // Step 2: Batch-fetch full post data (one query, no JOINs — denormalized schema)
  const posts = await db.query(
    `SELECT id, user_id, username, profile_pic_url, caption,
            media_url, like_count, comment_count, created_at
     FROM posts WHERE id = ANY($1::bigint[])
     ORDER BY created_at DESC`,
    [postIds.map(id => BigInt(id))]
  );

  return posts.rows;
  // Total: 2 network calls. Zero JOINs. Avg latency: 8–15 ms end-to-end.
}

The celebrity problem: fan-out on read

Fan-out on write has a hard limit: when Cristiano Ronaldo (600M followers) posts, fanning out to 600M Redis sorted sets synchronously is impossible — it would take minutes and create a massive write spike. Instagram's solution is a hybrid strategy with a celebrity threshold:

  • Regular users (followers < threshold, ~50K–1M): fan-out on write, pre-built feed
  • Celebrity accounts (followers > threshold): fan-out on read at request time
// Hybrid feed assembly: mix pre-built feed + celebrity posts at read time
async function getFeedHybrid(userId, page, pageSize) {
  // 1. Get pre-built feed items (regular accounts)
  const regularPostIds = await redis.zrevrange(`feed:${userId}`, 0, pageSize * 3);

  // 2. Get celebrity accounts this user follows
  const celebrities = await followGraphDb.query(
    `SELECT followed_id FROM follows
     WHERE follower_id = $1 AND is_celebrity = true`,
    [userId]
  );

  // 3. Fetch recent posts from celebrity accounts directly (fan-in at read time)
  let celebPostIds = [];
  if (celebrities.rows.length > 0) {
    const celebIds = celebrities.rows.map(r => r.followed_id);
    const celebPosts = await db.query(
      `SELECT id, created_at FROM posts
       WHERE user_id = ANY($1::bigint[])
       ORDER BY created_at DESC LIMIT $2`,
      [celebIds, pageSize * 2]
    );
    celebPostIds = celebPosts.rows.map(r => r.id.toString());
  }

  // 4. Merge, de-duplicate, sort by score, return page
  const allIds = [...new Set([...regularPostIds, ...celebPostIds])];
  // fetch full post data and sort by created_at...
  return fetchAndSortPosts(allIds, page, pageSize);
}

Data Duplication Strategy

Not all data is safe to duplicate. The guiding principle: duplicate data whose update frequency is low relative to read frequency. Instagram follows a clear taxonomy:

What Instagram duplicates (safe)

  • username — changes once every few months at most; stored on every post
  • display_name — same frequency as username
  • profile_pic_url — changes occasionally; stored on every post and comment
  • post like_count / comment_count — maintained by counter service, eventually consistent

What Instagram does NOT duplicate (unsafe)

  • is_verified badge — verification status can be revoked instantly and must be consistent everywhere immediately; fetched live
  • is_private account — privacy changes must be atomic; a post must not be visible after the account goes private
  • follower_count — updated on every follow/unfollow; too high churn to duplicate across many records

Async propagation on update via Kafka

// profile-update-service.js
// When a user updates their avatar, propagate asynchronously to all post copies

async function updateUserProfile(userId, updates) {
  // Step 1: Update the source of truth (users table)
  await db.query(
    `UPDATE users SET display_name = $1, profile_pic_url = $2, updated_at = NOW()
     WHERE id = $3`,
    [updates.displayName, updates.profilePicUrl, userId]
  );

  // Step 2: Publish profile-updated event to Kafka
  // Downstream consumers update denormalized copies asynchronously
  await kafka.produce('profile-updates', {
    userId,
    displayName: updates.displayName,
    profilePicUrl: updates.profilePicUrl,
    updatedAt: Date.now()
  });
}

// Kafka consumer: update denormalized copies in posts table
kafka.consume('profile-updates', async (event) => {
  const { userId, displayName, profilePicUrl } = event;

  // Batch update all posts by this user
  // (run in chunks to avoid locking the entire partition)
  let lastId = 0;
  while (true) {
    const result = await db.query(
      `UPDATE posts
       SET display_name = $1, profile_pic_url = $2
       WHERE user_id = $3 AND id > $4
       ORDER BY id LIMIT 1000
       RETURNING id`,
      [displayName, profilePicUrl, userId, lastId]
    );
    if (result.rowCount === 0) break;
    lastId = Math.max(...result.rows.map(r => r.id));
    await sleep(50);  // gentle pacing to avoid write storm
  }
});

The eventual consistency window here is measured in seconds to minutes — fully acceptable for a profile picture update. Users whose posts briefly show their old avatar while the async update propagates will not notice or complain.

NoSQL Schema Design for Read Optimization

Denormalization maps naturally to NoSQL databases, which are designed around query-first schema design rather than relational normalization. Two systems Instagram has used extensively are Cassandra and Redis.

Cassandra: wide rows optimized for feed access patterns

Cassandra organizes data by partition key (determines which node stores the data) and clustering key (determines sort order within the partition). A feed table designed for Instagram's access pattern stores all of a user's feed items in one wide row — one partition = one user's feed, ordered by timestamp. 

-- Cassandra feed table: one partition per user, ordered by post time
CREATE TABLE user_feed (
  follower_id   BIGINT,
  posted_at     TIMESTAMP,
  post_id       BIGINT,
  -- Denormalized post data (no JOIN ever needed)
  author_id     BIGINT,
  username      TEXT,
  profile_pic   TEXT,
  caption       TEXT,
  media_url     TEXT,
  like_count    INT,
  comment_count INT,
  PRIMARY KEY (follower_id, posted_at, post_id)
) WITH CLUSTERING ORDER BY (posted_at DESC, post_id DESC);

-- One query = one feed page (no JOINs, no aggregations)
SELECT * FROM user_feed
WHERE follower_id = 12345678
LIMIT 20;

-- Next page (token-based pagination using clustering key)
SELECT * FROM user_feed
WHERE follower_id = 12345678
  AND (posted_at, post_id) < ('2026-07-28 18:00:00', 9999999999)
LIMIT 20;

MongoDB's $lookup is a server-side JOIN. At small scale it is fine; at billion-document scale on sharded collections, it faces the exact same co-location problem as SQL JOINs. Instagram uses embedding for the author summary snapshot, accepting the write amplification in exchange for sub-millisecond single-document reads.

Write Amplification Trade-offs

Denormalization and fan-out on write impose write amplification — a single logical write event causes many physical write operations. Understanding the amplification factor is essential to evaluating the strategy's viability.

Fan-out amplification

  • Regular user (1,000 followers): 1 post = 1,000 Redis ZADD operations. Amplification factor: 1,000×. Fully acceptable; completes in <100ms.
  • Influencer (5M followers): 1 post = 5M writes. Takes 5–10 seconds to fan out fully. Async background job; user's post is immediately visible to the poster.
  • Celebrity (300M followers, e.g. Cristiano Ronaldo): 1 post = 300M writes. Impossible to fan out in reasonable time. Fan-out on read is used instead.

Profile update amplification

// Amplification analysis: username change
// Instagram user with 10,000 posts changes their username
// → 10,000 UPDATE operations on the posts table
// → 10,000 Cassandra cell updates in user_feed partitions of each follower
// → Up to N × 10,000 updates where N = number of followers

// Mitigation: lazy update (update-on-read)
async function getPost(postId) {
  const post = await db.query(`SELECT * FROM posts WHERE id = $1`, [postId]);
  const row = post.rows[0];

  // Check if the author's profile has been updated since this post was written
  const authorVersion = await redis.get(`user-version:${row.user_id}`);
  if (authorVersion && authorVersion !== row.author_version) {
    // Stale — fetch fresh author data and update lazily
    const author = await usersDb.query(
      `SELECT username, display_name, profile_pic_url, version
       FROM users WHERE id = $1`, [row.user_id]
    );
    // Update this specific post's denormalized fields lazily
    await db.query(
      `UPDATE posts SET username = $1, profile_pic_url = $2, author_version = $3
       WHERE id = $4`,
      [author.rows[0].username, author.rows[0].profile_pic_url,
       author.rows[0].version, postId]
    );
    return { ...row, ...author.rows[0] };
  }
  return row;
}

Read-repair for consistency

Read-repair is a pattern where stale denormalized data is corrected lazily on the read path rather than eagerly via background jobs. When a post is served and the author's profile version in the post row does not match the current profile version, the system returns the fresh data immediately (fetched from the users service) and asynchronously updates the stale post row. The read path bears a small extra cost (one additional users lookup on stale records), but background write amplification is eliminated.

When to Use Normalization vs Denormalization

The right choice depends on the read/write ratio, data size, and consistency requirements of each specific access pattern. There is no universal answer.

Dimension Normalized (JOIN) Denormalized (No JOIN)
Read latency Higher (multi-table query) Lower (single-table fetch)
Write latency Lower (one row updated) Higher (many rows updated)
Data consistency Strong (single source of truth) Eventual (propagation lag)
Storage cost Lower (no duplication) Higher (redundant copies)
Schema complexity Lower (clean schema) Higher (sync logic required)
Horizontal scaling Hard (cross-shard JOINs fail) Easy (all data in one row/doc)
Use when OLTP, small scale, write-heavy, strong consistency required OLAP, large scale, read-heavy, eventual consistency acceptable
Real examples Bank transactions, e-commerce orders, CMS Instagram feed, Twitter timeline, Netflix catalog

Practical decision framework

// When deciding whether to denormalize a field:
function shouldDenormalize(field) {
  const readFrequency  = getReadsPerSecond(field);
  const writeFrequency = getWritesPerSecond(field);
  const ratio = readFrequency / writeFrequency;

  // Rule of thumb:
  // ratio > 100:1  → strong candidate for denormalization
  // ratio 10–100:1 → consider denormalization, measure first
  // ratio < 10:1   → normalize; write amplification cost too high

  if (ratio > 100) return 'DENORMALIZE';
  if (ratio > 10)  return 'MEASURE_AND_DECIDE';
  return 'NORMALIZE';
}

// Instagram field ratios (approximate):
// username on posts:       10,000:1  → DENORMALIZE ✓
// profile_pic on posts:    50,000:1  → DENORMALIZE ✓
// post like_count display:  5,000:1  → DENORMALIZE (counter service) ✓
// is_private flag:            100:1  → DO NOT DENORMALIZE (consistency critical)
// follower_count:              50:1  → DO NOT DENORMALIZE (high write churn)

Key Takeaway

Instagram avoids JOINs at scale because JOINs are structurally incompatible with horizontal sharding: once data is split across nodes by partition key, cross-table JOINs require application-level scatter-gather that adds multiple network round trips to every read. The solution is three layered strategies working together: denormalization (store username and avatar inline on post rows to eliminate the users JOIN), pre-computed aggregates (store like_count and comment_count as integer columns maintained by a counter service to eliminate COUNT queries), and materialized feed views (fan-out on write to Redis sorted sets so that feed renders require only a ZRANGE and a batch post fetch — zero JOINs, zero aggregations, 8–15 ms end-to-end). The cost — write amplification, eventual consistency, and increased storage — is an explicit engineering trade-off accepted because read latency at 2 billion users is the constraint that matters most.
