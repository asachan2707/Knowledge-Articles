One Microservice Failure Takes Down Entire Platform: System Design Deep Dive on Circuit Breakers, Bulkheads, Timeouts, and Resilience Engineering

A recommendation service goes down during Black Friday. Within 90 seconds, the product page service goes down. Then inventory. Then checkout. The whole platform is dark — but only the recommendation service was actually broken. This deep dive covers cascading failure mechanics, the circuit breaker state machine (closed/open/half-open), bulkhead isolation, timeout configuration (the most dangerous knob in distributed systems), retry storm prevention, and the exact Netflix Hystrix and Resilience4j production patterns that stop cascades before they start.

Domain: System Design · Resilience Engineering · Distributed Systems Published: 2026-08-05

Cascading failure is the distributed system equivalent of a fire spreading through interconnected buildings. One building catches fire — and if the firebreaks are not in place, every connected building burns. In microservices, the fire is a slow or failing dependency, the fuel is unbounded thread pools and missing timeouts, and the firebreak is the circuit breaker. Most teams know what circuit breakers are. Far fewer understand why they are always misconfigured, and almost none have tested whether their circuit breakers actually open under load.

Core idea: A cascade failure does not begin with the failing service. It begins with the services that call the failing service — because they accumulate blocked threads, exhaust connection pools, and run out of the resources they need to serve unrelated requests. The recommendation service going down should never affect checkout. It will, unless you deliberately prevent it.

Story · The Recommendation Service That Killed Black Friday

How a Slow Dependency Took Down 11 Independent Services

ShopAll, a mid-size e-commerce platform, ran 11 microservices. The product page service called five downstream services: inventory (stock counts), pricing (dynamic discounts), images (CDN URLs), reviews (user ratings), and recommendations (personalized "you may also like"). Recommendations was the newest service — it called a third-party ML API to generate results.

On Black Friday at 8:00 AM, the ML API provider hit their own capacity limit. They did not return errors. They returned responses — after 28 seconds. HTTP 200 with valid JSON, just very, very slowly. This is the worst failure mode: a slow success.

The product page service had a thread pool of 200 threads for processing incoming requests. Each product page request called all five downstream services in parallel (using Promise.all). The recommendations call was timing out after 28 seconds. But there was no timeout configured — the default Node.js HTTP request timeout was 0 (infinity).

Within 2 minutes of the ML API slowdown: all 200 product page threads were blocked waiting for recommendations responses. New incoming product page requests queued. The queue grew faster than it drained. Application memory climbed. Node.js heap usage hit 98%. At 8:07 AM, the product page service OOM-killed itself.

When product pages went down, the API gateway's health check began routing traffic to the backup product page instances. But they were experiencing the same thread exhaustion. Within 4 minutes, all product page instances were down.

Then it got worse. The checkout service called product page to validate cart items. Product page was down. Checkout requests started queuing. Checkout's thread pool filled. At 8:18 AM, checkout went down. Inventory service — called by checkout — started receiving cascading timeout storms of retries. At 8:23 AM, inventory OOM-killed. By 8:25 AM, 11 services were degraded or down because a third-party recommendation API had gotten slow.

Not one of these failures was necessary. Every single one would have been prevented by three configuration changes: a 500ms timeout on recommendation calls, a circuit breaker that opened after 5 consecutive failures, and a bulkhead that isolated recommendation threads from the main product page thread pool.

Pattern 1

The Circuit Breaker State Machine

The circuit breaker pattern was named by Michael Nygard in Release It! (2007) after the electrical circuit breaker that cuts power when current exceeds a safe threshold. In software, the breaker monitors calls to a dependency and "trips" — stops sending calls — when the failure rate crosses a threshold, allowing the dependency time to recover.

The circuit breaker has three states:

CLOSED
Normal operation. All calls pass through to the dependency. The breaker counts failures (errors, timeouts) in a rolling time window. When the failure rate exceeds the configured threshold (e.g., 50% of calls in the last 10 seconds), the breaker trips to OPEN.
OPEN
Dependency is failing. All calls immediately return an error (or fallback value) without contacting the dependency. This prevents thread pool exhaustion and gives the dependency recovery time. After a configured wait period (e.g., 30 seconds), the breaker transitions to HALF-OPEN to test recovery.
HALF-OPEN
Testing recovery. A limited number of probe requests (e.g., 5) are allowed through. If they succeed, the breaker closes (normal operation resumes). If they fail, the breaker opens again for another wait period. This prevents thundering-herd recovery stampedes where all previously-blocked traffic slams the just-recovered service.

The most common misconfiguration: Setting the failure threshold to 100% (only open on total failure). A dependency that is failing 50% of the time is already causing serious damage — half your users are getting errors, and blocked threads are accumulating fast. Open the circuit at 50% failure rate (or even 30% for latency-sensitive paths), not 100%.

JavaScript — Circuit Breaker State Machine 
// circuit-breaker.js
// Production circuit breaker: sliding window, configurable thresholds,
// half-open probe limit, and synchronous fallback.

const STATE = Object.freeze({ CLOSED: 'CLOSED', OPEN: 'OPEN', HALF_OPEN: 'HALF_OPEN' });

export class CircuitBreaker {
  /**
   * @param {Function} fn                  - The upstream call to protect
   * @param {Object}   opts
   * @param {number}   opts.failureThreshold - % failure rate to trip (default 50)
   * @param {number}   opts.windowMs         - Rolling window in ms (default 10000)
   * @param {number}   opts.minRequests      - Min requests before evaluating (default 10)
   * @param {number}   opts.openDurationMs   - How long to stay OPEN (default 30000)
   * @param {number}   opts.halfOpenProbes   - How many probes in HALF_OPEN (default 5)
   * @param {Function} opts.fallback         - Called when OPEN; receives original args
   */
  constructor(fn, {
    failureThreshold = 50,
    windowMs = 10_000,
    minRequests = 10,
    openDurationMs = 30_000,
    halfOpenProbes = 5,
    fallback = null,
  } = {}) {
    this._fn = fn;
    this._threshold = failureThreshold;
    this._windowMs = windowMs;
    this._minRequests = minRequests;
    this._openDurationMs = openDurationMs;
    this._halfOpenProbes = halfOpenProbes;
    this._fallback = fallback;

    this._state = STATE.CLOSED;
    this._calls = [];           // Rolling window: [{ ts, success }]
    this._openedAt = null;
    this._probeCount = 0;
    this._probeSuccesses = 0;
  }

  get state() { return this._state; }

  async execute(...args) {
    this._pruneWindow();

    if (this._state === STATE.OPEN) {
      if (Date.now() - this._openedAt >= this._openDurationMs) {
        this._transitionTo(STATE.HALF_OPEN);
      } else {
        // Circuit is open — fail fast or return fallback
        if (this._fallback) return this._fallback(...args);
        throw new Error(`CircuitBreaker OPEN: dependency unavailable`);
      }
    }

    if (this._state === STATE.HALF_OPEN) {
      if (this._probeCount >= this._halfOpenProbes) {
        // Probe quota exhausted — still testing, reject additional calls
        if (this._fallback) return this._fallback(...args);
        throw new Error(`CircuitBreaker HALF_OPEN: probe quota exhausted`);
      }
      this._probeCount++;
    }

    const ts = Date.now();
    try {
      const result = await this._fn(...args);
      this._record(ts, true);
      if (this._state === STATE.HALF_OPEN) {
        this._probeSuccesses++;
        // All probes succeeded → close the circuit
        if (this._probeSuccesses >= this._halfOpenProbes) {
          this._transitionTo(STATE.CLOSED);
        }
      }
      return result;
    } catch (err) {
      this._record(ts, false);
      this._evaluateTrip();
      if (this._fallback) return this._fallback(...args);
      throw err;
    }
  }

  _record(ts, success) {
    this._calls.push({ ts, success });
  }

  _pruneWindow() {
    const cutoff = Date.now() - this._windowMs;
    this._calls = this._calls.filter(c => c.ts >= cutoff);
  }

  _evaluateTrip() {
    if (this._calls.length < this._minRequests) return;
    const failures = this._calls.filter(c => !c.success).length;
    const failureRate = (failures / this._calls.length) * 100;
    if (failureRate >= this._threshold) {
      this._transitionTo(STATE.OPEN);
    }
  }

  _transitionTo(newState) {
    // console.log(`[CircuitBreaker] ${this._state} → ${newState}`);
    this._state = newState;
    if (newState === STATE.OPEN) {
      this._openedAt = Date.now();
      this._calls = [];
    }
    if (newState === STATE.HALF_OPEN) {
      this._probeCount = 0;
      this._probeSuccesses = 0;
    }
    if (newState === STATE.CLOSED) {
      this._calls = [];
      this._openedAt = null;
    }
  }

  stats() {
    this._pruneWindow();
    const total = this._calls.length;
    const failures = this._calls.filter(c => !c.success).length;
    return {
      state: this._state,
      total,
      failures,
      failureRate: total ? ((failures / total) * 100).toFixed(1) + '%' : '0%',
    };
  }
}

// Usage in product page service:
const recommendationBreaker = new CircuitBreaker(
  (userId) => fetch(`http://recommendations-svc/user/${userId}`).then(r => r.json()),
  {
    failureThreshold: 50,   // Open at 50% failure rate
    windowMs: 10_000,       // Over the last 10 seconds
    minRequests: 10,         // Minimum 10 calls before evaluating
    openDurationMs: 30_000, // Stay open for 30 seconds
    halfOpenProbes: 5,       // Allow 5 probes before deciding recovery
    fallback: (userId) => ({ items: [], source: 'circuit-breaker-fallback' }),
  }
);

// The product page can now always return, even when recommendations is down:
async function getProductPage(productId, userId) {
  const [inventory, pricing, reviews, recommendations] = await Promise.allSettled([
    inventoryBreaker.execute(productId),
    pricingBreaker.execute(productId),
    reviewsBreaker.execute(productId),
    recommendationBreaker.execute(userId),  // Fails safely → returns empty list
  ]);

  return {
    inventory: inventory.status === 'fulfilled' ? inventory.value : null,
    pricing: pricing.status === 'fulfilled' ? pricing.value : null,
    reviews: reviews.status === 'fulfilled' ? reviews.value : null,
    recommendations: recommendations.value, // Always has a value (fallback)
  };
}
Pattern 2

Bulkhead Pattern: Resource Pool Isolation

The bulkhead pattern is named after the watertight compartments in a ship's hull. If one compartment is breached, the bulkhead contains the flooding — the rest of the ship survives. In software, the "water" is thread pool capacity, connection pool slots, or memory. Without bulkheads, a single slow dependency can flood the entire shared resource pool.

In the ShopAll outage, the product page service used a single shared thread pool for all five downstream calls. When recommendations blocked all 200 threads, it blocked the thread pool that was also serving inventory, pricing, reviews, and images. A bulkhead would have given recommendations its own isolated pool of 20 threads — and when those 20 were exhausted, calls to recommendations would fail immediately (not block shared threads), while the other 180 threads continued serving inventory, pricing, and reviews normally.

JavaScript — Bulkhead: Concurrency-Limited Executor per Service 
// bulkhead.js
// Limits concurrent calls to a dependency to a fixed pool size.
// When the pool is full, excess calls are rejected immediately (fail fast).

export class Bulkhead {
  /**
   * @param {number} maxConcurrent  - Max simultaneous in-flight calls (pool size)
   * @param {number} maxQueueSize   - Waiting requests allowed (0 = no queue, fail fast)
   */
  constructor(maxConcurrent = 20, maxQueueSize = 10) {
    this._max = maxConcurrent;
    this._maxQueue = maxQueueSize;
    this._active = 0;
    this._queue = [];
  }

  async execute(fn) {
    if (this._active < this._max) {
      return this._run(fn);
    }

    if (this._queue.length >= this._maxQueue) {
      // Bulkhead full — reject immediately
      throw new Error(`Bulkhead FULL: ${this._active} active, ${this._queue.length} queued`);
    }

    // Queue the request — wait for a slot to free up
    return new Promise((resolve, reject) => {
      this._queue.push({ fn, resolve, reject });
    });
  }

  async _run(fn) {
    this._active++;
    try {
      const result = await fn();
      return result;
    } finally {
      this._active--;
      this._drain();
    }
  }

  _drain() {
    if (this._queue.length > 0 && this._active < this._max) {
      const { fn, resolve, reject } = this._queue.shift();
      this._run(fn).then(resolve).catch(reject);
    }
  }

  stats() {
    return { active: this._active, queued: this._queue.length, capacity: this._max };
  }
}

// Per-dependency bulkheads — completely isolated pools:
const bulkheads = {
  recommendations: new Bulkhead(20, 5),  // 20 concurrent, 5 queued
  inventory:       new Bulkhead(80, 20), // 80 concurrent, 20 queued (critical path)
  pricing:         new Bulkhead(60, 15),
  reviews:         new Bulkhead(30, 10),
  images:          new Bulkhead(40, 10),
};

// Combine bulkhead + circuit breaker for full protection:
async function callWithResilience(service, ...args) {
  const bulkhead = bulkheads[service];
  const breaker = circuitBreakers[service];

  return bulkhead.execute(() => breaker.execute(...args));
}

// When recommendations is slow:
// - Recommendations bulkhead fills: 20 active + 5 queued = 25 threads max
// - Excess recommendations calls fail fast with BulkheadFull error
// - Inventory/pricing/reviews bulkheads remain completely unaffected
// - Product page service continues to respond normally (without recommendations)

Netflix production sizing: Netflix's Hystrix (now in maintenance mode, but the reference implementation) defaulted to 10 threads per service bulkhead and a queue size of 5. The rationale: with 10 threads blocked on a slow service, the maximum you can "donate" to that service before it hurts your total pool is approximately 5–10% of capacity. Beyond that, the bulkhead must reject — because the cost of holding more threads hostage outweighs the benefit of allowing more calls through to a failing dependency.

Pattern 3

Timeout Configuration: The Most Dangerous Knob in Distributed Systems

Timeouts are the last line of defense against a slow dependency. They are also the most commonly misconfigured resilience mechanism because the "right" value is non-obvious and context-dependent. A timeout that is too long allows threads to block for extended periods, enabling cascades. A timeout that is too short causes false failures — healthy services start returning errors because their tail latency occasionally exceeds the threshold.

The Timeout Cascade Problem

If Service A calls Service B (timeout 5s), which calls Service C (timeout 5s), which calls Service D (timeout 5s), a request that reaches D takes up to 5 seconds before timing out. C waits 5 seconds for D. B waits 5 seconds for C (after C's timeout fires). A waits 5 seconds for B. Total wall-clock time: 15 seconds. All three services hold threads for this entire duration.

The correct pattern is timeout budgets: each downstream call's timeout is derived from the remaining time budget of the inbound request. If A's SLA is 2 seconds and it has already spent 100ms on auth, B gets a 1.9-second timeout. B passes the remaining budget downstream as a deadline. When the budget is exhausted, all in-progress calls in the chain abort immediately.

JavaScript — Timeout Budgets with Context Propagation 
// timeout-budget.js
// Propagates remaining request deadline through async call chains.
// Every downstream call is bounded by the remaining time, not a fixed constant.

export class RequestContext {
  constructor(deadlineMs) {
    this._deadline = Date.now() + deadlineMs;
  }

  get remaining() { return Math.max(0, this._deadline - Date.now()); }
  get expired() { return this._deadline <= Date.now(); }

  /**
   * Execute fn with a timeout bounded by remaining deadline.
   * @param {Function} fn          - Async function returning a promise
   * @param {number}   minTimeoutMs - Fail immediately if remaining < this
   */
  async withDeadline(fn, minTimeoutMs = 50) {
    if (this.remaining < minTimeoutMs) {
      throw new Error(`RequestContext: budget exhausted (${this.remaining}ms remaining)`);
    }

    const timeoutMs = this.remaining;
    const timer = new Promise((_, reject) =>
      setTimeout(() => reject(new Error(`Timeout: exceeded ${timeoutMs}ms`)), timeoutMs)
    );

    return Promise.race([fn(), timer]);
  }
}

// In the product page handler — 2s total budget:
async function handleProductPageRequest(req, res) {
  const ctx = new RequestContext(2000); // 2 second total budget

  const results = await Promise.allSettled([
    ctx.withDeadline(() => callInventory(req.productId)),     // Uses remaining time
    ctx.withDeadline(() => callPricing(req.productId)),
    ctx.withDeadline(() => callReviews(req.productId)),
    ctx.withDeadline(() => callRecommendations(req.userId), 200), // Need at least 200ms
  ]);

  // Even if one call is slow, others abort as soon as budget is exhausted
  res.json({
    inventory:       results[0].status === 'fulfilled' ? results[0].value : null,
    pricing:         results[1].status === 'fulfilled' ? results[1].value : null,
    reviews:         results[2].status === 'fulfilled' ? results[2].value : null,
    recommendations: results[3].status === 'fulfilled' ? results[3].value : [],
  });
}

// Pass ctx to downstream calls as HTTP header for cross-service deadline propagation:
async function callInventory(productId, ctx) {
  const resp = await fetch(`http://inventory-svc/product/${productId}`, {
    signal: AbortSignal.timeout(ctx.remaining),
    headers: {
      'X-Request-Deadline': String(Date.now() + ctx.remaining), // UNIX ms
    },
  });
  return resp.json();
}

Antipattern

Retry Storms: How Good Intentions Create Cascades

When a service starts returning errors, every client that configured retries will retry. If Service B is handling 10,000 RPS and starts failing, and all callers retry up to 3 times with no backoff, B's inbound request rate jumps from 10,000 to up to 40,000 RPS — exactly when it is least capable of handling traffic. This is a retry storm, and it converts a recoverable overload into an unrecoverable collapse.

Three Rules for Safe Retries

  • Exponential backoff with jitter. Retry delays must grow exponentially (2×, 4×, 8×...) and include random jitter. Without jitter, all clients that hit an error at the same moment will retry at the same moment — synchronized retries reproduce the exact surge that caused the original failure.
  • Retry only idempotent operations. GET, HEAD, PUT, and DELETE with idempotency keys are safe to retry. POST (unless the API uses idempotency keys) is not. Retrying a POST payment request without an idempotency key creates duplicate charges.
  • Honour circuit breaker state before retrying. If a circuit breaker is OPEN for a dependency, do not retry calls to that dependency. The circuit breaker already knows the dependency is failing — retries are just noise. Retry only when the breaker is CLOSED or HALF_OPEN (probe mode).
JavaScript — Exponential Backoff with Jitter and Circuit Breaker Integration 
// resilient-fetch.js
// Retries with exponential backoff + full jitter.
// Respects circuit breaker state — skips retry if breaker is OPEN.

async function resilientFetch(breaker, url, fetchOpts = {}, retryOpts = {}) {
  const {
    maxRetries = 3,
    baseDelayMs = 100,
    maxDelayMs = 5_000,
    retryOn = [429, 500, 502, 503, 504],
  } = retryOpts;

  let attempt = 0;

  while (attempt <= maxRetries) {
    // Check circuit breaker before each attempt
    if (breaker.state === 'OPEN') {
      const fallback = breaker._fallback;
      if (fallback) return fallback(url);
      throw new Error('Service unavailable (circuit open)');
    }

    try {
      const response = await breaker.execute(() =>
        fetch(url, fetchOpts).then(async r => {
          if (!r.ok && retryOn.includes(r.status)) {
            const err = new Error(`HTTP ${r.status}`);
            err.status = r.status;
            err.retryable = true;
            throw err;
          }
          return r.json();
        })
      );
      return response; // Success
    } catch (err) {
      if (!err.retryable || attempt === maxRetries) throw err;

      // Exponential backoff with full jitter:
      // delay = random(0, min(maxDelay, baseDelay * 2^attempt))
      const cap = Math.min(maxDelayMs, baseDelayMs * Math.pow(2, attempt));
      const delay = Math.floor(Math.random() * cap);
      // console.log(`[retry] attempt ${attempt + 1} of ${maxRetries}, waiting ${delay}ms`);
      await new Promise(r => setTimeout(r, delay));
      attempt++;
    }
  }
}
Production Gotchas

Resilience Failure Modes Engineers Miss

  • Circuit breaker counts only errors, not slow successes. A service returning HTTP 200 after 28 seconds (like the ML API in the story) is not counted as a failure by a breaker configured to trip on HTTP errors only. Always include a timeout-based failure counter: if a call exceeds a latency threshold (e.g., 2× p95), count it as a failure for circuit breaker purposes, regardless of HTTP status.
  • Bulkhead queue as a pressure relief valve — not a buffer. A bulkhead queue of 100 items does not help if the service processes 10,000 RPS. The queue fills in 0.01 seconds and begins rejecting. Worse, items sitting in the queue for 5 seconds holding threads are just a slower version of thread pool exhaustion. Keep queue size small (5–20). The goal is fail-fast, not accumulate-and-process.
  • Half-open thundering herd after long outage. When a breaker has been OPEN for 5 minutes and transitions to HALF_OPEN, all callers that have been receiving fallback responses may simultaneously attempt real calls. Without a probe limit, this creates a thundering herd that overwhelms the just-recovering service. Set the half-open probe limit to a small number (5–10) and add randomized probe scheduling across clients.
  • Timeout too long in the wrong layer. Setting a 30-second timeout on a database query that takes 30 seconds means 30 seconds of thread blockage. If your upstream SLA is 2 seconds, the 30-second timeout is meaningless — the upstream has already failed before the timeout fires. Always set timeouts relative to your own SLA, not the dependency's maximum acceptable latency.
  • Testing circuit breakers under load, not under failure. Circuit breakers that work correctly in unit tests can fail under real load because the thread responsible for transitioning state is blocked by the same exhaustion condition that caused the trip. Chaos engineering (Netflix Chaos Monkey pattern) tests breaker behavior under production load, not just synthetic test conditions.
Checklist

Resilience Engineering Checklist

  • Every external HTTP call has an explicit timeout configured (not relying on platform defaults).
  • Timeouts are based on remaining request budget, not fixed constants.
  • Circuit breakers wrap all external service calls; threshold set at 50% failure rate (not 100%).
  • Circuit breakers count slow responses (latency > 2× p95) as failures, not just HTTP errors.
  • Bulkheads isolate thread/connection pools per downstream service.
  • Non-critical services (recommendations, analytics) have explicit fallback values so pages render without them.
  • Retries use exponential backoff with full jitter; maximum retries ≤ 3.
  • Retry logic skips retries when circuit breaker is OPEN.
  • Circuit breaker state is tested under load, not just in unit tests (chaos injection).
  • Half-open probe count is set to a small number (5–10) to prevent thundering herd on recovery.

Key Takeaway

In the ShopAll outage, 11 services went down because of two missing lines of configuration: a 500ms timeout and a circuit breaker threshold. The architectural patterns that would have prevented it — circuit breakers, bulkheads, timeout budgets, and jittered retries — are not complex to implement. They are complex to configure correctly, and they require active testing under load. The rule that a senior architect applies to every new service-to-service call is: assume the dependency will fail, plan the fallback first, and configure isolation so the failure cannot propagate upstream. Non-critical dependencies (recommendations, analytics, A/B testing) must never be able to take down critical paths (checkout, inventory, auth). That boundary is enforced by bulkheads, not by hoping the dependency stays up.
