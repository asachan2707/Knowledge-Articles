Refactoring a Monolith to Microservices: 10-Step Approach

A structured 10-step migration playbook for extracting microservices from a monolith — from domain analysis and database separation to the Strangler Fig pattern, Conway's Law alignment, observability, and managing the migration without downtime. Includes the common failure modes that derail migrations and how to avoid them.

Most monolith-to-microservices migrations fail not because of technical complexity but because of process failures: trying to migrate everything at once, drawing service boundaries before understanding the domain, and underestimating the operational complexity of distributed systems. This 10-step approach addresses those failure modes systematically.

Core idea: Successful migrations are incremental, boundary-first, and observability-first. You extract one service at a time, with a façade that can route traffic back to the monolith on any regression. The migration is "done" only when the monolith has nothing left and the last module has been extracted.

The 10-step playbook
1

Analyse the monolith domain boundaries

Map all modules, their dependencies, and their change frequency. Identify which modules are coupled (change together often) and which are independent (change rarely, have few cross-module calls). Independent modules with low coupling are the first extraction candidates.

2

Define bounded contexts with DDD

Apply Domain-Driven Design to identify bounded contexts — coherent areas of business logic with clear ownership. Each bounded context becomes a candidate service. Draw context maps showing how contexts relate: shared kernel, customer/supplier, anti-corruption layer.

3

Align team structure with Conway's Law

The architecture will eventually match your org structure whether you plan it or not. Restructure teams to own bounded contexts before extracting services. If the team structure doesn't support independent ownership, the extracted services will quickly become tightly coupled again.

4

Set up observability infrastructure first

Deploy distributed tracing (Jaeger/Zipkin), centralized logging (ELK/Loki), and metrics (Prometheus/Grafana) before extracting any service. You cannot debug a distributed system that you can't observe. This is the most commonly skipped step — and the most expensive one to skip.

5

Build the CI/CD pipeline per service

Each extracted service needs its own build, test, and deployment pipeline. Setting this up manually for every service extraction is slow. Templatize it once (GitHub Actions workflow template, Helm chart template) before extracting the first service.

6

Extract the database first (Database per Service)

The hardest part of any microservice extraction is database separation. Before extracting the service code, separate the tables owned by this module into a dedicated schema or database. Use the API gateway or the monolith itself to access the new database during the transition period.

7

Apply the Strangler Fig pattern

Build the new microservice alongside the monolith. A façade (reverse proxy or routing middleware) intercepts requests and routes them to either the legacy monolith or the new service. Start with 0% traffic to the new service; increase gradually as confidence builds. Rollback is immediate — flip the routing switch.

8

Introduce event-driven communication

Replace direct method calls across the new service boundary with event publishing. The monolith publishes events; the new service subscribes. This decouples the service from the monolith's internal state and creates the seam for future extractions.

9

Test at all levels: unit, integration, contract, E2E

Add consumer-driven contract tests (Pact) for every API boundary. Contract tests ensure that the service's API never breaks its consumers — even across independent deployment schedules. Integration tests verify the seam between the new service and the monolith. E2E tests verify the user-facing behaviour hasn't regressed.

10

Decommission the monolith module once migration is complete

Only delete monolith code when the new service has been stable in production for at least 2 weeks with full traffic. Maintain the façade routing until the old code is deleted — it's your rollback mechanism until then.

JavaScript Example

Strangler Fig façade with progressive traffic routing

JavaScript Example 
// Strangler Fig façade: routes traffic to monolith or new microservice
// Percentage of traffic to new service increases over time as confidence builds

class StranglerFacade {
  constructor(monolithUrl, newServiceUrl, config) {
    this.monolith = monolithUrl;
    this.newService = newServiceUrl;
    this._config = config; // reads MIGRATION_ROLLOUT_PERCENT from config store
  }

  async route(req) {
    const rolloutPercent = parseInt(await this._config.get('MIGRATION_ROLLOUT_PERCENT') ?? '0');
    const useNewService = Math.random() * 100 < rolloutPercent;

    const target = useNewService ? this.newService : this.monolith;
    const label = useNewService ? 'new-service' : 'monolith';

    const start = Date.now();
    try {
      const res = await fetch(`${target}${req.url}`, {
        method: req.method,
        headers: {
          ...req.headers,
          'x-routed-to': label,
          'x-trace-id': req.headers['x-trace-id'] || crypto.randomUUID(),
        },
        body: req.body ? JSON.stringify(req.body) : undefined,
      });

      const durationMs = Date.now() - start;
      console.log(JSON.stringify({ label, path: req.url, status: res.status, durationMs }));

      return res;
    } catch (err) {
      if (useNewService) {
        // Automatic fallback: new service failed, retry on monolith
        console.error(`[strangler] new service failed, falling back: ${err.message}`);
        return fetch(`${this.monolith}${req.url}`, {
          method: req.method,
          headers: { ...req.headers, 'x-routed-to': 'monolith-fallback' },
        });
      }
      throw err;
    }
  }
}

// Shadow mode: send to both services, use monolith response
// Used to compare responses before committing to the new service
class ShadowModeFacade {
  constructor(monolithUrl, newServiceUrl) {
    this.monolith = monolithUrl;
    this.newService = newServiceUrl;
  }

  async route(req) {
    // Run both in parallel, use monolith result
    const [primary, shadow] = await Promise.allSettled([
      fetch(`${this.monolith}${req.url}`, { method: req.method }),
      fetch(`${this.newService}${req.url}`, { method: req.method }),
    ]);

    // Log divergence for analysis
    if (primary.status === 'fulfilled' && shadow.status === 'fulfilled') {
      const [primaryBody, shadowBody] = await Promise.all([
        primary.value.json(),
        shadow.value.json(),
      ]);
      if (JSON.stringify(primaryBody) !== JSON.stringify(shadowBody)) {
        console.warn('[shadow] response divergence detected', { url: req.url });
        // Log both responses to a divergence store for analysis
      }
    }

    // Always return the monolith response during shadow mode
    return primary.status === 'fulfilled' ? primary.value : (() => { throw primary.reason; })();
  }
}
Migration anti-patterns to avoid: (1) Big-bang rewrite — trying to replace the monolith in one shot. Always fails. (2) Drawing service boundaries by technical layer ("the database service", "the auth service") instead of by business domain. (3) Skipping observability setup until after the first extraction. (4) Extracting services before separating their databases. (5) Removing the monolith code before 2+ weeks of stable production traffic on the new service.

Key Takeaway

Successful monolith-to-microservices migrations are boundary-first (DDD), team-aligned (Conway's Law), observability-first, and incremental (Strangler Fig). The most critical sequence: align team structure → separate databases → build the CI/CD template → set up observability → extract one service at a time with façade routing. Each extraction should take 2–4 weeks with a rollback path at every stage. The migration is not over until the monolith module is deleted, stable, and decommissioned — not when the new service first receives production traffic.
