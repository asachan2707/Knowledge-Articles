20 Java Backend Interview Questions for Senior Engineers

The questions senior Java backend engineers are actually asked, with architect-level answers. Covers JVM internals, concurrency primitives, Spring Boot production patterns, JPA/Hibernate pitfalls, GC tuning, reactive programming, microservice design, and the "why" behind Java's most misunderstood guarantees.

Domain: Java · Backend · Interview Prep · Senior Level Published: 2026-07-22

Senior Java interviews test not just "does it compile" but "would you bet production on this." The questions below probe the gap between Java knowledge and Java judgment — the difference between knowing what volatile does and knowing when not to use it.

1. What is the Java Memory Model (JMM) and why does it matter for concurrency?

The JMM defines when writes made by one thread are visible to other threads. Without it, the compiler and CPU are free to reorder instructions for performance — meaning a write in Thread A may never be seen by Thread B, or may appear in a different order than written.

Key guarantees: the happens-before relationship. A happens-before B means all writes visible to A are visible to B. Happens-before is established by: synchronized (unlock → lock), volatile writes/reads, Thread.start() / Thread.join(), and java.util.concurrent operations.

Interview signal: Candidates who only say "volatile makes a variable thread-safe" miss the JMM. Correct: volatile establishes happens-before for reads and writes, which prevents some but not all race conditions. volatile does NOT make compound actions (check-then-act, read-modify-write) atomic.

2. What is the difference between synchronized, volatile, and AtomicInteger?

  • synchronized: mutual exclusion + visibility. Only one thread executes the block at a time. Establishes happens-before at exit. Heavier — involves monitor acquisition, context switches under contention.
  • volatile: visibility only. Reads always see the latest write. No mutual exclusion — does NOT prevent race conditions on compound operations (i++ is read-modify-write = 3 operations, not 1).
  • AtomicInteger: atomic compound operations via CAS (Compare-And-Swap). incrementAndGet() is atomic. Implemented with volatile + CPU-level CAS instruction. Non-blocking — no lock acquisition, no context switch.

When to use each: AtomicInteger for counters. volatile for flags/state that are written by one thread and read by many. synchronized for compound operations on multiple variables that must be consistent together.

3. What is the N+1 query problem in Hibernate and how do you fix it?

When you load a list of N entities, and Hibernate issues 1 query for the list + N separate queries for each entity's lazy-loaded association. For 1,000 orders, loading each order's customer generates 1,001 queries instead of 1 join.

Fixes:

  • @EntityGraph or FETCH JOIN in JPQL: eagerly fetch the association in a single query.
  • @BatchSize(size = 100) on the collection: Hibernate batches the lazy-load queries into groups of 100 (reduces 1,000 queries to 10).
  • DTO projections with JPQL: SELECT specific fields instead of full entities — Hibernate never loads the entity graph at all.

Detection: Hibernate statistics or a query-counting DataSource wrapper (like P6Spy or DataSourceProxy). Any screen with query counts in the hundreds = N+1 candidate.

5. What is a ConcurrentModificationException and how do you prevent it?

Thrown when a collection is structurally modified (add/remove) while being iterated by its own iterator. The iterator's modCount check detects this at the next next() call (fail-fast behaviour).

Prevention strategies:

  • Use CopyOnWriteArrayList: iterator sees a snapshot; mutations are safe but expensive for write-heavy cases.
  • Collect removals to a separate list, apply after iteration.
  • Use Iterator.remove() instead of Collection.remove() during iteration — safe because the iterator tracks its own modification.
  • ConcurrentHashMap.forEach vs keySet().iterator() — the former is safe for concurrent structural modification (weakly consistent).

6. What is a ThreadLocal memory leak and when does it happen?

ThreadLocal values are stored in the ThreadLocalMap of the thread itself. In thread-pool environments (Tomcat, Spring), threads are reused — they are never garbage collected between requests. If a ThreadLocal is set during a request but not removed, the value lives for the lifetime of the thread (potentially forever), preventing GC of the stored object.

Fix: Always call threadLocal.remove() in a finally block at the end of the request lifecycle, or use Spring's RequestContextHolder (which manages cleanup automatically).

7. What is Spring's @Transactional and what are its proxy limitations?

@Transactional works via AOP proxy: Spring wraps the bean in a proxy that intercepts the method call, begins the transaction, calls the actual method, and commits or rolls back.

The self-invocation problem: If method A in a bean calls method B in the same bean, and method B is @Transactional, the transaction is NOT applied to B. The call bypasses the proxy entirely — it's a direct this.B() call, not proxy.B().

Other gotchas:

  • Default propagation is REQUIRED: joins existing transaction or starts a new one. REQUIRES_NEW starts a new transaction, suspending the outer one — useful for audit logging that must commit even if the outer TX rolls back.
  • Default rollback is unchecked exceptions only (RuntimeException and Error). Checked exceptions do NOT trigger rollback unless rollbackFor is set.
  • @Transactional on private methods is silently ignored.

8. Explain Project Loom virtual threads. How do they change backend architecture?

Virtual threads (Java 21) are lightweight threads managed by the JVM, not the OS. Creating 1 million virtual threads is cheap — they are not mapped 1:1 to OS threads. When a virtual thread blocks on I/O, the JVM unmounts it from its carrier thread; another virtual thread runs on that carrier. This is structured concurrency via cooperative scheduling.

Backend implications:

  • Thread-per-request models (Spring MVC, JDBC) become viable again at high concurrency. A 10k req/s service no longer needs a reactive programming model to avoid OS thread saturation.
  • Reactive programming (WebFlux, RxJava) advantage narrows — the primary motivation (non-blocking I/O without thread exhaustion) is now addressable with simpler imperative code on virtual threads.
  • synchronized blocks still pin virtual threads to carrier threads (OS threads). Prefer ReentrantLock in code that will run on virtual threads.
  • ThreadLocal memory leak risk is amplified — millions of cheap virtual threads holding ThreadLocals can exhaust heap. Use ScopedValue (Java 21 preview) as the replacement.

9. What are the differences between ConcurrentHashMap and Collections.synchronizedMap()?

  • synchronizedMap: wraps every method in a synchronized block on the map itself. Only one thread can read OR write at any time. Simple but high contention under concurrent reads.
  • ConcurrentHashMap: lock striping (Java 8+: CAS + segment-level synchronization). Reads are lock-free. Writes lock only the affected bucket. Concurrent reads and non-conflicting writes execute in parallel. Higher throughput under contention.

ConcurrentHashMap is weakly consistent: iterators reflect the state at some point during iteration, not necessarily the current state. It does NOT support null keys or values (synchronizedMap inherits from HashMap which does).

10. How would you design a rate limiter in Java?

Token bucket algorithm: a bucket fills at a fixed rate. Each request consumes one token. Requests when the bucket is empty are rejected. Allows short bursts up to bucket capacity. 

// Java rate limiter using Guava's RateLimiter (token bucket)
import com.google.common.util.concurrent.RateLimiter;
import java.util.concurrent.ConcurrentHashMap;

public class PerUserRateLimiter {
    private final ConcurrentHashMap<String, RateLimiter> limiters = new ConcurrentHashMap<>();
    private final double permitsPerSecond;

    public PerUserRateLimiter(double permitsPerSecond) {
        this.permitsPerSecond = permitsPerSecond;
    }

    public boolean tryAcquire(String userId) {
        RateLimiter limiter = limiters.computeIfAbsent(userId,
            k -> RateLimiter.create(permitsPerSecond));
        return limiter.tryAcquire(); // non-blocking — returns false if over limit
    }
}

// Usage in Spring filter
@Component
public class RateLimitFilter extends OncePerRequestFilter {
    private final PerUserRateLimiter limiter = new PerUserRateLimiter(100); // 100 req/s per user

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                     FilterChain chain) throws IOException, ServletException {
        String userId = extractUserId(req);
        if (!limiter.tryAcquire(userId)) {
            res.setStatus(429); // Too Many Requests
            res.getWriter().write("{\"error\": \"Rate limit exceeded\"}");
            return;
        }
        chain.doFilter(req, res);
    }
}

11–20: Quick-Reference Senior Questions

  • 11. What causes a deadlock in Java and how do you detect it? — Two threads each hold a lock the other needs. JVM thread dump shows BLOCKED threads with "waiting to acquire" cycles. Prevention: always acquire locks in a consistent global order; use tryLock(timeout) with fallback.
  • 12. What is the difference between equals() and == for Strings? — == compares references (are these the same object?). equals() compares content. String pool interning means literal Strings may pass == even from different compile units, but new String(...) always creates a new object. Always use equals() for content comparison.
  • 13. What is the difference between Callable and Runnable? — Runnable.run() returns void and cannot throw checked exceptions. Callable.call() returns a value and can throw checked exceptions. Use Callable with ExecutorService.submit() to get a Future for the result.
  • 14. What is a WeakReference and when would you use it? — A reference that does not prevent GC. If the referent has no strong references, it can be collected even if WeakReferences exist. Used in caches (WeakHashMap) where entries should expire when the key is no longer referenced elsewhere.
  • 15. What is Spring Boot's auto-configuration mechanism? — @SpringBootApplication includes @EnableAutoConfiguration, which uses spring.factories (or AutoConfiguration.imports in Boot 3) to load auto-configuration classes. Each class is annotated with @Conditional — it activates only when specified classes are on the classpath, beans are absent, etc. You can exclude auto-configs with exclude on the annotation.
  • 16. Explain Java's CompletableFuture composition. — thenApply (transform result synchronously), thenCompose (chain async operations, flatten futures), thenCombine (combine two independent futures), allOf / anyOf (wait for many). Run on common pool by default; pass a custom Executor for I/O-bound chains.
  • 17. What is the difference between @Component, @Service, @Repository, and @Controller? — All are specialisations of @Component; they are semantically equivalent for component scanning but carry different semantic meaning. @Repository also enables Spring's exception translation (SQL exceptions → DataAccessException hierarchy). @Controller enables Spring MVC request mapping.
  • 18. What is connection pool exhaustion and how do you diagnose it? — All connections in HikariCP pool are in use; new requests wait or fail with "Unable to acquire connection within XXXms." Diagnosis: HikariCP JMX metrics (HikariPool-1.pool.TotalConnections, ActiveConnections). Causes: long-running queries holding connections, N+1 queries, missing finally block for connection release, slow downstream (the DB is backed up).
  • 19. When would you use WebFlux vs Spring MVC? — WebFlux is non-blocking; the same thread handles multiple in-flight requests via event loop. Optimal for I/O-bound workloads with high concurrency (API gateways, streaming). Spring MVC + virtual threads (Java 21) closes much of the performance gap. WebFlux is harder to debug (stack traces are non-linear); prefer MVC + virtual threads unless reactive composition across multiple async sources is a core requirement.
  • 20. What is the Open Session in View anti-pattern? — Spring's default OSIV keeps the Hibernate session open across the full HTTP request including the view rendering layer. This means lazy-loaded associations can be accessed in Thymeleaf/JSP templates without triggering LazyInitializationException — but it also means unbounded queries can fire during view rendering, making it impossible to reason about query counts. Production recommendation: disable OSIV (spring.jpa.open-in-view=false) and use eager loading or DTO projections explicitly.
Bonus — 3 Questions That Expose Fake Senior Developers

3 Java Interview Questions That Expose 90% of "Senior Developers"

The questions above test backend engineering depth. The three below target a different failure mode: developers who know Spring Boot cold but have never confronted the JVM's own surprises. Framework expertise conceals language-level blind spots until production.

Q1: What does this print, and why?

Integer a = 127;
Integer b = 127;
System.out.println(a == b);  // true or false?

Integer c = 128;
Integer d = 128;
System.out.println(c == d);  // true or false?

Answer: a == b prints true; c == d prints false.

Why: Java's autoboxing calls Integer.valueOf(int), which caches instances for values in the range -128 to 127 (inclusive) in a static array. Integer.valueOf(127) returns the same cached object every time — so a and b point to the same reference, and == returns true. For 128, no cached instance exists; valueOf(128) allocates two new objects, so c and d are different references — == is false.

Why this exposes fake seniors: Real senior engineers know that == on boxed primitives is a reference comparison, not a value comparison, and that the cache boundary at 127 is a JLS-mandated constant, not an implementation detail. The fix is always equals(). The production failure this causes: comparisons inside if (userId == expectedId) work in tests (small IDs ≤ 127) but silently fail in production (large IDs).

Q2: This code adds an object to a HashMap, then can't find it. Why?

import java.util.*;

class User {
    int id;
    String name;

    User(int id, String name) { this.id = id; this.name = name; }

    @Override
    public boolean equals(Object o) {
        if (!(o instanceof User u)) return false;
        return id == u.id && name.equals(u.name);
    }
    // hashCode() is NOT overridden
}

public class Demo {
    public static void main(String[] args) {
        Map<User, String> roles = new HashMap<>();
        User u = new User(1, "alice");
        roles.put(u, "admin");

        User lookup = new User(1, "alice");
        System.out.println(roles.get(lookup)); // prints null — why?
    }
}

Answer: roles.get(lookup) returns null even though u.equals(lookup) is true.

Why: HashMap locates a bucket using hashCode() first, then checks equality. User inherits Object.hashCode(), which is based on object identity (memory address). u and lookup are different objects, so they have different hash codes, land in different buckets, and get() never even reaches the equals() check.

The contract: If a.equals(b), then a.hashCode() == b.hashCode() must hold. Violating this contract produces silent data loss — not an exception — making it one of the hardest production bugs to trace. Fix: override hashCode() consistently with equals() (use Objects.hash(id, name)).

Q3: What does this code print? (Static initializer ordering)

public class Config {
    static final int MAX = compute();
    static final int BASE = 10;

    static int compute() {
        return BASE * 2;  // BASE is not yet initialized — what is its value here?
    }

    public static void main(String[] args) {
        System.out.println(Config.MAX);  // prints 0 or 20?
    }
}

Answer: Prints 0, not 20.

Why: Static fields are initialized in source declaration order. When MAX = compute() runs, BASE has not yet been assigned its value — it is still at its default value for int, which is 0. So compute() returns 0 * 2 = 0, and MAX is permanently set to 0. Swapping the declaration order (BASE declared before MAX) fixes the problem.

Why this matters in production: The class loads successfully with no exception or warning. Config values silently take wrong defaults. This pattern typically surfaces when a configuration class initializes a cache size or timeout using a computed constant — everything works in unit tests (which may set the constants explicitly) but behaves incorrectly in integration builds.

Pattern: A true senior engineer knows these three failure modes cold — autoboxing cache boundary, equals/hashCode contract, and static initializer ordering — because they have either been burnt by one or spent time reading the JLS. Framework mastery cannot substitute for this foundational knowledge.

Key Takeaway

Senior Java interviews are distinguished by depth over breadth. The questions above test whether a candidate understands the JMM, JVM GC internals, Hibernate session lifecycle, and Spring's AOP proxy model — not whether they can recite API signatures. The expected answer to every question above includes at least one: a concrete failure scenario, a production decision heuristic, or a specific flag/metric that makes the concept observable. The three bonus questions at the end cut even deeper — they target the JVM language contract that Spring cannot hide: autoboxing equality, equals/hashCode, and static initialization order. Get all three right and you have earned the "senior" label at the JVM level.
