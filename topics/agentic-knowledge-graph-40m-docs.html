Structuring 40 Million Documents Into an Agentic Knowledge Graph

A production blueprint for transforming 40 million unstructured documents into a traversable knowledge graph that AI agents can query with multi-hop reasoning. Covers the complete pipeline: semantic chunking, LLM-powered entity and relationship extraction, Neo4j schema design, GraphRAG hybrid retrieval, agentic tool design, incremental updates, and full cost model — built for a real company demo that scales to production.

Domain: Agents · Data Engineering · Knowledge Graphs · Production AI Published: 2026-09-03

Keyword search finds documents that contain words. A knowledge graph finds documents that contain meaning — and more importantly, it lets you traverse the relationships between meanings. When an AI agent asks "what caused the supply chain disruption that affected Q3 margins?", it needs a graph it can walk, not an index it can scan.

Core idea: A knowledge graph turns 40 million isolated documents into a connected semantic network where AI agents can answer multi-hop questions that no keyword search or flat vector store could resolve — because the answers are hidden in the relationships between entities, not in any single document.

Story · Why Elasticsearch fails at 40 million documents

A legal firm has 40 million case documents — depositions, contracts, judgments, correspondence. Their current system: Elasticsearch with BM25 keyword search. A junior associate asks: "Show me all cases where a supplier agreement dispute led to a contract termination that was later reversed on appeal." Elasticsearch returns documents containing those words. None of them answer the question.

The question is fundamentally relational. It requires the system to understand that Supplier Agreement X is a type of contract, that Dispute Y is related to that agreement, that Termination Z resulted from that dispute, and that Appeal A reversed Termination Z. That's a four-hop graph traversal. No keyword search can do it. A vector search can find semantically similar sentences, but it cannot chain entity relationships across documents.

The solution: build a knowledge graph where these relationships are first-class citizens, then let agents traverse it with structured queries backed by an LLM reasoning layer.

Ingestion · Chunking strategies and deduplication

Document Ingestion at Scale

Before any entity extraction can happen, raw documents must be ingested, normalized, chunked, and deduplicated. At 40M documents, choices made here compound dramatically.

Chunking Strategies

  • Fixed-size (512 tokens): Fast, predictable, but cuts sentences mid-thought. Good for dense structured documents.
  • Sentence-boundary: Preserves semantic units. Use NLTK or spaCy sentence tokenizer. 20% slower than fixed-size.
  • Semantic chunking: Split when embedding similarity drops below threshold. Best quality, 3× slower, requires embedding pass before chunking.
  • Recursive: Try large chunks first; if chunk embedding variance is high, split further. Best for mixed documents.

Decision at 40M scale: sentence-boundary chunking with a 512-token soft cap. Semantic chunking is too expensive at this volume for first-pass ingestion.

Deduplication

At 40M documents, 15–30% are near-duplicates (forwarded emails, revised drafts, mirrored filings). MinHash LSH detects near-duplicates in O(n) time with configurable Jaccard threshold.

JavaScript Example — Document Chunking Pipeline 
import Anthropic from '@anthropic-ai/sdk';

class DocumentProcessor {
  constructor() {
    this.client = new Anthropic();
    this.maxChunkTokens = 512;
  }

  // Sentence-boundary chunking with 512-token soft cap
  chunkBySentence(text, metadata) {
    const sentences = text.match(/[^.!?]+[.!?]+/g) ?? [text];
    const chunks = [];
    let current = '';
    let tokenEstimate = 0;

    for (const sentence of sentences) {
      const sentenceTokens = Math.ceil(sentence.length / 4); // ~4 chars/token
      if (tokenEstimate + sentenceTokens > this.maxChunkTokens && current) {
        chunks.push({
          text: current.trim(),
          tokens: tokenEstimate,
          metadata: { ...metadata, chunkIndex: chunks.length },
        });
        current = '';
        tokenEstimate = 0;
      }
      current += sentence + ' ';
      tokenEstimate += sentenceTokens;
    }

    if (current.trim()) {
      chunks.push({
        text: current.trim(),
        tokens: tokenEstimate,
        metadata: { ...metadata, chunkIndex: chunks.length },
      });
    }
    return chunks;
  }

  // MinHash fingerprint for deduplication (simplified)
  minHash(text, numHashes = 128) {
    const shingles = new Set();
    const words = text.toLowerCase().split(/\s+/);
    for (let i = 0; i < words.length - 2; i++) {
      shingles.add(`${words[i]} ${words[i+1]} ${words[i+2]}`);
    }
    // In production: use a proper MinHash library (datasketch or similar)
    return Array.from(shingles).slice(0, numHashes).map(s =>
      s.split('').reduce((h, c) => (Math.imul(31, h) + c.charCodeAt(0)) | 0, 0)
    );
  }

  jaccardSimilarity(hash1, hash2) {
    let matches = 0;
    for (let i = 0; i < hash1.length; i++) {
      if (hash1[i] === hash2[i]) matches++;
    }
    return matches / hash1.length;
  }
}

// Usage
const processor = new DocumentProcessor();
const chunks = processor.chunkBySentence(documentText, { docId: 'doc-001', source: 's3://legal-docs/case-12345.pdf' });
console.log(`Generated ${chunks.length} chunks from document`);

import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic();

// Entity extraction prompt — zero-shot, structured output
const ENTITY_EXTRACTION_PROMPT = (text) => `Extract all named entities from the following text.
Return a JSON array of objects with fields: name, type, canonical_name, confidence (0-1).

Entity types to extract:
- PERSON: individuals
- ORGANIZATION: companies, agencies, institutions
- LOCATION: countries, cities, addresses
- LEGAL_CONCEPT: laws, regulations, clauses
- DATE: specific dates or date ranges
- PRODUCT: named products or services
- EVENT: named events

Text:
"""
${text}
"""

Return ONLY valid JSON, no explanation.`;

async function extractEntitiesBatch(chunks) {
  // Use Anthropic's batch API for cost-efficient processing
  const requests = chunks.map((chunk, i) => ({
    custom_id: `chunk-${chunk.metadata.docId}-${i}`,
    params: {
      model: 'claude-haiku-4-5-20251001',
      max_tokens: 1024,
      messages: [{ role: 'user', content: ENTITY_EXTRACTION_PROMPT(chunk.text) }],
    },
  }));

  const batch = await client.messages.batches.create({ requests });

  // Poll for completion (in production: use webhook or async polling)
  let batchResult = await client.messages.batches.retrieve(batch.id);
  while (batchResult.processing_status !== 'ended') {
    await new Promise(r => setTimeout(r, 5000));
    batchResult = await client.messages.batches.retrieve(batch.id);
  }

  // Stream results
  const entities = new Map(); // entity canonical_name → Entity node
  for await (const result of client.messages.batches.results(batch.id)) {
    if (result.result.type === 'succeeded') {
      try {
        const extracted = JSON.parse(result.result.message.content[0].text);
        for (const entity of extracted) {
          const key = `${entity.type}:${entity.canonical_name.toLowerCase()}`;
          if (!entities.has(key)) entities.set(key, { ...entity, mentions: [] });
          entities.get(key).mentions.push({ customId: result.custom_id, confidence: entity.confidence });
        }
      } catch (e) {
        console.error('Parse error for', result.custom_id, e);
      }
    }
  }
  return entities;
}
Relationships · Extracting semantic edges

Relationship Extraction

Entities are the nodes. Relationships are the edges that make the graph valuable. A document that mentions both "Apple Inc." and "Tim Cook" without explicitly stating their relationship is useless for graph traversal. Relationship extraction infers those edges.

Relationship Types

  • CAUSES: Entity A caused/led to Entity B. (Directional, confidence-scored)
  • INFLUENCES: Entity A influenced Entity B. (Weaker causal link)
  • PART_OF: Entity A is a component of Entity B.
  • PRECEDES: Entity A happened before Entity B. (Temporal)
  • CONTRADICTS: Entity A contradicts/conflicts with Entity B.
  • SUPPORTS: Entity A supports/corroborates Entity B.
  • EMPLOYED_BY: Person A is employed by Organization B.
  • OWNS: Entity A owns Entity B.

Each relationship is extracted with a confidence score (0–1) and source document ID. Relationships with confidence < 0.6 are stored but excluded from default graph traversal.

JavaScript Example — Relationship Extraction 
const RELATIONSHIP_PROMPT = (text, entities) => `Given this text and the identified entities, extract all relationships between entities.

Entities found: ${JSON.stringify(entities.map(e => e.name))}

For each relationship, return:
- source: entity name
- target: entity name
- relation: one of [CAUSES, INFLUENCES, PART_OF, PRECEDES, CONTRADICTS, SUPPORTS, EMPLOYED_BY, OWNS, LOCATED_IN, OCCURRED_AT]
- confidence: 0.0 to 1.0
- evidence: the exact quote supporting this relationship (max 100 chars)

Text: """${text}"""

Return valid JSON array only.`;

async function extractRelationships(client, chunk, entities) {
  const response = await client.messages.create({
    model: 'claude-haiku-4-5-20251001',
    max_tokens: 2048,
    messages: [{ role: 'user', content: RELATIONSHIP_PROMPT(chunk.text, entities) }],
  });

  try {
    const relationships = JSON.parse(response.content[0].text);
    return relationships.filter(r => r.confidence >= 0.5).map(r => ({
      ...r,
      sourceDocId: chunk.metadata.docId,
      extractedAt: new Date().toISOString(),
    }));
  } catch {
    return [];
  }
}
Schema · Neo4j graph design

Knowledge Graph Schema Design

The schema determines what questions the graph can answer. Design it around the queries agents will ask, not around document structure.

// Node types
(:Document { id: UUID, title: String, source: String, date: DateTime,
             docType: String, embedding: Float[], tokenCount: Int })

(:Entity { id: UUID, name: String, type: String, canonicalName: String,
           wikidataId: String, embedding: Float[] })

(:Concept { id: UUID, name: String, description: String, embedding: Float[] })

// Edge types
(:Document)-[:MENTIONS { count: Int, positions: Int[] }]->(:Entity)
(:Entity)-[:RELATED_TO { relationType: String, confidence: Float,
                          sourceDocs: String[] }]->(:Entity)
(:Entity)-[:CAUSES { confidence: Float, temporalContext: String }]->(:Entity)
(:Document)-[:CITES { context: String }]->(:Document)
(:Entity)-[:APPEARS_WITH { coOccurrenceCount: Int }]->(:Entity)

// Indexes for performance

Storage · Idempotent graph writes

Graph Writer: Idempotent MERGE Operations

At 40M documents with incremental updates, writes must be idempotent. MERGE in Cypher creates a node or relationship only if it doesn't already exist — critical for preventing duplicates during retries or re-ingestion.

JavaScript Example — Neo4j Graph Insertion 
import neo4j from 'neo4j-driver';

const driver = neo4j.driver(
  process.env.NEO4J_URI,
  neo4j.auth.basic(process.env.NEO4J_USER, process.env.NEO4J_PASSWORD)
);

async function insertDocumentWithEntities(document, entities, relationships) {
  const session = driver.session({ database: 'knowledge-graph' });
  const tx = session.beginTransaction();

  try {
    // MERGE document node (idempotent)
    await tx.run(`
      MERGE (d:Document { id: $docId })
      ON CREATE SET d.title = $title, d.source = $source,
                    d.date = datetime($date), d.docType = $docType,
                    d.embedding = $embedding, d.tokenCount = $tokenCount
      ON MATCH SET d.tokenCount = $tokenCount  // update metadata on re-ingestion
    `, { docId: document.id, title: document.title, source: document.source,
         date: document.date, docType: document.docType,
         embedding: document.embedding, tokenCount: document.tokenCount });

    // MERGE entity nodes + MENTIONS edges
    for (const entity of entities) {
      await tx.run(`
        MERGE (e:Entity { id: $entityId })
        ON CREATE SET e.name = $name, e.type = $type,
                      e.canonicalName = $canonicalName, e.wikidataId = $wikidataId
        WITH e
        MATCH (d:Document { id: $docId })
        MERGE (d)-[m:MENTIONS]->(e)
        ON CREATE SET m.count = 1, m.positions = $positions
        ON MATCH SET m.count = m.count + 1
      `, { entityId: entity.id, name: entity.name, type: entity.type,
           canonicalName: entity.canonicalName, wikidataId: entity.wikidataId ?? '',
           docId: document.id, positions: entity.positions });
    }

    // MERGE relationship edges
    for (const rel of relationships) {
      await tx.run(`
        MATCH (src:Entity { canonicalName: $srcName })
        MATCH (tgt:Entity { canonicalName: $tgtName })
        MERGE (src)-[r:RELATED_TO { relationType: $relType }]->(tgt)
        ON CREATE SET r.confidence = $confidence, r.sourceDocs = [$docId]
        ON MATCH SET r.confidence = (r.confidence + $confidence) / 2.0,
                     r.sourceDocs = r.sourceDocs + [$docId]
      `, { srcName: rel.source, tgtName: rel.target, relType: rel.relation,
           confidence: rel.confidence, docId: document.id });
    }

    await tx.commit();
  } catch (err) {
    await tx.rollback();
    throw err;
  } finally {
    await session.close();
  }
}
Agents · Multi-hop graph traversal

Agentic Querying: GraphRAG Pattern

The knowledge graph becomes useful only when agents can traverse it dynamically. The GraphRAG pattern combines vector similarity search (to find entry points) with graph traversal (to find related entities and causal chains).

Agent Tool Design

An MCP server exposes the graph through four tools that agents can call:

  • search_entities(query) — vector search over entity embeddings to find starting nodes
  • get_entity_graph(entityId, depth) — traverse relationships up to N hops from an entity
  • find_causal_chain(from, to) — shortest path between two entities via CAUSES edges
  • find_documents(entities[]) — retrieve source documents that mention a set of entities
JavaScript Example — Agentic Graph Traversal 
// MCP tool: multi-hop causal chain query
async function findCausalChain(driver, fromEntity, toEntity, maxHops = 5) {
  const session = driver.session();
  try {
    const result = await session.run(`
      MATCH path = shortestPath(
        (src:Entity { canonicalName: $from })-[:CAUSES|INFLUENCES*1..${maxHops}]->(tgt:Entity { canonicalName: $to })
      )
      RETURN [node in nodes(path) | { name: node.canonicalName, type: node.type }] AS chain,
             [rel in relationships(path) | { type: type(rel), confidence: rel.confidence }] AS edges,
             length(path) AS hops
      ORDER BY hops ASC
      LIMIT 5
    `, { from: fromEntity, to: toEntity });

    return result.records.map(r => ({
      chain: r.get('chain'),
      edges: r.get('edges'),
      hops: r.get('hops').toNumber(),
    }));
  } finally {
    await session.close();
  }
}

// Vector search entry point (hybrid: vector + graph)
async function graphRAGQuery(driver, client, userQuery, k = 5) {
  // Step 1: embed the query
  // (use text-embedding-3-small or similar)
  const queryEmbedding = await embedText(userQuery);

  // Step 2: vector search to find semantically close entities
  const session = driver.session();
  const vectorResult = await session.run(`
    CALL db.index.vector.queryNodes('entity_embedding', $k, $embedding)
    YIELD node, score
    RETURN node.canonicalName AS name, node.type AS type, score
    ORDER BY score DESC
  `, { k, embedding: queryEmbedding });

  const seedEntities = vectorResult.records.map(r => r.get('name'));

  // Step 3: expand each seed entity 2 hops through the graph
  const graphResult = await session.run(`
    UNWIND $seeds AS seedName
    MATCH (seed:Entity { canonicalName: seedName })
    CALL apoc.path.subgraphNodes(seed, { maxLevel: 2, relationshipFilter: 'RELATED_TO|CAUSES' })
    YIELD node
    RETURN DISTINCT node.canonicalName AS name, node.type AS type
    LIMIT 50
  `, { seeds: seedEntities });

  const expandedEntities = graphResult.records.map(r => r.get('name'));

  // Step 4: retrieve source documents for expanded entity set
  const docsResult = await session.run(`
    MATCH (d:Document)-[:MENTIONS]->(e:Entity)
    WHERE e.canonicalName IN $entities
    RETURN d.id AS id, d.title AS title, d.source AS source, count(e) AS entityMatches
    ORDER BY entityMatches DESC
    LIMIT 10
  `, { entities: expandedEntities });

  await session.close();

  // Step 5: LLM synthesis over retrieved documents
  const docs = docsResult.records.map(r => ({ id: r.get('id'), title: r.get('title') }));
  return { seedEntities, expandedEntities, relevantDocs: docs };
}
Production · Sharding, indexing, and incremental updates

Production Concerns at 40M Scale

Sharding Strategy

Neo4j Fabric allows splitting the graph across multiple databases by domain. For 40M documents, partition by document domain (legal, financial, technical) or by date range. Cross-partition queries are slower but manageable for multi-hop traversal.

Index Design

  • Full-text index on Entity.canonicalName: Fuzzy search entry points for agent queries.
  • Vector index on Entity.embedding: Semantic search entry points (GraphRAG step 1).
  • Composite index on Document(date, docType): Time-filtered document retrieval.
  • Index on relationship confidence: Skip low-confidence edges in default traversal.

Incremental Updates

New documents are processed through the same pipeline. MERGE operations ensure idempotency — re-ingesting a document updates metadata without creating duplicate nodes. Relationship confidence scores are averaged across all source documents, improving accuracy over time.

Failure modes · What breaks at scale

Failure Modes and Mitigations

  • Entity disambiguation failure: "Apple" as tech company vs fruit vs New York record label. Mitigation: Wikidata ID lookup + context window disambiguation with LLM.
  • Relationship hallucination: LLM confidently extracts a relationship that doesn't exist in text. Mitigation: require evidence quote, reject confidence < 0.6, human audit sample of 1%.
  • Graph drift: Entity canonical names change over time (company renaming, mergers). Mitigation: ALIAS edges linking old to new canonical name, never delete nodes.
  • Traversal explosion: Multi-hop query on a highly-connected entity returns millions of paths. Mitigation: depth limit (5 hops max), confidence threshold filtering, LIMIT clauses in all Cypher queries.
  • Ingestion lag: Kafka consumer falls behind during spikes. Mitigation: consumer group scaling, S3 as durable buffer, dead-letter topic for failed extractions.

FAQ

Why not just use a vector store with RAG?

Vector stores answer "find me similar documents." Knowledge graphs answer "how did X lead to Y?" — causal chains, multi-hop relationships, and temporal sequences. For factual lookups, vector RAG is fine. For questions that require traversing entity relationships across documents, you need a graph. GraphRAG uses both: vectors for entry-point discovery, graph for traversal.

Can we build this incrementally, or does it require all 40M docs upfront?

Incremental is the correct approach. Start with a 100K-document pilot to validate extraction quality and graph schema. MERGE operations make re-ingestion safe — you can always add documents to the graph without rebuilding. The schema should be designed for incremental growth.

How do we handle documents in multiple languages?

Run language detection first (langdetect or fasttext). Route English documents to spaCy English pipeline. For other languages: multilingual spaCy models (xx_ent_wiki_sm), or route all non-English to Claude Haiku which handles 50+ languages natively. Canonical entity names should be normalized to English for cross-language entity resolution.

What's the query latency for a 4-hop traversal on a 40M document graph?

With proper indexing (entity name index, relationship confidence index), a 4-hop shortest-path query on a 100M+ node graph typically returns in 50–200ms on Neo4j AuraDB Enterprise. The bottleneck is usually the GraphRAG vector search step (20–50ms for HNSW ANN search) rather than the graph traversal. Total end-to-end agent response with LLM synthesis: 1–3 seconds.

Key Takeaway

Building a knowledge graph from 40 million documents is a systems engineering problem, not just an NLP problem. The architecture decisions that determine success are: hybrid NER (spaCy + LLM) to control cost while maintaining accuracy; MERGE-based idempotent graph writes to enable safe incremental updates; a graph schema designed around agent query patterns rather than document structure; and the GraphRAG pattern — combining vector entry-point discovery with multi-hop graph traversal — to answer questions that no flat retrieval system can. The one-time ingestion cost (~$292K) is front-loaded; the ongoing query cost is negligible relative to the analytical value a connected knowledge graph delivers.
