Event-Driven Architecture: The Complete Guide to Building Loosely Coupled Distributed Systems

When EDA is right, how it works, all the patterns you need to build resilient async systems. Full deep dive: domain events vs integration events, Kafka vs RabbitMQ vs SQS, delivery guarantees, dead letter queues, choreography vs orchestration, schema evolution, CQRS integration, and a complete Node.js example wiring it all together.

Domain: Architecture · Distributed Systems · Async Messaging Published: 2026-07-29

Most distributed system failures are not caused by complex algorithms or bad data structures. They are caused by one service calling another service synchronously — and that other service being unavailable. Event-driven architecture breaks this chain. Services emit facts into a broker; downstream systems react in their own time, at their own pace, with no direct knowledge of who produced the event. The producer and consumer are decoupled in time, space, and implementation.

When EDA is clearly the right choice: you have multiple services that need to react to the same business event, you need to process high-throughput streams asynchronously, or you want to add new consumers without modifying the producer. If you have one caller and one callee and you need an immediate response, a synchronous REST call is still the right tool.

Story · The checkout service that brought down four teams

The checkout service called Payment, then Inventory, then Notification, then Shipping — all synchronously, one after the other. When the Payment service went down during a flash sale, checkout returned 500 errors immediately. Three other services — Inventory, Notification, and Shipping — were perfectly healthy but completely idle. Zero throughput. Every engineer in those three teams was staring at dashboards with nothing to fix.

The on-call rotation escalated through four teams. Checkout was down not because checkout had a bug, but because it depended synchronously on Payment, which had a deployment issue in one of its own dependencies. The blast radius of a single service's failure extended across the entire order flow. Recovery took 40 minutes of coordinated rollback. With EDA, checkout would have published an OrderPlaced event and returned success to the user. Payment would process that event when it recovered. The user experience degrades gracefully; the other services are never affected.

What Makes EDA Different

In synchronous request/response, the caller blocks until the callee responds. The caller knows the callee's address, knows what it will do, and depends on it being available. Coupling is bidirectional and temporal — both services must be up at the same time.

In event-driven architecture, the producer publishes an event to a broker and moves on. The producer has no knowledge of who consumes the event, how many consumers there are, or when they will process it. Adding a new consumer requires zero changes to the producer. Removing a consumer requires zero changes to the producer. The coupling is unidirectional and atemporal.

Events are immutable facts stated in the past tense. They describe something that already happened: OrderPlaced, PaymentProcessed, InventoryReserved. They are not instructions. This is the key conceptual distinction from commands.

Commands vs Events: A command is an instruction directed at a specific service — PlaceOrder, ChargeCard. It implies intent and expects a response. An event is a broadcast fact — OrderPlaced, CardCharged. It implies nothing about what should happen next; that is the consumer's concern. Commands have one handler. Events can have zero, one, or many handlers.

Event Types

Not all events are the same. Understanding the four types prevents you from designing systems that are technically event-driven but practically still tightly coupled.

1. Domain Events

Events that are meaningful within a single bounded context. SeatHeld, CartItemAdded, PasswordResetRequested. These events drive internal state transitions within one service or one team's domain. They are typically not published outside the bounded context — they are internal choreography tools.

2. Integration Events

Events published across service or team boundaries. OrderPlaced, UserRegistered, PaymentProcessed. These are the events that flow through your message broker. Because they cross team boundaries, their schema is a public API contract and must be versioned carefully. Schema changes require backward compatibility or a migration plan.

3. Event Notifications

Lightweight events that carry minimal payload — just enough for the consumer to know something happened and where to fetch the current state. Example: { "type": "UserUpdated", "userId": "u-123" }. The consumer calls back to the User service to retrieve the full user record. Payload is tiny; network overhead is low. The tradeoff: consumers need to make a follow-up read call, which reintroduces some synchronous coupling.

4. Event-Carried State Transfer

Events that carry the full state snapshot, so consumers never need to call back. Example: { "type": "UserUpdated", "userId": "u-123", "email": "...", "name": "...", "plan": "pro" }. Consumers are fully autonomous. The tradeoff: events are larger, and consumers may hold stale data if they miss events or fall behind. Requires robust replay and reconciliation.

Message Brokers: Kafka vs RabbitMQ vs SQS

The broker is the backbone of any EDA system. The choice of broker shapes your delivery guarantees, throughput ceiling, operational burden, and replay capabilities.

Feature Apache Kafka RabbitMQ AWS SQS / SNS
Model Distributed log; consumers pull from offset Message queue; broker pushes to consumers Managed queue (SQS) + pub/sub (SNS)
Throughput Millions of messages/sec per partition Tens of thousands/sec per queue Unlimited (managed); SQS scales automatically
Replay Yes — re-read from any offset, indefinitely No — messages deleted after ack No — messages deleted after ack (14-day retention max)
Routing Topic partitioning; consumer groups Rich exchanges: direct, fanout, topic, headers SNS topic fanout to multiple SQS queues
Ordering Guaranteed within a partition Per-queue with single consumer FIFO queues guarantee ordering; standard queues do not
Latency Low (5–15 ms) but higher than RabbitMQ Very low (sub-millisecond) Low (single-digit ms); FIFO queues slightly higher
Operations Complex; requires ZooKeeper/KRaft, tuning Moderate; single cluster, AMQP Zero; fully managed by AWS
Best for Event log, audit trail, stream processing, replay Work queues, complex routing, low-latency tasks AWS-native stacks, serverless, minimal ops burden

Rule of thumb: If you need to replay events (audit, backfill, reprocess after a bug fix), use Kafka. If you need complex routing logic with very low latency and do not need replay, use RabbitMQ. If you are on AWS and want zero operational overhead, use SQS/SNS. These are not mutually exclusive in large systems — many production architectures use all three for different purposes.

Delivery Guarantees

Every message broker makes one of three delivery promises. Understanding which guarantee your broker provides — and what it means for your consumer — is critical before you write a single handler.

At-Most-Once

The broker delivers the message once and does not retry if the consumer fails or the message is lost. The message may be lost. Zero duplicates, but potential data loss. Used only where loss is acceptable: metrics aggregation, ephemeral notifications, fire-and-forget logging.

At-Least-Once

The broker retries delivery until the consumer acknowledges. The message will be delivered, but may be delivered more than once (network timeout after processing but before ack, consumer restart mid-processing). This is the default for Kafka, RabbitMQ, and SQS. Your consumer must be idempotent — processing the same event twice must produce the same result as processing it once.

Exactly-Once

Kafka 0.11+ supports exactly-once semantics (EOS) within a Kafka-to-Kafka pipeline using transactions. In practice, exactly-once across a Kafka consumer that writes to an external database is very hard to guarantee — the Kafka offset commit and the database write cannot participate in the same atomic transaction without significant engineering overhead. Most teams do not implement true exactly-once end-to-end.

The pragmatic production choice: at-least-once + idempotent consumers. Design every consumer so that receiving the same event twice has no side effects. Store processed event IDs in a deduplication table; check before processing. This is simpler to implement and reason about than true exactly-once, and it is what the vast majority of production EDA systems use.

JavaScript Example — Idempotent Consumer with Deduplication 
// idempotent-consumer.js
async function handleOrderPlaced(event) {
  const { eventId, orderId, userId, total } = event;

  // Check if we've already processed this event
  const alreadyProcessed = await db.query(
    `SELECT 1 FROM processed_events WHERE event_id = $1`,
    [eventId]
  );
  if (alreadyProcessed.rows.length > 0) {
    console.log(`[dedup] Event ${eventId} already processed — skipping`);
    return; // safe to ack and move on
  }

  // Process within a transaction that also records the event ID
  await db.transaction(async (trx) => {
    await chargeCard(userId, total, { trx });
    await trx.query(
      `INSERT INTO processed_events (event_id, processed_at) VALUES ($1, NOW())`,
      [eventId]
    );
  });
}

Dead Letter Queues

A dead letter queue (DLQ) is where messages go when they cannot be processed successfully after a configured number of retries. Every production EDA system must have DLQs configured for every consumer. Without them, failed messages silently vanish.

What ends up in a DLQ

  • Messages with malformed or unexpected schema (upstream deployed a breaking change)
  • Messages that cause unhandled exceptions in the consumer (bug in handler code)
  • Messages that depend on external state that does not exist (foreign key violation, referenced entity deleted)
  • Messages that exceed the max retry count due to transient downstream failures

Monitoring DLQ depth

DLQ depth is one of the most important operational metrics in an EDA system. A rising DLQ depth means events are not being processed — business logic is silently not executing. Set an alert at depth > 0 for critical queues (payment events, order events). For lower-priority queues, alert at depth > threshold with a time window.

Replay strategies

  • Manual replay: after fixing the consumer bug, replay all DLQ messages by re-publishing them to the original topic. Requires confirming idempotency first.
  • Selective replay: if only a subset of messages failed (e.g. specific schema version), filter the DLQ and replay only those.
  • Automated replay with backoff: some systems automatically attempt DLQ replay on a schedule (every 30 minutes, exponential backoff) after the consumer has been redeployed.

Never delete a DLQ message without understanding why it failed. DLQ messages are forensic evidence. They tell you exactly which events your system failed to process and when. Store DLQ messages with the failure reason and consumer stack trace. Treat a non-empty DLQ as a P2 incident requiring root cause analysis.

Choreography vs Orchestration

When multiple services need to collaborate on a business workflow, you have two architectural options for coordinating them: choreography (each service reacts independently to events) or orchestration (a central coordinator tells each service what to do).

Choreography

Each service listens for events it cares about and emits new events when it completes its work. There is no central coordinator. The workflow emerges from the chain of event reactions. Services are maximally decoupled — they do not even know each other exists.

JavaScript Example — Choreography (no central coordinator) 
// order-service.js — emits the first event
async function placeOrder(userId, items) {
  const order = await db.createOrder({ userId, items, status: 'pending' });
  await kafka.produce('order.placed', {
    eventId: uuid(),
    orderId: order.id,
    userId,
    items,
    total: order.total
  });
  return order;
}

// payment-service.js — reacts to order.placed
kafka.consume('order.placed', async (event) => {
  const result = await chargeCard(event.userId, event.total);
  await kafka.produce('payment.processed', {
    eventId: uuid(),
    orderId: event.orderId,
    status: result.status  // 'success' | 'failed'
  });
});

// inventory-service.js — reacts to payment.processed
kafka.consume('payment.processed', async (event) => {
  if (event.status !== 'success') return;
  await reserveStock(event.orderId);
  await kafka.produce('inventory.reserved', {
    eventId: uuid(),
    orderId: event.orderId
  });
});

// shipping-service.js — reacts to inventory.reserved
kafka.consume('inventory.reserved', async (event) => {
  await scheduleShipment(event.orderId);
  await kafka.produce('shipment.scheduled', {
    eventId: uuid(),
    orderId: event.orderId
  });
});

Orchestration (Saga Pattern)

A central orchestrator (saga) explicitly calls each service in sequence, handles failures, and executes compensating transactions when a step fails. The orchestrator knows the full workflow. Individual services remain simple — they just execute the command they receive.

JavaScript Example — Orchestration (central saga) 
// order-saga.js — central orchestrator
async function runOrderSaga(orderId) {
  const saga = await SagaLog.create(orderId);

  try {
    // Step 1: charge payment
    const payment = await paymentService.charge(orderId);
    await saga.recordStep('payment', payment.id);

    // Step 2: reserve inventory
    const reservation = await inventoryService.reserve(orderId);
    await saga.recordStep('inventory', reservation.id);

    // Step 3: schedule shipping
    await shippingService.schedule(orderId);
    await saga.recordStep('shipping', null);

    await saga.complete();
  } catch (err) {
    // Compensate in reverse order
    if (saga.hasStep('inventory')) {
      await inventoryService.release(saga.getStepId('inventory'));
    }
    if (saga.hasStep('payment')) {
      await paymentService.refund(saga.getStepId('payment'));
    }
    await saga.fail(err.message);
    throw err;
  }
}

Comparison

Dimension Choreography Orchestration
Coupling Minimal — services only know the broker Orchestrator is coupled to all services
Visibility Hard — workflow is implicit, distributed across services Easy — workflow is explicit in one place
Failure handling Complex — compensating events must propagate through the chain Straightforward — orchestrator handles compensation centrally
Scalability Excellent — no central bottleneck Orchestrator can become a bottleneck
Best for Simple workflows, high throughput, many independent consumers Complex multi-step workflows with rollback requirements

When to choose: Start with choreography for simple reactive flows (A happens, B reacts, C reacts). Switch to orchestration when you need explicit compensation logic (payment charged but inventory failed — refund the payment), or when the choreography chain has grown to 5+ steps and is impossible to debug.

Event Schema Evolution

Event schemas are public contracts. Unlike internal data models, you cannot freely change them without coordinating with every consumer. Schema evolution done wrong causes silent data loss, deserialization failures, or downstream processing bugs.

Backward-compatible changes (safe — no coordination required)

  • Adding a new optional field with a default value
  • Adding a new event type to an existing topic
  • Widening a field type (int to long, string length increase)

Breaking changes (require coordination)

  • Renaming or removing a field that consumers depend on
  • Changing a field's type in an incompatible way (string to integer)
  • Changing a field from optional to required
  • Reordering fields in a format without named fields (CSV, positional binary)

Schema Registry

A schema registry (Confluent Schema Registry for Kafka, AWS Glue Schema Registry for SQS/Kinesis) enforces schema compatibility at publish time. Producers register their schema; the registry validates the new schema against the compatibility mode configured for that topic (BACKWARD, FORWARD, FULL). A producer that tries to publish a breaking change is rejected before the message reaches the broker.

Consumer-Driven Contract Testing

Pact and similar consumer-driven contract testing tools let each consumer define what fields it needs from an event, and let the producer's CI pipeline verify it does not break any registered consumer contract. This is the most reliable way to catch breaking schema changes before they reach production.

Versioning strategy for breaking changes: publish both schemas in parallel. Publish order.placed.v1 and order.placed.v2 simultaneously. Migrate consumers to v2. Once all consumers have migrated (verify via consumer group lag), deprecate and stop publishing v1. Never delete the topic until you are certain no consumer is still reading from it.

CQRS + EDA Integration

Command Query Responsibility Segregation (CQRS) pairs naturally with EDA. In CQRS, commands mutate state; queries read from separate, optimised read models. Events are the mechanism that keeps read models in sync with the write model.

When an order is placed (write model updated), the Order service publishes an OrderPlaced event. A separate Projection service consumes that event and updates the read model — a denormalised view optimised for the queries it serves (e.g. a Redis hash for the "my orders" API, an Elasticsearch document for the admin search interface). The write model and read models are eventually consistent; read models are always behind by the consumer lag.

JavaScript Example — Read Model Projection via Events 
// order-projection.js — consumes events to maintain a read model
kafka.consume('order.placed', async (event) => {
  // Update Redis read model for "my orders" API
  await redis.hset(
    `user-orders:${event.userId}`,
    event.orderId,
    JSON.stringify({
      orderId: event.orderId,
      status: 'pending',
      total: event.total,
      placedAt: event.timestamp
    })
  );
});

kafka.consume('payment.processed', async (event) => {
  const order = JSON.parse(
    await redis.hget(`user-orders:${event.userId}`, event.orderId) || '{}'
  );
  if (!order.orderId) return; // projection not yet built — will retry
  order.status = event.status === 'success' ? 'confirmed' : 'payment_failed';
  await redis.hset(
    `user-orders:${event.userId}`,
    event.orderId,
    JSON.stringify(order)
  );
});

// Query handler — reads from the projection, never from the write DB
async function getMyOrders(userId) {
  const orders = await redis.hvals(`user-orders:${userId}`);
  return orders.map(o => JSON.parse(o));
}

Eventual consistency in CQRS+EDA: a user places an order and immediately calls "my orders" — they may not see it yet (the projection consumer has not processed the event). Handle this with optimistic UI updates (show the order immediately on the client), a brief polling retry, or a short read-your-writes cache keyed by the user's session. Do not try to make the read model synchronously consistent; that negates the entire value of the pattern.

Full Node.js Example: Order Flow with Kafka

A complete event-driven order flow: order service publishes, payment service consumes and publishes, inventory service consumes and publishes. Each service is independent; adding a new service (e.g. fraud detection) requires zero changes to existing services.

JavaScript Example — Full EDA Order Flow (Node.js + Kafka) 
// kafka-client.js — minimal wrapper around kafkajs
import { Kafka } from 'kafkajs';
const kafka = new Kafka({ brokers: [process.env.KAFKA_BROKER] });
const producer = kafka.producer();
const consumer = kafka.consumer({ groupId: process.env.SERVICE_NAME });

await producer.connect();
await consumer.connect();

export const kafkaClient = {
  async produce(topic, payload) {
    await producer.send({
      topic,
      messages: [{ value: JSON.stringify({ ...payload, eventId: uuid(), timestamp: Date.now() }) }]
    });
  },

  async consume(topic, handler) {
    await consumer.subscribe({ topic, fromBeginning: false });
    await consumer.run({
      eachMessage: async ({ message }) => {
        const event = JSON.parse(message.value.toString());
        await handler(event);
      }
    });
  }
};

// ── order-service.js ──────────────────────────────────────────
async function placeOrder(userId, items) {
  const order = await db.createOrder({ userId, items, status: 'pending' });
  // Publish event — done. No waiting for payment, inventory, or anything else.
  await kafkaClient.produce('order.placed', {
    orderId: order.id,
    userId,
    items,
    total: order.total
  });
  return { orderId: order.id, status: 'pending' };
}

// ── payment-service.js ────────────────────────────────────────
kafkaClient.consume('order.placed', async (event) => {
  const result = await chargeCard(event.userId, event.total);
  await kafkaClient.produce('payment.processed', {
    orderId: event.orderId,
    status: result.status   // 'success' | 'failed'
  });
});

// ── inventory-service.js ──────────────────────────────────────
kafkaClient.consume('payment.processed', async (event) => {
  if (event.status === 'success') {
    await reserveStock(event.orderId);
    await kafkaClient.produce('inventory.reserved', {
      orderId: event.orderId
    });
  }
  // If payment failed, emit nothing — downstream services stay idle
});

// ── notification-service.js ───────────────────────────────────
// Added later — zero changes to any existing service
kafkaClient.consume('inventory.reserved', async (event) => {
  const order = await orderService.getOrder(event.orderId);
  await emailService.send(order.userId, 'order_confirmed', { orderId: event.orderId });
});

// ── shipping-service.js ───────────────────────────────────────
kafkaClient.consume('inventory.reserved', async (event) => {
  await schedulePickup(event.orderId);
  await kafkaClient.produce('shipment.scheduled', {
    orderId: event.orderId
  });
});

EDA Anti-Patterns

EDA introduces its own class of failure modes. These are the patterns that look reasonable in design documents but create serious operational problems in production.

  • Event sourcing everywhere. Event sourcing (storing every state change as an event, deriving current state by replaying the log) is powerful but expensive. It requires immutable event logs, complex snapshot strategies, and event store infrastructure. Most services do not need event sourcing — they need EDA for decoupling, which is a different thing. Only apply event sourcing where you genuinely need full audit history or temporal queries.
  • Chatty events. Publishing an event for every field change (UserNameUpdated, UserEmailUpdated, UserPhoneUpdated as separate events) leads to consumers processing dozens of events per user action, complex ordering dependencies, and fragile consumer logic. Prefer coarser-grained events that represent meaningful business facts (UserProfileUpdated with the full updated state).
  • Tight coupling through a shared event library. Packaging all event schemas into a single shared library (npm package, Maven artifact) that every service imports recreates tight coupling at the dependency level. A schema change in the library requires all services to update their dependency simultaneously — the same coordination problem you were trying to avoid. Prefer schema registry + code generation per service.
  • No DLQ configured. Without a dead letter queue, failed messages are either silently dropped (at-most-once) or cause the consumer to retry forever, blocking all subsequent messages on that partition. Every production consumer must have a DLQ, a maximum retry count, and a monitored alert on DLQ depth.
  • Treating the event bus as a database. Expecting the broker to be the permanent system of record for business state. Brokers are transport; they have retention limits. If Kafka is configured with 7-day retention and a consumer is down for 8 days, the events are gone. Business state must be persisted in a database; the broker is for propagation.

Decision Framework: EDA vs Synchronous

EDA is not always the right choice. Use this table to guide the decision for each integration point in your system.

Use Case Traffic Pattern Consistency Requirement Recommendation
Real-time inventory check at checkout Medium, bursty Strong (show current stock) Synchronous REST or gRPC
Send order confirmation email High, spiky Eventual (a few seconds delay is fine) EDA — publish OrderPlaced, Notification service consumes
Update search index after product change Low to medium, async Eventual (search lag acceptable) EDA — publish ProductUpdated, Search service consumes
Fraud check before payment High Strong (must block payment if fraud detected) Synchronous — fraud result needed before proceeding
Sync data to analytics warehouse Very high, continuous Eventual (hourly lag acceptable) EDA — Kafka consumer feeding the warehouse
Notify 10 downstream services of a user deletion (GDPR) Low, triggered Eventual but must reach all services EDA — publish UserDeleted, guaranteed delivery to all consumers
Login authentication High, latency-sensitive Synchronous by nature Synchronous — user is waiting for the response
Cascade updates across microservices after a config change Low, infrequent Eventual EDA — single publish fans out to all consumers

Key Takeaway

Event-driven architecture solves the right problem — temporal and spatial coupling between services — but it introduces its own complexity: eventual consistency, idempotency requirements, schema evolution discipline, and operational investment in broker infrastructure and DLQ monitoring. The core principle is simple: producers emit immutable facts; consumers react independently; the broker guarantees delivery. Start with at-least-once delivery and idempotent consumers. Use choreography for simple reactive flows; introduce an orchestrator only when compensation logic demands it. Treat your event schemas as public APIs and version them accordingly. The systems that do EDA well are not the ones that adopted it everywhere — they are the ones that chose it deliberately for the integration points where decoupling genuinely mattered.
