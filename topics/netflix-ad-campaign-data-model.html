Netflix Interview: Direct-Sold Ad Campaign Data Model

A senior system design question that exposes three things auctions handle automatically but direct-sold contracts make you model explicitly: upfront pricing, delivery guarantees, and inventory booking. Auction vs. Direct-Sold: Three Fundamental Shifts

Auction-based ad systems discover price competitively, win delivery automatically, and bid against real-time inventory. Removing the auction forces you to model three things explicitly.

Auction WorldDirect-Sold World
Price discovered at bid timePrice negotiated upfront, fixed on line item
Delivery won competitivelyDelivery promised contractually
Inventory bid forInventory booked against forecast

The question is testing whether you recognize this shift and can model each constraint separately — not just redraw a programmatic DSP with different labels.

Entity Hierarchy: Money Flows Down the Tree

Direct-sold relationships have a natural hierarchy. Every entity below inherits constraints from its parent and adds its own scheduling or delivery details.

Flow: Agency → Advertiser → Order → Line Item → Flight

The Critical Design Decision: Flights vs. Line Items

Budgets and dates belong on a flight (child entity), not on the line item itself. This is the interviewer's hidden test.

-- Line item: what was sold, at what rate, toward what goal CREATE TABLE line_item ( id UUID PRIMARY KEY, order_id UUID REFERENCES orders(id), name TEXT, priority INT, rate_type TEXT, -- CPM | CPC | CPV rate_amount NUMERIC(10,4), goal_type TEXT, -- impressions | clicks | spend goal_quantity BIGINT, pacing_strategy TEXT, -- asap | even | catch_up status TEXT -- draft | active | paused | completed ); -- Flight: the time-boxed delivery schedule for a line item CREATE TABLE flight ( id UUID PRIMARY KEY, line_item_id UUID REFERENCES line_item(id), start_at TIMESTAMPTZ, end_at TIMESTAMPTZ, budget_amount NUMERIC(12,2), budget_impressions BIGINT, pacing_target NUMERIC(6,4) -- allowed daily variance (e.g. 0.05 = ±5%) );
Why flights, not dates on line items? A campaign may run in phases — December pause, then January restart — under one negotiated rate. Putting dates on line items fragments frequency caps across rows that cannot communicate. The flight entity also enables catch-up pacing without touching the contract.

Pacing Strategies — Quantified

A 30M-impression flight over 30 days with ~42M available daily inventory illustrates how strategy choice determines whether delivery succeeds.

StrategyOutcome
Serve ASAPFinishes day 21, dark for 9 days
Even pacing (fixed daily target)97.72% delivery — 683,208 impressions short
Catch-up pacing (remaining ÷ remaining days)100% on day 30
 
// Catch-up pacing calculator
function dailyTarget(totalGoal, delivered, daysElapsed, totalDays) {
  const remaining = totalGoal - delivered;
  const daysLeft   = totalDays - daysElapsed;
  return daysLeft > 0 ? remaining / daysLeft : 0;
}

// Simulate 30-day flight: 30M impressions, ~1.4M/day available
function simulateFlight(goal, totalDays, dailyAvailable) {
  let delivered = 0;
  const log = [];

  for (let day = 1; day <= totalDays; day++) {
    const target  = dailyTarget(goal, delivered, day - 1, totalDays);
    const served  = Math.min(target * 1.05, dailyAvailable); // allow 5% burst
    delivered    += served;
    log.push({ day, target: Math.round(target), served: Math.round(served), cumulative: Math.round(delivered) });
  }

  return { delivered, pct: ((delivered / goal) * 100).toFixed(2), log };
}

const result = simulateFlight(30_000_000, 30, 1_400_000);
console.log(`Delivery: ${result.delivered.toLocaleString()} (${result.pct}%)`);
// → Delivery: 30,000,000 (100.00%)

Model implication: pacing_strategy cannot be a boolean. It needs the strategy name, a permitted daily variance, and a flag for whether the line item may front-load.

Targeting: Tree Structure, Not Wide Columns

A table with geography, device, daypart columns breaks immediately on boolean expressions like "US + mobile OR UK + CTV." Use a targeting tree instead.

CREATE TABLE targeting_node ( id UUID PRIMARY KEY, line_item_id UUID REFERENCES line_item(id), parent_id UUID REFERENCES targeting_node(id), operator TEXT, -- AND | OR | NOT dimension TEXT, -- geography | device | daypart | content_rating match_type TEXT, -- INCLUDE | EXCLUDE value_set_id UUID -- pointer to geography_set, device_set, etc. ); 
// Build a targeting tree: (US AND mobile) OR (UK AND CTV)
const tree = {
  operator: "OR",
  children: [
    {
      operator: "AND",
      children: [
        { dimension: "geography", match_type: "INCLUDE", values: ["US"] },
        { dimension: "device",    match_type: "INCLUDE", values: ["mobile"] }
      ]
    },
    {
      operator: "AND",
      children: [
        { dimension: "geography", match_type: "INCLUDE", values: ["UK"] },
        { dimension: "device",    match_type: "INCLUDE", values: ["CTV"] }
      ]
    }
  ]
};

function evaluateTargeting(tree, impression) {
  if (tree.dimension) {
    const match = tree.values.includes(impression[tree.dimension]);
    return tree.match_type === "INCLUDE" ? match : !match;
  }
  if (tree.operator === "AND") return tree.children.every(c => evaluateTargeting(c, impression));
  if (tree.operator === "OR")  return tree.children.some(c  => evaluateTargeting(c, impression));
  if (tree.operator === "NOT") return !evaluateTargeting(tree.children[0], impression);
}

// Test
console.log(evaluateTargeting(tree, { geography: "US", device: "mobile" })); // true
console.log(evaluateTargeting(tree, { geography: "US", device: "desktop" })); // false
console.log(evaluateTargeting(tree, { geography: "UK", device: "CTV" }));    // true

Creative Approval: State Machine, Not Boolean

An approved boolean breaks when policy contexts differ or when policies change after approval. Model it as a state machine scoped to a policy context.

States: submitted → in_review → approved → rejected → expired 
// Creative approval state machine
const TRANSITIONS = {
  submitted:  ["in_review"],
  in_review:  ["approved", "rejected"],
  approved:   ["expired"],   // forced when policy context changes
  rejected:   ["submitted"], // resubmit after edits
  expired:    ["submitted"]
};

class CreativeApproval {
  constructor(creativeId, policyContext) {
    this.creativeId    = creativeId;
    this.policyContext = policyContext; // "general_audience" | "kids" | "sports"
    this.state         = "submitted";
    this.history       = [];
  }

  transition(to, reviewerId, reason = "") {
    if (!TRANSITIONS[this.state].includes(to)) {
      throw new Error(`Invalid transition: ${this.state} → ${to}`);
    }
    this.history.push({ from: this.state, to, reviewerId, reason, at: new Date().toISOString() });
    this.state = to;
    return this;
  }

  // When policy context changes (e.g. ad slot reclassified as kids content)
  invalidateForPolicyChange(newContext) {
    if (this.state === "approved") {
      this.policyContext = newContext;
      this.transition("expired", "system", "Policy context changed — re-review required");
    }
  }
}

const approval = new CreativeApproval("ad-123", "general_audience");
approval.transition("in_review", "reviewer-1");
approval.transition("approved", "reviewer-1", "Meets all guidelines");
approval.invalidateForPolicyChange("kids"); // Forces re-review
console.log(approval.state); // "expired"
console.log(approval.history.map(h => `${h.from}→${h.to}`).join(", "));
// submitted→in_review, in_review→approved, approved→expired

The Versioning Trap — The Core Interview Insight

Every impression records a config_version. Without it, mid-flight renegotiations destroy reporting accuracy silently — no error thrown, just wrong numbers.

Example: 30M impression flight, rate drops from $22 CPM to $18 CPM on day 15.
Correct (version-aware): $599,669  |  Naive (current row join): $540,000  |  Error: $59,669 (~9.95% of campaign revenue)
CREATE TABLE line_item_version ( id UUID PRIMARY KEY, line_item_id UUID REFERENCES line_item(id), version INT NOT NULL, rate_amount NUMERIC(10,4), valid_from TIMESTAMPTZ NOT NULL, valid_to TIMESTAMPTZ, changed_by UUID, change_reason TEXT ); -- Impression table carries config_version for point-in-time join CREATE TABLE impression ( id UUID PRIMARY KEY, line_item_id UUID, config_version INT, -- snapshot of the version at serve time served_at TIMESTAMPTZ, user_id UUID, placement_id UUID ); 
// Point-in-time revenue calculation (version-aware)
function calculateRevenue(impressions, versionHistory) {
  return impressions.reduce((total, imp) => {
    const version = versionHistory.find(v =>
      v.version === imp.configVersion &&
      v.lineItemId === imp.lineItemId
    );
    if (!version) throw new Error(`Missing version ${imp.configVersion} for ${imp.lineItemId}`);
    // CPM = cost per 1000 impressions
    return total + (version.rateCpm / 1000);
  }, 0);
}

// Simulate mid-flight rate change
const versionHistory = [
  { lineItemId: "li-1", version: 1, rateCpm: 22.00, validFrom: "2026-12-01" },
  { lineItemId: "li-1", version: 2, rateCpm: 18.00, validFrom: "2026-12-15" }
];

// 15M impressions at v1 ($22 CPM) + 15M impressions at v2 ($18 CPM)
const impressions = [
  ...Array(15_000_000).fill({ lineItemId: "li-1", configVersion: 1 }),
  ...Array(15_000_000).fill({ lineItemId: "li-1", configVersion: 2 })
];

// Correct: (15M × $22 + 15M × $18) / 1000 = $330k + $270k = $600k
const correctRevenue = (15_000_000 * 22 + 15_000_000 * 18) / 1000;
console.log(`Correct:  $${correctRevenue.toLocaleString()}`); // $600,000

// Naive (wrong): 30M × $18 (current rate)
const naiveRevenue  = (30_000_000 * 18) / 1000;
console.log(`Naive:    $${naiveRevenue.toLocaleString()}`);   // $540,000
console.log(`Error:    $${(correctRevenue - naiveRevenue).toLocaleString()}`); // $60,000

Frequency Cap Leakage

With 8 distributed ad servers and a cap of 3 impressions/user/week, stale local counters allow users to see more ads than contracted.

Sync IntervalUsers Receiving 4th+ Impression
1 second~0%
60 seconds0.27%
5 minutes0.94%
 
// Distributed frequency cap with tolerance field
class FrequencyCap {
  constructor({ cap, windowMs, tolerancePct = 0.01, syncIntervalMs = 60_000 }) {
    this.cap          = cap;           // e.g. 3 impressions
    this.windowMs     = windowMs;      // e.g. 7 * 24 * 3600 * 1000 (1 week)
    this.tolerance    = tolerancePct;  // acceptable overshoot (model it, don't hide it)
    this.syncInterval = syncIntervalMs;
    this.localCounts  = new Map();     // userId → count (stale between syncs)
    this.lastSync     = Date.now();
  }

  // Called on each ad server before serving
  canServe(userId) {
    const count = this.localCounts.get(userId) ?? 0;
    const maxAllowed = Math.floor(this.cap * (1 + this.tolerance));
    return count < maxAllowed;
  }

  record(userId) {
    this.localCounts.set(userId, (this.localCounts.get(userId) ?? 0) + 1);
  }

  // Sync with central counter store (Redis, etc.) — resets local staleness
  async syncWithCentral(centralStore) {
    const now = Date.now();
    if (now - this.lastSync < this.syncInterval) return;

    for (const [userId, localCount] of this.localCounts) {
      await centralStore.increment(userId, localCount, this.windowMs);
      const centralCount = await centralStore.get(userId);
      this.localCounts.set(userId, centralCount);
    }
    this.lastSync = now;
  }
}

// Key insight: tolerance is a policy parameter, not a bug to hide
// Store it on the line_item so reports can explain overshoot
const cap = new FrequencyCap({ cap: 3, windowMs: 7 * 86_400_000, tolerancePct: 0.01, syncIntervalMs: 60_000 });
console.log(cap.canServe("user-1")); // true (count = 0)
cap.record("user-1"); cap.record("user-1"); cap.record("user-1");
console.log(cap.canServe("user-1")); // false (count = 3, maxAllowed = 3)
// With 1% tolerance, maxAllowed = 3 for cap=3 → no overshoot allowed
// A cap of 10 with 1% tolerance → maxAllowed = 10 (Math.floor(10.1) = 10)
Model insight: "A frequency cap is a policy with a tolerance rather than an invariant." The model should carry an acceptable_overshoot field so reporting can distinguish intentional overshoot from bugs.

The Generalizable Modeling Principle

Before placing an attribute directly on an entity, ask:

Can it differ across time, context, or contract phases?
If yes — it's a child entity with its own lifespan, not a column.

❌ Column on entity

  • Start/end dates on line item
  • Rate on order
  • Approved boolean on creative
  • Geography string on line item

✅ Child entity

  • Flight (start/end + budget + pacing)
  • line_item_version (rate history)
  • CreativeApproval (state machine)
  • targeting_node (boolean tree)

Key Takeaway

Direct-sold ad systems expose what auction systems hide. You must explicitly model the upfront rate, the delivery promise, and the inventory reservation — three separate concerns. The versioning trap (silent wrong numbers on mid-flight changes), the pacing strategy (catch-up beats even by 2.28pp), and the frequency cap tolerance (a policy, not an invariant) are the three questions that separate candidates who understand the domain from those who can draw a generic data model. Store config_version on every impression — it is the only way to produce correct revenue reports after renegotiation.
