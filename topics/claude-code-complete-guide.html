The Complete Claude Code Guide: CLAUDE.md, Skills, Hooks, Plugins & the Claude OS Execution Engine

One definitive reference to Claude Code's configuration layers. CLAUDE.md is the behavioral kernel. Skills are reusable operation packages invoked with slash commands. Hooks are event-driven shell automations that run outside Claude's context. Plugins extend Claude Code with external tools and MCP servers. Workflows orchestrate parallel sub-agents. Composed deliberately, they form "Claude OS": a programmable execution engine rather than a chat window.

Claude Code is not a chat window with a code editor attached. It is a layered system. Each layer handles a different kind of persistent configuration: CLAUDE.md (what Claude always knows), Hooks (what the system does automatically), Skills (what Claude can do on demand), Plugins (what external tools Claude can reach), and Workflows (how teams of agents are orchestrated).

Core idea: A standard session is reactive: you type, Claude responds. Configure these layers and the model flips. Claude becomes the orchestrator: you define which tasks trigger which agents, which quality gates must pass, how state persists between sessions, and what the output contract is. Claude executes; you review. This pattern is called Claude OS. It is not an Anthropic product, it is an architectural pattern built from features Claude Code already ships.

The origin of the pattern

Engineers who used Claude Code heavily in 2025 noticed a problem: powerful sessions were not reproducible. You got great results by carefully setting context, but the next session started from scratch. The solution was to externalise the "good session setup" into files Claude always reads, which is exactly what CLAUDE.md was designed for. Then hooks let you fire actions automatically on events. Then skills let you package multi-step operations as slash commands. Then workflows let you fan out to dozens of sub-agents in parallel. Each addition turned Claude from a chat tool into a runtime.

Architecture

The layers of a Claude OS system

L1Context LayerCLAUDE.md files: project conventions, architecture decisions, anti-patterns, tool preferences. Always in context.
L2Event LayerHooks: shell commands that fire on PreToolUse, PostToolUse, Stop, Notification events. Deterministic reactions.
L3Operation LayerSkills: slash commands that load specialised instructions and tools for a domain (deploy, review, test, document).
L4Integration LayerPlugins and MCP servers: GitHub, Postgres, Figma, Slack and custom tools so agents query real data instead of guessing.
L5Orchestration LayerWorkflows: JavaScript scripts that spawn, coordinate, and verify parallel sub-agents with structured output schemas.
Part 1 — CLAUDE.md

The behavioral operating system

CLAUDE.md is a Markdown file Claude reads at the start of every session. Everything in it is in Claude's context before you type a word. It acts simultaneously as:

Behavioral OS

Sets defaults for how Claude works — tone, commit style, testing approach, code style.

Context router

Tells Claude where to look for architecture decisions, runbooks, schemas, and API contracts.

Quality layer

Defines "done" — what tests must pass, what review checklist to follow, what conventions must hold.

Architectural memory

Preserves decisions that should outlast any single session — why you chose X over Y.

The anatomy of a good CLAUDE.md

# ProjectName

> One-sentence description of what this project is and its tech stack.

## Architecture
- Monorepo: apps/web (Next.js 15), apps/api (Node.js/Express), packages/shared
- Database: PostgreSQL via Drizzle ORM — all queries in src/db/
- Cache: Redis for sessions and job queues (BullMQ)
- Deployed on: Fly.io (API), Vercel (Web)

## Code conventions
- TypeScript strict everywhere — no `any`
- 2-space indent, single quotes
- Named exports only — no default exports
- Tests co-located with source: `foo.ts` → `foo.test.ts`

## Execution contracts (Claude: read carefully)
- Run `npm test` before every commit; STOP if any test fails
- DB migrations via `npm run db:migrate:make` only — never raw ALTER TABLE
- Secrets ONLY via environment variables — never in code

## Context pointers
- API types: packages/shared/types.ts
- DB schema: apps/api/src/db/schema.ts
- Architecture decisions: DECISIONS.md
- Deployment runbook: ops/RUNBOOK.md

## What NOT to do
- Do not use console.log in production code — use the logger at src/lib/logger.ts
- Do not add dependencies without checking the bundle size impact first
- Do not write comments that say WHAT the code does — only write WHY

Execution contracts and autonomy gates

For an OS-style setup, CLAUDE.md is the kernel: it also encodes how much freedom Claude has at each step, so the rest of the system can rely on it. 

## Execution contracts
- All DB queries go through `src/db/query.js` — never raw SQL strings in route files.
- Tests run with `npm test` before any commit. If tests fail, STOP and report.
- Migrations live in `db/migrations/`. Always generate with `npm run migrate:make`.

## Agent autonomy gates
- READ + analyse: autonomous, no confirmation needed.
- WRITE to src/: confirm file list before writing.
- EXEC shell commands: confirm if outside npm scripts.
- PUSH to git: always require explicit user approval.

The 200-line rule

Keep CLAUDE.md under 200 lines. Longer files dilute the important instructions. A 30-line CLAUDE.md Claude follows completely beats a 300-line one Claude ignores because it cannot identify what matters.

Multi-level CLAUDE.md hierarchy

  • ~/.claude/CLAUDE.md — global preferences (your voice, formatting preferences, tools you always use)
  • ./CLAUDE.md — project-level conventions (architecture, team standards)
  • ./src/auth/CLAUDE.md — directory-level context (security rules for auth module)
  • ./CLAUDE.local.md — personal overrides, git-ignored (your personal shortcuts)

Part 2 — Skills

The evolution from slash commands to packaged operations

Skills are Markdown files in .claude/skills/ that Claude loads when you invoke /skill-name. They evolved from simple slash command aliases into structured operation packages with specialised instructions, tool chains, and output contracts.

Skill anatomy

# .claude/skills/code-review.md
# Code Review

When invoked with `/code-review [--fix] [--comment]`:

1. Run `git diff main` to see all changed files.
2. For each changed file, check for:
   - Security: injection, hardcoded secrets, OWASP Top 10
   - Correctness: logic bugs, off-by-one errors, null/undefined paths
   - Performance: N+1 queries, synchronous blocking in async contexts
   - Style: deviations from CLAUDE.md conventions

3. Produce a structured report:
   - Category (security/correctness/perf/style)
   - File and line number
   - Severity (critical/high/medium/low)
   - Finding description
   - Suggested fix

4. If `--fix` flag: apply all low-risk (medium/low severity) fixes automatically.
   Ask for confirmation before applying critical/high severity fixes.

5. If `--comment` flag: post findings as inline GitHub PR comments using the `gh` CLI.

End with a one-line verdict: APPROVE / REQUEST_CHANGES / NEEDS_DISCUSSION.

Example: a deploy skill

# .claude/skills/deploy.md
# Deploy to Fly.io

When this skill is invoked:

1. Run `npm test` — if any test fails, stop and report. Do not proceed.
2. Run `npm run build` and confirm exit 0.
3. Run `flyctl status` and confirm the current deploy is healthy.
4. Run `flyctl deploy --ha=false` and stream output.
5. After deploy, run `flyctl status` again and confirm all instances are running.
6. Report: deploy duration, instance count, health check status.

If any step fails, report the exact error and suggest the most likely fix.
Do NOT roll back automatically — require explicit user confirmation.

Skill scope levels

  • Global skills (~/.claude/skills/) — available in every project
  • Project skills (.claude/skills/) — only available in this project
  • Anthropic built-in skills — /code-review, /run, /verify, /init, /deep-research are shipped with Claude Code
  • Plugin skills — skills from installed plugins (Figma, Slack, etc.)

Chaining skills in workflows

// Call a skill from a workflow script
const reviewResult = await agent('/code-review --fix', {
  label: 'review-and-fix',
  schema: {
    type: 'object',
    properties: {
      verdict:  { type: 'string', enum: ['APPROVE', 'REQUEST_CHANGES', 'NEEDS_DISCUSSION'] },
      findings: { type: 'array', items: { type: 'object' } },
      fixed:    { type: 'number' },
    },
    required: ['verdict', 'findings'],
  },
});

Best skills to write for your project

  • /deploy — test → build → deploy to staging/prod with health check verification
  • /db-migrate — generate, review, and apply database migrations safely
  • /onboard — guide a new contributor through setup and first task
  • /incident — triage production issue: check logs, recent deploys, error rates
  • /changelog — generate changelog entries from git log since last tag
Part 3 — Hooks

Event-driven automation outside Claude's context

Hooks are shell commands that Claude Code executes in response to lifecycle events. They run in a separate process, outside Claude's reasoning — which makes them deterministic, tamper-proof (they cannot be overridden by prompt injection), and ideal for quality gates.

Available hook events

  • PreToolUse — before Claude calls a tool (file write, bash command, MCP tool)
  • PostToolUse — after a tool call completes
  • Stop — when Claude finishes a response and is awaiting user input
  • Notification — when Claude sends a desktop notification
  • SubagentStop — when a sub-agent completes

Hook configuration

// .claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|NotebookEdit",
        "hooks": [
          {
            "type": "command",
            "command": "npm run lint -- --quiet 2>&1 | head -30",
            "timeout": 10000
          }
        ]
      },
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "node .claude/hooks/log-bash-command.js"
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "node .claude/hooks/block-destructive-commands.js"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"Claude is done\" with title \"Claude Code\"'"
          }
        ]
      }
    ]
  }
}

Hook context — reading what triggered

// .claude/hooks/block-destructive-commands.js
// Runs before every Bash tool call — can block dangerous commands
const input = JSON.parse(process.env.CLAUDE_TOOL_INPUT ?? '{}');
const command = input.command ?? '';

const DANGEROUS = [
  /rm\s+-rf\s+\//,        // rm -rf /
  /DROP\s+TABLE/i,         // SQL DROP
  /git\s+push\s+--force/,  // force push
  />\s*\/dev\/null\s*2>&1\s*&\s*disown/, // background detach
];

for (const pattern of DANGEROUS) {
  if (pattern.test(command)) {
    // Exit code 2 = hard block (Claude Code will not execute the tool)
    console.error(`BLOCKED: command matches dangerous pattern: ${pattern}`);
    process.exit(2);
  }
}

// Exit code 0 = allow
process.exit(0);
// .claude/hooks/log-bash-command.js
// PostToolUse — logs every Bash command with timestamp
import fs from 'fs';
import path from 'path';

const input  = JSON.parse(process.env.CLAUDE_TOOL_INPUT  ?? '{}');
const output = JSON.parse(process.env.CLAUDE_TOOL_OUTPUT ?? '{}');

const entry = {
  ts:      new Date().toISOString(),
  command: input.command,
  exit:    output.returncode,
  stdout:  (output.stdout ?? '').slice(0, 500),
};

const logPath = path.join('.claude', 'bash-audit.jsonl');
fs.appendFileSync(logPath, JSON.stringify(entry) + '\n');

Example: session-summary hook

A Stop hook (node .claude/hooks/session-summary.js) can persist state between sessions:

// .claude/hooks/session-summary.js
// Runs after every session ends — writes a summary to memory
import fs from 'fs';
import path from 'path';

const transcriptDir = process.env.CLAUDE_TRANSCRIPT_DIR ?? '.claude/transcripts';
const memoryDir     = '.claude/memory';

const today = new Date().toISOString().slice(0, 10);
const summaryPath = path.join(memoryDir, `session-${today}.md`);

// Append session end marker
fs.appendFileSync(summaryPath, `\n## Session ended ${new Date().toISOString()}\n`);
console.log('Session summary written to', summaryPath);

Hook exit codes

  • 0 — allow the tool call to proceed
  • 1 — report a warning but proceed
  • 2 — hard block: Claude Code will not execute the tool
Part 4 — Plugins & MCP

Extending Claude Code with external tools

Plugins connect Claude Code to external systems via MCP (Model Context Protocol). Each plugin exposes tools Claude can call, resources Claude can read, and sometimes skills Claude can invoke.

MCP configuration

// .mcp.json — project-level MCP servers
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    },
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres"],
      "env": { "POSTGRES_URL": "${DATABASE_URL}" }
    },
    "figma": {
      "command": "npx",
      "args": ["-y", "@figma/mcp-server-figma"],
      "env": { "FIGMA_API_TOKEN": "${FIGMA_API_TOKEN}" }
    },
    "slack": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-slack"],
      "env": { "SLACK_BOT_TOKEN": "${SLACK_BOT_TOKEN}" }
    }
  }
}

Global vs project MCP configuration

  • ~/.claude/mcp.json — always available in every project (personal tools: calendar, notes, terminal)
  • ./.mcp.json — project-specific tools (GitHub repo, project database, design system)
  • ~/.claude/settings.json — globally allowed/denied tool names

Building a custom MCP server

// my-custom-mcp/index.js
import { McpServer } from '@modelcontextprotocol/sdk/server/mcp.js';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';

const server = new McpServer({ name: 'my-tools', version: '1.0.0' });

// Define a tool Claude can call
server.tool('get_deployment_status', {
  description: 'Get the current deployment status from Fly.io',
  inputSchema: {
    type: 'object',
    properties: {
      app: { type: 'string', description: 'App name on Fly.io' },
    },
    required: ['app'],
  },
}, async ({ app }) => {
  const { execSync } = await import('child_process');
  const status = execSync(`flyctl status --app ${app} --json`).toString();
  return { content: [{ type: 'text', text: status }] };
});

// Define a resource Claude can read
server.resource('recent-errors', 'app://logs/errors', {
  description: 'Recent production error logs',
  mimeType: 'text/plain',
}, async () => {
  const logs = await fetchRecentErrors(); // your implementation
  return { contents: [{ uri: 'app://logs/errors', text: logs }] };
});

const transport = new StdioServerTransport();
await server.connect(transport);
// Register it in .mcp.json
{
  "mcpServers": {
    "my-tools": {
      "command": "node",
      "args": [".claude/mcp/my-custom-mcp/index.js"]
    }
  }
}

Part 5 — Workflows (Claude OS orchestration)

Orchestrating parallel sub-agents

The workflow layer is where Claude OS becomes genuinely powerful. A workflow script fans out work across many specialised agents, invokes skills, collects structured output, and synthesises a result. 

// .claude/workflows/pre-release-check.js
export const meta = {
  name: 'pre-release-check',
  description: 'Full pre-release quality gate: tests, security, perf, docs',
  phases: [
    { title: 'Scan',     detail: 'Parallel domain checks' },
    { title: 'Verify',   detail: 'Adversarial verification of findings' },
    { title: 'Report',   detail: 'Synthesise go/no-go decision' },
  ],
};

const CHECKS = [
  { key: 'security',   prompt: 'Audit src/ for OWASP Top 10: injection, XSS, insecure deps, hardcoded secrets. Return findings array.' },
  { key: 'tests',      prompt: 'Run `npm test` and report pass/fail counts, any flaky tests, coverage delta vs main.' },
  { key: 'perf',       prompt: 'Check for N+1 queries, missing indexes, synchronous blocking calls in request paths.' },
  { key: 'api-drift',  prompt: 'Compare openapi.yaml against route implementations. List endpoints that diverged.' },
  { key: 'docs',       prompt: 'Check README, DECISIONS.md, and inline JSDoc for stale references to removed APIs.' },
];

const FINDINGS_SCHEMA = {
  type: 'object',
  properties: {
    key:      { type: 'string' },
    ok:       { type: 'boolean' },
    findings: { type: 'array', items: { type: 'string' } },
    blocker:  { type: 'boolean' },
  },
  required: ['key', 'ok', 'findings', 'blocker'],
};

phase('Scan');
const results = await parallel(CHECKS.map(c => () =>
  agent(c.prompt, { label: `check:${c.key}`, phase: 'Scan', schema: FINDINGS_SCHEMA })
    .then(r => ({ ...r, key: c.key }))
));

const blockers = results.filter(Boolean).filter(r => r.blocker);

phase('Report');
const report = await agent(
  `Synthesise these pre-release check results into a go/no-go decision.
   Blockers found: ${blockers.map(b => b.key).join(', ') || 'none'}.
   Full results: ${JSON.stringify(results, null, 2)}`,
  {
    schema: {
      type: 'object',
      properties: {
        verdict:  { type: 'string', enum: ['GO', 'NO-GO'] },
        summary:  { type: 'string' },
        blockers: { type: 'array', items: { type: 'string' } },
      },
      required: ['verdict', 'summary'],
    },
  }
);

log(`Verdict: ${report.verdict} — ${report.summary}`);
return report;
Integration example

All the layers working together

// Scenario: Claude is asked to fix a production bug

// Layer 1 (Context): CLAUDE.md tells Claude where the logger is, what the coding conventions are,
//          and that tests must pass before any commit.

// Layer 2 (Events): PostToolUse hook runs eslint after every file write, catching linting errors
//          before Claude moves to the next step.

// Layer 3 (Skills): /code-review skill is invoked by the workflow after the fix is written,
//          checking security and correctness before committing.

// Layer 4 (Plugins): GitHub MCP lets Claude read the bug report from the open issue and
//          post the fix as a PR comment when done.

// Layer 5 (Workflows): the script that orchestrates it:
export const meta = {
  name: 'fix-bug',
  description: 'Find, fix, test, review, and PR a bug from a GitHub issue',
  phases: [{ title: 'Diagnose' }, { title: 'Fix' }, { title: 'Review' }, { title: 'PR' }],
};

phase('Diagnose');
const issue = await agent(`Use the GitHub MCP to read issue #${args.issueNumber}. Return the bug description and reproduction steps.`);

phase('Fix');
const fix = await agent(`Fix this bug: ${issue}. Write tests. Run npm test.`);

phase('Review');
const review = await agent('/code-review', { schema: REVIEW_SCHEMA });
if (review.verdict === 'REQUEST_CHANGES') {
  log('Review requested changes — revising fix');
  await agent(`Apply these review comments: ${JSON.stringify(review.findings)}`);
}

phase('PR');
await agent(`Create a GitHub PR for this fix. Title: "fix: ${issue.title}". Reference issue #${args.issueNumber}.`);

Key Takeaway

CLAUDE.md, Hooks, Skills, Plugins, and Workflows are the programmable layers of Claude Code. CLAUDE.md makes Claude consistent and sets the rules. Hooks make quality gates automatic and tamper-proof. Skills make complex operations single-command. Plugins connect Claude to your entire toolchain. Workflows orchestrate teams of agents. Configure all of them and Claude Code transforms from an AI assistant into a reproducible, auditable execution engine: Claude OS.
