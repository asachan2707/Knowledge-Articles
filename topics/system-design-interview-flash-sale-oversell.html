System Design Interview: How Would You Avoid Overselling Inventory During a Flash Sale?

Full interview answer for flash sale inventory design: Redis atomic decrements, database pessimistic locking, reservation TTLs, pre-sale warm-up, queue-based purchase serialisation, and the monitoring setup that catches oversell before it becomes a customer problem.

Domain: System Design · Inventory · Interview Prep Published: 2026-07-22

A flash sale is a concurrency stress test in production clothing. You have N items and potentially 100×N concurrent purchase attempts arriving in the first second. The naive read-check-decrement pattern will oversell every time. The correct design decouples the inventory reservation from the order fulfilment — and makes the reservation layer the only place where concurrency is handled.

Key distinction interviewers look for: "Inventory available" and "inventory reserved" are not the same thing. The flash sale problem is solved in the reservation layer, not the order layer.

Story · Myntra sold 4,200 units of a 500-unit exclusive drop

At 12:00:00 exactly, 62,000 concurrent users hit the checkout endpoint for a limited sneaker release. The application read available stock (500), confirmed it was positive, placed the order, then decremented. Under load, thousands of threads read "500" before any decrement had propagated. 4,200 orders were confirmed. 3,700 customers received cancellation emails two hours later.

The trust damage was worse than the technical failure. Every one of those 3,700 cancellations was a user who had already mentally bought the product. The correct design would have either accepted exactly 500 orders or rejected everything beyond 500 instantly — never confirmed and then cancelled.

Principle 1 — The Two-Phase Commit: Reserve, Then Purchase

Flash sale inventory should use a two-phase model:

  1. Reservation phase — immediately, atomically decrement a Redis counter. If successful, the user has a reservation with a TTL (e.g., 10 minutes to complete checkout).
  2. Purchase phase — the user completes payment. The reservation is converted to a confirmed order in the database. On timeout or failure, the reservation is released back to the Redis counter.

This decoupling means: only 500 users ever get past phase 1. The order/payment system never sees more than 500 concurrent checkout sessions. Oversell is structurally impossible.

Principle 2 — Redis Atomic Decrement (the core mechanism)

Redis executes commands single-threaded. DECR and Lua scripts are atomic — no two clients can race on them. This makes Redis the ideal reservation layer.

JavaScript Example — Redis Atomic Inventory Reservation 
// inventory-reservation.js — Node.js + ioredis
import Redis from 'ioredis';
const redis = new Redis(process.env.REDIS_URL);

// Lua script: atomic check-and-decrement
// Returns 1 on success, 0 on insufficient stock, -1 on item not found
const RESERVE_SCRIPT = `
  local key = KEYS[1]
  local qty = tonumber(ARGV[1])
  local userId = ARGV[2]
  local ttl = tonumber(ARGV[3])

  local current = redis.call('GET', key)
  if current == false then return -1 end  -- item not found
  if tonumber(current) < qty then return 0 end  -- insufficient stock

  redis.call('DECRBY', key, qty)

  -- Store reservation with TTL
  local reservationKey = 'reservation:' .. userId .. ':' .. key
  redis.call('SETEX', reservationKey, ttl, qty)

  return 1
`;

const reserveScript = redis.defineCommand('reserve', {
  numberOfKeys: 1,
  lua: RESERVE_SCRIPT
});

async function reserveInventory(productId, quantity, userId, ttlSeconds = 600) {
  const stockKey = `inventory:${productId}`;
  const result = await redis.reserve(stockKey, quantity, userId, ttlSeconds);

  if (result === -1) throw new Error('Product not found');
  if (result === 0)  throw new Error('Sold out');
  // result === 1: reservation successful

  return {
    reserved: true,
    expiresAt: new Date(Date.now() + ttlSeconds * 1000),
    reservationKey: `reservation:${userId}:${stockKey}`
  };
}

async function releaseReservation(productId, quantity, userId) {
  const stockKey = `inventory:${productId}`;
  const reservationKey = `reservation:${userId}:${stockKey}`;

  const pipeline = redis.pipeline();
  pipeline.del(reservationKey);
  pipeline.incrby(stockKey, quantity); // release back to pool
  await pipeline.exec();
}

async function confirmPurchase(productId, quantity, userId) {
  // 1. Release reservation from Redis
  await releaseReservation(productId, quantity, userId);

  // 2. Decrement in database (authoritative record)
  const result = await db.query(
    `UPDATE products SET stock = stock - $1
     WHERE id = $2 AND stock >= $1
     RETURNING stock`,
    [quantity, productId]
  );
  if (result.rowCount === 0) {
    // Redis said OK but DB says no — should not happen if DB was warm-loaded
    throw new Error('Database stock inconsistency — requires manual review');
  }
  return result.rows[0].stock;
}

Principle 3 — Queue-Based Serialisation for Extreme Load

For ultra-high-concurrency events (iPhone launches, concert tickets), even Redis can become a hot key bottleneck when millions of connections hit the same key per second. The solution: a pre-sale queue.

  1. At T-5 minutes, open a queue for purchase intent. Users click "join queue" — they get a queue position, not a purchase.
  2. At sale time, drain the queue at the controlled rate the checkout system can handle (e.g., 1,000/s).
  3. Only queued users with positions ≤ stock count get a purchase window. All others get "sold out" immediately.

Used by: Ticketmaster (virtual waiting room), Apple Store (access reservation), Puma SNKRS (randomised draw). The queue absorbs the request spike before it hits inventory logic.

Principle 4 — Pre-Sale Warm-Up

Cold Redis is dangerous for flash sales. Steps 15 minutes before go-live:

  1. Load exact inventory counts from the database into Redis (SET inventory:{productId} 500).
  2. Warm CDN caches with the product page (prevents the CDN miss cascade at T+0).
  3. Pre-scale backend instances to 3× normal capacity.
  4. Disable non-essential background jobs that compete for DB connections.
  5. Enable circuit breakers on downstream services (payment gateway, email) with shorter timeouts.

Principle 5 — TTL-Based Reservation Expiry

A user who reserves inventory but abandons checkout holds stock that nobody else can buy. TTL expiry handles this automatically:

  • Reservation TTL: 10 minutes (enough for checkout; short enough to recirculate quickly).
  • A background worker polls for expired reservations and calls releaseReservation().
  • Alternatively: Redis keyspace notifications trigger an event on key expiry. More real-time but adds operational complexity.

Edge case: If the user completes payment but the confirmPurchase call fails, their reservation TTL may expire and release stock that should be theirs. Fix: extend the reservation TTL immediately on successful payment, then confirm asynchronously. Payment success = TTL extension; order creation = async cleanup.

Failure Modes and Production Gotchas

  • Redis crash during sale — Redis is your reservation store. If it goes down, your inventory state is in Redis, not the DB. Fix: Redis Sentinel or Redis Cluster with AOF persistence. Inventory counts must survive a node restart.
  • Redis ↔ DB count drift — if a TTL expiry releases stock in Redis but the DB is not updated (because the order was already written), counts diverge. Fix: reconciliation job every 5 minutes comparing Redis count to DB available stock.
  • Hot key sharding — a single popular product's inventory key receives millions of ops/s. Fix: shard the key across N Redis slots (inventory:{productId}:shard{0..N}), atomically decrement a random shard, aggregate across shards for the total count display.
  • Browser refresh attacks — bots refresh repeatedly to score reservations. Fix: per-user rate limiting at the load balancer (not the application layer — add it early in the stack).

Architecture at a Glance

User → Load Balancer → Rate Limiter (per-user, Redis)
     → Queue (if using virtual waiting room)
     → Reservation Service:
         redis.reserve(productId, qty, userId, ttl=600)
         → 1: success → return reservation token
         → 0: sold out → return 409
     → Checkout Service (only for reservation holders)
         → Payment Gateway
         → confirmPurchase() → update DB + release Redis reservation
     → Async: order-placed event → fulfillment, email, analytics

Key Takeaway

Flash sale oversell is solved by separating reservation (Redis, atomic, instant) from purchase (database, transactional, async). Redis's single-threaded command execution makes it structurally impossible to oversell at the reservation layer. The rest of the design — TTL expiry, queue-based admission, warm-up, and reconciliation — handles the operational reality that surrounds a working core mechanism.
