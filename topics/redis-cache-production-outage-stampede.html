Redis Cache Causes Production Outage: Deep Dive on Cache Stampede, TTL Jitter, and Multi-Level Caching

A production e-commerce platform loads millions of cache keys at startup — product pages, user sessions, configuration values — all with the same TTL. Exactly one hour later, all of them expire simultaneously, the database receives a coordinated avalanche it was never designed to absorb, and the site goes dark for 23 minutes during peak traffic. This deep dive covers the mechanics of mass TTL expiry (distinct from single-key stampedes), the precise mathematical formulas for additive, multiplicative, and AWS-style full jitter, the XFetch probabilistic early-refresh algorithm applied to production context, multi-level caching with L1/L2/L3 tiers, the single-flight / request-coalescing pattern, and an 8-point production checklist for flash-sale readiness.

Story · The Synchronized Expiry Disaster

How a Startup-to-Scale Migration Destroyed Its Own Database

The engineering team had done everything right — or so they thought. A mid-size e-commerce platform was preparing for its biggest flash sale of the year. Thirty days earlier, they had migrated from a single PostgreSQL instance to a horizontally scaled architecture: six application servers behind a load balancer, a Redis cluster with three primaries and three replicas, and a read-replica PostgreSQL pool for the cache-miss fallback path. The architecture review was clean. The load tests had passed. Confidence was high.

What the team had not thought through was the cache warming strategy. On the day of the sale, at 9:00 AM, a warm-up script ran. It was elegant code: it iterated through the product catalog (1.4 million SKUs), fetched each product's pricing, inventory, and metadata from PostgreSQL, and wrote each result to Redis with a TTL of exactly 3600 seconds. The script ran for 47 minutes. By 9:47 AM, the Redis cache was warm and the cache hit rate was 99.8%. The database was near-idle. The team felt good.

At 10:47 AM — exactly 3600 seconds after the first cache keys were written — the disaster began. At 10:47:00, the first batch of keys expired. Within the next 47 minutes, all 1.4 million keys expired in the same sequence and at the same rate they were written, in waves. The traffic spike from the flash sale had begun at 10:00 AM. By 10:47 AM, there were 180,000 concurrent active users on the site. Every product page view, every "add to cart" operation, every recommendation widget — each needed a cache lookup.

Within the first 90 seconds of the expiry wave, 340,000 cache misses had occurred. Each miss spawned a PostgreSQL query. The read replica pool had 800 connections. All 800 were occupied within 3 seconds. The remaining 339,200 database queries queued. PostgreSQL CPU went to 100%. Query times that were 12ms under normal load bloated to 8,000ms. Application servers hit their 5-second request timeout limits and began returning HTTP 503 to users. Users refreshed. The retry storm tripled the outstanding request count.

By 10:49 AM, the primary PostgreSQL instance — which had been untouched by the read replicas — began receiving overflow queries as the replica pool collapsed entirely. At 10:50 AM, the primary OOM-killed due to uncontrolled connection growth. At that point, the entire platform was down. All six app servers had no usable backend. Redis was running perfectly and completely empty. The site was dark for 23 minutes. The flash sale had been live for exactly 50 minutes of its planned 24 hours before it was killed by the cache layer that was supposed to protect it.

The root cause was not a bad architecture. The architecture was sound. The root cause was one line of code: const TTL = 3600; — a fixed, unjittered, round-number TTL applied uniformly to every single cache key during a single warm-up pass. That one constant transformed a gradual cache refresh into a synchronized time-bomb.

Fundamentals

Why Mass TTL Expiry Is Categorically Worse Than a Single Hot-Key Expiry

There is an important distinction between two failure modes that are often conflated in system design discussions. Both are called "cache stampede," but they have different root causes, different magnitudes, and require different solutions.

Single hot-key stampede is the scenario most commonly discussed in interviews: one popular key (the iPhone 16 Pro listing, the homepage hero banner) expires while 50,000 concurrent users are reading it. All 50,000 requests simultaneously miss the cache and hit the database. This is dangerous, but the blast radius is bounded: one key, one query pattern, one table, one row. A mutex lock on that one key serialises the reconstruction and limits the DB to a single query.

Mass simultaneous TTL expiry is what happened in the story above: not one key but tens of thousands or millions of keys all becoming stale at the same moment. The effects are qualitatively different:

  • No single lock can help. A mutex works when all stampede participants are competing to reconstruct the same value. With mass expiry, each expired key has its own unique data to fetch. You would need a separate mutex for every single expired key — and a million simultaneous lock acquisitions creates its own Redis stampede.
  • Every query pattern fires simultaneously. A single hot-key stampede hits one table, one query. Mass expiry hits every query pattern across the entire application — product lookups, inventory checks, user session hydrations, config reads, recommendation fetches — all simultaneously. The database must handle an uncorrelated flood of diverse queries, not a duplicated flood of identical ones.
  • Memory allocation spikes. With millions of cache misses, each application server allocates memory for every in-flight database response simultaneously. Node.js heap usage and Python memory footprints can spike 10–20× in seconds, triggering GC pauses or OOM kills before the database even responds.
  • It cannot be fixed reactively. A single hot-key miss is noticed immediately from a single latency spike. Mass expiry produces a slow-rolling wave that may not be detected in monitoring until the database is already failing — by which point the queue is too deep to drain.

The key intuition: a single hot-key stampede is a spike — intense but targeted. Mass TTL expiry is an avalanche — every wall of the dam collapses simultaneously. The correct counter-measure for mass expiry is jitter, applied before the fact — not locks, applied reactively. You cannot lock your way out of a million simultaneous misses.

Mass expiry is triggered by four common engineering practices that seem reasonable in isolation:

  1. Cache warm-up scripts with a single fixed TTL — as in the story above. The script's sequential nature means keys expire in the same sequence and bunching they were written.
  2. Post-deployment cache flushes — flushing Redis after a code deploy to ensure stale data is cleared, then letting the application repopulate all keys organically. Every user who visits in the next few minutes generates a cache miss.
  3. Batch jobs that write many keys at midnight — nightly ETL jobs that regenerate pricing, rankings, or recommendation scores and write them all at 02:00 AM with a 24-hour TTL. Every night at 02:00 AM, the entire cache turns cold simultaneously.
  4. Feature flags or configuration values cached at application startup — all app servers start simultaneously after a deploy and cache config values with the same TTL. All expire simultaneously one hour later.
Core Solution

TTL Jitter — Formulas, Mathematics, and When to Use Each

Jitter is a random offset applied to a base TTL value to desynchronise the expiry of multiple keys that would otherwise expire at the same time. The concept is simple; the subtlety is in choosing the right jitter formula for the situation. There are three well-established approaches, each with different statistical properties and use cases.

1. Additive Jitter

Additive jitter adds a fixed random window to the base TTL. The formula is:

actual_TTL = TTL_base + random(0, TTL_base × jitter_factor)

Example with 10% jitter: actual_TTL = 3600 + random(0, 360)

Result: expiry times spread uniformly over a 360-second window after the base TTL.

Additive jitter is the most common form and the easiest to reason about. If you write 1,000 keys simultaneously with a base TTL of 3600 and 10% additive jitter, the keys will expire at a roughly uniform rate of ~2.8 keys per second over the 360-second jitter window, instead of all 1,000 expiring in the same second. The database sees approximately 2.8 cache misses per second instead of 1,000 simultaneous misses — a 357× reduction in burst load.

When to use: General purpose. Good default for any caching scenario. The lower bound is the base TTL, so keys are guaranteed to live for at least that long. This matters when your data has a strict minimum freshness requirement.

2. Multiplicative Jitter

Multiplicative jitter scales the random window relative to the base TTL using a multiplier centered on 1.0:

actual_TTL = TTL_base × (1 - jitter_half + random() × jitter_width)

Example: actual_TTL = TTL_base × (0.9 + random() × 0.2)

Result: TTL uniformly distributed in [TTL_base × 0.9, TTL_base × 1.1] — ±10% of base.

Multiplicative jitter centers the distribution around the intended TTL rather than pushing all keys longer. Half the keys will expire slightly before the base TTL; half will expire slightly after. This is more appropriate when the TTL represents a target freshness guarantee and you want equal probability of being early or late.

The practical difference from additive jitter is subtle but important at scale. With additive jitter, your p50 expiry is TTL + 0.05 × jitter_window — slightly longer than intended. With symmetric multiplicative jitter, p50 expiry is exactly TTL_base.

When to use: When TTL represents a data freshness SLA and you need to honor it on average — e.g., "user session data must not be older than 30 minutes on average." Multiplicative jitter keeps the mean expiry at exactly 30 minutes while spreading the distribution to avoid synchronized expiry.

3. AWS-Style Full Jitter

Full jitter, popularized by the AWS Architecture Blog's 2015 article on exponential backoff, does not preserve the base TTL at all. The key expires at a uniformly random time between 0 and the base TTL:

actual_TTL = random(0, TTL_base)

Example: actual_TTL = random(0, 3600)

Result: keys expire uniformly distributed over the entire [0, TTL_base] window.

Mean TTL: TTL_base / 2 — on average, keys live only half as long.

Full jitter provides the absolute maximum desynchronisation — expiry is spread uniformly over the entire TTL window rather than bunched near the end. The cost is that on average you are refreshing twice as often as the base TTL implies, consuming twice the database query budget. Individual keys may expire almost immediately (if random() returns near 0), which can be surprising in debugging.

When to use: Cases where stampede prevention is paramount and the cost of more frequent refreshes is acceptable — for example, cache keys that are very cheap to reconstruct but have extremely high concurrency. Also appropriate for retry backoff timers (the original AWS use case), not just TTL assignment. Not appropriate when your data has a minimum freshness guarantee that must be honored.

JavaScript — All Three Jitter Formulas 
// jitter-strategies.js
// All functions take TTL in seconds, return jittered TTL in seconds

/**
 * Additive jitter: TTL_base + random(0, TTL_base * factor)
 * Guarantees minimum freshness equal to TTL_base.
 * Default factor = 0.10 (10% window)
 */
function additiveJitter(ttlBase, factor = 0.10) {
  const jitterWindow = Math.floor(ttlBase * factor);
  return ttlBase + Math.floor(Math.random() * jitterWindow);
}

/**
 * Multiplicative jitter: TTL_base * (center ± half_range)
 * Symmetric: mean TTL equals TTL_base exactly.
 * Default: ±10% (0.9 to 1.1)
 */
function multiplicativeJitter(ttlBase, halfRange = 0.10) {
  const lowerBound = 1.0 - halfRange;
  const spread = halfRange * 2;
  const multiplier = lowerBound + Math.random() * spread;
  return Math.floor(ttlBase * multiplier);
}

/**
 * Full jitter (AWS-style): random(0, TTL_base)
 * Maximum desynchronization. Mean TTL = TTL_base / 2.
 * Use only when minimum freshness is not required.
 */
function fullJitter(ttlBase) {
  return Math.floor(Math.random() * ttlBase);
}

// Usage examples:
const BASE_TTL = 3600; // 1 hour

console.log('Additive:', additiveJitter(BASE_TTL));
// e.g. 3742 — always >= 3600

console.log('Multiplicative:', multiplicativeJitter(BASE_TTL));
// e.g. 3518 or 3681 — centered around 3600

console.log('Full:', fullJitter(BASE_TTL));
// e.g. 1847 — anywhere from 0 to 3600

// In practice — wrap your Redis SET calls:
async function setWithJitter(redis, key, value, baseTtl, strategy = 'additive') {
  const jitteredTtl = strategy === 'full'
    ? fullJitter(baseTtl)
    : strategy === 'multiplicative'
      ? multiplicativeJitter(baseTtl)
      : additiveJitter(baseTtl);

  await redis.set(key, JSON.stringify(value), 'EX', jitteredTtl);
  return jitteredTtl; // Return for logging/debugging
}

import time
import redis

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

def additive_jitter(ttl_base: int, factor: float = 0.10) -> int:
    """TTL_base + random(0, TTL_base * factor). Minimum = TTL_base."""
    jitter_window = int(ttl_base * factor)
    return ttl_base + random.randint(0, jitter_window)

def multiplicative_jitter(ttl_base: int, half_range: float = 0.10) -> int:
    """TTL_base * (0.9 to 1.1). Mean = TTL_base. Symmetric distribution."""
    lower = 1.0 - half_range
    spread = half_range * 2
    return int(ttl_base * (lower + random.random() * spread))

def full_jitter(ttl_base: int) -> int:
    """random(0, TTL_base). Mean = TTL_base / 2. Maximum desync."""
    return random.randint(0, ttl_base)

def cache_set(key: str, value, base_ttl: int = 3600, strategy: str = 'additive'):
    """Write to Redis with jittered TTL."""
    if strategy == 'multiplicative':
        ttl = multiplicative_jitter(base_ttl)
    elif strategy == 'full':
        ttl = full_jitter(base_ttl)
    else:  # additive
        ttl = additive_jitter(base_ttl)

    r.setex(key, ttl, __import__('json').dumps(value))
    return ttl

    pipeline.execute()
Algorithm

The XFetch Algorithm in Production Context

TTL jitter prevents mass expiry but does not help with individual hot keys that attract extreme concurrent load. For those, the XFetch algorithm (published at VLDB 2015 by Vattani, Chiariotti, and Tolomei) provides probabilistic early refresh — a single node proactively rebuilds the cache value before it expires, eliminating any miss window.

The full XFetch condition, checked on every cache read, is:

XFetch condition:
current_time - (delta × beta × ln(random())) >= expiry

Where delta is the measured time to fetch the value from the database (in seconds), beta is a tuning parameter (default 1.0), and expiry is the UNIX timestamp at which the cache entry expires.

Since ln(random()) for random in (0, 1) is always negative, the term -delta × beta × ln(random()) is always positive, making the left-hand side always greater than current_time. The gap to expiry shrinks as time passes; the probability that the positive offset bridges the gap rises accordingly.

The key production insight missed in textbook explanations is the tight coupling between delta and the TTL jitter strategy. XFetch works per-key, probabilistically. Jitter works at population level, deterministically. They solve different parts of the problem:

  • Jitter prevents 1.4 million keys from expiring in the same second (population-level problem).
  • XFetch prevents the single product page with 200,000 concurrent readers from generating a stampede when its individual TTL arrives (hot-key problem).
  • You need both, applied at different layers.

The storage format for XFetch requires three fields alongside the cached value. In Redis, this is typically stored as a JSON string or a Redis Hash:

JavaScript — XFetch with Jitter Integration 
// xfetch-production.js
import Redis from 'ioredis';
const redis = new Redis(process.env.REDIS_URL);

/**
 * XFetch read-through cache.
 * Combines probabilistic early refresh (XFetch) with additive jitter on write.
 *
 * Stored payload shape: { value, delta, expiry }
 *   - value:  the cached data
 *   - delta:  seconds it took to fetch from DB (for XFetch formula)
 *   - expiry: UNIX timestamp (seconds) when the entry expires
 */
async function xfetchGet(key, fetchFn, baseTtl = 3600, beta = 1.0) {
  const raw = await redis.get(key);

  if (raw !== null) {
    const { value, delta, expiry } = JSON.parse(raw);
    const now = Date.now() / 1000; // UNIX seconds

    // XFetch condition: current_time - delta*beta*ln(rand) >= expiry
    const xfetchScore = now - delta * beta * Math.log(Math.random());

    if (xfetchScore >= expiry) {
      // Proactive refresh — fire-and-forget, return current value immediately
      // This is the critical production detail: the user sees NO latency penalty
      setImmediate(() =>
        writeToCache(key, fetchFn, baseTtl).catch(err =>
          console.error(`[xfetch] background refresh failed for ${key}:`, err)
        )
      );
    }

    return value; // Always return current value — never block the request
  }

  // True cold miss — synchronous fetch, then write
  return writeToCache(key, fetchFn, baseTtl);
}

async function writeToCache(key, fetchFn, baseTtl) {
  const fetchStart = Date.now();
  const value = await fetchFn();
  const delta = (Date.now() - fetchStart) / 1000; // seconds

  // Additive jitter: 10% window
  const jitter = Math.floor(Math.random() * baseTtl * 0.10);
  const actualTtl = baseTtl + jitter;
  const expiry = Date.now() / 1000 + actualTtl;

  const payload = JSON.stringify({ value, delta, expiry });
  await redis.set(key, payload, 'EX', actualTtl);
  return value;
}

// Usage:
const product = await xfetchGet(
  `product:${productId}`,
  () => db.query('SELECT * FROM products WHERE id = $1', [productId]),
  3600,   // base TTL: 1 hour
  1.0     // beta: 1.0 = optimal per VLDB paper
);

In the production outage story, XFetch alone would not have saved the system — because the problem was mass expiry of unique keys, not a hot single key. But adding XFetch as a second layer means that even after jitter has spread the expiry wave, the most popular individual products (which attract the highest concurrent load) receive an additional layer of protection when their individual TTL approaches.

Architecture

Multi-Level Caching: L1, L2, L3 Architecture

Even a Redis cluster with microsecond read latency can become a bottleneck at extreme concurrency. If your application has 20 instances each serving 5,000 requests per second, and every request requires one Redis lookup, you are issuing 100,000 Redis operations per second. Redis handles this comfortably — but the network round-trip (even at 0.3ms per hop) adds up: 100,000 × 0.3ms = 30 CPU-seconds of wait time per second across the fleet.

The solution is multi-level caching — a hierarchy of three stores, each with different latency, capacity, and scope:

L1: In-Process Cache (Nanoseconds)

An in-process LRU (Least Recently Used) cache lives in the same memory space as the application. There is no network hop, no serialisation — just a hash map lookup in process memory. This is the fastest possible cache.

  • Latency: 50–500 nanoseconds (memory access)
  • Capacity: bounded by process heap — typically 64MB–512MB
  • Scope: per-process only — each application instance has its own L1
  • TTL: short — 1–30 seconds. Stale data risk is highest here.
  • Node.js: lru-cache npm package
  • Python: functools.lru_cache (size-bounded) or cachetools.TTLCache
  • Java: Caffeine or Guava Cache

The critical L1 tradeoff is data consistency across instances. If you have 20 app servers and a product price changes, up to 20 separate L1 caches may hold the stale price for up to the L1 TTL (e.g., 10 seconds). For most applications, this is acceptable. For financial or inventory data, it may not be.

L2: Shared Redis Cluster (Microseconds)

Redis is the canonical L2 cache: all application instances share it, so a write from one instance is immediately visible to all others. This is the primary cache tier for most production systems.

  • Latency: 0.1–2 milliseconds (network round-trip to local Redis)
  • Capacity: bounded by Redis cluster memory — typically GBs to TBs
  • Scope: shared across all application instances in the cluster
  • TTL: medium — minutes to hours. Jitter applied here.

L3: Database (Milliseconds)

The database (PostgreSQL, MySQL, DynamoDB) is the source of truth. All cache misses eventually fall through to L3. This tier is expensive, has limited connection pools, and must be protected at all costs.

  • Latency: 5–500 milliseconds depending on query complexity and index usage
  • Capacity: effectively unlimited (bounded by storage, not memory)
  • Scope: single source of truth for all instances
  • TTL: no TTL — the data lives here permanently until mutated

Three-Tier Lookup Code

The lookup order is always L1 → L2 → L3 (fast to slow). The write-back order is always L3 → L2 → L1 (authoritative to derived). On a write, you update the database first (L3), then invalidate or update L2 Redis, then invalidate L1 on each instance (via pub/sub or short TTL expiry).

JavaScript — Three-Level Cache Lookup 
// multi-level-cache.js
import { LRUCache } from 'lru-cache';
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL);

// L1: In-process LRU cache
// max 500 items, each lives at most 15 seconds in-process
const l1Cache = new LRUCache({
  max: 500,
  ttl: 15_000,  // 15 seconds in milliseconds
  ttlAutopurge: false,  // Lazy eviction — only purge on access
});

// L2: Redis (configured externally)
// L3: Database client (configured externally)

const L2_BASE_TTL = 3600;      // 1 hour base
const L2_JITTER_FACTOR = 0.10; // ±10% jitter window

function jitteredTtl(base = L2_BASE_TTL) {
  return base + Math.floor(Math.random() * base * L2_JITTER_FACTOR);
}

/**
 * Multi-level cache read: L1 → L2 → L3
 * Populates higher-level caches on miss (write-back).
 */
async function getProduct(productId) {
  const l1Key = `product:${productId}`;

  // ── L1 lookup (in-process, nanoseconds) ──────────────────────────────────
  const l1Hit = l1Cache.get(l1Key);
  if (l1Hit !== undefined) {
    // metrics.increment('cache.l1.hit');
    return l1Hit;
  }
  // metrics.increment('cache.l1.miss');

  // ── L2 lookup (Redis, microseconds) ─────────────────────────────────────
  const l2Raw = await redis.get(l1Key);
  if (l2Raw !== null) {
    const parsed = JSON.parse(l2Raw);
    // Populate L1 from L2 (short TTL — 15s)
    l1Cache.set(l1Key, parsed);
    // metrics.increment('cache.l2.hit');
    return parsed;
  }
  // metrics.increment('cache.l2.miss');

  // ── L3 lookup (database, milliseconds) ──────────────────────────────────
  // metrics.increment('cache.l3.query');
  const product = await db.query(
    'SELECT id, name, price, inventory FROM products WHERE id = $1',
    [productId]
  );
  if (!product.rows[0]) return null;

  const data = product.rows[0];

  // Write-back: populate L2 with jitter, then L1
  const ttl = jitteredTtl();
  await redis.set(l1Key, JSON.stringify(data), 'EX', ttl);
  l1Cache.set(l1Key, data);

  return data;
}

/**
 * Multi-level cache invalidation: database write → L2 del → L1 del
 * Always invalidate from source-of-truth outward.
 */
async function updateProduct(productId, updates) {
  // 1. Write to database (L3) — source of truth
  await db.query(
    'UPDATE products SET price = $1, inventory = $2 WHERE id = $3',
    [updates.price, updates.inventory, productId]
  );

  // 2. Invalidate L2 (Redis) — all instances will miss on next read
  const key = `product:${productId}`;
  await redis.del(key);

  // 3. Invalidate L1 on all instances via Redis pub/sub
  // Each app server listens to 'cache:invalidate' channel and clears its L1
  await redis.publish('cache:invalidate', JSON.stringify({ key }));
}

// Subscribe to invalidation events (run once per process at startup)
function subscribeToInvalidations() {
  const subscriber = redis.duplicate();
  subscriber.subscribe('cache:invalidate');
  subscriber.on('message', (channel, message) => {
    const { key } = JSON.parse(message);
    l1Cache.delete(key); // Evict from this process's L1
    // console.log(`[L1 invalidated] ${key}`);
  });
}
Python — Three-Level Cache with TTLCache and Redis 
# multi_level_cache.py
import json
import time
import redis
from cachetools import TTLCache
from threading import Lock

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

# L1: thread-safe in-process TTL cache
# Holds at most 1000 items, each for 15 seconds
_l1_cache = TTLCache(maxsize=1000, ttl=15)
_l1_lock = Lock()  # TTLCache is not thread-safe; protect with lock

L2_BASE_TTL = 3600

def _jittered_ttl(base: int = L2_BASE_TTL, factor: float = 0.10) -> int:
    import random
    return base + random.randint(0, int(base * factor))

def get_product(product_id: str) -> dict | None:
    cache_key = f"product:{product_id}"

    # L1: in-process cache (nanoseconds)
    with _l1_lock:
        if cache_key in _l1_cache:
            return _l1_cache[cache_key]

    # L2: Redis (microseconds)
    raw = r.get(cache_key)
    if raw is not None:
        data = json.loads(raw)
        with _l1_lock:
            _l1_cache[cache_key] = data  # Populate L1
        return data

    # L3: Database (milliseconds)
    # data = db.execute("SELECT * FROM products WHERE id = %s", (product_id,))
    data = fetch_from_db(product_id)  # your DB fetch fn
    if data is None:
        return None

    # Write-back: L3 → L2 → L1
    ttl = _jittered_ttl()
    r.setex(cache_key, ttl, json.dumps(data))
    with _l1_lock:
        _l1_cache[cache_key] = data

    return data

def update_product(product_id: str, updates: dict) -> None:
    """Invalidate from source of truth outward: L3 → L2 → L1."""
    cache_key = f"product:{product_id}"

    # 1. Persist to database (L3)
    save_to_db(product_id, updates)

    # 2. Delete from Redis (L2)
    r.delete(cache_key)

    # 3. Invalidate L1 locally (pub/sub handles remote instances)
    with _l1_lock:
        _l1_cache.pop(cache_key, None)

    # Publish invalidation to other instances
    r.publish('cache:invalidate', json.dumps({'key': cache_key}))

L1 Cache: The Consistency-Latency Tradeoff

The L1 cache trades consistency for latency. For a 15-second L1 TTL across 20 app servers, after a product price update, up to 20 × 15 = 300 person-seconds of stale price serves will occur before all L1 caches naturally expire. The pub/sub invalidation above reduces this to near-zero for most cases, but pub/sub delivery is not guaranteed under network partitions.

Engineering judgment is required:

  • Product descriptions, images, non-financial metadata: 30-second L1 TTL, no pub/sub needed.
  • Product prices, discount percentages: 5-second L1 TTL + pub/sub invalidation.
  • Inventory counts: Skip L1 entirely — serve from Redis directly. Inventory stale data causes overselling.
  • User authentication tokens: Skip L1 — security-sensitive, must be authoritative.
Pattern

Request Coalescing: The Single-Flight Pattern

TTL jitter and multi-level caching solve the mass-expiry problem and reduce per-request latency. But they do not fully solve the case where a single expensive cache key expires during a burst of concurrent requests all targeting the same key. For that scenario, the single-flight pattern (also called request coalescing or request deduplication) is the most elegant solution.

The idea is simple: if 1,000 requests simultaneously ask for the same cache key and the cache is cold, only one of those requests should issue the database query. The other 999 should wait in-process for that one query to complete, then share its result. There is no distributed coordination required — this is a per-process, in-memory deduplication.

Single-flight in Go: The golang.org/x/sync/singleflight package implements this pattern natively. In Go, it is idiomatic and widely used. In JavaScript, it is implemented manually using a Promise map. In Java, it can be implemented with CompletableFuture and a ConcurrentHashMap.

JavaScript — Single-Flight / Request Coalescing 
// single-flight.js
// A per-process in-flight request deduplicator.
// Guarantees that only one DB call is in-flight at a time per unique key.

class SingleFlight {
  constructor() {
    // Map from cache key → Promise of in-flight fetch
    this._inFlight = new Map();
  }

  /**
   * If a fetch for `key` is already in-flight, join it.
   * Otherwise, start a new fetch. All callers waiting on the same key
   * receive the same resolved value from a single database call.
   *
   * @param {string}   key     Cache key (used as dedup key)
   * @param {Function} fetchFn Async function that fetches from DB
   * @returns {Promise}   Resolved value (shared across all waiters)
   */
  async do(key, fetchFn) {
    // If a fetch is already in-flight for this key, join it
    if (this._inFlight.has(key)) {
      return this._inFlight.get(key);
    }

    // Start a new fetch — all future callers will join this promise
    const promise = fetchFn().finally(() => {
      // Clean up after the fetch completes (success or failure)
      this._inFlight.delete(key);
    });

    this._inFlight.set(key, promise);
    return promise;
  }
}

// Singleton per process
const singleFlight = new SingleFlight();

// Integration with the multi-level cache:
async function getProductWithCoalescing(productId) {
  const cacheKey = `product:${productId}`;

  // Check L1 first (no coalescing needed — nanosecond lookup)
  const l1Hit = l1Cache.get(cacheKey);
  if (l1Hit) return l1Hit;

  // Check L2 (Redis) — no coalescing needed, Redis handles concurrency
  const l2Raw = await redis.get(cacheKey);
  if (l2Raw) {
    const data = JSON.parse(l2Raw);
    l1Cache.set(cacheKey, data);
    return data;
  }

  // L2 miss → use single-flight for L3 (database) call
  // Even with 10,000 concurrent requests for the same cold key,
  // only ONE database query will execute. The rest wait and share the result.
  return singleFlight.do(cacheKey, async () => {
    const rows = await db.query(
      'SELECT * FROM products WHERE id = $1',
      [productId]
    );
    const data = rows[0] ?? null;

    if (data) {
      const ttl = additiveJitter(3600);
      await redis.set(cacheKey, JSON.stringify(data), 'EX', ttl);
      l1Cache.set(cacheKey, data);
    }

    return data;
  });
}

// Benchmark example — single-flight prevents database overload:
// Without single-flight: 10,000 concurrent requests → 10,000 DB queries
// With single-flight:    10,000 concurrent requests → 1 DB query
//                        The other 9,999 wait ~12ms for the one query to complete
Go — Single-Flight Using golang.org/x/sync/singleflight 
// product_cache.go
package cache

import (
    "context"
    "encoding/json"
    "time"

    "github.com/go-redis/redis/v8"
    "golang.org/x/sync/singleflight"
)

type ProductCache struct {
    redis  *redis.Client
    group  singleflight.Group
    db     DB
}

func (c *ProductCache) GetProduct(ctx context.Context, productID string) (*Product, error) {
    cacheKey := "product:" + productID

    // L2: Try Redis first
    raw, err := c.redis.Get(ctx, cacheKey).Result()
    if err == nil {
        var product Product
        json.Unmarshal([]byte(raw), &product)
        return &product, nil
    }

    // L2 miss: use singleflight to deduplicate DB calls
    // If 50,000 goroutines are waiting for this key, singleflight
    // ensures exactly ONE db.GetProduct() call fires.
    result, err, _ := c.group.Do(cacheKey, func() (interface{}, error) {
        product, err := c.db.GetProduct(ctx, productID)
        if err != nil {
            return nil, err
        }

        // Write back to Redis with jitter
        data, _ := json.Marshal(product)
        ttl := time.Duration(3600+rand.Intn(360)) * time.Second
        c.redis.Set(ctx, cacheKey, data, ttl)

        return product, nil
    })

    if err != nil {
        return nil, err
    }

    return result.(*Product), nil
}

Single-flight is particularly powerful in Go because the language's goroutine model means many thousands of goroutines can cheaply block on a channel waiting for a shared result. In JavaScript, the Promise-based implementation achieves the same effect via the event loop. In Python, an asyncio.Event or asyncio.shield achieves the same pattern in async code.

The limitation of single-flight is that it is per-process. If you have 20 application servers and a key goes cold simultaneously, each server will issue one database query — for a total of 20 queries, not 1. For truly extreme traffic, combine single-flight (per-process) with a distributed mutex (cross-process) for the L3 fallback. In practice, 20 queries instead of 200,000 queries is still a 10,000× improvement, and the additional complexity of a distributed mutex is rarely justified.

Advanced

Invalidation Cascade Strategy

Multi-level caching introduces a new problem: when data changes, how do you ensure all three cache tiers reflect the change promptly? Stale data sitting in L1 across 20 app servers can cause subtle bugs — users seeing old prices, ghost inventory, outdated permissions.

The canonical strategy is event-driven invalidation via a message bus:

  1. Write completes at L3 (database). The application, a CDC (Change Data Capture) connector, or a database trigger emits a product.updated event to Kafka or Redis Pub/Sub.
  2. L2 (Redis) invalidation. The event consumer deletes or updates the Redis key. All subsequent L2 reads will miss and fall through to L3.
  3. L1 invalidation across all instances. The event consumer publishes to a Redis Pub/Sub channel (cache:invalidate). Every app server process subscribes and immediately evicts the key from its in-process L1 cache.

Invalidation vs. update: prefer invalidation (delete the key) over in-place update (write the new value) for L2 and L1. Invalidation is simpler, avoids races between the write and a concurrent read, and ensures the next reader fetches fresh data from L3 directly. The only exception is when you have a high-frequency write pattern and can tolerate brief read amplification — in that case, update-in-place avoids the L3 fallback read.

The weak point of pub/sub invalidation is delivery guarantees. Redis Pub/Sub is fire-and-forget: if a subscriber is temporarily disconnected or lagged, it misses the invalidation message. The mitigation is a short L1 TTL (15–30 seconds) as a backstop — even if the pub/sub message is lost, the L1 entry will expire naturally within 30 seconds, bounding the stale-data window. This is an intentional design choice: pub/sub for fast-path invalidation, TTL for guaranteed eventual consistency.

For stricter consistency requirements (financial data, access control lists), skip L1 entirely and serve directly from L2 (Redis). Redis provides sufficient latency for most financial systems (sub-millisecond reads from a local cluster), and it is a shared, centralised store that can be invalidated with strong consistency.

Checklist

Production Checklist: 8 Things to Validate Before a Flash Sale

The following checklist captures the lessons from the production outage story and the technical deep dive above. Run through all eight before any high-traffic event.

  • Audit your cache warm-up script. Does it use a fixed TTL? If so, change it to use additive jitter of at least 10–15% of the base TTL. A warm-up script that writes 500,000 keys in 30 minutes will cause those 500,000 keys to expire in the same 30-minute window 1 TTL later — directly reproducing the production outage scenario.
  • Scan Redis for round-number TTLs. Run redis-cli --scan --pattern '*' | xargs -L 1 redis-cli TTL and check the TTL distribution. If you see thousands of keys with the exact same TTL remaining, you have a synchronized expiry bomb. Jitter them now with a read-and-rewrite pass.
  • Validate your L1 cache TTL is short and bounded. In-process caches that grow unboundedly or have multi-minute TTLs are consistency landmines. L1 TTL should be 5–30 seconds with a fixed maximum item count. Measure the heap overhead under peak load before the flash sale begins.
  • Test the single-flight behavior under synthetic load. Spin up a Redis instance with 0 keys and hammer a single cold key with 10,000 concurrent requests. Count how many database queries are executed. The answer should be 1 (or 1 per app server instance). If it is not, your single-flight implementation has a bug.
  • Set a database connection pool limit lower than the database's max. If your PostgreSQL server supports 800 connections and your application pool is also configured at 800, a cache-miss storm will exhaust every connection and begin queuing at the database layer itself — causing the "slow query feedback loop" where pool connections are held for longer, growing the queue. Set the application pool to 60–70% of the database maximum to leave headroom.
  • Configure and test your circuit breaker. Open the circuit breaker manually (simulate Redis failure), confirm the application falls back to L3 with rate limiting (not a 10,000-QPS DB blast), and confirm the breaker half-opens and closes correctly when Redis is restored. Circuit breaker behavior is notoriously easy to misconfigure.
  • Add cache-hit-rate monitoring with per-tier visibility. Instrument your cache layer to emit cache.l1.hit, cache.l1.miss, cache.l2.hit, cache.l2.miss, and cache.l3.query metrics. Alert when cache.l2.hit drops below your baseline (e.g., <90%). A cache miss rate spike is a leading indicator of an impending stampede — it will appear in your cache metrics minutes before it shows up as database CPU alarms.
  • Load test with a cold cache, not a warm one. Most load tests pre-warm the cache before sending traffic. This makes them useless for validating cold-start behavior. Run at least one load test with Redis completely flushed at the start of the traffic ramp. Measure how long it takes for the cache to reach target hit rate, and validate that the database survives the cold-start window without exceeding 70% connection pool utilization.

Production layering recommendation: Start with additive jitter on every cache write (zero overhead, eliminates batch-expiry risk). Add XFetch for all high-traffic cache reads (low overhead, handles individual hot keys). Add single-flight to the L3 fallback path (prevents per-process miss storms). Add circuit breaker on L3 (prevents full outage). Layer in L1 in-process cache after the above are validated and only for keys with acceptable consistency tradeoffs.

Production Gotchas

Failure Modes and Common Mistakes

  • Jitter too small for the key population. Adding ±30 seconds of jitter to 1 million keys sounds reasonable — but if those keys were written in a 30-second window (fast warm-up script), they expire over a 60-second window (30 original spread + 30 jitter). At 1M keys / 60s, that is still 16,667 expirations per second. For large key populations, calculate the required jitter window: target <100 expirations/second means you need at least key_count / 100 seconds of jitter window.
  • L1 cache causing memory pressure under load. An unbounded or large-bounded L1 cache can cause application server OOMs during traffic spikes. Each cache entry holds the deserialized object in heap. Under a traffic spike where many cold keys are fetched and written to L1, heap usage climbs rapidly. Set a hard item count maximum (e.g., 1000 items) and validate the p99 heap size under load test before enabling L1 in production.
  • Single-flight leaking errors to all waiters. If the one in-flight database query returns an error, the single-flight implementation shares that error with all 9,999 waiting callers simultaneously. Depending on your error handling, this can cause a large burst of error-path logic (retries, alerts, logging) to fire simultaneously — a different kind of stampede. Test your error paths explicitly.
  • Cache invalidation pub/sub message ordering. If a product is updated twice in rapid succession (price correction immediately followed by another update), there is a risk of the invalidation messages being processed out of order on some subscribers. If your L1 invalidation handler re-fetches from Redis on invalidation (rather than just deleting), it may fetch and cache the first version after the second update has already been written. Design invalidation as delete-only, not update-on-invalidation.
  • Forgetting to jitter your background refresh scheduler. A scheduled job that refreshes 100,000 hot keys every 5 minutes, if it runs at exactly 00:00, 05:00, 10:00, will write 100,000 keys with the same actual write timestamp. Even if you apply jitter at write time, the batch is still completed within a short window — and all 100,000 keys expire within that same jitter window. Add a sleep between batches within the job, or offset the job's start time by a random amount each run.
Takeaways

Key Takeaways

The production outage in this story was caused by a single constant: TTL = 3600 applied uniformly to 1.4 million cache keys during a sequential warm-up pass. That one decision made the entire cache layer a time-bomb that detonated exactly one hour after warm-up completed. The fix — additive jitter at 10–15% of the base TTL — is two lines of code. The architectural lesson it teaches takes 22 minutes to read and understand.

Mass TTL expiry and single-key hot-key stampedes are distinct problems requiring distinct solutions. Jitter (additive, multiplicative, or full) solves mass expiry at the population level. XFetch solves the individual hot-key problem without coordination. Single-flight handles the per-process concurrent miss storm. These are complementary, not competing — a production caching layer deploys all three together.

Multi-level caching (L1 in-process → L2 Redis → L3 database) is the correct architecture for extreme scale, but it introduces consistency complexity that must be managed explicitly. The invalidation cascade — event-driven from L3 outward, with pub/sub for L1 and TTL as the guaranteed-consistency backstop — is the right pattern. The L1 TTL should be short (5–30 seconds) and bounded by item count to prevent heap pressure.

The most important operational practice is instrumentation. Cache hit rate per tier (l1.hit, l2.hit, l3.query) is a leading indicator of a stampede developing, appearing minutes before database CPU or connection pool alarms. Monitor it in real time. Alert on significant drops. Treat a sudden cache miss rate spike as a P1 incident before the database feels it — because once the database is overwhelmed, the window to intervene gracefully has already closed.
