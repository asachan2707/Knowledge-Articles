Forget Loop Engineering. Graph Engineering Is About THIS

Loop engineering — the idea of structuring AI work as an autonomous cycle of discover → execute → verify → record → repeat — was the dominant paradigm for agentic AI in 2024–2025. It works beautifully for solo tasks. It falls apart the moment real-world complexity enters: multiple participants, task dependencies, approval gates, and conditional branches. Graph engineering replaces the loop with a structured dependency graph that can represent exactly the organizational complexity that loops cannot. This article explains the shift, the data model behind it, and how to implement it in JavaScript.

Source: GaoDalie_AI · Medium · 2026 Domain: AI · Agents · Agentic Engineering Published: 2026-08-05

The failure mode of loop engineering is not intelligence — it is structure. A loop agent can be brilliant at each individual step and still fail the overall task because it cannot represent the organizational dependencies between steps: "step B cannot start until step A completes AND a human approves it; step C must run only if step B returned a certain result; step D and E can run in parallel after C." A linear loop cannot encode these relationships. A directed acyclic graph (DAG) can.

Core idea: The organizational structure of a complex task is a graph, not a loop. Graph engineering is the discipline of making that structure explicit — encoding it as nodes (work items) and edges (dependencies, conditions, approvals) — so that the agent executing the work has a clear map, not just a next-step instruction.

Story · The Loop That Could Not Hire an Engineer

When a Brilliant Agent Failed a 5-Step HR Workflow

A team at a mid-size tech company built a loop-engineering agent to automate their engineering hiring workflow: source candidates → screen resumes → schedule interviews → collect feedback → extend offer. Each step worked perfectly in isolation. The agent could source 50 qualified candidates, screen them down to 10, and generate interview schedules beautifully.

The loop kept breaking in production. It would complete "schedule interviews" before all five interviewers had confirmed availability. It would "collect feedback" and then immediately generate an offer — without waiting for the engineering VP to review the feedback. It extended conditional offers before legal had cleared the candidate's background check (which ran in parallel). When a candidate declined, the loop did not know to go back to the 10-candidate shortlist — it restarted from sourcing.

The root cause was not the agent's quality. Every individual capability was excellent. The root cause was that the hiring process is a graph, not a loop. "Schedule interviews" has a dependency on "all 5 interviewers respond." "Extend offer" has a dependency on "feedback collected AND VP approval AND background check cleared." These are not sequential steps in a loop — they are nodes in a DAG with conditional edges, parallel branches, and human-in-the-loop approval gates.

When the team rebuilt it as a graph — with each step as a node, each dependency as an edge, and human approvals as gate nodes — the agent stopped making premature decisions. It knew exactly which nodes were ready (all predecessors complete), which were blocked (waiting on approvals), and which had branched differently than expected. The workflow completed successfully within two weeks of the rebuild.

Analysis

Why Loop Engineering Breaks at Organizational Complexity

Loop engineering was designed for single-agent, single-task workflows. It is optimal for: "Write tests for this codebase" or "Research this topic and summarize" — tasks where one agent cycles through a single sequence of steps to completion.

It breaks when real-world work involves:

  • Multiple participants (multi-agent). A loop has one actor. A hiring process has a recruiter agent, an interviewer agent, a background check system, and a VP as a human approver. A loop architecture cannot natively coordinate multiple actors with different permissions and capabilities.
  • Conditional branches. "If the candidate accepts, proceed to onboarding. If they decline, go back to the shortlist and offer to the next candidate." A loop either repeats or stops — it cannot branch based on a prior step's outcome.
  • Parallel work items. Background check and technical assessment can run simultaneously after the phone screen. A sequential loop cannot exploit this — it must process steps in order, leaving parallelism on the table.
  • Human approval gates. The VP must approve before the offer is sent. The loop has no native concept of "pause until external approval arrives" — it either polls (wasteful) or times out (broken).
  • Exception paths. If the background check fails, the workflow must go to a different branch (notify recruiter, re-evaluate shortlist) rather than continuing to the next sequential step.

Peter Steinberger's observation (OpenClaw, July 2026): "The agents aren't getting smarter fast enough to brute-force their way through organizational complexity. The bottleneck is never the intelligence — it is the structure. Give an agent a clear graph of dependencies and it executes reliably. Give it a vague instruction and a loop and it makes structurally wrong decisions even when each individual decision is locally correct."

Architecture

The Graph Data Model: Nodes, Edges, and States

A graph-engineered workflow is a directed acyclic graph (DAG) where:

Work Node
A unit of work executed by an agent (or human). Has an input schema (what the node needs to run), an execution function (what it does), and an output schema (what it produces).
Gate Node
A human or system approval step. The workflow pauses here until the gate condition is satisfied (approval received, SLA met, external system confirms). Downstream nodes cannot start until the gate opens.
Branch Node
Evaluates a condition and routes to one of several downstream paths. The branch logic is explicit (a JS function), not implicit in the agent's reasoning.
Parallel Fan-Out
Triggers multiple downstream nodes simultaneously. Downstream nodes share no state and can be executed by different agents in parallel. A join node (all-predecessors-complete) merges results.

Node States

StateMeaningNext transition
pendingNot yet runnable — predecessors incomplete→ ready when all predecessors succeed
readyAll predecessors complete; runnable now→ running when executor picks it up
runningAgent is executing→ success or failed
successCompleted; output available→ triggers successors to check readiness
failedExecution failed→ retry (if configured) or triggers exception path
skippedBranch condition excluded this path→ successors of this branch are also skipped
waiting_approvalGate node awaiting human input→ approved/rejected by gate handler
Implementation

Building a Graph Execution Engine in JavaScript

JavaScript — Graph Workflow Engine 
// graph-workflow-engine.js
// Minimal DAG execution engine for agentic workflows.
// Supports parallel execution, conditional branches, and approval gates.

const NODE_STATES = {
  PENDING: 'pending',
  READY: 'ready',
  RUNNING: 'running',
  SUCCESS: 'success',
  FAILED: 'failed',
  SKIPPED: 'skipped',
  WAITING_APPROVAL: 'waiting_approval',
};

export class WorkflowGraph {
  constructor() {
    this._nodes = new Map();   // id → node definition
    this._edges = new Map();   // id → Set of successor ids
    this._parents = new Map(); // id → Set of predecessor ids
    this._state = new Map();   // id → { status, output, error, startedAt, completedAt }
    this._approvalCallbacks = new Map(); // id → { resolve, reject }
  }

  /**
   * Add a work node.
   * @param {string}   id         - Unique node identifier
   * @param {Function} executeFn  - async (inputs) => output
   * @param {Object}   opts
   * @param {string[]} opts.deps  - Array of predecessor node ids
   * @param {string}   opts.type  - 'work' | 'gate' | 'branch' (default: 'work')
   * @param {Function} opts.branchFn - For type='branch': (input) => 'pathA' | 'pathB'
   */
  addNode(id, executeFn, { deps = [], type = 'work', branchFn = null } = {}) {
    this._nodes.set(id, { id, type, executeFn, branchFn });
    this._edges.set(id, new Set());
    this._parents.set(id, new Set(deps));
    this._state.set(id, { status: NODE_STATES.PENDING, output: null, error: null });

    // Register this node as a successor of each dependency
    for (const dep of deps) {
      if (!this._edges.has(dep)) this._edges.set(dep, new Set());
      this._edges.get(dep).add(id);
    }
  }

  /** Approve a waiting gate node. */
  approveGate(nodeId, approvalData = {}) {
    const cb = this._approvalCallbacks.get(nodeId);
    if (cb) {
      this._approvalCallbacks.delete(nodeId);
      cb.resolve(approvalData);
    }
  }

  /** Reject a waiting gate node (triggers failure path). */
  rejectGate(nodeId, reason = 'Rejected') {
    const cb = this._approvalCallbacks.get(nodeId);
    if (cb) {
      this._approvalCallbacks.delete(nodeId);
      cb.reject(new Error(reason));
    }
  }

  /** Collect outputs from predecessor nodes. */
  _gatherInputs(nodeId) {
    const inputs = {};
    for (const parentId of this._parents.get(nodeId)) {
      const parentState = this._state.get(parentId);
      if (parentState?.status === NODE_STATES.SUCCESS) {
        inputs[parentId] = parentState.output;
      }
    }
    return inputs;
  }

  /** Check if all predecessors are complete (success or skipped). */
  _isReady(nodeId) {
    for (const parentId of this._parents.get(nodeId)) {
      const status = this._state.get(parentId)?.status;
      if (status !== NODE_STATES.SUCCESS && status !== NODE_STATES.SKIPPED) {
        return false;
      }
    }
    return true;
  }

  async _executeNode(nodeId) {
    const node = this._nodes.get(nodeId);
    const state = this._state.get(nodeId);
    state.status = NODE_STATES.RUNNING;
    state.startedAt = Date.now();

    try {
      const inputs = this._gatherInputs(nodeId);

      let output;

      if (node.type === 'gate') {
        // Gate: pause and wait for external approval
        state.status = NODE_STATES.WAITING_APPROVAL;
        // Notify the approval handler (webhook, UI, etc.)
        await node.executeFn(inputs); // This should send notification
        output = await new Promise((resolve, reject) => {
          this._approvalCallbacks.set(nodeId, { resolve, reject });
        });
      } else if (node.type === 'branch') {
        // Branch: run the branch condition, skip one path
        const inputs2 = this._gatherInputs(nodeId);
        const branchResult = await node.branchFn(inputs2);
        output = { branch: branchResult };
        // Mark the non-taken branch successors as skipped
        for (const successorId of this._edges.get(nodeId)) {
          if (successorId !== branchResult) {
            this._markSkipped(successorId);
          }
        }
      } else {
        // Normal work node
        output = await node.executeFn(inputs);
      }

      state.status = NODE_STATES.SUCCESS;
      state.output = output;
      state.completedAt = Date.now();
    } catch (err) {
      state.status = NODE_STATES.FAILED;
      state.error = err.message;
      state.completedAt = Date.now();
      throw err;
    }

    return state.output;
  }

  _markSkipped(nodeId) {
    this._state.get(nodeId).status = NODE_STATES.SKIPPED;
    // Recursively skip all successors
    for (const successorId of this._edges.get(nodeId)) {
      this._markSkipped(successorId);
    }
  }

  /** Execute all ready nodes concurrently until the graph is complete. */
  async run() {
    // Initialize root nodes (no dependencies) as ready
    for (const [id] of this._nodes) {
      if (this._parents.get(id).size === 0) {
        this._state.get(id).status = NODE_STATES.READY;
      }
    }

    while (true) {
      // Find all ready nodes
      const readyNodes = [...this._nodes.keys()].filter(
        id => this._state.get(id).status === NODE_STATES.READY
      );

      if (readyNodes.length === 0) {
        // Check if done or deadlocked
        const pending = [...this._nodes.keys()].filter(id => {
          const s = this._state.get(id).status;
          return s === NODE_STATES.PENDING || s === NODE_STATES.RUNNING;
        });
        if (pending.length === 0) break; // All nodes terminal
        // Still running — wait for in-progress nodes to complete
        await new Promise(r => setTimeout(r, 50));
        continue;
      }

      // Execute all ready nodes in parallel
      await Promise.allSettled(readyNodes.map(async id => {
        this._state.get(id).status = NODE_STATES.RUNNING;
        try {
          await this._executeNode(id);
          // On success, check if any successors became ready
          for (const successorId of this._edges.get(id)) {
            if (this._isReady(successorId)) {
              this._state.get(successorId).status = NODE_STATES.READY;
            }
          }
        } catch {
          // Failed — successors remain PENDING (blocked)
        }
      }));
    }

    return Object.fromEntries(
      [...this._nodes.keys()].map(id => [id, this._state.get(id)])
    );
  }
}
JavaScript — Hiring Workflow as a Graph 
// hiring-workflow.js
// The hiring process encoded as a dependency graph.
// Parallel: background check + technical assessment run concurrently after phone screen.
// Gate: VP must approve before offer is extended.

import { WorkflowGraph } from './graph-workflow-engine.js';
import { callAgent } from './agent-runner.js';

export async function runHiringWorkflow(candidateId) {
  const graph = new WorkflowGraph();

  // Step 1: Source and screen (sequential, no deps)
  graph.addNode('source', async () => {
    return callAgent('Find top 50 engineers with background in distributed systems', { candidateId });
  });

  graph.addNode('screen', async ({ source }) => {
    return callAgent('Screen and rank candidates, return top 10', { candidates: source.candidates });
  }, { deps: ['source'] });

  graph.addNode('phone_screen', async ({ screen }) => {
    return callAgent('Schedule and conduct phone screens for top 5', { shortlist: screen.top10 });
  }, { deps: ['screen'] });

  // Step 2a and 2b: Parallel after phone screen
  graph.addNode('background_check', async ({ phone_screen }) => {
    return callAgent('Initiate background check for top candidate', { candidate: phone_screen.topCandidate });
  }, { deps: ['phone_screen'] });

  graph.addNode('technical_assessment', async ({ phone_screen }) => {
    return callAgent('Send technical assessment and collect responses', { candidate: phone_screen.topCandidate });
  }, { deps: ['phone_screen'] });

  // Step 3: Feedback aggregation — waits for both parallel steps
  graph.addNode('aggregate_feedback', async ({ background_check, technical_assessment }) => {
    return callAgent('Aggregate and summarize all evaluation results', {
      backgroundCheck: background_check,
      technicalScore: technical_assessment,
    });
  }, { deps: ['background_check', 'technical_assessment'] });

  // Step 4: VP approval gate — pauses workflow until human approves
  graph.addNode('vp_approval', async ({ aggregate_feedback }) => {
    // Send summary to VP via Slack/email — agent notifies, then pauses
    await callAgent('Send hiring recommendation to VP and request approval', {
      summary: aggregate_feedback,
    });
    // Graph pauses here — resumes when graph.approveGate('vp_approval') is called
  }, { deps: ['aggregate_feedback'], type: 'gate' });

  // Step 5: Conditional — what did the VP decide?
  graph.addNode('offer_decision', null, {
    deps: ['vp_approval'],
    type: 'branch',
    branchFn: async ({ vp_approval }) => {
      return vp_approval.approved ? 'extend_offer' : 'return_to_shortlist';
    },
  });

  graph.addNode('extend_offer', async ({ vp_approval }) => {
    return callAgent('Draft and send offer letter with compensation details', {
      approvalData: vp_approval,
    });
  }, { deps: ['offer_decision'] });

  graph.addNode('return_to_shortlist', async ({ screen }) => {
    return callAgent('Identify next candidate from shortlist and restart evaluation', {
      shortlist: screen.top10.slice(1), // Skip the rejected candidate
    });
  }, { deps: ['offer_decision'] });

  // Register VP approval webhook (in production, this is called by your approval UI)
  setTimeout(() => {
    // Simulate VP approving after 10 minutes
    graph.approveGate('vp_approval', { approved: true, vpNotes: 'Strong candidate, proceed.' });
  }, 10 * 60 * 1000);

  const results = await graph.run();
  return results;
}
Comparison

Loop Engineering vs Graph Engineering: When to Use Each

DimensionLoop EngineeringGraph Engineering
Best forSingle-agent, sequential tasks with one outcomeMulti-step workflows with dependencies, branches, and multiple participants
ParallelismNone (sequential by definition)Explicit — nodes with no shared predecessors run simultaneously
Human-in-the-loopDifficult — loop must poll or time outFirst-class — gate nodes pause the graph until approval arrives
Conditional logicAgent decides (implicit, hard to audit)Branch nodes with explicit condition functions (auditable, testable)
Error recoveryLoop retries or stopsException edges route to recovery paths without restarting from scratch
ComplexitySimple to build and understandMore upfront design; pays off at organizational scale
ExamplesCode review, research summary, unit test generationHiring pipeline, incident response, PR review + approval flow, procurement

The decision criterion: If your workflow has more than one participant, a conditional branch, or a human approval step — use a graph. If it is one agent doing one thing, a loop is simpler and perfectly adequate. Do not over-engineer solo tasks into graphs; they add overhead without benefit.

Production Gotchas

Graph Engineering Failure Modes

  • DAG cycles causing deadlocks. A graph with a cycle (A → B → C → A) will deadlock — no node can ever become ready because each is waiting for a predecessor that is waiting for it. Validate that the graph is acyclic at construction time, not at runtime. Add a cycle detection check (DFS-based topological sort) when nodes are registered.
  • Gate nodes with no timeout. An approval gate that never receives an approval (VP is on holiday, webhook delivery failed) blocks the entire downstream graph forever. Every gate node must have an escalation timeout: after N hours, escalate to the next approver, or auto-approve/auto-reject based on the configured policy.
  • Large fan-out nodes overloading downstream services. A parallel fan-out that creates 100 simultaneous agent tasks can overwhelm the LLM API's rate limits. Add a concurrency limiter to the executor — limit the number of simultaneously running nodes to a configurable pool size (e.g., 10) and queue the rest.
  • Outputs not versioned across runs. If a graph node is re-run after a partial failure, the previous output must be identifiable as stale. Store outputs with a runId and nodeExecutionId — never assume a cached output from a previous run is valid for a new run.

Key Takeaway

Graph engineering is not a replacement for loop engineering — it is its organizational extension. Loop engineering solves the problem of making a single agent autonomous. Graph engineering solves the problem of making a multi-step, multi-participant workflow reliable. The insight that makes graph engineering powerful is not the data structure — it is making the organizational structure of a task explicit. Once you encode dependencies, approval gates, and conditional branches as first-class graph elements rather than leaving them to the agent's implicit reasoning, two things happen: the agent makes fewer structural mistakes (because it cannot proceed until its dependencies are met), and the system becomes auditable (you can see exactly which node failed, why, and what state the graph was in when it did). That observability is the real payoff of graph engineering over loops.
