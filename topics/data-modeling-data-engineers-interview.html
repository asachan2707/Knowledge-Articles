Data Modeling for Data Engineers: The Complete Interview Guide (2026 Edition)

Comprehensive guide to data modeling concepts that appear in senior data engineering interviews — star schema vs. snowflake, SCD types, grain declaration, Data Vault 2.0, and the modeling decisions that determine whether a data warehouse stays fast at petabyte scale.

Domain: Data Engineering · Interview Prep · Data Warehousing Level: Senior / Staff Data Engineer Published: 2026-08-14

Data modeling is the one area where data engineering interviews diverge sharply from software engineering interviews. The interviewer is not asking whether you know that star schemas exist — they know you do. They are testing whether you understand WHY data is structured differently for analytics versus transactional workloads, and whether your instincts about grain, slowly changing dimensions, and schema trade-offs match what they would see from a senior engineer making real production decisions.

Core idea: Every data modeling decision is a trade-off between write simplicity (normalized) and read performance (denormalized). The right answer depends on whether you are designing for OLTP (many small reads/writes) or OLAP (few massive aggregation scans). Mixing them up is the single most common mistake interviewers screen for.

Story · The schema that looked perfect until the business asked a new question

A fintech startup designed their analytics warehouse with a beautifully normalized schema — seven tables, all in 3NF, referential integrity enforced everywhere. Six months later the business team asked: "What is our weekly revenue by customer acquisition channel, segmented by the plan the customer was on at the time of purchase?" The query required nine JOINs, ran for four hours on a 10TB dataset, and returned results that were wrong because a customer's plan had changed since their first purchase and the schema had no history of that change.

The problem was not the data. The problem was that the schema was designed for writing records correctly, not for querying analytical patterns efficiently. Two missing concepts — dimensional modeling and slowly changing dimensions — would have prevented both the four-hour query and the incorrect results. This guide covers both, plus everything else that separates a passing data engineering interview answer from a senior-level one.

Why Data Modeling Is Still a Core Interview Topic

Interviewers use data modeling questions to test a specific thing: whether you understand that analytics databases and transactional databases have fundamentally different query profiles, and whether your schema decisions reflect that understanding.

A transactional (OLTP) workload executes thousands of small, targeted queries per second: SELECT * FROM orders WHERE order_id = 12345. Normalization is good here — it eliminates data duplication, makes writes fast, and keeps the data consistent through foreign key constraints.

An analytical (OLAP) workload executes a small number of enormous aggregation queries: SELECT SUM(revenue) FROM orders JOIN customers ON ... WHERE order_date BETWEEN ... GROUP BY region, product_category. This query must scan hundreds of millions of rows. Every JOIN multiplies the query execution time. Normalization is the enemy here — the more normalized the schema, the slower analytical queries become.

Interviewers know this. When they ask "design a schema for an e-commerce analytics warehouse," they are waiting to see whether you reach for OLTP-style normalization (wrong) or dimensional modeling (right). The rest of this guide covers what "right" looks like in detail.

The Fundamentals: Conceptual → Logical → Physical

Every schema design starts at the conceptual level and progressively adds detail. Skipping levels is the most common cause of schemas that work on small data and fail at scale.

Conceptual Model

Identifies the entities and relationships without any implementation detail. Uses Entity-Relationship (ER) diagrams. Cardinality notation:

  • One-to-One (1:1) — one customer has exactly one loyalty account.
  • One-to-Many (1:N) — one customer places many orders.
  • Many-to-Many (M:N) — one order contains many products; one product appears in many orders.

The conceptual model answers: what are the business objects and how do they relate? It does not answer: how will we store them?

Logical Model

Translates conceptual entities into tables with columns, primary keys, and foreign keys. Resolves M:N relationships via bridge (junction) tables. Chooses data types at a semantic level (e.g., "this is a currency amount") without committing to a specific database engine's type system (e.g., DECIMAL(18,4) vs NUMERIC).

Physical Model

Translates the logical model to the specific storage engine being used. Decides: partitioning strategy, clustering keys, distribution keys (for Redshift), column ordering (for BigQuery nested repeated records), compression codecs, and index types. Physical modeling is where dimensional modeling, Data Vault, and medallion architecture choices have the biggest performance impact.

Normalization Deep Dive

Normalization is the process of organizing a relational schema to reduce data redundancy and improve data integrity. It proceeds through "normal forms," each removing a different class of redundancy.

First Normal Form (1NF)

Every column must contain atomic (indivisible) values — no multi-valued columns, no arrays stored as comma-separated strings. Each row must be uniquely identifiable by a primary key.

Violation example: an orders table with a product_ids column containing "101,102,103". Fix: create an order_items table with one row per product per order.

Second Normal Form (2NF)

Requires 1NF, plus: every non-key column must depend on the entire composite primary key, not just part of it. Only relevant for tables with composite keys.

Violation example: an order_items table with PK (order_id, product_id) that also stores customer_name. customer_name depends only on order_id, not on product_id. Fix: move customer_name to the orders table.

Third Normal Form (3NF)

Requires 2NF, plus: no transitive dependencies — no non-key column can depend on another non-key column. Every non-key column must depend directly and only on the primary key.

Violation example: an orders table storing both zip_code and city. city depends on zip_code, not on order_id. Fix: create a zip_codes table and reference it.

Boyce-Codd Normal Form (BCNF)

A stricter version of 3NF that handles edge cases with overlapping candidate keys. In practice, 3NF is sufficient for most OLTP schemas; BCNF arises only with complex composite key scenarios.

When Normalization Hurts

Context Normalization Why
OLTP (transactional) ✅ Use 3NF Point queries are fast; writes are simple; no update anomalies
OLAP (analytics warehouse) ❌ Denormalize Aggregation scans hate JOINs; columnar storage benefits from pre-joined wide tables
ML feature store ❌ Denormalize Training data must be a flat feature matrix; JOINs at training time are too slow
Data Vault (audit/compliance) ✅ Highly normalized Hubs/Links/Satellites are designed for auditability and incremental load, not query speed

Dimensional Modeling: Ralph Kimball's Framework

Dimensional modeling, developed by Ralph Kimball, is the standard approach for designing analytics warehouses. It organizes data into two types of tables: fact tables (measurable business events) and dimension tables (the context around those events).

Star Schema Anatomy

A star schema has one central fact table surrounded by dimension tables, connected by foreign keys. It looks like a star: the fact table is the hub, dimension tables are the spokes.

Grain Declaration — The Most Critical Step

The grain is the finest level of detail captured in a single fact table row. It must be declared before writing any DDL. The wrong grain is unfixable after the table is populated.

Example declarations:

  • "One row per order line item" — grain includes product_id; allows per-product revenue analysis.
  • "One row per order" — grain excludes product_id; cannot answer per-product questions from this table alone.
  • "One row per daily store summary" — pre-aggregated; cannot analyze individual transactions.

In interviews, declare the grain explicitly before drawing any table. Interviewers watch for this: engineers who skip grain declaration produce schemas that answer some questions and make others impossible.

Measures: Additive vs Semi-Additive vs Non-Additive

  • Additive — can be summed across all dimension combinations. Revenue, quantity. SUM(revenue) across any combination of date, product, region is meaningful.
  • Semi-additive — can be summed across some dimensions but not others. Account balance: summing across accounts on a given date is valid; summing across dates is not (that would double-count the same money across days). Use AVG or LAST_VALUE across time.
  • Non-additive — cannot be summed. Ratios, percentages, unit prices. Store as the components (numerator and denominator) and compute the ratio at query time.

Special Dimension Types

  • Degenerate Dimension — a dimension attribute stored directly in the fact table without a corresponding dimension table. Order number is the canonical example: it has no other attributes, so creating a dim_order with one column is wasteful. Store order_number directly in the fact table.
  • Junk Dimension — a dimension table that groups together a collection of low-cardinality flags and indicators from the fact table (e.g., is_gift_wrap, is_express_shipping, is_first_order). Avoids cluttering the fact table with many boolean columns. Enumerate all combinations as rows.
  • Role-Playing Dimension — a single dimension table used in multiple roles in the same fact table. A dim_date table can be used as order_date, ship_date, and delivery_date — three foreign keys to the same table, using aliases: dim_date AS order_date_dim, etc.
  • Bridge Table — resolves a many-to-many relationship between a fact table and a dimension. Example: one customer has multiple email tags (promotional, VIP, at-risk). A bridge_customer_tags table links customer_sk to tag_sk with a weighting factor.

Slowly Changing Dimensions (SCDs) — The Interview Trap

Slowly Changing Dimensions (SCDs) handle the fact that dimension attributes change over time. A customer moves to a different city. A product is reassigned to a different category. The question is: when you query historical orders, should you see the attribute value at the time of the order or the current attribute value?

This distinction matters enormously for accuracy. An e-commerce company that changed a customer's region from "West" to "East" mid-year will attribute all their orders (including historical ones) to "East" under SCD Type 1, giving incorrect regional revenue breakdowns for any period before the move.

SCD Types

  • Type 0 — Retain Original: The attribute never changes once loaded. Used for data that is truly immutable (date of birth, date of first purchase). Any incoming change is ignored.
  • Type 1 — Overwrite: Update the existing row with the new value. No history preserved. Use when the current value is all that matters (e.g., correcting a data entry error, updating a phone number where history has no analytical value). Fast and simple.
  • Type 2 — Add Row (Most Common): Insert a new row with the new attribute value, close out the old row. History is fully preserved. Each row has: effective_from, effective_to (NULL for the current row), and is_current flag. Fact table foreign keys point to the surrogate key of the dimension row that was current at the time of the event. Production gotcha: SCD Type 2 causes the dimension table to grow unboundedly. An index on is_current = TRUE is essential — without it, every query that needs only current values scans the entire history.
  • Type 3 — Add Column: Add a new column to track the previous value alongside the current value (e.g., current_region, previous_region). Simple but limited to one level of history. Use when only "current vs. immediately prior" matters (e.g., tracking a recent sales territory reassignment).
  • Type 4 — History Table: Keep the main dimension table clean (current values only) and move all history to a separate history table. Queries for current data are fast (no is_current filter needed); history queries join to the history table.
  • Type 6 — Hybrid (1 + 2 + 3): Combines Types 1, 2, and 3. Each row has SCD Type 2 history tracking (new row on change), plus a current_value column that is updated on every row to always reflect the most recent value (Type 1 overwrite on existing rows). Enables both: "what was the value at the time of the event?" (use effective_from/effective_to) and "what is the current value?" (use current_value without filtering by date). Most powerful but most complex to maintain.

Code Example: SCD Type 2 Upsert

JavaScript Example — SCD Type 2 Upsert 
// scd-type2-upsert.js — Node.js implementation of SCD Type 2 dimension update
// Assumes a PostgreSQL-compatible database accessed via a query() function

/**
 * Upsert a dimension record using SCD Type 2.
 * If the natural key exists with a changed value, close the current row
 * and insert a new row. If it's a new natural key, insert fresh.
 * If nothing changed, do nothing (idempotent).
 *
 * @param {object} db           - database connection with query(sql, params) method
 * @param {string} table        - dimension table name (e.g. 'dim_customer')
 * @param {string} naturalKey   - column name of the business/natural key (e.g. 'customer_id')
 * @param {object} incoming     - incoming dimension record { customer_id, region, plan, ... }
 * @param {Date}   effectiveDate - the date this change takes effect (usually TODAY)
 */
async function scdType2Upsert(db, table, naturalKey, incoming, effectiveDate) {
  const effectiveDateStr = effectiveDate.toISOString().slice(0, 10); // 'YYYY-MM-DD'

  // 1. Find the currently active row for this natural key
  const existing = await db.query(
    `SELECT * FROM ${table}
     WHERE ${naturalKey} = $1
       AND is_current = TRUE`,
    [incoming[naturalKey]]
  );

  if (existing.rows.length === 0) {
    // New natural key — insert as-is, no history to close
    await db.query(
      `INSERT INTO ${table} (${naturalKey}, effective_from, effective_to, is_current, ${
        Object.keys(incoming).filter(k => k !== naturalKey).join(', ')
      })
       VALUES ($1, $2, NULL, TRUE, ${
         Object.keys(incoming)
           .filter(k => k !== naturalKey)
           .map((_, i) => `$${i + 3}`)
           .join(', ')
       })`,
      [
        incoming[naturalKey],
        effectiveDateStr,
        ...Object.entries(incoming)
          .filter(([k]) => k !== naturalKey)
          .map(([, v]) => v)
      ]
    );
    return { action: 'INSERT', naturalKey: incoming[naturalKey] };
  }

  const current = existing.rows[0];

  // 2. Check if any tracked attribute actually changed
  const trackedAttributes = Object.keys(incoming).filter(k => k !== naturalKey);
  const hasChanged = trackedAttributes.some(attr => current[attr] !== incoming[attr]);

  if (!hasChanged) {
    return { action: 'NO_CHANGE', naturalKey: incoming[naturalKey] };
  }

  // 3. Close the current row — set effective_to to (effectiveDate - 1 day) and is_current = FALSE
  const closingDate = new Date(effectiveDate);
  closingDate.setDate(closingDate.getDate() - 1);
  const closingDateStr = closingDate.toISOString().slice(0, 10);

  await db.query(
    `UPDATE ${table}
     SET effective_to = $1,
         is_current   = FALSE
     WHERE ${naturalKey} = $2
       AND is_current = TRUE`,
    [closingDateStr, incoming[naturalKey]]
  );

  // 4. Insert the new active row
  await db.query(
    `INSERT INTO ${table} (${naturalKey}, effective_from, effective_to, is_current, ${
      trackedAttributes.join(', ')
    })
     VALUES ($1, $2, NULL, TRUE, ${trackedAttributes.map((_, i) => `$${i + 3}`).join(', ')})`,
    [
      incoming[naturalKey],
      effectiveDateStr,
      ...trackedAttributes.map(attr => incoming[attr])
    ]
  );

  return { action: 'UPDATE', naturalKey: incoming[naturalKey] };
}

Snowflake Schema vs. Star Schema

A snowflake schema normalizes dimension tables — sub-dimensions are broken into separate tables. For example, instead of storing product_category directly in dim_product, a snowflake schema creates a separate dim_category table that dim_product references.

Star Schema — Preferred for Analytics

  • Denormalized: all dimension attributes in a single table per dimension.
  • Fewer JOINs in queries — dimension data is pre-joined at ETL time.
  • Query performance: columnar engines (BigQuery, Redshift, Snowflake) are heavily optimized for wide, flat tables. Adding JOINs degrades performance at billion-row scale.
  • Redundancy: yes — "Electronics" appears in every dim_product row with that category. At analytic scale this is acceptable; storage is cheap, query time is not.

Snowflake Schema — When to Use It

  • When dimension tables are very large (tens of millions of rows) and deeply hierarchical, normalizing reduces storage.
  • When the business has strict DRY requirements on dimension attributes (a category name change must be made in one place).
  • Enterprise Data Vault architectures use snowflaked Hub/Link/Satellite structures.
  • Reality check: in practice, most modern cloud warehouses use star schemas because the query performance cost of extra JOINs outweighs the storage savings from normalization. Snowflake schemas are increasingly rare in new systems built on BigQuery, Redshift, or Databricks.

Storage Engine Implications

BigQuery and Snowflake use columnar micro-partition/clustering storage. Predicate pushdown means that a filter on a partitioned or clustered column skips reading entire file blocks. A denormalized star schema where the partition/cluster key is in the fact table (e.g., order_date) performs dramatically better than a snowflaked schema where you must JOIN through multiple tables to get to the partition key column.

Data Vault 2.0

Data Vault 2.0, developed by Dan Linstedt, is a modeling methodology designed for enterprise data warehouses where auditability, schema flexibility, and parallel load isolation are more important than query performance.

Three Building Blocks

  • Hub — stores unique business keys. One Hub per business entity: hub_customer (customer_id), hub_order (order_id), hub_product (product_id). Contains only: surrogate key, business key, load date, record source. No descriptive attributes. Immutable once loaded.
  • Link — stores relationships between Hubs. A link between customer and order contains: surrogate key, customer_hk (FK to hub_customer), order_hk (FK to hub_order), load date, record source. Many-to-many relationships are natural; no junction tables needed. Links are also immutable.
  • Satellite — stores descriptive attributes and their history. Attached to either a Hub or a Link. Contains: parent surrogate key, load date, load end date, record source, and the attributes. Each change to an attribute creates a new Satellite row — full change history, similar to SCD Type 2 but applied to every attribute change automatically.

Why Enterprises Use Data Vault

  • Audit trail by design — every row in every Satellite carries load date and record source. You can always answer: "Where did this data come from, and when was it loaded?"
  • Load isolation — Hubs, Links, and Satellites from different source systems load independently. A new source system adds its Satellites without modifying existing tables.
  • Schema flexibility — adding a new attribute means adding a new Satellite, not altering an existing table. No migrations, no downtime.

When NOT to Use Data Vault

Data Vault produces many JOINs at query time (reconstruct an entity = Hub + all Satellites). It is not suitable as the query-serving layer. Production architectures build a Business Vault (computed business rules in Links/Satellites) and Information Mart (denormalized star schema views over the Vault) on top. Never expose raw Data Vault tables to business users or BI tools — the query complexity is unmanageable.

Medallion Architecture (Bronze → Silver → Gold)

Popularized by Databricks, medallion architecture organizes a data lakehouse into three progressively refined layers. Each layer represents a different data quality level and serves different consumers.

Bronze (Raw)

Landing zone for raw, unmodified source data. No transformations — the data is stored exactly as received from the source (JSON events, CSV files, CDC change streams). Append-only: old data is never overwritten. Provides a full audit trail and the ability to reprocess if downstream logic changes.

Partitioning: by ingestion date, not event date. This way, "reprocess all data ingested on 2026-08-14" scans a single partition regardless of event timestamps.

Silver (Cleaned and Conformed)

Validated, deduplicated, typed, and joined with reference data. This is where:

  • Schema validation occurs (reject rows with NULL required fields).
  • Deduplication happens (CDC produces duplicate events; use watermarking + MERGE).
  • Data type casting (string "2026-08-14" → DATE).
  • Lookup / enrichment joins (enrich event with customer attributes from CRM).

Silver tables are idempotent: running the same transformation twice produces the same result. This requires using MERGE (upsert) rather than INSERT when loading, using the natural key as the merge condition.

Gold (Business-Level Aggregates)

Pre-aggregated, business-rule-applied, ready for consumption by BI tools and ML pipelines. Dimensional models (star schemas), wide aggregation tables, and feature store tables live here. Gold tables are rebuilt from Silver on a schedule — typically daily or hourly. Because they are derived from Silver (not Bronze), rebuilds are fast.

dbt in the Medallion Pipeline

dbt (data build tool) is the standard tool for Silver → Gold transformations. Each dbt model is a SQL SELECT statement; dbt materializes it as a table or view. Key dbt strategies:

  • table — full rebuild on every run. Correct but expensive for large datasets.
  • view — no materialized data; query runs the SQL every time. Only for cheap transforms.
  • incremental — on first run, builds full table. On subsequent runs, processes only new rows (filtered by a watermark column like updated_at). The merge strategy handles late-arriving updates; delete+insert handles partitioned tables where a whole partition needs rebuilding.

Gotcha: dbt incremental models with the append strategy (no merge key) will silently create duplicates if the same source row is loaded twice. Always specify a unique_key for idempotent incremental models.

Grain Declaration — The Single Most Critical Step

Grain is not just a naming convention. It determines what questions your fact table can answer. Getting grain wrong is the most common schema design failure in analytics warehouses, and it is unfixable without rebuilding the entire table from scratch.

Interview Scenario: Design a Sales Fact Table

The interviewer asks: "Design a sales fact table for an e-commerce platform." Before drawing any columns, declare the grain:

  • Option A: "One row per order" — measures: total_order_revenue, item_count. Cannot answer: "What is our revenue from Electronics products this month?"
  • Option B: "One row per order line item (one product per order)" — measures: line_item_revenue, quantity. Can answer any product-level question. This is the correct grain for a sales fact table.
  • Option C: "One row per daily sales summary by store" — pre-aggregated. Cannot answer any individual-order question. Only appropriate as a separate, purpose-built aggregate table.

The right grain is always the finest level of detail that the business actually generates. Pre-aggregating at load time destroys information permanently. Aggregate at query time (using GROUP BY) — it is reversible.

When Multiple Grains Are Needed

A single fact table must have a single, consistent grain. If business questions require both order-level and line-item-level analysis, create two fact tables: fact_orders (one row per order) and fact_order_items (one row per line item). They share the same dimension tables. This is Kimball's "multiple fact tables sharing conformed dimensions" pattern.

12 Real Interview Questions with Full Answers

1. Design a schema for an e-commerce analytics warehouse

Answer: Declare grain first: one row per order line item. Star schema with: fact_order_items (order_item_sk, order_sk, customer_sk, product_sk, date_sk, store_sk, revenue, quantity, discount_amount), surrounded by dim_customer (SCD Type 2), dim_product (SCD Type 2), dim_date (static calendar table, pre-populated for 10 years), dim_store (SCD Type 1 for most attributes, Type 2 for region changes). All keys are surrogate integers generated at ETL time — never use source system IDs as the DW key. Partition fact_order_items by order_date_sk-derived month, cluster by customer_sk for customer-centric queries.

2. What is grain and how do you declare it?

Answer: Grain is the precise description of what one row in a fact table represents. Declare it as a plain English sentence before writing DDL: "One row per order line item placed on the e-commerce platform." Every measure and foreign key in the table must be meaningful at this level of granularity. If a measure doesn't make sense at the grain (e.g., total_order_revenue in a line-item-grain table is redundant), either remove it or create a separate fact table.

3. When would you use SCD Type 2 vs Type 6?

Answer: Use SCD Type 2 when you need full point-in-time accuracy and the downstream query pattern always knows the time range it's asking about (joins fact to dim on a date range). Use Type 6 when you need both historical accuracy AND the ability to quickly ask "what region is this customer in right now?" without filtering by date — Type 6 adds a current_value column updated on every row, so WHERE is_current = TRUE returns current data and the effective_from/to columns still answer historical questions. Type 6 is more complex to maintain — use it only when both query patterns are genuinely needed.

4. Star vs snowflake — how do you choose?

Answer: Default to star schema for analytics. Snowflake schema reduces storage (no repeated dimension attributes) but adds JOINs at query time. Modern columnar storage engines (BigQuery, Redshift, Snowflake) are built around wide, flat table scans — JOINs are expensive. Use snowflake only when: (1) dimension tables are so large (>50M rows) that denormalization creates unacceptable storage costs, or (2) enterprise governance requires a single authoritative location for dimension attributes. In 2026, the overwhelming production choice is star schema.

5. How do you handle late-arriving data in a fact table?

Answer: Late-arriving facts (events that are delivered after their event date) require a MERGE (upsert) strategy rather than append. Use the natural business key as the merge condition; if a row with that key exists, update it; otherwise insert. For late-arriving dimension members (an order references a product_id that hasn't been loaded into dim_product yet), use a dummy dimension row: load the fact with a default surrogate key (e.g., -1 pointing to a "Unknown Product" dimension row), then correct it when the dimension member arrives via a retroactive update job. Never leave a NULL foreign key in a fact table — NULLs silently drop rows from aggregations.

6. What is a bridge table and when do you need one?

Answer: A bridge table resolves a many-to-many relationship between a fact table and a dimension. Classic example: a customer belongs to multiple customer segments simultaneously (high-value, new, at-risk). bridge_customer_segment has columns: customer_sk, segment_sk, weight_factor (how much to apportion revenue to each segment — typically 1/N where N is the number of segments). Join fact → bridge → dim_segment and multiply measure by weight_factor to avoid double-counting. Bridge tables are rare but the interview question catches engineers who have only seen simple star schemas.

7. How does Data Vault differ from dimensional modeling?

Answer: Purpose differs fundamentally. Dimensional modeling (Kimball) optimizes for query performance: denormalized star schemas minimize JOINs. Data Vault optimizes for auditability, parallel loading, and schema flexibility: every attribute change is tracked automatically, new sources can be added without modifying existing tables, and every row knows its origin. The trade-off: Data Vault queries require many JOINs to reconstruct a business entity. Production architectures layer dimensional marts on top of Data Vault — the Vault is the source of truth, the mart is the query layer.

8. What's the difference between a surrogate key and a natural key?

Answer: A natural key is the identifier that comes from the source system (e.g., customer_id from the CRM). A surrogate key is a warehouse-generated integer with no business meaning (e.g., customer_sk = 48291). Always use surrogate keys as DW primary keys because: (1) they survive source system key changes (a customer_id can be reassigned in some CRMs), (2) they enable SCD Type 2 — the same natural key can have multiple surrogate keys (one per historical version), (3) integers are faster to JOIN than varchar business keys. Store the natural key in the dimension as a searchable attribute, but never use it as the DW foreign key.

9. How would you model a many-to-many product-order relationship?

Answer: This is solved directly by grain declaration. If the fact table grain is "one row per order line item," then the fact table itself IS the resolution of the M:N relationship: each row has order_sk and product_sk. No bridge table needed. A bridge table is only required when the M:N relationship is between the fact table and a dimension in a way that isn't already encoded in the grain — for example, if a single order line item simultaneously belongs to multiple promotional campaigns, you need a bridge between the fact and dim_campaign.

10. How do you test data model quality in production?

Answer: Four layers of testing: (1) Schema tests — dbt's not_null, unique, accepted_values on every key column, run after every load. (2) Referential integrity — every foreign key in the fact table must have a matching row in its dimension. Zero NULLs, zero orphan keys. (3) Freshness checks — the max updated_at in the fact table should be within the expected pipeline SLA (e.g., <2 hours old). (4) Business logic validation — revenue for a given period should match the OLTP source within a tolerance (±0.01% allows for known rounding). Alert on any violation.

11. How does partitioning affect query performance in BigQuery/Redshift?

Answer: Partitioning divides a table into segments based on a column value (typically a date). A query with a WHERE order_date BETWEEN '2026-01-01' AND '2026-01-31' predicate scans only January's partition, not the full table — this is "partition pruning." In BigQuery, this eliminates bytes scanned (and therefore cost). In Redshift, use distribution keys alongside sort keys: distribution key determines which node stores which rows (match it to the most common JOIN column to minimize data shuffling); sort key determines the physical ordering within each node's blocks (match it to the most common filter/ORDER BY column for zone map skipping). The wrong distribution key on a large fact table can make every query 10-100× slower due to cross-node data movement.

12. What is the medallion architecture and when would you skip the bronze layer?

Answer: Medallion is Bronze (raw) → Silver (cleaned/conformed) → Gold (business aggregates). Never skip Bronze. Bronze is your recovery layer — if downstream transformations have a bug, you reprocess from Bronze without re-ingesting from the source. Skipping Bronze means any Silver-layer bug requires re-pulling potentially months of source data, which may no longer be available or affordable. The only exception: CDC change streams from a database (like Debezium) where the source log retention is guaranteed for a sufficient window (e.g., 30 days). Even then, a Bronze layer is best practice.

Failure Modes

  • Wrong grain chosen late — team realizes six months in that the fact table has order-level grain but they need line-item-level analysis. The only fix is a full table rebuild from the source. At petabyte scale, this is a multi-day, multi-thousand-dollar operation. Prevention: declare grain explicitly in the data model document before writing DDL.
  • SCD Type 2 causing join explosion — a dimension table with aggressive SCD Type 2 tracking grows to 100M+ rows from an originally 1M-row business entity set. Every query that joins to this dimension without filtering on is_current scans the entire history. Prevention: always add a partial index on the current flag; document expected row growth in the model design.
  • Missing surrogate keys — team uses source system natural keys as DW foreign keys. Source system does a key rotation (e.g., CRM migration assigns new customer IDs) and all historical fact table foreign keys become orphans overnight. Prevention: always generate and use warehouse-owned surrogate integer keys.
  • NULL foreign keys in fact tables — an ETL bug fails to resolve a natural key to a dimension surrogate. The fact row is loaded with NULL for product_sk. Any aggregation that groups by product will silently drop these rows from the result. Prevention: use a sentinel "Unknown" dimension row (surrogate key -1) rather than NULL; alert when any fact row references the sentinel at load time.

Production Gotchas

  • BigQuery partition expiry — BigQuery allows setting a partition expiry (TTL) on partitioned tables. A partition older than the TTL is automatically deleted. If you accidentally enable partition expiry on a Bronze layer table, you lose your historical recovery capability. Always verify partition expiry is disabled on Bronze and Silver tables; Gold tables can use expiry for cost management.
  • Snowflake clustering keys vs materialized views — Snowflake's automatic clustering orders micro-partitions by a clustering key, enabling partition pruning without explicit date partitions. But clustering has a maintenance cost: Snowflake runs background clustering jobs that consume credits. For tables with infrequent ad-hoc queries (Gold aggregates queried by BI tools), materialized views are often cheaper: the view is precomputed once and reused.
  • dbt incremental model strategies — delete+insert vs merge — merge (upsert) is correct for most incremental loads but requires a unique key and is expensive on very large tables (must compare every incoming row against the existing table). delete+insert is faster when you can define a partition range to overwrite (e.g., always reload the last 3 days' partitions): delete all rows in those partitions, then insert fresh. Use delete+insert for event-sourced tables where late-arriving events always fall within a predictable window.
  • Late-arriving dimension members — an event references an entity that hasn't been loaded into the dimension yet (e.g., a new product appears in orders before the product catalog feed has been ingested). Without handling, the fact load fails or creates an orphan key. Solution: use a dummy dimension row with sentinel key -1 for "Unknown"; add a monitoring job that detects orphan fact rows and retroactively links them once the dimension member arrives.

Practical Checklist Before Publishing Any Data Model

  • Grain is declared as a plain English sentence and documented in the model's README.
  • All fact table foreign keys use warehouse-generated surrogate keys, not natural keys.
  • Every fact table foreign key has a corresponding NOT NULL constraint or a sentinel row (-1) policy.
  • SCD type is explicitly chosen for each dimension attribute and documented.
  • If SCD Type 2 is used, a partial index on is_current = TRUE exists on each affected dimension.
  • Measures are classified as additive, semi-additive, or non-additive; non-additive measures are stored as components.
  • Fact table is partitioned (by date) and distribution/clustering keys match the dominant query pattern.
  • dbt models have not_null, unique, and referential integrity tests on all key columns.
  • A freshness SLA is documented and monitored in the data observability layer.
  • A data dictionary exists: column name, type, description, source, SCD type for each dimension attribute.
  • The model is reviewed by a second engineer before going to production — data model bugs are expensive to fix.

Key Takeaway

Data modeling for analytics is not about applying normalization rules — it is about making irreversible choices (grain, SCD type, partitioning) that determine what questions your warehouse can answer and how fast. Every decision involves a trade-off between write simplicity and read performance. A senior data engineer knows not just what each pattern does, but under what conditions to use it, what breaks when you get it wrong, and how to recover. Master grain declaration, SCD Type 2, and the medallion architecture and you will have the conceptual tools to answer every data modeling interview question you will face.
