Elasticsearch: Search & Analytics Engine Deep Dive

A production-grade guide to Elasticsearch — covering the inverted index, distributed architecture (shards/replicas/nodes), the write and read paths, Query DSL, data modeling (mappings, keyword/text/nested/join), ELK stack integrations, Index Lifecycle Management, shard sizing, vector search (k-NN/HNSW), and real-world deployments at Wikipedia, GitHub, Netflix, and Uber.

Elasticsearch is a distributed search and analytics engine built on Apache Lucene. It is the most widely adopted search engine in the world (DB-Engines rank #12; 77,500+ GitHub stars), powering full-text search, log analytics (ELK stack), APM, security (SIEM), and increasingly vector/semantic search with its k-NN capabilities.

Core idea: Elasticsearch wraps Lucene's inverted index in a distributed, RESTful shell. Every piece of data is stored as a JSON document in an index. Indices are split into shards (each shard is a self-contained Lucene instance); shards are distributed across nodes. A query fans out to all relevant shards (scatter phase), each scores locally, then results are merged at the coordinator (gather/reduce phase).

Architecture

Distributed node model

Node Roles

  • Master-eligible — participates in leader election; stores cluster state, manages shard allocation. Keep dedicated masters for clusters >5 nodes
  • Data — stores shards, handles CRUD and search. Split into data_hot / data_warm / data_cold / data_frozen for tiered storage
  • Coordinating-only — routes requests, merges results; no data; acts as a smart load balancer
  • Ingest — runs ingest pipelines (Grok, Gsub, Set processors) before indexing
  • ML — runs anomaly detection and trained model inference

Shards & Replicas

  • Primary shard — receives all writes; default 1 shard per index (since ES 7.0; was 5 before)
  • Replica shard — copy of primary; serves reads; default 1 replica per primary
  • Shard count is fixed at index creation — requires reindex to change primaries
  • Recommended shard size: 10–50 GB (Elastic guidance); smaller = more overhead
  • Over-sharding is a common anti-pattern: too many small shards consume heap and slow queries

Cluster Coordination (Zen2 / 7.x+)

  • Raft-based consensus for master election (replaced Zen1 in 7.0)
  • cluster.initial_master_nodes bootstraps first election; must list all master-eligible nodes
  • Quorum = majority of master-eligible nodes → split-brain prevention
  • Cluster state (mappings, shard assignments) replicated via Raft log
  • Minimum 3 master-eligible nodes in production

Index Anatomy

  • Index — logical namespace; maps to one or more shards
  • Shard — a Lucene index; contains segments, translog, bloom filter
  • Segment — immutable on-disk Lucene unit; accumulates until merge
  • Translog — write-ahead log for durability before segment flush
  • Alias — named pointer to one or more indices; enables zero-downtime reindexing
Inverted Index & Scoring

How Lucene finds and ranks documents

The inverted index maps each unique term to the list of documents containing that term (the posting list), plus optional frequency, position, and offset data. When you index a document, the text is passed through an analyzer (tokenizer → token filters) to produce terms. Each term is added to the inverted index for its field.

Inverted Index Components

  • Term dictionary — sorted FST (Finite State Transducer) of all terms; loaded into memory for fast lookup
  • Posting list — per-term: doc IDs, term frequency, positions (for phrase queries), offsets (for highlighting)
  • doc_values — columnar on-disk store for sorting, aggregations, scripting on keyword, numeric, date fields
  • fielddata — heap-resident columnar store for text fields (expensive; avoid unless necessary)
  • _source — original JSON document stored as-is; not used for search

BM25 Scoring (default since ES 5.0)

  • Okapi BM25 replaces TF-IDF as the default similarity algorithm
  • TF component: saturates at high frequencies (parameter k1, default 1.2)
  • IDF component: inverse document frequency — rare terms score higher
  • Length normalization: shorter fields score higher (parameter b, default 0.75)
  • Override per field: "similarity": "boolean" or custom BM25 with different k1/b
  • Use explain: true in queries to see per-doc score breakdown

Lucene segments are immutable — deletes mark documents as deleted in a bitmap; the segment is not rewritten. Updates = delete old + write new. Background segment merges consolidate small segments, reclaim space from deleted docs, and improve read performance.

Write & Read Path

How documents flow from client to disk

Write Path

1

Coordinating node receives request

Any node can be coordinator. Routes to the correct primary shard using a hash of the document ID (or custom routing key).

2

Primary shard writes translog + in-memory buffer

The translog is fsync'd every 5 seconds (or on each request for write_concern: true). Guards against data loss on crash.

3

Forwarded to replica shards

Primary waits for all in-sync replicas to acknowledge before returning success to the client (controlled by wait_for_active_shards).

4

Refresh (default every 1 second)

In-memory buffer is written to a new Lucene segment and made searchable. This is what makes ES near real-time (NRT) — not truly real-time. Disable or increase index.refresh_interval during bulk indexing for 2–3× throughput improvement.

5

Flush (periodic or when translog grows)

Segments are fsync'd to disk; translog is cleared. Default translog flush threshold: 512 MB or 30 minutes.

Read Path (Query → Fetch)

Two-phase search: Query phase — coordinator fans out to all relevant shards; each shard returns a lightweight list of matching doc IDs + scores (not the full documents). Coordinator merges, sorts, and selects the top N. Fetch phase — coordinator requests full document sources for only the top N doc IDs. This separation minimizes network transfer — only scores travel in phase 1, full docs in phase 2.
Query DSL

Key query types and aggregations

Query DSL Examples 
// 1. bool query — the Swiss Army knife
// must=AND(scored), filter=AND(not scored, cached), should=OR, must_not=AND NOT
{
  "query": {
    "bool": {
      "must":     [{ "match": { "title": "elasticsearch tutorial" } }],
      "filter":   [{ "term":  { "status": "published" } },
                   { "range": { "date": { "gte": "2024-01-01" } } }],
      "should":   [{ "match": { "tags": "search" } }],
      "must_not": [{ "term":  { "archived": true } }],
      "minimum_should_match": 1
    }
  }
}

// 2. match — full-text search, applies analyzer
{ "query": { "match": { "body": { "query": "quick brown fox", "operator": "and" } } } }

// 3. multi_match — search across multiple fields with boost
{
  "query": {
    "multi_match": {
      "query": "elasticsearch",
      "fields": ["title^3", "body", "tags^2"],
      "type": "best_fields"
    }
  }
}

// 4. term / terms — exact match (no analysis); use on keyword fields
{ "query": { "term":  { "status.keyword": "published" } } }
{ "query": { "terms": { "category": ["news", "tech"] } } }

// 5. range query
{ "query": { "range": { "price": { "gte": 10, "lte": 100 } } } }

// 6. nested query — preserves object-array relationships
{
  "query": {
    "nested": {
      "path": "comments",
      "query": {
        "bool": {
          "must": [
            { "match": { "comments.author": "Alice" } },
            { "range": { "comments.score": { "gte": 4 } } }
          ]
        }
      },
      "inner_hits": {}
    }
  }
}

// 7. function_score — boost by recency, popularity, geo distance
{
  "query": {
    "function_score": {
      "query": { "match": { "title": "search" } },
      "functions": [
        { "gauss": { "date": { "origin": "now", "scale": "7d", "decay": 0.5 } } },
        { "field_value_factor": { "field": "views", "modifier": "log1p", "factor": 0.5 } }
      ],
      "score_mode": "multiply"
    }
  }
}

Data Modeling

Mappings, field types, and design patterns

text vs keyword

  • text — analyzed (tokenized + lowercased); full-text search; no sorting/aggregation by default
  • keyword — not analyzed; exact match, sorting, aggregations, term queries
  • Multi-field pattern: map as text + sub-field .keyword as keyword — search on title, sort/aggregate on title.keyword
  • Dynamic mapping creates .keyword sub-field with ignore_above: 256
  • Use wildcard type for high-cardinality machine-generated strings requiring leading-wildcard searches

object vs nested

  • object (default) — flattens arrays of objects; destroys per-object field association
  • nested — each object indexed as a hidden Lucene document; preserves associations
  • Nested objects stored separately: 1 parent + N objects = N+1 Lucene docs
  • Default limits: 100 distinct nested field types, 10,000 nested objects per document
  • Use nested query to query nested; use reverse_nested agg to aggregate back to parent

join (parent-child)

  • Parent and child documents in same index; child must route to same shard as parent
  • Use when one entity significantly outnumbers the other (e.g., products → offers)
  • has_child / has_parent queries are expensive — adds significant query overhead
  • Only 1 join field per index; relations can be extended but not modified
  • Prefer denormalization over join for most workloads

Index Templates & Data Streams

  • Index templates — auto-apply mappings + settings to indices matching a pattern
  • Component templates — reusable mapping/settings fragments composed into index templates
  • Data streams — append-only time-series abstraction; write to current backing index; auto-rollover via ILM
  • Data stream name used as write alias; search queries all backing indices
  • Recommended for logs, metrics, traces — any time-series workload
Dynamic mapping caution: Dynamic mapping is true by default — Elasticsearch auto-detects types. This convenience causes mapping explosion in production (e.g., log ingest creating thousands of field mappings). Use "dynamic": "strict" on production indices and define all fields explicitly. The default limit is 1,000 total fields per index (index.mapping.total_fields.limit).
ELK Stack & Integrations

The Elastic ecosystem

Beats — Lightweight Shippers

  • Filebeat — tails log files; handles backpressure; sends to Logstash or ES directly
  • Metricbeat — system/service metrics (CPU, memory, MySQL, Nginx, Docker)
  • Packetbeat — network traffic analysis (HTTP, DNS, MySQL protocols)
  • Elastic Agent — unified agent replacing individual Beats; centrally managed via Fleet

Logstash — Ingest Pipeline

  • Input plugins: Filebeat, Kafka, S3, JDBC, HTTP
  • Filter plugins: Grok (regex parsing), Mutate (rename/type-cast), GeoIP, Date
  • Output plugins: Elasticsearch, S3, Kafka, email
  • For simple transformations, prefer ES ingest pipelines (built-in, lower ops overhead)
  • Logstash for complex multi-source fan-in, conditional routing, and heavy transformation

Elasticsearch Ingest Pipelines

  • Processors run on the ingest node before indexing
  • Common processors: Grok, GeoIP, Date, Rename, Remove, Set, Enrich, Script
  • Defined via PUT _ingest/pipeline/my-pipeline
  • Reference in index template or per-request via ?pipeline=my-pipeline
  • On-failure handling: per-processor fallback chains

Kafka → Elasticsearch

  • Kafka Connect Elasticsearch Sink Connector (Elastic or Confluent)
  • Reads Kafka topics → batches → bulk API to ES
  • Configurable: batch size, retry logic, index naming from topic name
  • Alternative: Logstash Kafka input → Elasticsearch output
  • For real-time search on streaming data: Kafka event → Logstash → ES → Kibana
Index Lifecycle Management (ILM)

Automated data tiering for time-series data

ILM automates index management through five phases based on age, document count, or size — moving data from fast expensive storage to cheap cold storage, then deleting it.

HOT — Active writes + reads; fastest nodes (NVMe SSD) WARM — Read-only; forcemerge to 1 segment; lower-spec nodes COLD — Infrequent reads; searchable snapshots optional; HDDs FROZEN — Rarely accessed; data stays in object storage (S3); mounted on demand DELETE — Index deleted
ILM Policy Example 
PUT _ilm/policy/logs-30d-policy
{
  "policy": {
    "phases": {
      "hot": {
        "min_age": "0ms",
        "actions": {
          "rollover": {
            "max_primary_shard_size": "50gb",  // roll when any shard hits 50 GB
            "max_age": "1d"                    // or after 1 day, whichever first
          },
          "set_priority": { "priority": 100 }
        }
      },
      "warm": {
        "min_age": "3d",                       // 3 days after rollover
        "actions": {
          "shrink":      { "number_of_shards": 1 },  // reduce to 1 shard
          "forcemerge":  { "max_num_segments": 1 },   // 1 segment = optimal read
          "set_priority": { "priority": 50 }
        }
      },
      "cold": {
        "min_age": "14d",
        "actions": {
          "searchable_snapshot": { "snapshot_repository": "s3-repo" },
          "set_priority": { "priority": 0 }
        }
      },
      "delete": {
        "min_age": "30d",
        "actions": { "delete": {} }
      }
    }
  }
}
Rollover triggers: ILM rolls an index when any rollover condition is met (first match). Common triggers: max_age, max_primary_shard_size (50 GB is a good default), max_docs. After rollover, the alias points to the new index; the old index progresses through ILM phases.
Shard Sizing & Performance

Operational tuning guide

Shard Sizing Rules

  • Target 10–50 GB per shard (Elastic's guidance)
  • Each shard has overhead: Lucene segments, heap metadata (~few MBs each)
  • Over-sharding: 1,000 × 1 GB shards is far worse than 20 × 50 GB shards
  • Max shard count per GB of heap: ~20 shards/GB (watch for OOM)
  • Rule: Total shards ≤ 20 × heap in GB

Heap & JVM

  • Set heap to 50% of available RAM, never exceed 31 GB (compressed OOPs limit)
  • Above 31 GB: JVM disables compressed object pointers → pointer size doubles → more GC pressure
  • Remaining 50% RAM: used by OS page cache for Lucene file access (critical for performance)
  • G1GC is default; ZGC available for large heaps with lower pause requirements
  • Circuit breakers prevent OOM: field data, request, in-flight bytes limits

Query Performance

  • filter context queries are cached (no scoring); use for non-relevance predicates
  • Shard request cache: caches full aggregation results for non-changed shards
  • Query cache (node level): caches bitsets for frequently used filter clauses
  • Enable _routing to route related docs to same shard → avoid full scatter-gather
  • Use search_after for deep pagination instead of from+size (avoids heap cost of large priority queues)

Bulk Indexing Tuning

  • Set index.refresh_interval: -1 during bulk load (disable refresh); reset after
  • Set index.number_of_replicas: 0 during initial load; re-enable after
  • Bulk API batch size: 5–15 MB per request (not document count)
  • Use multiple concurrent bulk threads: typically 2× data node count
  • Monitor for 429 Too Many Requests (indexing queue full) — back off and retry
Vector Search

k-NN and semantic search (ES 8.x+)

dense_vector field type

  • Stores floating-point vector embeddings (e.g., 768-dim BERT, 1536-dim OpenAI)
  • Supports HNSW (Hierarchical Navigable Small World) for approximate k-NN
  • Index parameters: m (graph connectivity, default 16), ef_construction (build accuracy, default 100)
  • Similarity: cosine, dot_product, l2_norm, max_inner_product
  • Exact k-NN (brute-force): set "index": false — no HNSW overhead, full accuracy, slower for large corpora

Hybrid Search (BM25 + Vector)

  • Combine lexical BM25 relevance with semantic vector similarity
  • Use sub_searches with Reciprocal Rank Fusion (RRF) normalizer (ES 8.14+)
  • Or: knn + query in same request with explicit boost weights
  • ELSER (Elastic Learned Sparse Encoder) — in-house sparse vector model for semantic search without dense vectors; uses sparse_vector field type
  • semantic_text field (ES 8.15+) — one-stop mapping for automatic chunking + inference pipeline

JavaScript Example

Full @elastic/elasticsearch client integration

JavaScript Example 
import { Client } from '@elastic/elasticsearch';

// Client setup with authentication
const es = new Client({
  node: process.env.ES_URL || 'https://localhost:9200',
  auth: {
    apiKey: process.env.ES_API_KEY,   // preferred for cloud
    // OR: { username: 'elastic', password: 'changeme' }
  },
  tls: { rejectUnauthorized: true },
  maxRetries: 3,
  requestTimeout: 30_000,
  compression: true,                  // gzip request/response bodies
});

// Create index with explicit mappings — never rely on dynamic mapping in production
async function createProductIndex() {
  await es.indices.create({
    index: 'products',
    settings: {
      number_of_shards:   2,
      number_of_replicas: 1,
      refresh_interval:   '1s',
    },
    mappings: {
      dynamic: 'strict',              // reject documents with unmapped fields
      properties: {
        title:       { type: 'text', fields: { keyword: { type: 'keyword' } } },
        description: { type: 'text', analyzer: 'english' },
        category:    { type: 'keyword' },
        price:       { type: 'double' },
        tags:        { type: 'keyword' },
        in_stock:    { type: 'boolean' },
        created_at:  { type: 'date' },
        embedding:   { type: 'dense_vector', dims: 128, index: true, similarity: 'cosine' },
      },
    },
  });
}

// Bulk indexing — most efficient way to ingest large volumes
async function bulkIndex(products) {
  const operations = products.flatMap(doc => [
    { index: { _index: 'products', _id: doc.id } },
    {
      title:       doc.title,
      description: doc.description,
      category:    doc.category,
      price:       doc.price,
      tags:        doc.tags,
      in_stock:    doc.inStock,
      created_at:  doc.createdAt,
      embedding:   doc.embedding,     // pre-computed vector from ML model
    },
  ]);

  const { items, errors } = await es.bulk({ operations, refresh: false });
  if (errors) {
    const failed = items.filter(i => i.index?.error);
    console.error(`${failed.length} bulk items failed`, failed);
  }
  return items.length / 2;
}

// Full-text search with filters, relevance boost, aggregations
async function searchProducts(params) {
  const { query, category, minPrice, maxPrice, page = 1, size = 20 } = params;

  const result = await es.search({
    index: 'products',
    from:  (page - 1) * size,
    size,
    query: {
      bool: {
        must: query
          ? [{ multi_match: { query, fields: ['title^3', 'description', 'tags^2'] } }]
          : [{ match_all: {} }],
        filter: [
          ...(category  ? [{ term:  { category } }] : []),
          ...(minPrice != null || maxPrice != null
            ? [{ range: { price: { gte: minPrice, lte: maxPrice } } }]
            : []),
          { term: { in_stock: true } },
        ],
      },
    },
    aggs: {
      by_category: {
        terms: { field: 'category', size: 20 },
        aggs: { avg_price: { avg: { field: 'price' } } },
      },
      price_histogram: {
        histogram: { field: 'price', interval: 50 },
      },
    },
    highlight: {
      fields: { title: { fragment_size: 100 }, description: { fragment_size: 150 } },
    },
    sort: [{ _score: 'desc' }, { created_at: 'desc' }],
  });

  return {
    total:        result.hits.total.value,
    hits:         result.hits.hits.map(h => ({ id: h._id, score: h._score, ...h._source, highlights: h.highlight })),
    aggregations: result.aggregations,
  };
}

// k-NN vector search — find similar products by embedding
async function findSimilar(queryEmbedding, topK = 10) {
  const result = await es.search({
    index: 'products',
    knn: {
      field:          'embedding',
      query_vector:   queryEmbedding,
      k:              topK,
      num_candidates: topK * 5,       // num_candidates > k for better accuracy
    },
    _source: ['title', 'category', 'price'],
  });
  return result.hits.hits.map(h => ({ id: h._id, score: h._score, ...h._source }));
}

// Index lifecycle management — update settings for bulk load then restore
async function bulkLoadOptimized(products) {
  await es.indices.putSettings({
    index: 'products',
    settings: { refresh_interval: '-1', number_of_replicas: 0 },
  });

  try {
    await bulkIndex(products);
  } finally {
    await es.indices.putSettings({
      index: 'products',
      settings: { refresh_interval: '1s', number_of_replicas: 1 },
    });
    await es.indices.refresh({ index: 'products' });
  }
}
Client best practices: (1) Use API key auth — scoped, revocable, no password in config. (2) Always use "dynamic": "strict" on production indices. (3) For bulk indexing, disable refresh and replicas, then restore after load. (4) Use search_after for pagination beyond 10k docs (not from+size). (5) Use filter context for non-scoring predicates — it enables caching. (6) Set num_candidates to 5–10× k for k-NN accuracy vs performance trade-off.
Pros & Cons

Trade-off summary

Advantages

  • Best-in-class full-text search — BM25, analyzed text, multi-field queries, highlighting, suggestions
  • Powerful aggregations — terms, histograms, nested, pipeline, composite; real-time analytics
  • Schema flexibility — dynamic mapping for prototyping; explicit mapping for production
  • ELK ecosystem — Beats, Logstash, Kibana, Fleet — complete observability stack out of box
  • Distributed, horizontally scalable — add nodes to scale read throughput linearly
  • Vector search native — HNSW k-NN, hybrid BM25+vector, ELSER semantic search
  • ILM data tiering — automatic hot/warm/cold/frozen lifecycle; Elastic searchable snapshots
  • Near real-time — documents searchable within ~1 second of indexing

Limitations

  • Not a primary database — no ACID transactions; writes may be lost on crash without replicas; eventual consistency
  • Complexity at scale — shard tuning, heap sizing, ILM, mapping management require expertise
  • Mapping immutability — cannot change existing field types; must reindex to change schema
  • Over-sharding danger — too many small shards exhaust heap and slow queries
  • High memory requirements — heap + page cache; production nodes typically 32–64 GB RAM
  • Licensing — Elastic changed to SSPL/Elastic License 2.0 in 2021; AWS forked as OpenSearch
  • Aggregation on text fields — requires fielddata (heap-resident) or .keyword multi-field (indexed twice)
  • No update-in-place — updates are delete + reindex under the hood; high update rate → segment bloat

Choosing between ES and Solr: Both are Lucene-based and offer similar core search capabilities. Elasticsearch has a larger ecosystem (ELK), better REST API ergonomics, stronger cloud offerings (Elastic Cloud), and leads in vector search. Solr has fully open-source licensing (Apache 2.0 vs SSPL) and is preferred in existing Hadoop/enterprise environments. DB-Engines score: Elasticsearch 94 vs Solr 33 — Elasticsearch has ~3× greater adoption.

Key Takeaway

Elasticsearch is the right choice when you need powerful full-text search with relevance tuning, real-time log analytics at scale (ELK stack), or a unified platform that now also handles vector/semantic search. Its distributed architecture (shards + replicas + nodes) enables horizontal read scalability and fault tolerance. The key operational challenges are: shard sizing (10–50 GB per shard; total shards ≤ 20× heap GB), mapping discipline (dynamic: strict + explicit field types in production), and data tiering (ILM hot/warm/cold/frozen). Elasticsearch is not a primary operational database — it is a search and analytics layer that sits alongside a source-of-truth store (PostgreSQL, Cassandra, MongoDB). The data flow is: primary database → change stream → Elasticsearch. Never treat ES as the system of record.
