Top 6 Microservices Patterns for Modern Software Architecture

The six patterns that appear in nearly every production microservices deployment: API Gateway, Circuit Breaker, Service Discovery, Saga, Event Sourcing, and Sidecar — each explained with its specific use case, how it works, and a JavaScript implementation sketch showing the core mechanics.

These six patterns appear in the vast majority of production microservices deployments because they solve the six most universal problems: client access complexity, cascading failures, dynamic service location, distributed transactions, state history, and cross-cutting operational concerns. Consider these your starting set — not your complete toolkit.

Core idea: These six are not independent — they compose. An API Gateway typically embeds a Circuit Breaker. Event Sourcing is commonly paired with CQRS. The Sidecar pattern runs the service mesh that implements Service Discovery. Understand how they combine, not just how they work in isolation.

The 6 patterns
Pattern 1 · Client access

API Gateway

Problem: Clients need data from multiple services for a single screen. Calling each service directly creates N network hops and exposes internal service topology.

Solution: Single entry point that routes, aggregates, authenticates, and rate-limits. Client makes one call; gateway handles the rest.

Use when: You have multiple client types (web, mobile, partner), or when cross-cutting concerns (auth, rate limiting) would otherwise be duplicated across services.

Pattern 2 · Failure isolation

Circuit Breaker

Problem: A slow or failed downstream service causes the caller to queue threads waiting for responses, eventually exhausting resources and taking down the caller too.

Solution: A proxy wraps every downstream call. Failure rate is tracked. When failures exceed a threshold, the circuit opens and requests fail-fast with a fallback response rather than waiting for a timeout.

Three states: Closed (normal operation) → Open (fail fast, no requests) → Half-Open (allow one test request; close if it succeeds, reopen if it fails).

Pattern 3 · Dynamic location

Service Discovery

Problem: Microservices in containers get new IP addresses on every restart. Hardcoded URLs break immediately.

Solution: Services register themselves in a Service Registry on startup and send heartbeats. Clients (or a load balancer) query the registry to find healthy instances. Two forms: Client-Side (client queries registry directly, Netflix Eureka) or Server-Side (load balancer queries registry, AWS ALB, Kubernetes).

Pattern 4 · Distributed transactions

Saga Pattern

Problem: A business operation spans multiple services (order + payment + inventory). Two-phase commit across microservices is impractical. How do you achieve consistency without a shared transaction?

Solution: A saga is a sequence of local transactions. Each step publishes an event that triggers the next. Failures trigger compensating transactions that undo prior steps. Orchestrated sagas use a central coordinator; choreographed sagas use events.

Pattern 5 · Audit & history

Event Sourcing

Problem: Traditional databases store current state only. You lose the history of how state changed — valuable for audit, debugging, and deriving new projections retroactively.

Solution: Every state change is stored as an immutable event. Current state is the result of replaying all events. Enables time-travel queries, retroactive projections, and complete audit trails.

Pattern 6 · Cross-cutting concerns

Sidecar

Problem: Every service needs logging, metrics, certificate rotation, and service mesh proxying. Implementing these in each service adds boilerplate and creates inconsistent implementations.

Solution: A helper container runs alongside the main service in the same pod/VM, sharing its network namespace. Handles operational concerns transparently. Created and retired with the parent service. Used in Istio and Linkerd service mesh implementations.

JavaScript Example

Service Discovery client + Event Sourcing replay

JavaScript Example 
// Client-side Service Discovery: client queries registry for healthy instances
class ServiceDiscoveryClient {
  constructor(registryUrl) {
    this.registryUrl = registryUrl;
    this._cache = new Map();
    this._ttl = 10_000; // cache entries for 10 seconds
  }

  async resolve(serviceName) {
    const cached = this._cache.get(serviceName);
    if (cached && Date.now() - cached.fetchedAt < this._ttl) {
      return this._roundRobin(cached.instances);
    }

    const res = await fetch(`${this.registryUrl}/services/${serviceName}`);
    const { instances } = await res.json(); // [{ url, healthy, weight }]
    const healthy = instances.filter(i => i.healthy);
    this._cache.set(serviceName, { instances: healthy, fetchedAt: Date.now(), index: 0 });
    return this._roundRobin(this._cache.get(serviceName));
  }

  _roundRobin(entry) {
    const url = entry.instances[entry.index % entry.instances.length].url;
    entry.index++;
    return url;
  }
}

// Event Sourcing: store events, rebuild state by replay
class EventStore {
  constructor() {
    this._events = new Map(); // aggregateId → events[]
  }

  append(aggregateId, event) {
    if (!this._events.has(aggregateId)) this._events.set(aggregateId, []);
    this._events.get(aggregateId).push({
      ...event,
      timestamp: new Date().toISOString(),
      seq: this._events.get(aggregateId).length,
    });
  }

  getEvents(aggregateId, fromSeq = 0) {
    return (this._events.get(aggregateId) ?? []).slice(fromSeq);
  }
}

// Rebuild current order state from events
function replayOrderEvents(events) {
  return events.reduce((state, event) => {
    switch (event.type) {
      case 'order.created':
        return { ...state, id: event.payload.id, status: 'pending', items: event.payload.items };
      case 'payment.completed':
        return { ...state, status: 'confirmed', paymentId: event.payload.paymentId };
      case 'order.shipped':
        return { ...state, status: 'shipped', trackingId: event.payload.trackingId };
      case 'order.cancelled':
        return { ...state, status: 'cancelled', reason: event.payload.reason };
      default:
        return state;
    }
  }, {});
}

// Usage
const store = new EventStore();
const orderId = 'ord-001';
store.append(orderId, { type: 'order.created', payload: { id: orderId, items: ['item-1'] } });
store.append(orderId, { type: 'payment.completed', payload: { paymentId: 'pay-123' } });
store.append(orderId, { type: 'order.shipped', payload: { trackingId: 'TRACK-456' } });

const currentState = replayOrderEvents(store.getEvents(orderId));
console.log(currentState);
// { id: 'ord-001', status: 'shipped', items: ['item-1'], paymentId: 'pay-123', trackingId: 'TRACK-456' }
Event Sourcing cost: The main cost is rebuild time. A long-lived aggregate with 10,000 events takes 10,000 reductions to compute current state. Mitigation: snapshots — periodically save a state snapshot and replay only events since the snapshot. Snapshots are an optimization, not the source of truth; the event log remains the canonical record.

Key Takeaway

These six patterns compose: API Gateway + Circuit Breaker at the entry point; Service Discovery in the gateway or load balancer; Saga for distributed workflows; Event Sourcing for audit-critical aggregates; Sidecar for operational cross-cutting concerns. Understanding the composition is what separates a pattern reference from applied microservices architecture. Start with Circuit Breaker and Service Discovery — they're operational safety nets. Add Saga and Event Sourcing when your business requirements demand distributed transactions and audit history.
