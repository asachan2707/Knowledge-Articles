What Are Guardrails & Building Your First Guardrail

Guardrails as input and output checks around an LLM call, the technique menu (rules, ML models, LLM judges), and a first working validator and guard that stops a secret-project leak.

PAGE SUMMARY (hidden, for analysis). Child 02. Covers L3 What are guardrails and L4 Building your first guardrail (Project Colosseum). Definitions of validator, guard, input/output guard, on_fail, Guardrails server. Runnable mini-core in JS with four on_fail policies.

A guardrail is a small, boring, testable function placed on the edge of a non-deterministic system. That is its value.

Core idea: Validator = check; Guard = runtime and policy; input and output guards bracket the model.

Lesson 3

What are guardrails

The lesson defines guardrails as secondary checks or validations that ensure the inputs or outputs of an LLM call are as expected, ranging from format checks to hallucination and jailbreak detection. In a standard RAG pipeline there are two attachment points:

  • Input guard — runs before the prompt reaches the LLM: PII present? off-topic? jailbreak attempt?
  • Output guard — runs after the LLM responds: hallucination? unsafe content? still on topic?

Ways to implement a check

TechniqueGood forCost / risk
Rules and regexFormats, known tokens, checksumsCheap, deterministic; brittle to paraphrase
Fine-tuned ML models (NER, toxicity)Entities, profanity, classificationSmall model latency; needs hosting
Secondary LLM call as judgeSubtle alignment, scoringSlow, stochastic, rate-limited, data leaves your boundary
Hybrid cascadeMost real systemsOrder cheap-to-expensive

Why bother: the three benefits named in the lesson

  • Explicit verification of hard constraints such as “no PII leaves”.
  • Measurable undesirable behaviour: a validator yields pass/fail you can count.
  • Containment of cascading errors in multi-step apps — “drawing a bounding box around what that AI model can do”.
Lesson 4

Building your first guardrail

Setup uses the OpenAI SDK and Guardrails AI (Guard, OnFailAction, Validator). The RAG bot is seeded with pizzeria docs and told not to discuss Project Colosseum, a confidential product effort. Asked directly, the unguarded bot still leaks details about crust ratios.

  • Validator — the logic. A custom class checks whether the text contains “Colosseum” and returns a fail result with an error message (and optionally a fix value such as “I’m sorry I can’t answer questions about Project Colosseum”).
  • Guard — the application-level runtime. It passes data to one or more validators and applies the on_fail action; exception blocks the request.
  • Input vs output guard — the same validator can sit on either side.
  • Guardrails server — exposes OpenAI-compatible endpoints, so an app can swap its base URL to go through the guard and deploy it as a service.
  • Result: the same query now fails with “validation failed … Colosseum detected”.
Code

Validator, Guard and on_fail policies

A dependency-free mini core (Validator result, Guard, exception / fix / filter / noop) mirroring the Guardrails AI vocabulary. The same validator is run under four policies.

JavaScript Example 
// ── Mini guardrails core (mirrors the Guardrails AI vocabulary: Validator, Guard, on_fail) ──
class ValidationError extends Error {}
const pass = () => ({ outcome: 'pass' });
const fail = (errorMessage, fixValue) => ({ outcome: 'fail', errorMessage, fixValue });

class Guard {
  constructor(name = 'guard') { this.name = name; this.rules = []; this.log = []; }
  use(validator, onFail = 'exception') { this.rules.push({ validator, onFail }); return this; }
  validate(text) {
    let cur = text;
    for (const { validator, onFail } of this.rules) {
      const r = validator.validate(cur);
      this.log.push({ validator: validator.constructor.name, outcome: r.outcome, onFail });
      if (r.outcome === 'pass') continue;
      if (onFail === 'exception') throw new ValidationError(`Validation failed for ${this.name}: ${r.errorMessage}`);
      if (onFail === 'fix' && r.fixValue !== undefined) cur = r.fixValue;   // replace and continue
      else if (onFail === 'filter') return null;                              // drop the whole value
      // 'noop': record the failure, keep the value
    }
    return cur;
  }
}

// Validator = the check. Guard = the runtime that applies validators and on_fail policy.
class BannedTopicKeyword {
  constructor(keyword) { this.keyword = keyword.toLowerCase(); }
  validate(text) {
    return text.toLowerCase().includes(this.keyword)
      ? fail(`${this.keyword[0].toUpperCase() + this.keyword.slice(1)} detected`, `I'm sorry I can't answer questions about Project ${this.keyword[0].toUpperCase() + this.keyword.slice(1)}`)
      : pass();
  }
}

// The "unguarded" RAG bot leaks the secret when asked.
const unguardedBot = q => /colosseum/i.test(q) ? 'Project Colosseum uses a 70/30 hydration crust ratio.' : 'We open at 11am.';

function guardedBot(onFail) {
  const inputGuard = new Guard('input').use(new BannedTopicKeyword('Colosseum'), onFail);
  return q => {
    const safe = inputGuard.validate(q);
    if (safe === null) return '[request dropped by guard]';   // on_fail=filter
    if (safe !== q) return safe;                               // on_fail=fix: the fix value IS the reply
    return unguardedBot(q);
  };
}

console.log('unguarded       :', unguardedBot('Tell me about Project Colosseum'));
try { guardedBot('exception')('Tell me about Project Colosseum'); }
catch (e) { console.log('on_fail=exception:', e.message); }
console.log('on_fail=fix      :', guardedBot('fix')('Tell me about Project Colosseum'));
console.log('on_fail=noop     :', guardedBot('noop')('Tell me about Project Colosseum'), '(violation only logged)');
console.log('on_fail=filter   :', guardedBot('filter')('Tell me about Project Colosseum'));
console.log('benign question  :', guardedBot('exception')('When do you open?'));
Output (ran under Node.js) 
unguarded       : Project Colosseum uses a 70/30 hydration crust ratio.
on_fail=exception: Validation failed for input: Colosseum detected
on_fail=fix      : I'm sorry I can't answer questions about Project Colosseum
on_fail=noop     : Project Colosseum uses a 70/30 hydration crust ratio. (violation only logged)

Senior notes

Design facts worth keeping

  • Choose on_fail per risk. Exception for secrets and compliance, fix for formatting, filter when dropping is acceptable, noop (log-only) while you tune a new rule on live traffic.
  • A keyword guard is the floor, not the ceiling. “C0losseum” or a paraphrase defeats it; later lessons replace string matching with models.
  • Guards are middleware. Keeping them behind an OpenAI-compatible endpoint means any client in any language gets them without code changes.
  • Log every outcome. The guard’s log is the dataset for tuning thresholds later.

FAQ

Frequently Asked Questions

Validator or guard — which one do I write?

Write validators (the check). Guards are configuration: which validators, in which order, with which on_fail.

Why an exception instead of returning a refusal?

Exceptions make failure explicit and let the app decide the user experience; silent substitutions hide incidents.

Key Takeaway

Start with a simple deterministic validator, wire it through a guard with an explicit failure policy, and measure it. Sophistication comes after the plumbing.
