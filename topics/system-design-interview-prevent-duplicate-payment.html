System Design Interview: How Would You Prevent a Payment from Being Processed Twice?

A complete interview answer covering idempotency keys, distributed locking, database constraints, crash-recovery with the Outbox pattern, Kafka exactly-once semantics, and the reconciliation jobs that catch what all other layers miss. The layered defence every senior engineer must know.

Domain: System Design · Payments · Interview Prep Credit: Javarevisited (Medium) Published: 2026-07-22

A payment can be duplicated at every layer of the stack: the client double-taps the Pay button; the network times out and the client retries; the payment service crashes after charging but before recording; Kafka redelivers an event the consumer already processed. No single mechanism stops all of these. The correct answer is a layered defence — client key, server lock, database constraint, event deduplication, and a reconciliation job for the gaps everything else misses.

Interview signal: Candidates who answer "use an idempotency key" are at L4. Candidates who explain idempotency keys and the crash scenario between charge and record and why you still need reconciliation are at L6+.

Story · The ₹12,000 double-charge that made headlines

A food delivery app processed a ₹600 order during a network instability event. The payment service charged the card, received the gateway response, and began writing the transaction record to PostgreSQL. The DB connection dropped. The write failed. The service returned 500. The client retried. The gateway, queried again, returned the same charge response (it was idempotent on their side). The service treated the second response as a new charge and issued a second debit. Twenty users reported the same issue that hour — total ₹12,000 in duplicate charges before monitoring caught it.

The fix was not complex — it required storing the gateway's transaction ID immediately on receipt and checking for it before any second write. But the gap between "charge happened" and "we recorded it" was where the bug lived, and it required explicit design to close.

Layer 1 — Idempotency Keys (client to server)

The client generates a UUID before sending the payment request. This key is bound to the logical operation (this cart checkout), not the HTTP request. On retry, the same key is sent. The server stores the result keyed by this ID; retries return the stored result without re-processing.

Key design decisions interviewers probe:

  • Who generates it? Always the client. If the server generates it, the "create key" call itself can be retried and generate multiple keys.
  • What is it bound to? Bind to user_id + order_id hash — not just a random UUID — so even a client that loses the key can re-derive it deterministically.
  • TTL? 24–72 hours. Long enough that retries within a session succeed; short enough that a week-old key does not block a legitimate repeat purchase.
  • What is stored? The full response (status code + body), not just a boolean. Return the exact same response on every duplicate.
JavaScript Example — Idempotency Key Handler 
// payment-service.js — idempotency key handling
import crypto from 'crypto';

function deriveIdempotencyKey(userId, orderId) {
  return crypto.createHash('sha256')
    .update(`payment:${userId}:${orderId}`)
    .digest('hex');
}

async function processPayment(userId, orderId, amount, paymentMethod) {
  const idemKey = deriveIdempotencyKey(userId, orderId);
  const cacheKey = `idem:${idemKey}`;

  // 1. Check for existing result (in-flight or completed)
  const existing = await redis.get(cacheKey);
  if (existing) {
    const result = JSON.parse(existing);
    if (result.status === 'processing') {
      throw new Error('Payment is currently being processed — retry in a few seconds');
    }
    return result; // return the stored outcome without re-charging
  }

  // 2. Mark as in-flight (prevents duplicate concurrent requests)
  const acquired = await redis.set(cacheKey, JSON.stringify({ status: 'processing' }),
    'EX', 300, 'NX'); // NX = only set if not exists
  if (!acquired) {
    throw new Error('Concurrent payment detected — retry shortly');
  }

  try {
    // 3. Call payment gateway
    const gatewayResult = await chargeCard(paymentMethod, amount);

    // 4. Persist to database (gateway txn ID is stored immediately)
    await db.query(
      `INSERT INTO payments (user_id, order_id, idempotency_key, gateway_txn_id, amount, status)
       VALUES ($1, $2, $3, $4, $5, 'success')
       ON CONFLICT (idempotency_key) DO NOTHING`, // DB-level safety net
      [userId, orderId, idemKey, gatewayResult.transactionId, amount]
    );

    const result = { status: 'success', transactionId: gatewayResult.transactionId, amount };
    // 5. Store completed result with 48hr TTL
    await redis.setex(cacheKey, 172800, JSON.stringify(result));
    return result;
  } catch (err) {
    await redis.del(cacheKey); // allow retry on genuine error
    throw err;
  }
}

Layer 2 — Database Unique Constraint

The idempotency key check in Redis is fast but non-atomic with the database write. Under extremely rare race conditions (two requests arriving within microseconds before the Redis key is set), both could pass the Redis check. The database constraint is the fallback: 

-- payments table: unique constraint at DB level
CREATE TABLE payments (
  id              BIGSERIAL PRIMARY KEY,
  user_id         BIGINT NOT NULL,
  order_id        BIGINT NOT NULL,
  idempotency_key CHAR(64) NOT NULL UNIQUE,  -- SHA-256 hex
  gateway_txn_id  VARCHAR(128) UNIQUE,        -- prevents duplicate gateway records
  amount          NUMERIC(12,2) NOT NULL,
  status          VARCHAR(20) NOT NULL,
  created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE UNIQUE INDEX payments_order_success
  ON payments (user_id, order_id)
  WHERE status = 'success';
-- Prevents two successful payments for the same order even if idempotency key is different

The partial index (WHERE status = 'success') allows a failed payment attempt to be retried (different idempotency key if the client rotates), while blocking a second successful charge for the same order.

Layer 3 — The Crash Recovery Gap (the hardest part)

The most dangerous window: the service calls the gateway, receives a successful charge response, and then crashes before writing to the database. On restart/retry:

  • The gateway is re-called. It returns the same charge response (it is idempotent).
  • The service writes the record — a second write for the first charge, or a true second charge if the gateway created a new transaction.

The fix: store the gateway's transaction_id immediately in the outbox table (same transaction as the order write) before calling the gateway. On crash+retry, check for an existing gateway_txn_id before making a new call. 

// crash-safe payment with outbox
async function crashSafePayment(client, userId, orderId, amount) {
  await client.query('BEGIN');

  // Store payment intent with gateway_txn_id = NULL (pending)
  const { rows } = await client.query(
    `INSERT INTO payments (user_id, order_id, idempotency_key, amount, status)
     VALUES ($1, $2, $3, $4, 'pending')
     ON CONFLICT (idempotency_key) DO UPDATE SET status = payments.status
     RETURNING id, gateway_txn_id, status`,
    [userId, orderId, deriveIdempotencyKey(userId, orderId), amount]
  );

  if (rows[0].gateway_txn_id) {
    await client.query('ROLLBACK');
    return { status: rows[0].status, transactionId: rows[0].gateway_txn_id }; // already charged
  }

  await client.query('COMMIT');
  const paymentId = rows[0].id;

  // Call gateway AFTER commit — if we crash here, on retry we detect pending record above
  const gatewayResult = await chargeCard(paymentMethod, amount);

  // Update with gateway result
  await db.query(
    'UPDATE payments SET gateway_txn_id = $1, status = $2 WHERE id = $3',
    [gatewayResult.transactionId, 'success', paymentId]
  );
  return { status: 'success', transactionId: gatewayResult.transactionId };
}

Layer 4 — Event Deduplication (Kafka/queues)

If payments are triggered or confirmed via events, Kafka's at-least-once delivery can replay an event that was already processed:

  • Consumer-side dedup store — store processed event_id in Redis with a TTL matching Kafka's retention period. On receive: check before processing.
  • Kafka idempotent producer (enable.idempotence=true) — prevents the producer from publishing the same message twice due to retries.
  • Exactly-once transactions — Kafka supports transactional producers + consumers. Expensive but guarantees exactly-once end-to-end.

Layer 5 — Reconciliation Jobs (the safety net)

No matter how well-designed the above layers are, edge cases slip through. A reconciliation job runs every hour (or every 5 minutes for high-value transactions):

  1. Query the payment gateway API for all transactions in the last window.
  2. Cross-reference against the payments table.
  3. Flag any gateway charge with no matching DB record → alert + manual review.
  4. Flag any DB record with status=success but no matching gateway charge → refund candidate.

Stripe, Razorpay, and Braintree all expose reconciliation APIs exactly for this purpose. Use them. Reconciliation is not a sign of a broken system — it is defence-in-depth for a system that handles money.

Key Takeaway

Preventing duplicate payments requires a layered defence, not a single mechanism. Idempotency keys stop client retries; database constraints stop race conditions; the pending-record pattern stops crash-recovery gaps; event deduplication stops queue replays; and reconciliation catches everything else. In an interview, naming all five layers and explaining which failure each one addresses is what separates L4 from L6.
