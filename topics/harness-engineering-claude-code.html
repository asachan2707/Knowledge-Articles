Harness Engineering Claude Code: Building a Production AI Coding Agent

What it actually takes to build Claude Code as a production system — the harness engineering behind the agent loop, tool execution, permission system, context management, streaming output, and the software architecture decisions that make an AI coding agent reliable, safe, and fast at enterprise scale.

Domain: Agentic Systems · AI Engineering · Claude Code · Production Filter: Agentic · Claude Code · Setup Credit: Building Claude Code with Harness Engineering (levelup.gitconnected.com) Published: 2026-07-22

Claude Code is not just an API wrapper that calls Claude and prints the response. It is a production engineering artifact: an agentic loop that coordinates tool execution, context management, streaming I/O, permission enforcement, and state persistence across an arbitrarily long task. The engineering decisions behind it are the same ones you face when building any production AI agent — and most of them are not about the AI at all.

Harness engineering: The infrastructure layer that wraps an AI model to make it useful in production. The harness handles tool dispatching, permission checks, output rendering, error recovery, and session management — everything the model itself cannot do. The model is the intelligence; the harness is the reliability.

The Agent Loop Architecture

An AI coding agent runs a loop: send message to model → receive response → if response contains a tool call, execute it → send result back → repeat until no more tool calls. This is the ReAct (Reasoning + Acting) pattern. 

// Simplified agent loop pseudocode (not Claude Code's actual implementation)
async function runAgentLoop(initialPrompt, tools, maxTurns = 50) {
  const messages = [{ role: 'user', content: initialPrompt }];
  let turn = 0;

  while (turn < maxTurns) {
    turn++;

    // 1. Send to model
    const response = await anthropic.messages.create({
      model: 'claude-opus-4-8',
      max_tokens: 8096,
      tools: tools.map(t => t.schema),
      messages,
    });

    // 2. Append assistant message
    messages.push({ role: 'assistant', content: response.content });

    // 3. Check for tool use
    const toolUses = response.content.filter(b => b.type === 'tool_use');
    if (toolUses.length === 0) {
      // Model responded without tool use = task complete or needs input
      if (response.stop_reason === 'end_turn') break;
    }

    // 4. Execute all tool calls in this turn
    const toolResults = await Promise.all(
      toolUses.map(async toolUse => {
        const tool = tools.find(t => t.name === toolUse.name);
        const result = await executeTool(tool, toolUse.input);
        return { type: 'tool_result', tool_use_id: toolUse.id, content: result };
      })
    );

    // 5. Send tool results back
    messages.push({ role: 'user', content: toolResults });
  }

  return messages;
}

This loop is the foundation. Every engineering decision that follows is about making this loop safe, observable, fast, and correct under real-world conditions.

Tool Architecture: The Tool Registry

A production agent has many tools. The tool registry manages their lifecycle: registration, schema validation, permission checks, execution routing, and error handling. 

// Tool registry — manages all available tools
class ToolRegistry {
  constructor(permissionSystem) {
    this.tools = new Map();
    this.permissions = permissionSystem;
  }

  register(tool) {
    // Validate tool schema at registration time, not call time
    if (!tool.name || !tool.description || !tool.schema || !tool.execute) {
      throw new Error(`Tool ${tool.name} missing required fields`);
    }
    this.tools.set(tool.name, tool);
    return this;
  }

  async execute(toolName, input, context) {
    const tool = this.tools.get(toolName);
    if (!tool) throw new Error(`Unknown tool: ${toolName}`);

    // Permission check before execution
    const allowed = await this.permissions.check(toolName, input, context);
    if (!allowed.granted) {
      if (allowed.requiresConfirmation) {
        // Pause loop, prompt user, wait for response
        const confirmed = await context.promptUser(
          `Allow ${toolName} with input: ${JSON.stringify(input, null, 2)}?`
        );
        if (!confirmed) return { content: 'User denied this action.', isError: true };
      } else {
        return { content: `Permission denied for ${toolName}`, isError: true };
      }
    }

    // Execute with timeout and error handling
    try {
      return await Promise.race([
        tool.execute(input, context),
        timeout(tool.timeoutMs ?? 30_000, toolName),
      ]);
    } catch (err) {
      context.logger.error({ toolName, err }, 'Tool execution failed');
      return { content: `${toolName} failed: ${err.message}`, isError: true };
    }
  }

  // Returns tool schemas for the model's `tools` parameter
  getSchemas() {
    return [...this.tools.values()].map(t => ({
      name: t.name,
      description: t.description,
      input_schema: t.schema,
    }));
  }
}

The Permission System

Claude Code's permission model is one of its most important engineering decisions. Tools are classified by risk level, and the user's permission mode determines which require confirmation. 

// Permission system — three tiers of tool risk
const ToolRisk = {
  READ_ONLY: 'read-only',       // Read files, grep, list dirs — always allowed
  WRITE: 'write',               // Edit files, create files — auto-allowed in most modes
  DESTRUCTIVE: 'destructive',   // Delete files, git push, run servers — require confirmation
  NETWORK: 'network',           // HTTP calls to external services — require confirmation
  SHELL: 'shell',               // Arbitrary bash — require explicit allow pattern
};

class PermissionSystem {
  constructor(mode, allowList = []) {
    // Modes: 'plan' (read-only), 'auto' (permissive), 'manual' (ask for everything)
    this.mode = mode;
    this.allowList = allowList; // pre-approved patterns
  }

  async check(toolName, input, context) {
    const risk = this.getToolRisk(toolName, input);

    if (this.mode === 'plan') {
      // Plan mode: only read-only tools allowed
      return { granted: risk === ToolRisk.READ_ONLY, requiresConfirmation: false };
    }

    if (this.mode === 'auto') {
      // Auto mode: allow everything except destructive shell commands not on allowList
      if (risk === ToolRisk.SHELL) {
        const allowed = this.allowList.some(pattern => new RegExp(pattern).test(input.command));
        return { granted: allowed, requiresConfirmation: !allowed };
      }
      return { granted: true, requiresConfirmation: false };
    }

    // Manual mode: everything requires confirmation
    return { granted: false, requiresConfirmation: true };
  }

  getToolRisk(toolName, input) {
    const riskMap = {
      'Read': ToolRisk.READ_ONLY,
      'Grep': ToolRisk.READ_ONLY,
      'Edit': ToolRisk.WRITE,
      'Write': ToolRisk.WRITE,
      'Bash': input?.command?.match(/rm|drop|truncate|git push/) ? ToolRisk.DESTRUCTIVE : ToolRisk.SHELL,
      'WebFetch': ToolRisk.NETWORK,
    };
    return riskMap[toolName] ?? ToolRisk.DESTRUCTIVE;
  }
}

Context Management: The Sliding Window Problem

Claude has a 200k token context window. A long agentic session — reading many files, making many tool calls — will eventually exhaust it. Context management is the harness's job, not the model's.

Claude Code's strategies:

  • Automatic compaction: When the context exceeds a threshold (e.g., 70% of max), the harness sends the full conversation to the model and asks it to produce a concise summary. The summary replaces the detailed history. Future turns have a shorter but semantically complete context.
  • Tool result truncation: Long tool outputs (large file reads, grep results with hundreds of matches) are truncated before being appended to context. The model is told the result was truncated and offered to request more.
  • Lazy file reading: The harness does not preload all relevant files into context. It gives the model Read/Grep tools and lets it request files on demand — only content the model actively requested enters context.
  • Rolling window for long tasks: For very long tasks, older completed subtask results are summarised and moved out of context while recent ones remain in full detail.
// Context budget tracking
class ContextBudget {
  constructor(maxTokens = 200_000) {
    this.maxTokens = maxTokens;
    this.used = 0;
    this.COMPACTION_THRESHOLD = 0.70; // compact at 70%
  }

  add(tokens) { this.used += tokens; }
  remaining() { return this.maxTokens - this.used; }
  shouldCompact() { return this.used / this.maxTokens > this.COMPACTION_THRESHOLD; }

  truncateToolResult(result, toolName) {
    const MAX_RESULT_TOKENS = 8_000; // ~32k characters
    const chars = result.length;
    if (chars <= MAX_RESULT_TOKENS * 4) return result;

    const truncated = result.slice(0, MAX_RESULT_TOKENS * 4);
    const dropped = chars - MAX_RESULT_TOKENS * 4;
    return `${truncated}\n\n[...${dropped} characters truncated. Use the ${toolName} tool again with more specific parameters to get the rest.]`;
  }
}

Streaming Output: The User Experience Layer

Without streaming, the user stares at a blank terminal for 10 seconds while the model generates a response. Streaming delivers text tokens as they are produced, which is critical for perceived responsiveness in an interactive coding session. 

// Streaming response handler
async function streamingAgentTurn(messages, tools) {
  process.stdout.write('\n'); // visual separator

  let fullText = '';
  let toolUses = [];

  const stream = await anthropic.messages.stream({
    model: 'claude-opus-4-8',
    max_tokens: 8096,
    tools: tools.getSchemas(),
    messages,
  });

  for await (const event of stream) {
    if (event.type === 'content_block_delta') {
      if (event.delta.type === 'text_delta') {
        process.stdout.write(event.delta.text); // stream text to terminal
        fullText += event.delta.text;
      }
      if (event.delta.type === 'input_json_delta') {
        // Accumulate tool input JSON (streamed in chunks)
        // Don't display to user — too noisy
      }
    }
    if (event.type === 'content_block_start' && event.content_block.type === 'tool_use') {
      // Signal to user that a tool is being invoked
      process.stdout.write(`\n[Calling ${event.content_block.name}...]\n`);
    }
  }

  const finalMessage = await stream.getFinalMessage();
  return finalMessage;
}

State Persistence: Resumable Sessions

A coding agent session can last hours. If the terminal is closed, the session should be resumable from where it left off — not restarted. This requires persisting the full message history and tool state. 

// Session persistence
import { createHash } from 'crypto';
import fs from 'fs/promises';

class SessionStore {
  constructor(sessionDir) {
    this.sessionDir = sessionDir;
  }

  sessionPath(sessionId) {
    return `${this.sessionDir}/${sessionId}.jsonl`;
  }

  async append(sessionId, turn) {
    // JSONL: one JSON object per line for streaming-safe appends
    const line = JSON.stringify({ ts: Date.now(), ...turn }) + '\n';
    await fs.appendFile(this.sessionPath(sessionId), line, 'utf-8');
  }

  async load(sessionId) {
    const content = await fs.readFile(this.sessionPath(sessionId), 'utf-8');
    return content.trim().split('\n')
      .filter(Boolean)
      .map(line => JSON.parse(line));
  }

  generateSessionId(cwd, gitBranch) {
    // Stable session ID tied to project + branch
    return createHash('sha256')
      .update(`${cwd}:${gitBranch}`)
      .digest('hex')
      .slice(0, 16);
  }
}

Key Engineering Lessons from Harness Design

  • The model is not the agent. The model generates text. The agent is the harness that executes actions, checks permissions, manages context, and talks to the user. These are separate concerns and should be separate code.
  • Tool errors must return to the model, not crash the loop. Every tool execution must be wrapped in try/catch. The error is returned as a tool result so the model can reason about it and try an alternative approach.
  • Max turn limits are safety rails, not success criteria. A 50-turn limit prevents infinite loops; it is not a quality floor. If the agent consistently hits the limit, the task decomposition or tool design is wrong.
  • Streaming is not optional for interactive agents. A 10-second silent terminal is not an acceptable UX for a coding agent. Stream tokens from the first byte.
  • Permission prompts must be atomic from the user's perspective. Never ask "is this OK?" mid-task without showing exactly what the action is. Permission request = full context, specific action, reversibility assessment.
  • Context is a resource — budget it like memory. Every tool result added to context costs future capacity. Tool output truncation and session compaction are not optimisations; they are correctness requirements for long tasks.

Key Takeaway

Building a production AI coding agent is 20% AI and 80% harness engineering. The model handles reasoning; the harness handles everything that makes reasoning safe to deploy: tool execution, permission enforcement, context budgeting, streaming output, session persistence, and error recovery. The architecture described here — tool registry, tiered permission system, context budget tracker, streaming loop, JSONL session store — is the minimum viable harness for a reliable agent. Any missing layer becomes an incident.
