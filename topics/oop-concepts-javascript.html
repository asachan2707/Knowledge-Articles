12 Core OOP Concepts Every Developer Should Know — In JavaScript

Object-oriented programming organises code around real-world entities — Users, Orders, Payments — keeping related data and behaviour together rather than scattering them across variables and functions. The 12 concepts below are not abstract theory; they are the vocabulary every code review, design discussion, and interview uses.

Core idea: OOP isn't about class syntax — it's about managing complexity as systems grow. The four pillars (Encapsulation, Abstraction, Inheritance, Polymorphism) are tools for controlling what can change without breaking what depends on it.

Story · When OOP pays off

A team had a sendNotification() function that was 400 lines long — a wall of if/else for email vs SMS vs push vs Slack. Adding a new channel meant touching the wall, risking every other channel. One refactor later: a NotificationChannel abstract class, four concrete subclasses, a factory — each channel was independently testable and a new channel was a new file, not a new risk.

The 12 concepts

Overview

1. Class

Blueprint for objects. Defines properties and methods shared by all instances of that type.

2. Object / Instance

A specific realisation of a class. new User('Alice') creates an object from the User class blueprint.

3. Encapsulation

Bundle data + behaviour together, hide internal details. Expose only what callers need via a public interface.

4. Abstraction

Expose what an object does, hide how it does it. Callers interact with the interface, not the implementation.

5. Inheritance

A child class inherits properties and methods from a parent. class Admin extends User.

6. Polymorphism

One interface, many implementations. A Channel.send() call works for Email, SMS, and Slack because each implements send().

7. Composition over Inheritance

Build complex objects by combining simpler behaviours rather than building deep inheritance trees.

8. Mixin

Inject reusable behaviour into a class without inheritance. Add Serializable or Loggable to any class.

9. Interface / Contract

Define what methods an object must have without specifying how. Enables programming to a contract, not an implementation.

10. SOLID: Single Responsibility

A class should have one reason to change. UserService handles user logic; EmailService handles email — never both.

11. SOLID: Open/Closed

Open for extension (add new subclasses), closed for modification (don't change the base class). New features → new files.

12. SOLID: Liskov Substitution

A subclass should be substitutable everywhere its parent is used without breaking the caller. The deepest OOP principle.

JavaScript Example

All 12 concepts in one coherent example

JavaScript Example 
// ── 1. Class & 2. Object ──────────────────────────────────────────
class User {
  // ── 3. Encapsulation: private field, controlled access ─────────
  #passwordHash;

  constructor(name, email, password) {
    this.name = name;
    this.email = email;
    this.#passwordHash = btoa(password); // real app: bcrypt
    this.createdAt = new Date();
  }

  checkPassword(password) {
    return btoa(password) === this.#passwordHash;
  }

  // ── 4. Abstraction: expose behaviour, hide detail ──────────────
  toString() {
    return `User(${this.name}, ${this.email})`; // caller never sees #passwordHash
  }
}

const alice = new User("Alice", "alice@example.com", "secret"); // Object

// ── 5. Inheritance ────────────────────────────────────────────────
class Admin extends User {
  constructor(name, email, password, permissions = []) {
    super(name, email, password);
    this.permissions = permissions;
  }

  can(action) { return this.permissions.includes(action); }
}

// ── 6. Polymorphism ───────────────────────────────────────────────
// Multiple channel types, all respond to send(message)
class NotificationChannel {
  send(message) { throw new Error("send() must be implemented"); }
}

class EmailChannel extends NotificationChannel {
  send(message) { return `📧 Email: ${message}`; }
}

class SMSChannel extends NotificationChannel {
  send(message) { return `📱 SMS (160 chars): ${message.slice(0, 160)}`; }
}

class SlackChannel extends NotificationChannel {
  send(message) { return `💬 Slack #general: ${message}`; }
}

// Caller doesn't know or care which channel — polymorphism
function notify(channels, message) {
  return channels.map((ch) => ch.send(message));
}

notify([new EmailChannel(), new SMSChannel(), new SlackChannel()], "Deploy complete");

// ── 7. Composition over Inheritance ──────────────────────────────
// Instead of NotificationChannel extends Loggable extends Retryable...
// compose behaviours:
function withRetry(channel, maxAttempts = 3) {
  return {
    async send(message) {
      for (let i = 0; i < maxAttempts; i++) {
        try { return await channel.send(message); }
        catch (err) { if (i === maxAttempts - 1) throw err; }
      }
    },
  };
}

const reliableEmail = withRetry(new EmailChannel());

// ── 8. Mixin — inject Serializable behaviour ──────────────────────
const Serializable = (Base) => class extends Base {
  toJSON() { return JSON.stringify(Object.fromEntries(
    Object.entries(this).filter(([k]) => !k.startsWith("#"))
  )); }
  static fromJSON(json) { return Object.assign(new this(), JSON.parse(json)); }
};

class SerializableUser extends Serializable(User) {}

// ── 9. Interface (contract via duck typing in JS) ─────────────────
function validateChannel(channel) {
  if (typeof channel.send !== "function") {
    throw new TypeError("channel must implement send(message)");
  }
}

// ── 10. Single Responsibility ─────────────────────────────────────
class UserRepository { // only handles persistence
  async findById(id) { /* DB query */ }
  async save(user) { /* DB insert/update */ }
}
class UserAuthService { // only handles auth
  generateToken(user) { return `token_${user.email}`; }
  verifyToken(token) { /* JWT verify */ }
}

// ── 11. Open/Closed Principle ─────────────────────────────────────
// Add a new channel WITHOUT modifying NotificationChannel or notify()
class TeamsChannel extends NotificationChannel {
  send(message) { return `🟦 Teams: ${message}`; }
}
notify([new TeamsChannel()], "New alert"); // works without any base changes

// ── 12. Liskov Substitution Principle ─────────────────────────────
// Admin must work everywhere User works
function greetUser(user) {
  console.log(`Hello, ${user.name}!`); // relies only on User interface
}
const admin = new Admin("Bob", "bob@example.com", "pw", ["delete"]);
greetUser(admin); // ✓ Admin substitutes for User without breaking greetUser
Liskov in practice: A common violation is a ReadOnlyList extending List but throwing on .add(). Callers that received a List and called .add() break silently. Fix: ReadOnlyList should not extend List — use composition or a separate interface.
FAQ

Interview questions

What's the difference between abstraction and encapsulation? Encapsulation is about hiding data (private fields, controlled access). Abstraction is about hiding complexity (exposing only the "what", hiding the "how"). Both achieve the goal of reducing coupling, but from different angles.

When should you prefer composition over inheritance? When you'd need more than 2–3 levels of inheritance, when behaviours need to be mixed in independently, or when the "is-a" relationship is forced. Composition is almost always more flexible for real-world systems.

Is JavaScript truly OOP? JavaScript is prototype-based and multi-paradigm. The class syntax is syntactic sugar over prototype chains. You get the patterns without strict enforcement — which means you need more discipline, not less.

Key Takeaway

OOP's four pillars — Encapsulation, Abstraction, Inheritance, Polymorphism — are different tools for the same job: managing what can change independently of what depends on it. Encapsulation prevents direct data manipulation. Abstraction hides implementation. Inheritance shares behaviour. Polymorphism enables one interface for many implementations. Add SOLID principles and you have the vocabulary for every serious code review, architecture discussion, and senior engineering interview.
