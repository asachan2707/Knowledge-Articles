Every time a rider opens Uber and sees cars moving on the map, a data pipeline is running that is more complex than it looks: 5 million driver phones emitting GPS coordinates every 4 seconds, 1.25 million location updates per second funnelled through Kafka, stored in geospatial indexes, queried in milliseconds by the dispatch system, and aggregated in real time to compute surge pricing by city zone. This is the complete end-to-end story.

Scale reference: 5M drivers × 15 GPS updates/minute = 75M location events/minute = 1.25M events/second sustained, 24/7, globally. Each event triggers reads across proximity search, driver availability, zone calculations, and demand forecasting. The write throughput is the easy part.

Core idea: The speed comes from three layered optimisations — spatial filtering that cuts 5 million drivers down to 50, permanent push connections that eliminate polling, and parallel ETA computation that scores each candidate simultaneously rather than sequentially.

Story · The problem that broke Monolith Uber

Early Uber ran on a Python/PostgreSQL monolith. This worked until driver density in major cities hit a threshold where the location update queries started competing with booking queries for database connections. A surge of booking requests during rush hour would slow down location updates; stale location data degraded matching quality; degraded matching caused retries; retries increased write load. The feedback loop collapsed the service.

The solution was not "more database." It was a complete rearchitecture around the insight that location tracking is a fundamentally different workload from booking: high-write, spatial, time-series, with completely different read patterns. Separating them was the founding act of Uber's microservices architecture.

Why this question matters

This problem sits at the intersection of real-time systems, distributed state, and geospatial algorithms — exactly the combination that separates senior engineers from the rest. It has been asked in virtually every FAANG-level system design loop since 2021. Answering it well requires knowing not just the components, but which tools to pick and why you would reject the alternatives.

Your interviewer already knows the happy-path diagram. What they are probing is whether you surface failure modes, quantify the bottlenecks, and design the failure-recovery logic without being prompted.

The complete use case

End-to-end: GPS ping to matched ride

The full journey of a location update from driver phone to matched rider:

  1. GPS emit: The driver app samples GPS every 4 seconds and sends a location update to Uber's servers. Payload: driver ID, latitude, longitude, bearing, speed, timestamp, accuracy radius.
  2. Mobile gateway: The update hits a regional API gateway (WebSocket for active drivers, HTTPS POST for background updates). The gateway authenticates, rate-limits per driver, and forwards to the location ingestion pipeline.
  3. Kafka ingestion: Location events are written to a Kafka topic partitioned by driver ID (consistent hashing ensures all updates for one driver land on one partition, maintaining order). Kafka provides durability and decouples the downstream consumers from the write rate.
  4. Location service consumers: Multiple services consume the Kafka topic independently: the Location Store (persists current driver position), the Zone Aggregator (updates supply/demand counts per geospatial cell), the ETA Calculator (updates routing graph edge weights), and the Telemetry Store (time-series data for analytics).
  5. Location Store: Writes the driver's current position to a fast in-memory data structure (Redis with geospatial indexes). The write path is a simple Redis GEOADD: GEOADD drivers:available {longitude} {latitude} {driver_id}.
  6. Proximity query (rider-side): When a rider opens the app, a GEORADIUS query retrieves all available drivers within N km: GEORADIUS drivers:available {longitude} {latitude} 5 km ASC COUNT 50. Redis executes this in O(N+log(M)) time — sub-millisecond at scale.
  7. Dispatch: When a rider requests a trip, the dispatch system runs a matching algorithm against available drivers in the rider's proximity, considering ETA, driver rating, vehicle type, and surge state. It sends a trip offer to the top-ranked driver.
  8. Offer/Accept loop: The dispatch system sends an offer to the driver app (push notification via APNS/FCM). If accepted, the booking is confirmed. If rejected or timed out, the next driver in the ranking receives an offer.

Geospatial indexing

Geospatial Indexing: Geohash, S2 and H3 Hexagons

The naive approach and why it fails

A straight SELECT * FROM drivers WHERE distance(lat, lng, :rider_lat, :rider_lng) < 5000 requires a full table scan of 5 million rows and runs the Haversine formula on every row. Even with a PostGIS R-tree index it cannot sustain 400 ride requests/sec at p99 < 200 ms. You need a lookup structure, not a search.

Geohash (legacy — do not use for production)

  • Interleaves latitude and longitude bits into a base-32 string.
  • Nearby strings share a common prefix — but only approximately. Two points 10 m apart can have completely different hashes if they straddle a grid boundary.
  • Cell shapes are rectangular, so neighbours are not equidistant from the centre.
  • Longitude precision varies: 111 km per degree at the equator, 0 km at the poles.
  • Red flag in interviews: proposing Geohash without mentioning its boundary discontinuity problem signals you have not thought this through.
  • Where it is still used: Redis's native GEOADD/GEORADIUS commands use geohash internally. For current driver positions (sub-second queries) that is the standard solution, trading tiny precision errors (about ±0.6 m at precision 12) for O(log N) writes and reads.

S2 Geometry (Google's choice)

  • Projects the Earth onto a cube face, then applies a Hilbert space-filling curve.
  • Handles poles naturally; great for coverage algorithms and exact region queries.
  • Computationally heavier and harder to reason about than H3.
  • Best fit: static geofencing, map tile coverage. Overkill for real-time driver lookup.

H3 — Uber's production choice

H3 divides the Earth into a hierarchy of regular hexagons at 16 resolution levels. Hexagons have one key property that rectangles and triangles lack: every neighbour of a hexagon shares a full edge and is equidistant from the centre. That makes radius expansion (searching progressively larger rings of cells) both fast and spatially uniform. 


H3 Resolution  |  Avg cell area   |  Practical use
---------------|------------------|-------------------------------
Res 4          |  1,770 km²       |  Country-level surge zones
Res 7          |  5.16 km²        |  City neighbourhood supply
Res 10         |  0.0296 km²      |  Driver-level matching (~170 m)
Res 12         |  0.0007 km²      |  Precise pickup pin

H3 resolution levels — Uber uses res 10 for driver lookup

How the lookup works

  • Driver comes online: GPS coordinates → H3 cell index at res 10 (e.g. 8a2a1072b59ffff) in O(1). Stored in Redis as a sorted set keyed by cell ID.
  • Rider requests: rider's GPS → H3 cell index. Query Redis for drivers in that cell + its 6 immediate neighbours (ring 1).
  • No drivers in ring 1: expand to ring 2 (18 additional cells), then ring 3, up to ring 5 (~max 5 km at res 10). This is the progressive radius expansion — O(1) per ring because neighbour lookup is a constant-time bitwise operation.
  • Result: instead of scanning 5 million global drivers, you examine 50–100 drivers in adjacent cells. That is the source of the speed.

// Node.js — H3 lookup (h3-js library)
import * as h3 from 'h3-js';

const RESOLUTION = 10;

// Convert GPS to H3 cell
function getH3Cell(lat, lng) {
  return h3.latLngToCell(lat, lng, RESOLUTION);
}

// Get all cells within k rings
function getSearchCells(lat, lng, rings = 1) {
  const center = getH3Cell(lat, lng);
  return h3.gridDisk(center, rings); // returns center + all cells in k rings
}

// Example: rider at (40.7128, -74.0060), search ring 1
const cells = getSearchCells(40.7128, -74.0060, 1);
// → 7 cells (center + 6 neighbours)
// Use these cell IDs to query Redis

What Uber uses H3 for

Aggregating at hex-cell level (equidistant neighbours) is more accurate for demand forecasting and surge zone calculation. Uber uses H3, at multiple resolutions from the world down to about 5 km² (res 7) cells, for:

  • Surge pricing zones: Each H3 cell at resolution 7 (~5 km²) has a real-time supply/demand ratio. Surge multiplier is computed per cell.
  • Demand forecasting: ML models predict demand by H3 cell + time horizon. Drivers on the app see demand heat maps based on H3 cell density.
  • Driver positioning: The in-app "move here" nudge is calculated by comparing current cell demand to adjacent cell demand — again using H3's uniform-distance neighbours.

Why hexagons over squares or circles

Beyond the equidistant-neighbour property above:

  • Hexagonal tessellation covers a map surface with no gaps and no overlaps.
  • H3 provides parent/child resolution traversal — a resolution-7 hexagon contains exactly 7 resolution-8 hexagons, enabling drill-down without recomputing indices.
The messaging backbone

Why Kafka is central to the location pipeline

At 1.25M location updates/second, no single downstream service can keep up synchronously. Kafka solves this by decoupling write speed from processing speed:

  • Durability: Location updates are written to disk in Kafka before any consumer processes them. No update is lost even if a consumer crashes.
  • Fan-out: Multiple independent consumers (Location Store, Zone Aggregator, ETA Calculator, Telemetry) each process the same event stream at their own pace without interfering with each other or with the write path.
  • Replay: Kafka retains events for a configurable period (typically 7 days). If a consumer needs to reprocess data (bug fix, backfill, new analytics model), it can replay from any offset without touching the write path.
  • Backpressure handling: If one consumer falls behind, Kafka queues its events independently. The write path is unaffected. The consumer catches up when capacity frees up.

Partitioning strategy

Location topic partitioned by driver_id mod N_partitions. This guarantees that all location updates for one driver land on one partition, which guarantees ordering within a driver's update stream. The Location Store consumer can maintain monotonic location state per driver without distributed locks.

Location pipeline

WebSocket Location Pipeline: 5 Million Concurrent Connections

Why WebSockets, not HTTP polling

An HTTP poll every 4 seconds from 5 million drivers means 1.25 million TCP connections opened and closed per second, each with a full TLS handshake. That is an order of magnitude more CPU overhead than maintaining persistent connections. WebSockets also eliminate the latency of connection setup per message: a location update becomes a single frame on an already-open socket.

Architecture of the gateway layer

  • Gateway nodes: Each handles 10,000–50,000 concurrent WebSocket connections. At 5 million connections you need ~100–500 gateway pods behind a load balancer.
  • Sticky sessions: All frames from driver ID X always route to the same gateway node. This keeps the routing state local and avoids cross-node fan-out on every message.
  • Heartbeat: Ping/pong every 30 seconds. If no pong, close connection and remove driver from Redis within 35 seconds to avoid stale location data.
  • Message format: Binary frames (MessagePack or Protobuf), not JSON text. Saves ~40% bandwidth at scale.

Dispatch system

Matching 5 million drivers to ride requests in real time

The dispatch problem: a rider requests a trip. The system must select the optimal driver and have them accept within seconds. The constraints: low ETA, high acceptance probability, efficient routing, fair distribution across drivers, surge zone awareness.

Dispatch algorithm

  1. Proximity retrieval: GEORADIUS query fetches available drivers within configurable radius (starts at 2 km, expands if insufficient supply).
  2. ETA calculation: For each candidate driver, compute estimated pickup time using current road graph + driver bearing. Uber's routing engine (based on OSRM or similar) computes these in parallel using precomputed contraction hierarchies.
  3. Scoring: Rank drivers by a composite score: ETA weight + driver rating weight + acceptance rate weight + distance-to-zone-boundary weight. The weights are tuned by market (city, time of day, surge state).
  4. Sequential offer: Offer to top-ranked driver. If rejected/timeout (15s default), move to next. Track rejection rate per driver — chronic high rejection rate affects scoring.
  5. Batch dispatch (high surge): During very high demand, use batch dispatch: simultaneously offer to multiple drivers and accept the first response. Reduces rider wait time at the cost of higher driver notification volume.

The matching graph problem

At peak, Uber runs thousands of concurrent matching operations per city, each with overlapping candidate driver sets. Naive sequential matching creates conflict: the same top-ranked driver could be offered multiple concurrent trips. The solution is a matching graph with reservation locks: when a driver enters the offer stage, they are "soft-locked" in the driver availability index — excluded from other concurrent matches until the offer resolves.

Dispatch protocol

Matching Algorithm: The Full Dispatch Protocol

Uber does not simply assign the geographically closest driver. It assigns the driver likely to arrive soonest, weighted by rating and penalised for high-surge zones. The full protocol is a supply pool search → parallel ETA scoring → ranked offer wave dispatch.

Distributed lock — preventing double-match

The race condition: two drivers press Accept within milliseconds of each other. Without a lock, both get a "trip created" confirmation and both drive to the pickup. This is the most important correctness constraint in the entire system. 


// Node.js — Redis lock acquire/release
const redis = require('ioredis');
const { v4: uuid } = require('uuid');

async function acquireLock(riderId, ttlSec = 10) {
  const token = uuid();
  // SET NX is atomic — only one caller wins
  const ok = await redis.set(
    `rider:${riderId}:lock`,
    token,
    'EX', ttlSec,
    'NX'             // only set if key does NOT exist
  );
  return ok === 'OK' ? token : null;
}

// Lua script: check token matches before deleting (atomic)
const RELEASE_SCRIPT = `
  if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
  else
    return 0
  end
`;

async function releaseLock(riderId, token) {
  return redis.eval(RELEASE_SCRIPT, 1, `rider:${riderId}:lock`, token);
}

// Usage in match handler
async function confirmMatch(riderId, driverId) {
  const token = await acquireLock(riderId);
  if (!token) throw new Error('Rider already matched');

  try {
    const rider = await getRider(riderId);
    if (rider.status !== 'requesting') return; // already cancelled or matched

    await db.query(
      `INSERT INTO trips (rider_id, driver_id, status)
       VALUES ($1, $2, 'accepted')
       ON CONFLICT (rider_id) DO NOTHING`,
      [riderId, driverId]
    );
  } finally {
    await releaseLock(riderId, token);
  }
}

Redis SET NX + Lua release — the only reliable way to prevent double-match

ETA engine

ETA Engine: Road Network, A* and Hybrid Traffic

The road network as a weighted directed graph

Every intersection is a node. Every road segment is a directed edge (one-way streets are single-direction edges). Each edge carries: distance in metres, speed limit, turn restrictions, road type (motorway / arterial / local). The graph for a single city has millions of nodes.

Dijkstra vs A*

Algorithmf(n)Search patternSpeed
Dijkstra g(n) — actual cost from start Expands uniformly in all directions O(E + V log V)
A* g(n) + h(n) — actual + heuristic Focuses toward the goal (straight-line estimate) 3–10× faster than Dijkstra on road graphs

A* works correctly as long as the heuristic h(n) is admissible — it never overestimates the true remaining cost. The great-circle (Haversine) distance divided by the fastest possible road speed is a perfect admissible heuristic for road routing.

Hybrid traffic model


// For each road segment edge:
estimated_speed =
  0.4 × real_time_speed[segment_id]         // Kafka stream, refreshed every 5 min
  + 0.6 × historical_avg_speed[segment_id]  // lookup by [hour_of_day][day_of_week]

// Edge travel time
edge_time_sec = edge_distance_m / (estimated_speed × 1000 / 3600)

// A* heuristic: great-circle distance / max possible speed
h(node) = haversine(node, destination) / MAX_SPEED_MPS

Traffic blending — 40% live data, 60% historical profile

Two-tier ETA computation

  • Fast ETA (30–50 ms): Run A* on a small subgraph (1 km radius), only to a depth of 100 nodes. Good enough for ranking the supply pool. Applied to all 20 candidates simultaneously in parallel goroutines / async workers.
  • Accurate ETA (200–500 ms): Full A* on the complete road network for the top 3 candidates. Used for the quoted arrival time shown to the rider.
  • Cache: Key = hash(from_h3_10, to_h3_10, hour_of_day), TTL 30 s. Cache hit rate ~65% for common origin/destination pairs.
Surge pricing

Surge Pricing: Real-Time Supply/Demand Balance

Surge pricing is not a business decision made per city — it is a continuous computation made per H3 cell every 30–60 seconds, driven by real-time supply (available drivers in the cell) and demand (unfulfilled trip requests in the cell).

Surge computation pipeline

  1. Supply signal: The Zone Aggregator consumes the location Kafka topic and maintains a count of available drivers per H3 cell in Redis. Updated continuously.
  2. Demand signal: Every trip request is assigned to its origin H3 cell. Unfulfilled requests older than N seconds constitute demand. Demand count per cell is maintained in Redis.
  3. Surge ratio: surge_ratio = demand_count / supply_count. When above 1 (more demand than supply), surge multiplier activates. The multiplier is a step function of the ratio (1.0x below threshold, 1.25x, 1.5x, 2.0x at discrete thresholds).
  4. Smoothing: Raw ratios spike during single large events (concerts, airports). An exponential moving average smooths the ratio over a rolling 2-minute window to avoid aggressive flicker.
  5. Distribution: Surge multiplier per cell is published to the rider and driver apps via a push channel. Driver app heat maps show which cells have the highest multiplier — incentivising driver repositioning.

The feedback loop and equilibrium

Surge pricing is a feedback mechanism: high prices incentivise more drivers to enter the area, increasing supply, which lowers the ratio, which reduces the surge multiplier. The system reaches equilibrium when supply meets demand at the market-clearing price. The speed of this equilibrium depends on how quickly drivers can reposition — typically 5–15 minutes in dense urban areas.

Story · Mumbai monsoon, 4 PM, 6.5× surge in 8 minutes

Mumbai, monsoon season. At 15:52, it starts raining heavily. By 16:00, 340,000 simultaneous ride requests are active in the city. Available drivers: 48,000. Demand/supply ratio: 7.08. Surge multiplier: 6.5×. A 5km trip that would cost ₹150 now costs ₹975.

The surge did not appear instantly — it built over 8 minutes as the pipeline detected the demand spike, computed ratios per hexagon, applied the multiplier function, and pushed updates to all active apps. During those 8 minutes, riders who tapped "Request Ride" at the pre-surge price saw a different price on the next screen. That inconsistency — quote given, price changed before confirmation — is a race condition with real financial consequences.

Surge pricing · implementation

Stream topology and multiplier code (H3 res-7 pipeline)

  1. Event ingestion — rider requests and driver GPS updates stream into Kafka topics ride-requests and driver-positions.
  2. H3 encoding — a stateless enrichment service converts each (lat, lng) to an H3 hexagon ID at resolution 7.
  3. Stream aggregation — a Flink or Kafka Streams job maintains a 5-minute sliding window count per hexagon: active requests and available drivers.
  4. Surge computation — every 30 seconds, per hexagon: compute demand/supply ratio, apply multiplier function, publish to surge-updates topic.
  5. Surge propagation — fan-out service pushes updated multipliers to all app instances with users in that hexagon.

  { maxRatio: 5.0,  multiplier: 3.0 },
  { maxRatio: 7.0,  multiplier: 5.0 },
  { maxRatio: Infinity, multiplier: 8.0 }, // hard cap — regulatory/PR reasons
];

function computeSurgeMultiplier(activeRequests, availableDrivers) {
  if (availableDrivers === 0) {
    return availableDrivers === 0 && activeRequests === 0 ? 1.0 : 8.0; // no drivers = max surge
  }
  const ratio = activeRequests / availableDrivers;
  const entry = SURGE_TABLE.find(t => ratio <= t.maxRatio);
  return entry.multiplier;
}

// Sliding window aggregator per hexagon (conceptual — actual uses Kafka Streams DSL)
class HexagonAggregator {
  constructor(hexId, windowMs = 5 * 60 * 1000) {
    this.hexId = hexId;
    this.windowMs = windowMs;
    this.requests = [];  // {timestamp, count}
    this.drivers = new Map(); // driverId → {lastSeen, status}
  }

  onRideRequest(count, timestamp) {
    this.requests.push({ timestamp, count });
    this.evictExpired(timestamp);
  }

  onDriverUpdate(driverId, status, timestamp) {
    this.drivers.set(driverId, { lastSeen: timestamp, status });
    this.evictStaleDrivers(timestamp);
  }

  evictExpired(now) {
    const cutoff = now - this.windowMs;
    this.requests = this.requests.filter(r => r.timestamp > cutoff);
  }

  evictStaleDrivers(now) {
    const cutoff = now - 120_000; // 2 min without update = driver gone offline
    for (const [id, d] of this.drivers) {
      if (d.lastSeen < cutoff) this.drivers.delete(id);
    }
  }

  computeSurge() {
    const activeRequests = this.requests.reduce((s, r) => s + r.count, 0);
    const availableDrivers = [...this.drivers.values()]
      .filter(d => d.status === 'available').length;
    return {
      hexId: this.hexId,
      multiplier: computeSurgeMultiplier(activeRequests, availableDrivers),
      activeRequests,
      availableDrivers,
      computedAt: Date.now()
    };
  }
}

// Surge smoothing: prevent rapid oscillation (annoys drivers and riders)
class SurgeSmoothing {
  constructor() { this.previous = new Map(); }

  smooth(hexId, newMultiplier) {
    const prev = this.previous.get(hexId) ?? 1.0;
    // Max change per 30s window: ±1.0x (prevents instant 1x → 6x jumps)
    const maxDelta = 1.0;
    const smoothed = Math.min(newMultiplier, prev + maxDelta);
    this.previous.set(hexId, smoothed);
    return smoothed;
  }
}

Surge pricing · correctness

Driver State Machine

A driver's availability for surge calculation depends on their state. The state machine: 

idle (available for dispatch)
  ↓ accepted ride request
en-route-to-pickup
  ↓ arrived at pickup geofence
waiting-at-pickup
  ↓ rider confirmed pickup
in-trip
  ↓ arrived at destination geofence
completing-trip
  ↓ payment confirmed
idle

Only drivers in idle state within a hexagon count as "available supply." A driver en-route to pickup in hexagon A should not count as supply in hexagon A — they are committed. This distinction is what makes demand/supply ratios accurate enough to be actionable.

Surge pricing · correctness

The Race Condition: Price Quote vs Price Confirmation

The most dangerous data consistency issue in surge pricing: a rider is shown a 1.5× quote, then the surge updates to 2.5× before they confirm. Do they pay 1.5× or 2.5×?

Uber's approach (based on patents and public engineering blogs):

  1. Issue a price token with the quote: a signed JWT containing the quoted price, hexagon, valid-until timestamp (typically 60 seconds).
  2. The rider must confirm within 60 seconds to lock in the quoted price.
  3. On confirmation, the server verifies the token has not expired. If expired, re-quote at the current surge.
  4. If the surge drops between quote and confirmation, the lower price wins (good for rider experience).
Surge pricing · operations

Failure Modes and Production Gotchas

  • Hexagon boundary effects — a driver at the border of two hexagons may contribute to the wrong hexagon's supply count. Fix: count drivers with location confidence radius > hexagon size as contributing to all overlapping hexagons.
  • Kafka partition imbalance — if surge events are partitioned by hexagon ID and one city (Mumbai during rain) generates 80% of events, that partition is a hot spot. Fix: add a random partition suffix when throughput spikes; re-aggregate in a downstream Flink job.
  • Surge propagation lag during connectivity spikes — the very events that drive high demand (a major event ending, sudden rain) also cause network congestion, delaying the surge propagation to app clients. Fix: cache the last-known surge multiplier per hexagon in Redis with 2-minute TTL; fall back to cached value if push delivery fails.
  • Driver GPS spoofing — fake driver positions in a hexagon inflate supply count and suppress surge multipliers, hurting legitimate drivers. Fix: validate GPS readings against real-time road network topology; a driver 500m from the nearest road is a spoofed signal.

Distributed systems challenges

The specific hard problems at Uber's scale

Clock skew and event ordering

Driver GPS timestamps come from device clocks, which drift and can be backdated. A location update received at server time T+5s with device timestamp T-2s creates ordering ambiguity. Solution: server-side ingestion timestamp overrides device timestamp for ordering purposes. Device timestamp is preserved for display but not used for sequencing.

GPS signal loss and stale positions

Tunnels, parking structures, and radio interference cause GPS dropout. A driver that hasn't sent an update in 30+ seconds may have moved significantly from their last known position. The Location Store marks drivers as "stale" after a configurable timeout and adjusts their probability weighting in dispatch — a stale driver is de-prioritised but not excluded until they've been absent for 5+ minutes.

Hotspot partitions

During major events (stadium concerts, NYE), thousands of drivers concentrate in one area. If location updates are partitioned by driver_id, the Kafka partitions are uniformly loaded. But if they were partitioned by geohash, the event cell's partition would receive 1000× normal load. Uber partitions by driver_id precisely to avoid geographic hotspot concentration in Kafka.

CAP theorem in practice

Uber accepts eventual consistency for driver positions: a rider may see a driver's position that is a few seconds old. This is an acceptable UX tradeoff. What Uber cannot accept is booking inconsistency: a driver accepting two simultaneous trips, or a trip being lost during a handoff. Booking data is stored in strongly-consistent datastores (originally MySQL, later sharded with Schemaless and eventually CockroachDB) with two-phase commit for the critical accept/assign state transition.

Global vs. regional architecture

Location data is inherently regional — a driver in São Paulo has no relevance to a rider in Singapore. Uber runs independent regional clusters (APAC, EMEA, Americas) with no cross-region replication for location data. Global services (accounts, payments, analytics) replicate cross-region with CRDT-based conflict resolution. The boundary between regional and global is enforced at the service layer.

Fault Tolerance & Distributed System Gotchas

CAP theorem — which services are AP vs CP

DataCAP trade-offReasoning
Driver location AP (availability + partition tolerance) Stale by 4 s is fine; location will update; showing wrong position briefly is acceptable
Trip / payment CP (consistency + partition tolerance) Cannot charge rider twice or create two trips — ACID required
Surge price AP A stale price for 10 s is fine; correctness matters less than liveness
Match lock CP The double-match invariant must hold under any failure

Redis cluster failover

  • Each shard: 1 primary + 1 replica. Cluster spread across 3 availability zones.
  • Primary failure detected via gossip protocol in < 1 second.
  • Replica election requires majority quorum (> N/2 nodes agree).
  • Clients auto-reconnect to new primary; in-flight GEOADD commands retried.
  • Lock TTL (10 s) ensures any failed match attempt auto-releases before the next retry window.

Interview Experience: How Uber Tests Surge Pricing in System Design

The following is drawn from a real Uber onsite system design interview (February 2026). The candidate was strong on the happy path but stumbled on multi-region regulatory edge cases — the exact failure mode that separates L4 from L5 candidates. The full incident analysis is instructive for anyone preparing for a Uber-style interview.

The Question (Verbatim)

"We need a system that can calculate dynamic pricing for every hexagonal zone in a city."

Requirements confirmed during clarification:

  • Ingest real-time ride requests + driver GPS pings
  • Update surge multipliers at least every 60 seconds
  • Output feeds the pricing service shown directly to riders

Non-Functional Requirements to state upfront (this signals senior-level thinking):

  • Latency: recalculate within 60s (P99 < 5s for the full pipeline)
  • Scale: 10M+ active users across 500+ cities globally
  • Availability: 99.99%; failure fallback = 1.0× (no surge) — never show a wrong high multiplier
  • Optimize for speed over accuracy — slightly stale multiplier beats no multiplier

Pro tip: The first clarification the candidate asked was "What happens if the surge calculator fails?" — asking about failure mode before starting the design signals senior-level thinking to the interviewer and typically unlocks deeper discussion.

  1. Clarify failure fallback first — establishes you think about production, not just the happy path.
  2. Propose H3 resolution 7 hexagons (~5 km²) — mentioning Uber's own open-source H3 library by name immediately signals you have studied Uber's actual stack.
  3. Sketch the data flow: GPS pings → H3 mapper → sliding window counters → Flink job → Redis cache → pricing service.

The Follow-Up That Broke the Candidate

"How do you handle surge pricing across city boundaries where hexagonal zones overlap different regulatory regions? NYC caps surge at 2.5×. Some cities ban surge entirely."

The candidate gave a vague answer about "a config per city." The interviewer pushed: how does a globally-processing Flink job know which regulatory rules apply per hex? The candidate stumbled. This was the turning point.

The correct answer — Regulatory Config Service:

A geo-tagged lookup table maps each H3 hex ID to its regulatory jurisdiction (city/state/country). The Flink job queries this at computation time: min(computed_multiplier, regulatory_cap_for_hex). The config is pre-loaded into the Flink job's in-memory state at startup and refreshed every 5 minutes via a separate Kafka compacted topic. A compacted topic means each H3 key only retains its latest regulatory config — the Flink job's startup snapshot is always complete without replaying the full history.

JavaScript Example — Regulatory Cap in Surge Calculation 
// regulatory-surge.js — applies regulatory cap to computed surge multiplier

/**
 * Returns the surge multiplier capped by the regulatory jurisdiction of the hexagon.
 * regulatoryCache is a Map pre-populated from the Kafka compacted config topic.
 *
 * @param {string} hexId           - H3 hexagon ID at resolution 7
 * @param {number} rawMultiplier   - multiplier computed from demand/supply ratio
 * @param {Map}    regulatoryCache - Map<hexId, {jurisdiction, maxSurgeMultiplier}>
 * @returns {number} capped multiplier
 */
function computeCappedSurge(hexId, rawMultiplier, regulatoryCache) {
  const jurisdiction = regulatoryCache.get(`reg:${hexId}`);
  if (!jurisdiction) return rawMultiplier; // no regulatory data for this hex → apply raw

  const cap = jurisdiction.maxSurgeMultiplier ?? Infinity;
  return Math.min(rawMultiplier, cap);
}

// Regulatory cache loader — runs at Flink job startup and on config topic updates
async function loadRegulatoryConfig(kafkaConsumer, cache) {
  // Consume the compacted topic from the beginning to get current config for all hexes
  for await (const message of kafkaConsumer.consume('surge-regulatory-config')) {
    const { hexId, jurisdiction, maxSurgeMultiplier } = JSON.parse(message.value);
    cache.set(`reg:${hexId}`, { jurisdiction, maxSurgeMultiplier });
  }
}

Behavioral Round: STAR-L Method

When asked "Tell me about a time you disagreed with a technical decision" — lead with data, not opinions. The STAR-L framework:

  • Situation: A notification system was polling the DB every 5 seconds, causing CPU spikes at peak hours.
  • Task: Proposed migrating to a Kafka-based event stream for notification delivery.
  • Action: Built a proof-of-concept in 3 days. Presented latency data: polling = 5s avg delivery; event-driven = 200ms avg. Addressed Kafka operational complexity concerns directly.
  • Result: Team adopted the event-driven approach. CPU usage dropped 60%.
  • Learning: "Data wins arguments, not opinions." Fight technical disagreements with prototypes and benchmarks, not rhetoric.

The "L" (Learning) in STAR-L is what differentiates a good behavioral answer from a great one — it shows reflection and growth, which is exactly what Uber's interviewers assess for senior candidates.

Common questions

FAQ

  • Why Redis for location storage and not a PostGIS database?

    PostGIS is excellent for persistent geospatial data — historical trip paths, city boundary definitions, permanent geographic objects. Driver location is ephemeral, volatile, and write-heavy: 1.25M updates/second with sub-millisecond read requirements. Redis's in-memory geospatial commands deliver sub-millisecond GEORADIUS queries and handle the write throughput. PostGIS would require significant sharding and hardware to match Redis's performance here. Many production systems use both: Redis for current location (real-time), PostGIS for historical queries (analytics, dispute resolution).

  • How does Uber handle the dispatch problem when the "best" driver keeps rejecting offers?

    Driver acceptance rate is a first-class signal in the dispatch scoring function. Drivers who chronically reject offers are scored lower in ranking — they still receive offers, but less frequently. This creates natural incentive alignment: a driver who consistently rejects rides loses priority and earns less. Additionally, the dispatch system tracks rejection reasons: a driver who rejected because they were about to end their shift is treated differently from a driver who rejected for no reason.

  • What happens during a network partition between regional data centres?

    Uber's regional architecture means most partition events are fully contained. A partition that isolates one data centre within a region falls back to the other data centres in that region — location data and dispatch continue operating. A partition that isolates an entire region is more severe: riders and drivers in that region experience degraded service (stale maps, slower dispatch) but the service does not go down completely because the regional cluster is self-contained. Global services (payments, accounts) use eventual consistency with conflict resolution for cross-region scenarios.

Key Takeaway

Uber's real-time core is a case study in separating workloads by their read/write characteristics: high-frequency ephemeral writes go to Kafka and Redis; durable transactional state goes to strongly-consistent SQL (with a distributed lock plus a UNIQUE constraint against double-matching); aggregated analytics go to columnar stores. Matching speed comes from three compounding optimisations: H3 indexing that cuts 5 million drivers to about 50 candidates, WebSocket push connections that remove handshake overhead at 1.25 million updates per second, and parallel A* ETA scoring. Surge pricing is a stream-processing problem whose hard parts are not the multiplier formula but the driver state machine (only idle drivers count as supply), hexagon boundary and partition effects, price tokens that prevent quote/confirmation races, and per-jurisdiction regulatory caps.

In the interview, the design is secondary to the reasoning. Surface trade-offs unprompted (AP for location but CP for trips and payments, Lua on lock release, wave dispatch rather than offering to everyone, regulatory config as a compacted topic), prepare both the naive and the production-grade answer for each deep dive, and show you have thought past the happy path. The complexity exists because the naive solutions break at exactly the scale Uber operates at.
