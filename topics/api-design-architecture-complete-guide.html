API Design & Architecture — The Complete Guide

Everything from the six major API architecture styles and when to choose each, to the design rules that make an API a joy to use, the performance techniques that can 10× throughput, and a from-scratch Node.js REST implementation — synthesised from five expert sources into one exhaustive reference.

Sources: YouTube — API Design & Architecture (1hr) · Top 7 API Performance · Good vs Bad APIs · RESTful APIs in 100s · Top 6 API Styles Domain: Backend Engineering Published: 2024–2026

An API is a contract. Every design decision — the style, the naming, the error format, the version strategy — either makes that contract easy to honour or easy to break. Most bad APIs aren't caused by wrong technology choices; they're caused by skipping the design phase and letting implementation details leak through the interface.

Core idea: API design is an outside-in discipline. You start with what the consumer needs, then decide what to expose and how — not the other way around. The six architecture styles each optimise for a different consumer need: REST for resources, GraphQL for flexible queries, gRPC for speed, WebSockets for bidirectional streams, webhooks for push events, and SOAP for strict contracts.

Story · The Monday-morning outage

A team ships a mobile app backed by a REST API designed in a weekend sprint. Endpoints are named after internal database tables: GET /tbl_user_data. There's no versioning. Errors return HTTP 200 with { "success": false } in the body. The iOS client parses the JSON body; the Android client checks the status code. When the team fixes the error format, both clients break in different ways simultaneously.

Three months later, a new product requirement forces a field rename. There's no version field, no deprecation path. Every client must update in lock-step or the app crashes. The team now spends more time managing API compatibility than building features.

Every rule in this guide exists to prevent exactly that scenario.

Part 1

The Six API Architecture Styles — and When to Use Each

There is no single best API style. Each solves a specific communication problem. Choosing the wrong one means fighting the protocol at every step.

1. REST (Representational State Transfer)

The dominant style for public and partner APIs. REST treats everything as a resource identified by a URI and acted on via standard HTTP methods. It is stateless, cacheable, and layerable. The uniform interface constraint is its greatest strength — any client that understands HTTP can call a REST API without prior knowledge.

  • Best for: Public-facing APIs, mobile backends, CRUD services, systems where caching matters.
  • Weakness: Over-fetching (getting more fields than needed) and under-fetching (requiring multiple round-trips for related data).
  • Constraint checklist: Stateless, client-server, cacheable, uniform interface, layered system, optional code-on-demand.

REST anti-pattern to avoid: Putting verbs in URLs (/getUser, /deletePost). The HTTP method is the verb. The URL names the resource.

2. GraphQL

Developed at Facebook to solve REST's over/under-fetching problem. The client defines the exact shape of the response in a query; the server returns precisely that. A single endpoint handles all operations: query (read), mutation (write), subscription (real-time stream).

  • Best for: Complex frontends with diverse data needs, mobile apps on constrained bandwidth, APIs aggregating multiple back-end services, product teams that ship UI changes frequently.
  • Weakness: Complex caching (no URL per resource), potential N+1 query problems server-side, steeper learning curve, schema management overhead.
  • Key concept — DataLoader: Batches and deduplicates database calls within a single request cycle to solve N+1.

3. gRPC (Google Remote Procedure Call)

Uses HTTP/2 and Protocol Buffers (protobuf) for binary serialisation. The API is defined in a .proto schema file; code is generated for both client and server in any supported language. Payload size is roughly 5–10× smaller than equivalent JSON; latency is significantly lower.

  • Best for: Internal microservice-to-microservice communication, polyglot systems, high-throughput pipelines, streaming use cases (client streaming, server streaming, bidirectional streaming).
  • Weakness: Not human-readable (binary), harder to debug without tooling, browser support requires a proxy layer (gRPC-Web), tight coupling to proto schema.
  • HTTP/2 benefits: Multiplexing (many requests over one connection), header compression (HPACK), server push.

4. WebSockets

Upgrades an HTTP connection to a persistent, full-duplex TCP channel. After the handshake, either side can send messages at any time without the request-response overhead. Ideal for any application requiring real-time data flow.

  • Best for: Live chat, collaborative editing, real-time dashboards, online games, trading platforms, live sports scores.
  • Weakness: Stateful connections make horizontal scaling harder (sticky sessions or a shared pub/sub layer like Redis Streams or Kafka is needed), no built-in request-response correlation.

5. Webhooks (Reverse APIs)

The server pushes data to the client when an event occurs, rather than the client polling. The client registers a callback URL; the server POSTs to that URL when the event fires. Stripe, GitHub, and Twilio all rely heavily on webhooks.

  • Best for: Event-driven integrations, payment confirmations, CI/CD triggers, IoT alerts, any flow where the client should react to server-side state changes.
  • Weakness: Client must be publicly accessible, delivery is not guaranteed (need retry + idempotency logic), ordering is not guaranteed, debugging is harder.
  • Reliability pattern: Sign payloads with HMAC-SHA256, validate the signature on receipt, return 200 immediately and process async to avoid timeouts.

6. SOAP (Simple Object Access Protocol)

An XML-based protocol with strict message structure, mandatory envelopes, and a WSDL (Web Services Description Language) contract. Predates REST. Still dominant in enterprise systems (banking, healthcare, government) because of its built-in standards for security (WS-Security), transactions (WS-AtomicTransaction), and reliability (WS-ReliableMessaging).

  • Best for: Enterprise integrations requiring formal contracts, regulated industries, systems that need built-in WS-* standards for transactions and security.
  • Weakness: Verbose XML overhead, steep learning curve, slower development velocity, poor fit for modern web/mobile clients.

Part 2

REST API Design Rules — Good vs Bad APIs

The difference between a good API and a bad one is rarely the technology. It's the discipline applied to naming, structure, and consistency.

Rule 1 — Use nouns, never verbs, in endpoints

The HTTP method already expresses the action. The URL should name the resource being acted on.

❌ Bad✅ Good
GET /getUsersGET /users
POST /createOrderPOST /orders
DELETE /deleteProduct?id=5DELETE /products/5
GET /fetchOrdersByUserGET /users/42/orders

Rule 2 — Use plural nouns for collections

Consistency matters more than grammar. /users for the collection, /users/{id} for a single resource.

Rule 3 — Logical nesting for relationships

Nest related resources to express ownership, but cap depth at 2–3 levels. Beyond that, references in the response body are cleaner than deeper URL nesting.

  • GET /articles/{id}/comments — correct, 2 levels
  • GET /users/{id}/posts/{postId}/comments/{commentId}/likes — too deep; better: GET /likes?commentId=X
  • Avoid mirroring database table structure in URLs — it leaks implementation and creates security risk

Rule 4 — HTTP methods map to CRUD precisely

MethodCRUDIdempotent?Safe?
GETReadYesYes
POSTCreateNoNo
PUTFull update / upsertYesNo
PATCHPartial updateConditionallyNo
DELETERemoveYesNo

Rule 5 — Always use standard HTTP status codes

Never return HTTP 200 with an error in the body — this breaks every HTTP-aware tool (load balancers, monitoring, caches, client frameworks). Use the correct code for every outcome:

  • 200 OK — successful GET, PUT, PATCH, DELETE
  • 201 Created — successful POST; include Location header pointing to new resource
  • 204 No Content — successful DELETE with no body
  • 400 Bad Request — client sent invalid data; include validation error details
  • 401 Unauthorized — not authenticated (missing or invalid credentials)
  • 403 Forbidden — authenticated but lacks permission
  • 404 Not Found — resource doesn't exist
  • 409 Conflict — state conflict (e.g. duplicate creation, optimistic lock failure)
  • 422 Unprocessable Entity — syntactically valid but semantically invalid request
  • 429 Too Many Requests — rate limit exceeded; include Retry-After
  • 500 Internal Server Error — unhandled server error; never expose stack traces
  • 503 Service Unavailable — dependency down or overloaded

Rule 6 — Return consistent, informative error bodies

A good error response tells the client what went wrong, why, and (where possible) how to fix it. Never just return a status code with no body.

JSON error body — recommended format 
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request body failed validation",
    "details": [
      {
        "field": "email",
        "issue": "must be a valid email address",
        "received": "not-an-email"
      }
    ],
    "requestId": "req_4kZ9mN2xP",
    "docsUrl": "https://api.example.com/docs/errors#VALIDATION_ERROR"
  }
}

Rule 7 — Filtering, sorting, and pagination via query parameters

  • Filtering: GET /products?category=shoes&maxPrice=100
  • Sorting: GET /products?sort=price&order=asc (or sort=-price for desc)
  • Offset pagination: GET /products?page=2&limit=20 — simple, but inconsistent on live data
  • Cursor pagination: GET /products?after=cursor_abc123&limit=20 — consistent for feeds (used by GitHub, Twitter/X)
  • Always include metadata in paginated responses: total, page, limit, nextCursor

Rule 8 — Version your API from day one

The moment a public client exists, breaking changes are a migration problem. There are three common versioning strategies — choose one and be consistent across the entire API:

  • URL path versioning (most common): /v1/users, /v2/users — visible, cacheable, easy to route
  • Query parameter versioning: /users?version=2 — easier to add but pollutes query strings
  • Header versioning: Accept: application/vnd.example.v2+json — clean URLs, harder to test in a browser

Additive changes (new optional fields, new endpoints) are non-breaking. Removing or renaming fields, changing types, or changing HTTP methods are breaking and require a new major version.

Rule 9 — Enforce HTTPS everywhere, always

There is no valid reason to serve an API over plain HTTP in 2026. TLS certificates from Let's Encrypt are free. Beyond encryption, use:

  • HSTS (Strict-Transport-Security) — forces browsers to upgrade to HTTPS
  • API keys — for identifying callers; rotate on compromise
  • OAuth 2.0 + JWT — for delegated user authentication; short-lived access tokens, long-lived refresh tokens
  • Principle of least privilege — each client gets only the scopes it needs

Rule 10 — Idempotency for mutation endpoints

Network retries are unavoidable. A payment endpoint that isn't idempotent will double-charge users on retry. Pattern: accept an Idempotency-Key header on all POST/PATCH/DELETE operations. Store the key and response; on duplicate key, return the cached response without re-executing.

Stripe's rule: Every POST mutation accepts Idempotency-Key. Keys are scoped to 24 hours. The same key always returns the same result, whether the original request succeeded, failed, or is still processing.

Part 3

7 Performance Techniques That Can 10× API Throughput

Performance problems in APIs are almost never caused by the web framework. They come from one of seven areas — and fixing them in order of impact produces the largest gains with the least risk.

1. Caching — the highest-leverage optimization

Every layer of the stack can cache. Each layer reduces load on the layer below:

  • HTTP response caching: Set Cache-Control: public, max-age=3600 on read-only endpoints. CDNs and reverse proxies (Nginx, CloudFront) cache responses at the edge — zero compute cost per hit.
  • Application-level cache (Redis): Store expensive query results with a short TTL. Cache-aside pattern: check cache → miss → query DB → write cache → return.
  • Semantic caching (for LLM APIs): Embed the query, find semantically similar past queries using vector search, return cached response if similarity exceeds threshold.
  • ETag / conditional GET: Server returns an ETag (hash of response); client sends If-None-Match: "etag-value" on next request; server returns 304 Not Modified if unchanged — no body transfer.

Avoid caching: Anything with user-specific data at a public CDN layer, or mutation responses (POST/PATCH/DELETE).

2. Connection pooling

Opening a new TCP+TLS connection per request costs ~100–500ms. Connection pools maintain a set of pre-opened connections and hand them off to requests. With a pool, connection overhead drops to near zero.

  • Database connection pools: PgBouncer for PostgreSQL, HikariCP for Java, pg-pool for Node.js. Set max to (CPU cores × 2) + storage latency headroom.
  • HTTP keep-alive: Reuses TCP connections for multiple requests. Enabled by default in HTTP/1.1. HTTP/2 multiplexes requests on a single connection — even better.
  • gRPC: HTTP/2 multiplexing means one connection handles hundreds of concurrent streams.

3. Async processing for long-running operations

Operations that take more than a few seconds (video processing, email sending, report generation, ML inference) should never block the HTTP response. Pattern:

  1. Client POSTs the operation request
  2. API immediately returns 202 Accepted with a job ID and a Location header pointing to a status endpoint
  3. Background worker processes the job (BullMQ, Celery, SQS Lambda)
  4. Client polls GET /jobs/{id} or receives a webhook when complete

4. Pagination — never return unbounded collections

GET /users without a limit will eventually return millions of rows, OOM the server, and timeout the client. Always:

  • Apply a default page size (20–100 items) and a maximum (1000)
  • Reject requests that exceed the max: 400 Bad Request
  • For feeds: use cursor pagination — it's stable even as records are inserted/deleted

5. Payload compression

JSON is verbose. Gzip compression typically reduces payload size by 60–80% with negligible CPU cost on modern hardware.

  • Enable Content-Encoding: gzip on responses if the client sends Accept-Encoding: gzip
  • For internal services: switch to protobuf (gRPC) — binary serialisation is 5–10× smaller than JSON before compression
  • For field-heavy responses: implement sparse fieldsets (?fields=id,name,email) to let clients request only what they need

6. Sparse fieldsets / response shaping

Allow clients to specify which fields to return. This reduces payload size, reduces database query projection cost, and aligns the API toward the consumer's actual need (similar to GraphQL's selection sets, but within REST):

  • GET /users/42?fields=id,name,email
  • GET /orders?fields=id,status,total&expand=items
  • Stripe and GitHub both support ?expand[]= to opt-in to nested objects

7. Rate limiting — protect performance by design

A single misbehaving client (or a DDoS) can saturate your API for everyone. Rate limiting is not just a security control — it is a performance guarantee for all other clients.

  • Token bucket: Each client gets N tokens per window. Each request consumes a token. Tokens refill at a fixed rate. Allows bursting.
  • Sliding window counter: Counts requests in the last N seconds using a rolling window. More accurate than fixed window.
  • Fixed window: Simple counter reset every window. Susceptible to burst at window boundary.
  • Respond with 429 Too Many Requests and headers: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset, Retry-After.
  • Implement at the API gateway layer (Kong, AWS API Gateway, Nginx) to protect all downstream services simultaneously.
Part 4

Building a REST API from Scratch — Node.js + Express

Theory without code is half the picture. Below is a production-shaped Express API implementing the patterns from Parts 2 and 3: proper routing, validation, error handling, caching, and rate limiting.

JavaScript Example — Full REST API skeleton (Node.js / Express) 
// server.js — production-shaped REST API skeleton
// npm install express express-rate-limit helmet compression cors
import express from 'express';
import rateLimit from 'express-rate-limit';
import helmet from 'helmet';
import compression from 'compression';
import cors from 'cors';

const app = express();

// ── Security & compression middleware ────────────────────────────────────
app.use(helmet());                          // sets secure HTTP headers
app.use(compression());                     // gzip all responses
app.use(cors({ origin: process.env.ALLOWED_ORIGINS?.split(',') }));
app.use(express.json({ limit: '1mb' }));    // parse JSON bodies

// ── Rate limiting (token bucket via fixed window) ─────────────────────────
const limiter = rateLimit({
  windowMs: 60 * 1000,   // 1-minute window
  max: 100,              // 100 requests per window per IP
  standardHeaders: true, // X-RateLimit-* headers in response
  legacyHeaders: false,
  handler: (req, res) => {
    res.status(429).json({
      error: {
        code: 'RATE_LIMIT_EXCEEDED',
        message: 'Too many requests. Please wait before retrying.',
        retryAfter: Math.ceil(req.rateLimit.resetTime / 1000),
      },
    });
  },
});
app.use('/api/', limiter);

// ── Simple in-memory cache (replace with Redis in production) ─────────────
const cache = new Map();
function cacheMiddleware(ttlSeconds) {
  return (req, res, next) => {
    if (req.method !== 'GET') return next();
    const key = req.originalUrl;
    const hit = cache.get(key);
    if (hit && Date.now() - hit.ts < ttlSeconds * 1000) {
      res.set('X-Cache', 'HIT');
      return res.json(hit.data);
    }
    // Override res.json to capture the response and cache it
    const originalJson = res.json.bind(res);
    res.json = (data) => {
      if (res.statusCode === 200) cache.set(key, { data, ts: Date.now() });
      res.set('X-Cache', 'MISS');
      return originalJson(data);
    };
    next();
  };
}

// ── Idempotency key middleware (for mutating endpoints) ───────────────────
const idempotencyStore = new Map(); // use Redis in production with 24h TTL
function idempotencyMiddleware(req, res, next) {
  const key = req.headers['idempotency-key'];
  if (!key) return next();
  if (idempotencyStore.has(key)) {
    const cached = idempotencyStore.get(key);
    res.set('X-Idempotency-Replayed', 'true');
    return res.status(cached.status).json(cached.body);
  }
  const originalJson = res.json.bind(res);
  res.json = (body) => {
    idempotencyStore.set(key, { status: res.statusCode, body });
    return originalJson(body);
  };
  next();
}

// ── Resource router: /api/v1/users ────────────────────────────────────────
const usersRouter = express.Router();

// GET /api/v1/users?page=1&limit=20&sort=createdAt&order=desc&fields=id,name
usersRouter.get('/', cacheMiddleware(60), async (req, res, next) => {
  try {
    const page    = Math.max(1, parseInt(req.query.page  ?? '1',  10));
    const limit   = Math.min(100, parseInt(req.query.limit ?? '20', 10));
    const sort    = ['createdAt','name','email'].includes(req.query.sort) ? req.query.sort : 'createdAt';
    const order   = req.query.order === 'asc' ? 'asc' : 'desc';
    const fields  = req.query.fields?.split(',').filter(Boolean);

    // Simulate DB query
    const users = await db.users.findMany({ page, limit, sort, order, fields });

    res.json({
      data: users,
      pagination: {
        page,
        limit,
        total: users.total,
        hasNextPage: page * limit < users.total,
      },
    });
  } catch (err) {
    next(err); // delegate to global error handler
  }
});

// GET /api/v1/users/:id
usersRouter.get('/:id', cacheMiddleware(300), async (req, res, next) => {
  try {
    const user = await db.users.findById(req.params.id);
    if (!user) return res.status(404).json({ error: { code: 'NOT_FOUND', message: `User ${req.params.id} not found` } });
    res.json({ data: user });
  } catch (err) { next(err); }
});

// POST /api/v1/users — with idempotency
usersRouter.post('/', idempotencyMiddleware, async (req, res, next) => {
  try {
    const { name, email, password } = req.body;
    // Validate — never trust client input
    const errors = [];
    if (!name  || typeof name  !== 'string') errors.push({ field: 'name',  issue: 'required string' });
    if (!email || !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email)) errors.push({ field: 'email', issue: 'valid email required' });
    if (!password || password.length < 8) errors.push({ field: 'password', issue: 'minimum 8 characters' });
    if (errors.length) return res.status(400).json({ error: { code: 'VALIDATION_ERROR', details: errors } });

    const user = await db.users.create({ name, email, password });
    res
      .status(201)
      .set('Location', `/api/v1/users/${user.id}`)
      .json({ data: user });
  } catch (err) {
    if (err.code === 'UNIQUE_VIOLATION') return res.status(409).json({ error: { code: 'CONFLICT', message: 'Email already registered' } });
    next(err);
  }
});

// PATCH /api/v1/users/:id — partial update
usersRouter.patch('/:id', idempotencyMiddleware, async (req, res, next) => {
  try {
    const allowed = ['name', 'email', 'bio'];
    const updates = Object.fromEntries(Object.entries(req.body).filter(([k]) => allowed.includes(k)));
    if (Object.keys(updates).length === 0)
      return res.status(400).json({ error: { code: 'NO_VALID_FIELDS', message: `Updatable fields: ${allowed.join(', ')}` } });

    const user = await db.users.update(req.params.id, updates);
    if (!user) return res.status(404).json({ error: { code: 'NOT_FOUND' } });
    res.json({ data: user });
  } catch (err) { next(err); }
});

// DELETE /api/v1/users/:id
usersRouter.delete('/:id', async (req, res, next) => {
  try {
    const deleted = await db.users.delete(req.params.id);
    if (!deleted) return res.status(404).json({ error: { code: 'NOT_FOUND' } });
    res.status(204).send();
  } catch (err) { next(err); }
});

app.use('/api/v1/users', usersRouter);

// ── Async job endpoint (202 pattern) ─────────────────────────────────────
app.post('/api/v1/reports', async (req, res) => {
  const jobId = crypto.randomUUID();
  // Enqueue the job — BullMQ/SQS/etc in production
  jobQueue.add('generateReport', { ...req.body, jobId });
  res
    .status(202)
    .set('Location', `/api/v1/jobs/${jobId}`)
    .json({ jobId, status: 'queued', estimatedSeconds: 30 });
});

app.get('/api/v1/jobs/:id', async (req, res) => {
  const job = await jobQueue.getJob(req.params.id);
  if (!job) return res.status(404).json({ error: { code: 'NOT_FOUND' } });
  res.json({ jobId: job.id, status: job.status, result: job.result ?? null });
});

// ── Global error handler ──────────────────────────────────────────────────
app.use((err, req, res, _next) => {
  const requestId = req.headers['x-request-id'] ?? crypto.randomUUID();
  console.error({ requestId, err });        // structured log — never send stack to client
  res.status(500).json({
    error: {
      code: 'INTERNAL_ERROR',
      message: 'An unexpected error occurred. Please try again.',
      requestId,
    },
  });
});

// ── Health check ──────────────────────────────────────────────────────────
app.get('/health', (_, res) => res.json({ status: 'ok', uptime: process.uptime() }));

app.listen(3000, () => console.log('API listening on :3000'));
Part 5

API Security Patterns

Security is not a layer you add after design. Every endpoint decision has a security implication.

Authentication vs Authorization

  • Authentication — Who are you? (API key, OAuth token, JWT)
  • Authorization — What can you do? (scopes, roles, resource ownership)

API Key authentication

Simplest form of auth. The client includes a secret key in the request (header preferred over query param to avoid logging). Good for server-to-server calls and public APIs with tiered access.

  • Always send in Authorization: Bearer sk_live_xxx header, never in the URL
  • Hash keys before storing (SHA-256); never store plaintext
  • Scope keys to minimum required permissions
  • Support programmatic rotation without downtime

OAuth 2.0 + JWT

The standard for user-delegated access. The access token is short-lived (15 min – 1 hour); the refresh token is long-lived (days – weeks) and stored server-side for revocation. JWT encodes claims (user ID, scopes, expiry) in the token body — no DB lookup needed to validate most requests.

  • Sign JWTs with RS256 (asymmetric) for public key verification by multiple services
  • Include exp, iat, jti (unique token ID) claims
  • Validate aud (audience) to prevent token misuse across services
  • Store refresh tokens in HttpOnly; Secure; SameSite=Strict cookies to prevent XSS theft

Input validation — never trust the client

  • Validate type, range, length, and format for every input field
  • Use allowlists for string fields where possible (e.g. sort parameter)
  • Parameterize all database queries — never concatenate user input into SQL
  • Limit request body size (1mb default is a good starting point)
  • Return 400 with field-level error details — never expose internal error messages

CORS — Cross-Origin Resource Sharing

Configure CORS to allow only trusted origins. Avoid Access-Control-Allow-Origin: * on APIs that carry user data or accept credentials.

JavaScript Example — Strict CORS configuration 
import cors from 'cors';

const ALLOWED_ORIGINS = new Set([
  'https://app.example.com',
  'https://admin.example.com',
  ...(process.env.NODE_ENV === 'development' ? ['http://localhost:5173'] : []),
]);

app.use(cors({
  origin: (origin, callback) => {
    // Allow server-to-server requests (no origin header)
    if (!origin || ALLOWED_ORIGINS.has(origin)) return callback(null, true);
    callback(new Error(`CORS: ${origin} not allowed`));
  },
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE', 'OPTIONS'],
  allowedHeaders: ['Content-Type', 'Authorization', 'Idempotency-Key', 'X-Request-ID'],
  credentials: true,
  maxAge: 86400, // preflight cache: 24 hours
}));
Part 6

API Design for Evolution — How to Change APIs Without Breaking Clients

The hardest part of API design is not building v1 — it is changing v1 without breaking the clients that depend on it. A few rules make this tractable:

Additive-only evolution (the safest approach)

You can always add new optional fields to a response without breaking existing clients (they ignore fields they don't know about). You can add new optional request parameters with sensible defaults. You can add new endpoints. These are non-breaking changes:

  • Adding new response fields
  • Adding new optional request parameters
  • Adding new endpoints or HTTP methods to existing endpoints
  • Changing error messages (but not error codes)
  • Expanding an enum with new values (clients should ignore unknown values)

Breaking changes — require a new version

  • Removing or renaming a response field
  • Changing a field's type (string → number)
  • Changing HTTP method for an existing endpoint
  • Changing the URL structure
  • Adding a required request parameter
  • Narrowing an enum (removing values)

Deprecation lifecycle

  1. Announce the deprecation with a minimum 6-month migration window for public APIs
  2. Add Deprecation: true and Sunset: date headers to deprecated endpoints
  3. Log usage of deprecated endpoints to identify clients that haven't migrated
  4. Reach out directly to active consumers before sunset
  5. Keep the old version alive for 30 days past the sunset date before removal

HATEOAS — Hypermedia as the Engine of Application State

The highest level of REST maturity. Responses include links describing what the client can do next, removing the need for clients to hard-code URL structures:

JavaScript Example — HATEOAS response 
// Response to GET /api/v1/orders/789
{
  "data": {
    "id": "789",
    "status": "pending",
    "total": 149.99
  },
  "_links": {
    "self":    { "href": "/api/v1/orders/789",         "method": "GET"    },
    "cancel":  { "href": "/api/v1/orders/789/cancel",  "method": "POST"   },
    "pay":     { "href": "/api/v1/orders/789/payment", "method": "POST"   },
    "customer":{ "href": "/api/v1/users/42",           "method": "GET"    }
  }
}
// A client that follows _links never needs to build URLs itself.
// Renaming /orders → /purchases only requires a server change, not a client change.
Part 7

API Documentation — The Contract Your Consumers Actually Read

An API without documentation is unusable to anyone outside the team that built it. Documentation is not optional — it is part of the product.

OpenAPI / Swagger specification

The industry standard for describing REST APIs. A YAML or JSON file that defines every endpoint, its parameters, request/response schemas, authentication requirements, and example values. Tooling generates interactive docs (Swagger UI, Redoc), client SDKs, and mock servers from the spec.

  • Define schemas for every request body and response object — not just fields, but types, constraints, and examples
  • Include at least one success example and one error example per endpoint
  • Use $ref to define shared schemas once and reference them everywhere
  • Spec-first (API-first) development: write the OpenAPI spec before the implementation, use it as the contract between teams

What good documentation must include

  • Base URL and environment URLs (staging, production)
  • Authentication instructions with a working example (curl + language SDKs)
  • Every endpoint: method, path, path parameters, query parameters, request body, all response codes and bodies
  • Error codes reference with human-readable explanations and remediation steps
  • Rate limits and quotas per plan tier
  • Changelog with deprecation notices
  • Getting-started guide that produces a real response in under 5 minutes

Developer experience metrics

  • TTFHW (Time to First Hello World) — how long until a new developer gets a valid response? Target: under 5 minutes
  • TTFPA (Time to First Productive App) — how long to build something real? This is the measure of whether your API delivers on its promise
Practical checklist

API Design Quality Checklist

Run this checklist before publishing any API endpoint:

  • Naming: URL uses nouns, plural for collections, no verbs, no implementation-detail leakage
  • HTTP methods: GET for reads, POST for creates, PUT for full updates, PATCH for partial, DELETE for removal
  • Status codes: 201 on create, 204 on empty delete, 400 for validation, 401 for auth, 403 for authz, 404 for missing, 409 for conflict, 429 for rate limit — never 200 for errors
  • Error body: Includes code, message, field-level details, requestId
  • Pagination: All collection endpoints accept limit/page (or cursor), have a maximum limit, return total count
  • Versioning: Version prefix present from day one (/v1/)
  • Security: HTTPS only, auth required on all non-public endpoints, input validated, SQL parameterised
  • Idempotency: POST mutations accept Idempotency-Key header
  • Caching: Cache-Control header set on GET responses, ETag/conditional GET for cacheable resources
  • Rate limiting: X-RateLimit-* headers on all responses, 429 with Retry-After
  • Async ops: Long-running operations return 202 with a job/status endpoint
  • Documentation: OpenAPI spec exists, every endpoint has at least one request and one error example
  • Evolution: New fields are optional, no fields removed or renamed without a version bump
  • CORS: Configured to allow only expected origins, not * on credentialed endpoints
FAQ

Common Questions

REST vs GraphQL — how do I decide?

Start with REST. GraphQL pays off when you have multiple clients with very different data requirements (web needs 30 fields, mobile needs 8), or when your backend is an aggregation of many services that each hold a slice of the data a page needs. If your API is simple CRUD with a stable consumer, REST is easier to build, cache, and maintain.

Should I version from day one even if I have no external consumers?

Yes. The moment you have a mobile app in production, you have an external consumer — app stores do not let you force-update users. A /v1/ prefix costs nothing to add but is painful to retrofit later.

What's the difference between PUT and PATCH?

PUT replaces the entire resource — fields you omit are deleted (or reset to defaults). PATCH applies a partial update — only fields included in the body are changed. Use PATCH for forms where users edit a subset of a record; use PUT for replace-entire-configuration operations.

When should I use WebSockets instead of polling?

When the client needs updates in under 1 second, or when the server-push rate is high (a message every few hundred milliseconds). For infrequent updates (every few seconds), Server-Sent Events (SSE) is simpler than WebSockets and works over HTTP/2. For truly infrequent updates (every 30+ seconds), polling is the simplest and most reliable choice.

How granular should rate limits be?

Apply at least three tiers: global (protect infra), per-API-key (protect fair use), and per-endpoint (protect expensive operations). A POST /search that triggers a full-text scan needs a tighter limit than GET /users/{id}.

Key Takeaway

A great API is not a technical artefact — it is a product. It has a consumer, a contract, and a lifecycle. The six architecture styles are each optimised for a different consumer need: pick REST for resources, GraphQL for flexible queries, gRPC for high-speed microservice calls, WebSockets for real-time streams, webhooks for event-driven push, and SOAP for enterprise contracts. Within REST, the rules are simple: nouns in URLs, HTTP methods for actions, correct status codes, consistent error bodies, pagination on all collections, HTTPS everywhere, version from day one, and idempotency keys on mutations. Performance is the sum of caching every safe response, pooling every connection, pushing long operations async, and rate-limiting aggressively at the gateway. Every line of production API code is a promise to every client that integrates with it — design it like you intend to keep that promise for the next five years.
