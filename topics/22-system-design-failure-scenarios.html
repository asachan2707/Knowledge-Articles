22 Scenario-Based System Design Questions That Reveal How Real Systems Break

Twenty-two scenario-based questions built from real distributed system failure patterns — each with the symptom, root cause, and production-proven fix. Covers payment failures, Kafka duplicates, double-booking race conditions, Redis cascades, slow microservice isolation, and more.

Story · The 3 AM Alert

3 AM. A senior engineer at a fintech startup receives a PagerDuty alert: "Payment success rate dropped to 60%." They log in to find hundreds of orders in a corrupted state: payment_collected = true, order_status = FAILED. Money has left customers' bank accounts. No orders were created.

The bug: the Payment Service called the payment gateway successfully, then attempted to write the order to MySQL — which was experiencing replication lag. The write failed silently. The payment was already committed. No rollback was possible across service boundaries. The engineer spent four hours writing a reconciliation script. 847 customers affected. This failure was entirely preventable with a transactional outbox pattern.

This guide documents 22 such failures — their symptoms, root causes, and fixes — so you can recognise them in a system design interview and prevent them before the 3 AM alert ever arrives.

Scenarios 1–4

Distributed Transactions, Deduplication, Race Conditions, and Cache Failures

Scenario 1: Payment Deducted But Order Not Created

Symptom: Customers are charged but orders don't appear in their accounts.

Root cause: The Payment Service successfully calls the payment gateway (Stripe), then tries to write the order to MySQL. That write fails (timeout, OOM, replication lag). The payment was already committed externally. No rollback is possible.

Fix — Transactional Outbox: Write the order AND an outbox event atomically to the same database in a single transaction. A relay process reads the outbox and publishes to Kafka. If relay fails, it retries from its last checkpoint. Downstream services consume from Kafka and create the order. If order creation ultimately fails after all retries, a Saga compensation action issues a refund.

JavaScript Example 
// Transactional outbox: order + event in one DB transaction
async function createOrderWithOutbox(client, paymentRef, cart) {
  await client.query('BEGIN');
  const { rows } = await client.query(
    'INSERT INTO orders (payment_ref, status, items) VALUES ($1, $2, $3) RETURNING id',
    [paymentRef, 'PENDING', JSON.stringify(cart.items)]
  );
  await client.query(
    'INSERT INTO outbox_events (aggregate_id, event_type, payload) VALUES ($1, $2, $3)',
    [rows[0].id, 'order.created', JSON.stringify({ orderId: rows[0].id, paymentRef })]
  );
  await client.query('COMMIT');
  return rows[0].id;
}
// Relay process polls outbox and publishes to Kafka — separate concern

Scenario 2: Kafka Consumer Processes the Same Message Twice

Symptom: Emails sent twice, inventory decremented twice, payments duplicated.

Root cause: Kafka delivers at-least-once. Consumer processes a message, the downstream call succeeds, then the consumer crashes before committing the offset. On restart, the consumer re-reads and re-processes the same message.

Fix — Idempotent Consumer: Store a dedup key (partition:offset or message UUID) in Redis with TTL before processing. On each message: check Redis — if key exists, skip and commit offset. If not, process, then SET the key.

JavaScript Example 
// Idempotent Kafka consumer using Redis dedup store
async function processMessage(redis, message) {
  const dedupKey = `dedup:${message.partition}:${message.offset}`;
  const alreadyProcessed = await redis.set(dedupKey, '1', 'EX', 86400, 'NX');
  if (!alreadyProcessed) {
    console.log('Duplicate message — skipping:', dedupKey);
    return; // commit offset without reprocessing
  }
  // Safe to process — we own this message
  await processOrderEvent(JSON.parse(message.value));
}

Scenario 3: Movie Tickets Double-Booked

Symptom: Two users both receive booking confirmations for the same seat.

Root cause: Read-modify-write race condition (TOCTOU). Both users read available = 1 simultaneously, both see the seat as available, both proceed, both confirm. Seat is sold twice.

Fix Option A — SELECT FOR UPDATE: DB-level exclusive row lock. The second reader blocks until the first commits or rolls back.

Fix Option B — Redis SETNX reservation lock: SET reservation:{seatId} {userId} EX 600 NX. Only one requester gets the lock. Second requester receives nil and sees "seat being reserved."

JavaScript Example 
// Redis SETNX seat reservation with 10-minute TTL
async function reserveSeat(redis, seatId, userId) {
  const key = `reservation:seat:${seatId}`;
  const acquired = await redis.set(key, userId, 'EX', 600, 'NX');
  if (!acquired) {
    return { success: false, reason: 'seat_already_reserved' };
  }
  // Proceed to DB confirmation within TTL window
  return { success: true, reservationKey: key };
}
// On payment confirmation: update DB, delete key
// On timeout or payment failure: key auto-expires, seat becomes available

Scenario 4: Redis Goes Down and Takes Down the Entire Platform

Symptom: 100% of requests return 500. Redis was a single instance with no replica.

Root cause: No circuit breaker on Redis calls. All application threads hung on TCP connect timeout (30 seconds). Thread pools exhausted. The database was fine — but the application was completely dead.

Fix: Circuit breaker around all Redis calls. If Redis returns errors or timeouts for N consecutive requests, OPEN the circuit — fall through to DB. Half-open probe every 30 seconds to check recovery. Deploy Redis Sentinel for automatic failover to a replica in under 30 seconds.

JavaScript Example 
// Simple circuit breaker for Redis with DB fallback
class CircuitBreaker {
  constructor({ threshold = 5, resetMs = 30_000 } = {}) {
    this.state = 'CLOSED'; this.failures = 0;
    this.threshold = threshold; this.resetMs = resetMs;
  }
  async call(redisFn, dbFallbackFn) {
    if (this.state === 'OPEN') return dbFallbackFn();
    try {
      const result = await redisFn();
      this.failures = 0;
      return result;
    } catch {
      if (++this.failures >= this.threshold) {
        this.state = 'OPEN';
        setTimeout(() => { this.state = 'CLOSED'; this.failures = 0; }, this.resetMs);
      }
      return dbFallbackFn();
    }
  }
}
Scenarios 5–8

Bulkheads, Cache Stampedes, Connection Pools, and Rate Limiters

Scenario 5: One Slow Microservice Degrades the Entire System

Symptom: The non-critical recommendations service started timing out at 2 seconds. Within minutes, the entire product page API returned 503.

Root cause: No timeout and no bulkhead isolation. The product page API called five services in parallel. When recommendations hung, all 5 goroutines/threads waited 2 seconds. With 1,000 req/sec, the thread pool filled in 2 seconds. All requests failed.

Fix — Bulkhead Pattern: Allocate a separate, bounded thread pool per downstream service. Recommendations gets 20 threads max. When its pool fills, fail-fast with a default response ("No recommendations available"). Set aggressive timeouts: recommendations 200ms, inventory 50ms.

JavaScript Example 
// Bulkhead: per-service concurrency limit with timeout
async function callWithBulkhead(fn, { maxConcurrent = 20, timeoutMs = 200 }) {
  // In practice, use a semaphore (p-limit) + AbortController
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeoutMs);
  try {
    return await fn({ signal: controller.signal });
  } catch (err) {
    if (err.name === 'AbortError') return null; // return fallback
    throw err;
  } finally {
    clearTimeout(timer);
  }
}

// Usage: non-critical service returns null on timeout — page still loads
const recommendations = await callWithBulkhead(
  () => fetchRecommendations(userId),
  { maxConcurrent: 20, timeoutMs: 200 }
) ?? [];

Scenario 6: Cache Stampede on Hot Key Expiry

Symptom: Every midnight, DB query rate spikes 50× for 2 minutes. DB CPU hits 95%.

Root cause: The "top products" cache key had TTL=86400, set exactly at midnight. All 50,000 product page requests simultaneously miss cache and hit the database — the thundering herd.

Fix — XFetch Algorithm: Instead of a hard TTL, probabilistically refresh early. The formula: now - (delta * beta * Math.log(Math.random())) >= expiry. As expiry approaches, the probability of deciding to refresh increases. With beta=1, on average exactly one early refresh occurs. No locks, fully distributed.

JavaScript Example 
// XFetch: probabilistic early refresh — no stampede
async function xfetchGet(redis, key, fetchFn, ttlSeconds) {
  const raw = await redis.hgetall(key);
  if (raw && raw.value) {
    const expiry = parseFloat(raw.expiry);
    const delta = parseFloat(raw.delta);
    const beta = 1.0;
    // Probabilistic check: refresh early if condition met
    if (Date.now() / 1000 - delta * beta * Math.log(Math.random()) < expiry) {
      return JSON.parse(raw.value); // Return cached value
    }
    // Condition met: async background refresh, still return current value
    fetchFn().then(v => cacheWithDelta(redis, key, v, ttlSeconds)).catch(() => {});
    return JSON.parse(raw.value);
  }
  // Cache miss: fetch and store
  const t0 = Date.now();
  const value = await fetchFn();
  const delta = (Date.now() - t0) / 1000;
  await cacheWithDelta(redis, key, value, ttlSeconds, delta);
  return value;
}
async function cacheWithDelta(redis, key, value, ttl, delta = 0.1) {
  const expiry = Date.now() / 1000 + ttl;
  await redis.hset(key, { value: JSON.stringify(value), expiry, delta });
  await redis.expireat(key, Math.ceil(expiry));
}

Scenario 7: Database Connection Pool Exhausted Under Load

Symptom: Error: too many connections. PostgreSQL max_connections=200. Application has 100 instances × 10 pool connections = 1,000 potential connections.

Root cause: Each app instance maintains its own connection pool. At 100 instances, the maximum potential connections exceed PostgreSQL's limit. During a deploy where all instances start simultaneously, a connection storm occurs.

Fix — PgBouncer: Deploy PgBouncer in transaction-pooling mode. 10,000 application connections are multiplexed to 200 real PostgreSQL connections. Pool sizing formula: connections = (cpu_cores × 2) + effective_spindle_count. For a 4-core server: 9 connections is the optimal PostgreSQL setting.

JavaScript Example 
// pgbouncer.ini — transaction pooling mode
// [databases]
// mydb = host=postgres port=5432 dbname=mydb
// [pgbouncer]
// pool_mode = transaction
// max_client_conn = 10000
// default_pool_size = 25  // per DB user — total ~200 DB connections
// server_idle_timeout = 600

// Application connects to PgBouncer (port 6432), not PostgreSQL directly:
import { Pool } from 'pg';
const pool = new Pool({
  host: 'pgbouncer',  // PgBouncer host
  port: 6432,
  database: 'mydb',
  max: 10,  // per app instance; PgBouncer multiplexes to DB
});

Scenario 8: Rate Limiter Allows 2× Traffic at Window Boundary

Symptom: The rate limiter allows 200 requests/minute per user. At the minute boundary, 200 requests arrive in the last second of minute 1 and 200 more in the first second of minute 2 — 400 requests in 2 seconds slip through.

Root cause: Fixed window counter. The counter resets at the exact minute boundary. Users who send requests at the boundary of two windows can double their effective rate.

Fix — Sliding Window Counter: Track both the previous window count and the current window count. Estimate the current rate as: prev_count × (1 - elapsed_fraction) + curr_count. O(1) memory, less than 0.1% error compared to the exact sliding window log.

JavaScript Example 
// Sliding window counter rate limiter using Redis
async function isAllowed(redis, userId, limit = 200, windowSecs = 60) {
  const now = Math.floor(Date.now() / 1000);
  const currWindow = Math.floor(now / windowSecs) * windowSecs;
  const prevWindow = currWindow - windowSecs;
  const elapsed = (now - currWindow) / windowSecs; // fraction of current window elapsed

  const [prevCount, currCount] = await redis.mget(
    `rl:${userId}:${prevWindow}`,
    `rl:${userId}:${currWindow}`
  );
  // Weighted estimate: contribution of prev window decreases as current window fills
  const estimate = (parseInt(prevCount) || 0) * (1 - elapsed) + (parseInt(currCount) || 0);
  if (estimate >= limit) return false;

  await redis.multi()
    .incr(`rl:${userId}:${currWindow}`)
    .expire(`rl:${userId}:${currWindow}`, windowSecs * 2)
    .exec();
  return true;
}
Scenarios 9–12

Retry Storms, Sync Gaps, File Integrity, and Auto-Scaling Lag

Scenario 9: Cascading Failure from Retry Storms

Symptom: The payment service is slow under high load. Client services retry. More retries add more load. Service degrades further. Complete failure in 60 seconds.

Root cause: All clients retry with the same fixed delay (retry after 1 second). When the service partially recovers, all waiting clients retry simultaneously — a synchronised thundering herd of retries.

Fix — Exponential Backoff with Full Jitter: delay = random(0, min(maxDelay, baseDelay × 2^attempt)). The jitter desynchronises retries across all clients. Add a circuit breaker: if error rate exceeds 50%, stop retrying and fast-fail.

JavaScript Example 
// Exponential backoff with full jitter
async function retryWithJitter(fn, maxRetries = 5, baseDelayMs = 100) {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt === maxRetries) throw err;
      const cap = Math.min(30_000, baseDelayMs * Math.pow(2, attempt));
      const delay = Math.random() * cap; // full jitter: uniform [0, cap]
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

Scenario 10: Search Index Out of Sync with Database

Symptom: Users find a product via search, navigate to it, but it shows as deleted. The search index has stale data.

Root cause: Dual-write pattern. Application writes to PostgreSQL first, then calls the Elasticsearch API. If the Elasticsearch write fails (timeout, ES node down), the data is in the DB but not indexed. Inconsistency grows silently over time.

Fix — Change Data Capture (CDC) with Debezium: Debezium tails the PostgreSQL WAL (write-ahead log). Every committed transaction generates a Kafka event. An Elasticsearch consumer reads from Kafka and updates the index. The database is always the source of truth. The index is always eventually consistent with the DB.

JavaScript Example 
// Debezium connector config (deploy to Kafka Connect cluster)
const debeziumConfig = {

  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "postgres",
    "database.port": "5432",
    "database.dbname": "shop",
    "table.include.list": "public.products",
    "topic.prefix": "shop",
    "plugin.name": "pgoutput"
  }
};
// Consumer subscribes to 'shop.public.products' Kafka topic
// and upserts into Elasticsearch on every INSERT/UPDATE/DELETE event

Scenario 11: User Uploaded File Corrupted After S3 Transfer

Symptom: Large file uploads (videos, PDFs) occasionally arrive corrupted. The upload reports success.

Root cause: S3 multipart upload splits files into N parts uploaded in parallel. If a part is silently corrupted during transit (TCP checksum collision, network bit-flip at the IP layer), S3 stores the corrupted part. The CompleteMultipartUpload call succeeds but the file is corrupt.

Fix: Compute SHA-256 of the file before uploading. Pass Content-MD5 header with each part (S3 validates each part on receipt). After CompleteMultipartUpload, verify the final checksum matches the pre-upload hash.

JavaScript Example 
import { createHash } from 'crypto';
import { readFile } from 'fs/promises';

async function uploadWithIntegrityCheck(s3, bucket, key, filePath) {
  const data = await readFile(filePath);
  const expectedHash = createHash('sha256').update(data).digest('hex');

  // Upload (simplified — production uses multipart for large files)
  await s3.putObject({
    Bucket: bucket, Key: key, Body: data,
    ChecksumSHA256: Buffer.from(expectedHash, 'hex').toString('base64'),
  });

  // Verify: head-object and compare checksum
  const head = await s3.headObject({ Bucket: bucket, Key: key });
  if (head.ChecksumSHA256 !== Buffer.from(expectedHash, 'hex').toString('base64')) {
    await s3.deleteObject({ Bucket: bucket, Key: key });
    throw new Error('Upload integrity check failed — file corrupted during transfer');
  }
  return { key, sha256: expectedHash };
}

Scenario 12: Auto-Scaling Triggers Too Late During Traffic Spike

Symptom: Flash sale starts at noon. Traffic spikes 10× in 30 seconds. Auto-scaling triggers at 12:05. Five minutes of degraded service.

Root cause: Auto-scaling based on CPU. CloudWatch aggregates CPU with a 1-minute lag. At 100% CPU, the scale-out decision is made. New EC2 instances take 3–5 minutes to boot and register with the load balancer. Total delay: 6–8 minutes.

Fix: Use SQS queue depth as a custom CloudWatch metric — queue depth grows in sub-seconds when traffic spikes, far faster than CPU. For known events: schedule scale-out 30 minutes before the event using AWS Scheduled Scaling or EC2 Auto Scaling scheduled actions.

JavaScript Example 
// AWS CLI: schedule scale-out 30 minutes before flash sale
// aws autoscaling put-scheduled-update-group-action \
//   --auto-scaling-group-name my-asg \
//   --scheduled-action-name pre-flash-sale \
//   --start-time "2026-07-16T11:30:00Z" \
//   --desired-capacity 50 \
//   --min-size 50

// Custom CloudWatch metric: SQS queue depth (reacts in seconds vs. CPU minutes)
import { CloudWatchClient, PutMetricAlarmCommand } from '@aws-sdk/client-cloudwatch';
const cw = new CloudWatchClient({});
await cw.send(new PutMetricAlarmCommand({
  AlarmName: 'HighQueueDepth',
  MetricName: 'ApproximateNumberOfMessagesVisible',
  Namespace: 'AWS/SQS',
  Threshold: 1000, ComparisonOperator: 'GreaterThanThreshold',
  EvaluationPeriods: 1, Period: 60, Statistic: 'Maximum',
  AlarmActions: ['arn:aws:autoscaling:...my-scaling-policy'],
}));
Scenarios 13–16

Leader Election, Session Loss, Webhook Failures, and Kafka Hotspots

Scenario 13: Leader Election Storm in Distributed System

Symptom: Distributed job scheduler starts running the same job N times simultaneously.

Root cause: Split-brain. The leader lease in ZooKeeper expired during a 2-second network partition. All N instances saw "no leader" and simultaneously elected themselves. The lease TTL was too short (1 second).

Fix: Use Raft consensus (etcd, Consul) instead of ZooKeeper ephemeral nodes. Raft guarantees at-most-one leader. Add a fencing token: each leader receives a monotonically increasing token. The storage backend rejects writes with a token lower than the last seen — preventing a deposed leader from causing side effects after it believes it has been re-elected.

JavaScript Example 
// Redis-based leader election with fencing token
async function acquireLeadership(redis, instanceId, ttlSeconds = 30) {
  // Atomic: SET only if not exists; returns current fencing token
  const acquired = await redis.set('leader:lock', instanceId, 'EX', ttlSeconds, 'NX');
  if (!acquired) return null;

  // Increment monotonic fencing token — storage backends check this
  const token = await redis.incr('leader:token');
  return token; // pass token with every write operation
}

async function doLeaderWork(redis, instanceId, token) {
  // Verify we still hold the lock before each critical operation
  const currentLeader = await redis.get('leader:lock');
  if (currentLeader !== instanceId) throw new Error('Lost leadership');
  // Include token in downstream writes for fencing
  await performJob({ fencingToken: token });
}

Scenario 14: Session Data Lost After Rolling Deployment

Symptom: 10–20% of users are logged out on every deployment.

Root cause: Session data stored in-memory on the application server (e.g., express-session with MemoryStore). Rolling deployment terminates old instances. Users whose session was on a terminated instance lose their session.

Fix: Externalise session storage to Redis. Use connect-redis with express-session. Sessions survive server restarts and are accessible from any instance. Set Redis key TTL = session timeout.

JavaScript Example 
import session from 'express-session';
import RedisStore from 'connect-redis';
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL);

app.use(session({
  store: new RedisStore({ client: redis, prefix: 'sess:' }),
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,
  cookie: {
    maxAge: 24 * 60 * 60 * 1000, // 24 hours
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
  },
}));
// Sessions now survive rolling deploys — any instance can serve any session

Scenario 15: Webhook Delivery Failing Silently

Symptom: Third-party integrations stop receiving webhooks. No errors in application logs. Customer reports the issue 4 hours later.

Root cause: Webhook delivery was a fire-and-forget HTTP call inside the payment callback handler. If the customer's endpoint returned 500 or timed out, the error was swallowed. No retry, no alerting, no dead-letter queue.

Fix: Webhook delivery service with exponential retry. On failure, enqueue to a Redis-backed retry queue with delays: 1s, 2s, 4s, 8s, 30s, 5min, 30min, 2h, 12h, 24h. After 10 failures, move to dead-letter queue. Add HMAC signature to each webhook payload for authenticity verification.

JavaScript Example 
import { createHmac } from 'crypto';

async function deliverWebhook(bull, endpoint, payload, secret) {
  const signature = createHmac('sha256', secret)
    .update(JSON.stringify(payload))
    .digest('hex');

  // Add to Bull queue with exponential backoff
  await bull.add(
    { endpoint, payload, signature },
    {
      attempts: 10,
      backoff: { type: 'exponential', delay: 1000 },
      removeOnComplete: true,
      removeOnFail: false, // keep in dead-letter queue for inspection
    }
  );
}

// Worker: deliver and verify response
async function webhookWorker(job) {
  const { endpoint, payload, signature } = job.data;
  const resp = await fetch(endpoint, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json', 'X-Signature-256': signature },
    body: JSON.stringify(payload),
    signal: AbortSignal.timeout(5000),
  });
  if (!resp.ok) throw new Error(`Endpoint returned ${resp.status}`);
}

Scenario 16: Hot Partition in Kafka

Symptom: Kafka consumer lag grows only on partition 0. That consumer is at 100% CPU. Partitions 1–15 are idle.

Root cause: Partition key is userId. A celebrity user generates 10M events per day — 100× the average. All their events go to the same partition (hash(userId) % N). One partition, one consumer thread.

Fix: Composite partition key: `${userId}#${randomSuffix}` where randomSuffix is random(0, 8). The celebrity's events spread across 8 partitions. Note: ordering within a user is lost — use a sequence number in the event payload if ordering matters.

JavaScript Example 
// Composite Kafka partition key to spread hot users
function getPartitionKey(userId, isHighVolume) {
  if (!isHighVolume) return String(userId);
  // Spread high-volume users across 8 virtual shards
  const shard = Math.floor(Math.random() * 8);
  return `${userId}#${shard}`;
}

await producer.send({
  topic: 'user-events',
  messages: [{
    key: getPartitionKey(userId, followerCount > 10_000),
    value: JSON.stringify({ userId, eventType, timestamp, seqNum: event.seqNum }),
  }],
});
// Consumer reconstructs per-user order using seqNum if needed
Scenarios 17–22

Slow Queries, Celebrity Fan-out, Distributed Crons, Memory Leaks, GDPR, Cold Starts

Scenario 17: Database Query Suddenly 100× Slower

Symptom: A specific API endpoint was p99 <50ms for 6 months. One day it becomes p99 = 8,000ms. No deployment occurred.

Root cause: The query had WHERE status = 'PENDING' AND created_at > ?. At low row counts, PostgreSQL used an index scan on created_at. As the table grew past 10M rows, the query planner switched to a sequential scan — because the index cost estimate crossed a threshold. 10M row sequential scan = 8 seconds.

Fix: Run EXPLAIN ANALYZE to see the query plan change. Create a composite index on the filtered columns: CREATE INDEX CONCURRENTLY idx_orders_status_created ON orders(status, created_at). The CONCURRENTLY option avoids a table lock. Add pg_stat_statements monitoring to detect plan changes before they reach production.

JavaScript Example 
// PostgreSQL: create composite index without table lock
// Run this during low-traffic period — takes minutes on large tables
// CREATE INDEX CONCURRENTLY idx_orders_status_created
//   ON orders(status, created_at DESC)
//   WHERE status IN ('PENDING', 'PROCESSING'); -- partial index saves space

// pg_stat_statements: find slowest queries
// SELECT query, mean_exec_time, calls
// FROM pg_stat_statements
// ORDER BY mean_exec_time DESC LIMIT 10;

// Node.js: always log slow queries

Scenario 18: Fan-Out Write Overwhelms Follower Queues

Symptom: When a celebrity with 80M followers posts, the fan-out job takes 12 minutes. Other users' timelines are delayed.

Root cause: Fan-out on write for all users. 80M Redis LPUSH operations, each O(1) but 80M sequential = minutes of Redis write saturation.

Fix — Hybrid Push-Pull: Fan-out on write for users with fewer than 10,000 followers. For celebrities: skip fan-out. On timeline read, fetch the 5 most recent posts from each celebrity the user follows (read-time pull) and merge with the user's Redis timeline in application code. The merge of 20 celebrity feeds × 5 posts = 100 items sorted in memory is negligible.

JavaScript Example 
// Hybrid fan-out: push for normal users, pull for celebrities
const CELEBRITY_THRESHOLD = 10_000;

async function onNewPost(redis, db, authorId, postId, timestamp) {
  const { rows } = await db.query('SELECT follower_count FROM users WHERE id=$1', [authorId]);
  const followerCount = rows[0].follower_count;

  if (followerCount <= CELEBRITY_THRESHOLD) {
    // Fan-out on write: push post ID to each follower's timeline ZSET
    const followers = await db.query('SELECT id FROM followers WHERE followee_id=$1', [authorId]);
    const pipeline = redis.pipeline();
    for (const { id } of followers.rows) {
      pipeline.zadd(`timeline:${id}`, timestamp, String(postId));
      pipeline.zremrangebyrank(`timeline:${id}`, 0, -501); // keep top-500
    }
    await pipeline.exec();
  } else {
    // Celebrity: mark for read-time pull — no fan-out
    await redis.sadd('celebrities', String(authorId));
  }
}

Scenario 19: Distributed Cron Job Runs N Times

Symptom: A daily digest email is deployed across 5 instances. Users receive 5 digest emails.

Root cause: Each instance runs its own cron scheduler. No coordination. All 5 execute simultaneously.

Fix: Redis SETNX leader lock before each cron execution. Only the instance that acquires the lock runs the job. TTL = job period to ensure the lock expires before the next run. The job itself must be idempotent — if two instances race at TTL boundary, the second run is a no-op.

JavaScript Example 
// Distributed cron: only one instance runs per period
async function runWithDistributedLock(redis, jobName, periodSecs, jobFn) {
  const lockKey = `cron:${jobName}`;
  const instanceId = process.env.INSTANCE_ID ?? Math.random().toString(36).slice(2);

  const acquired = await redis.set(lockKey, instanceId, 'EX', periodSecs, 'NX');
  if (!acquired) {
    console.log(`[${jobName}] Lock held by another instance — skipping`);
    return;
  }
  try {
    console.log(`[${jobName}] Running (lock acquired)`);
    await jobFn(); // must be idempotent
  } finally {
    // Only release if we still own the lock (prevents releasing another instance's lock)
    const current = await redis.get(lockKey);
    if (current === instanceId) await redis.del(lockKey);
  }
}

// Usage:
setInterval(() => runWithDistributedLock(redis, 'daily-digest', 86400, sendDigestEmails), 60_000);

Scenario 20: Memory Leak Causes OOM Kill Every 6 Hours

Symptom: Node.js process memory grows from 200 MB to 2 GB over 6 hours, then OOM-kills. Growth resumes on restart.

Root cause: An event listener was added inside a request handler: emitter.on('data', handler). Listeners accumulated because they were never removed. Each held a closure referencing request-scoped variables. Memory grows with every request.

Fix: Use emitter.once('data', handler) (auto-removes after one call) or call emitter.removeListener() in a cleanup block. Use WeakMap for object-keyed caches — WeakMap entries are garbage-collected when the key object is collected. Add heap snapshot monitoring.

JavaScript Example 
// Bug: listener added per request, never removed
// emitter.on('data', (chunk) => { ... requestContext ... }); // WRONG

// Fix 1: use once() — auto-removes after first emission
emitter.once('data', (chunk) => { processChunk(chunk, requestContext); });

// Fix 2: explicit cleanup with removeListener
function requestHandler(req, res) {
  const handler = (chunk) => processChunk(chunk, req);
  emitter.on('data', handler);
  res.on('finish', () => emitter.removeListener('data', handler)); // cleanup
}

// Fix 3: WeakMap for request-scoped caches (GC cleans up when req is collected)
const cache = new WeakMap(); // keys are request objects — auto-GC'd
function getCachedData(req) {
  if (!cache.has(req)) cache.set(req, computeExpensiveData(req));
  return cache.get(req);
}

// Monitor: alert when RSS exceeds 1.5GB
setInterval(() => {
  const { rss } = process.memoryUsage();
  if (rss > 1.5e9) console.error(`Memory warning: RSS ${(rss/1e9).toFixed(2)}GB`);
}, 30_000);

Scenario 21: GDPR Deletion Request Misses Derived Data

Symptom: A GDPR deletion request is processed. Account deleted. 3 months later, a data audit finds the user's data still in the analytics warehouse, recommendation model training set, and email suppression list.

Root cause: Deletion logic only removed from the primary user table and auth store. It did not fan out to 10+ downstream systems that stored derived copies of user data.

Fix: Publish a user.deleted event to a Kafka topic. Every downstream service that stores user data subscribes and implements a deletion handler. Maintain an audit log of confirmed deletions. GDPR Article 17 SLA: all systems must confirm deletion within 30 days.

JavaScript Example 
// GDPR deletion event published on account deletion
async function deleteUser(db, kafka, userId) {
  // 1. Anonymise/delete primary record
  await db.query('UPDATE users SET email=$1, name=$2, deleted_at=NOW() WHERE id=$3',
    [`deleted-${userId}@anon.invalid`, 'Deleted User', userId]);

  // 2. Publish deletion event — downstream services subscribe and purge
  await kafka.producer().send({
    topic: 'user-lifecycle',
    messages: [{
      key: String(userId),
      value: JSON.stringify({ event: 'user.deleted', userId, requestedAt: new Date().toISOString() }),
    }],
  });

  // 3. Log deletion request for audit trail
  await db.query('INSERT INTO gdpr_audit (user_id, event, ts) VALUES ($1, $2, NOW())',
    [userId, 'deletion_requested']);
}

// Each downstream service: subscribe to 'user-lifecycle' and handle deletion
// analytics-service: DELETE FROM events WHERE user_id = ?
// recommendation-service: DELETE FROM user_features WHERE user_id = ?
// email-service: add to suppression list, DELETE FROM preferences WHERE user_id = ?

Scenario 22: Cold Start Latency Spikes Every 30 Minutes

Symptom: Lambda function p99 latency is <100ms normally. Every 30 minutes there is a spike to 8 seconds, correlating with low-traffic periods.

Root cause: Lambda cold start. After ~15 minutes of inactivity, AWS recycles the execution environment. On the next invocation: runtime initialises, dependencies load, database connection pool initialises. Node.js + PostgreSQL connection: cold start = 5–8 seconds.

Fix A — Provisioned Concurrency: Lambda keeps N instances pre-initialised at all times. Cold starts are eliminated for provisioned instances. Cost: you pay for idle instances.

Fix B — Keep-warm ping (free): A CloudWatch Events rule triggers the Lambda every 5 minutes with a {"warm": true} event. The handler returns immediately on warm pings. Prevents recycling.

Fix C — Move initialisation outside handler: DB connection pool and SDK clients initialised at module level are reused across invocations in the same container.

JavaScript Example 
import { Pool } from 'pg';

// CORRECT: pool created at module level — shared across invocations in same container
const pool = new Pool({ connectionString: process.env.DB_URL, max: 2 });

export const handler = async (event) => {
  // Keep-warm handler: return immediately on ping events
  if (event.warm) return { statusCode: 200, body: 'warm' };

  // Actual logic — pool connection already warm from module init
  const { rows } = await pool.query('SELECT 1');
  return { statusCode: 200, body: JSON.stringify(rows) };
};

// CloudWatch Events rule (cron): runs every 5 minutes to keep warm
// { "source": "aws.events", "warm": true }

Pattern Analysis

Cross-Cutting Lessons from All 22 Scenarios

Grouping the 22 scenarios by root cause category reveals the most leveraged fixes:

  • Distributed transaction / atomicity (1, 3, 13): Use Saga + transactional outbox for cross-service atomicity. Avoid XA transactions in microservices — they create distributed locking that degrades availability.
  • Exactly-once semantics (2, 19): Idempotency key + dedup store. Treat all messaging as at-least-once from day one. The idempotency check cost (one Redis lookup) is negligible compared to the cost of a duplicate payment or double email.
  • Resource exhaustion (4, 5, 7, 16): Circuit breakers, bulkheads, connection pooling, and composite partition keys prevent single-component overload from cascading. Missing any one of these converts a partial failure into a total outage.
  • Timing and synchronisation (6, 8, 9, 12): Jitter, sliding windows, and predictive scaling break synchronised spikes. Synchronised behaviour in distributed systems is almost always a bug.
  • Data consistency (10, 21): CDC (Debezium) and event-driven deletion propagation keep derived stores consistent with the source of truth. Dual-writes are a consistency debt that grows silently until it fails loudly.
  • Operational hygiene (11, 14, 15, 17, 20, 22): Checksums, externalised sessions, retry queues, index monitoring, memory profiling, and keep-warm pings. These are not glamorous — but they prevent the category of failures that are discovered by customers, not by engineers.

The consistent thread across all 22 scenarios: none of these failures would have been caught by unit tests. Most would be caught by integration tests. All can be prevented by applying one of a handful of well-understood patterns. Distributed system failures are rarely caused by bugs in the happy path — they are caused by the absence of handling for the unhappy path.

Practical Checklist

What to Verify in Every Distributed System

  • Use transactional outbox for any write that must trigger a cross-service event.
  • Make all event consumers idempotent — assume every message will be delivered at least twice.
  • Put circuit breakers on every external dependency: Redis, database, downstream services.
  • Isolate thread/connection pools per downstream service (bulkhead pattern).
  • Use sliding window or token bucket rate limiting — never fixed window.
  • Add full jitter to all retry logic — synchronised retries amplify the failure they are meant to fix.
  • Use CDC (Debezium) to synchronise derived stores — dual-writes will diverge silently.
  • Compute and verify file checksums for all large file transfers — S3 multipart is not immune to corruption.
  • Externalise all session state — in-memory sessions are destroyed on rolling deployments.
  • Monitor DB query execution plans — they change silently as data volume grows.
  • Publish deletion events to Kafka and fan out to all downstream services for GDPR compliance.
  • Move DB connection pool and SDK client initialisation outside Lambda handlers.
FAQ

Common Questions

In the Saga pattern, what happens if the compensation transaction also fails?

Compensating transactions must themselves be idempotent and retried with exponential backoff. A compensation that fails after N retries goes to a dead-letter queue requiring manual intervention. This is why Saga compensations must be designed to be eventually successful — for example, a refund will keep retrying until the payment gateway becomes available again, because a failed compensation for a payment Saga means a customer was charged without receiving their order.

Should I always use idempotency keys for every API call?

For any call with side effects (write, payment, notification, state change): yes. For pure reads: no. The cost of an idempotency check (one Redis SETNX lookup, sub-millisecond) is negligible compared to the cost of a duplicate side effect — a double charge, a double notification, or an inventory double-decrement.

How do I choose between SELECT FOR UPDATE and Redis SETNX for concurrency control?

SELECT FOR UPDATE is correct when the final write must go to the same SQL database — it uses database-native row locking with full transactional guarantees. Redis SETNX is faster and works across service boundaries, but requires careful TTL management and does not integrate with SQL transactions. Use SELECT FOR UPDATE for single-database seat or inventory reservation; use Redis SETNX for cross-service reservation flows where you need to hold a lock while calling an external service.

How long should idempotency keys and dedup keys be stored?

At minimum: the maximum retry window plus a safety buffer. For payment idempotency keys: 24–48 hours (Stripe's standard is 24 hours). For Kafka consumer dedup keys: 2× the maximum consumer group lag (if max lag is 1 hour, store dedup keys for 2 hours). For API idempotency keys from external clients: 24 hours is the industry standard.

Key Takeaway

The 22 scenarios in this guide are not hypotheticals — they are failure patterns extracted from production incidents at real companies. What they share: none would have been caught by unit tests, most could be detected by integration tests, and all can be prevented by applying one of a handful of well-understood patterns. The most valuable insight is this: distributed system failures are rarely caused by bugs in the happy path. They are caused by the absence of handling for the unhappy path — the missing circuit breaker, the missing idempotency check, the missing composite partition key, the missing outbox event. Building robust distributed systems means coding the failure paths with the same rigour as the success paths. The 3 AM alert arrives when you don't.
