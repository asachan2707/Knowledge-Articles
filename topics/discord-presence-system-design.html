Discord Presence System Design Interview: "At What Scale?" and Follow-Up Variations

Full interview walkthrough for designing Discord's online/offline/idle presence system. Core design, then interviewer follow-ups at each scale tier: 100k users, 10M users, 150M+ users. Covers WebSocket fan-out, presence pub/sub, heartbeat design, eventual consistency trade-offs, and the exact points where naive designs break.

Domain: System Design · Interview Prep · Distributed Systems Published: 2026-07-22

Presence is the "green dot." Who is online, who is idle, who is offline. It sounds trivial until you ask: at 150M daily active users, how do you propagate a single user's status change to every one of their mutual friends in near-real-time, across 10,000+ WebSocket servers, without overwhelming either the servers or the storage layer?

Why Discord is the canonical example: Discord has 500M registered users, ~150M daily active users, and communities (servers) that can have 500,000+ members — all of whom subscribe to mutual presence. The fan-out for a presence change in a large server is a hard distributed systems problem.

Interviewer framing · "Design Discord's presence system"

Typical interviewer prompt: "Design a system that tracks whether users are online, offline, or idle, and shows that status to their friends and mutual server members in real time." Follow-ups: "What if users have 10,000 mutual server members? What if you have 150M users? What if the presence server crashes? How do you handle mobile app backgrounding?"

The correct approach is to start with a minimal correct design, then drive the interviewer to the scale breakpoints — because each breakpoint reveals a different architectural decision.

Phase 1: Core Design (Single Server, 100k Users)

At 100k users, a single presence server with a Redis store and WebSocket connections is sufficient.

Data model:

  • Redis Hash: presence:{userId} → { status: online|idle|offline, lastSeen: epoch, clientId: ws_abc }
  • TTL: 30 seconds. Refreshed by client heartbeat every 15 seconds. Expiry = offline.

Write path (user comes online):

  1. Client opens WebSocket connection to the presence server.
  2. Server writes SET presence:{userId} { status: online } EX 30.
  3. Server publishes presence-changed:{userId} to Redis Pub/Sub channel.
  4. All other users who have this user in their friend/server list receive the update via their WebSocket connections.

Heartbeat: Client sends a ping every 15 seconds. Server refreshes TTL. Missed heartbeats (server detects connection close or TTL expires) → status transitions to offline.

JavaScript Example — Presence Server Core 
// presence-server.js — Node.js + ws + ioredis
import { WebSocketServer } from 'ws';
import Redis from 'ioredis';

const redis = new Redis(process.env.REDIS_URL);
const redisSub = new Redis(process.env.REDIS_URL); // separate sub connection

const HEARTBEAT_INTERVAL_MS = 15_000;
const PRESENCE_TTL_S = 30;

// Map: userId → WebSocket connection
const connections = new Map();
// Map: userId → Set (users who need to be notified of this user's changes)
const subscriptions = new Map();

const wss = new WebSocketServer({ port: 3001 });

wss.on('connection', async (ws, req) => {
  const userId = extractUserIdFromToken(req.headers['authorization']);

  // Register connection
  connections.set(userId, ws);
  await setPresence(userId, 'online');

  // Subscribe to presence updates of user's friends/server members
  const peers = await getPeers(userId); // from DB: all mutual server members + friends
  for (const peerId of peers) {
    if (!subscriptions.has(peerId)) subscriptions.set(peerId, new Set());
    subscriptions.get(peerId).add(userId); // userId wants to know about peerId's changes
  }

  ws.on('message', async (data) => {
    const msg = JSON.parse(data);
    if (msg.type === 'heartbeat') {
      await redis.expire(`presence:${userId}`, PRESENCE_TTL_S);
    }
    if (msg.type === 'status-change') { // idle, dnd, etc.
      await setPresence(userId, msg.status);
    }
  });

  ws.on('close', async () => {
    connections.delete(userId);
    await setPresence(userId, 'offline');
  });
});

async function setPresence(userId, status) {
  await redis.setex(`presence:${userId}`, PRESENCE_TTL_S,
    JSON.stringify({ status, ts: Date.now() }));
  await redis.publish('presence-changes', JSON.stringify({ userId, status }));
}

// Subscribe to presence changes and fan out to interested users
redisSub.subscribe('presence-changes');
redisSub.on('message', (channel, message) => {
  const { userId, status } = JSON.parse(message);
  const interested = subscriptions.get(userId) ?? new Set();
  for (const subscriberId of interested) {
    const ws = connections.get(subscriberId);
    if (ws?.readyState === 1) { // OPEN
      ws.send(JSON.stringify({ type: 'presence-update', userId, status }));
    }
  }
});

Phase 2: Multi-Server Scaling (10M Users)

At 10M users, a single presence server can't hold all WebSocket connections. Horizontally scale to 100 presence servers. New problem: user A (on server 1) changes status, but user B (their friend) is connected to server 47. Server 1 must notify server 47, which then pushes to user B's WebSocket.

Solution: Pub/Sub routing layer

Each presence server publishes status changes to a shared Kafka topic presence-changes. Every other server consumes from this topic. On receiving a change, each server checks if any of its connected users subscribe to the changed user — if so, pushes the update. This is a broadcast approach — O(servers) fan-out per change.

Alternative: Presence routing table

Store a routing table in Redis: user-server:{userId} → server ID. When a presence change occurs, look up which server each subscriber is connected to and publish only to those specific servers. More targeted, less broadcast noise. Required at > 1,000 servers.

Phase 3: Large Server Problem (150M Users, 500k-Member Servers)

A user in a 500,000-member server changes status. Naively, this triggers 500,000 presence update notifications. At 150M DAU with each user averaging 5 server memberships, that is an enormous fan-out.

The "At What Scale?" breakpoints:

ScaleProblemSolution
100k usersNone — single server worksRedis + single presence server
1M usersSingle server saturated (~64k WS connections)Horizontal scale + Kafka broadcast
10M usersPub/sub broadcast to all servers is noisyRouting table: only notify servers with subscribers
50M usersLarge server fan-out (100k+ member servers)Presence aggregation: don't fan out status changes in massive servers
150M usersHeartbeat storm, presence storage at PB scaleHeartbeat batching, tiered presence (friends vs server members)

Tiered presence strategy (Discord's actual approach)

  • Tier 1 — Direct friends: Full real-time presence updates. Low fan-out (average user has ~50 friends).
  • Tier 2 — Small servers (< 1,000 members): Real-time presence via WebSocket push.
  • Tier 3 — Large servers (> 1,000 members): Pull-based presence. The member list shows presence, but updates are fetched on demand when a user opens the member list, not pushed. Stale by up to 60 seconds — but the bandwidth cost of real-time push for 500k members is not justifiable for the UX value.

Heartbeat Design and Failure Detection

Heartbeat: client sends ping every 15s. Server expects ping within 30s (2× interval for network jitter tolerance). Missed ping = connection lost = offline transition.

Mobile backgrounding: iOS and Android aggressively kill WebSocket connections when apps are backgrounded. Handling:

  • On background: send status: away before the app is backgrounded.
  • On disconnect without explicit away: 30s grace period before marking offline (may just be a network blip).
  • On reconnect: server detects presence:{userId} key exists → user was briefly disconnected, not offline → suppress the offline notification if the reconnect comes within the grace period.

Eventual Consistency and the Stale Presence Problem

At scale, presence is explicitly eventually consistent. The green dot a user sees is the last known state, not necessarily the current state. Acceptable because:

  • The consequence of a stale dot is cosmetic — you think someone is online when they're not.
  • The correct state converges within the heartbeat window (15–30 seconds).
  • Strong consistency for presence (requiring consensus on each status change) would be prohibitively expensive and latency-sensitive.

Key Takeaway

The Discord presence design is an exercise in recognising which component breaks at which scale — and having a targeted fix for each. Single server → Redis + pub/sub → routing table → tiered presence for large servers → heartbeat batching for mobile. The "at what scale?" framing is also the correct interview strategy: show the interviewer that you know where each design breaks, before they ask.
