The Beginner's Guide to Agentic AI: From Zero to Your First AI Agent

What separates a chatbot from an agent, how the agent loop works, what tool calling actually does at the code level, and how to build your first working agent in under 50 lines of Python.

SourcesHugging Face Agents Course, Anthropic building-effective-agents
Frameworks coveredsmolagents, LangChain, LangGraph, raw API
LevelBeginner — no prior AI engineering experience needed

A chatbot answers and waits. An agent acts, observes the result, decides what to do next, and keeps going until a goal is met. That one difference — the loop — is what makes agentic AI capable of completing multi-step tasks that no single prompt could handle.

Core idea: An agent is a loop wrapped around an LLM. The LLM reasons about what to do; the agent framework executes the action; the result feeds back into the LLM's context. Repeat until done.

The spectrum of agency

Not everything called an "agent" is the same. The autonomy spectrum runs from simple processors (LLM output → fixed action) all the way to multi-agent systems where one LLM orchestrates others. Most production deployments sit at levels 2–3 — routing and tool calling — not at full autonomous agency. Start at level 2. Add complexity only when it demonstrably helps.

The agent loop

Think → Act → Observe — the ReAct pattern

The core loop has three phases that cycle continuously:

  1. Think (Reason): the LLM receives the current context — system instructions, conversation history, tool definitions, previous results — and reasons about the next action. It may write this reasoning explicitly as a scratchpad before deciding.
  2. Act: the model emits a tool call — a structured JSON object naming a tool and providing arguments. The agent framework (not the model) executes the function.
  3. Observe: the tool's return value is added to the context as an observation message. The loop repeats. When the LLM produces a final answer instead of a tool call, the loop terminates.

This is the ReAct pattern (Reason + Act), from the 2022 paper of the same name. Every major agent framework — LangChain, LangGraph, smolagents, AutoGPT — implements a variation of this loop.

How tool calling works at the code level

A tool is a Python function with a name, a description, and typed arguments. The description is what the LLM reads to decide when and how to call the tool — write it as if briefing a junior engineer. 

from smolagents import tool

@tool
def calculator(a: int, b: int) -> int:
    """
    Multiply two integers together.
    Use when the user needs a numerical calculation.
    Args:
        a: first integer
        b: second integer
    """
    return a * b

The LLM never runs this function. It outputs structured text saying it wants to call calculator with specific arguments. Your agent framework parses that output and calls the actual Python function, then feeds the return value back to the LLM as the next observation.

Anatomy of an agent

The four core components

Strip away the framework branding and every agent is assembled from the same four parts. Knowing them lets you read any codebase or diagram and map it back to something familiar.

  • The model (brain): the LLM that interprets the goal and picks the next step. Its quality caps what the whole system can do.
  • Tools (hands): functions the loop can run on the model's behalf — search, calculators, database queries, file access, API calls.
  • Memory: whatever the agent can still "see" or look up when it decides. Three kinds matter, covered below.
  • Planning: how a big goal is split into smaller steps — either implicitly inside the model's reasoning or explicitly as a written task list the agent updates as it goes.

The loop itself is often described as four beats rather than three: perceive the input, reason about it, act, then evaluate whether the goal is met. The evaluate beat is just the "should I stop?" check that ends the ReAct cycle.

Three kinds of agent memory

  • In-context memory: the running message list inside the prompt. Fast and simple, but bounded by the context window and gone when the run ends.
  • External memory: facts stored outside the model — usually a vector database or plain database — and fetched by similarity or key when relevant. This is what RAG is.
  • Episodic memory: a record of past runs (what was tried, what worked) that the agent can consult next time, so it improves across sessions instead of starting cold.
Your first agent

A minimal working agent in ~30 lines

from smolagents import CodeAgent, DuckDuckGoSearchTool, HfApiModel

# 1. Choose an LLM
model = HfApiModel(model_id="meta-llama/Meta-Llama-3.1-8B-Instruct")

# 2. Give it a tool
tools = [DuckDuckGoSearchTool()]

# 3. Create the agent
agent = CodeAgent(tools=tools, model=model)

# 4. Run it
result = agent.run(
    "What is the current population of Tokyo, and how does it compare to Paris?"
)
print(result)

What happens internally: the agent sends the question + tool schema to the LLM → the LLM emits a search call → the agent executes the search → the result goes back to the LLM → the LLM either calls another tool or writes a final answer.

Choosing the right shape

Chains vs workflows vs agents: climb the ladder in order

  • Chain: a fixed list of LLM calls, each feeding the next. Predictable, cheap, easy to test. Covers more tasks than people expect.
  • Workflow: a chain with branches, loops and parallel legs, but where your code decides the path. Use it when the steps are known yet vary by input.
  • Agent: the model itself chooses the next step at runtime. Reserve it for problems where you cannot list the steps in advance.

Each rung trades predictability for flexibility, and costs more tokens and debugging time. Begin at a chain, move up only when you hit a concrete limit you can name.

The same logic applies to team size. A single agent with a handful of tools is the default. Reach for multiple agents — an orchestrator handing sub-tasks to specialists, as CrewAI and AutoGen encourage — only when one prompt can no longer hold all the instructions and tools without confusing the model.

Frameworks compared

Which framework to use when

  • smolagents (Hugging Face): minimal, beginner-friendly, best for learning the fundamentals without framework magic obscuring what is happening.
  • LangChain: most popular, fastest to get a basic agent running across many LLM providers. Richest ecosystem of pre-built tools and integrations.
  • LangGraph: more control over the loop — supports branching, cycles, and complex state machines. Better for production agents that need precise flow control.
  • LlamaIndex: strongest on retrieval and RAG-focused agents. Best choice for document Q&A and knowledge-base agents.
  • Raw API: Anthropic's own recommendation for production — "Start simple. Add framework complexity only when it demonstrably improves outcomes." Direct API calls are more debuggable and less surprising than framework abstractions.

Common workflow patterns beyond the basic loop

  • Prompt chaining: output of step N feeds step N+1 — for tasks with a fixed sequence of sub-problems.
  • Routing: LLM classifies input and directs to a specialist handler — good for support bots covering multiple domains.
  • Parallelisation: run subtasks simultaneously — dramatically faster for independent sub-problems.
  • Orchestrator-Workers: a central LLM breaks work into tasks and delegates to worker LLMs — scales to complex research or code generation tasks.
A 12-week plan

12-week learning path

Order matters: each block makes the next one understandable. Skipping to a framework in week one is the most common reason people can't debug their first agent.

  • Weeks 1–2, prompt engineering: system prompts, few-shot examples, structured output. Everything later depends on being able to steer a model reliably.
  • Weeks 3–4, the LLM API: call a provider directly, manage messages, stream, count tokens, handle rate limits.
  • Weeks 5–6, tool calling: define schemas, parse tool requests, return results.
  • Weeks 7–8, an agent loop from scratch: write the loop yourself, with no framework (example below).
  • Weeks 9–10, one framework: rebuild the same agent in LangGraph, smolagents, CrewAI, Pydantic AI or the OpenAI Agents SDK. Pick one; you now know what it hides.
  • Weeks 11–12, memory and vector databases: embeddings, retrieval, and persisting what an agent learns between runs.
Week 7–8 exercise

A research assistant with a hand-written loop

This agent has two tools — a calculator and a note-saver — and no framework. The calculator parses the expression into a syntax tree and only permits arithmetic nodes; it never passes model-generated text to eval(), which would let a prompt-injected string run arbitrary code. Install anthropic and set ANTHROPIC_API_KEY and MODEL (any current Claude model id). 

import ast, json, operator, os
import anthropic

OPS = {ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul,
       ast.Div: operator.truediv, ast.Pow: operator.pow, ast.USub: operator.neg}

def safe_calc(expr: str) -> float:
    def walk(node):
        if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
            return node.value
        if isinstance(node, ast.BinOp) and type(node.op) in OPS:
            return OPS[type(node.op)](walk(node.left), walk(node.right))
        if isinstance(node, ast.UnaryOp) and type(node.op) in OPS:
            return OPS[type(node.op)](walk(node.operand))
        raise ValueError("unsupported expression")
    return walk(ast.parse(expr, mode="eval").body)

NOTES = []
def run_tool(name, args):
    try:
        if name == "calculate":
            return str(safe_calc(args["expression"]))
        if name == "save_note":
            NOTES.append(args["text"])
            return f"saved ({len(NOTES)} notes)"
        return f"error: unknown tool {name}"
    except Exception as exc:          # report failures to the model, don't crash
        return f"error: {exc}"

TOOLS = [
    {"name": "calculate",
     "description": "Evaluate an arithmetic expression using + - * / ** and parentheses, e.g. '(12 + 8) * 1.5'.",
     "input_schema": {"type": "object",
                      "properties": {"expression": {"type": "string"}},
                      "required": ["expression"]}},
    {"name": "save_note",
     "description": "Store one short finding to include in the final report.",
     "input_schema": {"type": "object",
                      "properties": {"text": {"type": "string"}},
                      "required": ["text"]}},
]

client = anthropic.Anthropic()
MAX_ITERATIONS = 8

def run_agent(goal: str) -> str:
    messages = [{"role": "user", "content": goal}]
    for _ in range(MAX_ITERATIONS):                      # hard stop
        resp = client.messages.create(model=os.environ["MODEL"], max_tokens=1024,
                                      tools=TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":               # model gave a final answer
            return "".join(b.text for b in resp.content if b.type == "text")
        results = [{"type": "tool_result", "tool_use_id": b.id,
                    "content": run_tool(b.name, b.input)}
                   for b in resp.content if b.type == "tool_use"]
        messages.append({"role": "user", "content": results})
    return "Stopped: iteration limit reached."

if __name__ == "__main__":
    print(run_agent("If a team of 7 ships 3.5 features each per quarter, "
                    "how many per year? Save the result as a note, then summarise."))
What beginners get wrong

The three mistakes to avoid early

  • Over-agentic design: most production tasks only need level 2–3 autonomy, not a fully autonomous agent. Start with the simplest design that could work.
  • No stopping conditions: always set a maximum step limit. An agent without a stopping condition will loop indefinitely on ambiguous tasks or LLM errors.
  • Vague tool descriptions: the LLM reads your tool descriptions at inference time. Vague descriptions ("get data") cause wrong tool selection. Precise descriptions ("search the web and return the top 3 results as a list of dicts with title and url keys") get correct, reliable invocations.
Beyond the first three

Production pitfalls to design for

  • Infinite loops: beyond a step cap (the MAX_ITERATIONS above), watch for the agent repeating the same tool call with the same arguments and abort when it does.
  • Prompt injection: any text a tool fetches — a web page, an email, a PDF — can contain instructions aimed at your agent. Treat tool output as untrusted data, give tools the least privilege they need, and require human approval before irreversible actions.
  • Ignoring cost: every loop turn resends the growing context. Log tokens per run, set a budget, use a smaller model for easy steps, and trim old observations.
  • Missing error handling: tools time out, return junk, or throw. Catch the exception and return it as the observation (as run_tool does) so the model can retry or change approach, rather than crashing the run.
Keep building

Project ideas after your first agent

  • Personal assistant: calendar, email and notes tools, with confirmation before sending anything.
  • Coding agent: read files, run tests, propose a patch, and loop until the tests pass.
  • Research agent: search, read, and compile a cited brief on a topic.
  • Data analysis agent: load a CSV, write and run queries or plots, explain what it found.
  • Multi-agent pipeline: a planner, a researcher and a writer-reviewer passing work along.

Key Takeaway

An agent is a loop: the LLM thinks, calls a tool, observes the result, and repeats until the task is done. Start with a single tool in smolagents or raw API calls. Add tools and complexity only when you have demonstrated you need them. Write tool descriptions as if briefing a junior engineer — that description is literally what the model reads to decide whether and how to use the tool.
