12 Data Architecture Patterns Every Data Engineer Should Master in 2026

From Data Warehouse to Data Mesh — the 12 patterns that govern how modern data platforms are structured. Each pattern explained with its core trade-off, when to use it, and a JavaScript/SQL example that makes the abstract concrete.

Architecture patterns — not tool choices — determine a data platform's long-term success. Choosing Databricks vs Snowflake matters far less than choosing whether your platform should be a warehouse, a lakehouse, or a mesh. The tool executes the pattern; the pattern is the decision.

Core idea: Three questions organise all 12 patterns. Where does data live? (Warehouse, Lake, Lakehouse). How is it refined? (Medallion, Data Vault). How is it processed? (Lambda, Kappa, Event-Driven, and the rest).

Story · The wrong pattern at scale

A logistics company built a Lambda Architecture — separate batch and streaming paths for their shipment events. For two years it worked fine. Then the batch pipeline grew to 8-hour lag, and stakeholders wanted real-time shipment tracking. Maintaining two codebases for the same logic became unsustainable. They migrated to Kappa — one streaming path, batch jobs replaced by reprocessing from stored event log. They paid a migration cost that good upfront architecture selection would have avoided.

The 12 patterns

Organised by the question they answer

Where does data live?

1. Data Warehouse

Structured, schema-on-write storage optimised for analytics queries. SQL-first. Enforces data quality at ingestion time.

Use when: data is structured, schema is stable, BI/SQL analytics is primary use case. Tools: Snowflake, BigQuery, Redshift.

2. Data Lake

Raw, schema-on-read storage for any data format (CSV, JSON, Parquet, images, logs). Store first, structure later.

Use when: data formats are diverse/unknown, ML training data, long-term archive. Tools: S3, Azure Data Lake, GCS.

3. Lakehouse

Combines the flexibility of a data lake with the ACID transactions and performance of a warehouse. One storage layer for both analytics and ML.

Use when: you need both BI analytics and ML on the same data without duplication. Tools: Databricks Delta Lake, Apache Iceberg, Hudi.

How is data refined?

4. Medallion Architecture

Three-layer pipeline: Bronze (raw ingestion) → Silver (cleaned, deduplicated) → Gold (business-aggregated, query-ready). Each layer adds quality.

Use when: you need incremental quality gates and clear data lineage. Dominant pattern in Databricks/Delta ecosystems.

5. Data Vault

Historised, auditable modelling approach. Hubs (business keys), Links (relationships), Satellites (attributes with history). Never deletes, always appends.

Use when: regulatory requirements demand full history, or business keys change independently of attributes (finance, pharma).

How is data processed?

6. Lambda Architecture

Two parallel paths: batch layer (complete but slow) and speed layer (fast but approximate). Query layer merges both views.

Use when: you need both historical completeness and real-time freshness. Warning: maintaining two codebases for the same logic is expensive.

7. Kappa Architecture

Streaming-only — one code path. "Batch" queries are just streaming jobs over a stored event log (e.g., reprocess from Kafka day 0). Simpler than Lambda.

Use when: your batch jobs are just slow stream processing in disguise. Better operational simplicity than Lambda at the cost of reprocessing cost.

8. Event-Driven Architecture

All data changes emit events. Consumers subscribe and react asynchronously. No polling, no tight coupling between producers and consumers.

Use when: you need decoupled real-time data flows. Tools: Kafka, Flink, Kinesis.

9. Data Mesh

Decentralised, domain-oriented data ownership. Each domain team owns their data as a product — publishes it with SLAs, schema contracts, and documentation. Central governance platform, federated execution.

Use when: a central data team is a bottleneck at scale. Requires significant organisational maturity.

10. CDC (Change Data Capture)

Capture every insert/update/delete from a source DB as a stream of change events. Avoids full-table scans. Five techniques: log-based (most reliable), query-based, timestamp-based, trigger-based, snapshot.

Use when: syncing operational DB to analytics without ETL lag. Tools: Debezium, Airbyte, Fivetran.

11. Reverse ETL

Move data FROM your warehouse INTO operational systems (CRM, marketing tools, customer support). Activates analytics data in production workflows.

Use when: BI insights need to trigger actions in Salesforce, HubSpot, or custom APIs. Tools: Census, Hightouch.

12. Federated Query

Query data across multiple databases/services without moving it. The query engine pushes computation down to each source and merges results.

Use when: data must stay in multiple systems for compliance or ownership reasons. Tools: Trino, Athena Federated, Spark.

Most common mistake: Building a Data Lake when you need a Data Warehouse. Lakes are not cheaper warehouses — they trade schema enforcement for flexibility. If your data is structured and your users are BI analysts, a lake forces them to do work they shouldn't have to do.
JavaScript Example

Medallion pipeline in Node.js (Bronze → Silver → Gold)

JavaScript Example 
// Simplified Medallion pipeline for order events
// Bronze: raw ingestion as-is
async function ingestToBronze(rawEvents, db) {
  const rows = rawEvents.map((event) => ({
    raw_json: JSON.stringify(event),
    ingested_at: new Date().toISOString(),
    source: event._source ?? "api",
  }));
  await db.query(
    "INSERT INTO bronze_orders (raw_json, ingested_at, source) SELECT * FROM json_populate_recordset(null::bronze_orders, $1)",
    [JSON.stringify(rows)]
  );
}

// Silver: clean, deduplicate, validate
async function bronzeToSilver(db) {
  await db.query(`
    INSERT INTO silver_orders (order_id, user_id, amount, status, created_at)
    SELECT DISTINCT ON (order_id)
      (raw_json->>'id')::uuid          AS order_id,
      (raw_json->>'userId')::uuid      AS user_id,
      (raw_json->>'amount')::numeric   AS amount,
      raw_json->>'status'              AS status,
      (raw_json->>'createdAt')::timestamptz AS created_at
    FROM bronze_orders
    WHERE raw_json->>'id' IS NOT NULL       -- drop malformed rows
      AND (raw_json->>'amount')::numeric > 0 -- drop zero-amount orders
    ON CONFLICT (order_id) DO UPDATE SET
      status = EXCLUDED.status,
      amount = EXCLUDED.amount
  `);
}

// Gold: business aggregate — daily revenue by user segment
async function silverToGold(db) {
  await db.query(`
    INSERT INTO gold_daily_revenue (date, segment, total_revenue, order_count)
    SELECT
      DATE(so.created_at)     AS date,
      u.segment,
      SUM(so.amount)          AS total_revenue,
      COUNT(*)                AS order_count
    FROM silver_orders so
    JOIN users u ON u.id = so.user_id
    WHERE so.status = 'completed'
    GROUP BY DATE(so.created_at), u.segment
    ON CONFLICT (date, segment) DO UPDATE SET
      total_revenue = EXCLUDED.total_revenue,
      order_count = EXCLUDED.order_count
  `);
}

// Kappa-style: reprocess from event store on schema change
async function reprocessFromEventLog(db, fromDate) {
  const events = await db.query(
    "SELECT raw_json FROM bronze_orders WHERE ingested_at >= $1 ORDER BY ingested_at",
    [fromDate]
  );
  await db.query("TRUNCATE silver_orders, gold_daily_revenue");
  await bronzeToSilver(db);
  await silverToGold(db);
  console.log(`Reprocessed ${events.rowCount} events from ${fromDate}`);
}

Key Takeaway

Data architecture patterns are tools for answering three questions: where data lives, how it's refined, and how it flows. The Medallion pattern is currently the most universally applicable — it works with any storage layer and gives you clear quality gates. Lambda Architecture is being superseded by Kappa as streaming matures. Data Mesh is the right answer for large organisations where centralised teams are the bottleneck. Know all 12 patterns, but choose based on your team's maturity and your data's nature — not based on what the biggest tech companies use.
