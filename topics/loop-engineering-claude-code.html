Loop Engineering: Stop Prompting Claude, Start Automating

The shift from reactive prompting to autonomous loop engineering — where Claude finds work, acts on it, and escalates only when genuinely blocked. Covers Claude Code, Codex, and Cursor approaches, the "inspector problem" nobody ships, and how to build durable agentic loops in JavaScript.

Most people use Claude Code like a very fast intern: ask, receive, review, ask again. That's not agentic programming — it's manual programming with autocomplete. Loop engineering replaces the cycle of "prompt → output → prompt again" with an autonomous agent that decides what to do next, executes, checks its own work, and surfaces to you only when it's genuinely stuck.

Core idea: The loop itself — receive task, act, evaluate, repeat — is now commoditized across Claude Code, Codex, and Cursor. The only differentiating part is the exit condition: the inspector that decides "done." No tool ships that for you. It's yours to design.

Story · Why manual prompting is a bottleneck

A developer spent her morning running Claude Code in a rhythm: write feature → prompt Claude to write tests → prompt Claude to fix one failing test → prompt Claude to update docs → next feature. Each prompt took 30 seconds of attention. Multiply by 40 rounds per day and she was spending 20 minutes just switching context between prompts.

Loop engineering collapsed that. She defined a task manifest, set an acceptance criterion ("all tests green, docs updated"), and let Claude work the loop. She checked back when her coffee was ready. This isn't science fiction — it's a configuration change.

The anatomy of a loop

What every agentic loop contains

┌─────────────────────────────────────────────────────┐ │ LOOP ENGINEERING CYCLE │ ├─────────────────────────────────────────────────────┤ │ 1. RECEIVE task / objective / constraint │ │ 2. ACT edit code, run tests, call tools │ │ 3. EVALUATE did the output meet the criterion? │ │ 4. BRANCH yes → done │ no → loop │ stuck → escalate│ └─────────────────────────────────────────────────────┘

Step 3 — evaluation — is where all three tools differ and where most loops break. Claude Code evaluates via test output in the terminal. Codex evaluates in a cloud sandbox. Cursor evaluates in the IDE. But the criterion for "done" is something you set, not something the tool provides.

Tool comparison

Claude Code vs Codex vs Cursor: How Each Does Loops

Claude Code

  • Terminal-native
  • Single claude command entry point
  • Reads files, runs bash, loops until tests pass
  • Exit condition: you define in CLAUDE.md
  • Best for: repo-wide refactors, backend automation

Codex

  • Cloud-sandboxed execution
  • Isolated environment per task
  • No local state side-effects during run
  • Exit condition: CI pass / diff review
  • Best for: safe autonomous tasks, PRs from spec

Cursor

  • IDE-embedded loop
  • Background agents in editor context
  • Visual diff inline
  • Exit condition: accept/reject in UI
  • Best for: feature development with visual feedback
The inspector insight: All three tools gave away the loop because it's a commodity. The part no vendor ships — "is this output actually correct?" — is the only part with competitive value. Your acceptance function is your moat.
The naming trap

Context Engineering → Harness Engineering → Loop Engineering

The AI tooling world renames the same underlying skill every six months. Context engineering became harness engineering, which is now loop engineering. The underlying skill hasn't changed: how well can you define "done" for an AI agent, and how robustly can you detect deviation from it?

Watch out: Learning the tool names is not the same as learning the skill. Someone who can define a precise acceptance criterion for any task is worth 10x someone who knows three framework names.
JavaScript Example

Building a durable agentic loop with an inspector function

JavaScript Example 
import Anthropic from "@anthropic-ai/sdk";
import { execSync } from "child_process";
import fs from "fs";

const client = new Anthropic();

// The inspector — the only part you must write yourself
function inspect(taskOutput) {
  // Run tests and check for zero failures
  try {
    const result = execSync("npm test -- --reporter=json 2>&1", {
      encoding: "utf8",
    });
    const report = JSON.parse(result);
    if (report.numFailedTests === 0) {
      return { done: true, reason: `All ${report.numPassedTests} tests pass` };
    }
    return {
      done: false,
      reason: `${report.numFailedTests} test(s) failing`,
      failures: report.testResults?.flatMap((r) => r.testResults || []).filter((t) => t.status === "failed").map((t) => t.fullName),
    };
  } catch (e) {
    return { done: false, reason: "Test runner error", detail: e.message };
  }
}

// The loop
async function runAgenticLoop(task, maxTurns = 10) {
  const messages = [{ role: "user", content: task }];

  for (let turn = 0; turn < maxTurns; turn++) {
    const response = await client.messages.create({
      model: "claude-opus-4-8",
      max_tokens: 4096,
      system:
        "You are an autonomous coding agent. Edit files using your tools, run tests, and iterate until all tests pass. When you believe you are done, say DONE.",
      messages,
    });

    const assistantText = response.content
      .filter((b) => b.type === "text")
      .map((b) => b.text)
      .join("");

    messages.push({ role: "assistant", content: assistantText });

    // Run the inspector after each turn
    const verdict = inspect(assistantText);
    console.log(`Turn ${turn + 1} — ${verdict.done ? "✓ DONE" : "✗ " + verdict.reason}`);

    if (verdict.done) return { success: true, turns: turn + 1 };

    // Feed failures back into the loop as context
    messages.push({
      role: "user",
      content: `Inspector result: ${JSON.stringify(verdict, null, 2)}\n\nContinue fixing.`,
    });
  }

  return { success: false, reason: "Max turns reached" };
}

// Usage
runAgenticLoop(
  "Refactor auth.js to use async/await instead of callbacks. All existing tests must still pass."
).then(console.log);

The key insight: the inspector runs after every turn, not just at the end. Feeding the failure details back into the conversation as a user message gives Claude precise error context for the next iteration — much better than letting it guess what went wrong.

Practical checklist

How to apply loop engineering today

  • Write your acceptance criterion before writing your task prompt — if you can't describe "done", neither can Claude.
  • Start with tests as the inspector: zero test failures is the most objective signal you have.
  • Cap your loops at 5–10 turns and escalate to human review on breach — infinite loops waste tokens and hide real design problems.
  • Feed the inspector's output back verbatim as the next user message — precise error text beats generic "keep trying".
  • Log each turn's verdict to a file so you can audit why a loop stalled.
  • Use claude --headless with a task file for CI integration — the loop runs unattended on every PR.
FAQ

Common questions

Isn't this just an agentic loop with a different name? Exactly. The name "loop engineering" is new; the pattern is the ReAct loop from 2022. What's new is that mainstream tools now ship it by default, so you can build on it without a framework.

What if the inspector itself is wrong? This is the real design challenge. A bad inspector (tests that pass without verifying the actual requirement) defeats the whole system. Invest in your tests before investing in your loops.

Should I use Claude Code, Codex, or Cursor? For server-side/CLI work with precise acceptance criteria: Claude Code. For safe, isolated task execution from a spec: Codex. For feature development where visual diff matters: Cursor. All three can be configured to run unattended.

Key Takeaway

The agentic coding loop — receive, act, evaluate, repeat — is now a commodity baked into every major AI coding tool. What isn't commoditized is the inspector: the function that decides whether output actually meets your standard. Master that one thing — how to express "done" as a precise, machine-readable criterion — and you can delegate entire workflows to Claude, Codex, or Cursor and get back only what genuinely needs your judgment.
