Low-Level Design Roadmap: From Zero to Confident in 2026

A complete 8-week structured roadmap — from OOP fundamentals through every SOLID principle, all 23 Gang-of-Four design patterns, and 10 canonical LLD interview problems — with runnable JavaScript examples and the exact step-by-step interview approach used by engineers landing senior roles at top-tier product companies.

Domain: System Design · Architecture · OOP · Design Patterns Credit: lets-code-future · Medium Published: 2026-09-03

Low-Level Design is the craft layer of software engineering — where good intentions become maintainable code. Yet most engineers neglect it in favour of algorithmic problem-solving, only to discover in interviews and production that the ability to design a clean class hierarchy is what separates competent from exceptional engineers.

What this roadmap gives you: A week-by-week sequence from absolute fundamentals through interview-ready LLD fluency. Follow it linearly. The phases compound: you cannot apply design patterns correctly without internalising SOLID, and you cannot solve LLD interview problems without having the patterns in muscle memory.

Section 1 — What is LLD vs HLD?

Foundation · Understanding the Difference

High-Level Design (HLD)

HLD answers: how do the pieces of the system fit together? It operates at the architecture layer — deciding which services exist, how they communicate (REST, gRPC, message queues), where data lives, and how the system scales. HLD produces system diagrams with load balancers, databases, CDNs, microservices, and cache layers.

  • Service decomposition and boundaries
  • API contracts between services
  • Database selection (SQL vs. NoSQL, sharding strategy)
  • Caching strategy (Redis, Memcached, CDN)
  • Scalability, availability, and fault tolerance
  • CAP theorem trade-offs
  • Infrastructure: cloud provider, container orchestration, CI/CD

Low-Level Design (LLD)

LLD answers: how do we actually code this? It operates at the code design layer — deciding which classes and interfaces exist, what methods they expose, how they collaborate, and what data structures they use internally. LLD produces class diagrams, sequence diagrams, and ultimately well-structured code.

  • Class hierarchy and inheritance structure
  • Interface definitions and contracts
  • Method signatures and responsibilities
  • Data structures (which map/set/queue to use and why)
  • Design patterns that govern collaboration between objects
  • Error handling, edge cases, and validation
  • Extensibility: how new features plug in without rewriting existing code

Why LLD Matters in Interviews

Every company at the L5+ level expects LLD fluency. Here is what the interviewer is actually evaluating when they ask you to design a Parking Lot or a Library Management System:

Skill Being Tested What the Interviewer Observes
OOP thinking Do you model the domain with the right classes? Do you identify abstractions?
SOLID principles Does each class have one job? Do you extend rather than modify?
Design pattern recognition Do you apply the right pattern without being asked?
Interface-first thinking Do you define contracts before implementations?
Edge case handling Do you identify concurrent access, null inputs, and boundary conditions?
Communication Can you explain your design choices with clear reasoning?

Key insight: LLD interviews test OOP thinking and clean code discipline — not memorised solutions. An interviewer who gives you a Parking Lot problem has seen a hundred correct Parking Lot solutions. They are watching how you think, not whether you remember the answer.

Phase 1 (Weeks 1–2) — OOP Fundamentals

The Language of Objects

Object-Oriented Programming is not a feature of a language — it is a way of thinking about programs as collaborating objects with state and behaviour. You must internalise the four pillars before any design pattern will make sense.

1. Encapsulation

Encapsulation means bundling state (fields) and behaviour (methods) together, and controlling access to the state. The object owns its internal data; outside code interacts only through the public interface.

Without encapsulation: any piece of code can corrupt your object's state. With encapsulation: the object is the single source of truth for its own consistency.

JavaScript Example — Encapsulation 
// BAD: no encapsulation — balance is public
class BankAccountBad {
  constructor(owner, balance) {
    this.owner = owner;
    this.balance = balance; // anyone can set this.balance = -9999
  }
}

// GOOD: encapsulation via private fields (ES2022 #-syntax)
class BankAccount {
  #owner;
  #balance;

  constructor(owner, initialBalance) {
    if (initialBalance < 0) throw new Error('Initial balance cannot be negative');
    this.#owner = owner;
    this.#balance = initialBalance;
  }

  deposit(amount) {
    if (amount <= 0) throw new Error('Deposit amount must be positive');
    this.#balance += amount;
  }

  withdraw(amount) {
    if (amount <= 0) throw new Error('Withdrawal amount must be positive');
    if (amount > this.#balance) throw new Error('Insufficient funds');
    this.#balance -= amount;
  }

  get balance() { return this.#balance; }
  get owner()   { return this.#owner;   }

  toString() {
    return `BankAccount[${this.#owner}]: $${this.#balance.toFixed(2)}`;
  }
}

const acc = new BankAccount('Alice', 1000);
acc.deposit(500);
acc.withdraw(200);
console.log(acc.balance); // 1300
// acc.#balance = -9999;  // SyntaxError — private field inaccessible

2. Abstraction

Abstraction means exposing what an object does without exposing how it does it. Callers interact with simplified interfaces; implementation details are hidden. In practice this means: define a clean public API, keep internals private, and never let implementation detail leak through the interface.

3. Inheritance

Inheritance lets a child class acquire the behaviour of a parent, allowing code reuse across related types. The key rule: inheritance should model an is-a relationship. A SavingsAccount is-a BankAccount. A Car is-a Vehicle. If you cannot say "X is-a Y" clearly, you likely need composition instead.

JavaScript Example — Inheritance & Polymorphism 
class Shape {
  // Abstract method — subclasses must override
  area() {
    throw new Error(`${this.constructor.name}.area() not implemented`);
  }

  describe() {
    // Template method: structure fixed, details delegated to subclass
    return `${this.constructor.name} with area ${this.area().toFixed(2)}`;
  }
}

class Circle extends Shape {
  constructor(radius) {
    super();
    this.radius = radius;
  }
  area() { return Math.PI * this.radius ** 2; }
}

class Rectangle extends Shape {
  constructor(width, height) {
    super();
    this.width  = width;
    this.height = height;
  }
  area() { return this.width * this.height; }
}

class Triangle extends Shape {
  constructor(base, height) {
    super();
    this.base   = base;
    this.height = height;
  }
  area() { return 0.5 * this.base * this.height; }
}

// Polymorphism: same call, different behaviour based on runtime type
const shapes = [new Circle(5), new Rectangle(4, 6), new Triangle(3, 8)];
shapes.forEach(s => console.log(s.describe()));
// Circle with area 78.54
// Rectangle with area 24.00
// Triangle with area 12.00

// Total area without knowing shape types — open/closed principle preview
const totalArea = shapes.reduce((sum, s) => sum + s.area(), 0);
console.log(`Total area: ${totalArea.toFixed(2)}`);

4. Polymorphism

Polymorphism (many forms) allows a reference of a parent type to hold a child-type object and invoke child-specific behaviour at runtime. This is the mechanism that makes design patterns work: a Strategy reference can hold any concrete strategy; a Shape reference can hold any concrete shape. Code that works with abstractions works with all current and future implementations.

OOP Phase Checklist

  • Can you model a bank account, a vehicle, and a user hierarchy from scratch?
  • Do you default to private fields and expose only what callers need?
  • Can you identify when to use inheritance vs composition?
  • Do you understand method overriding and how runtime dispatch works?
  • Can you explain what "programming to an interface" means?

Phase 2 (Weeks 3–4) — SOLID Principles

The Five Laws of Maintainable Code

SOLID is an acronym for five principles formulated by Robert C. Martin (Uncle Bob) that together produce code that is easy to extend, understand, and maintain. Violating any one of them has a predictable consequence: code that becomes progressively harder to change.

S — Single Responsibility Principle (SRP)

A class should have one and only one reason to change.

"Reason to change" is a business stakeholder, not a feature. If both the billing team and the authentication team would ask you to change the same class, that class has two responsibilities. Split it.

Symptom of violation: "God classes" — one class that handles user authentication, sends emails, formats reports, and manages database connections. When the email format changes, you risk breaking authentication. That's the cost of mixing responsibilities.

JavaScript Example — SRP 
// VIOLATION: UserManager does too many things
class UserManagerBad {
  constructor(db) { this.db = db; }

  saveUser(user)          { /* DB logic */       }
  validateEmail(email)    { /* Validation logic */ }
  sendWelcomeEmail(user)  { /* Email logic */     }
  generateReport(users)   { /* Report logic */    }
  hashPassword(pwd)       { /* Crypto logic */    }
}
// Any of 5 different concerns changing requires touching this class.

// ── GOOD: each class has one responsibility ───────────────────────────────

class UserRepository {
  constructor(db) { this.db = db; }
  save(user) { return this.db.insert('users', user); }
  findById(id) { return this.db.query('SELECT * FROM users WHERE id=?', [id]); }
}

class UserValidator {
  validateEmail(email) {
    return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email);
  }
  validatePassword(pwd) {
    return pwd.length >= 8 && /[A-Z]/.test(pwd) && /\d/.test(pwd);
  }
}

class EmailService {
  sendWelcomeEmail(user) {
    // delegates to SMTP client — email concern only
    console.log(`Welcome email sent to ${user.email}`);
  }
}

class PasswordHasher {
  async hash(password) {
    // uses crypto — password concern only
    const encoder = new TextEncoder();
    const data = encoder.encode(password);
    const hashBuffer = await crypto.subtle.digest('SHA-256', data);
    return Array.from(new Uint8Array(hashBuffer))
      .map(b => b.toString(16).padStart(2, '0')).join('');
  }
}

// UserService orchestrates, but doesn't implement any of these concerns
class UserService {
  constructor(repo, validator, emailService, hasher) {
    this.repo         = repo;
    this.validator    = validator;
    this.emailService = emailService;
    this.hasher       = hasher;
  }

  async register(userData) {
    if (!this.validator.validateEmail(userData.email)) throw new Error('Invalid email');
    if (!this.validator.validatePassword(userData.password)) throw new Error('Weak password');
    const user = { ...userData, password: await this.hasher.hash(userData.password) };
    await this.repo.save(user);
    this.emailService.sendWelcomeEmail(user);
    return user;
  }
}

O — Open/Closed Principle (OCP)

Software entities should be open for extension, but closed for modification.

Once a class is tested and working, adding new behaviour should not require editing it. New behaviour is added by creating new classes that extend existing abstractions. If adding a new payment method requires editing a PaymentProcessor class, that class is not closed for modification.

JavaScript Example — OCP 
// VIOLATION: adding a new discount type requires modifying this function
function calculateDiscountBad(type, price) {
  if (type === 'student') return price * 0.8;
  if (type === 'senior')  return price * 0.75;
  if (type === 'member')  return price * 0.9;
  // Every new discount = edit this function = risk of regression
  return price;
}

// ── GOOD: new discounts extend without modifying ──────────────────────────

class DiscountStrategy {
  apply(price) { throw new Error('apply() not implemented'); }
}

class StudentDiscount extends DiscountStrategy {
  apply(price) { return price * 0.80; }
}

class SeniorDiscount extends DiscountStrategy {
  apply(price) { return price * 0.75; }
}

class MemberDiscount extends DiscountStrategy {
  apply(price) { return price * 0.90; }
}

// New requirement: flash sale. Add a class — nothing else changes.
class FlashSaleDiscount extends DiscountStrategy {
  constructor(pct) { super(); this.pct = pct; }
  apply(price) { return price * (1 - this.pct / 100); }
}

class PriceCalculator {
  constructor(discount) { this.discount = discount; } // Inject the strategy
  calculateFinal(price) { return this.discount.apply(price); }
}

const calc = new PriceCalculator(new FlashSaleDiscount(30));
console.log(calc.calculateFinal(100)); // 70 — no PriceCalculator code changed

L — Liskov Substitution Principle (LSP)

Subtypes must be substitutable for their base types without altering correctness.

If you have code that works with a Bird and you swap in a Penguin (a subtype), the code must still work. If Penguin overrides fly() to throw an exception, callers that call bird.fly() will break — LSP violated. The fix: restructure the hierarchy so that Penguin is not a subtype of a FlyingBird.

JavaScript Example — LSP 
// VIOLATION: Square extends Rectangle but breaks invariants
class Rectangle {
  constructor(w, h) { this.width = w; this.height = h; }
  setWidth(w)  { this.width  = w; }
  setHeight(h) { this.height = h; }
  area()       { return this.width * this.height; }
}

class SquareBad extends Rectangle {
  setWidth(w)  { this.width = this.height = w; } // Breaks Rectangle contract
  setHeight(h) { this.width = this.height = h; } // A rectangle where setWidth changes height!
}

// Code expecting Rectangle behaviour breaks with SquareBad:
function stretchWidth(rect) {
  rect.setWidth(10);
  console.assert(rect.area() === rect.height * 10, 'Area invariant broken!');
  // Fails for SquareBad when height was 5: area=100, expected 50
}

// ── GOOD: separate hierarchy that respects LSP ────────────────────────────
class Shape2 { area() { throw new Error('Not implemented'); } }

class Rect extends Shape2 {
  constructor(w, h) { super(); this.#w = w; this.#h = h; }
  #w; #h;
  withWidth(w)  { return new Rect(w, this.#h); } // Immutable — no mutation surprises
  withHeight(h) { return new Rect(this.#w, h); }
  area()        { return this.#w * this.#h; }
}

class Square extends Shape2 {
  constructor(s) { super(); this.#s = s; }
  #s;
  withSide(s) { return new Square(s); }
  area()      { return this.#s ** 2; }
}
// Square never promises to behave like a mutable Rectangle — no substitution risk

I — Interface Segregation Principle (ISP)

No client should be forced to depend on methods it does not use.

Fat interfaces that bundle many unrelated methods force implementing classes to provide stub implementations for methods they don't need. Split fat interfaces into focused, role-specific ones.

JavaScript Example — ISP 
// VIOLATION: fat "Worker" interface forces all workers to implement all methods
class WorkerBad {
  work()   { throw new Error('Not implemented'); }
  eat()    { throw new Error('Not implemented'); }
  sleep()  { throw new Error('Not implemented'); }
  recharge() { throw new Error('Not implemented'); }
}

class RobotBad extends WorkerBad {
  work()    { console.log('Robot working'); }
  eat()     { throw new Error('Robots do not eat!'); } // Forced stub — ISP violation
  sleep()   { throw new Error('Robots do not sleep!'); }
  recharge() { console.log('Robot recharging'); }
}

// ── GOOD: segregated interfaces ───────────────────────────────────────────
// In JavaScript we simulate interfaces via mixins / duck typing / documentation

const Workable   = (superclass) => class extends superclass { work()     {} };
const Feedable   = (superclass) => class extends superclass { eat()      {} };
const Sleepable  = (superclass) => class extends superclass { sleep()    {} };
const Rechargeable = (superclass) => class extends superclass { recharge() {} };

class Base {}

class Human extends Feedable(Sleepable(Workable(Base))) {
  work()   { console.log('Human working'); }
  eat()    { console.log('Human eating');  }
  sleep()  { console.log('Human sleeping'); }
}

class Robot extends Rechargeable(Workable(Base)) {
  work()     { console.log('Robot working');    }
  recharge() { console.log('Robot recharging'); }
  // No eat() or sleep() — Robot is not forced to stub them
}

const team = [new Human(), new Robot()];
team.forEach(member => member.work()); // Works for both
// team.forEach(member => member.eat()); // Would fail for Robot — by design

D — Dependency Inversion Principle (DIP)

High-level modules should not depend on low-level modules. Both should depend on abstractions. Abstractions should not depend on details. Details should depend on abstractions.

DIP is what makes Dependency Injection (DI) work. Instead of a class creating its own database connection, email client, or logger, it receives them as constructor parameters typed to interfaces. This makes the class testable (swap in a mock), flexible (swap in a different implementation), and decoupled from infrastructure.

JavaScript Example — DIP 
// VIOLATION: OrderService directly instantiates MySQLDatabase
class OrderServiceBad {
  constructor() {
    this.db = new MySQLDatabase(); // Hard-coded low-level dependency
    this.notifier = new SMSNotifier(); // Hard-coded low-level dependency
  }
  placeOrder(order) {
    this.db.save(order);
    this.notifier.send(order.customerId, 'Order placed');
  }
}

// ── GOOD: depend on abstractions, inject concretions ─────────────────────

// "Interfaces" (abstractions)
class OrderRepository {
  save(order)     { throw new Error('Not implemented'); }
  findById(id)    { throw new Error('Not implemented'); }
}
class NotificationService {
  send(userId, message) { throw new Error('Not implemented'); }
}

// Concrete low-level implementations
class MySQLOrderRepository extends OrderRepository {
  save(order)  { console.log('Saving to MySQL:', order.id); }
  findById(id) { return { id, items: [] }; /* MySQL query */ }
}

class InMemoryOrderRepository extends OrderRepository {
  #store = new Map();
  save(order)  { this.#store.set(order.id, order); }
  findById(id) { return this.#store.get(id); }
}

class EmailNotifier extends NotificationService {
  send(userId, msg) { console.log(`Email to ${userId}: ${msg}`); }
}
class SMSNotifier extends NotificationService {
  send(userId, msg) { console.log(`SMS to ${userId}: ${msg}`); }
}

// High-level module: depends only on abstractions
class OrderService {
  constructor(repo, notifier) { // Injected
    if (!(repo instanceof OrderRepository)) throw new Error('Invalid repo');
    this.repo     = repo;
    this.notifier = notifier;
  }
  placeOrder(order) {
    this.repo.save(order);
    this.notifier.send(order.customerId, `Order ${order.id} confirmed`);
  }
}

// Compose at the application boundary — swap without touching OrderService
const prodService  = new OrderService(new MySQLOrderRepository(), new SMSNotifier());
const testService  = new OrderService(new InMemoryOrderRepository(), new EmailNotifier());

prodService.placeOrder({ id: 'ORD-001', customerId: 'USR-42', items: ['widget'] });

Phase 3 (Weeks 5–6) — Design Patterns

Gang of Four · 23 Patterns · 3 Categories

Design patterns are reusable solutions to recurring object-oriented design problems. The Gang of Four (Gamma, Helm, Johnson, Vlissides) catalogued 23 patterns in their 1994 book. Every senior engineer is expected to recognise these patterns in code and apply them by name in design conversations.

How to learn patterns: Do not memorise them. For each pattern, understand the problem it solves, the structure it creates, and the trade-offs it introduces. Then find it in code you use daily (e.g., the Observer pattern is EventEmitter; the Iterator pattern is for...of).

Creational Patterns (5)

Creational patterns abstract the object creation process, giving you control over what gets created, who creates it, how it gets created, and when it gets created.

PatternProblem It SolvesKey Mechanism
Singleton Need exactly one instance (config, logger, connection pool) Private constructor + static instance reference
Factory Method Caller wants an object but shouldn't know the concrete type Subclass decides which class to instantiate
Abstract Factory Need to create families of related objects without specifying classes Factory of factories — one interface per product family
Builder Complex object with many optional parameters Step-by-step construction; fluent API
Prototype Create new objects by cloning existing ones clone() method on each object
JavaScript Example — Singleton Pattern 
// Module-level Singleton using ES module caching
// File: config.js — imported once, same instance everywhere

class Config {
  static #instance = null;

  #settings = {};
  #initialized = false;

  constructor() {
    if (Config.#instance) {
      return Config.#instance; // Return existing instance
    }
    Config.#instance = this;
  }

  initialize(settings) {
    if (this.#initialized) throw new Error('Config already initialized');
    this.#settings = Object.freeze({ ...settings });
    this.#initialized = true;
    return this;
  }

  get(key) {
    if (!this.#initialized) throw new Error('Config not initialized');
    return this.#settings[key];
  }

  static getInstance() {
    if (!Config.#instance) Config.#instance = new Config();
    return Config.#instance;
  }
}

// Usage
Config.getInstance().initialize({ dbHost: 'localhost', port: 5432, env: 'production' });

// Anywhere in the codebase:
const host = Config.getInstance().get('dbHost'); // 'localhost'
const port = Config.getInstance().get('port');   // 5432

console.assert(Config.getInstance() === Config.getInstance(), 'Must be same instance');
console.log('Same instance:', Config.getInstance() === Config.getInstance()); // true
JavaScript Example — Builder Pattern 
// Builder: complex QueryBuilder
class Query {
  constructor({ table, conditions, columns, orderBy, limit, offset, joins }) {
    this.table      = table;
    this.conditions = conditions;
    this.columns    = columns;
    this.orderBy    = orderBy;
    this.limit      = limit;
    this.offset     = offset;
    this.joins      = joins;
  }

  toString() {
    const cols  = this.columns.length ? this.columns.join(', ') : '*';
    let sql = `SELECT ${cols} FROM ${this.table}`;
    if (this.joins.length) sql += ' ' + this.joins.join(' ');
    if (this.conditions.length) sql += ' WHERE ' + this.conditions.join(' AND ');
    if (this.orderBy) sql += ` ORDER BY ${this.orderBy}`;
    if (this.limit)   sql += ` LIMIT ${this.limit}`;
    if (this.offset)  sql += ` OFFSET ${this.offset}`;
    return sql;
  }
}

class QueryBuilder {
  #table;
  #conditions = [];
  #columns    = [];
  #orderBy    = null;
  #limit      = null;
  #offset     = null;
  #joins      = [];

  from(table)          { this.#table = table;              return this; }
  select(...cols)      { this.#columns.push(...cols);      return this; }
  where(condition)     { this.#conditions.push(condition); return this; }
  orderBy(col)         { this.#orderBy = col;              return this; }
  limit(n)             { this.#limit = n;                  return this; }
  offset(n)            { this.#offset = n;                 return this; }
  join(clause)         { this.#joins.push(clause);         return this; }

  build() {
    if (!this.#table) throw new Error('Table is required');
    return new Query({
      table:      this.#table,
      conditions: this.#conditions,
      columns:    this.#columns,
      orderBy:    this.#orderBy,
      limit:      this.#limit,
      offset:     this.#offset,
      joins:      this.#joins,
    });
  }
}

// Fluent API — only set what you need
const query = new QueryBuilder()
  .from('orders')
  .select('id', 'customer_id', 'total')
  .join('LEFT JOIN users u ON u.id = orders.customer_id')
  .where('total > 100')
  .where('status = "shipped"')
  .orderBy('created_at DESC')
  .limit(20)
  .offset(40)
  .build();

console.log(query.toString());
// SELECT id, customer_id, total FROM orders
//   LEFT JOIN users u ON u.id = orders.customer_id
//   WHERE total > 100 AND status = "shipped"
//   ORDER BY created_at DESC LIMIT 20 OFFSET 40
JavaScript Example — Factory Pattern 
// Factory Method: notification factory based on channel type

class Notification {
  send(recipient, message) {
    throw new Error(`${this.constructor.name}.send() not implemented`);
  }
}

class EmailNotification extends Notification {
  send(recipient, message) {
    console.log(`[EMAIL] To: ${recipient} | Subject: Notification | Body: ${message}`);
    // Real: use nodemailer / SendGrid SDK
  }
}

class SMSNotification extends Notification {
  send(recipient, message) {
    console.log(`[SMS] To: ${recipient} | ${message.slice(0, 160)}`);
    // Real: use Twilio SDK
  }
}

class PushNotification extends Notification {
  send(recipient, message) {
    console.log(`[PUSH] Device: ${recipient} | Payload: ${message}`);
    // Real: use Firebase Cloud Messaging
  }
}

class SlackNotification extends Notification {
  send(recipient, message) {
    console.log(`[SLACK] Channel: ${recipient} | ${message}`);
    // Real: use Slack Web API
  }
}

// Factory: caller asks for a type, factory handles instantiation
class NotificationFactory {
  static #registry = {
    email: EmailNotification,
    sms:   SMSNotification,
    push:  PushNotification,
    slack: SlackNotification,
  };

  static create(type) {
    const NotificationClass = this.#registry[type.toLowerCase()];
    if (!NotificationClass) throw new Error(`Unknown notification type: ${type}`);
    return new NotificationClass();
  }

  // Extension point: register new types without changing this class
  static register(type, NotificationClass) {
    this.#registry[type.toLowerCase()] = NotificationClass;
  }
}

// Usage: caller never imports concrete classes
['email', 'sms', 'push', 'slack'].forEach(type => {
  NotificationFactory.create(type).send('user123', 'Your order has shipped!');
});

Structural Patterns (7)

Structural patterns deal with how classes and objects are composed to form larger structures.

PatternProblem It SolvesKey Mechanism
Adapter Incompatible interfaces need to work together Wrapper translates one interface to another
Bridge Abstraction and implementation should vary independently Composition over inheritance; decouple via abstraction
Composite Treat individual objects and compositions uniformly (trees) Component interface; Leaf and Composite implement it
Decorator Add responsibilities to objects dynamically without subclassing Wraps the original, extends behaviour, delegates core calls
Facade Simplify a complex subsystem behind a single interface Facade class orchestrates subsystem calls
Flyweight Large numbers of fine-grained objects with shared state Separate intrinsic (shared) from extrinsic (unique) state
Proxy Control access to an object (lazy init, logging, auth, caching) Proxy implements same interface; delegates to real object
JavaScript Example — Decorator Pattern 
// Decorator: add middleware behaviour to a logger without subclassing

class Logger {
  log(level, message) {
    const ts = new Date().toISOString();
    console.log(`[${ts}] [${level.toUpperCase()}] ${message}`);
  }
}

// Base decorator — delegates everything to the wrapped logger
class LoggerDecorator {
  constructor(logger) { this.logger = logger; }
  log(level, message) { this.logger.log(level, message); }
}

// Concrete decorators add behaviour around the core
class TimestampDecorator extends LoggerDecorator {
  log(level, message) {
    super.log(level, `[${Date.now()}ms] ${message}`);
  }
}

class SamplingDecorator extends LoggerDecorator {
  constructor(logger, rate = 0.1) { super(logger); this.rate = rate; }
  log(level, message) {
    if (Math.random() < this.rate) super.log(level, message);
    // Drops ~90% of debug logs in production
  }
}

class RedactionDecorator extends LoggerDecorator {
  #patterns = [
    /\b\d{16}\b/g,                   // Credit card numbers
    /\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b/g, // Email addresses
    /\bpassword=\S+/gi,              // Password values
  ];

  log(level, message) {
    const redacted = this.#patterns.reduce(
      (msg, pattern) => msg.replace(pattern, '[REDACTED]'),
      message
    );
    super.log(level, redacted);
  }
}

class RateLimitDecorator extends LoggerDecorator {
  #counts = new Map();
  #windowMs;
  #maxPerWindow;

  constructor(logger, maxPerWindow = 100, windowMs = 60_000) {
    super(logger);
    this.#maxPerWindow = maxPerWindow;
    this.#windowMs     = windowMs;
  }

  log(level, message) {
    const now    = Date.now();
    const window = Math.floor(now / this.#windowMs);
    const key    = `${level}:${window}`;
    const count  = (this.#counts.get(key) ?? 0) + 1;
    this.#counts.set(key, count);
    if (count <= this.#maxPerWindow) super.log(level, message);
    else if (count === this.#maxPerWindow + 1) super.log('warn', 'Rate limit reached — suppressing logs');
  }
}

// Compose decorators — order matters (redaction before sampling, rate-limit outermost)
const productionLogger =
  new RateLimitDecorator(
    new SamplingDecorator(
      new RedactionDecorator(
        new TimestampDecorator(new Logger())
      ), 0.05  // 5% sampling for debug
    ), 500     // max 500 logs/minute
  );

productionLogger.log('info', 'User 4432 logged in from 192.168.1.1');
productionLogger.log('error', 'Payment failed for card 4111111111111111');
// → [REDACTED] replaces card number

JavaScript Example — Observer Pattern 
// Observer (EventEmitter): classic pub/sub for decoupled communication

class EventEmitter {
  #listeners = new Map();

  on(event, listener) {
    if (!this.#listeners.has(event)) this.#listeners.set(event, new Set());
    this.#listeners.get(event).add(listener);
    return () => this.off(event, listener); // Returns unsubscribe function
  }

  once(event, listener) {
    const wrapper = (...args) => {
      listener(...args);
      this.off(event, wrapper);
    };
    return this.on(event, wrapper);
  }

  off(event, listener) {
    this.#listeners.get(event)?.delete(listener);
  }

  emit(event, ...args) {
    this.#listeners.get(event)?.forEach(listener => {
      try { listener(...args); }
      catch (err) { console.error(`Listener error on '${event}':`, err); }
    });
  }

  listenerCount(event) {
    return this.#listeners.get(event)?.size ?? 0;
  }
}

// Domain: StockMarket notifying subscribers of price changes
class StockMarket extends EventEmitter {
  #prices = new Map();

  updatePrice(symbol, price) {
    const prevPrice = this.#prices.get(symbol);
    this.#prices.set(symbol, price);
    this.emit('priceChange', { symbol, price, prevPrice });
    if (prevPrice && Math.abs(price - prevPrice) / prevPrice > 0.05) {
      this.emit('significantMove', { symbol, price, prevPrice, changePct: ((price - prevPrice) / prevPrice * 100).toFixed(2) });
    }
  }

  getPrice(symbol) { return this.#prices.get(symbol); }
}

// Multiple independent subscribers — market doesn't know or care about them
const market = new StockMarket();

// Portfolio tracker
const unsubPortfolio = market.on('priceChange', ({ symbol, price }) => {
  console.log(`[PORTFOLIO] ${symbol}: $${price}`);
});

// Alert system (one-time significant move alert)
market.once('significantMove', ({ symbol, price, changePct }) => {
  console.log(`[ALERT] ${symbol} moved ${changePct}% to $${price}`);
});

// Chart (only cares about specific tickers)
market.on('priceChange', ({ symbol, price }) => {
  if (['AAPL', 'TSLA'].includes(symbol)) {
    console.log(`[CHART] Updating ${symbol} candlestick: $${price}`);
  }
});

market.updatePrice('AAPL', 175.50);
market.updatePrice('AAPL', 185.30); // >5% move → triggers significantMove
market.updatePrice('GOOGL', 140.20);

unsubPortfolio(); // Clean unsubscribe
market.updatePrice('AAPL', 183.00); // Portfolio no longer notified

// ── Parking Spot ─────────────────────────────────────────────────────────
class ParkingSpot {
  #vehicle = null;

  constructor(id, type, floorNumber) {
    this.id          = id;
    this.type        = type;
    this.floorNumber = floorNumber;
    this.status      = SpotStatus.AVAILABLE;
  }

  isAvailableFor(vehicle) {
    return this.status === SpotStatus.AVAILABLE && vehicle.canFitIn(this.type);
  }

  assign(vehicle) {
    if (this.status !== SpotStatus.AVAILABLE) throw new Error(`Spot ${this.id} is not available`);
    this.#vehicle = vehicle;
    this.status   = SpotStatus.OCCUPIED;
  }

  free() {
    this.#vehicle = null;
    this.status   = SpotStatus.AVAILABLE;
  }

  get vehicle() { return this.#vehicle; }
}

// ── Ticket ───────────────────────────────────────────────────────────────
class Ticket {
  static #nextId = 1;

  constructor(vehicle, spot) {
    this.id        = `TKT-${String(Ticket.#nextId++).padStart(6, '0')}`;
    this.vehicle   = vehicle;
    this.spot      = spot;
    this.entryTime = new Date();
    this.exitTime  = null;
    this.isPaid    = false;
  }

  getDurationHours() {
    const end = this.exitTime ?? new Date();
    return (end - this.entryTime) / 3_600_000;
  }
}

// ── Pricing Strategy (OCP + Strategy pattern) ────────────────────────────
class PricingStrategy {
  calculateFee(ticket) { throw new Error('Not implemented'); }
}

class HourlyPricing extends PricingStrategy {
  #rates = { [SpotType.COMPACT]: 2, [SpotType.REGULAR]: 3, [SpotType.LARGE]: 5 };
  calculateFee(ticket) {
    const hours = Math.ceil(ticket.getDurationHours()); // Round up to next hour
    return hours * (this.#rates[ticket.spot.type] ?? 3);
  }
}

class DailyCapPricing extends PricingStrategy {
  #hourlyRate;
  #dailyCap;
  constructor(hourlyRate = 3, dailyCap = 25) {
    super();
    this.#hourlyRate = hourlyRate;
    this.#dailyCap   = dailyCap;
  }
  calculateFee(ticket) {
    const days    = Math.floor(ticket.getDurationHours() / 24);
    const remHours = Math.ceil(ticket.getDurationHours() % 24);
    return days * this.#dailyCap + Math.min(remHours * this.#hourlyRate, this.#dailyCap);
  }
}

// ── Parking Floor ─────────────────────────────────────────────────────────
class ParkingFloor {
  #spots = [];

  constructor(floorNumber, spotCounts) {
    // spotCounts: { COMPACT: 20, REGULAR: 30, LARGE: 10 }
    for (const [type, count] of Object.entries(spotCounts)) {
      for (let i = 1; i <= count; i++) {
        this.#spots.push(new ParkingSpot(`F${floorNumber}-${type[0]}${i}`, type, floorNumber));
      }
    }
  }

  findAvailableSpot(vehicle) {
    return this.#spots.find(s => s.isAvailableFor(vehicle)) ?? null;
  }

  getAvailableCount(spotType) {
    return this.#spots.filter(s => s.type === spotType && s.status === SpotStatus.AVAILABLE).length;
  }
}

// ── Parking Lot (Singleton + Facade) ─────────────────────────────────────
class ParkingLot {
  static #instance = null;
  #floors = [];
  #activeTickets = new Map(); // ticketId → Ticket
  #pricing;

  constructor(floors, pricing = new HourlyPricing()) {
    if (ParkingLot.#instance) return ParkingLot.#instance;
    this.#floors  = floors;
    this.#pricing = pricing;
    ParkingLot.#instance = this;
  }

  static getInstance(floors, pricing) {
    if (!ParkingLot.#instance) new ParkingLot(floors, pricing);
    return ParkingLot.#instance;
  }

  static reset() { ParkingLot.#instance = null; } // For testing

  parkVehicle(vehicle) {
    for (const floor of this.#floors) {
      const spot = floor.findAvailableSpot(vehicle);
      if (spot) {
        spot.assign(vehicle);
        const ticket = new Ticket(vehicle, spot);
        this.#activeTickets.set(ticket.id, ticket);
        console.log(`[ENTRY] ${vehicle.licensePlate} → spot ${spot.id} | Ticket: ${ticket.id}`);
        return ticket;
      }
    }
    throw new Error(`No available spot for ${vehicle.constructor.name} (${vehicle.licensePlate})`);
  }

  processExit(ticketId) {
    const ticket = this.#activeTickets.get(ticketId);
    if (!ticket) throw new Error(`Invalid ticket: ${ticketId}`);

    ticket.exitTime = new Date();
    const fee = this.#pricing.calculateFee(ticket);
    ticket.isPaid = true; // Simulate payment success

    ticket.spot.free();
    this.#activeTickets.delete(ticketId);

    console.log(`[EXIT]  ${ticket.vehicle.licensePlate} | Duration: ${ticket.getDurationHours().toFixed(2)}h | Fee: $${fee.toFixed(2)}`);
    return { ticket, fee };
  }
}

  new ParkingFloor(2, { COMPACT: 5, REGULAR: 10, LARGE: 3 }),
]);

Section 3 — LLD Interview Approach

Step-by-Step · 45-Minute Framework

Most LLD interview failures happen not because the candidate doesn't know OOP, but because they jump to implementation without a plan. This six-step framework, applied to every problem, consistently impresses interviewers.

Step 1 — Clarify Requirements (5 minutes)

Never start coding. Start asking questions. Frame your questions as use case scenarios: "Will there be multiple types of users, like admins and regular members?" rather than "What are the requirements?"

Write the requirements you agree on. Refer back to them when the interviewer asks why you made a design choice.

Step 2 — Identify Core Entities (5 minutes)

Read the requirements and underline nouns — they become your classes. Underline verbs — they become methods. Group related nouns under abstractions. Ask: which nouns are abstract types and which are concrete? Are there state transitions (ticket goes from issued to paid)?

Draw a rough entity list on the whiteboard. Not a full class diagram — just names and arrows showing which entities know about which other entities.

Step 3 — Define Interfaces First (10 minutes)

Before writing a single class implementation, write the interfaces (abstract classes in JavaScript). This forces you to think about contracts, not implementations. It also demonstrates SOLID thinking — you are programming to abstractions.

Say out loud: "I'm going to define the interface for X before implementing it, because this lets me swap implementations without changing callers."

Step 4 — Implement Concrete Classes (15 minutes)

Implement the most important classes first — typically the core entity, the facade, and any non-trivial collaboration. Use design patterns explicitly and by name when you apply them: "I'll use the Observer pattern here so the DisplayBoard updates automatically when spot availability changes."

Step 5 — Handle Edge Cases (5 minutes)

Walk through your design with these questions: What happens when the system is at capacity? What if payment fails? What if two requests arrive simultaneously? What if an entity is deleted while another process holds a reference to it?

Saying "I see a potential concurrency issue here — let me add a mutex/optimistic lock" impresses interviewers more than perfect code that ignores concurrency.

Step 6 — Discuss Extensibility (5 minutes)

End with: "If I needed to add X new feature, here's how my design handles it without modification — I'd just add a new class that implements this interface." This directly demonstrates OCP and shows you designed for the future.

Pro tip: Interviewers do not expect a perfect solution. They expect clear thinking, principled decisions, and awareness of trade-offs. A candidate who designs a clean 70% solution and explains it well beats a candidate who silently writes 100% of the code but can't explain any of it.

Section 4 — Common Mistakes to Avoid

Anti-Patterns · What Interviewers Notice

Mistake 1 — Starting with Implementation Instead of Interfaces

The most common mistake in LLD interviews is jumping straight to writing class ParkingLot { constructor() { this.spots = []; } } before thinking about what interfaces the system needs. Interfaces define the contract; implementations fulfil it. Without interfaces, you cannot swap implementations, cannot mock in tests, and cannot claim to follow DIP.

Fix: Always ask "what does this thing do?" before "how does it do it?" Write the abstract class / interface signature before the concrete class.

Mistake 2 — God Classes (SRP Violation)

A ParkingLotManager that manages spots, processes payments, sends notifications, calculates prices, and handles entry gates is a God class. It has too many reasons to change and is impossible to test in isolation.

Fix: When a class has more than ~5 public methods, ask whether any of them belong in a separate class. Apply SRP: one responsibility = one reason to change.

Mistake 3 — Inheritance over Composition

Deep inheritance hierarchies break fragility: a change in a grandparent class propagates in unexpected ways through all descendants. "Favour composition over inheritance" is one of the most quoted lines in the Gang of Four book for a reason.

Fix: When you find yourself creating more than two levels of inheritance, consider whether composition would serve better. Use interfaces + composition to achieve polymorphism without the fragility of deep hierarchies.

Mistake 4 — Skipping Edge Cases

Designing only for the happy path makes your design look naive. Edge cases are where real systems live — concurrency, failures, invalid inputs, resource exhaustion.

Fix: For every entity with state, ask: what are all the states? What transitions are invalid? For every operation, ask: what can go wrong?

Mistake 5 — No Design Pattern Recognition

When a candidate designs an Uber system and builds a rigid if/else dispatch chain for matching drivers, the interviewer knows they are not pattern-fluent. The same problem solved with a Strategy pattern signals seniority.

Fix: For any place where you see an if/else chain on types, consider Strategy or Factory. For any place where objects need to notify other objects, consider Observer. For any complex object with many options, consider Builder.

Mistake 6 — Treating All Fields as Public

Public fields mean any code anywhere can corrupt your object's state. This shows a lack of OOP fundamentals regardless of how correct the rest of the design is.

Fix: Default to private fields (#field syntax in JavaScript). Expose only what callers need via methods, and only expose what is safe to expose.

Section 5 — Resources and Practice

Books · Courses · Practice Platforms · References

Essential Books

  • Design Patterns: Elements of Reusable Object-Oriented Software — Gamma, Helm, Johnson, Vlissides (Gang of Four)
    The definitive reference. Read the intent, motivation, and applicability sections for each pattern; skip the C++ code.
  • Clean Code — Robert C. Martin (Uncle Bob)
    The practical companion to SOLID. Chapters on naming, functions, classes, and systems are essential reading before any LLD interview.
  • Head First Design Patterns — Freeman & Robson (O'Reilly)
    Most accessible introduction to patterns; visual learning with lots of "aha" moments. Start here before the GoF book.
  • Refactoring: Improving the Design of Existing Code — Martin Fowler
    Learn patterns by learning what bad code looks like and how to transform it. Indispensable for senior engineers.
  • Clean Architecture — Robert C. Martin
    Where LLD meets HLD. Shows how SOLID and design patterns compose into larger architectural structures.

Summary · 8-Week Roadmap at a Glance

Low-Level Design is a learnable skill, not a talent. The engineers who ace LLD interviews did not get lucky — they followed a structured path: OOP fundamentals first, SOLID principles second, design patterns third, and canonical problems last.

The single most important habit you can build is to define interfaces before implementations and to name the pattern you are applying when you apply it. These two habits, more than any memorised solution, signal the seniority that interviewers are looking for.

Eight weeks. Four phases. One canonical problem solved and internalised per day in week seven and eight. That is the path from zero to confident in 2026.
