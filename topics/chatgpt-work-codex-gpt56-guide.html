Complete Guide to the New ChatGPT: Work Mode, Codex, and What's Actually Useful in 2025

A practical guide for developers on the new ChatGPT capabilities — Work mode for teams, the Codex agentic coding agent, the GPT-4o/o-series model family, and honest comparisons with competing tools. What is genuinely useful vs what is marketing.

Domain: AI Tools · ChatGPT · LLMs · Developer Productivity Published: 2026-07-29

ChatGPT in 2025 is not the chatbot it was at launch. It has grown into a platform with model tiers, team workspaces, custom agents (GPTs), a terminal-native agentic coding tool (Codex), and a reasoning model family (o1, o3, o4). For engineers, knowing which layer to reach for — and when to reach for a competitor — is now a meaningful productivity decision.

Scope of this guide: Everything below reflects the state of OpenAI's products as of mid-2025. ChatGPT features ship fast — verify current availability and pricing at platform.openai.com before building production systems on top of any specific capability.

The New ChatGPT Landscape (2025)

OpenAI shipped a large number of product changes between mid-2024 and mid-2025. Understanding the layer structure helps you make better tool choices.

Model tiers

OpenAI now ships two parallel families: the GPT-4o family (fast, multimodal, low latency) and the reasoning model family (o1 → o3 → o4, slow but able to solve problems that require extended internal chain-of-thought). The two families are optimised for fundamentally different tasks and priced accordingly.

  • GPT-4o — the default model. Multimodal (text, image, audio). Good for everyday coding, summarisation, explanation, and RAG pipelines where latency matters.
  • GPT-4o mini — cost-optimised. ~10× cheaper per token than GPT-4o. Suited for high-volume classification, embedding pipelines, and structured-output extraction where task difficulty is low.
  • o1 / o3 / o4-mini / o4 — reasoning models. They spend tokens on an internal scratchpad before responding. Dramatically better on maths, multi-step logic, code debugging, and research-style tasks. o4 is the most capable but most expensive; o4-mini is the cost-accuracy sweet spot for most engineering use cases.

ChatGPT Teams / Work

The Teams plan adds collaboration infrastructure on top of the consumer product: shared custom instructions, custom GPT sharing within the organisation, admin controls, SSO, and a data-privacy guarantee that conversations are not used for OpenAI training. It is the offering that bridges "individual power user" and "company-wide rollout."

Codex CLI

Codex is OpenAI's terminal-native agentic coding agent. It runs locally, has access to your filesystem and shell, and can read files, write code, run tests, and iterate without you copy-pasting between a chat window and your editor. It is categorically different from the ChatGPT web interface — it is an agent, not a chat assistant.

From chatbot to platform

The architectural shift is: ChatGPT is now a distribution layer on top of OpenAI models. The model API, the ChatGPT consumer interface, the Teams workspace, the custom GPT marketplace, and Codex are all separate products sharing the same underlying model infrastructure. Each has distinct strengths, and the right mental model is to think of them as separate tools rather than one product.

ChatGPT Work Mode

ChatGPT Teams (sometimes called Work mode in product messaging) targets organisations that want ChatGPT as a shared productivity layer rather than a collection of individual subscriptions.

Workspace separation

Teams accounts give each member a workspace that is logically separated from personal usage. Conversations, custom GPTs, and files uploaded in the work workspace stay within the organisation. Members can keep a personal ChatGPT account alongside without cross-contamination.

Shared custom instructions

Admins can push custom instructions (system-level context) to all members. For an engineering team, this means every member's ChatGPT already knows: the tech stack, the preferred code style, the internal terminology, and any constraints (e.g. "this team does not use external dependencies without security review"). This eliminates the per-user re-configuration that burns time on individual plans.

GPT sharing within the organisation

Custom GPTs built by team members can be shared within the workspace (visible to all members, not published to the public marketplace). This makes it viable to invest in polished internal GPTs — a PR description writer, a code reviewer, a runbook generator — without exposing proprietary context.

Admin controls and data privacy

The Teams plan includes: SSO (SAML/OIDC), user provisioning via SCIM, audit logs, and the ability to restrict which GPTs members can access. Critically, the Terms of Service for Teams/Enterprise explicitly exclude conversation data from OpenAI model training — this is the contractual basis most legal and compliance teams require before approving company-wide rollout.

Who should use it

Teams mode makes the most sense when: (a) multiple people on a team need the same context injected without manual setup, (b) you want to share internal GPTs without publishing them, or (c) your legal team requires data-privacy guarantees. For a solo engineer the Plus plan is sufficient.

Custom GPTs for Teams

Custom GPTs are instruction-tuned agents you build on top of a base ChatGPT model. They can have a custom system prompt, uploaded knowledge files (PDFs, docs, code), enabled tools (web browsing, code interpreter, image generation), and — for API-connected GPTs — custom actions that call external APIs.

Building a team-specific GPT

The GPT builder UI walks you through: naming it, writing the system prompt, uploading knowledge files, and configuring capabilities. The system prompt is where most of the value is concentrated. A well-written prompt includes: role definition, output format requirements, what the GPT should refuse, and examples of ideal responses.

System prompt design for consistency

Key patterns for engineering team GPTs:

  • Constrain the role — "You are a senior Go engineer reviewing code only within this repository's style guide. Do not suggest refactors outside the scope of the requested change."
  • Specify output format — "Always return feedback as a bulleted list grouped by: correctness, performance, style. Each item must include: file and line reference, issue, and suggested fix."
  • Define refusal conditions — "If asked to generate code that writes to production databases without a dry-run flag, refuse and explain why."

Practical team GPT examples

Example System Prompt — PR Description Writer GPT 
You are a PR description writer for a Node.js/TypeScript monorepo.

When given a git diff or a list of changed files, you write a GitHub pull request
description in the following format:

## What changed
- [bullet list of functional changes, one sentence each]

## Why
[2-3 sentences explaining the motivation or the ticket context]

## Test plan
- [ ] [specific test steps the reviewer should follow]

Rules:
- Do not include implementation details the reviewer does not need to understand intent.
- If the diff touches database migrations, always add a rollback step to the test plan.

Example System Prompt — Code Reviewer GPT 
You are a senior backend engineer reviewing code changes in a Python/Django codebase.

For each review request, produce structured feedback under these headings:
1. Correctness — logic errors, edge cases, off-by-one errors
2. Security — injection risks, missing auth checks, secrets in code
3. Performance — N+1 queries, missing indexes, unnecessary allocations
4. Style — PEP 8 violations, naming inconsistencies, missing type hints
5. Tests — missing coverage, incorrect assertions, test isolation issues

If a section has no issues, write "None found."

Each finding: filename:line — issue description — suggested fix.

Do not suggest changes unrelated to the diff unless they are security issues.

Codex — The Agentic Coding Agent

Codex CLI is OpenAI's answer to the category of terminal-native AI coding agents. It is meaningfully different from the ChatGPT web interface and deserves separate mental modelling.

What Codex CLI is

Codex runs as a local process in your terminal. It has access to your filesystem, can read source files, write modified files, and execute shell commands (in a sandboxed environment by default). It operates in an agentic loop: receive task → read relevant files → make changes → run tests → iterate until the task is complete or it hits a stopping condition.

Sandbox and safety model

By default, Codex runs in suggest mode: it proposes changes and commands but requires your approval before executing. In auto-edit mode it writes files directly; in full-auto mode it also runs commands. The recommended posture for most workflows is auto-edit with full-auto reserved for throwaway sandbox environments.

Practical use cases

Codex shines for tasks with a well-defined acceptance criterion that can be verified by running a command:

  • Implement a GitHub issue — paste the issue description, Codex reads the relevant files, writes the implementation, and runs the test suite to verify.
  • Run tests and fix failures — codex "run npm test and fix all failing tests" in full-auto mode iterates until the suite passes or it exhausts its context.
  • Upgrade a dependency — update a package, run tests, and fix breaking changes in one agentic session.
  • Write tests for an untested module — point it at a file and ask for unit tests; it reads the implementation and writes tests that actually cover the logic.

Codex vs chat for coding: Use the ChatGPT web interface when you need to think through design, discuss tradeoffs, or explore options interactively. Use Codex when the task is concrete enough to be specified as an acceptance criterion and you want the agent to handle the mechanical work while you review the diff.

The GPT-5 Family — What Actually Changed

The model naming is confusing because OpenAI ships multiple dimensions of variation simultaneously: base capability (GPT-4o vs o-series), size/cost tier (mini vs full), and specialisation (vision, audio, embeddings). Here is a practical breakdown.

GPT-4o — the workhorse

GPT-4o is the default model across ChatGPT and the API. It is natively multimodal: a single model that processes text, images, and audio without stitching separate models together. For most engineering tasks — code generation, explanation, summarisation, Q&A, RAG — GPT-4o is the right default. It is fast (low latency, good for interactive use) and capable enough for the vast majority of real-world tasks.

o1 / o3 / o4 — reasoning models

The o-series models run an internal chain-of-thought before producing a response. This "thinking" is invisible to the user but results in dramatically better performance on problems requiring multi-step reasoning: complex debugging, algorithm design, mathematical proofs, and research-style analysis.

The tradeoff is latency and cost. o4 can take 30–120 seconds to respond on hard problems. The recommended rule of thumb:

  • Default to GPT-4o for speed-sensitive interactive tasks
  • Reach for o4-mini when the task requires extended reasoning but you want cost control
  • Use o4 (full) for the hardest one-off tasks where quality justifies the wait
  • Never use o-series in a hot path with strict latency SLOs

GPT-4o mini — cost-optimised tier

GPT-4o mini is roughly 10× cheaper per token than GPT-4o, with a capability level that is still very competitive. It is the right choice for high-volume applications: email classification, structured data extraction from large document sets, sentiment analysis at scale, or any pipeline where you run millions of inferences per day.

Model selection decision framework

Task type                        Recommended model
─────────────────────────────────────────────────────────

Algorithm design / debugging     o4-mini (most tasks) or o4

High-volume extraction/classif.  GPT-4o mini

Practical Workflows for Developers

The highest-leverage ChatGPT workflows for engineers are the ones you can run in under two minutes. Here are five patterns worth internalising.

1. Code review workflow

Paste a git diff and ask for review in specific dimensions rather than "review this code." The more specific the ask, the less noise in the response.

Prompt Pattern — Targeted Code Review 
You are a senior backend engineer. Review the following diff for:
1. Correctness — logic errors, missing error handling, edge cases
2. Security — injection risks, missing auth checks, unsafe deserialization
3. Performance — N+1 queries, unnecessary allocations, missing indexes

For each finding: filename:line | issue | suggested fix.
Ignore style issues unless they are likely to cause runtime bugs.

---DIFF---
[paste diff here]

2. Architecture diagram generation

Describe your system in plain English and ask for a Mermaid or PlantUML diagram. Paste the output directly into your ADR or README — GitHub renders Mermaid natively.

Prompt Pattern — Architecture to Mermaid 
Generate a Mermaid sequence diagram for the following flow:

A user submits a form. The frontend sends a POST to /api/orders.
The API validates the payload, writes an order row to PostgreSQL,
publishes an "order.created" event to Kafka, and returns 201.
A fulfilment worker consumes the event, calls the inventory service
to reserve stock, and updates the order status to "confirmed".

Use Mermaid sequenceDiagram syntax. Include the async Kafka step clearly.

3. SQL query generation

Describe your schema and query intent. Include sample data if the logic is non-trivial. Ask for an explanation alongside the query so you can verify the logic before running it.

Prompt Pattern — SQL from Intent 
Schema:
  orders(id, user_id, status, total_cents, created_at)
  order_items(id, order_id, product_id, quantity, unit_price_cents)
  products(id, name, category)

Write a PostgreSQL query that returns: for each product category,
the top 3 products by revenue (quantity * unit_price_cents) in the
last 30 days, among orders with status = 'completed'.

Include a brief explanation of how the window function works.

4. Regex generation

Describe the pattern in plain English, give examples of strings that should and should not match, and ask for the regex with an explanation of each capture group.

Prompt Pattern — Regex from Description 
Write a JavaScript regex that:
- Matches a semantic version string: MAJOR.MINOR.PATCH with optional pre-release
  (e.g. 1.2.3, 2.0.0-beta.1, 0.1.0-rc.3)
- Does NOT match: 1.2, v1.2.3, 1.2.3.4

Named capture groups: major, minor, patch, prerelease (optional).
Include test cases using String.match() showing both matches and non-matches.

5. Stack trace debugging

Paste the full stack trace, the function that threw, and a one-sentence description of what you expected to happen. Ask for root cause and fix, not just a description of the error.

Prompt Pattern — Root Cause from Stack Trace 
I expected this to write a record and return the new ID.
Instead I get this error:

TypeError: Cannot read properties of undefined (reading 'id')
  at createOrder (src/orders/service.ts:47:28)
  at POST /api/orders (src/routes/orders.ts:23:18)

Relevant code:
[paste the function]

What is the root cause and what is the minimal fix?
Do not suggest a full refactor — I want the minimal change to make this work.

Prompting Patterns for GPT Models

These patterns apply across the GPT family. They are not tricks — they are ways of reducing the ambiguity in your request, which directly improves output quality.

Chain-of-thought

Adding "think step by step" or "reason through this before answering" causes the model to externalise its reasoning, which catches errors earlier in the reasoning chain. Most useful with GPT-4o on multi-step problems; less necessary with o-series models (they already reason internally).

Pattern — Chain-of-Thought 
// Instead of:
"What is the time complexity of this algorithm?"

// Use:
"Walk through the algorithm step by step and determine its time complexity.
Show your reasoning for each loop or recursive call before giving the final answer."

Role setting

A role primes the model's response register — vocabulary, depth, what it considers relevant. For technical tasks, a specific role ("senior SRE with 10 years of Kubernetes experience") produces more useful output than a generic one ("experienced engineer").

Pattern — Role Setting 
"You are a senior SRE who has operated Kubernetes clusters at 500+ node scale.
Review the following deployment manifest and flag any reliability or operational
issues a team new to Kubernetes would miss. Be direct. Do not explain what
Kubernetes is."

Output format specification

Specifying the output format eliminates the post-processing step. Always define: format (JSON/markdown/plain), structure (fields, headings), and length constraints.

Pattern — Output Format 
"Return your analysis as a JSON array. Each item:
{
  'file': 'filename.ts',
  'line': 42,
  'severity': 'error' | 'warning' | 'info',
  'issue': 'one sentence description',
  'fix': 'one sentence suggested fix'
}
Return only the JSON. No markdown code fences, no preamble."

Constrained generation

Negative constraints prevent the model from adding things you do not want. Particularly useful for code generation where you want minimal output.

Pattern — Constrained Generation 
"Write a Node.js function that validates an email address.
Constraints:
- No external libraries. Use only Node.js built-ins.
- Do not add TypeScript types (this is a .js file).
- No JSDoc. No comments.
- No default exports. Named export only.
- Must handle null and undefined without throwing."

Few-shot examples

For tasks with a specific output style that is hard to describe in prose, show 2–3 input/output examples before the actual request. The model infers the pattern from examples more reliably than from a description.

Pattern — Few-Shot 
"Convert each commit message to a changelog entry in the format shown:

Input: fix: null pointer in user service when email is missing
Output: Fixed a null pointer error in the user service that occurred when the email field was absent.

Input: feat: add rate limiting to the /api/search endpoint
Output: Added rate limiting to the /api/search endpoint to prevent abuse.

Input: refactor: extract database connection logic to shared module
Output: [your turn — follow the same pattern]"

API Usage for Engineers

The OpenAI API gives you programmatic access to all models with structured outputs, function calling, and streaming. Here is what you need to know to build production integrations.

Pricing context (mid-2025)

Approximate pricing — always verify at platform.openai.com/pricing before sizing:

  • GPT-4o: ~$5/M input tokens, ~$15/M output tokens
  • GPT-4o mini: ~$0.15/M input, ~$0.60/M output
  • o4-mini: ~$1.10/M input, ~$4.40/M output (plus reasoning tokens)
  • o4: ~$10/M input, ~$40/M output (plus reasoning tokens)

For a typical RAG pipeline (1,000 calls/day, avg 2K input + 500 output tokens each): GPT-4o costs ~$35/day; GPT-4o mini costs ~$0.35/day.

Structured outputs (JSON mode)

Use response_format: { type: "json_object" } to guarantee valid JSON output. Use response_format: { type: "json_schema", json_schema: {...} } for schema-validated structured outputs (available on GPT-4o and later).

Function calling / tool use

Define tools as JSON schemas. The model decides when to call a tool and returns a structured tool call object instead of prose. Your code executes the function and returns the result back to the model for final synthesis. This is the foundation of agentic patterns.

Streaming responses

Use stream: true for interactive UIs where you want to show partial responses as they arrive. Do not use streaming in batch pipelines — the overhead is not worth it.

Node.js — GPT-4o API: Structured Output + Streaming + Tool Use 
// npm install openai
import OpenAI from 'openai';

const client = new OpenAI({ apiKey: process.env.OPENAI_API_KEY });

// ── 1. Simple structured output (JSON schema) ─────────────────────────────
async function extractCommitInfo(commitMessage) {
  const response = await client.chat.completions.create({
    model: 'gpt-4o',
    response_format: {
      type: 'json_schema',
      json_schema: {
        name: 'commit_info',
        strict: true,
        schema: {
          type: 'object',
          properties: {
            type: { type: 'string', enum: ['feat', 'fix', 'refactor', 'docs', 'chore'] },
            scope: { type: ['string', 'null'] },
            description: { type: 'string' },
            breaking: { type: 'boolean' },
          },
          required: ['type', 'scope', 'description', 'breaking'],
          additionalProperties: false,
        },
      },
    },
    messages: [
      { role: 'system', content: 'Extract commit metadata from conventional commit messages.' },
      { role: 'user', content: commitMessage },
    ],
  });

  return JSON.parse(response.choices[0].message.content);
}

// Usage
const info = await extractCommitInfo('feat(auth)!: add OAuth2 PKCE flow, remove legacy basic auth');
console.log(info);
// { type: 'feat', scope: 'auth', description: 'add OAuth2 PKCE flow...', breaking: true }


// ── 2. Streaming response ─────────────────────────────────────────────────
async function streamCodeReview(diff) {
  const stream = await client.chat.completions.create({
    model: 'gpt-4o',
    stream: true,
    messages: [
      {
        role: 'system',
        content: 'You are a senior engineer. Review code diffs concisely. Max 5 findings.',
      },
      { role: 'user', content: `Review this diff:\n\n${diff}` },
    ],
  });

  process.stdout.write('Review: ');
  for await (const chunk of stream) {
    const delta = chunk.choices[0]?.delta?.content ?? '';
    process.stdout.write(delta);
  }
  console.log(); // newline
}


// ── 3. Function / tool calling ─────────────────────────────────────────────
const tools = [
  {
    type: 'function',
    function: {
      name: 'get_github_issue',
      description: 'Fetch a GitHub issue by number',
      parameters: {
        type: 'object',
        properties: {
          repo: { type: 'string', description: 'owner/repo format' },
          issue_number: { type: 'integer' },
        },
        required: ['repo', 'issue_number'],
      },
    },
  },
];

async function agentWithTools(userMessage) {
  const messages = [
    { role: 'system', content: 'You help engineers triage GitHub issues.' },
    { role: 'user', content: userMessage },
  ];

  // First turn — may produce a tool call
  const response = await client.chat.completions.create({
    model: 'gpt-4o',
    tools,
    tool_choice: 'auto',
    messages,
  });

  const choice = response.choices[0];

  if (choice.finish_reason === 'tool_calls') {
    const toolCall = choice.message.tool_calls[0];
    const args = JSON.parse(toolCall.function.arguments);

    // Execute the tool (your implementation)
    const issueData = await fetchGitHubIssue(args.repo, args.issue_number);

    // Second turn — model synthesises the tool result
    messages.push(choice.message); // assistant's tool call message
    messages.push({
      role: 'tool',
      tool_call_id: toolCall.id,
      content: JSON.stringify(issueData),
    });

    const finalResponse = await client.chat.completions.create({
      model: 'gpt-4o',
      messages,
    });

    return finalResponse.choices[0].message.content;
  }

  return choice.message.content;
}


// ── 4. o4-mini for hard reasoning tasks ───────────────────────────────────
async function architectureAnalysis(systemDescription) {
  const response = await client.chat.completions.create({
    model: 'o4-mini',  // reasoning model — no system prompt, higher latency
    messages: [
      {
        role: 'user',
        content: `Analyze this distributed system for single points of failure and
                  race conditions. Propose concrete mitigations with implementation detail.

                  System: ${systemDescription}`,
      },
    ],
    // Note: o-series models do not support 'system' role messages in all configurations
    // and do not support temperature parameter
  });

  return response.choices[0].message.content;
}

In particular: model IDs change (gpt-4o-2024-11-20 style versioned aliases), structured output schema support varies by model version, and o-series API parameters differ from GPT-4o in ways the docs describe in detail.

Key Takeaway

ChatGPT in 2025 is a platform, not a product. The useful mental model for engineers: use GPT-4o as your interactive default, reach for o4-mini when a problem genuinely requires extended reasoning, use GPT-4o mini in high-volume API pipelines for cost efficiency, and deploy Codex CLI for agentic terminal tasks with a concrete acceptance criterion. Custom GPTs on Teams are worth the setup investment when multiple engineers need the same context without manual re-configuration. The comparison with Claude is not about which tool is better — it is about routing tasks to the model whose strengths match the task. The engineers getting the most leverage use both and have a clear heuristic for which to reach for.
