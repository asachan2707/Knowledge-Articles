Microservices Patterns: 7 Principles & Design Solutions

A structured reference covering the seven core microservices design principles, decomposition patterns (by business capability, subdomain, strangler fig), integration patterns (API Gateway, Aggregator, Proxy, Chained), database patterns (shared vs per-service), and querying patterns (API Composition, CQRS).

Microservices design patterns fall into four natural groups: how to decompose a system into services, how services integrate and communicate, how data is owned and managed, and how cross-service queries are served. Understanding this categorization makes it much easier to apply patterns correctly — you identify which group of problem you have, then select the pattern within that group.

Core idea: The four groups are decomposition → integration → database → query. Each group has its own set of patterns. Most architectural discussions conflate them — knowing which group you're in helps you select the right pattern and avoid applying a query-layer solution to a decomposition problem.

The 7 principles

Principles that should constrain every decision

1. Model around business domain

Service boundaries follow business capabilities, not technical layers. "User management" is a valid boundary. "All PostgreSQL queries" is not.

2. Culture of automation

Microservices without automated testing, CI/CD, and deployment pipelines are an antipattern — the operational overhead overwhelms any architectural benefit.

3. Hide implementation details

Services expose only their public API. Database schema, internal models, and implementation choices are fully encapsulated. No shared libraries that expose internals.

4. Decentralise everything

Data stores, governance, decision-making. Central control of any of these creates the bottleneck the architecture was trying to eliminate.

5. Deploy independently

A service that requires coordinated deployment with other services is not a microservice — it's a distributed monolith. Each service must deploy independently without breaking any consumer.

6. Isolate failure

A crashing service should affect only consumers of that specific service, not the entire system. Isolation requires Circuit Breakers, fallbacks, and timeout policies at every service boundary.

7. Observable

Distributed systems are not debuggable without distributed tracing, structured logs, and metrics per service. Observability is a first-class architectural requirement, not an afterthought.

Decomposition patterns

How to split a system into services

By Business Capability

Split along what the business does: Order Management, Payment Processing, Inventory, Shipping. Teams own entire business capabilities end-to-end.

By Subdomain (DDD)

Use Domain-Driven Design: core domain (your differentiator — build it), supporting domain (needed but not differentiating — consider buying), generic domain (commodity — use off-the-shelf).

Strangler Fig

Incrementally extract services from a monolith. A façade routes requests to either the legacy system or the new service. Legacy retires as extraction completes, function by function.

Integration patterns

How services communicate

API Gateway

Single entry point for all clients. Handles routing, auth, rate limiting, and protocol translation. Clients never call internal services directly.

Aggregator

A service that calls multiple downstream services, aggregates their responses, and returns a single combined result. Used when a single client request requires data from multiple services.

Proxy

A service that forwards requests to a single downstream service but adds a cross-cutting concern (logging, auth checking, protocol translation). Thinner than an aggregator.

Chained

Service A calls Service B which calls Service C in a chain. Each step adds to or transforms the request. Use sparingly — chains amplify latency and create cascading failure paths.

Branch

A service sends a request to multiple downstream services simultaneously (branching) and collects responses. Used when parallel independent operations are needed.

Async Messaging

Services communicate via events over a broker. Complete decoupling — producers don't know about consumers. Use for state change notifications and background workflows.

JavaScript Example

Aggregator pattern — parallel multi-service fetch

JavaScript Example 
// Aggregator service: combines data from Order, User, and Inventory services
// All three fetched in parallel; response aggregated into a single object

class OrderDetailAggregator {
  constructor(services) {
    this.orders    = services.orderService;
    this.users     = services.userService;
    this.inventory = services.inventoryService;
  }

  async getOrderDetail(orderId) {
    // Fetch base order first — need userId and itemIds
    const order = await this.orders.getById(orderId);

    // Now fetch user and inventory in parallel (independent of each other)
    const [user, inventoryItems] = await Promise.all([
      this.users.getById(order.userId),
      Promise.all(order.itemIds.map(id => this.inventory.getItem(id))),
    ]);

    return {
      orderId: order.id,
      status: order.status,
      customer: {
        id: user.id,
        name: user.name,
        email: user.email,
      },
      items: inventoryItems.map(item => ({
        id: item.id,
        name: item.name,
        price: item.price,
        quantity: order.quantities[item.id] ?? 1,
      })),
      total: order.total,
      createdAt: order.createdAt,
    };
  }
}

// Chained pattern — each service adds to the request
async function processOrderChained(orderData) {
  // Step 1: Validate → Step 2: Enrich → Step 3: Persist
  const validated = await validationService.validate(orderData);
  const enriched  = await enrichmentService.addUserContext(validated);
  const stored    = await persistenceService.save(enriched);
  return stored;
  // Warning: 3 sequential hops — latency compounds. Keep chains short.
}
Aggregator vs BFF: An Aggregator is a generic composition service that can serve any client. A BFF (Backend for Frontend) is client-specific — it shapes data precisely for one consumer type. Use an Aggregator when the composition logic is the same across clients; use a BFF when mobile, web, and partner API clients need substantially different shapes of the same underlying data.

Key Takeaway

Microservices patterns organize into four groups: decomposition (how to split), integration (how to communicate), database (who owns data), and query (how to read across service boundaries). The seven principles are the constraints every pattern must satisfy. When choosing a pattern, identify which group of problem you're in first — this eliminates the patterns that don't apply and narrows the choice to two or three relevant options.
