E-Commerce Order Processing: How a FAANG Engineer Answers This in a System Design Interview

A FAANG engineer's walkthrough of the e-commerce order processing system design interview: what L4 vs L5 vs L6 answers look like, the exact components to call out, the failure modes interviewers probe for, and the trade-off discussions that signal senior-level thinking.

Source: YouTube — System Design Interview with FAANG Engineer (2024) Domain: Interview Preparation / E-Commerce Systems
Story · Two Answers to the Same Question

Two candidates walk into the same interview room. Same question: "Design an e-commerce order processing system." They have 45 minutes. The interviewer takes notes.

Candidate A (rejected at L5): Picks up the marker immediately. Draws: frontend arrow to backend API arrow to MySQL database arrow to email notification. Lists features confidently: add to cart, checkout, pay, confirmation email. At the 20-minute mark: "I'd use MySQL for everything — it's reliable and we know it well." The interviewer nods. Then: "What happens if payment succeeds but inventory is out of stock?" Candidate A: "We'd check inventory first." Interviewer: "But what if the last item was taken between your inventory check and your payment completing?" Silence. Candidate A recovers: "We'd roll back the payment." Interviewer: "In a system where payment and inventory are separate services, how do you roll back a payment in the same transaction?" More silence.

Candidate B (hired at L5): Does not pick up the marker. Instead: "Before I start designing, I want to clarify a few constraints. What's the scale — 10k or 10M DAU? For inventory, do we need strong consistency — is occasional oversell acceptable, or must inventory counts be exact? Will this platform run flash sales?" After three minutes of requirement clarification, Candidate B draws: Order Service connecting to a Saga Orchestrator, which coordinates Payment Service, Inventory Service, and Notification Service, all connected via a Kafka event bus. "I'm using a Saga pattern here because payment and inventory reservation span two services — a single ACID transaction doesn't exist across service boundaries. Each step has a defined compensation action." When the interviewer asks about the race condition: "Inventory reservation uses a Redis atomic DECR with a floor check. We decrement atomically and if the result goes negative, we increment back and reject. This prevents oversell without a database-level lock that would serialize 100k concurrent requests."

The difference between these two candidates is not the number of services drawn. It is knowing which failure modes exist at each boundary, naming the patterns that prevent them, and explaining the cost each pattern carries. This guide teaches exactly that conversation.

Phase 1 — First 5 Minutes

Scoping the Question Before Drawing Anything

The single most revealing moment in any system design interview is the first 60 seconds. Interviewers deliberately leave requirements vague. Starting to draw without clarifying is not neutral — it signals that you design without requirements, which is exactly what causes production outages.

Interviewers deliberately leave requirements vague to see if you ask. Starting to draw without clarifying is the number one mistake in system design interviews. Clarifying requirements is not wasted time — it prevents you from designing the wrong system for the first 30 minutes and then throwing it away.

Scale questions

  • "How many DAU? What is the peak orders per second?"
  • "Do we need geographic distribution, or is this single-region?"
  • "What is our SLA on order creation latency — 200ms p99, or is 2 seconds acceptable?"

Consistency questions — the most important

  • "For inventory, is oversell acceptable? Can we show 'only 3 left' and occasionally be wrong, or must inventory counts be exactly correct?"
  • This single answer changes the entire inventory architecture. Eventual consistency = higher throughput. Strong consistency = Redis atomic operations or row-level locking, lower throughput but zero oversell.

Payment questions

  • "Are we building payment processing from scratch, or integrating with Stripe or Razorpay?"
  • "Do we need to handle refunds, partial refunds, and chargebacks in scope?"
  • "Is synchronous payment confirmation required, or can we show 'processing' and confirm async?"

Order flow questions

  • "What post-order steps are in scope — just order confirmation, or also fulfillment, shipping, and delivery tracking?"
  • "Do we need multi-item orders, or single-item only?"

Flash sale scope — always ask

  • "Will this platform run flash sales? Even one yes changes the inventory reservation design significantly."
  • If yes: you need Redis-based atomic reservation, not SQL-based. This is a design-level decision, not an optimization.

What a strong opening sounds like: "Before I start designing, let me clarify a few constraints. I'll assume 1M DAU, peak 10k orders per second during flash sales, strong consistency on inventory so no oversell, and we're integrating with Stripe for payments rather than building payment processing from scratch. Does that framing sound right?" Then wait for confirmation before picking up the marker.

Level Comparison

L4 vs L5 vs L6 Answer Comparison

Every dimension of a system design answer maps to a seniority signal. This table is the most direct way to calibrate where your current answer lands and what to add to reach the next level.

The key insight behind this table: L4 answers describe what to build. L5 answers describe how to build it so that it survives failure. L6 answers name which constraints drive the design and what it costs to accept those constraints. If your current answer only describes components, you are answering at L4 regardless of what level you are interviewing for. Move to L5 by walking through failure modes. Move to L6 by quantifying the trade-offs you are making.

The fastest way to upgrade an L4 answer to L5 in an interview is to say: "Before I move on, let me name the failure modes at this step." Then list them. Interviewers are trained to look for this. It is not pretentious — it is exactly the right thing to say.

Core Architecture

The 8 Components Every Strong Answer Must Mention

These eight components form the minimum viable architecture for an L5 answer. The key is not listing them — it is explaining why each boundary exists and what failure it prevents. If you draw a component without being able to say "without this, X failure mode occurs," the component does not count.

1. Order Service
Receives the checkout request, validates the cart contents, creates the order record in PENDING state, and orchestrates the Saga. This is the single source of truth for order state. Without it, order state is scattered across multiple services and there is no authoritative record of what was purchased.

2. Inventory Service
Manages item availability. Exposes reserve(itemId, quantity) and release(itemId, quantity) APIs. Both must be idempotent — the same reserve call with the same order ID should produce the same result regardless of how many times it is called. Without a dedicated Inventory Service, inventory logic lives inside the Order Service, making it impossible to scale inventory independently during flash sales.

3. Payment Service
Integrates with the payment gateway (Stripe). Exposes charge(orderId, amount, idempotencyKey) and refund(chargeId, idempotencyKey). Every call must be idempotent — a double charge is catastrophic and irreversible in the customer's trust. Without a dedicated Payment Service, payment logic inside the Order Service becomes too complex to test safely and too risky to deploy frequently.

4. Notification Service
Sends confirmation emails, SMS messages, and push notifications. Always on the asynchronous path — never block order creation waiting for email delivery. A slow email provider, an SMS gateway rate limit, or a notification template rendering error must never delay order confirmation. Without proper asynchronous separation, a slow SendGrid API call adds 800ms to every order.

5. Saga Orchestrator
Coordinates the multi-step order flow. Knows the current step of each in-flight order, what to execute next, and which compensating action to take if a step fails. Persists its own state to the database so it can recover after a crash. Without it, the Order Service contains complex state machine logic and compensation logic becomes tangled and untestable.

6. Transactional Outbox
Solves the dual-write problem: how do you update the database and publish a Kafka event atomically? The outbox writes both the business record and the event record in a single database transaction. A relay process reads the outbox and publishes to Kafka. Without it: the order state can update but the event not publish (or vice versa), leaving downstream services with a permanently incorrect view.

7. Event Bus (Kafka)
Decouples Saga steps and downstream consumers. Services subscribe to domain events rather than being called synchronously. This enables event replay for debugging, fan-out to multiple consumers (analytics, CQRS read model, notifications), and independent scaling. Without it: synchronous service-to-service calls create tight coupling, and one slow service cascades latency to all callers.

8. CQRS Read Model
A separate read-optimized store for order queries: order history, order tracking, customer support lookups. Written by projecting domain events from Kafka. Without it, every order history query hits the same PostgreSQL database as the high-throughput write path, creating read/write contention that degrades write performance during peak load.

If you draw these eight components and explain why each boundary exists, you have demonstrated senior-level design thinking. The critical test: for each component, can you name the specific failure mode that would occur without it? That explanation is what separates a system drawn on a whiteboard from a system designed to survive production.

Order Lifecycle

The Order Lifecycle State Machine

Explicitly drawing the state machine signals to the interviewer that you have thought about every transition, not just the happy path. Every state transition is an event on the Kafka bus. Every state is persisted to the database. If the system crashes at any point, it can recover by reading the last known state and re-executing from there.

CART
  |
  | (customer submits checkout)
  v
PENDING               -- order record created, saga started
  |
  | (inventory reservation succeeds)
  v
INVENTORY_RESERVED    -- items soft-locked for this order
  |
  | (payment charge succeeds)
  v
PAYMENT_CONFIRMED     -- funds captured, order committed
  |
  | (fulfillment service accepts the order)
  v
FULFILLMENT_IN_PROGRESS
  |
  | (warehouse ships the package)
  v
SHIPPED               -- tracking number emitted as domain event
  |
  | (carrier confirms delivery)
  v
DELIVERED             -- terminal state (happy path)


FAILURE PATHS (compensation runs in reverse):

  PENDING --> INVENTORY_UNAVAILABLE
    Saga: no compensation needed (nothing was charged yet)
    Order state --> CANCELLED

  INVENTORY_RESERVED --> PAYMENT_FAILED
    Saga: release inventory reservation
    Order state --> CANCELLED

  PAYMENT_CONFIRMED --> FULFILLMENT_FAILED
    Saga: refund payment charge, release inventory
    Order state --> CANCELLED

  SHIPPED --> customer requests return
    Order state --> RETURN_REQUESTED --> REFUND_PENDING --> REFUNDED

Why interviewers care about the state machine: it is the contract between the Order Service and the Saga Orchestrator. Every state is a point where the system can crash and must be able to recover. Every state transition that does not have a defined reversal (a compensation action) is a design gap — the system can get stuck with a customer charged but no order fulfilled.

The stuck order problem — always address this: What happens when an order stays in PAYMENT_INITIATED for more than five minutes? This means the payment gateway received the charge request but the response was lost in a network failure. The fix: an async payment status poller queries the payment gateway every 30 seconds for all orders in PAYMENT_INITIATED state with age greater than five minutes. Since the charge call used an idempotency key, querying the gateway for that key returns the existing result — either confirmed (advance state to PAYMENT_CONFIRMED) or failed (advance state to CANCELLED).

The state machine is not a diagram detail. It is the recovery contract. Every state is a crash recovery point. When you define a state, you are committing to: what action created this state, what action will move it forward, what action will compensate it if the forward action fails, and what happens if the system crashes while in this state. Interviewers at L5 and above expect all four of these to be answerable for every state you draw.

Reliability Pattern

Idempotency Everywhere

Idempotency is not an advanced topic. In a distributed system, every write operation will eventually be called more than once. Network timeouts cause retries. Saga compensation re-executes steps. Load balancers retry on connection errors. If your write operations are not idempotent, you will double-charge customers, double-reserve inventory, and send duplicate notifications. It is a matter of when, not if.

The double-charge scenario, step by step: The customer's browser submits the payment form. The request reaches the Payment Service. The Payment Service calls Stripe. Stripe charges the card successfully. The Stripe API response travels back over the network and is lost in a timeout. From the browser's perspective, the request failed. The browser retries. The Payment Service calls Stripe again. Without idempotency: the card is charged twice. With idempotency: both calls carry the same idempotency key; Stripe returns the cached result from the first call without executing a second charge.

Idempotency key design for each service:

ServiceIdempotency Key FormulaWhat Duplicate Handling Prevents
Order Service SHA-256(sessionId + cartHash) Duplicate checkout from browser retry creating two orders for one cart
Inventory Service orderId (already unique per order) Saga re-execution reserving the same inventory twice for the same order
Payment Service SHA-256(orderId + customerId + amount) Saga retry charging the customer twice for the same order
Notification Service SHA-256(orderId + notificationType) Kafka at-least-once delivery sending duplicate confirmation emails

Where to store idempotency keys: PostgreSQL, not Redis. Redis with a TTL is not durable — a restart or an eviction policy can remove the key before its purpose is served. A PostgreSQL table with the key and the response stored as JSON survives restarts, is queryable for debugging, and has the same transaction guarantees as the business data it protects. This is a distinction that separates L4 from L5 answers: "we'd use Redis to track whether a charge already happened" fails the durability test.

Distributed Consistency

Saga Pattern Deep Dive — Choreography vs Orchestration

The Saga pattern replaces the impossible: a single ACID transaction spanning multiple services and databases. Instead, it decomposes the business operation into local transactions, each touching exactly one service's database. When a step fails, previously committed steps are reversed by executing compensating transactions in reverse order. There is no automatic rollback — compensation must be explicitly designed for every step that changes durable state.

Choreography — event-driven, decentralized

In choreography, each service publishes an event after completing its step, and the next service in the flow subscribes to that event and executes its step.

Order flow with choreography: Order Service publishes order.created → Payment Service subscribes, charges the card, publishes payment.completed → Inventory Service subscribes, reserves stock, publishes inventory.reserved → Fulfillment Service subscribes, creates shipment.

Advantages: each service is independent and deployable separately; adding a new step only requires subscribing to the right event; no central coupling point.

Disadvantages: there is no central view of where any given order is in the flow; debugging a stuck order requires reading multiple services' logs and event streams; compensation (rollback) has no coordinator — each service must independently detect that a downstream step failed and compensate its own step.

Best for: simple two- or three-step flows with rare compensation paths and teams that value full decoupling over operational visibility.

Orchestration — explicit coordinator

In orchestration, a Saga Orchestrator calls each service in sequence, waits for the response, advances its own state machine, and decides what to execute next. The orchestrator owns the complete view of every order's progress.

Advantages: one place to see where any order is; clear compensation logic in one codebase; operational tooling (query all orders stuck at step X) is straightforward; easy to add timeouts and retries per step.

Disadvantages: the orchestrator becomes a coupling point — all services depend on it; if the orchestrator is down, new orders cannot progress; must be deployed with high availability.

Best for: complex flows with multiple compensation paths, audit trail requirements, or operational need to inspect in-flight order state. FAANG companies use orchestration for order processing because order state is business-critical, compensation logic is complex, and the ability to query "why is order X stuck?" is a daily operational need.

Compensation table — design this before the happy path

Forward StepWhat It ChangesCompensating Action
Reserve inventory Inventory count decremented; reservation record created Release reservation; increment inventory count
Charge payment Customer card charged; charge record created Refund the charge; mark charge as refunded
Create fulfillment Warehouse queue entry created; items picked Cancel fulfillment; return items to warehouse
Send confirmation notification Email/SMS sent to customer Send cancellation notification (cannot unsend the first email)

Note the last row: sending a notification cannot be undone. The compensation is to send a second notification explaining the cancellation. This is why the notification step is always last — all reversible operations run first, irreversible ones run after the order is committed. If the order is cancelled before reaching the notification step, no notification is sent. If it is cancelled after, the compensation is a follow-up notification.

Interview Drill

The Failure Questions Interviewers Ask

These four questions are asked at nearly every FAANG system design interview for e-commerce. An interviewer who has not asked these is leaving signal on the table. Prepare a concrete, specific answer for each. "We'd handle it" and "we'd add retry logic" are not answers — they are signals that you have not thought through the failure.

Question 1 — asked at almost every interview
Payment succeeds, but inventory reservation fails because the item just sold out. What happens?
The Saga Orchestrator receives the INVENTORY_UNAVAILABLE event from the Inventory Service. It executes the compensation for the previous step — payment: calls PaymentService.refund(chargeId, idempotencyKey). The idempotency key ensures this refund call is safe to retry. Sets order state to CANCELLED with reason INVENTORY_UNAVAILABLE. Publishes a cancellation event which the Notification Service consumes to send the customer an apology with an expected refund timeline (3–5 business days, constrained by the payment gateway, not by us). The inventory count is already correct — no rollback needed there because the reservation failed cleanly.
Question 2 — tests crash recovery understanding
The Saga Orchestrator crashes in the middle of executing a step. How does the system recover?
The Saga Orchestrator persists every state transition to the database before executing the next step — using the transactional outbox pattern so state and event are written atomically. On restart, the Orchestrator queries for all orders in intermediate states (PAYMENT_INITIATED, INVENTORY_RESERVING) with age greater than a timeout threshold. For each stuck order, it re-executes the current step using the same idempotency key that was assigned before the crash. Because all step calls are idempotent, re-executing a step that may have already succeeded is safe — the service returns the cached result without duplicating the action.
Question 3 — tests Kafka dependency understanding
Kafka goes down. Can orders still be processed?
Define the answer by what Kafka is used for in the design. If Saga coordination is synchronous (the Orchestrator calls services directly and Kafka is only for async fan-out like notifications and CQRS projection), then orders continue to process. Only asynchronous steps — notifications, analytics, read model updates — are delayed until Kafka recovers. If the Saga uses Kafka for step coordination itself, orders go to a local persistent queue (a database table with a poller that publishes to Kafka when it is available). This is acceptable partial degradation: orders queue up rather than fail. The maximum delay equals Kafka's recovery time. The important signal here is that you have separated the critical path (order creation, payment, inventory) from the non-critical async path (notifications, analytics).
Question 4 — the flash sale question, asked at almost every FAANG interview
100,000 concurrent flash sale orders for 1,000 units. How does the Inventory Service handle this without overselling or crashing?
Two-phase reservation. Phase 1: Redis atomic DECR. Before the flash sale starts, pre-load the inventory count: SET inventory:item:42 1000. On each reservation attempt: result = DECR inventory:item:42. If result is greater than or equal to zero, the reservation is tentatively accepted. If result is less than zero, execute INCR inventory:item:42 to undo the decrement and return SOLD_OUT. Redis DECR is atomic and executes in-memory in under 0.1ms — it handles 100k concurrent requests without contention. Phase 2: DB confirmation within 30 seconds. The tentatively-reserved orders write their confirmation to PostgreSQL. If confirmation fails (Redis and DB diverge after a Redis restart), release the Redis reservation. At most 1,000 DB writes succeed — the 99,000 rejections never hit the database. This handles the concurrency on the fast path and defers durability to the slow path.

The flash sale question is asked at almost every FAANG interview for e-commerce systems. If you answer it with "two-phase Redis reservation followed by database confirmation," you have demonstrated L5-level thinking. If you add "and we prevent the Redis-to-DB divergence by using a distributed lock during the pre-load window," you are at L6. If you say "we'd cache the inventory," you are at L3.

High-Concurrency Pattern

Flash Sale Design — Inventory Reservation Under 100k Concurrent Orders

This section deserves its own treatment because it is asked frequently and because the naive approach fails dramatically at scale. Walking through the progression from naive to correct signals exactly the kind of reasoning interviewers want to see.

The naive SQL approach and why it fails

SQL — Naive, Fails at Scale 
-- The naive approach: decrement with a guard
UPDATE items SET quantity = quantity - 1
WHERE id = ? AND quantity > 0;

-- At 100k concurrent requests:
-- 100k transactions attempt to lock the SAME row
-- Row-level lock contention serializes execution
-- Queue of waiting locks grows to 100k
-- Each waits for the previous to release
-- Total time: 100k * avg_lock_wait_time = minutes
-- Timeouts cascade; retries amplify the problem

The SKIP LOCKED pattern (PostgreSQL, moderate concurrency)

SQL — SKIP LOCKED for Row-Per-Unit Inventory 
-- Row-per-unit model: one database row per physical inventory unit
-- SKIP LOCKED: skip rows locked by other transactions instead of waiting
BEGIN;

SELECT id FROM inventory_units
WHERE item_id = ? AND status = 'available'
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- If no row returned: all units are locked (sold out or in-flight)
-- If a row is returned: this transaction holds the lock exclusively

UPDATE inventory_units
SET status = 'reserved', order_id = ?
WHERE id = ?;  -- the id from the SELECT above

COMMIT;

-- Result: concurrent transactions each grab a DIFFERENT row
-- Zero contention; each transaction completes immediately
-- Works well up to ~5,000 concurrent reservations per second
-- Above that: use Redis DECR for the hot path

The Redis atomic DECR pattern (flash sales at 100k/sec)

Redis — Atomic Inventory Reservation 
// Pre-load before flash sale starts (done once, before requests arrive)
// SET inventory:item:42 1000

async function reserveInventoryRedis(redisClient, itemId, orderId) {
  // DECR is atomic in Redis — no race condition possible
  const remaining = await redisClient.decr(`inventory:item:${itemId}`);

  if (remaining < 0) {
    // We went below zero — undo the decrement and reject
    await redisClient.incr(`inventory:item:${itemId}`);
    return { success: false, reason: 'SOLD_OUT' };
  }

  // Reservation tentatively accepted — confirm in DB within 30 seconds
  // Schedule async confirmation job
  await confirmationQueue.add({ itemId, orderId, expiresAt: Date.now() + 30_000 });

  return { success: true, reservationId: orderId };
}

// DB confirmation (runs asynchronously, at most 1000 times for 1000 units)
async function confirmReservationInDb(db, itemId, orderId) {
  try {
    await db.transaction(async (trx) => {
      // Write the durable reservation record
      await trx('inventory_reservations').insert({
        item_id: itemId,
        order_id: orderId,
        reserved_at: new Date(),
        status: 'CONFIRMED',
      });
    });
  } catch (err) {
    // Confirmation failed — undo the Redis decrement
    await redisClient.incr(`inventory:item:${itemId}`);
    throw err;
  }
}

Optimistic locking (for moderate concurrency, simpler systems)

SQL — Optimistic Locking with Version Column 
-- Add a version column to the inventory table
-- ALTER TABLE items ADD COLUMN version INTEGER NOT NULL DEFAULT 0;

-- On reservation attempt:
UPDATE items
SET quantity = quantity - 1, version = version + 1
WHERE id = ? AND version = ? AND quantity > 0;

-- If 0 rows affected: someone else updated first — retry with new version
-- Works well up to ~1,000 concurrent updates before retry storms degrade throughput
-- Never use this for flash sales at 100k concurrent requests

In the interview, walk through all three approaches in this order: naive (explain why it fails), SKIP LOCKED (explain when it works), Redis DECR (explain when it is required). This progression demonstrates that you know the trade-off space, not just one solution. An interviewer who asks "why not just use SKIP LOCKED?" is checking whether you know the throughput limits. The answer: SKIP LOCKED is excellent to about 5,000 reservations per second per database node; Redis DECR handles 100,000 per second on a single Redis node with sub-millisecond latency.

Code Reference

JavaScript: Saga Orchestrator Skeleton

This skeleton demonstrates the patterns discussed above in code: step definitions with execute and compensate functions, deterministic idempotency key generation, state persistence stubs, and compensation rollback on failure. In production, the orchestrator itself runs in a durable workflow engine such as Temporal. This code illustrates the shape of the logic, not the infrastructure.

JavaScript Example 
const crypto = require('crypto');

// Each step declares what it does and how to undo it.
// compensate() is called in reverse order when any step fails.
class SagaOrchestrator {
  constructor({ db, inventoryService, paymentService, fulfillmentService, notificationService }) {
    this.db = db;

    // Steps execute in order. Compensations run in reverse on failure.
    this.steps = [
      {
        name: 'validateCart',
        execute: async (ctx) => {
          const cart = await db.query(
            'SELECT * FROM carts WHERE id = $1 FOR SHARE', [ctx.cartId]
          );
          if (!cart) throw new Error('Cart not found or expired');
          ctx.cart = cart;
          await db.updateOrderState(ctx.orderId, 'CART_VALIDATED');
        },
        // Nothing durable was changed — no compensation needed
        compensate: async (_ctx) => {},
      },
      {
        name: 'reserveInventory',
        execute: async (ctx) => {
          // Idempotency key: same orderId always maps to the same reservation attempt
          const idempotencyKey = generateKey('reserve', ctx.orderId);
          const reservation = await inventoryService.reserve({
            orderId: ctx.orderId,
            items: ctx.cart.items,
            idempotencyKey,
          });
          ctx.reservationId = reservation.id;
          await db.updateOrderState(ctx.orderId, 'INVENTORY_RESERVED');
        },
        compensate: async (ctx) => {
          if (!ctx.reservationId) return; // step never succeeded — nothing to undo
          const idempotencyKey = generateKey('release', ctx.orderId);
          await inventoryService.release({ reservationId: ctx.reservationId, idempotencyKey });
          await db.updateOrderState(ctx.orderId, 'INVENTORY_RELEASED');
        },
      },
      {
        name: 'processPayment',
        execute: async (ctx) => {
          const idempotencyKey = generateKey('charge', ctx.orderId);
          const charge = await paymentService.charge({
            orderId: ctx.orderId,
            amount: ctx.cart.totalAmount,
            customerId: ctx.customerId,
            idempotencyKey,
          });
          ctx.chargeId = charge.id;
          await db.updateOrderState(ctx.orderId, 'PAYMENT_CONFIRMED');
        },
        compensate: async (ctx) => {
          if (!ctx.chargeId) return;
          const idempotencyKey = generateKey('refund', ctx.orderId);
          await paymentService.refund({ chargeId: ctx.chargeId, idempotencyKey });
          await db.updateOrderState(ctx.orderId, 'PAYMENT_REFUNDED');
        },
      },
      {
        name: 'createFulfillment',
        execute: async (ctx) => {
          const fulfillment = await fulfillmentService.create({
            orderId: ctx.orderId,
            items: ctx.cart.items,
            shippingAddress: ctx.shippingAddress,
          });
          ctx.fulfillmentId = fulfillment.id;
          await db.updateOrderState(ctx.orderId, 'FULFILLMENT_IN_PROGRESS');
        },
        compensate: async (ctx) => {
          if (!ctx.fulfillmentId) return;
          await fulfillmentService.cancel({ fulfillmentId: ctx.fulfillmentId });
          await db.updateOrderState(ctx.orderId, 'FULFILLMENT_CANCELLED');
        },
      },
      {
        name: 'sendNotification',
        execute: async (ctx) => {
          // Dedup key prevents duplicate emails from Kafka at-least-once delivery
          const dedupKey = generateKey('notify-confirm', ctx.orderId);
          await notificationService.sendOrderConfirmation({
            orderId: ctx.orderId,
            customerId: ctx.customerId,
            dedupKey,
          });
          await db.updateOrderState(ctx.orderId, 'CONFIRMED');
        },
        // Cannot unsend the confirmation email — compensate by sending cancellation
        compensate: async (ctx) => {
          const dedupKey = generateKey('notify-cancel', ctx.orderId);
          await notificationService.sendOrderCancellation({
            orderId: ctx.orderId,
            customerId: ctx.customerId,
            dedupKey,
          }).catch((err) => {
            // Notification failure during compensation must not block the rollback
            console.error('[Saga] Cancellation notification failed (non-blocking):', err.message);
          });
        },
      },
    ];
  }

  // Deterministic idempotency key: same inputs always produce the same key
  // Safe to re-execute the same step after a crash
  generateKey(operation, orderId) {
    return crypto.createHash('sha256')
      .update(`${operation}:${orderId}`)
      .digest('hex');
  }

  async runSaga(orderId, context) {
    const ctx = { orderId, ...context };
    const executedSteps = [];

    await this.db.updateOrderState(orderId, 'PENDING');

    for (const step of this.steps) {
      try {
        await step.execute(ctx);
        executedSteps.push(step); // track for rollback
      } catch (err) {
        console.error(`[Saga] Step "${step.name}" failed for order ${orderId}: ${err.message}`);
        // Roll back all completed steps in reverse order
        await this.rollback([...executedSteps].reverse(), ctx, orderId);
        await this.db.updateOrderState(orderId, 'CANCELLED');
        throw err; // Surface to caller so they can return an error to the user
      }
    }

    return { success: true, orderId, state: 'CONFIRMED' };
  }

  async rollback(stepsToCompensate, ctx, orderId) {
    await this.db.updateOrderState(orderId, 'CANCELLING');
    for (const step of stepsToCompensate) {
      try {
        await step.compensate(ctx);
      } catch (compensationErr) {
        // Compensation failure requires human intervention — alert on this
        console.error(
          `[Saga] COMPENSATION FAILED for step "${step.name}" on order ${orderId}.`,
          `Manual intervention required. Error: ${compensationErr.message}`
        );
        // Continue compensating other steps despite this failure
      }
    }
  }
}

module.exports = { SagaOrchestrator };
Interview Playbook

Interview Checklist — What to Say in Each Phase

A 45-minute system design interview has a predictable structure. Interviewers expect you to drive the pacing. If you are waiting to be told what to do next, you are not at L5. Here is what to say in each phase.

Phase 1: First 10 minutes — requirements and scoping

  • Open with: "Before I start designing, I want to clarify the requirements."
  • Ask scale, consistency, flash sale, and payment integration questions.
  • Explicitly state what is in scope and what is out of scope.
  • Close with: "I'll design for 1M DAU, 10k peak orders per second, strong inventory consistency with no oversell, and Stripe integration. Does that framing sound right?" Wait for confirmation.

Phase 2: Core design — the 5 trade-offs to discuss

  • Saga choreography vs orchestration: choose orchestration, explain why (centralized state, debuggable, handles complex compensation).
  • Synchronous vs asynchronous payment: synchronous for better UX (immediate feedback), asynchronous for higher availability (don't block if payment gateway is slow).
  • Strong vs eventual consistency on inventory: strong means no oversell (Redis DECR), eventual means higher throughput but occasional over-reservation that requires post-hoc cancellation.
  • Monolith vs microservices for initial deployment: at early stage, a modular monolith with clear subdomain boundaries is lower-risk; decompose when independent deployability becomes the bottleneck.
  • CQRS read model vs direct DB queries: CQRS for order history and dashboards (read-heavy, span multiple services), direct DB for immediate post-order confirmation (strong consistency required).

Phase 3: Scale discussion — bottlenecks to name proactively

  • Inventory service under flash sale: Redis DECR pre-allocation — do not wait for the interviewer to ask.
  • Order database under write load: shard by order ID or customer ID; most queries are customer-scoped.
  • Payment gateway rate limits: queue and retry with exponential backoff; do not hit the gateway directly from the Saga without rate awareness.
  • Notification storm: asynchronous Kafka consumer, separate queue, per-customer rate limit to prevent notification fatigue.

The 3 things not to say

  • "I'd just use a single database transaction for the order, payment, and inventory." — Distributed transactions across service boundaries do not exist. Saying this reveals that you do not know what you are designing around.
  • "We'd fix the race condition later once we hit scale." — If you can identify the race condition (and interviewers will expect you to), you must explain how to prevent it. Deferring a known correctness problem signals that you are not thinking about production reliability.
  • "I'd use microservices for everything from day one." — Premature decomposition is expensive. Saying this without qualification signals over-engineering instinct rather than judgment. Always acknowledge the monolith-first option and state when you would decompose.

FAQ

Common Interview Questions

Q: Should I use a Saga or a two-phase commit (2PC) for order processing?

Never propose 2PC across microservices in a production design. Two-phase commit is synchronous, blocks all participants for the duration of the transaction, and fails non-atomically if the coordinator crashes mid-commit — leaving participants in an indeterminate state. Kafka cannot participate in XA protocols at all, so any design that includes Kafka makes 2PC impossible on the event publishing path. Saga with idempotent compensating transactions provides eventual consistency without blocking. Use 2PC only within a single database instance, where it is the standard operation of a local transaction.

Q: How do I handle the case where the Saga Orchestrator itself crashes mid-execution?

The orchestrator persists every state transition to the database before executing the next step — using the transactional outbox pattern so both state and any outbound event are written atomically. On restart, the orchestrator queries for all orders in intermediate states (PENDING, INVENTORY_RESERVED, PAYMENT_INITIATED) and re-executes their current step using the same idempotency key that was assigned before the crash. Because all step calls are idempotent, re-executing a step that may have already succeeded returns the same result without duplicating the action. In production, use a durable workflow engine such as Temporal to handle this automatically rather than building crash recovery from scratch.

Q: Is the transactional outbox pattern overkill for a small team?

For a startup with fewer than 10,000 orders per day running a monolith: yes, it adds complexity that may not be worth the operational overhead at that scale. Use synchronous writes and accept the occasional inconsistency until you observe the failure mode in production. For any system at 100,000 orders per day or more with microservices: the transactional outbox is not overkill — it is the minimum viable guarantee for event-to-state consistency. The failure mode it prevents (order state updated but event not published, or event published but state not updated) occurs in production under load and is difficult to diagnose without it.

Q: In the interview, should I choose choreography or orchestration and how do I defend it?

Choose orchestration for the order flow and defend it on three grounds. First, operational debuggability: you need to be able to query "why is order X stuck at step Y" without correlating logs across four services. Second, compensation clarity: the rollback path for a payment-succeeded/inventory-failed scenario needs a clear coordinator — choreography leaves compensation to each service to figure out independently, which creates gaps. Third, business criticality: when a failure means a customer is charged but receives no goods, you need the tightest possible control over the compensation path. Acknowledge that choreography has real advantages (no coupling point, easier to add new consumers) and would be appropriate for non-critical async flows like analytics or notification fan-out.

Key Takeaways

What This Interview Tests

The e-commerce order processing question is not a test of how many services you know. It is a test of whether you understand that distributed transactions do not exist across service boundaries — and whether you know the specific failure modes that follow from that fact. The Saga pattern, transactional outbox, idempotency keys, and Redis inventory reservation are not patterns to memorize. They exist because specific failure modes occur in production without them: double charges from network retries, stuck orders from mid-saga crashes, event/state divergence from non-atomic writes, and inventory oversell from concurrent SQL updates. The strongest answers at L5 and L6 do not just name these patterns. They explain which failure each pattern prevents, what constraint it imposes (eventual consistency, extra infrastructure, added latency), and how the constraint is justified by the failure severity. If you can narrate the system from the perspective of "what can go wrong here and why does this component prevent it," you are thinking at the right level. That is the conversation the interviewer is trying to have with you.
