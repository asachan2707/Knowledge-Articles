Interview framework

How to solve any system design problem in 3 steps

Step 1 — Understand the problem

Clarify functional requirements (what the system does) and non-functional requirements (scale, latency, consistency, availability). Don't design before you know the constraints.

Step 2 — Break into sub-problems

Decompose by domain. For an e-commerce system: Product Listing, Search, Orders, Payments. Resist the urge to solve the whole thing at once.

Step 3 — Address 4 dimensions for each sub-problem

  • Database: SQL or NoSQL? Which specific DB? Schema design?
  • Caching: What to cache? TTL? Invalidation strategy?
  • Scaling & fault tolerance: Horizontal or vertical? Replication strategy?
  • Communication: Synchronous REST API or asynchronous message broker?

The trap: Only create sub-sub-problems when genuinely necessary. Over-engineering in an interview signals unclear thinking, not depth.

The RESHADED Framework for System Design Interviews

True system design mastery means approaching an unfamiliar problem, identifying real constraints, making architectural decisions, explaining costs, and adapting when requirements shift. The RESHADED framework structures this process.

RESHADED: Requirements → Estimation → Storage → High-level design → APIs → Detailed design → Evaluation → Distinctive considerations

Requirements-First Architecture

Numbers matter only when they change a decision:

  • Read/write ratio → caching strategy choice
  • Object size → storage and bandwidth tier
  • Write throughput → partitioning necessity
  • "I chose Cassandra because this feels like a Cassandra kind of day" — wrong answer

Failure-Driven Design Evolution (Social Feed Example)

// Each "version" represents a failure discovered and fixed
const socialFeedEvolution = [
  {
    version: 1,
    problem:  "User requests their feed → query all follows → join posts → slow",
    solution: "Add Redis cache for pre-computed feeds",
    tradeoff: "Cache invalidation complexity; eventual consistency on feed"
  },
  {
    version: 2,
    problem:  "Cache misses on cold-start; all users hit DB simultaneously",
    solution: "Pre-compute feeds asynchronously on post creation (push model)",
    tradeoff: "Storage cost grows with follower count; write amplification"
  },
  {
    version: 3,
    problem:  "Celebrity with 10M followers triggers 10M cache writes per post",
    solution: "Hybrid: push to regular users (≤ N followers), pull for celebrities",
    tradeoff: "Two code paths; fan-out threshold is a tunable parameter"
  },
  {
    version: 4,
    problem:  "Global users see stale feeds due to cross-region replication lag",
    solution: "Regional leader-follower replication with read-your-writes guarantee",
    tradeoff: "Cross-region writes add latency; consistency model per operation"
  }
];

// The interviewer is testing whether you can trace this evolution
// Not whether you can recite "version 3" from memory
socialFeedEvolution.forEach(({ version, problem, solution, tradeoff }) => {
  console.log(`v${version}: Problem → ${problem}`);
  console.log(`       Solution → ${solution}`);
  console.log(`       Tradeoff → ${tradeoff}\n`);
});

Practical checklist

System Design Decision Checklist

  • Define your SLO before choosing a database — consistency requirements determine CP vs AP trade-off.
  • Measure current bottleneck before optimizing — profile queries with EXPLAIN ANALYZE before adding caching layers.
  • Start with a SQL database unless you have a specific reason for NoSQL — PostgreSQL handles 10k req/s on a single server with proper indexing.
  • Use consistent hashing when planning to shard — range sharding with hash sharding creates rebalancing problems when nodes change.
  • Always implement rate limiting at the API gateway layer — application-layer rate limiting is a second line of defense, not the primary.
  • Add a message queue only when you have identified a real need: decoupling teams, absorbing spikes, or tasks exceeding the user's patience time (~2s).
  • Implement all three observability pillars (logs, metrics, traces) from day one — retrofitting distributed tracing is painful.
  • Design for at-least-once message delivery and make consumers idempotent — exactly-once is too expensive for most systems.
  • Test your failover procedure before you need it — active-passive failover that has never been exercised is not a failover plan.
  • Document your CAP trade-offs explicitly — future engineers should not have to reverse-engineer why you chose Cassandra over PostgreSQL.
Common questions

FAQ

  • Do I need to know all of this before I start building real systems?

    No. Know the basics (servers, scaling, caching, databases) and learn the rest when a real problem demands it. Most teams don't need Kafka or Raft until they're processing millions of events per second. Build, hit the wall, then reach for the next tool.

  • When should I use NoSQL instead of PostgreSQL?

    When your schema is genuinely unpredictable, your write throughput exceeds what a single Postgres master can handle, or you need built-in horizontal sharding. For most applications, Postgres with read replicas and proper indexing handles far more than engineers expect.

  • What's the difference between partitioning and sharding?

    Partitioning splits a table into sub-tables on the same server — the database engine handles routing transparently. Sharding splits data across different servers — your application code must know which shard to route each query to. Partitioning is simpler; sharding is more powerful but far more complex to operate.

  • Should I start with microservices or a monolith?

    Almost always start with a monolith. Microservices solve organisational and scaling problems that don't exist at the beginning. Premature microservices add distributed systems complexity (network calls, partial failures, data consistency) before you have the team size or traffic that justifies it.

  • Is eventual consistency safe for financial systems?

    Generally no. Financial ledgers require strong consistency — you cannot allow two ATMs to read a balance, both see $100, and both allow a $90 withdrawal (resulting in -$80). Banks use linearizable databases (or strict serializable transactions in SQL) for balance operations. However, some read paths (e.g., showing a user their transaction history) can tolerate eventual consistency.

  • When should I add Redis to my stack?

    Redis earns its place when you have: (a) session data that does not fit in-process due to multiple service instances, (b) a cache hit rate > 80% for a frequently-accessed dataset, (c) a specific Redis data structure need (Sorted Sets for leaderboards, Pub/Sub for real-time events, Streams for lightweight message queuing). Do not add Redis simply because "it will make things faster" — measure first.

  • What is the practical difference between p50, p95, and p99 latency?

    p50 is median — 50% of requests complete in this time or less. p95 means 95% of requests complete in this time. p99 means 99% do. If p50 is 20ms and p99 is 2000ms, you have a tail latency problem affecting 1% of users — at 1,000 req/s, that is 10 users per second experiencing 2-second responses. p99 is the latency your worst-affected users experience; optimize for it in customer-facing systems.

  • How do I decide between Kafka and SQS?

    Use Kafka when: multiple independent consumers need to independently read the same events (fan-out with different processing logic), you need replay (re-read historical events), you need message ordering within a partition, or you need high throughput (millions of events per second). Use SQS when: you want managed infrastructure with minimal ops overhead, you have a simple task-queue pattern with one consumer per message, or you do not need replay or fan-out.
