REST vs GraphQL vs gRPC

Three API styles compared, with Netflix's REST to GraphQL Federation journey.

2 min read · topic 1 of 6 in APIs

REST

  • Standard HTTP verbs + resource URLs
  • Stateless, cacheable
  • Simple uniform interface
  • May over-fetch / under-fetch
  • Best for: public APIs, simple CRUD, microservices

GraphQL

  • Single endpoint — client specifies exact fields
  • No over-fetching / under-fetching
  • Supports subscriptions (real-time)
  • Complex caching, shifts logic to client
  • Best for: frontend-heavy apps, rapidly evolving UI

gRPC

  • Protocol Buffers over HTTP/2
  • Strongly typed IDL (.proto files)
  • Bi-directional streaming
  • Smaller payload, faster than JSON
  • Best for: internal microservices, low-latency RPC

Netflix evolved: REST → BFF with Groovy/RxJava → GraphQL Federation. DGS (Domain Graph Services) own their schema; the gateway federates. Client specifies exactly what it needs, eliminating overfetch at TV/mobile/web scale.
