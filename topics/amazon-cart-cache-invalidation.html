Amazon Cart Shows Old Data: System Design Deep Dive on Cache Invalidation and Distributed Session Consistency

Why removing a cart item on mobile shows it again on desktop. A deep technical analysis: cache-aside with version vectors, pub/sub invalidation buses, Redis Hash data structures, eventual vs strong consistency trade-offs, and the full distributed session architecture that prevents stale reads at Amazon scale.

Domain: System Design · Caching · Distributed Systems Credit: CodeFarm (Medium) Published: 2026-07-22

"There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton. The Amazon cart stale-data problem is the canonical real-world manifestation of the first one. You remove an item on your phone. You open your laptop. The item is back. The source of truth (the database) is correct, but the cache serving your laptop's request has not been told yet.

The key insight: The cart is not one cached object — it is a distributed object replicated across potentially dozens of cache nodes in different regions. A write on one device must invalidate every copy of the cart, on every cache node, before the next read on any other device. The design question is how to do this without making reads and writes prohibitively slow.

Story · The Prime Day cart that kept resurrecting items

During Prime Day, a user removed an out-of-stock item from their cart on mobile, saw the cart update, and proceeded to the next product page. They opened the cart on their desktop browser 30 seconds later — the removed item was back. They removed it again. Checked on mobile — the desktop removal had not propagated yet. The item appeared and disappeared three times across two devices before finally stabilising.

What happened: mobile removal wrote to the database and invalidated the mobile-side cache node. The desktop was served by a different cache node in a different AZ. The invalidation event propagated via an async message bus with a 45-second lag during Prime Day traffic. Every read during that 45-second window served stale data.

The Cart Data Model at Scale

Amazon's cart is stored in a distributed key-value store (DynamoDB or a similar system) with the following logical structure: 

// Cart data model
{
  userId: "usr_789xyz",
  version: 42,                  // logical clock — increments on every write
  lastModified: 1721654400000,  // epoch ms
  items: {
    "prod_A1": { quantity: 2, addedAt: ..., price: 29.99 },
    "prod_B2": { quantity: 1, addedAt: ..., price: 14.99 }
  },
  sessionMetadata: {
    deviceId: "iphone_14_pro_abc",
    region: "ap-south-1"
  }
}

In Redis, the cart is stored as a Hash per userId:

  • Key: cart:{userId}
  • Fields: one per product ID, value = JSON-encoded item metadata
  • Extra field: _version — incremented atomically on every write
  • Extra field: _lastModified — epoch timestamp for TTL-free staleness detection

Using a Hash instead of a String means individual items can be updated with HSET/HDEL without serialising/deserialising the entire cart. For a cart with 50 items, this reduces serialisation cost by ~50×.

Cache Invalidation Strategies

1. Cache-Aside (Read Path)

On every read: check cache first. On miss: read from DynamoDB, populate cache with a TTL. Simple. The problem: TTL-based expiry is coarse. A 5-minute TTL means stale data for up to 5 minutes. Acceptable for product descriptions; not acceptable for cart state.

2. Write-Through (Write Path)

On every write: update both the database and the cache synchronously. Strong consistency — the cache is always current. Cost: every write pays double latency. For cart operations (add, remove, update quantity), this latency is usually acceptable.

3. Write-Behind / Write-Back

Write to cache first; flush to database asynchronously. Higher write throughput, but a crash between cache write and DB flush loses data. Not suitable for cart — lost items = lost revenue.

4. Event-Driven Invalidation (the Amazon approach)

On any cart mutation: write to the database, then publish a cart-invalidated:{userId} event to a pub/sub bus (Redis Pub/Sub, Kafka, or SNS). All cache nodes subscribed to that user's invalidation topic delete their copy of the cart. The next read on any node triggers a fresh DB fetch.

JavaScript Example — Cart Mutation with Cache Invalidation 
// cart-service.js — Node.js + ioredis + DynamoDB
import Redis from 'ioredis';
const redisPub = new Redis(process.env.REDIS_URL);
const redisSub = new Redis(process.env.REDIS_URL); // separate connection for sub
const redisCache = new Redis(process.env.REDIS_URL);

const CART_TTL = 3600; // 1hr — fallback TTL even with event-driven invalidation
const INVALIDATION_CHANNEL = 'cart-invalidation';

// Subscribe to invalidation events (all cache nodes run this)
redisSub.subscribe(INVALIDATION_CHANNEL, (err) => {
  if (err) console.error('Subscribe failed:', err.message);
});
redisSub.on('message', async (channel, message) => {
  if (channel !== INVALIDATION_CHANNEL) return;
  const { userId, version } = JSON.parse(message);
  const cacheKey = `cart:${userId}`;
  // Only delete if our cached version is <= the invalidation version
  const cachedVersion = await redisCache.hget(cacheKey, '_version');
  if (!cachedVersion || parseInt(cachedVersion) <= version) {
    await redisCache.del(cacheKey);
    console.log(`[cache] Invalidated cart:${userId} at version ${version}`);
  }
});

async function updateCart(userId, productId, quantity) {
  // 1. Write to DynamoDB (source of truth)
  const newVersion = await writeCartToDB(userId, productId, quantity);

  // 2. Update local cache (write-through for this node)
  const cacheKey = `cart:${userId}`;
  if (quantity === 0) {
    await redisCache.hdel(cacheKey, productId);
  } else {
    await redisCache.hset(cacheKey, productId, JSON.stringify({ quantity }));
  }
  await redisCache.hset(cacheKey, '_version', newVersion);
  await redisCache.expire(cacheKey, CART_TTL);

  // 3. Publish invalidation to all other cache nodes
  await redisPub.publish(INVALIDATION_CHANNEL,
    JSON.stringify({ userId, version: newVersion }));
}

async function getCart(userId) {
  const cacheKey = `cart:${userId}`;
  const cached = await redisCache.hgetall(cacheKey);

  if (cached && Object.keys(cached).length > 1) { // has items beyond metadata
    return parseCart(cached);
  }
  // Cache miss — fetch from DynamoDB
  const cart = await fetchCartFromDB(userId);
  if (cart) {
    await hydrateCache(cacheKey, cart);
  }
  return cart;
}

Distributed Session Consistency: The Multi-Device Problem

The cart is associated with a user, not a session. A user may have 4 active sessions: phone, tablet, laptop, smart TV. Each may be served by a different backend node in a different region, with its own local Redis cache.

The conflict model

Concurrent writes from multiple devices create conflicting versions. Without a conflict resolution strategy, last-write-wins can silently discard cart additions from one device.

Version vectors (Amazon's actual approach)

Each device maintains its own version counter. The cart is annotated with a vector of { deviceId: version } pairs. On merge:

  1. Compare version vectors.
  2. If one dominates (all entries ≥ the other), take the dominant version.
  3. If they are concurrent (neither dominates), merge using application-specific logic (for carts: union of items; for removals: removals win — "add-wins" causes ghost items, "remove-wins" is safer).

Session affinity as a partial fix

Sticky sessions route all requests from one user to the same cache node. This eliminates cross-node stale reads at the cost of load balancing flexibility. Amazon does NOT use sticky sessions for cart reads — it uses event-driven invalidation instead.

Failure Modes and Production Gotchas

  • Invalidation event lost — the pub/sub message drops (Redis Pub/Sub has no persistence guarantees). Fix: fallback TTL on all cache entries (1hr max) so no entry is stale forever; also run a periodic revalidation job for high-value carts (carts with items ≥ checkout threshold).
  • Split-brain between write and invalidation publish — DB write succeeds, invalidation publish fails. Next read on another node serves stale data. Fix: wrap write + publish in the Outbox pattern. The relay guarantees eventual publish.
  • Cache stampede on high-profile sale — many users open the same product's cart simultaneously after a stale TTL expires. Fix: "probabilistic early expiration" — start background refresh when remaining TTL < 20% with small probability.
  • Version counter overflow — version is a 32-bit int on many systems; at high write rates it wraps around. Use 64-bit integers or timestamps as logical clocks.
  • Bloom filter false positives — a Bloom filter can confirm an item is NOT in the cart (for quick "does this user have items?" checks) but cannot confirm it IS. Never use a Bloom filter for positive cart membership — it will generate false positives and trigger unnecessary DB reads.

Key Takeaway

Stale cart data is not a bug in the cart service — it is an expected property of a distributed cache. The architecture should make stale windows explicit, bounded, and bounded differently for different operations: eventual consistency (< 2s) for display, strong consistency for checkout. Event-driven invalidation via pub/sub shrinks the stale window; version vectors resolve concurrent writes from multiple devices; and the Outbox pattern ensures invalidation events are never silently dropped.
