Kafka Deep Dive: Event Ordering, Duplicate Processing, and Offset Management

Two of the most common Kafka production bugs, covered in one definitive guide. Events arriving out of sequence and the same event being processed twice are not random failures — they are predictable consequences of misusing Kafka's guarantees. This article explains exactly why they happen and how to prevent them with the right partition key strategy, offset commit discipline, and idempotent consumer design.

Domain: System Design · Kafka · Event Streaming · Distributed Systems Published: 2026-07-29
Story 1 · "Order Delivered" before "Order Shipped"

An e-commerce platform publishes lifecycle events — ORDER_PLACED, ORDER_SHIPPED, ORDER_DELIVERED — to a Kafka topic. A notification service consumes those events and sends push notifications to customers. One morning, customers started receiving "Your order has been delivered!" messages before "Your order has shipped!" messages. Some customers called support in a panic, convinced the courier had marked a delivery incorrectly.

The root cause: the partition key was userId, not orderId. Three consecutive events for the same order landed on three different partitions — each with its own independent commit log and its own independent consumer thread. Thread 2 (the DELIVERED event) simply ran faster than Thread 1 (the SHIPPED event) that day under load.

Story 2 · Payment processed twice

A payments team built a Kafka consumer that processed PAYMENT_INITIATED events and debited customer accounts. During a deployment, the consumer crashed between processing an event and committing its offset. On restart, Kafka replayed from the last committed offset — the consumer saw the same PAYMENT_INITIATED event again and debited the customer a second time.

With auto-commit enabled (the default), the offset had not yet been committed — auto-commit runs on a timer, not on successful processing. The team had unknowingly accepted at-least-once delivery without building an idempotent consumer to handle it. The fix was not to prevent replays (you cannot), but to make the consumer safe to replay.

Kafka's Core Guarantees (and Limits)

Kafka makes strong guarantees — but only within specific scopes. Understanding where the guarantees apply (and where they do not) is the foundation of every design decision below.

Within-partition ordering guarantee

Kafka guarantees that messages within a single partition are stored and delivered in the order they were produced. This is the only ordering guarantee Kafka makes. There is no ordering guarantee across partitions. A topic with 6 partitions has 6 independent, ordered commit logs. A consumer reading from all 6 partitions sees events in an interleaved sequence that respects per-partition order but not global order.

Mental model: Think of a topic as a set of N conveyor belts (partitions), each moving in order. Messages placed on the same belt stay in order relative to each other. Messages placed on different belts have no ordering relationship — the belts move at independent speeds.

At-least-once delivery by default

By default, a Kafka consumer with enable.auto.commit=true (the default) commits offsets on a timer (auto.commit.interval.ms, default 5 seconds). If the consumer processes a message and crashes before the timer fires, the offset is not committed. On restart, the consumer group resumes from the last committed offset — replaying messages that were already processed. This is at-least-once delivery: every message is guaranteed to be processed at least once, but possibly more than once.

What an offset actually is

An offset is a monotonically increasing integer that identifies a message's position within a partition. The first message in a partition has offset 0; the next has offset 1, and so on. Offsets are per-partition — partition 0 has its own offset sequence, partition 1 has its own, they are independent.

Consumer groups track their read progress using the internal topic __consumer_offsets. When a consumer commits an offset, it writes (group-id, topic, partition) → committed-offset into this topic. On restart or rebalance, the group resumes each partition from the last committed offset.

Consumer groups and partition assignment

A consumer group is a set of consumer instances that together consume all partitions of a topic. Kafka assigns each partition to exactly one consumer instance in the group at any point in time. If there are 6 partitions and 3 consumer instances, each instance handles 2 partitions. If an instance dies, Kafka triggers a rebalance and redistributes its partitions to surviving instances. Rebalances are a major source of ordering and duplicate problems — covered in detail below.

The Ordering Problem

Wrong partition key causes cross-partition ordering failures

Kafka routes messages to partitions using a hash of the message key: partition = hash(key) % numPartitions. Messages with the same key always land on the same partition and are therefore ordered relative to each other. Messages with different keys may land on different partitions — and Kafka makes no ordering promise between them.

The canonical mistake: using userId as the partition key for order lifecycle events. A user may have multiple orders in flight simultaneously. Events for order-A and order-B both hash to the same partition (same userId), but the events for a single order are not guaranteed to be on the same partition relative to each other if you accidentally use different keys.

Worse: if the producer sends events for the same order without a key (null key), Kafka uses round-robin or sticky partitioning — the ORDER_PLACED, ORDER_SHIPPED, and ORDER_DELIVERED events for order 123 end up on partitions 0, 3, and 5 respectively. Each partition's consumer processes them independently and at different speeds.

Rebalancing breaks ordering mid-stream

Even with a correct partition key, rebalances introduce a window of risk. When a consumer instance is added, removed, or crashes, Kafka reassigns partitions. During the rebalance, no consumer is actively polling. After the rebalance, a partition that was being processed by Consumer A may now be handled by Consumer B, starting from the last committed offset. If Consumer A had not committed an offset mid-batch, Consumer B replays those messages — and if Consumer A had partially processed them, Consumer B processes the same events again.

Incremental Cooperative Rebalancing (available since Kafka 2.4, enabled via CooperativeStickyAssignor) mitigates this by only moving partitions that need to move, instead of revoking all partitions. This drastically reduces the rebalance window and associated replay risk.

Partition Key Selection Strategy

Choose the key that defines your ordering domain

The partition key should be the entity whose events must be ordered relative to each other. Ask: "For what unit does the order of events matter to my consumer?" That unit is your partition key.

  • E-commerce order lifecycle → orderId. All events for a single order land on the same partition, in production order.
  • Chat messages in a conversation → conversationId. All messages in the same conversation are ordered; conversations are independent.
  • User activity events → userId (if you need per-user ordering) or sessionId (if sessions are independent).
  • Financial ledger entries for an account → accountId.

Hot partition trade-off

Choosing a good ordering key may create hot partitions. A highly active user, a viral product, or a single merchant with millions of transactions all produce more events than average for their key — concentrating traffic on one partition. Mitigation strategies:

  • Sub-key salting: append a suffix orderId + "-" + (random % N) to spread load, but accept that you lose strict ordering within the spread (only works when strict ordering is not required).
  • Partition count scaling: more partitions dilutes hot keys — but Kafka does not automatically rebalance existing data when you add partitions. New messages for a key hash to a new partition; old messages stay.
  • Application-level sequencing: use sequence numbers inside the event payload (see below) and let the consumer enforce ordering even after a hot partition is split.

Sequence numbers as a secondary guarantee

Even with the correct partition key, producer retries can cause out-of-order delivery within a partition if the idempotent producer is not enabled. Add a sequenceNumber field to every event payload, scoped to the ordering domain (e.g., per orderId). The consumer tracks the last-seen sequence number and can detect gaps or out-of-order arrivals.

  "eventId": "evt-8f3a2c",
  "orderId": "ORD-12345",
  "sequenceNumber": 3,         // 1=PLACED, 2=SHIPPED, 3=DELIVERED
  "eventType": "ORDER_DELIVERED",
  "timestamp": "2026-07-29T10:30:00Z"

Event buffering with a sequence-aware consumer

When strict ordering is required and late arrivals are possible, implement a consumer-side sequence buffer. The consumer holds events that arrive with a gap in the sequence, waiting for the missing events before processing the buffered batch.

JavaScript Example — Sequence-Aware Consumer Buffer 
// sequence-buffer.js — Node.js
class OrderEventBuffer {
  constructor({ maxWaitMs = 5000, onProcess }) {
    this.buffers = new Map();   // orderId → { nextExpected, pendingEvents, timeoutId }
    this.maxWaitMs = maxWaitMs;
    this.onProcess = onProcess; // callback for in-order events
  }

  receive(event) {
    const { orderId, sequenceNumber } = event;

    if (!this.buffers.has(orderId)) {
      this.buffers.set(orderId, { nextExpected: 1, pending: new Map() });
    }

    const state = this.buffers.get(orderId);

    if (sequenceNumber === state.nextExpected) {
      // In-order arrival — process immediately, then drain any buffered successors
      this._processAndDrain(orderId, event);
    } else if (sequenceNumber > state.nextExpected) {
      // Out-of-order — buffer and start a wait timer if not already running
      state.pending.set(sequenceNumber, event);
      if (!state.timeoutId) {
        state.timeoutId = setTimeout(() => this._forceFlush(orderId), this.maxWaitMs);
      }
    }
    // sequenceNumber < nextExpected → duplicate, discard
  }

  _processAndDrain(orderId, event) {
    const state = this.buffers.get(orderId);
    this.onProcess(event);
    state.nextExpected++;

    // Drain any buffered in-order successors
    while (state.pending.has(state.nextExpected)) {
      const next = state.pending.get(state.nextExpected);
      state.pending.delete(state.nextExpected);
      this.onProcess(next);
      state.nextExpected++;
    }

    if (state.pending.size === 0 && state.timeoutId) {
      clearTimeout(state.timeoutId);
      state.timeoutId = null;
    }
  }

  _forceFlush(orderId) {
    // Gap in sequence — process buffered events in order despite the gap, alert monitoring
    const state = this.buffers.get(orderId);
    const sorted = [...state.pending.values()].sort((a, b) => a.sequenceNumber - b.sequenceNumber);
    console.warn(`[sequence-buffer] Gap detected for order ${orderId}. Force-flushing ${sorted.length} events.`);
    for (const event of sorted) {
      this.onProcess(event);
    }
    this.buffers.delete(orderId);
  }
}

// Usage
const buffer = new OrderEventBuffer({
  maxWaitMs: 5000,
  onProcess: (event) => notificationService.send(event),
});

kafkaConsumer.on('message', (msg) => {
  const event = JSON.parse(msg.value);
  buffer.receive(event);
});

// OrderEventProducer.java
import org.apache.kafka.clients.producer.*;
import com.fasterxml.jackson.databind.ObjectMapper;

@Service
public class OrderEventProducer {

    private final KafkaProducer<String, String> producer;
    private final ObjectMapper mapper = new ObjectMapper();

    public OrderEventProducer() {
        Properties props = new Properties();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        // Enable idempotent producer — prevents duplicate messages due to producer retries
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
        props.put(ProducerConfig.ACKS_CONFIG, "all");
        props.put(ProducerConfig.RETRIES_CONFIG, Integer.MAX_VALUE);
        this.producer = new KafkaProducer<>(props);
    }

    public void publishOrderEvent(OrderEvent event) throws Exception {
        // KEY = orderId — ensures all events for the same order go to the same partition
        // WRONG would be: key = userId (different orders of the same user could be on different partitions)
        String key = event.getOrderId();
        String value = mapper.writeValueAsString(event);

        ProducerRecord<String, String> record = new ProducerRecord<>("order-events", key, value);
        producer.send(record, (metadata, exception) -> {
            if (exception != null) {
                log.error("Failed to send event for order {}: {}", event.getOrderId(), exception.getMessage());
            } else {
                log.info("Event {} sent to partition {} offset {}",
                    event.getEventType(), metadata.partition(), metadata.offset());
            }
        });
    }
}

The Duplicate Processing Problem

The exact failure sequence

Understanding duplicates requires tracing the precise sequence of operations between poll, process, and commit: 

1. Consumer calls poll() — Kafka returns messages [offset 100, 101, 102]
2. Consumer processes offset 100 — writes to DB, calls payment API  ✓
3. Consumer processes offset 101 — writes to DB, calls payment API  ✓
4. Consumer processes offset 102 — writes to DB, calls payment API  ✓
5. Consumer is about to call commitSync(offset=103)
6. JVM crashes / OOM kill / network failure / deployment restart
7. On restart, consumer resumes from last committed offset: 100
8. Consumer processes offset 100 again — payment API called TWICE  ✗

This is not a bug — it is exactly what Kafka's at-least-once delivery guarantee means. The responsibility for handling replay is always on the consumer.

Auto-commit timing issues

With enable.auto.commit=true (the default), Kafka commits the offset automatically every auto.commit.interval.ms milliseconds (default: 5000ms). Auto-commit happens at the start of the next poll() call if the interval has elapsed — it commits whatever offset was returned by the previous poll. This means auto-commit does not know whether your application has finished processing the batch. A slow consumer that takes 10 seconds to process a batch will never see the auto-commit fire mid-batch — commit only happens when poll() is called again.

Dangerous pattern: Handing messages to a thread pool and returning from the poll() loop immediately. The auto-commit fires when the next poll() is called, before the thread pool has finished processing the previous batch. Messages can be committed before being processed, causing at-most-once delivery (loss on crash), not at-least-once.

commitSync vs commitAsync trade-offs

Manual commit gives you control over exactly when the offset is committed, but you must choose between blocking and non-blocking behaviour:

  • commitSync() — blocks until the broker acknowledges the commit. Retries automatically on transient failures. Safest for correctness; throughput impact depends on broker round-trip time. Use when losing the commit would cause downstream harm (financial transactions, billing).
  • commitAsync() — non-blocking, fires and forgets. Faster throughput, but does not retry on failure (retrying an async commit can commit a stale offset if a later commit already succeeded). Use with a failure callback that logs or alerts. Suitable for high-throughput analytics pipelines where occasional replay is acceptable.
Java Example — Manual Commit with commitSync 
// ManualCommitConsumer.java
import org.apache.kafka.clients.consumer.*;

@Service
public class PaymentEventConsumer {

    public void run() {
        Properties props = new Properties();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "payment-processor");
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false); // CRITICAL: disable auto-commit
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");

        try (KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props)) {
            consumer.subscribe(List.of("payment-events"));

            while (true) {
                ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(1000));

                for (ConsumerRecord<String, String> record : records) {
                    try {
                        processPaymentEvent(record.value());
                    } catch (Exception e) {
                        // Log and dead-letter — do NOT commit if processing failed
                        deadLetterQueue.send(record, e);
                        continue;
                    }
                }

                // Commit AFTER successfully processing the entire batch
                // commitSync() blocks and retries until the broker confirms
                try {
                    consumer.commitSync();
                } catch (CommitFailedException e) {
                    log.error("Commit failed — rebalance occurred: {}", e.getMessage());
                    // The partition was reassigned. The new owner will re-process from last committed offset.
                }
            }
        }
    }

    // commitAsync alternative — higher throughput, use for non-critical pipelines
    private void commitAsync(KafkaConsumer<String, String> consumer) {
        consumer.commitAsync((offsets, exception) -> {
            if (exception != null) {
                log.error("Async commit failed for offsets {}: {}", offsets, exception.getMessage());
                metrics.increment("kafka.commit.failure");
            }
        });
    }
}

Delivery Semantics Comparison

Semantic Mechanism Failure Behaviour Trade-off When to Use
At-most-once Commit offset before processing (or fire-and-forget without waiting for ACK) Messages can be lost on crash Lowest latency, no duplicates, but data loss possible Metrics, logs, analytics — where occasional loss is acceptable
At-least-once Commit offset after successful processing; retry on failure Messages replayed on crash — may be processed more than once No data loss, but consumer must handle duplicates (idempotency required) Most business events — notifications, order updates, audit logs
Exactly-once Kafka transactions: atomic commit of consumed offset + produced output Transactional — commit succeeds or entire transaction is rolled back No loss, no duplicates; performance overhead (~20–30% throughput reduction); only works within Kafka ecosystem Financial processing, billing, inventory deduction — zero tolerance for duplicates

Idempotent Consumer Patterns

An idempotent consumer produces the same outcome whether it processes an event once or ten times. This is the practical solution to at-least-once delivery. There are three main approaches:

Pattern 1: Redis Deduplication

Store processed event IDs in Redis with a TTL. Before processing any event, check if it was already processed. The SET NX command is atomic — it sets the key only if it does not exist, making the check-and-mark operation race-condition-free.

JavaScript Example — Redis Dedup 
// kafka-consumer-dedup.js — Node.js + ioredis
import Redis from 'ioredis';
const redis = new Redis(process.env.REDIS_URL);

const DEDUP_TTL_SECONDS = 86400; // 24 hours — events older than this won't be replayed anyway

async function processWithDedup(event) {
  const dedupeKey = `seen:${event.eventId}`;

  // SET key 1 EX 86400 NX — atomic: set only if not exists, with 24h TTL
  const isNew = await redis.set(dedupeKey, '1', 'EX', DEDUP_TTL_SECONDS, 'NX');

  if (!isNew) {
    console.log(`[dedup] Skipping duplicate event: ${event.eventId}`);
    return { skipped: true };
  }

  // Event is new — process it
  await processPayment(event);
  return { processed: true };
}

// Kafka consumer loop
for await (const { message } of consumer.run()) {
  const event = JSON.parse(message.value.toString());
  await processWithDedup(event);
  await consumer.commitOffsets([{ ...message.offset }]);
}

Pattern 2: Database Unique Constraint

Use the event ID as a unique key in the target database table. Any attempt to insert a duplicate event will fail with a unique constraint violation — handle it gracefully as a skip.

Java Example — DB Unique Constraint Dedup 
// PaymentEventProcessor.java — PostgreSQL + JDBC
@Transactional
public void processPaymentEvent(PaymentEvent event) {
    try {
        // Insert into processed_events first — will throw on duplicate
        jdbcTemplate.update(
            "INSERT INTO processed_events (event_id, processed_at) VALUES (?, NOW())",
            event.getEventId()
        );

        // Only reaches here if event_id was not already present
        accountService.debitAccount(event.getAccountId(), event.getAmount());
        ledgerService.record(event);

    } catch (DuplicateKeyException e) {
        // event_id already exists in processed_events → duplicate replay
        log.warn("Duplicate event {} — skipping", event.getEventId());
        // Do not rethrow — this is expected behaviour
    }
}

// SQL: create the constraint
// CREATE TABLE processed_events (
//   event_id   VARCHAR(64) PRIMARY KEY,
//   processed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
// );
// The PRIMARY KEY constraint provides both dedup and the unique guarantee.

Pattern 3: Natural Idempotency

Some operations are naturally safe to repeat. Design your business logic to be idempotent without external dedup state:

  • Upsert instead of insert: INSERT ... ON CONFLICT (id) DO UPDATE SET status = EXCLUDED.status — re-applying the same update is a no-op if the value is unchanged.
  • Set operations instead of increments: Instead of UPDATE balance = balance - 100 (wrong on replay), store the final target state: UPDATE balance = 900 WHERE event_id = ? AND balance != 900.
  • Conditional transitions: UPDATE orders SET status = 'shipped' WHERE id = ? AND status = 'placed' — replaying a SHIPPED event on an already-shipped order is a safe no-op.
JavaScript Example — Conditional State Transition (Natural Idempotency) 
// order-status-updater.js
async function handleOrderShipped(event) {
  const { orderId, trackingNumber } = event;

  // Safe to replay: only transitions if still in 'placed' state
  const result = await db.query(
    `UPDATE orders
     SET status = 'shipped', tracking_number = $1, shipped_at = NOW()
     WHERE order_id = $2 AND status = 'placed'
     RETURNING order_id`,
    [trackingNumber, orderId]
  );

  if (result.rowCount === 0) {
    // Either order doesn't exist, or status is already 'shipped' / 'delivered'
    // Both cases are safe to ignore — idempotent no-op
    console.log(`[idempotent] No update needed for order ${orderId} — already beyond 'placed' state`);
    return;
  }

  await notificationService.sendShippedEmail(orderId);
}

Exactly-Once with Kafka Transactions

Kafka's transactional API provides exactly-once semantics within the Kafka ecosystem: a consumer reads messages, transforms them, and produces output — all in an atomic transaction. Either everything commits together or nothing does.

The key primitive is sendOffsetsToTransaction(), which atomically commits the consumed offset alongside the produced messages in a single transaction. If the producer crashes mid-transaction, the partially written data is invisible to consumers with isolation.level=read_committed.

Java Example — Kafka Transactional Producer (Read-Process-Write) 
// TransactionalPaymentProcessor.java
Properties producerProps = new Properties();
producerProps.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
producerProps.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "payment-processor-txn-1"); // unique per instance
producerProps.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
producerProps.put(ProducerConfig.ACKS_CONFIG, "all");

KafkaProducer<String, String> producer = new KafkaProducer<>(producerProps);
producer.initTransactions(); // registers this transactional.id with the broker

Properties consumerProps = new Properties();
consumerProps.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
consumerProps.put(ConsumerConfig.GROUP_ID_CONFIG, "payment-txn-group");
consumerProps.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
consumerProps.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed"); // skip uncommitted messages

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(consumerProps);
consumer.subscribe(List.of("payment-initiated"));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));

    producer.beginTransaction();
    try {
        for (ConsumerRecord<String, String> record : records) {
            PaymentEvent event = deserialize(record.value());
            PaymentResult result = paymentGateway.charge(event);

            // Produce the result to output topic — part of the same transaction
            producer.send(new ProducerRecord<>("payment-completed", event.getOrderId(),
                serialize(result)));
        }

        // Atomically commit: consumed offsets + produced messages in one transaction
        // If this succeeds, offsets AND output are visible together.
        // If this fails, NEITHER is committed — consumer replays from last committed offset.
        Map<TopicPartition, OffsetAndMetadata> offsets = currentOffsets(consumer, records);
        producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());

        producer.commitTransaction();

    } catch (ProducerFencedException | OutOfOrderSequenceException e) {
        // Fatal — another instance with the same transactional.id took over
        producer.close();
        throw e;
    } catch (Exception e) {
        producer.abortTransaction(); // rolls back produced messages + offset commit
        log.error("Transaction aborted, will replay: {}", e.getMessage());
    }
}

private Map<TopicPartition, OffsetAndMetadata> currentOffsets(
        KafkaConsumer<?,?> consumer, ConsumerRecords<?,?> records) {
    Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
    for (TopicPartition partition : records.partitions()) {
        long lastOffset = records.records(partition).stream()
            .mapToLong(ConsumerRecord::offset).max().orElseThrow();
        offsets.put(partition, new OffsetAndMetadata(lastOffset + 1));
    }
    return offsets;
}

Kafka Streams: exactly_once_v2

Kafka Streams applications can opt into exactly-once processing with a single configuration change. The v2 variant (available since Kafka 2.5) uses a new epoch-based fencing mechanism that eliminates the need for a dedicated transaction coordinator per stream task and significantly reduces overhead compared to the original exactly_once (now deprecated). 

// Kafka Streams application.properties
processing.guarantee=exactly_once_v2
# Requires: Kafka broker >= 2.5, replication.factor >= 3 for internal topics

// Java — StreamsConfig
Properties streamsConfig = new Properties();
streamsConfig.put(StreamsConfig.APPLICATION_ID_CONFIG, "order-processor");
streamsConfig.put(StreamsConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
streamsConfig.put(StreamsConfig.PROCESSING_GUARANTEE_CONFIG,
    StreamsConfig.EXACTLY_ONCE_V2); // "exactly_once_v2"

KafkaStreams streams = new KafkaStreams(topology, streamsConfig);
streams.start();

Limitation: Kafka's exactly-once guarantee is scoped to Kafka-to-Kafka operations. If your consumer calls an external HTTP API, writes to a database, or sends an email — those side effects are outside the transaction boundary. For those cases, you still need idempotent consumers (Patterns 1–3 above). Exactly-once only prevents duplicate Kafka messages, not duplicate external effects.

Best Practices Checklist

  1. Choose partition key by ordering domain, not by convenience. Use the entity ID whose events must be sequenced (orderId, conversationId, accountId). Never use a null key for topics where order matters.
  2. Enable idempotent producer. Set enable.idempotence=true on all producers. This prevents duplicate messages caused by producer retries at zero extra cost (Kafka 3.x enables this by default).
  3. Disable auto-commit for any consumer with side effects. Set enable.auto.commit=false and use commitSync() after successfully processing each batch. Auto-commit's timer-based behaviour is incompatible with safe at-least-once processing.
  4. Make every consumer idempotent. Choose one of the three patterns — Redis dedup, DB unique constraint, or natural idempotency — and apply it consistently. At-least-once delivery is guaranteed; your consumer must handle it.
  5. Include eventId in every event payload. A globally unique, stable event identifier is the prerequisite for all deduplication strategies. Use UUIDs generated by the producer, not by the consumer.
  6. Include sequenceNumber scoped to the ordering domain. A monotonically increasing sequence number per entity (orderId, accountId) lets consumers detect gaps and out-of-order arrivals even when the partition key is correct.
  7. Use CooperativeStickyAssignor to minimize rebalance disruption. Configure partition.assignment.strategy=CooperativeStickyAssignor to avoid revoking all partitions during rebalances. This reduces the replay window and improves consumer group stability.
  8. Dead-letter queue for poison pills. Never let a message that cannot be processed block the consumer indefinitely. After N retries, route to a DLQ topic. Monitor the DLQ — a growing DLQ is a signal of a schema change, data corruption, or a downstream service failure.
  9. Use exactly-once (Kafka transactions) only when external idempotency is impossible. Kafka transactions have overhead and complexity. Most applications are better served by at-least-once + idempotent consumers. Reserve transactions for financial or inventory systems where external idempotency is impractical.
  10. Monitor consumer group lag, not just throughput. Rising consumer lag is the first sign of a processing bottleneck, a poison pill loop, or a rebalance storm. Set alerts on lag thresholds (e.g., lag > 10,000 for more than 5 minutes) per consumer group and partition.

Key Takeaway

Kafka does not deliver globally ordered, exactly-once messages out of the box — and that is a deliberate design choice that enables its horizontal scalability. The framework's contract is clear: within-partition ordering, at-least-once delivery by default. Both the ordering and duplicate problems stem from not designing within these constraints.

The ordering problem is solved at the producer: choose the partition key to be the entity whose events must be sequenced. Add sequence numbers as a belt-and-suspenders guarantee. The duplicate problem is solved at the consumer: disable auto-commit, commit after processing, and make every consumer idempotent. Kafka transactions provide exactly-once when you need it — but most systems do not, because a well-designed idempotent consumer is simpler and nearly as safe.
