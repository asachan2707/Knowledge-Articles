Spec-Driven Development with Claude Code: The SPEC.md Pattern, and How GSD, Spec Kit, OpenSpec and Taskmaster AI Compare

AI coding sessions follow a predictable degradation curve: sharp focus at the start, gradual drift in the middle, incoherence by hour three. The cause is not the model — it is the absence of a persistent spec that survives beyond the context window. Spec-Driven Development (SDD) fixes this. Here is the pattern, the spec format, how to structure Claude Code sessions so quality holds for hours, not minutes, and how the four main SDD tools (GSD, Spec Kit, OpenSpec, Taskmaster AI) differ so you can pick the right one.

Applies toClaude Code, Cursor, any long-running AI coding session

The hour-three problem is so consistent it is almost a law: start an AI coding session on a non-trivial feature, and by the third hour the model is contradicting its own earlier decisions, asking for context you already provided, or drifting away from the architecture it established an hour ago. Most developers blame the model. The actual cause is the session structure — specifically, the absence of a spec.

Core idea: SDD tools are session state managers, not code generators. A context window is not a project memory. It is a sliding window that forgets. Spec-Driven Development moves the project state out of the context window and into a persistent, structured spec file. The context window reads from the spec; it doesn't store it. Tools differ in who writes the spec, what format it takes, and how tightly the agent is bound to it.

The degradation curve explained

What actually happens inside a 3-hour session

Hour 0: Session start — fresh, sharp, coherent

Full context available. The model holds the entire problem clearly. Decisions are deliberate. Architecture choices are explained. Code quality is high.

Hour 1: Middle phase — compression begins

Earlier turns start getting compressed. The specific error message from 40 turns ago is summarised away. The architectural decision from turn 12 is no longer verbatim. The model is reasoning from summaries, not from original constraints.

Hour 2: Drift — re-learning what was established

The model starts asking for context you gave in hour one. It makes decisions that contradict hour-one architecture. If you don't notice and correct immediately, the codebase accumulates contradictions.

Hour 3: Incoherence — what you end up with

The code works on the happy path but has inconsistent error handling, mixed patterns, and architectural decisions that conflict. Debugging it requires understanding two separate mental models of the same system.

The cure is not shorter sessions. Long sessions are where most of the value is. The cure is externalising state — writing down every decision, constraint, and progress marker so the model reads from the file rather than from its compressed memory.

The pattern behind every SDD tool

Spec-Driven Development — the pattern, not the tool

The externalised-state idea has four steps, and every SDD tool implements some version of them:

  1. Define the spec. A structured document that includes: what to build, what constraints apply, what's already done, what the next action is, and what "done" looks like for each piece.
  2. Ground the agent in the spec. Every agent session starts by loading the spec. The agent's first job is to orient against the spec, not dive into code.
  3. Update the spec as work progresses. Completed tasks get marked. New decisions get recorded. The spec is the source of truth, not the agent's context window.
  4. Resume from the spec. When a session ends (or an agent loses context), the next session picks up from the spec, not from memory.

The spec format

What a good SDD spec contains

A spec is not a PRD or a design doc. It is a session state file — a minimal structure that lets an agent orient itself, know what's done, and know what's next, without any prior context.

The minimal spec — five required sections

<!-- SPEC.md — the only file Claude Code needs to resume any session -->

# Webhook Service — Spec

## What we're building
An idempotent Stripe webhook handler. Receives events, verifies signatures,
processes payment_intent.succeeded and charge.refunded events, records every
event in webhook_events table, sends to dead-letter queue on failure.

## Stack & constraints
- Node.js 22 / TypeScript 5 strict
- Express 5, Prisma ORM, BullMQ, PostgreSQL
- All DB access via src/db/ modules — no raw SQL outside db layer
- No console.log — always src/lib/logger.ts
- Every DB write in a transaction
- Tests must pass before any commit

## Architecture decisions (record every non-obvious decision here)
- Using express.raw() before JSON middleware — Stripe needs raw body for signature verification
- Processing in BullMQ worker, not inline — allows retries without re-calling Stripe
- Idempotency check BEFORE processing — prevents duplicate writes under concurrent webhook delivery
- Dead-letter queue threshold: 3 failures — Stripe also retries, so we don't need more

## Progress
### Done
- [x] Express route POST /webhooks/stripe
- [x] Stripe signature verification middleware (src/middleware/stripeSignature.ts)
- [x] BullMQ worker setup (src/workers/webhookWorker.ts)
- [x] Idempotency check layer (src/db/webhookEvents.ts)

### In progress
- [ ] payment_intent.succeeded handler — needs order update + email trigger

### TODO
- [ ] charge.refunded handler
- [ ] Dead-letter queue consumer
- [ ] Integration tests (6 test cases defined in SPEC_TESTS.md)

## Current task
Implement payment_intent.succeeded handler in src/handlers/paymentSucceeded.ts.
- Update order status to 'paid' via src/db/orders.ts
- Trigger email via src/services/email.ts
- Both in a single transaction — if email fails, do NOT roll back order update
- Record success in webhook_events table
The SDD session protocol

How to structure every Claude Code session

Session start (always)

// What you say at the start of every session:
"Read SPEC.md. Orient yourself on where we are (Progress section).
Your current task is in the 'In progress' section.
Before writing any code, confirm your understanding of the current task
and the constraints in the Architecture Decisions section."

// Why this works:
// - Forces the model to read the spec before touching any file
// - The confirmation step catches misunderstandings before they become code
// - Architecture decisions section prevents hour-three re-invention

During the session

// Tell the model to update the spec as it works
"After completing the current task, update SPEC.md:
1. Move the completed task from 'In progress' to 'Done'
2. If you made any non-obvious architectural decisions, add them to Architecture Decisions
3. Move the next TODO item to 'In progress'
Do this BEFORE writing the implementation — not after."

// Why before: updating the spec first forces the model to think about the task
// as a whole before diving into implementation detail. It's a forcing function
// for planning, not just executing.

Mid-session recovery (when you notice drift)

// When the model starts drifting, use this:
"Stop. Read SPEC.md Architecture Decisions section.
Explain how your last response is consistent with decision [X].
If it's not, revise the response before continuing."

// The key insight: don't just say "you got that wrong" — point to the spec.
// The spec is the source of truth. Referring to it directly re-grounds the model.

Session end

// At the end of every session:
"Update SPEC.md before we close:
1. Mark completed tasks as done
2. Add any new architectural decisions made this session
3. Update 'Current task' to the next unblocked item
4. If you discovered any constraints we should add, add them to the Constraints section"

// This 2-minute close ensures the next session can start immediately
// with accurate state — no re-reading commits or reconstructing what happened.
CLAUDE.md integration

Wiring SDD into every project automatically

# CLAUDE.md — project-level SDD configuration

## Spec-Driven Development

This project uses SPEC.md as the single source of truth for session state.

### At the start of every session (mandatory)
1. Read SPEC.md fully — especially Architecture Decisions and Current Task
2. Confirm your understanding of the current task before writing code
3. Do NOT start implementing without this step

### During a session
- Update SPEC.md's Progress section as you complete tasks
- Add architectural decisions to SPEC.md as you make them — don't wait until the end
- If a task requires a decision not covered by SPEC.md, add it before implementing

### When you encounter a conflict
If you are about to do something that contradicts SPEC.md Architecture Decisions:
1. STOP
2. Re-read the relevant decision
3. Either follow the decision or explicitly ask whether to update it
Never silently override a spec decision

### Recovery prompt (if context seems corrupted)
"Ignore everything in our conversation history. Read SPEC.md and resume from Current Task."

## Files never to modify without updating spec
- Any file listed in SPEC.md's Architecture Decisions section
- src/lib/logger.ts — this is shared infrastructure
- src/db/ — all DB changes require spec update first
JavaScript: spec validation tool

Validate spec consistency with a small script

// scripts/validate-spec.js — catch spec drift before it becomes code drift
import fs   from 'fs/promises';
import path from 'path';
import { glob } from 'glob';

async function validateSpec(specPath = 'SPEC.md') {
  const spec     = await fs.readFile(specPath, 'utf8');
  const issues   = [];

  // Check 1: every file mentioned in spec actually exists
  const fileRefs = spec.match(/src\/[^\s`\]]+\.[jt]sx?/g) ?? [];
  for (const ref of fileRefs) {
    try   { await fs.access(ref); }
    catch { issues.push(`Missing file referenced in spec: ${ref}`); }
  }

  // Check 2: no task is both "Done" and "In progress"
  const doneSection    = spec.match(/### Done\n([\s\S]*?)(?=###|$)/)?.[1] ?? '';
  const progressSection = spec.match(/### In progress\n([\s\S]*?)(?=###|$)/)?.[1] ?? '';
  const doneTasks      = [...doneSection.matchAll(/\[x\] (.+)/g)].map(m => m[1].trim());
  const progressTasks  = [...progressSection.matchAll(/\[ \] (.+)/g)].map(m => m[1].trim());

  for (const t of progressTasks) {
    if (doneTasks.includes(t)) issues.push(`Task appears in both Done and In Progress: "${t}"`);
  }

  // Check 3: "Current task" matches something in In progress
  const currentTask = spec.match(/## Current task\n([\s\S]*?)(?=##|$)/)?.[1].trim();
  if (currentTask && progressTasks.length > 0) {
    const matched = progressTasks.some(t => currentTask.toLowerCase().includes(t.toLowerCase().slice(0,30)));
    if (!matched) issues.push('Current task does not match any In Progress item');
  }

  if (issues.length === 0) {
    console.log('✓ SPEC.md is consistent');
    return true;
  }

  console.error(`SPEC.md has ${issues.length} issue(s):`);
  issues.forEach(i => console.error(`  ✗ ${i}`));
  return false;
}

const ok = await validateSpec();
process.exit(ok ? 0 : 1);
The tool landscape

GSD, Spec Kit, OpenSpec, Taskmaster AI — what each one is

GSD (Get Stuff Done)

Execution-first, minimal ceremony

GSD generates a TASKS.md file from a short natural language description. Focus is on getting a task list out of your head and into a format the agent can check off. Minimal spec overhead — GSD's "spec" is really a tasklist with just enough context.

Best for: solo devs, small features, rapid iteration

Spec Kit

Template-driven, team-oriented

Spec Kit provides opinionated spec templates covering requirements, architecture decisions, API contracts, and test plans. Output is a structured directory (specs/) with separate files per concern. Designed for teams where specs need review before execution.

Best for: team projects, feature specs that need review

OpenSpec

Schema-first, validation-enforced

OpenSpec defines a JSON/YAML schema for specs and validates agent output against it. Agents must produce structured output that matches the spec schema. Tightest coupling between spec and agent — the spec IS the contract, not a suggestion.

Best for: multi-agent systems, quality-gate pipelines

Taskmaster AI

PRD-to-tasks AI pipeline

Taskmaster takes a Product Requirements Document (PRD) as input, calls an AI to decompose it into an ordered task graph with dependencies, complexity estimates, and implementation notes. The richest context per task — but requires a PRD first.

Best for: large features, when you have a PRD or can write one

In practice

What each tool looks like in a Claude Code session

GSD — the fast path

// GSD workflow: fast from description to tasks
// 1. Run: gsd init "add idempotent webhook handler for Stripe payment events"
// 2. GSD generates TASKS.md

// TASKS.md (auto-generated by GSD)
# Webhook Handler — Stripe Payment Events

## Status: In Progress

### Tasks
- [x] Set up Express route POST /webhooks/stripe
- [x] Add Stripe signature verification middleware
- [ ] Implement idempotency check (DB lookup by event.id before processing)
- [ ] Add payment_intent.succeeded handler
- [ ] Add dead-letter queue for failed events
- [ ] Write integration tests

## Constraints
- TypeScript strict mode
- All DB access via src/db/ modules

// 3. In Claude Code: "read TASKS.md and continue from the current task"
// Claude picks up from the first unchecked task.
// Fast, low ceremony, good for single-dev work.

OpenSpec — the validation path

// OpenSpec: schema defines what "done" means — agent output validated against it
// specs/webhook-handler.spec.yaml

name: webhook-handler
version: "1.0"
description: Idempotent Stripe webhook processing

requirements:
  functional:
    - id: F1
      description: Verify Stripe signature on every request
      acceptance: Returns 400 with error body when signature invalid
    - id: F2
      description: Idempotency check before processing
      acceptance: Second call with same event.id returns 200 but makes no DB writes

  non_functional:
    - id: NF1
      description: P99 response latency < 500ms
    - id: NF2
      description: All errors logged with event.id for traceability

implementation:
  tasks:
    - id: T1
      title: Signature verification middleware
      requirement_refs: [F1]
      status: done
      artifacts:
        - path: src/middleware/stripeSignature.ts
          type: implementation
        - path: src/middleware/__tests__/stripeSignature.test.ts
          type: test

  validation:
    - each task must reference at least one requirement
    - artifacts must exist at specified paths before status can be "done"

// OpenSpec validates that the code files actually exist before marking tasks done.
// Tightest coupling — agent can't "mark done" without producing the right artifacts.
Decision guide

How to choose

  • Use GSD if you want to start coding in under 5 minutes, you're working alone, and the feature is small to medium. GSD's value is speed of setup, not depth of structure.
  • Use Spec Kit if you're on a team and want specs to be reviewable artifacts in pull requests. The template structure maps well to how product and engineering teams already communicate.
  • Use OpenSpec if you're building a multi-agent system or want schema-validated proof that requirements are met before merging. Overkill for solo work; essential for automated quality gates.
  • Use Taskmaster AI if you have a large feature (20+ tasks), you already have a PRD or can write one in 30 minutes, and you want the agent to understand task dependencies. The richer per-task context dramatically reduces context drift on long features.

The hybrid that works: Many teams use Taskmaster to decompose features and generate the initial task graph, then drop into GSD-style TASKS.md for daily execution. Heavy decomposition once; light execution every session.

Integration with Claude Code

Loading a tool-managed spec (Taskmaster example) into Claude Code sessions

// CLAUDE.md — wire any SDD tool into every session
## Spec-Driven Development

This project uses Taskmaster AI for task management.

### Session start (always do this first)
Run `taskmaster status` to see current task state.
Never start implementing without reading the current task first.

### During implementation
- Work on one task at a time
- Mark tasks done only when tests pass: `taskmaster set-status --id  --status done`
- If you discover a new task not in the graph: `taskmaster add-task --prompt "..."`
- If blocked: mark as blocked with a reason, don't skip

### Context loss recovery
If you lose context mid-session:
1. Run `taskmaster status` — this gives you the full current state
2. Run `taskmaster show --id ` — this gives full task context
3. Continue from there. Never restart from scratch.

## DO NOT
- Start a new feature without checking if a task exists for it
- Mark a task done before its tests pass
- Implement tasks out of dependency order

Key Takeaways

  • AI coding sessions fall apart at hour three because the context window is not a project memory. SDD externalises state into a SPEC.md that the agent reads at the start of every session.
  • The spec's five sections (what / stack-constraints / decisions / progress / current-task) plus the session protocol (orient from spec, update as you go, close with a spec update) let every session resume with accurate state.
  • All four SDD tools solve the same root problem and differ in ceremony, team fit, and binding strength: GSD is fastest for solo work, Spec Kit is team-native, OpenSpec is the strictest quality gate, Taskmaster AI gives the richest per-task context for large features.
  • Choose by team size, feature complexity, and how much upfront structure you will invest; a common hybrid is Taskmaster for decomposition and GSD-style TASKS.md for daily execution.
