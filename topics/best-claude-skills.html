Claude Skills: The Best Ones and How to Build Them Well

What 100 field-tested Claude Skills taught one author about which categories actually save time, combined with the Skills 2.0 engineering toolkit (Skill-Creator, progressive disclosure, evals) for writing skills that trigger correctly and stay reliable.

Sources Medium · Artificial Corner (The PyCoach, Apr 2026); DEV Community (Gao Dalie, Pasquale Pillitteri, 2026)
Focus Best skill categories, SKILL.md design, evals, A/B testing, progressive disclosure

Claude Skills are reusable instruction packs — a folder containing a SKILL.md file, optional scripts, and reference assets — that teach Claude to follow your formatting rules, brand standards, and repeatable workflows. Done well, they turn a generalist chatbot into a deterministic assistant for a specific job. Skills 2.0 then took the format from a clever trick to a real engineering surface.

Core idea: the best Claude Skills do not try to be clever. They narrow the problem, constrain the output, make the result predictable, and are tested like code. Anthropic itself found bugs in 5 of 6 of its own skills when it ran evals against them.

Story · Why this experiment matters

Most "100 things I tried" articles are filler. The reason this one is different is that the author actually ran each Skill against real work, then asked one specific question: would I use this again on Monday?

That single filter killed most of the list. What survived was a small set of Skills that the author kept quietly enabling for client deliverables — not because they were impressive, but because they had stopped being noticeable. That is the bar.

What Claude Skills actually are

Reusable instructions that change Claude’s default behavior

A Skill is essentially a portable, composable capability pack. At minimum it is a SKILL.md file that tells Claude when the skill applies, what it should do, what format the output should follow, and what tools or files it can use. Optional scripts and reference docs let the skill behave more like a small program than a prompt.

To enable Skills, the article points users to Settings → Capabilities → Skills, then Preferences → Skills to browse and install ones that match their workflow. Once installed, Claude quietly invokes the right Skill when the task matches its description.

Skills 2.0 · What changed

The first wave of Claude Skills felt like elaborate prompts. Skills 2.0 added a Skill-Creator (a meta-skill that drafts and iterates skills for you), progressive disclosure so context windows stay clean even with dozens of skills installed, and a built-in eval system that tests skills the way you would test code.

That shift turned skills into something you can ship, version, and improve — not something you write once and hope works.

Best skills in practice

The categories of Skills that consistently won

1. Presentations and visuals

The standout in this category is the Slide Deck Builder, which converts rough bullet points into a fully structured, visually styled presentation. It removes the two slowest parts of slide work: outlining and design. The article notes that decks produced this way are still editable, but feel ready-to-ship instead of ready-to-fix.

2. Marketing and brand-aligned content

The most useful marketing Skills enforce brand voice, color palette, formatting, and length constraints. Instead of producing generic AI copy, they produce copy that already passes a brand review, which is what actually saves time in a real team.

3. Business operations

Skills in this group automate repeating internal artifacts: meeting notes, status updates, weekly reports, customer summaries, and similar documents. The win is consistency. Every output looks the same, which makes it usable downstream.

4. No-code building and prototyping

Several Skills focus on turning a description into a working artifact: a one-pager, a small interactive tool, or a structured spec. These Skills shine when they have strong defaults and refuse to invent details you did not provide.

5. Coding and developer workflows

The best developer Skills are scoped narrowly: code review checklists, commit message generators, test scaffolders, refactor helpers. They do not try to “be a senior engineer.” They do one thing reliably.

What separates good Skills from bad ones

Design principles the top Skills shared

  • Treat context as scarce: they avoid loading huge instructions and only ask for what they need.
  • Narrow the problem precisely: a good Skill solves one well-defined task, not a vague category.
  • Prefer deterministic output over cleverness: the same input should produce the same shape of output.
  • Decompose large tasks: they break work into smaller, checkable steps instead of one giant prompt.
  • Include examples: few-shot patterns inside the skill anchor format and tone.
  • Fail loudly: when input is missing or ambiguous, they ask rather than hallucinate.

The article makes a sharp observation: most failed Skills are not failures of the model. They are failures of scope. Skills that try to be “a marketing assistant” are weaker than Skills that say “turn this rough changelog into a 5-bullet release tweet using our voice rules.”

The two skill types

Capability uplift vs encoded preferences

1. Capability uplift

Teaches Claude something it cannot do well by default — your proprietary testing framework, an internal DSL, or a specialized output format. The skill carries domain knowledge the base model does not have.

2. Encoded preferences

Sequences what Claude already knows into your specific workflow — your writing style, your folder conventions, your release process. The skill carries your taste, not new knowledge.

Most failed skills mix the two. The best skills pick one and commit.

Anatomy of SKILL.md

The two parts that matter most

A SKILL.md file has two critical parts. Get either wrong and the skill fails silently.

YAML frontmatter — loaded at startup

  • name — the skill's identifier and trigger.
  • description — when to use it. This is what Claude reads to decide whether to invoke the skill.
  • Optional: triggers, allowed-tools, context injection settings.

Main content — loaded only when triggered

  • Keep it under ~500 lines — past that, the skill becomes its own context problem.
  • Step-by-step instructions, not vague guidance.
  • Concrete examples (few-shot patterns anchor format and tone).
  • Use progressive disclosure: link to large reference files instead of inlining them.
A working SKILL.md

What a tight SKILL.md actually looks like

---
name: release-tweet
description: Convert a raw changelog into a 5-bullet release tweet
  in our brand voice. Use when input mentions "changelog",
  "release notes", or a list of merged PRs.
allowed-tools: []
---

# Release Tweet Composer

## Output format
- Exactly 5 bullets, each starting with a verb.
- 240 character total cap.
- No emojis. No marketing superlatives.
- Always end with the release version in parentheses.

## Refuse if
- The input has no version number.
- The input has no shipped features.
- The release is internal-only.

## Example
Input: "v2.4.0 — Added bulk import, fixed CSV parsing, ..."
Output:
- Add bulk import for CSV files
- Fix parsing on quoted fields
- ...
(v2.4.0)

Notice what is missing: cleverness. The skill does one task, with rules, with examples, with a refusal condition. That is exactly why it works.

Progressive disclosure

Why skills don't blow up your context

Progressive disclosure means the skill's frontmatter is loaded into Claude's awareness at all times, but the full body and any reference files only load when the skill is actually triggered. That is what makes 50+ installed skills feasible — only the active one occupies context.

Practically: keep frontmatter descriptions tight and unambiguous, push verbose details into the body, and push large references into linked files.

Knowledge vs action

Skills as the "action" layer next to RAG's "knowledge" layer

A base model plus retrieval gives you knowledge: it knows things, and RAG lets it look up your private facts. Neither guarantees that a job gets done the same way twice. Skills are the action layer. They package a procedure so the model repeats a routine task identically on Monday and on Friday, instead of improvising a new approach each run.

Rule of thumb: if the question is "what is true?", reach for retrieval. If it is "how do we always do this?", write a skill. Many real agents use both: RAG supplies the facts, a skill supplies the routine that consumes them.

Because a skill is just Markdown that lands in the context window, every line costs tokens. That is why the folder layout below is designed around loading as little as possible, as late as possible.

Anatomy of a skill folder

Three tiers of loading: catalog, body, resources

Keep one top-level skills/ directory and give every skill its own subfolder. The layout follows the open agentskills.io convention: 

skills/
  release-tweet/
    SKILL.md          # front matter + core instructions
    references/       # long, rarely needed detail (style guide, schemas)
      voice-rules.md
    scripts/          # deterministic helpers the agent runs, not re-derives
      count_chars.js
    assets/           # optional: templates, images, fixtures

Tier 1 · Catalog (always loaded)

Only name and description from each front matter block sit in the prompt. The model scans this short list to decide which skill, if any, is relevant. Dozens of skills cost a few hundred tokens.

Tier 2 · Body (loaded on a match)

Once a skill is chosen, its full SKILL.md is read. Keep it to the steps that are needed on every run.

Tier 3 · References and scripts (loaded on demand)

Anything long and only occasionally relevant moves into references/, with a one-line pointer in the body such as "for edge cases, read references/voice-rules.md". The model opens the file only when the situation calls for it. This extends the earlier point about linking large files instead of inlining them: the pointer is the mechanism that makes the third tier work.

Scripts and sandbox hygiene

Let code do the deterministic parts

LLMs are poor calculators and inconsistent counters. If a step has one correct answer (counting characters, validating a schema, converting units, rendering a file), put it in scripts/ and have the skill say "run this script" rather than "work it out". The output is then exact and repeatable, and the script's source never needs to occupy context; only its result does.

Running code the agent can reach brings its own discipline:

  • Vet before you execute: read third-party skill scripts like any dependency before allowing them to run.
  • Run in a sandbox: no access to your home directory, credentials, or unrestricted network.
  • Clean up after success: wipe the sandbox once a run completes so temp files and secrets cannot leak into the next task.
Runnable example

A tiny skill loader with lazy loading (Node 20+)

This loader builds the tier-1 catalog for a system prompt, then reads the body or a reference file only when asked. Save it as loader.mjs, put a skills/ folder beside it, and run node loader.mjs. If no skills folder exists it creates a sample one so the demo runs as is. 

loader.mjs
import { readdir, readFile, mkdir, writeFile, stat } from 'node:fs/promises';
import { join, resolve, sep } from 'node:path';

const ROOT = resolve('skills');

// Parse the leading "---" block; supports "key: value" and indented continuation lines.
function parseFrontMatter(text) {
  const m = text.match(/^---\r?\n([\s\S]*?)\r?\n---\r?\n?([\s\S]*)$/);
  if (!m) return { meta: {}, body: text };
  const meta = {};
  let key = null;
  for (const line of m[1].split(/\r?\n/)) {
    const kv = line.match(/^([A-Za-z][\w-]*):\s*(.*)$/);
    if (kv) { key = kv[1]; meta[key] = kv[2].trim(); }
    else if (key && /^\s+\S/.test(line)) meta[key] += ' ' + line.trim();
  }
  return { meta, body: m[2] };
}

// Tier 1: read front matter only; keep the file path so the body can load later.
export async function buildCatalog(root = ROOT) {
  const catalog = new Map();
  for (const entry of await readdir(root, { withFileTypes: true })) {
    if (!entry.isDirectory()) continue;
    const file = join(root, entry.name, 'SKILL.md');
    try {
      const { meta } = parseFrontMatter(await readFile(file, 'utf8'));
      if (!meta.name || !meta.description) {
        console.warn(`skip ${entry.name}: needs name and description`);
        continue;
      }
      catalog.set(meta.name, { dir: join(root, entry.name), file, description: meta.description });
    } catch (err) {
      if (err.code !== 'ENOENT') throw err;
    }
  }
  return catalog;
}

export function catalogPrompt(catalog) {
  const lines = [...catalog].map(([name, s]) => `- ${name}: ${s.description}`);
  return `Available skills (ask to load one by name):\n${lines.join('\n')}`;
}

// Tier 2: full body, only when the model picks this skill.
export async function loadSkill(catalog, name) {
  const s = catalog.get(name);
  if (!s) throw new Error(`Unknown skill: ${name}`);
  return parseFrontMatter(await readFile(s.file, 'utf8')).body.trim();
}

// Tier 3: a reference file, confined to the skill's own references/ folder.
export async function loadReference(catalog, name, relPath) {
  const s = catalog.get(name);
  if (!s) throw new Error(`Unknown skill: ${name}`);
  const refDir = join(s.dir, 'references');
  const target = resolve(refDir, relPath);
  if (!target.startsWith(refDir + sep)) throw new Error('Reference path escapes references/');
  return readFile(target, 'utf8');
}

async function seedDemo() {
  try { await stat(ROOT); return; } catch { /* create below */ }
  const dir = join(ROOT, 'release-tweet');
  await mkdir(join(dir, 'references'), { recursive: true });
  await writeFile(join(dir, 'SKILL.md'),
`---
name: release-tweet
description: Turn a raw changelog into a 5-bullet release tweet.
  Use when the input mentions release notes or merged PRs.
---
# Release Tweet
Exactly 5 bullets. For tone questions read references/voice-rules.md.
`);
  await writeFile(join(dir, 'references', 'voice-rules.md'), 'No emojis. Start bullets with verbs.\n');
}

// Demo
if (import.meta.url === `file://${process.argv[1]}`) {
  await seedDemo();
  const catalog = await buildCatalog();
  console.log(catalogPrompt(catalog));          // always in the prompt
  console.log('\n--- body (on demand) ---');
  console.log(await loadSkill(catalog, 'release-tweet'));
  console.log('--- reference (on demand) ---');
  console.log(await loadReference(catalog, 'release-tweet', 'voice-rules.md'));
}

Notice the path check in loadReference: a skill that can read arbitrary paths is a skill that can be tricked into reading secrets, which ties back to the sandbox rules above.

The 1% trick: evals

Test your skills like you test your code

Skills 2.0 ships a built-in eval system. It is the single biggest separator between skills that look good and skills that work.

  • Run test prompts against your skill and measure pass rate.
  • Detect regressions when you tweak the instructions.
  • Spot when the skill is no longer needed because the base model improved.
  • Blind A/B test the skill against raw Claude — sometimes raw is better.
  • Tune trigger accuracy — false fires waste tokens, missed fires waste the skill.

When Anthropic ran evals on its own bundled skills, it found problems in 5 of 6. If they need evals, so do you.

Practical learning

How to choose and write your own Skills

The most useful Skills tend to be the ones you would otherwise write a checklist for at work. If you keep re-explaining the same context to Claude — your tone, your folder structure, your output format — that is the exact shape of a good Skill.

  • Pick a task you do at least weekly that has a fixed shape.
  • Write the skill description as if onboarding a junior teammate, not a model.
  • Include 1–2 worked examples inside SKILL.md.
  • Define the output format strictly (fields, length, tone, structure).
  • Tell the Skill what to refuse or ask about, not just what to do.
  • Iterate by running it on real inputs and tightening the parts that drift.
Common questions

FAQ for teams adopting and authoring Skills

  • How are Skills different from custom GPTs or system prompts?

    Skills are scoped, file-based, composable, and version-controllable. A custom GPT is one big monolithic persona; a Skill is a small task. You can have dozens of Skills active and Claude picks the right one.

  • Do Skills work with the API or only the chat product?

    Skills are part of the Claude product surface. For pure API workflows you generally embed the same instructions directly in your prompts or system messages. The mental model is portable either way.

  • Should we share Skills across the team?

    Yes — that is where most of the value compounds. Treat them like internal tools: review them, version them, and keep a small README for each. A team-shared Skill is a reusable workflow.

  • When are Skills the wrong tool?

    When the task is genuinely creative, ambiguous, or one-off. Skills shine when the same shape of work repeats. For exploratory thinking, a normal conversation is still better.

  • How do I know my skill is auto-triggering correctly?

    Run the eval suite with prompts that should fire it and prompts that should not. The trigger accuracy metric is the number to optimize.

  • Is the Skill-Creator a substitute for writing my own?

    For first drafts, yes. For production-quality skills, no — it gives you a starting point you then have to scope, constrain, and eval.

  • When should I delete a skill?

    When evals show it does not beat raw Claude on the same input. Deleting unhelpful skills is part of maintaining the suite.

Key Takeaway

The best Claude Skills are not impressive demos. They are small, narrow, deterministic helpers that quietly remove repeated work. Most people write a skill once, declare victory, and never test it; the top 1% write a tight SKILL.md, scope the trigger, run evals, A/B test against raw Claude, and delete skills that stop earning their seat. Tight scope, predictable output, and disciplined testing — not creativity — are what make a skill worth keeping.
