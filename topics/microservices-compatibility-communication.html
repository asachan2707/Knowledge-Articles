Designing for Compatibility, Efficiency & Seamless Communication in Microservices

A practical guide to backward and forward compatibility, binary vs text encoding formats, and choosing the right communication protocol — HTTP, gRPC, WebSockets, or message brokers — for each inter-service use case. Drawn from Melik Karapetyan's LinkedIn guide inspired by Kleppmann's Designing Data-Intensive Applications.

SourceMelik Karapetyan · LinkedIn · Feb 2024
TagsArchitecture, System Design, Microservices, Communication
JS Example✓ Schema evolution safe updates, protocol comparison

Every microservice boundary is a contract. When that contract changes — a new field added, a type changed, a field removed — both sides of the boundary must remain operational. Getting this wrong causes silent data corruption, unexpected 500s, and deployment coordination nightmares. Getting it right means services can evolve independently without coordination.

Core idea: Treat every post-deployment field as optional. New code must tolerate missing old fields (backward compatibility). Old code must tolerate extra new fields (forward compatibility). This one rule eliminates most breaking changes without versioning APIs.

Story · The silent data corruption bug

A payment service deployed a new version that added a currency field to its order schema. The old order-processing service still wrote orders — but it did a full-row overwrite using its older schema. Every order written by the old service silently dropped the currency field that newer orders had set. The bug was invisible until a report showed all orders created during the 6-hour overlap window had no currency — and refund calculations were wrong.

The fix was architectural: partial updates only, never full-row overwrites. A rule that should have been in the service contract from day one.

1 — Compatibility

Backward vs Forward Compatibility

TypeDefinitionHow to achieve it
Backward compatibilityNew code reads data written by old codeNew fields must be optional; handle missing fields gracefully
Forward compatibilityOld code reads data written by new codeOld code must ignore unknown fields; only update known fields — never overwrite the whole record
JavaScript Example 
// BAD: full overwrite breaks forward compatibility
async function updateOrder_UNSAFE(db, orderId, partialData) {
  // If old service runs this, it wipes fields added by newer services
  await db.query("UPDATE orders SET data = $1 WHERE id = $2", [
    JSON.stringify(partialData), orderId
  ]);
}

// GOOD: partial update — only touch fields we know about
async function updateOrder_SAFE(db, orderId, partialData) {
  // Build SET clause only for known fields
  const knownFields = ['status', 'amount', 'userId'];
  const updates = Object.entries(partialData)
    .filter(([key]) => knownFields.includes(key));

  if (updates.length === 0) return;

  const setClauses = updates.map(([key], i) => `${key} = $${i + 2}`).join(', ');
  const values = [orderId, ...updates.map(([, v]) => v)];

  await db.query(`UPDATE orders SET ${setClauses} WHERE id = $1`, values);
}

// Schema evolution: new field is always optional
function parseOrder(raw) {
  return {
    id: raw.id,
    userId: raw.userId,
    amount: raw.amount,
    status: raw.status,
    currency: raw.currency ?? 'USD',   // safe default — missing in old records
    metadata: raw.metadata ?? {},      // added in v3 — tolerate absence
  };
}
2 — Encoding

Encoding Formats: Text vs Binary

FormatTypeKey traitBest for
JSONTextHuman-readable; no int/float distinctionExternal APIs, debugging, config
XML / CSVTextVerbose, no binaryLegacy integrations, spreadsheets
MessagePackBinaryCompact key+value encodingHigh-throughput internal APIs needing JSON-like structure
Protocol BuffersBinaryInteger field labels (not strings); backward-safe if labels never changegRPC inter-service calls, typed contracts
AvroBinaryValues only — no labels in data, schema stored separatelyKafka topics, bulk data pipelines, maximum compression
Protobuf compatibility rule: Adding new optional fields is always safe. Removing optional fields is safe. Never change an integer field tag — that is the label other services use to parse your message. Changing it silently corrupts all previously serialised data.
3 — Communication Protocols

Choosing the right protocol for each interaction

ProtocolPatternStrengthsWeaknesses
HTTP/RESTSync request/responseUniversal, debuggable, widely cachedTight coupling; cascading timeouts
HTTP/2Multiplexed syncSingle connection, header compression, fasterSingle connection = single bottleneck under very high load
gRPCSync RPC over HTTP/2 + ProtobufTyped contracts, streaming, multi-languageNetwork errors look like local errors; complex serialisation for large payloads
WebSocketsBidirectional persistentFull-duplex, low latency, real-time pushStateful — complicates horizontal scaling; CSWSH security risk
Message Brokers (Kafka/RabbitMQ)Async pub/subFully decoupled; producer doesn't wait; replay possibleEventual consistency; harder to debug; potential bottleneck if overused
HTTP async workarounds: HTTP is synchronous by design. To approximate async with HTTP: use Webhooks (server calls a client-provided URL when work is done) or Long Polling (client holds connection open; server responds when ready). Both are valid — neither is as clean as a message broker for genuinely async pipelines.
Decision guide

Which protocol for which situation

  • External client → API: HTTP/REST. Clients expect it; tooling is universal.
  • Internal service → service (performance-critical): gRPC. Typed, fast, streaming support.
  • Real-time push to browser/mobile: WebSockets. Nothing else gives true bidirectional low-latency.
  • Decoupled async workflows (orders, emails, events): Kafka or RabbitMQ. Fire and forget; consumers subscribe independently.
  • Inter-service batch data: Avro over Kafka. Maximum throughput, schema-controlled evolution.

Key Takeaway

Microservice compatibility is not a versioning problem — it is a discipline problem. Apply three rules consistently: treat new fields as optional, never do full-row overwrites, and choose your encoding format based on whether human readability or wire efficiency matters more for each boundary. The protocol choice follows from the interaction pattern: synchronous queries, real-time streams, and async pipelines each have a clear winner. Getting these right at the start costs almost nothing; retrofitting them costs weeks.
