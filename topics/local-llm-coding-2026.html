The cloud API abstraction hides enormous costs: per-token billing, data egress fees, latency from round-trips, vendor lock-in, and the legal risk of sending proprietary text to a third party. Local LLMs eliminate all four simultaneously — but they substitute a different cost: upfront hardware investment, operational complexity, and a capability ceiling that, in 2025-26, sits about 6-12 months behind frontier models. Knowing exactly where that ceiling is, and which use cases land safely below it, is the entire skill.

Core idea: Local LLMs are not a free alternative to GPT-4 — they are a different trade-off surface. You trade peak intelligence and maintenance-free access for data sovereignty, zero marginal cost, and sub-100 ms first-token latency on suitable hardware. The right question is never "can I run it locally?" but "does my task fit the capability budget of a model I can afford to run?"

Story · Healthcare SaaS, 2024

A mid-size EMR (electronic medical records) vendor was spending $340,000/year on OpenAI API calls to power a clinical-note summarisation feature. The legal team flagged that HIPAA BAA coverage from OpenAI did not extend to model training opt-out guarantees for their tier. Procurement mandated a 90-day proof-of-concept for an on-prem alternative.

The team evaluated Llama 3 70B Q4_K_M on a pair of A100-80GB nodes. Summarisation quality (measured by physician rating) dropped from 4.4/5 to 4.1/5 — acceptable. Average latency fell from 2,400 ms (API round-trip) to 380 ms (local GPU). Annual hardware amortisation: $68,000. Break-even: 7 months.

The hidden win was contractual: the compliance team could now sign off that no patient data ever left the data centre. The product shipped 60 days later with a "100% on-prem AI" selling point that differentiated it in competitive deals.

Why Run LLMs Locally

The Five Reasons That Actually Matter

Blog posts enumerate ten reasons to run models locally. In practice, only five show up in production decisions:

  1. Data sovereignty and privacy. GDPR, HIPAA, SOC 2, and internal data-classification policies prohibit sending certain data categories to third-party inference APIs. Local deployment is the only technically compliant solution — signing a BAA does not substitute for not transmitting data.
  2. Deterministic cost. API billing is O(tokens). A 100k-document classification pipeline at GPT-4o prices costs $200–$800 per run. On a leased A10G, the marginal cost is electricity — roughly $0.40/hour. After the hardware break-even, batch jobs become nearly free.
  3. Latency.  Tier-1 API providers target P50 first-token latency around 400–800 ms under normal load, spiking to 3–5 s during congestion. A quantised 7B model on a consumer GPU delivers first token in under 50 ms. For streaming UIs or real-time pipelines, this is the difference between a fluid and a broken experience.
  4. Offline and air-gapped operation. Defence, industrial control, and field-deployed applications cannot rely on internet connectivity. A quantised model on a laptop runs on a plane, in a submarine, or in a factory with no network dependency.
  5. Fine-tuning and customisation control. You cannot fine-tune GPT-4o on arbitrary data and retain the weights. With local models you own the fine-tuned artefact — and you can re-run RLHF experiments without incurring per-sample API charges.

What is NOT on the list: "Better quality." At any given point in time, frontier cloud models (GPT-4o, Claude Opus, Gemini Ultra) outperform any locally runnable model on complex reasoning, long-context, and multi-step tasks. Running locally is a strategic trade, not a quality upgrade.

Hardware Requirements

Sizing Your Hardware: The Real Numbers

The most common mistake is conflating model parameter count with memory requirement. A 7B model at full precision (BF16) needs ~14 GB of VRAM. At Q4 quantisation it drops to ~4.5 GB, fitting a 6 GB RTX 3060. Know the arithmetic before buying hardware.

Apple Silicon: The Underappreciated Option

M-series Macs use unified memory — CPU and GPU share the same DRAM pool. An M3 Max with 128 GB unified memory runs a Q4_K_M 70B model entirely in-memory with ~15 t/s generation. The bandwidth (400 GB/s on M3 Max) exceeds many discrete GPU setups for LLM inference, which is memory-bandwidth-bound, not compute-bound at typical batch sizes. For a developer workstation, a 64 GB M4 Pro Mac Studio at ~$2,000 beats a $4,500 RTX 4090 workstation for model sizes up to 34B.

CPU-Only Inference

llama.cpp's AVX-512 kernels and BLAS optimisations make CPU inference viable for 7B models: roughly 8–15 t/s on a modern Ryzen 9 or Core i9. This is acceptable for batch summarisation but painful for interactive use. If the only hardware is a laptop without discrete GPU, stick to 3–7B models. Anything larger is unusably slow.

Model Formats

GGUF, GPTQ, AWQ, ExLlamaV2: Which Format to Use

The format war is mostly settled in 2025: GGUF via llama.cpp is the de-facto standard for local inference. Understanding why — and when to deviate — is still important.

GGUF (llama.cpp)
A self-contained binary format that bundles weights, tokeniser, and metadata in a single file. CPU-friendly quantisation (uses Q-series like Q4_K_M). Runs on CPU, CUDA, Metal, ROCm with the same binary. Best for: Ollama, LM Studio, Jan.ai, anything cross-platform. Use this unless you have a specific reason not to.
GPTQ (AutoGPTQ)
GPU-only post-training quantisation that applies group-wise 4-bit or 8-bit weights. Slightly better quality than GGUF Q4 at the same bit-width due to calibration-based quantisation. Requires a CUDA GPU. Use when you have a pure-CUDA server pipeline and need the extra quality point.
AWQ (Activation-Aware Weight Quantisation)
Preserves "important" weights (identified by activation magnitude) at higher precision. Matches Q5 GGUF quality at Q4 memory footprint. vLLM and TGI (HuggingFace Text Generation Inference) support AWQ natively — better for GPU server deployments than GGUF.
ExLlamaV2 (EXL2)
Mixed-precision quantisation that budgets bits per tensor layer. Highest quality per GB among all formats. Requires ExLlamaV2 inference engine. Best for: maximising quality on fixed GPU VRAM when you're running a single model on a dedicated machine.

Decision rule: Use GGUF for anything involving Ollama or a Mac. Use AWQ + vLLM for a production Linux GPU server serving concurrent users. Use EXL2 only if you're squeezing maximum quality out of a 24 GB GPU and are willing to manage the ExLlamaV2 ecosystem.

Quantisation Deep-Dive

Q4_K_M vs Q5_K_M vs Q8_0: The Real Trade-offs

GGUF quantisation levels follow the pattern Q{bits}_{method}_{variant}. The key variants for production use:

Q4_K_M
Fastest · smallest · ~2% perplexity loss
Q5_K_M
Balanced · ~15% larger than Q4 · ~1% loss
Q6_K
Near-lossless · 50% larger than Q4
Q8_0
Functionally lossless · 2× size of Q4

The "_K_M" suffix means "K-quant, medium" — a calibration-based scheme that allocates higher precision to layers that are more sensitive to quantisation (typically attention layers). This is why Q4_K_M performs noticeably better than naive Q4_0 at the same file size.

Practical guidance

  • Q4_K_M: Default for everyday use. Fits the largest model your VRAM supports. Perplexity loss is indistinguishable to humans on conversational or summarisation tasks.
  • Q5_K_M: Use when you have 10–15% headroom in VRAM and the task is sensitive (code generation, structured JSON output, mathematical reasoning). The extra precision reduces token probability smearing.
  • Q8_0: Use only for evaluation baselines or when you're fine-tuning from a quantised checkpoint. The 2× memory cost rarely buys enough quality for production interactive workloads.

Coding-specific quantisation notes

  • Q8_0 — near full-precision quality, ~1.1× model size in RAM. Use if you have headroom.
  • Q4_K_M — best quality-per-GB trade-off. Default recommendation. ~4× compression vs fp16.
  • Q4_K_S — slightly smaller than K_M, slightly lower quality. Use when K_M won't fit.
  • Q3_K_M — noticeable quality drop on hard reasoning. Only if K_M doesn't fit.
  • Q2_K — significant degradation. Avoid for coding tasks.

Rule: Q4_K_M is the default. Only go lower if the model won't fit. Going higher rarely pays off enough to justify the RAM cost.

The perplexity trap: Perplexity benchmarks measure statistical deviation from FP16 output. A 2% perplexity increase does not mean 2% worse answers. On simple tasks, Q4_K_M is subjectively indistinguishable from FP16. On complex multi-step reasoning, the degradation compounds. Benchmark your specific task, not perplexity.

Tooling Landscape

Choosing Your Local LLM Runtime

RECOMMENDED

Ollama

One-command install. Manages model downloads, GGUF format, Metal/CUDA/ROCm acceleration automatically. Exposes an OpenAI-compatible REST API on localhost:11434. Best-in-class DX for developers. Use as the default starting point for any new project.

GUI

LM Studio

Desktop GUI with a model browser, chat interface, and built-in server mode. Excellent for non-developers and rapid model evaluation. Supports GGUF natively. The server mode is OpenAI-compatible. Not ideal for headless/server deployments.

ADVANCED

llama.cpp (direct)

The C++ inference engine that powers most of the ecosystem. Best-in-class CPU performance, bleeding-edge quantisation formats, full control over hyperparameters. Required when you need features before Ollama exposes them (e.g., speculative decoding, context extension).

GUI

Jan.ai

Open-source desktop app similar to LM Studio. Strong privacy focus (all local, no telemetry). Useful for team-wide internal deployment where you want a polished interface without LM Studio's licensing grey area.

GUI

GPT4All

Nomic AI's desktop app. Includes a local document ingestion pipeline and embedding model. Good entry point for non-technical users doing document Q&A. Less flexible than Ollama for programmatic access.

PRODUCTION

vLLM

Python serving framework with PagedAttention for high-throughput GPU inference. Supports AWQ, GPTQ, FP8. The right choice for multi-user API servers on NVIDIA hardware. Not designed for CPU or Apple Silicon.

Integration Patterns

Connecting Local Models to Your Stack

Ollama exposes an OpenAI-compatible API at http://localhost:11434/v1. Any library that accepts an OpenAI base URL works without modification: LangChain, LlamaIndex, Instructor, Continue.dev, OpenWebUI. The next sections show Node.js clients and editor setup in detail.

LangChain / LlamaIndex

Both frameworks have first-class Ollama support. Pass base_url="http://localhost:11434" to the ChatOpenAI or Ollama LLM class. No API key required. Model switching is a single string change.

Part 2 · JavaScript integration

Calling local Ollama from Node.js

// ollama-client.js — OpenAI-compatible API
// Ollama exposes an OpenAI-compatible endpoint at /v1

import OpenAI from 'openai'; // works with Ollama!

const ollama = new OpenAI({
  baseURL: 'http://localhost:11434/v1',
  apiKey:  'ollama', // Ollama ignores the key but the SDK requires one
});

// 1. Basic code completion
async function complete(prompt, model = 'qwen2.5-coder:32b-instruct-q4_K_M') {
  const response = await ollama.chat.completions.create({
    model,
    messages: [
      { role: 'system', content: 'You are an expert JavaScript engineer. Return only code, no explanation.' },
      { role: 'user',   content: prompt },
    ],
    temperature: 0.1, // low temp for code — determinism matters
  });
  return response.choices[0].message.content;
}

// 2. Streaming completion (great for VS Code extension / CLI)
async function completeStreaming(prompt, onChunk) {
  const stream = await ollama.chat.completions.create({
    model: 'qwen2.5-coder:14b-instruct-q4_K_M',
    messages: [{ role: 'user', content: prompt }],
    stream: true,
  });

  for await (const chunk of stream) {
    const text = chunk.choices[0]?.delta?.content ?? '';
    if (text) onChunk(text);
  }
}

// 3. Code review helper
async function reviewCode(filePath, code) {
  return complete(`Review this ${filePath} file for bugs, security issues, and improvements:\n\n${code}`);
}

// 4. Batch refactor — send multiple files
async function refactorFiles(files) {
  const results = await Promise.all(
    files.map(({ name, content }) =>
      complete(`Refactor this ${name} to use modern async/await and fix any issues:\n\n${content}`)
        .then(refactored => ({ name, refactored }))
    )
  );
  return results;
}

// Usage
const code = await complete('Write a rate limiter using a token bucket algorithm in Node.js');
console.log(code);

Using Ollama's native API directly

// Direct Ollama API (without OpenAI SDK)
async function ollamaChat(messages, model = 'qwen2.5-coder:14b-instruct-q4_K_M') {
  const res = await fetch('http://localhost:11434/api/chat', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ model, messages, stream: false }),
  });
  const data = await res.json();
  return data.message.content;
}

// List available models
async function listModels() {
  const res = await fetch('http://localhost:11434/api/tags');
  const { models } = await res.json();
  return models.map(m => ({ name: m.name, size: m.size, modified: m.modified_at }));
}

// Check if a model is loaded (warm)
async function isModelLoaded(model) {
  const res  = await fetch('http://localhost:11434/api/ps');
  const data = await res.json();
  return data.models?.some(m => m.name === model) ?? false;
}

Code Example

Ollama API: Streaming Chat + Model Management

JavaScript Example 
// Ollama OpenAI-compatible streaming chat + model management
// Node 18+ with native fetch; no additional dependencies required.

const OLLAMA_BASE = "http://localhost:11434";

// ─── 1. List locally available models ───────────────────────────────────────
async function listLocalModels() {
  const res = await fetch(`${OLLAMA_BASE}/api/tags`);
  if (!res.ok) throw new Error(`Ollama not running? ${res.status}`);
  const { models } = await res.json();
  return models.map(m => ({
    name:        m.name,
    sizeGB:      (m.size / 1e9).toFixed(1),
    modifiedAt:  m.modified_at,
    paramSize:   m.details?.parameter_size,
    quantLevel:  m.details?.quantization_level,
  }));
}

// ─── 2. Pull a model if not present ─────────────────────────────────────────
async function ensureModel(modelName) {
  const models = await listLocalModels();
  if (models.some(m => m.name === modelName)) {
    console.log(`[ollama] ${modelName} already present`);
    return;
  }

  console.log(`[ollama] pulling ${modelName}...`);
  const res = await fetch(`${OLLAMA_BASE}/api/pull`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ name: modelName, stream: true }),
  });

  const reader = res.body.getReader();
  const decoder = new TextDecoder();
  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    const lines = decoder.decode(value).split("\n").filter(Boolean);
    for (const line of lines) {
      const event = JSON.parse(line);
      if (event.total && event.completed) {
        const pct = ((event.completed / event.total) * 100).toFixed(0);
        process.stdout.write(`\r  ${event.status} ${pct}%  `);
      } else {
        console.log(`  ${event.status}`);
      }
    }
  }
  console.log("\n[ollama] pull complete");
}

// ─── 3. Streaming chat with OpenAI-compatible API ───────────────────────────
async function* streamChat(model, messages, options = {}) {
  const body = {
    model,
    messages,
    stream: true,
    options: {
      temperature:  options.temperature  ?? 0.7,
      top_p:        options.top_p        ?? 0.9,
      num_predict:  options.maxTokens    ?? 512,
      num_ctx:      options.contextSize  ?? 4096,
    },
  };

  const res = await fetch(`${OLLAMA_BASE}/v1/chat/completions`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(body),
  });

  if (!res.ok) {
    const err = await res.text();
    throw new Error(`Ollama error ${res.status}: ${err}`);
  }

  const reader  = res.body.getReader();
  const decoder = new TextDecoder();
  let   buffer  = "";

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split("\n");
    buffer = lines.pop(); // keep incomplete last line

    for (const line of lines) {
      if (!line.startsWith("data: ")) continue;
      const raw = line.slice(6).trim();
      if (raw === "[DONE]") return;
      try {
        const chunk = JSON.parse(raw);
        const delta = chunk.choices?.[0]?.delta?.content;
        if (delta) yield delta;
      } catch {
        // Malformed chunk; skip
      }
    }
  }
}

// ─── 4. Utility: collect full response from stream ──────────────────────────
async function chat(model, userMessage, systemPrompt = "") {
  const messages = [
    ...(systemPrompt ? [{ role: "system", content: systemPrompt }] : []),
    { role: "user", content: userMessage },
  ];

  let output = "";
  process.stdout.write(`[${model}] `);
  for await (const token of streamChat(model, messages)) {
    process.stdout.write(token);
    output += token;
  }
  process.stdout.write("\n");
  return output;
}

// ─── 5. Example: multi-turn conversation with context tracking ───────────────
async function runDemo() {
  const MODEL = "llama3.1:8b"; // or "qwen2.5:14b", "mistral:7b"

  await ensureModel(MODEL);

  const history = [];
  const turns = [
    "Explain what a GGUF file is in two sentences.",
    "What quantisation level would you recommend for an 8 GB GPU?",
    "Why is Q4_K_M better than plain Q4_0?",
  ];

  for (const userMsg of turns) {
    history.push({ role: "user", content: userMsg });
    console.log(`\nUser: ${userMsg}`);
    process.stdout.write("Model: ");

    let reply = "";
    for await (const token of streamChat(MODEL, history)) {
      process.stdout.write(token);
      reply += token;
    }
    console.log();
    history.push({ role: "assistant", content: reply });
  }
}

runDemo().catch(console.error);
Production Local Deployment

Serving Multiple Models at Scale

A single Ollama instance on a developer machine is not the same problem as serving 10 concurrent users with 3 different models on a shared GPU node. Here are the production considerations that most tutorials skip.

GPU Memory Management

Ollama keeps the last-used model loaded in GPU VRAM with a 5-minute idle timeout by default. If you have two models (e.g., a chat model and an embedding model), they will compete for VRAM. Set OLLAMA_MAX_LOADED_MODELS=2 and OLLAMA_GPU_MEMORY_FRACTION=0.9 to give Ollama explicit control. For vLLM on dedicated servers, use tensor parallelism (--tensor-parallel-size 2) to split a 70B model across two A100s.

Request Queuing and Concurrency

LLM inference is not parallelisable the way a stateless API is — each generation step is autoregressive and serialises on the GPU. Ollama processes requests sequentially per model. For higher throughput, vLLM's PagedAttention enables continuous batching: it packs multiple in-flight requests into a single GPU kernel pass, dramatically improving utilisation under concurrent load. Real-world throughput improvement: 2–8× over naive serial inference at 10+ concurrent requests.

Context Window and KV Cache

The KV cache stores attention keys/values for the current context. At 4096 tokens, a 7B model needs ~512 MB of VRAM for KV cache. At 32k tokens, that grows to ~4 GB. Setting context length too high means fewer concurrent requests fit in memory. Set num_ctx to the minimum your use case requires, not the model's maximum.

OpenAI-Compatible Reverse Proxy

For team deployments, run LiteLLM proxy in front of Ollama. LiteLLM adds rate limiting per API key, request logging, cost tracking (even for local models, useful for capacity planning), and fall-through to cloud APIs if the local GPU is saturated. This lets you switch the backend without changing client code. 

# litellm_config.yaml — local-first with cloud fallback
model_list:
  - model_name: "gpt-4o"         # what clients send
    litellm_params:
      model: "ollama/llama3.1:8b" # what LiteLLM uses
      api_base: "http://localhost:11434"
  - model_name: "gpt-4o"         # fallback if local fails
    litellm_params:
      model: "openai/gpt-4o"
      api_key: os.environ/OPENAI_API_KEY

router_settings:
  routing_strategy: "latency-based-routing"
  fallbacks: [{ "gpt-4o": ["gpt-4o"] }]
Failure Modes

What Goes Wrong and Why

  • Model eviction under memory pressure. On macOS, the OS will page out GPU memory to system RAM when other applications demand it. The model is reloaded from disk on the next request — adding 5–30 seconds of cold-start latency. Solution: set OLLAMA_KEEP_ALIVE=-1 to pin the model in memory permanently, and ensure other applications don't compete.
  • Tokeniser mismatch in fine-tuning. If you use a fine-tuned model but load it with the wrong tokeniser (common when converting from HuggingFace to GGUF), output becomes garbled after the special tokens. Always verify the tokeniser embedded in the GGUF matches the base model version.
  • Context overflow without truncation. Sending a prompt that exceeds num_ctx silently truncates from the beginning of the message, not the end. The model "forgets" the system prompt. Implement explicit token counting (using the /api/tokenize endpoint) before sending long prompts.
  • Temperature=0 is not fully deterministic. On GPU floating-point, the same prompt with temperature=0 may produce different outputs across runs due to non-deterministic CUDA operations. If reproducibility is a hard requirement, set a fixed seed ("seed": 42) in the Ollama request.
  • Quantisation artefacts in structured output. Asking a Q4_K_M model for strict JSON produces malformed JSON ~5–15% of the time on complex schemas due to probability smearing. Use Ollama's format: "json" parameter (which enables grammar-constrained sampling) or the Instructor library for validated structured output.
  • Thermal throttling on sustained load. Consumer GPUs (RTX 40-series) throttle at 83°C. Running a 7B model for 30 minutes in a poorly ventilated case can reduce sustained throughput by 20–30%. Monitor nvidia-smi dmon for thermal events; GPU temperature should be below 75°C at sustained inference load.
Scaling Constraints & Production Gotchas

The Ceiling You Will Hit

Local LLM deployment has hard scaling limits that cloud deployments do not:

  • Single GPU = single model bottleneck. You cannot horizontally scale a local GPU node the way you add API concurrency. A single RTX 4090 handles ~3–5 concurrent streaming requests at 7B before latency degrades below acceptable thresholds. Plan capacity in terms of GPU nodes, not servers.
  • Model update lag. Open-weight models lag frontier APIs by 6–18 months on complex reasoning tasks. If your use case competes on AI quality (not privacy/cost), local deployment may be a strategic mistake. Reassess quarterly.
  • No serverless cold-start elasticity. Cloud APIs scale to zero and burst to thousands of QPS instantly. A local GPU node is always-on (power draw: 200–400 W for a GPU workstation) and has a fixed concurrency ceiling. For bursty workloads, the economics shift toward cloud at high peak-to-average ratios.
  • Operational burden. You own model updates, GGUF compatibility, driver upgrades, and hardware failure recovery. Add this to TCO calculations. A small team spending 4 h/week on LLM infrastructure incurs ~$50k/year in engineering cost — often exceeding the API bill it replaces.

The break-even heuristic: Local deployment is economically justified when your monthly API bill exceeds ~$2,000 OR when compliance mandates on-prem processing. Below that threshold, the operational overhead rarely justifies the hardware investment.

Decision framework

When to Use Local vs Cloud

  • Use local when: working with private code, need offline access, running many completions (cost control), want low latency on M-series hardware.
  • Use cloud when: problem requires state-of-the-art reasoning (Claude Opus/Sonnet, GPT-4o), need multi-modal (vision), require very long context (>128k tokens), prototyping speed matters more than privacy.
  • Hybrid setup: local model for autocomplete and quick edits; cloud model for architecture review, complex debugging, and multi-file refactors.
Anti-Patterns

When NOT to Use Local LLMs

As important as the deployment guide is knowing when to stop. Avoid local LLMs for:

  • Complex multi-step reasoning and agent tasks. Tasks requiring 5+ reasoning steps (research synthesis, complex code refactoring, multi-document analysis) still show meaningful quality gaps between 70B local models and GPT-4o/Claude Opus. The gap shrinks but is not zero.
  • SOTA benchmark-critical applications. If your product's competitive differentiation is AI quality (e.g., a legal research assistant that must be demonstrably more accurate than competitors), use the frontier cloud model. The quality delta compounds on edge cases.
  • Prototypes and low-traffic MVPs. The overhead of local deployment is not justified when you're validating an idea. Start with cloud APIs, migrate to local only after you've confirmed the use case is real and the volume warrants it.
  • Teams without a dedicated DevOps owner. Model management, hardware provisioning, and inference server operations are a real ongoing cost. If nobody on the team owns it, it will rot.
Practical Checklist

Before You Deploy a Local LLM

  • Confirm hardware: verify available VRAM, system RAM, and thermal headroom for sustained inference load
  • Choose model size that fits VRAM at Q4_K_M quantisation with 20% headroom for KV cache
  • Start with Ollama unless you have a specific reason to use another runtime
  • Set OLLAMA_KEEP_ALIVE=-1 in production to avoid cold-start latency
  • Set num_ctx to the minimum required context length, not the model maximum
  • Use format: "json" or grammar-constrained sampling for structured output tasks
  • Implement token counting before sending long prompts to avoid silent truncation
  • Monitor GPU temperature under sustained load; target below 75°C
  • Add a seed parameter if output reproducibility is a requirement
  • For multi-user serving, evaluate vLLM (CUDA) or LiteLLM proxy for concurrency management
  • Document the hardware TCO: amortised cost + power + operational overhead vs API bill
  • Benchmark your specific task (not perplexity) at Q4_K_M vs Q5_K_M before committing to a format
  • Plan for model updates: schedule quarterly reviews of available open-weight models
  • For coding: run a 14B model (Qwen2.5-Coder) for tab autocomplete and a 32B model for chat or refactors; consider a hybrid with a cloud model for architecture review and complex debugging
FAQ

Common Questions

Can I run a 70B model on a Mac with 32 GB unified memory?

Technically yes via CPU inference, but it is practically unusable: expect 1–3 tokens per second. At minimum, use a 64 GB Mac (M3 Max or M4 Max) for comfortable 70B inference (~12–15 t/s). With 32 GB, stick to 13B or 32B models.

Is Ollama suitable for production multi-user deployments?

Ollama works for small teams (2–10 concurrent users on a dedicated machine). For higher concurrency, vLLM's PagedAttention and continuous batching offer significantly higher throughput. Ollama is optimised for developer experience, not maximum throughput. Use it behind a LiteLLM proxy to add rate limiting and logging.

What is the practical difference between GGUF and safetensors?

Safetensors is HuggingFace's safe tensor serialisation format — it stores weights at full or half precision without quantisation. It is used for fine-tuning, training pipelines, and vLLM serving. GGUF is a quantised inference format for llama.cpp. They serve different parts of the lifecycle: safetensors for training/evaluation, GGUF for inference on constrained hardware.

How do I know if my GPU will work with Ollama?

Ollama supports NVIDIA (CUDA 11.3+), AMD ROCm (limited Linux support), and Apple Silicon Metal. NVIDIA support is most mature. For ROCm, check the official compatibility list — not all consumer AMD GPUs are on it. Intel Arc GPUs are supported via SYCL in llama.cpp but not yet in Ollama. When in doubt, test with ollama run llama3.2:3b "hello" and check if GPU utilisation spikes in nvidia-smi or Activity Monitor.

Can I use local LLMs with LangChain / LlamaIndex without modification?

Yes. Both frameworks support Ollama natively as a provider. Additionally, the OpenAI-compatible endpoint (http://localhost:11434/v1) means you can use the standard ChatOpenAI class with a custom base_url and a dummy API key — no code changes required beyond the configuration.

What is the smallest model worth using for real tasks?

Phi-3 mini (3.8B) and Gemma 2 2B are surprisingly capable for classification, summarisation, and extraction tasks. Phi-3 mini hits GPT-3.5 quality on many benchmarks. For interactive chat, 7B is the minimum that feels natural. For code completion, Qwen2.5-Coder 7B is the current sweet spot. Below 3B, output quality degrades noticeably on nuanced prompts.

Key Takeaway

Local LLM deployment is a deliberate architectural trade: you exchange the frontier model quality and zero-ops simplicity of cloud APIs for data sovereignty, deterministic cost, and sub-100 ms latency. The technical pieces — GGUF quantisation, Ollama, OpenAI-compatible APIs — are mature enough that deployment is not the hard part; the hard part is judging whether your task fits the capability ceiling of models you can run and whether the economics justify the operational overhead. For coding, Apple Silicon crossed the viability threshold: Qwen2.5-Coder-32B on an M4 Max matches or beats GPT-4o on HumanEval and runs fully offline. Start with Ollama and Q4_K_M (about 90% of the quality at 25% of the RAM), use Continue.dev for the editor, a hybrid local-plus-cloud setup for hard problems, and reach for vLLM or 70B models only when the data shows you need them.
