URL Shortener System Design

TinyURL Architecture + Crash Recovery During Peak Traffic

A complete URL shortener design covering short code generation (Base62 vs hashing vs random), the redirect pipeline, Redis caching, analytics via Kafka, rate limiting, and — critically — what happens when the service crashes during IPL Finals with 100M concurrent users, and how to engineer the recovery.

Source: System Design Interview Prep · Domain: Backend Architecture / System Design

War Story

IPL Finals 2024: The Cascade Nobody Planned For

It was 7:28 PM IST. The IPL Finals were seventeen minutes away from the first ball. A sports media company had embedded shortened links across every push notification, SMS campaign, and sponsored tweet sent to 180 million subscribers. The link format: lnk.example.in/ipl24. By all pre-game estimates, peak traffic was supposed to reach 12,000 requests per second. The system was sized for 15,000. Engineers felt comfortable.

At 7:31 PM, Redis memory utilisation crossed 95%. The allkeys-lru eviction policy kicked in — exactly as configured. The problem was not the policy itself but what it chose to evict. IPL campaign URLs had been pre-warmed that morning, but they were accessed in sharp bursts with quiet periods between bursts. LRU saw those quiet periods as staleness and evicted the very URLs that 100 million users were about to click simultaneously. In two minutes, the Redis cache miss rate went from its normal 2% to 87%.

Each cache miss became a direct PostgreSQL query. At 87% miss rate and 12,000 req/s, that translated to roughly 10,440 DB queries per second against a pool of 200 connections. The pool filled in under four seconds. New requests queued. Queue depth grew faster than it drained. At queue depth 5,000, application servers began timing out while waiting for a connection. The timeout error was swallowed by a retry loop — each retry requesting another connection, accelerating the death spiral.

At 7:39 PM — nine minutes after the first alert — all three application server clusters started failing health checks. The load balancer took them out of rotation. Every shortened link in every notification returned a 502. Users hammered refresh. The match started. The outage lasted 40 minutes. Post-incident analysis identified three root causes that were each independently preventable: no PgBouncer connection pooler, a single-shard Redis instance with no horizontal overflow, and no event-aware pre-warming policy that guaranteed minimum TTLs for campaign-critical codes. This article is the system design that would have prevented all three.

Requirements

Functional and Non-Functional Requirements

Functional Requirements

  • Shorten URL — Given a long URL, produce a unique short code (7 characters). Optionally accept a custom alias.
  • Redirect — Given a short code, redirect the user to the original long URL with HTTP 302.
  • Custom Alias — Users with accounts can choose a vanity slug (e.g., /ipl24) subject to availability and blocklist checks.
  • Link Expiry — Every link can have an optional expiry timestamp. After expiry, the short code returns 410 Gone.
  • Analytics — Record click events (timestamp, IP, referrer, user-agent) and expose aggregate counts per link.
  • Deactivation — Link owners can deactivate a code before expiry.

Non-Functional Requirements

  • Availability: 99.99% uptime (<52 minutes downtime per year). No single points of failure.
  • Latency: Redirect p99 < 50 ms. Shorten API p99 < 200 ms.
  • Scale: 100 million daily active users. Up to 15,000 redirect requests per second at peak.
  • Durability: No shortened link may silently disappear. Deletions are soft-deletes.
  • Security: Phishing URL scanning, rate limiting per IP and per user account, reserved-word blocklist.
Capacity Estimation

Numbers That Drive Architecture Decisions

Capacity estimation is not box-ticking. Every number below directly determines an architecture choice later in this document. Work through them before designing anything.

Write Path (URL Creation)

  • 1 million new shortened URLs per day
  • 1,000,000 / 86,400 seconds ≈ 11.6 writes/sec average
  • Peak writes (campaigns launching at the same time): ~100 writes/sec

Read Path (Redirects)

  • 100 million DAU, average 1 redirect click per user per day
  • 100,000,000 / 86,400 ≈ 1,157 req/sec average
  • Peak (prime-time, live events): 10,000–15,000 req/sec
  • Read-to-write ratio: 1,157 / 11.6 ≈ 100:1

90% of all traffic is reads. Every architectural investment should prioritise read latency and read availability first. The write path can tolerate more latency.

Storage

  • Average row size: ~500 bytes (code 7B + long URL 200B + metadata 293B)
  • 5-year URL retention: 1M/day × 365 × 5 = 1.825 billion rows
  • 1.825B × 500 bytes ≈ 912 GB (≈ 1 TB with indexes)
  • PostgreSQL on a managed cloud instance: fits comfortably on a 2TB SSD volume

Cache Sizing

  • Observation: top 20% of URLs account for 80% of traffic (Pareto principle)
  • Total active URL rows at any time: ~5 million (rolling 30-day active window)
  • Top 20% = 1 million URLs × 500 bytes = 500 MB hot set
  • With expiry metadata and Redis overhead, provision 10 GB Redis RAM for safety headroom
  • At 95% hit rate, DB receives ~580 req/sec instead of 11,570 — a 20× reduction in DB load
Core Algorithm

Short Code Generation — Three Strategies

Generating a collision-free, short, opaque code is the most interview-discussed part of URL shortener design. There are three serious strategies, and each has a different failure mode.

Strategy 1: Sequential ID + Base62 Encoding

A database auto-increment ID (e.g., 1,000,000) is encoded in Base62 (characters 0-9, a-z, A-Z) to produce a short string. ID 1,000,000 encodes to 4c92.

  • Pros: Zero collision risk, simple implementation, natural ordering.
  • Cons: Sequential codes are guessable — an attacker can enumerate all active links by incrementing the code. Race conditions exist in distributed writes (two app servers requesting the next ID simultaneously). Requires a centralised sequence generator (single point of failure unless you use a distributed counter like Zookeeper or Snowflake).

Verdict: Acceptable for internal tools. Avoid for public-facing links where enumeration is a threat.

Strategy 2: MD5 Hash Truncation

Hash the long URL with MD5, take the first 7 characters of the hex digest, and use that as the code. The same long URL always produces the same code (deterministic deduplication is free).

  • Pros: Deterministic — shortening the same URL twice returns the same code. Naturally distributed, no central counter needed.
  • Cons: Collision probability is non-trivial at scale. With 7 hex characters (16^7 = 268M combinations) and 100M URLs, the birthday paradox gives ~15% collision probability. Requires a bloom filter or DB lookup on every write to check collisions. If collision, must append a counter and rehash — complicating the determinism property.

Verdict: Workable with a bloom filter but adds write-path complexity.

Strategy 3: Random 7-Character Alphanumeric (Recommended)

Generate a cryptographically random 7-character string from the Base62 alphabet. The key space is 62^7 ≈ 3.5 trillion combinations. At 1 billion URLs, the collision probability is less than 0.03%.

  • Pros: Non-enumerable, truly distributed (no central counter), simple implementation.
  • Cons: Requires collision detection on every write. Use a bloom filter (in-memory probabilistic structure) to check if a code has been used before hitting the DB. Bloom filter false-positive rate at 1 billion elements is tunable — a 10 GB bloom filter gives <0.001% false positives.

Verdict: Best for production public-facing services. Pair with a bloom filter in Redis and a DB unique constraint as the authoritative backstop.

A bloom filter is your first line of collision defence. If the filter says "not seen," insert immediately. If it says "possibly seen," do a DB lookup to confirm. Only ~0.001% of writes need the DB lookup. The DB unique constraint is your safety net, not your primary check.

Architecture

The Redirect Pipeline

The redirect is the hottest path in the system — it must complete in under 50 ms at the p99. Every component in the pipeline must be chosen with that budget in mind.

Full Request Path

  1. DNS — Short domain resolves to Anycast IP of a global CDN (e.g., CloudFront, Fastly). Latency: ~5 ms for cached DNS.
  2. CDN Edge Node — For static redirects (permanent campaigns), a CDN can cache the 302 response at the edge and serve it without hitting the origin. Cache-Control: max-age=300 for non-personalised links. Latency: ~2 ms at edge hit.
  3. Load Balancer — Layer-7 (e.g., NGINX, AWS ALB) distributes requests across app server pool. Health checks every 5 seconds.
  4. Application Server — Receives GET /:code, extracts the 7-character code. Budget: <40 ms for full application logic.
  5. Redis Cache Lookup — Hash lookup: HGETALL url:{code}. Returns long_url, expires_at, is_active. If HIT and not expired and active: proceed to step 6. If MISS: proceed to step 7. Redis latency: ~0.5 ms on localhost, ~2 ms across VPC.
  6. Cache HIT Path — Check expiry (in-process calculation, no I/O). Emit Kafka click event asynchronously. Return HTTP 302 with Location: {long_url}. Done. Total latency: ~10–15 ms.
  7. Cache MISS Path — Query PostgreSQL: SELECT long_url, expires_at, is_active FROM short_urls WHERE code = $1. DB latency: ~5–10 ms. Populate Redis cache with TTL = min(remaining_expiry, 86400 seconds). Return HTTP 302. Total latency: ~20–30 ms.

Why 302 Not 301?

HTTP 301 is a permanent redirect. Browsers cache it indefinitely and will never re-request the short URL. This means: no analytics (you never see the click again), no ability to update the destination URL, and no expiry enforcement (the browser will keep redirecting forever even after the link expires). HTTP 302 is temporary — the browser always re-requests the short URL, giving you click analytics, destination update capability, and expiry enforcement. The tiny extra roundtrip is worth every one of those capabilities.

Data Model

Database Schema

PostgreSQL is the authoritative store. Redis is the read cache. ClickHouse stores analytics events. All three have different schemas designed for their specific access patterns.

PostgreSQL — short_urls table

CREATE TABLE short_urls (
  id           BIGSERIAL PRIMARY KEY,
  code         CHAR(7)      NOT NULL UNIQUE,
  long_url     TEXT         NOT NULL,
  user_id      BIGINT       REFERENCES users(id) ON DELETE SET NULL,
  custom_alias BOOLEAN      NOT NULL DEFAULT FALSE,
  created_at   TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  expires_at   TIMESTAMPTZ,               -- NULL means no expiry
  is_active    BOOLEAN      NOT NULL DEFAULT TRUE,
  click_count  BIGINT       NOT NULL DEFAULT 0  -- approximate, updated async
);

-- Primary lookup index (used on every redirect)
CREATE UNIQUE INDEX idx_short_urls_code ON short_urls (code);

-- Expiry cleanup job index
CREATE INDEX idx_short_urls_expires_at ON short_urls (expires_at)
  WHERE expires_at IS NOT NULL AND is_active = TRUE;

-- User dashboard: list all links by owner
CREATE INDEX idx_short_urls_user_id_created ON short_urls (user_id, created_at DESC);

Redis — per-code hash

HSET url:{code}
  long_url     "https://example.com/very/long/path"
  expires_at   "2025-12-31T23:59:59Z"   (or "never")
  is_active    "1"

EXPIRE url:{code} 86400   -- 24-hour TTL, refreshed on access

Index Strategy

The idx_short_urls_code unique index on the 7-character CHAR(7) column is the only index that needs to be fast for the redirect hot path. Because CHAR(7) values are fixed-width and the index is B-tree, a lookup is O(log n) — at 1 billion rows it is approximately 30 comparisons, well under 1 ms of CPU time. The DB latency you see in production is dominated by network and connection overhead, not the lookup itself — which is why PgBouncer (connection pooling) matters more than index tuning at scale.

Analytics

Analytics Pipeline: Kafka + ClickHouse

Analytics must never touch the redirect critical path. Every millisecond added to the redirect for analytics purposes is a latency regression affecting 100 million users. The architecture is: fire-and-forget on the critical path, process asynchronously.

Event Flow

  1. Application server handles redirect (Redis HIT or DB MISS). After writing the 302 response header, it publishes a Kafka event to the url.clicks topic. This publish is non-blocking — the response is sent to the client before the Kafka acknowledgement returns. If Kafka is temporarily unavailable, events are buffered in a local in-process queue (max 10,000 events, drop oldest on overflow).
  2. Kafka consumers (a separate service) read from url.clicks, enrich events (reverse IP geolookup, UA parsing), and batch-insert into ClickHouse.
  3. ClickHouse stores raw click events in a MergeTree table partitioned by day. Materialised views compute per-link aggregates (total clicks, unique IPs, top referrers) every 5 minutes.
  4. The analytics API reads from ClickHouse materialised views — never from PostgreSQL click_count. The click_count column in PostgreSQL is an approximate counter updated by a background job every 15 minutes, used only for quick sorting in the user dashboard.

Analytics events are always asynchronous. If the analytics pipeline fails completely, no user sees a broken redirect. Decouple write latency from analytics latency by making analytics a side effect, never a dependency.

Kafka Topic Design

  • Topic: url.clicks, 24 partitions (1 per hour-of-day allows time-based routing)
  • Partition key: code — ensures all clicks for a given URL land on the same partition for in-order processing
  • Retention: 7 days (allows replay if ClickHouse consumer falls behind)
  • Replication factor: 3 (tolerates 2 broker failures)
Security

Rate Limiting and Security

Rate Limiting

Rate limiting is applied at two layers: the CDN edge (coarse-grained, IP-based, protects against DDoS) and the application layer (fine-grained, per-user and per-IP, protects against abuse).

  • Shorten API (POST /api/v1/shorten): Token bucket, 10 req/min per IP for unauthenticated users, 100 req/min per user account for authenticated users. Burst allowance: 3× for the first 5 seconds. Implemented via a Redis sorted set with sliding window counters.
  • Redirect API (GET /:code): No rate limiting on individual redirects (it would break normal browsing). DDoS protection via CDN rate limiting at the edge (e.g., Cloudflare rate limiting at 1,000 req/min per IP).
  • Analytics API: 60 req/min per authenticated user. Results are cached for 5 minutes per code.

Phishing and Malware Prevention

  • Google Safe Browsing API — checked asynchronously within 10 seconds of URL creation. If flagged, the link is deactivated and the creator is notified. Re-scan every 24 hours for active links.
  • Domain blocklist — maintained list of known phishing/malware domains. Checked synchronously at creation time (in-process hash set lookup, O(1)). Updated from threat intelligence feeds every hour.
  • Custom alias reserved words — blocked from use as custom aliases: api, admin, help, login, logout, signup, www, blog, status, and ~200 others. Stored in a static file loaded at startup.
  • URL length limit — Maximum long URL length: 2,048 characters (matches browser URL bar limits). Longer URLs are rejected with 400 Bad Request.
Incident Analysis

THE CRASH SCENARIO — IPL Finals: A Three-Phase Failure

This is the section that separates good system design from great system design. Understanding failure cascades — not just happy-path architecture — is what makes the difference between a system that survives peak events and one that becomes a post-mortem.

Phase 1: Redis Memory Exhaustion and LRU Betrayal (T+0 to T+8 min)

The system was configured with a single Redis instance: 8 GB memory, maxmemory-policy allkeys-lru. Campaign URLs for the IPL Finals had been pre-warmed at 6:00 AM that morning. By 7:00 PM, 13 hours of normal traffic had filled Redis to 94% capacity with a mix of URLs: news articles, sports scores, e-commerce links, and the IPL campaign codes.

When the first wave of pre-match traffic arrived at 7:15 PM, Redis started evicting. The allkeys-lru policy evicts the key that was least recently accessed. IPL campaign URLs — url:ipl24, url:match7, url:mvp — had been pre-warmed but were accessed in burst patterns (pre-match hype, halftime, post-match). Between those bursts, LRU saw them as cold and evicted them. Meanwhile, a steady stream of e-commerce short links kept those keys warm.

By 7:31 PM, all pre-warmed IPL codes had been evicted at least once. As the 7:45 PM match-start rush began, every IPL code was a cache miss. Cache miss rate: 2% (baseline) → 87% (during peak).

Phase 2: DB Connection Pool Exhaustion (T+8 to T+15 min)

Each cache miss caused the application server to open a connection to PostgreSQL and query the short_urls table. PostgreSQL was configured with max_connections = 200. The application servers had no PgBouncer — every application thread held its own direct connection.

At 12,000 req/s and 87% miss rate: 10,440 DB queries/second. With each query taking ~8 ms, the number of concurrent in-flight queries at any instant was 10,440 × 0.008 ≈ 84 concurrent connections just for redirects. Combined with write traffic, analytics API connections, and dashboard queries, the 200-connection pool was exhausted within 4 seconds of peak traffic arriving.

New connection attempts from application servers were queued by the PostgreSQL accept queue. The application servers used a synchronous connection model with a 5-second timeout. As the queue depth grew, connections started timing out before they could execute any query. The timeout error was logged but the application server's retry logic issued a fresh connection request — which also needed a new connection from the already-exhausted pool. Each retry made the problem worse.

Phase 3: Application Server Failure and Full Outage (T+15 to T+55 min)

With PostgreSQL accepting no new connections, the redirect handler began returning 500 errors on cache misses. But 87% of requests were cache misses. So 87% of requests returned 500. The load balancer health check endpoint was GET /health — which itself required a Redis ping and a DB health check. With DB connections unavailable, the health check failed. The load balancer marked all three app server clusters as unhealthy and stopped routing traffic. All users received 502 Bad Gateway from the load balancer itself.

Recovery required: (1) identifying the root cause (took 22 minutes — engineers initially suspected the DB itself had crashed, not connection exhaustion), (2) manually restarting application servers to release connection leaks, (3) manually pre-warming Redis from a DB snapshot, (4) gradually re-enabling traffic. Total outage: 40 minutes.

Three changes would have prevented this entirely: PgBouncer (connection pooling), Redis Cluster (horizontal memory scaling to avoid OOM), and event-aware pre-warming (guaranteed minimum TTL for VIP campaign codes). None of them are complex. All of them were known best practices. The failure was a planning failure, not a technical one.

Recovery Steps (What Was Actually Done)

  1. Immediate: Scale Redis vertically (emergency resize to 32 GB). This took 8 minutes and required a Redis restart.
  2. Immediate: Restart application servers to release leaked connections.
  3. Immediate: Manually re-insert top 10,000 URLs into Redis via a one-time script pulling from PostgreSQL.
  4. Short-term: Add PgBouncer in transaction-pooling mode between app servers and PostgreSQL. Pool size: 20 connections per app server, max 400 total. Each query holds a connection for ~8 ms, then releases it — allowing 1 physical connection to serve hundreds of application threads.
  5. Medium-term: Deploy Redis Cluster with 3 primary shards + 3 replicas. Each shard holds ~3.3 GB of URL data. No single shard can OOM without triggering failover. Horizontal scaling is additive.

Prevention Architecture (What Should Have Been Built)

  • Event-Aware Capacity Planning: A pre-event runbook triggers 24 hours before any scheduled peak event (sports, sales, launches). It identifies all short codes associated with the event and sets a minimum TTL floor of 7,200 seconds (2 hours) on those Redis keys. LRU cannot evict a key with a TTL floor because the key is continuously re-expired before it appears cold. The runbook is triggered by the campaign management system automatically when any link is tagged with a peak-event label.
  • PgBouncer in Transaction Pooling Mode: Every app server connects to PgBouncer on localhost. PgBouncer maintains a pool of 20 long-lived connections to PostgreSQL per app server. Each application query borrows a connection for the duration of one query (~8 ms), then returns it. 200 application threads can share 20 physical connections with no queuing at normal loads. At extreme loads, PgBouncer queues requests and applies backpressure, rather than exhausting the DB.
  • Circuit Breaker Pattern: The DB lookup code path has a circuit breaker. If the error rate exceeds 50% over a 10-second window, the circuit opens and the redirect handler immediately returns 503 with a Retry-After: 30 header, rather than hanging connections. Users see a fast failure with a retry hint, rather than a 40-second timeout hanging their browser.
  • Redis Memory Alert at 70%: PagerDuty alert fires when Redis memory hits 70%. On-call engineer has 30 minutes to scale before LRU eviction becomes aggressive. At 95%, automated horizontal shard addition kicks in (Redis Cluster resharding).
  • Graceful Degradation: If Redis is unavailable AND the DB circuit breaker is open, the service returns 503 with Retry-After: 60 instead of hanging. A static fallback page explains the service is temporarily overloaded. This prevents cascading browser retries from amplifying the load.

Implementation

Redirect Handler Implementation

The following handler implements the full redirect pipeline: Redis cache-aside, circuit breaker, PostgreSQL fallback, and async Kafka event publish. This is production-ready Node.js using ioredis and pg.

JavaScript Example 
const Redis = require('ioredis');
const { Pool } = require('pg');
const { Kafka } = require('kafkajs');

const redis = new Redis({ host: process.env.REDIS_HOST, port: 6379 });
const pgPool = new Pool({ connectionString: process.env.DATABASE_URL, max: 20 });
const kafka = new Kafka({ brokers: [process.env.KAFKA_BROKER] });
const kafkaProducer = kafka.producer();
kafkaProducer.connect();

// Circuit breaker state
const circuit = { state: 'CLOSED', failures: 0, lastAttempt: 0 };
const FAILURE_THRESHOLD = 5;
const RESET_TIMEOUT_MS = 30_000;

async function redirectHandler(req, res) {
  const code = req.params.code;

  // 1. Redis cache lookup
  const cached = await redis.hgetall(`url:${code}`);
  if (cached && cached.long_url) {
    if (cached.is_active === '0') return res.status(410).end();
    if (cached.expires_at !== 'never' && new Date(cached.expires_at) < new Date()) {
      return res.status(410).end();
    }
    publishClickEvent(code, req);  // fire-and-forget
    return res.redirect(302, cached.long_url);
  }

  // 2. Circuit breaker check
  if (circuit.state === 'OPEN') {
    const elapsed = Date.now() - circuit.lastAttempt;
    if (elapsed < RESET_TIMEOUT_MS) {
      res.set('Retry-After', '30');
      return res.status(503).json({ error: 'Service temporarily unavailable' });
    }
    circuit.state = 'HALF_OPEN';
  }

  // 3. DB fallback
  try {
    const { rows } = await pgPool.query(
      'SELECT long_url, expires_at, is_active FROM short_urls WHERE code = $1',
      [code]
    );
    if (!rows.length) return res.status(404).end();

    const row = rows[0];
    if (!row.is_active) return res.status(410).end();
    if (row.expires_at && new Date(row.expires_at) < new Date()) return res.status(410).end();

    // 4. Populate Redis cache
    const ttl = row.expires_at
      ? Math.floor((new Date(row.expires_at) - Date.now()) / 1000)
      : 86400;
    await redis.hset(`url:${code}`, {
      long_url: row.long_url,
      expires_at: row.expires_at ? row.expires_at.toISOString() : 'never',
      is_active: row.is_active ? '1' : '0',
    });
    if (ttl > 0) await redis.expire(`url:${code}`, Math.min(ttl, 86400));

    circuit.state = 'CLOSED';
    circuit.failures = 0;

    publishClickEvent(code, req);  // fire-and-forget
    return res.redirect(302, row.long_url);

  } catch (err) {
    circuit.failures++;
    circuit.lastAttempt = Date.now();
    if (circuit.failures >= FAILURE_THRESHOLD) circuit.state = 'OPEN';
    res.set('Retry-After', '30');
    return res.status(503).json({ error: 'Service temporarily unavailable' });
  }
}

function publishClickEvent(code, req) {
  setImmediate(async () => {
    try {
      await kafkaProducer.send({
        topic: 'url.clicks',
        messages: [{
          key: code,
          value: JSON.stringify({
            code,
            timestamp: new Date().toISOString(),
            ip: req.ip,
            userAgent: req.headers['user-agent'],
            referrer: req.headers['referer'] || null,
          }),
        }],
      });
    } catch (_) { /* analytics failure must never affect redirect */ }
  });
}

module.exports = { redirectHandler };
Checklist

Production Readiness Checklist

  • Always use 302 not 301 redirects — 301 caching breaks analytics, expiry, and destination updates
  • Pre-warm event-critical URLs 24 hours before any scheduled peak event
  • Set a minimum TTL floor (7,200 seconds) for VIP and campaign-linked codes to prevent LRU eviction during burst gaps
  • Use PgBouncer in transaction-pooling mode between all application servers and PostgreSQL
  • Deploy Redis Cluster with at least 3 primary shards for horizontal memory scaling — a single Redis instance is a memory ceiling and a single point of failure
  • Put all analytics on the async Kafka path — never block a redirect on analytics I/O
  • Set Redis memory alert at 70% capacity (PagerDuty) and automated resharding at 85%
  • Use a bloom filter for collision detection during short code generation — DB unique constraint is the backstop, not the primary check
FAQ

Frequently Asked Questions

Why 302 not 301?

HTTP 301 is a permanent redirect that browsers cache indefinitely. Once a browser caches a 301, it will never send another request to your short URL — meaning you lose all click analytics, cannot update the destination URL, and cannot enforce link expiry. HTTP 302 is temporary: the browser always re-requests the short URL, giving you full control and visibility. The cost is one extra DNS + TCP roundtrip per click, which is negligible compared to the capabilities you gain. Always use 302 for user-facing shortened links.

How to prevent link enumeration?

With random Base62 7-character codes (key space: 62^7 ≈ 3.5 trillion), brute-force enumeration is computationally infeasible — an attacker requesting 1,000 codes/sec would need 111 years to cover 1% of the space. Additionally: rate limit unauthenticated redirect attempts to 1,000 req/min per IP (anything beyond that pattern is scanning, not browsing), return 404 for all invalid codes (do not distinguish "never existed" from "expired"), and log enumeration attempts for security alerting.

How to handle link expiry at scale?

Two mechanisms work together. First, Redis TTL is set to min(time_until_expiry, 86400) on every cache write — Redis will automatically evict expired keys, so no expired key will ever be served from cache. Second, a background PostgreSQL job runs every hour and soft-deletes rows where expires_at < NOW() AND is_active = TRUE. Use the partial index CREATE INDEX ... WHERE expires_at IS NOT NULL AND is_active = TRUE to make this job fast even at billions of rows. Never check expiry by running a full table scan.

What is the read-to-write ratio?

At 100M DAU with 1M new URLs/day: approximately 100:1 read-to-write ratio (1,157 redirects/sec average vs 11.6 writes/sec). At peak events this can reach 1,000:1 (15,000 redirects/sec vs the same 11.6 writes/sec — campaign launches do not scale with event traffic). This extreme read dominance is why the entire architecture optimises for read latency: Redis caching, CDN edge caching, read replicas, and connection pooling are all read-path investments.

Key Takeaways

What This System Teaches

The URL shortener is a deceptively simple system with a deceptively brutal failure mode. On the surface it is a key-value lookup with a redirect. Under the hood it is a read-heavy, latency-critical, cache-dependent service that must sustain 15,000 req/sec with <50 ms p99 and 99.99% availability — including during the moments when 100 million users all click the same link at the same time.

The IPL Finals crash is the canonical lesson: event-aware capacity planning is not optional. The system was technically correct on a normal day. It was operationally incomplete on a peak day. The gap between those two states is exactly what distinguishes a junior system design from a senior one.

Three changes would have prevented the 40-minute outage: PgBouncer (converts connection exhaustion from a hard wall into graceful backpressure), Redis Cluster (converts a single-shard OOM from a total cache failure into a partial one), and event-aware pre-warming with TTL floors (converts LRU eviction during burst gaps from a silent killer into a non-issue). None of them are exotic. All of them are known best practices.

Apply this pattern to every read-heavy system you design: identify the hottest cache keys, guarantee their residency before peak events, pool your connections, and implement circuit breakers so fast failures beat slow timeouts every time.

System design is not about knowing the right answer. It is about knowing which failure modes matter and which three changes would prevent the most damage. In any interview, the scenario you trace through a failure cascade will always be remembered more than the happy-path architecture.
