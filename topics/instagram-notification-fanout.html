Instagram Notification Storm: System Design Deep Dive on Fanout Architecture and Push Notification Scalability

One post from a 50M-follower account triggers 50M push notifications. Deep dive on fanout-on-write vs fanout-on-read, the celebrity problem, APNs/FCM rate limits, Kafka partitioning for notification queues, deduplication, and the hybrid strategy that Instagram and Twitter actually use.

Domain: System Design · Notifications · Architecture Credit: CodeFarm (Medium) Published: 2026-07-22

The naive approach to notifications is a for-loop: iterate over all followers, call the push API for each. At 50 million followers, this loop takes hours. It exhausts connection pools, violates provider rate limits, and causes cascading failures in the notification pipeline. The correct design treats notifications as a rate problem, not a volume problem — and solves it with distributed fanout, back-pressure, and provider-aware throttling.

Numbers that matter: APNs allows ~15M notifications/hour per certificate. FCM allows ~600M/day per project. Instagram serves 2B+ daily active users. Neither provider ceiling is reachable with a naive fanout loop from a single service instance.

Story · Cristiano Ronaldo posts. 600M followers. Notification pipeline melts.

Ronaldo has 600M Instagram followers. When he posts, the notification service must fanout to 600M devices. At Instagram's scale, this is ~167,000 notifications per second just for that single post — sustained for about an hour until the tail of follower notification windows closes.

Celebrities like this are not edge cases at Instagram — they are the designed-for scenario. The architecture cannot treat a 600M-follower account the same as a 500-follower account. The fanout strategy must be fundamentally different based on account tier.

Fanout Strategies

Fanout-on-Write (Push Model)

When a user posts, immediately write the post ID to every follower's notification inbox. Read time is O(1) — the inbox already has the data.

  • Pros: Fast reads; notifications arrive quickly.
  • Cons: Write amplification. One post from a 10M-follower account = 10M writes. Storage per user scales with follow count × post frequency.
  • Suitable for: Normal accounts (< 10k followers). The write amplification is manageable.

Fanout-on-Read (Pull Model)

Store only the post itself. When a follower opens the app, compute their notification feed at read time by aggregating posts from all followed accounts.

  • Pros: No write amplification; simple storage model.
  • Cons: Read time scales with number of accounts followed × recency depth. O(n followings) per read. Extremely slow for active users following 1,000+ accounts.
  • Suitable for: Low-activity feeds or as a fallback for unread tail data.

Hybrid Model (Instagram / Twitter actual approach)

  • Normal accounts (< 1M followers): fanout-on-write into follower inboxes.
  • Celebrity accounts (> 1M followers): fanout-on-read — the celebrity's post is NOT pre-written to 600M inboxes. Followers pull it at read time.
  • The client merges both sources: pre-written inbox entries + celebrity pull results.

The Notification Pipeline Architecture

  1. Event ingestion — post-created event lands in Kafka topic post-created.
  2. Fanout service — reads the event, determines the author's follower tier, fetches follower list from the follower-graph service, publishes one notification-job message per follower to a partitioned Kafka topic.
  3. Notification workers — consume from notification-job, look up user device tokens and notification preferences, batch calls to APNs/FCM.
  4. Provider gateways — APNs (iOS), FCM (Android), Web Push — each with their own rate limits and batching APIs.
  5. Delivery receipt handler — processes APNs/FCM delivery callbacks, marks tokens as inactive for bounced tokens.
JavaScript Example — Fanout Worker with Kafka 
// notification-fanout-worker.js — Node.js + Kafka
import { Kafka } from 'kafkajs';

const kafka = new Kafka({ clientId: 'fanout-worker', brokers: [process.env.KAFKA_BROKER] });
const consumer = kafka.consumer({ groupId: 'notification-fanout-group' });
const producer = kafka.producer({ idempotent: true }); // exactly-once producer

const CELEBRITY_THRESHOLD = 1_000_000; // followers
const BATCH_SIZE = 500; // follower IDs per Kafka message batch

async function startFanoutWorker() {
  await consumer.connect();
  await producer.connect();
  await consumer.subscribe({ topic: 'post-created', fromBeginning: false });

  await consumer.run({
    eachMessage: async ({ message }) => {
      const post = JSON.parse(message.value.toString());
      const { postId, authorId, contentType } = post;

      const followerCount = await getFollowerCount(authorId);

      if (followerCount >= CELEBRITY_THRESHOLD) {
        // Celebrity: store post reference only; followers pull at read time
        await markCelebrityPost(postId, authorId);
        console.log(`[fanout] Celebrity post ${postId} — fanout-on-read`);
        return;
      }

      // Normal account: fanout-on-write
      let cursor = null;
      let totalFanned = 0;
      do {
        const { followers, nextCursor } = await getFollowersBatch(authorId, cursor, BATCH_SIZE);
        cursor = nextCursor;
        totalFanned += followers.length;

        // Batch publish notification jobs
        await producer.send({
          topic: 'notification-jobs',
          messages: followers.map(followerId => ({
            key: followerId,  // partition by follower for ordering guarantees
            value: JSON.stringify({ postId, authorId, followerId, contentType,
                                    notificationType: 'new-post', ts: Date.now() })
          }))
        });
      } while (cursor);

      console.log(`[fanout] Post ${postId} fanned to ${totalFanned} followers`);
    }
  });
}

// Notification worker: batches APNs/FCM calls
async function sendNotification(notificationJob) {
  const { postId, authorId, followerId } = JSON.parse(notificationJob);
  const user = await getUserPreferences(followerId);

  if (!user.notificationsEnabled || !user.deviceToken) return;
  if (await isDuplicate(postId, followerId)) return; // dedup check

  // Batch with other pending notifications (external batching service)
  await notificationBatcher.add({
    token: user.deviceToken,
    platform: user.platform, // 'apns' | 'fcm'
    payload: {
      title: `New post from ${await getDisplayName(authorId)}`,
      body: 'Tap to view',
      data: { postId, type: 'new-post' }
    }
  });
}

// Deduplication: have we already sent this notification?
async function isDuplicate(postId, followerId) {
  const key = `notif:sent:${postId}:${followerId}`;
  const set = await redis.set(key, 1, 'EX', 86400, 'NX'); // 24hr TTL
  return set === null; // null means key already existed = duplicate
}

APNs and FCM — Provider-Level Constraints

ProviderBatch sizeRate limitRetry on failureToken invalidity
APNs (Apple)1 (no batch API)~15M/hr per certificateExponential backoff; respect Retry-After header410 = unregistered token, delete immediately
FCM (Google)Up to 500 per batch API call~1M/min per project503/429 = back off; 4xx = dead tokencanonical_ids response field = token changed
Web Push1 per call (VAPID)Varies by browser vendor410 = unsubscribed endpoint410 = delete subscription

Production rule: Never hit a provider at more than 80% of their rate limit. Use a token-bucket rate limiter per provider within the notification worker. APNs in particular will ban your certificate if you send too aggressively — recovery requires Apple support and takes days.

Failure Modes and Production Gotchas

  • Kafka lag during celebrity post — a 600M-follower post creates 600M Kafka messages. Even with 100 partitions and 1,000 workers, the queue may take 10+ minutes to drain. This is acceptable if SLA is "notification within 30 minutes." If SLA is tighter, pre-scale the worker fleet based on a "celebrity post detected" signal.
  • Stale device tokens — users uninstall the app but their token remains in the database. APNs returns 410; your worker must delete the token immediately, otherwise every fanout pays the cost of a dead call plus the 410 round-trip. Token graveyard accumulates quickly.
  • Notification flood on re-follow — if a user unfollows and re-follows, they should not receive all historical posts as new notifications. The notification dedup store (Redis, 24hr TTL) handles this, but the key must be scoped to (postId, followerId), not just postId.
  • Do-Not-Disturb ignoring — push notifications sent during a user's DND hours damage engagement. Store user timezone and DND preferences; delay delivery using a scheduled notification queue.
  • Notification grouping — 50 new posts from 50 different accounts should not generate 50 individual notifications. Group by account or content type and send one summary notification. Both APNs (notification groups) and FCM (collapse key) support this natively.

Key Takeaway

The Instagram notification problem is a rate problem, not a storage problem. The hybrid fanout model — write-amplification for normal accounts, pull for celebrities — balances write cost against read latency. Provider rate limits are the real ceiling; a token-bucket rate limiter per provider, combined with Kafka back-pressure, is what prevents the notification pipeline from collapsing the moment a celebrity posts.
