Microservices are not a technology — they are an organisational pattern. The same system can be correctly implemented as a monolith, a set of microservices, or a serverless-hybrid depending on team size, deployment velocity, and data ownership requirements. Choosing blindly leads to distributed monoliths — the worst of both worlds.

Core idea: Start from your team's bounded contexts, not from a technology checklist. Every microservices pattern exists to solve a specific failure mode of the alternative. Understand the failure mode first, then adopt the pattern.

Story · When microservices hurt

An e-commerce startup split their monolith into 22 microservices after reading a Netflix case study. Six months later: deployment complexity tripled, a simple checkout flow spanned 7 synchronous service calls, and a single service timeout cascaded into a full checkout blackout. They had microservices but not the team structure, observability, or failure isolation that makes them worth the complexity.

The Netflix case study that inspired them had one critical footnote: Netflix spent three years building the tooling infrastructure before the services themselves made sense. The architecture pattern wasn't the product. The investment in resilience tooling was.

Core patterns

The 12 patterns every microservices engineer uses

1. API Gateway

Single entry point for all clients. Handles auth, rate limiting, routing, and response aggregation. Clients never talk to services directly.

2. Circuit Breaker

Stops calling a failing service after N failures, returns fallback immediately. Prevents cascade failures across service boundaries.

3. Event-Driven / Pub-Sub

Services emit events to a broker (Kafka, RabbitMQ). Other services subscribe. No direct coupling — a new consumer never changes the producer.

4. Saga Pattern

Distributed transactions via a chain of local transactions + compensating actions. Choreography (events) or Orchestration (central coordinator).

5. CQRS

Separate read and write models. Write path optimized for consistency; read path optimized for query performance (separate DB projections).

6. Strangler Fig

Incrementally replace monolith: route specific paths to new services while the monolith handles the rest. Refactor without a big-bang rewrite.

7. Service Mesh

Sidecar proxy (Istio, Linkerd) handles mTLS, observability, retries, and traffic shaping without any service code changes.

8. Bulkhead

Isolate critical paths into separate thread pools or service instances. A failing bulk operation cannot steal resources from real-time requests.

9. Sidecar

Attach a helper process alongside the main container. Handles logging, config refresh, secret rotation — without touching service code.

10. Backends for Frontends (BFF)

Each client type (mobile, web, partner) gets a dedicated API layer that aggregates and shapes data specifically for its needs.

11. Outbox Pattern

Write the event to a local DB table (outbox) in the same transaction as the business record. A relay process publishes it. Guarantees at-least-once delivery.

12. Connection Pooling

Reuse established DB connections instead of opening/closing per request. Eliminates the biggest latency overhead in microservice-to-DB calls.

JavaScript Example

API Gateway pattern with circuit breaker in Node.js

JavaScript Example 
// Minimal API Gateway with circuit breaker state
const express = require("express");
const app = express();

// Circuit breaker state per upstream service
const breakers = new Map();

function getBreaker(serviceId) {
  if (!breakers.has(serviceId)) {
    breakers.set(serviceId, { failures: 0, openUntil: 0, threshold: 5, ttl: 30_000 });
  }
  return breakers.get(serviceId);
}

async function callUpstream(serviceId, url, options = {}) {
  const breaker = getBreaker(serviceId);
  const now = Date.now();

  // Circuit is open — return fallback immediately
  if (breaker.openUntil > now) {
    throw new Error(`Circuit open for ${serviceId} — retry after ${new Date(breaker.openUntil).toISOString()}`);
  }

  try {
    const res = await fetch(url, { signal: AbortSignal.timeout(3000), ...options });
    if (!res.ok) throw new Error(`${serviceId} returned ${res.status}`);
    breaker.failures = 0; // reset on success
    return res.json();
  } catch (err) {
    breaker.failures += 1;
    if (breaker.failures >= breaker.threshold) {
      breaker.openUntil = now + breaker.ttl;
      console.warn(`[circuit] Opened for ${serviceId} after ${breaker.failures} failures`);
    }
    throw err;
  }
}

// Gateway route — aggregates user + order data (BFF pattern)
app.get("/api/dashboard/:userId", async (req, res) => {
  const { userId } = req.params;
  try {
    const [user, orders] = await Promise.allSettled([
      callUpstream("user-svc", `http://user-service/users/${userId}`),
      callUpstream("order-svc", `http://order-service/orders?userId=${userId}`),
    ]);

    res.json({
      user: user.status === "fulfilled" ? user.value : null,
      orders: orders.status === "fulfilled" ? orders.value : [],
      degraded: user.status === "rejected" || orders.status === "rejected",
    });
  } catch (err) {
    res.status(503).json({ error: "Gateway error", message: err.message });
  }
});

// Event-driven outbox relay (simplified)
async function outboxRelay(db, kafka) {
  const unsent = await db.query("SELECT * FROM outbox WHERE sent_at IS NULL ORDER BY created_at LIMIT 100");
  for (const row of unsent.rows) {
    await kafka.send({ topic: row.topic, messages: [{ key: row.aggregate_id, value: row.payload }] });
    await db.query("UPDATE outbox SET sent_at = NOW() WHERE id = $1", [row.id]);
  }
}

app.listen(3000, () => console.log("Gateway on :3000"));
Refactoring from monolith

The Strangler Fig migration playbook

  1. Map your bounded contexts — identify domains with clear ownership (orders, users, inventory). These become service candidates.
  2. Put an API Gateway in front first — route 100% of traffic through it before splitting anything. You get observability and the ability to route by path.
  3. Extract the least-coupled domain first — email notifications, reporting, or PDF generation are good starting points. They have no cross-domain writes.
  4. Use the Outbox pattern for any domain with events — don't try dual writes; they will eventually split under load.
  5. Move the database last — run with a shared DB longer than feels comfortable. Split the DB only after the service boundary is proven stable.
Avoid distributed monolith: If services share a database and call each other synchronously across many hops, you get all the complexity of microservices with none of the independence. The tell: one service deploy requires coordinating three others.
FAQ

Common questions

Microservices vs Serverless — which is better? Different tools. Microservices give you long-running process control and state ownership. Serverless excels for stateless event handlers with unpredictable burst traffic. The hybrid pattern uses microservices for core domains and serverless for edge compute, media processing, and integrations.

How do you handle distributed transactions? You mostly avoid them. Design service boundaries so that writes stay within one service. Where you can't, use the Saga pattern with compensating transactions, not 2PC.

What's the minimum viable observability stack? Distributed tracing (OpenTelemetry), structured JSON logs with trace IDs, and RED metrics (Rate, Errors, Duration) per service. Without trace IDs that span service boundaries, debugging is nearly impossible.

Key Takeaway

Microservices patterns — API Gateway, Circuit Breaker, Saga, Event-Driven, CQRS, Strangler Fig — each exist to solve a specific failure mode. The right time to adopt a pattern is when you've experienced the failure it prevents, not before. Start with a well-structured monolith, add an API Gateway for observability, and extract services along bounded context lines only when independent deployment velocity is genuinely blocked. Every pattern adds complexity; that complexity only pays off when the alternative would cost more.
