An order processing system is the central nervous system of any e-commerce platform. It touches every team, every database, and every dollar. Getting it wrong means overselling inventory, double-charging customers, or silently losing orders under load. Getting it right means knowing exactly which distributed systems patterns to apply — and which popular claims to reject.

Core idea: Decompose by business subdomain, own the database per service, chain local transactions via Saga instead of 2PC, publish events reliably via the Transactional Outbox, and make every consumer idempotent. Everything else is an optimisation on top of these five moves.

Story · The double-charge incident

A mid-size retailer launched a flash sale. Traffic spiked 40×. The payment service received the same order request twice — once from the user's tap, once from a mobile retry after a network timeout. Both requests cleared the idempotency check because the team had implemented it with a Redis key that expired after 30 seconds. Two charges hit the customer's card. The refund took three days. The support tickets took a week to clear.

The root cause was not the retry — retries are correct behaviour. The root cause was a non-durable idempotency key (Redis TTL, not a database journal). This guide is the architecture that prevents exactly that class of failure, at any scale.

Story · Flipkart Big Billion Days — 50,000 users, money gone, no laptop

11:57 PM on Big Billion Days. Aarav adds a ₹4,999 laptop to his cart, enters his UPI PIN, and watches the screen. Payment gateway responds in 800 ms: SUCCESS. The checkout service calls the inventory service to reserve the unit. The inventory service is under extreme load — 200,000 requests/second — and the response takes 12 seconds before timing out. The checkout service marks the order FAILED. Aarav's bank statement shows a debit. Flipkart's order history shows nothing.

The automatic refund process runs on a T+3 batch job. Aarav will not see his ₹4,999 for three business days. He opens a support ticket. He leaves a one-star review. He tells his family.

This scenario hit approximately 50,000 users during a single Big Billion Days event — not because the engineers were negligent, but because no one explicitly designed the rollback path. The payment service and the inventory service each worked correctly in isolation. The bug was in the gap between them.

Phase 1 — Domain decomposition

What services do you need?

Start with business subdomains, not technology. Each service owns its own isolated database — no cross-service JOINs. Three valid isolation tiers exist: private tables within a shared DB (monolith on-ramp), schema-per-service, or a fully dedicated database server per service.

Order Service

Owns the order lifecycle state machine from PENDING to DELIVERED. The authoritative record of what the customer bought.

PostgreSQL (ACID, row locking)

Inventory Service

Manages stock reservation and release. Flash-sale concurrency handled via SKIP LOCKED row-per-unit pooling (Shopify-verified).

MySQL + Vitess sharding

Payment Service

Authorization, capture, refund. All mutating operations accept an idempotency key stored in a durable journal table — never Redis TTL.

PostgreSQL + idempotency journal

Fulfillment Service

Warehouse pick/pack/ship. Integrates with external WMS via outbound events. Owns shipment tracking state.

PostgreSQL + outbox table

Notification Service

Email, SMS, push. Pure consumer — subscribes to domain events, never owns any state. Idempotent by message ID.

Kafka consumer + SendGrid/Twilio

Cart Service

Ephemeral pre-order state. Lost cart = low business impact. Read-heavy, session-scoped. No saga participation needed.

Redis (TTL-based)

Order Read Model (CQRS)

Denormalized view for order history, dashboards, and multi-service queries. Updated by consuming domain events. Eventually consistent.

MongoDB / DynamoDB

Search / Catalog Service

Product discovery and search. Separate from order domain. Synced from product master via CDC.

Elasticsearch / Typesense
Architect principle: If a JOIN would cross a service boundary, you have a design problem. Either the two services should be one, or you need a CQRS read model that pre-joins the data via events.

Step order is a design choice. The diagram above authorizes payment first and then reserves stock; many designs (and the interview version of this answer) reserve inventory first, because a soft reservation is cheap to undo while a payment is not. Pick one order deliberately and design the compensations around it. The failure paths below assume inventory is reserved first and payment is captured second.

Design trap: Do not let multiple services write to the order status field. Only the Order Service owns orders.status. Other services communicate state changes via events; the Order Service updates its own state in response.

The stuck order problem — always address this

What happens when an order stays in PAYMENT_INITIATED for more than five minutes? The payment gateway received the charge request but the response was lost in a network failure. The fix: an async payment status poller queries the gateway every 30 seconds for all orders in PAYMENT_INITIATED older than five minutes. Because the charge used an idempotency key, querying the gateway for that key returns the existing result — either confirmed (advance to PAYMENT_CONFIRMED) or failed (advance to CANCELLED).

The state machine is the recovery contract, not a diagram detail. Every state is a crash recovery point. For each state you define you are committing to: what action created it, what action moves it forward, what action compensates it if the forward action fails, and what happens if the system crashes while in it. A state transition without a defined reversal is a design gap: the customer can end up charged with no order fulfilled.

Phase 3 — Distributed consistency

Why ACID breaks across services, and the Saga pattern

Verified 3-0 (microservices.io + Microsoft Azure Architecture Center): The Saga pattern enables distributed consistency across microservices without 2PC by decomposing a multi-service operation into local transactions, each updating exactly one service's database. When a step fails, it executes compensating transactions — there is no automatic ACID-style rollback.

The cross-service problem

Within a single relational database, ACID is cheap: BEGIN; UPDATE inventory ...; INSERT INTO orders ...; COMMIT; either both writes succeed or neither does, and application code never sees a half-written state. In a microservices architecture the Payment Service and the Inventory Service own separate databases and are connected only by a network. There is no shared transaction coordinator — no single COMMIT that spans both.

If you charge the card (Payment DB write succeeds) and then the inventory call times out or crashes, you are in an inconsistent distributed state: money is taken, there is no reservation and no order, and nothing will automatically undo the payment.

Why not 2PC / distributed transactions?

Two-phase commit asks every participant “are you prepared to commit?” and then sends COMMIT to all or ROLLBACK to all. It fails at microservices scale for compounding reasons. Spanning a database and Kafka is not viable at all — Kafka cannot be enlisted in XA protocols — and even between two RDBMS instances it behaves badly:

  • Blocking locks — participants hold locks from Phase 1 until the Phase 2 decision arrives. One slow participant blocks every other transaction touching the same rows, and under load this cascades into lock storms.
  • Coordinator is a single point of failure — if it crashes between phases, participants sit in a “prepared” limbo with locks held until a human intervenes.
  • CAP theorem — 2PC needs every participant reachable. Under a network partition it is unavailable: it chooses consistency over availability, the wrong trade-off for a checkout that must keep taking orders while one downstream service is degraded.

The industry has moved to the Saga pattern. Use 2PC only inside a single database instance, where it is simply how a local transaction works.

The fundamental truth: in a network partition you must choose between Consistency and Availability. For user-facing transactions availability usually wins — take the order and reconcile asynchronously rather than block the user until every downstream service confirms atomically.

What a Saga is, and what it trades away

A Saga is a sequence of local transactions. Each step commits to its own database and publishes an event (or receives a command). If step N fails, the saga runs compensating transactions for steps 1 through N-1. No global lock is held across steps; the saga accepts temporal inconsistency — for a brief period money may be charged before the order is confirmed — and restores consistency when a failure is detected. It trades atomicity for availability: the inconsistency window is typically seconds to minutes and always resolves to a consistent final state.

A saga is never “abandoned”: it always runs to one of two terminal states, Completed (all forward steps succeeded) or Compensated/Aborted (a failure occurred and all compensations ran). Typical state names:

  • STARTED — saga executing forward steps normally
  • ABORTING — a step failed, compensating transactions executing in reverse
  • ABORTED / COMPENSATED — all compensations complete, saga fully rolled back
  • COMPLETED — all forward steps succeeded
PENDING
  → step 1 succeeds → STEP_1_DONE
  → step 2 succeeds → STEP_2_DONE
  → step 3 fails   → COMPENSATING
  → comp 2 runs    → STEP_2_COMPENSATED
  → comp 1 runs    → STEP_1_COMPENSATED
  → all done       → COMPENSATED (terminal)
Critical isolation gap (Verified 3-0, InfoQ + Microsoft): The saga provides no cross-service isolation. The effective isolation level across the business transaction is "read uncommitted". Each service's local transaction commits while the saga is still running — intermediate states are visible to concurrent operations. Concrete anomalies: dirty reads, lost updates, fuzzy reads. You must design countermeasures explicitly.

Countermeasures for saga isolation gaps

  • Semantic locks: Set a flag (e.g., order.status = RESERVING) before committing a saga step. Other operations see this and back off or wait.
  • Pessimistic views: Read model queries filter out orders in intermediate saga states.
  • Versioned optimistic locking: Add a version column to aggregates; UPDATE increments it. Concurrent writes fail with a version mismatch and retry.

Choreography in practice

Order flow with choreography: Order Service publishes order.created → Payment Service charges the card and publishes payment.completed → Inventory Service reserves stock and publishes inventory.reserved → Fulfillment Service creates the shipment. If inventory fails, it emits INVENTORY_FAILED and the Payment Service reacts by refunding.

async function placeOrder(cart, userId) {
  const order = await db('orders').insert({ userId, status: 'PENDING', items: cart.items });
  await kafka.produce('ORDER_PLACED', { orderId: order.id, amount: cart.total, userId });
  return order;
}

// PaymentService: reacts to ORDER_PLACED
kafka.subscribe('ORDER_PLACED', async ({ orderId, amount, userId }) => {
  try {
    const charge = await paymentGateway.charge({ userId, amount, idempotencyKey: orderId });
    await db('payments').insert({ orderId, chargeId: charge.id, status: 'CHARGED' });
    await kafka.produce('PAYMENT_COMPLETED', { orderId, chargeId: charge.id });
  } catch (err) {
    await kafka.produce('PAYMENT_FAILED', { orderId, reason: err.message });
  }
});

// InventoryService: reacts to PAYMENT_COMPLETED
kafka.subscribe('PAYMENT_COMPLETED', async ({ orderId }) => {
  const order = await db('orders').findById(orderId);
  try {
    await db('inventory').reserveItems(order.items, orderId);
    await kafka.produce('INVENTORY_RESERVED', { orderId });
  } catch (err) {
    await kafka.produce('INVENTORY_FAILED', { orderId, reason: err.message });
  }
});

// PaymentService: compensates if inventory fails
kafka.subscribe('INVENTORY_FAILED', async ({ orderId }) => {
  const payment = await db('payments').findByOrderId(orderId);
  await paymentGateway.refund({ chargeId: payment.chargeId, idempotencyKey: `refund-${orderId}` });
  await db('payments').update(orderId, { status: 'REFUNDED' });
  await kafka.produce('PAYMENT_REFUNDED', { orderId });
});

Orchestration in practice

The orchestrator owns the complete view of every order's progress. FAANG-style order platforms use it because order state is business-critical, compensation is complex, and “why is order X stuck?” is a daily operational question. Choreography remains a good fit for non-critical async flows such as analytics or notification fan-out.

// SagaOrchestrator — owns the saga state machine
class CheckoutSagaOrchestrator {
  async start(sagaId, payload) {
    await this.saveSagaState(sagaId, 'CHARGING_PAYMENT');
    await kafka.produce('CMD_CHARGE_PAYMENT', { sagaId, ...payload });
  }

  async onPaymentCharged(sagaId, chargeId) {
    await this.saveSagaState(sagaId, 'RESERVING_INVENTORY');
    await kafka.produce('CMD_RESERVE_INVENTORY', { sagaId, chargeId });
  }

  async onInventoryReserved(sagaId) {
    await this.saveSagaState(sagaId, 'CREATING_ORDER');
    await kafka.produce('CMD_CREATE_ORDER', { sagaId });
  }

  async onOrderCreated(sagaId) {
    await this.saveSagaState(sagaId, 'COMPLETED');
    // saga done — notify user
  }

  // Compensation path
  async onInventoryFailed(sagaId) {
    await this.saveSagaState(sagaId, 'COMPENSATING_PAYMENT');
    const state = await this.loadSagaState(sagaId);
    await kafka.produce('CMD_REFUND_PAYMENT', { sagaId, chargeId: state.chargeId });
  }

  async onPaymentRefunded(sagaId) {
    await this.saveSagaState(sagaId, 'COMPENSATED');
    // saga ended with rollback — notify user
  }
}

JavaScript Example — Saga Orchestrator (Order Flow) 
// Durable saga orchestrator — each step is a local transaction
// In production: use Temporal.io or Apache Camunda for durability

class OrderSagaOrchestrator {
  constructor({ inventoryService, paymentService, fulfillmentService, orderRepo }) {
    this.inventory = inventoryService;
    this.payment = paymentService;
    this.fulfillment = fulfillmentService;
    this.orderRepo = orderRepo;
  }

  async execute(orderId) {
    const saga = await this.orderRepo.createSaga(orderId, 'STARTED');

    try {
      // Step 1: reserve inventory (local transaction in Inventory Service)
      const reservation = await this.inventory.reserve(orderId);
      await saga.recordStep('INVENTORY_RESERVED', reservation.id);

      // Step 2: authorize payment (local transaction in Payment Service)
      const auth = await this.payment.authorize(orderId, { idempotencyKey: `order_${orderId}_auth` });
      await saga.recordStep('PAYMENT_AUTHORIZED', auth.chargeId);

      // Step 3: confirm order (local transaction in Order Service)
      await this.orderRepo.transition(orderId, 'CONFIRMED');
      await saga.recordStep('ORDER_CONFIRMED');

      // Step 4: hand to fulfillment (local transaction in Fulfillment Service)
      await this.fulfillment.allocate(orderId);
      await saga.complete();

    } catch (err) {
      // Compensate in reverse order
      await saga.transition('ABORTING');
      await this.#compensate(saga, orderId);
      await saga.transition('ABORTED');
      throw err;
    }
  }

  async #compensate(saga, orderId) {
    const steps = await saga.getCompletedSteps(); // ['PAYMENT_AUTHORIZED', 'INVENTORY_RESERVED']

    for (const step of steps.reverse()) {
      switch (step.name) {
        case 'PAYMENT_AUTHORIZED':
          await this.payment.reverse(step.data, { idempotencyKey: `order_${orderId}_refund` });
          break;
        case 'INVENTORY_RESERVED':
          await this.inventory.release(step.data);
          break;
      }
    }
  }
}

Compensating transactions

A compensating transaction is a business-level semantic undo. It is not a database rollback — the original transaction already committed. A compensation is a new forward transaction that reverses the business effect. Design the table below before the happy path.

Forward StepWhat It ChangesCompensating Action
Reserve inventoryInventory count decremented; reservation record createdRelease reservation; return units to the available pool
Charge paymentCustomer card/UPI charged; charge record createdIssue full refund to the original payment method; mark charge as refunded
Create orderOrder record created (CONFIRMED)Cancel order record (CANCELLED)
Create fulfillment / schedule shippingWarehouse queue entry created; pickup scheduled with logistics providerCancel fulfillment and pickup request; return items to warehouse
Send confirmation notificationEmail/SMS/push sent to customerSend cancellation notification (“Order cancelled, refund initiated”) — the first message cannot be unsent

Notifications cannot be undone, which is why that step goes last: all reversible operations run first and irreversible ones run after the order is committed. If the order is cancelled before the notification step, nothing is sent; if after, the compensation is a follow-up message.

Compensations must be idempotent

The orchestrator may retry on a network timeout and the broker may redeliver. If the refund is issued twice, the customer receives double the money back — a real production bug. The rule: calling a compensation N times must have the same observable effect as calling it once. The usual implementation is check-before-act, plus a gateway-side idempotency key.

JavaScript — Idempotent refund compensation 
async function issueRefund({ orderId, chargeId }) {
  // Check if we already processed this compensation
  const existing = await db('refunds').where({ orderId }).first();
  if (existing) {
    console.log(`[refund] Already refunded orderId=${orderId}, skipping`);
    return existing; // idempotent: return the same result
  }

  // Issue the actual refund via payment gateway
  const refund = await paymentGateway.refund({
    chargeId,
    idempotencyKey: `refund-${orderId}` // gateway-side idempotency too
  });

  // Record the refund (prevents duplicate processing on retry)
  await db('refunds').insert({
    orderId,
    refundId: refund.id,
    amount: refund.amount,
    createdAt: new Date()
  });

  return refund;
}

Reference implementation: step-list orchestrator with compensations

This skeleton shows step definitions with execute and compensate functions, deterministic idempotency key generation, state persistence stubs and reverse-order rollback. In production the orchestrator runs inside a durable workflow engine such as Temporal; this code illustrates the shape of the logic, not the infrastructure.

JavaScript Example 
const crypto = require('crypto');

// Each step declares what it does and how to undo it.
// compensate() is called in reverse order when any step fails.
class SagaOrchestrator {
  constructor({ db, inventoryService, paymentService, fulfillmentService, notificationService }) {
    this.db = db;

    // Steps execute in order. Compensations run in reverse on failure.
    this.steps = [
      {
        name: 'validateCart',
        execute: async (ctx) => {
          const cart = await db.query(
            'SELECT * FROM carts WHERE id = $1 FOR SHARE', [ctx.cartId]
          );
          if (!cart) throw new Error('Cart not found or expired');
          ctx.cart = cart;
          await db.updateOrderState(ctx.orderId, 'CART_VALIDATED');
        },
        // Nothing durable was changed — no compensation needed
        compensate: async (_ctx) => {},
      },
      {
        name: 'reserveInventory',
        execute: async (ctx) => {
          // Idempotency key: same orderId always maps to the same reservation attempt
          const idempotencyKey = generateKey('reserve', ctx.orderId);
          const reservation = await inventoryService.reserve({
            orderId: ctx.orderId,
            items: ctx.cart.items,
            idempotencyKey,
          });
          ctx.reservationId = reservation.id;
          await db.updateOrderState(ctx.orderId, 'INVENTORY_RESERVED');
        },
        compensate: async (ctx) => {
          if (!ctx.reservationId) return; // step never succeeded — nothing to undo
          const idempotencyKey = generateKey('release', ctx.orderId);
          await inventoryService.release({ reservationId: ctx.reservationId, idempotencyKey });
          await db.updateOrderState(ctx.orderId, 'INVENTORY_RELEASED');
        },
      },
      {
        name: 'processPayment',
        execute: async (ctx) => {
          const idempotencyKey = generateKey('charge', ctx.orderId);
          const charge = await paymentService.charge({
            orderId: ctx.orderId,
            amount: ctx.cart.totalAmount,
            customerId: ctx.customerId,
            idempotencyKey,
          });
          ctx.chargeId = charge.id;
          await db.updateOrderState(ctx.orderId, 'PAYMENT_CONFIRMED');
        },
        compensate: async (ctx) => {
          if (!ctx.chargeId) return;
          const idempotencyKey = generateKey('refund', ctx.orderId);
          await paymentService.refund({ chargeId: ctx.chargeId, idempotencyKey });
          await db.updateOrderState(ctx.orderId, 'PAYMENT_REFUNDED');
        },
      },
      {
        name: 'createFulfillment',
        execute: async (ctx) => {
          const fulfillment = await fulfillmentService.create({
            orderId: ctx.orderId,
            items: ctx.cart.items,
            shippingAddress: ctx.shippingAddress,
          });
          ctx.fulfillmentId = fulfillment.id;
          await db.updateOrderState(ctx.orderId, 'FULFILLMENT_IN_PROGRESS');
        },
        compensate: async (ctx) => {
          if (!ctx.fulfillmentId) return;
          await fulfillmentService.cancel({ fulfillmentId: ctx.fulfillmentId });
          await db.updateOrderState(ctx.orderId, 'FULFILLMENT_CANCELLED');
        },
      },
      {
        name: 'sendNotification',
        execute: async (ctx) => {
          // Dedup key prevents duplicate emails from Kafka at-least-once delivery
          const dedupKey = generateKey('notify-confirm', ctx.orderId);
          await notificationService.sendOrderConfirmation({
            orderId: ctx.orderId,
            customerId: ctx.customerId,
            dedupKey,
          });
          await db.updateOrderState(ctx.orderId, 'CONFIRMED');
        },
        // Cannot unsend the confirmation email — compensate by sending cancellation
        compensate: async (ctx) => {
          const dedupKey = generateKey('notify-cancel', ctx.orderId);
          await notificationService.sendOrderCancellation({
            orderId: ctx.orderId,
            customerId: ctx.customerId,
            dedupKey,
          }).catch((err) => {
            // Notification failure during compensation must not block the rollback
            console.error('[Saga] Cancellation notification failed (non-blocking):', err.message);
          });
        },
      },
    ];
  }

  // Deterministic idempotency key: same inputs always produce the same key
  // Safe to re-execute the same step after a crash
  generateKey(operation, orderId) {
    return crypto.createHash('sha256')
      .update(`${operation}:${orderId}`)
      .digest('hex');
  }

  async runSaga(orderId, context) {
    const ctx = { orderId, ...context };
    const executedSteps = [];

    await this.db.updateOrderState(orderId, 'PENDING');

    for (const step of this.steps) {
      try {
        await step.execute(ctx);
        executedSteps.push(step); // track for rollback
      } catch (err) {
        console.error(`[Saga] Step "${step.name}" failed for order ${orderId}: ${err.message}`);
        // Roll back all completed steps in reverse order
        await this.rollback([...executedSteps].reverse(), ctx, orderId);
        await this.db.updateOrderState(orderId, 'CANCELLED');
        throw err; // Surface to caller so they can return an error to the user
      }
    }

    return { success: true, orderId, state: 'CONFIRMED' };
  }

  async rollback(stepsToCompensate, ctx, orderId) {
    await this.db.updateOrderState(orderId, 'CANCELLING');
    for (const step of stepsToCompensate) {
      try {
        await step.compensate(ctx);
      } catch (compensationErr) {
        // Compensation failure requires human intervention — alert on this
        console.error(
          `[Saga] COMPENSATION FAILED for step "${step.name}" on order ${orderId}.`,
          `Manual intervention required. Error: ${compensationErr.message}`
        );
        // Continue compensating other steps despite this failure
      }
    }
  }
}

Phase 4 — Reliable event publishing

Transactional Outbox + CDC

The dual-write problem: how do you update the database AND publish an event to Kafka atomically? If you do them separately, one can succeed and the other can fail — leaving the system in an inconsistent state.

Verified 3-0 (microservices.io + Debezium + InfoQ): The Transactional Outbox pattern resolves this by writing the business record AND the outbox event in a single database transaction. A separate CDC relay (Debezium watching the WAL/binlog) forwards outbox records to Kafka. Guarantee: events are published if and only if the database transaction commits.

How it works

  1. Service executes a local transaction:
    • INSERT / UPDATE the business table (e.g., orders)
    • INSERT a record into the outbox table (event type + payload)
    • Single COMMIT — both writes are atomic
  2. Debezium tails the database WAL/binlog, detects the outbox INSERT, publishes to Kafka.
  3. Kafka consumers receive the event and process it.
At-least-once delivery is mandatory (Verified 3-0): After a relay crash, Debezium may republish an event it already sent (before it could record the offset). Every consumer across every service boundary must be idempotent. This is not optional.

Why it matters inside every saga step: the service must write to its database and publish an event, two separate I/O operations. If it crashes between them, the database write succeeds but the event is never published and the saga stalls silently.

Refuted myth (0-3): "CDC captures INSERT events regardless of deletion, so the outbox table stays empty at rest with no disk growth." — False. CDC fires at point-of-INSERT. Outbox records must persist until the relay confirms publication and marks them sent.
JavaScript Example — Outbox Pattern + Idempotent Consumer 
// --- Writer side: atomic business write + outbox INSERT ---

async function confirmOrder(db, orderId, paymentId) {
  return db.transaction(async (trx) => {
    // Business write
    await trx('orders')
      .where({ id: orderId })
      .update({ status: 'CONFIRMED', payment_id: paymentId, updated_at: new Date() });

    // Outbox write (same transaction — atomic)
    await trx('outbox').insert({
      id: crypto.randomUUID(),
      event_type: 'OrderConfirmed',
      aggregate_id: orderId,
      payload: JSON.stringify({ orderId, paymentId }),
      created_at: new Date(),
      published: false,
    });
  });
}

// --- CDC relay (Debezium forwards outbox rows to Kafka automatically) ---
// No application code needed here — Debezium watches the WAL

// --- Consumer side: idempotent processing via journal table ---

async function handleOrderConfirmed(db, message) {
  const messageId = message.headers['message-id']; // UUID from outbox.id

  return db.transaction(async (trx) => {
    // Check journal — skip if already processed
    const existing = await trx('processed_events')
      .where({ message_id: messageId })
      .first();

    if (existing) {
      console.log(`[idempotent] Skipping already-processed message ${messageId}`);
      return; // safe to return — idempotent
    }

    // Do the actual work
    const payload = JSON.parse(message.value);
    await trx('fulfillment_queue').insert({
      order_id: payload.orderId,
      status: 'QUEUED',
      created_at: new Date(),
    });

    // Record in journal (same transaction — atomic)
    await trx('processed_events').insert({
      message_id: messageId,
      processed_at: new Date(),
    });
  });
}

No Debezium? A polling relay

Without CDC, a separate relay process polls the outbox table and forwards unpublished events to the broker, marking each published only after the broker confirms receipt. Failed publishes are retried on the next cycle, which is another reason consumers must be idempotent.

JavaScript Example — Polling outbox relay 
// Step 2: Relay process — separate process, runs on an interval
async function relayOutboxEvents() {
  // Fetch unpublished events in creation order
  const events = await db('outbox_events')
    .where({ published: false })
    .orderBy('created_at', 'asc')
    .limit(100);

  for (const event of events) {
    try {
      // Publish to Kafka (or any broker)
      await kafka.produce(event.event_type, event.payload, {
        key: event.aggregate_id // partition by aggregate for ordering
      });

      // Mark published only after broker confirms receipt
      await db('outbox_events')
        .where({ id: event.id })
        .update({ published: true, published_at: new Date() });
    } catch (err) {
      // Relay will retry this event on next poll cycle — do not mark published
      console.error(`[outbox-relay] Failed to publish event ${event.id}:`, err.message);
    }
  }
}

// Relay runs every second (or use Debezium CDC for zero-polling production setup)
setInterval(relayOutboxEvents, 1000);

Phase 5 — Reliability pattern

Idempotency everywhere

Idempotency is not an advanced topic. In a distributed system every write will eventually be called more than once: network timeouts cause retries, saga compensation re-executes steps, and load balancers retry on connection errors. Without idempotency you will double-charge customers, double-reserve inventory and send duplicate notifications — it is a matter of when, not if.

The double-charge scenario, step by step: the browser submits the payment form; the Payment Service calls Stripe; Stripe charges the card; the response is lost in a timeout. From the browser's perspective the request failed, so it retries and the Payment Service calls Stripe again. Without idempotency the card is charged twice. With idempotency both calls carry the same key and Stripe returns the cached result of the first call.

Key design for each service

ServiceIdempotency Key FormulaWhat Duplicate Handling Prevents
Order Service SHA-256(sessionId + cartHash) Duplicate checkout from browser retry creating two orders for one cart
Inventory Service orderId (already unique per order) Saga re-execution reserving the same inventory twice for the same order
Payment Service SHA-256(orderId + customerId + amount) Saga retry charging the customer twice for the same order
Notification Service SHA-256(orderId + notificationType) Kafka at-least-once delivery sending duplicate confirmation emails

Where to store keys: a durable database, not Redis

Use PostgreSQL, not Redis with a TTL. A restart or eviction policy can remove a Redis key before its purpose is served — exactly the root cause of the double-charge incident above. A PostgreSQL table with the key and the response stored as JSON survives restarts, is queryable for debugging and has the same transaction guarantees as the business data it protects. “We'd use Redis to track whether a charge already happened” fails the durability test.

Client-generated keys and server-side lookup

The key must be generated client-side and tied to the cart/checkout session, not to the request attempt, so the same key survives page refreshes, tab closures and network retries. The server stores the key-to-response mapping and returns the cached result on any duplicate call. (The 24-hour expiry in the sample below is a product decision, not a technical requirement.)

JavaScript — Idempotency key storage and lookup 
// Server-side idempotency middleware
async function withIdempotency(idempotencyKey, operation) {
  // Check for cached result
  const cached = await db('idempotency_keys')
    .where({ key: idempotencyKey })
    .first();

  if (cached) {
    // Return the same result as the original call — do NOT re-execute
    console.log(`[idempotency] Cache hit for key=${idempotencyKey}`);
    return JSON.parse(cached.result);
  }

  // Execute the operation for the first time
  const result = await operation();

  // Store the result so future retries return it
  await db('idempotency_keys').insert({
    key: idempotencyKey,
    result: JSON.stringify(result),
    created_at: new Date(),
    expires_at: new Date(Date.now() + 24 * 60 * 60 * 1000) // 24-hour TTL
  });

  return result;
}

// Usage in checkout handler
app.post('/checkout', async (req, res) => {
  const idempotencyKey = req.headers['x-idempotency-key']; // UUID from client
  if (!idempotencyKey) return res.status(400).json({ error: 'x-idempotency-key required' });

  const result = await withIdempotency(idempotencyKey, async () => {
    return await checkoutService.initiateCheckout(req.body);
  });

  res.json(result);
});

Idempotency at the API layer (Stripe's pattern)

For payment operations, the client passes an idempotency key on every mutating request. The server stores the key-to-response mapping in a durable database journal (not Redis with a TTL).

// Payment service: idempotent charge endpoint
// Key stored in PostgreSQL — survives restarts, not subject to TTL eviction

async function chargeWithIdempotency(db, { idempotencyKey, orderId, amount, currency }) {
  // Check for existing result
  const existing = await db('idempotency_keys')
    .where({ key: idempotencyKey })
    .first();

    // Return the same response as the original request — no double charge

  }

  // Execute the charge
  const charge = await paymentGateway.charge({ orderId, amount, currency });

  // Store result durably (within same transaction as charge record)
  await db('idempotency_keys').insert({

    response_body: JSON.stringify(charge),
    created_at: new Date(),
    order_id: orderId,
  });

  return charge;
}

Idempotency key format — ULID vs UUIDv4

Verified 2-1 (Shopify Engineering — directionally plausible, not a universal benchmark): Switching from UUIDv4 to ULID for idempotency keys reduced INSERT statement duration by ~50% in one Shopify payment system. Mechanism: ULID is timestamp-prefixed (lexicographically sequential), aligning inserts at the B-tree index tail and eliminating random leaf splits. UUIDv4 is fully random, scattering writes across the B-tree.
Refuted (0-3): "Idempotency keys must use ULID and have a validity window of 24 hours or less." — The 24-hour window is not universally verified. ULID is a performance optimisation, not a functional requirement. The validity window is a product/business decision.
Phase 6 — Query scaling

CQRS — Separating reads from writes

Verified 3-0 (microservices.io): CQRS read models use denormalized views backed by NoSQL document stores or key-value stores optimized for specific query patterns, enabling high-throughput reads. The concrete tradeoff is eventual consistency — read replicas may lag behind the write side at any moment.

The problem it solves: a query like "show the customer their order with item names, payment status, and current shipment ETA" spans three services (Order, Payment, Fulfillment). You cannot JOIN across their databases. You have two options:

OptionHowTradeoff
API Composition API gateway fans out to all three services, joins the responses in memory Always fresh data; higher latency; 3 network hops per request
CQRS Read Model Consume domain events, build a pre-joined document in MongoDB/DynamoDB Sub-millisecond reads; N seconds lag; extra infrastructure
Refuted myth (0-3): "CQRS is mandatory when using database-per-service." — False. API composition is a valid alternative for simpler query patterns. CQRS is recommended for high-read-volume, complex cross-service queries — not universally required.

When to choose CQRS over API Composition:

  • Read volume is 10× or more than write volume
  • Query spans more than 2 services
  • Real-time freshness is not required (order history, dashboards)
  • Complex aggregations or full-text search across multiple entities
JavaScript Example — CQRS Read Model Builder 
// Event-driven read model builder
// Consumes domain events → builds denormalized order documents in MongoDB

const { Kafka } = require('kafkajs');
const { MongoClient } = require('mongodb');

const kafka = new Kafka({ clientId: 'order-read-model', brokers: ['kafka:9092'] });
const consumer = kafka.consumer({ groupId: 'order-read-model-group' });

async function buildReadModel() {
  const mongo = await MongoClient.connect(process.env.MONGO_URI);
  const orders = mongo.db('read_models').collection('orders');

  await consumer.connect();
  await consumer.subscribe({ topics: ['order-events', 'payment-events', 'fulfillment-events'] });

  await consumer.run({
    eachMessage: async ({ topic, message }) => {
      const event = JSON.parse(message.value.toString());

      switch (event.type) {
        case 'OrderCreated':
          // Upsert: create the document skeleton
          await orders.updateOne(
            { orderId: event.orderId },
            { $setOnInsert: { orderId: event.orderId, items: event.items, customerId: event.customerId, status: 'PENDING', createdAt: event.timestamp } },
            { upsert: true }
          );
          break;

        case 'PaymentAuthorized':
          // Merge payment data into the existing document
          await orders.updateOne(
            { orderId: event.orderId },
            { $set: { paymentStatus: 'AUTHORIZED', paymentId: event.chargeId, amount: event.amount } }
          );
          break;

        case 'OrderShipped':
          // Merge fulfillment data — no cross-service JOIN needed at query time
          await orders.updateOne(
            { orderId: event.orderId },
            { $set: { status: 'SHIPPED', trackingNumber: event.trackingNumber, estimatedDelivery: event.eta } }
          );
          break;
      }
    },
  });
}

  return orders.findOne({ orderId }); // returns the full pre-joined document

Vitess sharding — Shopify's verified approach

Inventory reservation under flash sales: from naive to correct

Flash sales (for example 100,000 concurrent orders for 1,000 units) deserve their own treatment because the naive approach fails dramatically. Walking the progression from naive to correct is exactly the reasoning an interviewer wants to see.

1. The naive SQL approach and why it fails

SQL — Naive, Fails at Scale 
-- The naive approach: decrement with a guard
UPDATE items SET quantity = quantity - 1
WHERE id = ? AND quantity > 0;

-- At 100k concurrent requests:
-- 100k transactions attempt to lock the SAME row
-- Row-level lock contention serializes execution
-- Queue of waiting locks grows to 100k
-- Each waits for the previous to release
-- Total time: 100k * avg_lock_wait_time = minutes
-- Timeouts cascade; retries amplify the problem

2. Optimistic locking (moderate concurrency, simpler systems)

SQL — Optimistic Locking with Version Column 
-- Add a version column to the inventory table
-- ALTER TABLE items ADD COLUMN version INTEGER NOT NULL DEFAULT 0;

-- On reservation attempt:
UPDATE items
SET quantity = quantity - 1, version = version + 1
WHERE id = ? AND version = ? AND quantity > 0;

-- If 0 rows affected: someone else updated first — retry with new version
-- Works well up to ~1,000 concurrent updates before retry storms degrade throughput
-- Never use this for flash sales at 100k concurrent requests

3. SELECT ... SKIP LOCKED with row-per-unit pooling

Verified (Shopify Engineering): Shopify replaced Redis counters with MySQL using SELECT ... SKIP LOCKED for flash-sale inventory. Row-per-unit pooling: one database row per physical inventory unit. Concurrent workers grab different units without blocking each other.
SQL — SKIP LOCKED for Row-Per-Unit Inventory 
-- Row-per-unit model: one database row per physical inventory unit
-- SKIP LOCKED: skip rows locked by other transactions instead of waiting
BEGIN;

SELECT id FROM inventory_units
WHERE item_id = ? AND status = 'available'
LIMIT 1
FOR UPDATE SKIP LOCKED;

-- If no row returned: all units are locked (sold out or in-flight)
-- If a row is returned: this transaction holds the lock exclusively

UPDATE inventory_units
SET status = 'reserved', order_id = ?
WHERE id = ?;  -- the id from the SELECT above

COMMIT;

-- Result: concurrent transactions each grab a DIFFERENT row
-- Zero contention; each transaction completes immediately
-- Works well up to ~5,000 concurrent reservations per second
-- Above that: use Redis DECR for the hot path
JavaScript Example — Inventory Reservation with SKIP LOCKED 
// Row-per-unit inventory reservation — handles concurrent flash-sale requests
// Each inventory unit is its own row; SKIP LOCKED lets workers grab different units concurrently

async function reserveInventoryUnit(db, productId, orderId) {
  return db.transaction(async (trx) => {
    // Grab one available unit, skip any rows locked by concurrent transactions
    const [unit] = await trx.raw(`
      SELECT id FROM inventory_units
      WHERE product_id = ? AND status = 'available'
      LIMIT 1
      FOR UPDATE SKIP LOCKED
    `, [productId]);

    if (!unit) {
      throw new Error(`Out of stock: product ${productId}`);
    }

    // Mark as reserved in the same transaction
    await trx('inventory_units')
      .where({ id: unit.id })
      .update({ status: 'reserved', order_id: orderId, reserved_at: new Date() });

    // Write outbox event atomically
    await trx('outbox').insert({
      id: crypto.randomUUID(),
      event_type: 'InventoryReserved',
      aggregate_id: orderId,
      payload: JSON.stringify({ orderId, productId, unitId: unit.id }),
    });

    return unit.id;
  });
}

// Release on cancellation — compensating transaction
async function releaseInventoryUnit(db, unitId) {
  return db.transaction(async (trx) => {
    await trx('inventory_units')
      .where({ id: unitId })
      .update({ status: 'available', order_id: null, reserved_at: null });

    await trx('outbox').insert({
      id: crypto.randomUUID(),
      event_type: 'InventoryReleased',
      aggregate_id: unitId,
      payload: JSON.stringify({ unitId }),
    });
  });
}

4. Redis atomic DECR as a hot-path gate (flash sales at 100k/sec)

Two-phase reservation. Phase 1: pre-load the count (SET inventory:item:42 1000) and DECR on each attempt; below zero means INCR to undo and reject as sold out. Redis DECR is atomic and in-memory, so it absorbs 100k concurrent requests. Phase 2: tentatively reserved orders write a durable confirmation to the database within 30 seconds; if confirmation fails (Redis and DB diverge after a Redis restart) the Redis reservation is released. At most 1,000 DB writes happen; the 99,000 rejections never touch the database. Redis is therefore a fast admission gate, never the source of truth.

Redis — Atomic Inventory Reservation 
// Pre-load before flash sale starts (done once, before requests arrive)
// SET inventory:item:42 1000

async function reserveInventoryRedis(redisClient, itemId, orderId) {
  // DECR is atomic in Redis — no race condition possible
  const remaining = await redisClient.decr(`inventory:item:${itemId}`);

  if (remaining < 0) {
    // We went below zero — undo the decrement and reject
    await redisClient.incr(`inventory:item:${itemId}`);
    return { success: false, reason: 'SOLD_OUT' };
  }

  // Reservation tentatively accepted — confirm in DB within 30 seconds
  // Schedule async confirmation job
  await confirmationQueue.add({ itemId, orderId, expiresAt: Date.now() + 30_000 });

  return { success: true, reservationId: orderId };
}

// DB confirmation (runs asynchronously, at most 1000 times for 1000 units)
async function confirmReservationInDb(db, itemId, orderId) {
  try {
    await db.transaction(async (trx) => {
      // Write the durable reservation record
      await trx('inventory_reservations').insert({
        item_id: itemId,
        order_id: orderId,
        reserved_at: new Date(),
        status: 'CONFIRMED',
      });
    });
  } catch (err) {
    // Confirmation failed — undo the Redis decrement
    await redisClient.incr(`inventory:item:${itemId}`);
    throw err;
  }
}

In the interview, walk the approaches in this order: naive (why it fails), optimistic locking (works to roughly 1,000 concurrent updates before retry storms), SKIP LOCKED (excellent to about 5,000 reservations per second per database node) and Redis DECR plus durable confirmation (about 100,000 per second on one Redis node with sub-millisecond latency). An interviewer asking “why not just SKIP LOCKED?” is checking whether you know the throughput limits.

Timeouts and failure classification

The most dangerous failure is not a clean error but a silent hang: a service call with no timeout waits forever, the caller's thread pool fills up, and the whole system cascades. Every inter-service call in a saga must have an explicit timeout set in code (not an OS default), sized to roughly 3x the downstream p99.

  • Transient failures — network blip, brief overload, GC pause. Retry with exponential backoff plus jitter (prevents synchronized retry storms), capped at 3–5 attempts.
  • Permanent failures — invalid card, out-of-stock item, fraud flag. They will not resolve on retry: trigger compensation immediately instead of wasting retries on a business error.
JavaScript — Retry with exponential backoff + jitter 
        async function callWithRetry(fn, { maxRetries = 3, baseDelayMs = 200 } = {}) {
  let lastError;
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (isPermanentFailure(err)) {
        throw err; // Don't retry permanent errors — trigger compensation immediately
      }
      lastError = err;
      if (attempt < maxRetries) {
        // Exponential backoff with jitter: delay = base * 2^attempt + random(0, base)
        const delay = baseDelayMs * Math.pow(2, attempt) + Math.random() * baseDelayMs;
        console.warn(`[retry] attempt ${attempt + 1} failed, retrying in ${Math.round(delay)}ms`);
        await new Promise(r => setTimeout(r, delay));
      }
    }
  }
  throw lastError; // All retries exhausted — caller decides: compensate or DLQ
}

function isPermanentFailure(err) {
  // HTTP 4xx (except 429 Too Many Requests) are permanent
  return err.statusCode && err.statusCode >= 400 && err.statusCode < 500
    && err.statusCode !== 429;
}

// Usage in saga step
async function chargePayment({ sagaId, amount, userId }) {
  const timeout = 5000; // 5s explicit timeout
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeout);
  try {
    return await callWithRetry(
      () => paymentGateway.charge({ userId, amount }, { signal: controller.signal }),
      { maxRetries: 3, baseDelayMs: 300 }
    );
  } finally {
    clearTimeout(timer);
  }
}

Dead Letter Queue for stuck sagas

After retries are exhausted and the failure is not permanent, the saga is stuck: it cannot proceed, and nobody has decided to compensate — a customer has money taken and no order. After N failed retries, publish the saga event to a Dead Letter Queue (a special Kafka topic or queue) that operators monitor via a dashboard.

  • Each DLQ entry is a specific customer waiting for resolution.
  • Operations sees sagaId, current step, failure reason, customer ID, amount and timestamp.
  • They choose to manually complete (override inventory, confirm order) or manually compensate (trigger refund).
  • Define a DLQ SLA, for example “all stuck sagas resolved within 2 hours”.
JavaScript — Publish to DLQ after exhausted retries 
        async function processSagaStep(event) {
  const { sagaId, step, payload, retryCount = 0 } = event;
  const MAX_RETRIES = 5;

  try {
    await executeStep(step, payload);
  } catch (err) {
    if (retryCount >= MAX_RETRIES) {
      // Give up — send to DLQ for human review
      await kafka.produce('saga.dlq', JSON.stringify({
        sagaId,
        step,
        payload,
        failureReason: err.message,
        failedAt: new Date().toISOString(),
        retryCount
      }));
      await db('saga_executions').where({ sagaId }).update({
        status: 'STUCK',
        stuckAt: new Date(),
        stuckStep: step,
        stuckReason: err.message
      });
      // Alert ops team via PagerDuty / Slack webhook
      await alertOps({ sagaId, step, err });
      return;
    }

    // Requeue with incremented retry count
    const delay = Math.pow(2, retryCount) * 1000;
    await requeueWithDelay({ ...event, retryCount: retryCount + 1 }, delay);
  }
}

Saga state persistence and recovery

Never hold saga state in process memory. If the orchestrator restarts (deployment, crash, OOM kill) every in-flight saga is lost, permanently stuck with no record of where it was — not even the DLQ can pick it up. Persist saga state durably before any step is initiated; on restart, query all non-terminal sagas and resume them. This is also the answer to “the orchestrator crashes mid-step”: re-execute the current step with the same idempotency key.

SQL — Saga execution state table 
CREATE TABLE saga_executions (
  saga_id         UUID PRIMARY KEY,
  saga_type       VARCHAR(100) NOT NULL,         -- e.g. 'CHECKOUT_SAGA'

  status          VARCHAR(50)  NOT NULL,          -- PENDING, IN_PROGRESS, COMPLETED, COMPENSATING, COMPENSATED, STUCK
  payload         JSONB        NOT NULL,          -- full saga context (order, user, amounts)
  created_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  completed_at    TIMESTAMPTZ,
  stuck_reason    TEXT
);

        // On orchestrator service startup

    .whereNotIn('status', ['COMPLETED', 'COMPENSATED', 'STUCK'])
    .orderBy('created_at', 'asc');

  console.log(`[startup] Resuming ${inFlight.length} in-flight sagas`);

  for (const saga of inFlight) {
    // Re-emit the command for the current step — idempotency keys ensure no duplication
    await orchestrator.resumeFromStep(saga.saga_id, saga.current_step, saga.payload);
  }
}

Candidate B (hired at L5): Does not pick up the marker. Instead: "Before I start designing, I want to clarify a few constraints. What's the scale — 10k or 10M DAU? Interview Drill

The failure questions interviewers ask

These four questions are asked at nearly every FAANG system design interview for e-commerce. An interviewer who has not asked these is leaving signal on the table. Prepare a concrete, specific answer for each. "We'd handle it" and "we'd add retry logic" are not answers — they are signals that you have not thought through the failure.

Question 1 — asked at almost every interview
Payment succeeds, but inventory reservation fails because the item just sold out. What happens?
The Saga Orchestrator receives the INVENTORY_UNAVAILABLE event from the Inventory Service. It executes the compensation for the previous step — payment: calls PaymentService.refund(chargeId, idempotencyKey). The idempotency key ensures this refund call is safe to retry. Sets order state to CANCELLED with reason INVENTORY_UNAVAILABLE. Publishes a cancellation event which the Notification Service consumes to send the customer an apology with an expected refund timeline (3–5 business days, constrained by the payment gateway, not by us). The inventory count is already correct — no rollback needed there because the reservation failed cleanly.
Question 2 — tests crash recovery understanding
The Saga Orchestrator crashes in the middle of executing a step. How does the system recover?
The Saga Orchestrator persists every state transition to the database before executing the next step — using the transactional outbox pattern so state and event are written atomically. On restart, the Orchestrator queries for all orders in intermediate states (PAYMENT_INITIATED, INVENTORY_RESERVING) with age greater than a timeout threshold. For each stuck order, it re-executes the current step using the same idempotency key that was assigned before the crash. Because all step calls are idempotent, re-executing a step that may have already succeeded is safe — the service returns the cached result without duplicating the action.
Question 3 — tests Kafka dependency understanding
Kafka goes down. Can orders still be processed?
Define the answer by what Kafka is used for in the design. If Saga coordination is synchronous (the Orchestrator calls services directly and Kafka is only for async fan-out like notifications and CQRS projection), then orders continue to process. Only asynchronous steps — notifications, analytics, read model updates — are delayed until Kafka recovers. If the Saga uses Kafka for step coordination itself, orders go to a local persistent queue (a database table with a poller that publishes to Kafka when it is available). This is acceptable partial degradation: orders queue up rather than fail. The maximum delay equals Kafka's recovery time. The important signal here is that you have separated the critical path (order creation, payment, inventory) from the non-critical async path (notifications, analytics).
Question 4 — the flash sale question, asked at almost every FAANG interview
100,000 concurrent flash sale orders for 1,000 units. How does the Inventory Service handle this without overselling or crashing?
Two-phase reservation. Phase 1: Redis atomic DECR. Before the flash sale starts, pre-load the inventory count: SET inventory:item:42 1000. On each reservation attempt: result = DECR inventory:item:42. If result is greater than or equal to zero, the reservation is tentatively accepted. If result is less than zero, execute INCR inventory:item:42 to undo the decrement and return SOLD_OUT. Redis DECR is atomic and executes in-memory in under 0.1ms — it handles 100k concurrent requests without contention. Phase 2: DB confirmation within 30 seconds. The tentatively-reserved orders write their confirmation to PostgreSQL. If confirmation fails (Redis and DB diverge after a Redis restart), release the Redis reservation. At most 1,000 DB writes succeed — the 99,000 rejections never hit the database. This handles the concurrency on the fast path and defers durability to the slow path.

The flash sale question is asked at almost every FAANG interview for e-commerce systems. If you answer it with "two-phase Redis reservation followed by database confirmation," you have demonstrated L5-level thinking. If you add "and we prevent the Redis-to-DB divergence by using a distributed lock during the pre-load window," you are at L6. If you say "we'd cache the inventory," you are at L3.

Interview Playbook

What to say in each phase

A 45-minute system design interview has a predictable structure. Interviewers expect you to drive the pacing. If you are waiting to be told what to do next, you are not at L5. Here is what to say in each phase.

Phase 1: First 10 minutes — requirements and scoping

  • Open with: "Before I start designing, I want to clarify the requirements."
  • Ask scale, consistency, flash sale, and payment integration questions.
  • Explicitly state what is in scope and what is out of scope.
  • Close with: "I'll design for 1M DAU, 10k peak orders per second, strong inventory consistency with no oversell, and Stripe integration. Does that framing sound right?" Wait for confirmation.

Phase 2: Core design — the 5 trade-offs to discuss

  • Saga choreography vs orchestration: choose orchestration, explain why (centralized state, debuggable, handles complex compensation).
  • Synchronous vs asynchronous payment: synchronous for better UX (immediate feedback), asynchronous for higher availability (don't block if payment gateway is slow).
  • Strong vs eventual consistency on inventory: strong means no oversell (Redis DECR), eventual means higher throughput but occasional over-reservation that requires post-hoc cancellation.
  • Monolith vs microservices for initial deployment: at early stage, a modular monolith with clear subdomain boundaries is lower-risk; decompose when independent deployability becomes the bottleneck.
  • CQRS read model vs direct DB queries: CQRS for order history and dashboards (read-heavy, span multiple services), direct DB for immediate post-order confirmation (strong consistency required).

Phase 3: Scale discussion — bottlenecks to name proactively

  • Inventory service under flash sale: Redis DECR pre-allocation — do not wait for the interviewer to ask.
  • Order database under write load: shard by order ID or customer ID; most queries are customer-scoped.
  • Payment gateway rate limits: queue and retry with exponential backoff; do not hit the gateway directly from the Saga without rate awareness.
  • Notification storm: asynchronous Kafka consumer, separate queue, per-customer rate limit to prevent notification fatigue.

The 3 things not to say

  • "I'd just use a single database transaction for the order, payment, and inventory." — Distributed transactions across service boundaries do not exist. Saying this reveals that you do not know what you are designing around.
  • "We'd fix the race condition later once we hit scale." — If you can identify the race condition (and interviewers will expect you to), you must explain how to prevent it. Deferring a known correctness problem signals that you are not thinking about production reliability.
  • "I'd use microservices for everything from day one." — Premature decomposition is expensive. Saying this without qualification signals over-engineering instinct rather than judgment. Always acknowledge the monolith-first option and state when you would decompose.

FAQ

Common architect and interview questions

Q: Choreography or orchestration for the order saga, and how do I defend it?

Choose orchestration for the order flow and defend it on three grounds. First, operational debuggability: you can query “why is order X stuck at step Y” without correlating logs across four services. Second, compensation clarity: the rollback path for payment-succeeded/inventory-failed needs a coordinator, whereas choreography leaves each service to work it out and creates gaps. Third, business criticality: when a failure means a customer is charged and receives nothing, you need the tightest control over the compensation path. Order processing has 4–6 steps (inventory, payment, fulfillment, notifications), an explicit cancellation path and an audit-trail need. Acknowledge that choreography has real advantages (no coupling point, easy to add consumers) and suits simple 2-step async flows and non-critical fan-out.

Q: Should I use a Saga or two-phase commit (2PC) for order processing?

Never propose 2PC across microservices. It is synchronous, blocks all participants for the duration of the transaction, and fails non-atomically if the coordinator crashes mid-commit. Kafka cannot participate in XA protocols at all, so any design with Kafka makes 2PC impossible on the event-publishing path. A Saga with idempotent compensating transactions gives eventual consistency without blocking.

Q: How does the customer see their order status without lag?

Two-tier approach: for the confirmation page immediately after checkout, read from the write-side Order Service directly (strong consistency). For the order history page accessed later, read from the CQRS read model (eventually consistent, sub-ms latency). Tell product that the history page may be N seconds behind.

Q: How do we handle flash sales without overselling?

Layer the solution by throughput. Up to about 5,000 reservations/second per node, use the row-per-unit pattern with SELECT ... FOR UPDATE SKIP LOCKED: each unit is one row and concurrent workers grab different units without blocking. Beyond that, use a Redis DECR admission gate for the hot path, but always follow it with a durable database confirmation within a time window and release the Redis reservation if confirmation fails. Do not use Redis counters as the sole source of truth — they are not durable across restarts and create a dual-write problem with the inventory database.

Q: How does the system recover when the Saga Orchestrator crashes mid-execution?

The orchestrator persists every state transition before executing the next step, using the transactional outbox so state and any outbound event are written atomically. On restart it queries all orders in intermediate states (PENDING, INVENTORY_RESERVED, PAYMENT_INITIATED) older than a timeout and re-executes the current step with the same idempotency key assigned before the crash. Because every step is idempotent, re-running a step that may already have succeeded returns the cached result without duplicating the action. In production use a durable workflow engine such as Temporal rather than building crash recovery from scratch.

Q: Is the transactional outbox overkill for a small team?

For a startup under about 10,000 orders/day on a monolith, probably yes: use synchronous writes and accept the occasional inconsistency until you see the failure mode. For microservices at 100,000 orders/day or more it is the minimum viable guarantee of event-to-state consistency. The failure it prevents (state updated but event not published, or the reverse) occurs under load and is hard to diagnose without it.

Q: When should we start with microservices vs a modular monolith?

Start with a well-structured modular monolith that enforces subdomain boundaries via module/package boundaries (no cross-module internal imports). Migrate using the Strangler Fig pattern when independent deployability, scaling or team autonomy actually becomes the bottleneck. Premature decomposition is more expensive than delayed decomposition.

Q: What monitoring is critical for the order saga?

Three things: (1) Saga stuck in ABORTING — a compensating transaction failed and rollback cannot complete; requires human intervention, alert immediately (this is what the DLQ feeds). (2) Outbox lag — rising Debezium CDC lag means events are not publishing and every downstream service is affected. (3) Idempotency key collision rate — rising collisions indicate abnormal retry behavior or upstream bugs.

Key Takeaway

“Payment deducted, order failed” is not a payment bug or an inventory bug; it is a distributed transaction bug — the absence of an explicit compensation path for partial failure across service boundaries. An enterprise order processing system is a distributed state machine where every transition is a local transaction, every event is published through an outbox, every consumer and compensation is idempotent, and every saga step has its compensation designed before the happy path is written. The Saga does not eliminate inconsistency; it makes it temporary and bounded by guaranteeing every saga ends COMPLETED or COMPENSATED, with the DLQ ensuring nothing is silently lost. Saga, Outbox, idempotency keys, CQRS, SKIP LOCKED and geographic circuit breaking are not independent choices but a layered answer to one question: how do you move money, stock and data reliably across services that can each fail independently, at any time, under any load? In an interview, the strongest L5/L6 answers explain which failure each pattern prevents, what constraint it imposes (eventual consistency, extra infrastructure, latency) and why that constraint is justified.
