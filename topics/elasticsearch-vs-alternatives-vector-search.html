Elasticsearch vs Alternatives & Vector/AI Search in ES 8.x / 9.x

A production-grade technical reference covering Elasticsearch vs Apache Solr, OpenSearch, Typesense, Meilisearch, Algolia, and PostgreSQL tsvector — with feature comparison tables, a decision guide, and complete JSON examples for kNN vector search, hybrid BM25+kNN with Reciprocal Rank Fusion, ELSER sparse semantic search, and every quantization option (int8_hnsw, int4_hnsw, bbq_hnsw).

TagsSearch, Elasticsearch, Vector Search, kNN, HNSW, Semantic Search, OpenSearch, Solr, Algolia
JS Example✓ Node.js Elasticsearch client — kNN indexing, hybrid search, ELSER ingest pipeline

Elasticsearch dominates search infrastructure for a reason: it handles petabyte-scale datasets, ships with the most complete aggregation engine in open-source search, and as of version 8.x has become a first-class vector database with native HNSW, quantization, and hybrid BM25+kNN search — all in a single cluster. But "use Elasticsearch for everything" is wrong. For product search on a startup's 2 M SKUs, Typesense is faster to ship and cheaper to run. For a team already on PostgreSQL with modest search requirements, tsvector avoids the operational overhead of a separate cluster entirely.

Core idea: The right search tool depends on three axes — data scale (documents + query volume), feature surface needed (aggregations, geo, analytics, ML), and operational cost budget (team size, infra). Elasticsearch wins when two or more axes are demanding. Alternatives win when you can accept a narrower feature set for a much simpler operational story.

Real-world scenario

Three teams, three right answers

Team A (e-commerce, 50 M SKUs, real-time faceting, geo-search, analytics dashboards, ML-powered recommendations) → Elasticsearch. No other tool in this list handles all five simultaneously at that scale.

Team B (SaaS startup, 500 K user records, need instant search with typo tolerance, two engineers, ship in a week) → Typesense Cloud or Meilisearch. Zero JVM, single binary, excellent developer UX, done in an afternoon.

Team C (internal knowledge base, 100 K docs, team already on managed PostgreSQL, search is a secondary feature) → PostgreSQL tsvector + pg_trgm. No new infrastructure, no new operational surface, good enough relevance for internal tooling.

This article gives you the exact data to make that call confidently.

Part 1 — Elasticsearch history & architecture

Elasticsearch: what it is and where it came from

Elasticsearch was created by Shay Banon in 2010 as a REST API wrapper around Apache Lucene — the same library that powered Apache Solr (released 2004). Where Solr exposed Lucene through XML configuration files, Elasticsearch made everything JSON over HTTP, added automatic sharding and replication from day one, and introduced a cluster state model that made distributed search feel trivial to deploy.

1
Lucene at the core — Both ES and Solr write Lucene segments on disk. ES adds a distributed coordination layer (master election, shard allocation, cross-cluster replication) on top. Lucene provides inverted indexes, BM25 scoring, and since Lucene 9, HNSW graphs for vector search.
2
REST-first, schema-optional — ES auto-detects field types on first document. You can define explicit mappings for production accuracy, but the defaults work for prototyping. Solr requires schema.xml or the managed schema API.
3
Aggregations engine — ES aggregations (bucket, metric, pipeline) are richer and faster than Solr's faceting. Deep nested aggregations, scripted metrics, and percentile calculations are first-class.
4
Elastic Stack — Kibana (visualization), Logstash (ingest), Beats (lightweight shippers), Fleet (agent management), and the ML/AI capabilities (ELSER, E5, inference API) are all developed by Elastic and tested against the same release cycle.
DB-Engines ranking: As of mid-2025, Elasticsearch consistently ranks #1 in the search engine category on db-engines.com, ahead of Solr. Both are far ahead of OpenSearch, Typesense, and Meilisearch in raw market presence, though the newer tools are growing faster from a smaller base.
Part 2 — Head-to-head comparisons

Elasticsearch vs Apache Solr

Elasticsearch vs OpenSearch

OpenSearch is the most directly API-compatible alternative to Elasticsearch. Amazon Web Services forked Elasticsearch 7.10.2 in January 2021 after Elastic changed the license from Apache 2.0 to the Server Side Public License (SSPL), which AWS argued was not an open-source license. OpenSearch was released as Apache 2.0 and is governed by the OpenSearch project (AWS as primary contributor).

You're on AWS and need Apache 2.0 licensing or deep AWS service integration

Amazon OpenSearch Service is the path-of-least-resistance for AWS-native teams. OpenSearch's Apache 2.0 license also removes any ambiguity for organizations with open-source compliance requirements. If you need the latest Elastic AI features (ELSER v2, BBQ quantization, Inference API with Anthropic/OpenAI), stay on Elasticsearch.

Elasticsearch vs Typesense

Typesense (first commit 2015, written in C++) is purpose-built for instant, typo-tolerant product/document search. It stores the primary index in RAM, requires no JVM, and ships as a single binary. As of v30.x it supports vector/semantic search (HNSW), joins, geo search, and a built-in RAG pipeline.

Its key limitation: aggregation depth. If you need multi-level pipeline aggregations or petabyte-scale, ES wins.

Elasticsearch vs Meilisearch

Meilisearch (2018, written in Rust) targets the sweet spot of excellent developer UX for small-to-medium datasets. It's a single binary with no external dependencies, completes queries in under 50 ms using memory-mapped disk storage and DiskANN-based vector search, and has excellent SDK coverage (10+ languages). As of recent versions it also includes a built-in RAG mode.

Elasticsearch vs Algolia

Algolia (2012) is SaaS-only — there is no self-hosted option. It is written in C++ (same as Typesense, which was created partly as an open-source alternative to it). Algolia's value proposition is unmatched developer UX, sub-10ms search, excellent InstantSearch UI libraries (React, Vue, Angular, iOS, Android), and a global CDN for search infrastructure.

Algolia is the fastest path to production-grade consumer search with beautiful InstantSearch UI components. For startups validating a product, the developer time saved easily justifies the cost. The inflection point where Elasticsearch becomes cheaper depends on query volume and record count — typically at tens of millions of records or millions of searches per month, Elastic self-hosted or Elastic Cloud becomes more economical.

Elasticsearch vs PostgreSQL tsvector

PostgreSQL's full-text search stack — tsvector + tsquery + pg_trgm + GIN indexes — is genuinely capable for moderate search workloads. It adds zero infrastructure overhead for teams already on Postgres, supports BM25-like ranking via ts_rank and ts_rank_cd, and since pgvector (v0.5+) it even supports HNSW vector search on the same data.

Part 4 — Vector/AI Search in Elasticsearch 8.x / 9.x

dense_vector field type: complete reference

Since ES 8.0, dense_vector with "index": true builds an HNSW graph (via Lucene's HNSW implementation) enabling approximate nearest-neighbor (ANN) search. Dimensions up to 4096 are supported.

Element types

element_typeBytes per dimNotes
float4Default. Full precision 32-bit float.
bfloat162ES 9.3+. Half precision; some accuracy loss.
byte1Integer per dimension; manual quantization.
bit1/8dims must be multiples of 8; only l2_norm similarity.

Similarity options

SimilarityScore formulaWhen to use
cosine(1 + cosine(q, v)) / 2Default. Unnormalized embeddings. Most sentence-transformers.
dot_product(1 + dot(q, v)) / 2When vectors are pre-normalized to unit length (slightly faster).
l2_norm1 / (1 + l2_norm(q,v)²)Euclidean distance; image embeddings, coordinate-like spaces.
max_inner_productVaries (handles negative)Asymmetric similarity; product recommendation embeddings.

HNSW index_options

HNSW — Hierarchical Navigable Small World
HNSW builds a multi-layer proximity graph. At query time, it starts at the highest layer (fewest nodes, long-range connections) and greedily descends toward the query vector, becoming more fine-grained at each layer. It trades a small recall penalty for dramatically faster search than exact brute-force — O(log N) per query instead of O(N). Key parameters:

m (default 16) — the number of bidirectional links per node per layer. Higher m = better recall + more memory.
ef_construction (default 100) — candidate list size during graph construction. Higher = better quality graph + slower indexing.

Quantization index types

TypeMemory reductionAccuracy lossConstraint
hnsw1× (none)None (exact float)—
int8_hnsw~4×Very low~25% disk overhead for raw floats retained
int4_hnsw~8×Lowdims must be even; ~12.5% overhead
bbq_hnsw~32×Moderate (mitigated by reranking)dims > 64; ~3.1% overhead; use oversample 3–5×
flat / *_flatSame as aboveExact searchBrute-force; for small or pre-filtered sets
ES 9.x default quantization: In ES 9.0 float vectors default to int8_hnsw. In ES 9.1+ vectors with dims ≥ 384 default to bbq_hnsw. For ES 8.x, hnsw (no quantization) remains the default — you must opt in to quantization explicitly in 8.x.

Hybrid Search: BM25 + kNN

Hybrid search combines keyword relevance (BM25) with vector similarity (kNN). ES supports two patterns: linear score combination using boost weights, and Reciprocal Rank Fusion (RRF) which is the recommended approach as it requires no manual weight tuning.

Pattern A — Linear combination (manual boost weights)

Elasticsearch JSON 
POST /articles/_search
{
  "query": {
    "match": {
      "title": {
        "query": "vector database performance",
        "boost": 0.3
      }
    }
  },
  "knn": {
    "field":          "embedding",
    "query_vector":   [0.042, 0.856, -0.514],
    "k":              10,
    "num_candidates": 50,
    "boost":          0.7
  },
  "size": 10
}
// Final score = 0.3 * bm25_score + 0.7 * knn_score

Pattern B — Reciprocal Rank Fusion (RRF) — recommended

RRF ranks documents by their position in each sub-retriever's result list. Formula: score += 1.0 / (rank_constant + rank). No weight tuning needed — works out-of-the-box for most use cases.

Elasticsearch JSON 
POST /articles/_search
{
  "retriever": {
    "rrf": {
      "retrievers": [
        {
          "standard": {
            "query": {
              "match": {
                "title": "vector database performance"
              }
            }
          }
        },
        {
          "knn": {
            "field":          "embedding",
            "query_vector":   [0.042, 0.856, -0.514],
            "k":              50,
            "num_candidates": 100
          }
        }
      ],
      "rank_window_size": 50,
      "rank_constant":   20
    }
  },
  "size": 10
}

RRF: BM25 + ELSER (three-way fusion)

Elasticsearch JSON 
POST /articles/_search
{
  "retriever": {
    "rrf": {
      "retrievers": [
        {
          "standard": {
            "query": { "match": { "title": "latency optimization techniques" } }
          }
        },
        {
          "standard": {
            "query": {
              "sparse_vector": {
                "field":        "content_embedding",
                "inference_id": "my-elser-endpoint",
                "query":        "How do I reduce server response times?"
              }
            }
          }
        },
        {
          "knn": {
            "field":          "embedding",
            "query_vector":   [0.042, 0.856, -0.514],
            "k":              50,
            "num_candidates": 100
          }
        }
      ],
      "rank_window_size": 50,
      "rank_constant":   20
    }
  }
}
RRF vs linear combination: RRF is preferred because it eliminates the need to tune boost weights, which are score-scale dependent and shift when you change analyzers or embedding models. RRF only cares about ordinal rank, making it robust to these changes. Use linear combination only when you have a well-validated score normalization pipeline.

ELSER — Elastic Learned Sparse Encoder

ELSER is Elastic's own NLP model for sparse vector semantic search. Unlike dense vector models (which map text to a fixed 384/768/1536-dimensional float vector), ELSER produces a weighted bag of vocabulary tokens — essentially a learned expansion of the query/document into semantically related terms. This maps naturally to Lucene's inverted index and produces very competitive semantic relevance without the memory overhead of dense HNSW graphs.

Step 1 — Index mapping with sparse_vector

Elasticsearch JSON 
PUT /articles
{
  "mappings": {
    "_source": {
      "excludes": ["content_embedding"]
    },
    "properties": {
      "content":           { "type": "text" },
      "content_embedding": { "type": "sparse_vector" }
    }
  }
}

Step 2 — Ingest pipeline to generate embeddings at index time

Elasticsearch JSON 
PUT /_ingest/pipeline/elser-ingest
{
  "processors": [
    {
      "inference": {
        "model_id": ".elser_model_2",
        "input_output": [
          {
            "input_field":  "content",
            "output_field": "content_embedding"
          }
        ]
      }
    }
  ]
}

// Index a document through the pipeline
PUT /articles/_doc/1?pipeline=elser-ingest
{
  "content": "HNSW graphs enable approximate nearest-neighbor search in logarithmic time."
}

Step 3 — Query with sparse_vector

Elasticsearch JSON 
POST /articles/_search
{
  "query": {
    "sparse_vector": {
      "field":        "content_embedding",
      "inference_id": "my-elser-endpoint",
      "query":        "How does approximate nearest-neighbor search work?"
    }
  }
}

// Boost with keyword fallback for hybrid semantic+lexical
POST /articles/_search
{
  "query": {
    "bool": {
      "should": [
        {
          "sparse_vector": {
            "field":        "content_embedding",
            "inference_id": "my-elser-endpoint",
            "query":        "How does approximate nearest-neighbor search work?",
            "boost":        1
          }
        },
        {
          "match": {
            "content": {
              "query": "approximate nearest-neighbor",
              "boost": 0.3
            }
          }
        }
      ],
      "minimum_should_match": 1
    }
  },
  "min_score": 10
}
ELSER token limit: ELSER only processes the first 512 extracted tokens per field. For long documents, chunk first (e.g., paragraphs of 256–400 tokens), store chunks in a nested field or as separate documents, then use nested kNN or multi-result aggregation.

Inference API — connecting external models

The Elasticsearch Inference API (/_inference) lets you route text through external model providers at both index time (via ingest pipeline) and query time (via query_vector_builder or sparse_vector). This eliminates the need to generate embeddings outside Elasticsearch and then insert them.

Elasticsearch JSON 
// Create an inference endpoint for OpenAI text-embedding-3-small

JavaScript Example

Node.js: full semantic search pipeline with Elasticsearch client

JavaScript Example 
import { Client } from "@elastic/elasticsearch";
import { pipeline } from "@xenova/transformers";

const es = new Client({ node: "http://localhost:9200" });
const INDEX = "knowledge-articles";

// ── 1. Create index with int8_hnsw quantized dense vector ──────────────────
async function createIndex() {
  await es.indices.create({
    index: INDEX,
    mappings: {
      properties: {
        title:     { type: "text" },
        body:      { type: "text" },
        category:  { type: "keyword" },
        embedding: {
          type:       "dense_vector",
          dims:       384,
          index:      true,
          similarity: "cosine",
          index_options: {
            type:            "int8_hnsw",
            m:               16,
            ef_construction: 100,
          },
        },
      },
    },
  });
  console.log(`Index "${INDEX}" created.`);
}

// ── 2. Generate embedding using all-MiniLM-L6-v2 (384 dims) ───────────────
async function embed(text) {
  const extractor = await pipeline(
    "feature-extraction",
    "Xenova/all-MiniLM-L6-v2"
  );
  const output = await extractor(text, { pooling: "mean", normalize: true });
  return Array.from(output.data); // Float32Array → plain array
}

// ── 3. Index documents ─────────────────────────────────────────────────────
async function indexDocuments(docs) {
  const operations = await Promise.all(
    docs.map(async (doc) => [
      { index: { _index: INDEX } },
      { ...doc, embedding: await embed(`${doc.title} ${doc.body}`) },
    ])
  );

  const { errors } = await es.bulk({
    operations: operations.flat(),
    refresh: true,
  });

  if (errors) throw new Error("Bulk indexing errors detected");
  console.log(`Indexed ${docs.length} documents.`);
}

// ── 4. kNN semantic search ─────────────────────────────────────────────────
async function semanticSearch(queryText, k = 5) {
  const queryVector = await embed(queryText);

  const { hits } = await es.search({
    index: INDEX,
    knn: {
      field:          "embedding",
      query_vector:   queryVector,
      k,
      num_candidates: k * 10,
    },
    fields: ["title", "category"],
    _source: false,
  });

  return hits.hits.map((h) => ({
    score: h._score,
    title: h.fields.title?.[0],
    category: h.fields.category?.[0],
  }));
}

// ── 5. Hybrid search: BM25 + kNN via Reciprocal Rank Fusion ───────────────
async function hybridSearch(queryText, size = 5) {
  const queryVector = await embed(queryText);

  const { hits } = await es.search({
    index: INDEX,
    retriever: {
      rrf: {
        retrievers: [
          {
            standard: {
              query: {
                multi_match: {
                  query:  queryText,
                  fields: ["title^2", "body"],
                },
              },
            },
          },
          {
            knn: {
              field:          "embedding",
              query_vector:   queryVector,
              k:              50,
              num_candidates: 100,
            },
          },
        ],
        rank_window_size: 50,
        rank_constant:    20,
      },
    },
    size,
    fields: ["title", "category"],
    _source: false,
  });

  return hits.hits.map((h) => ({
    score:    h._score,
    title:    h.fields.title?.[0],
    category: h.fields.category?.[0],
  }));
}

// ── 6. ELSER sparse vector search ─────────────────────────────────────────
async function elserSearch(queryText, size = 5) {
  const { hits } = await es.search({
    index: INDEX,
    query: {
      sparse_vector: {
        field:        "content_embedding",
        inference_id: "my-elser-endpoint",
        query:        queryText,
      },
    },
    size,
    min_score: 5,
  });

  return hits.hits.map((h) => ({ score: h._score, id: h._id }));
}

// ── 7. Demo run ────────────────────────────────────────────────────────────
const docs = [
  { title: "HNSW Explained",   body: "Hierarchical Navigable Small World graphs enable ANN search.", category: "ml" },
  { title: "BM25 vs TF-IDF",   body: "BM25 adds term frequency saturation and document length normalisation.", category: "search" },
  { title: "Vector Databases", body: "Pinecone, Weaviate, Qdrant, and Elasticsearch for vector storage.", category: "databases" },
];

await createIndex();
await indexDocuments(docs);

const results = await hybridSearch("approximate nearest neighbor algorithms");
console.log("Hybrid search results:", results);
Practical checklist

Production vector search checklist

1
Choose the right similarity metric up front — cosine for most sentence-transformers (outputs are not unit-normalized by default), dot_product only if you explicitly L2-normalize before indexing, l2_norm for coordinate or image embeddings. Changing similarity requires reindexing.
2
Pick quantization for your scale — Start with int8_hnsw (4× memory savings, negligible accuracy loss). Use bbq_hnsw with rescore_vector.oversample: 4.0 at very large scale (> 100 M vectors). Avoid unquantized hnsw for float vectors in production unless you've measured that int8 accuracy is insufficient.
3
Set num_candidates = k × 10 as a baseline — Recall improves as num_candidates increases relative to k. For most production workloads, num_candidates = 5×–10× k is a reasonable starting point. Benchmark recall@k to tune further.
4
Use RRF for hybrid search, not manual boosts — RRF is score-scale-agnostic and requires no re-tuning when you change analyzers or embedding models. Reserve linear combination only for cases where you have robust score normalization.
5
Chunk long documents for ELSER — ELSER processes only the first 512 tokens. For documents longer than ~400 words, chunk at paragraph boundaries and store chunks as nested objects or separate documents.
6
Use the Inference API for model management — Configuring inference endpoints in ES (not in your application code) makes embedding model changes a single PUT request and eliminates embedding generation latency from your application layer.
7
Filters should be pre-filters, not post-filters — Pass filter inside the knn block. ES applies the filter during HNSW traversal, guaranteeing exactly k results. A post-filter (boolean query wrapping knn) can return fewer than k results.
FAQ

Frequently asked questions

What is the difference between kNN search and semantic search?

kNN search is the algorithm: find the k nearest vectors in a dense vector space using HNSW. Semantic search is the application: represent text as dense embeddings using a language model (e.g., all-MiniLM-L6-v2), then use kNN to find semantically similar documents. Semantic search requires kNN, but kNN can be used for any dense vector (images, audio, user behavior) — not just semantic text search.

Can I upgrade from hnsw to bbq_hnsw without reindexing?

Yes. You can upgrade index_options along the progression: flat → int8_flat → int4_flat → bbq_flat → hnsw → int8_hnsw → int4_hnsw → bbq_hnsw using the Update Mapping API. You cannot downgrade. The upgrade triggers a background segment merge to apply quantization.

When should I use ELSER vs a dense embedding model?

ELSER (sparse) is better for domain-general keyword-centric searches where precision matters and you can't afford the memory overhead of a 1536-dim dense model. It also works well in hybrid with BM25 via RRF. Dense models (e.g., all-MiniLM-L6-v2, OpenAI text-embedding-3-small) are better when semantic intent is the primary signal, especially for question-answering or RAG pipelines. At large scale, dense + bbq_hnsw can be more memory-efficient than ELSER's sparse inverted index if vectors are highly compressed.

Does OpenSearch support the same kNN syntax as Elasticsearch?

No. OpenSearch uses its own k-NN plugin with different syntax: "knn": true in the index mapping and a knn query type with vector and k fields. It supports multiple algorithms (HNSW via Lucene, FAISS, NMSLIB) but the configuration and query syntax differ significantly from ES 8.x. Migration between ES 8.x and OpenSearch 2.x vector search requires query rewriting.

What's the maximum vector dimension in Elasticsearch?

4096 dimensions for float/bfloat16/byte element types. For bit vectors, dimensions must be a multiple of 8 with no stated ceiling beyond the 4096 cap. Most production embedding models fit well within this limit: all-MiniLM-L6-v2 is 384 dims, OpenAI text-embedding-3-small is 1536 dims, text-embedding-3-large is 3072 dims.

Key Takeaway

Elasticsearch is the most complete search and AI-search platform in open source — but "most complete" means most complex. The right call is to match tool to workload: use Typesense or Meilisearch when simplicity and developer speed matter more than scale, use OpenSearch when Apache 2.0 licensing or AWS-native integration is non-negotiable, use Algolia when you need consumer-grade UX delivered yesterday, and use PostgreSQL tsvector when search is secondary and your data is already in Postgres. When you do choose Elasticsearch, the modern vector search stack — int8_hnsw or bbq_hnsw mappings, kNN queries with rescore_vector, and RRF-based hybrid retrieval — closes the gap with purpose-built vector databases while keeping all your analytics, aggregations, and operational tooling in one cluster.
