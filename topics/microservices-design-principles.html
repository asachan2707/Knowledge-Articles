Microservices Design Principles & Patterns

Seven foundational design principles — high cohesion, single responsibility, decentralised data, design for failure — paired with eight patterns (Event Sourcing, CQRS, BFF, API Gateway, Strangler, Circuit Breaker, Externalized Configuration) and the considerations teams skip that cause production failures.

Microservices fail in production not because of bad technology choices but because of violated principles. A service that owns too much (low cohesion), shares a database with five others (centralised data), or has no failure isolation strategy will eventually bring down a system that looks architecturally correct on paper.

Core idea: The seven principles below are not guidelines — they are constraints. Violating any one of them creates technical debt that compounds exponentially with the number of services.

The 7 principles

Design principles that prevent production failures

1

High Cohesion / Low Coupling

Related logic lives together (high cohesion); services have minimal dependencies on each other (low coupling). A service that calls 10 others synchronously for every request has low cohesion and high coupling — both problems.

2

Define Scope Properly

Boundaries must align with independent business modules — not technical layers. "All database access" is not a good service boundary. "Everything related to order lifecycle" is.

3

Single Responsibility Principle

A service should have exactly one reason to change. If adding a new payment provider requires also changing the notification service, the boundary is wrong.

4

Design for Failure

Assume every downstream call can fail. Every service must have a defined fallback: cached data, a degraded response, or a graceful error — not a 500 that cascades upward.

5

Build Around Business Capabilities

Each service solves a distinct business problem and can choose its own technology stack. The ordering service can use PostgreSQL while the recommendation service uses a graph DB.

6

Decentralise Data

Every microservice owns its own database. No shared data stores. Cross-service data access happens only through APIs, not direct DB queries. This is the hardest principle to maintain under time pressure and the most important not to violate.

7

Manage Traffic

Use autoscaling and circuit breakers. A service that cannot shed load gracefully under traffic spikes will take down everything that depends on it.

JavaScript Example

Externalized config + Strangler façade pattern

JavaScript Example 
// Externalized Configuration — config loaded from environment / config service
// Never hardcode credentials or service URLs in application code
class ConfigService {
  constructor() {
    this._cache = new Map();
  }

  get(key) {
    if (this._cache.has(key)) return this._cache.get(key);
    const value = process.env[key];
    if (!value) throw new Error(`Missing required config: ${key}`);
    this._cache.set(key, value);
    return value;
  }

  // Refresh from a remote config store (Consul, AWS Parameter Store, etc.)
  async refresh(configStoreUrl) {
    const res = await fetch(`${configStoreUrl}/config`);
    const fresh = await res.json();
    for (const [k, v] of Object.entries(fresh)) {
      this._cache.set(k, v);
    }
  }
}

const config = new ConfigService();

// Strangler Fig Façade — routes to legacy or new service per feature flag
class OrderFacade {
  constructor(legacyOrderSystem, newOrderService, config) {
    this.legacy = legacyOrderSystem;
    this.newSvc = newOrderService;
    this.config = config;
  }

  async createOrder(data) {
    const useNew = this.config.get('FEATURE_NEW_ORDER_SERVICE') === 'true';
    if (useNew) {
      return this.newSvc.create(data);
    }
    return this.legacy.createOrder(data); // still on monolith
  }

  async getOrder(orderId) {
    // Read from whichever system owns this orderId
    const newOrder = await this.newSvc.findById(orderId).catch(() => null);
    if (newOrder) return newOrder;
    return this.legacy.getOrder(orderId); // fallback to legacy
  }
}

// Usage: swap the flag in config, no code change needed
// FEATURE_NEW_ORDER_SERVICE=true → routes to new microservice
// FEATURE_NEW_ORDER_SERVICE=false → routes to legacy monolith
Pre-adoption checklist: Before adopting microservices, verify your team can handle: inter-service communication design, distributed data consistency, security across boundaries, automated testing at unit/integration/contract/component levels, and centralised monitoring. Missing any one of these will make microservices slower than the monolith they replaced.

Key Takeaway

The seven design principles are non-negotiable constraints, not optional guidelines. High cohesion, low coupling, single responsibility, design for failure, capability-aligned boundaries, decentralised data, and traffic management — violate any of them and the complexity cost of microservices exceeds the benefit. The eight patterns implement these principles in code. Learn the principle first, then the pattern becomes obvious.
