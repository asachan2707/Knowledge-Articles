Kubernetes for Application Developers — From Pods to Production

Kubernetes from an app developer's perspective: pods, deployments, services, ingress, and config patterns you use every sprint — not the cluster-admin internals. Covers resource limits, health probes, HPA, rolling updates, RBAC, Helm, and how to translate a docker-compose file into production-ready Kubernetes manifests, with full kubectl examples throughout.

Source: Kubernetes Docs · Kelsey Hightower · Brendan Burns Domain: DevOps / Cloud Published: 2026

Kubernetes is often taught from the cluster-operator perspective — networking plugins, etcd quorum, node taints. But most developers interact with Kubernetes at a much higher layer: writing manifests, debugging failing pods, wiring up services, and configuring autoscaling. This guide covers the Kubernetes primitives a backend or full-stack developer actually uses every sprint, with enough depth to understand why things work the way they do.

Core idea: Kubernetes is a desired-state reconciliation engine. You declare what you want (a Deployment with 3 replicas, a Service pointing to them) and Kubernetes continuously works to make reality match the declaration. Understanding this model explains almost every behaviour that otherwise looks magical or frustrating.

Story · The 3 AM OOMKilled pod

A developer deploys a Node.js service. It works perfectly during load testing. On the first real traffic spike in production, pods start crashing with status OOMKilled. The developer had never set resources.limits.memory. Without limits, Kubernetes has no signal to schedule the pod on a node with available memory — it just places it anywhere, and the pod expands until the node's kernel kills it.

Setting resources.requests (what Kubernetes uses for scheduling) and resources.limits (the hard ceiling) is one of those things that feels optional in development and becomes mandatory the first time you hit production. This guide covers it — and the dozen other non-obvious settings that make the difference between a fragile deployment and a resilient one.

Core Primitives

Pods, Deployments, and StatefulSets

Pod

The smallest deployable unit in Kubernetes. A Pod contains one or more containers that share a network namespace (same IP, same localhost) and can share volumes. You almost never create Pods directly — you create Deployments or StatefulSets that manage Pods for you. Direct Pod creation is used for one-off debug sessions (kubectl run -it --rm debug --image=busybox -- sh) and nothing else.

Deployment

A Deployment manages a ReplicaSet which manages Pods. It handles rolling updates, rollbacks, and scaling. The Deployment's spec.template is the Pod spec that all replicas are created from. When you change the image or environment variables in the template, Kubernetes rolls out new Pods and terminates old ones according to the strategy settings.

Key Deployment settings to understand:

  • replicas — desired number of Pod copies. Set to at least 2 in production for zero-downtime deploys.
  • strategy.type: RollingUpdate — the default; replaces old pods gradually. maxUnavailable: 0 + maxSurge: 1 ensures zero downtime.
  • strategy.type: Recreate — kills all old pods before starting new ones. Use for stateful apps that can't run two versions simultaneously.
  • revisionHistoryLimit — how many old ReplicaSets to keep for rollback. Default is 10; reduce to 3 to save etcd storage.

StatefulSet

Like a Deployment but for stateful apps (databases, queues). Pods get stable, ordered names (mysql-0, mysql-1), stable DNS hostnames, and stable PersistentVolumeClaims. Pods are created and deleted in order (0 first, 0 last). Use StatefulSets for anything that needs stable network identity or persistent storage tied to a specific pod.

Networking

Services, Ingress, and DNS

Service types

A Service is a stable network endpoint in front of a set of Pods. Pods have ephemeral IPs that change on restart; Services provide a stable virtual IP (ClusterIP) and DNS name.

  • ClusterIP (default) — internal-only IP, reachable only within the cluster. Use for pod-to-pod communication. DNS name: service-name.namespace.svc.cluster.local. In the same namespace, just service-name resolves.
  • NodePort — exposes the service on a port on every node's IP. Useful for quick access from outside the cluster during development. Not recommended for production (uses a high port number, bypasses load balancer).
  • LoadBalancer — provisions an external load balancer in the cloud (AWS ELB, GCP CLB). Each LoadBalancer service creates one external IP. Expensive at scale — prefer a single Ingress controller with multiple path rules instead.
  • ExternalName — maps a service name to an external DNS name. Useful for referencing external databases or APIs from within the cluster without hardcoding external hostnames in your app config.

Ingress

Ingress is an API object that defines HTTP/HTTPS routing rules. An Ingress controller (nginx-ingress, Traefik, AWS ALB Ingress Controller) watches Ingress objects and configures an external load balancer accordingly. One load balancer, many services — the correct pattern for production.

Ingress supports host-based routing (api.example.com → service A, app.example.com → service B) and path-based routing (/api/v1/* → backend service, /* → frontend service). TLS termination is configured on the Ingress with a secretName pointing to a TLS certificate stored as a Kubernetes Secret.

Configuration

ConfigMaps, Secrets, and Environment Variables

ConfigMap

Stores non-sensitive configuration as key-value pairs. Mount as environment variables or as files in a volume. Keep ConfigMaps small and specific — one per service, not a global config blob. When a ConfigMap changes, Pods must be restarted to pick up the new values (unless using a volume mount, which auto-updates but can cause config drift mid-run).

Secret

Stores sensitive data (passwords, API keys, TLS certs). Values are base64-encoded in etcd (not encrypted by default — enable Encryption at Rest in your cluster config for true security). Mount as environment variables or volume files. In production, use an external secrets operator (External Secrets Operator with AWS Secrets Manager/Vault) to sync secrets from a dedicated secrets store rather than storing raw values in the cluster.

Environment variables vs volume mounts

Environment variables are convenient but have a downside: the container process sees them at startup only — a ConfigMap update requires a Pod restart. Volume mounts are updated automatically by kubelet (typically within 60 seconds) but the process must re-read the file. For most 12-factor apps that read config at startup, environment variables are simpler. For configurations that need hot-reloading (feature flags, TLS cert rotation), use volume mounts.

Reliability

Health Probes, Resource Limits, and HPA

Liveness, Readiness, and Startup probes

Kubernetes uses three probe types to manage Pod lifecycle:

  • Liveness probe — "is the container still alive?" If it fails, Kubernetes kills and restarts the container. Use for detecting deadlocks or hung processes. Keep the liveness check very simple — an HTTP 200 from a /healthz endpoint that returns immediately. Never make the liveness probe depend on a database connection — a DB outage should not restart your app pods.
  • Readiness probe — "is the container ready to receive traffic?" If it fails, the Pod is removed from the Service's endpoint list (traffic stops flowing to it) but the container is not restarted. Use this to prevent traffic during startup warmup and to gracefully handle temporary dependency failures. The readiness probe can check external dependencies.
  • Startup probe — "is the container still initialising?" Replaces liveness during slow startup. If the startup probe hasn't succeeded within failureThreshold × periodSeconds, the container is killed. Use this for apps with long initialisation times (JVM warmup, large model loading) so the liveness probe isn't killing them before they're ready.

Resource requests and limits

resources.requests is what Kubernetes uses for scheduling — the scheduler only places a Pod on a node that has at least that much free capacity. resources.limits is the hard ceiling — the container is throttled (CPU) or killed (memory) if it exceeds this value.

Best practice: set requests to the typical workload level and limits to the maximum you can tolerate. For CPU, a request of 100m (0.1 core) with a limit of 500m is common for a lightweight Node.js service. For memory, requests and limits are often set equal to prevent eviction under memory pressure.

Horizontal Pod Autoscaler (HPA)

HPA watches a metric (CPU utilisation, memory, or custom metrics via Prometheus Adapter) and scales the Deployment's replica count up or down to maintain a target value. Example: targetCPUUtilizationPercentage: 70 scales out when average CPU across all pods exceeds 70% of the CPU request. HPA requires resources.requests to be set — it calculates utilisation as current usage / request.

JavaScript Example

Complete Deployment Manifest and kubectl Cheat Sheet

JavaScript Example 
// Generate Kubernetes manifest programmatically (useful for templating)
// In practice you'd write YAML directly; this shows the structure as JS objects

const deployment = {
  apiVersion: 'apps/v1',
  kind: 'Deployment',
  metadata: { name: 'api-server', namespace: 'production' },
  spec: {
    replicas: 3,
    revisionHistoryLimit: 3,
    selector: { matchLabels: { app: 'api-server' } },
    strategy: {
      type: 'RollingUpdate',
      rollingUpdate: { maxUnavailable: 0, maxSurge: 1 },
    },
    template: {
      metadata: { labels: { app: 'api-server' } },
      spec: {
        containers: [{
          name: 'api',
          image: 'myregistry/api-server:v1.2.3',  // always pin to a tag, never :latest
          ports: [{ containerPort: 3000 }],
          env: [
            { name: 'NODE_ENV', value: 'production' },
            { name: 'DB_URL', valueFrom: { secretKeyRef: { name: 'api-secrets', key: 'db-url' } } },
          ],
          resources: {
            requests: { cpu: '100m', memory: '128Mi' },
            limits:   { cpu: '500m', memory: '512Mi' },
          },
          livenessProbe: {
            httpGet: { path: '/healthz', port: 3000 },
            initialDelaySeconds: 10,
            periodSeconds: 10,
            failureThreshold: 3,
          },
          readinessProbe: {
            httpGet: { path: '/ready', port: 3000 },
            initialDelaySeconds: 5,
            periodSeconds: 5,
            failureThreshold: 3,
          },
        }],
      },
    },
  },
};

// kubectl cheat sheet (shell commands)
const kubectlCheatSheet = `
# Apply a manifest
kubectl apply -f deployment.yaml

# Check rollout status
kubectl rollout status deployment/api-server -n production

# Roll back to previous version
kubectl rollout undo deployment/api-server -n production

# Scale manually (override HPA temporarily)
kubectl scale deployment/api-server --replicas=5 -n production

# Get pod logs (last 100 lines, follow)
kubectl logs -l app=api-server -n production --tail=100 -f

# Exec into a running pod
kubectl exec -it deploy/api-server -n production -- sh

# Describe a pod (events, resource usage)
kubectl describe pod <pod-name> -n production

# Get events sorted by time
kubectl get events --sort-by=.metadata.creationTimestamp -n production

# Port-forward to a pod for local debugging
kubectl port-forward deploy/api-server 3000:3000 -n production

# Check HPA status
kubectl get hpa -n production

# View current resource usage
kubectl top pods -n production
kubectl top nodes
`;

console.log('Deployment manifest:', JSON.stringify(deployment, null, 2));
console.log(kubectlCheatSheet);
Advanced Topics

RBAC, PersistentVolumes, and Namespaces

Namespaces

Namespaces are virtual clusters within a cluster. Use them to separate environments (staging, production) or teams. Resources in different namespaces can communicate via their full DNS names (service-name.namespace.svc.cluster.local). NetworkPolicies can enforce namespace isolation. Do not use the default namespace for production workloads — create named namespaces.

RBAC basics

Role-Based Access Control governs who can do what in the cluster. A Role (namespace-scoped) or ClusterRole (cluster-wide) defines a set of permissions (verbs like get, list, create on resources like pods, secrets). A RoleBinding grants a Role to a ServiceAccount, user, or group.

As an application developer, your main RBAC concern is the Pod's ServiceAccount. By default pods use the default ServiceAccount in their namespace. If your pod needs to call the Kubernetes API (e.g., to discover other services or manage CRDs), create a dedicated ServiceAccount with the minimum required permissions — don't use cluster-admin.

PersistentVolumes and PersistentVolumeClaims

A PersistentVolume (PV) is a piece of storage provisioned in the cluster (cloud disk, NFS mount). A PersistentVolumeClaim (PVC) is a request for storage by a Pod — it specifies size, access mode (ReadWriteOnce for a single pod, ReadWriteMany for shared), and StorageClass. In cloud environments, PVCs are typically satisfied dynamically by a StorageClass that provisions cloud disks on demand.

Most application developers only interact with PVCs (not PVs directly). For StatefulSets, use volumeClaimTemplates — each pod replica gets its own PVC automatically.

Helm & Local Dev

Helm Charts, Minikube, and docker-compose to Kubernetes

Helm charts

Helm is the package manager for Kubernetes. A chart is a collection of YAML templates with configurable values. helm install my-release ./chart --values prod.yaml renders the templates with the given values and applies them. Charts can be versioned, shared, and parameterised — a chart for a microservice typically exposes values for image tag, replica count, resource limits, and ingress hostname, keeping the base manifests DRY across environments.

Use Helm for anything you need to deploy to multiple environments with different configurations. Use helm diff (plugin) to preview changes before applying. For simple single-environment setups, plain kubectl apply -f with Kustomize overlays is a lighter alternative.

Local development with minikube and kind

minikube runs a single-node Kubernetes cluster in a VM or container on your machine. Includes addons for ingress, metrics-server, and dashboard. minikube image load myimage:tag pushes a local Docker image into the cluster without a registry.

kind (Kubernetes IN Docker) creates multi-node clusters as Docker containers — faster to start than minikube and easier to script for CI. Load images with kind load docker-image myimage:tag.

Translating docker-compose to Kubernetes

The mental model:

  • service in compose → Deployment + Service in Kubernetes.
  • environment variables → ConfigMap (non-sensitive) or Secret (sensitive) mounted as env vars.
  • volumes → PersistentVolumeClaim (or emptyDir for ephemeral scratch space).
  • ports → containerPort in the Pod spec; exposed via a Service or Ingress.
  • depends_on → readiness probes + retry logic in the app. Kubernetes doesn't have a built-in ordering primitive — design your app to retry on startup.
  • networks → Kubernetes networking is flat within a cluster. Use NetworkPolicies to restrict communication between namespaces or pods.

Use kompose convert to auto-generate Kubernetes manifests from a docker-compose.yml as a starting point, then review and refine the output — the generated manifests rarely set resource limits, health probes, or proper secret management out of the box.

The most common migration mistake: Copying docker-compose health checks (test: ["CMD", "curl", "-f", "http://localhost:3000/health"]) directly into Kubernetes liveness probes without understanding the restart semantics. A failing liveness probe kills the pod — ensure your liveness check is truly "is the process alive?" and not "is the database reachable?".

Practical Checklist

Kubernetes Application Readiness — What to Nail

  • Always set resources.requests and resources.limits — without them, the scheduler is flying blind and your pods will be OOMKilled.
  • Never use :latest tag in production manifests — pin to a specific image digest or version tag for reproducible deployments.
  • Separate liveness and readiness probes: liveness = "is the process alive", readiness = "is it ready to serve traffic". Never check external dependencies in a liveness probe.
  • Set strategy.rollingUpdate.maxUnavailable: 0 for zero-downtime deploys. Ensure at least 2 replicas.
  • Use namespaces to separate production from staging. Never put production workloads in default.
  • Store secrets in a dedicated secrets manager (Vault, AWS Secrets Manager) and sync to Kubernetes Secrets using External Secrets Operator — don't store raw secret values in YAML committed to git.
  • Add a PodDisruptionBudget to prevent all replicas of a critical service from being evicted simultaneously during node maintenance.
  • Configure HPA with custom metrics (RPS, queue depth) rather than just CPU — CPU is a lagging indicator for many workload types.
  • Use kubectl rollout undo to roll back — don't re-apply an old manifest, which bypasses revision tracking.
  • Run kubectl top pods and kubectl top nodes weekly to check resource utilisation and right-size your requests/limits.

Key Takeaway

Kubernetes is not a deployment destination — it's a control plane that continuously reconciles your desired state with reality. As an application developer, the highest-leverage Kubernetes skills are: writing correct resource limits and health probes (they prevent the majority of production incidents), understanding Services and Ingress routing (they determine how your users reach your code), and using Deployments with rolling update strategies (they enable zero-downtime deploys). Helm handles the repetition across environments. Everything else — RBAC, PVs, network policies — you'll learn as you need it. Start with the primitives, write manifests by hand before reaching for Helm, and always use kubectl describe pod as your first debugging tool.
