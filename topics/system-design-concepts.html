One structured path through system design: 33 building-block concepts (load balancing, consistent hashing, CAP, OAuth 2.0, WebSockets, observability and more) interleaved with 28 case-study chapters from rate limiter to stock exchange and 9 reading guides on the papers behind them. Learn each concept, then see it assembled into a real design.

System design mastery is not about memorising every technology. It is about internalising the patterns that appear again and again: a hash ring, a log, a cache, a queue, an idempotency key, an index shaped to the query. Interview prompts change, but these building blocks do not. This guide teaches the concepts first, then walks the classic designs in dependency order, so by the time you reach a payment system or a stock exchange you have already met every primitive it is made from.

How to use this guide: work through the eight stages in order. In each stage read the concept deep dives first, then the case-study chapters that apply them, then (optionally) the reading guides, which compare a chapter's design with the original paper or engineering post. Mark concepts read as you go; your progress is saved locally, and chapters you have read elsewhere in the hub show a tick.

Stage 1 of 8

Foundations & Method

How systems grow, how to size them, and how to run the interview. Start with the growth map and the interview loop, then learn the stateless, cached, load-balanced tier that every later design assumes.

Concepts to learn 5

Concept 01

Statelessness

Keeping services free of session state so any instance can handle any request. Externalising state to Redis or databases, sticky sessions as an anti-pattern, and why statelessness is the prerequisite for horizontal scaling.

Architecture
Concept 02

Load Balancing

Distributes incoming traffic across multiple servers so no single node is overwhelmed. The foundation of every horizontally scalable system.

Distributed Systems
Concept 03

Caching

Stores frequently accessed data in fast memory to reduce database load and response latency. One of the highest-leverage performance tools available.

Performance
Concept 04

Content Delivery Network (CDN)

Distributes static assets across geographically distributed edge servers so users download from the nearest location, cutting latency globally.

Infrastructure
Concept 05

Auto Scaling

Automatically adds or removes compute resources based on defined metrics, matching capacity to actual demand in real time to balance cost and availability.

Stage 2 of 8

Distributed Data

Partitioning, replication, consistency and the databases built on them. Concepts first (database choice, sharding, consistent hashing, CAP, consistency models, concurrency control), then the Dynamo-style store, ID generation and URL shortener that put them together.

Concepts to learn 6

Concept 06

Database Selection

Relational, document, wide-column, graph, time-series, and search engines — what each optimises for, which workloads break them, and the decision framework architects use to pick the right database for each job.

Data Architecture
Concept 07

Sharding

Splits a large dataset horizontally across multiple database nodes using a shard key. Enables scale far beyond what a single machine can hold.

Data Architecture
Concept 08

Consistent Hashing

Distributes data across nodes so that only a minimal fraction of keys must be remapped when a node joins or leaves. Powers distributed caches and storage rings.

Distributed Systems
Concept 09

CAP Theorem

You can have only two of three: Consistency, Availability, and Partition Tolerance. Why every distributed database makes this choice, how CP and AP systems behave during network splits, and the PACELC extension.

Distributed Systems
Concept 10

Consistency Models

Strong, eventual, causal, and read-your-writes consistency — what each guarantees, which systems offer them, and how CAP theorem forces trade-offs between consistency and availability in distributed databases.

Distributed Systems
Concept 11

Concurrency Control

Optimistic locking (version fields, compare-and-swap), pessimistic locking (SELECT FOR UPDATE), and MVCC — the mechanisms that prevent lost updates when multiple clients write the same record simultaneously.

Stage 3 of 8

Traffic Control & Resilience

Protecting services from overload, slow dependencies and unsafe retries. Timeouts, retries, idempotency, circuit breakers, then rate limiting and throttling form one safety system, learned in the order a failing call meets them; the rate limiter chapter assembles it.

Concepts to learn 6

Concept 12

Timeouts

Connection, read, and deadline timeouts prevent slow or hung downstream services from blocking your threads forever. Setting them correctly is one of the most impactful reliability decisions in any service.

Resilience
Concept 13

Retry Strategies

How to safely retry failed operations — immediate, fixed, exponential backoff with jitter, and deadline-aware retries. The difference between making a system resilient and making it a DDoS against your own downstream.

Resilience
Concept 14

Idempotency

Designing operations so that executing them multiple times produces the same result as once. The key to safe retries and reliable distributed systems.

API Design
Concept 15

Circuit Breaker

Monitors downstream service calls and automatically stops attempts when failure rate exceeds a threshold, preventing cascading failures across the system.

Resilience
Concept 16

Rate Limiting

Controls how many requests a client can make in a time window, protecting services from overload, abuse, and the noisy-neighbour problem.

API Design
Concept 17

Throttling

Slowing down rather than rejecting requests — the leaky bucket algorithm, queue-based throttling, and the difference between rate limiting (stop) and throttling (slow). How it protects downstream services under gradual overload.

APIs, Security & Integration

The contract between services and clients: shape, safety, evolution. Start with the style (REST vs GraphQL), then the contract (schemas, pagination, bulk calls, errors, versioning), the edge (gateway, discovery, authentication, OAuth 2.0) and finally push-style APIs (event-driven APIs, webhooks). Async Messaging, Real-Time & Product Systems

Queues, fan-out, long-lived connections, then the classic consumer-scale designs. Message queues, pub/sub and WebSockets are the primitives; crawl, notify, feed, chat, search, video and sync show them in production.

Concept 30

Message Queue

Decouples producers from consumers — producers enqueue messages, consumers process them asynchronously at their own pace. Enables reliable async workflows.

Async Architecture

Publish-Subscribe

Multiple consumers each receive a copy of every message published to a topic. Powers real-time fan-out, notifications, and event-driven architectures.

Key Takeaway

These 33 concepts are the shared vocabulary of modern software architecture, and every design in the handbook reduces to the same three questions: what is the access pattern, what must be strictly correct versus eventually correct, and what breaks first at 10x. Every system design interview, architecture review and scaling post-mortem is a story about one or more of these patterns applied well or ignored. Learn the mechanics behind each one: not just the name, but the how, the why it breaks, and when to reach for it.
