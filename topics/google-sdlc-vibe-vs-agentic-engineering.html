Google's SDLC Guide: Drawing a Hard Line Between Vibe Coding and Agentic Engineering

Google's updated SDLC guidelines distinguish two fundamentally different modes of AI-assisted development. Vibe coding produces output quickly but transfers ownership and understanding to the AI. Agentic engineering uses AI as a force multiplier while the engineer retains architectural ownership, review discipline, and accountability.

The Core Distinction

The distinction is not about how much AI is used — it is about who retains understanding and accountability for what gets produced.

Vibe Coding

  • Prompt → accept → ship
  • Speed is the primary metric
  • Engineer often can't explain the code
  • Testing is "does it run"
  • Debugging is "ask the AI to fix it"
  • Knowledge lives in the AI session
  • Architecture emerges from prompts

Agentic Engineering

  • Spec → AI implements → engineer reviews
  • Correctness is the primary metric
  • Engineer can explain every decision
  • Testing is a defined process with coverage
  • Debugging means understanding root cause
  • Knowledge lives in the engineer's head
  • Architecture is designed, not generated

Google's SDLC Principles for AI-Assisted Development

1. Specification Before Generation

Write a spec (in code, comments, or a design doc) before prompting the AI to implement. The spec is the engineer's artifact — it defines what the AI should produce and gives the reviewer a standard to check against.

2. Review Like You Wrote It

AI-generated code gets the same review rigor as human-written code. The bar is not "does it look plausible" but "would I stake my name on this in production." If you can't fully review a diff, the diff is too large.

3. Security Posture Is Non-Negotiable

AI models have no memory of your security requirements across sessions. Every generated diff must be checked against: injection (SQL, command, path traversal), authentication/authorization, secret handling, and dependency supply chain. Automated scanning is a floor, not a ceiling.

4. Test Coverage Is the Engineer's Responsibility

AI can write tests, but the engineer defines what gets tested. Generated tests tend to test the implementation (what the code does) rather than behavior (what it should do). The test spec is written by humans; AI writes the test code to match it.

5. Architectural Decisions Are Not Delegated to AI

Choice of data store, service topology, API shape, consistency model — these are engineering decisions made by engineers, not AI outputs accepted without scrutiny. AI assists with implementation; humans own the design.

6. Accountability Cannot Be Transferred

"The AI generated it" is not a valid explanation for a production incident. The engineer who merged the code is accountable. This changes how you use AI: you use it to accelerate work you understand, not to produce work you don't.

Specification-First Development Pattern

/**
 * SPECIFICATION (written by engineer before AI generates any code)
 *
 * Module: UserAuthentication
 *
 * Requirements:
 * - Validate email format (RFC 5322, reject + aliasing)
 * - Hash passwords with bcrypt, cost factor 12 minimum
 * - Rate limit: 5 failed attempts → 15-minute lockout per IP
 * - Sessions: JWT, 1-hour expiry, RS256 signing (no HS256)
 * - Audit log: every auth attempt (success + failure) with timestamp, IP, userAgent
 *
 * Security invariants:
 * - Timing-safe comparison for password hashes (prevent timing attacks)
 * - Error messages must not distinguish "user not found" from "wrong password"
 * - Session tokens must be revocable (store JTI in Redis with TTL)
 *
 * Test requirements (define before implementation):
 * - Valid login flow
 * - Invalid password (wrong creds, same error as missing user)
 * - Rate limit trigger and lockout duration
 * - Token expiry enforcement
 * - Revoked token rejection
 */

// AI implements against the spec above — engineer reviews against each requirement

const crypto = require("crypto");
const bcrypt  = require("bcrypt");
const jwt     = require("jsonwebtoken");

class AuthenticationService {
  constructor({ redisClient, jwtPrivateKey, jwtPublicKey }) {
    this.redis      = redisClient;
    this.privateKey = jwtPrivateKey;
    this.publicKey  = jwtPublicKey;
    this.BCRYPT_ROUNDS = 12;  // Spec: cost factor 12 minimum
    this.RATE_LIMIT_ATTEMPTS = 5;
    this.LOCKOUT_DURATION_MS = 15 * 60 * 1000; // 15 minutes
  }

  async login(email, password, { ip, userAgent }) {
    const auditEntry = { email, ip, userAgent, timestamp: new Date().toISOString() };

    // Check rate limit before anything else
    const lockoutKey = `auth:lockout:${ip}`;
    const isLocked = await this.redis.exists(lockoutKey);
    if (isLocked) {
      await this.audit({ ...auditEntry, event: "login_blocked_lockout" });
      // Spec: same error message for all auth failures — no user enumeration
      throw new Error("Authentication failed");
    }

    // Load user — intentionally catches both "not found" and "wrong password" as same error
    const user = await this.findUserByEmail(email);
    const passwordValid = user
      ? await bcrypt.compare(password, user.passwordHash) // Spec: timing-safe via bcrypt
      : await this.dummyBcryptCompare();                  // Constant time even for missing users

    if (!user || !passwordValid) {
      await this.recordFailedAttempt(ip);
      await this.audit({ ...auditEntry, event: "login_failed" });
      throw new Error("Authentication failed"); // Spec: same message for both failure modes
    }

    // Success path
    await this.clearFailedAttempts(ip);

    // Spec: JWT with RS256, 1-hour expiry, revocable via JTI
    const jti = crypto.randomUUID();
    const token = jwt.sign(
      { sub: user.id, email: user.email, jti },
      this.privateKey,
      { algorithm: "RS256", expiresIn: "1h" } // Spec: RS256 only (no HS256)
    );

    // Store JTI for revocation support
    await this.redis.setEx(`auth:jti:${jti}`, 3600, "valid");
    await this.audit({ ...auditEntry, event: "login_success", userId: user.id });

    return { token };
  }

  async verifyToken(token) {
    const payload = jwt.verify(token, this.publicKey, { algorithms: ["RS256"] });

    // Spec: revocable tokens — check JTI is still valid
    const jtiValid = await this.redis.exists(`auth:jti:${payload.jti}`);
    if (!jtiValid) throw new Error("Token has been revoked");

    return payload;
  }

  async revokeToken(jti) {
    await this.redis.del(`auth:jti:${jti}`);
  }

  async recordFailedAttempt(ip) {
    const key = `auth:attempts:${ip}`;
    const attempts = await this.redis.incr(key);
    await this.redis.expire(key, 900); // 15 minutes

    if (attempts >= this.RATE_LIMIT_ATTEMPTS) {
      await this.redis.setEx(`auth:lockout:${ip}`, 900, "locked");
    }
  }

  async dummyBcryptCompare() {
    // Constant-time dummy hash to prevent timing attack on user enumeration
    await bcrypt.compare("dummy", "$2b$12$00000000000000000000000000000000000000000000000000000000");
    return false;
  }

  async findUserByEmail(email) { /* db lookup */ }
  async clearFailedAttempts(ip) { await this.redis.del(`auth:attempts:${ip}`); }
  async audit(entry) { console.log("[AUDIT]", JSON.stringify(entry)); }
}
Review discipline in practice: The spec above takes 10 minutes to write. It becomes the checklist for the code review. Every requirement in the spec maps to a test. Every security invariant is a line item in the security review. The AI generates the implementation; the spec is what you review against.

The Agentic Engineering Gate Pattern

For teams using AI agents to generate code (not just assist), a gate pattern ensures every generated diff goes through the same review process as human-written code. 

// Automated pre-merge gate for AI-generated code
class AgenticEngineeringGate {
  constructor({ securityScanner, testRunner, coverageThreshold = 80 }) {
    this.securityScanner = securityScanner;
    this.testRunner      = testRunner;
    this.coverage        = coverageThreshold;
  }

  async evaluate(diff) {
    const results = await Promise.all([
      this.runSecurityChecks(diff),
      this.runTestSuite(diff),
      this.checkTestCoverage(diff),
      this.checkSpecCompliance(diff),
    ]);

    const [security, tests, coverage, specCompliance] = results;
    const allPassed = results.every(r => r.passed);

    return {
      passed: allPassed,
      gates: { security, tests, coverage, specCompliance },
      recommendation: allPassed ? "MERGE" : "BLOCK",
      // AI-generated diffs get extra scrutiny
      reviewNotes: this.generateReviewNotes(results, diff.metadata?.aiGenerated)
    };
  }

  async runSecurityChecks(diff) {
    const findings = await this.securityScanner.scan(diff.code);
    const critical  = findings.filter(f => f.severity === "CRITICAL");
    const high      = findings.filter(f => f.severity === "HIGH");

    return {
      passed: critical.length === 0 && high.length === 0,
      findings: { critical, high, medium: findings.filter(f => f.severity === "MEDIUM") }
    };
  }

  async runTestSuite(diff) {
    const result = await this.testRunner.run({ affectedFiles: diff.changedFiles });
    return { passed: result.failed === 0, ...result };
  }

  async checkTestCoverage(diff) {
    const coverage = await this.testRunner.getCoverage(diff.changedFiles);
    return {
      passed: coverage.line >= this.coverage,
      lineCoverage: coverage.line,
      branchCoverage: coverage.branch
    };
  }

  async checkSpecCompliance(diff) {
    // Verify every requirement in the spec file has at least one test
    if (!diff.specFile) return { passed: true, note: "No spec file provided" };
    const requirements = this.parseRequirements(diff.specFile);
    const covered      = requirements.filter(req => this.hasTestForRequirement(req, diff.testCode));
    return {
      passed: covered.length === requirements.length,
      covered: covered.length,
      total:   requirements.length,
      uncovered: requirements.filter(r => !covered.includes(r))
    };
  }

  generateReviewNotes(results, isAIGenerated) {
    const notes = [];
    if (isAIGenerated) {
      notes.push("⚠️  AI-generated diff: apply full review rigor, not just plausibility check");
      notes.push("Review against spec, not just implementation correctness");
      notes.push("Verify security invariants manually — scanner is a floor not a ceiling");
    }
    return notes;
  }

  parseRequirements(specFile) { return []; }
  hasTestForRequirement(req, testCode) { return false; }
}

What This Means for Teams

  • AI fluency is a skill, not a shortcut. Teams that learn to use AI as a force multiplier (spec → AI → rigorous review) ship more reliably than teams that use it to skip thinking.
  • Review processes don't become optional. They become more important — because generated code is often syntactically correct but semantically wrong in subtle ways that only humans reviewing against requirements will catch.
  • Specification writing is a first-class skill. The engineer who writes the clearest specifications gets the best AI-generated code. This is a new form of technical leverage.
  • Security tooling needs updating. AI models have no inherent knowledge of your security policies. Automated scanning must be configured to catch the patterns AI models commonly produce (e.g., HS256 JWTs, insufficient bcrypt rounds, user enumeration).
  • The vibe coder pays later. Vibe-coded systems accumulate technical debt that is invisible until production — behavior that wasn't specified wasn't tested, and behavior that wasn't tested will fail in unexpected ways.
The accountability principle: "The AI generated it" is never a valid incident report. When a security vulnerability or production failure comes from AI-generated code, the engineer who reviewed and merged it is responsible. This is why understanding what you're merging is non-negotiable.

Key Takeaway

Google's SDLC guide draws the line at understanding and accountability, not at how much AI is used. Vibe coding optimizes for speed of generation; agentic engineering optimizes for correctness and maintainability of the result. The practical difference: write the spec before prompting, review generated code against the spec (not just plausibility), and apply the same security review you'd apply to any diff. The specification-first pattern is not overhead — it is the mechanism that makes AI-assisted development reliable rather than lucky.
